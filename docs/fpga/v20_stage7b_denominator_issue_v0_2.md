## §1. 背景（v0.1 のまま・変更なし）

### 1.1 段7-B の目的

段7-C で得た書込ストール率 **13.2%**（YUI OS・CEN=1）が
事前定義の近傍帯（12〜18%）に該当したため、ライトバッファ前倒しの判定が保留された。
段7-B はこの保留を解消するための工程である。

### 1.2 案D（1ビン法）の合格条件

計画書 v0.5 §5.1.6.1 は、モデル妥当性ゲート（U-4）を次の2式で判定すると定める。

```
b_measured = (stall_rd + stall_wr) / N            → 合格条件1: b_measured + 1 が 4.0〜6.0
a_measured = (C_total − stall_rd − stall_wr) / I  → 合格条件2: 1.0 以上・≒18 として説明可能
```

- `C_total`／`stall_rd`／`stall_wr` … **RTL 側**（`tb_cpu_v8e_dhry_v0_3`・Dhrystone -O0・CEN=0）
- `N`（アクセス回数）／`I`（命令数） … **emu23 側**

計画書 v0.5 §5.1.6 の表は「Dhrystone -O0 CEN=0 で完結」と記すのみで、
**emu23 側をどのオプション条件で走らせた値を `N`／`I` とするかは書かれていない。**

### 8.3 ★原因（確定）★

★データ処理は完全に同一であり、命令フェッチだけが課金走行で 91,181 件少ない。★
これが意味するのは次の 1 点である。

> ★データアクセスを伴わずに命令フェッチのみを繰り返す区間 — すなわち待ちループ —
> の周回数が、課金の有無によって変わっている。★

課金走行では 1 周あたりの経過サイクルが増えるため、
★待ち条件が成立するまでの周回数が減る。★
待ちループはレジスタ内で完結し、データメモリを触らないため、
★`R8`／`W8`／`R16`／`W16` に一切現れない。★ 観測と完全に整合する。

★これは emu23 の欠陥ではない。実機でも同じことが起こる、正常な挙動である。★
（有識者回答 §5 の「測定系の欠陥である可能性」は ★否定された★。）

### 8.4 ★それでも分母問題は解決しない — 本版の主題★

★有識者回答 §1.1 は次のように述べている。★

> ★両者とも完走している以上、区間は構造的に一致しているはず★
> ★同一プログラムを同一入力で完走させた 3 回の走行で、
> アクセス回数が 1.42 倍も違ってよい理由が無い★

★実測はこれを部分的に否定した。★
区間の**開始と終端**は一致している。しかし ★待ちループの周回数は課金に依存する量であり、
「同一プログラム・同一入力・完走」であっても一致しない。★
★1.42 倍違ってよい理由は、存在した。★

ここから本質的な困難が導かれる。

```
b_measured = (stall_rd + stall_wr) / N
```

★分子は RTL（CEN=0）の実測値、分母 `N` は emu23 の値である。★
★ところが `N` は「待ちループを何周したか」に依存し、それは
メモリ待ち時間に依存する。★

★つまり分子と分母が独立ではない。★
RTL の CEN=0 走行における待ちループ周回数は、
emu23 のどの走行の周回数とも一致する保証がない。
★RTL 側の実効 LAT が emu23 の校正値 5 とわずかでも違えば、周回数が変わり `N` が変わる。★

★これは「どの走行を選ぶか」で解決する問題ではない。★
