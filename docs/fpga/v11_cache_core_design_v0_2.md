### 0.3 ★②-A' の帰結を本工程に反映する（本書で最も重要な前提）★

②-A' の結論は「速度依存デッドロックは実在せず、TB v0.2 の M-5 判定が
速度依存であったこと」であった。②-B はキャッシュヒット時に実効レイテンシが
LAT=4 相当より短くなるため、**同じ判定器の脆弱性を必ず踏む**。

したがって本工程では以下を**遵守事項**とする。

| # | 遵守事項 |
|---|---|
| B-1 | 検証には **`tb_cpu_v8b_prod_v0_3.sv` 以降**を使用する。v0.2 の使用を禁止する |
| B-2 | 新たに判定を追加する場合、**速度非依存であること**を設計時に明記する（原則137） |
| B-3 | FAIL が出た場合、**RTL を疑う前に判定器を疑う**。判定器の速度非依存性を先に確認する |

**②-A' で得た量子化ビン構造（実測・2026-08-30）**

| ビン | LATENCY_NORMAL | M-5 到達 cycle |
|---|---|---|
| 群1 | 4 / 5 / 6 | 2,810,474 |
| 群2 | 7 / 12 | 3,754,937 |

CPU:PSRAM = 8:1 のため PSRAM レイテンシは CPU 視点で 8 単位に量子化される。
**LAT を 1 減らしても、同一ビン内であれば性能は 1 サイクルも改善しない。**

~~②-B の性能評価は「LAT を下げる」ではなく「アクセスそのものを消す」ことで
ビンを跨ぐ、という観点で行う。~~

★**v0.2 是正（M-6）**★：後半は誤りである。**量子化ビンは `LATENCY_NORMAL` を
掃引したときに M-5 が階段状にしか動かないという PSRAM レイテンシ側の性質**であり、
キャッシュは `LAT` を変えずに**アクセス回数そのものを減らす**。
削減されたアクセス数に比例して総サイクル数は**連続的に**減るのであって、
ビン構造には従わない。

> ⚠️ この基準を採ると、**群1（2,810,474）に届かない改善を「効果なし」と誤判定する**
> 危険があった。ヒット率 40% でも十分な改善であり得る。

**正しい観点**：ビン構造が示すのは「**LAT の微調整では性能が動かない＝レイテンシを
削る方向は打ち止めである**」ことのみ。だからこそ ②-B（アクセス回数を減らす方向）に
意味がある、という**動機づけ**として用いる。合否基準には用いない（→ §10.5）。

## 1. ★クロックドメインと配置（M-1 対応・本版の中核）★

### 1.1 実源が示す構造

`ysd8800_v5_membus_v0_6.sv` L196-212 および L150-171 のブロック図より：

```
  CPUコア（cpu_clk 4MHz・論理アドレス16bit）
        │ mem_addr[15:0] / mem_wdata[7:0] / mem_rdata[7:0] / mem_rd / mem_wr / mem_ready
  ┌─────┴──────────────┐
  │ ysd8800_addr_decoder │  ← $FC80 判定
  └──┬───────────────┬──┘
 MMIO側│               │RAM側
  ┌───┴────────┐  ┌───┴──────────┐
  │ mmio_stub  │  │ ysd8800_mmu  │ ← 純組合せ
  └────────────┘  └───┬──────────┘
                       │ phys_addr[19:0]
              ┌────────┴────────┐
              │  cdc_bridge     │ ★ここがドメイン境界★
              └────────┬────────┘
              ┌────────┴────────┐
              │  psram_ctrl     │（psram_clk 32MHz）
              └─────────────────┘
```

**クロック比は 8:1**（`cpu_clk` 4MHz / `psram_clk` 32MHz）。

### 1.2 ★配置の決定（C-1 対応）★

**キャッシュ段は `addr_decoder` の RAM 側分岐の内側、`mmu` の後段、
`cdc_bridge` の CPU 側に置く。**

```
  ysd8800_mmu ──┬─► phys_addr[19:0]
                │
        ┌───────┴────────────────┐
        │ ★ysd8800_cache（新規）★ │ ← ヒット判定は cpu_clk
        └───────┬────────────────┘
                │ ミス時のみラインフィル要求
        ┌───────┴────────┐
        │  cdc_bridge     │
        └───────┬────────┘
        ┌───────┴────────┐
        │  psram_ctrl     │
        └─────────────────┘
```

**この配置の帰結**

| 項目 | 内容 |
|---|---|
| `is_mmio` 条件 | ★**不要**★。MMIO アクセスは `addr_decoder` で分岐済みでキャッシュ段に到達しない（C-1 の推奨どおり） |
| インデクス | **物理アドレス**（MMU 後段）でインデクスする。コンテキストスイッチ時のフラッシュ不要 |
| ヒット時 | ★**CDC を越えない**★。これが利得の源泉である |

> ★レビュー指摘 M-1 の (B) 案（PSRAM 側配置）を採らない理由★
> (B) ではヒットでも CDC 往復（A-2q 後で約 3 cpu cyc）を必ず払う。
> 現行のミスが約 4 cpu cyc なので **4 → 3 にしかならず、キャッシュを入れる意味が消える**。
> よって **(A) 側配置は必須**であり、選択の余地はない。

### 1.3 ★ラインフィルの成立条件（M-1 の矛盾の解消）★

指摘のとおり、`beat_valid` の 32 サイクルは **`psram_clk` の 32 サイクル
＝ `cpu_clk` の 4 サイクル**である。キャッシュ段全体を `cpu_clk` に置くと
32 バイトを取り込めない。**そこで記憶構造をドメインで分割する。**

| 構造 | ドメイン | 実体 | 理由 |
|---|---|---|---|
| `data_ram` | ★**デュアルクロック・デュアルポート BSRAM（DPB）**★ | BSRAM | 書込＝`psram_clk`（フィル）／読出＝`cpu_clk`（ヒット） |
| `tag_ram` | `cpu_clk` | ★**FF アレイ**★（→ §8.2） | ヒット判定は CPU 側で完結する必要がある |
| `valid_r` | `cpu_clk` | FF アレイ | 一括クリアのため（§4.1） |

**CDC が発生する箇所は 1 つだけである。**

```
  フィル要求発行  : cpu_clk → psram_clk （既存 cdc_bridge の req 経路に相乗り）
  各 beat の書込  : psram_clk 内で完結（★CDC 不要★・DPB の書込ポート）
  フィル完了通知  : psram_clk → cpu_clk （既存 ack 経路 L139/L148 に相乗り）
  タグ／valid 更新: cpu_clk 内（★フィル完了時の 1 イベントのみ★）
```

> ★**ビート毎の CDC は発生しない**★（レビュー M-1 の指摘どおり）。
> これが本構成の要である。ビート毎に CDC を行う設計にすると
> 8:1 のクロック比では追従できない。

> ⚠️ ★`ack` はレベルではなく**立上りエッジ**が `cdc_bridge_v0_4` L139
> （`suppress_r <= ack_sync[0] & ~ack_sync[1];`）で 1 cpu cyc パルス化される。★
> バースト設計書 §1.3 M-2 の警告に従い、**各 beat で `ack` を立てる改造をしてはならない。**

### 1.4 ★PSRAM 書込経路は CPU のみ（C-3 対応・実源確認済）★

`ysd8800_v5_membus_v0_6.sv` L275/L378/L403 のインスタンス接続より、
`psram_ctrl` への要求経路は `addr_decoder` → `mmu` → `cdc_bridge` の**単一経路**であり、
**DMA マスタは存在しない**。YSD8003（ストレージ）は `mmio_stub` 内部に
インスタンス化され、CPU の `LDB`/`STB` 経由でのみデータが移動する。

★**したがってコヒーレンシ問題は発生しない。**★

> ⚠️ ②.5 以降で DMA を導入する場合、**本前提が崩れる**。
> その際は DMA 対象領域の非キャッシュ化、またはフラッシュ機構が必須になる。
> 本書 §7.1 の `FLUSH` ビットはその布石でもある。

### 1.5 ★DPB の同一アドレス同時アクセス★

フィル進行中（`psram_clk` 側で書込中）に、`cpu_clk` 側から同一ラインを読む
可能性がある。**本設計では発生させない**：

- フィル中は `valid_r[index] = 0` のままである（valid はフィル完了時に立てる）
- したがってヒット判定は必ず不成立となり、`data_ram` の読出結果は使われない
- さらに §9.4 により、フィル中の CPU 要求は `mem_ready` で待たせる

★**valid をフィル完了時にのみ立てる**ことが、DPB 競合の回避策そのものである。★

## 2. 構成の決定（★要レビュー論点 その1★）

### 2.1 資源見積もり（GW1NR-9・BSRAM 26 ブロック × 18Kbit）

物理アドレス 20 ビット（`MEM_AW=20`）を前提とする。

| 容量 | ライン | ライン数 | index | offset | tag幅 | データ | タグ | 概算BSRAM |
|---|---|---|---|---|---|---|---|---|
| 4 KB | 32 B | 128 | 7 | 5 | 8 b | 32 Kb | 1.1 Kb | 約 2.1 |
| 8 KB | 32 B | 256 | 8 | 5 | 7 b | 64 Kb | 2.0 Kb | 約 4.1 |
| 16 KB | 32 B | 512 | 9 | 5 | 6 b | 128 Kb | 3.5 Kb | 約 8.2 |
| 16 KB | 16 B | 1024 | 10 | 4 | 6 b | 128 Kb | 7.0 Kb | 約 8.4 |

（タグ幅 = 20 − index − offset、有効ビット 1 を各ラインに付加）

> ★E-1 対応・「概算 BSRAM」列の算出根拠★
> GW1NR-9 の BSRAM は 18Kbit ブロックだが、★**x9 構成（パリティ付き）ではなく
> x8 構成で使うため、1 ブロックあたりの実効容量は 16Kbit**★である。
> 例（8 KB / 32 B）：データ 64Kb ÷ 16Kb = **4.0 ブロック** ＋ タグ 1 ブロック ≒ **4.1**。
> `valid_r` は BSRAM ではなく FF アレイに置くため（§4.1）、本列には含まない。

### 2.2 ★推奨案：8 KB / 32 バイトライン★

**推奨理由**

1. **BSRAM 消費が約 4 ブロック**で、26 ブロックのうち 22 ブロックを他用途
   （②.5 の GPIO 拡張バス・デバッグ DIO、将来の MMU 拡張）に残せる。
   16 KB は 8 ブロックを消費し、余裕が減る。
2. ライン 32 バイトは ②-A の `BURST_MAX=32` と**一致**する。
   バースト設計書 §1.2 は「②-B のライン長上限。②-B で最終確定」としており、
   32 を採るとバースト側の変更が不要になる（1変更1検証に資する）。
3. YUI OS 本体は 56,416 バイト。8 KB は約 14 %。ダイレクトマップの
   コンフリクトミスが問題になるかは実測で判断すべきであり、
   まず小さい構成で G-0 を通し、必要なら容量を上げるのが安全である。
4. emu23 側の既定は 16 KB だが、`--cache-size` で可変であるため、
   **RTL 実装値に合わせて emu23 側を 8 KB で走らせれば比較可能**である。

### 2.3 ★決定を要する事項★

| ID | 論点 | 推奨 | 代替 |
|---|---|---|---|
| **D-B1** | キャッシュ容量 | **8 KB** | 4 KB（資源優先）／16 KB（性能優先・emu23 既定と一致） |
| **D-B2** | ラインサイズ | **32 B** | 16 B（ミスペナルティ半減・バースト側変更不要だが空間局所性を活かせない） |
| **D-B3** | 方式 | **ダイレクトマップ**（emu23 §5.1 と一致） | 2-way（BSRAM は足りるが比較器 2 系統・置換ロジックが増える） |

> ★レビュー時にこの 3 点をご判断いただきたい。★
> 以降の記述は D-B1=8KB / D-B2=32B / D-B3=ダイレクトマップを仮に採った場合のものである。

## 3. アドレス分解

```
物理アドレス 20 ビット（MMU 後段）

  19                 13 12          5 4        0
 +---------------------+-------------+----------+
 |     tag  (7 bit)    | index (8bit)| off(5bit)|
 +---------------------+-------------+----------+
```

- 配置は **MMU 物理アドレスの後段**（`emu23_cache_base_design_v1_0.md` §5.1）。
  物理アドレスでインデクスするため、**コンテキストスイッチ時のフラッシュが不要**。
  （OS-9 の MMU 運用と同じ思想。論理アドレスでインデクスすると
  プロセス切替のたびに全無効化が要り、YUI OS のように切替頻度が高い系では損になる。）

## 4. 記憶構造

| 配列 | 幅 | 深さ | 実体 |
|---|---|---|---|
| `tag_ram` | 7 | 256 | BSRAM または分散 RAM |
| `valid_r` | 1 | 256 | ★FF アレイ（BSRAM ではない）★ |
| `data_ram` | 8 | 8192 | BSRAM（バイトアドレッサブル） |

### 4.1 ★`valid` を FF に置く理由（重要）★

`valid` を BSRAM に置くと、**一括クリアが 1 サイクルでできない**。
CCR による無効化・全フラッシュは全ライン同時クリアを要求するため、
256 ビットの FF アレイとして持ち、`valid_r <= '0` で一括クリアする。

256 FF は GW1NR-9 の資源（8,640 LUT / 6,480 FF 相当）に対して十分小さい。

### 4.2 ★データ RAM をバイト幅にする理由（M-3 是正）★

~~ISA2.3 は `LDB`/`STB` を持ち、奇数アドレスアクセスが発生する。ワード幅 RAM に
するとバイト書き込みでリードモディファイライトが必要になり、ライトスルーの
タイミングが複雑化する。バイト幅とし、16 ビットアクセスは 2 バイト分を同時に扱う。~~

~~⚠️ ライン境界を跨ぐ 16 ビットアクセス（offset = 31 のワードアクセス）は
2 ラインに跨る。この扱いを §7.3 で規定する。~~

★**v0.2 是正（M-3・KY34 実源確認）**★

`ysd8800_v5_membus_v0_6.sv` **L205-206**：

```systemverilog
input  logic [7:0]  mem_wdata,
output logic [7:0]  mem_rdata,
```

★**CPU 抽象バスのデータ幅は 8 ビットである。**★
`cdc_bridge_v0_4` L121 以降も 8 ビットで一貫している。

**したがって：**

| 事項 | v0.1 の認識 | ★実際★ |
|---|---|---|
| メモリ段から見た 16 ビットアクセス | 存在する | ★**存在しない**★ |
| `LDW`/`STW` の扱い | メモリ段で 2 バイトを同時処理 | ★**CPU コアが既に 2 回のバイトトランザクションに分解して発行している**★ |
| ライン境界跨ぎ | offset=31 で 2 ラインに跨る | ★**発生しない**★。offset=31 のバイトアクセスと offset=0 のバイトアクセスが**独立に 2 回**来るだけで、それぞれが独立にヒット／ミス判定されて正しく動く |

**結論（バイト幅とすること自体）は正しいので維持する。ただし理由を差し替える：**

> `data_ram` をバイト幅（8 × 8192）とするのは、★**CPU 抽象バスがそもそも
> 8 ビットだから**★である。ワード幅にすると、8 ビットのバス幅との整合のために
> かえってバイトイネーブル制御が必要になる。

> ★KY34（実ファイルが真実）の適用事例である。★
> 「ISA2.3 に `LDW`/`STW` がある」ことと「メモリバスが 16 ビットである」ことは
> **別の話**であり、後者は実源を見なければ分からなかった。
> v0.1 は前者から後者を推論してしまい、★**存在しない問題（ライン跨ぎ）に
> 対策（D-B7・バイパス機構）を設計しかけていた。**★
> 実装・検証（`tb_cache_wt_poc` の跨ぎ検証）まで無駄が波及するところであった。

## 5. CCR（キャッシュ制御レジスタ）（★要レビュー論点 その2★）

### 5.1 ビット定義（★M-5 対応・是正版★）

CCR は 16 ビットレジスタだが、★**バスは 8 ビット**★（§4.2）である。
実源の他デバイス（`mmio_stub` L228-230：`$FC80 TX（下位）/ $FC81（上位）`）に倣い、
★**偶数番地＝下位バイト、奇数番地＝上位バイト**★で割り付ける。

#### 下位バイト（`$FF12`）

| ビット | 名称 | 種別 | リセット値 | 意味 |
|---|---|---|---|---|
| 0 | `CEN` | R/W | **0** | 1 = キャッシュ有効。**リセット値 = disable**（決定済み） |
| 1 | `FLUSH` | ★**W1T（write-1-to-trigger, self-clearing）**★ | 0 | 1 書込で全ライン無効化を起動。★**読み出しは常に 0 を返す**★（起動中も 0） |
| **7:2** | — | RO | 0 | ★**予約（読み出しは常に 0）**★ |

#### 上位バイト（`$FF13`）

| ビット | 名称 | 種別 | リセット値 | 意味 |
|---|---|---|---|---|
| 8 | `HIT_EN` | R/W | 0 | ヒット／ミスカウンタ計数有効 ★**初版では非実装**（M-7・D-B5）★ |
| **15:9** | — | RO | 0 | ★**予約（読み出しは常に 0）**★ |

★**v0.1 からの是正点（M-5）**★

| # | v0.1 | ★v0.2★ |
|---|---|---|
| ① | ビット 4・5・6・7 が定義も予約もされていなかった | ★**7:2 を予約（読み出し 0）と明記**★。抜けたまま実装すると読み出し値が実装依存になる |
| ② | `FLUSH` を「W1S」と表記 | ★**W1T（write-1-to-trigger, self-clearing）**★ に是正。W1S ではない。読み出しは常に 0 と規定 |
| ③ | 16 ビットレジスタのバイト割付が未記述 | ★`$FF12`＝下位／`$FF13`＝上位 と明記★。`HIT_EN`（ビット 8）は `$FF13` に載る |

> ⚠️ ③は `kernel_v12_11.asm` 側の定義と直結する。★KY41 4 点整合の対象★であり、
> RTL・カーネル・`yuios_memmap_design` の 3 箇所に**同時反映**すること。

### 5.2 ★決定を要する事項★

| ID | 論点 | 内容 |
|---|---|---|

### 5.3 ★MMIO マップ実源確認（`ysd8800_mmio_stub_v0_8.sv` L219-243）★

| 範囲 | 用途 | 出典 |
|---|---|---|
| `$FC80`–`$FC87` | YSD8001 UART | L229-230 |
| `$FC88`–`$FC8F` | **空き** | — |
| `$FC90`–`$FC9F` | YSD8002 Timer | L236-237 |
| `$FCA0`–`$FCB1` | YSD8003 Storage | L242-243 |
| `$FCB2`–`$FCB5` | YSD8004 IRQ | L224-225 |
| `$FCB6`–`$FEFF` | **空き** | — |
| `$FF00`–`$FF0F` | MMU PTR[0..15] | L219-220 |
| `$FF10` | MMU MCR | L221 |
| `$FF11`–`$FFFF` | **空き** | — |

**推奨 `$FF12`（および将来 `$FF14`/`$FF16` をカウンタ用に予約）の理由**

1. キャッシュは MMU 物理アドレスの後段に置かれる**メモリ系制御**であり、
   MMU MCR（`$FF10`）の直後に並べるとアドレスマップの意味的まとまりが保てる。
2. `$FC80` 台のデバイス群（UART/Timer/Storage/IRQ）は**周辺デバイス**であり、
   そこに混ぜるとデバイスとメモリ制御の区別が失われる。
3. `$FF11` ではなく `$FF12` とするのは、**16 ビットアクセスの偶数アラインを保つ**ため。
   ISA2.3 はバイトアドレッサブルだが、`LDW`/`STW` の奇数アドレスアクセスは
   アラインメント例外の対象であり、制御レジスタは偶数番地に置くのが安全である。

> ⚠️ 確定にあたっては `kernel_v12_11.asm` および `yuios_memmap_design` 側の
> MMIO 定義とも突合し、**両者に同時に反映**すること（KY41 4点整合）。

## 6. ★ヒット経路のサイクル設計（M-2 対応）★

### 6.1 なぜ本節が要るのか

v0.1 は「ヒット時 `mem_ready` は 1 cpu cycle で返す」と書いたが、根拠が無かった。
★**Gowin の BSRAM は同期読み出し**★であり、アドレスをクロック端で取り込んで
出力は次サイクルに現れる。したがって `tag_ram` を BSRAM に置くと
**タグ比較が 1 サイクル遅れ、ヒットは最短でも 2 cpu cyc になる**。

★これは損益分岐ヒット率を大きく動かす。★

| ヒット遅延 | 損益分岐（現行ミス 4 cyc・キャッシュミス 10 cyc と仮定） | 条件 |
|---|---|---|
| **1 cyc** | `1h + 10(1−h) < 4` → ★`h > 66.7%`★ | `tag_ram` が組合せ読出 |
| 2 cyc | `2h + 10(1−h) < 4` → ★`h > 75.0%`★ | `tag_ram` が BSRAM |

★**8 KB ダイレクトマップで 75% は容易でない。1 cyc ヒットを設計目標とする。**★

### 6.2 ★`tag_ram` の実体を一意に決定する★

| 構造 | v0.1 | ★v0.2 決定★ | 理由 |
|---|---|---|---|
| `tag_ram` | 「BSRAM **または** 分散 RAM」（両論併記） | ★**FF アレイ（256 × 7 bit = 1,792 FF）**★ | 組合せ読出により `valid_r` と同位相で比較でき、1 cyc ヒットが成立する |
| `valid_r` | FF アレイ | FF アレイ（変更なし） | 一括クリア（§4.1） |
| `data_ram` | BSRAM | BSRAM（DPB・変更なし） | 8 KB は FF では不可能 |

**資源影響**：`tag_ram` 1,792 FF ＋ `valid_r` 256 FF ＝ 約 2,048 FF。
GW1NR-9 は 6,480 FF 相当であり、約 32% を消費する。

> ⚠️ ★これは軽い消費ではない。★ 容量を 16 KB に上げると `tag_ram` は
> 512 × 6 = 3,072 FF となり、`valid_r` と合わせて約 3,584 FF（55%）に達する。
> ★**D-B1 で 8 KB を選ぶ根拠が、BSRAM だけでなく FF 側にも生じた。**★

### 6.3 ヒット経路のサイクル図

`mem_rd` 立上りサイクルを N とする。

```
        │  cycle N-1  │   cycle N    │  cycle N+1  │
────────┼─────────────┼──────────────┼─────────────┤
mem_addr│    ────     │   有効       │             │
phys_addr│   ────     │ 有効(MMU純組合せ・同一サイクル)
index    │   ────     │ 有効(組合せ) │             │
tag_ram  │   ────     │ 出力有効(FF・組合せ読出)   │
valid_r  │   ────     │ 出力有効(FF) │             │
hit      │   ────     │ ★確定(組合せ比較)★        │
data_ram │ アドレス供給│ ★出力有効★  │             │
mem_ready│   ────     │ ★1★         │             │
mem_rdata│   ────     │ ★有効★      │             │
```

★**成立条件**★：`data_ram`（BSRAM・同期読出）の出力を cycle N に間に合わせるには、
**アドレスを cycle N-1 に与えておく必要がある**。

**解決策：`data_ram` は投機読出とする。**

```
  data_ram の読出アドレス = { index, offset }   ← mem_addr から純組合せで生成
  ★hit 判定を待たずに常時読み出す★
  hit が成立しなければ結果を捨てるだけ（副作用なし）
```

`mem_addr` は CPU が cycle N-1 の終わりには確定させているため、
`cpu_clk` の立上りで `data_ram` にアドレスが取り込まれ、cycle N に出力が揃う。
★タグ比較（組合せ）と同一サイクルで揃うため、1 cyc ヒットが成立する。★

> **MC6809 で言えば、命令フェッチと同時にオペランドを先読みしておき、
> アドレッシングモードが確定した時点で使うか捨てるかを決めるのと同じ発想である。**
> 読出に副作用が無い（MMIO はここに来ない・§1.2）からこそ許される最適化であり、
> ★MMIO をキャッシュ段の外に出した §1.2 の判断が、ここで効いている。★

### 6.4 ★タイミング上のリスク（実装時に要確認）★

| # | リスク | 確認方法 |
|---|---|---|
| 1 | `mem_addr` → `mmu`（純組合せ）→ `index` → `tag_ram`（組合せ読出）→ 比較 → `mem_ready` が **1 サイクル（250ns @4MHz）に収まるか** | 工程③（FPGA 実装）の合成時にタイミングレポートで確認 |
| 2 | 250ns は 4MHz としては極めて緩い制約であり、通常は問題にならない | — |

★4MHz という低速動作が、この組合せ経路を許容する。★
高クロック設計であれば `tag_ram` を BSRAM に置いて 2 cyc ヒットを受け入れる
ことになるが、本設計ではその必要がない。

## 7. 動作仕様

### 7.1 ★`CEN=0` 時のバイパス経路（N-2 対応・G-0 の成立条件）★

★**`CEN=0` のとき、信号は純組合せでバイパスされ、レジスタを一切経由しない。**★

```systemverilog
// 概念（実装時に厳密化）
assign fill_req   = CEN ? (miss & mem_rd) : 1'b0;   // CEN=0 ならフィル要求を出さない
assign to_bridge  = CEN ? cache_req : cpu_req;      // ★純組合せ selector★
assign mem_rdata  = (CEN & hit) ? data_ram_q : bridge_rdata;
assign mem_ready  = (CEN & hit) ? 1'b1       : bridge_ready;
```

**なぜ必須か（N-2 の指摘）**：キャッシュ段を挿入した時点でパスにレジスタが
1 段入ると、★`CEN=0` でも 1 サイクル増えて G-0 が落ちる★。
②-A の `burst_len=1` 完全等価性（バースト設計書 §3.4）と同型の保証を
成立させるには、バイパスが**組合せでなければならない**。

> ★実装時の確認方法★：段2 完了時点で G-0 を実施し、M-1〜M-5 が
> ②-A' 実測値と**1 サイクルも違わない**ことを確認する（§9 段2）。
> 1 でもずれたら、それはバイパス経路にレジスタが入っている証拠である。

### 7.2 読み出し

```
  hit = valid_r[index] && (tag_ram[index] == tag) && CEN

  hit :
      data_ram から返す（投機読出・§6.3）。PSRAM アクセスを発行しない。
      mem_ready は ★1 cpu cycle★ で返す（根拠は §6.3）。

  miss:
      1) ライン先頭アドレス（下位 5 ビット = 0）で
         psram_ctrl に burst_len = 32 のリード要求を発行
      2) beat_valid が psram_clk の 32 サイクル連続で 1 になるので、
         各 beat を data_ram[index*32 + n] に書く
         ★この書込は psram_clk ドメイン・DPB の書込ポート（§1.3）★
      3) 全 beat 完了（ack の立上り）後に、cpu_clk ドメインで
         tag_ram[index] <= tag ; valid_r[index] <= 1
      4) 要求されたバイトを返す
```

> ★`is_mmio` 条件は不要である（C-1）。★
> キャッシュ段は `addr_decoder` の RAM 側分岐の内側に置かれるため、
> MMIO アクセスはそもそもキャッシュ段に到達しない（§1.2）。

> ★`ack` はレベルではなく**立上りエッジ**が `cdc_bridge_v0_4` L139 で
> 1 cpu cyc パルス化される。★
> バースト設計書 §2.3 M-2 の警告に従い、**各 beat で `ack` を立てる改造を
> してはならない**。

### 7.3 書き込み（ライトスルー / ノーライトアロケート）

| 状況 | キャッシュ | PSRAM |
|---|---|---|
| `CEN=0` | ★触らない★ | 書く |
| ヒット | 該当バイトを更新 | 書く |
| ミス | ★触らない（ノーライトアロケート）★ | 書く |
| MMIO | 触らない | 書く（従来経路） |

`we=1` のとき `burst_len` は必ず 1（バースト設計書 §2.3 M-3）。

### 7.4 ~~ライン境界を跨ぐ 16 ビットアクセス~~ ★本節は撤回（M-3）★

~~offset = 31 の 16 ビットアクセスは 2 ラインに跨る。推奨案：跨ぎアクセスは
キャッシュをバイパスし、従来経路で処理する。理由：2 ライン同時ヒット判定は
比較器 2 系統とインデックス 2 系統を要し、ダイレクトマップの利点である
単純さを失う。~~

~~| **D-B7** | 跨ぎアクセスの扱い。推奨：バイパス（キャッシュ非更新） |~~

★**v0.2 撤回（M-3）**★：CPU 抽象バスは 8 ビット（§4.2）であり、
メモリ段から見た 16 ビットアクセスは**存在しない**。
ライン跨ぎという事象そのものが発生しないため、**本節および D-B7 は不成立**。
対策は不要である。

### 7.5 ★ラインフィル中の CPU 要求（C-2 対応）★

フィルは `psram_clk` 側で進行するが、その間に CPU から要求が来る可能性がある。
また `data_ram` の書込ポートは `psram_clk` 側（フィル用）であり、
CPU 側の書込ヒットと競合し得る。

★**決定：ラインフィル進行中は、CPU 側の要求を `mem_ready=0` で待たせる。**★

| 項目 | 内容 |
|---|---|
| 実害 | フィルは psram_clk 32 サイクル ＝ ★**cpu_clk 約 4 サイクル**★。待たせても軽微 |
| 利点 | DPB のポート競合・調停ロジックが**丸ごと不要**になる |
| 副次効果 | フィル中に同一ラインへ書込ヒットが来る競合も、構造的に発生しない |

> ★ダイレクトマップ＋ブロッキングキャッシュ（ノンブロッキングにしない）と
> することで、②-B の実装複雑度を大幅に下げている。★
> ノンブロッキング化は ②-B を閉じたあとの改良項目とする。

### 7.6 ★`FLUSH` とラインフィルの相互作用（C-4 対応）★

`FLUSH`（または `CEN` 立上りの暗黙フラッシュ・D-B6）が**フィル途中**に
発行されると、`valid_r <= '0` した直後にフィルが完了して
`valid_r[index] <= 1` してしまい、★**フラッシュしたはずのラインが復活する**★。

★**決定：フラッシュ発行時、進行中のフィルは「中止」扱いとし、
完了しても `valid_r` / `tag_ram` を更新しない。**★

```
  flush 発行 → fill_abort_r <= 1
  ack 到達時 : if (fill_abort_r) 何もしない（valid を立てない）
               else             tag_ram[index] <= tag ; valid_r[index] <= 1
  fill_abort_r は ack 受領でクリア
```

- PSRAM 側のバースト転送は**中断せず最後まで走らせる**
  （途中で `req` を落とすとバースト設計書 §2.3 の req/ack 4 相契約に違反する）
- 読み捨てるだけなので副作用は無い（読出に副作用が無い＝§6.3 と同じ根拠）

> ★§8.4 の `tb_cache_flush_poc` に本ケースを検証項目として追加する。★

②-A 設計書 §5.1 は基準値を「全て二次情報。段0 で一次確定させる」と留保していた。
★**本書の時点で、LAT=4/5/6/7/12 の全 5 ビンについて一次確定が完了している。**★
根拠は、②-A' において `tb_cpu_v8b_prod_v0_3`（判定を速度非依存に是正済み）で
全ビンを実走行し、`PROD PASS` を得たことである。

> ⚠️ ★重要な注記★
> LAT=12 の M-5 = 3,754,937 は、①.5（CDC 削減 A-2q）**適用後**の値である。
> A-2q 適用前の 4,772,836 と混同してはならない（−21.3% 改善後の値）。
> また ②-A 設計書 §5.1 に記載された値は **v0.2 の TB による測定**であり、
> ★判定器が速度依存であった時期のものであるが、LAT=12 群については
> 判定が成立していたため値そのものは有効★である。

**G-0 の意義**：`CEN=0` ならキャッシュ段は「素通し」でなければならない。
1 サイクルでもずれたら、それは無効化されていないこと（＝バイパス経路に
レジスタが入っていること・§7.1）を意味する。
②-A の `burst_len=1` 完全等価性（バースト設計書 §3.4）と同型の負制御である。

#### ★判断基準（M-6 対応・差替版）★

| # | 基準 | 内容 |
|---|---|---|
| **①** | **削減量の絶対値** | M-5 到達 cycle の減少量を★**連続量として**★評価する。基準値は §8.1 の LAT=12 一次確定値 **3,754,937** |
| **②** ★本命★ | **emu23 予測との整合** | `emu23 --cache-size 8192 --cache-line 32 --cache-stats` でヒット率 *h* を取得し、*h* から予測される削減量と RTL 実測の削減量が整合するか |

**なぜ②が本命か**：ヒット率という**独立変数**で予測が立つため、
「キャッシュが効いたか」だけでなく★**測定系そのものが妥当か**★を同時に検証できる。
予測と実測が乖離した場合、それはキャッシュの効果不足ではなく、
**モデルか実装のどちらかが間違っている**ことを示す。

> ⚠️ ★v0.1 の「ビンを跨ぐか」を採ってはならない理由（M-6）★
> 量子化ビンは `LATENCY_NORMAL` を掃引したときの PSRAM 側の性質であり、
> キャッシュは `LAT` を変えずアクセス回数を減らす。削減は**連続的**である。
> この基準を採ると★**ヒット率 40% でも十分な改善であるものを
> 「ビンを跨いでいないので効果なし」と誤判定する**★。

**検証順序**（KY-K-add7）：emu23 ゴールデン測定 → RTL 測定 → 差分確認。
