## 0. 本メモの目的

「RTL上でYUI OSが動作したが、CPU⇔PSRAM間のメモリ転送が約30倍遅い」という
課題に対し、キャッシュ導入の実現性を検討した。その結論と根拠、および
工程変更の決定事項を、後続チャットへ引き継ぐ。

## 1. 問題の定量分解（30倍の正体）

現行RTL（`tb_cpu_v8b_prod_v0_1.sv`）の設定:

| 項目 | 値 | 出典 |
|---|---|---|
| CPU clk | 100MHz（10ns） | tb_cpu_v8b_prod_v0_1.sv |
| PSRAM clk | 25MHz（40ns） | 同上 |
| LATENCY_NORMAL | 12（PSRAM cyc） | ysd8800_psram_ctrl_v0_2 |
| LATENCY_REFRESH | 15 | 同上 |
| REFRESH_PPM | 500（=0.05%） | 同上 |

1バイトアクセスあたりのCPUサイクル換算:

| 要素 | PSRAM cyc | CPU cyc換算 |
|---|---|---|
| PSRAMアクセス本体 | 12 | 48 |
| req 2FF同期（CPU→PSRAM） | 2〜3 | 8〜12 |
| ack 2FF同期（PSRAM→CPU） | — | 2〜3 |
| req_hold ワンショット | — | 1 |
| **計** | | **約60 CPU cyc/byte** |

さらに現行RTLは16bitアクセスをバイト2回に分割している（後述§3）ため、
16bitロード1回で約120 CPU cyc。理想メモリ比で実効60倍相当。
**報告された「30倍」はむしろ控えめな見積り。**

## 2. ★最重要発見★ Tang Nano 9K 内蔵PSRAMの実仕様

### 2.1 デバイス

- FPGA: Gowin GW1NR-LV9QN88PC6/I5
- QN88Pパッケージに **32Mbit×2ダイのPSRAM**（計64Mbit）
- ダイは **W955D8MBYA 相当（HyperRAM）** とされる
- BSRAM: **486Kbit / 26個**（＝約58KB、**現在未使用**）
- オンボードクロック 27MHz、**PLL 2個**

### 2.2 現行モデルのパラメータの出所

デファクト標準である zf3氏のPSRAMコントローラ
（https://github.com/zf3/psram-tang-nano-9k）の仕様が、
`ysd8800_psram_ctrl_v0_2` のパラメータと**完全一致**する:

- 読出しレイテンシ 1x=12cyc / 2x=15cyc
- リフレッシュによる2x発生率 約0.05%
- **16bitワードアクセスとバイトアクセスの両方をサポート**
- **バースト未使用**
- 1:1クロック設計（メモリとメインロジックが同一クロック）
- **最大83MHz**

→ 我々のビヘイビアモデルは zf3コントローラの写しである。

### 2.3 ★ここから導かれる3つの帰結★

#### 帰結1: psram_clk 25MHz はデバイス制約ではない（**確認済: PLL未使用の暫定値**）

- 上限83MHz。実例として vector06cc 移植者は **48MHzで動作**させ、
  16bitリード10cyc / 32bitリード11cyc を達成している。
- 27MHz × 3 = **81MHz** が第一候補。**RTL変更ゼロで約3.2倍**。
- 要検証: HyperRAMの初期レイテンシ設定（latency count）は動作周波数に
  依存するため、81MHzで12cycのまま成立するかは実機確認が必要。
  仮に14〜16cycへ伸びてもクロックが3.2倍なので実時間では確実に速くなる。

#### 帰結2: バイト幅パスで半分損している

コントローラは16bitワードを**同じ12cyc**でこなせる。
現行は16bitフェッチのたびに 12+12=24cyc 払っている。

#### 帰結3: ★本命★ ワイドアクセスのコストがほぼタダ

16bit=10cyc、32bit=11cyc → **16bit追加あたり +1cyc**。線形外挿:

| 転送幅 | PSRAM cyc | バイト単価 |
|---|---|---|
| 1バイト（現行） | 12 | 12.0 |
| 16bit | 12 | 6.0 |
| 32Bライン | 12+15 ≒ 27 | **0.84** |

**32バイトを1バイトの2.2倍のコストで取得可能＝バイト単価で14倍。**

→ HyperRAMはバースト前提のデバイスであり、
**現在の「毎回1バイトのランダムアクセス」はこのデバイスに対する最悪の使い方**。
キャッシュの本質的効能は「ヒットを速くする」ことより
**アクセスパターンを最悪から最良へ変換すること**にある。

（※検討初期に述べた「バースト無しなら空間局所性の利得はゼロ」という
　慎重論は、この事実により**撤回**する。）

## 3. ★重要★ バス16bit化には2種類あり、混同してはならない

| | 内容 | 必要な改修 |
|---|---|---|
| **(A) CPU側バスの16bit化** | CPUコアFSMに16bitアクセス状態を新設し `mem_size` を出す。decoder/MMU/バス幅を16bit化 | **CPUコア改修が必須** |
| **(B) メモリ側パスのワイド化** | キャッシュ⇔PSRAM間を16bit／ライン転送化 | cdc_bridge / psram_ctrl のみ |

**現行CPUコアは `S_MEMR_LO` → `S_MEMR_HI` というFSM状態で、
16bitアクセスをバイト2回のバスサイクルに分解して発行している。**
この分解はCPUコア内部で起きているため、下流（decoder / cdc_bridge /
psram_ctrl）だけを16bit幅にしても、**上から降ってくる要求はバイト単位のままで
効果が出ない**（器を広げても注ぐ側が細ければ流量は変わらない）。

### ★結論: キャッシュを入れるなら (A) は不要★

CPUコアが `S_MEMR_LO`→`S_MEMR_HI` で連続2バイト読みを出したとき、
キャッシュ挿入後は:

```
LO読み → ミス → 32Bラインフィル（27 PSRAM cyc）→ 応答
HI読み → ★同じラインにヒット★ → 1cyc で応答
```

**2バイト目はタダになる。(A)を実施した場合（16bitを1回12cyc）よりさらに速い。**

副次効果:
- **不整列16bitアクセスの場合分けが発生しない。**
  (A)を行うとラインまたぎ／不整列の処理が必要になる
  （`tb_cpu_memalign_v0_1.sv` で検証してきた領域）が、
  CPU側をバイト粒度のまま残せばキャッシュはバイト単位で応じるだけでよい。
  **設計リスクが一段丸ごと消える。**
- ヒット時は元々1〜2cycなので、(A)で短縮できるのは高々1cyc。投資対効果が悪い。

→ **(A) は V9合流後の独立テーマとして残す。**
　 キャッシュ導入後の実測値を見てから判断すること。
　 順序を逆にすると「苦労して(A)をやった後にキャッシュを入れてほとんど効かない」
　 という結果になる。

## 4. キャッシュ挿入位置

```
CPUコア ysd8800_cpu（★無改修★）
  └ ysd8800_addr_decoder（★無改修★）
       ├ MMIO側 → mmio_stub（CCR追加のみ・キャッシュ対象外）
       └ RAM側 → ysd8800_mmu（★無改修★）
                   │ phys_addr[19:0]
             ┌─────┴─────┐
             │ ★CACHE★  │ ← 新規挿入（ここだけ）
             └─────┬─────┘
                   │ phys_addr'[19:0]
                 cdc_bridge（v0.3・ライン転送対応）
                 psram_ctrl（v0.3・16bit/バースト対応）
```

### ★物理アドレスキャッシュとする理由（決定的）★

YUI OSはコンテキストスイッチのたびに PTR[0..15] を書き換える。
**論理アドレスでインデックスすると、プロセス切替のたびに全フラッシュが必須**
となりキャッシュの旨味が消える。MMU後段に置けばPTR変更はキャッシュから見て
透過であり、**フラッシュ不要**。

### スヌープ不要

現構成には**他のバスマスタが存在しない**（YSD8003のSDはMMIO経由のPIO）。
DMAを将来導入する時に初めて問題になる、と割り切れる。

### MMIOは分岐が別なので当然キャッシュされない（設計上きれい）

## 5. 推奨仕様（たたき台・要レビュー）

| 項目 | 案 | 根拠 |
|---|---|---|
| 種別 | 統合（I/D分離しない） | 自己書換え・ローダのコード書込みでのコヒーレンシ問題を回避 |
| 方式 | ダイレクトマップ | 比較器1個・1cycヒット。LUT4が8,640しかないため連想度は抑える |
| 容量 | 16KB（32KBも可） | BRAM潤沢（§6） |
| ライン | 32B | HyperRAMのバースト特性を活かす |
| 書込 | ライトスルー／ノーライトアロケート | 第1版はこれ一択。ダーティ管理不要＝バグ余地が激減 |
| 無効化 | MMIOに **CCR**（Cache Control Reg）1本追加、全体invalidate | ローダ・自己書換え時の逃げ道。**必須** |
| 退路 | **CCR.EN=0 で完全バイパス**（V8-bとbit-exact等価） | V3.5でMMU無効時の等価性を確保したのと同じ思想 |

### BRAM資源見積り（16KB / 32B line / ダイレクトマップ）

- データ部 16KB = 128Kbit → BSRAM 8個
- タグ部: 物理20bit − index 9bit − offset 5bit = tag 6bit + valid = 7bit × 512line
  = 3.5Kbit → BSRAM 1個
- **計 9/26個（35%）**

→ **2-way 16KB でも 32KB ダイレクトマップでも収容可能。容量制約は皆無。**
　 YUI OSのカーネル常駐部が16〜32KBに収まるなら、
　 **カーネルは事実上フルBRAM常駐**となりヒット率95%超が見込める。

## 7. 将来の追加検討事項（実機実装工程で測定）

### 7.1 CDCブリッジそのものの消滅可能性

zf3コントローラは**1:1クロック設計**。
もしCPUとPSRAMを**同一クロックで回せる**なら、
**CDCブリッジごと消滅し、2FF同期器の往復10cyc前後がまるごと無くなる。**
GW1NR-9でYSD8800コアが何MHz出るかは合成しないと不明だが、
多段FSMのマルチサイクル構成のためクリティカルパスは短いはず。
**実機実装工程の測定項目に入れること。**

### 7.2 アイドル時プリフェッチ

PSRAM側はCPUが実行フェーズにいる間ずっと遊んでいる。
ミス処理完了後に**次ラインを投機的に先読み**すれば、
レイテンシを実行時間の裏に隠せる。逐次フェッチが支配的な命令ストリームに有効。
挿入モジュール内で完結するため追加コストは小さい。第2段以降のオプション。

## 8. 危険予知（本テーマ固有・記録）

### KY-a: CDCブリッジのプロトコル再現漏れ（★最大の罠★）

`ysd8800_cdc_bridge_v0_2` は、CPU側が `mem_rd` を下げずにアドレスだけ変えて
連続発行する（`S_MEMR_LO`→`S_MEMR_HI`）ケースを `req_hold` ワンショットで捌いている。
**キャッシュのマスタ側ポートがこの挙動を正確に模倣しないと、
データ取り違え・多重発行・取りこぼしが起きる。**
しかもこれは単発テストでは絶対に出ず、Dhrystone実走で初めて化けるタイプ。

**対策**: `tb_cdc_bridge_v0_1.sv` の「背中合わせ連続要求」テストケースを、
キャッシュ挿入後の構成に対してそのまま再実行できる形で移植する（既存TB資産が使える）。

### KY-b: その他の実装上の定番漏れ

- ラインフィル中にCPUが**別ラインへアクセス**（割込ベクタフェッチ等）した場合の扱い。
  第1版は「フィル完了まで ready 保留」で確実に。
- **リセット時のvalidビット全クリア。** BRAMだと1cycで消せないので初期化カウンタが必要。
  **実装漏れの定番。**

### KY-c: モデルのパラメータを実デバイス仕様だと思い込む危険

`LATENCY_NORMAL=12` は zf3コントローラの「バースト非対応・1:1クロック」という
**実装上の制約**であり、HyperRAMデバイスの物理的限界ではない。
混同すると「12cycは動かせない定数だ」と誤認し、キャッシュだけで殴りに行って
**タダで手に入る①③を取り逃がす。**

これは CHAT80 §4「物理アドレス線は既に20bit幅で引いてある」を鵜呑みにして
CDCブリッジが16bit固定だったことを見落としかけた件（KY34）と**同じ構造の罠**。

### KY-d: 「幅を広げれば速くなる」という直感に従い、上流の要求粒度を確認せず下流だけ16bit化する危険

本検討で実際に発生した。decoder / cdc_bridge / psram_ctrl を16bit化しても、
CPUコアがバイト単位で要求を出す限り**改修工数を払って効果ゼロ**だった（§3）。

**防止策**: バス幅を変更する際は必ず「要求を発行している最上流のFSM」まで遡り、
その粒度を実ソースで確認してから着手する。中間段の信号幅だけを見て判断しない。

## 11. ① emu23 大規模改修に織り込むべき項目（キャッシュ検討の観点から）

キャッシュ設計にはアドレストレースが必須。RTLシミュレーションでYUI OS起動〜シェルまで
回してトレースを採るのは時間もトークンも掛かりすぎるため、**emu23側で行う。**
また、MMU導入時に emu23 v1.09 を黄金参照にしたのと同じ構図で、
**キャッシュ付きマシンの黄金参照が必要**になる。

| # | 項目 | 優先 | 備考 |
|---|---|---|---|
| 1 | **メモリアクセスのサイクル課金モデル**（`--mem-latency N` 等） | 高 | 現emu23は理想メモリ(1cyc)想定。RTLとの乖離を埋める |
| 2 | **物理アドレストレース出力**（MMU変換後addr＋R/W＋cyc） | 高 | キャッシュ設計の唯一の入力データ |
| 3 | パラメタライズド・キャッシュシミュレータ（容量/ライン長/連想度/ライトポリシー可変） | 中 | Python後処理ツールでの代替も可。emu23本体を膨らませたくない場合は分離 |
| 4 | CCR（キャッシュ制御レジスタ）のMMIOモデル | 中 | RTLと同一アドレスに置き黄金参照性を維持 |

**1と2だけでも先行させる価値がある。**

※ ユーザ指定の「その他3つほどの改良」については本チャットで未ヒアリング。
　 **後続チャットで内容を確認すること。**
