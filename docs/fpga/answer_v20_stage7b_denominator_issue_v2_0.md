## §1. Q-5 への回答：★現状の分子はフェッチを分離していない★

### 1.1 結論

★案(d) は現状の分子では成立しない。★

`v18` のストールカウンタは ★TB トップの `mem_rd` / `mem_wr` / `mem_ready`★ を観測する
（`v18` §2.1・§2.2）。★この地点では命令フェッチとデータ読出は同じ `mem_rd` として現れ、
区別する情報が信号上に存在しない。★

CPU の観測出力（`ysd8800_cpu_v0_1_FIXED.sv` L250-263）は
`dbg_pc` / `dbg_a` / `dbg_b` / `dbg_x` / `dbg_sp` / `dbg_flags` / `dbg_halt` /
`dbg_irq_pending` / `irq0_ack` の 9 本であり、★アクセス種別を示す出力は無い。★

### 1.2 分離しようとすれば可能ではある（ただし勧めない）

CPU 内部の状態 enum には ★`S_FETCH` / `S_OPFETCH`★ が存在する（同 L269-271）。
TB から `u_cpu.state` を階層参照すれば、★DUT 無改変で★ フェッチ由来のストールを切り分けられる。

★しかし勧めない。★

| # | 理由 |
|---|---|
| 1 | ★C-4 規律により 4 ビンの再測定が必要になる★（`v18` が 1 回の改版に 3 目的を束ねた理由そのもの） |
| 2 | ★内部状態への階層参照は、TKT-V7 §4.2 で「偶然正しいだけの観測点」として退けた形に近い★ |
| 3 | ★そもそも不要である★ — §2 の案(f) を採れば分離の必要が消える |

## §2. Q-4 への回答：★案(f) — 分母も RTL 側から取る★

### 2.1 問題の構造を言い換える

§8.4 の困難は正確である。整理すると次になる。

> ★`b = 分子(RTL) / 分母(emu23)` という式が、2 つの系にまたがっている。★
> ★そして分母は「メモリ待ち時間に依存する量」である。★
> ★測ろうとしている当のもの（待ち時間）が、分母を動かす。★

★案(a)〜(c) はいずれも「emu23 のどの走行を選ぶか」であり、この構造を変えない。★
案(d) は分子側を削って対応しようとしたが、Q-5 のとおり分子が削れない。

★系をまたぐのをやめれば済む。★

### 2.2 案(f)：`N` を RTL の `bus_ack` から取る

`v18` §2.2 は ★3 分類の 1 つとして `bus_ack` を既に計数している。★

```
待ちなし: (mem_rd || mem_wr) && mem_ready  → bus_ack
```

★`mem_ready` が 1 アクセスにつき 1 サイクルだけ立つなら、`bus_ack` は
そのビンで完了したアクセスの回数そのものである。★

したがって

```
b_measured = (stall_rd + stall_wr) / bus_ack     ★すべて RTL 側の値★
```

| 項目 | 案(f) | 案(a)〜(d) |
|---|---|---|
| 系をまたぐか | ★またがない★ | またぐ |
| 待ちループ周回数の影響 | ★分子・分母の両方に同じ周回数が入るため相殺される★ | 分母だけ別系の周回数になる |
| 分子と分母の独立性 | ★問題が消える★（同一走行の同一区間から採る） | ★§8.4 の困難が残る★ |
| 追加の測定 | ★不要★（段7-C で既に計数済） | 案(d) は分子の再測定が必要 |
| emu23 の改修 | ★不要★ | — |

★`b_measured` は「1 アクセスあたり平均何サイクル待ったか」であり、
RTL 内で完結して定義できる量である。★ emu23 の校正値 `lat − 1 = 4` との比較は、
★その後で行えばよい。★ 比較する相手が定数なので、系差は入らない。

### 2.3 案(f) を採る前に確認すべき 2 点

| # | 確認事項 | 方法 |
|---|---|---|
| ★1★ | ★`bus_ack` がアクセス回数と一致するか★（`mem_ready` が 1 アクセス 1 サイクルのパルスであり、`mem_rd` が ready 後も残らないこと） | ★指摘書 v18 §3.3（N-1）で提案した恒等式 `stall_wr + stall_rd + bus_ack + idle == C_total` が成立していれば、取りこぼしと重複計上は無い★。`v18` v0.4 でこれを実装していれば、そのログで足りる |
| ★2★ | ★MMIO 除外（U-11）★ | ★案(f) でも必須★。分子・分母ともに RAM 側のみで揃える。指摘書 v18 §2.3（M-3）で分離を要求済であり、`v18` v0.4 に RAM 側の値があるはず |

★確認1 が成立しない場合（`mem_rd` が ready 後も 1 サイクル残る等）、`bus_ack` は
アクセス回数の定数倍になる。★ その場合でも ★倍率が判れば補正できる★ ので致命的ではない。

### 2.4 ★副次的な利得：条件2 の代替が手に入る★

案(f) は `b` を RTL 内で閉じるが、`a_measured = (C_total − stall)/I` の `I` は
★RTL 側に命令カウンタが無いため★ emu23 から採るしかない。★同じ困難が残る。★

そこで ★合格条件2 を差し替えることを提案する。★

合格条件2 の目的は §5.1.3 に「★モデルが偶然フィットしただけを弾く★」と定義されている。
これは次で同等以上に果たせる。

> ★新・合格条件2：RTL の `bus_ack`（RAM 側）と、emu23 測定 A（`--no-cache-model`）の `N` との
> 乖離が一定範囲内であること。★

★これは「emu23 のモデルが RTL と同じ量の仕事をしているか」の直接検査であり、
U-4 が本来欲しかったモデル忠実度そのものである。★

さらに ★(a)(b)(c) の `N` を `bus_ack` と並べれば、どの走行が RTL に最も近いかが定量的に出る。★
★待ちループの周回数差は「モデル忠実度の指標」に転化する。★ 邪魔者が測定量になる。

★参考★：RTL は 1 命令あたり約 21.9 サイクル（`1,070,369 / 48,785` ではなく
★正しくは `C_total / I_RTL`。`I_RTL` は未知★）を要するため、
★UART 待ちループの周回数は emu23 のどの走行よりさらに少なくなるはずである。★
すなわち ★`bus_ack` は (c) の 234,285 よりも小さく出ると予想される。★
★この予想が当たるかどうか自体が、機構理解の検証になる。★（§3 の機構が正しければそうなる）

### 2.5 案(d) についての評価

★着眼は良い。★ 「走行条件に依存しない分母を選ぶ」という発想は正しい方向である。
実際、データアクセス 4 種が完全一致するという実測は ★強い性質★ であり、使いたくなる。

★不採用の理由は Q-5 の一点のみである★ — 分子を揃えられない。
★もし将来フェッチ／データを分離した測定が別の目的で必要になったら、案(d) は再浮上する。★
その可能性を §9 に記録として残されたい（KY41）。

### 2.6 案(e) についての補足

★§9 の「待ちループの周回数差は地点では揃わない」という評価は正しい。★
`-b ADDR` は「同じ地点まで走らせる」ものであり、
★同じ地点に到達するまでに何周したかは揃えられない。★ 正しい評価である。

## §3. Q-6 への回答：★特定は完了できる。実源で確定しており、トレースは不要★

### 3.1 待ちループの正体（実源）

★UART の TX レディ待ちである。★ 2 つの実源が噛み合う。

| # | 事実 | 実源 |
|---|---|---|
| ★1★ | ★emu23 は UART TX を `tx_complete_cycle = cpu.cycle + 4167` でモデル化★（9600bps@4MHz） | `emu23_v2_15.c` L1096, L1267, L254 |
| ★2★ | ★`putchar` は TX レディをポーリングするビジーウェイトを持つ★（`_putchar_wait` へ `BEQ` で戻る） | `scc23_v2_07.c` L3648-3656 |
| 3 | UART 出力は ★9 バイト★（`"N=10\n"` ＋ `"P:20"`） | `dhry_timer.c` L625, L551-554 |
| 4 | ポーリングは ★MMIO 読出★ であり `mem_charge()` に到達しない | `emu23_v2_15.c` L1540-1560 |

★事実4 が決め手である。★ ポーリングループは
★命令フェッチ（`F` に計上）＋ MMIO 読出（どの kind にも計上されない）★ しか行わない。
★データアクセス 4 種にまったく現れない★ という §8.2 の実測と完全に一致する。

そして ★`tx_complete_cycle` は `cpu.cycle` 基準★ である。
課金走行では `cpu.cycle` が 1 命令あたり数サイクル進むため、
★4167 サイクルに到達するまでの周回数が減る。★ §8.3 の推論どおりである。

### 3.2 ★定量的にも整合する★

| 量 | 値 |
|---|---|
| UART 待ちの総サイクル | 9 バイト × 4167 ＝ ★37,503★ |
| (b) の 1 命令あたりサイクル | (58,418 ＋ 143,749) / 58,418 ＝ ★3.46★ |
| フェッチ差（実測） | ★91,181★ |

走行 (a) は 1 命令 = 1 サイクルであるから、待ちループで実行された命令数 ≒ 37,503。
(b) ではその ★1/3.46★ になる。差分の命令数 ≒ 37,503 × (1 − 1/3.46) ≒ ★26,660 命令★。

これがフェッチ 91,181 バイトに対応するなら、★1 命令あたり 3.42 フェッチバイト★ となる。

★実測の (b) は `calls F / I` ＝ 192,061 / 58,418 ＝ ★3.29 バイト/命令★。★

★3.42 と 3.29 — 数%の一致である。★
★機構は定量的にも裏付けられた。★

### 3.3 結論

★§7 の「推定であり特定していない」という注記は、本回答の §3.1〜3.2 をもって解消できる。★
★`--trace-addr` による PC 頻度比較は不要である。★

★K-1（推定のまま判定に進む）の危険は消える。★
なお ★案(f) を採れば、そもそも待ちループ周回数は判定に影響しない★ ため、
特定の要否という問いは二重に解消される。★それでも機構を突き止めておく価値はある★ —
段7-B の後続（案ε の単一サーバ模擬）でも、★同じ「時間依存の周回数」が顔を出すからである。★

### 3.4 ★案ε への波及（重要）★

★案ε は emu23 のトレース上の時刻でキュー挙動を模擬する。★
本件で判明した性質——★待ちループの周回数が課金モデルに依存する★——は、
★案ε のトレースにもそのまま乗っている。★

- トレース中の ★UART 待ちループ由来のフェッチ行★ は、RTL 実機とは異なる回数だけ現れる
- これらは ★キャッシュにヒットし、メモリを占有しない★ ため、単一サーバ模擬では ★投入されない★
- ★したがって α への影響は限定的である★（サーバ占有に寄与しないため）

★ただし「時刻」には影響する。★ 待ちループの周回数が違えば、
★書込の到着間隔（サイクル差）が実機とずれる。★
★案ε の限界として §4.6 に 1 行追加されたい。★

> ★α は emu23 の時刻に基づく推定値であり、UART 待ちループの周回数が実機と異なるため、
> 書込の到着間隔にも系差が含まれる。★
