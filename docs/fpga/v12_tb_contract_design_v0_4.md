★TB が DUT の外部契約を独自に再実装し、そちらが間違う。★

### 1.2 ★なぜ段5 の前にやるのか★

段5（FLUSH / `CEN` 立上り無効化 / `fill_abort_r`）は ★新規に単体 TB を書く工程★である。

| 失敗 | 現れ方 | 気づけるか |
|---|---|---|
| 効きすぎ（過剰フラッシュ） | 性能劣化 | ✅ M-5 で気づける |
| ★効かなさすぎ（フラッシュ漏れ）★ | ★コヒーレンシ破壊★ | ❌ ★静かに壊れる★ |

★偽 FAIL に時間を溶かした状態で「静かに壊れる不具合」を追うのは最悪の組み合わせである。★
よって本対策は段5 の**前**に置く。

## §2. 契約の確定（★実源確認済★）

対策の前提として、★DUT の外部契約を実源から確定する★。
以下は推測ではなく実ファイルの引用に基づく（KY34）。

### 2.1 契約 ~~C-α：ready と同時に要求を下げる~~ → ★**C-α'：ready 後に同一要求を保持しない**★

#### ★2.1.0 v0.1 の誤り（取り消し・M-1）★

> ~~**契約 C-α**：`cpu_mem_ready` が 1 の次サイクルで `cpu_mem_rd`/`cpu_mem_wr` は 0 でなければならない。~~
> ~~実 CPU は ready と同時に要求を下げるため発生しない。~~

★この契約定義は誤りである。実 CPU の動作と正面から矛盾する。★

**反証（実源・レビュー M-1）**

```
  ysd8800_cpu_v0_1_FIXED.sv
    L750  S_MEMR_LO: begin if (mem_ready) next_state = S_MEMR_HI; end
    L880  S_MEMR_HI: begin mem_addr = addr_r + 16'd1; mem_rd = 1'b1; end
```

★cycle N で `ready=1` → cycle N+1 は `S_MEMR_HI` で `mem_rd=1`。★
同型の経路は他にも存在する（すべて実源確認済）：

| 遷移 | 行 | 次サイクルの要求 |
|---|---|---|
| `S_MEMR_LO` → `S_MEMR_HI` | L750 / L880 | `mem_rd=1`（16bit ロード） |
| `S_FETCH` → `S_OPFETCH` | L618 / L871-872 | `mem_rd=1`（命令フェッチ） |
| `S_PUSH_LO` → `S_PUSH_HI` | L787 / L889 | `mem_wr=1`（PUSH） |
| `S_POP_LO` → `S_POP_HI` | L806 / L892 | `mem_rd=1`（POP） |

★旧 C-α を導入すれば、命令フェッチのたびに発火する。★
`$error` にしていても ★切り分け不能なログの洪水★ となり、
★本設計が解こうとしている「偽 FAIL に時間を溶かす」問題を自ら再生産する。★

#### ★2.1.1 なぜ ready の次サイクルに要求が立つのが正しいのか★

```
  ysd8800_cdc_bridge_v0_4.sv
    L110  logic suppress_r;   // readyと同位相のreq抑止信号
    L119  assign req_level = (cpu_mem_rd | cpu_mem_wr) & ~suppress_r;
    L131  suppress_r <= ack_sync[0] & ~ack_sync[1];
```

`suppress_r` の抑止幅は★ちょうど 1 cpu cyc★。cycle N+1 では `suppress_r=0` に戻るため、
`rd` が立っていれば ★**新しいアドレス**で新しい要求が発火する★。
これは 4 相ハンドシェイクを ★1 サイクルの無駄なく回すための意図された設計★であり、
★工程①.5 の A-2q の成果そのもの★である。

#### ★2.1.2 では段4 の誤りは何だったのか★

| 主体 | ready 後の「継続」 |
|---|---|
| ★実 CPU★ | 必ず ★**新しい要求**★（アドレスまたは種別が変化） |
| ★段4 の TB★ | ★**同一アドレス・同一種別の要求を保持**★ → 同一要求の再送 |

★旧 C-α はこの区別を捉えていなかった。★
「要求が継続しているか」ではなく ★「同じ要求を保持しているか」★ が問うべき性質である。

#### ★2.1.3 再定式化★

★**契約 C-α'**：`cpu_mem_ready` が 1 のサイクルの次サイクルで要求が継続する場合、
それは**新しい要求**（アドレスまたは種別が変化している）でなければならない。
★同一アドレス・同一種別の要求を保持してはならない。★★

## §3. T-B：バス契約アサーションの常設（★最優先★）

### 3.1 方針

★DUT 側に常設する。★ TB 側ではない。

理由：TB 側に置くと ★TB を書く人が assert も書くことになり、同じ人が同じ誤解をする★。
契約は DUT の性質であるから、DUT の隣に置くのが正しい。
（KY78 の「契約の実装が2箇所あると片方が古くなる」への直接の対処）

### 3.2 配置先（★M-4 反映：監視する境界を明示★）

★工程②-B 以降、CPU 抽象バスの境界は **2 箇所** ある。★

```
   CPU ──[境界①]── キャッシュ段 ──[境界②]── cdc_bridge ── psram_ctrl
```

★v0.1 は境界②（`cdc_bridge`）にしか assert を置いていなかった。★
段5 で新規に書く TB（`tb_cache_flush_poc` 等）は ★キャッシュ段を直接 DUT とする★ため、
`cdc_bridge` はインスタンス化されず ★assert が1本も効かない★構成であった。
★「新規 TB が危険だから対策する」と言いながら、その新規 TB に届かない★という
致命的な穴であり、M-4 として是正する。

| 契約 | ★監視する境界★ | 配置モジュール | 監視するポート |
|---|---|---|---|
| ★C-α'★ | ★①CPU ⇔ キャッシュ段★ | ★`ysd8800_cache_v0_x.sv`★ | `cpu_ready_o` / `cpu_rd_i` / `cpu_wr_i` / `cpu_phys_addr_i` |
| ★C-α'★ | ②キャッシュ段 ⇔ `cdc_bridge` | `ysd8800_cdc_bridge_v0_4.sv` | `cpu_mem_ready` / `cpu_mem_rd` / `cpu_mem_wr` / 物理アドレス |
| C-β | ②の下流（PSRAM 受理） | `ysd8800_psram_ctrl_v0_3.sv` | `req` / `burst_len` / `we` / `blen_r` |

| ~~C-δ~~ | ~~①の隣（キャッシュ段内）~~ | ~~`ysd8800_cache_v0_x.sv`~~ | ★**不採用（恒偽・§3.2.0.0）**★ |

##### ★3.2.0.0 不採用の理由：条件が恒偽である★

★実装着手時に実源を確認した結果、C-δ の条件は構造上、真になりえないことが判明した。★

```
  ysd8800_cache_v0_3.sv
    L143  wire fill_req = ccr_cen_i & miss & cpu_rd_i;
    L144  wire fill_sel = ccr_cen_i & (fill_req | fill_active_r);
    L330  assign burst_len_o = fill_sel ? BLEN_W'(LINE_SIZE) : BLEN_W'(1);
    L334  assign br_rd_o     = ccr_cen_i ? (fill_req | fill_active_r) : cpu_rd_i;
```

★`ccr_cen_i=1` のとき `fill_sel` と `br_rd_o` は同一の式である。★ したがって：

```
  CEN=1 かつ br_rd_o=1  ⟹  fill_sel=1  ⟹  burst_len_o = LINE_SIZE(32)
```

C-δ の条件 `ccr_cen_i && br_rd_o && !br_wr_o && (burst_len_o == 1)` は ★恒偽★。
★実装すれば「書いたが絶対に発火しない検査器」となり、§7 R-1 そのものになる。★

##### ★3.2.0.1 設計時の誤り：症状の発生箇所と原因の所在を取り違えた★

C-δ は段4 の症状（`blen_r=1` のままフィルが走る）を
★「キャッシュ段が誤った `burst_len` を出した」★と捉えて設計した。

★しかし実際には、キャッシュ段の出力は一度も誤っていない。★
真因は ★`fill_sel=0` の時点で既に req が psram に到達していた★ことであり、
★値の誤りではなくタイミングの問題★であった。

> ★教訓：検査器を設計するときは「何が誤っていたか」を実源で確認する。★
> 症状が観測された場所（`psram_ctrl` の `blen_r`）と、
> 原因が存在する場所（req 到達タイミング）は一致しない。
> ★原則138（切り分けは系の外側から入れる）の設計版である。★

##### ★3.2.0.2 代替：既存の検査器で覆われている★

段4 の真因（タイミング）を捉える検査器は ★既に C-α'（境界②）が担っている★。
N-3 のとおり、境界②の C-α' は `fill_active_r` の deassert タイミングの
検証器を兼ねる。★C-δ を無理に生かすより、既存検査器で覆われていると整理する。★

## §4. T-A：バスアクセスタスクの共有インクルード化

### 4.1 方針

`do_read` / `do_write` を ★`bus_tasks.svh` に1箇所集約★し、
各 TB は `` `include `` するだけにする。

### 4.2 記述案

```systemverilog
// bus_tasks.svh  v0.1  (2026-09-01)
//   ★契約 C-α に準拠したバスアクセスタスク。★
//   各 TB はこれを include し、独自に do_read/do_write を書かないこと。
//   ★理由: 段4 で TB 独自実装が ready の1cyc後に req を下げ、
//          同一要求が再送された（TKT-V1）。★

task automatic do_read(input logic [19:0] addr, output logic [7:0] data);
    @(posedge cpu_clk);
    cpu_mem_addr <= addr;
    cpu_mem_rd   <= 1'b1;
    // ★ready を検出した「その」サイクルで下げる（1cyc 遅らせない）★
    do @(posedge cpu_clk); while (!cpu_mem_ready);
    data       = cpu_mem_rdata;
    cpu_mem_rd <= 1'b0;
endtask

// ★M-3：do_write（C-β の遵守に直結する）★
//   注意: psram_ctrl L165 の書込条件は ★we をポート直接参照★しており、
//         ★受理時にラッチされない★。したがって wr / wdata は
//         ★ready 成立まで保持し続けなければならない★。
task automatic do_write(input logic [19:0] addr, input logic [7:0] data);
    @(posedge cpu_clk);
    cpu_mem_addr  <= addr;
    cpu_mem_wdata <= data;      // ★① addr/wdata/wr を同時に立てる★
    cpu_mem_wr    <= 1'b1;
    // ★② ready 検出まで3つとも保持する★
    do @(posedge cpu_clk); while (!cpu_mem_ready);
    cpu_mem_wr    <= 1'b0;      // ★③ ready を検出した「その」サイクルで下げる★
    @(posedge cpu_clk);
    cpu_mem_wdata <= 'x;        // ★④ wdata は wr を下げた「後」に変更する★
endtask
```

> ★要点は「ready を検出したそのサイクルで下げる」ことのみである。★
> 段4 の誤りは、検出後にもう1サイクル `@(posedge)` を挟んでいたことだった。

### 4.3 適用範囲（★限定する★）
