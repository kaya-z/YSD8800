# V8-D Dhrystone RTL 膨張率調査 総合レポート

- **文書ID**: v8d_expansion_analysis_v1_0.md
- **作成日**: 2026-07-24
- **対象工程**: V8-D（Dhrystone iverilog動作確認）
- **経緯**: CHAT115 で膨張率2000倍発見・CHAT116 で11段階切り分け実施
- **状態**: **真因の局在完了・PC破壊機序は未特定**（Step K で継続）

---

## 1. 事象概要

Dhrystone Number_Of_Runs=1 (emu23: 4,872 cyc) を iverilog RTL で実行すると、**1,000万 cyc でも完走せず uart_cnt=4 (`N=1\n` のみ) で停滞**。膨張率は **200倍以上**を大幅超過し**実質2,000倍以上**。

UART 出力は `"N=1\n"` (4B) で止まり、期待値 `"N=1\nP:20"` (8B) の後半が出ない。

## 2. 切り分け経過サマリ

### Step A: IRQ 副作用（仮説α）→ 否定

- startup_harness23 の `EI` を `DI` に置換
- iverilog 実行: FLAGS bit7(IE) が 0 で維持されることを確認 = IRQ 抑止成功
- **結果**: 膨張率変わらず。**タイマーIRQ は主因ではない**

### Step B: PC ヒストグラム（256B/bin）

| Bin | サイクル数 | 累積比率 |
|---|---|---|
| $2400-24FF (Func_2内) | 4,298,860 | 43.0% |
| $2500-25FF (Func_2内) | 3,664,796 | 36.6% |
| $2300-23FF (Func_1内) | 1,900,132 | 19.0% |
| $2600-26FF (L_0140以降) | 64,034 | 0.6% |

**98.6% が Func_1+Func_2 に集中**。Func_2 は 293 行のはずが 800万cyc消費。

### Step C1: PSRAM wait 最小化（仮説δ）→ 否定

- LATENCY_NORMAL 12→2、LATENCY_REFRESH 15→2 に変更
- **結果**: cycle 消費が Step B と**完全一致**（bin別カウント含めて全一致）
- **PSRAM wait は主因ではない**。CPU側 or cdc_bridge 側で決定論的に cycle消費している

### Step D: 主要エントリ通過回数

| エントリ | 実測 | 期待 | 判定 |
|---|---|---|---|
| main ($04CC) | 2 | 1 | 微妙 |
| dhrystone ($0579) | 1 | 1 | ✅ |
| for_cond ($07CB) | 1 | 2 | ⚠️ |
| for_body ($0835) | 1 | 1 | ✅ |
| **Func_1 ($23B4)** | **3558** | 3 | 🚨 |
| **Func_2 ($248D)** | **3559** | 1 | 🚨 |

**Func_1/Func_2 が毎回セットで 3558/3559 回**呼ばれている。

### Step E1: Func_1 入口の引数観測

10回連続で完全に同じ引数:
- arg1_lo = 0x59 ('Y')
- arg2_lo = 0x52 ('R')

Int_Loc が変化していない = while ループが抜けていない。

### Step E2: Func_1 RET直後の A レジスタ

10回連続で **A=0x0001** (Ident_2)。期待は A=0 (Ident_1)。

論理上「'Y' != 'R' なので Ident_1 を返す」はずが Ident_2 を返している。

### 単体TB: CMPI/BEQ 隔離検証

`LDW A,#1 → CMPI A,#0 → BEQ +5 → LDW A,#$AAAA → HALT` を最小プログラムで実行:
- **HALT時 A=0xAAAA** ✅（正常動作）
- BEQ 直前 FLAGS=0000 (Z=0) → 正しく不成立
- **CMPI/BEQ 単体は emu23 と完全一致で正常**

→ **CPU RTL の CMPI/BEQ 単体バグは否定**

### Step F: Func_2 while ラベル通過

| ラベル | 通過 | 意味 |
|---|---|---|
| L_0139 ($24C9) while先頭 | 3558 | while判定を3558回実行 |
| L_0143 ($2586) Int_Loc++ ルート | 3557 | Func_1==Ident_1 判定成立 |
| L_0145 ($260D) JMP L_0139 | 3557 | while継続点 |
| L_0140 ($2610) while抜け後 | 3557 | while から抜けたのは3557回 |

**while ループは毎回 1反復で正常抜け**（Int_Loc: 2→3 で 3<=2偽 → 抜け）。

### Step G: for本体 JSR _Func_2 ($08E8) 通過

- JSR _Func_2 通過 = **1** （期待通り）
- Func_2 入口 = 3559

**for本体からの Func_2 呼出は1回のみ。しかし Func_2 は3559回入っている = Func_2 のRETがFunc_2入口へ戻る**。

### Step H: Func_2 RET ($27B8) 到達

- **0 回**

**Func_2 は RET まで到達していない**。L_0140 の後、途中で Func_2 入口へ戻っている。

### Step I: L_0140 以降のラベル通過

| ラベル | 通過 |
|---|---|
| L_0140 ($2610) | 3557 |
| L_0149 ($2630) | **0** |
| L_0150 ($2634) | **0** |
| L_0151, L_0152, L_0147, L_0148, L_0153, L_0155, L_0156, L_0157 | **全 0** |
| L_0138 ($27B0) | **0** |

**$2610 と $2630 の間、わずか 32 バイトの中で PC が $248D に飛ぶ**。

### Step J: $2610 到達時状態観測

3回連続で:
```
A=0000 B=0001 X=f798 SP=f792 FLAGS=0081
PSRAM [X-6=f792][X-5]=9a f7  (LDW A,[X+FFFA]の読出元)
PSRAM [$2610..$2617]=26 00 fa ff 43 30 02 00
```

- **PSRAM 上の命令列は正常**（`LDW A,[X+FFFA] / SUBI SP,#2 / ...`）
- **[X-6][X-5] = 9A F7** = Ch_Loc位置に **前フレームのゴミが残っている**
- $2614/$2618/$261A/$2626 は**全て 0回通過**

## 3. 判明した Ch_Loc の 8/16bit 混在

### 3-1. C言語ソース

```c
Boolean Func_2 (Str_30 Str_1_Par_Ref, Str_30 Str_2_Par_Ref)
{
  REG One_Thirty  Int_Loc;
  Capital_Letter  Ch_Loc;      // char型 (1byte)

  Int_Loc = 2;
  while (Int_Loc <= 2)
    if (Func_1(...) == Ident_1) {
      Ch_Loc = 'A';           // ★ここが問題
      Int_Loc += 1;
    }
    
  if (Ch_Loc >= 'W' && Ch_Loc < 'Z')  // ★Ch_Locを参照
    ...
```

### 3-2. アセンブラ（scc23 v2.03 生成）

**Ch_Loc = 'A' の代入** (L3045-3055):
```asm
LDW A, #65          ; A = 'A' (0x41)
SUBI SP, #2
STW A, [SP]         ; PUSH A
MOV A, X
SUBI A, #6          ; A = X-6 (Ch_Locアドレス)
LDW B, [SP]         ; B = 0x0041
ADDI SP, #2
SUBI SP, #2
STW X, [SP]         ; PUSH X
MOV X, A            ; X = X-6
STB B, [X]          ; ★[X-6] ← B下位バイトのみ (0x41)★
LDW X, [SP]
ADDI SP, #2
```

**Ch_Loc の参照** ($2610・L_0140直後):
```asm
LDW A, [X + #$FFFA]  ; ★A = [X-6][X-5] (2バイト読み)★
```

### 3-3. バグの本質

- **STB で 1バイトだけ書き**（[X-6] = 0x41）
- **LDW で 2バイト読み**（A = 0xF7 0x41 = 0xF741、上位は前フレームのゴミ）
- emu23 では `[X-5]` が常に 0 のため隠蔽（emu23 の初期化仕様 or メモリ配置差）
- iverilog RTL では PSRAM 上のゴミがそのまま読まれる

## 4. 未特定の機序

### 未解明: PC が $248D に飛ぶ機序

Ch_Loc 汚れ = A レジスタに 0xF741 が入るだけで、**論理的には PC には影響しない**。

しかし観測は明確に:
- $2610 (L_0140) 到達
- $2614 (LDW直後の SUBI SP,#2) 到達せず
- $2626 (BGE) 到達せず
- $2634 (L_0150) 到達せず
- **PC が $248D (Func_2入口) にジャンプしている**

## 5. 残された仮説

### 仮説θ1: LDW_XI 命令 (opcode 0x26) 実装バグ

- 特定条件（メモリの上位バイトが 0xF7 など）で PC が破壊される可能性
- V2 系 TB で LDW_XI 単体は検証済のはずだが、実行文脈で発現

### 仮説θ2: IRQ 受理経路

- FLAGS bit7 (IE)=1 のため IRQ 受理される可能性
- しかし IRQ0 ベクタ=$0025、IRQ1=$0026 で $248D ではない
- 何らかの理由で **ベクタ値の計算が壊れて $248D になる**可能性

### 仮説θ3: PSRAM の隣接アドレス干渉

- PSRAM モデルの $2610 fetch 時に、キャッシュ or アドレス生成でバグ
- $248D への迷い込み

## 6. 次工程（Step K）の設計方針

**PC 遷移の1cyc毎生ダンプ**を実施。$2610 到達後 50cyc 分の PC を記録し、$2610→?→?→$248D の中間経路を実測。
