# startup_harness23_v16.asm `_irq1_handler` レジスタ退避欠落 バグ指摘書

- **文書ID**: startup_harness23_v16_irq1_regsave_bug_report_v1_0.md
- **起票者**: Claude（設計レビュー担当）
- **起票日**: 2026-07-26
- **対象ファイル**: `startup_harness23_v16.asm` L120-126（`_irq1_handler`）
- **バグ種別**: 割込ハンドラのレジスタ退避欠落（呼出元 A/B 破壊）
- **発見経緯**: scc23 v2.04 char ロード修正設計書 v1.0 のレビュー（§2.5 割込ハンドラの X 使用実態確認）過程で、隣接ハンドラの実源を精査中に発見
- **判定**: **既存バグ確定・別件起票扱い**（scc23 v2.04 修正とは独立に対応必要）
- **優先度**: 中〜高（原則「見えているバグは先に潰す」に従い、scc23 v2.04 リリース前後で対応推奨）

## 0. 要約

- **バグ**: `_irq1_handler` が呼出元コンテキストの A/B レジスタを退避せずに使用し、IRET 後に呼出元の A/B が破壊される
- **同一ファイル内の非対称**: `_timer_handler`（L98-111）は A/B/X を `_isr_wk_a/b/x` に退避しているが、`_irq1_handler` は退避していない
- **退避ワーク領域は既存**: `_isr_wk_a/b/x` ($000C-$0011) は既に設置されており、使用しない技術的理由なし
- **実害**: 現時点で顕在化しにくいが、V8-b 以降で YUI OS ファイルマネージャがストレージ経由 read/write を発行すると非決定的な間欠バグとして顕在化する

---

## 1. 事実確認（実源）

### 1.1 バグ位置

**startup_harness23_v16.asm L120-126**（原文引用）:

```asm
_irq1_handler:
    ; IRQ_STATを読み出してからWrite-to-Clearでクリア
    ; スタブ実装: 全ビットクリアしてIRET
    LDW  A, #$FCB2      ; IRQ_STAT アドレス      ← A を無条件上書き
    LDW  B, [A]         ; IRQ_STATを読み出し     ← B を無条件上書き
    STW  B, [A]         ; Write-to-Clear（読み出し値を書き戻す）
    IRET
```

### 1.2 対比: `_timer_handler` は正しく退避している

**startup_harness23_v16.asm L98-111**（原文引用）:

```asm
_timer_handler:
    STW  A, [_isr_wk_a]     ; A/B/X を退避（中断されたコードを保護）
    STW  B, [_isr_wk_b]
    STW  X, [_isr_wk_x]

    LDW  A, #$FC90          ; TCR アドレス
    LDW  B, #$0023          ; TIMER_EN|IRQ_EN|IRQ_ACK ＝ ACK＋再武装
    STW  B, [A]             ; TCR ← 状態ビット込みの完全値

    LDW  A, [_isr_wk_a]     ; A/B/X を復元
    LDW  B, [_isr_wk_b]
    LDW  X, [_isr_wk_x]
    IRET
```

**設計意図の明示**：同ファイル L63-66（コメント原文）:

> ================ ISR退避ワーク（v1.6 / V5新設）================
> `_timer_handler` が TCR ACK を発行する際に A/B/X を破壊するため、中断されたコードのレジスタを保護する退避先が必要になった。

**同じ理由が `_irq1_handler` にも当てはまる**（LDW A,#$FCB2 で A を、LDW B,[A] で B を破壊）にも関わらず、退避が実装されていない。

### 1.3 CPU 側 IRQ 受理仕様の実源

**emu23_v111.c L1224-1236**（原文引用）:

```c
if (cpu.irq_pending >= 0 && (cpu.flags & FL_IE)) {
    int irq = cpu.irq_pending;
    cpu.irq_pending = -1;
    push16(cpu.pc);                // PC を先に push (§7.5)
    push16((uint16_t)cpu.flags);   // FLAGS を後に push
    cpu.flags &= ~FL_IE;           // IE = 0
    uint16_t vec = rd16((uint16_t)(irq * 2));
    cpu.pc = vec;
    ...
}
```

**CPU が自動 push するのは PC と FLAGS のみ**。A/B/X は呼出元コードの責任で保存する必要がある。これは MC6809 系の思想と一致（ハードは PC/CCR のみ、汎用レジスタはソフト側で PSH/PUL）。

### 1.4 IRQ1 の運用実態

**startup_harness23_v16.asm L13, L48**（原文引用）:

```
;   IRQ1ハンドラ: _dummy_irq → _irq1_handler（YSD8004経由デバイス対応）
```

```
.word _irq1_handler     ; IRQ1: YSD8004経由デバイス
```

IRQ1 は YSD8004 経由の YSD8003 ストレージ完了通知として使われる。V6-A 以降のストレージアクセスで発生。

## 2. 実害シナリオ

### 2.1 顕在化パターン

以下の状況で **ユーザランド側の非決定的動作**が発生する：

1. ユーザランドコード（scc23 生成コード）が計算中に A レジスタで値を保持
2. YSD8003 ストレージ完了 IRQ1 が非同期発生
3. `_irq1_handler` 実行中に A が `$FCB2` に上書きされ、B が IRQ_STAT の内容に上書きされる
4. IRET 後、ユーザランドは破壊された A/B で処理を続行 → **想定と異なる計算結果 or アドレス参照 or 分岐**

### 2.2 現時点で顕在化しにくい理由

- YSD8003 ストレージ完了 IRQ は SD カード読出コマンド完了時のみ発生 → 発生頻度が低い
- 現状は cat/ls デモ (V8-a) 程度で、ストレージ操作の直前後にレジスタ整合性を要求する処理が限定的
- V8-D Dhrystone は SD 経路削除（案S1）のため IRQ1 が発生しない
- 単純なテストプログラムでは A/B の値保持期間が短く、IRQ タイミングに当たらない確率が高い

### 2.3 将来顕在化する条件

- **V8-b 以降**: YUI OS ファイルマネージャがストレージ read/write を頻発
- **YUI OS 上のユーザランドプログラム**: scc23 生成コードがストレージ操作と並行動作
- **scc23 v2.04 修正後の相互作用**: char 読出しが `ADDI X → LDB A → SUBI X` の3命令列になり、LDB 直後の A に char 値が入るが、この間に IRQ1 が受理されると A が破壊される
  - ただしこの相互作用は「scc23 v2.04 が悪化させた」わけではなく、**scc23 全体で常に発生していた既存問題**が可視化されるだけ

### 2.4 デバッグ困難性

- 非同期 IRQ タイミングに依存する間欠発生 → 再現性が低い
- ユーザランド側のバグに見え、原因追跡が長期化する
- **scc23 側のコード生成バグと誤診される可能性**（scc23 v2.04 の教訓の再来）

## 3. 修正案

### 3.1 案A（最小修正・推奨）: `_timer_handler` と同じ退避パターンにする（X も含む）

```asm
_irq1_handler:
    STW  A, [_isr_wk_a]     ; A/B/X を退避（_timer_handler と同一パターン）
    STW  B, [_isr_wk_b]
    STW  X, [_isr_wk_x]

    LDW  A, #$FCB2          ; IRQ_STAT アドレス
    LDW  B, [A]             ; IRQ_STATを読み出し
    STW  B, [A]             ; Write-to-Clear

    LDW  A, [_isr_wk_a]     ; A/B/X を復元
    LDW  B, [_isr_wk_b]
    LDW  X, [_isr_wk_x]
    IRET
```

**利点**:
- 全 IRQ ハンドラの退避方針が対称化 → 保守性向上
- 将来 `_irq1_handler` が X を使う実装に拡張しても影響なし
- コーディングパターンの一貫性 → レビュー時の目視確認容易

**欠点**:
- 実行サイクル数が増加（STW×3 + LDW×3 = 6命令追加）
- ただし IRQ1 は低頻度発生のため実性能への影響は微小

### 3.2 案B: 実際に使うレジスタ (A/B) のみ退避

```asm
_irq1_handler:
    STW  A, [_isr_wk_a]     ; A/B のみ退避（X は本ハンドラで使用しないため不要）
    STW  B, [_isr_wk_b]

    LDW  A, #$FCB2
    LDW  B, [A]
    STW  B, [A]

    LDW  A, [_isr_wk_a]
    LDW  B, [_isr_wk_b]
    IRET
```

**利点**: 最小限のオーバーヘッド（STW×2 + LDW×2 = 4命令追加）

**欠点**:
- 将来 `_irq1_handler` を拡張して X を使う実装にした際、退避追加を忘れる危険
- ハンドラ間で退避パターンが非対称 → 保守性がやや低下

### 3.3 レビュア推奨: 案A

**理由**:
- IRQ1 は現状スタブ実装（L122 コメント「スタブ実装」）で、将来必ず本格実装される
- 本格実装時に X が使われる可能性が高い（データ転送用など）
- 退避漏れバグは同種の非決定的間欠バグを再発させる高リスク
- 実行サイクル数の差は無視できるレベル（IRQ1 発生頻度が低い）
- **全ハンドラ対称化の保守性メリット > 微小な性能差**

## 4. 退避ワーク領域共有問題（追加確認）

### 4.1 現状仕様の安全性

`_timer_handler` と `_irq1_handler` が同じ退避ワーク領域 `_isr_wk_a/b/x` を共有することの正当性：

**emu23_v111.c L1230**（原文）:
```c
cpu.flags &= ~FL_IE;   // IRQ 受理時に IE をクリア
```

- IRET まで別 IRQ は受理されない（FL_IE は IRET 時にスタックから復元される）
- したがって timer_handler 実行中に irq1 が受理される、あるいはその逆は起こらない
- **ワーク領域共有は現行仕様下では安全**

### 4.2 将来の懸念（申し送り）

IRQ ネスティング（ハンドラ内で明示的に `EI` を実行して別 IRQ を受理する運用）を導入する場合、退避ワーク領域共有は**壊れる**。この場合、スタック退避方式（`PUSH A/B/X`）への移行が必要。

**推奨**: `_isr_wk_a/b/x` の設置コメント（L63-66）に「IRQ ネスティング未対応。ネスティング導入時はスタック退避方式に変更必要」の1行を追記。

## 5. scc23 v2.04 との関係

### 5.1 独立性の確認

- **scc23 v2.04 の修正案（案3: `ADDI X → LDB A → SUBI X`）は本バグと独立に安全**
  - `_irq1_handler` は X を触らないため、v2.04 案3 の X 復元は問題なく完了する
- **本バグは scc23 全般に対して既存**：v2.04 修正の有無に関わらず、IRQ1 受理後は呼出元の A/B が破壊される
- **scc23 v2.04 承認は本バグとは無関係に有効**

### 5.2 併せて対応すべき理由

- scc23 v2.04 レビュー §7.3 で提案した「割込ハンドラの X 使用規約」に、**A/B 退避規約も含める**べき
- 現状の `_irq1_handler` はこの規約に違反しており、規約明文化と並行して修正する必要がある

### 5.3 修正順序の提案

1. **scc23 v2.04 実装・検証**（本バグと独立に進行）
2. **本バグ修正**（`_irq1_handler` 退避追加）を別 PR/リビジョンで対応
3. **YUI OS 設計書に規約明文化**: 「割込ハンドラは呼出元の A/B/X を破壊してはならない。使用する場合は必ず退避・復元すること」

## 6. 検証計画

### 6.1 単体検証

修正版 `startup_harness23_v17.asm`（v16→v17 版数アップ）で以下を確認：

1. 従来テスト（V8-a cat/ls デモ、V8-D Dhrystone）が引き続き PASS
2. IRQ1 発生を意図的に誘発する単体 TB を作成し、IRQ1 前後の A/B 値が保存されることを実測
   - 例: ユーザランドで A=$1234, B=$5678 に設定 → NOP ループ → IRQ1 発生 → IRET 後 A=$1234, B=$5678 のまま

### 6.2 回帰チェック

プロジェクト規約に従い Dhrystone 完走確認：
- emu23 上の Dhrystone 完走（IRQ1 非発生パスなので変化なし想定）
- V8-D RTL 回帰（IRQ1 非発生パスなので変化なし想定）

### 6.3 実害確認テスト（推奨・オプション）

修正**前**の v16 で以下を試行し、バグが実際に顕在化することを確認しておくと教訓が残る：

- ユーザランドで A/B に定数を設定 → ストレージ read を発行して IRQ1 を誘発 → IRET 後の A/B を検査
- **期待**: 修正前は A=$FCB2 になる。修正後は元の値が保持される

これは「見えているバグ」の可視化として原則76（実源照合）の実践となる。

## 8. 本レビューでの追記（原則76 の運用強化）

### 8.1 前回 scc23 v2.04 レビューの見落とし

scc23 v2.04 レビュー §2 実源照合サマリで「全ハンドラで X 使用実態を確認、判定は全ハンドラで成立」と述べたが、これは **X を使わないことしか確認しておらず、A/B の退避有無を確認していなかった**。設計書 §2.5 が「割込ハンドラの X 使用実態」に焦点を当てていたため、レビュアも X に視野が限定されていた。

### 8.2 教訓

**設計書のスコープに引きずられず、隣接実源に別バグが潜んでいないか常に警戒する**。今回の指摘（かやぬまさんから）は、この視野拡張の実例として非常に価値がある。原則76（実源照合）の運用として、「設計書の主張範囲だけでなく、周辺実源の一貫性も確認する」ことをレビュー手順に組み込む。
