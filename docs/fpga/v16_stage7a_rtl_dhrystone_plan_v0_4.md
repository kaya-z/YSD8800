### 1.2 ★終端の定義（本計画の要）★

★段7-A の測定終端は `dbg_halt` のアサート時点の `cycle_count` とする。★

根拠：P-3 により、Dhrystone は `_main` から復帰して必ず `HALT` に到達する。
`dbg_halt = (state == S_HALT)`（`ysd8800_cpu_v0_1_FIXED.sv` L907）は
★CPU 内部状態の直接反映であり、速度依存が原理的に無い。★

★この選択は段6 の M-5 判定（UART 部分列一致）より堅い。★
段6 の M-5 は TKT-U1（出力順序の入替）の影響を受け、
`CEN=1` で `M-3: 0` になる副作用を抱えていた。
`dbg_halt` はこの種の速度依存を持たない。

★ただし `dbg_halt` 固有の性質として、`cycle_count` に UART 送出待ちが混入する（C-5）。
扱いは §5.2 に定める。★

### 1.3 段7-B を emu23 改修とする根拠（記録）

emu23 の課金式は 4 分岐（読みヒット / 読みミス / 書きヒット / 書きミス）のみで
（`emu23_v2_15.c` L89-93）、★「キャッシュを持たない CPU が PSRAM を直接叩く」課金経路が存在しない。★

- `cache_enable==0` は課金 0 ＝ **理想メモリ**であり、RTL の `CEN=0` とは別物
- `--cache-size` の最小値は `--cache-line` と同値（同 L618）であり、
  1 ライン構成にしても★32B ライン内の連続アクセスはヒットしてしまう★。
  段6 実測で *h_f*=0.9981 であったから、フェッチはほぼヒットのまま残り、
  「全ミス近似」にならない

## §4. 新規 TB の設計（S-1）★M-1 反映：差分 3 点 → 6 点 → ★v0.3 で 7 点★★

### 4.1 差分が 3 点では成立しない理由（実源）

v0.1 は差分を D-1〜D-3 の 3 点としたが、★本番 TB には UART 判定以外に
YUI OS 固有の観測・監視が存在し、そのままでは Dhrystone が測定前に強制終了する。★

| 実源 | 内容 | Dhrystone での挙動 |
|---|---|---|
| L457-466 | M-1 プローブ：`dbg_pc == 16'h0E00`（`_kstart`）到達検出 | Dhrystone は `$0E00` を実行しない → 永久に `m1_reached=0` |
| L490-494 | ★`M1_TIMEOUT_CYCLES = 10_000` で `!m1_reached` なら `finalize_and_exit(0)`★ | ★10,000 cycle で強制終了。emu23 実測 48,785 cycle にすら届かない★ |
| L498-501 | `M2_TIMEOUT_CYCLES = 200_000`（`m1_reached` 前提） | M-1 撤去後の次の誤発火源 |
| L505-509 | `UART_STALL_LIMIT = 5_000_000` の UART 停滞監視 | 測定中は UART を出さない → 撤去または延長が必要 |
| L299-306 | CL-1(4)：`mem[$0E00]` が `$00` なら「HEX ロード失敗の可能性」WARN | Dhrystone イメージでは誤警告 |

★「差分は最小」という方針自体は正しく、誤っていたのは差分の数え上げであった。★
D-4〜D-6 を追加しても §4.2 の目的（CDC・PSRAM・契約監視の流用）は損なわれない。
撤去対象はいずれも★YUI OS ワークロード固有の判定器★であり、CDC/PSRAM/契約監視には該当しない。

### 4.2 差分一覧（確定）

| # | 差分 | 内容 |
|---|---|---|
| D-1 | ロード対象 | `$readmemh("yuios_road2.hex", …)` → `$readmemh("dhry_final.hex", …)` |
| D-2 | 終端判定 | UART 部分列一致（M-1〜M-5）を撤去し、★`dbg_halt` 立上りで `cycle_count` を記録して `$finish`★ |
| D-3 | SD カードモデル | 接続したまま★参照しない★（撤去は差分と波及リスクを増やすため行わない。R-2 でレビュー支持済） |
| ★D-4★ | PC プローブ・TIMEOUT | ★M-1 PC プローブ（`$0E00`）、M1/M2 TIMEOUT、CL-3 SP assert（`$477E`）を撤去★ |
| ★D-5★ | UART 停滞監視 | ★撤去する。異常終端は `MAX_CYCLES` 到達のみとする★ |
| ★D-6★ | ロード健全性チェック | CL-1(4) の `mem[$0E00]` チェックを、★リセットベクタ `mem[$0000]/[$0001]` が `_startup` を指すことの確認★に差し替える |
| ★**D-7**★ | ★**MISMATCH モニタ（v0.3 追加）**★ | ★**キャッシュ返却値と PSRAM 実体を読出完了サイクルごとに照合する**★。`mem_rd && mem_ready && (mem_addr < 20'hFC80)` の条件で `mem_rdata` と `u_membus.u_psram_ctrl.mem[mem_addr]` を比較し、不一致を報告する。★母数（照合実施回数 `read_checked`）を必ず併記する★ |

### ★4.3 D-7 を設ける理由（v0.3 新設）★

★出力ベースの判定器は内部データの破壊を検出できない（KY96）。★

D-2 で終端を `dbg_halt` に、UART を「記録するが判定に用いない」（§4.2）と定めた結果、
★本計画の一次判定は「完走したか」「UART が期待どおりか」しか見ていない。★
キャッシュが誤ったバイトを返しても、それが出力に現れなければ素通しになる。

これは仮想の懸念ではない。★段4〜段6 の 4 段にわたり、YUI OS の G-C1 は
M-5 = 2,010,458 で完全一致し続けながら、実際には誤返却を 3 回起こしていた★
（TKT-V7 / `phase4_ticket_ledger_v1_6.md` §7.7）。
★「変わらないこと」を安定の証拠と解釈していたが、判定器の死角だっただけである（KY99）。★

★母数を必ず出す理由★：照合が 0 件でも「MISMATCH = 0」と表示される。
これは判定器が機能していない状態と合格が区別できないということであり、
陽性対照の思想（KY91）を判定器自身に適用したものである。
本計画では ★`read_checked == 0` を INVALID として扱い、PASS としない。★

### ★4.4 新ゲート G-M（v0.3 新設）★

| ゲート | 内容 | 合格基準 |
|---|---|---|
| ★**G-M**★ | ★キャッシュ返却値と PSRAM 実体の一致★ | ★`MISMATCH == 0` かつ `read_checked > 0`★ |

★G-M は偽陽性を出さない。★書込の `cpu_ready_o` は `br_ready_i` 素通し
（`ysd8800_cache` L440-442）でポステッドではなく、`psram_ctrl` は `mem[]` 更新と
`ack` を同一サイクルで行う（`ysd8800_psram_ctrl_v0_3.sv` L165-172）ため、
★書込直後の読出でも誤検出は起きない★。ゆえにハードゲートとして扱える。

★UART 出力は撤去せず記録する。★
ただし★判定には用いない★（速度依存を判定器に持ち込まない）。

★T-2/T-3（RTL）で 819/48785 は観測されない。★

`CEN=1` ビンの作り方は `HANDOVER_CHAT153.md` §5 に従う。
★TB 側 `force` ではなく `_poc` RTL 改変を用いる理由（C-3）★：
CCR は CEN 立上りで暗黙フラッシュを起こす仕様（機能B）であり、
`force` で外部から値を変えると★立上り検出の挙動が実機と異なる★おそれがある。
段6 と同一手法を採ることで比較可能性も担保される（U-6）。

### 5.2 記録項目（C-5 反映）

`putchar` は UART TX レディ待ちのビジーウェイトを伴うため、
`cycle_count`（reset→halt）には★9 バイト分の送出待ちが含まれる。★
CEN=0/1 に共通の定数オフセットであるため★差分（削減量）は汚染されない★が、
★削減率の分母を膨らませる★ため、段6 の 46.46% と直接比較する際に僅かに不利に働く。

★P-11 により `"N="` の送出は `timer_start()` の直前であるから、
これを計測区間の始点マーカーとして使える。★

| 記号 | 記録内容 |
|---|---|
| C-total | reset → `dbg_halt` の cycle |
| ★C-first★ | reset → ★最初の UART TX（`'N'`）★の cycle |
| ★C-body★ | ★C-total − C-first ＝ Dhrystone 本体＋末尾出力の区間★。実質の計算区間 |

削減率は★C-total と C-body の両方で算出し、併記する。★

### ★5.3 実測で判明したインデックス誤り（v0.3 是正）★

v0.2 §5.2 は UART の並びを前提に `C-core = tx[4]('P') − tx[3]('\n')` としていたが、
★実測での並びは `N(0) =(1) 1(2) 0(3) \n(4) P(5) :(6) 2(7) 0(8)` であり、
正しくは `C-core = tx[5] − tx[4]` である。★

TB 側は実測 1 本目で是正済（`tb_cpu_v8e_dhry_v0_2.sv` 該当コメント）。

★教訓：承認済の計画書でも、添字を伴う定義は実測の 1 本目で必ず突き合わせる。★
KY92（同型）の再確認である。

## §6. 判定基準

### 6.1 一次判定（機能）

★以下をすべて満たすこと。★

| # | 判定 |
|---|---|
| J-1 | ★T-2・T-3 とも `dbg_halt` に到達すること★（TIMEOUT・異常終了でないこと）（C-4） |
| J-2 | ★T-2 と T-3 の UART 出力が一致すること★。期待値は `"N=10\n"` ＋ `"P:20"` の 9 バイト（P-10） |
| J-3 | ★先頭が `'P'` であること★。`'P'` は `dhrystone()` の内部自己検証の合否であり（P-8）、`'F'` なら論理が壊れている |

★J-2 は md5 を用いず生の出力で判定する。★
UART バイト多重集合 md5 の算出方法が版により異なる問題（`HANDOVER_CHAT153.md` §6-4）を
判定器に持ち込まないため。9 バイトなら目視・`diff` で足りる。

一致しなければキャッシュが論理を壊しており、★性能の議論に進んではならない。★

★N-1（推奨）の扱い★：`dbg_halt` 時のデータ領域チェックサム比較は、
J-3（内部自己検証）が既に論理正当性を担保するため★本計画では実施しない★。
ただし J-3 が `'F'` を返した場合の原因切分け手段として有効であるから、
★異常時の追加調査手段として §8 に記録する。★

### 6.2 二次判定（性能）

★本測定は「削減率が何%以上なら合格」という形の合否判定を行わない。★

理由：段7 の目的は性能目標の達成確認ではなく、
★YUI OS 起動とはアクセスパターンが異なるワークロードでの挙動の把握★である
（`HANDOVER_CHAT153.md` §3.1）。
削減率が段6（46.46%）より小さくても、それは★キャッシュの欠陥ではなく設計の性質★である。

| 観点 | 内容 |
|---|---|
| O-1 | ★フェッチ由来の削減比率が段6（約90%）からどう変わるか★ |
| O-2 | ★段4 の T7（書込→密着読出）が起動では露見しなかった★事実に照らし、新たな異常が出ないか |
| O-3 | 削減率が著しく低い場合はキャッシュ構成（8KB / 32B ライン / ダイレクトマップ）の妥当性を再検討する |

★O-3 の「著しく低い」の目安を 10% 未満とする。ただしこれは根拠のある閾値ではなく、
異常を疑い再検討に入るための★目安★であって★合否基準ではない★（N-4）。
「10% を割ったから失敗」という引用をしてはならない。★

### 6.3 ★予測との突合は段7-B に持ち越す★

段6 で用いた「emu23 ヒット率 → 予測削減 → RTL 実測」の突合は、
★emu23 側に「キャッシュ無し」の基準が無いため段7-A では実施できない★（§1.3）。
段7-B（emu23 改修）の完了後に、段7-A の実測値と突合する。
