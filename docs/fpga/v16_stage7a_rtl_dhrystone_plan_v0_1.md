## §1. 前提の確認（★本節を最初に置く理由＝KY94★）

段6 計画 v0.1 は `--cache-stats` で *h* と *f* が取れる前提で書かれたが、
実際には取得できず、実施段階で計画の作り直しが発生した
（`HANDOVER_CHAT153.md` §8.3）。本書ではこれを繰り返さないため、
★計画の記述前に前提を実源で確認し、その結果を本節に記録する。★

### 1.1 確認済の事実（2026-09-05・実源で確認）

| # | 事実 | 実源 |
|---|---|---|
| P-1 | Dhrystone バイナリは `make dhrystone` で `dhry_final.bin` として生成できる | `Makefile` L149-165 |
| P-2 | ソースは `dhry_timer.c`、ハーネスは `startup_harness23_v17.asm` | `Makefile` L90, L150 |
| P-3 | ★ハーネスは `JSR _main` の復帰直後に `HALT` する★ | `startup_harness23_v17.asm` L90-92 |
| P-4 | 本番 TB は `dbg_halt` を観測できる | `tb_cpu_v8b_prod_v0_3.sv` L240 |
| P-5 | 本番 TB は `yuios_road2.hex` を★ハードコードで★`$readmemh` する | 同 L292 |
| P-6 | 本番 TB の終端判定は UART 文字列（`"0123MD"` 部分列一致） | 同 L376-439 |

### 1.2 ★終端の定義（本計画の要）★

★段7-A の測定終端は `dbg_halt` のアサート時点の `cycle_count` とする。★

根拠：P-3 により、Dhrystone は `_main` から復帰して必ず `HALT` に到達する。
これは UART 出力の順序や速度に一切依存しない。

★この選択は段6 の M-5 判定（UART 部分列一致）より堅い。★
段6 の M-5 は TKT-U1（出力順序の入替）の影響を受け、
`CEN=1` で `M-3: 0` になる副作用を抱えていた
（`HANDOVER_CHAT153.md` 参照の段4 記録 §3.2）。
`dbg_halt` はこの種の速度依存を原理的に持たない。

### 1.3 段7-B を emu23 改修とする根拠（記録）

emu23 の課金式は 4 分岐（読みヒット / 読みミス / 書きヒット / 書きミス）のみで
（`emu23_v2_15.c` L89-93）、★「キャッシュを持たない CPU が PSRAM を直接叩く」課金経路が存在しない。★

- `cache_enable==0` は課金 0 ＝ **理想メモリ**であり、RTL の `CEN=0` とは別物
- `--cache-size` の最小値は `--cache-line` と同値（同 L618）であり、
  1 ライン構成にしても★32B ライン内の連続アクセスはヒットしてしまう★。
  段6 実測で *h_f*=0.9981 であったから、フェッチはほぼヒットのまま残り、
  「全ミス近似」にならない

したがって emu23 単体での ON/OFF 比較には改修が必要であり、
2026-09-05 にユーザー決定で改修（案δ）を採用した。

## §4. 新規 TB の設計（S-1）

本番 TB からの差分は★次の 3 点のみ★とする。差分を最小に保つことで、
本番 TB で検証済の CDC・PSRAM・契約監視をそのまま流用する。

| # | 差分 | 内容 |
|---|---|---|
| D-1 | ロード対象 | `$readmemh("yuios_road2.hex", …)` → `$readmemh("dhry_final.hex", …)` |
| D-2 | 終端判定 | UART 部分列一致（M-1〜M-5）を撤去し、★`dbg_halt` 立上りで `cycle_count` を記録して `$finish`★ |
| D-3 | SD カードモデル | Dhrystone は SD を使わないため、モデルは接続したまま★参照しない★（撤去はしない＝差分最小） |

★UART 出力は撤去せず、参考情報として記録する。★
Dhrystone の結果（Dhrystones/sec 等）が UART に出るなら論理的正当性の確認に使えるため。
ただし★判定には用いない★（速度依存を判定器に持ち込まない）。

## §6. 判定基準

### 6.1 一次判定（機能）

★T-2 と T-3 の UART 出力（Dhrystone の実行結果）が一致すること。★
一致しなければキャッシュが論理を壊しており、性能の議論に進んではならない。

### 6.2 二次判定（性能）

★本測定は「削減率が何%以上なら合格」という形の合否判定を行わない。★

理由：段7 の目的は性能目標の達成確認ではなく、
★YUI OS 起動とはアクセスパターンが異なるワークロードでの挙動の把握★である
（`HANDOVER_CHAT153.md` §3.1）。
削減率が段6（46.46%）より小さくても、それは★キャッシュの欠陥ではなく設計の性質★である。

得られた値は次の観点で解釈する。

| 観点 | 内容 |
|---|---|
| O-1 | ★フェッチ由来の削減比率が段6（約90%）からどう変わるか★。Dhrystone は関数呼出が多く局所性の性質が異なる |
| O-2 | ★段4 の T7（書込→密着読出）パターンが起動では露見しなかった★事実に照らし、新たな異常が出ないか |
| O-3 | 削減率が著しく低い（例：10% 未満）場合は、キャッシュ構成（8KB / 32B ライン / ダイレクトマップ）の妥当性を §9 で再検討する |

### 6.3 ★予測との突合は段7-B に持ち越す★

段6 で用いた「emu23 ヒット率 → 予測削減 → RTL 実測」の突合は、
★emu23 側に「キャッシュ無し」の基準が無いため段7-A では実施できない★（§1.3）。
段7-B（emu23 改修）の完了後に、段7-A の実測値と突合する。
