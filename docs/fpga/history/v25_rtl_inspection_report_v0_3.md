## 2. 段0.5′ 実測結果

### 2.1 構成（C-0、v0.1既報）

実測構成＝C-0（`WBUF_EN=0`／`PHY_EN=0`／`BAUD_EN=0`）。M-1〜M-5・G-Mはベースラインと完全一致（詳細は変更なし、v0.1参照）。

### 2.2 ★C-2構成（実機構成）実測 — W-2/W-3是正版★

**W-2是正：C-0とC-2でM-1〜M-5が完全一致した理由**

v0.2での説明（「TBが`uart_tx_valid_o`のバイトレベル信号のみを監視しているから」）は**誤りでした**。ご指摘の通り、これはTKT-V12で一度誤って導出され、review v1.7のC-36で是正済みの推論と同型の誤りです。

正しい理由（`v24_tktv12_uart_phy_design_v0_6_5.md` §17.5 C-36、実測11,422サイクル/文字 ≫ 1文字時間4,170サイクルに基づく）：

> **起動部の出力はUART律速ではなく、CPU（スケジューリング）律速である。`emit-char`がTX_READYをポーリングする時点で、UARTの送信完了（PHY_EN=1時4,170サイクル／PHY_EN=0時4,167サイクル）はとうに終わっている。したがって両者の3サイクル/バイトの差は、ソフトウェアからは一切観測されない。** この関係はUART律速の連続出力区間（将来のバルク転送等）でのみ表面化する。

C-36自体は本点検が新たに導いたものではなく、TKT-V12で既出の知見です。**同じ実験（C-0とC-2の起動シーケンス比較）を、既存の知見を確認せずに独自に再実施し、既に誤りと分かっている理由づけを再現してしまった**点は、原則147が求める「検証手段を計画に載せる前に一次資料で確認する」の観点から反省点です。

**W-3是正：C-2構成が実際に効いていたことの正の証拠**

v0.2の時点では、C-2実行ログに`$error`が出ていたことを見落として報告していました。再確認したところ、以下が判明しました。

1. **当初のC-2実行ログ（`sim_phy1.log`）に`$error`が出ていた**：
   ```
   ERROR: ysd8800_ysd8001_v0_3.sv:470: YSD8001: rxd_i is X/Z after reset (PHY_EN=1) -- TB must drive rxd_i (review v1.3 R-10)
   ```
   点検用TBが`uart_rxd_i`ポートを未接続のまま`PHY_EN=1`にしていたため、RTL自身の契約違反検出（`ysd8001` L466-470）が正しく発火していました。M-1〜M-5・PROD PASSの表示に紛れて見落としており、「見えているバグは先に潰す」の原則に反していました。お詫びして訂正します。

2. **是正**：点検用TBの派生版`tb_cpu_v8b_prod_v0_5_inspect_phy1_poc.sv`を新設し、`uart_rxd_i`を`1'b1`（UARTアイドル値）に結線。再実行した結果：
   - `$error`は発生せず（是正確認）
   - **`uart_txd_o`のトグル回数＝158回**（`always @(posedge cpu_clk)`で階層参照カウント）を新たに計測し、物理シリアライザが実際に動作していることを直接確認
   - M-1〜M-5・G-M・PROD PASSは変わらず一致

| 項目 | 是正後C-2実測値 |
|---|---|
| M-1〜M-5 | 7/74,512/222,994/320,156/3,754,937（一致） |
| `$error`（rxd_i） | ★なし（是正確認）★ |
| `uart_txd_o`トグル数 | **158回**（新規計測・正の証拠） |

**実行範囲の明記**：本C-2実測はboot単独シナリオ（M-5＝自動事後診断列"0123MD"検出まで）であり、コマンド入力は含まない。`PHY_EN=1`時は疑似ポート`rx_valid_i`が無視される（`ysd8001` L123・L222）ため、本テストではRX側の物理受信動作は検証していない。

**主根拠の明記（Info I-1対応）**：C-2構成でコンソールが実際に成立するかについての主たる根拠は、本点検の追加実測ではなく、**TKT-V12のM-10（専用TB`tb_cpu_v8b_prod_v0_6_1_phy_poc.sv`、本番カーネルでの"YUI> "起点の対話・§17.2）**である。本点検のC-2実測はこれを補強する副次的確認と位置づける。

### 2.3 MMIOログ・`--strict-mmio`（W-6対応・シナリオ分離）

★v0.2までの誤り（W-6(a)是正）★：段0.5′のRTL動的トレース（`mmio_trace.log`）と、emu23の`--strict-mmio`確認は**別々のシナリオ**でした。

- **RTL動的トレース**：boot単独（TBは`uart_rx_valid_i=1'b0`固定、ユーザー入力なし）
- **emu23 `--strict-mmio`確認**：boot＋`ver`／`ls`をUART入力として供給（emu23単体の別実行）

両者を「boot+ver+lsシナリオ」と一括りにしていたのは誤りです。詳細区分は点検記録表v0.2のC-002／C-004を参照。

**1件差（4,876 vs 4,875）の原因確定（W-6(b)）**：最終アクセス（cycle=3,754,937、M-5検出と同一サイクル）を除くと4,875件に一致。既存`mmio_acc`カウンタ（ノンブロッキング代入`<=`）は同一サイクルの`$display`実行時点で更新前の値を読むのに対し、新設カウンタ（ブロッキング代入`=`）は即時反映される、という**代入方式の違いによる境界サイクルの表示タイミング差**であり、両カウンタとも機能的には正しい。
