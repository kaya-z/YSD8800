## §3.1-R 挿入位置の前提の訂正

### 3.1-R.1 ★崩れた前提★

v0.2 §3.1 は、採用理由 2 として次を掲げた。

> 「cache の内部にも手を入れない。TKT-V7 の修正直後であり、`fill_*` 系の状態に隣接した改修は避ける」

★この方針自体は妥当だが、「下流に置けば cache に触れずに済む」という帰結は誤りであった。★

理由は、★cache と psram_ctrl が wbuf を**迂回して直結**している経路が存在するためである。★

| 信号 | 向き | 実装位置 | wbuf 経由 |
|---|---|---|---|
| `req`/`we`/`addr`/`wdata` | cache→下流 | `membus_v0_13` L557-567 | ★経由する★ |
| `burst_len` | cache→psram_ctrl | 同 L531 / L626 | ★迂回（直結）★ |
| `beat_valid` | psram_ctrl→cache | 同 L534 / L627 | ★迂回（直結）★ |
| `psram_rdata` | psram_ctrl→cache | 同 L535 | ★迂回（直結）★ |

★wbuf は「要求経路」だけを横取りしたが、「フィルのデータ経路」はそのまま cache と psram_ctrl を結んでいた。★

### 3.1-R.2 ★一般化された教訓★

> ★モジュールを直列に挿入しても、挿入点を迂回するサイドバンド経路がある限り、
> 上流モジュールの内部前提からは切り離されない。★

挿入位置の妥当性は「要求経路のどこに入るか」ではなく、
★「挿入によって、下流の要求発行者が何個になるか」★で判定すべきであった。
wbuf 挿入により、psram_ctrl から見た要求発行者は ★1 個（cache）から 2 個（cache／wbuf ドレイン）へ増えた。★

## §5.2-R フィルとの関係（真因・実源確認済 2026-09-20）

### 5.2-R.1 v0.2 の記述のどこまでが正しいか

v0.2 §5.2 は次のように述べた。

> 「フィル開始は `fill_req` であり `up_rd_i` として現れる。したがって §5.1 の対策がそのままフィルにも効く。特別扱いは不要。」

★この記述は cpu_clk 側については正しい。★

実源確認（`membus_v0_13` L559 / `cache_v0_6` L517）により、
`up_rd_i = cbr_rd = br_rd_o = ccr_cen_i ? (fill_req | fill_active_r) : cpu_rd_i` であり、
★フィル中は `upstream_idle=0` となって wbuf はドレインを開始しない★（`wbuf_v0_2` L163-167）。

したがって ★「フィルとドレインが psram_ctrl 上で同時に重なる」ことは無い。★
`burst_len=32` がラッチされている間の要求は必ず cache 由来であり、
★ドレイン書込が `blen_r≠1` のために破棄される事故（`psram_ctrl` L165）は発生しない。★

> ★本節は 2026-09-20 に一度「書込消失が起きる」と誤って報告した件の訂正記録である。★
> ★要求経路の直結だけを見て排他制御を確認せずに断定した。KY34（実源優先）の不徹底。★

### 5.2-R.2 ★崩れていたのは「フィルの終了時刻」の前提である★

v0.2 が暗黙に置いていたのは次である。

> ★暗黙前提 P-T：cpu_clk 側でフィルが終わった時点で、psram_clk 側のフィル状態も終わっている。★

★これが偽である。★

```
cpu_clk 側 : fill_active_r ↓ → cbr_rd ↓ → HOLD_GRACE(3cyc) → ドレイン書込 req 発行
psram_clk側: fill_sel ↓ ─[2FF 同期]→ fill_gate_ps ↓        ★2 psram cyc 遅れる★
             fill_armed_r は !fill_gate_ps でのみクリアされる（cache_v0_6 L456-461）
```

★この「残存窓」にドレイン書込が psram_ctrl へ到達すると、次が起きる。★

| # | 事象 | 実装位置 |
|---|---|---|
| 1 | `blen_r=1` のため ★メモリへの書込自体は正常に成立する★ | `psram_ctrl_v0_3` L165 |
| 2 | ★`beat_valid` が立つ（`we` を問わない）★ | 同 L169 |
| 3 | cache 側は `fill_gate_ps=1` かつ `fill_armed_r=1` のため `beat_take` 成立 | `cache_v0_6` L409 |
| ★4★ | ★`data_ram[{idx_use, beat_no}] <= psram_rdata_i` で直前ラインを汚染★ | 同 L486 |
| ★5★ | ★`fill_armed_r=1` のため L497 のアサーションは発火しない＝無音破壊★ | 同 L497-499 |

★破壊されるのは PSRAM ではなくキャッシュラインである。★
★実測で MISMATCH が全て `wbv=0`（バッファ非保持アドレス）であったことと整合する。★

### 5.2-R.3 前提の再掲（cache 側が明文化していたもの）

`cache_v0_6.sv` L490-494 は前提を明記していた。

- P-A：バースト間に `beat_valid=0` の期間が存在する
- ★P-B：`fill_gate_ps` 中に非フィルのバーストが出ない★

★破れたのは P-B である。★
★そして P-B 違反を検出するはずのアサーションは、`fill_armed_r` を条件に含めていたため沈黙した。★
（アサーション自体が「違反者は必ず未武装で来る」という前提に立っていた）

### 5.5.3 ★採用案D の内容★

`ysd8800_psram_ctrl_v0_4.sv` を起こし、PS_BUSY の 1 行のみを変更する。

```systemverilog
// v0.3: beat_valid <= 1'b1;            // we を問わず立つ
// v0.4: 書込アクセスではビートを出さない
        beat_valid <= ~we;
```

PS_BURST 側（L193-195）は★変更しない★。
理由：バースト書きは v0.3 M-3 で未サポートと明記され `blen_r==1` に限定済みであり、
★PS_BURST に入るのは読出だけである★（`psram_ctrl_v0_3` L160-164）。

### 5.5.4 ★案D が安全である根拠★

| # | 根拠 |
|---|---|
| ★1★ | ★読出経路の `beat_valid` は一切変わらない。★工程②-B の全測定（CEN=0/1・フィル・単バイト読出）はビット単位で不変のはず |
| ★2★ | 書込時の `beat_valid` を利用している受け手は ★cache の I-2 フィルゲートのみ★であり、そこでは「弾く対象」として扱われている（`cache_v0_6` L382-383）。★立たなくなって困る受け手が存在しない★ |
| 3 | `ack` は `beat_valid` と独立に PS_BUSY で立つ（L174）。★書込完了のハンドシェイクは影響を受けない★ |
| 4 | cdc_bridge は `ack` の立上りを見る（L196-198 のコメント）。★`beat_valid` を見ていない★ |

★根拠1・2 は実装確認済だが、★★★根拠1 は W-0 再測定で実証すること（§7.6）。★★★
