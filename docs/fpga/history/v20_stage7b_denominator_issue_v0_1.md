## §1. 背景

### 1.1 段7-B の目的

段7-C で得た書込ストール率 **13.2%**（YUI OS・CEN=1）が
事前定義の近傍帯（12〜18%）に該当したため、ライトバッファ前倒しの判定が保留された。
段7-B はこの保留を解消するための工程である。

### 1.2 案D（1ビン法）の合格条件

計画書 v0.5 §5.1.6.1 は、モデル妥当性ゲート（U-4）を次の2式で判定すると定める。

```
b_measured = (stall_rd + stall_wr) / N        → 合格条件1: b_measured + 1 が 4.0〜6.0
a_measured = (C_total − stall_rd − stall_wr) / I  → 合格条件2: 1.0 以上・≒18 として説明可能
```

- `C_total`／`stall_rd`／`stall_wr` … **RTL 側**（`tb_cpu_v8e_dhry_v0_3`・Dhrystone -O0・CEN=0）
- `N`（アクセス回数）／`I`（命令数） … **emu23 側**

計画書 v0.5 §5.1.6 の表は「Dhrystone -O0 CEN=0 で完結」と記すのみで、
**emu23 側をどのオプション条件で走らせた値を `N`／`I` とするかは書かれていない。**

### 2.3 原因の推定（★未検証・仮説★）

Dhrystone は**自己タイミング型**のベンチマークであり、
タイマ割込による計測区間の打切り、および UART ビジーウェイトを含む。

課金が重い走行ほど、規定時間内に到達できるプログラム地点が変わる。
すなわち **3つの走行は「同じプログラムの同じ区間」を実行していない。**

これは計画書 v0.5 §7.1 K-10 が既に警告している事象そのものである。

> ★K-10：系をまたぐ値を渡すときは、渡す直前に単位を宣言する。
> 揃えるべきは時間軸の値ではなく **プログラム地点** である★

★本件は「単位」ではなく「区間」の不一致であるが、K-10 の後段（プログラム地点で揃える）に該当する。★

★なお本節は仮説である。確定させるには §5 Q-3 の確認が要る。★

## §3. 判定への影響（★これが依頼の核心★）

### 3.1 影響の大きさ

`a_measured` の分母 `I` を (a) 48,785 とするか (c) 56,127 とするかで、
**同じ RTL 実測値に対して `a_measured` が約 15% 変わる。**

参考として、RTL 側 `C_total = 1,070,369`（Dhrystone -O0 CEN=0・段7-A 実測）に対し、
仮に `stall_rd + stall_wr = S` とすると：

```
I = 48,785 のとき : a = (1,070,369 − S) / 48,785
I = 56,127 のとき : a = (1,070,369 − S) / 56,127     ← 約 13% 小さく出る
```

合格条件2 は「≒18 として説明可能」であるから、
★分母の選び方だけで合否が動きうる。★

`b_measured` はさらに影響が大きい。分母 `N` が 333,846 と 234,285 では **1.42 倍**の開きがあり、
合格条件1 の判定帯（`b + 1` が 4.0〜6.0）を**分母の選択だけで跨ぐ**。

### 3.2 なぜ勝手に決めてはならないか

- 計画書 v0.5 §7.1 **K-3「判定基準を測定後に決める」**に該当する
- §5.3 の測定無効条件は「合格条件を満たさない」場合を無効と定めるが、
  ★分母の定義が揺れている状態での不合格は、モデルの不合格ではない★
  （K-9 と同型：入力側の問題をモデルの正否と読み違える危険）

## §5. ★ご検討いただきたい事項★

### Q-1（主）：案D の `N`／`I` はどの走行の値を採るべきか

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| ★案(a)★ | ★`--cache-stats` 単独（`charge_enable=0`）の `I=48,785`／`N=333,846`★ | ★課金しないため `cycles` が命令数と一致し、区間が RTL の CEN=0 走行と最も近いと推定される★。HANDOVER §6 で既に採取済 | ★`N=333,846` が測定 B/A（24万台）と大きく違う理由が未解明★ |
| 案(b) | 測定 A（`--no-cache-model`）の `I=56,127`／`N=234,285` | RTL の CEN=0 と**課金モデルが対応する**走行である | 区間が RTL と一致する保証はない |
| ★案(c)★ | ★`-b ADDR` でプログラム地点を揃えて再取得する★ | ★K-10 の本来の解。区間の一致を構造的に保証できる★（計画書 §5.1.6.3 に「M-1 の解でもあった」と記録済） | 手順が増える。打切り地点の選定が要る |

★作成者の現時点の所見★：案(c) が原理的に正しいが、
案(a) で `N` が 1.42 倍違う理由（Q-3）が説明できれば案(a) でも足りる可能性がある。

### Q-2：`b_measured` の分母 `N` は「アクセス回数」でよいか

段7-C のストールは **RTL のクロック数**である。
一方 emu23 の `N` は **`mem_charge()` の呼出回数**（1 バイト単位）である。

★16bit アクセスは呼出側がバイト単位で 2 回呼ぶ（計画書 §3.2.1・実源 L1567-1568／L1731-1732）。
RTL 側も 8bit バスの 2 トランザクションであるため対応は取れている★とされているが、
★RTL のストールカウンタが「トランザクション単位」で数えているか「クロック単位」で数えているかは未確認★である。
後者なら `b_measured` は `(lat − 1)` ではなく別の量になる。

これは U-11 と併せて確認すべき事項と考えるが、ご見解を伺いたい。

### Q-3：`N` が走行条件で 1.42 倍変わる理由の確認方法

`--cache-stats` 単独（333,846）と `-mc` 併用（242,665）で `N` が大きく違う。
★仮説は「自己タイミング型ベンチのため実行区間が変わった」であるが未検証である。★

確認案：
1. `-b ADDR`（指定アドレス到達で打切り）で両条件を同一地点に揃え、`N` が一致するかを見る
2. `--trace-addr` で両条件のトレースを取り、先頭 N 行が一致するかを見る（区間の分岐点が特定できる）

★ただし 2 は段6 実績で 1.46GB／20秒のトレースが出るため、`agg_trace_v1_0.py` の流用が前提となる。★
