## §1. 論点1 — ミス時のライン先頭アドレス生成

### 1.1 事実（実源確認済）

`ysd8800_cdc_bridge_v0_4.sv` ★**L120**★（v0.1 は L122 と誤記・E-1）：

```systemverilog
assign psram_addr = cpu_phys_addr;   // ★素通し★
```

★ブリッジはアドレスを一切加工しない。★
また ★**L119**★（v0.1 は L120 と誤記・E-1）：

```systemverilog
assign req_level = (cpu_mem_rd | cpu_mem_wr) & ~suppress_r;
```

★要求の発火も `rd`/`wr` から直接生成される。★

### 1.2 帰結

設計書 §7.2 の「ライン先頭アドレス（下位5ビット=0）で発行」を実現するには、
★**キャッシュ段が下流へ出す `br_phys_addr_o` を丸める**★以外に経路がない。
ブリッジ側の改造は不要である（改造してはならない：①.5 の A-2q 成果を壊す）。

### 1.3 ★決定 D-C1（v0.2 で全面是正・M-1 対応）★

#### ★v0.1 の誤り（取り消し）★

~~```systemverilog~~
~~assign br_phys_addr_o = (ccr_cen_i & fill_active)~~
~~                      ? {cpu_phys_addr_i[PHYS_AW-1:5], 5'b00000}~~
~~                      : cpu_phys_addr_i;~~
~~```~~

★**上式は誤りである。2つの欠陥があった。**★

| # | 欠陥 | 実源根拠 |
|---|---|---|
| ① | `fill_active` が★登録信号★（§3 で `fill_active_r`）なら、1 になるのは cycle N+1。しかし `cdc_bridge_v0_4` **L119** の `req_level` は★**組合せ**★であり、`mem_rd` を出した瞬間に req が立つ。`psram_ctrl` は req 受理サイクル（**L139-156**）で `blen_r` をラッチするため、★**cycle N の時点では `fill_active_r=0` → `blen_r=1` がラッチされ、バーストにならない**★ | `cdc_bridge_v0_4.sv` L119／`psram_ctrl_v0_3.sv` L139-156 |
| ② | ★`burst_len` の駆動条件が未記述だった★。アドレス丸めだけ規定しても、`burst_len` が 1 のままでは 1 バイトしか転送されない | 設計書 §1.2（配線のみ追記・切替条件は段3 の宿題として残っていた） |

> ★①の帰結が厄介な点★：`blen_r=1` でも★1 バイトは正しく返る★ため、
> 「なんとなく動いてしまう」。ラインフィルだけが成立せず、
> 性能が出ないという形でしか現れないため発見が遅れる。
> ★①.5 の A-2 相殺問題（`req_hold` が 1 サイクルを食う）と同型の「1 サイクルのずれ」である。★

#### ★v0.2 是正版★

```systemverilog
// ★組合せ★でフィル開始を検出する（設計書 §7.1 の fill_req を使う）
wire fill_req  = ccr_cen_i & miss & cpu_rd_i;          // 組合せ・開始の検出
wire fill_sel  = ccr_cen_i & (fill_req | fill_active_r); // 開始 or 継続

// ★アドレス丸めと burst_len は【同一条件】で切り替える★
assign br_phys_addr_o = fill_sel ? {cpu_phys_addr_i[PHYS_AW-1:5], 5'b00000}
                                 : cpu_phys_addr_i;
assign burst_len_o    = fill_sel ? BLEN_W'(32) : BLEN_W'(1);
```

| 条件 | アドレス | `burst_len` | 根拠 |
|---|---|---|---|
| `CEN=0` | ★素通し★ | ★1★ | ★G-0 の成立条件★。1ビットでも変えると落ちる |
| `CEN=1`・ヒット | 素通し | 1 | 下流へ要求を出さない |
| `CEN=1`・ミス（cycle N） | ★丸め★ | ★32★ | `fill_req`（組合せ）が即座に立つ |
| `CEN=1`・フィル継続 | ★丸め★ | ★32★ | `fill_active_r` が保持する |

> ★`fill_req`（組合せ・開始の検出）と `fill_active_r`（登録・継続の保持）は
> **責務を分離**する★（kaizen「変数の責務は1つに絞る」）。
> 片方だけでは成立しない：`fill_req` だけでは 2 サイクル目以降に丸めが外れ、
> `fill_active_r` だけでは初回に間に合わない。

> ⚠️ ★`CEN=0` の経路に丸めまたは `burst_len=32` が漏れ込むことが
> 段3 最大の G-0 破壊要因である。★実装後、`CEN=0` 固定で G-0 を回して確認すること。

#### ★検証項目（M-1 対応・必須）★

★`tb_cache_core_poc` で `psram_ctrl` 内部の `blen_r` を階層参照し、
ミス発生時に ★**32 になっていること**★ を観測する。★
`blen_r=1` のままでも 1 バイトは正しく返るため、
★出力バイトの正しさだけでは本欠陥を検出できない★。

## §2. 論点2 — `fill_hit_byte_r` のキャプチャとドメイン

### 2.1 当初の懸念

設計書 §7.2 2) は
「`beat_cnt == req_offset_r` の beat を `fill_hit_byte_r` にキャプチャ」
と規定する。ここで各信号のドメインは：

| 信号 | ドメイン |
|---|---|
| `beat_valid` / `psram_rdata` / `beat_cnt` | ★`psram_clk`★ |
| `req_offset_r`（req 受理時にラッチ） | ★`cpu_clk`★ |
| `fill_hit_byte_r` の読み手（`mem_rdata`） | ★`cpu_clk`★ |

比較 `beat_cnt == req_offset_r` は★**ドメインを跨ぐ**★。
設計書 §1.3 は「CDC が発生する箇所は1つだけ」と述べるが、
★この比較は数に入っていない★。

### 2.2 ★実源確認で判明した事実（懸念の解消）★

`ysd8800_psram_ctrl_v0_3.sv` を精読した結果、
★**懸念は成立しない**★ことが判明した。根拠は3点。

**(a) `ack` は最終ビートまで立たない（L194-201）**

```
PS_BURST: ★ackはここでは触らない(0のまま維持)★
          if (beat_cnt == (blen_r - 1)) ack <= 1'b1;  // 最終バイトで初めて立てる
```

**(b) `cpu_mem_ready` は `ack` 立上りからさらに 2FF 遅れる**

`cdc_bridge_v0_4.sv` L139：`suppress_r <= ack_sync[0] & ~ack_sync[1];`
`ack` → `ack_sync[0]` → `ack_sync[1]`／`suppress_r` と
★最低 2 cpu cyc（= 16 psram cyc）遅れて `ready` が返る★。

**(c) ★v0.2 是正（M-2）★ `req_offset_r` の余裕は「無限」ではなく有限である**

~~req を出した後、CPU は `ready=0` で待たされる（設計書 §7.5）。~~
~~★CPU が次のアドレスを出せないため、`req_offset_r` は準静的である。★~~

★上記 v0.1 の記述は根拠として不正確であった。★
`req_offset_r` は `cpu_clk` posedge でラッチされる登録信号であり、
値が確定するのは ★cycle N+1★。一方 `psram_ctrl` が req を受理するのは
★cycle N の開始から約 2 psram cyc 後★（`cdc_bridge` L119 が組合せのため）。
すなわち ★**`req_offset_r` の確定は req 受理より「後」**★ である。

★正しい根拠は「使われるタイミングとの差」である：★

| 事象 | req 受理からの時間 | 実源根拠 |
|---|---|---|
| `req_offset_r` 確定 | ★約 8 psram cyc★（＝1 cpu cyc・クロック比 8:1） | — |
| 最初のビート（`beat_cnt=0`）が出る | ★`LATENCY_NORMAL` psram cyc★ | `psram_ctrl_v0_3.sv` L148-149（`-2` 補正込み） |

★**余裕 = `LATENCY_NORMAL − 8` psram cyc**★

| `LATENCY_NORMAL` | 余裕 | 判定 |
|---|---|---|
| 12（本番） | ★4 psram cyc（125 ns）★ | ✅ 成立 |
| 7 | 0 未満 → ★**成立しない**★ | ⚠️ |
| 5・4 | ★**成立しない**★ | ⚠️ |

> ⚠️ ★**重大な申し送り**★
> ★`LATENCY_NORMAL` を 8 以下に下げると本前提は崩れる。★
> これは①.5 で得た量子化構造（LAT を下げるとビンが下がる）と直結しており、
> ★将来の PSRAM 高速化と正面から衝突し得る★。
> G-0 の LAT=5 ビンは `CEN=0` のため本経路を通らず**検出できない**ことに注意。
> LAT を下げる改善を行う際は、★本節を必ず読み直すこと★。

### 2.3 ★結論★

| 懸念 | 判定 | 根拠 |
|---|---|---|
| `req_offset_r` を `psram_clk` 側で使う | ★**安全（ただし条件付き）**★ | ★v0.2 是正（M-2）★ 余裕は ★`LATENCY_NORMAL − 8` psram cyc★。LAT=12 で 4 cyc（125 ns）。★`LATENCY_NORMAL ≤ 8` では成立しない★ |
| `fill_hit_byte_r` を `cpu_clk` で読む | ★**安全**★ | (a)(b) 読み手が値を使うのは `ready` 成立時。最終ビート書込から★最低 16 psram cyc★の余裕がある |

★**これは「調停で解く」のではなく「タイミング上そもそも競合しない」構造である。**★
設計書 §1.5 が DPB 競合を
「競合しても結果が使われない構造」で消したのと★同じ思想★である。

### 2.4 ★決定 D-C2★

`req_offset_r` は ★`cpu_clk` でラッチし、`psram_clk` 側から参照してよい★。
★2FF 同期器を挿入しない。★

> ★2FF を入れてはならない理由★
> `req_offset_r` は 5 ビットの**多ビット信号**である。
> 多ビット信号に 2FF 同期器を各ビット独立に掛けると、
> ビット間スキューで★中間値が出る★（古典的な多ビット CDC の誤り）。
> 準静的な値に同期器は不要であり、掛けるほうが危険である。

> ⚠️ ★STA 制約が必要（v0.2 是正・N-1）★
> `req_offset_r` → `psram_clk` 側の比較器、および
> `fill_hit_byte_r` → `cpu_clk` 側の読出しは ★非同期パス★である。
>
> ★**`set_false_path` ではなく `set_max_delay` を使うこと。**★
> `set_false_path` は「タイミングを一切検証しない」宣言であり、
> ★配置配線が余裕を超える遅延を作っても警告が出ない★。
>
> | 経路 | ★余裕★ | 推奨制約 |
> |---|---|---|
> | `req_offset_r` → `psram_clk` 比較器 | ★`LATENCY_NORMAL − 8` psram cyc＝**4 cyc / 125 ns**（LAT=12 時）★ | `set_max_delay 125` |
> | `fill_hit_byte_r` → `cpu_clk` 読出 | ★16 psram cyc＝**500 ns**★ | `set_max_delay 500` |
>
> `cdc_bridge_v0_4` **L150** の `cpu_mem_rdata = psram_rdata`
> （★既に同種の非同期データパスであり STA 制約必須と明記済み★）と同型。
> → ★Step 8-Impl の制約ファイルに、**制約種別・値・根拠（余裕サイクル数）**
> まで含めて追記すること（申し送り）★

## §3.5 ★M-3 対応：段3 の書込ライン無効化（暫定措置）★

### 3.5.1 問題

★段3 を「読み出しのみ」とすると、`CEN=1` で G-1 が**必ず失敗する**。★

```
① アドレス A を読む → キャッシュにライン充填
② アドレス A に書く → PSRAM は更新されるが ★キャッシュは古い値のまま★
③ アドレス A を再度読む → ★キャッシュヒットして古い値が返る★
```

YUI OS は Forth のデータスタック・変数領域・TCB へ
★書いた直後に読む★動作を絶えず行うため、確実に露見する。

★危険なのは FAIL の性質である。★
これは「実装ミス」ではなく ★**工程分割そのものに起因する仕様上の不整合**★
であり、★原則136（判定器を疑う）を適用しても原因に辿り着かない★。
②-A' で3チャットを費やしたのと★同じ構図を自ら作り込む★ことになる。

### 3.5.2 ★決定 D-C4（M-3 推奨案 a を採用）★

★段3 に「書込時のライン無効化」を入れる。★

```systemverilog
// 段3 暫定措置: 書き込みは常にキャッシュラインを無効化する。
//   保守的だが★コヒーレント★であり、CEN=1 で G-1 が成立する。
//   ★段4 でこれを「該当バイトを更新」（ライトスルー）に置換する。★
if (ccr_cen_i && cpu_wr_i && hit) valid_r[index] <= 1'b0;
```

| 案 | 判定 | 理由 |
|---|---|---|
| ★(a) 書込ライン無効化★ | ★**採用**★ | ★1行で済み★、段4 への移行が「無効化 → 更新」の★単一置換★になる。段3 で G-1 を通せば、段4 の FAIL はライトスルー実装の問題に限定できる |
| (b) G-1 を段4 へ送る | 不採用 | システムで一度も動かさないまま段4 へ進むため切り分け範囲が広がる |
| (c) 段3 に書込ヒット更新を含める | 不採用 | 1変更1検証に反する |

> ★教訓：段分けの各段は「それ単体で意味のある状態」になっていること。★
> 分割自体は正しくても、★中間状態の非コヒーレンシが未定義★だと
> ゲートが原因不明の FAIL を出す。
