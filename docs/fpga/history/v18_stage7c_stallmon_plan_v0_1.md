## 2. 測定の定義（★結果を見る前に確定させる★）

### 2.1 観測点

★観測点は CPU 側バス（TB トップ階層の `mem_rd` / `mem_wr` / `mem_ready`）とする。★

**根拠**：キャッシュ出力の `cpu_ready_o` は `ysd8800_v5_membus` を通って CPU に届くため、
`cpu_ready_o` が低い期間と CPU が実際に停止している期間は一致する保証がない。
★TKT-V7 §4.2.1 で観測点を物理側へ寄せた判断と同じ論点である。★

実源確認（本チャットで実施済・KY34）：

| 信号 | 所在 | 確認 |
|---|---|---|
| `mem_rd` / `mem_wr` / `mem_ready` | `tb_cpu_v8e_dhry_v0_2.sv` L139-141（TB トップの `logic`） | ✅ 実在 |
| 同上 | `tb_cpu_v8b_prod_v0_3_mon_poc.sv` L130 付近・L236/L249 | ✅ 実在 |
| `irq0_fire_count` | `tb_cpu_v8e_dhry_v0_2.sv` L425 / L474-482 | ✅ ★Dhrystone 側は実装済★ |
| 同上 | YUI OS TB | ❌ ★未実装。本計画で追加する★ |

### 2.2 積算の切り分け（3分類・排他）

`cpu_clk` の posedge ごとに、`cpu_rst_n` が真のとき次を積算する。

| 分類 | 条件 | カウンタ | 意味 |
|---|---|---|---|
| ★書込ストール★ | `mem_wr && !mem_ready` | `stall_wr` | ★ライトスルーの代償（本命）★ |
| 充填ストール | `mem_rd && !mem_ready` | `stall_rd` | ミス時のラインフィル待ち |
| 待ちなし | `(mem_rd \|\| mem_wr) && mem_ready` | `bus_ack` | 即応 |

★`mem_rd` と `mem_wr` が同時に立つことは無い前提である。★
この前提自体を検証するため、`mem_rd && mem_wr` を `bus_both` として別途計数し、
★0 でなければ本測定は無効とする（判定器自身の陽性確認・原則136）。★

### 2.3 母数の定義（★KY94 を踏まないため先に決める★）

| 記号 | 定義 |
|---|---|
| ★`C_total`★ | ★リセット解除から終端（Dhrystone=`dbg_halt` / YUI OS=M-5 検出）までの総 `cpu_clk` サイクル数★ |
| 書込ストール率 | `stall_wr / C_total` |
| 充填ストール率 | `stall_rd / C_total` |

★母数は `C_total` とする。「バスアクセスがあったサイクルのみ」を母数にすると、
CPU 全体に対する影響度が分からなくなるため採用しない。★
なお参考値として `stall_wr / (stall_wr + stall_rd + bus_ack)`（バス占有中の内訳）も併記する。

## 3. 測定マトリクス（4ビン）

| ビン | ワークロード | ビルド | CEN | TB | 終端 |
|---|---|---|---|---|---|
| B-1 | Dhrystone | -O0 | 0 | `tb_cpu_v8e_dhry_v0_3` | `dbg_halt` |
| B-2 | Dhrystone | -O0 | 1 | 同上 | `dbg_halt` |
| B-3 | YUI OS | — | 0 | `tb_cpu_v8b_prod_v0_4_mon_poc` | M-5 |
| B-4 | YUI OS | — | 1 | 同上 | M-5 |

★ビルドは -O0 に固定する。-O0 が絶対ゲートの条件だからである（HANDOVER155 §4.2）。
-O1 は本計画の対象外とする。★

### 3.1 ★陽性対照（KY91）★

★B-1／B-3（CEN=0）ではキャッシュが無効であり、全アクセスが PSRAM に出る。
したがって `stall_wr + stall_rd` が支配的になるはずである。★
★CEN=0 で書込ストールがほぼ 0 と出た場合、それはモニタが機能していない証拠であり、
測定結果ではなくモニタを疑う。★

## 4. 判断基準（★結果を見てから解釈を決めない：C-1★）

### 4.1 段7-C（書込ストール率）

| 実測（CEN=1・B-2/B-4 の高い方） | 判断 |
|---|---|
| ★15% 超★ | ★ライトバッファを工程②.5 へ前倒し検討する★ |
| 15% 以下 | ★工程③以降（工程④の一項目）に据え置く★（HANDOVER155 §3.3 の決定を維持） |

★概算では 6〜7%（CDC 往復込みで 1 割弱）と見込まれている。
すなわち「据え置き」が予測される結果であり、15% はその予測を覆す閾値として置く。★

### 4.2 TKT-V8（IRQ0 発火回数）

期待値：`C_total / 40,000` 回（40,000 cyc 周期）。

| 実測（YUI OS・B-3/B-4） | 判断 |
|---|---|
| ★期待値の ±20% 以内★ | ★重大度「低」を維持。工程③以降へ後送り可★ |
| ★それ以外（Dhrystone と同様の極端な過少）★ | ★重大度「高」へ改訂。工程②.5 の前に潰す★ |

★±20% は、M-5 到達タイミングのゆらぎとタイマ再武装のオーバーヘッドを許容する幅である。
Dhrystone 側の実測（CEN=0 で 1 回・CEN=1 で 0 回）は期待値の 1% 未満であり、
この閾値でも明確に「異常」と判定される。★

⚠ ★本件はまだ RTL（`ysd8800_ysd8002_v0_3.sv`）もカーネルのタイマ処理も一行も読んでいない。★
本計画は ★再現有無の確認まで★であり、原因究明は含まない。
★「YUI OS でも乖離」と出た場合に初めて TKT-V8 本調査を起票する。★

### 5.3 ★S-1：PASS 条件の是正★

現状（`tb_cpu_v8e_dhry_v0_2.sv` L613-616）：
PASS 表示は `finalize_and_exit(pass)` の引数のみに依存し、
`pass` は ★`dbg_halt` 到達だけで 1 になる★。
そのため ★UART 5 バイトの暴走実行でも `=== V8-e DHRY PASS ===` が出る★（T-1 で実測）。

是正後の PASS 条件（論理積）：

```
pass_final = pass                       // 正常終端（dbg_halt 到達）
           && (tx_count == 9)           // UART 9 バイト到達
           && (mism_count == 0)         // G-M: 誤返却なし
           && (rdchk_count > 0);        // G-M: 判定器が機能した
```

★`rdchk_count > 0` を落としてはならない。これが無いと
「モニタが一度も動かなかった」を「合格」と読んでしまう（KY96）。★

FAIL 時は ★どの条件で落ちたかを個別に `$display` する★。
「FAIL とだけ出る判定器」は原因切り分けに使えないためである。

⚠ ★是正の副作用★：本 TB は段7-A・TKT-V7 の T-1〜T-7 で使用した。
★T-1（暴走の再現）は是正後 FAIL 表示になる。これは正しい挙動であり、
過去の T-1 結果を否定するものではない（当時から実質 FAIL だった）。★
★source ledger および段7-A 計画書に、この表示変更を注記する必要がある。★
