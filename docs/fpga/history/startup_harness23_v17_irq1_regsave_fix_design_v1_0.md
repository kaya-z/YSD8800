呼出元コードの A/B/X が保存されるようにする。完成形を
**`startup_harness23_v17.asm`** として確定する。

## 1. バグの確定内容

### 1.1 症状

**`startup_harness23_v16.asm` L120-126**（実源引用）:

```asm
_irq1_handler:
    ; IRQ_STATを読み出してからWrite-to-Clearでクリア
    ; スタブ実装: 全ビットクリアしてIRET
    LDW  A, #$FCB2      ; IRQ_STAT アドレス      ← A を無条件上書き（呼出元 A 破壊）
    LDW  B, [A]         ; IRQ_STATを読み出し     ← B を無条件上書き（呼出元 B 破壊）
    STW  B, [A]         ; Write-to-Clear
    IRET
```

IRQ1 受理時、CPU が自動 push するのは PC と FLAGS のみ（§2.4）。
A/B/X は呼出元の責任で保存する必要があるが、本ハンドラは A/B を
**無退避で破壊**したまま IRET する。

### 1.2 `_timer_handler` との非対称性

**同ファイル L98-111**（実源引用）:

```asm
_timer_handler:
    STW  A, [_isr_wk_a]     ; A/B/X を退避
    STW  B, [_isr_wk_b]
    STW  X, [_isr_wk_x]

    LDW  A, #$FC90          ; TCR アドレス
    LDW  B, #$0023          ; TIMER_EN|IRQ_EN|IRQ_ACK
    STW  B, [A]             ; TCR ← 状態ビット込みの完全値

    LDW  A, [_isr_wk_a]     ; A/B/X を復元
    LDW  B, [_isr_wk_b]
    LDW  X, [_isr_wk_x]
    IRET
```

**同ファイル L63-66**（実源引用・退避ワーク設置の設計意図）:

```
; ================ ISR退避ワーク（v1.6 / V5新設）================
; _timer_handler が TCR ACK を発行する際に A/B/X を破壊するため、
; 中断されたコードのレジスタを保護する退避先が必要になった。
```

**同じ理由が `_irq1_handler` にも当てはまる**（LDW A,#$FCB2 で A を、
LDW B,[A] で B を破壊）にも関わらず、退避が実装されていない。
これは**設計の非対称であり、レビュー時に見逃された欠陥**である。

### 1.3 発生条件と実害

| 条件 | 発現 |
|---|---|
| IRQ1（YSD8003 ストレージ完了）が受理される | 前提条件 |
| 呼出元コードが受理時点で A に有意な値を保持 | **A 破壊で発現** |
| 呼出元コードが受理時点で B に有意な値を保持 | **B 破壊で発現** |
| 呼出元コードが X のみ保持 | **X は元々未使用のため発現せず** |

**現時点で顕在化しにくい理由**（バグ指摘書 §2.2 と一致）:
- YSD8003 ストレージ完了 IRQ は SD カード読出コマンド完了時のみ発生
- V8-D Dhrystone は SD 経路削除のため IRQ1 が発火しない
- 現状 cat/ls デモ（V8-a）程度で発生頻度が低い

**将来顕在化する条件**:
- **V8-b 以降**: YUI OS ファイルマネージャがストレージ read/write を頻発
- **YUI OS 上のユーザランドプログラム**が並行動作
- 非同期タイミング依存のため間欠発生・デバッグ困難

## 2. ISA・実装制約の一次確認

### 2.1 IRQ 受理時に CPU が保存するもの

**`emu23_v111.c` L1224-1236**（実源引用）:

```c
if (cpu.irq_pending >= 0 && (cpu.flags & FL_IE)) {
    int irq = cpu.irq_pending;
    cpu.irq_pending = -1;
    push16(cpu.pc);                // PC を先に push
    push16((uint16_t)cpu.flags);   // FLAGS を後に push
    cpu.flags &= ~FL_IE;           // IE = 0
    uint16_t vec = rd16((uint16_t)(irq * 2));
    cpu.pc = vec;
    ...
}
```

**保存されるのは PC と FLAGS のみ**。A/B/X はソフトウェアの責任。
これは MC6809 の CCR/PC 自動退避と同じ思想。

### 2.2 IRET 時の復元経路

**`emu23_v111.c` L1261-1268**（実源引用）:

```c
case 0x04: /* IRET  FLAGS←pop / PC←pop  (§7.6) */
    cpu.flags = (uint8_t)pop16();  // FLAGS を先に pop
    cpu.pc    = pop16();           // PC を後に pop
    break;
```

**IRET は FLAGS 全体を pop 復元する** → IE ビットも同時に元に戻る。
よって「IRQ 受理時 IE=0 → IRET で元の IE 復元」が保証される。

**帰結（バグ指摘書 §4.2 の裏付け）**: IRQ ハンドラ実行中は
（明示的 EI を書かない限り）別 IRQ は受理されない。よって
`_timer_handler` と `_irq1_handler` が同じ `_isr_wk_a/b/x` を
共有しても、両者の同時実行はあり得ず**現行仕様下で安全**。

### 2.3 退避ワーク領域の実源確認

**`startup_harness23_v16.asm` L67-75**（実源引用）:

```asm
    .org  $000C
_isr_wk_a:
    .word $0000
    .org  $000E
_isr_wk_b:
    .word $0000
    .org  $0010
_isr_wk_x:
    .word $0000
```

$000C-$0011 の 6バイト。ゼロ初期化。既設で追加の割付作業は不要。

### 2.4 STW/LDW 命令のフラグ副作用

- STW: フラグ非更新（ストアのみ）
- LDW: `set_zn()` でフラグ更新（§2.3 §2.4 は `emu23_v111.c` L1310-1408 で確認）

**帰結**: 退避シーケンス末尾の `LDW X, [_isr_wk_x]` が Z/N を更新するが、
その直後は `IRET` で FLAGS 全体が pop 復元される。よって
退避・復元によるフラグ副作用は呼出元に伝播しない。

## 3. 修正案の比較

### 3.1 候補案（バグ指摘書 §3 を再掲）

| 案 | 概要 | 命令数増 | 判定 |
|---|---|---|---|
| **案A** | **A/B/X 全退避（`_timer_handler` と対称化）** | **+6命令**（STW×3+LDW×3） | **★採用★** |
| 案B | 実際に使う A/B のみ退避 | +4命令（STW×2+LDW×2） | 却下 |

### 3.2 案A 採用の根拠

**技術的根拠:**
1. **保守性**: 全 IRQ ハンドラの退避パターンが対称化される。将来 `_irq1_handler`
   が本格実装で X を使う拡張を受けても、退避漏れの再発を防げる
2. **性能影響が微小**: IRQ1 は低頻度（SD 読出完了時のみ）で発生。
   +6命令の実行コストは実性能に影響しない
3. **スタブ実装からの拡張への配慮**: L122 コメントで「スタブ実装」と
   明記されており、本格実装時に X を使う可能性が高い

**設計思想的根拠（バグ指摘書 §3.3）:**
- 「使用するレジスタ ⊂ 退避されるレジスタ」を保守レビュー時の
  確認ルールに組み込む前提として、**対称化が最も検証しやすい**
- コーディングパターンの一貫性 → レビュー時の目視確認容易

### 3.3 案B 却下の根拠

**却下理由:**
- 「使う分だけ退避」は将来変更時の退避漏れリスクが高い
- 現に本バグ自体が「スタブ実装だから A/B しか使わない → 退避不要」
  という同種の判断ミスから生まれている可能性が高い（推測だが原因構造として同型）
- +6命令と+4命令の差は 2命令のみで、性能差は無視できる

### 3.4 修正後コード（案A・確定）

```asm
_irq1_handler:
    ; v1.7 修正: A/B/X を退避（_timer_handler と対称化）
    ; 理由: LDW A,#$FCB2 で A を、LDW B,[A] で B を破壊するため
    ;       呼出元レジスタの保護が必要。
    ;       X は本ハンドラでは未使用だが、将来拡張時の退避漏れを防ぐため
    ;       _timer_handler と同一パターンに揃える（案A採用）。
    STW  A, [_isr_wk_a]
    STW  B, [_isr_wk_b]
    STW  X, [_isr_wk_x]

    ; IRQ_STATを読み出してからWrite-to-Clearでクリア
    LDW  A, #$FCB2      ; IRQ_STAT アドレス
    LDW  B, [A]         ; IRQ_STATを読み出し
    STW  B, [A]         ; Write-to-Clear（読み出し値を書き戻す）

    LDW  A, [_isr_wk_a] ; A/B/X を復元
    LDW  B, [_isr_wk_b]
    LDW  X, [_isr_wk_x]
    IRET
```

## 4. 安全性・副作用の解析

### 4.1 レジスタ・フラグへの副作用

修正後のハンドラは、既存 `_timer_handler` と同型のパターンで:
- 実行前後で A/B/X は完全に元の値を保持
- FLAGS は IRET で pop 復元されるため、ハンドラ内の LDW による Z/N 更新は
  呼出元に伝播しない
- SP は IRQ 受理時 push（PC,FLAGS = 4B）と IRET 時 pop で釣り合い、
  ハンドラ内の STW/LDW は SP を触らない

**結論**: **呼出元から見て可観測な副作用ゼロ**。

### 4.2 退避ワーク共有の安全性（§2.2 の裏付け）

- IRQ 受理時 IE=0（emu23 L1230）
- ハンドラ内で明示的 EI を書かない限り、別 IRQ は受理されない
- IRET で FLAGS 全体を pop 復元 → IE 元に戻る
- **`_timer_handler` と `_irq1_handler` の同時実行は現行仕様下で不可能**
- したがって `_isr_wk_a/b/x` の共有は安全

### 4.3 将来の IRQ ネスティング導入時のリスク

ハンドラ内で明示的 `EI` を書いて割込ネスティングを許可する運用に将来
変更した場合、`_isr_wk_a/b/x` 共有は**壊れる**（内側 IRQ が外側 IRQ の
退避内容を上書き）。この場合はスタック退避方式（`PUSH A/B/X`）への
移行が必要。

**判断**: 本設計はネスティング未対応の現行仕様前提で確定させ、
ネスティング導入時は別途改修する（§7 申し送り）。

### 4.4 命令サイズ・実行サイクル数への影響

**命令サイズ:**
- 追加命令: STW×3（$FCxx形式 = 4B/命令）+ LDW×3（4B/命令）
- 増分: **+24バイト**（正確値は hasm23 出力で最終確認）

**実行サイクル数:**
- IRQ1 発火時のみ増加。V8-D Dhrystone は IRQ1 非発火なのでゼロ影響
- V8-a cat/ls デモでは SD 読出回数 × 6命令分の追加 = 数百サイクル
  程度の増加（体感不可）

### 4.5 既存テストへの回帰リスク

- **V8-D Dhrystone**: IRQ1 非発火経路 → 変化なし想定
- **V8-a cat/ls**: IRQ1 発火経路だが、修正後は呼出元のレジスタが
  保護されるため、むしろ**バグが解消される方向**に変化する可能性がある
  （現状は IRQ1 タイミング依存で偶然通過している可能性）

## 7. 将来課題（申し送り・KY41）

### 7.1 IRQ ネスティング対応（§4.3 参照）

将来ハンドラ内で `EI` を書いて割込ネスティングを許可する運用に変更する場合、
`_isr_wk_a/b/x` 共有は壊れる。**スタック退避方式（PUSH/POP）への移行**が必要。
`_isr_wk` の設置コメント（L63-66）に「IRQ ネスティング未対応。導入時は
スタック退避方式に変更必要」の1行を追記することを推奨。

### 7.2 割込ハンドラのコーディング規約明文化

- **本規約案（`yuios_design_v2_7.md` 追記候補）:**
  ```
  [規約: 割込ハンドラのレジスタ退避規則]

  すべての割込ハンドラは、実行中に触るレジスタ（A/B/X）を必ず
  _isr_wk_a/b/x に退避し、IRET 直前に復元しなければならない。

  スタブ実装（少数レジスタしか触らない場合）でも、将来拡張時の
  退避漏れを防ぐため、全レジスタ（A/B/X）の退避パターンで実装
  すること（_timer_handler パターンを踏襲）。

  例外: X をフレームポインタとして参照する用途を割込ハンドラ内で
  使う場合は、scc23 v2.04 との相互作用について事前に設計検討必須。
  ```

- **kaizen.txt 追加候補（バグ指摘書 §7.3 と同旨）:**
  > 割込ハンドラのレビュー時は「使用するレジスタ ⊂ 退避されるレジスタ」の
  > 集合関係を確認する。既存パターンを参考実装として設計を書いた際に
  > 非対称が見逃されるため、同種のハンドラを追加する際は既存パターンを
  > コピーして始めるルール化を推奨。

### 7.3 スタブ実装であることの明示強化

現行 `_irq1_handler` は L122 に「スタブ実装」コメントがあるが、本格実装
までに以下が必要になる可能性:
- IRQ_STAT bit 判定によるハンドリング分岐
- YSD8003 コマンド完了通知の受け取り処理
- YUI OS ファイルマネージャへの通知

本格実装時に本設計書の退避パターンを踏襲することを、v1.7 のコメントで
明示する（§6 手順3 の改版履歴で言及）。

### 7.4 他の割込ハンドラの点検

`_align_handler`（L131）は `HALT` のみ、`_syscall_handler`（L155-162）は
`JMP _harness_dispatch` のみで A/B/X を触らないため、本修正の対象外。
ただし将来の本格実装時には同じ退避規約を適用すること。
