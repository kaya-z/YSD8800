## 1. 本フェーズの位置づけと目的

### 1.1 なぜV3.7を新設したか（工程是正の経緯）

旧ロードマップ v1.1 では、割込コントローラ（YSD8004）の実装は **V7（全デバイス実装後）** に置かれていた。しかしこれは**依存の向きが逆**であった。

- 各デバイス（UART/タイマー/ストレージ）は、割込出力先として YSD8004 を**必要とする**
- 一方 YSD8004 自体は**デバイス非依存**であり、ダミー刺激で単体検証が完結する
- CPU側のIRQ受理機構は **V1/V2で実装・検証済**（`tb_cpu_irq` / `tb_cpu_irq_iret` / `tb_cpu_align_irq`）

つまり「CPU ← YSD8004 ← デバイス」という鎖のうち、**両端が先に完成し、中間だけが後回し**という不整合が生じていた。このままV4（UART）に進むと、IRQ線の接続先が無いためポーリングのみ検証し、V7で割込経路を再検証する**二度手間**となる。

→ **「実装＝前倒し（V3.7）／統合検証＝据置（V7）」** に分割することとし、2026-07-12 承認（番号体系は案A：既存V4以降の番号を動かさない）。

### 1.2 V3.7のスコープ

**含む（本フェーズ）:**
- YSD8004 レジスタ（IRQ_STAT / IRQ_MASK）の実装
- 割込要求の集約（複数デバイス → IRQ1 の1本へ）
- CPU `irq_in` への接続
- 単体TB（レジスタR/W・Write-to-Clear・マスク・集約）
- CPU結合TB（emu23協調等価）

**含まない（V7へ据置）:**
- 複数IRQ源が**実在する状態**での多重割込・衝突負荷試験
- IRQ受理列（サイクル列）の統合等価検証
  → 源（UART/タイマー/ストレージ）が揃わないと実施不能のため、V7の位置は妥当

## 2. ★IRQ2優先選択（旧§3.5将来課題）の扱い — N/Aクローズ★

本項は V3.7 の設計入力として最初に確定すべき事項であった（ロードマップ v1.2 に明記）。**実ソース照合の結果、N/A（実装対象が存在しない）としてクローズする。**

### 2.1 課題の内容（`emu23_device_design_v1_3.docx` §3.5）

> §3.2「pending中で最も優先順位の高いIRQを受理する」の厳密実装のうち、IRQ1とIRQ2の優先選択ロジックは現状未実装である。再評価機構は irq_stat 非0時に一律IRQ1を再pendingする。IRQ2（§3.1で「予備」）が将来使用される時点で、IRQ1/IRQ2の優先選択を実装する必要がある。

### 2.2 ★調査結果：ISA2.3に「IRQ2」は定義されていない★

`ISA2_3_v231.docx` §8.1/§8.2 の**実照合**により、以下が判明した。

| irq_id | 名称 | ベクタ | 状態 |
|---|---|---|---|
| 0 | reset | $0000 | 使用中 |
| 1 | irq0（タイマー） | $0002 | 使用中 |
| 2 | irq1（YSD8004経由） | $0004 | 使用中 |
| 3 | **align例外** | $0006 | **使用中** |
| 4 | syscall | $0008 | 使用中 |

**ISA2.3 の割込は irq_id = 0〜4 の5種であり、「IRQ2」という割込は存在しない。**
`irq_id=3` は **align例外**が占有しており、「IRQ2」に割り当てられる番号は無い。

すなわち `emu23_device_design_v1_3` §3.1 の優先順位表にある **「IRQ2＝予備」の行は、ISA仕様書に存在しない割込を記載したものであり、設計書側の誤りである。**

### 2.3 実装側の裏付け（emu23 v1.09 実照合）

- `ysd8004_raise()`（L314-329）は **常に `cpu.irq_pending = 2`（＝IRQ1）しか設定しない**
- IRQ_STAT再評価機構（L1576-1578）も **`irq_stat != 0` なら一律 `irq_pending = 2`**
- IRQ_STAT のビット定義は **bit0=UART_RX / bit1=STOR / bit2=UART_TX の3本のみ**（L298-300）

**→ emu23（黄金リファレンス）に IRQ2 を生成するコードパスは存在しない。**
黄金値が存在しない以上、RTL側に実装しても**検証不能**であり、偽合格の温床となる。

### 2.4 結論

**V3.7 では IRQ2 優先選択ロジックを実装しない。**
YSD8004 は **IRQ1 の1本のみ**を出力する（CPUへは `irq_in = 3'd2` を与える）。

### 2.5 ★将来拡張の余地（記録・資産として明記）★

ただし**拡張の余地は残されている**。これは重要な資産なので記録する。

**(a) ベクタテーブルに空きが3枠ある**

ベクタテーブル領域は **$0000–$000F の16バイト＝全8枠**（ISA2.3 §9.1/§9.2 実照合。Forceマシン／ベアメタル共通）。5枠使用済、**3枠が空き**。

| irq_id | ベクタ | 状態 |
|---|---|---|
| 5 | $000A | **★空き★** |
| 6 | $000C | **★空き★** |
| 7 | $000E | **★空き★** |

**(b) CPUコアは無改修でこの3枠に到達可能**

CPUコア（`ysd8800_cpu_v0_1_FIXED.sv` v0.5.7）の割込入力は **3bitバス**であり、値を素通しでラッチする。

```systemverilog
input logic [2:0] irq_in;                    // L231：3bit（0〜7を表現可能）
if (state == S_IRQCHK && irq_in != 3'd0)
    irq_pending <= irq_in;                   // L1224-1225：値を素通し
```

ベクタアドレスは **`vec = irq_id × 2` の算術計算**（テーブル引きではない）。
したがって `irq_in = 3'd5` を与えれば **自動的に $000A へ分岐する**。
**IRQ番号ごとの `case` 文や特別扱いは一切存在しない。**

**(c) 将来割込源を追加する場合の2案**

- **案①（推奨・改修不要）:** YSD8004 の IRQ_STAT にビットを追加し、**IRQ1 へ集約**する。CPU・ISA・ベクタテーブルは**一切無改修**。ハンドラが IRQ_STAT を読んで発生源を判別する。これは割込コントローラを置く本来の意義であり、MC6809 + PIA/ACIA が複数のIRQ出力をワイヤードORで1本の `IRQ` 線に束ね、ハンドラ側でステータスを読んで源を判別するのと同一の構造である。
- **案②（専用ベクタが必要な場合）:** `irq_id = 5/6/7` に新規割込を割り当てる。**CPUコアのRTLは無改修**だが、ISA仕様書 §8.1/§8.2・emu23（黄金）・スタートアップのベクタテーブル定義の**同時改版**が必要。専用ベクタを持てるため発生源判別が不要＝高速。

**汎用的な周辺デバイスは案①、低レイテンシが要る割込（将来のDMA完了等）は案②**、という使い分けが素直である。

### 2.5b ★【v0.2新設】重要な副次発見：V2-eの「4→2正規化」の正体★

レビュー（`v3_7_design_review_reply_v1_0.docx` §4）の独立実照合により、**V2-eで争点となった現象の正体が判明した。** V3.7の設計入力として極めて重要なため、ここに記録する。

**従来の理解（誤り）:** 「SYSCALL（`irq_pending=4`）が YSD8004 経由で 2 に**正規化**される」

**正しい理解:** これは正規化ではなく、**pending保護ロジック**の一部である。

`ysd8004_raise()`（emu23 v1.09 L322-327・実照合）:

```c
if (irq_stat != 0) {
    /* pending保護: 既存の高優先IRQを蹴落とさない */
    if (cpu.irq_pending < 0  ||   /* 何もpending無し          */
        cpu.irq_pending == 2 ||   /* 既にIRQ1 → 上書き無害     */
        cpu.irq_pending == 4) {   /* SYSCALL → IRQ1優先で上書きOK */
        cpu.irq_pending = 2;
    }
    /* それ以外（==1 timer / ==3 align）は保護される */
}
```

すなわち「**デバイスがIRQを上げたとき、たまたま SYSCALL が pending なら IRQ1 を優先して上書きしてよい**」という優先順位ルールである。SYSCALL 単独では `ysd8004_raise()` 自体が呼ばれないため `4` のまま残る。これは **V2-eの決着（SYSCALL単独 → `vec=$0008`）と完全に整合する。**

**★導出される実質的な優先度序列★**

| 優先度 | irq_pending | 挙動 |
|---|---|---|
| **高** | **1（timer）／3（align）** | **保護される**（IRQ1に蹴落とされない） |
| 中 | 2（IRQ1・YSD8004） | 上書き無害 |
| **低** | **4（SYSCALL）** | **IRQ1に譲る**（上書きされる） |

**→ `timer/align > IRQ1 > SYSCALL`**

この序列は **V5（タイマー追加）のRTL調停で写像する必要がある**（§4.4b 参照）。

### 2.6 波及する文書改版（V3.7完了後に実施）

- `emu23_device_design_v1_3.docx` → **v1.4**
  - §3.1 優先順位表から **「IRQ2＝予備」の行を削除**（ISAに存在しないため）
  - §3.5 将来課題を **本メモ §2 の内容でクローズ**（責務の帰属誤りの訂正を含む）
  - **【v0.2追記】§3.2 の「優先順位」記述に、§2.5b で判明した実質序列（`timer/align > IRQ1 > SYSCALL`）を明記する**

## 3. YSD8004 レジスタ仕様（emu23 v1.09 実照合・黄金）

### 3.1 レジスタマップ

| アドレス | レジスタ | 幅 | 属性 | リセット値 | 出典 |
|---|---|---|---|---|---|
| `$FCB2` | IRQ_STAT | 16bit | R / **Write-to-Clear** | `0x0000` | emu23 L294, L761 |
| `$FCB4` | IRQ_MASK | 16bit | R/W（**1=マスク / 0=許可**） | **`0x0004`** | emu23 L295, L307, L762 |

### 3.2 IRQ_STAT ビット定義（emu23 L298-300 実照合）

| bit | 名称 | 発生源 | 割当フェーズ |
|---|---|---|---|
| 0 | UART_RX | YSD8001 UART 受信 | V4 |
| 1 | STOR | YSD8003 ストレージ 完了/エラー | V6 |
| 2 | UART_TX | YSD8001 UART 送信（TDRE） | V4 |
| 3-15 | 予約 | — | 将来（案①の拡張枠） |

### 3.3 ★IRQ_MASK リセット値に関する重要注意★

**リセット値は `0x0004`（bit2=UART_TX がマスクされた状態）である。**

- マスク論理は **1=マスク / 0=許可**
- したがってリセット直後は **UART_RX・STOR は許可、UART_TX のみ禁止**
- 根拠: emu23 L307（`static uint16_t irq_mask = 0x0004;`）／`ysd8001_uart_design_v1_2` §3.6

**KY項目:** ここを `0x0000` で実装すると、V4（UART）でTX割込が想定外に発火し、emu23との等価性が破れる。**リセット値の実装ミスは本フェーズの最大の危険箇所である。**

### 3.4 動作仕様

**割込の発火（emu23 `ysd8004_raise()` L314-329 相当）:**

```
allowed = source_bits & ~IRQ_MASK    // マスクで許可されたビットのみ
if (allowed == 0) return             // 全マスク → 何もしない
IRQ_STAT |= allowed                  // STATにOR（ラッチ）
if (IRQ_STAT != 0) assert IRQ1       // STAT非0の間、IRQ1をアサート
```

**クリア（Write-to-Clear・emu23 L761）:**

```
書込値のビットが1の箇所をクリア:  IRQ_STAT &= ~wdata
```

**★重要★ IRQ1 の出力は「IRQ_STAT != 0」のレベル信号である。**
ハンドラが IRQ_STAT をクリアするまでアサートされ続ける（レベルセンシティブ）。
これにより、ハンドラが源を処理し忘れたまま IRET すると再度受理される（＝取りこぼさない）。

## 4. ★設計上の主要論点（レビュー対象）★

### 4.1 論点1: レジスタ幅 16bit vs バス幅 8bit の不整合 ★要判断★

**問題:**
- emu23 の IRQ_STAT/IRQ_MASK は **16bitレジスタ**（`uint16_t`）
- しかし FPGA 側のバスは **バイト粒度（8bit）**
  （`ysd8800_addr_decoder_v0_1.sv`: `mmio_wdata [7:0]` / `mmio_rdata [7:0]` 実照合）
- V3.5 の MMIOスタブも **8bitポート**（`ysd8800_mmio_stub_v0_2.sv` L46-47 実照合）

**現に使用されているビットは bit0-2 のみ**であり、上位8bitは全て予約（未使用）である。

**選択肢:**

- **案A（推奨）: 下位8bitのみ実装。`$FCB2`/`$FCB4` はバイトアクセス。**
  - 実装が単純。現行の全ビット（bit0-2）を包含する
  - CPU が `LDW`（16bitロード）で `$FCB2` を読むと `$FCB2`(下位) + `$FCB3`(上位) の2バイトアクセスになる。**`$FCB3` を「常時 `0x00` を返す上位バイト」として実装すれば、16bitアクセスでも emu23 と等価**になる
  - 将来ビットが8本を超えたら上位バイトを実装すればよい（拡張余地は残る）
- **案B: 16bitレジスタとして完全実装（`$FCB2`/`$FCB3` の2バイト構成）**
  - emu23 と幅まで完全一致するが、bit8-15 は永久に未使用の可能性が高い
  - 実装コストが増えるだけで実利が薄い

**推奨: 案A。** ただし**`$FCB3`/`$FCB5`（上位バイト）を必ずデコードし `0x00` を返すこと**。ここをデコードし忘れると、16bitアクセス時に上位バイトが不定値となり emu23 と食い違う。

→ **★レビュー確認事項1: 案Aで良いか★**

### 4.2 論点2: YSD8004 の配置（MMIOスタブ内 vs 独立モジュール）★要判断★

**選択肢:**

- **案A: `ysd8800_mmio_stub_v0_2.sv` を v0.3 に拡張し、内部にYSD8004を追加**
  - MMIOのデコードが1箇所に集まり単純
  - しかし MMIOスタブが「MMU用レジスタ＋割込コントローラ」の**責務混在**になる
- **案B（推奨）: `ysd8800_ysd8004_v0_1.sv` を独立モジュールとして新規作成し、MMIOスタブから接続**
  - **責務が明確**（YSD8004は独立したデバイスである）
  - **デバイス非依存で単体TBが書ける**（V3.7の設計思想そのもの）
  - V4以降で UART/タイマー/ストレージを追加する際も同じ流儀で並べられる
  - MMIOスタブ側は `$FCB2/$FCB4` へのアクセスをYSD8004へルーティングするだけ

**推奨: 案B。** 責務分離を優先する。V4以降で同様のデバイスが増えることを考えると、ここで「デバイスを独立モジュールとして並べる」パターンを確立しておく価値が高い。

→ **★レビュー確認事項2: 案Bで良いか★**

### 4.3 論点3: 割込入力インタフェース（V4以降のデバイスとの接続規約）

YSD8004 の入力は **各デバイスからの「割込要求パルス」** とする。

```systemverilog
input logic irq_src_uart_rx,   // V4で接続（現状は0固定）
input logic irq_src_stor,      // V6で接続（現状は0固定）
input logic irq_src_uart_tx,   // V4で接続（現状は0固定）
```

**規約:** 各入力は **1クロックのパルス**（レベルではない）。YSD8004 が IRQ_STAT にラッチして保持する。
デバイス側は「イベント発生時に1クロックだけ上げる」。以降の保持は YSD8004 の責務。

**V3.7時点では全て `1'b0` 固定**（デバイス未実装のため）。TBからは直接刺激を与えて検証する。

→ この規約を V4/V5/V6 の設計入力とする。

### 4.4 論点4: CPU `irq_in` への接続と優先順位

CPU の `irq_in` は**3bitの番号バス**であり、複数の割込源を同時に表現できない（単一値）。
V3.7時点で CPU に割込を出しうるのは以下：

| 源 | irq_in 値 | 実装フェーズ |
|---|---|---|
| align例外 | 3 | **CPU内部**（V1実装済） |
| SYSCALL | 4 | **CPU内部**（V1実装済） |
| タイマー | 1 | V5（未実装） |
| **YSD8004** | **2** | **★V3.7（本フェーズ）★** |

**V3.7では YSD8004 → `irq_in = 3'd2` の経路のみを追加する。**

**★注意★ CPU内部の align/SYSCALL は `irq_pending` を直接設定する**（`irq_in` を経由しない）。
したがって V3.7 で外部から `irq_in` に与えるのは **2（YSD8004）のみ**であり、
タイマー（1）は V5 で追加する。**この時点で外部からの多重要求は発生しない**（源が1つのため）。

→ **多重要求の調停は V5（タイマー追加時）に初めて必要になる。**
現行 CPU は `irq_pending` が単一値であり、後着が先着を上書きする構造である。
emu23 はこれを `ysd8004_raise()` の**pending保護ロジック**（L322-327：IRQ0/IRQ3 は蹴落とさない）
＋**IRQ_STAT再評価機構**（L1576-1578：IRET後に irq_stat 非0なら IRQ1 を再pending）で回避している。

**→ ★V5での要検討事項として申し送る★**（V3.7のスコープ外だが、設計の連続性のため記録）

### 4.4b ★【v0.2新設・レビュー承認条件】V5申し送り内容の補強 — emu23の調停は2段構えである★

レビュー確認事項5は **「申し送り内容を具体化すること」を条件に承認**された（`v3_7_design_review_reply_v1_0.docx` §5）。以下を **V5の設計入力として確定**する。

**emu23 の多重割込調停は、独立した2つの機構の組合せ（2段構え）である。片方だけを写像すると破綻する。**

#### 【第1段】pending保護ロジック（`ysd8004_raise()` 内・L322-327）

- **役割:** 後着の IRQ1 が、先着の **timer(1) / align(3) を蹴落とさない**
- **これが無いと:** 単純な後着上書きとなり、**タイマー割込が握り潰される**
- **RTL上の対応箇所:** **CPU側の `irq_pending` 更新条件**に相当する

現行CPU（`ysd8800_cpu_v0_1_FIXED.sv` v0.5.7 L1199・実照合）は、

```systemverilog
if (state == S_IRQCHK && irq_in != 3'd0)
    irq_pending <= irq_in;      // ★無条件の素通しラッチ（保護なし）★
```

であり、**timer(1) が pending 中に YSD8004 が 2 を出すと上書きされうる。**

#### 【第2段】IRQ_STAT 再評価機構（毎命令・L1576-1578）

- **役割:** `irq_pending < 0 && irq_stat != 0` なら **IRQ1 を再pending**
- **効果:** 第1段で保護されて後回しになった IRQ1 が、先着IRQの処理完了後（IRET後）に**自然に復活する＝取りこぼさない**

#### ★重要な設計上の含意：第2段はRTLで「自動的に成立する」★

**YSD8004 の IRQ1 出力を「`IRQ_STAT != 0` のレベル信号」にしておけば（§3.4 のとおり）、第2段は追加実装なしで成立する。**

理由：CPU が `S_IRQCHK` に戻るたび、`irq_in` は **2 のままアサートされ続けている**（IRQ_STAT がクリアされていないため）。よって**再受理される**。

> **→ すなわち「IRQ1をレベル出力にする」という設計選択が、emu23 の再評価機構と等価になる。**
> この対応関係は V3.7 の設計判断（§3.4・KY-D）が V5 まで効いてくることを意味し、**レベル出力は必須**である（パルス出力にすると第2段が崩れる）。

#### ★V5で残る設計判断（主要論点として申し送り）★

**第1段（保護）は自動成立しない。** V5でタイマーを追加する際、以下のいずれかを選ぶ必要がある。

| 案 | 内容 | 備考 |
|---|---|---|
| **案A** | CPU の `irq_pending` 更新条件に**保護条件（優先度比較）を入れる** | emu23 の第1段を直接写像。CPUコアRTLの改修が必要 |
| **案B** | **タイマー側もレベル保持**にし、蹴落とされても再評価で復活させる | CPUコア無改修。ただしタイマー側にレベル保持機構が要る |

**→ V5 の主要論点として申し送る。** どちらを選ぶにせよ、**§2.5b の実質序列（`timer/align > IRQ1 > SYSCALL`）を満たすこと**が完了条件となる。

### 9.3 所見: MC6809 + PIA/ACIA との対比

§2.5(c) 案①の「IRQ_STATにビットを追加し IRQ1 へ集約、ハンドラが STAT を読んで源を判別」は、**まさに MC6809 + PIA/ACIA の古典構成**である。複数デバイスの割込出力を**ワイヤードORで1本の `IRQ` 線に束ね**、ハンドラがデバイスのステータスレジスタをポーリングして源を特定する——**OS-9 の IRQポーリングテーブル**もこの構造の上に成り立っていた。

YSD8004 がその役割を果たし、CPU の `irq_in = 2`（IRQ1）1本に集約する設計は、**この伝統に忠実**である。かつ §2.5(b) で判明したとおり、CPUコアは3bitの `irq_in` を素通しで `vec = id*2` に落とすため、**専用ベクタが要る低レイテンシ割込（案②）には空き3枠（`$000A`/`$000C`/`$000E`）で対応できる。**

> **集約と専用ベクタの両方に道が開かれている点は、設計資産として価値が高い。**

### 9.4 実装時の厳守事項（レビュー指定）

1. **KY-A（IRQ_MASK リセット値 `0x0004`）の警戒は正しい。** S3単体TBの**第1項目**とする方針を**厳守**すること。
2. **`$FCB3`/`$FCB5`（上位バイト）のデコード＋`0x00`返しは必須**（S3項目8で検証）。
3. **IRQ1 は必ずレベル出力**（`IRQ_STAT != 0`）。パルスにすると §4.4b【第2段】が崩れ、V5で取りこぼしが発生する。
