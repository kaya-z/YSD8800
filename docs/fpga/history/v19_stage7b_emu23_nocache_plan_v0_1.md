## §2. 現状の制約（★実源で確認済・2026-09-06★）

`emu23_v2_15.c` の課金機構は下記の構造である。

| 事項 | 実源 | 内容 |
|---|---|---|
| 課金分岐 | L790-806 | ★4 分岐のみ★（読みヒット / 読みミス / 書きヒット / 書きミス） |
| 既定動作 | L775 | `cache_enable==0` で即 `return 0` ＝ ★理想メモリ★ |
| レイテンシ | L592 | `lat[6] = {5,5,5,5,5,5}`（F, R8, W8, R16, W16, FILL）※段6 で校正済 |
| 制御変数 | L570-571 | `cache_enable`（判定）と `charge_enable`（課金）は★別変数★（C-9） |

★**「キャッシュを持たない CPU が PSRAM を直接叩く」課金経路が存在しない。**★

- `cache_enable==0` は課金 0 ＝ 理想メモリであり、★RTL の `CEN=0` とは別物★
- `--cache-size` を最小（＝`--cache-line`）にしても、32B ライン内の連続アクセスは
  ヒットしてしまう。段6 実測で *h_f*=0.9981 であったから
  ★「全ミス近似」にはならない★（`v16` §1.3）

## §3. 改修設計（案δ）

### 3.1 追加する第5の状態

| 状態 | `cache_enable` | 新フラグ `nocache_model` | 課金 |
|---|---|---|---|
| 既定（理想メモリ） | 0 | 0 | 0（R1 死守） |
| キャッシュ有効 | 1 | 0 | 現行4分岐 |
| ★キャッシュ無し★【新設】 | 1 | ★1★ | ★全アクセスが PSRAM 直行★ |

### 3.2 課金式（★新設分★）

```
読み（F/R8/R16）: lat[kind] - 1
書き（W8/W16）  : lat[kind] - 1
```

★根拠★：RTL の `CEN=0` では `cache` モジュールが純バイパスとなり、
CPU の各アクセスが `cdc_bridge` 経由で ★単発アクセス★ として PSRAM に到達する。
★ラインフィル（`cache_line × lat[LAT_FILL_IDX]`）は発生しない★。
したがって読みも書きも単発レイテンシで課金するのが RTL 対応である。

★`-1` の由来は現行4分岐と同一（PSRAM 応答の 1 サイクルは CPI 側に含まれるため）。
新設分だけ規約を変えてはならない。★

### 3.3 実装方針

- ★`mem_charge()` の中に分岐を1つ足すだけ★とし、関数を分割しない
  （課金の積算箇所を1か所に集約する現行方針を維持）
- `nocache_model` 時は ★`cache_valid[]`／`cache_tag[]` を一切触らない★
  （キャッシュが存在しない以上、状態を持つこと自体が誤り）
- `stat_hit`／`stat_miss` は ★全件 miss として計上する★
  （`--cache-stats` の意味が変質するため §5 の N-1 で明示表示する）
- トレース出力（L811-815）の `hit` 欄は常に 0 になる

### 3.4 新設オプション

```
--no-cache-model     キャッシュ非搭載モデルで課金する（cache_enable も同時に立てる）
```

★`--cache-size`／`--cache-line` と同時指定された場合は★
★エラーとして停止する（黙って無視しない）。★ 意味が矛盾するため。

## §4. ★D-1：ご確認いただきたい設計判断★

★**本計画で最も重要な未確定事項であり、承認前に決定を要する。**★

筆者の提案は下記のとおりであるが、★これは提案であり決定ではない★。

### 提案：ライトバッファ効果の上限を emu23 で直接測る

段7-C が測ったのは「書込ストールが全体の何%か」であり、
★これは削減余地の**上限**であって、ライトバッファで実際に消える量ではない。★

そこで emu23 に ★書込課金を 0 にした第3の測定（理想ライトバッファ）★ を加え、
下記3点の比較で判断することを提案する。

| 測定 | 条件 | 得られるもの |
|---|---|---|
| A | `--no-cache-model` | CEN=0 相当の総サイクル |
| B | 現行4分岐（キャッシュ有効） | CEN=1 相当の総サイクル |
| C | B ＋★書込課金を 0★ | ★理想ライトバッファ搭載時★の総サイクル |

★判定基準（案・事前確定を要する）★

| (B−C)/B ＝ ライトバッファ効果の上限 | 判断 |
|---|---|
| 10% 以上 | 工程②.5 へ前倒し |
| ★5〜10%★ | 工程③（FPGA 実装）で資源に余裕があれば実施 |
| 5% 未満 | ★工程④へ据え置き（現行方針の追認）★ |

★この基準値（10%／5%）は筆者の提案値であり、根拠は
「段7-C で `stall_wr` が CEN=0/1 でほぼ不変（差 0.04〜0.06%）＝
書込はキャッシュ非依存」という観測のみである。★
★測定前に確定させる必要がある（`v18` の運用と同じ・後出し禁止）。★
