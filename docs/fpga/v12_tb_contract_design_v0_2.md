## §1. 目的と背景

### 1.1 解こうとしている問題

★TB が DUT の外部契約を独自に再実装し、そちらが間違う。★
結果、★DUT は正しいのに落ちる（偽 FAIL）★。

| 時期 | 損失 |
|---|---|
| ②-A' | 1チャット |
| 段3 | 誤認しかけ |
| 段4 | 該当チャットの大半 |

### 1.2 ★なぜ段5 の前にやるのか★

段5（FLUSH / `CEN` 立上り無効化 / `fill_abort_r`）は ★新規に単体 TB を書く工程★である。
既存 TB の手直しではなく、★段4 と同じ構図がそのまま再現し得る★。

さらに段5 の失敗モードは非対称である：

| 失敗 | 現れ方 | 気づけるか |
|---|---|---|
| 効きすぎ（過剰フラッシュ） | 性能劣化 | ✅ M-5 で気づける |
| ★効かなさすぎ（フラッシュ漏れ）★ | ★コヒーレンシ破壊★ | ❌ ★静かに壊れる★ |

★偽 FAIL に時間を溶かした状態で「静かに壊れる不具合」を追うのは最悪の組み合わせである。★
よって本対策は段5 の**前**に置く。

### 1.3 非目標（★やらないこと★）

## §2. 契約の確定（★実源確認済★）

対策の前提として、★DUT の外部契約を実源から確定する★。
以下は推測ではなく実ファイルの引用に基づく（KY34）。

### 2.1 契約 ~~C-α：ready と同時に要求を下げる~~ → ★**C-α'：ready 後に同一要求を保持しない**★

#### ★2.1.0 v0.1 の誤り（取り消し・M-1）★

> ~~**契約 C-α**：`cpu_mem_ready` が 1 の次サイクルで `cpu_mem_rd`/`cpu_mem_wr` は 0 でなければならない。~~
> ~~実 CPU は ready と同時に要求を下げるため発生しない。~~

★この契約定義は誤りである。実 CPU の動作と正面から矛盾する。★

**反証（実源・レビュー M-1）**

```
  ysd8800_cpu_v0_1_FIXED.sv
    L750  S_MEMR_LO: begin if (mem_ready) next_state = S_MEMR_HI; end
    L880  S_MEMR_HI: begin mem_addr = addr_r + 16'd1; mem_rd = 1'b1; end
```

★cycle N で `ready=1` → cycle N+1 は `S_MEMR_HI` で `mem_rd=1`。★
同型の経路は他にも存在する（すべて実源確認済）：

| 遷移 | 行 | 次サイクルの要求 |
|---|---|---|
| `S_MEMR_LO` → `S_MEMR_HI` | L750 / L880 | `mem_rd=1`（16bit ロード） |
| `S_FETCH` → `S_OPFETCH` | L618 / L871-872 | `mem_rd=1`（命令フェッチ） |
| `S_PUSH_LO` → `S_PUSH_HI` | L787 / L889 | `mem_wr=1`（PUSH） |
| `S_POP_LO` → `S_POP_HI` | L806 / L892 | `mem_rd=1`（POP） |

★旧 C-α を導入すれば、命令フェッチのたびに発火する。★
`$error` にしていても ★切り分け不能なログの洪水★ となり、
★本設計が解こうとしている「偽 FAIL に時間を溶かす」問題を自ら再生産する。★

#### ★2.1.1 なぜ ready の次サイクルに要求が立つのが正しいのか★

```
  ysd8800_cdc_bridge_v0_4.sv
    L110  logic suppress_r;   // readyと同位相のreq抑止信号
    L119  assign req_level = (cpu_mem_rd | cpu_mem_wr) & ~suppress_r;
    L131  suppress_r <= ack_sync[0] & ~ack_sync[1];
```

`suppress_r` の抑止幅は★ちょうど 1 cpu cyc★。cycle N+1 では `suppress_r=0` に戻るため、
`rd` が立っていれば ★**新しいアドレス**で新しい要求が発火する★。
これは 4 相ハンドシェイクを ★1 サイクルの無駄なく回すための意図された設計★であり、
★工程①.5 の A-2q の成果そのもの★である。

#### ★2.1.2 では段4 の誤りは何だったのか★

| 主体 | ready 後の「継続」 |
|---|---|
| ★実 CPU★ | 必ず ★**新しい要求**★（アドレスまたは種別が変化） |
| ★段4 の TB★ | ★**同一アドレス・同一種別の要求を保持**★ → 同一要求の再送 |

★旧 C-α はこの区別を捉えていなかった。★
「要求が継続しているか」ではなく ★「同じ要求を保持しているか」★ が問うべき性質である。

#### ★2.1.3 再定式化★

★**契約 C-α'**：`cpu_mem_ready` が 1 のサイクルの次サイクルで要求が継続する場合、
それは**新しい要求**（アドレスまたは種別が変化している）でなければならない。
★同一アドレス・同一種別の要求を保持してはならない。★★

v0.1 §2.1 は「実源確認済」としていたが、★引用した行の内容は正確でも、

## §3. T-B：バス契約アサーションの常設（★最優先★）

### 3.1 方針

★DUT 側に常設する。★ TB 側ではない。

理由：TB 側に置くと ★TB を書く人が assert も書くことになり、同じ人が同じ誤解をする★。
契約は DUT の性質であるから、DUT の隣に置くのが正しい。
（KY78 の「契約の実装が2箇所あると片方が古くなる」への直接の対処）

### 3.2 配置先（★M-4 反映：監視する境界を明示★）

★工程②-B 以降、CPU 抽象バスの境界は **2 箇所** ある。★

```
   CPU ──[境界①]── キャッシュ段 ──[境界②]── cdc_bridge ── psram_ctrl
```

★v0.1 は境界②（`cdc_bridge`）にしか assert を置いていなかった。★
段5 で新規に書く TB（`tb_cache_flush_poc` 等）は ★キャッシュ段を直接 DUT とする★ため、
`cdc_bridge` はインスタンス化されず ★assert が1本も効かない★構成であった。
★「新規 TB が危険だから対策する」と言いながら、その新規 TB に届かない★という
致命的な穴であり、M-4 として是正する。

| 契約 | ★監視する境界★ | 配置モジュール | 監視するポート |
|---|---|---|---|
| ★C-α'★ | ★①CPU ⇔ キャッシュ段★ | ★`ysd8800_cache_v0_x.sv`★ | `cpu_ready_o` / `cpu_rd_i` / `cpu_wr_i` / `cpu_phys_addr_i` |
| ★C-α'★ | ②キャッシュ段 ⇔ `cdc_bridge` | `ysd8800_cdc_bridge_v0_4.sv` | `cpu_mem_ready` / `cpu_mem_rd` / `cpu_mem_wr` / 物理アドレス |
| C-β | ②の下流（PSRAM 受理） | `ysd8800_psram_ctrl_v0_3.sv` | `req` / `burst_len` / `we` / `blen_r` |
| C-γ | MMIO | `ysd8800_mmio_stub_v0_9.sv` | CCR 書込経路 |

> ★境界①への配置が本 v0.2 の要点である。★
> 段5 の TB がキャッシュ段単体を叩く場合、★効くのは境界①の assert だけ★である。

#### ★3.2.1 独立モジュール化を採らない理由★

C-α' を `bus_contract_checker.sv` として切り出し、両境界へ `bind` する案も考えられる。
しかし ★Icarus 12.0 の `bind` 対応は未確認★であり、
M-2 で `assert property` が未サポートと判明した実績を踏まえると、
★素直に各モジュールへ埋め込むほうが確実★である。

★重複は生じるが、重複2箇所は「契約の実装が2箇所ある」（KY78）とは異なる。★
両者とも★同一の契約 C-α' の検査器★であり、DUT の外部契約の再実装ではない。
ただし ★片方だけ直す事故★を防ぐため、両者に同一のコメントブロックを付し、
★「対になる検査器がもう1箇所にある」ことを明記する★。

### 3.3 ★記述案（M-2：`always` 手続き版へ全面変更）★

#### 3.3.0 ★前提：Icarus 12.0 は concurrent assertion を一切サポートしない★

レビューにて Icarus Verilog 12.0（実機と同版）で実地確認された確定事実：

| 記述 | 結果 |
|---|---|
| `assert property` ＋ 時相演算子（`\|=>`） | ★**syntax error**★ `Error in property_spec of concurrent assertion item.` |
| `assert property` ＋ 単純ブール | ★**未実装**★ `sorry: concurrent_assertion_item not supported.` |
| ★`always` ブロック ＋ `$error`★ | ★**通過**★ |

> ★`always_ff` を使うと `$error` は合成できないという警告が出る。
> `` `ifndef SYNTHESIS `` で囲むため実害はないが、★警告ゼロを保つため `always` を使う★。★

#### ★3.3.1 C-α'（境界①・キャッシュ段の CPU 側）★

★本コードはレビューにて Icarus 12.0 でのコンパイルと陽性／陰性の動作確認まで実施済★。

```systemverilog
// ============================================================
//  ★バス契約アサーション C-α'（TKT-V1 / T-B・2026-09-01 追加）★
//    契約: ready の次サイクルで要求を継続する場合、それは
//          ★新しい要求（アドレスまたは種別が変化）★でなければならない。
//          ★同一アドレス・同一種別の保持は契約違反★。
//    経緯: 段4 で TB が ready 後も同一要求を保持し、再送が発生した。
//          DUT は正しいのに落ち、切り分けに数時間を要した（TKT-V1）。
//    ★注意: 実CPUは ready の次サイクルに新しい要求を出す（S_MEMR_LO→HI 等）。
//            「要求が継続していること」自体は契約違反ではない。★
//    ★対の検査器が cdc_bridge 側（境界②）にもある。片方だけ直さないこと。★
//    実装: Icarus 12.0 は assert property 未サポートのため手続き版。
//          always_ff は $error に合成不可警告が出るため always を使う。
//    合成: `ifndef SYNTHESIS で囲む（工程③へ持ち込まない）
// ============================================================
`ifndef SYNTHESIS
    logic                ready_d, rd_d, wr_d;
    logic [PHYS_AW-1:0]  addr_d;
    always @(posedge cpu_clk or negedge cpu_rst_n) begin
        if (!cpu_rst_n) begin
            ready_d <= 1'b0; rd_d <= 1'b0; wr_d <= 1'b0; addr_d <= '0;
        end else begin
            if (ready_d && (cpu_rd_i || cpu_wr_i)
                        && (cpu_rd_i == rd_d) && (cpu_wr_i == wr_d)
                        && (cpu_phys_addr_i == addr_d))
                $error("[CONTRACT C-a'] same req held after ready: addr=%h rd=%b wr=%b t=%0t",
                       cpu_phys_addr_i, cpu_rd_i, cpu_wr_i, $time);
            ready_d <= cpu_ready_o;
            rd_d    <= cpu_rd_i;
            wr_d    <= cpu_wr_i;
            addr_d  <= cpu_phys_addr_i;
        end
    end
`endif
```

**レビューでの実行結果（Icarus 12.0）**

```
== 陰性1: 実CPU相当 S_MEMR_LO->S_MEMR_HI (addr変化) ==   （発火なし）
== 陽性:  段4のバグ相当 ready後に同一要求を保持 ==
ERROR: [CONTRACT C-a'] same req held after ready: addr=02000 rd=1 wr=0 t=105
```

★境界②（`cdc_bridge`）へは同一構造で、ポート名を
`cpu_mem_ready` / `cpu_mem_rd` / `cpu_mem_wr` / 物理アドレスに読み替えて配置する。★

#### ★3.3.2 C-β（`psram_ctrl`・C-2 反映）★

C-β は ★`psram_clk` ドメイン★であり、★「req 受理サイクル」というイベント★を
捉える必要があるため C-α' より記述が難しい。★2本に分ける。★

```systemverilog
`ifndef SYNTHESIS
    logic [BLEN_W-1:0] blen_shadow;   // 受理時の burst_len を保存
    logic              we_shadow;     // ★受理時の we を保存（比較用）★
    logic              xfer_active;

    always @(posedge psram_clk or negedge psram_rst_n) begin
        if (!psram_rst_n) begin
            blen_shadow <= '0; we_shadow <= 1'b0; xfer_active <= 1'b0;
        end else begin
            // ---- C-β-1: 受理サイクルで burst_len / we が不定でないこと ----
            if ((ps_state == PS_IDLE) && req) begin
                if ((burst_len === 'bx) || (we === 1'bx))
                    $error("[CONTRACT C-b1] burst_len/we is X at req accept t=%0t", $time);
                blen_shadow <= burst_len;
                we_shadow   <= we;
                xfer_active <= 1'b1;
            end
            // ---- C-β-2: 転送完了まで we が変化しないこと ----
            //   ★psram_ctrl L165 は we をポート直接参照する（受理時ラッチではない）★
            else if (xfer_active) begin
                if (we !== we_shadow)
                    $error("[CONTRACT C-b2] we changed during transfer: %b -> %b t=%0t",
                           we_shadow, we, $time);
                if (ps_state == PS_IDLE) xfer_active <= 1'b0;   // 完了
            end
        end
    end
`endif
```

> ★C-β-2 が段4 の真因を直接捉える検査器である。★
> 段4 では再送の最中に `we` が書込→読出へ変化していた。

#### ★3.3.3 C-γ（`mmio_stub`・C-2 反映）★

```systemverilog

    logic [15:0] ccr_shadow;
    always @(posedge cpu_clk or negedge cpu_rst_n) begin
        if (!cpu_rst_n) ccr_shadow <= '0;
        else begin
            // ★$FF13 への書込で CCR が変化してはならない★
            //   FLUSH は $FF12 bit1 である。$FF13 ではない（TKT-V2/KY79）
            if (wr && (addr == CCR_HI_ADDR) && (ccr_r !== ccr_shadow))
                $error("[CONTRACT C-g] CCR changed by write to $FF13 (HIT_EN unimpl) t=%0t",
                       $time);
            ccr_shadow <= ccr_r;
        end
    end
`endif
```

> ★本検査器の価値★：`HANDOVER_CHAT150` §12 は FLUSH を `$FF13` と誤記していた（TKT-V2）。
> ★アドレスを取り違えた TB は、この assert によりその場で落ちる。★

#### 3.3.4 記述上の共通要点

| # | 要点 | 理由 |
|---|---|---|
| 1 | ~~★`disable iff (!rst_n)`★ を必ず付ける~~ → ★`always` 版では `if (!rst_n)` の else 側に置く★ | リセット中の不定で誤発火させない（M-2 により記法が変わった） |

| 5 | ★`always_ff` ではなく `always` を使う★ | `$error` は合成不可という警告が出るため（M-2 実地確認） |

### 3.4 ★`$error` か `$fatal` か★

★`$error` を採用する。★

| 案 | 評価 |
|---|---|
| `$fatal` | 即停止。★ただし G-0 実行中に誤発火すると、無関係な回帰が全部止まる★ |

> `$fatal` にすると導入した瞬間に既存資産が全部止まり、
> ★本来の作業（段5）に入れなくなる★。まず `$error` で実態を観測する。

## §4. T-A：バスアクセスタスクの共有インクルード化

### 4.1 方針

`do_read` / `do_write` を ★`bus_tasks.svh` に1箇所集約★し、
各 TB は `` `include `` するだけにする。

### 4.2 記述案

```systemverilog
// bus_tasks.svh  v0.1  (2026-09-01)
//   ★契約 C-α に準拠したバスアクセスタスク。★
//   各 TB はこれを include し、独自に do_read/do_write を書かないこと。
//   ★理由: 段4 で TB 独自実装が ready の1cyc後に req を下げ、
//          同一要求が再送された（TKT-V1）。★

task automatic do_read(input logic [19:0] addr, output logic [7:0] data);
    @(posedge cpu_clk);
    cpu_mem_addr <= addr;
    cpu_mem_rd   <= 1'b1;
    // ★ready を検出した「その」サイクルで下げる（1cyc 遅らせない）★
    do @(posedge cpu_clk); while (!cpu_mem_ready);
    data       = cpu_mem_rdata;
    cpu_mem_rd <= 1'b0;
endtask

// ★M-3：do_write（C-β の遵守に直結する）★
//   注意: psram_ctrl L165 の書込条件は ★we をポート直接参照★しており、
//         ★受理時にラッチされない★。したがって wr / wdata は
//         ★ready 成立まで保持し続けなければならない★。
task automatic do_write(input logic [19:0] addr, input logic [7:0] data);
    @(posedge cpu_clk);
    cpu_mem_addr  <= addr;
    cpu_mem_wdata <= data;      // ★① addr/wdata/wr を同時に立てる★
    cpu_mem_wr    <= 1'b1;
    // ★② ready 検出まで3つとも保持する★
    do @(posedge cpu_clk); while (!cpu_mem_ready);
    cpu_mem_wr    <= 1'b0;      // ★③ ready を検出した「その」サイクルで下げる★
    @(posedge cpu_clk);
    cpu_mem_wdata <= 'x;        // ★④ wdata は wr を下げた「後」に変更する★
endtask
```

> ★要点は「ready を検出したそのサイクルで下げる」ことのみである。★
> 段4 の誤りは、検出後にもう1サイクル `@(posedge)` を挟んでいたことだった。

### 4.3 適用範囲（★限定する★）

| 対象 | 適用 |
|---|---|
| ★段5 で新規に書く TB★ | ★必須★ |
| `tb_cache_wt_poc.sv`（段4） | ★適用する★（既に正しいが、実装を1箇所へ寄せる） |
| `tb_cpu_v8b_prod_v0_3.sv` | ★適用しない★（実 CPU 駆動でありバスマスタを持たない） |
| その他既存 TB | ★適用しない★（触ると回帰の被疑が増える。1変更1検証） |

### 4.4 ★T-A 適用後の必須確認★

`tb_cache_wt_poc` を `bus_tasks.svh` 版へ差し替えた後、
★T1〜T7 が ALL PASS を維持すること★を確認する（G-2 相当の位置づけ）。
★差し替えで落ちたら、落ちた原因が共有タスク側にある。★

#### ★4.4.1 C-1：サイクル数も確認項目に加える★

キャッシュ導入後 `mem_ready` は ★組合せ出力★になる
（`v11_cache_core_design_v0_5` §7.1：`(CEN & hit & data_q_valid) ? 1'b1 : ...`）。
TB が NBA で `cpu_rd` を駆動し、それが組合せで `mem_ready` に戻る構成となるため
★同一時刻内の評価順序が絡む★。

| 確認項目 | 期待 |

> ★PASS/FAIL だけ見ていると「動くが1サイクル余計にかかる」を見逃す。★
