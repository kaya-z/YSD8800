## §1. 背景と問題

### 1.1 現象

段5-d の陽性対照⑦（`ysd8800_cache_v0_4_broken7_poc.sv`）実行時、
境界② の契約検査器 C-α' が **1 事象に対して 84 回発火**した。

発火自体は**正しい**。C-α' が問うている命題（同一要求が ready 後も保持されている）は
実際に成立しており、検査器は仕様どおりに動作している。
問題は**報告の粒度**であり、検出能力ではない。

### 1.2 なぜ段6 の着手前に是正が必要か

段6 は **発火回数を期待値に含める工程**である。

| 段5 までの判定 | 段6 の判定 |
|---|---|
| 「発火0件であること」 | 「発火が期待どおりの**回数**であること」 |

1 事象で 84 回発火する検査器を抱えたまま回数判定を導入すると：

1. ログが発火メッセージで埋まる
2. **同時に起きている別の失敗が埋没する**
3. しかも「発火した」という事実自体は正しいため、**異常として気づきにくい**

3 が本件の危険の本質である。誤検出であればログを見た時点で気づくが、
本件は正しい報告が過剰なだけなので、**見逃しの原因になっても警報が鳴らない**。

### 2.3 多重発火の機序（実源からの推定）

境界② の実装（`ysd8800_cdc_bridge_v0_4.sv` L188-206）：

```systemverilog
always @(posedge cpu_clk or negedge cpu_rst_n) begin
    if (!cpu_rst_n) begin
        cb_ready_d <= 1'b0; cb_rd_d <= 1'b0; cb_wr_d <= 1'b0; cb_addr_d <= '0;
    end else begin
        if (cb_ready_d && (cpu_mem_rd || cpu_mem_wr)
                       && (cpu_mem_rd == cb_rd_d) && (cpu_mem_wr == cb_wr_d)
                       && (cpu_phys_addr == cb_addr_d))
            $error("[CONTRACT C-a'/b2] same req held after ready: ...");

        cb_ready_d <= cpu_mem_ready;
        ...
    end
end
```

`cb_ready_d` は `cpu_mem_ready` の 1 サイクル遅延である。
したがって **`cpu_mem_ready` が複数サイクル張り付いたまま同一要求が保持されると、
そのサイクル数だけ条件が真になり、毎サイクル `$error` が呼ばれる。**

陽性対照⑦ は「C-8 違反＋中止フラグ sticky」であり、
`cpu_ready_o` が解放されない状態が継続する。84 回はこの継続長に対応する。

> ★注意（KY89）：上記の「84＝継続サイクル数」は**機序の説明であって
> 検証の期待値ではない**。是正後の期待値は §6 のとおり
> **実際に壊した DUT を走らせて確定する**。★

## §3. 是正設計

### 3.1 設計方針

> **違反は「状態」である。1 事象＝1 報告とする。**

C-β-2 との差異は**再アーム条件**である。

| 検査器 | 事象の範囲 | 再アーム条件 |
|---|---|---|
| C-β-2 | 1 転送 | 次の転送の受理サイクル（`PS_IDLE && req`） |
| **C-α'（本件）** | 違反が継続している連続区間 | **違反条件が偽になったとき** |

C-α' には「転送」に相当する自然なスコープが存在しない。
そこで**違反条件の連続区間を 1 事象とみなす**。

### 3.2 実装（境界①：`ysd8800_cache_v0_5.sv`）

```systemverilog
`ifndef SYNTHESIS
    logic                ca_ready_d, ca_rd_d, ca_wr_d;
    logic [PHYS_AW-1:0]  ca_addr_d;
    logic                ca_viol;        // ★TKT-V6: 違反条件（組合せ）★
    logic                ca_reported;    // ★TKT-V6: 1事象につき1回だけ報告★

    // ★違反は「状態」であり継続する。サイクル毎に報告すると1事象で
    //   数十回発火し、段6 の回数判定でログを埋め、別の失敗を隠す。
    //   よって★1事象につき1回だけ★報告する。（TKT-V6 / 2026-09-04）
    //   イディオムは psram_ctrl の C-β-2（cbeta_reported）と同型。
    assign ca_viol = ca_ready_d && (cpu_rd_i || cpu_wr_i)
                                && (cpu_rd_i == ca_rd_d)
                                && (cpu_wr_i == ca_wr_d)
                                && (cpu_phys_addr_i == ca_addr_d);

    always @(posedge cpu_clk or negedge cpu_rst_n) begin
        if (!cpu_rst_n) begin
            ca_ready_d  <= 1'b0;
            ca_rd_d     <= 1'b0;
            ca_wr_d     <= 1'b0;
            ca_addr_d   <= '0;
            ca_reported <= 1'b0;
        end else begin
            if (ca_viol && !ca_reported) begin
                $error("[CONTRACT C-a'] same req held after ready: addr=%h rd=%b wr=%b t=%0t",
                       cpu_phys_addr_i, cpu_rd_i, cpu_wr_i, $time);
                ca_reported <= 1'b1;
            end
            else if (!ca_viol) begin
                ca_reported <= 1'b0;    // ★事象終了で再アーム★
            end

            ca_ready_d <= cpu_ready_o;
            ca_rd_d    <= cpu_rd_i;
            ca_wr_d    <= cpu_wr_i;
            ca_addr_d  <= cpu_phys_addr_i;
        end
    end
`endif
```

### 3.3 実装（境界②：`ysd8800_cdc_bridge_v0_5.sv`）

同一構造。信号名のみ `cb_viol` / `cb_reported`、参照信号は
`cpu_mem_rd` / `cpu_mem_wr` / `cpu_phys_addr` / `cpu_mem_ready`。
メッセージ文字列 `[CONTRACT C-a'/b2]` は**変更しない**（既存ログ grep 手順との互換のため）。

### 3.4 ★変更しない事項（明示）★

| # | 事項 | 理由 |
|---|---|---|
| 1 | 違反条件そのもの（`ca_viol` の論理式） | 検出能力を変えない。**変えるのは報告の粒度のみ** |
| 2 | `$error` のメッセージ書式 | 既存の grep／ログ判定手順が依存 |
| 3 | `` `ifndef SYNTHESIS `` の囲い | 工程③ へ検査器を持ち込まない方針は不変 |
| 4 | 遅延レジスタ（`*_ready_d` 等）の更新位置 | 段5 まで正しく動作している。触らない |
| 5 | 境界③ C-γ（`mmio_stub` L450） | 多重報告の事実がない。★本件の範囲外★ |

### 3.5 設計上の性質

| 性質 | 説明 |
|---|---|
| 検出能力の保存 | 違反が発生すれば**必ず 1 回は**報告される。落とすのは 2 回目以降の重複のみ |
| 別事象の分離 | 違反が一旦解消して再発した場合、`ca_reported` が再アームされるため**再び報告される** |
| 偽陰性のリスク | 「違反が連続する区間の途中で、別アドレスの違反が始まる」場合、2 件目が抑止され得る。ただし C-α' の条件は `ca_addr_d` との一致を含むため、**アドレスが変われば `ca_viol` は一旦偽になり再アームされる**。よってこのケースは成立しない |
| 合成への影響 | なし（`` `ifndef SYNTHESIS `` 内） |
| 実行性能 | `assign` 1 本と FF 1 個の追加。無視できる |

### 6.2 ★V-2 を主判定器とする理由（KY89）★

> 「発火 0 件になった」は、**検査器を壊しても達成できる**。
> 是正が「重複だけを落とし、検出能力を保存した」ことを示すには、
> ★実際に違反する DUT を走らせ、1 回だけ発火することを確認する★以外にない。

これは段5 で得た KY89（設計書の症状予測を期待値にしない。
期待値は実際に壊した DUT を走らせて決める）の直接の適用である。

### 6.3 実施順序

```
1. rtl6.f 作成 → V-1（正常 DUT・発火0件）
2. 陽性対照⑦ を v0_5 ベースへ移植 → V-2（★1回発火★）
3. V-3（G-0 LAT=12）
4. V-4（G-C1 CEN=1／LAT=12）
5. md5 実測・ledger 登録
```

★V-2 を V-3/V-4 より先に置く。★
非退行試験を先に通すと「通ったから良い」で V-2 が省略される危険がある（KY80 と同型の心理）。

| 事項 | 理由 |

| G-0 LAT=5 ビン | 本変更は `` `ifndef SYNTHESIS `` 内の**報告粒度のみ**であり、レイテンシ依存の論理に一切触れない。LAT=12 で非退行が示せれば命題は閉じる |
| G-2（ビルド回帰） | RTL のみの変更であり、ツールチェーン・バイナリに影響しない |
| 陽性対照①〜⑥ の再実行 | いずれも「発火するか否か」の試験であり、回数に依存しない |
