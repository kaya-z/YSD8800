## §3. 実施内容

### 3.1 ★T-1：emu23 ゴールデン測定（ヒット率 *h* の取得）★

★検証順序は §8.5 の指定どおり「emu23 → RTL → 差分確認」とする（KY-K-add7）。★
RTL 実測（§2）は既にあるが、★emu23 側を先に確定させてから突合する★。
逆順にすると、★RTL の値に合うようにモデル側の解釈を後付けする誘惑が生じる★。

**★M-1 反映：取得手段を `--trace-addr` へ変更した（2026-09-04）★**

~~`./emu23 yuios_road2.bin --cache-size 8192 --cache-line 32 --cache-stats`~~

★**`--cache-stats` では *h* も *f* も取得できない。**★

| 実源 | 内容 |
|---|---|
| `emu23_v2_15.c` L595 | `stat_hit` / `stat_miss` / `stat_charged` の3変数のみ |
| L808 | `if (hit) stat_hit++; else stat_miss++;` — ★`is_write` を見ずに一括計上★ |
| L645-659 | `cache_report_summary()` の出力は `hit` / `miss` / `rate` / `charged` の ★4値のみ★ |

→ ★アクセス種別の内訳が出力に一切残らない。★
→ ★読みと書きを事後に分離できず、フェッチとデータ読みも区別できない。★

**★正しい取得手段（L810-816・実装済）★**

```c
if (trace_fp) {
    char k = (kind == ACC_FETCH) ? 'F' : (is_write ? 'W' : 'R');
    fprintf(trace_fp, "%llu,0x%05X,%c,%d\n",
            (unsigned long long)cpu.cycle, pa, k, hit);
}
```

★1 アクセスごとに「cycle, 物理アドレス, 種別(F/W/R), hit(0/1)」を CSV 出力する。★
★これを集計すれば *h* も *f* も両方得られる。★

**採用コマンド**

```
./emu23 yuios_road2.bin -mc --mem-latency <定義> \
        --cache-size 8192 --cache-line 32 --trace-addr trace.csv
```

★`--cache-stats` は総計の照合用として別途併用する★
（`--trace-addr` と同時指定するとトレースが抑止されるため・L3823）。

**集計は Python 後処理とする**（emu23 側 L739 以降のトレースヘッダの枠組みに乗せる）。

**RTL 構成との対応（★C-2 反映：レビュー確認結果を転記★）**

| 項目 | RTL（`ysd8800_cache_v0_5.sv`） | emu23 | 確認 |
|---|---|---|---|
| ライン数 | 256（`IDX_W=8`） | — | ⬜ |
| ラインサイズ | 32 B（`BLEN_W=6`） | `--cache-line 32`（★既定 32★） | ⬜ |
| 総容量 | 256 × 32 = ★8,192 B★ | `--cache-size 8192`<br>★**既定は 16384。指定を忘れると黙って 2 倍の構成で走る**★ | ⬜ |
| 方式 | ダイレクトマップ・ライトスルー／ノーライトアロケート | ★一致★（L791-806 で確認済）<br>書き：`add = lat[kind]-1`（ヒット/ミスによらず PSRAM 到達・ラインを確保しない）<br>読みヒット：`add = 0`<br>読みミス：`add = (cache_line × lat[FILL]) - 1` | ✅ |
| ★充填コスト構造★ | ★`LAT + 31`（②-A バースト）★ | ★`cache_line × FILL` ＝ 32 × FILL（クリティカルワードファースト無し・L801）★ | ★**不一致**（→ §3.2A）★ |

> ★`--cache-size` の既定が 16384 である点に注意。★
> ★指定漏れは黙って通り、構成不一致のまま突合してしまう（R-2 そのもの）。★

### 3.2 ★T-2：予測削減量の算出★

**必要な独立変数**

| 記号 | 意味 | 取得元 |
|---|---|---|
| *h* | 読みヒット率 | ★T-1（`--trace-addr` の集計。`k=='R'` および `k=='F'` の hit 率）★ |
| *f* | ★**読みアクセス（F + R）に占める命令フェッチ（F）の割合**★ | ★T-1（`--trace-addr` の集計）★ |
| 書き比率 | W / (F + R + W) | ★T-1（同上）★ |
| LAT | PSRAM レイテンシ | 12（本番想定値） |

**★M-2 反映：*f* の定義を是正した（2026-09-04）★**

~~*f* =「全メモリアクセスに占める命令フェッチの割合」~~ ★**分母に書きを含めるのは誤り**★

*f* が設計書 §6.3／§6.4 で使われている文脈は ★ヒット遅延の非対称性★
（★フェッチは 1 cyc ヒット、データアクセスは 2 cyc ヒット★）の重み付けである。
損益分岐の式は

```
f·(1·h + P(1−h)) + (1−f)·(2h + P(1−h)) < 現行
```

という形で、★`f` と `1−f` は**読みの内訳**を分けるものとして使われている★。
→ ★分母に書きを含めると `f` が過小になり、予測削減量を系統的に誤る。★

★**T-2 着手前の必須確認**★：設計書 §6.4 の仮定値 *f* が
★どちらの定義であったかを実源で確認し、置き換えの際に定義がすり替わらないようにする★。
v0.6 §9.2.4 の「実測 *f* で仮定を置き換える」が本工程の要求事項である以上、
★定義の一致は必須★である。

### 3.2A ★前提の明示：emu23 と RTL で充填コストの構造が異なる（N-1 反映）★

| | 充填コスト |
|---|---|
| emu23（L801） | ★`cache_line × FILL` ＝ 32 × FILL★（1 バイトずつ 32 回分） |
| RTL（②-A バースト） | ★`LAT + 31` psram cyc★（初回 LAT の後、1 バイト/サイクル） |

★これは「emu23 は CPI=1 固定だからサイクル一致はあり得ない」という既知事項とは**別の**差異である。★
★構造そのものが違うため、`FILL` に何を与えるかで予測削減量が大きく動く。★

→ ★§3.3 は「削減の桁と傾向を見る」としているが、桁を見るだけでも
　　`FILL` の設定次第で 1 桁動き得る。★
→ ★T-2 で式を確定する際、`FILL` の選び方とその根拠を明文化する。★

> ★A-2（式を事前固定しない）と矛盾しない。★
> ★固定しないと言っているのは**式**であって、**前提の明示**はむしろ必要である。★

★*f* は v0.6 時点では**仮定値**であった（§9.2.4 L1327）。★
★段6 で実測 *f* を得て仮定を置き換えることが、本工程の要求事項の一つである。★

**予測式**

読みヒットはキャッシュ内で完結し（0 サイクル）、読みミスはラインフィル（LAT_FILL）を要する。
書きはライトスルーゆえ常に下流へ抜ける。よって

```
予測削減 ≒ (読みアクセス数) × h × (1回あたりの節約サイクル)
```

★「1回あたりの節約サイクル」の確定には、PSRAM バースト（②-A）の
　ライン充填コストを考慮する必要がある。★
→ ★具体式は T-1 の実測値を見てから確定する（KY89：症状予測を期待値にしない）。★
→ ★本計画では式を先に固定しない。★ 固定すると★実測を式に合わせて解釈する★危険がある。

### 11.2 ★T-2：予測削減量（式は実測後に確定・A-2 のとおり）★

### 11.3 ★T-3：突合 → **整合**★

| | 値 | 削減率 |
|---|---|---|
| 予測削減 | **1,903,905** | 50.70% |

★§8.5 ②「独立変数から立てた予測と実測の整合」は成立。★
乖離 8.4% は ★*P* = 10（§6.4 が「約 8〜9 を保守側に丸めた」値）★ と
★基準 4 cyc という粗い近似★ から生じるもので、★予測が保守側に外れる方向★として説明がつく。
→ ★キャッシュ実装・測定系ともに妥当と判断する。★

★削減の約 90% はフェッチ由来★（1,711,065 / 1,903,905）。
§6.3 で見出した「`mem_addr` の default 代入によりフェッチが 1 cyc ヒットになる」
非対称性が、そのまま効果の主因になっている。

### 11.4 ★N-1（充填コスト構造差）は本測定に影響しなかった★

| | 充填コスト |
|---|---|
| emu23 | `line × FILL` = 32 × FILL |
| RTL | `LAT + 31` |

★*h* と *f* はヒット/ミス判定のみで決まり、**レイテンシ値に依存しない**。★
→ ★emu23 は独立変数（*h*・*f*）の供給源に徹し、コストモデル（*P*）は RTL 側で閉じている。★
→ ★構造差は予測に混入しない。★

> ★教訓：モデル間の差異は「どの量をどちらから取るか」を分離すれば無害化できる。★
> ★差異があるからといって突合を諦める必要はない。★

### 11.5 ★測定上の注意（申し送り）★

★`--trace-addr` をファイルに落とすと 20 秒で 1.46 GB に達した。★
→ ★必ずストリーム集計すること★（`agg_trace_v1_0.py`：stdout の M-5 マーカー検出で停止）。
→ emu23 には★実行ステップ上限のオプションが無い★ため、停止条件は外部から与える必要がある。
