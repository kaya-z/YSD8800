## 1. 確定した真因（Step 8-I 検証で実証済み）

**emu23のIRET命令（case 0x04）が、IRQ種別を問わず無条件に `YSD8002_iret()` を呼び、
タイマーの次回発火サイクルを `現在cycle + period` へ再設定している。**

これにより、タイマー以外のIRQ（IRQ1=YSD8004経由）のハンドラがIRETするたびに
タイマーの次回発火が後ろへ先送りされ、IRQ1高頻度発火時にタイマーIRQが大量欠落する。

### 1.1 設計書違反であることの根拠
`ysd8002_timer_design_v1_0.docx §5.3` は明確に規定している:
> 「IRQ0（タイマー）のみを対象とする。**他のIRQ（align, syscall等）のIRETでは呼び出さない。**
>  呼び出し判定（タイマーIRQか否か）はemu22側で行う。」

すなわち当初設計は正しく、**実装が設計書に違反していた**（実装バグ）。

### 1.2 実証データ（irqtest）
| 条件 | タイマー受理（理論983） |
|---|---|
| 衝突なし | 983（正常） |
| 衝突あり・現行v1.06 | 1（欠落） |
| 衝突あり・修正試行(FIX_IRET) | 983（完全復活） |

### 1.3 これまで実害が顕在化しなかった理由
Dhrystone/yuios通常動作はUART送信完了IRQ・ストレージEXEC完了IRQを
高頻度では発生させないため、タイマーとIRQ1の衝突がほぼ起きなかった。
ただしドライバタスク化・実用負荷では確実に顕在化する構造的欠陥。

## 2. 修正方式の比較

### 案1: タイマーIRQ実行中フラグ方式（FIX_IRET・検証済み）
タイマーIRQ受理時に `timer_in_service=1` を立て、IRET時に
このフラグが立っている時のみ `YSD8002_iret()` を呼ぶ（呼んだらクリア）。

```c
/* IRQ受理部 (exec_one) */
int irq = cpu.irq_pending;
if (irq == 1) timer_in_service = 1;   /* タイマーIRQ受理 */
...
/* IRET (case 0x04) */
if (timer_in_service) {
    YSD8002_iret(cpu.cycle);
    timer_in_service = 0;
}
```

- ✅ 設計書§5.3の「タイマーIRQのIRETでのみ呼ぶ」を素直に実装
- ✅ 検証で欠落完全解消（1→983）を実証済み
- ⚠️ ネスト割り込み（ハンドラ内EI）時にフラグが単純bool だと不正確になりうる
      → 本プロジェクトは原則ネスト禁止（§3.2）。EIでのネストは稀。要レビュー(R1)
- FPGA整合: ハードでは「タイマーIRQ ACK」が next 再設定トリガになるのが自然。
  フラグ方式はこのACKセマンティクスのソフトモデル化として妥当。

### 案2: タイマー自律フリーラン方式
`YSD8002_iret` を廃止し、タイマーが受理の有無に関わらず
`next_irq_cycle += period` で自律的に次回発火を進める（オートリロード）。

- ✅ IRET命令とタイマーを完全分離（責務分離が最もクリーン）
- ✅ 実機ハードタイマー（フリーランカウンタ）に最も忠実
- ❌ 現行の `next_irq_cycle = UINT64_MAX`（IRET前連続発火防止）方式と非互換。
      タイマーIRQ未処理のまま次が来る「割り込み取りこぼし」挙動が変わる
- ❌ 影響範囲大。Dhrystone計測（SW_START/STOP）の挙動再検証が必要
- ❌ §5.2注記「UINT64_MAX方式でIRET前連続発火を防ぐ」という確定仕様を変更することになる

### 案3: IRQ番号を引数化して判定をYSD8002_iret内に閉じ込め
`YSD8002_iret(cycle, irq_id)` とし、内部で `if(irq_id==0) 再設定`。

- ✅ 判定ロジックをタイマーモジュール内に集約
- ⚠️ IRET時点では「どのIRQから戻るか」の情報が無い（受理時にしか分からない）
      → 結局タイマー実行中フラグか、IRQ番号スタックの保持が必要。案1の変形

## 3. 採用案（提案）: **案1（タイマーIRQ実行中フラグ方式）**

理由:
1. 設計書§5.3の規定をそのまま実装でき、**設計と実装の乖離を解消する最短経路**
2. `next_irq_cycle = UINT64_MAX` 方式（§5.2確定仕様）を変更せず、影響範囲が最小
3. 検証で欠落完全解消を実証済み（リスク低）
4. FPGA実装時は「タイマーIRQ ACK信号で next カウンタをリロード」に自然に対応

### 3.1 実装詳細
- 追加変数: `static int timer_in_service = 0;`（emu23グローバル）
- exec_one IRQ受理部: `if (irq == 1) timer_in_service = 1;`
  （irq_pending==1 がタイマー。emu23のIRQ番号ずれに注意: pending=1→IRQ0タイマー）
- case 0x04 IRET: `timer_in_service` が真の時のみ `YSD8002_iret()` 呼出＋フラグクリア
- 既存の無条件 `YSD8002_iret(cpu.cycle);` を上記条件付きに置換

### 3.2 ネスト割り込みの扱い（R1論点）
§3.2「IRQ受理時IE=0、原則ネスト禁止。ハンドラ内EI実行時のみ高優先ネスト許可」。
タイマー(IRQ0)は外部最高位なので、タイマーハンドラ内でEIしても
それより高優先はNMI(IRQ3)のみ。NMIハンドラはHALT想定のためIRET戻りなし。
よって単純boolフラグで実害は出ない見込み。ただしレビューで妥当性確認(R1)。

## 3.3 FPGA実装への影響（v0.2追記）

### 3.3.1 結論
案1の `timer_in_service` フラグは**ソフトウェアエミュレータ固有の足場**であり、
FPGAのRTLには写像されず消滅する。よって案1採用によるFPGA実装の追加手間は
ほぼゼロ。むしろ emu23 から「IRET命令にタイマー再設定が相乗りする」という
非ハード的構造を除去するため、将来のFPGA実装との整合性は向上する。

### 3.3.2 根拠：YSD8002_iret はソフト固有の擬似モデル
emu23 の `YSD8002_iret` 問題の本質は、「IRET命令の実行」という1点に
「タイマー次回発火サイクル再設定」を相乗りさせた逐次実行モデル特有の構造。
ハードウェアのタイマー（MC6840 PTM / 6522 VIA 系の自走カウンタに相当）は、
カウンタが0到達で IRQ アサート＋PERIOD自動リロードを行い、CPUの IRET や
どのIRQを処理中かとは**物理的に無関係**にクロックで自走する。すなわち
「他IRQのIRETで先送りされる」現象はハードには元々存在しない。

### 3.3.3 案1のRTL写像（概念）
```systemverilog
always_ff @(posedge clk) begin
  if (rst) begin
    cnt <= PERIOD; timer_irq <= 1'b0;
  end else if (cnt == 16'd0) begin
    cnt <= PERIOD;            // オートリロード（CPU非依存）
    timer_irq <= 1'b1;        // IRQアサート
  end else begin
    cnt <= cnt - 16'd1;
    if (timer_ack) timer_irq <= 1'b0;  // ハンドラACK/クリアで落とす
  end
end
```
→ `timer_in_service` 相当のレジスタ・ロジックは一切現れない。

### 3.3.4 案1 vs 案2 のFPGA観点での逆転
- ソフト（emu23）: 案1=影響最小 / 案2=影響大
- FPGA: **案2（自律フリーラン）こそハードの自然な姿**
- ただし emu23 と FPGA は別レイヤであり、それぞれに最適な実装でよい。
  emu23 の責務は「ISA2.3 をサイクル精度で正しく再現」すること。案1はこれを
  最小リスクで達成。FPGA は別途ハード自然形（自走カウンタ=案2的）で記述する。
  両者の内部構造が一致する必要はなく、**外部から観測されるIRQ発火列が一致**
  すれば等価。これがエミュ⇔FPGA等価性検証の基準となる。

### 3.3.5 案1採用時のFPGA影響まとめ
| 観点 | 影響 |
|---|---|
| RTL追加ロジック | なし（timer_in_serviceはハードに写像されない） |
| タイマーモジュール | 自走カウンタ＋オートリロード（どの案でも結局これ） |
| IRET命令のRTL | スタックpop＋PC/FLAGS復帰のみ。タイマーへの配線不要 |
| 割り込みコントローラ | §3.1固定優先順位の優先度エンコーダを組むのみ |

### 3.3.6 等価性検証時の唯一の留意点
emu23 は `next_irq_cycle = UINT64_MAX` で「IRET前の連続発火を防ぐ」方式
（§5.2確定仕様＝オーバーラン抑止）。FPGAの自走カウンタを素朴に書くと、
ハンドラ処理中でもカウンタ0到達で次IRQをアサートしうる。emu23と挙動を
合わせるには、FPGA側に「timer_irqがクリアされるまで次のリロード由来IRQを
ペンドさせない（1段ラッチで握る）」ロジックが要る。period=40000サイクルでは
実害はまず出ない稀ケースだが、**将来のエミュ⇔FPGA等価性検証で
この境界挙動を1項目として確認**すること。
