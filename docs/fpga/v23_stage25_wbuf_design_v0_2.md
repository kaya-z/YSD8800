## §1. 目的と到達目標

### 1.1 目的

★書込ストールを吸収するライトバッファ（深さ D=2）を実装し、CPU が PSRAM 書込の
完了を待たされる時間を削減する。★

### 1.2 目標値

| 量 | 値 | 格 |
|---|---|---|
| 書込ストール率（上限） | ★13.2%★ | ★RTL 実測★（`v18` v0.5 §11.4） |
| α(2)（吸収率） | 1.0000 | ★モデル推定★（`v19` v0.8 §5.1.7.3） |
| 実効削減率（見込み） | ★13.20%★ | ★上記2つの積＝推定値★ |

> ⚠ ★13.2% は RTL 実測だが α はモデル推定値である。★
> ★「13.2% の削減が実測で確認された」と引用してはならない★（`v19` v0.8 §4.6）。
> ★α(1)=0.998 は artifact であり引用禁止★（同 §5.4.4）。

### 1.3 ★深さが D=2 である理由（構造的帰結）★

★8bit バス上で 16bit 書込が 2 トランザクションに分かれる以上、
1 回の書込命令を丸ごと受け止めるには 2 スロット要る。★
書込の 95.9% が 16bit ペアであり（Dhrystone 実測）、★D=1 の吸収率は 0.5 が構造的上限★。

★「D=1 は脆いから安全側に D=2」ではない。「D=1 では構造的に足りない」である。★

## §2. 現行書込経路（実ソース確認済・2026-09-18）

### 2.1 経路

```
CPU → addr_decoder → MMU → cache v0.6 → cbr_* → cdc_bridge v0.5 → psram_ctrl v0.3
                   ↘ mmio_stub v0.9（★別経路★）
```

### 2.2 実装の実体

| 箇所 | 実装 | 出典 |
|---|---|---|
| 書込の下流出力 | `br_wr_o = cpu_wr_i`（★素通し★） | `ysd8800_cache_v0_6.sv` L519 |
| 書込時の ready | `cpu_ready_o = br_ready_i`（★CDC 直結★） | 同 L526-528 |
| 書込ヒット時 | `wr_hit = ccr_cen_i & cpu_wr_i & hit`（★キャッシュも更新★） | 同 L349 |
| CDC の req | `req_level = (cpu_mem_rd｜cpu_mem_wr) & ~suppress_r` | `ysd8800_cdc_bridge_v0_5.sv` L130 |
| CDC の ready | `cpu_mem_ready = suppress_r`（assign 出力） | 同 L121 |

★書込は cache を素通りして CDC の ready をそのまま待っている。これが `stall_wr` の実体である。★

### 2.3 ★確認事項の解消（設計前提の確定）★

| # | 確認事項 | 結果 | 根拠 |
|---|---|---|---|
| ★1★ | MMIO 書込が `cbr_*` を通るか | ★**通らない**★。`is_mmio = (addr >= $FC80)` で分岐し、MMIO は `mmio_*` で `mmio_stub` へ直行。キャッシュ入力は `ram_wr` のみ | `membus_v0_12.sv` L198 / L354 / L414 / L497 |
| ★2★ | 契約 C-α'（TKT-V1）との関係 | ★cache の**上流**（CPU 側）を監視しており本改修の直接対象外。ただし §6.2 の注意あり★ | `cache_v0_6.sv` L536-580 |
| ★3★ | 書込ヒット時にキャッシュが更新されるか | ★**更新される**（`wr_hit`）★。方式A の前提が成立 | 同 L349 |

★①が「通らない」であったことは重要である。★
★MMIO はレジスタ書込の副作用順序が意味を持つため、バッファに入れてはならない。★
★経路が最初から分かれているため、本設計で特別な抑止を設ける必要がない。★

## §3. 設計方針

### 3.1 挿入位置

★cache の下流／cdc_bridge の上流（cpu_clk 域）に新規モジュールとして挿入する。★

```
cache v0.6 → ★wbuf v0.1★ → cdc_bridge v0.5 → psram_ctrl v0.3
```

| 採用理由 | 内容 |
|---|---|
| ★1★ | ★cdc_bridge の内部に手を入れない★。CDC は工程①.5 で −21.3% を出した最も繊細な部位であり、ここを触れば全性能測定のやり直しになる |
| 2 | cache の内部にも手を入れない。TKT-V7 の修正直後であり、`fill_*` 系の状態に隣接した改修は避ける |
| 3 | ★cpu_clk 単一ドメインで閉じる★。CDC 跨ぎ状態を新設しない（§6.1） |

### 3.2 ★方式A（ドレイン方式）の採用★

★PSRAM 読出の前にバッファを空にする。アドレス比較によるフォワーディングは行わない。★

| 方式 | 内容 | 判定 |
|---|---|---|
| ★A：ドレイン★ | PSRAM 読出要求の前にバッファを空にする | ★**採用**★ |
| B：フォワーディング | バッファ内容と読出アドレスを比較し一致すれば転送 | ★不採用★ |

★採用根拠（実測に基づく）★：

| # | 根拠 |
|---|---|
| ★1★ | ★CEN=1 の読出ヒット率は 99.73%（段6 実測）であり、ヒット時は PSRAM へ読出要求を出さない★（`br_rd_o` はフィル時のみ 1・L517）。★PSRAM を読むのは全読出の 0.27% だけ★で、ドレイン発生頻度はごく低い |
| ★2★ | ★書込ヒット時はキャッシュも更新される（`wr_hit`）★ため、書込直後の読出はキャッシュがヒットで答える。★バッファ内の未書込データを読む経路はフィル時のみに限られる★ |
| ★3★ | ★方式B は比較器・データ選択・追加状態を要し、TKT-V7 と同型の「無言のデータ破壊」の面積を広げる★。見返り（0.27% の経路の高速化）に見合わない |

### 3.3 ★方式A の既知の限界（明記）★

★CEN=0 では全読出が PSRAM へ出るため、ドレインが多発しライトバッファの効果はほぼ消える。★
★これは仕様である。CEN=0 は評価用モードであり、本番構成は CEN=1 であるため実害はない。★

★ただし CEN=0 の性能測定値は本改修の前後で変わりうる。★
★測定時は CEN=0/CEN=1 の双方を採り、CEN=0 側の悪化がドレインで説明できることを確認する（§7.3）。★

## §4. 構造設計

### 4.1 ★バッファの形★

★「アドレス＋データのレジスタ 2 組」ではなく、
「アドレス 1 本 ＋ 2 バイトのデータ ＋ バイト有効フラグ」を採る。★

| 要素 | 幅 | 意味 |
|---|---|---|
| `wb_addr_r` | PHYS_AW | ★バッファに入っている**最初のバイト**のアドレス★ |
| `wb_data_r[0]` | 8 | 下位バイト |
| `wb_data_r[1]` | 8 | 上位バイト |
| `wb_be_r[1:0]` | 2 | ★バイト有効フラグ★ |
| `wb_valid_r` | 1 | バッファ有効 |

★根拠★：16bit 書込のペアはアドレスが連続している
（回答書 `answer_v21_stage7b_alpha_fragility_v1_0.md` §4.3）。
★TKT-V10 が「この形で要件を満たすか確認すること」と指示していた事項に対する結論である。★

#### 4.1.1 ★【v0.2 是正】ペア判定は「偶数境界」ではなく「±1」で行う★

★v0.1 は `wb_addr_r` を「ペアの先頭アドレス（偶数境界）」と定義していたが、
**16bit アクセスが常に偶数境界から始まるという保証は無い**。★

| 事実 | 実源 |
|---|---|
| scc23 の大域データはオブジェクト単位で偶数バイトに丸められる | `scc23_v2_07.c` L4622 |
| ★これはオブジェクトの「大きさ」の話であり、構造体メンバのオフセット・ポインタ演算・キャスト経由の 16bit アクセスまで偶数を保証しない★ | 同 L4616-4622 |
| ★ISA2.3／バスはバイトアドレッシングであり整列の要求は無い★ | `addr_decoder`（8bit データ幅） |

★典型的には偶数になるが、保証ではない。★
★保証でないものを前提に置くと、外れたときに「稀にしか起きない誤り」になる——最も高くつく形である。★

★是正★：★2 バイト目の受理条件を `up_addr_i == wb_addr_r ± 1` とする。★

| 利点 | 内容 |
|---|---|
| 1 | ★偶数境界かどうかを一切問わない（前提そのものが消える）★ |
| 2 | ドレインは `wb_addr_r`（小さい方）から 2 バイト連続で出すだけ |
| 3 | 8bit 単発は `wb_be_r` の片側のみ ＝ §4.2 の表はそのまま成立 |
| ★4★ | ★`±1` としたのは、16bit 書込が下位バイト先行か上位バイト先行かを設計が仮定しないためである。どちらでも同じ挙動になる（仮定を 1 つ減らせる）★ |

★これにより実装の分岐が減り、KY98（暗黙前提は密着ケースで破れる）の芽も摘める。★

### 4.2 ★この形で要件を満たすかの検証★

| ケース | 充足 | 備考 |
|---|---|---|
| 16bit 書込（連続アドレス・95.9%） | ★○★ | 1 エントリで 2 スロット分を保持 |
| 8bit 書込単発 | ★○★ | `wb_be_r` の片側のみ 1 |
| ★連続しない 2 書込が続けて来る場合★ | ★△★ | ★1 エントリでは保持できない。先行分をドレインしてから受ける（§5.3）★ |

> ⚠ ★これは「D=2 相当の吸収」を常に保証するものではない。★
> ★アドレス連続の 16bit ペアに対してのみ D=2 相当となる。★
> ★書込の 95.9% がペアであるため実効上は足りるが、★
> ★「D=2 の汎用キューを置いた」のとは**別物**である。この差を §7.4 で測定して確認する。★

### 4.3 インタフェース

| 方向 | 信号 | 接続元/先 |
|---|---|---|
| 上流（cache 側） | `up_addr_i` / `up_wdata_i` / `up_wr_i` / `up_rd_i` / `up_ready_o` / `up_rdata_o` | cache の `br_*` |
| 下流（CDC 側） | `dn_addr_o` / `dn_wdata_o` / `dn_wr_o` / `dn_rd_o` / `dn_ready_i` / `dn_rdata_i` | cdc_bridge の `cpu_mem_*` |
| 制御 | `wbuf_en_i` | ★CCR 経由（§4.5）★ |
| 観測 | `dbg_wb_hit_o` / `dbg_wb_drain_o` / `dbg_wb_full_o` | ★TB 観測用（§7.2）★ |

### 4.4 動作

| # | 事象 | 動作 |
|---|---|---|
| 1 | 書込・バッファ空 | ★`up_ready_o` を **同一サイクル（純組合せ）** で返す★。エントリに登録。下流へ req 開始 |
| 2 | 書込・★`wb_addr_r ± 1` の隣接バイト★ | ★同じく同一サイクルで返す★（`wb_be_r` の他方を立てる） |
| 3 | 書込・別アドレス（連続でない） | ★ドレイン完了まで `up_ready_o=0`★。完了後に受理 |
| 4 | ★読出要求（`up_rd_i`）★ | ★`wb_valid_r` が 1 の間 `up_ready_o=0` とし、ドレイン完了後に下流へ読出を通す★ |
| 5 | ドレイン中 | 下流 `dn_wr_o` を保持し `dn_ready_i` を待つ。バイト単位で順次 |
| 6 | `wbuf_en_i=0` | ★全面バイパス（純組合せ素通し）★。§4.5 |

#### 4.4.1 ★【v0.2 追加】`up_ready_o` の生成方式★

★`up_ready_o` は**純組合せ**で生成する（登録出力にしない）。★

| 状態 | `up_ready_o` |
|---|---|
| `wbuf_en_i=0`（バイパス） | ★`dn_ready_i` 素通し★ — 現行 `cpu_ready_o = br_ready_i`（L526-528）と同一 |
| 書込・受理可 | ★1（同一サイクル）★ |
| 書込・ドレイン待ち | 0 |
| 読出・`wb_valid_r=1` | 0（ドレイン完了まで） |
| 読出・`wb_valid_r=0` | `dn_ready_i` 素通し |

★理由★：★現行の書込は純組合せ素通しであり、バイパス時に W-0 の完全一致を取るにはこの経路を
維持しなければならない。★
★有効時に登録出力へ変えると 1 サイクルの差が生じ、W-0 以外のビンで波形が変わる。★
★それ自体は想定内だが、明示しておかないと「効果」と「レイテンシ変化」が測定値の中で混ざる。★

### 4.5 ★イネーブル制御（CCR）★

★`wbuf_en_i=0` で現行と**ビット単位・サイクル単位で同一**の波形になること。★

これは段2 のキャッシュ導入時に採られた手法と同じである
（`membus_v0_12.sv` L523-525 の記述）。★これにより★：

- ★G-0（バイト完全一致）を無改修状態で再確認できる★
- ★改修前後の比較測定が同一ビットストリームで行える★
- ★不具合時に切り分けの起点が確保される★

★CCR のビット割当は TKT-V11 と併せて決定する（§8.1）。★
★ただし**測定は `mmio_stub` の `_poc`（`wbuf_en` リセット値 `1'b1`）で行うため、
CCR ビット割当は本改修の前提条件ではない**。★
★TKT-V11 への順序依存は存在しない。★

## §5. ハザードと対策

### 5.1 ★読出ハザード（方式A の中核）★

★危険★：バッファに未書込データがある状態で PSRAM 読出が走ると古い値を読む。

★対策★：`up_rd_i` が来たとき `wb_valid_r=1` なら ★ドレイン完了まで `up_ready_o=0`★。

★この検査は「アドレスが一致するか」を見ない。★
★一致判定を入れれば方式B になり、比較器と誤判定の余地が生じる。★
★**valid なら無条件に待つ**——これが方式A の安全性の源である。★

### 5.2 ★フィルとの関係★

★CEN=1 のフィルは 32 バイトのバースト読出である（`burst_len_o = LINE_SIZE`）。★
フィル開始は `fill_req = ccr_cen_i & miss & cpu_rd_i` であり、★`up_rd_i` として現れる★。
したがって §5.1 の対策がそのままフィルにも効く。★特別扱いは不要。★

### 5.3 書込ハザード

★危険★：連続しないアドレスへの書込が続くと 1 エントリでは保持できない（§4.2）。

★対策★：★先行分をドレインしてから受理する★（`up_ready_o=0` で待たせる）。
★この場合の性能は現行と同等であり、悪化はしない。★

### 5.4 ★リセット・FLUSH との関係★

| 事象 | 要件 |
|---|---|
| リセット | ★`wb_valid_r <= 0`★ |
| ★CCR FLUSH★ | ★**ドレインを先に完了させてから** FLUSH を実行すること★ |
| ★CEN 立下り★ | ★同上★ |

> ⚠ ★これはライトバックで問題になる「書き戻していないデータを捨てる」のと同型である。★
> ★ライトスルーであっても、バッファに滞留している間は同じ危険が生じる。★
> ★FLUSH/CEN の意味論そのものは変えないが、**タイミングの制約が新たに加わる**。★

#### 5.4.1 ★【v0.2 追加】ドレイン先行は誰が保証するか★

★保証の主体は wbuf モジュール自身とする。★

| 方式 | 内容 | 判定 |
|---|---|---|
| ★(i)★ | ★wbuf が `flush_req_i` / `cen_falling_i` を受け、`wb_valid_r=0` になるまで `flush_ack_o` を返さない★ | ★**採用**★ |
| (ii) | CCR 書込を受けた側（mmio_stub／cache）がドレイン完了を待ってから FLUSH を発行 | ★不可★ |

★(ii) を不可とする理由★：★CCR 書込を受けた側にバッファの状態を見せることになり、
モジュール間に新たな依存が生じる。★
★wbuf の内部状態は wbuf の外へ出さない——これは §3.1 で cdc_bridge / cache の内部に
手を入れないと決めた方針と同じ筋である。★

★`flush_req_i` / `flush_ack_o` のハンドシェイクは §4.3 のインタフェースに追加する。★

## §6. ★TKT-V7 の教訓の適用★

### 6.1 ★CDC 跨ぎ状態を新設しない★

★TKT-V7 は、ライトスルーという最も単純な設計ですら
CDC を跨ぐ状態（`beat_cnt_r`）の不備で 4 ゲート段階にわたり無言でデータを壊した（KY99）。★

★本設計は cpu_clk 単一ドメインで閉じる。★
★`dn_ready_i` は cdc_bridge が既に同期済みの信号であり、新たな 2FF 同期器を設けない。★
★これは §3.1 の挿入位置選定の主要動機である。★

### 6.2 ★境界②の検査器から見た相手が変わる★

★cdc_bridge 側（境界②）にも契約 C-α' の対検査器がある（`cache_v0_6.sv` L553 の注記）。★
★本改修により、その検査器から見た「上流」が CPU からライトバッファに変わる。★

★要件★：★ライトバッファは `dn_ready_i` の次サイクルに同一要求を保持してはならない。★
★保持すれば境界②の検査器が発火する。★

★注意★：★「片方だけ直さないこと」と明記されている。★
★境界①（cache 上流）と境界②（cdc_bridge）の検査器は同一の再アーム方式を採っており、
方式が片側だけ変わると回数の帰属が非対称になり段6 の回数判定が狂う。★
★本設計では検査器そのものを改変しない。★

#### 6.2.1 ★【v0.2 追加】2 バイト連続ドレインは違反にならない（確認済）★

```
ysd8800_cache_v0_6.sv L572-575（境界①・境界②も同方式）:
  assign ca_viol = ca_ready_d && (cpu_rd_i || cpu_wr_i)
                && (cpu_rd_i == ca_rd_d) && (cpu_wr_i == ca_wr_d)
                && (cpu_phys_addr_i == ca_addr_d);
```

★違反条件に**アドレス一致**が含まれている。★
★ドレインの 2 バイト目はアドレスが ±1 異なるため `ca_viol` は成立しない。★

L546-548 のコメントも「実CPUは ready の次サイクルに新しい要求を出す（S_MEMR_LO→S_MEMR_HI 等）。
要求が継続していること自体は契約違反ではない」と明記しており、★ドレインはまさにこの形である。★

★実装時は「2 バイト目でアドレスを必ず更新する」ことだけ守ればよい。★
★無駄な 1 サイクル空きを入れる必要はない。★

### 6.3 ★G-M ゲートを当初から有効にする — ただし判定式の拡張が必須★

★TKT-V10 の指示どおり、実装当初から G-M（MISMATCH 合計 = 0）を有効にする。★
★「動いてから検査器を足す」をしない。★
★根拠：出力ベースの判定器は内部データの破壊を検出できない（KY96）。★
★母数がなければ判定器の不作動と合格を区別できない。★

#### 6.3.1 ★【v0.2 追加】現行 G-M はそのままでは使えない★

★G-M はキャッシュが返した値と `u_membus.u_psram_ctrl.mem[]` を毎アクセス照合する（TKT-V7 §4.2）。★
★この判定が偽陽性を出さない根拠は、次の 2 点であった。★

| 根拠 | 実源 |
|---|---|
| ★書込時の `cpu_ready_o` は `br_ready_i` 素通し ＝ psram の ack を待つ（**ポステッドでない**）★ | `ysd8800_cache_v0_6.sv` L526-528 |
| `psram_ctrl` は `mem[] <= wdata` と `ack <= 1` を同一サイクルで実行 | `ysd8800_psram_ctrl_v0_3.sv` L165-172 |

★→ ready 成立時点で `mem[]` は必ず更新済であり、書込直後の読出でも偽陽性は生じなかった。★

> ⚠ ★本改修はこの前提を正面から壊す。★
> ★§4.4-1「書込・バッファ空 → `up_ready_o` を即返す」は**ポステッド書込そのもの**である。★

★偽陽性の発生手順（稀ではなく常態になる）★：

| # | 事象 |
|---|---|
| 1 | CPU が $X へ 16bit 書込 → ★wbuf が即 ready★。`mem[$X]` はまだ旧値 |
| 2 | 同時に ★`wr_hit` によりキャッシュは更新済★ |
| 3 | 直後に $X を読出 → ★キャッシュヒットで新値を返す★（ヒット率 99.73%） |
| 4 | G-M が `mem[$X]`（旧値）と比較 → ★MISMATCH★ |

★書込直後の読出は極めて多い。W-3 は実装初日から真っ赤になる。★
★そしてその中に本物の欠陥が紛れても区別できない。★
★「MISMATCH が出るのは想定内」という運用に落ちた瞬間、G-M は判定器として死ぬ（KY99）。★

#### 6.3.2 ★拡張仕様（案a を採用）★

★照合の期待値を「`mem[]` にバッファ内容を上書きしたもの」とする。★

```
期待値(addr) = (wb_valid_r && wb_be_r[i] && (wb_addr_r + i) == addr)
             ? wb_data_r[i]
             : mem[addr]
```

| 案 | 内容 | 判定 |
|---|---|---|
| ★(a)★ | ★期待値を `mem[]` ＋ バッファ内容の重ね合わせとする★ | ★**採用**★。判定の網を一切緩めない。TB 内の数行で済む |
| (b) | `wb_valid_r=1` の間は照合を休止 | ★不可。最も壊れやすい期間に検査を止めることになる★ |
| (c) | ドレイン完了時点でまとめて照合 | 検出が遅れ、どのアクセスで壊れたか分からなくなる |

★(a) により、G-M は「キャッシュ・バッファ・PSRAM の三者が整合しているか」の検査に格上げされる。★
★ライトバッファはまさにその三者整合を壊しうる改修であるから、検査器も同じ射程に広げるのが筋である。★

#### 6.3.3 ★拡張後の確認事項★

| # | 確認 |
|---|---|
| ★1★ | ★W-3 の合格条件に「母数 > 0」が入っていること（KY96）★ |
| ★2★ | ★`wb_valid_r=1` の期間に照合が**実際に走っている**ことを確認する★ — ★期待値だけ直して照合条件を狭めると、静かに検査対象が減る★ |

> ★本件は「検査器を作った当人が、次の改修でその前提を壊す」という形である。★
> ★判定器は、それが依拠する設計上の前提とともに記録し、
> 前提を変える改修では判定器の再検証を改修の一部として計画に含める必要がある。★
> ★KY として起票する（採番は `kaizen2.txt` 実ファイルから／本設計書では採番しない）。★
