## 1. ★★M-11 の解決：案 A-2q（最終案）★★

### 1.1 推奨 (a) A-2'' の評価結果 — ★不採用★

レビュー推奨の A-2''（`req_level = (rd|wr) & ~ack_sync[1]`）を PoC で実測した。

| 版 | 連続 read 間隔 | 総時間 |
|---|---|---|
| BASE | 5 cpu_clk | 15,625,000 ps |
| A-2' | 4 cpu_clk | 13,125,000 ps |
| ★**A-2''**★ | ★**5 cpu_clk**★ | 15,375,000 ps |

★**A-2'' は BASE と同じ 5 cpu_clk に戻り、−1 cyc の効果が消失**★。
`ack_sync[1]` は psram 側が ack を落とすまで High を維持するため、**抑止期間が
1 cpu cyc を超えて延び**、次 req の発行を遅らせるためである。
レビュー §3 M-11 が「★ただし抑止期間が延びるため −1 cyc が維持されるかを PoC で
再測すること★」と注記していた懸念が、そのまま現実化した。

→ **(a) は不採用。** ただし **(c)（グリッチ許容）にも進まない**。以下の別解を得た。

### 1.2 ★案 A-2q（新設・採用推奨）★

**着想**：M-11 の本質は「**組合せデコードが CDC でサンプルされる**」ことである。
逆に言えば、★**FF の「入力側」に現れるハザードは、クロック端までに確定するため無害**★。
したがって抑止信号を「**登録済・単一 FF 出力**」にすれば、Q はグリッチを持たない。

問題は「登録すると 1 サイクル遅れる」ことだが、★`ack_sync[0]`（1 段目）を使って
1 サイクル早く叩く★ことで解決できる。

```systemverilog
    logic suppress_r;   // ★登録済・単一FF出力のreq抑止信号★

    always_ff @(posedge cpu_clk or negedge cpu_rst_n) begin
        if (!cpu_rst_n) begin
            ack_sync <= 2'b00; ack_sync_d <= 1'b0; suppress_r <= 1'b0;
        end else begin
            ack_sync   <= {ack_sync[0], psram_ack};
            ack_sync_d <= ack_sync[1];
            suppress_r <= ack_sync[0] & ~ack_sync[1];   // ★D入力のハザードは無害★
        end
    end

    assign req_level     = (cpu_mem_rd | cpu_mem_wr) & ~suppress_r;  // ★単一FF出力★
    assign cpu_mem_ready = suppress_r;                               // ★単一FF出力★
    assign cpu_mem_rdata = psram_rdata;                              // 非同期データパス
```

#### 1.2.1 タイミング（`psram_ack` 立上りを起点に）

| cpu_clk | `ack_sync[0]` | `ack_sync[1]` | `suppress_r` | 動作 |
|---|---|---|---|---|
| k | 0→1 | 0 | 0 | 1 段目が捕捉 |
| **N**(=k+1) | 1 | 0→1 | ★**0→1**★ | ★`ready`=1・`req_level` 抑止★ |
| N+1 | 1 | 1 | ★**1→0**★ | 抑止解除 → **次 req が通る** |

→ ★**抑止はちょうど 1 cpu cyc、かつ `ready` と完全同位相**★。A-2' と同一の挙動を、
グリッチフリーで実現する。

#### 1.2.2 ★メタステービリティ★

`suppress_r` は `ack_sync[0]` を叩く。すなわち★この経路も 2FF 相当の
同期段数（`ack_sync[0]` → `suppress_r`）を持つ★。A-4（2FF→1FF）のような
耐性低下は**生じない**。原則82 との整合は保たれる。

#### 1.2.3 実測結果

> ★★**v0.4 重要注記：本表はすべて「連続 read」負荷モデル
> （`cpu_mem_rd` を上げっぱなし）での値である。**★★
> 2026-08-26 の N-4 検証により、★この負荷モデルは実 CPU を代表しない★
> ことが判明した（実 CPU は演算状態で `mem_rd` を落とす）。
> 負荷モデルによる評価の違いは §1.4 を参照のこと。

| 版 | 連続 read 間隔 | 総時間 | CDC 越え信号 | CPU 向け ready |
|---|---|---|---|---|
| BASE | 5 | 15,625,000 ps | 登録済 | 登録済 |
| A-2 | 5（相殺） | 15,375,000 ps | 登録済 | ★組合せ★ |
| A-2' | **4** | 13,125,000 ps | ★組合せ（危険）★ | ★組合せ★ |
| A-2'' | 5（効果消失） | 15,375,000 ps | 登録済 | ★組合せ★ |
| ★**A-2q**★ | ★**4**★ | **13,125,000 ps** | ★**登録済**★ | ★**登録済**★ |

★★**A-2q は A-2' と完全に同一の性能（4 cpu_clk・13,125,000 ps）を、
グリッチフリーで達成する。**★★

### 1.4 ★★負荷モデル依存性（v0.4 新設・N-4 の発見）★★

2026-08-26 の N-4 負方向対照において、★A-2 単独版がシステムで **−7.3%** の
改善を示した★（v0.3 §1.2.3 の「相殺」＝実質 0% という予測に反する）。

#### 原因

`tb_cdc_interval_poc.sv` は `cpu_mem_rd` を**上げっぱなし**にしていたが、
実 CPU は `always_comb`（`ysd8800_cpu_v0_1_FIXED.sv` L853-860）で `state` から
`mem_rd` をデコードしており、★演算状態では `mem_rd` が落ちる★。
その区間では旧 `req_hold` は何も阻害しないため、A-2 の −1 cyc が外に出る。

#### 両モデルでの再測（`tb_cdc_interval_gap_poc.sv` 新設）

| 負荷モデル | BASE | **A-2 単独** | **A-2q** |
|---|---|---|---|
| 連続 read（`rd` 上げっぱなし） | 5 | ★**5（相殺）**★ | ★**4**★ |
| 間隙あり（`rd` を 1cyc 下げる） | **6** | ★**5（−1cyc）**★ | **5** |

#### システム実測（V8-b・BASE-01 比）

| 版 | M-5 | BASE 比 |
|---|---|---|
| BASE-01 | 4,772,836 | — |
| ★A-2 単独★ | 4,426,738 | ★**−7.3%**★ |
| ★**A-2q**★ | **3,754,937** | ★**−21.3%**★ |

#### 結論

★**§4.2 の分析（`req_hold` が連続時に相殺する）自体は正しい。
誤っていたのは「したがって実質 0%」という外挿である。**★
実ワークロードは連続区間と間隙区間の混在であり、
A-2 は間隙区間でのみ効く（部分的）のに対し、
★A-2q は両区間で効く★ため約 3 倍の効果を持つ。

> ⚠️ **A-2' / A-2'' の評価も同一の連続 read モデル下の値である。**
> A-2'' が「効果消失」とされた判断も、間隙ありモデルでは異なり得る。
> ★ただし A-2q は両モデルで最良（連続 4／間隙 5）であり、採用結論は不変。★

→ **KY73 起票**：単体 TB の負荷モデルが実ワークロードを代表しない場合、
単体測定は★正しい値を返しながら誤った設計判断を導く★。

## 2. ★M-10 の決着（懸念1 の復活と解消）★

v0.1 §4.2 の「懸念1：CPU コア L198 に `mem_addr→mem_ready→state→stack_ctx` の
閉路で Icarus がハングした履歴あり」を、★取消線ではなく**決着**として復活★させる
（v0.2 で無言消失させたのは KY41 違反であり、指摘を受諾する）。

### 2.1 実源確認

| 対象 | 実源 | 駆動形態 |
|---|---|---|
| `mem_rd` | `ysd8800_cpu_v0_1_FIXED.sv` **L853-860** | ★**`always_comb`**★（`state` からのデコード） |
| `mem_ready` | `next_state` の `always_comb` に入力 | 組合せ入力 |
| `state` | FF | ★登録済★ |

### 2.2 経路の追跡と結論

```
suppress_r(FF) → cpu_mem_ready → CPU next_state(comb) → state(FF) → mem_rd(comb)
                                                                      ↓
                                        req_level(comb) → req_sync[0](FF・psram域)
```

★**`state` の FF で切れており、組合せループは閉じない。**★

さらに重要な点として──

> ★★**A-2q において `cpu_mem_ready` は登録済 FF 出力（`suppress_r`）であり、
> 現行 BASE の登録済 `cpu_mem_ready` と構造的に完全同一である。
> 変わるのは位相が 1 サイクル早いことだけで、組合せ構造は一切変化しない。**★★

したがって L198 の閉路履歴は **A-2q には該当しない**。
（A-2/A-2'/A-2'' は ready が組合せ出力になるため該当し得たが、いずれも不採用）

### 2.3 `mem_rd` のグリッチについて（★既存条件★）

`mem_rd` が `always_comb` である以上、`req_level` にはハザードが乗り得、
それが `req_sync` で psram_clk サンプルされる。★ただしこれは
**BASE の `req_level = (rd|wr) & !req_hold` にも同一に存在する既存条件**であり、
A-2q が新たに導入するものではない★。

**本工程のスコープ外**とし、②または③で別途評価する（起票のみ）。

## 3. C-4 / C-5 の確認結果

### C-4：アドレス変更と req 抑止の時間差 — ★安全★

A-2q では CPU が N で ready を受け、同じ N で次アドレスを出し得る。一方
`req_level` の抑止が psram 側に届くのは `req_sync` の 2FF 分（約 62.5ns）遅れる。
→ ★「新アドレス」かつ「`psram_req` が依然 1」の窓が存在する★。

**判定：安全**。`ysd8800_psram_ctrl_v0_2.sv` **L125-128** より、この期間
`psram_ctrl` は `PS_WAIT_REQ_LOW` にあり、★**req の立下りを待っている状態で
新規要求を受理しない**★。アドレスが変化しても取り込まれない。

### C-5：`cpu_mem_rdata` のリセット系 — ★安全★

`assign cpu_mem_rdata = psram_rdata;` により、リセット値は `psram_rst_n` 系に従う。

| 実源 | 内容 |
|---|---|
| `ysd8800_v5_membus_v0_3.sv` L177/L189 | `cpu_rst_n` と `psram_rst_n` は**独立ポート** |
| `tb_cpu_v8b_prod_v0_2.sv` L181 | ★`psram_rst_n = 1`（**先に解除**）★ |
| 同 L185 | `cpu_rst_n = 1`（後に解除） |

→ ★**CPU 起動時点で `psram_rdata` は既に初期化済**★。不定は生じない。

**ただし★実装条件★**：この安全性は「psram 側が先に解除される」順序に依存する。
③ FPGA 実機のリセット回路設計時に**同順序を保証すること**を申し送る
（`mmio_stub` の `8'h00`→`8'hFF` と同種の「リセット値の暗黙前提」に該当するため、
★暗黙にせず明文化する★）。
