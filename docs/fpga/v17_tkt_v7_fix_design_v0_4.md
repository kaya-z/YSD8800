## §1. 欠陥の概要

### 1.1 現象

★キャッシュ有効（CEN=1）時、背中合わせの連続ミスで、ミス完了時に返すバイトが
前回の値のまま更新されない。★

| ワークロード | ビルド | CEN | 誤返却 / 総読出 | 結果 |
|---|---|---|---|---|
| Dhrystone | -O0 | 0 | 0 | 正常 |
| Dhrystone | -O0 | 1 | 0 | 正常 |
| Dhrystone | -O1 | 0 | 0 | 正常 |
| ★Dhrystone★ | ★-O1★ | ★1★ | ★1 件★ | ★**暴走・HALT**★ |
| YUI OS 起動 | — | 0 | 0 | 正常 |
| ★YUI OS 起動★ | — | ★1★ | ★**3 件**★ | ★**PASS するが汚染**★ |

★N-3：総読出アクセス数は T-1 で母数として記録する（3/N の稀少性を示すため）。★
YUI OS 起動は M-5 まで 2,010,458 cycle であり、読出は少なくとも数十万回のオーダーである。
★数十万回に 3 回という稀少性こそが、長期潜伏を許した性質である。★

### 1.2 ★既存ゲートを通過していた★

YUI OS 起動（CEN=1）は M-5 = 2,010,458 で ★G-C1 と完全一致しながら、
誤返却を 3 回起こしていた。★

- 3 件はすべて同一アドレス `$0A540`・同一値（cache=`$24` / psram=`$02`）
- `$0A540` = 42,304 = 1,322 × 32 ＝ ★32B ライン境界（offset 0）★
- Dhrystone の `$01A20` = 6,688 = 209 × 32 と ★完全に同型★

★段4 以降 M-5 が 4 段連続で不変だったのは「安定の証拠」ではなく、
誤った値が実行フローに効かない箇所だったにすぎない。★

### 1.3 ★なぜ検出できなかったか（判定器の限界）★

G-1 の判定は ★UART バイト列の md5★ であった。
返却値が壊れても出力に現れなければ md5 は一致する。
★出力ベースの判定器は、内部データの破壊を原理的に検出できない。★

## §2. 真因（実測で確定）

### 2.1 欠陥の連鎖

```
wire fill_sel = ccr_cen_i & (fill_req | fill_active_r);   // L169
```

★前フィルの `fill_active_r` 立下りと、新ミスの `fill_req` 立上りが隣接すると
`fill_sel` は 1 を保ったまま途切れない。★

```
if (!fill_gate_ps) beat_cnt_r <= '0;          // L397-398 ← 発火しない
else if (beat_valid_i) begin
    beat_cnt_r <= beat_cnt_r + 1;
    if (beat_cnt_r == BLEN_W'(req_offset_r))  // L405 ← 一致の窓を逃す
        fill_hit_byte_r <= psram_rdata_i;
end
```

→ `beat_cnt_r` がリセットされず、新ラインの beat 0 が `beat_cnt_r=34` の時点で到着。
→ `beat_cnt_r == req_offset_r(0)` が ★一度も成立しない★。
→ `fill_hit_byte_r` は前回値のまま返る。

### 2.2 実測波形（Dhrystone -O1 / CEN=1）

```
cyc=78169  req_off=31  beat=18  gate_ps=1  fhb=$23   ← 前ライン($0d0)フィル中
cyc=78173  req_off=31  beat=32  gate_ps=1  fhb=$43   ← 前ライン完了・rdy=1
cyc=78175  req_off=0   beat=34  gate_ps=1  fhb=$43   ← ★新ライン($0d1)開始。gate_ps 落ちず★
cyc=78179  req_off=0   beat=0   gate_ps=1  fhb=$43   ← ラップして 0。既に手遅れ
cyc=78181  rdy=1  rdata=$43  dq=$30                  ← ★誤返却（正しくは $30）★
cyc=78182  hit=1  dq=$30                             ← data_ram の中身は正しい
```

★`data_ram` の記憶内容は正しく、ミス完了時の返却値だけが壊れる。★
この限定的な壊れ方が、長期の潜伏を許した。

### 2.3 ★欠陥は 2 層ある★（M-2 反映）

| # | 問題 | 内容 |
|---|---|---|
| ★(1)★ | `beat_cnt_r` のリセット根拠 | psram_clk 側カウンタのリセットを、★cpu_clk 由来 `fill_sel` の「途切れ」★に依存。異ドメイン信号の**不在**を同期根拠にしており脆い |
| ★(2)★ | ★`req_offset_r` および `fill_index_r`★ の CDC 前提 | いずれもマルチビットで 2FF 同期できないため「フィル期間中は安定」という前提で裸のまま psram_clk 側で使用（L405／L412-414）。★連続ミスでは前提が崩れる★。L87-89 が前提の存在を明示している |

★M-2 の指摘どおり `fill_index_r` も同一の前提に立つ（L88-89）。★
offset だけを psram 側へ移すと ★同じ前提に立つ 2 信号のうち片方だけが保護された
非対称な構造★となり、KY98 の再発源が残る。★両方を同時にラッチする。★

### 2.4 発火条件（一般形）

★「前のミスの直後に次のミスが来ること」のみ。★
ライン境界跨ぎや `-O1` は必要条件ではない。
offset 0 で顕在化したのは、★offset 0 は必ず最初のビートであり、
カウンタがずれていると一致機会が最も失われやすい★ため。

→ ★コード配置が変われば -O0 でも踏み得る。既存ゲートの通過は偶然に近い。★

## §3. 修正方針

### 3.1 採用案：★案 B'★

> ★psram_clk 側で `beat_valid_i` の立上りをバースト開始とみなし、
> そこで `beat_cnt_r` を 0 相当にし、同時に `req_offset` と `fill_index` をラッチする。★

### 3.2 却下案とその理由（記録）

| 案 | 内容 | 判定 |
|---|---|---|
| A | `fill_index_r` の変化検出でリセット | ★却下★。同一 index・異 tag の ping-pong で `fill_index_r` が変化せず再発 |
| B（原案） | psram_ctrl から req 受理パルスを新設 | ★不採用★。`psram_ctrl` の出力は `ack`/`rdata`/`beat_valid`/`dbg_refresh_hit` のみ（L61-77）。新設は他モジュールへ波及 |
| C | `fill_sel` に強制ギャップを挿入 | ★却下（2026-09-05 ユーザー判断）★。性能低下し段7-A の削減効果を損なう |
| ★案3（段4・撤去済）★ | ★フィルゲートを beat_valid 静穏後に武装する★ | ★C-1：B' と外形が似るが射程が異なる★。§3.2.1 参照 |
| ★B'★ | `beat_valid_i` 立上りをバースト開始とみなす | ★採用★ |

#### 3.2.1 ★案3 との関係（C-1）★

| 項目 | 案3（段4） | ★B'（本件）★ |
|---|---|---|
| 対象問題 | 書込→密着読出における★残留ビートの誤取込★ | ★連続ミス時のカウンタ未リセット★ |
| 結論 | ★効果なし。真因は TB 起因★（`bus_tasks` の deassert タイミング）だった | — |
| 機構 | ゲートの★武装を遅らせる★ | ★カウンタの同期点を実イベントに移す★ |

★案3 の「効果なし」という記録は、B' の否定材料にならない。★
案3 は段4 の別問題への対策として試され、その問題には効かなかった。
問題が異なる以上、射程が異なる（KY93：同型の診断でも同型の対処が効くとは限らない、の逆向きの適用）。

### 3.3 B' の利点

| # | 利点 |
|---|---|
| 1 | ★信号追加が不要★。変更が `ysd8800_cache_v0_5.sv` 内に閉じる |
| 2 | ★比較の両辺が psram_clk ドメイン内で閉じる★。(2) の CDC 前提が不要になる |

### 3.4 ★B' が依存する前提（M-4 反映：2 件）★

#### 前提 P-A：バースト間には必ず `beat_valid=0` の期間が存在する

| 事実 | 実源 |
|---|---|
| `PS_WAIT_REQ_LOW` で `beat_valid <= 1'b0` | `ysd8800_psram_ctrl_v0_3.sv` L212 |
| `PS_IDLE` でも明示クリア | 同 L141 |
| 次バーストの beat 0 は `busy_cnt = LATENCY − 2` 経過後 ＝ ★最低 11 psram cyc の空き★ | 同 L147-149 |
| バースト内は `PS_BUSY`（beat 0）→`PS_BURST`（毎サイクル `beat_valid<=1`）で連続 | 同 L169, L193-195 |
| リフレッシュは `refresh_this_access` としてアクセス開始時に織り込み、★途中に割り込まない★ | 同 L168 |

★→ `beat_valid` 立上りはバースト開始と 1:1 対応する。★
（出典：レビュー v1.0 §5 V-1〜V-3。本設計者も L169/L193-195 を直接確認済）

#### ★前提 P-B（M-4 で追加）：`fill_gate_ps==1` の期間中に非フィルのバーストが発行されない★

- `beat_valid` は ★blen=1 の単バイト読出・書込でも立つ★（`psram_ctrl` L169／`cache` L82・既知事項 I-2）
- これが起きると、その立上りが ★フィルのバースト開始と誤認され★、
  `beat_cnt_r` と `req_off_ps_r` がフィル途中でリセットされる
  ＝ ★今回と同型の欠陥が別経路で再発する★
- cdc_bridge の 4 相ハンドシェイクにより単一未完了要求しか存在しないはずだが、
  ★これは前提であって未検証である★

★KY90 に従い、P-A・P-B・P-C とも §5 の T-2 で実測検証する。静的確認と実測は別物である。★
★P-B は RTL 内アサーション（§3.5・N-1）として常設する。★

#### ★前提 P-C（C-2 で追加）：ラッチ時点で `req_offset_r` / `fill_index_r` が安定であること★

`burst_start` でこれらを★生のまま★ラッチする以上、その時点での安定性が前提になる。
これは P-A/P-B とは別の前提である。

| 項目 | 値・根拠 |
|---|---|
| バースト開始のタイミング | psram への req 受理から ★`LATENCY_NORMAL − 2` 以上経過した時点★（`psram_ctrl` L147-149） |
| `req_offset_r` の確定時期 | ★req 発行前に cpu 側で確定★（`cache` L164） |
| ★余裕★ | ★10 psram cyc 以上★（`LATENCY_NORMAL` = 12 の場合） |

★⚠ `LATENCY_NORMAL` を将来短縮する改造が入ったとき、真っ先に見直すべき箇所である。★
既存コメント L386 の「⚠ LATENCY_NORMAL <= 2 では本前提が崩れる」と同種の注意が B' にも要る。

### 3.5 実装イメージ（★レビュー対象・実装は次チャット★／M-2・M-3 反映）

★`beat_no` を「現ビート番号」の単一定義とし、捕捉比較とポートAで共用する。★

```
// ---- psram_clk ドメイン ----
logic                  beat_valid_d;
logic                  fill_armed_r;     // ★N-1：バースト捕捉中フラグ★
logic [OFF_W-1:0]      req_off_ps_r;     // ★psram 側にラッチした要求 offset★
logic [IDX_W-1:0]      fill_index_ps_r;  // ★同・フィル先 index（M-2）★

wire burst_start = fill_gate_ps & beat_valid_i & ~beat_valid_d;

// ★現ビート番号の単一定義（M-3）★
wire [BLEN_W-1:0]  beat_no  = burst_start ? BLEN_W'(0) : beat_cnt_r;
wire [OFF_W-1:0]   off_use  = burst_start ? req_offset_r    : req_off_ps_r;
wire [IDX_W-1:0]   idx_use  = burst_start ? fill_index_r    : fill_index_ps_r;

// ★N-1：ビート消費は「捕捉中」のバーストに限る★
wire beat_take = fill_gate_ps & beat_valid_i & (burst_start | fill_armed_r);

always_ff @(posedge psram_clk or negedge psram_rst_n) begin
    if (!psram_rst_n) begin
        fill_gate_meta  <= 1'b0;
        fill_gate_ps    <= 1'b0;
        beat_valid_d    <= 1'b0;
        fill_armed_r    <= 1'b0;
        beat_cnt_r      <= '0;
        req_off_ps_r    <= '0;
        fill_index_ps_r <= '0;
        fill_hit_byte_r <= 8'h00;
    end else begin
        fill_gate_meta <= fill_sel;
        fill_gate_ps   <= fill_gate_meta;
        beat_valid_d   <= beat_valid_i;

        if (!fill_gate_ps) begin
            // ★N-1：旧コードの規律を捨てない。★
            //   機能上は burst_start で足りるが、波形の可読性が上がり、
            //   前提 P-A が崩れた場合の被害を「先頭からのずれ」に限定できる。
            beat_cnt_r   <= '0;
            fill_armed_r <= 1'b0;
        end else begin
            if (burst_start) begin
                req_off_ps_r    <= req_offset_r;    // ★開始時に1回だけラッチ★
                fill_index_ps_r <= fill_index_r;    // ★M-2★
                fill_armed_r    <= 1'b1;
            end
            if (beat_take) begin
                beat_cnt_r <= beat_no + BLEN_W'(1);
                if (beat_no == BLEN_W'(off_use))
                    fill_hit_byte_r <= psram_rdata_i;
            end
        end
    end
end

// ---- ポートA：ラインフィル書込（★M-3：beat_no / idx_use を共用★）----
always_ff @(posedge psram_clk) begin
    if (beat_take)
        data_ram[{idx_use, beat_no[OFF_W-1:0]}] <= psram_rdata_i;
end

// ---- ★N-1：無音の失敗経路を残さない（RTL 内アサーション）----
//   P-A/P-B が破れたときに「無音のデータ破壊」ではなく即時失敗させる。
`ifndef SYNTHESIS
always_ff @(posedge psram_clk) begin
    if (psram_rst_n && fill_gate_ps && beat_valid_i && !fill_armed_r && !burst_start)
        $error("[CACHE] unarmed beat consumed: P-A/P-B broken @%0t", $time);
end
`endif
```

★注意点★

| # | 事項 |
|---|---|
| I-1 | ★ポートAも `beat_no` / `idx_use` を使う★（M-3）。従来は裸の `beat_cnt_r` / `fill_index_r` を使っており、カウンタがずれると格納位置もずれた（今回は偶然一致していた） |
| I-2 | ★「1 ビートずれ」は構造で排除する★。`beat_no` が現ビート番号の単一定義であるため、`beat_cnt_r <= '0` してから加算する形にはならない（原則：内部状態変数の変更箇所を集約） |
| I-3 | `req_offset_r`／`fill_index_r` のラッチは★バースト開始の 1 回のみ★。以後 cpu 側が変化しても影響しない |

## §4. MISMATCH モニタのゲート化（★2026-09-05 ユーザー承認済★）

### 4.1 背景

本欠陥は ★出力ベースの判定器（UART md5）では原理的に検出できない。★
キャッシュ返却値と PSRAM 実体を直接照合する監視が必要である。

### 4.2 仕様（★v0.3：U-A 決着・観測点を確定★）

★観測点：キャッシュ境界（`u_membus.u_cache` のポート）★

| 信号 | 内容 |
|---|---|
| `cpu_phys_addr_i` | ★MMU 出力 `phys_addr`（20bit 物理）★ |
| `cpu_rd_i` | `ram_rd`（★RAM パス専用。MMIO は来ない★） |
| `cpu_ready_o` | `ram_ready` |
| `cpu_rdata_o` | `ram_rdata`（★照合対象★） |

根拠：`ysd8800_v5_membus_v0_11.sv` L482-493。

```
if (cpu_rst_n && u_membus.u_cache.cpu_rd_i && u_membus.u_cache.cpu_ready_o) begin
    if (u_membus.u_cache.cpu_rdata_o !==
        u_membus.u_psram_ctrl.mem[u_membus.u_cache.cpu_phys_addr_i]) ...
end
```

★本観測点を採る理由★

| # | 理由 |
|---|---|
| 1 | ★比較の両辺が物理アドレスで揃う★。`u_psram_ctrl.mem[]` は物理添字であり、MMU 有効時（YUI OS・将来の Ph.8）でも食い違わない |
| 2 | ★`$FC80` フィルタが不要になる★。`ram_rd` は RAM パス専用でありデコーダ前段で MMIO が分岐済み。「なぜ除外するのか」を将来の読み手が考えずに済む |
| 3 | キャッシュの入出力そのものを見るため、★上流（CPU・デコーダ）の実装変更に影響されない★ |

#### 4.2.1 ★旧観測点（CPU 側・論理 16bit）の評価★

v0.2 までは CPU 側で観測し `mem_addr < 20'hFC80` で MMIO を除外していた。
★実測の結果、偽陰性は生じていなかった★（新旧とも 3 件・同一アドレス／同一値）。
YUI OS 起動時（M-5 到達まで）の当該 RAM アクセスが恒等写像領域であったためである。

★ただし旧観測点が正しかったのは偶然であり、MMU の使い方が変われば破綻する。★
Ph.8（MMU 連携）が将来工程にある以上、運任せにはしない。
★→ 新観測点を G-M の正式仕様とする。★

### 4.3 ★合格基準への追加：新ゲート G-M★

★全ワークロード・全ビンで `MISMATCH total = 0` であること。★
G-0/G-1/G-2 と並ぶゲートとして常設する。

| 項目 | 内容 |
|---|---|
| 監視対象 | 読出完了サイクル（`mem_rd & mem_ready`）の全アクセス |
| 読出のみで十分な理由 | ★ライトスルーのため書込は PSRAM に直行し、キャッシュ側の返却値という概念が無い★（レビュー R-4） |
| 表示上限 | 先頭 20 件。★総数は必ず表示する★ |
| 判定 | `MISMATCH total` が 0 でなければ FAIL |

#### 4.3.1 ★偽陽性が生じない根拠（N-3・G-M をハードゲート化できる理由）★

書込が★ポステッド★（psram 完了前に ready を返す）だと、直後の読出ヒットで
「キャッシュは新値・`mem[]` は旧値」となり ★偽の MISMATCH★ が出る。しかし本設計では生じない。

| 事実 | 実源 |
|---|---|
| ★書込時の `cpu_ready_o` は `br_ready_i` の素通し★（`ccr_cen_i & cpu_rd_i` が偽）＝ psram の ack を待つ | `ysd8800_cache_v0_5.sv` L440-442 |
| `psram_ctrl` は `mem[mem_idx] <= wdata` と `ack <= 1'b1` を ★同一サイクル★で実行 | `ysd8800_psram_ctrl_v0_3.sv` L165-174 |

★→ ready 成立時点で `mem[]` は必ず更新済であり、書込直後の読出でも偽陽性は生じない。★
★したがって G-M は「total=0 で FAIL」というハードゲートにできる。★

### 4.4 モニタ自身の妥当性（★陽性対照・KY91★）

| ビン | MISMATCH | 意味 |
|---|---|---|
| Dhrystone -O1 / CEN=1 | ★1★ | ★陽性★ |
| Dhrystone -O1 / CEN=0 | 0 | ★陰性対照★（同一コードで CEN のみ変更） |
| YUI OS / CEN=1 | ★3★ | 陽性 |
| YUI OS / CEN=0 | 0 | 陰性対照 |

★「発火すること」ではなく「前後で差が出ること」で妥当性を示している（KY91）。★

#### 4.4.1 ★観測点非依存の確認（v0.3 追加）★

観測点を CPU 側（論理）→ キャッシュ境界（物理）へ変更しても、
★検出結果は完全に同一★であった。

| 観測点 | YUI OS CEN=1 | YUI OS CEN=0 | M-5 |
|---|---|---|---|
| CPU 側（論理・v0.2 まで） | 3 件（`$0A540` / `$24` vs `$02`） | 0 件 | 2,010,458 |
| ★キャッシュ境界（物理・v0.3）★ | ★3 件（同一アドレス・同一値）★ | 0 件 | 2,010,458 |

★モニタが観測点の実装詳細に依存せず、欠陥そのものを捕らえていることの裏付けである。★

★C-4：修正後にモニタが「常に 0 を返す壊れ方」をしていないことの担保★
→ ★T-1（修正前の再現）で MISMATCH=1 を観測した同一モニタを、
コード無改変のまま T-3 に用いる。★
モニタを触るなら T-1 をやり直す。

### 5.1 ★T-5b でサイクル一致を要求しない理由（M-1）★

★誤った値が CPU に返っていた以上、その値は実行に取り込まれている。★
是正すれば分岐・ループ回数・UART 出力タイミングが変わりうるのだから、
M-5 が 2,010,458 と一致する保証はない。★一致しないことは欠陥ではない。★

★差が出た場合は「3 件の誤返却が実行に与えていた影響量」として記録する。★
これは §1.2 の「M-5 一致は安定の証拠ではなかった」という主張の定量的裏付けになる。

#### 5.1.1 ★T-5b の判定表（C-1：結果を見てから解釈を決めない）★

T-5b は ★どちらに転んでも「想定内」である★ 珍しい試験である。
★結果を見てから解釈を決めないよう、判定を先に定めておく。★

| T-5b の結果 | 意味 | 記録・処置 |
|---|---|---|
| M-5 が 2,010,458 と一致 | 3 件の誤返却は ★制御フローにもタイミングにも影響していなかった★ | 段6 の値をそのまま維持。G-C1 は不変 |
| M-5 が変化 | 誤返却が実行に影響していた（影響量が定量化された） | ★新値を G-C1 の基準として採用し、段6 の旧値は取り消さず併記★（§6.1 の方針どおり） |

#### 5.1.2 ★G-1（UART バイト列 md5）の扱い（C-1）★

出力が変われば md5 も変わる。
★「G-1 不一致＝FAIL」と機械的に処理すると、正しい修正を欠陥と誤判定する。★

| 項目 | 扱い |
|---|---|
| T-5b における G-1 | ★md5 の一致を要求しない★ |
| 変化した場合 | ★基準値を更新する（旧値は取り消さず併記）★ |
| 理由 | ★本修正は「誤った値を正す」ものであり、出力が変わることは是正の結果であって欠陥ではない★ |
| ★適用範囲★ | ★本修正に限った例外的扱いである。恒常的に md5 を軽視してよいという意味ではない★ |

★⚠ `HANDOVER_CHAT153.md` §6-4 のとおり、UART バイト多重集合 md5 の算出方法は
版によって異なり比較不能である。★基準更新を行うなら、算出方法を固定してから行うこと。★

### 5.2 T-4/T-5a で「サイクル不変」を要求する理由

これらは ★修正前 MISMATCH=0 のビン★であり、修正によってデータは変わらない。
本修正は返却値のみを是正するものであり、★タイミングを変えてはならない★。
★サイクル数が動いたら、意図しない副作用が入ったことを意味する。★
