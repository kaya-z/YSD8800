## §1. 欠陥の概要

### 1.1 現象

★キャッシュ有効（CEN=1）時、背中合わせの連続ミスで、ミス完了時に返すバイトが
前回の値のまま更新されない。★

| ワークロード | ビルド | CEN | 誤返却 | 結果 |
|---|---|---|---|---|
| Dhrystone | -O0 | 0 | 0 | 正常 |
| Dhrystone | -O0 | 1 | 0 | 正常 |
| Dhrystone | -O1 | 0 | 0 | 正常 |
| ★Dhrystone★ | ★-O1★ | ★1★ | ★1 件★ | ★**暴走・HALT**★ |
| YUI OS 起動 | — | 0 | 0 | 正常 |
| ★YUI OS 起動★ | — | ★1★ | ★**3 件**★ | ★**PASS するが汚染**★ |

### 1.2 ★既存ゲートを通過していた★

YUI OS 起動（CEN=1）は M-5 = 2,010,458 で ★G-C1 と完全一致しながら、
誤返却を 3 回起こしていた。★

- 3 件はすべて同一アドレス `$0A540`・同一値（cache=`$24` / psram=`$02`）
- `$0A540` = 42,304 = 1,322 × 32 ＝ ★32B ライン境界（offset 0）★
- Dhrystone の `$01A20` = 6,688 = 209 × 32 と ★完全に同型★

★段4 以降 M-5 が 4 段連続で不変だったのは「安定の証拠」ではなく、
誤った値が実行フローに効かない箇所だったにすぎない。★

### 1.3 ★なぜ検出できなかったか（判定器の限界）★

G-1 の判定は ★UART バイト列の md5★ であった。
返却値が壊れても出力に現れなければ md5 は一致する。
★出力ベースの判定器は、内部データの破壊を原理的に検出できない。★

本件は、キャッシュ返却値と PSRAM 実体を毎アクセス照合する
★直接照合モニタ★を投入して初めて可視化された。

## §2. 真因（実測で確定）

### 2.1 欠陥の連鎖

```
wire fill_sel = ccr_cen_i & (fill_req | fill_active_r);   // L169
```

★前フィルの `fill_active_r` 立下りと、新ミスの `fill_req` 立上りが隣接すると
`fill_sel` は 1 を保ったまま途切れない。★

```
if (!fill_gate_ps) beat_cnt_r <= '0;          // L397-398 ← 発火しない
else if (beat_valid_i) begin
    beat_cnt_r <= beat_cnt_r + 1;
    if (beat_cnt_r == BLEN_W'(req_offset_r))  // L405 ← 一致の窓を逃す
        fill_hit_byte_r <= psram_rdata_i;
end
```

→ `beat_cnt_r` がリセットされず、新ラインの beat 0 が `beat_cnt_r=34` の時点で到着。
→ `beat_cnt_r == req_offset_r(0)` が ★一度も成立しない★。
→ `fill_hit_byte_r` は前回値のまま返る。

### 2.2 実測波形（Dhrystone -O1 / CEN=1）

```
cyc=78169  req_off=31  beat=18  gate_ps=1  fhb=$23   ← 前ライン($0d0)フィル中
cyc=78173  req_off=31  beat=32  gate_ps=1  fhb=$43   ← 前ライン完了・rdy=1
cyc=78175  req_off=0   beat=34  gate_ps=1  fhb=$43   ← ★新ライン($0d1)開始。gate_ps 落ちず★
cyc=78179  req_off=0   beat=0   gate_ps=1  fhb=$43   ← ラップして 0。既に手遅れ
cyc=78181  rdy=1  rdata=$43  dq=$30                  ← ★誤返却（正しくは $30）★
cyc=78182  hit=1  dq=$30                             ← data_ram の中身は正しい
```

★`data_ram` の記憶内容は正しく、ミス完了時の返却値だけが壊れる。★
この限定的な壊れ方が、長期の潜伏を許した。

### 2.3 ★欠陥は 2 層ある★

| # | 問題 | 内容 |
|---|---|---|
| ★(1)★ | `beat_cnt_r` のリセット根拠 | psram_clk 側のカウンタのリセットを、★cpu_clk 由来 `fill_sel` の「途切れ」★に依存させている。異ドメイン信号の**不在**を同期の根拠にしており脆い |
| ★(2)★ | `req_offset_r` の CDC 前提 | 5bit マルチビットを 2FF 同期できないため「フィル期間中は安定」という前提で裸のまま psram_clk 側の比較（L405）に使用。★連続ミスでは 31→0 とフィル中に変化し前提が崩れる★（L87 のコメントが前提の存在を明示している） |

★案 B（psram_clk 側の事象で同期）だけでは (1) しか直らない。(2) の同時解決が必要。★

### 2.4 発火条件（一般形）

★「前のミスの直後に次のミスが来ること」のみ。★
ライン境界跨ぎや `-O1` は必要条件ではない。
今回 offset 0 で顕在化したのは、★offset 0 は必ず最初のビートであり、
カウンタがずれていると一致機会が最も失われやすい★ため。

→ ★コード配置が変われば -O0 でも踏み得る。既存ゲートの通過は偶然に近い。★

## §3. 修正方針

### 3.1 採用案：★案 B'★

> ★psram_clk 側で `beat_valid_i` の立上りをバースト開始とみなし、
> そこで `beat_cnt_r` を 0 にリセットし、同時に `req_offset` をラッチする。★

### 3.2 却下案とその理由（記録）

| 案 | 内容 | 判定 |
|---|---|---|
| A | `fill_index_r` の変化検出でリセット | ★却下★。同一 index・異 tag のライン競合（ping-pong）では `fill_index_r` が変化せず再発する |
| B（原案） | psram_ctrl から req 受理パルスを引き出して同期 | ★不採用★。`psram_ctrl` の出力は `ack`/`rdata`/`beat_valid`/`dbg_refresh_hit` のみで、バースト開始専用信号が無い。新設は他モジュールへ波及する |
| C | `fill_sel` に強制的に 1 サイクルのギャップを挿入 | ★却下（2026-09-05 ユーザー判断）★。性能低下し、段7-A で確認した削減効果を損なう |
| ★B'★ | `beat_valid_i` 立上りをバースト開始とみなす | ★採用★。§3.3 参照 |

### 3.3 B' の利点

| # | 利点 |
|---|---|
| 1 | ★信号追加が不要★。変更が `ysd8800_cache_v0_5.sv` 内に閉じる |
| 2 | ★比較の両辺が psram_clk ドメイン内で閉じる★。(2) の CDC 前提が不要になる |
| 3 | 同期の根拠を「異ドメイン信号の**途切れ**」から「★バースト開始という実イベント★」へ移す |
| 4 | 性能への影響がない（サイクル数を変えない） |

### 3.4 ★B' が依存する前提と、その実源確認★

★前提：バースト中に `beat_valid` が途切れないこと。★

| 事実 | 実源 |
|---|---|
| `PS_BUSY` で beat 0 を出す際に `beat_valid <= 1'b1` | `ysd8800_psram_ctrl_v0_3.sv` L169 |
| `PS_BURST` は 1 psram cyc につき 1 バイトを出し毎サイクル `beat_valid <= 1'b1` | 同 L193-195 |
| リフレッシュは `refresh_this_access` としてアクセス開始時のレイテンシに織り込まれる。★バースト途中に割り込まない★ | 同 L168 |
| 総サイクル数 = LAT + (blen_r − 1)（例：blen=32, LAT=12 → 43 psram cyc） | 同 L190-191 |

★したがってバースト内で `beat_valid` は連続し、立上りがバースト開始と 1:1 対応する。★

★KY90 に従い、本前提は §5 の T-2 で検証対象とする（注記で済ませない）。★

### 3.5 実装イメージ（★レビュー対象・実装は次チャット★）

```
// psram_clk ドメイン
logic beat_valid_d;
logic [OFF_W-1:0] req_off_ps_r;      // ★psram_clk 側にラッチした要求 offset★

always_ff @(posedge psram_clk or negedge psram_rst_n) begin
    if (!psram_rst_n) begin
        beat_valid_d <= 1'b0;
        beat_cnt_r   <= '0;
        req_off_ps_r <= '0;
        fill_hit_byte_r <= 8'h00;
    end else begin
        beat_valid_d <= beat_valid_i;
        if (fill_gate_ps && beat_valid_i && !beat_valid_d) begin
            // ★バースト開始：カウンタをリセットし要求 offset をラッチ★
            beat_cnt_r   <= BLEN_W'(1);          // 本ビートが beat 0
            req_off_ps_r <= req_offset_r;
            if (req_offset_r == '0)
                fill_hit_byte_r <= psram_rdata_i;
        end else if (fill_gate_ps && beat_valid_i) begin
            beat_cnt_r <= beat_cnt_r + BLEN_W'(1);
            if (beat_cnt_r == BLEN_W'(req_off_ps_r))
                fill_hit_byte_r <= psram_rdata_i;
        end
    end
end
```

★注意点（実装時に必ず確認すること）★

| # | 事項 |
|---|---|
| I-1 | ★ポートA（`data_ram` 書込・L412-414）も `beat_cnt_r` を使う。★ 同じリセット規律に従わせること。現状は `{fill_index_r, beat_cnt_r[OFF_W-1:0]}` であり、カウンタがずれると格納位置もずれる（今回は偶然一致していた） |
| I-2 | バースト開始サイクルでは「本ビートが beat 0」である。`beat_cnt_r` を 0 にしてから加算すると 1 ビートずれる |
| I-3 | `req_offset_r` のラッチは★バースト開始の 1 回のみ★。以後 cpu 側が変化しても影響しない |
| I-4 | ★`blen=1`（単バイト読出・書込）でも `beat_valid` は立つ★（I-2 既知事項）。`fill_gate_ps` によるゲートを外さないこと |

## §4. MISMATCH モニタのゲート化（★2026-09-05 ユーザー承認済★）

### 4.1 背景

本欠陥は ★出力ベースの判定器（UART md5）では原理的に検出できない。★
再発防止には、キャッシュ返却値と PSRAM 実体を直接照合する監視が必要である。

### 4.2 仕様

```
always @(posedge cpu_clk) begin
    if (cpu_rst_n && mem_rd && mem_ready && (mem_addr < 20'hFC80)) begin
        if (mem_rdata !== u_membus.u_psram_ctrl.mem[mem_addr]) begin
            ... $display("[MISMATCH] addr=$%05x cache=$%02x psram=$%02x @cycle=%0d", ...);
            mism_count = mism_count + 1;
        end
    end
end
```

| 項目 | 内容 |
|---|---|
| 監視対象 | 読出完了サイクル（`mem_rd & mem_ready`）の全アクセス |
| 除外 | ★MMIO 領域（`$FC80` 以上）★。キャッシュ非対象のため |
| 判定 | ★`MISMATCH total` が 0 でなければ FAIL★ |
| 表示上限 | 先頭 20 件（ログ肥大の防止）。総数は必ず表示する |

### 4.3 ★合格基準への追加★

★新ゲート G-M：全ワークロード・全ビンで `MISMATCH total = 0` であること。★

これを G-0/G-1/G-2 と並ぶゲートとして常設する。

### 4.4 モニタ自身の妥当性（★陽性対照・KY91★）

| ビン | MISMATCH | 意味 |
|---|---|---|
| Dhrystone -O1 / CEN=1 | ★1★ | ★陽性★ |
| Dhrystone -O1 / CEN=0 | 0 | ★陰性対照★（同一コードでキャッシュを切ると消える） |
| YUI OS / CEN=1 | ★3★ | 陽性 |
| YUI OS / CEN=0 | 0 | 陰性対照 |

★同一バイナリで CEN のみを変えて差が出ることを確認済み。★
「発火すること」ではなく「★前後で差が出ること★」で妥当性を示している（KY91）。
