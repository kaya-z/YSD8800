## §1. 背景と問題

### 1.1 現象

段5-d の陽性対照⑦（`ysd8800_cache_v0_4_broken7_poc.sv`）実行時、
境界② の契約検査器 C-α' が **1 事象に対して 84 回発火**した。

発火自体は**正しい**。C-α' が問うている命題（同一要求が ready 後も保持されている）は
実際に成立しており、検査器は仕様どおりに動作している。
問題は**報告の粒度**であり、検出能力ではない。

### 1.2 なぜ段6 の着手前に是正が必要か

段6 は **発火回数を期待値に含める工程**である。

| 段5 までの判定 | 段6 の判定 |
|---|---|
| 「発火0件であること」 | 「発火が期待どおりの**回数**であること」 |

1 事象で 84 回発火する検査器を抱えたまま回数判定を導入すると：

1. ログが発火メッセージで埋まる
2. **同時に起きている別の失敗が埋没する**
3. しかも「発火した」という事実自体は正しいため、**異常として気づきにくい**

3 が本件の危険の本質である。誤検出であればログを見た時点で気づくが、
本件は正しい報告が過剰なだけなので、**見逃しの原因になっても警報が鳴らない**。

### 2.3 多重発火の機序（実源からの推定）

境界② の実装（`ysd8800_cdc_bridge_v0_4.sv` L188-206）：

```systemverilog
always @(posedge cpu_clk or negedge cpu_rst_n) begin
    if (!cpu_rst_n) begin
        cb_ready_d <= 1'b0; cb_rd_d <= 1'b0; cb_wr_d <= 1'b0; cb_addr_d <= '0;
    end else begin
        if (cb_ready_d && (cpu_mem_rd || cpu_mem_wr)
                       && (cpu_mem_rd == cb_rd_d) && (cpu_mem_wr == cb_wr_d)
                       && (cpu_phys_addr == cb_addr_d))
            $error("[CONTRACT C-a'/b2] same req held after ready: ...");

        cb_ready_d <= cpu_mem_ready;
        ...
    end
end
```

`cb_ready_d` は `cpu_mem_ready` の 1 サイクル遅延である。
したがって **`cpu_mem_ready` が複数サイクル張り付いたまま同一要求が保持されると、
そのサイクル数だけ条件が真になり、毎サイクル `$error` が呼ばれる。**

陽性対照⑦ は「C-8 違反＋中止フラグ sticky」であり、
`cpu_ready_o` が解放されない状態が継続する。84 回はこの継続長に対応する。

> ★注意（KY89）：上記の「84＝継続サイクル数」は**機序の説明であって
> 検証の期待値ではない**。是正後の期待値は §6 のとおり
> **実際に壊した DUT を走らせて確定する**。★

## §3. 是正設計

### 3.1 ★設計方針（v0.3 で差し替え）★

> **違反は「状態」である。1 事象＝1 報告とする。**（この上位方針は不変）

#### 3.1.1 ★v0.2 方式（旧・実測により否定）★

~~再アーム条件＝**違反条件（`viol`）が偽になったとき**。違反の連続区間を 1 事象とみなす。~~

★**2026-09-04 の実測により本方式は否定された。**★
陽性対照⑦ における境界② の発火は ★**是正前 84 回／是正後 84 回で不変**★ であった。
**記録として残す**（KY41）。誤りの内容は §3.1.2 に記す。

#### 3.1.2 ★否定された理由 — 84 回の機序は「連続」ではなかった★

v0.2 §2.3 は 84 回の機序を「`cpu_mem_ready` が複数サイクル張り付き、
そのサイクル数だけ条件が真になる」＝★連続区間★と推定していた。**これが誤りであった。**

★実測（2026-09-04）★：

| 観測項目 | 実測値 |
|---|---|
| 発火間隔 | ★2,000,000 ps 一定★ |
| CPU クロック周期 | 250,000 ps（TB L36：`always #125000`） |
| → 間隔 | ★**8 CPU サイクル**★ |
| アドレス分布 | ★84 件すべて `addr=00000`★ |

すなわち 84 回は **1 本の連続区間ではなく、`fill_abort_r` が sticky になった
CPU が 8 サイクル周期で同一アドレスを再送し続ける「再送ループ」が 84 周した**もの。
各周の違反は 1 サイクルで終わり、間に 7 サイクルの非違反区間が入る。

→ ★旧方式は 7 サイクルの空白ごとに再アームし、84 事象と数える。★
→ ★人間が見れば明らかに 1 つの障害だが、旧方式の「事象」の定義がそれを捉えられない。★

> ★v0.2 §2.3 に「機序の説明であって検証の期待値ではない」と保険をかけていた点は
> 機能した（KY89）。しかし★保険をかけただけで、その推定を検証する試験は組んでいなかった★。
> ★推定に保険をかけるだけでは足りない。保険をかけた推定こそ試験すべきである。★

#### 3.1.3 ★方式A（新・実測で確認済）★

★再アーム条件を次の2つとする。★

| # | 再アーム条件 | 意図 |
|---|---|---|
| 1 | ★バスがアイドル（`rd` も `wr` も 0）になった★ | 要求が引っ込めば事象は終わり |
| 2 | ★要求（アドレスまたは種別）が、報告済のものと変化した★ | 別の要求は別事象 |

実装は「★報告した要求そのものを記憶し（`*_rep_addr` / `*_rep_rd` / `*_rep_wr`）、
同一要求である限り再報告しない★」形をとる。

★これにより「事象」の定義が★連続サイクル★から★同一要求が引っ込むまで★へ変わる。★
再送ループは要求が引っ込まないので 1 事象として数えられる。

★C-β-2 との関係★：C-β-2 は「1 転送＝1 事象」であった。方式A は
「1 要求＝1 事象」であり、★スコープの取り方は C-β-2 と同じ思想★である。
v0.2 の旧方式だけが「連続サイクル」という異質なスコープを採っていた。

### 3.2 実装（境界①：`ysd8800_cache_v0_5.sv`）★方式A★

```systemverilog
`ifndef SYNTHESIS
    logic                ca_ready_d, ca_rd_d, ca_wr_d;
    logic [PHYS_AW-1:0]  ca_addr_d;
    logic                ca_viol;
    logic                ca_reported;
    // ★報告済の要求を記憶し、同一要求の再送を抑止する★
    logic                ca_rep_rd, ca_rep_wr;
    logic [PHYS_AW-1:0]  ca_rep_addr;
    logic                ca_same_as_reported;

    assign ca_viol = ca_ready_d && (cpu_rd_i || cpu_wr_i)
                                && (cpu_rd_i == ca_rd_d)
                                && (cpu_wr_i == ca_wr_d)
                                && (cpu_phys_addr_i == ca_addr_d);

    assign ca_same_as_reported = ca_reported
                              && (cpu_rd_i        == ca_rep_rd)
                              && (cpu_wr_i        == ca_rep_wr)
                              && (cpu_phys_addr_i == ca_rep_addr);

    always @(posedge cpu_clk or negedge cpu_rst_n) begin
        if (!cpu_rst_n) begin
            ca_ready_d  <= 1'b0; ca_rd_d <= 1'b0; ca_wr_d <= 1'b0;
            ca_addr_d   <= '0;
            ca_reported <= 1'b0;
            ca_rep_rd   <= 1'b0; ca_rep_wr <= 1'b0; ca_rep_addr <= '0;
        end else begin
            if (ca_viol && !ca_same_as_reported) begin
                $error("[CONTRACT C-a'] same req held after ready: addr=%h rd=%b wr=%b t=%0t",
                       cpu_phys_addr_i, cpu_rd_i, cpu_wr_i, $time);
                ca_reported <= 1'b1;
                ca_rep_rd   <= cpu_rd_i;
                ca_rep_wr   <= cpu_wr_i;
                ca_rep_addr <= cpu_phys_addr_i;
            end
            else if (!cpu_rd_i && !cpu_wr_i) begin
                ca_reported <= 1'b0;    // ★バスアイドルで再アーム★
            end

            ca_ready_d <= cpu_ready_o;
            ca_rd_d    <= cpu_rd_i;
            ca_wr_d    <= cpu_wr_i;
            ca_addr_d  <= cpu_phys_addr_i;
        end
    end
`endif
```

### 3.5 設計上の性質

| 性質 | 説明 |
|---|---|
| 検出能力の保存 | 違反が発生すれば**必ず 1 回は**報告される。落とすのは 2 回目以降の重複のみ |

### 6.1.2 ★V-2b で `bus_tasks_broken_poc.svh`（1cyc 版）を採らなかった理由★

当初 M-1 の指示どおり ★deassert を 1 サイクル遅らせる TB★ を作成したが、
★是正前でも境界①は 1 回しか発火しなかった★（実測）。

→ ★これでは「一度きり化が効いたか」を判定できない★（是正前後とも 1 回）。
→ ★deassert を 6 サイクル遅らせる `bus_tasks_broken6_poc.svh` を採用★し、
　 是正前 103 回・方式A 22 回という★差のある対照★を得た。

> ★陽性対照は「発火すること」だけでなく「**是正の前後で差が出ること**」まで
> 確認して初めて判定器になる。★

### 6.2.1 ★V-2b の必要性と作り方（M-1 反映）★

**なぜ V-2 では代替できないか**

陽性対照⑦ が壊しているのは★キャッシュ段の C-8／中止フラグ sticky★であり、
キャッシュが下流へ要求を保持し続けることで**境界②**が発火する。
一方**境界①**（CPU→キャッシュ段）は、TB が `bus_tasks.svh` を正しく使う限り
契約違反を起こさない。

→ ★V-2 を実行しても、境界①に新設する `ca_viol` / `ca_reported` は
**一度も真にならない**。★

★これは段5 の U-1 と同型の問題である。★

> 「陰性で発火 0 件」は「配線されている」ことを意味しない。
> ★配線されていない検査器も発火 0 である。★

本件はさらに悪く、**是正した論理が一度も実行されないまま
「V-1 で 0 件・V-2 で 1 回」という結果が揃い、完了条件を満たしてしまう。**
仮に境界①の実装で `else if (!ca_viol)` を書き忘れて再アームされなくても、
★V-2b が無ければ検出されない。★

**作り方（DUT は壊さない。TB の差し替えのみ）**

`bus_tasks.svh` v0.1 L59-61 を `_poc` 派生で 1 negedge 遅らせる（KY38）。

```systemverilog
//  bus_tasks_broken_poc.svh  v0.1  ★V-2b 専用・本番に使わないこと★
//  段4 で実際に起きた誤り（ready 後も同一要求を保持）を再現する。
            d = cpu_rdata;
            @(negedge cpu_clk);     // ★★意図的な誤り：1cyc 遅らせる★★
            cpu_rd = 1'b0;
```

これにより `suppress_r`(1cyc) を抜けて再送が起こり、境界① C-α' を直撃する。

★注意：`bus_tasks.svh`（本番）の md5 が不変であることを実測確認すること（KY38）。★

### 6.2 ★V-2 を主判定器とする理由（KY89）★

> 「発火 0 件になった」は、**検査器を壊しても達成できる**。
> 是正が「重複だけを落とし、検出能力を保存した」ことを示すには、
> ★実際に違反する DUT を走らせ、1 回だけ発火することを確認する★以外にない。

これは段5 で得た KY89（設計書の症状予測を期待値にしない。
期待値は実際に壊した DUT を走らせて決める）の直接の適用である。

★補強（N-2 反映）：V-2 は**参照追従の確認**も兼ねる。★
仮に `membus_v0_11` が誤って旧版（`cache_v0_4` / `cdc_bridge_v0_4`）を参照していた場合、
是正前の論理が動くため ★V-2 は 84 回発火し、即座に検出される★（R-2・R-3 と同じ効果）。
★この二重の役割ゆえ、V-2 を主判定器に置く判断はさらに強い。★
同じことは V-2b にも当てはまる（境界①側の参照追従を確認する）。

### 6.5 ★発火回数の集計手段（C-1 反映）★

段6 は回数を期待値に含める工程であるため、★集計コマンドまで確定させる。★

`grep -c` の対象文字列を上記のとおり固定すること。

非退行試験を先に通すと「通ったから良い」で V-2 が省略される危険がある（KY80 と同型の心理）。
