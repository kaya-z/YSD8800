## 1. Q8.8 仕様の正本（実源照合済・KY34）

**推測ではなく scc23 v2.06 の実装から抽出**した。スクリプトはこれと
**bit 単位で一致**しなければならない。

### 1.1 リテラル変換（`scc23_v2_06.c` L1090-1091）

```c
/* [v2.00] §4.3: float定数。double->Q8.8(int16)変換。 */
static int16_t to_fixed(double x) { return (int16_t)(x * 256.0); }
```

- `x * 256.0` を **`int16_t` へキャスト**
- C の浮動小数点→整数変換は **ゼロ方向への切り捨て**（四捨五入ではない）
- 16bit 符号付き ⇒ 表現範囲 **-32768 〜 +32767**（実数値で約 -128.0 〜 +127.99609375）
- 分解能 1/256 = 0.00390625

**検算**：8.5 × 256 = 2176 = `0x0880` ✅（誤記の `0x0850` = 2128 = 8.3125 は別物）

### 1.2 四則演算（`scc23_v2_06.c` L1140-1155）

```c
static int fold_binop_val(sir_op_t op, int a, int b, ctype_t type) {
    if (type==T_FLOAT) {
        switch (op) {
        case SIR_ADD:  return (int16_t)(a + b);
        case SIR_SUB:  return (int16_t)(a - b);
        case SIR_FMUL: {
            int32_t tmp = (int32_t)a * b;
            if (tmp > (int32_t)0x7FFF00 || tmp < -(int32_t)0x800000)
                warning("float overflow in constant FMUL");
            return (int16_t)(tmp >> 8);
        }
        case SIR_FDIV:
            if (b == 0) { error("division by zero"); return 0; }
            return (int16_t)(((int32_t)a << 8) / b);
        default: return 0;
        }
    }
    ...
}
```

| 演算 | 式 | 丸め方向 | 備考 |
|---|---|---|---|
| 加算 | `(int16_t)(a + b)` | — | int16 でラップ |
| 減算 | `(int16_t)(a - b)` | — | int16 でラップ |
| **乗算** | `(int16_t)(((int32_t)a * b) >> 8)` | **算術右シフト＝負の無限大方向** | overflow warning あり |
| **除算** | `(int16_t)(((int32_t)a << 8) / b)` | **C の整数除算＝ゼロ方向** | b=0 は error |

### 1.3 ★重要論点：丸め方向の非対称★

**乗算と除算で丸め方向が異なる**：

- **FMUL** は `>> 8`（算術右シフト）→ **負の無限大方向**（floor）
  - 例：`-1 >> 8 == -1`（0 にならない）
- **FDIV** は `/`（C の整数除算）→ **ゼロ方向**（truncate）
  - 例：`-1 / 256 == 0`

**この非対称は scc23 の実装そのままであり、ヘルパスクリプトも同一に再現する。**
「数学的に正しい丸め」に直してはならない。**ヘルパの役割は scc23 の挙動を
正確に予測することであり、あるべき姿を示すことではない**（原則120 の趣旨）。

### 1.6 ★実測で判明：負のリテラルを含む式は定数畳み込みされない★

> ★v0.2 E-1 反映★：本節は起草中の発見として §1.5 に挿入したため節番号が
> 1.3 → 1.5 → 1.4 の順に乱れていた。読み順を整えるため **§1.6 として末尾へ改番**した
> （内容は不変・KY41）。以降、本文書内の「§1.5」への参照は「§1.6」に読み替える。

設計メモ起草時の実測（scc23 v2.06）で判明した重要事項：

```c
int main() { float r; r = -1.0 / 3.0; return 0; }
```

の生成コードは：

```
    LDW  A, #256          ; 1.0 の Q8.8
    LDW  B, #0
    SUB  B, A             ; 0 - 1.0 として単項マイナスを実行時計算
    MOV  A, B
    ...
    LDW  A, #768          ; 3.0 の Q8.8
    JSR  _fdiv            ; ★ランタイム呼出＝畳み込まれていない★
```

**単項マイナスは `0 - x` として実行時に展開される**ため、
`-1.0 / 3.0` は `fold_binop_val` に到達せず定数畳み込みされない。

**ヘルパ設計への影響**：
- ヘルパの F3（C式評価）が返すのは「**定数畳み込みが行われた場合の値**」である
- 負のリテラルを含む式では、scc23 は畳み込まず**ランタイム `_fdiv`/`_fmul` で計算**する
- ランタイム実装の丸めが `fold_binop_val` と一致するかは**別途確認が必要**（§7.5 に申し送り）
- **ヘルパの出力に「畳み込み対象か否か」の注記を付ける**ことを F3 の要件に追加する

**正値のみの式では畳み込みが行われることを実測確認済**（§4.2 の V2 で正式検証）：

| 式 | 実測即値 | 検算 | 判定 |
|---|---|---|---|
| `1.0/3.0` | 85 | `(256<<8)/768 = 85.33 → 85` | ✅ |
| `2.0/3.0` | 170 | `(512<<8)/768 = 170.67 → 170` | ✅ |
| `0.5*0.5` | 64 | `(128*128)>>8 = 64` | ✅ |
| `0.1*0.1` | 2 | `(25*25)>>8 = 625>>8 = 2` | ✅ |
| `5.0/7.0` | 182 | `(1280<<8)/1792 = 182.86 → 182` | ✅ |

**§1 で抽出した仕様が実測と完全一致することを確認済**（KY34）。

### 1.4 オーバーフロー判定条件（FMUL）

```c
if (tmp > (int32_t)0x7FFF00 || tmp < -(int32_t)0x800000)
    warning("float overflow in constant FMUL");
```

- `0x7FFF00` = 8388352、`-0x800000` = -8388608
- **warning であり error ではない**（値は `(int16_t)(tmp >> 8)` として返る）
- ヘルパは同条件で**警告表示**し、値も同様に返す

## 2. スクリプト設計

### 2.1 名称と配置

- 名称：**`q88.py`**（版数 v1.0）
- 配置：`tools/`（C-1 の `tests_c1/` と並ぶ補助ツール置き場）
- 実行系：Python 3（プロジェクトで既に `gen_matrix.py` 等に使用）

### 2.2 提供機能

| # | 機能 | 用途 |
|---|---|---|
| F1 | **実数 → Q8.8 hex**（`to_fixed` 相当） | 期待値の手計算を排除（C-2 の主目的） |
| F2 | **Q8.8 hex → 実数** | 生成 asm 中の即値を読むときの逆変換 |
| F3 | **C 式の評価**（`2.5 / 4.0` 等を Q8.8 演算で計算） | 演算結果の期待値生成 |
| F4 | **バッチ変換**（複数値を一括） | テストケース一覧の期待値生成 |
| F5 | **自己検証モード**（`--selftest`） | scc23 実挙動との一致確認 |

### 2.3 F3（C式評価）の対象範囲

**本 v0.1 のスコープ**：
- 二項演算 `+` `-` `*` `/` の**1段**（例：`2.5 * 4.0`）
- 括弧を含む複数段の式（例：`(1.5 + 2.5) * 2.0`）
- 単項マイナス（例：`-2.5`）

**スコープ外**（申し送り §7）：
- 変数・関数呼び出しを含む式
- 比較演算・論理演算
- int と float の混在式（I2F 昇格の再現）→ §7.1

**★v0.2 N-2 反映：スコープ外入力は「明示エラー」とする★**

F3 が **int リテラル**（例：`2.5 + 3` の `3`）を検出したら、
**黙って float として扱わず、明示的にエラーを返す**：

```
$ python3 q88.py --eval "2.5 + 3"
ERROR: integer literal '3' in expression.
       int/float mixed expressions are not supported (see design memo §7.1).
       scc23 applies wrap_i2f (<<8) to the int side; this helper does not
       reproduce that promotion yet. Write '3.0' if you meant a float.
```

**理由**：`3` を暗黙に `3.0` とみなすと、scc23 の実挙動（`wrap_i2f` による `<<8` 昇格）と
一致する保証がなく、**誤った期待値を生成する**リスクがある。これは §3.3 で挙げた
「ヘルパが誤った期待値を自動生成する装置になる」最重要リスクそのものである。
**対応していないものは、黙って推測せずエラーにする**。

### 2.4 出力形式

```
$ python3 q88.py 8.5
8.5           -> 0x0880  (2176)   [exact]

$ python3 q88.py 0.1
0.1           -> 0x0019  (25)     [truncated: 0.09765625, err=-0.00234375]

$ python3 q88.py --eval "2.5 / 4.0"
2.5           -> 0x0280  (640)
4.0           -> 0x0400  (1024)
2.5 / 4.0     -> 0x00A0  (160)    = 0.625        [FDIV: (640<<8)/1024]

$ python3 q88.py --batch values.txt
（1行1式で一括処理）
```

**`[exact]` / `[truncated]` の表示**は、C-2 の目的（手計算ミス防止）に加え
**「Q8.8 で表現できない値」への気づき**を与えるために設ける。
0.1 のような値は誤差を持つため、期待値作成時に見落とすと後で混乱する。

### 2.5 F5 自己検証モード（`--selftest`）の設計

**ヘルパ自身が間違っていたら本末転倒**であるため、自己検証を必須機能とする。

**方式**：既知の値ペアを内蔵し、変換結果を照合する。

#### 2.5.1 グループA：基本変換（F1）

| 入力 | 期待 hex | 根拠 |
|---|---|---|
| 8.5 | `0x0880` | **C-2 の元となった誤記事例**（誤 `0x0850`） |
| 2.5 | `0x0280` | C-1 テストで使用・実測済 |
| 4.0 | `0x0400` | C-1 テストで使用・実測済 |
| 1.0 | `0x0100` | 単位元 |
| 0.5 | `0x0080` | 小数部の基本 |
| -1.0 | `0xFF00` | 負値 |
| -2.5 | `0xFD80` | 負値の小数 |

#### 2.5.2 グループB：割り切れる演算（丸めなし）

| 入力 | 期待 hex | 期待10進 | 経路 |
|---|---|---|---|
| `2.5 / 4.0` | `0x00A0` | 0.625 | FDIV |
| `2.5 * 4.0` | `0x0A00` | 10.0 | FMUL |
| `1.5 + 2.5` | `0x0400` | 4.0 | 加算 |

#### 2.5.3 ★グループC：丸め方向の非対称を検出するケース★（v0.2 M-1 反映・必須）

> **★v0.2 M-1 反映★**：v0.1 の内蔵10件（グループA＋B）は**全て割り切れる値**で
> 丸めが一切発生せず、負値ケースも F1（リテラル変換）のみだった。そのため
> **実装者が FMUL を truncate で、あるいは FDIV を floor で実装しても self-test は
> 全 PASS してしまい**、§1.3 で「最重要論点」とした丸め非対称の検証が
> 機能していなかった（レビュー指摘 M-1）。本グループを必須ケースとして追加する。

| # | 入力 | 期待 hex | 期待10進 | 誤実装時の値 | 検出内容 |
|---|---|---|---|---|---|
| C1 | **`-1.0 / 3.0`** | `0xFFAB` | **-85** | floor なら **-86**(`0xFFAA`) | **FDIV のゼロ方向丸め**を検証 |
| C2 | **`-0.1 * 0.1`** | `0xFFFD` | **-3** | truncate なら **-2**(`0xFFFE`) | **FMUL の floor（算術右シフト）**を検証 |
| C3 | **`-0.5 * 0.1`** | `0xFFF3` | **-13** | truncate なら **-12**(`0xFFF4`) | 同上（C2 の補強） |
| C4 | `1.0 / 3.0` | `0x0055` | 85 | — | 正値だが**丸めが発生**（85.33→85） |
| C5 | `0.1 * 0.1` | `0x0002` | 2 | — | 丸め発生（625>>8=2）・§1.6 実測済 |

**C1〜C3 が非対称検証の要**である。いずれも**丸め方向を取り違えると値が変わる**ため、
実装ミスを確実に検出できる。

**★レビュー提示ケースからの差し替え（v0.2 で強化）★**：
レビュー指摘 M-1 は FMUL 検証に `-1.0 * 0.1` を提示したが、レビュー反映時の検算で
**このケースは floor/truncate ともに -25 となり分岐しない**（`-6400 >> 8 = -25`、
`-6400 / 256 = -25`）ことが判明した。そこで**実際に分岐する** `-0.1 * 0.1`（C2）と
`-0.5 * 0.1`（C3）へ差し替えた。検算結果：

| 式 | a | b | tmp = a×b | floor（正） | truncate（誤） | 分岐 |
|---|---|---|---|---|---|---|
| `-1.0 * 0.1` | -256 | 25 | -6400 | -25 | -25 | ✗ 同値 |
| **`-0.1 * 0.1`** | -25 | 25 | -625 | **-3** | -2 | ✅ 分岐 |
| **`-0.5 * 0.1`** | -128 | 25 | -3200 | **-13** | -12 | ✅ 分岐 |

（`-625 >> 8` は算術右シフトで -3、`-625 / 256` はゼロ方向で -2。
tmp が 256 の倍数だと両者は一致するため、**倍数でない負値**を選ぶ必要がある。）

#### 2.5.4 グループC の位置づけ（scc23 実挙動突合の対象外）★重要★

§1.6 のとおり、**負のリテラルを含む式は scc23 では定数畳み込みされず**
ランタイム `_fmul`/`_fdiv` で計算される。したがってグループC の負値演算ケース
（C1〜C3）は：

- **self-test の対象**：`fold_binop_val` を再現するヘルパの**内部ロジック検証**として実施する
- **V2（scc23 実挙動突合）の対象外**：scc23 側が畳み込まないため即値として現れない

**V2 では正値の丸め発生ケース（C4・C5 等）を使う**（§4.2 に明記）。

なお、ランタイム `_fmul`/`_fdiv` の丸めが `fold_binop_val` と一致するかは
**別問題**であり §7.5 に申し送る（不一致なら潜在バグ）。

さらに **scc23 実挙動との突合**を行う（§4 V2）。

### 2.6 C-1 マトリクステストとの連携（将来）

C-1 設計メモ v0.4 §7.2 の「数値一致検証」は、本ヘルパを使って以下の形で実現できる：

1. `q88.py --eval "2.5 / 4.0"` で期待値 `0x00A0` を生成
2. C-1 の `m1_f_div_*_p` ケースを emu23 で実行し、結果レジスタ値を取得
3. 両者を照合

**本 v0.1 では 1 のみを提供**（2/3 は emu23 連携が必要なため §7.3 に申し送り）。

## 3. 安全性・副作用の解析

### 3.1 コンパイラ本体への影響

**なし**。補助スクリプトのみで scc23 本体は触らない。
Dhrystone 絶対ゲート・-O1 cycles ともに不変。

### 3.2 既存テストへの影響

**なし**。C-1 マトリクステスト（24/24 PASS）は golden byte 一致による構造的検証であり、
本ヘルパとは独立している。

### 3.3 ヘルパ自体の誤りリスク（最重要）

**ヘルパが間違っていると、誤った期待値を「自動生成」する装置になり、
手計算より危険**（誤りが機械的に量産され、かつ「自動化したから正しい」という
誤った安心感を与える）。

**対策**：
1. **実源から仕様を抽出**（§1・推測禁止・KY34）
2. **`--selftest` を必須実装**（§2.5）
3. **scc23 実挙動との突合を検証項目に含める**（§4 V2）
4. 丸め方向の非対称（§1.3）を**意図的にそのまま再現**し、
   「数学的に正しく直す」誘惑を設計段階で禁止

## 4. 検証計画

### 4.1 V1: `--selftest` 全 PASS

§2.5 の内蔵ケース全て（グループA/B/C）が PASS すること。特に：

- **8.5 → `0x0880`**（C-2 の元となった誤記事例）が正しく変換されること
- **★グループC（§2.5.3）の丸め非対称検出ケースが PASS すること★**
  - C1 `-1.0/3.0` → **-85**（`0xFFAB`）：floor 実装なら -86 で FAIL するはず
  - C2 `-0.1*0.1` → **-3**（`0xFFFD`）：truncate 実装なら -2 で FAIL するはず
  - C3 `-0.5*0.1` → **-13**（`0xFFF3`）：truncate 実装なら -12 で FAIL するはず

**negative test の実施**：実装完了後、意図的に FDIV を floor で／FMUL を truncate で
実装した版を作り、**self-test が FAIL することを確認**する。
self-test が「壊れた実装を検出できること」自体を検証する（C-1 の negative test と同趣旨）。

### 4.2 V2: scc23 実挙動との突合（最重要）

**方式**：ヘルパの計算結果と、scc23 v2.06 が実際に生成する即値を照合する。

1. テスト用 C ソースを生成（例：`float x; x = 2.5 / 4.0;`）
2. scc23 v2.06 でコンパイルし、生成 asm 中の即値（`LDW A, #160` 等）を抽出
3. `q88.py --eval "2.5 / 4.0"` の結果（`0x00A0` = 160）と一致することを確認

**★v0.2 反映：V2 の対象は「正値の丸め発生ケース」★**

§1.6 のとおり **負のリテラルを含む式は scc23 で畳み込まれない**ため、
即値として asm に現れず突合できない。したがって V2 の対象は
**正値かつ丸めが発生する式**とする（§2.5.4 参照）。

**対象ケース**（最低限）：
- 加算・減算・乗算・除算の各1件以上（**全て正値リテラル**）
- **丸めが発生する式**：`1.0 / 3.0`（→85）、`2.0 / 3.0`（→170）、
  `0.1 * 0.1`（→2）、`5.0 / 7.0`（→182）
  — いずれも §1.6 で実測済。ヘルパ出力との一致を正式検証する
- 割り切れる式：`2.5 / 4.0`（→160）、`0.5 * 0.5`（→64）

**負値演算ケース（§2.5.3 C1〜C3）は V2 の対象外**。
これらは self-test（V1）でヘルパ内部ロジックを検証する位置づけ。
ランタイム `_fmul`/`_fdiv` との突合は §7.5 の申し送り事項。

### 4.3 V3: 境界値・異常系

- オーバーフロー（FMUL の warning 条件）
- ゼロ除算（error）
- Q8.8 表現範囲外の入力（例：200.0）
- 表現できない値（0.1 等）の `[truncated]` 表示

### 4.4 V4: 誤記事例の再現防止

C-2 の元となった誤記（8.5 → `0x0850`）が、ヘルパ使用により
**発生し得ない**ことを確認（`q88.py 8.5` が必ず `0x0880` を返す）。

## 6. 実装時の再現要件（確認済・v0.2 N-1 反映）

> ★v0.2 N-1 反映★：v0.1 は本節を「実装前の追加確認事項」としていたが、
> **§1.6 の実測（`1.0/3.0`→85、`0.5*0.5`→64、`0.1*0.1`→2 等が実測と完全一致）により
> 既に実証済**であり、未確認事項ではない。「確認済の再現要件」へ位置づけを改める。
> 未確認事項が残っているかのような記述はレビュー承認の判断を曖昧にするため。

以下は **確認済の事実**であり、Python 実装で**明示的に再現すべき要件**である：

| # | 事実（確認済） | Python 側の再現方法 |
|---|---|---|
| 1 | `(int16_t)` キャストは **2 の補数ラップ**（C99 では実装定義だが gcc ビルドの scc23 は 2 の補数）。§1.6 実測で実証 | `ctypes.c_int16(v & 0xFFFF).value` で明示再現 |
| 2 | FMUL の `>> 8` は負数に対し **算術右シフト**（C99 では処理系定義だが gcc は算術シフト）。§1.6 実測（`0.1*0.1`→2 等）および §2.5.3 の検算で実証 | Python の `>>` は整数に対し算術シフトのため素直に `tmp >> 8` |
| 3 | FDIV の `/` は **ゼロ方向切り捨て**（C の整数除算） | Python の `//` は floor のため**そのまま使えない**。`abs()` で商を取り符号を後付けする実装が必須 |

**特に #3 は要注意**：Python の `//` を素朴に使うと floor になり、
scc23（ゼロ方向）と**負値で結果が食い違う**（§2.5.3 C1：-85 が -86 になる）。

## 7. 将来課題（申し送り・KY41）

### 7.1 int / float 混在式の対応

現状 F3 は float のみ。`2.5 + 3`（int 混在）は scc23 では `wrap_i2f` により
int 側が `<< 8` されてから演算される。この昇格規則の再現は v0.2 以降で検討。

### 7.2 変数を含む式

`x * 2.5`（x は変数）のような式は静的に評価できない。
シンボリックな出力（例：`x_q88 * 640 >> 8`）を返す機能は将来検討。

### 7.3 emu23 連携による数値一致検証

C-1 設計メモ v0.4 §7.2 の「演算結果の数値一致検証」を完成させるには、
emu23 実行結果との照合が必要。本ヘルパはその**期待値生成側**を担う。
実行側との結合は Phase 2 以降または C-1 の拡張として検討。

### 7.5 ランタイム `_fmul`/`_fdiv` の丸めと `fold_binop_val` の一致確認

§1.6 の実測で、**負のリテラルを含む式は定数畳み込みされずランタイム
`_fmul`/`_fdiv` で計算される**ことが判明した。ヘルパは `fold_binop_val`
（コンパイル時畳み込み）を再現するが、**ランタイム実装の丸めが
これと一致するかは未確認**である。

不一致があれば「コンパイル時に畳み込まれた場合と、実行時に計算された場合で
結果が異なる」ことになり、それ自体が潜在バグである。
**★v0.2 で優先度引き上げ★**（レビュー観点8への回答を反映）：
本件は「コンパイル時畳み込みと実行時計算で結果が異なる」潜在バグであり、
**C-3 と同種の値破壊**につながる。Phase 2 を待たず、
**C-2 完了後の短時間調査として実施する**。

調査手順（想定）：
1. `_fmul`/`_fdiv` のランタイム実装（scc23 が emit するアセンブラ）を実源照合
2. シフト方向（`SAR` か `SHR` か）・除算の符号処理を確認
3. `fold_binop_val` の丸めと一致するか判定
4. 不一致なら設計メモを起票し修正（Phase 1 の追加タスク or Phase 2 へ繰入）

### 7.6 単項マイナスの定数畳み込み

§1.6 のとおり単項マイナスは `0 - x` として実行時展開され畳み込まれない。
最適化の観点では `-1.0` を直接 `0xFF00` の定数として畳み込む余地がある
（Phase 5「残る最適化」の候補）。ただし本 C-2 のスコープ外。

### 7.4 Q16.16 への拡張

Phase 6（Q16.16・32bit float）着手時、本ヘルパを Q16.16 対応へ拡張する
（`--format q16.16` 等）。仕様は Phase 6 の設計時に確定する。
