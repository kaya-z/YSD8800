## 1. 背景と目的

### 1.1 現状の欠落

emu23 の対話モード（REPL）には**読み出し手段のみ**が存在し、**書き込み手段が皆無**である。

| 方向 | 論理アドレス | 物理アドレス |
|---|---|---|
| 読み出し | `mem` / `memw` | `physmem`（`--mmu` 時） |
| **書き込み** | **無し** | **無し** |

CLI 側にも `--poke` 相当のオプションは存在しない。

### 1.2 これが問題になる場面

| 場面 | 現状の回避策 | 問題 |
|---|---|---|
| 特定の変数値でのみ再現するバグの調査 | 値を作る asm を書いて再ビルド | 再現までのサイクル数が変わり、条件が変わる |
| MMIO レジスタの単発試験（TCR に書いてタイマー挙動を見る等） | テスト用 asm を都度作成 | KY38 の `_poc` ファイルが増え続ける |
| 異常値注入（境界値・不正ポインタ）による堅牢性確認 | 不可能に近い | KY54（否定形テスト先行）の実施を阻害 |
| ブレークポイント停止後の状態を変えて分岐を試す | 不可能 | 二分探索的なデバッグができない |

**とりわけ KY54（否定形テストを先行する）を実践するうえで、
異常値を直接注入できないことは構造的な制約になっている。**

### 1.3 目的

対話モードから**任意アドレスへバイト／ワード単位で書き込む**手段を提供する。

## 2. 実現可能性の検討（`sim_impl_policy_v0_2.md` 準拠）

承認済みポリシー **「ハードウェア実現不可能な機能をシミュレータに実装してはならない」**
に照らして検討する。

| 観点 | 判定 |
|---|---|
| 実機での相当機能 | ★**存在する**★ デバッグモニタ（ROM モニタ）による メモリ書き換えは MC6809 系では標準的機能である（ASSIST09 の `M` コマンド等）。JTAG/SWD 経由のメモリ書き込みも一般的 |
| FPGA 実装との対応 | 工程②.5 の**デバッグ DIO** および UART 経由モニタで実現可能 |
| CPU 動作への介入 | 無し。メモリ内容を変えるだけで、CPU の FSM や ISA には一切影響しない |

**結論：ポリシーに抵触しない。** むしろ工程②.5 のデバッグ DIO 設計の
先行検討として位置づけられる。

> ★**設計判断**★ 本機能は **ISA に新命令を追加しない**。
> ISA2.3 の命令セットは不変であり、`hasm23` / `scc23` / RTL への波及は無い。

## 3. 仕様

### 3.1 決定事項（ユーザ指示・2026-08-21）

| 項目 | 決定 |
|---|---|
| 提供形態 | **対話コマンドのみ**（CLI オプションは実装しない） |
| アドレス空間 | **論理・物理の両方** |
| MMIO 領域の扱い | ★**実機同等に副作用を発火させる**★ |

### 3.2 コマンド体系

既存の読み出しコマンドと**対をなす命名**とする。

| コマンド | 機能 | 対をなす読み出し |
|---|---|---|
| `setb <addr> <val> [<val>...]` | 論理アドレスへ**バイト**書き込み | `mem` |
| `setw <addr> <val> [<val>...]` | 論理アドレスへ**ワード**書き込み（16bit・リトルエンディアン） | `memw` |
| `setpb <addr> <val> [<val>...]` | 物理アドレスへ**バイト**書き込み（`--mmu` 時のみ） | `physmem` |
| `setpw <addr> <val> [<val>...]` | 物理アドレスへ**ワード**書き込み（`--mmu` 時のみ） | — |

**書式**

- `<addr>`：16 進。`$` 前置・`0x` 前置・裸の 16 進すべて許容（既存 `b` コマンドと同じ流儀）
- `<addr>`：**シンボル名も許容**（`--sym` 指定時。既存 `b <addr|label>` と同じ解決経路を再利用）
- `<val>`：16 進。複数指定で**連続アドレスへ順に書き込む**
- 物理アドレスは 20bit（`--mmu` 時の `PHYS_AW`）

**使用例**

```
YUI> setb $0400 12 34 56        # $0400,$0401,$0402 に 0x12,0x34,0x56
YUI> setw $F000 1234            # $F000=0x34, $F001=0x12（リトルエンディアン）
YUI> setb Ch_1_Glob 41          # シンボル解決
YUI> setpb 0E00 FF              # 物理 $0E00 に 0xFF（--mmu 時）
```

### 3.3 出力

書き込み後、**書いた領域を読み返して表示する**（原則123：動作確認≠正常性確認）。

```
YUI> setb $0400 12 34 56
0400: 12 34 56
```

> **理由**：MMIO 領域では書いた値がそのまま読めるとは限らない
> （書き込み専用レジスタ、書き込みで自動クリアされるビット等）。
> **読み返して表示することで、書けたつもりで書けていない事故を防ぐ。**
> 読み返し自体も副作用を持ちうる MMIO では注意が必要（§4.3）。

## 4. 設計上の重要論点

### 4.1 ★論点1：サイクル課金の汚染防止（最重要）★

**改良4（v2.10）でメモリアクセスにサイクル課金が入った。**

```c
void wr8(uint16_t a, uint8_t v) { ...  mem_charge(pa, ACC_WR8); ... }
void wr16(uint16_t a, uint16_t v) { ... mem_charge(pa_lo, ACC_WR16); ... }
```

**デバッガの書き込みが `mem_charge()` を通ると、`-mc` / `--mem-latency` の
測定値が汚染される。** また `--cache-stats` のヒット率も歪む。

昨日確定した `-mc` = **339,240** は RTL と残差 0 で一致している値であり、
**デバッガ操作でこれが揺らぐことは絶対に避けねばならない。**

**方式：`dbg_access` グローバルフラグによる課金抑止**

```c
/* [v2.12] デバッガ由来のメモリアクセス中は 1。
 * CPU の命令実行に由来しないアクセスはサイクルを消費しない。 */
int dbg_access = 0;

static unsigned mem_charge(uint32_t pa, acc_kind_t kind)
{
    if (dbg_access) return 0;          /* ★v2.12 追加：デバッガ操作は非課金★ */
    if (!cache_enable) return 0;       /* ←既存。R1 死守 */
    ...
}
```

呼び出し側は `dbg_access` を立てて `wr8()` を呼び、必ず戻す。

```c
dbg_access = 1;
wr8(addr, val);
dbg_access = 0;
```

**採用理由**

| 案 | 評価 |
|---|---|
| 案A：`mem_charge()` 冒頭でフラグ判定 | ★**採用**★ 課金点が `mem_charge()` の 1 箇所に集約されているため、**抑止も 1 箇所で済む**。KY55（計上点の多重／欠落）の教訓に沿う |
| 案B：デバッガ専用の書き込み関数を別に作る | ✗ `wr8()` の MMIO ディスパッチを複製することになり、**原則122（兄弟実装）違反**。MMIO 副作用ありの要件と両立しない |
| 案C：書き込み前後で `cpu.cycle` を保存・復元 | ✗ キャッシュ統計の汚染を防げない。また `cpu.cycle` 以外の副作用に無力 |

> ★**KY 的注意**★ `dbg_access` の**戻し忘れ**が最大の危険である。
> 立てた直後の関数から**必ず 1 経路で戻る**構造にし、途中 `return` を作らない。
> 実装時に「立てる箇所」と「戻す箇所」の数が一致することを `grep -c` で機械照合する。

### 4.2 論点2：物理書き込みと MMU

`setpb` / `setpw` は **MMU 変換をバイパス**し、物理メモリ配列へ直接書く
（既存 `physmem` の読み出し経路と対称）。

| 項目 | 扱い |
|---|---|
| MMU 変換 | **行わない**（物理アドレスをそのまま使用） |
| `--mmu` 非指定時 | コマンド自体を**受け付けない**（既存 `physmem` と同じ扱い） |
| MMIO 帯（$FC80-$FFFF）を物理指定した場合 | ★§4.3 参照★ |

### 4.3 ★論点3：MMIO 副作用の扱い★

**ユーザ決定：実機同等に副作用を発火させる。**

論理アドレス側（`setb` / `setw`）は既存 `wr8()` / `wr16()` をそのまま通すため、
MMIO ディスパッチと副作用が自動的に効く。**追加実装は不要。**

| 書き込み先 | 挙動 |
|---|---|
| UART TX（$FC80 等） | **文字が出力される** |
| YSD8002 TCR | **タイマーが起動／停止する。SW_START/SW_STOP も発火する** |
| YSD8003 制御レジスタ | **SD アクセスが開始される** |
| MMU PTR / MCR | **マッピングが変わる** |

> ★**警告を要する事項**★
> `setb` で YSD8002 の TCR に SW_START/SW_STOP を書くと、
> **`score_r` が破壊され測定値が無意味になる。**
> 副作用ありを選択した以上これは仕様どおりだが、
> **MMIO 帯への書き込み時は警告を表示する**こととしたい（§4.4）。

**物理アドレス側の扱い（要レビュー判断）**

MMIO は MMU 変換対象外である（`v3_5_design_memo` §2.3）。
したがって「物理アドレス $FC80」という概念は本来存在しない。

| 案 | 内容 |
|---|---|
| ★**案1（推奨）**★ | 物理側は**純粋な物理メモリ配列のみ**を対象とし、MMIO ディスパッチを行わない。$FC80 以降を物理指定しても RAM として書く |
| 案2 | 物理側でも MMIO 帯を検出して副作用を発火させる |

**案1 を推奨する。** 理由は、既存の読み出し `physmem` が
**物理メモリ配列を直接ダンプする実装**であり、対称性を保つべきだからである。
物理側で MMIO を叩きたい場合は論理側 `setb` を使えばよい。

### 4.4 論点4：安全策

| # | 安全策 | 理由 |
|---|---|---|
| 1 | **MMIO 帯（$FC80-$FFFF）への書き込み時は警告を表示** | 副作用ありのため、意図しない発火を防ぐ。`[WARN] MMIO write: side effects may occur` |
| 2 | **書き込み後に読み返して表示**（§3.3） | 原則123。書けたつもりを防ぐ |
| 3 | **`-q` モードでは無効**（対話モード専用） | 測定の再現性を守る |
| 4 | **`dbg_access` により非課金**（§4.1） | 測定値の汚染防止 |

### 5.2 実装順序（1変更1検証）

### 5.3 ★KY54：否定形テストを先行する★

正常系より先に以下を確認する。

| # | 否定形テスト | 期待 |
|---|---|---|
| N1 | `setb` を引数なしで実行 | `Usage:` 表示・クラッシュしない |
| N2 | `setb` にアドレスのみ（値なし） | `Usage:` 表示 |
| N3 | 不正な 16 進文字列（`setb zz 12`） | エラー表示・書き込まない |
| N4 | `setpb` を `--mmu` 無しで実行 | 拒否メッセージ |
| N5 | 物理アドレスが範囲外（20bit 超） | 拒否・配列外書き込みしない |
| N6 | `-q` モードで REPL コマンドが効かないこと | そもそも REPL に入らない |
| N7 | ★`setb` 実行後に `-mc` の値が変わらないこと★ | **課金汚染なし** |

**N7 が本機能で最も重要な否定形テストである。**

## 8. レビューで判断を仰ぎたい点

| # | 論点 |
|---|---|
| **Q-1** | コマンド名を `setb`/`setw`/`setpb`/`setpw` としてよいか。MC6809 系モニタの流儀（ASSIST09 の `M`、`OS-9` の `dEd`）に寄せる案もある |
| **Q-2** | §4.3 の物理側 MMIO の扱いは**案1（MMIO ディスパッチしない）**でよいか |
| **Q-3** | §4.1 の `dbg_access` 方式（案A）でよいか。課金抑止を `mem_charge()` の 1 箇所に集約する設計 |
| **Q-4** | §3.3 の「書き込み後に読み返して表示」は、MMIO 領域では読み返し自体が副作用を持ちうる。**MMIO 帯では読み返しを省略**すべきか |
| **Q-5** | レジスタへの書き込み（`set A 1234` 等）も併せて実装すべきか。本設計では**対象外**としているが、デバッグ用途では同様に有用である |
