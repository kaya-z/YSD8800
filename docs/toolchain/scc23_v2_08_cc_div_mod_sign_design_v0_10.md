## 0. ゴールと前提

### 0.1 ゴール

1. `_cc_div`/`_cc_mod` に符号分離・絶対値化処理を追加し、C99 準拠に是正する。
2. `_cc_mod` にゼロ除算ガードを新設し、`x % 0` の実機ハングを解消する。
3. INT_MIN（-32768）を含む全境界値で正しい結果を返す。
4. **【v0.4】** ランタイム肥大が **Dhrystone ビルド**で成立すること（§3.8）。
5. **【v0.5】** ランタイム肥大が **YUI OS ユーザーランド（Cプロセス区画）**でも成立すること。
   そのための応急処置として**ランタイム出力を細粒度化**する（§3.11）。
6. **【v0.7】** 細粒度化が**既存の検証資産（C-1 golden）**に与える影響を、
   ルールに則って処理すること（§4.10）。

### 0.2 着手前の絶対条件（原則43）

§3.1〜§3.7 の `_cc_div`/`_cc_mod` 本体修正は**実装済・検証済（§4.6）**。
§3.11（細粒度化）は**指摘書 v6.0 で承認済であり、実装着手可**。

> ⚠ **ただし §4.10 の golden 更新方針が承認されるまで、
> `goldens/*.golden.asm` および `c1_goldens_bundle_*.txt` を書き換えてはならない。**
> C-1 の**実行と差分の観察は可**（指摘書 v6.0 §8）。

### 1.5 ISA2.3 の比較・分岐の実像

| 項目 | 実源 | 内容 |
|---|---|---|
| FLAGS | `emu23_v2_13.c`（v2.13）L248-249 | `FL_Z`(0x01) / `FL_N`(0x02) のみ。**V・C フラグ非存在** |
| フラグ更新 | 同 L2210-2213 `set_zn()` | `Z ← (v==0)`、`N ← (v & 0x8000)` |
| CMP / CMPI | 同 L2521 / L2528 | `set_zn((uint16_t)(*rd - *rs))` — **差の bit15 を N に入れるだけ** |
| BLT / BGE | 同 L2634-2643 | **BLT: N=1 で分岐／BGE: N=0 で分岐** |
| LDW | 同 L2438 | `set_zn(*rd)` — **フラグを破壊する** |

**帰結1**：`BLT` は `N XOR V` ではなく **`rD − rS` の bit15** を見るだけ。
反例：`CMP A,B`（A=$8000, B=$0002）→ `$7FFE` → bit15=0 → **N=0** → `BLT` 不成立。

**帰結2**：符号なし比較分岐（`BLO`/`BHS`/`BCC`/`BCS`）は存在しない
（`hasm23_v1_04.c`（v1.04）L165-168）。

**帰結3（本設計の基盤）**

> **命題**：`A ∈ [0, 32768]`、`B ∈ [1, 32768]`（符号なし解釈）のとき、
> `CMP A, B` 後の N フラグは符号なし比較 `A < B` と厳密に一致する。
>
> **証明**：N = `(A − B) mod 2^16` の bit15。
> - `A ≥ B` のとき `A − B ∈ [0, 32768]`。`A−B = 32768` は `A=32768, B=0` のみで、
>   前提 `B ≥ 1` により起こり得ない。よって `[0, 32767]` → bit15=0 → **N=0**。
> - `A < B` のとき `A − B ∈ [−32768, −1]` → `mod 2^16` で `[32768, 65535]` → bit15=1 → **N=1**。∎

**X レジスタ**：`PUSH`/`POP` は A/B/X の3本が定義済（`hasm23_v1_04.c` L97-102）。
`parse_reg`（同 L268-271）で X=2 として受理。**§4.1 のスモークテストで実機動作を確認済**。

```
_cc_div:
    PUSH X                          ; callee-save（X=符号フラグ）
    CMPI A, #0
    BEQ  _ccdiv_zero                ; 経路C: 除数0
    LDW  X, #0
    CMPI A, #0                      ; ※LDW がフラグを破壊するため再度必要
    BGE  _ccdiv_apos
    XORI X, #1
    NOT  A
    ADDI A, #1                      ; A = |除数|（$8000 のときは $8000 のまま）
_ccdiv_apos:
    STW  A, [_C_DIV_A]
    CMPI B, #0
    BGE  _ccdiv_bpos
    XORI X, #1
    NOT  B
    ADDI B, #1
_ccdiv_bpos:
    STW  B, [_C_DIV_B]
    LDW  A, #0
    STW  A, [_C_DIV_Q]
_ccdiv_loop:                        ; ★v2.07 から無変更★
    LDW  A, [_C_DIV_B]
    LDW  B, [_C_DIV_A]
    CMP  A, B
    BLT  _ccdiv_done
    SUB  A, B
    STW  A, [_C_DIV_B]
    LDW  A, [_C_DIV_Q]
    ADDI A, #1
    STW  A, [_C_DIV_Q]
    JMP  _ccdiv_loop
_ccdiv_done:
    LDW  A, [_C_DIV_Q]
    CMPI X, #0
    BEQ  _ccdiv_ret
    NOT  A
    ADDI A, #1
_ccdiv_ret:
    POP  X
    RET
_ccdiv_zero:
    LDW  A, #0
    POP  X
    RET
```

**スタック収支**：経路N（通常）・経路C（ゼロ除算）とも `PUSH X` 1回／`POP X` 1回＝**±0**。
**実測サイズ：124B**（$D98E-$DA09・既定値マップ時）。

### 3.4 `_cc_mod` 改修後の確定命令列（実装済）

```
_cc_mod:
    PUSH X
    CMPI A, #0
    BEQ  _ccmod_zero                ; ★新設：ゼロ除算ガード★
    LDW  X, #0
    CMPI A, #0
    BGE  _ccmod_apos
    NOT  A                          ; ★除数は絶対値化のみ。XORI X,#1 を置かない★
    ADDI A, #1
_ccmod_apos:
    STW  A, [_C_DIV_A]
    CMPI B, #0
    BGE  _ccmod_bpos
    XORI X, #1                      ; ★ここだけ符号フラグ更新（C99: 剰余の符号=被除数）★
    NOT  B
    ADDI B, #1
_ccmod_bpos:
    STW  B, [_C_DIV_B]
_ccmod_loop:                        ; ★v2.07 から無変更★
    LDW  A, [_C_DIV_B]
    LDW  B, [_C_DIV_A]
    CMP  A, B
    BLT  _ccmod_done
    SUB  A, B
    STW  A, [_C_DIV_B]
    JMP  _ccmod_loop
_ccmod_done:
    LDW  A, [_C_DIV_B]
    CMPI X, #0
    BEQ  _ccmod_ret
    NOT  A
    ADDI A, #1
_ccmod_ret:
    POP  X
    RET
_ccmod_zero:
    LDW  A, #0
    POP  X
    RET
```

**スタック収支**：2経路とも **±0**。**実測サイズ：102B**（$DA0A-$DA6F・既定値マップ時）。

> **「-0」が生じない**：符号付与で A=0 のとき `NOT 0` = $FFFF、`ADDI #1` = $0000 で **0 のまま**。

### 3.5 影響範囲（コード面）

- **呼び出し元コード生成は無変更**。
- ⚠ **ワーク領域の共用**：`_C_DIV_A`（$DBFA）・`_C_DIV_B`（$DBFC）は
  **int除算と float ランタイムで共用**（`scc23_v2_07.c`（v2.07）L3947、L4063）。
  安全性は「**float演算中に `_cc_div`/`_cc_mod` は走らない**」という**相互排他の前提**による。
- `_C_DIV_Q`（$DBFE）は `_cc_div` 専用。
- ワーク領域 `$DBE8`-`$DBFF`（24B）の**アドレス割付は無変更**。
- `_fmul`/`_fdiv` の**コードは無変更**。
- **`scc23_Functional_Spec` の改版が必要**。

### 3.6 INT_MIN 専用経路を設けない根拠（v0.2 §3.6 の削除記録）

**削除の根拠**：§1.5 帰結3の命題により、`A ∈ [0,32768]`・`B ∈ [1,32768]` では
`CMP`/`BLT` が符号なし比較として厳密に機能する。この範囲は §3.7.1 の不変条件で保証される。

**等価性の確認**：
- **旧経路1**：ループ前の1回減算＋`Q=1` は、ループの1回目の反復と**等価**
  （`1 + floor((32768−d)/d) = floor(32768/d)`）。
- **旧経路2**：`100 − $8000` は bit15=1 → 即 done で商0・余り100。
  `$8000 − $8000 = 0` は bit15=0 → 1回減算して商1・余り0。

**削除の効果**：分岐経路 5本→**3本**、サイズ増 約240B→**約125B**。

### 3.7 守るべき不変条件

#### 3.7.1 【不変条件 I：オペランド範囲】

> 減算ループに入る時点で、
> - 被除数（`_C_DIV_B`）は符号なし解釈で **[0, 32768]**
> - 除数（`_C_DIV_A`）は符号なし解釈で **[1, 32768]**

**成立理由**：上限 32768＝入口の絶対値化／除数の下限 1＝入口のゼロ除算ガード／
剰余の単調減少＝ループは `SUB A,B` のみ。

**依存している ISA 仕様**：
> ⚠ ISA2.3 の FLAGS 定義（Z/N のみ。V・C 非存在）と `BLT`=N=1 / `BGE`=N=0 に依存。
> **V フラグ追加で `BLT` が `N XOR V` へ再定義された場合、
> または 32bit 型対応でオペランド範囲が変わった場合は再検証が必須。**

**実装要件**：生成 asm の両ルーチン直前に警告コメントを出力（実装済）。

```
; NOTE: BLT is N-only (no V flag in ISA2.3). Valid while |rem|<=32768 and 1<=|div|<=32768.
```

##### 3.11.3.4 フラグを立てる箇所：**`scc23_v2_08.c`（v2.08）L3115**

> **【v0.7・B-1】実装者が直接編集する箇所であるため、ファイル名と版数を明示する。
> これは `scc23_v2_08.c`（v2.08・本改修で作成済）の L3115 である。**
> **`scc23_v2_07.c`（v2.07）では L3092 に相当**（v2.08 でヘッダコメント23行を追加したため）。

関数呼び出しの `JSR` を生成しているのは **`emit_expr()` 内の L3115 が唯一**である
（`grep -n 'emit("    JSR  _%s"' scc23_v2_08.c` で確認。他の `JSR` 生成は
`_cc_mul`/`_cc_div`/`_cc_mod`/`_fmul`/`_fdiv` の演算子経路のみで、いずれも既にフラグ制御済）。

**現状（`scc23_v2_08.c` L3110-3118）**：

```c
                emit_lval(arg);   /* アドレスを渡す */
            else
                emit_expr(arg);   /* 値をロードして渡す */
            emit_push_a();
        }
        emit("    JSR  _%s", n->fname);          /* ← L3115 */
        if (n->nargs>0)
            emit("    ADDI SP, #%d", n->nargs*2);  /* [F2] ★省略禁止 */
        break;
```

**変更後**：L3115 の直前に以下を挿入する。

```c
        /* [v2.08] 組込ランタイム関数の使用を記録（設計書v0.7 §3.11.3.4）。
         *   emit_runtime() 側で未使用関数の出力を抑止するため。
         *   ここは関数呼び出しJSR生成の唯一の箇所（演算子経路は別途フラグ済）。 */
        if      (strcmp(n->fname,"putchar")==0) g_use_putchar=1;
        else if (strcmp(n->fname,"getchar")==0) g_use_getchar=1;
        else if (strcmp(n->fname,"puts"   )==0) g_use_puts   =1;
        else if (strcmp(n->fname,"strcpy" )==0) g_use_strcpy =1;
        else if (strcmp(n->fname,"strcmp" )==0) g_use_strcmp =1;
        else if (strcmp(n->fname,"memcpy" )==0) g_use_memcpy =1;

```

**この位置の妥当性**：`emit_runtime()` は parse ループ完了後に呼ばれる
（`scc23_v2_08.c`（v2.08）L296 の改版履歴「RUNTIME 出力を parse loop の後へ」）。
したがって**全関数の本体生成が終わってからランタイムが出力される**ため、
L3115 で立てたフラグは確実に反映される。

> 予測値（`putchar` 34 ＋ `_cc_div` 124 ＋ `_cc_mod` 102）は、
> **Dhrystone 用の配置（`--runtime-org 0x0100`）で測った関数サイズを流用**したものである。
> 既定値マップでの実測は `_putchar`＋`_putchar_wait` = 34B（$D780-$D7A1・予測どおり）、
> `_cc_div` = 124B（$D7A2-$D81D・予測どおり）、
> **`_cc_mod` = 約 96B**（$D81E-$D87B ＋末尾 `POP X`/`RET`）で、
> **`_cc_mod` の 6B と末尾処理の計上差が乖離の正体**である。
> 判定は PASS（終端 $D87B < $DA80）であり、次回の見積りでは
> **同一配置で測った値を使う**こと。


既定値マップ（`putchar` と `/` `%` のみ使用）では
`getchar`/`puts`/`strcpy`/`strcmp`/`memcpy` の**5関数 492B が削減**され、
出力は `_putchar` / `_cc_div` / `_cc_mod` の3つのみとなった。

#### 4.10.1 予告：**細粒度化により golden 12件に必ず差分が生じる**

1. **判定方式**：`run_c1_matrix.sh` の `golden_cmp()` は

## 5. 実装時の重点確認項目

1. **X の callee-save**：全経路で `PUSH X` / `POP X` が1対1であること。→ 実装済・確認済

3. **`_cc_mod` の絶対値化では除数の符号を符号フラグに反映しない**（C99）。→ 実装済・確認済

5. **ISA2.3 に無い命令を使わない**。
6. **§3.7.1 の警告コメントを生成 asm に出力すること**。→ 実装済・確認済

    「混ざる前に分ける」こと**（§4.10.2）。中間バイナリによる段階比較が確実である。
    受入基準を作る前に、**その成果物に入っている変更を列挙する**。
18. **【v0.8】検証は「消してから作り直す」こと**（§4.10.6）。
    往復検証は、古い成果物が残っていると**欠落を素通しする**。
    バンドル・生成物の検証では、出力先を削除してから再生成する。
19. **【v0.8】受入基準・判定スクリプトも成果物として版数管理すること**。
    本改修では判定方式を3度作り直した（v1.1 → v1.2（没）→ **v1.3 採用**）。
20. **【v0.9・最重要】レビュー条件が「追記し、承認を得るまで」の形をとる場合、
    追記の完了は着手条件を満たさない。承認の受領をもって着手すること**（§0.6・§4.10.4）。
    **自分が書いた禁止条項の充足判定を、自分で行わない。**
    条件に「承認」「レビューを経る」の文言があれば、**相手からの応答が着手の合図**である。
21. **【v0.9】プロジェクト登録物のファイル名を版数の根拠にしないこと**（§0.7）。
    登録物は最新とは限らず、またファイル名と本体ヘッダが食い違うこともある
    （`yuios_build_procedure_v1_18.md` は L1 が「v1.17」のままであった）。
    **ファイル名・本体ヘッダ・改版履歴・項目表の4点を突き合わせること**（KY41）。
22. **【v0.10】検証に用いた道具（ツール）が更新されたら、
    「どの検証がその道具に依存するか」を項目ごとに洗い出し、依存するものを再実施すること**（§0.7.2）。
    **代表的な検証を1つ通しただけで「足場は同じ」と結論しない。**
    - ❌ Dhrystone のゲートが一致したから単体検証も通るはず（v0.9 の誤り）
    - ✅ Dhrystone は負数を通らない → **符号処理は未検証** → 単体検証も再実施する
    - 再実施の要否は「**その検証結果がツールの挙動で変わりうるか**」で判断する。
      `.sym` のアドレス比較・生成 asm の diff は**アセンブラ／コンパイラの出力**を見るもので
      エミュレータに依存しない。
23. **【v0.10】ゲート値・実測値を記録するときは、測定に用いたツールの版数を併記すること**（§0.3.3）。
      値は測定器と不可分である。
