## 1. 背景 ― C-1指摘の要旨

設計書 v1.1 に対する第2次レビューで、C-1（Critical）が条件付きクローズとされ、
「24件の空区間往復が**なぜ生成されるのか**、その因果を明示せよ」と要求された。

- P1 のスコープは **空区間往復のみ**（超保守）。asm 上で以下の4命令が完全隣接する箇所を対象とする:
  ```
  SUBI SP, #2
  STW  A, [SP]
  LDW  B, [SP]
  ADDI SP, #2
  ```
  これを `MOV B, A` 1命令へ置換する。
- dhry_timer.c を `-O1` でコンパイルした asm 上に、この4命令連続パターンが **24件** 実在する。

レビュアは因果仮説として「右オペランド emit（`emit_expr(n->right)`）が0命令を出力した結果、
push直後にpopが隣接して空往復になる」を提示した。

## 2. 追補調査 ― 生成起源の実測（v0.9 で到達・本 v1.0 に再掲）

### 2.1 emit経路プローブによる実測（KY34: 実ソース・実生成時点で確認）

poc `scc23_v2_03_poc.c` に、`emit_push_a()`（L2146）／`emit_pop_b()`（L2150）の
呼び出し境界と、その間に emit される命令数を記録するプローブを仕込み、実測した。

**結果**: 単一の push_a/pop_b ペアで、区間内命令数が **0（真の空往復）となるものは 0 件**。
区間内命令数の分布は以下（最小は1、0は皆無）:

| 区間内命令数 | ペア数 |
|---|---|
| 1 | 73 |
| 2 | 28 |
| 3 | 6 |
| …（4以上省略） | … |
| **0** | **0（皆無）** |

### 2.2 結論 ― 境界偶然マッチ

asm 上の4命令連続パターン24件は、**単一の push_a/pop_b ペアが空になったものではない**。
実体は「**境界偶然マッチ（boundary coincidence match）**」である:

- あるSIRノードの pop_b の後半（`ADDI SP, #2`）と、
  別のSIRノードの push_a の前半（`SUBI SP, #2`）等が、命令ストリーム上で隣接し、
  結果として4命令窓 `SUBI / STW A / LDW B / ADDI` に**偶然**一致したもの。
- 24件すべてで、当該4命令窓の**直前行が `MOV A, B`** であった（共通の前文脈）。

### 2.3 因果仮説の実測否定

この実測により、以下がいずれも**実データで否定**された:

- ~~当初説明「配列添字ネストによる空往復」~~ … 実測により否定（真の空往復ペアが0件のため）。
- ~~レビュア因果仮説「右オペランドemitの0命令化による空往復」~~ … 実測により否定（同上）。

※ KY41に従い、否定された旧説明は取り消し線で保持する。
  教訓: レビュアの因果仮説すら実測で否定されうる。仮説は実証するまで確定しない。

### 2.4 v0.9 時点での安全性の論点（未確定だった事項）

境界偶然マッチと判明したことで、v1.1設計の安全性正当化「**空区間ゆえA不変**」の
論拠（単一ペアが空だからAが保存される、という理屈）は**崩れた**。

ただし、当該4命令を**純粋な命令列**として見れば:
```
SUBI SP, #2    ; SP -= 2
STW  A, [SP]   ; [SP] = A   （デッドストア: 直後にSP復帰するため書いた値は死ぬ）
LDW  B, [SP]   ; B = [SP] = A
ADDI SP, #2    ; SP += 2    （SP収支ゼロ）
```
正味効果は「**B = A ＋ デッドストア＋SP収支ゼロ**」であり、
生成起源が単一ペアか境界偶然マッチかに**関わらず**、`MOV B, A` とのローカル等価が
命令列レベルで成立**しうる**。ただし v0.9 時点ではこれは机上論であり、
**emu23 実行等価による最終実証が必要**とされた（本 v1.0 §3で実施）。

## 3. emu23 実行等価検証（本 v1.0 で追記・2026-07-02実施）

### 3.1 目的

24件を `MOV B, A` に置換した Dhrystone が、置換前と**外部観測等価**
（UART出力・P値＝計算結果・正常終了）であることを実機（emu23）実行で確認する。
一致すれば、生成起源によらず P1（空区間往復置換）の安全性が実証される。

### 3.2 手順の健全性確認（KY: 偽の合格を排除）

本検証では「置換が実際にバイナリへ反映されているか」を実行比較の**前に**機械確認した。
これを怠ると「同一binを2回実行して一致」という偽の合格を出す危険があるため（KY事項）。

| 確認項目 | 手段 | 結果 |
|---|---|---|
| base asm 再現性 | scc23 v2.02 で再生成し既存 dhry_base.asm と cmp | **バイト一致**（6116行） |
| p1 asm 再現性 | p1_apply.py 再適用し既存 dhry_p1.asm と cmp | **バイト一致**（6044行、-72行=24×3） |
| 置換件数 | p1_apply.py 出力 | **24件**、SP純移動 置換前後とも -110 で不変 |
| **obj 反映確認** | dhry_base.asm.obj と dhry_p1.asm.obj を cmp | **DIFFER**（char 850 相違、6873バイト差）→ 置換はobjに反映済み |
| bin 反映確認 | dhry_base.bin と dhry_p1.bin を cmp | **DIFFER**（char 2022 相違） |
| MOV B,A 数の整合 | grep | base 3個 → p1 27個（=元3＋置換24）。整合 |

### 3.3 「obj/bin サイズが base・p1 で同一」の謎の解明

検証中、両 obj が「20822 bytes code」・両 bin が 21846 バイトで**サイズ同一**という
不審点があった（HANDOVER §5-1）。3仮説を検証した結論:

- **(c) 置換未反映 → 否定**。obj/bin とも cmp で相違が確認された。
- **(a) パディング説 → 正解**。hasm23 の "bytes code" は `code_buf_pos`
  （hasm23_v1_04.c L1311）であり、`.org` で固定配置された領域レイアウトの
  **最大到達オフセット（確保長）**を表す。コード本体が縮んでも、後続の固定
  `.org`（data/runtime）が末尾位置を決めるため、縮んだ分は未使用（ゼロ）となり
  total は不変。実コード量は非ゼロバイト数で **base 10149 → p1 9957（−192バイト）** と
  確実に減少しており、置換は効いている。
- **(b) フィールド意味 → 部分的に正**。"bytes code" は「命令バイト総和」ではなく
  「code_buf 確保長」である。

### 3.4 実行結果（emu23 v1.09、timeout 60s 付き＝KY29）

実行コマンド（**引数順序に注意**、§5参照）:
```
timeout 60 ./emu23 dhry_base.bin -q
timeout 60 ./emu23 dhry_p1.bin  -q
```

| メトリクス | base | p1（置換後） | 判定 |
|---|---|---|---|
| N（実行ループ回数） | 10 | 10 | **一致** |
| **P値（Dhrystone計算結果）** | **20** | **20** | **一致（機能等価の核心）** |
| Number_Of_Runs | 10 | 10 | 一致 |
| 正常終了 | HALT / exit=0 | HALT / exit=0 | **一致** |
| cycles | 47885 | 47795 | **−90（置換が効いた証拠）** |
| Dhrystones/sec | 835 | 836 | 派生値（cycle減の帰結） |
| total_cycles（タイマ） | 83042 | 82892 | 派生値 |

### 3.5 判定

- 差分は **cycles とその派生値のみ**。
- **外部観測の機能的等価性（P:20＝計算結果、出力構造、正常終了）は完全に成立**。
- cycles が **90 減少**したことは、置換が実際に実行され最適化効果が出ている
  積極的証拠である（HANDOVER §5-2 の傍証条件を満たす）。
  静的削減72命令に対し動的削減90cyclesとなるのは、置換窓の一部がループ内にあり
  実行回数が静的出現数を上回るためで、矛盾しない（YSD8800はCPI=1固定）。

### 3.6 結論

**P1（空区間往復置換）は emu23 実行等価により安全性が実証された。**
生成起源が「境界偶然マッチ」であっても、当該4命令のローカル正味効果は
`B = A ＋ デッドストア＋SP収支ゼロ` であり、`MOV B, A` と外部観測等価である。
これにより設計書 v1.1 の安全性正当化を、v1.2 で以下へ差し替える根拠が得られた:

> 旧: 「空区間ゆえ A 不変」（単一ペア前提・論拠崩壊）
> 新: 「4命令ローカル正味効果 = B=A + デッドストア（SP収支ゼロ）、
>      かつ emu23 実行等価（P:20一致・cycles−90）で実証」

## 4. 発見事項（申し送り）

emu23 v1.09 の正しい引数順序は `emu23 prog.bin [prog.dbg [prog.sym]] [options]`
（**bin が先、オプションが後**）である。usage 表記および実挙動で確認済み。
HANDOVER §3 記載の `./emu23 -q dhry_base.bin`（オプション先頭）は誤りで、
この順序では `-q: No such file or directory` エラーとなる。

→ ビルド手順書 `yuios_build_procedure_v1_8.docx` に Dhrystone 単体 CLI 手順が
  含まれる場合、この引数順序を反映した改版を促すべき（規約: ツール使い方変更時は
  手順書改版を促す）。ただし Dhrystone 単体手順は過去実績 CLI で手順書外の可能性もあり、
  その場合は本メモおよび次 HANDOVER への明記で足りる。

## 5. この追補調査から得た kaizen 候補

- asm 出力の逆引きだけで「生成元」を語ると誤る。emit 経路プローブで生成時点を実測せよ（KY34深化）。
- プローブ自身が観測対象を汚染しうる（観測者効果）。件数一致による裏取りが有効。
- レビュアの因果仮説すら実測で否定されうる。仮説は実証するまで確定しない。
- ツールの出力フィールド（"bytes code" 等）の**意味**を確認せずサイズ同一を
  「置換未反映」と即断しない。ソース（算出変数）で意味を確定してから判断する。
- 実行等価検証では「出力一致」の前に「置換のバイナリ反映（cmp）」を機械確認し、
  偽の合格を排除する。
