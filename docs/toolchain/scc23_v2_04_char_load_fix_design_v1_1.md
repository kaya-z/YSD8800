## 0. ゴールと前提

### 0.1 ゴール

scc23 が生成する **ローカル変数／関数パラメータの char 型スカラ**の**読出コード**を、
store 側（1バイト: STB）と非対称な LDW（2バイト）から、**LDB（1バイト）に是正**する。
完成形を **scc23 v2.04** として確定する。

### 0.2 着手前の絶対条件（原則43）

本書は**設計フェーズの成果物**である。実装着手前に必ず: レビュー → 指摘反映・承認 →
工程確認 → KY → 「ご安全に！」→ 実装。実装は KY38 に従い、本番 `scc23_v2_03.c` は
直接改変せず、**新ファイル `scc23_v2_04.c`** として起こす。**承認前の実装着手は厳禁。**

### 0.3 現在地（KY34・実ファイル確認済み）

- scc23 v2.03 確定（`SCC_VERSION "2.03"`）。P2a/P2b/P3/P1 実装済み。
- 本バグの影響：**Dhrystone は emu23 と TB $00 初期化で偶然通過している**が、
  実 FPGA の PSRAM 電源投入時内容は不定のため実機では非決定的動作。
- CPUコア RTL は無罪確定（CHAT119 内部信号観測により）。修正対象は scc23 のみ。

## 1. バグの確定内容

### 1.1 症状

Dhrystone `Func_1` の以下のCソース（`dhry_all_ansi2.c` L1006-1020）:

```c
Enumeration Func_1 (Capital_Letter Ch_1_Par_Val, Capital_Letter Ch_2_Par_Val)
{
  Capital_Letter        Ch_1_Loc;
  Capital_Letter        Ch_2_Loc;

  Ch_1_Loc = Ch_1_Par_Val;      /* char 代入: 1バイト書込 (STB) */
  Ch_2_Loc = Ch_1_Loc;          /* char 読出→代入: ★2バイト読出(LDW)★ */
  if (Ch_2_Loc != Ch_2_Par_Val)
    return (Ident_1);
  ...
}
```

scc23 v2.03 が生成するアセンブラ（該当箇所・実測）:

```
    ; Ch_2_Loc = Ch_1_Loc  (Ch_1_Loc はスタック上の char)
    LDW  A, [X + #$FFFC]     ← ★バグ★ 2バイト読み込み
    ...
    ; store 側は正しく STB
    STB  A, [X]              ← 1バイト書き込み（正しい）
```

Ch_1_Loc（`Capital_Letter` = char = 1バイト）はスタック上に1バイトしか
書かれていないにも関わらず、**2バイトを読み込む**。上位バイトは
「同じスタック領域の隣接バイト（別変数、または未書込領域）」となり、
不定値が A レジスタの上位に混入する。

### 1.2 発現条件と影響範囲

| 条件 | 発現 |
|---|---|
| char 型のローカル変数（`auto` 相当）を読む | **発現** |
| char 型の関数パラメータを読む | **発現** |
| char 型のグローバル変数を読む | 発現しない（L2513 の SC_GLOBAL 分岐で LDB を使用） |
| char へのストア | 発現しない（`emit_store_b_at_a` で STB を使用） |
| char ポインタ経由のロード（`*p`） | 発現しない（別経路） |
| int（16bit）ローカル変数を読む | 発現しない（LDW 2バイトが正しい） |

**実害の顕在化条件:**

読み出す char 変数の**隣接スタック位置が未書込**、かつ**その領域の
物理RAM初期値が不定**である場合に、値が非決定的になる。

- **emu23 上では顕在化しない**: `uint8_t mem[MEM_SIZE]` はグローバル配列で
  C 規約によりゼロ初期化されるため、未書込領域は常に 0x00。char 値の
  下位バイトが正しければ、上位が 0x00 で「結果的に char 値と一致」する。
- **実 FPGA では顕在化する**: PSRAM 電源投入時の内容は不定。
- **昨日の TB（1KB初期化）では顕在化した**: 残り全域が X のまま X 汚染。

## 2. ISA2.3 上の制約（KY34: 実源確認）

修正案を絞る前提となる ISA/実装の一次確認結果:

### 2.1 LDB 命令の仕様

**`hasm23_v1_04.c` L105-108** 実源:

```c
{"LDB",  "A", EXT_ABS,   0x10},   // LDB A,[imm16]
{"LDB",  "A", EXT_INDRX, 0x11},   // LDB A,[X]
{"LDB",  "B", EXT_ABS,   0x12},   // LDB B,[imm16]
{"LDB",  "B", EXT_INDRX, 0x13},   // LDB B,[X]
```

→ **LDB は `[imm16]` と `[X]` の2形式のみ**。`[X+offset]` 形式は存在しない。
これが本設計書の修正案を制約する最大要因。

### 2.2 LDB の値拡張規則

**`emu23_v111.c` L1308** 実源:
```c
case 0x11: // LDB A,[X]
    cpu.a = rd8(cpu.x);
    break;
```

`rd8()` 戻り値 `uint8_t` を `cpu.a`（`uint16_t`）に代入 → C規約で**ゼロ拡張**。
`set_zn()` の呼出しなし → **フラグ非更新**。

### 2.3 LDW の値拡張規則

**`emu23_v111.c` L1395-1403** 実源:
```c
case 0x26: { /* LDW rD, [X + imm16] */
    ...
    *rd = rd16(addr);
    set_zn(*rd);
}
```

**フラグ更新あり**。

### 2.4 ADDI/SUBI の X レジスタ対応

**`hasm23_v1_04.c` L145-147** 実源:
```c
{"ADDI",    0x41, 1, 1, 0},
{"SUBI",    0x43, 1, 1, 0},
```

レジスタ指定可、`X`=2（L271 で確認）。scc23 v2.03 も既に `SUBI SP, #2` を
多用しており、非 A/B 宛のレジスタ操作は運用実績あり。

### 2.5 割込ハンドラの X 使用実態（本修正の副作用検討用）

**`startup_harness23_v16.asm` L98-112** 実源（`_timer_handler`）:

```asm
_timer_handler:
    STW  A, [_isr_wk_a]     ; A/B/X を退避（値保存のみ）
    STW  B, [_isr_wk_b]
    STW  X, [_isr_wk_x]
    ...
    LDW  A, [_isr_wk_a]     ; A/B/X を復元
    LDW  B, [_isr_wk_b]
    LDW  X, [_isr_wk_x]
    IRET
```

**割込ハンドラは X を単に値保存/復元するのみ**。「X をフレームポインタとして
参照する経路」は割込側に存在しない。よって修正案で X を一時的にずらしている
最中に割込が入っても、割込復帰後に元の X に戻すため機能に問題は生じない
（本判定は §4.4 で詳述）。

## 3. 修正案の比較

### 3.1 候補案

| 案 | 概要 | 命令数 | 判定 |
|---|---|---|---|
| 案1 | `MOV A,X` → `ADDI A,off` → `emit_load_at_a(1)` | 約8命令 | 却下（冗長） |
| 案2 | store 側を STW に変更（対称化） | 1命令 | **却下（不可）** |
| **案3** | **`ADDI X,#off` → `LDB A,[X]` → `SUBI X,#off`** | **3命令** | **★採用★** |
| 案4 | `LDW A,[X+off]` → `AND A,#$00FF`（ゼロ拡張） | 2命令 | 保留（§3.4 参照） |

### 3.2 案2 却下の根拠

store 側を STW（2バイト書込）に変更すると、以下のシナリオで**隣接バイトを破壊する**:

- 構造体メンバの `char` フィールド（次フィールドを踏む）
- char 配列の要素（次要素を踏む）
- 隣接するローカル変数（他変数を踏む）

Cの意味論として不許容。**採用不可**。

### 3.3 案3 の詳細（採用案）

**修正後コード（案）:**

```c

2511:             int is_char=(s->type==T_CHAR);
2512:             if (s->sclass==SC_GLOBAL) {
2513:                 unsigned addr=(unsigned)(DATA_ORG+s->offset);
2514:                 if (is_char) emit("    LDB  A, [$%04X]", addr&0xFFFF);
2515:                 else         emit("    LDW  A, [$%04X]", addr&0xFFFF);
2516:             } else {
2517:                 int off=real_offset(s);
2518:                 if (is_char) {
2519:                     /* v2.04 修正: char は STB(1B) で書くので LDB(1B) で対称化。
2520:                        LDB は [X] 形式しかないため、X を一時的にずらして読み、
```

- `off==0` の場合は1命令で完了（性能最適）
- `off!=0` の場合は3命令（既存 LDW 1命令に対し +2命令）
- X の値は本ブロック内で一時変更されるが、必ず元に戻す
- A レジスタはゼロ拡張された char 値を保持（既存の SC_GLOBAL 経路と一貫）

### 3.4 案4 との比較（AND による上位ゼロ化）

`ANDI A, #$00FF` で上位バイトをゼロ化する案:

```c
if (off==0)     emit("    LDW  A, [X]");
else if (off>0) emit("    LDW  A, [X + #%d]", off);
else            emit("    LDW  A, [X + #$%04X]", (unsigned short)off);
if (is_char)    emit("    ANDI A, #$00FF");
```

**利点:** X を触らない、割込に対する不安が原理的にゼロ、命令数常に2命令。

**欠点:**
- `LDW A,[X-4]` のような読出しで、`X-4` と `X-3` の**2バイトを実際にメモリ読出**する。
  そのうち `X-3` が別変数の場合、**論理的には無関係な読出しが発生**する。
- 実 FPGA では「未マップ領域を読んだ場合に何が起きるか」が RTL/PSRAM 仕様依存。
  例: X-4 がスタック最上部で X-3 が MMIO 領域だった場合の副作用は未定義。
- CHAT119 で見つかった**根本問題**（1バイト書込→2バイト読出の非対称性）は解決しない。

**判定:** 案4 は**対症療法**であり、案3 が根本治療。**案3 を採用**。
ただし案4 は将来的なピープホール最適化として保留する余地はある（下記 §7）。

## 4. 安全性・副作用の解析

### 4.1 レジスタ・フラグへの副作用

案3 実行前後の状態:

| 項目 | 実行前 | ADDI X,#off 後 | LDB A,[X] 後 | SUBI X,#off 後 |
|---|---|---|---|---|
| A | ? | 変化なし | **char 値(ゼロ拡張)** | 変化なし |
| B | ? | 変化なし | 変化なし | 変化なし |
| X | FP | FP+off | FP+off | **FP に復元** |
| Z/N | ? | ADDI 結果 | **LDB は非更新** | **SUBI 結果** |

**副作用は A レジスタとフラグ Z/N のみ**（既存 LDW 経路も A と Z/N を変える点は同じ）。
差分は「フラグ Z/N が LDB 実行時ではなく末尾 SUBI 実行時に更新される」点のみ。

### 4.2 呼出元コードのフラグ依存

scc23 v2.03 は条件分岐の直前で**必ず `CMPI A, #0` を明示出力**する
（実源確認: `scc23_v2_03.c` L2701-2721, L2739-2741）。よって
`SIR_SYM` 直後のフラグ状態には依存しない。

**ただしピープホール最適化（P1/P3）は Z/N 読出を見て置換抑止**する
（`scc23_v2_03.c` L822 の G5 規則）。本修正で末尾命令が SUBI に
変わるため、**ピープホール置換の対象・非対象が変化する可能性がある**。
→ §5 回帰テストで Dhrystone サイクル数と生成コードの変化を確認。

### 4.3 メモリアクセスの安全性

案3 では **X が一時的に off だけずれる**。もし `off` が過大で
`X+off` が別セグメント（MMIO 領域 $FCxx など）を指すと、
LDB 実行時に MMIO を読む副作用が発生し得る。

**評価:**
- `off` は関数の**ローカルフレーム内**を指すため、範囲は数十バイト〜数百バイト程度
- スタック領域とMMIO領域は分離されている（memmap v2.4）
- 従って現行の関数フレーム設計下で本問題は原理的に発生しない

念のため、修正実装時に「off の絶対値が異常に大きい場合の警告出力」を
追加する案もあるが、複雑化を避け**採用見送り**（余計な条件分岐が
コンパイラ本体のバグ源になる方が高リスク）。

### 4.4 割込との相互作用（本修正案の最重要検討事項）

**懸念:** `ADDI X,#off` から `SUBI X,#off` までの2〜3命令区間で割込が入った場合、
割込ハンドラ側から X が「フレームポインタとして無効な値」に見えないか。

**判定:** §2.5 の一次確認により、**割込ハンドラは X を単に値保存/復元する
のみで、フレームポインタとして参照する経路はない**。したがって:

- 割込受理時: 破壊済み X が `_isr_wk_x` に保存される（値保存だけなので問題なし）
- 割込ハンドラ実行中: X は割込ハンドラ内の任意用途に使われる（自由）
- IRET 直前: `_isr_wk_x` から破壊済み X を復元
- IRET 後: 中断された `LDB` または `SUBI X` から実行再開
  - `LDB A,[X]` 中断の場合: 再開時 X = 中断時の値（= off だけずれた FP）
  - `SUBI X,#off` 中断の場合: 再開時 X = 中断時の値（= off だけずれた FP）
- SUBI X,#off 完了後: X が元の FP に戻る

**結論: 機能上の問題なし**。ただし本挙動は「割込ハンドラが X を値保存以外に
使わない」という前提に依存する。この前提を将来変更する場合は本設計を
見直す必要がある（下記 §6 の申し送り）。

### 4.5 その他の副作用

- **命令サイズ:** 既存 `LDW A,[X+imm16]` = 4バイト（EXT+sub+imm16）に対し、
  修正後 `ADDI X,#imm + LDB A,[X] + SUBI X,#imm` = **10バイト**（実源根拠：
  `hasm23_v1_04.c` L465-483 `parse_ldw_stw_size` 関数と ADDI/SUBI サイズ
  規則より、ADDI/SUBI = 4B、LDB [X] = 2B、合計 4+2+4 = 10バイト。v1.0 の
  「次項で要検算」の但し書きは v1.1 で実源から確定できたため削除）。
  差分 = **+6バイト/読出箇所**。
- **char 読出頻度**：Dhrystone フル版で char 型ローカル/パラメータ読出は
  複数箇所発生し、実測サイクル増加は +380 cyc（+0.79%）に留まる
  （CHAT120 実測 48405→48785）。
- **書式指示子の一貫性（v1.1 追記・指摘2）**：§3.3 の修正コード内で `off>0`
  分岐は `emit("ADDI X, #%d", off)` / `emit("SUBI X, #%d", off)` として
  正の10進で出力、`off<0` 分岐は `emit("SUBI X, #%d", -off)` / `emit("ADDI X, #%d", -off)`
  として `-off` で正の値化してから10進で出力する。書式指示子は全て `%d`（10進）で
  一貫。既存の LDW 経路が `off<0` で `%04X`（16進符号なしキャスト）を使うのは
  LDW `[X + #imm16]` 形式が16bit即値を直接埋め込むアドレッシングモードのため
  別ルート（オペコード自体が符号無視の16bit加算）で、修正版とは経路が異なる。
- **実行サイクル数:** 3命令に増えるため、char 読出が多い関数で若干の遅化。
  Dhrystone サイクル数への影響は §5.2 で実測する。

## 7. 将来課題（申し送り・KY41）

### 7.1 案4（ANDI ゼロ拡張）のピープホール化

案4 は根本治療ではないが、「`LDW A,[X+off]` → 直後に `ANDI A,#$00FF`」の
2命令列が生成された場合に、これを「`SUBI X,#off` → `LDB A,[X]` → `ADDI X,#off`」に
置換するピープホールを追加する余地がある（char 型ポインタ経由の読出しなど、
本設計書の対象外経路への一般化）。

### 7.2 char 型のフラグ更新差異

LDB は Z/N を更新しないが LDW は更新する。既存 scc23 は条件分岐前に
必ず CMPI を出すため実害はないが、将来「char 値を直接 BEQ で判定する」
最適化を入れる場合は本差異を考慮する必要がある。

### 7.3 割込ハンドラでの X 使用規約の固定化

本修正の安全性は「割込ハンドラが X を値保存以外に使わない」という
現行前提に依存する。この前提を **YUI OS 側のコーディング規約として明文化**
すべきかを検討（`yuios_design_v2_7.md` への追記候補）。

**v1.1 追記（指摘4反映・具体的な規約ルール文言案）**：

`yuios_design_v2_7.md` への追記候補として、以下のルール文言を提案する：

```
[規約: 割込ハンドラの X レジスタ使用制限]

割込ハンドラ内では、X レジスタを「STW で退避 → LDW で復元」以外の
用途に使用してはならない。理由: scc23 v2.04 以降、char 型ローカル変数の
読出に「ADDI X,#off → LDB A,[X] → SUBI X,#off」の3命令列を生成する。
中間の LDB/SUBI 実行中に割込が入り、割込ハンドラが X をフレームポインタ
相当に書き換えると、復帰時にユーザランド側の X が不正となる。

本規約に反する必要が生じた場合は scc23 修正案の再検討必須。

参照: scc23_v2_04_char_load_fix_design_v1_1.md §4.4（割込との相互作用）
```

**規約の位置付け**：

- 現行の `startup_harness23_v17.asm`（v1.7・工程2 実装）の全ハンドラ
  （`_timer_handler`／`_irq1_handler`／`_align_handler`／`_syscall_handler`）は
  X を値保存・復元以外に使用しておらず、本規約に既に準拠している
- 将来 YUI OS の割込ハンドラ実装（`_kernel_dispatch` 差替時等）でも本規約を
  維持することで、scc23 v2.04 との相互作用問題を回避する
- 本規約は「割込ハンドラのレジスタ退避規則」（工程2 設計書 §7.2）と併せ
  YUI OS 側でルール化することを推奨
