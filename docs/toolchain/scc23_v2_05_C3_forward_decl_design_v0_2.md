## 0. ゴールと前提

### 0.1 ゴール

前方未定義（プロトタイプ宣言も関数定義も先に出ていない）状態で **float 返し関数**
を呼び出すと、戻り値型が T_INT にフォールバックされ、その後の float 演算で
`wrap_i2f` が `SIR_I2F` ノードを挿入して結果を破壊する既知バグ（設計書§9・C-3）
を **実際に修正**する。

**v0.1 での誤結論（撤回）**：v0.1 は「型伝播ロジックは既に正しい」「真の課題はユーザに
気づかせる手段」と結論した。しかし実ソース `binop_promote` は、未定義関数由来の
T_INT SIR_CALL が float 文脈に混入すると **`wrap_i2f` により I2F ノードを挿入して
値を破壊する**。よって型伝播ロジックは正しくなく、警告だけでは修正にならない。

完成形を **scc23 v2.05** として確定する。

### 0.2 着手前の絶対条件（原則43）

本書は**設計フェーズの成果物**である。実装着手前に必ず: **レビュー → 指摘反映・承認
→ 工程確認 → KY → 「ご安全に！」→ 実装**。実装は KY38 に従い、本番
`scc23_v2_04.c` は直接改変せず、**新ファイル `scc23_v2_05.c`** として起こす。
**承認前の実装着手は厳禁。**

### 0.3 現在地（KY34・実ファイル確認済）

## 1. バグの確定内容（PoC 実証済・v0.2 で機序を修正）

### 1.1 症状

**PoC ケース**（本設計メモ v0.1 起票時に実測・v0.2 でも同じ実測結果を採用）：

```c
/* case2_no_proto.c: プロトタイプ宣言なし・前方未定義 */
int main() {
    float x;
    x = getval() + 1.0;
    return 0;
}
float getval(void) { return 2.5; }
```

**scc23 v2.04 が生成するアセンブラ（該当箇所・実測）**：

```
    JSR  _getval          ; float 返し (A = Q8.8 で 2.5 = 0x0280)
    LDW  B, #8            ; ★ I2F ノードの emit（<<8 シフト） ★
    SHL  A, B             ; ★ A を 8bit 左シフト → 値破壊（0x0280 → 0x8000） ★
    ; 以下、既に Q8.8 の値を「int→Q8.8」として二重昇格した結果で加算
```

対して **プロトタイプ宣言ありのケース**（`float getval(void);` を前置）では、
上記 `LDW B,#8 / SHL A,B` の2命令が挿入されず、正しく Q8.8 加算コードが生成される
（v0.1 起票時に diff で確認済）。

### 1.2 発現条件と影響範囲

| 条件 | 発現 |
|---|---|
| プロトタイプ宣言あり＋前方 float 関数呼び出し | 発現しない |
| **プロトタイプ宣言なし＋前方 float 関数呼び出し** | **発現** |
| プロトタイプ宣言なし＋前方 int 関数呼び出し | 発現しない（T_INT で正解） |
| 定義済み関数を後方から呼び出し（順序が正しい） | 発現しない |

**実害の顕在化条件**：
- Dhrystone（`dhry_all_ansi2.c`）は **float を使用しない**ため実害なし
  → 絶対ゲートには影響しない
- 現行の YUI OS カーネル／ユーザランドは **float を使用しない**ため実害なし
- Q8.8 float を使う将来のユーザランドコードで、プロトタイプなしで前方 float 関数を
  呼ぶと**確実に発現**する

### 1.3 バグの位置（1次ソース照合・v0.2 で機序を明確化）

**バグの真の機序は「型伝播 → 値破壊」の2段構造である**（v0.1 は1段目のみ見て
「型伝播は既に正しい」と誤結論した）。

#### 1.3.1 1段目：T_INT 誤伝播（`scc23_v2_04.c` L1868-1898）

```c
1868:         /* 関数呼び出し */
1869:         const char *peek=next_tok();
1870:         if (strcmp(peek,"(")==0) {
1871:             sir_node_t *cn=sir_new(SIR_CALL);
1872:             strncpy(cn->fname,name,IDENT_LEN-1);
1873:             /* [FIX 2026-06-25] 関数戻り値型を関数シンボルから引く。 */
1876:             {
1877:                 sym_t *cfs=sym_find(name);
1878:                 if (cfs && cfs->sclass==SC_FUNC) {
1879:                     cn->type = cfs->type;
1880:                     cn->base = cfs->base;
1881:                 } else {
1882:                     cn->type = T_INT; cn->base = T_INT;   ← ★1段目：誤伝播発生点★
1883:                 }
1884:             }
```

プロトタイプ宣言も本体定義もない未定義関数は SC_FUNC 登録がなく T_INT にフォールバック。
**これ自体は「未知の型を int として扱う」という単なる仮定**であり、int 演算で使う限り
問題ない。

#### 1.3.2 2段目：I2F 二重昇格で値破壊（`scc23_v2_04.c` L1186-1218）

```c
1186: static sir_node_t *binop_promote(sir_op_t int_op, sir_node_t *l, sir_node_t *r) {
1187:     int lf = l && l->type==T_FLOAT;   ← 未定義 getval() は T_INT → lf=0
1188:     int rf = r && r->type==T_FLOAT;   ← 定数 1.0 は T_FLOAT → rf=1
1189:     if (!lf && !rf) { ... }           ← rf=1 なので通らない
1190:     /* どちらかfloat -> 両辺floatへ昇格 */
1198:     l = wrap_i2f(l);   ← ★2段目：T_INT扱いの getval() に I2F 挿入・値破壊★
1199:     r = wrap_i2f(r);
```

`wrap_i2f`（L1054-1066）は `n->type != T_FLOAT` なら **`SIR_I2F` ノードを挿入**する：

```c
1054: static sir_node_t *wrap_i2f(sir_node_t *n) {
1055:     if (!n) return n;
1056:     if (n->type==T_FLOAT) return n;
1057:     if (n->op==SIR_CONST && n->type!=T_FLOAT) { ... }
1063:     sir_node_t *c=sir_new(SIR_I2F); c->left=n;
1064:     c->type=T_FLOAT; c->base=T_FLOAT;
1065:     return c;
1066: }
```

この `SIR_I2F` ノードが後段で `LDW B,#8 / SHL A,B` にコード生成され、**既に Q8.8
表現になっている getval() の戻り値をさらに 8bit 左シフト**して破壊する。

#### 1.3.3 結論：型伝播ロジックは正しくない

v0.1 の誤結論「コンパイラ側の型伝播ロジックは既に正しい」を**撤回**する。
- 型伝播は「未定義関数 → T_INT」という仮定を無条件に採用しており、その仮定が
  float 文脈で崩れると `binop_promote` + `wrap_i2f` が値を破壊する
- ゆえに真の課題は「T_INT 誤伝播が float 文脈に混入することを検出し、
  値破壊を実際に阻止すること」であり、警告出力だけでは不足

## 2. 修正案の比較（v0.2 で全面再構成）

### 2.1 候補案（v0.2 で案D 追加・主候補差替え）

| 案 | 概要 | 本体改変 | 値破壊阻止 | 判定 |
|---|---|---|---|---|
| 案A | プロトタイプ運用ルール化のみ（コンパイラ非改変・ドキュメント整備） | なし | ✗ | 却下 |
| 案B | 2パス化（1パス目で関数シンボル全収集、2パス目で式生成） | 大 | ○ | 却下（リスク過大） |
| 案C | 未定義関数呼び出しに warning 出力（型伝播ロジックは不変） | 軽微 | ✗ | 単独では不採用（値破壊放置）／案D の補助として併用 |
| **案D** | **未定義 SIR_CALL が float 文脈に入る場合 error 停止（1パス局所修正）** | **軽微** | **○** | **★採用（主候補）★** |

### 2.2 案B 却下の根拠（v0.1 と同一・保持）

- 2パス化はパーサ本体構造の大規模改造となり、Dhrystone 絶対ゲート（826/48405/P:20/21846B・-O0-strict）
  破壊リスクが高い
- 現行の Small-C 系 1パス構造から離れ、将来の scc22 系プリプロセッサ移植（Phase 3）
  との整合性も悪化する
- **1パスのまま案D で値破壊を確実に阻止できる**（レビュー指摘 M-1 反映）ため、
  2パス化の労力に見合わない

### 2.3 案A・案C 単独の限界（v0.2 で追記）

- **案A（ドキュメントのみ）**：書き忘れを検出できず、値破壊も阻止しない
- **案C 単独（警告のみ）**：警告は出るが**値破壊自体は依然として発生**。
  「実害が出る前に対処すべき」（設計書§9）という要求を満たさない。
  レビュー指摘 C-1 が明示するとおり、**案C 単独では C-3 のゴール未達**

### 2.4 案D の詳細（採用・主候補）

**方針**：値破壊の唯一の発生点である `binop_promote` の float 経路
（L1197-1199）に対し、「未定義関数由来の SIR_CALL が入る場合は error 停止」の
判定を追加する。fail-safe 原則により、壊れたコード生成を阻止する。

**判定条件**：ノード `n` について以下2つを満たすとき「未定義関数由来」と判定：
1. `n->op == SIR_CALL`
2. `sym_find(n->fname)` が SC_FUNC を返さない（NULL、または sclass 不一致）

**修正コード案**（`binop_promote` に判定ヘルパを追加）：

```c
/* [v2.05 C-3] 未定義関数呼び出し由来の SIR_CALL か判定。
 * float 文脈で使うと wrap_i2f が I2F を誤挿入し値破壊するため、
 * float 経路侵入前に error 化する fail-safe 判定に使う。 */
static int is_undecl_call(sir_node_t *n) {
    if (!n || n->op != SIR_CALL) return 0;
    sym_t *s = sym_find(n->fname);
    if (s && s->sclass == SC_FUNC) return 0;
    return 1;
}

static sir_node_t *binop_promote(sir_op_t int_op, sir_node_t *l, sir_node_t *r) {
    int lf = l && l->type==T_FLOAT;
    int rf = r && r->type==T_FLOAT;
    if (!lf && !rf) {
        sir_node_t *f = try_fold(int_op, l, r, T_INT);
        if (f) return f;
        sir_node_t *a = fold_algebraic(int_op, l, r);
        if (a) return a;
        return sir_binop(int_op, l, r);
    }
    /* [v2.05 C-3] float 経路に入る前に未定義関数呼び出しを検出。
     * T_INT 誤伝播 → wrap_i2f 誤挿入 → 値破壊 を防ぐため error 停止。
     * ユーザには「プロトタイプ宣言を追加せよ」と促す。 */
    if (is_undecl_call(l)) {
        error("undeclared function '%s' used in float context: "
              "add prototype declaration to avoid silent value corruption",
              l->fname);
    }
    if (is_undecl_call(r)) {
        error("undeclared function '%s' used in float context: "
              "add prototype declaration to avoid silent value corruption",
              r->fname);
    }
    /* どちらかfloat -> 両辺floatへ昇格 */
    l = wrap_i2f(l);
    r = wrap_i2f(r);
    /* ...（以降 v2.04 と同一）... */
}
```

```c

1877:                 sym_t *cfs=sym_find(name);

1879:                     cn->type = cfs->type;

1881:                 } else {
1882:                     /* [v2.05 C-3] 未定義関数呼び出し警告（早期通知）。
1883:                        T_INT フォールバックは維持（int 文脈では従来動作を保つ）。
1884:                        float 文脈で使われた場合は binop_promote で error 停止する。 */
1885:                     warning("call to undeclared function '%s': assumed to return int. "
1886:                             "add prototype declaration if returning float/pointer/char.",
```

## 3. 安全性・副作用の解析（v0.2 で案D に対応）

### 3.1 生成コードへの影響

- **プロトタイプ宣言あり**：既存動作と完全に同一（警告も error も出ない）
- **プロトタイプ宣言なし＋int 文脈**：既存動作と完全に同一 + 警告 1行（案C）
- **プロトタイプ宣言なし＋float 文脈**：**error 停止**（案D）
  - コード生成が抑止されるため、壊れた asm は出力されない
  - `error_count > 0` により後段（`main` の判定）で非0終了する

**Dhrystone への影響**：
- `dhry_all_ansi2.c` は **float を使用しない**ため float 経路には入らない
- ゆえに **error は発生しない**
- 警告は多数出るが、生成コードは v2.04 と **byte-exact 一致** → 絶対ゲート維持

### 3.2 error 化の妥当性（fail-safe 原則）

- 現行 v2.04 では「値破壊した壊れた asm を無警告で出力」しており、リンクも走り、
  実行時に**値が壊れることが表面化しない**（サイレント破壊）
- v2.05 で error 停止させることで、**破壊されたバイナリが実機に届く前に検出**できる
- ユーザは error メッセージに従いプロトタイプ宣言を追加すれば、コード生成が
  復旧する（プロトタイプありの経路は PoC case1 で正常動作を実証済）

### 3.3 emu23 動作への影響

Dhrystone で error が発生しないため、emu23 上の実行結果は不変。V1 検証で確認する。

### 3.4 コンパイル時間への影響

`is_undecl_call` は `sym_find` 1回・sclass 比較のみ。無視できる。

### 3.5 既存の float 使用テストへの影響

- v2.00 の float テスト群（Q8.8 テスト・§7 実施）は **プロトタイプ付き**で書かれている想定
- 実装承認後の V2 検証で「既存 float テストが全て PASS」を確認する
- 万一 error になるテストがあれば、それは元々の書き忘れであり、プロトタイプ追加で修正できる

## 7. 将来課題（申し送り・KY41）

### 7.1 プロトタイプ付き Dhrystone への移行

- 現行 `dhry_all_ansi2.c` は K&R スタイル（プロトタイプなし）で、v2.05 では
  警告が大量出力される
- Phase 1 C-1 マトリクステスト整備時に、プロトタイプ付き版（`dhry_all_ansi2_proto.c`）
  の作成を検討
- ただし絶対ゲート（byte-exact）を維持するため、**現行 K&R 版と生成コードが同一**
  であることが前提

### 7.2 `defined` フラグの区別（レビュー N-1 への回答）

- 現行 L4300 では、プロトタイプ宣言と関数本体定義の両方で `fs->defined=1` が立つ
- レビュー N-1 は「`defined` フラグ問題は C-3 の根治に直結。本スコープに格上げすべき」と指摘
- **本 v0.2 では Phase 2 送りとする**。理由：
  1. PoC case1（プロトタイプあり）で **現状の型伝播は正しく動作している**ことを
     実源で実証済（L1878 の `cfs->sclass==SC_FUNC` 判定は `defined` を見ていない）
  2. `defined` フラグ厳格化は「プロトタイプ宣言なしで本体定義済の関数を後方から呼ぶ
     ケース」の区別に必要となるが、これは C-3 の実害シナリオではない
  3. `defined` フラグ厳格化は `sym_t` の意味論変更を伴い、Phase 2（型システム統合）
     で `T_UINT`/`T_BOOL` 実装と併せて行う方が整合的
  4. C-3 のゴール（値破壊阻止）は案D＋案C で達成できる
- 将来 Phase 2 で `defined` フラグを分離した際、本 C-3 修正の警告メッセージを
  「宣言のみあり／完全未定義」で区別することを検討

### 7.3 error 抑止フラグ

- 将来 `-Wno-error=implicit-float` 相当のコマンドラインオプション追加を検討
- 現時点では追加せず、値破壊阻止を最優先とする

### 7.4 案B（2パス化）の再検討余地

- 将来的にコンパイラを大規模改造する場面（例：本格レジスタ割付・Phase 5）で
  2パス化が別途必要になった場合、C-3 対応もそのタイミングで統合できる
- ただし本 Phase 1 では案D＋案C で十分

### 7.5 float 文脈以外での値破壊の可能性

- 案D は「float 文脈での I2F 誤挿入」のみを検出・阻止する
- 他の文脈（例：pointer 文脈での誤伝播）でも類似のバグがあるかは Phase 2 の
  型システム統合時に総点検を推奨
