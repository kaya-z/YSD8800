## 0. ゴールと前提

### 0.1 ゴール

`scc23_v2_00_design_v2_10.docx` §9 C-1 の指摘に対応する：
- **戻り値型（float/int）× 演算（+/-/*/÷）× 右辺種別（定数/変数/call）** のマトリクステストを整備
- 上記マトリクステストを回帰スイートに組み込み、**全 PASS** を C-1 完了条件とする
- 将来の Phase 2（型システム統合）で回帰を検出するための **セーフティネット** を先に張る

### 0.2 前提

- 本タスクは **本体改変なし**（テスト整備のみ・原則43 軽量版でよい）
- scc23 v2.05 の C-3 修正により、「プロトタイプなし＋前方未定義 float 関数」は **error 停止**となる。ゆえに従来ならすり抜けたバグ再発シナリオを**マトリクスの正例側（error 発生）**として組み込める
- テストは既存の scc23 テストと同居可能な形式（`.c` ソース＋期待値ファイル）とする

### 0.3 C-3 との連続性

C-3 完了により以下が確定：
- プロトタイプ宣言あり → 正しく型伝播（コード生成が v2.04 と byte-exact）
- プロトタイプなし＋int 文脈 → warning のみ・T_INT フォールバック動作
- プロトタイプなし＋float 文脈 → error 停止（fail-safe）

C-1 は上記3挙動を**マトリクスとして網羅**し、Phase 2 以降で意図せず変化しないことを保証する。

## 1. マトリクス設計

### 1.1 次元と組合せ

| 次元 | 値 |
|---|---|
| 戻り値型 | int, float |
| 演算 | +, -, *, / |
| 右辺種別 | 定数, 変数, call |
| プロトタイプ | あり, なし |

**組合せ**：戻り値型2 × 演算4 × 右辺種別3 × プロトタイプ2 = **48 通り**

### 1.2 期待挙動の分類（golden 基準版 = scc23 v2.05）

C-3 修正により以下の3挙動に分類できる（**golden 基準版 = scc23 v2.05**・M-2 反映）：

| プロトタイプ | 戻り値型 | 期待挙動 |
|---|---|---|
| あり | int | 正常コード生成（int 演算）・**v2.05 golden asm と byte 一致** |
| あり | float | 正常コード生成（float 演算・Q8.8）・**v2.05 golden asm と byte 一致** |
| なし | int | warning 出力＋正常コード生成（T_INT フォールバック）・**v2.05 golden asm と byte 一致** |
| なし | float | **error 停止**（案D 発火・値破壊阻止・非0終了 AND `used in float context` メッセージ） |

**golden 基準版固定の意義（M-2）**：本テストは「Phase 2 以降で回帰を検出するセーフティネット」（§0.1）が目的。C-3 実装の前後で `m1_f_*_*_n`（float×proto なし）の期待挙動が「値破壊 asm 出力」→「error_stop」へ変化した歴史がある。golden 基準版を **scc23 v2.05 に固定**することで、Phase 2 以降で挙動が変わった場合に「v2.05 golden からの差分＝回帰疑い」と一義的に判定できる。C-2 の数値ヘルパ整備前でも、版固定により回帰基準は成立する。

### 1.3 テストケース命名規約

`m1_<戻値型>_<演算>_<右辺>_<proto>.c`
- `<戻値型>`: `i`（int）／`f`（float）
- `<演算>`: `add`／`sub`／`mul`／`div`
- `<右辺>`: `k`（constant）／`v`（variable）／`c`（call）
- `<proto>`: `p`（あり）／`n`（なし）

例：`m1_f_add_c_n.c` = float 戻し × 加算 × call × プロトタイプなし → error 停止期待

### 1.4 テスト削減の可否

48 通り全実装は冗長。以下の削減を提案：
- **演算4種は加算・除算の2種に削減**（加算は最小コスト・除算は Q8.8 で最も複雑）
- **削減根拠（v0.2 N-1 反映）**：元 C-3 バグ（`float関数() + 定数`）は**加算で顕在化**しており加算を残すのは必須。除算（FDIV）は Q8.8 の**最複雑経路**（`_fdiv` ランタイム呼出・シフト補正・ゼロ除算保護）ゆえ、この2種で境界を代表化できる。乗算（FMUL オーバーフロー warning 経路）・減算は加算・除算に挙動が包含され、削減リスクは低い。§7.1 で完全網羅計画に回収する。
- **戻り値型2 × 演算2 × 右辺種別3 × プロトタイプ2 = 24 通り**が現実的なテスト規模

ただし C-2（Q8.8 ヘルパスクリプト）整備後は 48 通り全実装への拡張を検討。

## 2. 実装方針

### 2.1 ディレクトリ構造

```
/mnt/project/tests_c1/     ← 新設（プロジェクトナレッジには登録しない場合、開発時のみ）
  m1_i_add_k_p.c            ← 各テストソース（24 or 48 個）
  m1_f_div_c_n.c
  ...
  expected/                 ← 期待値
    m1_i_add_k_p.expected   ← "compile_ok" or "error_stop" or "warning_only" 等の期待判定
  goldens/                  ← v2.05 凍結 asm（golden 基準版・M-2 反映）
    m1_i_add_k_p.golden.asm
    ...
  run_c1_matrix.sh          ← マトリクス実行スクリプト（PASS/FAIL 集計）
  README.md                 ← テスト設計と実行手順（golden 版数明記）
```

### 2.2 期待値判定の分類

各テストの期待値は以下の3種類：
- `compile_ok`：warning 0件・error 0件・生成 asm あり・**v2.05 golden asm と byte 一致**
- `warning_only`：warning ≧1件・error 0件・生成 asm あり・**v2.05 golden asm と byte 一致**
- `error_stop`：**非0終了 AND error メッセージに `used in float context` を含む**（AND 条件必須・N-2 反映）

**error_stop の AND 条件が必須である実源根拠（N-2）**：
実源照合（scc23_v2_05.c L4651-4656）で確認：
```c
    if(error_count>0)
        fprintf(stderr,"scc23: %d error(s) in '%s'\n",error_count,src_name);
    ...
    return error_count?1:0;
```
`compile` 関数は **error が発生しても生成を最後まで継続**する（`emit_runtime()`／`emit_data_section()` を実行し `out_fp` を fclose）。案D の `error()` は `error_count++` のみでその場では exit しない。結果、**壊れた asm（値破壊を含む部分出力）が asm ファイルに残る**（実測：case2_no_proto.c で 262 行の asm が出力され `LDW B,#8` 誤 I2F が残存）。ゆえに「非0終了」だけを判定に使うと壊れた asm の残存を見逃す。error メッセージの内容チェックを併用する AND 条件でこれを検出する。

### 2.3 実行値の算出（v0.2 M-1 反映：golden 差分を主判定に）

「戻り値型 × 演算 × 右辺種別」の生成 asm が期待通りか判定：

**主判定（compile_ok / warning_only ケース）**：
- **v2.05 で凍結した golden asm と byte 一致**することを判定（v0.1 の単純 grep から変更・M-1 反映）
- golden は本設計メモ承認後の実装フェーズで、v2.05 に各テストソースを投入し出力 asm を凍結して作成
- Phase 2 以降で挙動が変わったら byte 差分で即検出

**主判定（error_stop ケース）**：
- **非0終了 AND error メッセージ「`used in float context`」を含む**の AND 条件（§2.2・N-2 反映）
- **加えて**、生成された asm があっても後続工程（hasm23）に渡さない運用（§2.6）

**補助判定（golden 未整備時のサニティチェック）**：
- v0.1 で主判定にしていた「生成 asm 中に `LDW B,#8 / SHL A,B` が含まれるか否か」は補助へ格下げ（M-1 反映）
- **理由（実源根拠）**：`SIR_I2F` の emit は `LDW B,#8 / SHL A,B`（scc23_v2_05.c §S6・L169）で、**明示キャスト `(float)i` や正当な int→float 昇格でも同一命令列が生成される**。単純 grep では「当該 call 戻り値ノードに対する誤挿入か」「正当な I2F か」を弁別できず false positive を招く
- ゆえに主判定は golden 差分とし、grep はあくまで初回 golden 生成時のサニティ補助（誤 I2F が正当箇所にしか無いことの目視確認）に留める

### 2.4 期待値ファイル形式（v0.2 M-2 反映：golden_version フィールド追加）

```
# m1_f_add_c_n.expected
expect_result=error_stop
expect_error_contains=used in float context
expect_error_contains=undeclared function
golden_version=v2.05
golden_asm=(該当ケースが error_stop のため golden 不要)
```

```
# m1_f_add_c_p.expected（プロトタイプあり float ケース）
expect_result=compile_ok
golden_version=v2.05
golden_asm=goldens/m1_f_add_c_p.golden.asm
```

**フィールド定義**：
- `expect_result`：`compile_ok` / `warning_only` / `error_stop` のいずれか
- `expect_error_contains`：error_stop ケースで必須。error メッセージに含まれるべき文字列（複数指定可・全て含む＝AND 条件）
- `golden_version`：**golden の基準版**。Phase 2 以降で golden 更新時にも版を明示（M-2 反映）
- `golden_asm`：golden asm ファイル名（`goldens/` サブディレクトリに配置）。error_stop ケースは asm を後続に渡さない運用（§2.6）のため省略可

```bash

# 対応 scc23: v2.05 以降

PASS=0; FAIL=0; total=0
for src in m1_*.c; do
    ...
done
echo "Result: $PASS/$total PASS"
```

### 2.6 error_stop 時の運用ルール（v0.2 N-2 反映：新設）

**背景**：実源照合（§2.2）で確認したとおり、scc23 v2.05 の `compile` は error 発生でも生成を最後まで継続し、壊れた asm（値破壊を含む部分出力）が出力される。ゆえに `error_stop` ケースで**生成された asm を後続工程（hasm23）に渡すと、壊れたバイナリが生成される事故が起こりうる**。

**運用ルール**：
1. `error_stop` ケースでは、テスト完了後に **生成 asm を削除** するか、**別ディレクトリ（例：`corrupt_asms/`）に隔離** する
2. `run_c1_matrix.sh` は error_stop 判定時に自動的に隔離処理を行う
3. リンク工程（hasm23 呼び出し）は `expect_result != error_stop` のケースのみ実施（本 C-1 では実施しないが、将来 CI 統合時のルールとする）
4. 壊れた asm が誤ってプロジェクトナレッジや outputs に流出しないよう、`.gitignore` 相当の除外を検討

**参照**：scc23 v2.05 の error() 実装（L536-548）／compile() の生成継続挙動（L4651-4656）。exit 化するかは Phase 2 以降の課題（現行の設計思想を尊重し本 C-1 では触らない）。
