# 1. 目的とスコープ

本文書は、scc23 Cコンパイラ（Small-C移植ベース・YSD8800 ISA2.3対応）の v2.03 以降の改良工程を Phase 0〜6 として定義する工程表である。従来この6フェーズ構成は口頭合意のみで正式文書化されておらず、進捗と予定の確認(latest) 2026-07-04 ロードマップにて「次回scc23系チャットで文書化を推奨」と警告されていた懸案を解消するために起草する。

本文書は工程の粒度・依存関係・完了条件・本体改変の有無を定義することに限定し、各Phaseの詳細設計（IR拡張の具体仕様・命令生成の実装詳細等）には踏み込まない。詳細設計は各Phase着手時に行い、レビュー承認を経てから実装する（原則43）。

## 1.1 設計原則（本ロードマップ全体に適用）

- **汎用性原則**：scc23の拡張機能は「既存YUI OS（Forthカーネル＋Cユーザランド）でも、将来の置き換えC言語OSでも使える汎用機能」として設計する。特定OS専用の妥協はしない。両OSは非排他であり、いずれか一方向けに機能を歪めない。

- **unsigned実装方式の確定**：符号なし型は、OS拡張設計側の `is_unsigned` フラグ追加方式ではなく、v2.x側で既に予約済みの **`T_UINT`（IR層の型種別）方式** に統一する。IR層に型を持たせる方式のほうが符号なし専用命令（`SIR_CMP_LT_U` 等）を活かした最適化がしやすく、どちらのOSでも恩恵を受けられるため。

- **ISA厳守**：ISA2.3（ISA2_3_v231.docx）に存在しない命令を生成コードに混入させない。

- **回帰ゲート厳守**：コンパイラ本体を改修する各Phaseの完了条件に、Dhrystone絶対ゲート（-O0-strict：826/48405/P:20/21846B）の維持を必須で含める。

## Phase 1：検証負債対応（C-1／C-2／C-3）

v2.00 Step10のバグ修正（call型伝播）で露呈した検証負債（scc23_v2_00_design_v2_10.docx §9）に対応する。Phase 2で型システムに手を入れる前に片付けておくことで、型変更時の回帰検出網を先に整備する狙い。

| 項目 | 根拠（設計書§9） | 完了条件 | 本体改変 |
| --- | --- | --- | --- |
| **C-3**：float関数の前方宣言なし呼び出し（潜在バグ） | 未定義関数callはT_INTフォールバック。前方未定義のfloat返し関数を先に呼ぶと誤昇格が再発しうる。「実害が出る前に対処すべき既知の制約」 | プロトタイプ宣言の型記録 or 2パス化により、前方未定義float関数呼び出しで正しい戻り値型が伝播すること。回帰テスト追加 | あり（前方宣言の型記録機構） |
| **C-1**：call戻り値型の網羅テスト不足 | float関数()+定数バグがStep1〜9をすり抜けた。戻り値型(float/int)×演算(+/-/*/÷)×右辺種別(定数/変数/call)のマトリクステストを回帰スイートに追加すべき | 上記マトリクステストを回帰スイートに追加し全PASS | なし（テスト整備のみ） |
| **C-2**：Q8.8期待値の手計算ミス防止 | 期待値手計算で誤記が発生（8.5を0x0850と誤記、正0x0880）。C式→Q8.8 hex変換ヘルパスクリプトを用意し手計算を排除すべき | C式→Q8.8 hex変換ヘルパスクリプトを整備し、期待値生成を自動化 | なし（補助スクリプトのみ） |

**着手順**：C-3（本体改変を伴い、かつ実害リスクありのため最優先）→ C-1（マトリクステスト整備）→ C-2（ヘルパスクリプト）。C-1/C-2は本体非改変のため、C-3の検証にも活用できる。

**注意**：C-3は本体改変を伴うため、着手時は `_poc` 生成（本番非改変・KY38）とし、Dhrystone絶対ゲート維持を完了条件に含める。C-1/C-2はテスト・スクリプト整備のみで本体を触らない。

## Phase 2：型システム統合（T_BOOL＋T_UINT＋比較命令リネーム）

v2.00で型enumに予約のみ確保した T_BOOL／T_UINT を実装に格上げする。

| 項目 | 根拠 | 内容 |
| --- | --- | --- |
| T_UINT実装 | 設計書§型システム表「uint：T_UINT・予約のみ・今回未実装」 | 符号なし型を実装。符号拡張ロジック（LDB等）を追加。unsignedは前述の通りT_UINT方式で統一 |
| T_BOOL実装 | 設計書§型システム表「bool：T_BOOL・予約のみ・今回未実装」 | bool型を実装に格上げ |
| 比較命令リネーム | v2.8既定方針 | SIR_LT→SIR_CMP_LT_S 等。符号付き／符号なしを命令名で区別。bool/unsigned実装と同時実施 |
| 回帰確認 | 回帰ゲート厳守原則 | Dhrystone絶対ゲート（826/48405/P:20）不変確認 |

**本体改変**：あり（IR型種別の実装化・命令生成拡張）。`_poc` 生成必須。

## Phase 3：OS拡張・独立機能（Phase 2と並行着手可）

型システムと無関係な独立機能。低リスク。将来の独立C言語OS向けだが、現YUI OSとも非排他。

| 項目 | 内容 |
| --- | --- |
| プリプロセッサ移植 | scc22資産（`handle_define` 等）の移植。型システムと無関係で低リスク |

**本体改変**：あり。ただし型システムと独立のため、Phase 2と並行着手可能（リソース一本化の観点ではPhase 2完了後を推奨）。

# 5. 依存関係と着手順の要約

- Phase 0（完了）→ Phase 1 を次に着手する。
- Phase 1 のうち C-1/C-2 は本体非改変のため先行整備可。C-3 は本体改変あり。
- Phase 2（型システム）は Phase 1 完了後に着手。Phase 3 は Phase 2 と独立のため並行可（推奨はPhase 2完了後）。
- Phase 4 は Phase 2 完了（型システム安定）が着手条件。
- Phase 5 は最適化枠。
- Phase 6 は memmap拡張（ABI変更）が前提のため最後。

# 6. 未確定事項・レビュー論点

- **論点1**：Phase 1〜3の着手前提を「Phase 0完了後」としたが、Phase 3の一部はPhase 1/2と並行できなくもない。リソース一本化の観点で直列（Phase 1→2→3）を既定とするか、Phase 3の並行着手を明示的に許容するか。
- **論点2**：Phase 4の着手条件を「Phase 2完了後」としたが、この順序でよいか。
- **論点3**：本ロードマップは工程表（粒度・順序・完了条件）に限定し、各Phaseの詳細設計は着手時に別途行う（原則43）方針でよいか。
- **論点4**：Phase 5/6はO2フェーズ・大工事であり優先度が低い。現時点で末尾配置としているが、将来の優先度見直し余地を明記しておくべきか。
