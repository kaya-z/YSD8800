## 1. 目的

REPL（対話デバッガ）において、**ブレークポイント（BP）で停止した位置から `c`（continue）で実行を再開できない**欠陥を解消する。

あわせて、**同一の根本原因を持つ `t`（trace）** も同時に修正する
（`kaizen` 方針「見えているバグは先に潰す。残したまま進行しない」に従う）。

---

## 2. 現象（実測・ネガティブコントロール取得済）

### 2.1 再現環境

| 項目 | 値 |
|---|---|
| 実行バイナリ | `emu23_v113_ref`（`emu23_v1_13.c` を無改変ビルド） |
| テストプログラム | `b4_bp_poc_v2.asm` v0.2（`_poc` サフィックス＝KY38 準拠） |
| ラベル | `START=$0100` / `L1=$0104` / `L2=$010c` |
| 入力コマンド列 | `b 0104` → `b 010c` → `c` → `c` → `c` → `q` |

### 2.2 実測結果（要約：debug_style_guide ルールD 準拠）

```
期待: BREAK@0104 → c → BREAK@010c → c → HALT
実測: BREAK@0104 → c → BREAK@0104 → c → BREAK@0104 （PC が前進しない）❌
```

**該当行のみ抜粋**

```
(emu) ** BREAK @0104 **
PC=0104 A=0001 ...
(emu) ** BREAK @0104 **     ← 1回目の c。PC 不変
PC=0104 A=0001 ...
(emu) ** BREAK @0104 **     ← 2回目の c。PC 不変
PC=0104 A=0001 ...
```

A レジスタが `0001`（＝`L1` の `LDW A,#$0002` を**未実行**）のまま変化しないことから、
**1命令も実行されていない**ことが機械的に確認できる。

---

## 3. 原因（実ソース照合＝KY34）

`emu23_v1_13.c` L2087-2090

```c
// c  — continue (run until halt or breakpoint)
} else if (cmd[0] == 'c') {
    if (cpu.halted) { printf("CPU is halted\n"); continue; }
    while (!cpu.halted && !is_break(cpu.pc)) exec_one();
}
```

**`while` の入口で `is_break(cpu.pc)` を判定している。**
BP 停止位置では定義上 `is_break(cpu.pc) == 1` であるから、
**ループ本体が 1 回も回らずに即座に復帰する**。これが本欠陥の全体である。

### 3.1 同一欠陥の波及（`t`）

L2092-2098

```c
// t  — trace (step + dump after each instruction)
} else if (cmd[0] == 't') {
    if (cpu.halted) { printf("CPU is halted\n"); continue; }
    while (!cpu.halted && !is_break(cpu.pc)) {
        exec_one();
        dump_regs();
    }
}
```

**`c` と完全に同一の入口判定構造**であり、同じく BP 停止位置から再開できない。

### 3.2 正常な実装（`s`）— 修正の手本

L2076-2085

```c
// s [N]  — step N instructions
if (cmd[0] == 's') {
    if (cpu.halted) { printf("CPU is halted\n"); continue; }
    int n = 1;
    if (sscanf(cmd + 1, "%d", &n) != 1) n = 1;
    // [FIX BUG-8] exec_one() 後にも is_break をチェック
    while (n-- > 0 && !cpu.halted) {
        exec_one();
        if (is_break(cpu.pc)) break;
    }
}
```

`s` は **「先に `exec_one()`、その後 `is_break` 判定」** という後置判定になっており、
BP 停止位置からでも正しく前進する。

> **★教訓★ 過去に `s` だけが `[FIX BUG-8]` で修正され、`c`／`t` に横展開されなかった。**
> **同一構造を持つ兄弟実装は、一方を直したら必ず全数を洗い出すこと**（kaizen 候補、§8 参照）。

### 3.3 実行系ループの全数確認

実源 grep により、REPL 内で `exec_one()` を回すループは **`s` / `c` / `t` の 3 箇所のみ**であることを確認した。
`n`（非対話ステップ）・`-q`（一括実行）は REPL 外であり BP 判定を持たないため対象外。

| コマンド | 構造 | 判定 |
|---|---|---|
| `s` | 後置判定 | ✅ 正常（修正不要） |
| **`c`** | **前置判定** | ❌ **要修正** |
| **`t`** | **前置判定** | ❌ **要修正** |

---

## 4. 修正方式（案1：do-while 形／ユーザー承認済方針）

### 4.1 採用方式

**`c` / `t` を「入口で無条件に 1 命令実行 → 以降 BP 判定」の後置判定（do-while）構造に改める。**
これは `s` の実装と同一の思想であり、REPL 内 3 コマンドの構造が統一される。

### 4.2 不採用とした案（記録として保持）

| 案 | 内容 | 不採用理由 |
|---|---|---|
| 案2 | 「BP 停止直後だけ判定をスキップする」状態変数を持つ | 内部状態変数が増え、`s`/`c`/`t` 間で整合管理が必要になる。**コンパイラ実装設計原則3「内部状態変数の変更箇所は一か所に集約」に反する**。案1 で同等の結果が状態変数なしに得られるため不要 |

### 4.3 修正後コード（`c`）

```c
// c  — continue (run until halt or breakpoint)
//     [v1.14 / B-4 EMU-C] BP停止位置から再開できるよう後置判定(do-while)化。
//     入口で is_break を見ると停止位置で 0 回ループになり前進しない。
} else if (cmd[0] == 'c') {
    if (cpu.halted) { printf("CPU is halted\n"); continue; }
    do {
        exec_one();
    } while (!cpu.halted && !is_break(cpu.pc));
}
```

### 4.4 修正後コード（`t`）

```c
// t  — trace (step + dump after each instruction)
//     [v1.14 / B-4 EMU-C] c と同一の根本原因。後置判定(do-while)化。
} else if (cmd[0] == 't') {
    if (cpu.halted) { printf("CPU is halted\n"); continue; }
    do {
        exec_one();
        dump_regs();
    } while (!cpu.halted && !is_break(cpu.pc));
}
```

### 4.5 差分の規模

| 項目 | 値 |
|---|---|
| 変更関数 | `repl()` のみ（1 関数） |
| 変更箇所 | **2 箇所**（`c` / `t`） |
| 追加した状態変数 | **なし** |
| 既存オプション体系への影響 | **なし** |

## 5. 仕様として確定させる挙動（重要・マニュアル改版対象）

本修正により、以下が **emu23 の正式仕様**となる。

### 5.1 「`c` は必ず 1 命令以上実行する」

| 状況 | 修正前 | **修正後（仕様）** |
|---|---|---|
| BP 停止位置で `c` | 前進しない（欠陥） | **その命令を実行してから次の BP／HALT まで走る** |
| BP を置いた**直後のアドレスに現在いる**状態で `c` | 前進しない | **その BP では止まらず、次の BP／HALT まで走る** |
| BP なしで `c` | HALT まで走る | 同じ（**非回帰**） |
| `halted` 状態で `c` | `CPU is halted` | 同じ（**非回帰**。`do` に入る前に `continue` する） |

> **★この挙動は意図的である★**
> 「現在 PC の BP では止まらない」は MC6809 モニタや OS-9 `debug` 等、
> SWI 方式 BP を持つ古典的デバッガの慣例（BP 命令を復元・実行してから再武装する）と一致する。
> **これがなければ BP からの継続が原理的に不可能**であるため、副作用ではなく必然の仕様である。

### 5.2 `t` も同一仕様

`t` は「1 命令実行＋レジスタダンプ」を BP／HALT まで繰り返す。
修正後は **`c` と同じく必ず 1 命令以上実行する**。

### 5.3 `s` は非変更

`s` は既に後置判定であり、挙動は一切変わらない（**非回帰**）。

## 8. kaizen 候補（本チケットで得た教訓）

### 8.1 ★兄弟実装は「一方を直したら全数を洗い出す」★

`s` は過去に `[FIX BUG-8]` で後置判定に修正されていたが、
**同一構造の `c` / `t` へ横展開されず、B-4 として残存した。**

> **同じ形をしたコードが複数ある場合、1 箇所の修正は「残りが未修正である」ことの証拠でもある。**
> 修正時は必ず**同一構造の全数を実源 grep で列挙**し、横展開の要否を判定すること。

（今回はこれに従い、`exec_one()` を回すループを全数列挙して 3 箇所を確定した＝§3.3）

### 8.2 ★「動くようになった」は「壊れていない」を意味しない★

BP 再開の修正は、**BP 判定自体を無効化しても「前進する」**。
よって前進の確認だけでは不十分で、**「次の BP で再び止まる」ことの確認が必須**である。

> **修正の検証は「直したい症状の消失」と「壊してはいけない機能の生存」を対で取る。**
