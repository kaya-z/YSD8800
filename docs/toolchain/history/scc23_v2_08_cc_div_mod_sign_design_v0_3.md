## 0. ゴールと前提

int 除算・剰余を C99 準拠の結果に是正する。あわせて `_cc_mod` にゼロ除算ガードを新設し、

## 1. バグの確定内容（実源照合済）

### 1.1 実測症状（HANDOVER §2.1 より再掲・レビューで全5行の正確性を再確認済）

| 式 | C（コンパイル時畳み込み） | `_cc_div`（実行時） | 反復 | 症状 |
|---|---|---|---|---|
| `7 / 2` | 3 | 3 | 4 | 一致 |
| `-7 / 2` | -3 | 0 | 1 | 誤値 |
| `-100 / 7` | -14 | 0 | 1 | 誤値 |
| `7 / -2` | -3 | 16381 | 16382 | 誤値＋実質ハング |
| `-7 / -2` | 3 | 0 | 1 | 誤値 |

`7 / -2` の 16381/16382 は、A=7 に対し負の除数 -2 を減算（＝加算）し続け、
$7FFF を越えて $8001 へラップした時点で `BLT` が成立するまで回るためである。

### 1.2 原因（実源照合済・`scc23_v2_07.c` L3894-3918 が `_cc_div`、L3923-3937 が `_cc_mod`）

```
_cc_div:                        ; 実源 L3894-
    CMPI A, #0
    BEQ  _ccdiv_zero            ; ゼロ除算ガードあり（_cc_div のみ）
    STW  A, [_C_DIV_A]          ; _C_DIV_A ← 除数
    STW  B, [_C_DIV_B]          ; _C_DIV_B ← 被除数
    LDW  A, #0
    STW  A, [_C_DIV_Q]
_ccdiv_loop:
    LDW  A, [_C_DIV_B]          ; A ← 被除数
    LDW  B, [_C_DIV_A]          ; B ← 除数
    CMP  A, B
    BLT  _ccdiv_done
    SUB  A, B
    ...
```

**絶対値化・符号退避処理が皆無**である。オペランドが負のまま減算ループへ入るため、
`CMP`/`BLT` による終了判定が意図した意味を持たない。

`_cc_mod`（L3923-3937）は同じ減算ループ構造だが、**`CMPI A,#0` / `BEQ` に相当する
ゼロ除算ガードが存在しない**。`b==0` の場合ループが無限に回り、実機ハングする。

### 1.3 `_cc_mul` は対象外（既確認）

`_cc_mul` は論理右シフト方式であり、2の補数の性質上、符号を意識せずとも積は正しく求まる。

### 1.4 呼び出し規約（実源照合・確定）

呼び出し元は `scc23_v2_07.c` L2825（`JSR _cc_div`）、L2833（`JSR _cc_mod`）、
L3146-3147（複合代入 `/=` `%=`）。いずれも同一規約である。

```
emit_expr(n->left);   emit_push_a();
emit_expr(n->right);  emit_pop_b();
JSR _cc_div / _cc_mod
```

- **呼出直前：A レジスタ = right（除数）、B レジスタ = left（被除数）**
- `_fdiv`（L4066-4068 のコメント）と同一規約であり、**レジスタ読み替えは不要**。

> ⚠ **実装者が最も踏みやすい落とし穴**：
> **レジスタ名 A/B と、ワーク変数名 `_C_DIV_A`/`_C_DIV_B` は対応しない。**
> `_C_DIV_A` = **除数**、`_C_DIV_B` = **被除数** である。
> さらにループ内では `LDW A,[_C_DIV_B]` により **A レジスタに被除数**が入る。
> 「A だから除数」と読むと必ず誤る。

### 1.5 ISA2.3 の比較・分岐の実像（**v0.3 で全面訂正**・レビュー v2.0 B-1）

> ⚠ **v0.2 §1.5 の記述「$8000 は `BLT` に対して常に負値として振る舞う」は事実誤認であった。**
> 本節は実源照合に基づき全面的に書き改める。誤った理由付けを後版へ伝播させないため、
> 誤りであった旨をここに明記して記録する。

**実源で確定した事実**

| 項目 | 実源 | 内容 |
|---|---|---|
| FLAGS の構成 | `ISA2_3_v231.docx` L71 / `emu23_v2_13.c` L248-249 | `FL_Z`(0x01) / `FL_N`(0x02) / IE のみ。**V（オーバーフロー）・C（キャリー）フラグは存在しない** |
| フラグ更新 | `emu23_v2_13.c` L2210-2213 `set_zn()` | `Z ← (v==0)`、`N ← (v & 0x8000)`。**Z と N のみ** |
| CMP / CMPI | 同 L2521 / L2528 | `set_zn((uint16_t)(*rd - *rs))` — **差の bit15 を N に入れるだけ** |
| BLT / BGE | 同 L2634-2643 / `ISA2_3_v231.docx` L230-231 | **BLT: N=1 で分岐／BGE: N=0 で分岐** |

**帰結1：`BLT` は真の符号付き比較ではない。**
`BLT` は `N XOR V` ではなく **`rD − rS` の bit15** を見るだけである。
反例：`CMP A,B`（A=$8000, B=$0002）→ `$8000 − $0002 = $7FFE` → bit15=0 → **N=0** →
`BLT` は成立しない。すなわちこの場合 $8000 は「B 以上」と正しく判定される。

**帰結2：符号なし比較分岐は存在しない。**
`BLO`/`BHS`/`BCC`/`BCS` は命令表（`hasm23_v1_04.c` L165-168）に無く、条件分岐は
`BEQ`/`BNE`/`BLT`/`BGE` の4種のみである。

**帰結3（本設計の基盤）：限定された範囲では `BLT` が符号なし比較として厳密に機能する。**

> **命題**：`A ∈ [0, 32768]`、`B ∈ [1, 32768]`（符号なし解釈）のとき、
> `CMP A, B` 後の N フラグは符号なし比較 `A < B` と厳密に一致する。
>
> **証明**：N = `(A − B) mod 2^16` の bit15。
> - `A ≥ B` のとき `A − B ∈ [0, 32768]`。ただし `A−B = 32768` となるのは `A=32768, B=0` のみで、
>   前提 `B ≥ 1` により起こり得ない。よって `A − B ∈ [0, 32767]` → bit15=0 → **N=0**。
> - `A < B` のとき `A − B ∈ [−32768, −1]` → `mod 2^16` で `[32768, 65535]` → bit15=1 → **N=1**。∎

この命題により、**絶対値化後の値が $8000（=32768）であっても既存の減算ループは正しく動作する**。
これが §3.6（INT_MIN 専用経路の削除）と §3.7（不変条件）の根拠である。

**PUSH/POP と X レジスタについて**：
`PUSH`/`POP` は拡張命令表（`hasm23_v1_04.c` L97-102）に A/B/X の3本が定義済。
`X` は `parse_reg`（L271）で 2 として受理され、ALU 系命令は `rD` を汎用に取る。
実行側も `emu23_v2_13.c` L2216-2224 の `get_reg_ptr(2)` → `&cpu.x` で解決される。
**`LDW X,#0` / `CMPI X,#0` / `XORI X,#1` はアセンブル・実行とも可能**である（§4.1）。

## 2. 期待値の手計算による確定（実装からの生成禁止）

### 2.1 C99 規則

- `/`：ゼロ方向丸め
- `%`：`a == (a/b)*b + a%b` を満たすように定義され、**結果の符号は被除数 `a` と同じ**

（`a` = left = B レジスタ = `_C_DIV_B`、`b` = right = A レジスタ = `_C_DIV_A`）

### 2.2 期待値表（実装後の突合せ基準）

**基本ケース**

| a (被除数) | b (除数) | a/b | a%b | 検算 (a/b)×b + a%b |
|---:|---:|---:|---:|---|
| 7 | 2 | 3 | 1 | 3×2 + 1 = 7 ✓ |
| -7 | 2 | -3 | -1 | (-3)×2 + (-1) = -7 ✓ |
| 7 | -2 | -3 | 1 | (-3)×(-2) + 1 = 7 ✓ |
| -7 | -2 | 3 | -1 | 3×(-2) + (-1) = -7 ✓ |
| -100 | 7 | -14 | -2 | (-14)×7 + (-2) = -100 ✓ |
| 100 | -7 | -14 | 2 | (-14)×(-7) + 2 = 100 ✓ |
| 0 | 5 | 0 | 0 | 0 ✓ |

**ゼロ除算ケース（v0.3 で復活・レビュー v2.0 B-3）**

v0.1 にあった 2 行が v0.2 で脱落していた。本版で復活させ、かつ**実装定義動作が確定した
ため期待値を明記する**（v0.1 の「(ゼロ除算)」より情報が増えている）。

| a | b | a/b | a%b | 根拠 |
|---:|---:|---:|---:|---|
| 5 | 0 | **0** | **0** | §3.3 `_ccdiv_zero` / §3.4 `_ccmod_zero` がいずれも `LDW A,#0` |
| -5 | 0 | **0** | **0** | 同上（ガードは符号判定より前に置くため被除数の符号に依らない） |

> C99 ではゼロ除算は未定義動作。本実装は **0 を返す**ことを scc23 の**実装定義動作**として
> 宣言する（§3.5・§6）。ハードウェア例外は発生させない（ISA2.3 に除算例外機構が無い）。

**追加ケース**

| a | b | a/b | a%b | 目的・検算 |
|---:|---:|---:|---:|---|
| -3 | 5 | 0 | -3 | 商0への符号付与で「-0」が生じないこと。0×5+(-3) = -3 ✓ |
| 0 | -5 | 0 | 0 | 被除数0＋負除数の経路 ✓ |
| 32767 | 1 | 32767 | 0 | 反復回数 32767 |
| **-32768** | **1** | **-32768** | **0** | **反復回数の最悪値 32768 反復**（C-3 で訂正）。§3.1 案C の別件起票根拠値 |

**境界ケース：INT_MIN**（表記を「商=／余=」に統一・レビュー v2.0 C-4）

§3.6 のとおり専用経路は設けないが、**検証項目としては必須**であり全行を維持する。

| a | b | C99 期待 | 本設計での結果 | 判定 |
|---:|---:|---|---|---|
| -32768 | 2 | 商=-16384, 余=0 | **商=-16384, 余=0** | ✓ |
| -32768 | 1 | 商=-32768, 余=0 | **商=-32768, 余=0**（商32768=$8000、符号付与後も $8000） | ✓ |
| -32768 | 3 | 商=-10922, 余=-2 | **商=-10922, 余=-2**（検算 (-10922)×3+(-2) = -32768 ✓） | ✓ |
| -32768 | -2 | 商=16384, 余=0 | **商=16384, 余=0**（符号XORで正） | ✓ |
| 100 | -32768 | 商=0, 余=100 | **商=0, 余=100**（`100−$8000` の bit15=1 → 即 done） | ✓ |
| -32768 | -32768 | 商=1, 余=0 | **商=1, 余=0**（`$8000−$8000=0` → N=0 → 1回減算） | ✓ |
| **-32768** | **-1** | **UB（オーバーフロー）** | **商=$8000 (-32768), 余=0** | **実装定義動作**として宣言 |

> `-32768 / -1` は 16bit で +32768 が表現不能。商 32768 = $8000 を得るが符号フラグは
> XOR の結果 0（正）となるため符号付与は行われず、**$8000（= -32768）が返る**。

### 2.3 符号規則の要点

- **商の符号** = `sign(a) XOR sign(b)`
- **剰余の符号** = **`sign(a)` のみ**（除数の符号に依存しない）
  — `-100 % 7 = -2` と `100 % -7 = 2` の対称性がこれを示す

⇒ 絶対値化・ゼロ除算判定は共通化できるが、**出口の符号付与ロジックは div と mod で別**。

## 3. 修正方針

### 3.1 案比較

| 案 | 内容 | 評価 |
|---|---|---|
| **案A（採用）** | 既存の減算ループ構造は維持。入口で符号退避・絶対値化、出口で符号付与を追加 | 動作実績のあるループを変更しないため最小差分。「1変更1検証」原則に合致 |
| 案B | `_fdiv` の24bitシフト減算方式へ全面置換 | 構造が全く異なり検証範囲が広がる。int は16bit のため24bit精度は過剰。不採用 |
| 案C | 16bit シフト減算（restoring division）へ置換 | 反復16回固定で性能面は優位（案Aは最悪 **32768** 反復）。ただし本件の主眼は**正しさの回復**であり、算法置換を同時に行うと1変更1検証に反する。**今回不採用**とし、性能改善は **v2.09 以降の別件として起票**する |

> 用語について：本設計は「`_fdiv` の方式を移植」するのではない。
> `_fdiv` は符号フラグを**ワーク領域**（`WSIGN` = `_C_DIV_B`）で保持するのに対し、
> 本設計は **X レジスタ保持**であり保持媒体が異なる。正しくは
> 「**`_fdiv` と同等の符号分離の考え方を、減算ループ構造へ新規適用する**」である。

### 3.2 符号フラグの保持媒体：**X レジスタ**

**X を「符号フラグ（0=正 / 1=負）」として使用する。**

採用理由：

1. **スタック保持のリスク回避**：`JSR` の戻り番地と同一スタックを共有するため、
   PUSH した符号フラグは全経路で確実に POP せねばならず、1箇所の漏れで暴走する。
   X 保持ならスタック収支は `PUSH X`/`POP X` の1対1に固定され、構造的に破綻しない。
2. **`PUSH X` がデッドコードでなくなる**：X に符号を載せれば callee-save が本来の意味を持ち、
   **命令数・サイクルは増えない**。
3. **div と mod が同一構造になる**：`XORI X,#1` を A にも適用するか B のみに適用するかの
   違いだけになり、C99 の符号規則が命令列にそのまま写る。

既存ループ本体（`_cc_div` L3901-3911、`_cc_mod` L3925-3933）は
`LDW / CMP / BLT / SUB / STW / ADDI / JMP` のみで構成され **X を使用しない**ことを実源確認済。
アドレッシングも絶対（`[_C_DIV_B]`）でインデックス修飾を使わないため、
**ループを跨いで X に符号情報を保持できる**。

> **フォールバック案（記録・発動見込みなし）**：v0.2 では X への ALU 演算が emu23 で
> 未検証であったため、`_C_DIV_Q`（$DBFE。`_cc_div` 専用で `_cc_mod`・`_fmul`・`_fdiv` は不使用）を
> 符号フラグに使う代替案を用意していた。§1.5 末尾および §4.1 のとおり
> **X の使用可能性はアセンブラ・エミュレータ双方の実源で確認済**であり、
> 本代替案の**発動見込みはない**。記録として残す。

### 3.3 `_cc_div` 改修後の確定命令列（**v0.3 で 3経路構成へ簡素化**）

```
_cc_div:
    PUSH X                          ; callee-save（X=符号フラグとして使用）
    CMPI A, #0
    BEQ  _ccdiv_zero                ; 経路C: 除数0
    LDW  X, #0                      ; 符号フラグ初期化（0=正）
    ; ---- 除数 A の符号処理 ----
    CMPI A, #0
    BGE  _ccdiv_apos
    XORI X, #1                      ; 除数が負 → 符号反転
    NOT  A
    ADDI A, #1                      ; A = |除数|（$8000 のときは $8000 のまま＝32768）
_ccdiv_apos:
    STW  A, [_C_DIV_A]
    ; ---- 被除数 B の符号処理 ----
    CMPI B, #0
    BGE  _ccdiv_bpos
    XORI X, #1                      ; 被除数が負 → 符号反転
    NOT  B
    ADDI B, #1                      ; B = |被除数|（$8000 のときは $8000 のまま＝32768）
_ccdiv_bpos:
    STW  B, [_C_DIV_B]
    LDW  A, #0
    STW  A, [_C_DIV_Q]              ; 商初期値 0
_ccdiv_loop:                        ; ★既存ループ本体は完全に無変更★
    LDW  A, [_C_DIV_B]              ; A ← 被除数（残余）  ※§3.7 の不変条件下で
    LDW  B, [_C_DIV_A]              ; B ← 除数            ※CMP/BLT は符号なし比較として機能
    CMP  A, B
    BLT  _ccdiv_done
    SUB  A, B
    STW  A, [_C_DIV_B]
    LDW  A, [_C_DIV_Q]
    ADDI A, #1
    STW  A, [_C_DIV_Q]
    JMP  _ccdiv_loop
_ccdiv_done:                        ; 経路N: 通常
    LDW  A, [_C_DIV_Q]
    CMPI X, #0
    BEQ  _ccdiv_ret
    NOT  A
    ADDI A, #1                      ; 商が負 → 2の補数化
_ccdiv_ret:
    POP  X
    RET
_ccdiv_zero:                        ; 経路C: ゼロ除算 → 0 返し（実装定義動作）
    LDW  A, #0
    POP  X
    RET
```

**スタック収支の確認**

| 経路 | 内容 | PUSH | POP | 収支 |
|---|---|---|---|---|
| 経路N | 通常（`_ccdiv_loop` → `_ccdiv_done` → 符号付与 → `_ccdiv_ret`） | X ×1 | X ×1 | **±0** ✓ |
| 経路N' | 商が正で符号付与をスキップ（`_ccdiv_done` → `BEQ` → `_ccdiv_ret`） | X ×1 | X ×1 | **±0** ✓ |
| 経路C | ゼロ除算（`_ccdiv_zero`） | X ×1 | X ×1 | **±0** ✓ |

**全経路で `PUSH X` 1回・`POP X` 1回。`RET` 時のスタックトップは常に戻り番地。**
（v0.2 は 5経路だった。§3.6 の削除により 3経路へ減少＝実装事故リスク低減）

### 3.4 `_cc_mod` 改修後の確定命令列

```
_cc_mod:
    PUSH X
    CMPI A, #0
    BEQ  _ccmod_zero                ; ★新設：ゼロ除算ガード（HANDOVER 最重要指摘）
    LDW  X, #0
    ; ---- 除数 A：絶対値化のみ。符号フラグには反映しない（C99）----
    CMPI A, #0
    BGE  _ccmod_apos
    NOT  A
    ADDI A, #1
_ccmod_apos:
    STW  A, [_C_DIV_A]
    ; ---- 被除数 B：剰余の符号はこちらのみで決まる（C99）----
    CMPI B, #0
    BGE  _ccmod_bpos
    XORI X, #1                      ; ★ここだけ符号フラグを更新する
    NOT  B
    ADDI B, #1
_ccmod_bpos:
    STW  B, [_C_DIV_B]
_ccmod_loop:                        ; ★既存ループ本体は完全に無変更★
    LDW  A, [_C_DIV_B]
    LDW  B, [_C_DIV_A]
    CMP  A, B
    BLT  _ccmod_done
    SUB  A, B
    STW  A, [_C_DIV_B]
    JMP  _ccmod_loop
_ccmod_done:
    LDW  A, [_C_DIV_B]
    CMPI X, #0
    BEQ  _ccmod_ret
    NOT  A
    ADDI A, #1                      ; 被除数が負 → 剰余も負
_ccmod_ret:
    POP  X
    RET
_ccmod_zero:                        ; ゼロ除算 → 0 返し（実装定義動作）
    LDW  A, #0
    POP  X
    RET
```

**スタック収支**：`_cc_div` と同様、全3経路で `PUSH X` 1回 / `POP X` 1回＝**±0**。

> **「-0」が生じないことの確認**：`_ccmod_done` の符号付与で A=0 のとき
> `NOT 0` = $FFFF、`ADDI #1` = $0000 となり **0 のまま**。
> 同じく `_ccdiv_done` で商0の場合も 0 のまま（例：`-3 / 5` = 0、`0 % -5` = 0）。

### 3.5 影響範囲

- `_cc_div`/`_cc_mod` の**呼び出し元コード生成は無変更**（L2825 / L2833 / L3146-3147）。
- ⚠ **ワーク領域の共用**：`_C_DIV_A`（$DBFA）・`_C_DIV_B`（$DBFC）は
  **int除算と float ランタイムで共用**されている。
  実源 L3947「`_C_DIV_A=$DBFA` を符号フラグに借用(float中はcc_div非走行)」、
  L4063「`WR=_C_DIV_A, WSIGN=_C_DIV_B`」。
  安全性は「**float演算中に `_cc_div`/`_cc_mod` は走らない**」という**相互排他の前提**に
  よってのみ担保されている。**本改修はこの不変条件を変更しない**
  （符号フラグは X レジスタに置くため領域を新規に消費しない）。
- `_C_DIV_Q`（$DBFE）は `_cc_div` 専用。本改修でも商保持にのみ使用。
- ランタイムワーク領域 `$DBE8`-`$DBFF`（24B）の**アドレス割付は無変更**。新規確保なし。
- `_fmul`/`_fdiv` の**コードは無変更**。
- 新規ラベルが増える：`_cc_div` に `_ccdiv_apos` / `_ccdiv_bpos` / `_ccdiv_ret`、
  `_cc_mod` に `_ccmod_apos` / `_ccmod_bpos` / `_ccmod_zero` / `_ccmod_ret`。
- **`scc23_Functional_Spec` の改版が必要**：
  ゼロ除算時 0 返し・`-32768 / -1` が $8000 を返すことを**実装定義動作**として記載する。

### 3.6 INT_MIN 専用経路を設けない根拠（**v0.2 §3.6 の削除と、その証明の記録**）

> **v0.2 の §3.6 は「|被除数|=32768 のとき事前に1回減算する経路1」「|除数|=32768 のとき
> 短絡する経路2」を規定していた。v0.3 ではこれを削除する。**
> 原則「前の版の情報を欠落させない」に従い、**何を削除し、なぜ不要と判断したか**を本節に記録する。

**削除の根拠**：§1.5 帰結3の命題により、`A ∈ [0,32768]`（剰余）・`B ∈ [1,32768]`（除数）の
範囲では `CMP`/`BLT` が**符号なし比較として厳密に機能する**。この範囲は §3.7 の不変条件として
入口の絶対値化とゼロ除算ガードにより保証される。したがって $8000 を特別扱いする必要がない。

**削除しても結果が変わらないことの確認**（v0.2 §3.6 の各経路との等価性）：

- **旧経路1（|被除数|=32768）**：ループ前に1回減算し `Q=1` を計上する処理は、
  ループが自然に行う1回目の反復と**完全に等価**。総商は
  `1 + floor((32768−d)/d) = floor(32768/d)` で一致する。
- **旧経路2（|除数|=32768）**：`|被除数| < 32768 → 商0・余り=被除数`、`= 32768 → 商1・余り0` は、
  ループが自然に到達する結果と一致する（`100 − $8000` は bit15=1 → 即 done で商0・余り100。
  `$8000 − $8000 = 0` は bit15=0 → 1回減算して商1・余り0）。

**§2.2 の境界ケース全7行は、専用経路なしでも設計書記載どおりの結果になる**
（レビュー v2.0 の手追い検証と、本設計側の再確認が一致）。

**削除による効果（試算）**

| 項目 | v0.2（専用経路あり） | v0.3（削除後） | 差 |
|---|---:|---:|---:|
| `_cc_div` 追加命令数（対 v2.07） | 約 31 | 約 16 | −15 |
| `_cc_mod` 追加命令数 | 約 32 | 約 16 | −16 |
| コードサイズ増（両ルーチン計） | 約 +240 B | **約 +125 B** | −115 B |
| 分岐経路数（各ルーチン） | 5 | **3** | −2 |

**削除を選んだ理由**：分岐経路の削減は、本件で最も危険な `POP X` 漏れのリスクを直接下げる。
また「将来 ISA に V フラグが追加された場合の保険」として存置する案も検討したが、
**保険として機能しない**と判断した。仮に `BLT` が `N XOR V` へ再定義された場合、
壊れるのは旧経路が守ろうとした $8000 のケースだけでなく、**減算ループ本体そのもの**である
（剰余は [0,32768] を動くため通常ケースも同時に影響を受ける）。部分的な保護に留まる冗長コードを
持つより、**§3.7 で不変条件を明文化する方が将来の改修者に対して有効**である。

### 3.7 守るべき不変条件（**v0.3 新設**・レビュー v2.0 C-2）

本ランタイムの正しさは、以下の不変条件に依存している。
**この条件が破れると、無警告で誤値を返すようになる。**

**【不変条件】**
> 減算ループに入る時点で、
> - 被除数（`_C_DIV_B`）は符号なし解釈で **[0, 32768]**
> - 除数（`_C_DIV_A`）は符号なし解釈で **[1, 32768]**
> であること。

**成立理由**：
- 上限 32768：入口の絶対値化により、int16 の絶対値の最大は 32768（$8000）に収まる。
- 除数の下限 1：入口のゼロ除算ガード（`CMPI A,#0` / `BEQ`）が 0 を排除する。
- 剰余の単調減少：ループは `SUB A,B` のみで剰余を減らすため、初期値の上限を超えない。

**依存している ISA 仕様**：
> ⚠ **本ランタイムは `ISA2_3_v231.docx` L71 の FLAGS 定義（Z/N のみ。V・C フラグ非存在）と、
> `BLT`=N=1 / `BGE`=N=0 の定義（同 L230-231）に依存している。**
> `BLT` が `rD − rS` の bit15 を見るだけであるからこそ、上記範囲で符号なし比較として機能する。
> **ISA に V フラグが追加され `BLT` が `N XOR V` へ再定義された場合、
> または 32bit 型対応等でオペランド範囲が変わった場合は、本ランタイムの再検証が必須である。**

**実装要件**：生成 asm の `_cc_div` / `_cc_mod` の直前に、以下の警告コメントを出力すること。

```
; NOTE: BLT is N-only (no V flag in ISA2.3). Valid while |rem|<=32768 and 1<=|div|<=32768.
```

## 4. 検証計画

### 4.1 X レジスタ ALU 演算のスモークテスト（**v0.3 で必須→推奨へ格下げ**・レビュー v2.0 C-1）

v0.2 では「emu23 側の実行が未検証」として実装の最優先必須項目に置いていたが、
実源照合により**アセンブル・実行とも可能であることが確定した**。

| 層 | 実源 | 結果 |
|---|---|---|
| アセンブル（レジスタ解決） | `hasm23_v1_04.c` L268-271 | `parse_reg("X")` = 2 |
| アセンブル（`LDW X,#imm`） | 同 L1073-1077 | `rD = parse_reg(op1t)` — X 可 |
| アセンブル（`CMPI`/`XORI`） | 同 L1210-1218 | `rD = parse_reg(trim(op1))` — X 可 |
| 実行（レジスタ解決） | `emu23_v2_13.c` L2216-2224 | `get_reg_ptr(2)` → `&cpu.x` |
| 実行（`CMPI`/`XORI`/`NOT`/`ADDI`） | 同 L2496-2582 | いずれも `get_reg_ptr(rb >> 4)` で rD 解決 |

したがって §3.2 のフォールバック案は**発動見込みなし**。
ただし実施自体は無害かつ安価であるため、**実装初期のスモークテストとして推奨**する
（数行の asm を `hasm23` → `emu23` に通し、`LDW X,#0` / `XORI X,#1` / `CMPI X,#0` の
挙動を確認する）。万一 NG の場合は**無断で方式変更せず**、v0.4 として再レビューを受ける。

### 4.2 回帰検証

> ⚠ **絶対ゲートの byte-exact 維持は達成不可能であり、撤回する。**
> Dhrystone は `_cc_div`・`_cc_mod` を**両方使用**している。
>
> | 実源 | 行 | 使用演算 |
> |---|---|---|
> | `dhry_all_ansi2.c` | L526 `if (n >= 10) print_num(n / 10);` | `/` → `_cc_div` |
> | `dhry_all_ansi2.c` | L527 `putchar('0' + n % 10);` | `%` → `_cc_mod` |
> | `dhry_all_ansi2.c` | L662 `Int_1_Loc = Int_2_Loc / Int_3_Loc;` | `/` → `_cc_div` |
>
> したがって `g_use_div=1` かつ `g_use_mod=1` となり、ランタイム blob に符号処理と
> ゼロ除算ガードが加わる分、**生成 asm は必ず変化する**。

**判定基準**

1. **【必須・PASS条件】Dhrystone の数値出力が v2.07 と完全一致すること。**

   根拠を実源事実で裏付ける（v0.2 の「オペランドは全て非負」という漠然とした理由から改める。
   レビュー v2.0 B-5）：
   - `dhry_all_ansi2.c` L430 は **`#define my_printf`（本体なし＝無効マクロ）**であり、
     L578 以降の全 `my_printf(...)` 呼出は**プリプロセスで消滅**する。
     結果表示に伴う除算は**一切実行されない**。
   - 実際に出力を行うのは `main` 末尾のみ（L529-536）：`putchar('P'/'F')`, `putchar(':')`,
     `print_num(result)`。`result` は 20（絶対ゲート `P:20`）で `print_num(20)` は再帰1段、
     すなわち `_cc_div` 2回・`_cc_mod` 2回のみ。しかも**タイマ停止後（測定区間外）**。
   - **測定区間内の除算は L662 の1箇所のみ**。`Int_2_Loc == 9`、`Int_3_Loc == 7` で商1、
     減算ループは**2反復で終了**する。
   - **`%`（`_cc_mod`）は測定区間内で一度も実行されない**。

   ⇒ 測定区間内の除算オペランドは `9 / 7` のみで両方とも正、出力は `print_num(20)` のみで正。
   したがって**数値出力の完全一致は確実に成立するはず**であり、これが正しい回帰判定基準となる。
   一致しなければ**設計または実装の誤り**として原因究明する。

2. **【再ベースライン】コードサイズ・サイクル数は v2.08 の新実測値を採取し、新ゲートとする。**
   - 採取項目：-O0-strict の `<Dhrystone値>/<cycles>/P:<passes>/<size>B`、および -O1 の cycles
   - 採取後、**`tool_version_ledger_v1_23.md` → v1.24 へ差分更新**して新ゲート値を記録する
     （メインラインでの版数衝突回避のため**差分更新**とすること）
   - `HANDOVER_SCC23_PHASE1_v1_0.md` および `tests_c1_README.md` の絶対ゲート記載も
     併せて改版する（KY41：4点整合）

3. **【事前見積り】増分の概算**（実測との乖離チェック用・**v0.3 で実バイト長に基づき訂正**）

   v0.2 の「1命令2〜3B」という前提は誤りであった。実源に基づく正しいバイト長：

   | 命令 | バイト | 根拠 |
   |---|---:|---|
   | `CMPI` / `XORI` / `ADDI` | **4** | `ISA2_3_v231.docx` L211 |
   | `LDW rD,#imm16` / `LDW rD,[abs]` / `STW rS,[abs]` | **4** | `hasm23_v1_04.c` L472, L481（`1+1+2`） |
   | `BEQ` / `BLT` / `BGE` / `JMP` | **3** | `ISA2_3_v231.docx` L230-231（rel16） |
   | `NOT` / `SUB` / `CMP` / `MOV` | **2** | 同 L204-211 |
   | `PUSH` / `POP` | **2** | `hasm23_v1_04.c` L465-467 |
   | `RET` | **1** | 同 L428 近傍 |

   追加命令は `CMPI`・`XORI`・`LDW #imm`・分岐が大半のため**実効平均 約 3.5〜3.8 B/命令**。

   ⇒ **追加命令数 約32（両ルーチン計）× 約3.9 B ≒ コードサイズ増 約 +125 B**

   **サイクル増**：上記1のとおり、測定区間内で実行されるのは `_cc_div` の
   `9 / 7`（2反復）が `Number_Of_Runs` 回のみ。増分は
   「符号処理の追加分（十数サイクル）× `Number_Of_Runs`」に限定され、
   **48405 に対して 1% 未満**と見込む。**サイズ増の方が支配的**である。
   実測が概算から大きく外れた場合は原因を調査する。

4. **【確認済】-O1 ピープホールはランタイム blob を対象としない**（レビュー v2.0 C-5）。
   `scc23_v2_07.c` L212 のとおり「関数生成入口で `g_insbuf_on=1`、RET後に
   `peephole_pass()` → `insbuf_flush()` → `on=0`」であり、ピープホールは
   **関数本体の生成中のみ**作動する。`emit_runtime` によるランタイム blob 出力は**対象外**。
   新設する `CMPI X,#0` / `BGE` の並びが変換される懸念はない。

### 4.3 単体検証（PoC）

§2.2 の期待値表**全20ケース**（基本7＋ゼロ除算2＋追加4＋境界7）を emu23 上で実測し、
**実装からではなく本書の手計算値**と突合する。重点確認：

- 旧 `7 / -2` の「16382回反復（実質ハング）」が解消し `-3` を返すこと
- `x % 0` が**ハングせず 0 を返す**こと（新設ガードの動作）

## 5. 実装時の重点確認項目

1. **X の callee-save**：全3経路で `PUSH X` / `POP X` が1対1であること（§3.3/§3.4 の表で確認済）。
   特に**ゼロ除算経路での `POP X` 漏れ**に注意（v0.1 からの継続警戒項目）。
2. **`_C_DIV_A` = 除数 / `_C_DIV_B` = 被除数**（レジスタ名 A/B と対応しない・§1.4 の警告）。
3. **`_cc_mod` の絶対値化では除数の符号を符号フラグに反映しない**（C99：剰余の符号は被除数のみ）。
   `_cc_div` からコピーして作ると必ず間違えるため、`XORI X,#1` の位置を最後に再確認すること。
4. **`NOT` は `rD` のみ使用（`rS=0` 固定）**（`hasm23_v1_04.c` L158）。
5. **ISA2.3 に無い命令を使わない**（`BLO`/`BHS` 等は存在しない・§1.5 帰結2）。
6. **§3.7 の警告コメントを生成 asm に出力すること**（実装漏れやすい・不変条件の可視化）。
7. **前方宣言の義務化**（v2.06 以降）：`scc23_v2_08.c` 内で新規関数を追加する場合は
   C99 準拠のプロトタイプを必ず置くこと。
8. **工程確認・KY の段階で台帳と実ファイルの4点整合を再確認すること**（本書冒頭の版数表）。
