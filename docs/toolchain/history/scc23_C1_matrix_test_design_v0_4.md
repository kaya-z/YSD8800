## 0. ゴールと前提

### 0.1 ゴール

`scc23_v2_00_design_v2_10.docx` §9 C-1 の指摘に対応する：
- **戻り値型（float/int）× 演算（+/-/*/÷）× 右辺種別（定数/変数/call）** のマトリクステストを整備
- 上記マトリクステストを回帰スイートに組み込み、**全 PASS** を C-1 完了条件とする
- 将来の Phase 2（型システム統合）で回帰を検出するための **セーフティネット** を先に張る

### 0.2 前提

- 本タスクは **本体改変なし**（テスト整備のみ・原則43 軽量版でよい）
- scc23 v2.06 の C-3＋C-3追補により、**プロトタイプなしの関数呼び出しは全て error 停止**となる（案G・前方宣言必須化）。ゆえに従来ならすり抜けたバグ再発シナリオを**マトリクスの正例側（error 発生）**として組み込める
- テストは既存の scc23 テストと同居可能な形式（`.c` ソース＋期待値ファイル）とする

### 0.3 C-3 との連続性

C-3 完了により以下が確定：
- プロトタイプ宣言あり → 正しく型伝播（コード生成が v2.04 と byte-exact）
- プロトタイプなし＋int 文脈 → warning のみ・T_INT フォールバック動作
- プロトタイプなし＋float 文脈 → error 停止（fail-safe）

C-1 は上記3挙動を**マトリクスとして網羅**し、Phase 2 以降で意図せず変化しないことを保証する。

**golden 基準版固定の意義（M-2）**：本テストは「Phase 2 以降で回帰を検出するセーフティネット」（§0.1）が目的。C-3 実装の前後で `m1_f_*_*_n`（float×proto なし）の期待挙動が「値破壊 asm 出力」→「error_stop」へ変化した歴史があり、さらに v2.06 の案G で `proto=n` の全ケースが error_stop へ統一された。golden 基準版を **scc23 v2.06 に固定**することで、Phase 2 以降で挙動が変わった場合に「v2.06 golden からの差分＝回帰疑い」と一義的に判定できる。

### 1.3 テストケース命名規約

`m1_<戻値型>_<演算>_<右辺>_<proto>.c`
- `<戻値型>`: `i`（int）／`f`（float）
- `<演算>`: `add`／`sub`／`mul`／`div`
- `<右辺>`: `k`（constant）／`v`（variable）／`c`（call）
- `<proto>`: `p`（あり）／`n`（なし）

例：`m1_f_add_c_n.c` = float 戻し × 加算 × call × プロトタイプなし → error 停止期待

### 1.4 テスト削減の可否

48 通り全実装は冗長。以下の削減を提案：
- **演算4種は加算・除算の2種に削減**（加算は最小コスト・除算は Q8.8 で最も複雑）
- **削減根拠（v0.2 N-1 反映）**：元 C-3 バグ（`float関数() + 定数`）は**加算で顕在化**しており加算を残すのは必須。除算（FDIV）は Q8.8 の**最複雑経路**（`_fdiv` ランタイム呼出・シフト補正・ゼロ除算保護）ゆえ、この2種で境界を代表化できる。乗算（FMUL オーバーフロー warning 経路）・減算は加算・除算に挙動が包含され、削減リスクは低い。§7.1 で完全網羅計画に回収する。
- **戻り値型2 × 演算2 × 右辺種別3 × プロトタイプ2 = 24 通り**が現実的なテスト規模

ただし C-2（Q8.8 ヘルパスクリプト）整備後は 48 通り全実装への拡張を検討。

## 2. 実装方針

### 2.1 ディレクトリ構造

```
/mnt/project/tests_c1/     ← 新設（プロジェクトナレッジには登録しない場合、開発時のみ）
  m1_i_add_k_p.c            ← 各テストソース（24 or 48 個）
  m1_f_div_c_n.c
  ...
  expected/                 ← 期待値
    m1_i_add_k_p.expected   ← "compile_ok" or "error_stop" or "warning_only" 等の期待判定
  goldens/                  ← v2.06 凍結 asm（golden 基準版・v0.4 で更新）
    m1_i_add_k_p.golden.asm
    ...
  run_c1_matrix.sh          ← マトリクス実行スクリプト（PASS/FAIL 集計）
  README.md                 ← テスト設計と実行手順（golden 版数明記）
```

### 2.2 期待値判定の分類

各テストの期待値は以下の3種類：
- `compile_ok`：warning 0件・error 0件・生成 asm あり・**v2.06 golden asm と byte 一致**
- `warning_only`：warning ≧1件・error 0件・生成 asm あり・**v2.06 golden asm と byte 一致**
  - **★v0.4 注記★：v2.06 時点では該当ケース 0 件**（案G により未定義 call は全て
    error 化されたため）。**分類は残す**（判断根拠は §3.4 相当・v2.06 設計メモ §3.4）。
    `run_c1_matrix.sh` は該当0件でも集計が成立すること（空分類を正常に扱えること）を確認する。
- `error_stop`：**非0終了 AND error メッセージに所定の文字列を含む**（AND 条件必須）

#### 2.2.1 `expect_error_contains` の確定（v0.4・v2.06 実測 V7 に基づく）

v2.06 の V7 検証で、案G／案D の error 出力件数を全 `proto=n` 12 ケースについて実測した：

| ケース種別 | 案G（`add a prototype declaration before use`） | 案D（`used in float context`） |
|---|---|---|
| 片側 float 定数/変数（`f_*_k_n` / `f_*_v_n`） | 1件 | 1件 |
| **両辺とも未定義 call**（`*_*_c_n`） | 2件 | **0件** |
| int 文脈のみ（`i_*_k_n` / `i_*_v_n`） | 1件 | 0件 |

**確定事項**：
- **主判定に使うのは案G のメッセージ**（`add a prototype declaration before use`）。
  **全 12 ケースに必ず出る**ため、一律指定して安全
- **案D のメッセージ（`used in float context`）は判定に使わない**。
  片側 float の 4 ケースにしか出ないため、**一律指定すると両辺未定義ケース
  （`*_*_c_n`）で AND 条件が成立せず FAIL する**（v2.06 設計メモ §4.7 の警告どおり）

**error_stop の AND 条件が必須である実源根拠（N-2）**：
実源照合（scc23_v2_05.c L4651-4656／v2.06 も同一）で確認：
```c
    if(error_count>0)
        fprintf(stderr,"scc23: %d error(s) in '%s'\n",error_count,src_name);
    ...
    return error_count?1:0;
```
`compile` 関数は **error が発生しても生成を最後まで継続**する。案G／案D の `error()` は
`error_count++` のみでその場では exit しない。結果、**壊れた asm（値破壊を含む部分出力）が
asm ファイルに残る**（実測：`m1_f_div_c_n` で `_cc_div` が残存）。ゆえに「非0終了」だけを
判定に使うと壊れた asm の残存を見逃す。error メッセージの内容チェックを併用する
AND 条件でこれを検出し、§2.6 の隔離運用で後続工程への流出を防ぐ。

### 2.3 実行値の算出（v0.2 M-1 反映：golden 差分を主判定に）

「戻り値型 × 演算 × 右辺種別」の生成 asm が期待通りか判定：

**主判定（compile_ok / warning_only ケース）**：
- **v2.06 で凍結した golden asm と byte 一致**することを判定（v0.1 の単純 grep から変更・M-1 反映）
- golden は実装フェーズで、**v2.06** に各テストソースを投入し出力 asm を凍結して作成
- Phase 2 以降で挙動が変わったら byte 差分で即検出

**主判定（error_stop ケース）**：
- **非0終了 AND error メッセージ「`add a prototype declaration before use`」を含む**の AND 条件（§2.2/§2.2.1・v2.06 V7 実測で確定）
- **加えて**、生成された asm があっても後続工程（hasm23）に渡さない運用（§2.6）

**補助判定（golden 未整備時のサニティチェック）**：
- v0.1 で主判定にしていた「生成 asm 中に `LDW B,#8 / SHL A,B` が含まれるか否か」は補助へ格下げ（M-1 反映）
- **理由（実源根拠）**：`SIR_I2F` の emit は `LDW B,#8 / SHL A,B`（scc23_v2_05.c §S6・L169）で、**明示キャスト `(float)i` や正当な int→float 昇格でも同一命令列が生成される**。単純 grep では「当該 call 戻り値ノードに対する誤挿入か」「正当な I2F か」を弁別できず false positive を招く
- ゆえに主判定は golden 差分とし、grep はあくまで初回 golden 生成時のサニティ補助（誤 I2F が正当箇所にしか無いことの目視確認）に留める

### 2.4 期待値ファイル形式（v0.2 M-2 反映：golden_version フィールド追加）

```
# m1_f_add_c_n.expected（v0.4: v2.06 基準）
expect_result=error_stop
expect_error_contains=add a prototype declaration before use
golden_version=v2.06
golden_asm=(該当ケースが error_stop のため golden 不要)
```

```
# m1_f_add_c_p.expected（プロトタイプあり float ケース）
expect_result=compile_ok
golden_version=v2.06
golden_asm=goldens/m1_f_add_c_p.golden.asm
```

★v0.4 注意★: `expect_error_contains` に `used in float context`（案D 由来）を
一律指定してはならない。両辺とも未定義 call のケースでは案D が発火せず 0 件のため、
AND 条件が成立せず FAIL する（§2.2.1・v2.06 V7 実測）。

**フィールド定義**：
- `expect_result`：`compile_ok` / `warning_only` / `error_stop` のいずれか
- `expect_error_contains`：error_stop ケースで必須。error メッセージに含まれるべき文字列（複数指定可・全て含む＝AND 条件）
- `golden_version`：**golden の基準版**（v0.4 で **v2.06** に更新）。Phase 2 以降で golden 更新時にも版を明示（M-2 反映）
- `golden_asm`：golden asm ファイル名（`goldens/` サブディレクトリに配置）。error_stop ケースは asm を後続に渡さない運用（§2.6）のため省略可


### 2.6 error_stop 時の運用ルール（v0.2 N-2 反映：新設）

**背景**：実源照合（§2.2）で確認したとおり、scc23 の `compile`（v2.05／v2.06 とも同一）は error 発生でも生成を最後まで継続し、壊れた asm（値破壊を含む部分出力）が出力される。ゆえに `error_stop` ケースで**生成された asm を後続工程（hasm23）に渡すと、壊れたバイナリが生成される事故が起こりうる**。

**運用ルール**：
1. `error_stop` ケースでは、テスト完了後に **生成 asm を削除** するか、**別ディレクトリ（例：`corrupt_asms/`）に隔離** する
2. `run_c1_matrix.sh` は error_stop 判定時に自動的に隔離処理を行う
3. リンク工程（hasm23 呼び出し）は `expect_result != error_stop` のケースのみ実施（本 C-1 では実施しないが、将来 CI 統合時のルールとする）
4. 壊れた asm が誤ってプロジェクトナレッジや outputs に流出しないよう、`.gitignore` 相当の除外を検討

**参照**：scc23 の error() 実装（L536-548・v2.05／v2.06 同一）／compile() の生成継続挙動（L4651-4656）。exit 化するかは Phase 2 以降の課題（現行の設計思想を尊重し本 C-1 では触らない）。

## 7. 将来課題（申し送り・KY41）

### 7.1 演算 4 種完全網羅

本 v0.3 は加算・除算の2種に削減（削減根拠は §1.4）。C-2 完了後、乗算・減算も追加し 48 通り完全網羅を検討。

### 7.2 Q8.8 数値検証

~~現状は「生成 asm に誤 I2F 挿入がないか」の**構造的検証**のみ。~~（v0.1 記述・v0.3 で訂正）

**現状（v0.2 以降の正）**：主判定は **golden asm との byte 一致による構造的検証**（§2.3・M-1 反映）。誤 I2F の grep は golden 未整備時のサニティ補助へ格下げ済み。

C-2 の Q8.8 ヘルパスクリプト整備後、**演算結果の数値一致検証**（Q8.8 期待値と emu23 実行結果の一致確認）を追加する。golden byte 一致は「生成コードが変わっていないこと」を保証するが、「生成コードが正しい値を計算すること」は保証しないため、両者は補完関係にある。

### 7.3 CI 統合

Makefile ターゲット化（例：`make c1-matrix`）で、コンパイラ本体改修時の回帰チェックに組み込む。Phase 2 着手前に整備が理想。

### 7.4 マトリクス範囲拡張

将来 Phase 2 で `T_BOOL` / `T_UINT` が実装されると、戻り値型が 4 種に増える。マトリクス設計はこの拡張を見越して命名規約に余地を残す（`m1_u_add_k_p.c` = uint 版等）。

### 7.5 golden 更新ルール（v0.3 新設・OBS-2 反映）★重要★

**背景（失敗モード）**：golden 方式には「**回帰時に安易に golden を上書きして回帰を握り潰す**」という典型的な失敗モードがある。本テストは Phase 2 型システム統合時の回帰検出網（§0.1）が目的であり、この失敗モードが発生すると本テストの存在意義そのものが失われる。

**更新ルール（厳守）**：

1. **原則：golden との差分は「回帰疑い」として調査する。** 差分が出た時点で自動的に golden を更新してはならない。
2. **調査手順**：
   - 差分箇所を特定（`diff goldens/X.golden.asm out/X.asm`）
   - 差分が生じた変更（コンパイラ改修）を特定
   - その変更が **意図した仕様変更か／意図しない回帰か** を判定
3. **golden 更新が許されるのは、仕様変更が正当と判断された場合のみ**。その際は以下を必須とする：
   - **変更理由の記録**（どの改修により、なぜ生成コードが変わったのか）
   - `golden_version` を新版へ刻み直す（例：`golden_version=v2.07`）
   - 更新した golden ファイルと変更理由を設計文書またはコミットログに残す
4. **無検討の上書きは禁止**。`run_c1_matrix.sh` に golden 自動更新機能（`--update-golden` 等）を実装する場合も、**既定では無効**とし、明示フラグ + 確認プロンプトを必須とする。
5. **Dhrystone 絶対ゲート（826/48405/P:20/21846B）との併走**：golden 差分が出た場合、Dhrystone 絶対ゲートも同時に確認する。絶対ゲートが破れていれば確実に回帰、維持されていれば仕様変更の可能性を検討する材料になる。

**責任分界**：golden 更新の判断は設計レビューを経ること（原則43）。テスト実行者が単独で golden を上書きしない。
