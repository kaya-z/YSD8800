## 1. 目的とスコープ

### 1.1 目的

emu23 は現在 CPI=1 固定（既定）または命令固有 CPI（`-mc`）で動作するが、
いずれも **理想メモリ前提**であり、PSRAM アクセス待ちを含まない。

本改良は **メモリアクセスのサイクル課金**と**物理アドレストレース出力**を追加し、
将来のキャッシュ RTL 開発（工程②）に必要な定量的基盤を整備する。

### 1.2 スコープ（H-2 決定）

| # | 項目 | 本改良 |
|---|---|---|
| 1 | メモリアクセスのサイクル課金モデル | ✅ **対象** |
| 2 | 物理アドレストレース出力 | ✅ **対象** |
| 3 | キャッシュシミュレータ本体 | ❌ 対象外（Python 後処理に分離＝H-1） |
| 4 | CCR（キャッシュ制御レジスタ）の MMIO モデル | ❌ 対象外（別段） |

### 1.3 非目標

- 実機性能の絶対予測（本モデルは相対評価＝キャッシュ効果の測定が目的）
- キャッシュ方式（容量・ライン長・連想度）の決定

## 3. ★課金モデル（本設計の中核）★

### 3.1 前提の確定：先行課題の検証結果（段0 / 段0'）

#### 3.1.1 RTL 版数差（段0）

`ysd8800_cycle_count_table_v1_0.md` の対象は CPU コア **v0.5.6**、現行 RTL は **v0.5.8**。
差分 2 件を実源確認した結果、**いずれも FSM 状態遷移に影響しない**。

| 版 | 変更内容 | 修正箇所 | 状態遷移への影響 |
|---|---|---|---|
| v0.5.7 | `S_SUBOP` に `mem_rd=1'b1` 追加 | L869（バス出力 `always_comb`） | **無し**（`next_state` は L684-686 で無変更） |
| v0.5.8 | `S_IRQCHK` ラッチ条件に `irq_pending==0` 追加 | L1263（`always_ff`） | **無し**（受理可否のみ変更） |

> **判定：CPI 差分なし。サイクル表 v1.0 は v0.5.8 に対しても有効。**
> 実効 CPI 7.21 は改良4 の分母として使用可能。

#### 3.1.2 PSRAM レイテンシ（段0'）★前提の重大な訂正★

`cache_study_handover_v1_0.md` §2 の **「約 60 CPU cyc/byte」は誤り**である。
同文書の換算表は `cpu_clk=100MHz : psram_clk=25MHz`（比 4:1）を前提としていたが、
**現行 TB は `cpu_clk=4MHz : psram_clk=32MHz`（比 1:8）に修正済**。

| 出典 | cpu_clk | psram_clk |
|---|---|---|
| `tb_cpu_v8b_prod` **v0.1**（旧・ハンドオーバーの出典） | 100MHz (#5) | 25MHz (#20) |
| **v0.2（現行・実源 L165/L174）** | **4MHz (#125)** | **32MHz (#15.625)** |

現行比で引き直した結果と、実測による裏取り：

| 検証 | 値 |
|---|---|
| 机上再計算 | **約 5〜6 CPU cyc/byte** |
| 実測逆算（下記） | **約 5.0 CPU cyc/byte** |

実測の根拠（`yuios_build_procedure_v1_14.md` v1.11 欄）：

| 測定 | cycles |
|---|---|
| emu23 `-mc`（理想メモリ） | 351,761 |
| RTL 実測（PSRAM 経由, `tb_cpu_v8d_char_fix_v0_1.sv`） | **1,317,401** |
| 差＝メモリ待ちの実費 | **965,640** |

比は **3.75 倍**（旧見積もりの 60 倍ではない）。

> ⚠ **改良4 への帰結**
> - `--mem-latency` の現実的な値は **5 前後**（60 ではない）
> - `psram_clk 25→81MHz で 3.2 倍` 改善案（ハンドオーバー §212）は**無意味化**。
>   現行は既に 32MHz であり、CPU が 4MHz なので律速は PSRAM 側にない
> - キャッシュの価値は消えないが、**旧見積もりより小さい**（3.75 倍分の削減余地）
> - `cache_study_handover_v1_0.md` は **v1.1 改版が必要**（§11 に起票）

### 3.2 ★二重計上の防止（本日の KY 本命）★

#### 3.2.1 サイクル表に含まれるメモリアクセス

`ysd8800_cycle_count_table_v1_0.md` の内訳欄を実源確認した結果、
**メモリアクセスは 1 バイトあたり 1 サイクル**として既に計上されている。

| FSM 状態 | 表での計上 | アクセスバイト数 |
|---|---|---|
| `FETCH` / `OPFETCH` | 各 1 | 各 1 |
| `IMML` / `IMMH` | 各 1 | 各 1 |
| `SUBOP` | 1 | 1 |
| `MEMR8` / `MEMW8` | 1 | 1 |
| `MEMR_LO/HI` / `MEMW_LO/HI` | **2** | **2** |
| `PUSH_LO/HI` / `POP_LO/HI` | **2** | **2** |
| `DECODE` / `EXEC_*` / `WRITEBACK` | 1 | **0**（メモリアクセス無し） |

根拠例（同表 L54, L62, L91）：

```
NOP           0x00  CPI=2  FETCH, OPFETCH
LDW rD,[imm16] 0x22 CPI=8  FETCH,OPFETCH,IMML,IMMH,DECODE,MEMR_LO/HI,WRITEBACK
LDB A,[imm16] 1F/10 CPI=7  FETCH,OPFETCH,SUBOP,DECODE,IMML,IMMH,MEMR8
```

#### 3.2.2 課金式（★取り違え厳禁★）

> **★ペナルティは「バイトごと」に (レイテンシ − 1) を加算する。★**
> **レイテンシそのものを加算してはならない。アクセス回数ごとでもない。**

```
ヒット時         : 追加課金 0                       （表の値がそのまま正しい）
ミス時（1バイト）: 追加課金 = (LAT - 1)
ミス時（2バイト）: 追加課金 = 2 × (LAT - 1)
```

この `−1` は `emu23_mc_design_v0_6.md` §3.1.1 の IRQ における `−1`
（表に既に含まれる分を差し引く）と**同一の構図**である。
Phase C でレビュー M-1 として同型の事故を起こしかけているため、
**§8 の検証項目で必ず手計算検算すること。**

#### 3.2.3 なぜ「アクセス回数ごと」ではないか

現行 RTL は **16bit アクセスをバイト 2 回に分割**している
（`cache_study_handover_v1_0.md` §3 / 本設計 §3.1.2）。
表側も `MEMR_LO/HI` で 2 サイクル計上している。
したがって **バイト単位で対応が取れており、アクセス単位では取れない。**

### 3.3 アクセス種別と課金パラメータ

`--mem-latency` は**アクセス種別ごと**に持つ（決定事項・粒度 (a)）。

| 種別 ID | 発生元 | バイト数 | 既定値 | 備考 |
|---|---|---|---|---|
| `LAT_FETCH` | `fetch8()` | 1 | **5** | 命令フェッチ |
| `LAT_RD8` | `rd8()` | 1 | **5** | データ読み 8bit |
| `LAT_WR8` | `wr8()` | 1 | **5** | データ書き 8bit |
| `LAT_RD16` | `rd16()` | 2 | **5**（/byte） | バイト 2 回に分割して課金 |
| `LAT_WR16` | `wr16()` | 2 | **5**（/byte） | 同上 |

**既定値 5 は暫定**であり、§9 の校正手順で実測から確定させる。

> ★注意★ `LAT_RD16` は「16bit アクセス全体のレイテンシ」ではなく
> **1 バイトあたりの値**である。総課金は `2 × (LAT_RD16 − 1)`。
> ここを「全体の値」と解釈すると 2 倍の誤差を生む。

### 3.4 レイヤの役割分担（`-mc` との関係）

```
実効サイクル = 命令実行の内部コスト（-mc デフォルト表 ＝ 理想メモリ＝全ヒット相当）
             + メモリ課金（本改良の新レイヤ ＝ ミス時のペナルティのみ）
```

| レイヤ | 担当 | 値の出所 |
|---|---|---|
| 命令内部 | `mc_step()`（既存・**無改造**） | サイクル表 v1.0 |
| メモリ課金 | **`mem_charge()`（新規）** | 実測校正した LAT 値 |

`--mem-latency` は **`-mc` と併用可**。ただし `-mc` 無しで併用した場合、
`-mc` 無しは CPI=1 固定であり表との対応が無いため、
**`--mem-latency` は `-mc` 指定時のみ有効**とし、単独指定時は警告して無効化する（§6.3）。

## 4. キャッシュモデル

### 4.1 構成（H-5）

| 項目 | 値 |
|---|---|
| 方式 | ダイレクトマップ |
| I/D | **統合（unified）** |
| 容量 | 16 KB（可変パラメータ） |
| ラインサイズ | 32 バイト（可変パラメータ） |
| 書き込み | ライトスルー / ノーライトアロケート |
| 配置 | **MMU 物理アドレスの後段** |

**配置理由**：物理アドレスでインデクスすることで、
コンテキストスイッチ時のフラッシュが不要になる（OS-9 の MMU 運用と同様の思想）。

### 4.2 統合とする理由（設計判断の記録）

1. CPU コアは**シングルイシューの多サイクル FSM** であり、
   命令フェッチとデータアクセスが同一サイクルに重なる構造が無い
   → 分離型（modified Harvard）の最大の利点である並行アクセスが機能しない
2. Tang Nano 9K（GW1NR-9）の BSRAM が有限であり、2 系統に割る利得が無い
3. YUI OS はプログラムローダを持つ＝実質的に自己書き換え相当の動作をする。
   分離型では I/D コヒーレンス制御（キャッシュ無効化命令）が必要になり、
   **ISA2.3 に無い命令の追加を要求してしまう**（プロジェクト規約に抵触）

> ※ アーキテクチャそのものは **von Neumann**（命令・データ同一アドレス空間）で不変。
>   本項はマイクロアーキテクチャ（キャッシュ段）の話である。

### 4.3 MMIO の扱い（H-4）

MMIO 領域は**キャッシュ対象外**とし、**課金もしない**。

実装は既存の `mmio_classify()` を流用する（実源 `rd8()` L1296 以降、`rd16()` L1050-1051）。
`rd16()` は既に**バイト粒度で 2 回分類**しているため、バイト単位課金と自然に整合する。

| 分類 | キャッシュ | 課金 |
|---|---|---|
| `MMIO_NOT_IN_SPACE`（＝通常メモリ） | 対象 | **する** |
| `MMIO_MAPPED` / `MMIO_MAPPED_UNSUPPORTED` / `MMIO_UNMAPPED` | 対象外 | **しない** |

## 5. 実装設計

### 5.1 フック位置（案 B）

課金関数は **1 本に集約**する（kaizen「内部状態変数の変更箇所を一か所に集約」）。

| 関数 | 実源行 | フック内容 |
|---|---|---|
| `fetch8()` | L256 | `mem_charge(pa, ACC_FETCH, 1)` |
| `rd8()` | L1296 | `mem_charge(pa, ACC_RD8, 1)`（MMIO 分岐後） |
| `wr8()` | L1400 | `mem_charge(pa, ACC_WR8, 1)` |
| `rd16()` | L1039 | `mem_charge()` を **2 回**（lo/hi 各バイト） |
| `wr16()` | L1141 | 同上 |

**★配置位置の注意★**（Phase C の KY 再発防止）
`mem_charge()` は `cpu` 構造体宣言より**後**に置くこと。
Phase C で関数を `cpu` 宣言より前に置きビルドエラーを起こしている。

### 5.2 新規関数

```c
/* アクセス種別 */
typedef enum {
    ACC_FETCH = 0, ACC_RD8, ACC_WR8, ACC_RD16, ACC_WR16
} acc_kind_t;

/* 課金＋トレース（1バイト単位で呼ぶ）
 *  pa   : MMU変換後の物理アドレス
 *  kind : アクセス種別
 *  戻り : 追加課金サイクル数（ヒット時0 / ミス時 LAT-1）
 * ★R1: cache_enable==0 なら何もせず即0を返す★ */
static unsigned mem_charge(uint32_t pa, acc_kind_t kind);
```

### 5.3 ★R1 死守（既定経路の非退行）★

Phase C の R1 と同一の構図。

> **`cache_enable == 0`（既定）なら `mem_charge()` はキャッシュ配列を参照せず即座に `0` を返す。**
> このとき emu23 の挙動は **v2.00 と完全に同一**でなければならない。

段ごとに G-1〜G-6 を確認する（§8.2）。

### 5.4 状態変数

| 変数 | 型 | 用途 |
|---|---|---|
| `cache_enable` | `int` | 課金の有効/無効（既定 0） |
| `cache_tag[]` | `uint32_t*` | タグ配列（動的確保） |
| `cache_valid[]` | `uint8_t*` | 有効ビット |
| `lat[5]` | `unsigned` | アクセス種別ごとのレイテンシ |
| `trace_fp` | `FILE*` | トレース出力先（NULL=無効） |
| `stat_hit` / `stat_miss` | `uint64_t` | 統計 |

## 6. オプション仕様（H-3）

### 6.1 `--mem-latency`

```
--mem-latency N              全種別を N に設定
--mem-latency FILE           種別ごとの定義ファイルを読む
```

定義ファイル書式（`-mc` の `.cyc` に倣う）：

```
# emu23 mem latency definition
FETCH  5
RD8    5
WR8    5
RD16   5
WR16   5
```

**引数消費は可変**（`-mc` と同じ EMU-A パターン）。
`-` で始まる次引数は消費しない（typo によるサイレント誤読の防止）。

### 6.2 `--trace-addr`

```
--trace-addr             stderr へ出力
--trace-addr FILE        FILE へ出力
```

出力書式（CSV・Python 後処理が読む一次データ）：

```
cyc,pa,kind,hit
1234,0x01A00,F,1
1240,0x0C120,R,0
```

| 列 | 意味 |
|---|---|
| `cyc` | 発生時点の `cpu.cycle` |
| `pa` | **MMU 変換後の物理アドレス** |
| `kind` | `F`=fetch / `R`=read / `W`=write |
| `hit` | 1=ヒット / 0=ミス |

> トレースは **1 バイトにつき 1 行**。Dhrystone 1 回で約 20 万行規模になるため、
> 既定は無効とし、明示指定時のみ出力する。

### 6.3 併用規則

| 指定 | 動作 |
|---|---|
| `-mc` のみ | 従来どおり（v2.00 相当） |
| `-mc` ＋ `--mem-latency` | **本改良の本命**。課金が加算される |
| `--mem-latency` のみ（`-mc` 無し） | **警告を出して課金を無効化**（§3.4 の理由） |
| `--trace-addr` のみ | 課金せずトレースのみ出力（キャッシュ判定は行う） |

## 8. 検証項目

### 8.1 ★手計算検算テスト（KY 防止策2）★

Phase C の C-03（`3N+4`）に倣い、**手で検算できる最小テスト**を置く。

**T-01：全ミス・単純ループ**

キャッシュ容量を 32 バイト（1 ライン）に設定し、
32 バイト離れた 2 アドレスを交互にアクセスして**必ずミスさせる**。

```
期待値 = (-mc のみの cycles) + (総アクセスバイト数) × (LAT - 1)
```

`LAT=5` なら 1 バイトあたり **+4**。
トレース出力の行数＝総アクセスバイト数と**一致すること**を同時に確認する。

**T-02：全ヒット**

ライン内に収まる連続アクセスのみを行い、
**追加課金が 0**（`-mc` のみの値と完全一致）であることを確認する。

**T-03：16bit アクセスの 2 バイト課金**

`LDW rD,[imm16]`（CPI=8, `MEMR_LO/HI`＝2 バイト）を全ミスさせ、
追加課金が **`2 × (LAT − 1)` であって `(LAT − 1)` ではない**ことを確認する。

> ★これが二重計上 KY の直接の検証項目である。★

**T-04：MMIO 非課金**

UART レジスタ（`$FC80` 系）へのアクセスで**課金が発生しない**ことを確認する。

## 9. ★レイテンシ値の実測校正手順★

既定値 5 は暫定である。以下で確定させる。

| # | 手順 |
|---|---|
| 1 | Dhrystone を `-mc --trace-addr` で走らせ、**総アクセスバイト数 B** を実測する（トレース行数） |
| 2 | RTL 実測との差分 **965,640 cycles**（＝1,317,401 − 351,761）を分子とする |
| 3 | `LAT − 1 = 965,640 ÷ B` から **LAT を逆算**する |
| 4 | 種別ごとの内訳が必要なら、トレースの `kind` 列で分類集計する |
| 5 | 確定値を定義ファイルの既定として本設計書 v1.0 に反映する |

> この手順は**全ミス条件での校正**である。RTL 側にキャッシュは無いため、
> 全アクセスが PSRAM に到達しており、前提として妥当。
