## 0. 本工程の目的と前提

### 0.1 目的

本体プロジェクトの決定（**案B：Cランタイムの共有化**）を受け、scc23 に
`--emit-runtime-only` と `--rt-shared` を実装し、Cプロセス区画の RUNTIME 768B を
CODE/DATA へ転用できる状態にする。

### 0.2 責任分界（申し送り §5・§6 のとおり。**本工程に YUI OS 回帰は含まれない**）

| ゲート | 内容 | 担当 |
|---|---|---|
| **G-D1** | Dhrystone 絶対ゲート（`--rt-shared` なし）がビット一致 | **本プロジェクト** |
| **G-D2** | 道2移行後の `dhry_final.bin` がビット一致 | **本プロジェクト** |
| **G-D3** | Dhrystone の生成コードに拡張ワークが現れない | **本プロジェクト** |
| G-RT1 | fib を `--rt-shared` でビルドし ProcMgr 経由で $D400 実行 | 本体 |
| G-RT2 | RT-JT 全スロットを1回以上通過 | 本体 |
| G-RT3 | `$3F00` マジック破壊で エラー終了 | 本体 |

`yuios.bin` への `SECTION rt` 追加は申し送り §4.4 のとおり**本体のビルド構成**であり、
本プロジェクトは `yuios.bin` に一切触れない。
代わりに **R3 で `rt23.obj`／`rt_jt.inc` の受入テスト**（§R3-4）を行い、
本体の手元で初めて破損が判明する事態を防ぐ。

| **★T3-1★** | **既存 12 変数（$DBE8-$DBFF）の番地は一切動かさない。** `#define C_XSAVE_ADDR 0xDBE8` はそのまま |
| T3-2 | 拡張分は**下側 $DBC0-$DBE7（40B）に新設** |
| T3-3 | 新設変数は **`--rt-shared` 時のみ参照**（X-4：申し送りの「または float 使用時」は既定モードで DATA $DA80-$DBE7 と重なりうるため採らない）。**Dhrystone の生成コードに現れないことを回帰で確認** |

> **理由**（申し送り §3.3）：`C_XSAVE` はユーザコード側の inc/dec 退避で使われ、
> `_C_MUL_A` 等は `EQU $%04X` で絶対番地として生成コードに埋め込まれる。
> `--data-org`/`--runtime-org` に連動しない。
> したがって **Dhrystone（ベアメタル）も $DBE8-$DBFF を使っており**、
> 番地を動かすと md5 が変わる。

### R4-3 Cプロセス区画の再配分（`--rt-shared` 時のみ）

| 領域 | 現行（v2.4） | 新（v2.5） | 差 |
|---|---|---|---|
| crt0 | $D400-$D43F（64B） | 不変 | — |
| CODE | $D440-$D77F（832B） | **$D440-$D9FF（1472B）** | +640B |
| RUNTIME | $D780-$DA7F（768B） | **廃止（共有化）** | −768B |
| DATA | $DA80-$DBE7（360B） | **$DA00-$DBBF（448B）** | +88B |
| ワーク（既存12変数） | $DBE8-$DBFF（24B） | **番地不変** | 0 |
| ワーク（拡張分） | — | **$DBC0-$DBE7（40B）** | +40B |

### R4-4 ゲート判定

| ゲート | 判定基準 |
|---|---|
| **G-D1** | `--rt-shared` を**付けない**ビルドで、本改修前後の出力が **md5 一致**。ゲート **818/48875/P:20/21846B**（X-1。申し送りの 819/48785 は v2.07 基準） |
| **G-D3** | Dhrystone の生成コードに **$DBC0-$DBE7 が現れない** |
| （参考） | C-1 マトリクス **24/24 PASS**（golden v1.2 基準） |

| 時期 | 出来事 |

#### 9.2.2 なぜ番号を再利用しないのか

案C を v2.12 に移した結果、v2.09 が空く。ここで **v2.10（T1）を v2.09 に繰り上げる**
選択もあり得たが、**採らない**。理由は2つある。

**(1) 版数と実施順序の一致を優先する**

繰り上げると、すでに設計書 v0.2〜v0.8 および本ロードマップ v1.0〜v1.1 に記録された
「v2.09：案C」「v2.10：T1」の対応が**版によって意味が変わる**ことになる。
どの文書のどの版を読んでいるかで v2.09 の指すものが違う状態は、
**`Makefile` v1.1／v1.3 の取り違え（設計書 v0.9 §0.5）と同種の混乱**を生む。

**(2) 欠番の害は「調べる手間」だけで、それは本節で解消できる**

欠番があると「v2.09 は何だったのか」を後から調べることになる——これが唯一の害である。
**本節と、`scc23_v2_10.c` のソースヘッダ（§9.2.3）に理由を書けば、その手間は発生しない。**
一方、番号を繰り上げた場合の害（過去文書との不整合）は、**文書を書き換えない限り消えない**。

⇒ **記録で解消できる害を選び、書き換えでしか解消できない害を避ける。**

#### 9.2.3 記載箇所（**両方に書くこと**）

|---|---|---|
| 1 | **本節（ロードマップ §9.2）** | 経緯・判断理由（本節） |
