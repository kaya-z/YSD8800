## 0. ゴールと前提

### 0.1 ゴール

前方未定義（プロトタイプ宣言も関数定義も先に出ていない）状態で **float 返し関数**
を呼び出すと、戻り値型が T_INT にフォールバックされ、`wrap_i2f` が誤って
int→Q8.8 昇格を挿入して結果を破壊する既知バグ（設計書§9・C-3）を解消する。

完成形を **scc23 v2.05** として確定する。

### 0.2 着手前の絶対条件（原則43）

本書は**設計フェーズの成果物**である。実装着手前に必ず: **レビュー → 指摘反映・承認
→ 工程確認 → KY → 「ご安全に！」→ 実装**。実装は KY38 に従い、本番
`scc23_v2_04.c` は直接改変せず、**新ファイル `scc23_v2_05.c`** として起こす。
**承認前の実装着手は厳禁。**

### 0.3 現在地（KY34・実ファイル確認済）

- scc23 v2.04 確定（`SCC_VERSION "2.04"`・L240）。CHAT121 で char ロード幅バグ修正
  V3 全PASS（4パターン初期値独立で cycles 完全一致 1,317,412）。
- Phase 0（P1 peephole）完了・Phase 1 未着手。
- 絶対ゲート：-O0-strict 826/48405/P:20/21846B（v2.04 で維持確認済）。

## 1. バグの確定内容（PoC 実証済）

### 1.1 症状

**PoC ケース**（本設計メモ起票時に実測）：

```c
/* case2_no_proto.c: プロトタイプ宣言なし・前方未定義 */
int main() {
    float x;
    x = getval() + 1.0;
    return 0;
}
float getval(void) { return 2.5; }
```

**scc23 v2.04 が生成するアセンブラ（該当箇所・実測）**：

```
    JSR  _getval          ; float 返し (A = Q8.8 で 2.5 = 0x0280)
    LDW  B, #8            ; ★ 誤挿入された wrap_i2f ★
    SHL  A, B             ; ★ A を 8bit 左シフト → 値破壊 ★
    ; 以下、既に Q8.8 の値を「int→Q8.8」として二重昇格した結果で加算
```

対して **プロトタイプ宣言ありのケース**（`float getval(void);` を前置）では、
上記 `LDW B,#8 / SHL A,B` の2命令が挿入されず、正しく Q8.8 加算コードが生成される
（本設計メモ起票時に diff で確認済）。

### 1.2 発現条件と影響範囲

| 条件 | 発現 |
|---|---|
| プロトタイプ宣言あり＋前方 float 関数呼び出し | 発現しない |
| **プロトタイプ宣言なし＋前方 float 関数呼び出し** | **発現** |
| プロトタイプ宣言なし＋前方 int 関数呼び出し | 発現しない（T_INT で正解） |
| 定義済み関数を後方から呼び出し（順序が正しい） | 発現しない |

**実害の顕在化条件**：
- Dhrystone（`dhry_all_ansi2.c`）は **float を使用しない**ため実害なし
  → 絶対ゲートには影響しない
- 現行の YUI OS カーネル／ユーザランドは **float を使用しない**ため実害なし
- Q8.8 float を使う将来のユーザランドコードで、プロトタイプなしで前方 float 関数を
  呼ぶと**確実に発現**する

### 1.3 バグの位置（1次ソース照合）

**`scc23_v2_04.c` L1868-1898**（`parse_primary` の関数呼び出し処理）：

```c
1868:         /* 関数呼び出し */
1869:         const char *peek=next_tok();
1870:         if (strcmp(peek,"(")==0) {
1871:             sir_node_t *cn=sir_new(SIR_CALL);
1872:             strncpy(cn->fname,name,IDENT_LEN-1);
1873:             /* [FIX 2026-06-25] 関数戻り値型を関数シンボルから引く。
1874:                旧: 無条件T_INT固定→float返し関数でwrap_i2fが二重I2F昇格しバグ。
1875:                未定義(前方宣言なし)の場合のみT_INTフォールバック。 */
1876:             {
1877:                 sym_t *cfs=sym_find(name);
1878:                 if (cfs && cfs->sclass==SC_FUNC) {
1879:                     cn->type = cfs->type;
1880:                     cn->base = cfs->base;
1881:                 } else {
1882:                     cn->type = T_INT; cn->base = T_INT;    ← C-3 の実害発生点
1883:                     cn->base = T_INT;
1884:                 }
1885:             }
```

現行ロジックは「シンボルテーブルに SC_FUNC 登録がなければ T_INT」であり、
プロトタイプ宣言を書けば SC_FUNC 登録され型伝播が正しく機能する。

**`scc23_v2_04.c` L4292-4374**（`parse_global` の関数宣言処理）で、**既に
プロトタイプ宣言のパース経路は存在する**（L4373-4374）：

```c
4373:         const char *body=next_tok();
4374:         if(strcmp(body,";")==0){sym_pop_locals();cur_func=NULL;return;}
```

`;` で終わればプロトタイプとして SC_FUNC 登録のみ行い本体をパースせずに戻る
処理は既に実装されている。ただし L4300 で `fs->defined=1` を先に立てているため
「宣言のみ」と「本体定義済」の区別がついていない（後述 §7 で申し送り）。

**結論**：C-3 の実害は「ユーザがプロトタイプ宣言を書き忘れる」ことが原因であり、
コンパイラ側の型伝播ロジックは既に正しい。真の課題は **ユーザに気づかせる手段** と
**ワークアラウンド運用の周知**である。

## 2. 修正案の比較

### 2.1 候補案

| 案 | 概要 | 本体改変 | 判定 |
|---|---|---|---|
| 案A | プロトタイプ運用ルール化のみ（コンパイラ非改変・ドキュメント整備） | なし | 保留（不十分） |
| 案B | 2パス化（1パス目で関数シンボル全収集、2パス目で式生成） | 大 | **却下（リスク過大）** |
| **案C** | **プロトタイプ宣言サポート状態を維持しつつ、未定義関数呼び出しに warning 出力（既存動作は不変）** | **軽微** | **★採用候補★** |

### 2.2 案B 却下の根拠

- 2パス化はパーサ本体構造の大規模改造となり、Dhrystone 絶対ゲート（826/48405/P:20/21846B・-O0-strict）
  破壊リスクが高い
- 現行の Small-C 系 1パス構造から離れ、将来の scc22 系プリプロセッサ移植（Phase 3）
  との整合性も悪化する
- **実害顕在化ケースは float 関数の前方未定義呼び出しに限られ、稀**であり、
  2パス化の労力に見合わない

### 2.3 案A の限界

- ドキュメントに「float 関数はプロトタイプ宣言必須」と書くだけでは、
  **書き忘れを検出できない** → C-1（マトリクステスト整備）で網は張れるが、
  ユーザ側コードでの検出が遅れる
- 「実害が出る前に対処すべき」という設計書§9の要求を満たさない

### 2.4 案C の詳細（採用候補）

**方針**：現行の型伝播ロジック（L1877-1884）は変更せず、**未定義関数呼び出し検出時に
警告を出力**する。警告により、ユーザは「プロトタイプ宣言を書けば型伝播が正しく機能する」
ことに気付ける。

**修正コード案**：

```c
1876:             {
1877:                 sym_t *cfs=sym_find(name);
1878:                 if (cfs && cfs->sclass==SC_FUNC) {
1879:                     cn->type = cfs->type;
1880:                     cn->base = cfs->base;
1881:                 } else {
1882:                     /* [v2.05 C-3] 未定義関数呼び出し警告。
1883:                        T_INT フォールバックは維持（後方互換・Dhrystone絶対ゲート保護）。
1884:                        float 返し関数の場合、プロトタイプ宣言なしだと wrap_i2f が
1885:                        誤挿入され値が壊れる（設計書§9 C-3）。ユーザに警告して
1886:                        プロトタイプ宣言の追加を促す。 */
1887:                     warn("call to undeclared function '%s': assumed to return int. "
1888:                          "add prototype declaration if returning float/pointer/char.", name);
1889:                     cn->type = T_INT; cn->base = T_INT;
1890:                 }
1891:             }
```

**変更点**：
- L1887-1888 の `warn(...)` 呼び出し1行追加のみ
- 既存の T_INT フォールバック動作は完全に維持（後方互換保証）
- Dhrystone は K&R スタイル（プロトタイプなし）でビルドされているため
  **大量の warning が出力される**が、絶対ゲート（byte-exact）には影響しない

### 2.5 warn() 関数の存在確認

`scc23_v2_04.c` に `warn()` 関数が既に定義されているかを実装前に確認する（§6 参照）。
存在しない場合は `fprintf(stderr, "warning: ...")` を直接記述する（既存の
`error()` 実装を参考）。

## 3. 安全性・副作用の解析

### 3.1 生成コードへの影響

- **プロトタイプ宣言あり**：既存動作と完全に同一（warning も出ない）
- **プロトタイプ宣言なし**：生成コードは既存動作と完全に同一（T_INT フォールバックのまま）
  ＋ stderr に warning 1行

**Dhrystone への影響**：
- `dhry_all_ansi2.c` はプロトタイプなしのため、warning が大量に出る（100件程度想定）
- ただし**生成コードは完全に不変** → byte-exact 絶対ゲート維持
- warning 抑止フラグ `-Wno-implicit-decl` 等の導入は本フェーズでは見送り
  （警告こそが目的であるため）

### 3.2 emu23 動作への影響

生成コードが不変のため、emu23 上の実行結果も不変。V1 検証で確認する。

### 3.3 コンパイル時間への影響

warn() 呼び出しは1件あたり数マイクロ秒。100件出ても数ミリ秒の増加に留まる。

### 3.4 stderr 出力量への影響

Dhrystone ビルド時に **100件程度の warning が出る想定** で、CI ログや
ビルドログが冗長化する副作用がある。

**対策**：
- ビルド手順書（`yuios_build_procedure_v1_11.docx`）の改版検討（§6 に列挙）
- 将来的にプロトタイプ付き Dhrystone（`dhry_all_ansi2_proto.c` 等）への
  移行を Phase 1 C-1 マトリクステスト整備時に検討（申し送り §7.1）

## 7. 将来課題（申し送り・KY41）

### 7.1 プロトタイプ付き Dhrystone への移行

- 現行 `dhry_all_ansi2.c` は K&R スタイル（プロトタイプなし）で、v2.05 では
  warning が大量出力される
- Phase 1 C-1 マトリクステスト整備時に、プロトタイプ付き版（`dhry_all_ansi2_proto.c`）
  の作成を検討
- ただし絶対ゲート（byte-exact）を維持するため、**現行 K&R 版と生成コードが同一**であることが前提

### 7.2 `defined` フラグの区別

- 現行 L4300 では、プロトタイプ宣言と関数本体定義の両方で `fs->defined=1` が立つ
- 「宣言のみ／本体済」の区別ができないため、将来的にプロトタイプなしの呼び出しに
  「未定義関数エラー」を出す等の厳格化は現状不可
- Phase 2（型システム統合）で `sym_t` 拡張を行う際に併せて検討

### 7.3 warning 抑止フラグ

- 将来 `-Wno-implicit-decl` 相当のコマンドラインオプション追加を検討
- 現時点では追加せず、警告こそが目的とする

### 7.4 案B（2パス化）の再検討余地

- 将来的にコンパイラを大規模改造する場面（例：本格レジスタ割付・Phase 5）で
  2パス化が別途必要になった場合、C-3 対応もそのタイミングで統合できる
- ただし本 Phase 1 では警告出力（案C）で十分
