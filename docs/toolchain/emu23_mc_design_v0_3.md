## 1. 目的と適用範囲

### 1.1 目的

emu23 は現在 **CPI=1 固定**であり、`cpu.cycle` は実質「実行命令数」である。
本改修により、オプション `-mc` 指定時に限り **命令ごとに固有サイクル数で歩進**させ、
RTL 実装（`ysd8800_cpu` v0.5.x）に近いサイクル挙動を扱えるようにする。

### 1.2 適用範囲外（本 Phase では扱わない）

- **メモリウェイト**（PSRAM 待ち）：要求 R6 により理想メモリ前提。対象外
- **キャッシュ挙動**：改良4（Phase C 後）
- **RTL 実測との自動突合**：D-6 の決定により第1段では行わない（§9.3）

## 3. 用語と前提（★KY：ここを取り違えると全体が狂う★）

### 3.1 `S_IRQCHK` の扱い（D-3 決定）

サイクル表 §1.3 は、**命令間で必ず通る `S_IRQCHK` の 1 サイクルを「命令固有 CPI」に含めていない**。
本設計では **emu23 側で毎命令 +1 する**方式を採る。

```
1命令あたりの歩進量 = mc_table[opcode]（表の命令固有CPI） + 1（S_IRQCHK）
```

**採用理由**：RTL の実クロック数と突合することが R5 の目的であり、
RTL では `S_IRQCHK` が実在の 1 サイクルを消費するため。

**★設計書明記事項★**：`mc_table[]` に格納する値は**表の値そのもの**であり、
`+1` は加算時に行う。外部定義ファイル（§6）に書く値も**表と同じ意味（IRQCHK 非込み）**とする。

### 3.1.1 ★IRQ だけ符号が逆である（レビュー M-1）★

**命令とは逆に、割込受理の表の値「9」は IRQCHK を含む。** 以下に並べて示す。

| 種別 | 表に書かれた値の意味 | 格納値 | 加算時の補正 |
|---|---|---|---|
| **命令** | IRQCHK **非込み** | 表の値そのまま | **＋1** |
| **割込受理** | IRQCHK **込み** | 表の値そのまま（9） | **−1** |

**この符号の非対称は事故要因である。** 実装時・ファイル記述時ともに必ず本表を参照すること。

**根拠**：
1. `ysd8800_cycle_count_table_v1_0.md` §割込関連の状態連鎖が
   `IRQCHK, IRQ_ACCEPT, PUSH_LO/HI×2, MEMR_LO/HI` と**先頭に IRQCHK を明記**している
2. `ysd8800_cpu_v0_1_FIXED.sv` L610-612 にて、受理シーケンスは `S_IRQCHK` を**入口として通過**する。
   命令間共通の IRQCHK と受理冒頭の IRQCHK は**同一の 1 サイクル**であり別物ではない

**★導出過程の記録（根拠の取り違え防止）★**
表の状態連鎖を素朴に数えると `1+1+4+2 = 8` であり、表の値 9 と 1 合わない。
表 §1.4 のとおり受理は**較正由来の実測値**であるから、採用すべきは 9 である。
実加算値 8 は「**実測値 9 から重複する IRQCHK 1 を引いた結果**」であって、
「状態数を数えて 8 にした」のではない。偶然一致しているだけである。

### 3.2 HALT の CPI（レビュー C-1 回答：**3 に改める**）

v0.2 では 2 としていたが、**3 に是正する**。

**根拠**：表 §2 の HALT 行の状態連鎖は `FETCH, OPFETCH, HALT` の **3 状態**である。
表の注記が言う「CPI=4 は **dbg_halt 到達検出コスト**を含む較正基準値」の意味は、
**除くべきが「検出コスト 1」（4−3=1）であって「S_HALT」ではない**と解する。
`S_HALT` は RTL 上で実在する 1 サイクルであり、命令コストとして計上するのが自然である。

> v0.2 の「2」は「括弧付きだから使わない」という消極的根拠に依っており、レビュー C-1 の指摘どおり弱かった。
> **状態連鎖という一次情報に基づき 3 を採る。**（旧案 2 は棄却。棄却記録として本項に残す）

影響：HALT は停止直前の 1 回しか実行されないため、最終 cycle 値が v0.2 案比 +1 となるのみ。

### 3.3 BRK（0x06）の扱い（レビュー M-4 回答：**案 a を採用し CPI=2**）

**実源確認結果（KY34）**：

| 対象 | 事実 |
|---|---|
| emu23 | `emu23_v1_14.c` L1706-1708 に `case 0x06: /* BRK */` が**実装済** |
| RTL デコーダ | `ysd8800_decoder_v0_1.sv` L29, L114 に `ID_BRK`（`8'h06`）が**定義されている** |
| RTL CPU FSM | `ysd8800_cpu_v0_1_FIXED.sv` に **`ID_BRK` の処理は存在しない**（grep で 0 件） |
| サイクル表 | BRK の行は**無い** |

**結論**：RTL では BRK はデコードされるが FSM で個別処理されず、
**`S_FETCH, S_OPFETCH` を経て次命令へ抜ける（NOP と同一経路）**。よって **CPI = 2** とする。

**選択理由**：案 b（emu23 固有の特例）を採らないのは、上記のとおり
**RTL デコーダに `ID_BRK` が実在し、RTL 実機にも存在する命令だから**である。
「RTL に無い命令」という案 b の前提が実源で否定された。

**★警告を出さないこと★**：BRK をデフォルト表に**明示的に載せる**ことで、
§4.3 の「未定義 opcode」警告が出ないようにする。BRK は意図的に踏むデバッグ命令であり、
警告が出るとデバッグ体験を損なう。

> ⚠ 派生の申し送り：RTL FSM が `ID_BRK` を未処理としている件は、
> **RTL 側にデバッグトラップ機能が無い**ことを意味する。本 Phase の対象外だが
> `emu23_kairyo.txt` への起票を推奨する（§13 参照）。

### 3.4 リセット 2 サイクルの扱い（レビュー C-2 回答：**計上しない**）

サイクル表 §割込関連に「リセット ｜ 2 ｜ RESET_LO, RESET_HI」があるが、
**`-mc` 時もリセットサイクルは計上しない**（`cpu.cycle` は 0 起点のまま）。

**理由**：emu23 の `cpu.cycle` 起点定義を変えると、`-mc` 無しの経路にも波及して
**G-4（`-q` stdout の byte-exact 一致）を壊す恐れ**がある。R1 死守を優先する。

### 3.5 表に無い命令

サイクル表は悉皆ではない。表に載っていない opcode に遭遇した場合の既定値を §4.3 に定める。

## 4. サイクル表のデータ構造

### 4.1 2 段表（★0x1F はプリフィックス★）

実源確認（`emu23_v1_14.c` L1521-1534）により、**`0x1F` は拡張プリフィックス**であり、
直後の 1 バイトがサブオペコードである。したがって単純な 256 エントリ表では引けない。

```c
#define MC_UNDEF 0xFFFF                 /* 未定義マーカ */
static uint16_t mc_table[256];          /* 主 opcode 用 */
static uint16_t mc_table_ext[256];      /* 0x1F サブオペ用 */
static uint16_t mc_irq_accept;          /* 割込受理コスト（既定 9・IRQCHK込み） */
static int      mc_enable = 0;          /* 0=CPI固定1（既定） 1=マシンサイクル */
```

### 4.2 引き方（★レビュー M-2 是正：`fetch8()` を使う★）

```c
uint16_t cpi;
if (cpu.ir == 0x1F)  cpi = mc_table_ext[ fetch8(cpu.pc) ];   /* ★MMU経路で peek★ */
else                 cpi = mc_table[cpu.ir];
```

**★`mem[cpu.pc]` 直読は不可★**（v0.2 案を棄却）。

**根拠**（レビュー M-2 / 実源）：

| 行 | 内容 |
|---|---|
| L234-235 | `static inline uint8_t fetch8(uint16_t a) { return phys_rd8(mmu_translate(a)); }` |
| L1714 | 実行部（`case 0x1F`）は `uint8_t sub = fetch8(cpu.pc++);` |

実行部は **MMU 変換を通した `fetch8`** でサブオペを読む。`mem[cpu.pc]` は論理アドレスで
物理配列を直接引くため、`--mmu` 有効時に**実行部と異なるバイトを読む**。
結果、**論理結果は正しいまま cycle だけ狂う**という発見困難なバグになる。

**実装上の注意**：`cpu.cycle` 加算は `fetch8(cpu.pc++)` の直後（L1665-1666）にあり、
この時点で `cpu.pc` はサブオペを指している。`fetch8()` は `pc` を進めないため peek として使える。
**`cpu.pc` を進めてはならない**（実行部が改めて読む）。

### 4.2.1 PC ラップ時のガード（レビュー C-5 回答：**ガードしない**）

`cpu.pc == 0xFFFF` で `0x1F` を実行した場合、`fetch8()` は `uint16_t` 引数ゆえ
ラップして `0x0000` を読む。**これを意図した挙動として許容し、境界ガードは設けない。**

**理由**：実行部 L1714 の `fetch8(cpu.pc++)` も**同一のラップ挙動**を示す。
peek 側にだけガードを入れると、**実行部と CPI 引きで異なるバイトを参照する**ことになり、
M-2 で排除したのと同型の不整合を自ら作り込むことになる。**実行部と経路・挙動を完全一致させる**ことを優先する。

> なお `instr_size()` L1522 のガードはディスアセンブラ用（実行しないアドレスも走査する）であり、
> 目的が異なる。同一視しないこと。

### 4.3 未定義 opcode の扱い

| 状況 | 動作 |
|---|---|
| `mc_table[op] == MC_UNDEF` | **既定値 4** を使用し、**初回のみ** stderr に警告を1行出す |
| 警告文言 | `emu23: [-mc] no cycle entry for opcode 0xNN, using default 4` |
| 拡張表の場合 | `emu23: [-mc] no cycle entry for ext opcode 0xNN, using default 4` |

**★警告カウントは主表・拡張表で別（レビュー C-4 回答）★**
opcode 空間が別であるため、共通 1 回にすると主表で 1 回出た後に拡張表の未定義が黙殺される。
`mc_warned_main` / `mc_warned_ext` の 2 変数で各 1 回とする。

**★禁止事項★**：警告文言に `Dhrystones/sec` / `cycles` / `P:` の文字列を含めてはならない
（HANDOVER §7.1：`2>&1` 合流後に grep するため誤検出する）。上記文言は本条件を満たす。

既定値 4 の根拠：表 §3 の CPI 分布で最頻はレジスタ ALU 系の 4（レビュー C-4 にて妥当と承認済）。

## 5. 歩進ロジックの変更

### 5.1 命令サイクル（★R1 死守の要★）

現行（L1665-1666）：

```c
cpu.ir = fetch8(cpu.pc++);
cpu.cycle++;
```

変更後：

```c
cpu.ir = fetch8(cpu.pc++);
cpu.cycle += mc_step();     /* mc_enable==0 のとき必ず 1 を返す */
```

`mc_step()` は `mc_enable==0` なら**表を一切参照せず即座に 1 を返す**。
これにより **既定動作は現行と完全に同一**であり、G-1〜G-5 は不変であるべきである。

### 5.2 割込受理（★レビュー M-1 是正：実加算は 8★）

L1655-1662 の IRQ 受理ブロック末尾（`cpu.pc = vec;` の後）に追加：

```c
/* 表の 9 は IRQCHK 込み。IRQCHK は §3.1 で毎命令 +1 済みゆえ二重計上を避ける */
if (mc_enable) cpu.cycle += (mc_irq_accept - 1);   /* 既定 9 → 実加算 8 */
```

根拠・導出過程は §3.1.1 に記載。**v0.2 の `+= mc_irq_accept`（9）は誤りとして棄却。**

### 5.3 タイマーへの影響（D-4）

`YSD8002` / `ysd8001` は `cpu.cycle` を基準に発火判定する（L948, L2027, L2052）。
`-mc` 時は `cpu.cycle` の意味が変わるため、**タイマー発火が実命令数ベースで早くなる**。

**これは仕様として正しい**。RTL 実機では 4MHz の実クロックでタイマーが動くため、
`-mc` の方がむしろ実機に近い。**追加の補正は行わない**。

### 5.3.1 C-10 が FAIL した場合の扱い（レビュー N-6 回答・事前決定）

タイマー周期が実効 2〜4 倍速くなるため、`-mc` 時に YUIOS シェルが破綻する可能性がある。
**FAIL した場合の方針をあらかじめ次のとおり定める。**

| 段階 | 対応 |
|---|---|
| 1 | **仕様として許容する**（`-mc` は実機に近い挙動であり、割込頻度増もまた実機の姿である） |
| 2 | ただし FAIL の**態様を記録**する（起動不能か／プロンプトは出るが応答が遅いか／ハングか） |
| 3 | **タイマー分周の補正は行わない**。補正は「emu23 を実機から遠ざける」方向であり R5 に反する |
| 4 | C-10 は**参考測定**と位置づけ、**Phase C の完了条件から外す**（G-5 は `-mc` 無しで担保済） |

**この事前決定により、C-10 FAIL 時の手戻りは生じない。**

## 6. サイクル定義ファイル形式（D-1 決定）

### 6.1 方針

`ysd8800_cycle_count_table_v1_0.md` は Markdown 表であり機械可読でない。
**Markdown をパースしない。** 独自の簡易テキスト形式を新規定義する。

### 6.2 書式

```
# emu23 machine-cycle definition file
# 形式: <キー> <CPI>
#   キー: 0xNN    … 主 opcode      値は IRQCHK 非込み（emu23 が実行時 +1 する）
#         X:0xNN  … 0x1F サブオペ  同上
#         IRQ     … 割込受理       ★値は IRQCHK 込み（emu23 が実行時 -1 する）★
#   ※ IRQ だけ補正の符号が逆である。設計書 §3.1.1 を参照のこと。
# 記載しなかったキーはデフォルト表の値を保持する（差分上書き）。
0x00 2
0x20 4
X:0x00 6
IRQ 9
```

**★書式ファイル自身のコメントに符号の非対称を明記する**（レビュー N-4 採用）。

- 数値は 10 進 / `0x` 付き 16 進の双方を受理
- **記載されなかった opcode はデフォルト表の値を保持する**（差分上書き方式）
- 同一キーが複数回現れた場合は**後勝ち**

### 6.3 差分上書きとする理由

全数記載を強制すると、1 命令だけ実験したいときに 40 行以上書く必要が生じる。
デフォルト表を土台に差分を当てる方が実用的である（改良4 のキャッシュ実験でも有用）。

### 6.4 エラー方針

| 事象 | 動作 |
|---|---|
| ファイルが開けない | stderr にエラー出力し **exit(1)**（明示指定の黙殺は EMU-A の教訓に反する） |
| 行が解釈不能 | stderr に行番号付き警告を出し、その行を無視して継続 |
| CPI が 0 または 1000 超 | 同上（範囲外として無視） |

**上限 1000 の根拠（レビュー N-2 回答）**：型は `uint16_t`（上限 65535）で、
`MC_UNDEF = 0xFFFF` と衝突させないことが必須条件である。技術的には 65534 まで許容できるが、
**理想メモリ前提の CPI が 3 桁を超えることは物理的にありえない**ため、
「明らかな誤記を弾く」実用的な閾値として 1000 を採る。型上限に張り付けると誤記が素通りする。

## 7. 引数解析（D-2 決定）★最重要リスク箇所★

### 7.1 問題の所在（実源確認済・実測で症状再現済）

`emu23_v1_14.c` L2422-2466 の EMU-A 前置パスは、**オプションごとに `extra` が固定値**である
（0 / 1 / 2 のいずれか）。`-mc` は**引数を取ることも取らないこともある初のオプション**である。

§9.1 の陰性対照により、**未対策では `cyc.txt` がサイレントにシンボルテーブルとして読まれる**ことを実測で確認済。

### 7.2 消費数決定表（★実装の唯一の参照★）

`-mc` に続く argv を `nxt = argv[i+1]` とする。

| 条件 | `extra` | `-mc` の値 |
|---|---:|---|
| `i+1 >= argc`（次が無い） | 0 | デフォルト表 |
| `nxt[0] == '-'`（オプション様） | 0 | デフォルト表 |
| 上記以外 | **1** | `nxt` をファイル名として採用 |

**`-` 始まりで判定する理由**：ファイルの存在チェック（`access()`）で判定すると、
**タイプミスしたファイル名が黙ってデフォルト動作に落ちる**（サイレント失敗＝EMU-A と同じ病）。
`-` 始まりでない以上はファイル名として扱い、開けなければ §6.4 により exit(1) とする。
（レビュー C-3 にて本方針は妥当と承認済）

> ⚠ **既知の制限**：`-` で始まるファイル名は指定できない。実用上問題ないと判断する。
> **設計書（本項）と `emu23_debug_manual` v1.6 の `-mc` の節の双方に明記する**（§11 参照）。

### 7.3 実装位置と usage 更新（★レビュー M-3 是正：確定形★）

1. L2425-2459 のオプション表に `-mc` を追加する。値の回収は `--dbg`/`--sym` と同じく
   **前置パス内で行う**（`mc_file_opt` に保存）。表読み込みは `load_bin()` の後、CPU 初期化の前。
2. **L2308 の usage 文字列に `-mc [file]` を追記する**（条件形ではなく確定事項）。

   ```c
   "usage: emu23 prog.bin [prog.dbg [prog.sym]] [options]\n"
   ```

3. **★usage も「例示≠全数」である★**（原則124）。実装時に **`grep -n "usage" emu23_v1_14.c` を実行し、
   usage 文字列が複数箇所に分かれていないか全数確認する**こと。L2308 は grep で見つかった 1 例に過ぎない。

**★横展開確認（原則122）★**：EMU-A のオプション表はコメント L2408-2410 で
「本表が実装の唯一の参照」と明記されている。`-mc` 追加時に本表と usage の**両方**を更新する。
