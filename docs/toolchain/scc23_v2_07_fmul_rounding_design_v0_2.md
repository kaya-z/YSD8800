## 1. バグの確定内容（実源照合＋検算で実証）

### 1.1 二つの実装で丸め方向が異なる

| 実装 | 場所 | 方式 | 丸め方向 |
|---|---|---|---|
| `fold_binop_val`（**コンパイル時**畳み込み） | `scc23_v2_06.c` L1145-1150 | `(int16_t)((int32_t)a*b >> 8)` | **floor**（算術右シフト） |
| `_fmul`（**実行時**ランタイム） | 生成 asm `_fmul:` 〜 `_fmul_ret:` | 絶対値で計算 → 符号を後付け | **ゼロ方向**（truncate） |

### 1.2 実源：`fold_binop_val`（コンパイル時・floor）

`scc23_v2_06.c` L1145-1150：

```c
        case SIR_FMUL: {
            int32_t tmp = (int32_t)a * b;
            if (tmp > (int32_t)0x7FFF00 || tmp < -(int32_t)0x800000)
                warning("float overflow in constant FMUL");
            return (int16_t)(tmp >> 8);       /* ← 算術右シフト = floor */
        }
```

gcc では負値の右シフトは算術シフトであり、`-625 >> 8 == -3`（floor）。

### 1.3 実源：`_fmul` ランタイム（実行時・ゼロ方向）

scc23 v2.06 が生成するアセンブラ（抜粋・実測）：

```
_fmul:
    PUSH X
    STW  A, [_C_MUL_A]
    STW  B, [_C_MUL_B]
    LDW  A, #0
    STW  A, [_C_DIV_A]        ; 符号フラグを 0 に初期化
    STW  A, [_C_MUL_R]
    LDW  A, [_C_MUL_A]
    CMPI A, #0
    BGE  _fmul_a_pos
    NOT  A
    ADDI A, #1                ; ★A を絶対値化（2の補数）★
    STW  A, [_C_MUL_A]
    LDW  A, [_C_DIV_A]
    XORI A, #1                ; ★符号フラグを反転★
    STW  A, [_C_DIV_A]
_fmul_a_pos:
    ... (B も同様に絶対値化・符号フラグ反転) ...
_fmul_b_pos:
    LDW  X, #0
_fmul_loop:                   ; ★非負同士でシフト加算積を計算★
    ...
_fmul_loop_end:
    LDW  A, [_C_DIV_A]
    CMPI A, #0
    BEQ  _fmul_ret
    LDW  A, [_C_MUL_R]
    NOT  A
    ADDI A, #1                ; ★符号フラグが立っていれば結果を反転★
    STW  A, [_C_MUL_R]
_fmul_ret:
    LDW  A, [_C_MUL_R]
    POP  X
    RET
```

**両オペランドを絶対値化して非負で計算し、最後に符号を付ける**方式。
非負域では floor と truncate は同一なので、**全体としてゼロ方向丸め**になる。

### 1.4 実測された不一致（検算）

★v0.2 E-1 反映：`to_fixed` 後の Q8.8 生値（a, b）と積 tmp を併記した★
（読者が独立検算する際、`to_fixed(0.3)` を 77 と誤る等の取り違えを防ぐため。
正しくは `0.3 × 256 = 76.8` → ゼロ方向切り捨てで **76**。）

| 式 | a (Q8.8) | b (Q8.8) | tmp = a×b | コンパイル時（fold・floor） | 実行時（`_fmul`・ゼロ方向） | 差 |
|---|---|---|---|---|---|---|
| `-0.1 * 0.1` | -25 | 25 | -625 | **-3** | **-2** | 1 |
| `-0.5 * 0.1` | -128 | 25 | -3200 | **-13** | **-12** | 1 |
| `-0.1 * 0.3` | -25 | 76 | -1900 | **-8** | **-7** | 1 |
| `-1.5 * 0.1` | -384 | 25 | -9600 | **-38** | **-37** | 1 |
| `-1.0 * 0.1` | -256 | 25 | -6400 | -25 | -25 | 一致（256 の倍数） |
| `-2.5 * 0.3` | -640 | 76 | -48640 | -190 | -190 | 一致（256 の倍数） |
| `0.1 * 0.1` | 25 | 25 | 625 | 2 | 2 | 一致（正値） |
| `2.5 * 4.0` | 640 | 1024 | 655360 | 2560 | 2560 | 一致（正値） |

**不一致の条件**：**積 `tmp` が負、かつ 256 の倍数でない**とき、
1 LSB（1/256 ≒ 0.0039）ずれる。積が 256 の倍数なら両者は一致する。

（この条件は C-2 の self-test グループC でケース選定に用いた条件と同一である。）

### 1.5 `_fdiv` は一致（不一致は FMUL のみ）

`_fdiv` も絶対値方式（`_C_DIV_B` を符号フラグとして使用、末尾で 2 の補数反転）だが、
`fold_binop_val` の FDIV も `(int32_t)(a<<8) / b` すなわち **C の整数除算＝ゼロ方向**
であるため、**両者は一致する**。

**したがって修正対象は FMUL のみ**である。

### 1.6 なぜ今まで顕在化しなかったか

1. 負値の float 乗算がプロジェクト内の実コードで使われていない
   （既存ソース全6本で float ランタイム参照 0 件・§3.1）
2. **負のリテラルを含む式は定数畳み込みされない**（C-2 設計メモ §1.6）。
   単項マイナスが `0 - x` として実行時展開されるため、負値の乗算は
   **常に実行時パス（`_fmul`）のみが使われていた**
3. C-2 で**丸め仕様の正本を確定させた**ことで、初めて両者を突き合わせられた

### 1.6.1 ★実測：不一致は「現に発現する」ことを確認（起草時追加実証）★

§1.6 で「負リテラルは畳み込まれないため未顕在」と述べたが、
**減算で負値を作れば畳み込み経路に入る**ことが実測で判明した。
すなわち**不一致は理論上の懸念ではなく、現に発現する**。

| 式 | 畳み込み | 生成される値 | 経路 |
|---|---|---|---|
| `0.1 * -0.1` | されない（`JSR _fmul` 1件） | **-2** | 実行時（ゼロ方向） |
| **`(0.0 - 0.1) * 0.1`** | **される（ランタイム呼出 0 件）** | **-3** | コンパイル時（floor） |
| **`0.1 * (0.0 - 0.1)`** | **される（ランタイム呼出 0 件）** | **-3** | コンパイル時（floor） |

**数学的に同一の値（-0.01）を計算する式が、書き方によって -3 と -2 に分かれる。**

単項マイナス `-0.1` は `0 - 0.1` として実行時展開されるため畳み込まれないが、
**明示的に `(0.0 - 0.1)` と書くと定数畳み込みが効く**ため、
`fold_binop_val` の floor 丸めが適用される。

この事実により、本件は「将来の最適化で顕在化しうる潜在バグ」ではなく
**「現行 v2.06 で既に発現しているバグ」**と位置づけを改める。
V1 検証はこの2式の結果一致をもって行う（§4.1 の代替検証は不要）。

### 1.7 なぜ今修正すべきか（時限爆弾性 → 現に発現）

現時点では「畳み込まれない」ことにより不整合が表面化していない。しかし：

- C-2 設計メモ §7.6 で**単項マイナスの定数畳み込み**を Phase 5 の最適化候補として
  申し送っている。これを実装すると、**同じ式が突然 -3 になる**
- 変数経由で負値が入る場合も実行時パスだが、将来の定数伝播最適化で
  畳み込まれる可能性がある
- すなわち**最適化を1つ入れた途端に計算結果が変わる**状態であり、
  「最適化が挙動を変えてはならない」という大原則に反する

**最適化の前提（意味論の一意性）が壊れている**ため、Phase 5 を待たず今直すべきである。

## 2. 修正案の比較

### 2.1 候補案

| 案 | 概要 | 改修範囲 | 生成コード影響 | 判定 |
|---|---|---|---|---|
| **案A** | **コンパイル時（`fold_binop_val`）をランタイムに合わせる**（floor → ゼロ方向） | **C 1行** | 定数畳み込み結果のみ（既存ソースは float 未使用ゆえ実質なし） | **★採用★** |
| 案B | ランタイム（`_fmul`）をコンパイル時に合わせる（ゼロ方向 → floor） | アセンブラ生成ロジック | `_fmul` の asm が変わる・コード量/サイクル増 | 却下 |
| 案C | 申し送りとして記録し Phase 2 以降で対応 | なし | なし | 却下 |

### 2.2 案A 採用の根拠

1. **実行時の挙動を正とするのが自然**
   実機で実際に動くのはランタイム側である。コンパイル時の定数畳み込みは
   「実行時と同じ結果を先に計算しておく」最適化に過ぎず、
   **最適化が挙動を変えてはならない**。したがって
   「コンパイル時を実行時に合わせる」のが原理的に正しい方向である。
2. **改修が最小**（C の1行 vs アセンブラ生成ロジックの改修）
3. **ゼロ方向は C の慣習と整合**（C の整数除算はゼロ方向。FDIV も既にゼロ方向）
4. **FMUL と FDIV の丸め方向が統一される**
   現状は FMUL=floor／FDIV=ゼロ方向という非対称だったが、
   修正後は**両方ゼロ方向**となり、仕様が単純化される
5. **絶対ゲートへの影響なし**（§3.1 実測）

### 2.3 案B 却下の根拠

- ランタイム `_fmul` を floor にするには、絶対値方式をやめて符号付きシフトにするか、
  負値時に補正（余りがあれば -1）を入れる必要がある
- **アセンブラのコード量と実行サイクルが増える**（4MHz の実機で不利）
- 生成 asm が変わるため、FPGA 検証済みバイナリとの差分が生じる
- 案A で同じ目的をより低コストで達成できる

### 2.4 案C 却下の根拠

- 「見えているバグは先に潰すこと。残したまま進行しないこと」に反する
- §1.7 のとおり**最適化を1つ入れると顕在化する時限爆弾**であり、
  Phase 5（最適化）着手前に解消しておくべき
- C-2 レビュー反映確認書 §5 も「C-2 で丸め仕様の正本が確定した今が好機」と推奨

### 2.5 案A の実装（`scc23_v2_06.c` L1145-1150）

**修正前**：

```c
        case SIR_FMUL: {
            int32_t tmp = (int32_t)a * b;
            if (tmp > (int32_t)0x7FFF00 || tmp < -(int32_t)0x800000)
                warning("float overflow in constant FMUL");
            return (int16_t)(tmp >> 8);
        }
```

**修正後（案）**：

```c
        case SIR_FMUL: {
            int32_t tmp = (int32_t)a * b;
            if (tmp > (int32_t)0x7FFF00 || tmp < -(int32_t)0x800000)
                warning("float overflow in constant FMUL");
            /* [v2.07] 丸め方向をランタイム _fmul に一致させる。
               旧: (int16_t)(tmp >> 8) は算術右シフト＝floor。
               ランタイム _fmul は両オペランドを絶対値化して非負で計算し
               最後に符号を付ける方式＝ゼロ方向丸め。両者は積が負かつ
               256 の倍数でないとき 1 LSB ずれていた（C-2 §7.5 調査で発覚）。
               コンパイル時畳み込みは「実行時と同じ結果を先に計算する」最適化で
               あり挙動を変えてはならないため、実行時側に合わせる。
               (設計書 scc23_v2_07_fmul_rounding_design_v0_x.md §2.5) */
            {
                int32_t mag = (tmp < 0) ? -tmp : tmp;   /* 絶対値 */
                int32_t q   = mag >> 8;                  /* 非負なので floor==trunc */
                return (int16_t)((tmp < 0) ? -q : q);
            }
        }
```

**設計上の注意**：
- `-tmp` は `tmp == INT32_MIN` のとき未定義動作になるが、
  `tmp = a * b` で `a`,`b` はいずれも int16 範囲（±32768）ゆえ
  `|tmp| <= 32768*32768 = 2^30` であり INT32_MIN には到達しない（安全）
- オーバーフロー warning の条件・位置は**変更しない**（既存挙動維持）

### 2.6 修正案の等価性検算（実施済）

修正案とランタイム `_fmul` のアルゴリズムを Python で再現し、
全ケースで一致することを確認した：

| 式 | 現行 fold | **修正案 fold** | `_fmul` ランタイム | 一致 |
|---|---|---|---|---|
| `-0.1 * 0.1` | -3 | **-2** | -2 | ✅ |
| `-0.5 * 0.1` | -13 | **-12** | -12 | ✅ |
| `-0.1 * 0.3` | -8 | **-7** | -7 | ✅ |
| `-1.5 * 0.1` | -38 | **-37** | -37 | ✅ |
| `-1.0 * 0.1` | -25 | -25 | -25 | ✅ |
| `-2.5 * 0.3` | -190 | -190 | -190 | ✅ |
| `0.1 * 0.1` | 2 | 2 | 2 | ✅ |
| `2.5 * 4.0` | 2560 | 2560 | 2560 | ✅ |
| `0.5 * 0.5` | 64 | 64 | 64 | ✅ |

### 3.1 既存ソースへの影響（実測・影響ゼロ）

scc23 v2.06 で各ソースをコンパイルし、生成 asm 中の float ランタイム参照を実測：

| ソース | `_fmul`/`_fdiv` 参照 | 案A 適用時の影響 |
|---|---|---|
| `dhry_all_ansi2.c`（**絶対ゲート対象**） | **0 件** | **なし** |
| `fib.c` | 0 件 | なし |
| `sd_sample.c` | 0 件 | なし |
| `v6_sdread_test_poc.c` | 0 件 | なし |
| `v8_catls_demo_poc.c` | 0 件 | なし |
| `dhry_timer.c` | 0 件 | なし |

**既存ソースは全て float 演算を使用していない**ため、案A の影響は原理的にゼロ。
V2 で byte-exact を実測確認する。

### 3.2 生成コードが変わる条件

**負の定数同士（または片方が負）の FMUL が定数畳み込みされる場合のみ**。

ただし C-2 §1.6 のとおり**負リテラルを含む式は畳み込まれない**ため、
実際に畳み込みで負値 FMUL が発生するのは：
- 定数伝播で負値が入る場合（現状 scc23 に定数伝播はない）
- 将来 §7.6 の単項マイナス畳み込みを実装した場合

**★§1.6.1 の実測により訂正★**：`(0.0 - 0.1) * 0.1` のように
**減算で負値を作れば畳み込み経路に入る**ことが判明した。
したがって「生成コードが変わるケースは存在しない」わけではなく、
**そのような式を含むソースをコンパイルすると生成コードが変わる**。

ただし §3.1 のとおり既存ソースは float 演算を一切使用していないため、
**既存ビルドへの影響は依然としてゼロ**である（V2/V4 で実測確認する）。

### 3.3 C-2 ヘルパ（`q88.py`）への波及★重要★

**`q88.py` は `fold_binop_val` を再現しているため、案A 適用後は
ヘルパ側も同じ修正が必要**である。

| 対象 | 修正内容 |
|---|---|
| `q88.py` の `q_mul()` | `arith_shr8(tmp)` → ゼロ方向（絶対値→符号後付け） |

### 7.1 C-2 self-test グループC の目的変更

案A により FMUL と FDIV の丸めが**ゼロ方向で統一**されるため、
C-2 self-test グループC の位置づけが「丸め**非対称**の検出」から

修正後の期待値：

| # | 式 | v2.06 期待 | **v2.07 期待** | 誤実装（floor）なら |
|---|---|---|---|---|
| C1 | `-1.0 / 3.0` | -85 | **-85（不変）** | -86 |
| C2 | `-0.1 * 0.1` | -3 | **-2（変更）** | -3 |
| C3 | `-0.5 * 0.1` | -13 | **-12（変更）** | -13 |
| C4 | `1.0 / 3.0` | 85 | 85（不変） | — |
| C5 | `0.1 * 0.1` | 2 | 2（不変） | — |

**検出力は維持される**（floor で誤実装すると C2/C3 が FAIL）。
グループ名を「ROUNDING ASYMMETRY detection」から
「ROUNDING DIRECTION detection」等へ改めることを推奨。

### 7.2 単項マイナスの定数畳み込み（Phase 5 候補）

C-2 設計メモ §7.6 の申し送り。本 v2.07 で丸めが統一されたため、
**単項マイナスを畳み込んでも結果が変わらなくなる**。
すなわち本修正は §7.6 の最適化を安全に実装できる前提を整えるものでもある。

### 7.3 `_fdiv` の丸めは一致済（対応不要）

§1.5 のとおり `_fdiv` と `fold_binop_val` の FDIV は両者ゼロ方向で一致。
本修正の対象外。

### 7.4 ★確認済・別件起票要★ `_cc_div` / `_cc_mod` に符号処理が無い（重大）

> **★v0.2 N-1 反映★**：v0.1 は本節を「`_cc_mul`/`_cc_div` も同様の突合を推奨
> （未確認）」としていたが、レビュー指摘 N-1 を受けて**実源照合とシミュレーションを実施**した
> 結果、**懸念は実在し、しかも FMUL の 1 LSB ずれより深刻**であることが判明した。
> 本節を「未確認・推奨」から「**確認済・別件として起票要**」へ格上げする。

#### 7.4.1 実源：`_cc_div` に絶対値化・符号フラグが無い

`_fmul`/`_fdiv` が持つ符号分離（`NOT`+`ADDI #1` による絶対値化、
符号フラグの XOR 管理、末尾での符号適用）が **`_cc_div` には一切無い**：

```
_cc_div:
    CMPI A, #0
    BEQ  _ccdiv_zero        ; 除数 0 のガードはある
    STW  A, [_C_DIV_A]      ; 除数
    STW  B, [_C_DIV_B]      ; 被除数（残り）
    LDW  A, #0
    STW  A, [_C_DIV_Q]
_ccdiv_loop:
    LDW  A, [_C_DIV_B]      ; 残り
    LDW  B, [_C_DIV_A]      ; 除数
    CMP  A, B
    BLT  _ccdiv_done        ; ★符号付き比較★
    SUB  A, B
    STW  A, [_C_DIV_B]
    LDW  A, [_C_DIV_Q]
    ADDI A, #1
    STW  A, [_C_DIV_Q]
    JMP  _ccdiv_loop
_ccdiv_done:
    LDW  A, [_C_DIV_Q]
    RET
```

単純な引き算ループであり、`BLT` が符号付き比較のため**負値で破綻する**。

#### 7.4.2 シミュレーション結果（実装をそのまま再現）

| 式 | C（`fold_binop_val` int 経路） | `_cc_div`（実行時） | 反復回数 | 症状 |
|---|---|---|---|---|
| `7 / 2` | 3 | 3 | 4 | 一致 |
| `100 / 7` | 14 | 14 | 15 | 一致 |
| **`-7 / 2`** | **-3** | **0** | 1 | 初回で `rem < divisor` が真→即終了。**誤値** |
| **`-100 / 7`** | **-14** | **0** | 1 | **誤値** |
| **`7 / -2`** | **-3** | **16381** | **16382** | `rem -= b` で残りが増加し続け、int16 ラップでようやく停止。**誤値＋大量サイクル消費** |
| **`-7 / -2`** | **3** | **0** | 1 | **誤値** |

**`7 / -2` は 16382 回ループする**。4MHz の実機では 1 回の除算に数十ミリ秒を要し、
実質的なハングに近い挙動となる（レビュー指摘の「無限ループの恐れ」は、
正確には「int16 ラップで停止するまで約 16000 回ループ」であった）。

#### 7.4.3 `_cc_mod` はさらに深刻（ゼロ除算ガードすら無い）

```
_cc_mod:
    STW  A, [_C_DIV_A]      ; ★ゼロ除算ガードが無い★
    STW  B, [_C_DIV_B]
_ccmod_loop:
    LDW  A, [_C_DIV_B]
    LDW  B, [_C_DIV_A]
    CMP  A, B
    BLT  _ccmod_done        ; ★符号付き比較★
    SUB  A, B
    STW  A, [_C_DIV_B]
    JMP  _ccmod_loop
_ccmod_done:
    LDW  A, [_C_DIV_B]
    RET
```

- **符号処理が無い**（`_cc_div` と同じ問題）
- **さらにゼロ除算ガードが無い**。`_cc_div` の `CMPI A,#0 / BEQ _ccdiv_zero` に
  相当する処理が `_cc_mod` には存在しない。
  ⇒ **`x % 0` は `rem -= 0` を繰り返す真の無限ループ**（実機ハング確定）

#### 7.4.4 `_cc_mul` は問題なし（確認済）

`_cc_mul` には符号処理が無いが、これは**問題ない**：

- 乗数を `SHR`（**論理**右シフト）で 1 ビットずつ落とし、0 になるまでループする方式
- 負の乗数でも論理シフトなので **16 回以内に必ず 0 になり停止**する
- 2 の補数の性質により、符号を意識せずシフト加算しても**積は正しく求まる**

したがって `_cc_mul` は対象外。

#### 7.4.5 別件起票の推奨（本 v2.07 のスコープ外）

**本件は v2.07（FMUL 丸め）のスコープ外**であり、本設計書に取り込まない
（**1変更1検証**の原則）。以下を別チケットとして起票することを推奨する：

| 項目 | 内容 |
|---|---|
| 対象 | `_cc_div` / `_cc_mod` の符号未対応（`_cc_mul` は対象外） |
| 重大度 | **高**（誤値返し＋実質ハング。`_cc_mod` のゼロ除算は真の無限ループ） |
| 修正方針（案） | `_fdiv` と同じ絶対値方式（絶対値化 → 符号フラグ XOR → 末尾で符号適用）を移植。`_cc_mod` にはゼロ除算ガードも追加 |
| 剰余の符号規則 | C99 では `a % b` の符号は **被除数 a と同じ**（`-7 % 2 == -1`）。`_fdiv` 方式の単純移植では符号規則が異なる可能性があるため要確認 |
| 優先度 | **Phase 2 を待たず起票**。C コードで `-x / y` は自然に書かれうるため実害リスクは FMUL より高い |
| 未顕在の理由 | 既存ソース（Dhrystone 等）で負値の int 除算・剰余が使われていないため |

**なお本 v2.07 と同時に修正してはならない**。1変更1検証の原則に従い、
v2.07（FMUL 丸め）を完了・検証してから別途着手する。

### 7.5 kaizen 原則追加候補

本件から得られる教訓：

> **同一の意味論を持つ処理が2箇所に実装されている場合（コンパイル時畳み込みと
> 実行時ランタイム等）、両者が一致することを明示的に検証する。
> 最適化は挙動を変えてはならない。**

C-2 で「丸め仕様の正本」を確定させたことが発見の契機であり、
**仕様の正本化がバグ発見につながった実例**でもある。
kaizen 原則119/120 の提案と併せて採否をご判断いただきたい。
