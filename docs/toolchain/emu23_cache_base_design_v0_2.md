## 1. 目的とスコープ

### 1.1 目的

emu23 は現在 CPI=1 固定（既定）または命令固有 CPI（`-mc`）で動作するが、
いずれも **理想メモリ前提**であり、PSRAM アクセス待ちを含まない。

本改良は **メモリアクセスのサイクル課金**と**物理アドレストレース出力**を追加し、
将来のキャッシュ RTL 開発（工程②）に必要な定量的基盤を整備する。

### 1.2 スコープ（H-2 決定）

| # | 項目 | 本改良 |
|---|---|---|
| 1 | メモリアクセスのサイクル課金モデル | ✅ **対象** |
| 2 | 物理アドレストレース出力 | ✅ **対象** |
| 3 | キャッシュシミュレータ本体 | ❌ 対象外（Python 後処理に分離＝H-1） |
| 4 | CCR（キャッシュ制御レジスタ）の MMIO モデル | ❌ 対象外（別段） |

### 1.3 非目標

- 実機性能の絶対予測（本モデルは相対評価＝キャッシュ効果の測定が目的）
- キャッシュ方式（容量・ライン長・連想度）の決定
  ※ ただし**その決定に用いるデータを産出する**のが本改良である。
    したがって**ラインサイズを評価できるモデルであることは必須要件**（M-1 の教訓）

## 3. ★課金モデル（本設計の中核）★

### 3.1 前提の確定：先行課題および実源調査の結果

#### 3.1.1 RTL 版数差（段0）

`ysd8800_cycle_count_table_v1_0.md` の対象は CPU コア **v0.5.6**、現行 RTL は **v0.5.8**。
差分 2 件を実源確認した結果、**いずれも FSM 状態遷移に影響しない**。

| 版 | 変更内容 | 修正箇所 | 状態遷移への影響 |
|---|---|---|---|
| v0.5.7 | `S_SUBOP` に `mem_rd=1'b1` 追加 | L869（バス出力 `always_comb`） | **無し**（`next_state` は L684-686 で無変更） |
| v0.5.8 | `S_IRQCHK` ラッチ条件に `irq_pending==0` 追加 | L1263（`always_ff`） | **無し**（受理可否のみ変更） |

> **判定：CPI 差分なし。サイクル表 v1.0 は v0.5.8 に対しても有効。**

#### 3.1.2 ★PSRAM レイテンシ（段0'）— 机上推定であることの明示（M-4 是正）★

`cache_study_handover_v1_0.md` §2 の **「約 60 CPU cyc/byte」は前提が誤っている**。
同文書の換算表は `cpu_clk=100MHz : psram_clk=25MHz`（比 4:1）を前提としていたが、
**現行 TB は `cpu_clk=4MHz : psram_clk=32MHz`（比 1:8）に修正済**。

| 出典 | cpu_clk | psram_clk |
|---|---|---|
| `tb_cpu_v8b_prod` **v0.1**（旧・ハンドオーバーの出典） | 100MHz (#5) | 25MHz (#20) |
| **v0.2（現行・実源 L38-40 / L166 / L174）** | **4MHz (#125)** | **32MHz (#15.625)** |

**★v0.1 の重大な誤り（自己申告）★**
v0.1 §3.1.2 は「実測逆算 約 5.0 CPU cyc/byte」と記したが、**これは実測ではない**。
実際には「1 命令あたり平均 4 バイト」という**筆者の仮定**を置いた推定であり、
総アクセスバイト数 B は測定していない。B は §9 手順 1（本改良の実装後）で初めて得られる。
**推定を実測と称することは KY34 に反する。**以後、本文書では**机上推定**と明記する。

#### 3.1.3 ★机上推定の計算過程（実源根拠付き・M-4 / C-1 是正）★

**実源：`ysd8800_psram_ctrl_v0_2.sv`**

| 項目 | 実源の値 | 行 |
|---|---|---|
| データ幅 | **8bit**（`wdata`/`rdata` とも `logic [7:0]`） | L53 / L57 |
| インタフェース | req/ack 4 相ハンドシェイク | L55-56 |
| FSM | `PS_IDLE` → `PS_BUSY` → `PS_WAIT_REQ_LOW` | L66 |
| **連続転送（バースト）モード** | **存在しない** | FSM に該当状態なし |
| `LATENCY_NORMAL` | **12** psram_clk | L43 |
| `LATENCY_REFRESH` | 15 psram_clk（発生率 0.05%） | L44-45 |

**実源：`ysd8800_cdc_bridge_v0_2.sv`**

| 要素 | 内容 | 行 |
|---|---|---|
| ack 2FF 同期 | psram→cpu。**CPU クロックドメイン** | L89 |
| req 2FF 同期 | cpu→psram。**PSRAM クロックドメイン** | L107-111 |
| req_hold ワンショット | CPU クロックドメイン | L15 記載 |

**換算（`cpu:psram = 1:8`）**

| 要素 | 生値 | ドメイン | CPU cyc 換算 |
|---|---|---|---|
| PSRAM アクセス本体 | 12 psram cyc | psram | 12 ÷ 8 = **1.50** |
| req 2FF 同期 | 2 psram cyc | psram | 2 ÷ 8 = **0.25** |
| ack 2FF 同期 | 2 cpu cyc | **cpu** | **2.00** |
| req_hold ワンショット | 1 cpu cyc | cpu | **1.00** |
| **計** | | | **約 4.75 CPU cyc/byte（机上推定）** |

> ★この 4.75 は**机上推定であり、設計判断の根拠に用いてはならない**。★
> 確定は §9 の校正手順（実装後）による。

**C-1 への回答：律速の所在（v0.1 の断定を撤回）**

v0.1 は「CPU が 4MHz なので律速は PSRAM 側にない」と断じたが、**これは誤りである**。
レビュー指摘のとおり、メモリ待ちは実行時間の **73%**（965,640 / 1,317,401）を占め、
**律速はメモリ側にある**。

ただし内訳を分解すると、支配項は次のとおりである。

| 分類 | CPU cyc | 比率 |
|---|---|---|
| PSRAM 本体＋req 同期（**psram_clk に依存**） | 1.75 | 37% |
| **CDC ack 同期＋req_hold（cpu_clk に依存・昇圧しても不変）** | **3.00** | **63%** |

したがって **psram_clk 昇圧の効果は限定的**である。
32→81MHz（約 2.5 倍）としても削減できるのは 1.75→0.7 程度で、
全体は 4.75→3.7、すなわち **約 1.28 倍**にとどまる（旧試算の 3.2 倍には遠く及ばない）。

> ⚠ **v0.1 の「無意味化」という断定も撤回する**。効果は皆無ではないが限定的である。

**より効果が大きいと推定される施策（工程②への申し送り）**

| 施策 | 見込み | 備考 |
|---|---|---|
| **PSRAM のバースト転送対応** | **大** | §3.5 参照。キャッシュ導入の前提条件になりうる |
| CDC の削減（cpu_clk / psram_clk の関係見直し） | 中 | 支配項 3.00 cyc の削減 |
| psram_clk 昇圧 | 小（約 1.28 倍） | 上記のとおり |

### 3.2 ★課金式（M-1 / M-2 是正・本設計の心臓部）★

#### 3.2.1 サイクル表に含まれるメモリアクセス

`ysd8800_cycle_count_table_v1_0.md` の内訳欄より、
**メモリアクセスは 1 バイトあたり 1 サイクル**として既に計上されている。

| FSM 状態 | 表での計上 | アクセスバイト数 |
|---|---|---|
| `FETCH` / `OPFETCH` | 各 1 | 各 1 |
| `IMML` / `IMMH` | 各 1 | 各 1 |
| `SUBOP` | 1 | 1 |
| `MEMR8` / `MEMW8` | 1 | 1 |
| `MEMR_LO/HI` / `MEMW_LO/HI` | **2** | **2** |
| `PUSH_LO/HI` / `POP_LO/HI` | **2** | **2** |
| `DECODE` / `EXEC_*` / `WRITEBACK` | 1 | **0** |

根拠例（同表 L54, L62, L91）：

```
NOP            0x00  CPI=2  FETCH, OPFETCH
LDW rD,[imm16] 0x22  CPI=8  FETCH,OPFETCH,IMML,IMMH,DECODE,MEMR_LO/HI,WRITEBACK
LDB A,[imm16]  1F/10 CPI=7  FETCH,OPFETCH,SUBOP,DECODE,IMML,IMMH,MEMR8
```

#### 3.2.2 ★課金式（4 分岐）★

> **★取り違え厳禁★**
> 課金は**バイト単位**で行い、末尾の `−1` は**表に既に含まれる 1 サイクルの相殺**である。
> **同時に、課金漏れ（過少課金）も等しく危険である**（M-1 の教訓）。

| 事象 | 追加課金 | 根拠 |
|---|---|---|
| **読みヒット** | **0** | PSRAM へ到達しない。表の値がそのまま正しい |
| **読みミス** | **(LINE_SIZE × LAT_FILL) − 1** | ライン全体を充填する（M-1） |
| **書きヒット** | **LAT_WR − 1** | ★ライトスルーゆえヒットでも PSRAM へ到達する★（M-2） |
| **書きミス** | **LAT_WR − 1** | ノーライトアロケートゆえライン充填は無い（M-2） |

**★実装者への注意（M-2 の再発防止）★**

> **ライトスルー／ノーライトアロケートでは、書き込みのヒット判定は課金額に影響しない。**
> 「書きもヒット判定して 0 にする」のは誤りである。
> ヒット判定は**タグ更新の要否**にのみ関係する（ヒット時はキャッシュ側も更新する）。

**クリティカルワードファースト：無しとする。**
ミスしたバイトを先に返す最適化は現行 RTL に存在しない（§3.5）。
したがってライン充填完了まで待つモデルとし、課金は上表のとおりミス時に一括計上する。

#### 3.2.3 なぜ「アクセス回数ごと」ではなく「バイトごと」か

現行 RTL は 16bit アクセスをバイト 2 回に分割し、表側も `MEMR_LO/HI` で 2 サイクル計上している。
**バイト単位でのみ対応が取れる。**

### 3.3 アクセス種別と課金パラメータ（C-3 対応）

| 種別 ID | 発生元 | 1 回あたりバイト数 | 既定値 | 備考 |
|---|---|---|---|---|
| `LAT_FETCH` | `fetch8()` | 1 | **5**（仮） | 命令フェッチ |
| `LAT_RD8` | `rd8()` | 1 | **5**（仮） | データ読み 8bit |
| `LAT_WR8` | `wr8()` | 1 | **5**（仮） | データ書き 8bit |
| `LAT_RD16` | `rd16()` | 2 | **5**（仮） | **1 バイトあたりの値** |
| `LAT_WR16` | `wr16()` | 2 | **5**（仮） | **1 バイトあたりの値** |
| **`LAT_FILL`** | ライン充填 | LINE_SIZE | **5**（仮） | **1 バイトあたりの値**（M-1 新設） |

> ★**既定値 5 は §9 で確定するまでの仮値であり、設計判断の根拠に用いてはならない**★（M-4）
> §3.1.3 の机上推定は 4.75 であるが、整数の仮値として 5 を置く。

**C-3 への回答：(a) を採用する。**
種別は分析用途のため分けるが、**既定では全種別同値**とする。
`RD8` と `RD16` に異なる値が設定された場合、**物理的にありえない条件**であるため
起動時に stderr へ警告を出す（実行は継続する。分析目的の意図的設定を許すため）。

`LAT_FETCH` を分けることには意味がある（命令フェッチは逐次アクセスであり、
将来バースト対応した際に効率が異なりうる）。

> **`LAT_FILL` は `LAT` と別パラメータとする**（レビュー M-1 の要求）。
> ただし**現行 RTL では両者は同値である**（§3.5）。
> 別パラメータとするのは、工程②でバースト対応した場合の評価を可能にするためである。

### 3.4 レイヤの役割分担（`-mc` との関係）

```
実効サイクル = 命令実行の内部コスト（-mc デフォルト表 ＝ 理想メモリ＝全ヒット相当）
             + メモリ課金（本改良の新レイヤ ＝ §3.2.2 の 4 分岐）
```

| レイヤ | 担当 | 値の出所 |
|---|---|---|
| 命令内部 | `mc_step()`（既存・**無改造**） | サイクル表 v1.0 |
| メモリ課金 | **`mem_charge()`（新規）** | §9 で校正した LAT 値 |

`--mem-latency` は **`-mc` 指定時のみ有効**。単独指定時は警告して無効化する（§6.6）。

### 3.5 ★現行 RTL はバースト非対応である（M-1 の重要な帰結）★

§3.1.3 の実源調査より、`ysd8800_psram_ctrl_v0_2.sv` は
**8bit 幅・req/ack 1 バイト 1 トランザクション**であり、**連続転送モードを持たない**。

> **したがって現行 RTL では `LAT_FILL = LAT` である。バースト償却は存在しない。**

レビュー M-1 は「PSRAM はバースト転送でコマンド発行オーバーヘッドが償却されるため
通常 `LAT_FILL < LAT`」と述べているが、**現行 RTL には当てはまらない**。

**帰結（工程②への最重要の申し送り）**

32 バイトラインの充填コストは `32 × 4.75 ≈ 152 CPU cyc` に達する。
**ライン充填コストがキャッシュの利得を食い潰す可能性がある。**

| ライン | 充填コスト（机上推定） | 損益分岐に必要なヒット率（概算） |
|---|---|---|
| 8 B | 約 38 cyc | 低い |
| 32 B | 約 152 cyc | 高い |
| 128 B | 約 608 cyc | 極めて高い |

> ⚠ **「キャッシュ RTL 開発（工程②）」より先に「PSRAM バースト対応」を検討すべき**
> という結論すらあり得る。**この判定こそが本改良のトレース解析の主目的**である。
> §1.3 の非目標（方式の決定）には触れないが、**判定材料は本改良が産出する**。

## 4. キャッシュモデル

### 4.1 構成（H-5）

| 項目 | 値 |
|---|---|
| 方式 | ダイレクトマップ |
| I/D | **統合（unified）** |
| 容量 | 16 KB（`--cache-size` で可変） |
| ラインサイズ | 32 バイト（`--cache-line` で可変） |
| 書き込み | **ライトスルー / ノーライトアロケート** |
| **ライトバッファ** | **無しを仮定する**（M-2） |
| クリティカルワードファースト | **無し**（§3.2.2） |
| 配置 | **MMU 物理アドレスの後段** |

> ★**ライトバッファ無しの仮定について**★
> ライトバッファがあれば書き込みは非ブロッキングとなり課金は 0 に近づく。
> 現行 RTL に存在しないため**無しを仮定**する。
> 工程②で採用する場合は**別途モデル化が必要**であり、本設計の課金式は使えない。

**配置理由**：物理アドレスでインデクスすることで、
コンテキストスイッチ時のフラッシュが不要になる（OS-9 の MMU 運用と同様の思想）。

### 4.2 統合とする理由（設計判断の記録）

1. CPU コアは**シングルイシューの多サイクル FSM** であり、
   命令フェッチとデータアクセスが同一サイクルに重なる構造が無い
   → 分離型（modified Harvard）の最大の利点である並行アクセスが機能しない
2. Tang Nano 9K（GW1NR-9）の BSRAM が有限であり、2 系統に割る利得が無い
3. YUI OS はプログラムローダを持つ＝実質的に自己書き換え相当の動作をする。
   分離型では I/D コヒーレンス制御（キャッシュ無効化命令）が必要になり、
   **ISA2.3 に無い命令の追加を要求してしまう**（プロジェクト規約に抵触）

> ※ アーキテクチャそのものは **von Neumann**（命令・データ同一アドレス空間）で不変。
>   本項はマイクロアーキテクチャ（キャッシュ段）の話である。

### 4.3 MMIO の扱い（H-4）

MMIO 領域は**キャッシュ対象外**とし、**課金もしない**。
実装は既存の `mmio_classify()` を流用する。

| 分類 | キャッシュ | 課金 |
|---|---|---|
| `MMIO_NOT_IN_SPACE`（＝通常メモリ） | 対象 | **する** |
| `MMIO_MAPPED` / `MMIO_MAPPED_UNSUPPORTED` / `MMIO_UNMAPPED` | 対象外 | **しない** |

## 5. 実装設計

### 5.1 フック位置（案 B・E-1 是正＝**MMIO 分岐行に統一**）

課金関数は **1 本に集約**する（kaizen「内部状態変数の変更箇所を一か所に集約」）。

| 関数 | **分岐行（フック挿入の基準）** | フック内容 |
|---|---|---|
| `fetch8()` | **L256**（MMIO 分岐なし。関数本体） | `mem_charge(pa, ACC_FETCH)` |
| `rd8()` | **L1300**（`mmio_classify` 分岐） | 分岐後に `mem_charge(pa, ACC_RD8)` |
| `wr8()` | **L1402**（同上） | 分岐後に `mem_charge(pa, ACC_WR8)` |
| `rd16()` | **L1050-1051**（バイト粒度 2 回分類） | 各バイトで `mem_charge()` を**計 2 回** |
| `wr16()` | **L1149-1150**（同上） | 同上 |

> ★フックは **MMIO 分岐の後**に置くこと★（§4.3。分岐前に置くと MMIO も課金される）

**★配置位置の注意★**（Phase C の KY 再発防止）
`mem_charge()` は `cpu` 構造体宣言より**後**に置くこと。
Phase C で関数を `cpu` 宣言より前に置きビルドエラーを起こしている。

### 5.2 新規関数

```c
/* アクセス種別 */
typedef enum {
    ACC_FETCH = 0, ACC_RD8, ACC_WR8, ACC_RD16, ACC_WR16
} acc_kind_t;

/* 課金＋トレース（1バイト単位で呼ぶ）
 *  pa   : MMU変換後の物理アドレス
 *  kind : アクセス種別
 *  戻り : 追加課金サイクル数（§3.2.2 の 4 分岐）
 * ★R1: cache_enable==0 なら何もせず即0を返す★
 * ★書きは write-through ゆえヒットでも課金する（設計書 §3.2.2）★ */
static unsigned mem_charge(uint32_t pa, acc_kind_t kind);
```

### 5.3 ★R1 死守（既定経路の非退行）★

> **`cache_enable == 0`（既定）なら `mem_charge()` はキャッシュ配列を参照せず即座に `0` を返す。**
> このとき emu23 の挙動は **v2.00 と完全に同一**でなければならない。

段ごとに G-1〜G-6 を確認する（§8.2）。

### 5.4 状態変数

| 変数 | 型 | 用途 |
|---|---|---|
| `cache_enable` | `int` | 課金の有効/無効（既定 0） |
| `cache_size` / `cache_line` | `unsigned` | 容量・ラインサイズ（既定 16384 / 32） |
| `cache_tag[]` | `uint32_t*` | タグ配列（動的確保） |
| `cache_valid[]` | `uint8_t*` | 有効ビット |
| `lat[6]` | `unsigned` | 種別ごとのレイテンシ（`LAT_FILL` 含む） |
| `trace_fp` | `FILE*` | トレース出力先（NULL=無効） |
| `stat_hit` / `stat_miss` / `stat_charged` | `uint64_t` | 統計 |

> **N-3 不採用の理由**：`valid` を tag 最上位ビットに畳む案は、
> 20 万アクセス規模では実用差が小さく、**可読性とデバッグ容易性を優先**する。

## 6. オプション仕様

### 6.1 `--mem-latency`

```
--mem-latency N              全種別を N に設定
--mem-latency FILE           種別ごとの定義ファイルを読む
```

定義ファイル書式（`-mc` の `.cyc` に倣う）：

```
# emu23 mem latency definition
FETCH  5
RD8    5
WR8    5
RD16   5
WR16   5
FILL   5
```

**引数消費は可変**（`-mc` と同じ EMU-A パターン）。
`-` で始まる次引数は消費しない（typo によるサイレント誤読の防止）。
未知のキーは**エラーとして `exit(1)`**（サイレント破棄の禁止＝Phase C M-5 の教訓）。

### 6.2 `--trace-addr`（C-2 対応）

```
--trace-addr             stderr へ出力
--trace-addr FILE        FILE へ出力
```

**★出力の先頭に必ずヘッダ行を出す★**（C-2）

```
# emu23 v2.10 trace / mc=1 lat=F5,R5,W5,FILL5 cache=16384/32 unified wt-nwa nowb
cyc,pa,kind,hit
1234,0x01A00,F,1
1240,0x0C120,R,0
```

| 列 | 意味 |
|---|---|
| `cyc` | 発生時点の `cpu.cycle`。**`-mc` 無しでは実行命令数を意味する**（単位が異なる） |
| `pa` | **MMU 変換後の物理アドレス** |
| `kind` | `F`=fetch / `R`=read / `W`=write |
| `hit` | 1=ヒット / 0=ミス |

> ヘッダ行により、Python 後処理（H-1）が**前提の取り違えを検出できる**。
> これは H-1 の二段構えを安全に回すための前提条件である。

### 6.3 `--cache-stats`（N-1 採用）

トレースを出力せず、ヒット/ミスの計数のみ行う集計モード。
ラインサイズ掃引時に同一実行を繰り返すため、6MB 規模のトレース出力を回避する。

### 6.4 `--cache-size` / `--cache-line`（M-3 是正）

```
--cache-size N        キャッシュ総容量（バイト。既定 16384）
--cache-line N        ラインサイズ（バイト。既定 32）
```

**検査規則（サイレント丸めの禁止）**

| 条件 | 動作 |
|---|---|
| 2 の冪でない | stderr へエラー出力し **`exit(1)`** |
| `cache_size < cache_line` | stderr へエラー出力し **`exit(1)`** |
| いずれも 0 以下 | 同上 |

> ダイレクトマップのインデックス計算はマスク演算のため、非 2 冪は不正である。
> `--mem-latency` が「typo によるサイレント誤読の防止」を掲げている以上、
> **黙って丸めてはならない。**

**`cache_enable` との関係（M-3-3）**

> `--cache-size` / `--cache-line` は **`cache_enable` を立てない**（構成の指定のみ）。
> `cache_enable` を立てるのは **`--mem-latency` / `--trace-addr` / `--cache-stats`** のいずれか。
> サイズだけ指定した場合は**構成が変わるだけで課金もトレースも起きず、
> 挙動は v2.00 と完全に同一**である（R1 死守）。

### 6.5 統計出力（C-4 是正）

**終了時に stderr へ 1 行サマリを出力する。**

```
[CACHE] hit=123456 miss=7890 rate=93.98% charged=31560
```

> ★**警告文言規約（Phase C §4.3 で確立）を遵守すること**★
> Makefile が `2>&1` 合流後に grep するため、
> **`Dhrystones/sec` / `cycles` / `P:` の語を含めてはならない。**
> 上記例が `charged`（`cycles` ではない）としているのはこのためである。
>
> v0.1 は本規約に一切言及しておらず**横展開漏れ（原則122）**であった。

出力は `cache_enable != 0` のときのみ。既定では出力しない（R1 死守）。

### 6.6 併用規則

| 指定 | 動作 |
|---|---|
| `-mc` のみ | 従来どおり（v2.00 相当） |
| `-mc` ＋ `--mem-latency` | **本改良の本命**。課金が加算される |
| `--mem-latency` のみ（`-mc` 無し） | **警告を出して課金を無効化**（§3.4 の理由） |
| `--trace-addr` のみ | 課金せずトレースのみ出力（キャッシュ判定は行う。ヘッダに `mc=0` を記録） |
| `--cache-size` / `--cache-line` のみ | **何も起きない**（§6.4） |

## 8. 検証項目

### 8.1 ★手計算検算テスト（4 分岐すべてを網羅）★

Phase C の C-03（`3N+4`）に倣い、**手で検算できる最小テスト**を置く。

| ID | 対象分岐 | 内容 | 期待値 |
|---|---|---|---|
| **T-01** | **読みミス** | 容量 32B（1 ライン）・ライン 32B とし、32B 離れた 2 アドレスを交互に読む | `(-mc のみ) + N × ((32 × LAT_FILL) − 1)` |
| **T-02** | **読みヒット** | ライン内に収まる連続読みのみ | **追加課金 0**（`-mc` のみと完全一致） |
| **T-03** | **16bit の 2 バイト課金** | `LDW rD,[imm16]` を全ヒットさせ、`STW` で書く | 読み 0／書きは **2 × (LAT_WR − 1)** |
| **T-04** | **MMIO 非課金** | UART レジスタ（`$FC80` 系）へアクセス | **追加課金 0** |
| **T-05** | **ラインサイズ掃引**（M-1） | ライン 32B と 64B で同一プログラムを実行 | **ヒット率上昇による削減**と**充填コスト増**が**両方動く**こと |
| **T-06** | **書きヒット**（M-2） | ライン内に収まる同一アドレスへ連続書き込み | **追加課金 = N × (LAT_WR − 1)**。★0 ではない★ |

> **T-01 の意図（N-2）**：容量 32B＝1 ラインの構成では**全アドレスが同一インデックスに落ちる**ため、
> 異なるタグのアドレスを交互にアクセスすれば必ず衝突ミスとなる。
> ライン数を増やした構成ではこの前提が崩れるため、テスト改変時は注意すること。

> **T-05 / T-06 は本レビューで新設**された。
> v0.1 の T-01〜T-04 は**読み系に偏っており**、書きヒットのテストが存在しなかった。
> これが M-2（書きヒット課金漏れ）が発見されにくかった原因である。

## 9. ★レイテンシ値の実測校正手順（順序依存を明記・M-4）★

> ★**手順 1 の B が得られるまで、LAT の確定値は存在しない。**★
> §3.3 の既定値 5 および §3.1.3 の机上推定 4.75 は**いずれも仮値**であり、
> **他文書の改版や設計判断を駆動してはならない。**

| # | 手順 |
|---|---|
| 1 | Dhrystone を `-mc --trace-addr` で走らせ、**総アクセスバイト数 B** を実測する（トレース行数−ヘッダ行） |
| 2 | RTL 実測との差分 **965,640 cycles**（＝1,317,401 − 351,761）を分子とする |
| 3 | `LAT − 1 = 965,640 ÷ B` から **LAT を逆算**する |
| 4 | 種別ごとの内訳は、トレースの `kind` 列で分類集計して求める |
| 5 | 机上推定 4.75 と実測値の乖離を評価する。**乖離が大きい場合はモデルの誤りを疑う**（KY54 の精神） |
| 6 | 確定値を定義ファイルの既定として本設計書 v1.0 に反映する |

> この手順は**全ミス条件での校正**である。RTL 側にキャッシュは無いため、
> 全アクセスが PSRAM に到達しており、前提として妥当。
>
> ★ただし手順 3 は `LAT_FILL` を分離できない★（RTL にキャッシュが無くライン充填が存在しないため）。
> `LAT_FILL` は §3.5 のとおり**現行 RTL では `LAT` と同値**として扱い、
> バースト対応後の値は工程②で別途取得する。
