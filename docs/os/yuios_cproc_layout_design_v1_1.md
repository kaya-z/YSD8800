## 1. 目的とスコープ

### 1.1 目的
ProcMgr が固定ロード領域 `$C000-$C7FF`（PROC-LOAD-ADDR=$C000・PROC-MAX-SIZE=$0800＝2KB）へ
読み込む C プロセスバイナリの内部レイアウト（crt0 / CODE / RUNTIME / DATA の4領域配置）を
正式定義する。本設計は scc23 のベースアドレス引数化と memmap v2.0 のCプロセス領域定義の
共通入力となる。

### 1.2 スコープ（Phase1）
- **対象**：2KB以内に収まる小規模 C プロセス（fib 等の検証用・将来の小ユーティリティ）。
- **対象外**：Dhrystone（〜21KB）等の大規模プロセス。これは案B方針により Phase2（MMU統合・
  Ph.8）へ送る。本設計では扱わない。
- **非PIC前提**：scc23 出力は非PIC（DATA領域を絶対アドレス `#$XXXX+offset` で参照）。
  Phase1 はロードアドレス固定（$C000）のため非PICで成立する。PIC化は本設計のスコープ外。

### 1.3 案B採択の根拠（容量方針）
1. YSD8800 は16ビットCPU（64KB空間）。現行レイアウトは辞書 $5100-$EFFF（約40KB）等で
   上位を消費済みで、21KB連続領域を辞書を大幅圧縮せずに確保できない（物理制約）。
2. 大規模プロセスはバンク切替/ページングで空間拡張するのが正攻法であり、Ph.8 MMU の
   守備範囲（MC6809 に対する 6829 MMU / OS-9 Level Two DAT と同系譜）。Phase1で作り込むと
   MMU導入時に二重設計・手戻りになる。
3. Phase1の目的は「Cプロセスが $C000系で起動・IPC・終了する機構の実証」であり、
   小プロセスで機構の健全性を固める関心の分離が PDCA・1変更1検証に合致する。

## 3. 2KB 区画レイアウト（方式α・v1.1実測再設計）

> **【v1.1 改訂】M-1/M-2 対応**：v1.0 の区画割り（crt0 32B/CODE 992B/RUNTIME 512B/DATA 512B）は
> RUNTIME が実測 709B で 512B 枠を 197B 超過し DATA を侵食していた。実アセンブル（hasm23 v1.02・
> .sym/.dbg）の実測値に基づき区画境界を再設計する。容量根拠は実測一次（'F55'動作実証は容量根拠
> から切離す。§3.2 参照）。

### 3.1 区画定義（v1.1 確定）

```
$C000 ┌────────────────────────────┐ PROC-LOAD-ADDR / _proc_entry
      │ crt0  (startup_proc)        │  64B   $C000-$C03F  実需13B
$C040 ├────────────────────────────┤ CODE-ORG
      │ CODE  (JMP _main / C関数群)  │ 832B   $C040-$C37F  実需748B
$C380 ├────────────────────────────┤ RUNTIME-ORG
      │ RUNTIME (_putchar/_puts/    │ 768B   $C380-$C67F  実需709B
      │   _strcpy/_memcpy/_cc_mul…) │
$C680 ├────────────────────────────┤ DATA-ORG
      │ DATA  (大域変数/文字列)      │ 384B   $C680-$C7FF  実需≈150B
$C7FF └────────────────────────────┘ PROC-MAX-SIZE 上限
$C800   ── PAGE-POOL-BASE（MemMgr・別管理。Cプロセス領域外）──
```

| 領域 | 開始 | 終了 | 枠容量 | 実需(実測) | 余裕 | scc23マクロ | 内容 |
|---|---|---|---|---|---|---|---|
| crt0 | $C000 | $C03F | 64B | 13B | +51B | （固定・scc23対象外） | _proc_entry → JSR _main → TASK-EXIT |
| CODE | $C040 | $C37F | 832B | 748B | +84B | CODE_ORG=$C040 | JMP _main・ユーザC関数（_main/_fib等） |
| RUNTIME | $C380 | $C67F | 768B | 709B | +59B | RUNTIME_ORG=$C380 | Cランタイム（全ヘルパ固定の上限値） |
| DATA | $C680 | $C7FF | 384B | ≈150B | +234B | DATA_ORG=$C680 | 大域変数・文字列リテラル |
| **合計** | $C000 | $C7FF | **2048B** | | | | =PROC-MAX-SIZE $0800 ぴったり |

> **【v1.0 旧定義（取消・記録保存）】** ~~crt0 $C000-$C01F(32B) / CODE $C020-$C3FF(992B) /~~
> ~~RUNTIME $C400-$C5FF(512B) / DATA $C600-$C7FF(512B)~~ → RUNTIME 512B が実測709Bに対し過小で
> DATA侵食。M-1により上記 v1.1 値へ訂正。

### 3.2 区画割りの根拠（v1.1：実測一次・M-2対応）

各区画の容量根拠は **hasm23 v1.02 による実アセンブルの .sym/.dbg 実測値**を一次根拠とする。
（v1.0 の「'F55'動作実証済だから妥当」は論理不成立。emu23 はメモリ保護を持たず、RUNTIME が
DATA区画に食い込んでも当該領域にDATA実体が無ければ破壊が顕在化しない。fib は大域変数がほぼ
無く侵食域にDATAが無いため *たまたま動作しただけ*。動作実証は「機構が起動・IPC・終了する」
ことの実証であり、容量妥当性の根拠ではない。M-2）

実測値（fib_proc_exp.asm を hasm23 v1.02 でアセンブル・.sym 確認）：

| 区画 | .org起点 | 実終端 | 実使用 | 根拠 |
|---|---|---|---|---|
| crt0 | $C000 | $C00C | 13B | JSR _main/JSR TASK_EXIT×2/JMP の4命令（命令長合計13B・C-3） |
| CODE | $C040 | （fib時 $C30B 相当） | 748B | _fib/_main 等。258命令で748B（v1.0の「212命令」は誤り・C-3訂正） |
| RUNTIME | $C380 | （全ヘルパ） | 709B | _putchar/_getchar/_puts/_strcpy/_strcmp/_memcpy/_cc_mul/_cc_div/_cc_mod の最大集合 |
| DATA | $C680 | — | ≈150B | DATA実需実測サンプル（D-1）：char配列+文字列2本+int配列16+int で約150B |

- **RUNTIME 709B は「全ヘルパ無条件出力」の上限値**：scc23 v1.01 の `emit_runtime()`（L2587）は
  使用フラグによる条件分岐を持たず、全ヘルパを無条件出力する（実体確認済）。よって RUNTIME
  実需はどのプロセスでも約709B固定。これを枠768Bで安全に収容する。
- **将来オンデマンド化（§9申し送り）で RUNTIME 実需は減る方向**にしか動かないため、768B枠は
  上限として安全側。区画再設計の手戻りは生じない。

### 3.3 crt0 の確定仕様（startup_proc_v1_0.asm 既存・変更なし）
- `.org $C000`、`_proc_entry:` → `JSR _main` → `JSR TASK_EXIT($0460)` → ガードループ。
- **命令長根拠（C-3）**：JSR _main(3B) / JSR TASK_EXIT(3B) / JSR TASK_EXIT(3B) / JMP(3B) ＋
  ラベル境界で実測終端 $C00C（13B使用）。64B枠に十分収まる。
- SP/X は初期化しない（TASK-CREATE が tid 固有スタック saved_sp=CALLSTK_TOP/saved_x=DATASTK_TOP
  を設定済。crt0で上書きすると破壊する）。
- main 復帰後は HALT 厳禁（OS全停止になる）。TASK-EXIT で自タスクのみ終了。
- **注**：crt0 の .org を v1.1 で $C000 固定のまま、CODE_ORG を $C020→$C040 へ後退させたため、
  crt0 枠が 32B→64B に拡大（実需13Bに対し余裕十分）。crt0 自体のコードは不変。

## 4. 区画跨ぎ防止（αの弱点対策・v1.1 M-3改訂）

### 4.1 リスク
方式αは固定区画のため、CODE部が枠を超えて RUNTIME 区画へ食い込む、あるいは RUNTIME が DATA
区画へ食い込む「区画跨ぎ」が起こりうる。v1.0 では実際に RUNTIME が DATA を 197B 侵食していた
（M-1）。プロセスが成長した際に静かに破壊が起きないよう、ビルド時検出を必須とする。

### 4.2 既存ツールの担保とその限界（M-3：v1.0の過信を是正）

> **【v1.1 改訂】** v1.0 は「W001／lnk23 overlap で二重担保」としたが、実験版を hasm23 で
> アセンブルしても **W001 は発火しなかった**。本ケースで既存機構が機能しない理由を明記する。

1. **hasm23 v1.02 W001 の限界**：W001 は「**書込済バイトへの上書き衝突**」時のみ検出する機構
   （hasm23_v1_02.c L760-764）。RUNTIME が DATA区画($C680〜)を越えても、**DATA実体が無い／少ない
   場合は上書き衝突が起きず W001 では検出できない**。fib は DATA 未使用のため実験版で W001 は
   一度も発火しなかった。→ **W001 任せにしてはならない。**
2. **lnk23 overlap の限界**：lnk23 の `place_sections()` はセクション重なりを検出する
   （lnk23.c L575）が、実験版は単一asmを hasm23 へ直接投入しており **lnk23 を一度も通っていない**。
   よって v1.0 の lnk23 overlap 担保は本実証では**未実証（設計上可能 止まり）**。

### 4.3 ビルド手順での担保（v1.1：明示チェックを必須化・M-3）
W001 / lnk23 overlap に依存せず、**各区画の .sym/.dbg 実終端アドレスを区画境界と機械的に比較**
する明示チェックをビルド手順に組み込む（これが一次担保）：

1. Cプロセスをアセンブル後、**.sym から各区画の最終ラベル＋命令長で実終端を求め**、
   以下を機械的に検査（スクリプト or 監査）：
   - crt0 実終端 ≦ $C03F
   - CODE 実終端 ≦ $C37F
   - RUNTIME 実終端 ≦ $C67F
   - DATA 実終端 ≦ $C7FF
2. いずれか超過 → 「2KB枠/区画超過」＝Phase1対象外プロセス（β移行 or MMU待ち）と判断。
3. 補助的に hasm23 W001=0 を確認（ただし§4.2の限界ゆえ**補助**。一次は上記実終端検査）。
4. lnk23 overlap 担保は **Step4 で実 lnk23 経由構成にて初めて検証される**（それまで未実証・§9）。

## 5. scc23 への要求仕様（改修対象・本設計の出力）

### 5.1 要求：ベースアドレス引数化
現行 scc23 v1.01 は CODE_ORG/DATA_ORG/RUNTIME_ORG を `#define` ハードコード（$0400/$4000/$0100）。
これを起動引数で指定可能にする。

| 追加オプション | 対応マクロ | Cプロセス用の値（v1.1） | 既定値（後方互換） |
|---|---|---|---|
| `--code-org <addr>` | CODE_ORG | $C040 | $0400 |
| `--data-org <addr>` | DATA_ORG | $C680 | $4000 |
| `--runtime-org <addr>` | RUNTIME_ORG | $C380 | $0100 |

- **後方互換**：オプション省略時は現行の既定値（$0400/$4000/$0100）を使用。既存ビルド
  （Dhrystone等の $0400系単体ビルド）が壊れないこと（回帰必須）。
- **改修箇所**：`#define` を可変（グローバル変数 or パース結果）化。CODE_ORG=2箇所（L3378,3383）、
  RUNTIME_ORG=2箇所（L3374,2589）、DATA_ORG=演算形式11箇所（#define除く実参照・全て
  `DATA_ORG+offset`・C-1訂正）が一括追従。

### 5.2 非PIC構造の明示（設計上の制約）
- DATA_ORG をオプション化しても、値は「コンパイル時に確定して絶対アドレス埋込」する方式を維持する。
  すなわち scc23 はコンパイル時に DATA開始アドレスを知る必要がある（リンク時遅延解決はしない）。
- これは Phase1 のロードアドレス固定（$C000）前提で成立する。完全な再配置可能性（PIC）は
  本設計のスコープ外（Phase2 MMU検討と併せて再評価）。

### 5.3 回帰要件（プロジェクト原則）
- scc23 改修後、**Dhrystone 等の既存 $0400系単体ビルドが従来どおりコンパイル・動作すること**を
  回帰確認する（ツール改修時の Dhrystone 回帰原則）。
- 回帰は ProcMgr 経由ではなく従来の単体ビルド経路（$0400系）で実施。Cプロセス（$C000系）とは別軸。

## 6. 将来 β（連続配置）移行の前提

本設計は方式αだが、将来 lnk23 によるセクション連続配置（方式β）へ移行できる余地を残す。

### 6.1 移行が可能な根拠
- scc23 の出力は既に各セクション境界を `.org` で明示する構造（CODE/RUNTIME/DATA 各 .org）。
  α＝この .org を固定区画値に設定する運用、β＝lnk23 算出の連続配置値に設定する運用、と
  **出力フォーマットは両方式で共通**。
- §5.1 でベースアドレスを引数化しておけば、β移行時は「引数の供給元を固定値→lnk23算出値」に
  差し替えるだけ。**scc23 本体の再設計は不要**。

### 6.2 移行に必要な作業
1. **lnk23 拡張**：セクション連結（前セクション終端→次セクション開始を算出）機能の追加。
   これがβの主作業。
2. scc23 は §5.2 の「コンパイル時アドレス確定」方式を維持（PIC化はしない）。
   lnk算出値をコンパイル時引数で受領する形にする。
3. 完全PIC化（絶対参照の相対化）は **Phase2 MMU 検討と併せて要否を再評価**。それまでは
   非PIC＋コンパイル時アドレス確定を許容する。

### 6.3 移行トリガ
- αの固定区画（CODE 992B 等）を超える小プロセスが現実に必要になったとき。
- Phase1の小プロセス限定（案B）の間はαで十分であり、β移行は急がない。

## 7. memmap v2.0 への反映事項

本設計の確定値を memmap v1.7→v2.0 改版時に反映する：

1. **Cプロセス領域の正式定義**：$C000-$C7FF を「Cプロセスロード領域（Phase1・2KB固定区画）」
   として登録。内訳（crt0 $C000-$C03F / CODE $C040-$C37F / RUNTIME $C380-$C67F /
   DATA $C680-$C7FF）を明記（v1.1実測再設計値）。
2. **CALLSTK/DATASTK 式の文書追従**：§6.4.3等の計算式を `$F07F/$F87F`→`$F07E/$F87E`（偶数）へ
   修正（実体は既に偶数化済。文書を実体に追従させる。standing instruction 消化）。
3. **PAGE-POOL-BASE=$C800 との隣接関係**：Cプロセス領域上限 $C7FF の直上が PAGE-POOL-BASE
   $C800 であることを明記（衝突しないことの確認）。
4. **scc23 アドレス契約**：CODE_ORG=$C040/RUNTIME_ORG=$C380/DATA_ORG=$C680 を「Cプロセス
   ビルド時の標準org値」として記載（v1.1実測再設計値）。

## 9. 未決事項・申し送り

  隣接する点は、scc23 が CODE を $C040 から出力する際に crt0 と正しくリンクされること
  （lnk23 結合）を Step4 実装で実機確認する。

### 9.1 v1.1 レビュー指摘 C/D への対応・申し送り
- **C-2（申し送り）**：実験版の .org 物理配置がソース上で逆順（$C000→$C400→$C020→$C600）。
  hasm23 単体は .org 追従で成立するが、Step4 で lnk23 の `place_sections()` へ載せ替える際、
  逆順構造が overlap 判定とどう相互作用するか**未検証**。Step4 で実 lnk23 経由構成にて検証する。
- **D-1（解消済）**：DATA実需を実測サンプル（char配列+文字列2本+int配列16+counter）で約150B と
  実測。DATA枠384Bに十分収まる（余裕234B）。文字列多用の小プロセスでも当面充足の見通し。
- **D-2（申し送り・Phase2送り可）**：§6.2 β移行で「lnk算出値をコンパイル時引数で scc23 に渡す」
  には、lnk がセクション連結する前に scc23 がアドレスを確定する**順序依存（鶏卵問題）**がある。
  解法候補は (1) 2パス（1パス目で各セクションサイズ測定→lnk連結値算出→2パス目で確定値埋込）、
  (2) 事前固定割当（本v1.1のα＝固定区画がまさにこれ）。Phase2 で要見通し。
- **D-3（オンデマンド化の前提・申し送り→scc23改修設計へ）**：RUNTIME に含むヘルパ集合
  （_putchar〜_cc_mod の9種）は現状 scc23 が**全プロセス共通の最大集合を無条件出力**する
  （`emit_runtime()` L2587 に使用フラグ分岐なし・実体確認済）。プロセスごとに未使用ヘルパを
  削れれば RUNTIME 実需は変動するが、本v1.1は**最大集合709Bを上限**として固定区画768Bで安全に
  収容しており、見積り基準は「全ヘルパ固定＝709B上限」で確定済。

### 9.2 scc23 改修設計への申し送り（次工程）
- **ヘルパのオンデマンド出力（要望事項）**：使用したヘルパのみ RUNTIME に出力する改善を
  scc23 改修設計で扱う。各ヘルパへの JSR 発行箇所（_cc_mul: L1632,1795,1971,2094 /
  _cc_div: L1803,2095 / _cc_mod: L1811,2096 等）で使用フラグを立て、`emit_runtime()` で

  使わない小プロセスでは省かれる。**本v1.1区画はオンデマンド化後も実需が減る方向のため安全側**
  （区画再設計不要）。これは Phase1/Phase2 共通で効く全体改善であり、区画設計とは別軸。
