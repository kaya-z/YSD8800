## 1. 背景

`emu23_kairyo.txt` 項番1 は「emu23 の対話モード（`-it`）で YUI OS シェルに入力できない」という要求である。
調査の結果、**emu23 側の不具合ではなく YUI OS スケジューラの欠陥**であることが確定した。
本書はその修正設計を定義する。

---

## 2. 調査で確定した事実（実源・実測）

### 2.1 emu23 側は健全

| 検証条件 | 結果 |
|---|---|
| 最小エコープログラム + `-it`（パイプ／PTY 両方） | 受信成功 ✅ |
| YUI OS + `-it` / `-q`、**ブート中**に投入 | 「YUIOS V0.10.18」応答 ✅ |
| YUI OS + `-it` / `-q`、**ブート後**に投入（tty／パイプ両方） | 無反応 ❌ |

→ tty か否かは無関係。投入タイミングのみで再現性が決まる。

### 2.2 ハング時の CPU 実測値

調査ビルド（`emu23_dbg_poc.c`、`ysd8001_tick` に定点観測を挿入）による 12 サンプル、全て同一傾向：

```
cyc=20000000  pc=0105 flags=00 pend=1 irq_stat=0000 ustat=0001
cyc=60000000  pc=00F7 flags=00 pend=1 irq_stat=0000 ustat=0001
cyc=160000000 pc=0116 flags=00 pend=1 irq_stat=0000 ustat=0001
（他 9 サンプルも pc は $00DB〜$0116 の範囲内）
```

- `flags` の `FL_IE`（`emu23_v111.c` L125: `0x80`）が**常時 0**＝割込禁止のまま
- `irq_pending=1`（IRQ0 タイマー）が**永久に未受理**のまま滞留
- PC は全サンプルが `$00DB`〜`$0116` の範囲内

### 2.3 PC 範囲のシンボル対応（`yuios_road2.sym`）

```
00c4 _irq_sched
00d0 _sched
00db _sched_chk      ← ループ先頭
0119 _sched_found    ← ループ出口（READY 発見時のみ）
```

→ CPU は **IRQ0_HANDLER 内のタスク探索ループ `_sched`〜`_sched_chk` を回り続けている**。

### 2.4 真因（実源該当行）

`IRQ0_HANDLER`（`.org $0030`）は入口で `DI` を実行する。その後の探索ループは以下の構造で、
**「1周しても READY が無かった場合」の脱出路が存在しない**。

```asm
_irq_sched:
    LDW  A, [CUR_TASK]
    STW  A, [L1_WK_B]          ; ★開始tidを保存しているが…
    ADDI A, #1
_sched:
    CMPI A, #16
    BLT  _sched_chk
    LDW  A, #0
_sched_chk:
    STW  A, [L1_WK_A]          ; ★L1_WK_B との比較が無い＝1周検出が無い
    ...（TCBアドレス計算）...
    LDW  B, [X]
    CMPI B, #1                 ; READY?
    BEQ  _sched_found
    LDW  A, [L1_WK_A]
    ADDI A, #1
    JMP  _sched                ; ★READY が無ければ永久に回る
```

`L1_WK_B` に開始 tid を保存しているにもかかわらず、**参照されていない**。実装漏れである。

### 2.5 対照：SYSCALL 側には正しく実装されている

`_sched_common`（`.org $02C0`）は同じ探索を行うが、1周検出とアイドル処理を持つ。

```asm
_sc_chk:
    LDW  B, [L1_WK_B]          ; ★開始tidと比較
    CMP  A, B
    BEQ  _sc_idle              ; ★1周した→アイドルへ
    STW  A, [L1_WK_A]
    ...
_sc_idle:
    EI
    NOP
    DI
    JMP  _sched_common         ; 割込を1命令分だけ通して再走査
```

→ **同一機能の 2 実装で片方だけ欠落している非対称**が本欠陥の正体である。

### 2.6 発症条件

`IRQ0_HANDLER` は、割込時のタスクが `state==RUNNING(2)` の場合のみコンテキストを保存し、
その際 `RUNNING→READY(1)` に落とす（L509-510）。この場合は自分自身が READY として発見されるため脱出できる。

**発症するのは、割込時のタスクが非 RUNNING（WAIT/アイドル）だった場合**である。
このとき保存はスキップされ（L483 `BNE _irq_sched`）、READY タスクが 0 個になり得る。

これがブート直後は入力が通り、全タスクが待機に入った瞬間に固まる理由を説明する。
シェルは `GETC` で UART 待ちに入るため、**入力を待っている状態そのものがハング条件**になる。

---

## 3. 修正方針

**`_sched_chk` に `_sc_chk` と同一の 1周検出を追加し、IRQ0 側にもアイドル処理 `_irq_idle` を新設する。**

独自方式は採らず、**既に動作実績のある `_sc_idle` の構造をそのまま踏襲**する（原則: 実績ある実装に合わせる）。

### 3.1 変更内容（2箇所）

**(1) `_sched_chk` 先頭に 1周検出を挿入**

```asm
_sched_chk:
    LDW  B, [L1_WK_B]          ; ★追加: 開始tidと比較（読むだけ）
    CMP  A, B                  ; ★追加
    BEQ  _irq_idle             ; ★追加: 1周した→アイドルへ
    STW  A, [L1_WK_A]
    ...（以降は現行のまま）
```

**(2) `_sched` ループ直後に `_irq_idle` を新設**

```asm
_irq_idle:
    EI
    NOP
    DI
    JMP  _irq_sched            ; CUR_TASK 基準で開始tidを取り直して再走査
```

### 3.2 設計判断の根拠

| 判断 | 内容 | 根拠 |
|---|---|---|
| `L1_WK_B` を比較に使う | 既に `_irq_sched` で開始 tid が格納済み。追加ワークは不要 | L512-513 の実源。`_sched_chk` 以降で `L1_WK_B` は読み書きされないため副作用なし |
| 戻り先を `_irq_sched` とする | `CUR_TASK` から開始 tid を取り直す。`_sc_idle` が `_sched_common` へ戻るのと同一作法 | `_sc_idle` L660-663 |
| `EI / NOP / DI` の 3 命令構成を踏襲 | 割込を「1命令分だけ」通す確立された手法。EI 直後の 1 命令で割込受理される前提 | `_sc_idle` と同一 |
| `B` レジスタ破壊 | `_sched_chk` は元々 `B` を TCB 読出に使うため破壊前提。追加破壊なし | L529-534 |
| ISA2.3 命令のみ使用 | `LDW` / `CMP` / `BEQ` / `EI` / `NOP` / `DI` / `JMP` はすべて既存コードで使用実績あり | ISA2.3 |

### 3.3 これで入力が通る理由

1. 全タスク待機 → `_irq_idle` に到達 → `EI` で割込許可
2. 打鍵 → emu23 が `ysd8004_raise(bit0)` → IRQ1 受理
3. `IRQ1_HANDLER` が `rx_push` → `UART_STAT` WTC → `wake_uart_waiter` でシェルを READY 化
4. `IRET` で `_irq_idle` に復帰 → `DI` → `_irq_sched` 再走査 → シェルを発見 → `_sched_found` で切替

## 4. リスクと対策（KY）

| # | リスク | 影響 | 対策 |
|---|---|---|---|
| R1 | **アイドル中の多重割込によるスタック増加**。`_irq_idle` の `EI` 窓でタイマー IRQ0 が入ると `IRQ0_HANDLER` が入れ子になる | 待機が長時間続くとカーネルスタックを消費し続ける可能性 | 本 v0.1 では `_sc_idle` と同等の既存リスク水準に留める（新規リスクではない）。定量評価は §5 の T4 で実測し、必要なら別工程で対策 |
| R2 | `_sched_found` は `DI` を持たない（`_sc_found` は持つ）。アイドル経由で来ると EI 状態のまま到達しないか | コンテキスト切替中の割込＝破壊的 | `_irq_idle` が `JMP _irq_sched` の前に `DI` を実行するため、`_sched_found` 到達時は必ず DI 状態。**現行フローと同一**であることを T3 で確認する |
| R3 | 1周検出の境界誤り（開始 tid 自身を検査しない／2周する） | 特定 tid のタスクが選ばれない飢餓 | `_sc_chk` と**完全に同一の比較順序**にすることで挙動を一致させる。T2 で全 tid 走査を確認 |
| R4 | `L1_WK_B` が IRQ1 ハンドラ等と共有ワークで、アイドル中の IRQ1 に破壊される | 再走査時に誤った開始 tid で 1周検出が誤動作 | **実装前に `L1_WK_B` の全参照箇所を grep で洗い出し、IRQ1 経路が触らないことを確認する（実装着手の前提条件）** |
