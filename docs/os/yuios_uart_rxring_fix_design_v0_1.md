## 1. 対象データ構造（実源確定）

`kernel_v12_9.asm` L385-L392 近傍の EQU 定義より。

| シンボル | アドレス | 幅 | 意味 |
|---|---|---|---|
| `UART_RX_RING_BUF` | `$FC46` | 16 B | 受信リングバッファ本体（1バイト/スロット） |
| `UART_RX_HEAD` | `$FC56` | 2 B | 書込インデックス 0–15（L389） |
| `UART_RX_TAIL` | `$FC58` | 2 B | 読出インデックス 0–15（L390） |
| `UART_RX_COUNT` | `$FC5A` | 2 B | 滞留バイト数 |
| `UART_WAIT_TID` | `$FC5E` | 2 B | `UART_GETC` 待ちクライアント tid（0=なし） |

### ★アドレス配置上の危険（本欠陥の増幅要因）★

```
$FC46 ┌──────────────────┐
      │ RING_BUF[0..15]  │  16 B
$FC56 ├──────────────────┤
      │ UART_RX_HEAD     │
$FC58 │ UART_RX_TAIL     │
$FC5A │ UART_RX_COUNT    │
$FC5C │ (予約)           │
$FC5E │ UART_WAIT_TID    │  ← RING_BUF 先頭から +24
      └──────────────────┘
```

**`RING_BUF` の直後に制御変数が隣接している。**
このため、リングバッファ先頭を基点とした誤ったオフセット書込は、
アクセス違反にならず**制御変数を静かに破壊する**。欠陥①の被害が
「クラッシュ」ではなく「永久ハング」になったのはこの配置に起因する。

## 2. 欠陥①: `wake_uart_waiter` の X レジスタ非復元

### 2.1 症状

`UART_GETC` で待機に入ったタスク（シェル）が、1文字受信しても**永久に起床しない**。
UART 割込は正常に発生し、`rx_push` によるバッファ書込も正常。
にもかかわらず待機者が READY にならない。

### 2.2 真因

`wake_uart_waiter`（L1766〜）は L1784 で `MOV X, A` により
X = TCB アドレスを確立した後、L1787 で `JSR rx_pop` を実行する。

`rx_pop` のヘッダコメント L1827 には **「破壊: A, B, X」と明記**されており、
実際 L1834 の `MOV X, A` により **X = `&buf[TAIL]` のまま復帰**する。

修正前のコードは `rx_pop` 復帰後も X を TCB ポインタとして使用していたため、
以降の `STW A,[X+#nn]` 群が **リングバッファ領域を基点に着弾**した。

### 2.3 着弾解析（TAIL=0 のとき）

| 命令 | 意図した宛先 | 実際の着弾先 | 影響 |
|---|---|---|---|
| `STW A,[X+#16]` | TCB+16 ipc_msg[0] | `$FC46+16 = $FC56` | **HEAD 破壊** |
| `STW A,[X+#18]` | TCB+18 ipc_msg[1] | `$FC58` | **TAIL 破壊** |
| `STW A,[X+#20]` | TCB+20 ipc_msg[2] | `$FC5A` | **COUNT 破壊** |
| `STW A,[X+#22]` | TCB+22 ipc_msg[3] | `$FC5C` | 予約領域 |
| `STW A,[X+#24]` | TCB+24 **ipc_valid=1** | **`$FC5E = UART_WAIT_TID`** | ★致命★ |

最後の 1 行が決定的である。`ipc_valid=1` を書いたつもりが
**`UART_WAIT_TID = 1`** を書いていた。その直後 L1816-1817 で
`UART_WAIT_TID = 0` がクリアされるため、待機者情報は失われ、
かつクライアント TCB の `ipc_valid` は 0 のまま。
**待機者は永久に起床せず、READY タスクが 0 個になる**
（→ TKT-00 のスケジューラ無限ループを誘発）。

### 2.4 修正（実装済み・L1788-1792）

```asm
    JSR  rx_pop                 ; A = byte (下位8bit)
    ; ★v0.12.9: rx_pop は X を破壊する（X=&buf[TAIL] のまま復帰）ため
    ;   TCBポインタを復元する。（以下略・実源参照）
    LDW  X, [IPC4_WK_SRCTCB]    ; ★X = TCBアドレス を復元（A は保持）
```

`IPC4_WK_SRCTCB`（`$47A0`）には L1783 で TCB アドレスが格納済みであり、
`rx_pop` はこの変数に触れないため復元元として安全。

**A レジスタが保持される点が重要**：`LDW X,[addr]` は A を破壊しない。
`rx_pop` の戻り値（受信バイト）は A に載ったまま L1793 で使用される。

## 3. 欠陥②: `rx_pop` のアドレス／インデックス混同

### 3.1 症状

1文字目は正しく取得できるが、**2文字目以降が NUL になる**。
実測では `v` の後に NUL×3 が観測された（HANDOVER_CHAT128.md §3.2）。

### 3.2 真因

修正前 L1839 相当は `MOV B, X` であった。この時点の X は
L1834 の `MOV X, A` により **`&buf[TAIL]`（絶対アドレス）**である。
インデックスではない。

```
TAIL=0 のとき  X = $FC46
MOV B,X     →  B = $FC46
ADDI B,#1   →  B = $FC47
ANDI B,#$000F → B = 7      ← ★$FC47 の下位4bit が 7★
```

**`$FC46` の下位4bit が 6** であるため、TAIL は +1 ではなく
**+7 進む**（正確には `(base_low4 + 1 + n) mod 16` に飛ぶ）。
次回 pop は未書込スロットを読み、初期値 0（NUL）を返す。

### 3.3 修正（実装済み・L1839-1843）

```asm
    LDW  B, [UART_RX_TAIL]      ; ★B = TAIL（インデックス）を再取得
    ADDI B, #1
    ANDI B, #$000F              ; TAIL = (TAIL+1) mod 16
    STW  B, [UART_RX_TAIL]
```

インデックスをレジスタから流用せず**メモリから再取得**する方式に変更。

## 4. ★構造的原因: 対になるコードの非対称性★

`rx_push`（L1339〜）と `rx_pop`（L1830〜）は対の操作でありながら、
**インデックスの扱い方が非対称**であった。

| | `rx_push`（L1348-1359） | `rx_pop`（修正前） |
|---|---|---|
| アドレス計算 | `LDW B,[HEAD]` → `LDW A,#$FC46` → `ADD A,B` | `LDW X,[TAIL]` → `LDW A,#$FC46` → `ADD A,X` |
| **インデックス保持先** | **B（アドレスは A）** | **X（アドレスも X に上書き）** |
| インデックス更新 | `LDW A,[HEAD]` で**再取得** ✅ | `MOV B,X` で**流用** ❌ |

`rx_push` はアドレスとインデックスを**別レジスタに分離**していたため
正しく動作していた。`rx_pop` は `MOV X,A` でインデックスを潰した上に
そのレジスタからインデックスを取り出そうとした。

> **本件は kaizen 原則5（変数の責務は1つに絞る）のレジスタ版である。**
> X が「インデックス」→「アドレス」と役割を変えたのに、
> 後半のコードは前半の役割を前提にしていた。

### 提案: kaizen 原則102（§8 に詳細）

## 5. 検証設計（A-4 後半・**未実施**）

### 5.1 検証方針

KY54 に従い**ネガティブテスト先行**。異常系（オーバーラン・折返し）を
正常系より先に実行する。

### 5.2 検証項目

| ID | 分類 | 内容 | 合否基準 |
|---|---|---|---|
| **V-1** | 異常系 | **オーバーラン**: 待機者不在の状態で 17 バイト以上を連続投入 | `COUNT` が 16 を超えない。17バイト目が破棄され、HEAD/TAIL/WAIT_TID が破壊されない |
| **V-2** | 異常系 | **TAIL 折返し**: TAIL=15 の状態から 1 バイト pop | TAIL が 0 に戻る（16 や 7 にならない） |
| **V-3** | 異常系 | **欠陥①の直接再現条件**: TAIL=0 で起床経路を通す | `UART_WAIT_TID` が `1` にならない。クライアント TCB+24（ipc_valid）が 1 になる |
| **V-4** | 境界 | **16バイト境界一周**: 16 バイト連続投入→16 バイト連続取得 | 取得列が投入列と完全一致。TAIL/HEAD が共に 0 へ戻る |
| **V-5** | 正常系 | 連続複数文字入力（`ver\r` 等） | 全文字が欠落・NUL 化なく取得される |
| **V-6** | 回帰 | ベースライン再現（HANDOVER §6） | `YUIOS V0.10.18` まで到達 |

### 5.3 実施方法

`emu23` のメモリダンプ機能を用い、各ケースで
`$FC46`–`$FC5F`（26 バイト）を採取して期待値と数値比較する（原則10）。

投入は `-it` モードへのパイプ入力、または UART MMIO への直接注入で行う。
**V-1〜V-4 は 16 バイト超の投入が必要**なため、パイプ投入で
`printf` により所定バイト列を送出する。

### 5.4 ★V-6 の位置づけ★

**本チケットは YUI OS カーネルのみの修正であり、emu23 を改修しない。**
したがって **Dhrystone 回帰は規約適用対象外**である
（HANDOVER_CHAT128.md §3.3 の判定に同じ）。
V-6 はカーネル側の非回帰確認として実施する。

## 8. kaizen 登録候補（原則102）

> **原則102: 対になる操作（push/pop, send/recv, alloc/free）は、
> レジスタ／変数の割り当てを対称に設計する。**
>
> 一方が「インデックスは B、アドレスは A」で他方が「インデックスもアドレスも X」
> のように非対称だと、レビュー時に**差分としてではなく別実装として**読まれ、
> 誤りが検出されない。対称であれば片方を読むだけで他方の誤りが浮き上がる。
>
> **系1**: 1 つのレジスタに 2 つの役割（インデックスとアドレス）を持たせない。
> 役割が変わる時点でレジスタを分ける。役割変更が避けられない場合は、
> 変更点にコメントで「以降 X は〜を意味する」と明記する。
>
> **系2**: 派生値（アドレス）から原値（インデックス）を逆算・流用しない。
> 原値は**保持元から再取得**する。1 命令の節約より正しさを優先する。
>
> ※ 原則6（副作用スコープの明記）は「呼ばれる側」の規律だが、
> 本原則は「呼ぶ側」が破壊一覧を**読んで守る**ための構造的支援である。
> `rx_pop` は「破壊: A,B,X」を正しく明記していたにもかかわらず
> 呼び出し側が守らなかった。**明記だけでは防げない**ことの実例。
