## 1. 症状

`TASK_CREATE` が返す tid が誤った値になる。実測では `$F87E`（データスタック頂上値）
が返ることが観測された。正常時は 0〜15 の範囲の tid が返る。

発生は**間欠的**であり、再現には `EI` 実行から数命令の窓に IRQ0 が入る必要がある。

---

## 2. 対象データ構造（実源確定）

| シンボル | アドレス | 実源行 | 用途 |
|---|---|---|---|
| `L1_WK_A` | `$4780` | L295 | **ループ変数（現スキャン tid）** |
| `L1_WK_B` | — | L554 で参照 | スケジューラ走査の開始 tid |
| `L1_WK_TMP` | — | L532 | TCB アドレス計算の一時 |
| `L1_WK_C` | — | L535 | TCB アドレス計算の一時 |
| `TC_WK_TID` | `$479A` | L309 | TASK_CREATE の DSP 退避 |

### 2.1 ★`L1_WK_A` の用途が2系統で重複している★

L290 のコメントは `L1_WK_A = ループ変数(現スキャンtid)` と定義するが、
**実際には以下の3系統がすべて同じ `$4780` を使っている。**

| 系統 | 使用箇所（実源行） | 文脈 |
|---|---|---|
| **① スケジューラ走査** | L531／L553／L583 | **IRQ0 ハンドラ内**（非同期に走る） |
| **② TASK_CREATE 走査** | L855／L871／L887／L904／L932 | タスクコンテキスト |
| ③ MsgPool 走査 | L1021／L1034／L1045 | タスクコンテキスト |
| ④ その他 | L682／L699／L710 | タスクコンテキスト |

**①だけが IRQ コンテキストで非同期に実行される。**
②③④は互いに排他だが、①はいつでも割り込んでくる。
この非対称性が本欠陥の構造的な土台である。

## 3. 真因

### 3.1 該当コード（修正前）

`TASK_CREATE` の正常終了経路。修正前は以下の順序であった。

```asm
_tc_done:
    LDW  X, [TC_WK_TID]
    EI                          ; ← ここで IRQ 許可
    SUBI X, #2
    LDW  A, [L1_WK_A]           ; ★EI の「後」に L1_WK_A を読んでいた
    STW  A, [X]                 ; 戻り値 tid を DSP へ
    RET
```

### 3.2 競合の成立

`EI` から `LDW A,[L1_WK_A]` までの窓に IRQ0（タイマ）が入ると、
IRQ0 ハンドラはスケジューラ走査 `_sched_chk` を実行する。

**実源 L531**:
```asm
_sched_chk:
    STW  A, [L1_WK_A]           ; ★走査中の tid で上書きされる
```

走査は L527 の `CMPI A,#16` で 0〜15 を巡回するため、
`L1_WK_A` は**IRQ0 が抜けた時点の走査位置**に置き換わる。
`TASK_CREATE` はその汚染値を tid として返す。

### 3.3 ★被害が `$F87E` として観測された理由★

戻り値が `$F87E`（データスタック頂上）になった実測は、
`L1_WK_A` の汚染だけでは説明できない（走査値は 0〜15 の範囲）。

これは **TKT-04（`A` レジスタ非保存）が重畳した結果**である（§5 参照）。
本チケットの修正後も `EI` 窓に IRQ0 を強制注入すると `$F87E` が再現することを
2026-08-03 に確認済みであり、**両者は独立した別欠陥**である。

## 4. 修正（実装済み・L929-937）

```asm
    ; ★v0.12.9(別チケット): EI後に L1_WK_A を読むと、その窓で入った
    ;   IRQ0のスケジューラ走査が L1_WK_A を上書きし、誤ったtidを返す。
    ;   L1_WK_A の読出を EI より前に移動する。
    LDW  A, [L1_WK_A]           ; ★EIより前にtidを確保
    LDW  X, [TC_WK_TID]
    EI
    SUBI X, #2
    STW  A, [X]
    RET
```

### 4.1 設計判断

| 選択肢 | 内容 | 採否 |
|---|---|---|
| **案① 読出を `EI` より前へ移動** | 1行移動のみ。DI 区間が数命令伸びる | **採用** |
| 案② `L1_WK_A` を専用変数に分離 | 系統ごとに別変数を割り当てる | 不採用（§6 で再検討） |
| 案③ IRQ0 ハンドラで `L1_WK_A` を退避・復元 | ハンドラ入口/出口に push/pop | 不採用 |

**案①を採る理由**:

1. **DI 区間の延長が最小**（`LDW` 1命令ぶん）。割込レイテンシへの影響が無視できる
2. `TASK_CREATE` は元々 L849 で `DI` してから走査しており、
   **`L1_WK_A` の有効期間は本来 DI 区間内で閉じているべきもの**であった。
   案①は設計意図に戻す修正であり、新たな概念を導入しない
3. 案③は IRQ0 の割込レイテンシを直接悪化させる。IRQ0 はスケジューラであり
   最も高頻度に走るため、ここへのコスト追加は避けたい

### 4.2 修正の一般形

> **DI 区間で確立した値は、`EI` より前にレジスタへ確保すること。**
> `EI` の後に共有変数を読むのは、DI 区間の外で DI 区間の成果を参照する行為であり、
> 保護が切れている。

## 5. ★TKT-04 との境界（混同防止・本書の主要目的）★

TKT-01 と TKT-04 は**同一の症状**（`TASK_CREATE` の戻り値異常）を出すため、
極めて混同しやすい。以下に境界を確定する。

| | **TKT-01（本書・解決済）** | **TKT-04（未着手）** |
|---|---|---|
| 壊れるもの | **ワーク変数 `L1_WK_A`（`$4780`）** | **`A` レジスタそのもの** |
| 壊す主体 | IRQ0 のスケジューラ走査が同じ変数を使う（L531） | `IRQ0_HANDLER` が非 RUNNING コンテキストでは TCB 保存をスキップして他タスクへ切替える |
| 影響範囲 | `L1_WK_A` を `EI` 後に読む箇所のみ | **`EI` 窓を持つ全カーネル経路の可能性** |
| 修正 | 読出を `EI` より前へ移動（1行） | **未定**（調査工程が必要） |
| 状態 | **実装済・検証済（T-A/T-B）** | 現象確認のみ |

**判定基準**: `EI` 窓の IRQ0 で
- **メモリ上の値**が変わる → TKT-01 系
- **レジスタの値**が変わる → TKT-04 系

> ★TKT-01 を修正しても症状が完全には消えないのは正常である。★
> 残渣が TKT-04 であり、両者は独立に対処する必要がある。
> 2026-08-06 のセッションでも「L910-911 のバグはどうなったか」という
> 混乱が実際に発生しており、本節はその再発防止を意図する。

### 5.1 行番号のずれについて（記録）

本欠陥は発見当時「L910-911」と呼称されていたが、
その後 TKT-00 の `_irq_noready` 追加等によりファイルが伸び、
**v0.12.10 では L932-934 に位置する**。

> **行番号による欠陥の呼称は、ファイルが変化すると即座に陳腐化する。**
> 以後はチケット ID と**シンボル名**（`TASK_CREATE` 正常終了経路の `L1_WK_A` 読出）
> で参照すること（§8 原則105 提案）。

## 6. ★横展開調査（同種欠陥の残存確認・**未実施**）★

本欠陥の本質は「**`EI` の後に、DI 区間で確立した共有変数を読む**」ことである。
同じパターンが他所に残っていないか調査する必要がある。

### 6.1 調査対象

| # | 調査内容 | 方法 | 状態 |
|---|---|---|---|
| **S-1** | `EI` の後方数命令以内で `L1_WK_*` を読む箇所の全数調査 | `EI` の全出現位置を列挙し、後続命令の共有変数読出を検出 | **一次実施済（§6.1.1）** |
| **S-2** | `EI` 後に `TC_WK_*` / `MISC_WK_*` / `IPC4_WK_*` を読む箇所 | 同上（変数名を拡大） | **一次実施済（§6.1.1）** |
| **S-3** | IRQ0 ハンドラが書き換える全変数の洗い出し | `_sched` 経路の `STW *,[...]` を列挙し衝突変数を特定 | ⬜ 未実施 |

#### 6.1.1 ★S-1／S-2 一次スクリーニング結果（2026-08-06 実施）★

**結果: 同種欠陥の追加検出は 0 件。**

`kernel_v12_10.asm` の `EI` は 8 箇所（L703／L877／L934／L970／L1071／L1106／L1196／L1259）。
各 `EI` の後続8行以内に `L1_WK_*` / `TC_WK_*` / `MISC_WK_*` / `IPC4_WK_*` の
読出があるかを機械的に走査し、2件がヒットしたが**いずれも誤検出**であった。

| 検出箇所 | ヒット内容 | 判定 | 理由 |
|---|---|---|---|
| EI@703 | L710 `LDW A,[L1_WK_A]` | **誤検出** | L710 は `_sc_found` ラベル内であり `BEQ _sc_found`（L698）で到達する**別経路**。直前 L709 に `DI` がある |
| EI@1106 | L1111 `LDW X,[IPC4_WK_X]` | **誤検出** | EI@1106 の直後は L1107 `RET`。L1111 は `_ipc4call_enq_ok` ラベル内の**別経路** |

**追加確認**: `_sched_common`（L670〜）の走査区間について、
`L1_WK_A` の書込（L682）から読出（L699／L710）までの間に `EI` が無いことを確認した。
唯一の `EI`（L703 `_sc_idle`）は直後 L705 で `DI` し、
L706 で `JMP _sched_common` して**走査を先頭からやり直す**ため、
古い `L1_WK_A` が参照されることはない。

> ★本スクリーニングの限界★
> 行番号ウィンドウによる機械的走査であり、**制御フローを追跡していない**。
> 上記2件の誤検出はまさにその限界（ラベル境界を跨いだ）に由来する。
> 逆に「`EI` の遥か後方で読む」パターンは検出できない。
> **S-3（IRQ0 が書く全変数の洗い出し）と組み合わせた再調査を推奨する。**

### 6.2 S-3 の重要性

§2.1 のとおり `L1_WK_A` は**4系統で共用**されている。
IRQ0 が書き換える変数は `L1_WK_A` だけとは限らず、
L532 `L1_WK_TMP`／L535 `L1_WK_C` も同様に書き換えている。

**`L1_WK_TMP` と `L1_WK_C` は TASK_CREATE でも使用されている**（L856／L859）。
これらが `EI` 後に読まれる箇所があれば**同種の欠陥**である。

> **本チケットは `L1_WK_A` の1箇所を潰したにすぎない。**
> 同じ土台（IRQ0 とタスクコンテキストのワーク変数共用）から
> 別の欠陥が生えている可能性は高い。S-1〜S-3 の実施を強く推奨する。

### 6.3 恒久対策の検討（案②の再評価）

S-1〜S-3 の結果によっては、§4.1 で不採用とした
**案②（IRQ0 専用ワーク変数の分離）** が恒久対策として妥当になる。

| 判定 | 対応 |
|---|---|
| 同種欠陥が 0〜1 件 | 案①（個別修正）の継続で十分 |
| 同種欠陥が 2 件以上 | **案②（IRQ0 専用変数への分離）を別チケットで検討** |

コストは `L1_WK_A/TMP/C` の IRQ0 専用複製3個（6バイト）と、
`_sched` 経路の参照先変更のみであり、大きくない。

## 8. kaizen 登録候補

### 8.1 ★原則105（新規）★

> **原則105: 割込ハンドラとタスクコンテキストでワーク変数を共用してはならない。
> やむを得ず共用する場合は「有効期間が DI 区間内で閉じている」ことを保証する。**
>
> **系1**: DI 区間で確立した値は、`EI` より**前に**レジスタへ確保する。
> `EI` の後に共有変数を読むのは、保護が切れた後に保護区間の成果を参照する行為である。
>
> **系2**: 共有変数の宣言箇所に**「どのコンテキストから書かれるか」を明記する**。
> `L1_WK_A` のコメントは「ループ変数(現スキャンtid)」とだけ書かれており、
> **IRQ0 ハンドラが非同期に書き換えることが読み取れなかった**。
> 用途ではなく**書き手**を書くこと。
>
> **系3**: 欠陥を**行番号で呼称しない**。ファイルが変化すると即座に陳腐化し、
> 後日の追跡で「その行には別のコードがある」という混乱を生む（§5.1 で実際に発生）。
> チケット ID とシンボル名で参照する。

### 8.2 原則102 系2 との関係

原則102 系2（派生値から原値を逆算せず、原値は保持元から再取得する）と
本原則 系1 は**一見矛盾する**ように読める。

| | 原則102 系2 | 原則105 系1 |
|---|---|---|
| 指示 | メモリから**再取得**せよ | **事前にレジスタへ確保**せよ |

**矛盾しない。適用条件が異なる。**

- **原則102 系2**: 保持元が**汚染されない**場合。再取得が最も確実
- **原則105 系1**: 保持元が**非同期に汚染されうる**場合。汚染前に退避が必要

**判定手順**: その変数を**割込ハンドラが書くか**を確認する。
書くなら原則105（事前確保）、書かないなら原則102（再取得）。

> ★この判定を誤ると、TKT-02 で潰した欠陥②を再生産することになる。
> どちらの原則も「レジスタとメモリのどちらを信じるか」を扱っており、
> **答えは「非同期の書き手が居るか」で決まる。**
