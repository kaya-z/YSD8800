## 1. 背景

`emu23_kairyo.txt` 項番1 は「emu23 の対話モード（`-it`）で YUI OS シェルに入力できない」という要求である。
調査の結果、**emu23 側の不具合ではなく YUI OS スケジューラの欠陥**であることが確定した。
本書はその修正設計を定義する。

## 2. 調査で確定した事実（実源・実測）

### 2.1 emu23 側は健全

| 検証条件 | 結果 |
|---|---|
| 最小エコープログラム + `-it`（パイプ／PTY 両方） | 受信成功 ✅ |
| YUI OS + `-it` / `-q`、**ブート中**に投入 | 「YUIOS V0.10.18」応答 ✅ |
| YUI OS + `-it` / `-q`、**ブート後**に投入（tty／パイプ両方） | 無反応 ❌ |

→ tty か否かは無関係。投入タイミングのみで再現性が決まる。

### 2.2 ハング時の CPU 実測値

調査ビルド（`emu23_dbg_poc.c`、`ysd8001_tick` に定点観測を挿入）による 12 サンプル、全て同一傾向：

```
cyc=20000000  pc=0105 flags=00 pend=1 irq_stat=0000 ustat=0001
cyc=60000000  pc=00F7 flags=00 pend=1 irq_stat=0000 ustat=0001
cyc=160000000 pc=0116 flags=00 pend=1 irq_stat=0000 ustat=0001
（他 9 サンプルも pc は $00DB〜$0116 の範囲内）
```

- `flags` の `FL_IE`（`emu23_v111.c` L125: `0x80`）が**常時 0**＝割込禁止のまま
- `irq_pending=1`（IRQ0 タイマー）が**永久に未受理**のまま滞留
- PC は全サンプルが `$00DB`〜`$0116` の範囲内

### 2.3 PC 範囲のシンボル対応（`yuios_road2.sym`）

```
00c4 _irq_sched
00d0 _sched
00db _sched_chk      ← ループ先頭
0119 _sched_found    ← ループ出口（READY 発見時のみ）
```

→ CPU は **IRQ0_HANDLER 内のタスク探索ループ `_sched`〜`_sched_chk` を回り続けている**。

### 2.4 真因（実源該当行）

`IRQ0_HANDLER`（`.org $0030`）は入口で `DI` を実行する。その後の探索ループは以下の構造で、
**「1周しても READY が無かった場合」の脱出路が存在しない**。

```asm
_irq_sched:
    LDW  A, [CUR_TASK]
    STW  A, [L1_WK_B]          ; ★開始tidを保存しているが…
    ADDI A, #1
_sched:
    CMPI A, #16
    BLT  _sched_chk
    LDW  A, #0
_sched_chk:
    STW  A, [L1_WK_A]          ; ★L1_WK_B との比較が無い＝1周検出が無い
    ...（TCBアドレス計算）...
    LDW  B, [X]
    CMPI B, #1                 ; READY?
    BEQ  _sched_found
    LDW  A, [L1_WK_A]
    ADDI A, #1
    JMP  _sched                ; ★READY が無ければ永久に回る
```

`L1_WK_B` に開始 tid を保存しているにもかかわらず、**参照されていない**。実装漏れである。

### 2.5 対照：SYSCALL 側には正しく実装されている

`_sched_common`（`.org $02C0`）は同じ探索を行うが、1周検出とアイドル処理を持つ。

```asm
_sc_chk:
    LDW  B, [L1_WK_B]          ; ★開始tidと比較
    CMP  A, B
    BEQ  _sc_idle              ; ★1周した→アイドルへ
    STW  A, [L1_WK_A]
    ...
_sc_idle:
    EI
    NOP
    DI
    JMP  _sched_common         ; 割込を1命令分だけ通して再走査
```

→ **同一機能の 2 実装で片方だけ欠落している非対称**が本欠陥の正体である。

### 2.6 発症条件

`IRQ0_HANDLER` は、割込時のタスクが `state==RUNNING(2)` の場合のみコンテキストを保存し、
その際 `RUNNING→READY(1)` に落とす（L509-510）。この場合は自分自身が READY として発見されるため脱出できる。

**発症するのは、割込時のタスクが非 RUNNING（WAIT/アイドル）だった場合**である。
このとき保存はスキップされ（L483 `BNE _irq_sched`）、READY タスクが 0 個になり得る。

これがブート直後は入力が通り、全タスクが待機に入った瞬間に固まる理由を説明する。
シェルは `GETC` で UART 待ちに入るため、**入力を待っている状態そのものがハング条件**になる。

## 3. 修正方針

### 【v0.3】現行方針

**`_sched_chk` に 1周検出を追加し、READY タスクが 0 個なら `IRET` して割込元へ戻す。**

`IRQ0_HANDLER` は **run-to-completion（必ず短時間で抜ける）** を守る。
アイドルは**カーネルコンテキストの `_sc_idle` が担当する**という役割分担を明確化する。

### ~~【v0.2】旧方針（却下）~~

~~`_sched_chk` に `_sc_chk` と同一の1周検出を追加し、IRQ0 側にもアイドル処理 `_irq_idle`
（`EI / NOP / DI` ループ）を新設する。既に動作実績のある `_sc_idle` の構造をそのまま踏襲する。~~

**却下理由**: `_sc_idle` が安全なのは、そこが**割込ハンドラの外側（カーネルコンテキスト）**だからである。
同じ構造を**割込ハンドラの内側**に置くと、`EI` で受理した IRQ0 が `IRQ0_HANDLER` に再入し、
再入先でも READY が無いため再び `EI` …と無限に入れ子になる。**`IRET` の実行機会が永久に来ない**ため
スタックが単調に伸び続ける。§9 の実測を参照。

### 3.1 変更内容（2箇所）

**(1) 1周検出の挿入位置 —— ★状態チェックの「後」であること★（v0.5 で訂正）**

**v0.5 現行（正）**: 1周検出は TCB の状態チェック（`CMPI B,#1` / `BEQ _sched_found`）の**後**に置く。

```asm
_sched_chk:
    STW  A, [L1_WK_A]
    ...（TCBアドレス計算）...
    LDW  B, [X]
    CMPI B, #1
    BEQ  _sched_found           ; ← CUR_TASK 自身もここで拾える
    ; --- 1周検出（★状態チェックの後）---
    LDW  A, [L1_WK_A]
    LDW  B, [L1_WK_B]           ; B = 開始tid(= CUR_TASK)
    CMP  A, B
    BEQ  _irq_noready           ; 16個すべて検査済でREADY無し
    ADDI A, #1
    JMP  _sched
```

**訂正理由（実測により判明）**

1周検出を状態チェックの**前**に置くと、走査は `CUR_TASK+1 → 15 → 0 → CUR_TASK-1` で打ち切られ、
**`CUR_TASK` 自身が一度も検査されない**。`IRQ0_HANDLER` は割込時の RUNNING タスクを
`RUNNING→READY` に落とすが（L509-510）`CUR_TASK` は据え置くため、
**「唯一の実行可能タスクが直前まで走っていた自分自身」のケースで永久にスケジュールされなくなる。**

実測（`kernel_v12_9.asm` 暫定版・メモリ直読）:

```
UART_WAIT_TID=6  CUR_TASK=3  st0=3  st1=5  st2=5  st3=1(READY)
```

→ TCB3 が READY のまま放置され、`_sc_sched` を延々と回り続けた。

修正前（`kernel_v12_8` 以前）は 1周検出が無かったため走査が周回し 2 周目に自分自身を拾えていた。
**1周検出の追加がこの経路を塞いだ回帰である。**

### ~~**(1旧・v0.2〜v0.4)** `_sched_chk` 先頭に 1周検出を挿入~~

```asm
_sched_chk:
    LDW  B, [L1_WK_B]          ; ★追加: 開始tidと比較（読むだけ）
    CMP  A, B                  ; ★追加
    BEQ  _irq_noready          ; ★追加: 1周してREADY無し→IRETで割込元へ（v0.4改名）
    STW  A, [L1_WK_A]
    ...（以降は現行のまま）
```

**(2) `_irq_noready` を新設（v0.3 で内容を全面差替）**

```asm
_irq_noready:
    LDW  A, [IRQ_WK_A]         ; 中断時 A を復元
    LDW  B, [IRQ_WK_B]         ; 中断時 B を復元
    LDW  X, [IRQ_WK_X]         ; 中断時 X を復元
    IRET                       ; 割込元へ戻す（アイドルは _sc_idle が担当）
```

ラベル名は v0.2 の `_irq_idle` から **`_irq_noready` に改名**する。
「アイドルする場所」ではなく「READY 不在で何もせず戻る出口」であることを名前で表すため。

~~```asm~~
~~_irq_idle:~~
~~    EI~~
~~    NOP~~
~~    DI~~
~~    JMP  _irq_sched~~
~~```~~ ← **v0.2 方式・却下**

**復元内容の根拠（実源 `kernel_v12_9.asm` L453-456）**

`IRQ0_HANDLER` は入口で `DI` 後に `A → IRQ_WK_A` / `X → IRQ_WK_X` / `B → IRQ_WK_B` を退避する。
`_irq_noready` へ至る経路ではコンテキスト保存（TCB への保存）は行われていない
（非 RUNNING のため L483 `BNE _irq_sched` で保存をスキップしている）。
したがって **`IRQ_WK_*` の 3 本を戻して `IRET` すれば中断点の状態が完全に復元される**。

`IRET` は FLAGS を復元するため、割込元の `FL_IE` 状態もそのまま戻る。

**【v0.3】配置位置は v0.2 と同一（ラベル名のみ `_irq_noready` に変更）**

**【v0.2 追記・I-03 対応】配置位置の明示**

【v0.4】`_irq_noready:` は **`_sched` ループ末尾の `JMP _sched` の直後、かつ `_sched_found:` の直前**に置く（配置位置は v0.2 の `_irq_idle` と同一。ラベル名と中身のみ差替）。
`kernel_v12_8.asm` での該当箇所は以下（L515〜L539 相当）。

```asm
_sched_chk:
    ...
    LDW  B, [X]
    CMPI B, #1
    BEQ  _sched_found
    LDW  A, [L1_WK_A]
    ADDI A, #1
    JMP  _sched                ; ← 無条件分岐。ここで通常フローは必ず断たれる
                               ;    ★この直後に _irq_noready を置く★
_irq_noready:                  ; ← 新設（到達は BEQ _irq_noready からのみ）
    LDW  A, [IRQ_WK_A]         ; 【v0.4】v0.2 の EI/NOP/DI/JMP から全面差替
    LDW  B, [IRQ_WK_B]
    LDW  X, [IRQ_WK_X]
    IRET                       ; ← 割込元へ復帰。_sched_found へ落ち込まない

_sched_found:                  ; ← 既存。位置は変えない
    LDW  A, [L1_WK_A]
    ...
```

**通常フローが落ち込まないことの根拠（2点）**

1. `_irq_noready` の**直前は `JMP _sched`（無条件分岐）**。したがって `_sched_chk` 側から
   `_irq_noready` へフォールスルーする経路は存在しない。
2. 【v0.4】`_irq_noready` の**末尾は `IRET`**。したがって `_irq_noready` から
   `_sched_found` へフォールスルーする経路も存在しない。
   ~~（v0.2: 末尾も `JMP _irq_sched`（無条件分岐）のため落ち込まない）~~

→ `_irq_noready` への到達経路は **`_sched_chk` 先頭の `BEQ _irq_noready` のみ**である。

なお `IRQ0_HANDLER` は `.org $0030` 配置で、直近の次の `.org` は `$01C0`（`kf_r2_kern.asm` L574）。
現行の `_sched_found` 以降のコードは `$0119`〜であり、**追加 7 行（概算 16 バイト）を挿入しても
`$01C0` 境界には十分な余裕がある**。`.org` 重なり（hasm23 W001）は発生しない見込みだが、
実装後に W001 警告が出ないことを確認すること。

### 3.3 これで入力が通る理由

### 【v0.4】現行フロー（v0.3 方式）

1. 全タスク待機 → `_irq_noready` に到達 → `IRQ_WK_A/B/X` を復元して **`IRET`**
2. 割込元（カーネルの `_sc_idle`）へ復帰 → **`_sc_idle` の `EI` で割込許可**
3. 打鍵 → emu23 が `ysd8004_raise(bit0)` → IRQ1 受理
4. `IRQ1_HANDLER` が `rx_push` → `UART_STAT` WTC → `wake_uart_waiter` でシェルを READY 化
5. `IRET` で `_sc_idle` に復帰 → `DI` → `_sched_common` 再走査 → シェルを発見 → `_sc_found` で切替

**要点**: 割込許可は `_sc_idle`（割込ハンドラの**外側**）でのみ行う。
`IRQ0_HANDLER` は READY が無ければ即座に `IRET` して抜けるため、再入によるスタック蓄積が起きない。

### ~~【v0.2】旧フロー（却下）~~

~~1. 全タスク待機 → `_irq_idle` に到達 → `EI` で割込許可~~
~~2. 打鍵 → `ysd8004_raise(bit0)` → IRQ1 受理~~
~~3. `IRQ1_HANDLER` が `rx_push` → `wake_uart_waiter` でシェルを READY 化~~
~~4. `IRET` で `_irq_idle` に復帰 → `DI` → `_irq_sched` 再走査 → `_sched_found` で切替~~

**却下理由**: 手順1の `EI` が IRQ0 の再入を招き、手順4 の `IRET` に到達できない（§9 参照）。

## 9. v0.2 実装結果と却下理由（v0.3 新設）

### 9.1 実施内容（2026-08-04）

- T0（`L1_WK_B` grep 確認）: **PASS**
- `kernel_v12_9.asm` を作成し、v0.2 方式（`_irq_idle` に `EI / NOP / DI / JMP _irq_sched`）を実装
- ビルド健全性 B1〜B5: **全 PASS**（`_irq_idle` @ `$0122`、md5 `ed84f3d9928b0c6a32273e0ddca22c54`、W001 なし）

### 9.2 T1 結果: **FAIL**

```
$ ( sleep 5; printf 'ver\r' ) | ./emu23 yuios_road2.bin -it --disk disk.img
YUIOS Booted!
0YUI> 123M[YSD8002] total_cycles=181564381  elapsed=45391 ms
```

シェル応答が返らないうえ、**emu23 が HALT で終了**した（v0.2 実装前は終了しなかった）。

### 9.3 計測による原因確定

`emu23_dbg2_poc.c`（`ysd8001_tick` に `_irq_idle` 到達回数と SP の最小/最大を計測）による実測：

```
cyc=20000000  pc=00F2 sp=3FCA spmin=3FCA idle_hits=53164
cyc=100000000 pc=0117 sp=20C6 spmin=20C6 idle_hits=267540
cyc=180000000 pc=00F6 sp=01C2 spmin=01C2 idle_hits=481916
```

- `_irq_idle` には**到達している**（`idle_hits` が単調増加）→ 1周検出の実装自体は正しい
- しかし **SP が `$3FCA` → `$01C2` へ単調減少**（約 4 バイト/tick）
- `$0000` を割り込んでカーネル領域を破壊し HALT に至る

### 9.4 却下理由（構造的な誤り）

`_irq_idle` の `EI` でタイマー IRQ0 を受理すると `IRQ0_HANDLER` に**再入**する。
再入先でも READY タスクは 0 個のままなので再び `_irq_idle` に到達し `EI` する。
これが 100Hz で無限に繰り返され、**`IRET` の実行機会が一度も訪れない**。
`IRET` されない再入は積んだスタックを戻さないため、SP は単調減少する。

`_sc_idle` が安全なのは**割込ハンドラの外側**にあり、そこで受理した IRQ0 が
`IRET` で必ず戻ってくるからである。**同一のコード片でも、割込ハンドラの内側に置くと意味が変わる。**

### 9.5 得られた知見（kaizen 登録候補）

> **割込ハンドラの内側に `EI` を含む待機ループを置いてはならない。**
> ハンドラ内で割込を許可すると同一ハンドラへの再入が起こり、`IRET` の実行機会が失われて
> スタックが単調に伸び続ける。ハンドラは run-to-completion を守り、待機は
> カーネルコンテキスト（割込ハンドラの外）で行うこと。
>
> 系: 「実績のある既存コード片をそのまま流用する」判断は、**流用先の実行コンテキストが
> 同一であること**を確認して初めて成立する。コード片の同一性は安全性を保証しない。

**積み残し**: v0.3/v0.4 方式ではアイドル時に 100Hz でタイマー割込ごとの走査を繰り返すビジーループとなる。
省電力のため **ISA3.0（YSD8810）で WAI 相当命令を検討する**こと（§7.1）。
