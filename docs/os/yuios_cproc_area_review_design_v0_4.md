## 0. 結論（先出し）

**推奨は案B「Cランタイムの共有化 — カーネル成長予約 $2000-$3FFF の上半分 $3000-$3FFF をランタイム専用領域に割り当て、プロセス区画からランタイムを追い出す」**（v0.3: 配置を上端へ変更＝C-1）。

- Cプロセス区画 $D400-$DBFF（2KB）・辞書天井 $D3FF・PROC-LOAD-ADDR・**crt0 は不変**。
- 区画内の RUNTIME 768B が丸ごと CODE/DATA に転用でき、逼迫の根本原因（全プロセスで同一のランタイムを区画内に複製している構造）が消える。
- **カーネル定数（kernel_forth / tgt）の変更は 0 件。ただし ProcMgr（kernel_forth）に RT 版数照合ワードを 1 つ追加する**（v0.3・M-3 で正確化。v0.2 までの「変更対象は scc23・lnk23・文書のみ」は不正確だったので撤回）。その他の変更対象は scc23（出力モード追加）・lnk23（重なり検出）・ビルド手順書・memmap/ABI 文書。

## 2. 問題の本質

申し送り書 §2.3 のとおり、ランタイム 752B のうち 492B は使用有無に関係なく出力される。しかし細粒度化（応急処置）しても、`printf` 級のプログラムでは大半が必要になり効果が薄い（§4-1）。

**本質は「プロセスごとに同一内容のランタイムを区画内に複製している」構造**であり、区画サイズをいくら調整しても機能追加のたびに再逼迫する。ゆえに区画の再配分（案A）より、ランタイムを区画外へ出す（案B）を優先すべきである。

## 4. 案B 詳細

### 4.1 領域割当（memmap v2.5 案）

**v0.3（C-1・N-1 反映）: RT を予約の上端に置き、カーネル成長域を連続にする。**

| アドレス | サイズ | 用途 | 備考 |
|---|---|---|---|
| $1476-$2FFF | 約 7.0KB | カーネル成長域（連続） | 実終端 $1475 から RT 直下まで連続 |
| $3000-$3EFF | 3.75KB | **Cランタイム本体（RT-CODE）** | v2.08 実測 ~840B。unsigned 除算・32bit・float・printf 分を見込む |
| $3F00-$3FFF | 256B | **ランタイム・エントリテーブル（RT-JT）** | 「$3FFF 直下の固定テーブル」。先頭 4B: マジック+版数。以降 3B/エントリ `JMP abs`（最大 84 エントリ） |

（v0.2 案＝RT-JT $2000-$20FF／RT-CODE $2100-$2FFF／予約残 $3000-$3FFF は、カーネル成長域が $1476-$1FFF の約 2.8KB に分断されるため不採用。）

- **RT 領域はコードのみ**（書き込みなし）。memmap §3.1 の「$0000-$3FFF は write 禁止前提（FPGA で ROM 化候補）」および lnk23 R17（$0000-$3FFF を ROM 扱い・lnk23_v2_01.c L613）と整合する。
- **Ph.8（Level 2・MMU）への制約（v0.3・C-2）: MMU 設計は RT ページ（$3000-$3FFF）をユーザプロセスから read/exec 可能な共有マップにすること。** カーネル領域を丸ごとユーザから隠すと `JSR $3Fxx` が実行できず RT が呼べなくなる。
- ランタイムのワーク変数（`_C_MUL_*`/`_C_DIV_*`/`_C_MEMCPY_*`）は**プロセス区画内の固定オフセット**（現行 $DBE8-$DBFF）に据え置く。Level 1（1スロット）では絶対番地参照で問題なく、Level 2（MMU）でも「各プロセスの同一仮想番地」として自然に再入可能になる。

### 4.2 Cプロセス区画の再配分（案A' を併用）

RUNTIME 768B が空くので、区画内を以下に再配分する（数値はレビューで確定）。

| 領域 | 現行（v2.4） | 案（v2.5） | 差 |
|---|---|---|---|
| crt0 | $D400-$D43F（64B） | 不変 | — |
| CODE | $D440-$D77F（832B） | **$D440-$D9FF（1472B）** | +640B |
| RUNTIME | $D780-$DA7F（768B） | **廃止（共有化）** | −768B |
| DATA | $DA80-$DBE7（360B） | **$DA00-$DBBF（448B）** | +88B |
| ランタイムワーク（既存 12 変数） | $DBE8-$DBFF（24B） | **$DBE8-$DBFF（24B）・番地不変** | 0 |
| ランタイムワーク（拡張分・新設） | — | **$DBC0-$DBE7（40B）** | +40B → §5.2-2 の `_C_DIV_A/B` float 共用を解消（float 専用変数を新設） |

**v0.3（M-2）:** 既存ワーク番地は `#define C_XSAVE_ADDR 0xDBE8`（scc23_v2_07.c L418）の絶対値で、`--data-org`/`--runtime-org` に連動せず、`_C_MUL_A` 等は `EQU $%04X`（同 L3851-3858）で生成コードに埋め込まれる。`C_XSAVE` はユーザコード側の inc/dec 退避（同 L3174-3220）でも使われるため、**Dhrystone（ベアメタル）も $DBE8-$DBFF を使っている**。既存番地を動かすと Dhrystone の md5 が変わり §8.1 のビット一致が破れる。よって既存 12 変数は据え置き、拡張分は**下側 $DBC0-$DBE7 に新設**し、`--rt-shared` 時または float 使用時のみ参照させる。Dhrystone の生成コードに新設変数が現れないことを回帰で確認する。

### 4.3 呼び出し規約（ABI 追記事項）

1. scc23 は `JSR _cc_div` 等の**シンボル参照**を出力し、アドレスは `rt_jt_v<版>.inc`（EQU 群）で与える。区画内ランタイム出力は行わない。
2. 各ランタイム関数は RT-JT の固定スロット経由で呼ぶ（`JSR $3Fxx` → `JMP 実体`）。**スロット番号は一度割り当てたら不変**（追加は末尾のみ）。
   **RT-JT 採用の判断根拠（v0.3・C-4）:** .inc 方式（直接 JSR）でも RT 改版時は再アセンブルで済み再コンパイルは不要である。JT が真に効くのは**ユーザバイナリを SD（YUIFS）に保存し、RT 改版後も再ビルドせずロードし続ける運用**であり、YUI OS はその運用（mkfs_yuifs で SD イメージに格納したバイナリを ProcMgr がロード）を前提としているため JT を採用する。コストは呼び出しごとの JMP 1 命令と 256B。
   **規約の重さ（v0.4・M-5）:** Level 1 ではユーザバイナリ側に期待版数を持たせない（§4.3-3 (a)）ため、**「スロット番号不変・追加は末尾のみ」が SD 上の古いバイナリを守る唯一の仕組み**となる。守られなかった場合に検出する手段は無い。RT-JT のスロット表は `rt_jt_v<版>.inc` に版数付きで管理し、既存スロットの変更をレビュー必須事項とする。
3. **照合は ProcMgr（kernel_forth の `PROC_EXEC` 系）に置く（v0.3・M-3 で確定）。crt0（64B 固定・ProcMgr のロード手順に直結）には触れない。**
   **照合の射程（v0.4・M-5 で案 (a) に決定）:** 期待値が kernel_forth 内の定数である以上、比較の両辺は同じ yuios.bin から来るため、この検査は**「rt23.obj がリンクされているか／RT-JT 領域が破損していないか」の自己整合検査（マジック検査）**である。~~ロード時点の RT 版数がビルド手順書指定の版と一致するかの検査~~（v0.3 の記述は実質同じ検査であり、版数の意味づけは撤回）。
   - RT-JT 先頭 4B は **マジック 16bit（$3F00）＋版数 16bit（$3F02）の 2 語**（C-2）。Level 1 の ProcMgr は `$3F00 @ RT-MAGIC = IF … ELSE エラー終了 THEN` でマジックのみ検査する。版数語は将来（下記 (b)）のために領域を確保し、rt23.asm が出力する。
   - **RT-MAGIC = $E3A5**（アスキー列に見えない値。kernel_v12_11.asm.bin 5,238B 中に $E3A5／$A5E3 の並びは 0 回）。
   - **Level 2 の予定（案 (b)・KY41 で記録）:** ユーザバイナリに期待 RT 版数を持たせる。crt0 のコードは不変のまま、crt0 末尾の固定オフセットに 2B データ欄を設け（crt0 は scc23 生成のため「crt0 不変」と両立しうる・要確認）、ProcMgr が $3F02 と照合して古いバイナリを弾く。これにより C-4 の JT 採用根拠（SD 保存バイナリの継続使用）と照合設計が噛み合う。案 (c)（mkfs_yuifs のディレクトリエントリに持たせる）は mkfs_yuifs と ProcMgr の両方が変わるため不採用。
4. レジスタ規約・スタック規約は現行 YSD8800_ABI_spec のまま（JSR/RET は ISA2.3 に存在・ISA3.0 §8.6.2 でも USP 使用で継続）。

### 4.4 ビルド構成

| 成果物 | 生成方法 |
|---|---|
| `rt23_v<版>.asm` | scc23 に `--emit-runtime-only` を追加し、ランタイム全関数＋RT-JT を単独出力。**`.org $3000`（RT-CODE）→ `.org $3F00`（RT-JT）の昇順で出力すること**（v0.4・M-4a/C-1。正は §4.1）。hasm23 -c は最初の .org をセクション原点とし以降を 0 基準で詰める（hasm23_v1_04.c L223-229）ため、$3F00 を先に書くと $3000 へ戻れない。この順序なら rt23.obj は $3000-$3FFF の 4KB 一括セクションとなり、lnk23 の `mem_used[]` 検出で他セクションの誤侵入がその場で検出される |

| `yuios.bin` | lnk23 に SECTION rt を追加（道2・固定配置）。**前提: §5.2-1 の重なり検出バグを先に修正**（固定配置セクションが 1 つ増えるため）。修正仕様は **§8.2** 参照（Dhrystone の意図的重なりを壊さない方式で行う） |

## 8. Dhrystone との兼ね合い（v0.2 新設・レビュー指摘対応）

### 8.0 前提（実源）

Dhrystone は YUI OS 上では動作しない**別のベアメタル・ターゲット**である。

| 項目 | 値 | 実源 |
|---|---|---|
| scc23 引数 | `--code-org 0x0400 --data-org 0x4000 --runtime-org 0x0100` | Makefile L152（申し送り §6.2 では v2.08 で `0x0480` へ変更予定） |
| ハーネス | `startup_harness23_v17.asm` を `.org $0000`（110B） | 同 asm L48-74 |
| リンク | `SECTION code 0x0000 dhry.asm.bin` ＋ `SECTION harness 0x0000 …`（.bin 後勝ち） | Makefile L161 |
| 絶対ゲート | 819 / 48785 / P:20 / 21846B（scc23 v2.07・`-O0-strict`） | Makefile L8、yuios_build_procedure v1.14（申し送り §5.2-3 の正値） |
| 位置づけ | 21KB のため 2KB 区画には入らず、MMU（Ph.8）対象 | memmap v2.4 §14.7 |

Dhrystone と YUI OS が共有するのは **scc23 / hasm23 / lnk23 というツール**であり、**メモリマップは共有しない**。したがって本見直しで Dhrystone に影響するのはツール改修の副作用のみである。

### 8.1 絶対ゲートへの影響と `--rt-shared` を opt-in にする根拠

共有ランタイム（案B）では、ランタイム呼び出しが `JSR 実体` から `JSR RT-JT → JMP 実体` となり、**呼び出しごとに JMP 1 命令分の cycles とテーブル分のバイト数が増える**。Dhrystone をこの経路に乗せると絶対ゲート（DPS / cycles / バイト数）が必ず変わり、ツール改修の回帰チェックとしての意味を失う。

よって：
- scc23 の既定値と Dhrystone ビルド（Makefile L152 の CLI 指定）は**現行の区画内出力（直接 JSR）を維持**する。
- `--rt-shared` は YUI OS ユーザーランド専用の opt-in とする。
- 案B 実装後も Dhrystone ゲートは **819/48785/P:20/21846B にビット一致**しなければならない（scc23 改修時の回帰条件）。

### 8.2 lnk23 重なり検出修正（§5.2-1）の仕様 — Dhrystone の意図的重なりとの両立

申し送り §5.2-1 が「エラーが出ない」と指摘したリンク（`code 0x0000` と `harness 0x0000`）は、**Dhrystone が意図的に依存している後勝ち結合**である（dhry.asm.bin は先頭 $0000-$00FF がゼロ詰め、ハーネスがそこを上書きする）。`check_memory()`（lnk23_v2_01.c L1245）をそのまま有効化すると、**正常な Dhrystone ビルドが `section overlap` エラーで停止する**。

一方 yuios.bin は道2（hasm23 -c の .obj・load_addr/has_org 尊重）へ移行済みで、forth.obj=$5100 / kernel.obj=$0000 に分離されており重なりは存在しない（yuios_build_procedure v1.18 §4.11）。

修正仕様（案）：

| 項目 | 内容 |
|---|---|
| 検出の有効化（**v0.3・M-1 で方式変更**） | ~~スクリプトモードでも `check_memory()` を呼ぶ~~ → **不成立**。`check_memory()` は `lsecs[]`（`nlsecs`）を走査する（L577-630）が、`run_script()` は `lsecs[]` を構築せず `mem[a]`/`mem_used[a]` へ直接書く（L940）ため、早期 return を廃止しても `nlsecs==0` で何も検査されない。**修正は `mem_used[]` 方式**：`run_script()` のバイト書込箇所（L940）で `if (mem_used[a]) overlap++;` を行い、重なり範囲（先頭・末尾）を集計して 1 行で報告する。既定はエラー、`--allow-overlap` で警告に落とす |
| 重なりの判定単位 | **バイト単位**（`mem_used[]`）。ゼロ詰めも書込済みとして 1 になるため「ゼロ詰めを空きとみなす例外は設けない」方針と自然に整合する |
| `check_memory()` 経由を採らない理由（C-3） | `lsecs` を構築して `check_memory()` を通す設計にすると、`opt_machine` 既定 `MACH_BAREMETAL`（L214）の `text_end > 0x3FFF` 検査（L640-643）で yuios.bin（forth $5100）と Dhrystone（$0100-$5xxx）の両方が `-m none/force` 無しでは止まる。`mem_used[]` 方式はこの検査を経由しない |
| Dhrystone 側の対処 | Dhrystone ビルドも**道2へ移行**する（`hasm23 -c dhry.asm` → dhry.obj は `.org $0100` の has_org により load_addr=$0100、harness.obj=$0000）。これで重なりが消え、検出有効化と両立する |
| 後方互換 | .bin 後勝ちモードは廃止。どうしても必要な場合のみ `--allow-overlap` を明示させる（既定はエラー） |
| 回帰条件 | 道2 移行後の dhry_final.bin が**ビット一致**（21846B・md5）、ゲート 819/48785/P:20 一致。yuios.bin 56,416B・md5 不変。**依存点（v0.3・C-5）: このビット一致は `write_binary()` が $0000 から連続で書き出す（先頭アドレスを切り詰めない）ことに依存する**。lnk23 v2.02 でこの挙動を変えないこと |
| 版数 | lnk23 v2.01 → **v2.02**、Makefile v1.1 → v1.2（scc23 改良プロジェクト側の v1.2 改版予定と衝突するため要調整）、yuios_build_procedure v1.18 → v1.19 |

### 8.3 共有ランタイム経路の回帰ゲート（Dhrystone で覆えない部分）

Dhrystone は**ランタイム関数本体**の回帰にはなるが、以下は通らない：RT-JT 経由の呼び出し／版数照合／crt0 との結合／ProcMgr からの $D400 ロード。

よって案B には**YUI OS 側の回帰ゲート**を別途定める：

| ゲート | 内容 | 実源 |
|---|---|---|
| G-RT1 | `fib`（startup_proc v1.1 crt0 ＋ `--rt-shared` でコンパイル）を ProcMgr `PROC_EXEC` 経由で $D400 に実行し、期待出力一致 | Ph.5 Step4 本体（HANDOVER_CHAT55/56 系） |
| G-RT2 | `/` `%` `*`・`strcpy`・`memcpy` を使う最小 C テストで RT-JT の全スロットを 1 回以上通過 | 新規（レビューで対象関数を確定） |
| G-RT3 | **RT-JT 領域（$3F00 マジック）を故意に破壊した yuios.bin** で PROC_EXEC がエラー終了することを確認（v0.4・M-5 (a) に合わせて書き換え。~~版数不一致バイナリ~~ は Level 1 では作れないため Level 2 (b) の試験へ移す） | 新規 |

### 8.4 Dhrystone を共有ランタイムに乗せることは不可（明記）

RT 領域を $2000-$3FFF のいずれに置いても（v0.4・C-3 訂正）、Dhrystone のコード（$0480 から約 21.8KB＝$0480〜約$5B00）と**物理的に衝突**する。共有化は YUI OS ユーザーランド限定であり、Dhrystone は今後も区画内（ベアメタル）方式で維持する。

### 8.5 v0.1 からの位置づけ変更

§8.2 により、**lnk23 v2.02（重なり検出＋Dhrystone 道2 移行）は案B の前提条件**に格上げする。実装順は lnk23 v2.02 → Makefile/Dhrystone 道2 回帰 → scc23 → ビルド手順書 → G-RT1〜3。
