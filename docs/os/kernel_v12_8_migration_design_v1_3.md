**設計負債**（原則77）である。本設計書は、この負債を「直す前に記録」する
目的も兼ねる。

**本 v1.3 は Pre-0〜Pre-6 の全実測結果を反映し、v1.2 レビュー指摘 2件も反映した最終版。**

### 1.2 なぜ据え置きが継続したか（Why-Why 分析）

- Why-1: Makefile v1.1 改版時（CHAT121）に kernel 版数の同期が漏れた。
- Why-2: scc23 v2.04 対応の焦点が dhrystone 側（絶対ゲート 826→819）に絞られており、yuios 側は「対象範囲外」として意識から外れた。
- Why-3: V8-b 着手までは「yuios.bin を RTL で回す」場面が存在しなかったため、kernel v12.7/v12.8 差異が実害として顕在化する機会が無かった。
- Why-4: kernel v12.7→v12.8 移行の独立工程が明示的に立てられていなかった（暗黙に「emu23 動作確認完了 = 完了」と扱われた）。

### 1.3 再発防止（原則追加候補・§10 に総括）

**候補原則A**：ツール／サブシステム（RTL・emu23・kernel・scc・hasm・lnk）のいずれかで「実装契機の変更」を行った場合、他サブシステムの追随状況を Makefile（版数・KERN_SRC 参照・絶対ゲート）に **明示リスト**で書き留め、追随完了までは Makefile ヘッダに「追随未完タグ」を残す。

**候補原則B**（v1.2 で追加）：実装差分のバイト数予測は、命令サイズの単純加算ではなく、**メモリマップ制約（`.org` パディング・セクション境界）まで含めた実測ベース**で確定する。「実装差分の存在」を確認したければ、バイナリ内の**特徴バイトパターンの直接検索**を判定基準にすべき。

**候補原則C**（v1.3 で追加）：**コメント記述と実出力の照合も実源照合（原則76）の一環**とする。ソースコメントに書かれた文字列（例："0123MD" マーカー）が実際にどのような形式で出力されるか（プロンプト分離・空白挿入等）は実行して確認する。設計書の判定基準に「特定文字列」を組み込む場合、必ず実測出力で最終形を確定させる。

### 2.2 yuios 絶対ゲート値の再凍結（v1.2 で根本改訂・v1.3 で継承）

| 項目 | v1.1 予測 | v1.2/v1.3 実測確定 |
|---|---|---|
| yuios 絶対ゲート（サイズ） | 56,424B（+8B 予想） | **56,416B（v12.7 と同一・不変）** |
| yuios 絶対ゲート（内容） | サイズ一致のみ | **サイズ 56,416B ＋ TCR-ACK バイトパターン `21102300230190fc` が 1 箇所存在** |
| リファレンス `REF_BIN` | `yuios_ref_road2_I3.bin`（v12.7 由来） | **`yuios_ref_road2_I4.bin`（v12.8 由来・Pre-5 で凍結）** |
| 旧リファレンス扱い | 現用 | **`yuios_ref_road2_I3_archived.bin` にリネーム保持**（Pre-5 で退避完了） |

**サイズが不変である構造的理由**（v1.2 §2.2 継承）：

kernel_v12_8.asm には kernel_v12_7.asm と同一の `.org` 指定が並ぶ（$0020, $0030, $01C0, $02C0, $0380, ...）。v12.8 で追加された +8B の TCR-ACK 命令列（`.org $0030` セクション内・具体位置 offset $003D）は、次の `.org $01C0` までのゼロパディング領域（$01C0 - $0030 = **400B の余裕**）が -8B されるだけで、次のセクション以降のアドレスは変わらない。結果として：

- kernel .obj のコードサイズ：v12.7=5,238B、v12.8=**5,238B**（変わらず）
- kernel .obj のシンボル数：v12.7=167、v12.8=**169**（TCR / TCR_ACK_REARM の 2 EQU 分のみ増加）
- yuios.bin のトータルサイズ：v12.7=56,416B、v12.8=**56,416B**（変わらず）

これは YSD8800 ISA / hasm23 の `.org` 挙動として正常。もし追加サイズが 400B 枠を超えていたら hasm23_v1_04.c L915-917 の `.org backward` エラーで**ビルド失敗**する安全機構がある（v1.2 レビュー指摘2 反映）。

**新旧リファレンスのハッシュ値**（Pre-5 で確定）：

- 新（現用・I4）：MD5 = `7a6a5b87afb1ef9f413a7d0c1360e706`
- 旧（退避・I3_archived）：MD5 = `a1f1001fe96d9c2e7b4db8e47d4046e4`
- サイズ同一・内容 **271バイト差**のため、ハッシュ値照合が識別の唯一の手段。

### 2.3 新 AC-1（TCR-ACK バイトパターン方式・v1.2 で新設・v1.3 で継承）

**新 AC-1**：`yuios_road2.bin` に対し、**TCR-ACK 命令列の 8B バイトパターン `21 10 23 00 23 01 90 fc`**（連続 16 進文字列 `21102300230190fc`）が **1 箇所ちょうど**存在すること。

**弁別性の実証**（Pre-3 実施済）：
- v12.7 版バイナリ：0 hit（TCR-ACK パターン存在せず）
- v12.8 版バイナリ：**1 hit**（offset $003D に存在）

**Pre-5 での再確認**（新旧リファレンスに対する適用）：
- yuios_ref_road2_I4.bin（v12.8 由来・新）：1 hit ✅
- yuios_ref_road2_I3_archived.bin（v12.7 由来・退避）：0 hit ✅

**判定コマンド**（環境非依存版）：

```bash
od -An -tx1 -v yuios_road2.bin | tr -d ' \n' | grep -oE '21102300230190fc' | wc -l
# 期待値: 1
```

`xxd` が無い環境でも動作するよう `od + tr + grep` で構成。

**バイトパターンの根拠**（実源・v1.2 §2.3 継承）：

| 命令 | ISA2.3 バイト表現 | 根拠 |
|---|---|---|
| `LDW B, #$0023` | `21 10 23 00` | hasm23_v1_04.c L763 / L1064-1073 の LDW opcode=$21・B_reg=$10・imm16 little-endian |
| `STW B, [$FC90]` | `23 01 90 fc` | 同・STW opcode=$23・B_reg=$01・abs16 little-endian |

- kernel_v12_8.asm L353 `TCR_ACK_REARM EQU $0023` = TIMER_EN($01) | IRQ_EN($02) | IRQ_ACK($20) = $23
- kernel_v12_8.asm L352 `TCR EQU $FC90`
- kernel_v12_8.asm L458-459 で `LDW B, #$TCR_ACK_REARM` / `STW B, [TCR]`

### 2.4 Dhrystone 絶対ゲートは不変

Makefile v1.1 → v1.2 で **819/48785/P:20 変更なし**。

Dhrystone は kernel を積まない C 単体プログラム（`dhry_timer.c` + `startup_harness23_v17.asm`）で構成される。kernel v12.7/v12.8 の差異は Dhrystone の実行経路に影響しない。**Pre-6 実測で 819/48785/P:20 完全一致を実証**。

## 4. 工程分割理由（原則87 系）

「kernel v12.7 → v12.8 化」と「V8-b（yuios.bin RTL 実行）」を **同一工程で実施しない**のは、失敗時の弁別可能性を確保するため。

同時実施した場合：
- V8-b で失敗した際、「v12.8 実装バグ」／「RTL バグ」／「新絶対ゲート値誤設定」のいずれが原因か切り分け不能。

分割実施の場合：
- Pre 工程で emu23 上の v12.8 動作を確定 → RTL 側の凍結との整合が確認できた状態で V8-b に着手 → V8-b で失敗した場合は「RTL vs emu23 の差」に切り分けが絞られる（原則87：弁別能力のある負例）。

**Pre 工程内でも原則87 の直接適用**：
- AC-1：v12.7 版=0 hit / v12.8 版=1 hit（バイトパターン検索）
- AC-2：v12.7 版=`123MD` 未到達 / v12.8 版=`123MD` 到達（emu23 動作対比）
- AC-3：新旧リファレンスの MD5 明示区別
- AC-4：新リファレンスとの MD5 完全一致（自己整合性）

**すべての AC が弁別性を持つ**（v1.3 で総括）。

## 9. Pre 工程実施時の教訓（原則76・原則87 の運用強化）

### 9.1 教訓1（原則76 の適用範囲拡張）

実源照合は「命令サイズ計算」だけでは不十分。**メモリマップ制約（`.org` パディング・セクション境界）まで含めた実源照合**が必要。今回、hasm23_v1_04.c で LDW=4B・STW=4B を確定させたのは正しかったが、それが **yuios.bin のトータルサイズにそのまま反映される**という前提が誤っていた。ISA レベルの命令サイズと、リンク後のバイナリレイアウトは別の層。

### 9.2 教訓2（原則87 の判定基準構造の妥当性）

「弁別能力のある判定基準」を立てる際、**判定基準自体の構造妥当性**も確認すべき。「サイズ一致」は**サイズが変わる保証がある場合のみ**弁別に使える。今回のように `.org` パディングで吸収される変更では、サイズ判定は弁別性を持たない。より堅牢な判定基準は「**バイナリ内の特徴バイトパターン検索**」など、実装差分の存在を直接確認する方式。

### 9.3 教訓3（設計予測の実源事前検証）

「+8B ちょうど増える」という予測は、実際にビルドして確認するまで検証しなかった。今後、サイズ予測を判定基準に組み込む場合は、**設計書起票時に暫定ビルドで実測確認**することを推奨。

### 9.4 教訓4（v1.3 新設・コメント記述と実出力の照合）

**ソースコメントに書かれた文字列（例：kernel_forth_v0_10_18.fs L34「非回帰=0123MD」）が実際にどのような形式で出力されるかは実行して確認する必要がある**。今回、コメント上の "0123MD" は、実出力では `0YUI> 123MD` としてプロンプト末尾の "0" と非回帰マーカーの間に空白が挟まる形で出力されていた。設計書 v1.2 では判定文字列を "0123MD" と記載していたが、v1.3 で "123MD" に修正。

**再発防止**：設計書の判定基準に「特定文字列」を組み込む場合、必ず実測出力で最終形を確定させる。コメント記述は仕様ではなく設計者の意図の表現であり、実出力とは別物。

### 9.5 教訓5（v1.3 新設・打切り手段の選定）

`emu23 -n <STEPS>` は「N ステップ実行してトレース出力」オプションで、UART 出力が制御される可能性がある。**「一定時間で強制終了して UART 出力を保持する」用途には `timeout` コマンド（SIGTERM）の方が確実**。設計書 v1.1 レビュー §5.4 の 3 案（`-n` / `timeout` / watchpoint）から `-n` を選んでいたが、Pre-4 実測で問題が判明。判定基準の実行手段は複数案を Pre 工程で実測比較すべき。

### 9.6 判定基準立案チェックリスト（v1.2 で提案・v1.3 で拡張）

1. [ ] 判定基準の**変化条件**は本当に成立するか？（サイズ変化なら「サイズが変わる保証」があるか？）
2. [ ] 判定基準の**変化しない場合**（同一結果になる場合）を想定したか？
3. [ ] 判定基準は**弁別性**を持つか？（対比する 2 状態で必ず異なる結果を返すか？）
4. [ ] 判定基準は**実測可能**か？（判定コマンドが環境依存で動作不能にならないか？）
5. [ ] 判定基準は**偶然の一致**（偽陽性）を排除できるか？（パターンの一意性は保証されるか？）
