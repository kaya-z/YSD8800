## 1. 文書の目的とスコープ

### 1.1 目的

本書は、Ph.3.5-c で確定した **MAX_TASKS = 16 / POOL_SIZE = 32** の前提に基づき、YUI OS の物理メモリ配置を再設計する。

### 1.2 解決すべき問題

`HANDOVER_CHAT22.docx` および現行 v1.2 メモリマップで露呈した以下の問題を恒久的に解決する：

1. **タスクスタック領域の物理衝突**（v0.11.3 で暫定修正済、本書で正式設計）
   - 旧設計：CALL 256 + DATA 256 = 512B 必要、GAP は $100 のみ
   - tid=N のデータ範囲と tid=N+2 のコール範囲が完全重なり
2. **TCB プール容量不足**（8 タスク×80B → 16 タスク×80B に拡大必要）
3. **MsgPool（IPC4 Pool 方式）の配置領域未確保**（512 B 新規必要）
4. **カーネル変数領域と Forth 領域の境界曖昧化**（review12.txt 指摘）
5. **MMIO 境界の暗黙化**（`$FC80-` 以降を「絶対 RAM 利用禁止」と明示する必要）

### 1.3 スコープ

**本書に含むもの：**
- アドレス空間全体（$0000-$FFFF）の領域分割と境界確定
- 各領域の用途・容量・成長余地
- 新旧アドレス対照表
- 既存コード／Forth 定数の修正箇所網羅
- スタック worst-case 解析

**本書のスコープ外：**
- TCB レイアウトの変更（→ TCB 設計 v1.1 で確定済）
- IPC4 アルゴリズム（→ IPC4 Pool 設計 v1.1 で確定済）
- Ph.4 以降の FileMgr/Shell/libc の具体実装（領域**予約のみ**確保）

### 1.4 設計上の前提

YSD8800 の現状から：
- **総アドレス空間：** $0000-$FFFF（64 KB）
- **MMIO：** $FC80-$FFFF（128 B）固定、これ以降は RAM 利用禁止
- **ベクタテーブル：** $0000-$000F（16 B、ROM 性質、変更不可）
- **カーネルコード（Force）：** ROM 領域として扱う（$0010 以降）

## 3. 設計方針

### 3.1 全体方針

1. **「最大消費量」ベースで領域を確保する**（論理的な区切りでなく実消費量）
2. **将来増殖が確実な領域（Forth 辞書、カーネル変数）には成長予約を付与する**
3. **MMIO は $FC80- に固定、それ以降は絶対 RAM 利用禁止**（FPGA 実装時の制約とも整合）
4. **既存 API 互換性を最大限維持**（Forth `CONSTANT` の値は再配置時のみ変更）
5. **アドレス対照表で機械的な修正を可能にする**（網羅性の保証）

### 3.2 領域分離原則

レビュー指摘 #4 を反映し、以下の 3 ゾーンに分割：

| ゾーン | 範囲 | 性質 |
|---|---|---|
| **カーネルコード**（ROM 性質） | $0000-$3FFF | 実行コード、変更不可 |
| **カーネルデータ**（RAM、固定） | $4000-$4FFF | TCB / カーネル変数 / MsgPool / カーネル予約 |
| **Forth ゾーン**（RAM、可変） | $5000-$EFFF | Forth 辞書、Forth ワーク、テストバッファ |
| **タスクスタック**（RAM、固定） | $F000-$FBFF | 16 タスク × 2 スタック |
| **OS 共有変数**（RAM、固定） | $FC00-$FC7F | ドライバ変数、IPC 共有等 |
| **MMIO**（I/O） | $FC80-$FFFF | UART / SD / IRQ コントローラ等 |

「カーネル」と「Forth」を**完全に別ゾーンに分離**することで、片方の成長が他方を侵食する事故を防ぐ。

## 4. 新メモリマップ（v1.1 確定版）

### 4.1 全体マップ

**v1.1 で確定**：案 J（stack guard 64 B 新設）＋ KERN_SP 専用確保 ＋ MMIO サイズ修正。

| アドレス範囲 | サイズ | 用途 | 種別 | 成長方向 |
|---|---|---|---|---|
| $0000–$000F | 16 B | ベクタテーブル | write 禁止前提 | 固定 |
| $0010–$0FFF | 4 KB | カーネルコード本体（kernel.asm） | write 禁止前提 | 上方向（必要に応じ拡張） |
| $1000–$1FFF | 4 KB | カーネルコード拡張領域（IRQ ハンドラ等） | write 禁止前提 | 上方向 |
| $2000–$3FFF | 8 KB | **カーネルコード成長予約** | write 禁止前提 | (予約) |
| $4000–$44FF | 1280 B | **TCB プール（16 タスク × 80 B）** | RAM | 固定 |
| $4500–$46FF | 512 B | **MsgPool（32 entry × 16 B）** | RAM | 固定 |
| **$4700–$477F** | **128 B** | **カーネル専用スタック（KERN_SP）** ★v1.1 新設 | RAM | 下方向 |
| **$4780–$47BF** | **64 B** | **カーネルワーク変数（frequently used: L1_WK / IRQ_WK / IPC4_WK 等）** ★v1.1 細分 | RAM | 上方向 |
| **$47C0–$47FF** | **64 B** | **カーネルワーク予約（reserved growth）** ★v1.1 新設 | RAM | (予約) |
| $4800–$4FFF | 2 KB | **カーネル成長予約**（FileMgr / inode / block cache 等） | RAM | (予約) |
| $5000–$BFFF | 28 KB | Forth 辞書（Dictionary） | RAM | 上方向 |
| $C000–$DFFF | 8 KB | **Forth コード成長予約** | RAM | (予約) |
| $E000–$EBFF | 3 KB | Forth ワークスペース（HERE 等） | RAM | 上方向 |
| $EC00–$EFFF | 1 KB | テストバッファ（TEST_SRC_BUF / TEST_DST_BUF 等） | RAM | 固定 |
| $F000–$F7FF | 2 KB | **コールスタック領域（16 タスク × 128 B）** | RAM | 下方向 |
| $F800–$FBFF | 2 KB | **データスタック領域（16 タスク × 128 B）** | RAM | 下方向 |
| **$FC00–$FC3F** | **64 B** | **stack guard 領域（$A55A 埋め、MMIO 突入防止）** ★v1.1 新設 | RAM | 固定 |
| **$FC40–$FC7F** | **64 B** | OS 共有変数（UART/STOR ドライバ変数等、scheduler 共有） ★v1.1 縮退 | RAM | 固定 |
| $FC80–$FFFF | **896 B** ★v1.1 修正 | MMIO（UART / SD / IRQ コントローラ等） | I/O | **絶対 RAM 禁止** |

**合計内訳（v1.1 修正）：**
- write 禁止前提領域: 16 KB（コード 8 KB + 予約 8 KB）
- カーネル RAM: 4 KB（TCB 1280 B + MsgPool 512 B + KERN_SP 128 B + ワーク 64 B + 予約 64 B + カーネル成長予約 2 KB）
- Forth RAM: 40 KB（辞書 28 KB + 予約 8 KB + ワーク 3 KB + テスト 1 KB）
- スタック RAM: 4 KB（コール 2 KB + データ 2 KB）
- stack guard: 64 B（v1.1 新設）
- OS 共有 RAM: 64 B（v1.1 縮退）
- MMIO: **896 B**（v1.1 修正、$FFFF - $FC80 + 1 = $0380 = 896）

**v1.1 重要設計判断：**

1. **「write 禁止前提領域」表現**（review16.txt 中程度④）：旧表記「ROM」は emu23 上では物理的に RAM として実装されているため誤解を生む。FPGA 化時には ROM 化候補だが、現状は「write 禁止のお約束」で扱う領域として表現を厳密化。
2. **stack guard 領域 $FC00-$FC3F**（review16.txt 重大②）：データスタックと OS 共有変数の間に 64 B のガードを設置。データスタックオーバーフロー時に即 MMIO 突入することを防ぐ。$A55A 埋めで初期化し、診断ワード `CHK-GUARD`（§7 参照）で破壊検出可能。
3. **KERN_SP 専用領域 $4700-$477F**（review16.txt 論点 2）：旧設計の「タスクスタック流用」を完全に排除。kernel context と task context の物理分離により、SYSCALL / nested IRQ / panic dump / VFS 等の将来拡張に備える。
4. **カーネルワーク領域の細分**（review16.txt 推奨）：frequently used (64 B) と reserved growth (64 B) に分けることで、将来のワーク変数追加時の整理が容易に。
5. **MMIO サイズ計算の正確化**：$FFFF - $FC80 + 1 = 896 B。FPGA 実装時のアドレスデコーダ設計の前提となるため、正確な値を記載。

### 4.2 MMIO 境界（$FC80-）の固定化

レビュー指摘 #3 を反映し、以下を**設計原則**として確定：

> **$FC80 以降は MMIO 専用領域。RAM として使用してはならない。**

具体的なデバイス配置（kernel_v11_3.asm 由来）：

| アドレス | デバイス | 用途 |
|---|---|---|
| $FC80 | UART_TX | UART 送信 |
| $FC82 | UART_RX | UART 受信 |
| $FC84 | UART_STAT | UART ステータス |
| $FCA0-$FCB0 | YSD8003 SD | ストレージ I/F |
| $FCB2 | IRQ_STAT | YSD8004 IRQ ステータス |
| $FCB4 | IRQ_MASK | YSD8004 IRQ マスク |
| $FCB6-$FFFF | (予備) | 将来デバイス用 |

FPGA 実装時のアドレスデコーダもこの境界に整合させる。

### 4.3 MsgPool 専用領域の新設

IPC4 Pool 設計 v1.1 で確定した 32 entry × 16 B = 512 B のプールを、**TCB プール直後**に配置：

```
$4000  ┌──────────────────────────┐
       │ TCB プール (1280 B)      │  16 task × 80 B
$44FF  └──────────────────────────┘
$4500  ┌──────────────────────────┐
       │ MsgPool (512 B)          │  32 entry × 16 B
$46FF  └──────────────────────────┘
$4700  ┌──────────────────────────┐
       │ カーネルワーク変数 (256 B)│
$47FF  └──────────────────────────┘
```

設計判断：
- **TCB と MsgPool を隣接**：cache locality（YSD8800 にキャッシュは無いが、将来 FPGA 拡張時に有利）
- **MsgPool 先頭 = $4500**：16 B 境界に揃い、tid×16 のインデックス計算が簡素
- **境界 $46FF / $4700 は明確**：枯渇診断時のメモリダンプが見やすい

### 4.4 カーネル成長予約領域の意義

`$4800-$4FFF`（2 KB）を「カーネル成長予約」として確保。  
review12.txt / review14.txt で挙げられた将来需要：

| 想定用途 | 推定サイズ |
|---|---|
| Scheduler work（priority queue 等） | ~64 B |
| Inode cache | ~256 B |
| Block cache | ~512 B |
| Pathname buffer | ~256 B |
| TTY line buffer | ~128 B |
| Semaphore / mutex 構造体 | ~128 B |
| Other（timer 構造体、port table 等） | ~256 B |
| **合計見込み** | **~1.6 KB** |

→ 2 KB の予約で十分カバー可能。

### 4.5 Forth 成長予約領域

`$C000-$DFFF`（8 KB）を「Forth コード成長予約」として確保。  
review12.txt 指摘「FileMgr / Shell / libc / compiler runtime が入ると E000- だけでは足りない」に対応：

| 想定用途 | 推定サイズ |
|---|---|
| FileMgr 本体 | ~3 KB |
| Shell 本体 | ~2 KB |
| libc 互換ワード群 | ~2 KB |
| 辞書最終末尾余裕 | ~1 KB |
| **合計見込み** | **~8 KB** |

辞書本体は $5000-$BFFF（28 KB）に置き、足りなくなったら $C000- まで拡張する設計（lnk23 の SECTION 順序で対応）。

**【v1.1 注記：将来不足可能性】**（review15.txt 中程度①）
本見積もり（合計 ~8 KB）は楽観的である可能性がある。Forth は辞書膨張しやすく、特に：
- debug ワード群（dump、trace、breakpoint 等）
- 文字列処理ワード（string、format、parse）
- パス処理ワード（path、glob、resolve）
- パーサ関連ワード

が増えると 8 KB 予約を超過する可能性がある。
Ph.4 以降の FileMgr / Shell 実装時に予約が逼迫したら、メモリマップ設計書 v2.0 で再配置を検討する。具体的には：
- カーネル成長予約（$4800-$4FFF, 2 KB）の余剰部分を Forth 側に移譲する
- テストバッファ（$EC00-$EFFF, 1 KB）を非検証時には Forth 領域として使用可能にする

辞書 HERE 値の監視（lnk23 リンクログ／Forth 起動時 HERE 出力）で枯渇を早期検出する（§9 K26 参照）。

## 6. スタック worst-case 解析

レビュー指摘 #5（review14.txt）に応えるため、各タスクのスタック消費を解析する。

### 6.1 コールスタック（return アドレススタック）の worst-case

#### 6.1.1 通常タスクの IPC4 CALL 経路

```
USER: IPC4-CALL
  ├─ Forthレベル：DOCOL の RSP push   = +2 (return addr)
  ├─ アセンブラ JSR 多段：典型 2-3 段  = +6
  ├─ DI/EI 区間内の関数呼出         = +4
  └─ スケジューラ JSR チェイン        = +6
合計： ~18 B（worst case）
```

#### 6.1.2 IRQ ハンドラのネスト

```
IRQ0 (timer):
  ├─ ハードウェア push: PC + FLAGS    = +4
  ├─ ハンドラ内で A/B/X 退避        = +6
  └─ scheduler 呼出までの JSR       = +4
IRQ1 (UART) が IRQ0 直後に発火する場合（マスク許可時）:
  └─ IRQ1 ハンドラがさらに +14
合計： ~28 B（双方発火 worst case）
```

#### 6.1.3 IPC4-CALL ＋ IRQ の合成 worst case

通常 CALL 中に IRQ が両方発火するシナリオ：
- 通常 18 B + IRQ 28 B = **46 B**

#### 6.1.4 nested JSR の制約

- Forth カーネル内では IPC4 や TASK プリミティブが多段の JSR チェインを構成
- Force コンパイラの実測：DOCOL+ INNER + 共有ワード呼出で典型 8 段（16 B）
- worst case で 16 段 ≈ 32 B

#### 6.1.5 コールスタック合計 worst case

| 項目 | サイズ |
|---|---|
| 通常 IPC4-CALL チェイン | 18 B |
| IRQ0 + IRQ1 ネスト | 28 B |
| Forth ワード深いネスト | 32 B |
| 安全マージン | 20 B |
| **合計** | **~98 B** |

→ **コールスタック 1 タスク 128 B**（$80）あれば余裕。

### 6.2 データスタック（パラメータスタック）の worst-case

#### 6.2.1 通常 Forth 演算

- DSP は X レジスタ管理、ワード境界で 2 B push/pop
- 典型 Forth ワードは 4-8 個のスタック深度
- `R> >R` 等で一時退避するパターンあり

#### 6.2.2 IPC4 メッセージ受け渡し

- IPC4-CALL: msg[4] + tid = 5 word push（pre）／ reply 4 word push（post）
- IPC4-RECV: 4 word push
- 一時的に 10 word（20 B）程度

#### 6.2.3 Force コンパイラ実行時

- compile 中に locals/temp で 16 word 程度（32 B）が見込まれる

#### 6.2.4 Dhrystone 等のベンチマーク

- 構造体ローカル展開で 20 word 程度（40 B）

#### 6.2.5 データスタック合計 worst case

| 項目 | サイズ |
|---|---|
| 通常 Forth | 16 B |
| IPC4 ピーク | 20 B |
| Compiler runtime | 32 B |
| Dhrystone | 40 B |
| 安全マージン | 20 B |
| **合計** | **~128 B** |

→ **データスタック 1 タスク 128 B**（$80）あれば余裕。

### 6.3 1 タスクあたりのスタック容量決定

| 項目 | 容量 |
|---|---|
| コールスタック | 128 B（$80）+ 余裕 64 B = **192 B（$C0）** |
| データスタック | 128 B（$80）+ 余裕 64 B = **192 B（$C0）** |
| GAP（衝突防止） | **0 B**（192 + 192 = 384 B = $180、ぴったり配置） |

### 6.3 1 タスクあたりのスタック容量決定

§6.1 と §6.2 の worst-case 解析より：

| 項目 | worst-case | 余裕込み |
|---|---|---|
| コールスタック | 98 B | **128 B（$80）** |
| データスタック | 128 B | **128 B（$80）** |
| 1 タスク合計 | 226 B | **256 B（$100）** |

**TASK_STK_GAP = $100**（コール $80 + データ $80）と確定する。

### 6.4 16 タスク全体のスタック領域配置

#### 6.4.1 配置方針：コール／データの**完全領域分離**

旧設計の根本欠陥は「同一領域内にコールスタックとデータスタックを交互配置」していたことである：

```
[旧設計（衝突あり）]
$F800  ┌─────────┐
       │ tid=N データ │
       │ tid=N コール │
       │ tid=N+1 データ│ ← tid=N コールと衝突しうる
       │ tid=N+1 コール│
       │ ...           │
$FBCF  └─────────┘
```

新設計では**コール領域とデータ領域を物理的に独立**させる：

```
[新設計（衝突不可能）]
$F000  ┌──────────────────────────────┐
       │ コールスタック領域 ($800=2KB)│ 16 タスク × $80
$F7FF  └──────────────────────────────┘
$F800  ┌──────────────────────────────┐
       │ データスタック領域 ($800=2KB)│ 16 タスク × $80
$FBFF  └──────────────────────────────┘
```

#### 6.4.2 配置サイズの正当性

- 16 タスク × $80（コール）= $800 = 2 KB
- 16 タスク × $80（データ）= $800 = 2 KB
- 合計 $1000 = 4 KB
- 配置：$F000-$FBFF（4 KB）にちょうど収まる

#### 6.4.3 アドレス計算式

```
CALLSTK_TOP(tid) = $F000 + (tid + 1) × $80 - 1   （= $F07F when tid=0）
DATASTK_TOP(tid) = $F800 + (tid + 1) × $80 - 1   （= $F87F when tid=0）
```

アセンブリ実装：`tid << 7` で 1 命令計算可能（hasm23 の SHL 対応）。

#### 6.4.4 旧設計との決定的違い

> **旧：「コール頂上から下に $100 下げてデータ頂上」という相対配置**
> → 隣接 tid のスタックが重なるリスク常時あり
>
> **新：コール領域とデータ領域が完全に独立した連続ブロック**
> → 物理的に重なれない構造

**衝突可能性をゼロにする設計上の不変条件**：
- `(tid+1) × $80 ≤ $800` であること（コール側）→ tid ≤ 15 で OK
- `(tid+1) × $80 ≤ $800` であること（データ側）→ tid ≤ 15 で OK
- → **MAX_TASKS = 16 まで確実に衝突しない**

#### 6.4.5 タスクごとの配置詳細

| tid | CALLSTK_TOP | DATASTK_TOP | コールスタック範囲 | データスタック範囲 |
|---|---|---|---|---|
| 0  | $F07F | $F87F | $F000-$F07F (128 B) | $F800-$F87F (128 B) |
| 1  | $F0FF | $F8FF | $F080-$F0FF (128 B) | $F880-$F8FF (128 B) |
| 2  | $F17F | $F97F | $F100-$F17F (128 B) | $F900-$F97F (128 B) |
| ... | ... | ... | ... | ... |
| 15 | $F7FF | $FBFF | $F780-$F7FF (128 B) | $FB80-$FBFF (128 B) |

### 6.5 スタック設計の最終確定

| 項目 | 値 |
|---|---|
| コールスタック領域 | $F000-$F7FF（2 KB） |
| データスタック領域 | $F800-$FBFF（2 KB） |
| 1 タスクあたりコール容量 | 128 B（$80） |
| 1 タスクあたりデータ容量 | 128 B（$80） |
| アドレス計算 | `BASE + (tid+1) × $80 - 1`（tid << 7 で 1 命令） |
| **衝突可能性** | **なし**（領域が物理的に分離されている） |

**Ph.3.5-b の最重要設計判断：** 旧設計で根本欠陥だった「コール／データ混在配置」を**完全分離**することで、HANDOVER_CHAT22 で発生したスタック衝突バグを**構造的に再発不能**にする。これは単なるアドレス変更ではなく、設計の不変条件を変える本質的修正である。

### 6.6 スタック watermark 診断要件（v1.1 新設）

レビュー指摘（review15.txt 中程度②、review16.txt 論点 3）に応え、**設計要件**を明記する（実装は Ph.3.5 実装フェーズに持ち越し、案 A）。

**要件：**
- スタック領域および guard 領域は**起動時に既知値で初期化可能な配置**とする
- コール／データスタック未使用部：**$0000 で初期化**（push されると上書きされる）
- guard 領域 ($FC00-$FC3F)：**$A55A で初期化**（破壊検出用 canary）
- カーネル専用スタック ($4700-$477F)：**$0000 で初期化**、$4700 に canary $A55A を配置

**watermark 診断の概要（実装は Ph.3.5）：**
```
診断ワード `STACK-WATERMARK ( tid -- depth )`
  指定 tid のスタックを下方向から走査し、$0000 でない最初の位置を返す
  → タスクごとの最大スタック使用量が判明

診断ワード `CHK-GUARD ( -- ok? )`
  guard 領域 ($FC00-$FC3F) を全走査し、全要素が $A55A であれば true
  KERN_SP の canary ($4700) もチェック
  → スタックオーバーフロー／カーネルスタック破壊の検出
```

**運用方針：**
- Ph.3.5 実装後、Dhrystone・回帰テスト後に `STACK-WATERMARK` を全 tid で実行
- 想定（コール 98 B / データ 128 B）と実測の差分を確認、設計マージンの妥当性を検証
- `CHK-GUARD` はデバッグビルドで scheduler 周期ごとに実行（リリースビルドでは無効化）

**初期化コードの設計上の前提：**
カーネル `_kstart` で以下を実装する（実装は Ph.3.5）：
1. TCB プール、MsgPool、カーネル専用スタックを $0000 でクリア
2. guard 領域 $FC00-$FC3F を $A55A で埋める
3. KERN_SP の canary $4700 = $A55A
4. （オプション）コール／データスタック領域も $0000 でクリア

## 7. 領域成長予約の運用ルール

### 7.1 「予約」の定義

本書で「予約」と記した領域は：
- **現フェーズで配置・初期化を行わない**
- **将来の使用時まで実コードからの参照を禁止する**
- **アセンブラ／リンカで `.org` ジャンプの目印として使う**

### 7.2 成長時の手続き

予約領域に新規データを置く際は：
1. メモリマップ設計書（本書）を改版
2. 配置アドレスと用途を表に追加
3. アセンブラ EQU 定義／Forth CONSTANT を新規追加（既存変更禁止）
4. アドレス対照表を更新

これにより**メモリマップ管理が一元化**される。

### 7.3 予約消尽時の対応

予約 8 KB が枯渇した場合：
- まず**未使用 EQU 定義の整理**（廃止された変数の削除）
- 次に**Forth 辞書の縮減**（未使用ワードの削除）
- それでも足りなければ**メモリマップ全体の見直し**（→ 設計書 v2.0 改版）

### 7.4 stack guard 領域の運用（v1.1 新設）

レビュー指摘（review15.txt 重大②、review16.txt 推奨）に応え、guard 領域の運用ルールを定義する。

**目的：**
- データスタックオーバーフロー時に MMIO レジスタを破壊しないための「緩衝地帯」
- 破壊検出によるデバッグ支援

**配置：**
- $FC00-$FC3F（64 B）
- データスタック領域 ($F800-$FBFF) と OS 共有変数領域 ($FC40-$FC7F) の間

**初期化：**
- カーネル `_kstart` で起動直後に **$A55A** で全 64 B を埋める
- $A55A はビットパターンが目立ち、デバッグ時のメモリダンプで識別しやすい

**診断ワード `CHK-GUARD ( -- ok? )`（設計のみ、実装は Ph.3.5）：**
```forth
\ guard 領域全 32 ワード ($FC00-$FC3E) が $A55A であるかチェック
\ さらに KERN_SP の canary ($4700) も同様にチェック
\ どこかが破壊されていたら false、すべて健全なら true
\ 破壊位置を UART に出力する版（CHK-GUARD-VERBOSE）も推奨
```

**運用方針：**
- デバッグビルドでは scheduler 周期ごとに `CHK-GUARD` を実行（割込ハンドラから呼出）
- リリースビルドでは無効化（オーバーヘッド削減）
- `CHK-GUARD` 失敗時は UART にエラー出力後、無限ループ HALT で異常終了

**guard 64 B が十分か：**
レビュー指摘（review16.txt）どおり、guard の目的は「MMIO 即突入の防止」であり「オーバーフロー完全防止」ではない。64 B あれば暴走を 32 ワード分遅らせられ、その間に IRQ ハンドラが `CHK-GUARD` で検出可能。Ph.3.5 実装後の実測で不足が判明したら拡張を検討する。

### 10.3 スタック分離検証（最重要）

複数タスクを同時動作させ、コール／データスタックの領域に**マジック値**を書き込み、相互侵入が起きないことを確認。

検証手順：

```
1. 全タスク（tid=0..15）を起動し、各 tid のコール／データスタックの未使用部に
   固有のマジック値を書込む：
   - tid=N のコールスタック未使用部 = $A500 + N
   - tid=N のデータスタック未使用部 = $5A00 + N

2. 全タスクを複数周期動作させる（IPC4-CALL や TASK-SLEEP 等で切替）。

3. 各 tid のスタック領域を再走査し、マジック値が保持されていることを確認。
   （実際に push/pop した範囲は上書きされるため、未使用部のみ検証）

4. 隣接 tid の領域（例：tid=0 のコール末尾と tid=1 のコール先頭）を境界として、
   一方への書込が他方に侵入していないことを確認。
```

特に確認すべき境界（§6.4.5 表より）：

| 境界 | アドレス | 意味 |
|---|---|---|
| tid=0/1 コール境界 | $F07F / $F080 | 隣接 tid 間の独立性 |
| tid=15 コール末尾 | $F7FF | コールスタック領域全体の上限 |
| tid=0 コール / tid=0 データ | $F07F / $F800 | コール領域とデータ領域の独立性（最重要）|
| tid=15 データ末尾 | $FBFF | データスタック領域全体の上限。直後 $FC00 が guard 領域 |

### 10.4 guard 領域・KERN_SP canary 検証（v1.1 新設）

| 項目 | 方法 |
|---|---|
| guard 初期化 | `_kstart` 実行直後に $FC00-$FC3F の全 64 B が $A55A であることを emu23 で確認 |
| KERN_SP canary | `_kstart` 実行直後に $4700 が $A55A であることを emu23 で確認 |
| `CHK-GUARD` 動作 | 正常時 true、guard 領域に故意に異常値を書込んだ場合 false が返ることを確認 |
| カーネル動作中の guard 健全性 | Dhrystone 完走後に `CHK-GUARD` が true を返すことを確認 |
| **MMIO 突入防止の確認** | デバッグ用に故意のスタックオーバーフローを発生させ、guard で停止することを確認（destructive test、別ビルドで実施） |
