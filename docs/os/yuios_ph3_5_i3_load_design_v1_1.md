## 1. 目的と検証項目

TCB 設計書 §7.1 の worst-case「16 タスク全員が CALL 発行 → 全員 WAIT_REPLY、
in-flight=16」を**物理的に再現**し、以下を実測で裏取りする。

| # | 検証項目 | 合格基準 |
|---|---|---|
| V1 | in-flight 負荷時にプール（容量32）が枯渇しない | **カーネルが記録するプール占有 high-water mark（HWM）の実測値 ≤ 32**（§2.3）。HWM 観測が V1 の本質（指摘 No.1）。 |
| V2 | プール枯渇時もパニックしない | 意図的枯渇で ERR_IPC_NOSLOT($FFFE) 返却・実行継続（V2 は派生試験） |
| V3 | スタック watermark が 128B 枠に収まる | 全 tid のコール／データスタック使用が ≤128B、guard intact |
| V4 | 全 CALL が正しく REPLY を受け取る | 各タスクが期待 reply 値を受信し、UART に成功記号を出す |

> **【脚注・指摘 No.4】厳密 16 in-flight は本試験では未検証**：本試験は 15 クライアント
> （§2.1）で実施し、V1 はプール占有 HWM の実測（§2.3）で判定する。TCB 設計書 §7.1 が
> 想定した厳密 16 in-flight（全 16 タスクが各 1 件・§2.4）の物理再現には、サーバ自身も
> 別サーバへ CALL する**二段サーバ構成**が必要であり、これは **Ph.5 ProcMgr 以降の課題**
> として残す。本試験で「16 worst-case そのもの」は検証しないことを明記する（設計文書
> 改版時の情報欠落防止）。

## 2. 試験構成（フル16タスクハーネス）

### 2.1 タスク配置（MAX_TASKS=16 を使い切る）

| tid | タスク | 役割 |
|---|---|---|
| 0 | MAIN（既存・起動タスク） | ハーネス起動後アイドル |
| 1 | **ECHO-SERVER**（新規） | RECV→受信値+1 を REPLY するエコーサーバ |
| 2〜15 | **LOAD-TASK ×14**（新規） | 一斉に ECHO-SERVER へ CALL |

→ CALL 発行側は tid 2〜15 の **14 タスク**＋（MAIN も加える場合 15）。
in-flight 最大は「サーバが REPLY を保留している間に全クライアントが WAIT_REPLY」
の同時数。14 クライアントで in-flight=14、設計の 16 に近い負荷を与える。

**16 を厳密に満たす案**：ECHO-SERVER を tid=1 に置き、クライアントを MAIN(0)＋
tid 2〜15（14）＝**15 クライアント**にできる。サーバ自身は CALL しないので
in-flight 上限は 15。**完全な 16 は「サーバも別サーバへ CALL する二段構成」が必要**
だが、プール容量 32 に対し 15〜16 はマージン内であり、容量検証としては
15 で POOL_SIZE 半分超の負荷を与えられるため十分。**本試験は 15 クライアントで実施**し、
「in-flight=15 で枯渇せず」を V1 の実測値とする（32 の安全マージン妥当性確認）。

### 2.2 同時性の作り方（in-flight を溜める機構）

単純に各クライアントが CALL すると、サーバが即 REPLY して in-flight=1 のまま捌ける。
**同時に 15 個を溜める**には、サーバが「15 個受信し終えるまで REPLY しない」
バッチ方式を採る：

```
ECHO-SERVER:
  BEGIN
    received < EXPECTED?  →  RECV して sender tid を配列に記録、received++
  received == EXPECTED になったら
    記録した全 sender へ順に REPLY    \ ここで初めて全員が起床
  AGAIN
```

- クライアントが CALL すると enqueue されサーバが RECV するまでプールに滞留。
- サーバが 15 個 RECV するまで REPLY しない間、15 クライアントは全員 WAIT_REPLY。
- この瞬間が **in-flight=15**（プール内 dequeue 済み＋WAIT_REPLY 中の reply 待ち）。

※ 厳密には「プール滞留数」と「WAIT_REPLY 数」は別物。プール枯渇(V1)は
**enqueue 時点**で起きるため、15 クライアントが RECV 前に一斉 enqueue した瞬間の
プール占有（最大 15）が POOL_SIZE=32 を超えないことが V1 の本質。

### 2.3 プール占有 high-water mark の観測（v1.1 新設・指摘 No.1）

**問題（指摘 No.1）**：§2.2 のバッチサーバは「1 個ずつ RECV（dequeue）しながら 15 個
溜める」ため、サーバが先に RECV を回し始めるとプール占有は 15 に達する前に減りうる。
WAIT_REPLY 数（in-flight=15）の同時成立を観測しても、それは V1 が問う**プール占有
ピーク**とは別の瞬間であり、現状のバッチ方式では占有 HWM を取り逃す。

**対策（案A 採用）**：カーネルの IPC4 プール管理に**占有 high-water mark カウンタ**を
追加する。試験版 kernel_forth_i3_load.fs（KY38・本番無改変）に以下を実装：

- `POOL-INUSE`（現在占有数）と `POOL-HWM`（占有数の最大値）を **$50A0-$50A3**（2 ワード・
  §3.2 で確保）に置く。
- `_ipc4_enqueue` 成功（alloc）時：`POOL-INUSE++`、`POOL-INUSE > POOL-HWM` なら更新。
- `IPC4_REPLY`/RECV による解放（free）時：`POOL-INUSE--`。
- カーネル ASM 側の alloc/free 箇所にフックを置くため、本カウンタは **kernel_v12_7.asm
  の試験版**（`kernel_v12_7_i3.asm`・KY38 別ファイル）にも最小フックを追加する。
  Forth だけでは alloc/free の瞬間を捉えられないため。
- 試験終了時、MAIN が `POOL-HWM` を UART へ 16 進 2 桁で出力（例 `H0F`）。

**V1 判定**：出力された `POOL-HWM ≤ 32`（$20）であれば V1 PASS。これが「32 で足りる」の
直接実測となる。**WAIT_REPLY 同時数ではなく、占有 HWM を一次証拠とする**。

> フック追加は IPC4 の alloc/free 2 箇所のみ（インクリメント/デクリメント＋最大値更新）。
> emu23 改修は不要（カーネル側のみ）。ただし ASM カーネル試験版を作るため、ビルドは
> 本番 kernel_v12_7.asm でなく kernel_v12_7_i3.asm を用いる（KY38）。

### 2.4 既存タスクとの in-flight 合算上限（v1.1 新設・指摘 No.2）

**TCB 設計書 §7.1 の定義**：各タスクは IPC4-CALL 後に WAIT_REPLY するため、**1 タスクが
同時に保持できる in-flight request は最大 1 件**。したがって in-flight の理論上限は
**同時に WAIT_REPLY し得るタスク数 = 全タスク数を超えない**。

**合算上限の数式**：

```
in-flight_total ≤ (CALL を発行し得るタスク数)
              ≤ MAX_TASKS − (純サーバタスク数)
```

本試験のタスク内訳（§2.1・MAX_TASKS=16）：

| 分類 | tid | 数 | in-flight 寄与（各最大1） |
|---|---|---|---|
| ECHO-SERVER（純サーバ・CALL しない） | 1 | 1 | 0 |
| 新規 LOAD-TASK ＋ MAIN | 0,2〜15 | 15 | ≤15 |
| 既存タスク（FILEMGR 等のサーバ／ドライバ） | （試験版では起動しない方針） | — | （§下記）|

**既存タスクの扱い（指摘 No.2 への回答）**：本試験版 kernel_forth_i3_load.fs では、
**既存の UART-TEST/STOR-TEST/FILEMGR-TEST 等のテストタスクと FILEMGR/STOR/UART/MEMMGR
サーバ群を起動しない**（I3-HARNESS のみ起動）。これにより合算 α を排除し、
in-flight は新規 15 のみ。よって：

```
in-flight_total ≤ 15 ＜ POOL_SIZE = 32   （安全マージン 17）
```

が**数式として成立**する。既存タスク群を同時起動して α を加える混在試験は、
本試験の後段（オプション・§5 I3-K2）で別途行い、その際は §2.3 の POOL-HWM で
合算ピークを実測する。混在時も理論上限は「全 16 タスクが各 1 件 = 16 ≤ 32」を
超えない（TCB §7.1）。

## 3. 実装方針（KY36 準拠：Dスタック完結・グローバルループ変数禁止）

### 3.1 新規ワード

| ワード | 内容 |
|---|---|
| `ECHO-SERVER-TASK` | §2.2 のバッチエコーサーバ。sender 記録は専用配列 `I3-SENDER-BUF`（$5080-$509F・§3.2） |
| `LOAD-TASK` | `(自tid をメッセージにして) ECHO-SERVER(tid=1) へ IPC4-CALL → reply 検証 → 成功なら UART に記号` |
| `I3-HARNESS-START` | tid 2〜15（14個）の LOAD-TASK を TASK-CREATE。MAIN もクライアントに加える（計15） |
| `POOL-HWM-PUTC` | 試験終了時に `POOL-HWM`（$50A2）を `Hxx` 形式で UART 出力（§2.3・V1 判定用） |
| （ASM フック） | `kernel_v12_7_i3.asm` の `_ipc4_enqueue` 成功時に INUSE++/HWM 更新、free 時に INUSE--（§2.3・KY38 別ファイル） |

### 3.2 sender 記録バッファ

`I3-SENDER-BUF`：**$5080-$509F（32B＝16ワード）に確保**。当初 $EC00 系 TEST バッファ
への配置を検討したが、$EC00-$EFFF は STOR-TEST/FILEMGR-TEST が時分割で全域使用
しており（HANDOVER_CHAT43 で実際に FT-RW-BUF 上書き破壊が発生した領域）、
競合を避けるため **FileMgr 残余領域**に隔離する。
あわせて §2.3 の占有カウンタを **$50A0=POOL-INUSE / $50A2=POOL-HWM**（計 4B）に置く。

> **【脚注・指摘 No.3】$5080-$50FF 未使用の物理確認（memmap v1.6 / kernel_forth_v0_10_11.fs）**
> - FileMgr 専用領域は **$4800-$505F**（2144B・memmap v1.6 §5.1 正式登録）。
> - FT-NAME2-BUF=$5060、FT-STAT-BUF=$5070（FILE_STAT 結果・16B → $507F まで）。
> - grep にて **$5080-$50FF を参照する定義はカーネルソースに皆無**を確認（2026-06-05）。
> - Forth 辞書先頭は **$5100**（memmap v1.6 §アドレス対照表）。よって $5080-$50FF（128B）は
>   FileMgr 残余の未使用域であり、辞書とも分離。本試験は $5080-$50A3（36B）を使用。
> - **留意**：当域は本来「カーネル成長予約（FileMgr 成長用）」。本試験バッファは試験版
>   （kernel_forth_i3_load.fs・KY38 別ファイル）限定の一時使用であり、本番カーネルには
>   持ち込まない。将来 FileMgr が当域を使う場合も試験版とは独立（時間的にも排他）。

### 3.3 成功判定の UART 記号

全クライアントが正しい reply（送信値+1）を受け取ったら、各クライアントが
`'a'+tid` を UART 出力。MAIN が全タスク起動後に区切り記号 `'#'` を出す。
期待出力：`#` の後に 15 個のクライアント記号（順不同）。

## 4. 計測手順

```
# ビルド（kernel_forth_i3_load.fs を v0.10.11 と同じ手順でビルド。ASMは kernel_v12_7_i3.asm）
# 実行（watermark 付き・常駐OSなので --wm-steps で打切り）
printf "c\nq\n" | timeout 90 ./emu23_wm yuios_i3.bin --disk disk.img \
    -i /dev/null -q -w --wm-steps 10000000 2>wm.txt >uart.txt
```

- `uart.txt`：`#` ＋ 15 記号 ＋ `POOL-HWM`（`Hxx`）が出れば V1・V4 判定可能。
- `wm.txt`：全 tid の used ≤128B、guard intact なら V3 PASS。
- **V1 判定**：`uart.txt` の `Hxx`（POOL-HWM）が `≤ $20`（32）であること。

> **【脚注・指摘 No.5】emu23 スループットと --wm-steps の整合根拠（2026-06-05 実測）**
> - Dhrystone（83,613 cycles）の wall 実行時間 ≒ **0.029 秒**で完走。
> - Ph.4 総合試験（現行カーネル）の完走に要した命令数を実測：
>   `--wm-steps 1000000`→`…OR`、`3000000`→`…WV`、`10000000`→`…WVXY` 完走。
>   ∴ **総合試験完走は 500 万〜1000 万命令**で足りる。
> - 本 I3 試験はタスク数が増えるため余裕を見て **`--wm-steps 10000000`（1000 万）** を採用
>   （v1.0 の 2000 万から下方修正。完走実績 1000 万に合わせる）。
> - emu23 スループットは Dhrystone 実測から概算 **数百万 cycle/秒オーダー**。`timeout 90` 秒
>   なら 1000 万命令は十分処理可能（exit=124 timeout の再発なし）。万一打切られた場合でも
>   UART が `…Y` 相当まで出ていれば watermark/HWM は確定済み（emu23_watermark v1.1 §4.1）。

## 5. KY（本試験固有）

- **I3-K1**: バッチサーバが EXPECTED 未達で永久 WAIT（クライアント不足）。
  → クライアント数とEXPECTEDを定数で一致させ、TASK-CREATE 成功数を確認。
- **I3-K2**: 15 クライアント同時 enqueue でもプールは 15 ≤ 32 で枯渇しない想定だが、
  既存 7 タスク（FILEMGR 等）の in-flight と合算しうる。試験は既存サーバ群を
  停止せず動かすため、合算ピークを wm/プール監視で確認。
- **I3-K3**: KY38 継続。本番 kernel_forth_v0_10_11.fs / emu23_v104.c 無改変。
  試験版は kernel_forth_i3_load.fs。
- **I3-K4**: emu23 改修なし（計測は既存 emu23_wm）。∴ 本試験で Dhrystone 回帰不要
  （Force/カーネルへのワード追加のみ）。
- **I3-K5**: WAIT_REPLY 永久 block（TCB §5.3.8）。サーバが必ず全員へ REPLY する
  ことをコードで保証。timeout 機構は未実装（Ph.5 課題）なので試験は決定的に組む。
