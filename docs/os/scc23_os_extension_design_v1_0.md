# **1. 背景と前提**

## **1.1 検討の経緯**

scc23実ソース（v1.03時点）の機能調査により、OS実装に不可欠な以下4機能が不足していることを確認した。

| **機能** | **現状** | **不足の影響** |
| --- | --- | --- |
| プリプロセッサ（`#include`/`#define`/`#ifdef`） | 未実装（字句解析段階でキーワード処理なし） | マルチファイルOSのヘッダ共有が事実上不可能 |
| 関数ポインタ | 型システム（T_INT/T_CHAR/T_PTR/T_ARRAY/T_VOID/T_STRUCT/T_UNION）に存在しない | 割り込みベクタ・システムコールディスパッチテーブルをCで書けない |
| `unsigned`/`signed`修飾子 | 未実装 | MMIO・ビットフラグ操作で符号拡張バグの危険 |
| `static`（ファイルスコープ・関数内static） | 未実装 | カプセル化不可。全変数がグローバル化 |

## **1.2 重要な前提：scc22に移植元実装が現存する**

scc22_v3_03.c（scc23の前身、ISA2.2時代のコンパイラ）には**プリプロセッサ機能（`handle_define`/`SC_DEFINE`シンボルクラス/`#ifdef`-`#else`-`#endif`制御）が既に実装されている**ことを確認した。

- 実装済み：`#define NAME VALUE`（値マクロ）、`#define NAME(...)`（引数マクロは空展開で読み飛ばしのみ）、`#ifdef`/`#ifndef`/`#else`/`#endif`
- 未実装：`#include`（scc22にも存在しない）

これは**ゼロから設計するのではなく、既存実装を移植する**ことで工程を大幅短縮できることを意味する。scc23のv2.00 float対応（Step1でscc23_v1_04.cをコピーして開始する方式）と同じ考え方で、本工程もscc22の該当部分を移植起点とする。

## **1.3 本工程のスコープ外**

| **項目** | **理由** |
| --- | --- |
| `#include` | scc22にも実装がなく、移植元が存在しない。本工程では「複数.cファイルを別々にscc23でコンパイルしhasm23/lnk23でリンクする」運用（既存のYOFフロー）で代替し、言語機能としての`#include`は見送る |
| 可変長引数（`...`、`va_list`） | YSD8800_ABI_spec.docx §10「未サポート」に明記。OSカーネル実装の必須要件ではないため本工程では対象外 |
| 関数ポインタを介した間接呼び出し命令 | startup_harness23_v15.asmのコメントに明記の通り、ISA2.3には間接JSR（`JSR [X]`）が無い。本工程ではテーブル参照→`STW`→直接`JSR`相当のディスパッチ展開で対応し、ISA拡張は別途検討事項とする（§5参照） |
| ビットフィールド（`struct`の`: N`指定） | 手動ビット演算で代替可能。優先度低 |
| `long`（32bit整数） | 16bitアーキテクチャでの必要性が低い |

# **2. 依存関係分析と並行化の検討**

最短工程を組むため、4機能間の依存関係を分析する。

| **機能** | **型システムへの影響** | **コード生成への影響** | **他機能との依存** |
| --- | --- | --- | --- |
| プリプロセッサ | なし（字句解析より前段の処理） | なし | **独立**（字句解析の前処理として動作するため、他3機能と完全に分離） |
| unsigned/signed修飾子 | 型フラグ追加のみ（既存T_INT/T_CHARに`is_unsigned`属性を付与） | 符号拡張命令の分岐が必要 | **独立**（既存型システムへの属性追加であり、関数ポインタ・staticと無関係） |
| static変数 | なし | シンボル管理（sclass）の拡張のみ | **独立**（既存のSC_GLOBAL/SC_LOCALと並列のsclass追加） |
| 関数ポインタ | 型システムに新規型種別（T_FUNCPTR等）の追加が必要 | コード生成（呼び出し展開）に変更が必要 | **他3機能と独立だが、実装規模が最大** |

**結論：4機能は相互依存がなく、技術的には完全並行で実装可能。** ただし実務上はレビュー単位を分けた方が安全なため、本設計では「2系列の並行ストリーム」に分けて最短化を図る。

# **3. 工程設計（最短化）**

## **3.1 全体構成：2ストリーム並行**

```
ストリーム①（移植中心・低リスク）        ストリーム②（新規実装中心・中リスク）
─────────────────────────────  ─────────────────────────────
Step A1: プリプロセッサ移植              Step B1: unsigned/signed型属性追加
Step A2: プリプロセッサ単体テスト         Step B2: static変数（sclass拡張）
                                          Step B3: 関数ポインタ型システム追加
                                          Step B4: 関数ポインタ コード生成
                                          Step B5: B1〜B4 結合テスト
─────────────────────────────  ─────────────────────────────
              ↓                                    ↓
        Step C: 結合テスト（全機能・Dhrystone回帰・設計書改版）
```

ストリーム①はscc22からの移植が中心で実装リスクが低く、ストリーム②は新規実装（特に関数ポインタ）を含むためリスクと工数が高い。**両ストリームは独立に着手可能**であり、人手が1名であっても「①を先に短時間で終わらせ、②に専念する」順序にすることで手戻りリスクを下げつつ全体最短化できる。

## **3.2 ストリーム① 詳細**

| **Step** | **作業** | **対象ファイル** | **検証方法** |
| --- | --- | --- | --- |
| A1 | scc22_v3_03.cの`handle_define`/`skip_to_endif`/`skip_to_endif_only`/`SC_DEFINE`をscc23_v2_xx.cへ移植。字句解析の冒頭（行頭`#`検出部）にプリプロセッサディスパッチを追加 | scc23_v2_xx.c | コンパイル通過（既存機能への影響なしをgrep差分で確認） |
| A2 | `#define`定数・`#ifdef`/`#else`/`#endif`の単体テスト（OS向けの典型パターン：`#define MAX_TASKS 16`、`#ifdef DEBUG`） | テストCソース新規作成 | 期待通りの展開・分岐結果をemu23実行で確認 |

**移植afterの注記：** scc22の実装は値マクロ・条件コンパイルのみで、引数付きマクロ（関数マクロ）は「空展開で読み飛ばし」という簡易処理だった。本工程でもこの制約を維持し、関数マクロの正式実装はスコープ外とする（§1.3とは別に明記：OS実装では値マクロと条件コンパイルがあれば大半のケースに対応できるため、優先度を上げない）。

## **3.3 ストリーム② 詳細**

| **Step** | **作業** | **対象ファイル** | **検証方法** |
| --- | --- | --- | --- |
| B1 | 型情報構造体に`is_unsigned`フラグを追加。`unsigned`/`signed`キーワードの字句解析・型解析への反映。`unsigned char`は0〜255、`unsigned int`は0〜65535として扱う符号拡張ロジックをemit_expr/emit_lvalの該当箇所（LDB等）に追加 | scc23_v2_xx.c | `unsigned char c = 0xFF; if (c > 0)` 等の境界値テストでemu23実行確認 |
| B2 | sclassに`SC_STATIC_GLOBAL`（ファイルスコープstatic）・`SC_STATIC_LOCAL`（関数内static）を追加。後者はDATA領域に固定アドレス確保し、関数の再入時も値を保持する設計（ローカル変数のスタック確保から除外） | scc23_v2_xx.c | ファイルスコープstatic変数の外部非可視確認（grep等でアセンブリ出力にシンボル衝突がないことを確認）。関数内static変数が2回目の呼び出しで前回値を保持することをemu23実行で確認 |
| B3 | 型enumに関数ポインタ型を追加（既存`T_PTR`に`points_to_func`属性を付与する方式を推奨。新規enum値追加よりも既存ポインタ処理との共用部分が大きく実装コストが低い）。宣言構文`int (*fp)(int, int);`の構文解析対応 | scc23_v2_xx.c | 宣言のみのコンパイル通過確認（代入・呼び出しはB4で検証） |
| B4 | 関数ポインタへの代入（`fp = my_func;`）・関数ポインタ経由の呼び出し（`fp(1,2);`）のコード生成。ISA2.3に間接JSRが無い制約（§1.3）への対応として、「ポインタ値をワークアドレスにSTWし、固定の間接ディスパッチスタブ（既存のstartup_harness23_v15.asmにある`_syscall_disp_ptr`相当の仕組みを流用）経由でJSR」という展開方式を採用 | scc23_v2_xx.c | 関数ポインタ配列（簡易ベクタテーブル）を介した呼び出しがemu23上で正しい関数に到達することを確認 |
| B5 | B1〜B4の結合テスト：`unsigned`型の関数ポインタテーブル（ディスパッチテーブルの典型形）を実際に組んで一括動作確認 | テストCソース新規作成 | 「`unsigned int (*dispatch[4])(unsigned int);`相当の簡易テーブルからの呼び出し」が正しく動作することをemu23実行で確認 |

## **3.4 結合（Step C）**

| **Step** | **作業** | **対象ファイル** | **検証方法** |
| --- | --- | --- | --- |
| C1 | ストリーム①②全機能を1つのscc23ビルドに統合 | scc23_v2_xx.c | 既存回帰テスト（既存のscc23単体テスト群）全PASS確認 |
| C2 | Dhrystone回帰（既存の絶対ゲート：826/48405/P:20）再確認 | dhry_all_ansi2.c | サイクル数・出力が既存ベースラインと同一であることを確認（新機能未使用コードパスに影響がないことの確認） |
| C3 | 4機能を組み合わせた簡易マイクロカーネル雛形（割り込みベクタテーブル＋static変数によるタスク状態保持＋プリプロセッサによる定数定義）の試作・動作確認 | テストCソース新規作成 | emu23上で簡易ベクタディスパッチ＋static状態保持が動作することを確認 |
| C4 | 設計書改版（toolchain23_design・scc23_v2_00系設計書への統合記載） | toolchain23_design_vX_X.docx | KY41（追記のみ・4点整合）に従い改版 |

# **4. 最短化のポイント（まとめ）**

| **ポイント** | **効果** |
| --- | --- |
| プリプロセッサをscc22から移植（新規設計しない） | ストリーム①の設計工数をほぼゼロ化。実装も移植中心で数時間〜半日規模 |
| 4機能の相互独立性を活用し2ストリーム並行 | 直列実装比でクリティカルパスを関数ポインタ（最大工数の機能）のみに圧縮 |
| 関数ポインタをT_PTR属性拡張として実装（新規enum値ではなく） | 既存のポインタ関連コード（emit_lval等のT_PTR分岐）を再利用でき、実装範囲を縮小 |
| 結合テストをC1〜C4の4段に絞り、Dhrystone回帰は既存ゲート値の再確認のみ | 新規ベンチマーク設計を不要にし、既存の絶対ゲート（826/48405/P:20）を流用 |

# **5. スコープ外・将来検討事項**

| **項目** | **内容** |
| --- | --- |
| ISA2.3への間接JSR命令追加 | 関数ポインタ呼び出しの効率化に直結するが、ISA拡張は本工程のスコープ外。現状はディスパッチスタブ方式（§3.3 B4）で機能要件は満たすが、命令数は増える。将来ISA2.4等で検討 |
| `#include`の実装 | 移植元（scc22）にも実装がないため見送り。複数ファイルのコンパイル＋lnk23リンクという既存運用で当面代替する |
| 関数マクロ（引数付き`#define`）の正式実装 | scc22同様、空展開のみで正式なマクロ展開機能は持たない。OS実装の初期段階では値マクロ＋条件コンパイルで大半をカバーできるため優先度を上げない |

# **6. KY活動（危険予知）**

| **危険予知（KY）** | **防止策** |
| --- | --- |
| プリプロセッサ移植時、scc22とscc23の字句解析の前処理タイミングが異なり、移植したコードがそのまま動かない | Step A1で必ず既存scc23の字句解析エントリポイントを先に確認し、scc22側の呼び出しコンテキストとの差異を洗い出してから移植する |
| 関数ポインタのコード生成（B4）で、ISA2.3に間接JSRが無いことを忘れ、存在しない命令を生成してしまう | kaizen.txt原則「ISAにない命令を使用しないこと」を厳守。実装前にISA2_3_v231.docxで間接JSR系命令の有無を再確認してから着手する |
| unsigned型の符号拡張ロジックを追加した際、既存のsigned int/char処理に意図しない副作用を与える | Step B1完了後、既存のDhrystone回帰（int/char中心）を必ず実行し、符号拡張ロジック追加が既存パスに影響していないことを確認する |
| 4機能を並行実装した結果、結合時（Step C1）に想定外の組み合わせバグ（例：static関数ポインタ変数）が出る | Step B5で組み合わせテスト（unsigned×関数ポインタ）を先行実施し、Step C1前に主要な組み合わせパターンを洗い出しておく |
