## 1. 目的とスコープ

### 1.1 背景（ブロッカー）
scc23 v1.01 は CODE_ORG=$0400 / DATA_ORG=$4000 / RUNTIME_ORG=$0100 を `#define` ハードコード
している。ProcMgr が C プロセスを $C000 系（PROC-LOAD-ADDR=$C000）へロードするには、これらを
Cプロセス用の値（レイアウト設計書 v1.1 確定値）に変えてコンパイルする必要がある。現状は
使い捨て実験版（scc23_exp_c000.c）で #define を書き換えて対応しており、本番ツールに恒久機能と
して取り込む必要がある（Step4 の前提条件）。

### 1.2 本改修のスコープ
本改修は2点：

- **(A) ベースアドレス引数化（必須・主目的）**：`--code-org` / `--data-org` / `--runtime-org`
  オプションを追加し、`#define` ハードコードを上書き可能にする。省略時は現行既定値で後方互換。
- **(B) 演算子系ヘルパ オンデマンド出力（付加価値）**：cc_mul/cc_div/cc_mod を、当該演算子が
  プログラム中で使われた場合のみ emit_runtime で出力する。未使用なら省く（RUNTIME 実需削減）。

### 1.3 スコープ外（申し送り）
- **関数系6ヘルパ（putchar/getchar/puts/strcpy/strcmp/memcpy）のオンデマンド化**：検出が
  builtin 関数呼び出し解決経路に紛れ、設計・実装・取りこぼし検証の手数が大きい。案イ採択により
  本改修では扱わず、将来改善として §7 に申し送る。本改修後も関数系6個は従来どおり無条件出力。
- **printf/sprintf/strlen**：builtins 登録（L3386）はあるが emit_runtime に実体定義が無い
  （呼ぶと未定義ラベル）。本改修のスコープ外（現状維持。別途実装課題として §7 申し送り）。
- **非PIC構造のPIC化**：本改修でも非PIC（DATA絶対参照）は維持。PIC化は Phase2 MMU 検討と併せて
  別途（レイアウト設計書 v1.1 §5.2 と整合）。

### 1.4 バージョン付与
本改修後の scc23 を **v1.02** とする（SCC_VERSION 更新）。起動時・コンパイル時・出力ASMコメントに
バージョン表示する既存機構（L3360,3370,3372）を踏襲（ツールはバージョンが分かるように表示する原則）。

## 2. 改修対象の実体（2026-06-10 grep確認）

本章は改修着手前に scc23_v1_01.c を grep で確認した実体（KY34/KY39）。

### 2.1 引数パース部（現状）
- `main()` L3353-3363。現状オプションは `-o <file>` / `-v`(=`--version`) のみ（L3358-3361）。
- ソースファイル名は非オプション引数（L3362 `argv[i][0]!='-'`）。

### 2.2 ORG マクロと参照箇所
| マクロ | #define | 参照箇所 | 用途 |
|---|---|---|---|
| CODE_ORG | L75 `0x0400` | L3378（.org）, L3383（JMP _mainコメント） | コードセクション先頭 |
| RUNTIME_ORG | L74 `0x0100` | L3374（.org）, L2589（コメント） | ランタイム先頭 |
| DATA_ORG | L73 `0x4000` | L2884（.org）, L2882（コメント）, 絶対参照11箇所（L1586,1599,1650,1663,1711,1722,1741,1994,2007 等・全て `DATA_ORG+offset` 形式） | データセクション先頭＋大域変数絶対アドレス |

- **出力順序**：RUNTIME（L3374）→ CODE（L3378）→ user code → DATA（emit_data_section L2884）。
- DATA_ORG は `.org` 1箇所＋**コード中の絶対参照11箇所**（非PIC）。全て `(unsigned)(DATA_ORG+offset)`
  の演算形式に統一されているため、DATA_ORG を変数化すれば11箇所が一括追従する（個別ハードコード
  埋込ではない）。

### 2.3 emit_runtime のヘルパ構成（実体定義9個）
emit_runtime（L2587-2873）は使用フラグ分岐を一切持たず、全ヘルパを無条件出力する。実体定義は：

| ヘルパ | 種別 | emit開始 | 呼出検出箇所 | アドレスEQU |
|---|---|---|---|---|
| _putchar | 関数系 | L2597 | builtin呼出経路 | （なし） |
| _getchar | 関数系 | L2613 | builtin呼出経路 | （なし） |
| _puts | 関数系 | L2623 | builtin呼出経路 | （なし） |
| _strcpy | 関数系 | L2659 | builtin呼出経路 | （なし） |
| _strcmp | 関数系 | L2705 | builtin呼出経路 | （なし） |
| _memcpy | 関数系 | L2755 | builtin呼出経路 | （なし） |
| _cc_mul | 演算子系 | L2798(EQU)/L2801(body) | SIR_MUL emit（L1632,1795,1971,2094） | _C_MUL_A/B/R（L2798-2800） |
| _cc_div | 演算子系 | L2830(EQU)/L2833(body) | SIR_DIV emit（L1803,2095） | _C_DIV_A/B/Q（L2830-2832） |
| _cc_mod | 演算子系 | L2859(body) | SIR_MOD emit（L1811,2096） | **_C_DIV_A/B を共用（自前EQUなし）** |

### 2.4 ★重要な依存関係（オンデマンド化設計の核心）
- **cc_mod は `_C_DIV_A`/`_C_DIV_B` を参照する**（L2861-2862,2867-2869）が、これらの EQU 定義は
  **cc_div ブロック（L2830-2831）にある**。
- よって **cc_mod を出力するなら _C_DIV_A/_C_DIV_B の EQU 定義も必ず出力する**必要がある。
  cc_mod 単独出力では未定義ラベルになる（オンデマンド化のバグ要因）。
- cc_mul は _C_MUL_A/B/R（自前EQU L2798-2800）で独立。cc_div は _C_DIV_A/B/Q（自前EQU）で独立。
- **依存ルール**：`cc_mod 使用 ⇒ _C_DIV_A/_C_DIV_B のEQU定義が必要`。

## 3. (A) ベースアドレス引数化 設計

### 3.1 方式：#define をグローバル変数化
現状の `#define CODE_ORG 0x0400` 等を、初期値付きグローバル変数へ置換する。

```c
/* 改修前: #define */
#define DATA_ORG    0x4000
#define RUNTIME_ORG 0x0100
#define CODE_ORG    0x0400

/* 改修後: グローバル変数（既定値=現行値で後方互換） */
static unsigned g_data_org    = 0x4000;
static unsigned g_runtime_org = 0x0100;
static unsigned g_code_org    = 0x0400;
```

- 既存の `CODE_ORG`/`DATA_ORG`/`RUNTIME_ORG` 参照を、対応するグローバル変数名へ機械的に置換する
  （CODE 2箇所・RUNTIME 2箇所・DATA 13箇所＝.org/コメント2＋絶対参照11）。
- `(unsigned)(DATA_ORG+s->offset)` は `(unsigned)(g_data_org+s->offset)` になり、変数化で一括追従。
- **マクロ名の機械置換**のため、置換漏れ防止に grep -c で改修前後の出現数照合を行う（§5検証）。

### 3.2 オプション仕様
| オプション | 対応変数 | 16進パース | Cプロセス用の値（v1.1） | 省略時（後方互換） |
|---|---|---|---|---|
| `--code-org <addr>` | g_code_org | `$XXXX` / `0xXXXX` 受理 | $C040 | 0x0400 |
| `--runtime-org <addr>` | g_runtime_org | 同上 | $C380 | 0x0100 |
| `--data-org <addr>` | g_data_org | 同上 | $C680 | 0x4000 |

- 引数パース（main L3357 ループ）に分岐追加。値は `strtoul(arg,NULL,16)` 等で16進解釈。
  先頭 `$` 接頭辞も受理する（プロジェクト慣習）か、`0x`/裸16進のみとするかは §3.3 で確定。
- パース後、`emit` で使われる `.org`/絶対参照は全てグローバル変数を見るため自動反映。

### 3.3 16進パースの受理形式（確定）
- `0xC040`（C慣習）と `C040`（裸16進）を受理。`$C040`（アセンブラ慣習）も受理する。
  実装：先頭が `$` ならスキップして以降を base16 で `strtoul`、`0x` は strtoul が解釈。
- 不正値（解釈不能）はエラー終了（`fprintf(stderr,...); return 1;`）。

### 3.4 バージョン表示更新
- `SCC_VERSION` を "1.02" へ更新、`SCC_DATE` を 2026-06-10 へ。
- 起動時表示（L3360/L3370）でバージョンが分かる（既存機構踏襲）。
- 任意：`-v` 表示に現行 org 設定値も併記すると運用で有益（必須ではない）。

## 4. (B) 演算子系ヘルパ オンデマンド化 設計

### 4.1 方式：使用フラグ → emit_runtime で条件出力
3つの使用フラグを設け、SIR_MUL/DIV/MOD の emit 時に立て、emit_runtime で立ったヘルパのみ出力。

```c
static int g_use_mul = 0;
static int g_use_div = 0;
static int g_use_mod = 0;
```

### 4.2 フラグ立て位置（呼出検出）
SIR_MUL/DIV/MOD の `JSR _cc_xxx` emit 箇所で対応フラグを立てる：

| フラグ | 立てる箇所（JSR _cc_xxx emit 直前/直後） |
|---|---|
| g_use_mul = 1 | L1632, L1795, L1971, L2094（SIR_MUL の JSR _cc_mul） |
| g_use_div = 1 | L1803, L2095（SIR_DIV の JSR _cc_div） |
| g_use_mod = 1 | L1811, L2096（SIR_MOD の JSR _cc_mod） |

- これらは全コード生成（パース→IR→emit）が emit_runtime より**前**に走るため、emit_runtime 到達
  時点でフラグは確定している。**※出力順序の確認（§4.4）が前提条件。**

### 4.3 emit_runtime の条件出力（依存ルール込み）
emit_runtime の cc_mul/cc_div/cc_mod 各ブロックを if で包む。§2.4 の依存を反映：

```c
/* cc_mul: 独立。g_use_mul なら EQU+body 出力 */
if (g_use_mul) {
    emit("_C_MUL_A EQU ..."); ... emit("_cc_mul:"); ... /* L2798-2828 */
}
/* cc_div の EQU は cc_div 本体 と cc_mod の両方が要る → 出力条件は (div or mod) */
if (g_use_div || g_use_mod) {
    emit("_C_DIV_A EQU ..."); emit("_C_DIV_B EQU ..."); emit("_C_DIV_Q EQU ..."); /* L2830-2832 */
}
/* cc_div body: g_use_div のみ */
if (g_use_div) {
    emit("_cc_div:"); ... emit("_ccdiv_done:"); ... /* L2833-2851 */
}
/* cc_mod body: g_use_mod のみ（_C_DIV_A/B は上のif(div||mod)で定義済） */
if (g_use_mod) {
    emit("_cc_mod:"); ... emit("_ccmod_done:"); ... /* L2859-2872 */
}
```

- **★依存ルール（§2.4）**：`_C_DIV_A/B/Q` の EQU は `g_use_div || g_use_mod` で出力する。
  これにより cc_mod 単独使用でも _C_DIV_A/_C_DIV_B が定義され、未定義ラベルにならない。
  （_C_DIV_Q は cc_div 専用だが、3本まとめて出しても無害＝アドレスEQUのみでコード増えない）
- 関数系6ヘルパ（putchar〜memcpy）は **if で包まず従来どおり無条件出力**（スコープ外）。

### 4.4 ★前提条件：出力順序の検証（設計上の要確認）
- フラグ方式が成立するには「全コード生成（フラグ立て）が emit_runtime（フラグ参照）より前に完了」
  していること。現状 main は `emit_runtime()`（L3376）→ user code parse（L3393以降）の順で、
  **emit_runtime が user code パースより前**に呼ばれている。
- このままだと **emit_runtime 実行時点でフラグが立っておらず、オンデマンド化が機能しない**。
- **対策（設計判断）**：emit_runtime をコード生成の**後**に呼ぶよう出力順序を変更する必要がある。
  ただし出力ASMの物理配置（RUNTIME→CODE→DATA）は .org で制御されるため、**emit する順序を
  変えても .org があれば最終バイナリ配置は不変**（hasm23 が .org 追従）。
  - 案: パース結果を一旦バッファ（文字列 or 一時ファイル）に貯め、全パース後に
    「.org RUNTIME → emit_runtime（フラグ確定後）→ .org CODE → バッファ flush → .org DATA」
    の順で出力する。
  - または2パス化（1パス目でフラグ収集、2パス目で出力）。
- **この出力順序変更は (B) の実装難易度の主因**であり、レビューで方式の妥当性を要確認（D項）。

### 4.5 効果と安全性
- 乗除算を使わない小プロセス（fib等）：cc_mul/div/mod（実測 約200B弱）が省かれ RUNTIME 実需減。
- 乗除算を使う Dhrystone 等：必要ヘルパが含まれる（あなたの要望「必要に応じて使用」を満たす）。
- レイアウト設計書 v1.1 の RUNTIME 768B 枠は「全ヘルパ固定 708B」を上限に確保済。オンデマンド化で
  実需は**減る方向**のみ。区画は安全側で手戻りなし。

## 5. 検証計画（回帰必須）

### 5.1 (A) 引数化の検証
1. **後方互換（最重要）**：オプション省略で従来と同一出力になること。改修前 scc23 v1.01 と
   改修後 v1.02 で同一 .c をコンパイルし、出力ASMが一致（diff 0）すること。
2. **Dhrystone 回帰（ツール改修原則）**：`dhry_all.c` を**オプション省略（$0400系）**でコンパイル
   → hasm23 → lnk23 → emu23 で従来どおり動作すること。ツール改修時の Dhrystone 回帰原則を満たす。
3. **新オプション動作**：`--code-org $C040 --runtime-org $C380 --data-org $C680` で fib.c を
   コンパイルし、.org が指定値で出力されること（grep 確認）。

### 5.2 (B) オンデマンド化の検証
1. **乗除算なし**（fib）：出力に `_cc_mul:`/`_cc_div:`/`_cc_mod:` が**現れない**こと。
2. **乗算のみ**：`a*b` のみのコードで `_cc_mul:` のみ出力、div/mod 無しを確認。
3. **剰余のみ**（cc_mod 単独）：`a%b` のみのコードで `_cc_mod:` が出力され、かつ
   **`_C_DIV_A`/`_C_DIV_B` の EQU 定義も出力される**こと（§2.4 依存ルールの検証・最重要）。
   アセンブル（hasm23）で未定義ラベルエラーが出ないこと。
4. **全演算**：`*` `/` `%` 全使用で3ヘルパ全出力を確認。

### 5.3 統合検証（レイアウト設計書 v1.1 連携）
- `scc23 --code-org $C040 --runtime-org $C380 --data-org $C680 fib.c` 出力を
  crt0（startup_proc_v1_0.asm）と結合 → hasm23 → lnk23 → emu23 で **'F55' 再現**。
  （レイアウト設計書 v1.1 §9.1 の Step4 実機確認と接続）
- 各区画の .sym 実終端 ≦ 区画境界（v1.1 §4.3 機械検査）を確認。

### 5.4 置換漏れチェック
- 改修後、`grep -c "CODE_ORG\|DATA_ORG\|RUNTIME_ORG"` で旧マクロ名の残存ゼロを確認
  （変数名へ全置換されたこと）。

## 7. 申し送り・将来改善

- **関数系6ヘルパのオンデマンド化**（putchar/getchar/puts/strcpy/strcmp/memcpy）：削減効果は
  演算子系より大きい（残り約500B）が、builtin 呼出解決経路でのフラグ立てが必要で手数大。
  将来改善として別設計で扱う（案イ申し送り）。
- **printf/sprintf/strlen の実体実装**：builtins 登録のみで emit_runtime 実体が無い。呼ぶと
  未定義ラベル。別途実装課題（本改修スコープ外）。
- **完全PIC化**：DATA絶対参照（11箇所）の相対化。Phase2 MMU 検討と併せて要否再評価
  （レイアウト設計書 v1.1 §6.3 / §5.2 と整合）。
- **scc23 v1.10 設計（float/定数畳み込み）との関係**：本改修は v1.10 とは独立（v1.02 として
  先行）。v1.10 実装時に本改修分をマージすること（版数管理留意）。
- **ビルド手順書改版**：新オプション追加によりCプロセスのビルド手順が変わる。
  yuios_build_procedure の改版が必要（開発途中のツール使い方変更 → 手順書改版を促す原則）。
