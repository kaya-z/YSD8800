## 0. 本設計書の位置付け（原則43 本質的動機）

本改訂の**本質的動機**は「RTL 実装との整合が取れているのは kernel v12.8 のみであり、
FPGA V8-b 工程（yuios.bin の RTL 実行）に着手するためには kernel v12.8 化と、
それに伴う yuios サイズ変化に応じた絶対ゲート再設定が不可避である」ことにある。

Makefile v1.1 は scc23 v2.04 対応で dhrystone 側の絶対ゲートを更新したが、
kernel 側は v12.7 のままに据え置かれていた。これは CHAT120〜122 の作業範囲外で
あったための「意図的な据え置き」ではあるが、V8-b 着手時点で顕在化する
**設計負債**（原則77）である。本設計書は、この負債を「直す前に記録」する
目的も兼ねる。

## 1. 設計負債の記録（原則77）

### 1.1 顕在化した経緯

| 時点 | 出来事 |
|---|---|
| 2026-07-13 | emu23 v1.10 でタイマー再武装契機を「IRET 命令」→「TCR bit5 書込」へ変更（kaizen 原則73 対応）。同日 kernel v12.8 実装完了。 |
| 2026-07-13 以降 | RTL 側（`ysd8800_ysd8002_v0_3.sv` 等）は V5 TCR-ACK 方式で凍結。 |
| CHAT117〜119 | V8-D 工程（Dhrystone RTL 動作確認）。kernel 非依存の C プログラム対象のため、kernel 版数差異は顕在化せず。 |
| CHAT120〜122 | scc23 v2.04（char ロード幅是正）・startup_harness23 v1.7（IRQ1 A/B/X 全退避）。**kernel は対象外**。Makefile v1.1 化はしたが KERN_SRC は v12.7 のまま。 |
| CHAT123（本チャット） | V8-b（yuios.bin RTL 実行）着手時、方針①検討により **RTL と kernel v12.7 の非整合が発覚**。 |

### 1.2 なぜ据え置きが継続したか（Why-Why 分析）

- Why-1: Makefile v1.1 改版時（CHAT121）に kernel 版数の同期が漏れた。
- Why-2: scc23 v2.04 対応の焦点が dhrystone 側（絶対ゲート 826→819）に絞られており、yuios 側は「対象範囲外」として意識から外れた。
- Why-3: V8-b 着手までは「yuios.bin を RTL で回す」場面が存在しなかったため、kernel v12.7/v12.8 差異が実害として顕在化する機会が無かった。
- Why-4: kernel v12.7→v12.8 移行の独立工程が明示的に立てられていなかった（暗黙に「emu23 動作確認完了 = 完了」と扱われた）。

### 1.3 再発防止（原則追加候補）

**候補原則**：ツール／サブシステム（RTL・emu23・kernel・scc・hasm・lnk）のいずれかで
「実装契機の変更」を行った場合、他サブシステムの追随状況を Makefile（版数・
KERN_SRC 参照・絶対ゲート）に **明示リスト**で書き留め、追随完了までは
Makefile ヘッダに「追随未完タグ」を残す。

（正式起票は本工程完了後に kaizen.txt へ提案。本設計書内では言及のみ）

**Makefile v1.1 実源の在処**（レビュー指摘5 対応）：

  CHAT123 開始時点で削除操作の影響により実源ディレクトリから消失。

  として取得。本設計書はこの実源を Makefile v1.1 として扱う。
- Pre-2 実施時にプロジェクトナレッジへ v1.2 として再登録する。

| 項目 | 変更前（Makefile v1.1） | 変更後（Makefile v1.2） |
|---|---|---|
| `KERN_SRC` | `kernel_v12_7.asm` | `kernel_v12_8.asm` |

**根拠**：
- kernel v12.8 は V5 TCR-ACK 方式（RTL 実装と整合）に対応（kernel_v12_8.asm ヘッダ §v0.12.8）。
- kernel v12.7 の IRQ0_HANDLER には TCR bit5 書込みが無く、RTL 上で走らせるとタイマーが二度と発火しない（永久停止）。
- V8-b（yuios.bin RTL 実行）の前提条件として v12.8 化は不可欠。

### 2.2 yuios 絶対ゲート値の再凍結

| 項目 | 変更前（Makefile v1.1） | 変更後（Makefile v1.2） |
|---|---|---|
| yuios 絶対ゲート | 56,416 バイト完全一致 | **56,424 バイト完全一致**（+8B確定・Pre-3 で実測確認） |
| リファレンス `REF_BIN` | `yuios_ref_road2_I3.bin`（v12.7 由来） | `yuios_ref_road2_I4.bin`（v12.8 由来・本工程で凍結） |
| 旧リファレンス扱い | 現用 | **`yuios_ref_road2_I3_archived.bin` にリネーム保持**（Q-B 保持決定・前版情報欠落防止） |

**確定命令内訳（kernel_v12_8.asm L458-459 で実源確認済）**：

1. `LDW B, #$TCR_ACK_REARM` — 4B（opcode + reg_byte + imm16、hasm23_v1_04.c L465-483 準拠）
2. `STW B, [TCR]` — 4B（opcode + reg_byte + abs16、hasm23_v1_04.c L465-483 準拠）

**サイズ変化：+8 バイト確定**（EQU 定数直接指定により A レジスタ不要、実装は 2命令に集約）。

なお kernel_v12_8.asm ヘッダ L12 は「ACK 3命令挿入」と記述されているが、これは当初計画（3命令）が実装最適化で 2命令に集約された経緯を反映していない**既存記述（実装との食い違い）**と推定される。本設計書 v1.1 では実源優先で **+8バイト確定**表記に整理する。

**予想サイズ**：56,416 + 8 = **56,424 バイト**。Pre-3 で実測確定する。

## 4. 工程分割理由（原則87 系）

「kernel v12.7 → v12.8 化」と「V8-b（yuios.bin RTL 実行）」を **同一工程で
実施しない**のは、失敗時の弁別可能性を確保するため。

同時実施した場合：
- V8-b で失敗した際、「v12.8 実装バグ」／「RTL バグ」／「新絶対ゲート値誤設定」
  のいずれが原因か切り分け不能。

分割実施の場合：
- Pre 工程で emu23 上の v12.8 動作を確定 → RTL 側の凍結との整合が確認できた
  状態で V8-b に着手 → V8-b で失敗した場合は「RTL vs emu23 の差」に切り分けが
  絞られる（原則87：弁別能力のある負例）。

さらに Pre-4 の AC-2（案C）自体が原則87 の直接適用となっており、
「v12.7 は永久停止する / v12.8 は完走する」の弁別対比で TCR-ACK 修正の
妥当性そのものを実証する。
