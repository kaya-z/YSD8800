## 0. 本設計書の位置付け（原則43 本質的動機）

本改訂の**本質的動機**は「RTL 実装との整合が取れているのは kernel v12.8 のみであり、
FPGA V8-b 工程（yuios.bin の RTL 実行）に着手するためには kernel v12.8 化と、
それに伴う yuios 絶対ゲートの再設定が不可避である」ことにある。

Makefile v1.1 は scc23 v2.04 対応で dhrystone 側の絶対ゲートを更新したが、
kernel 側は v12.7 のままに据え置かれていた。これは CHAT120〜122 の作業範囲外で
あったための「意図的な据え置き」ではあるが、V8-b 着手時点で顕在化する
**設計負債**（原則77）である。本設計書は、この負債を「直す前に記録」する
目的も兼ねる。

**本 v1.2 は Pre-3 実測結果を反映し、AC-1 の判定基準を根本改訂する。**

### 1.2 なぜ据え置きが継続したか（Why-Why 分析）

- Why-1: Makefile v1.1 改版時（CHAT121）に kernel 版数の同期が漏れた。
- Why-2: scc23 v2.04 対応の焦点が dhrystone 側（絶対ゲート 826→819）に絞られており、yuios 側は「対象範囲外」として意識から外れた。
- Why-3: V8-b 着手までは「yuios.bin を RTL で回す」場面が存在しなかったため、kernel v12.7/v12.8 差異が実害として顕在化する機会が無かった。
- Why-4: kernel v12.7→v12.8 移行の独立工程が明示的に立てられていなかった（暗黙に「emu23 動作確認完了 = 完了」と扱われた）。

### 1.3 再発防止（原則追加候補）

**候補原則A**：ツール／サブシステム（RTL・emu23・kernel・scc・hasm・lnk）のいずれかで
「実装契機の変更」を行った場合、他サブシステムの追随状況を Makefile（版数・
KERN_SRC 参照・絶対ゲート）に **明示リスト**で書き留め、追随完了までは
Makefile ヘッダに「追随未完タグ」を残す。

**候補原則B（本 v1.2 で追加）**：実装差分のバイト数予測は、命令サイズの単純加算ではなく、
**メモリマップ制約（`.org` パディング・セクション境界）まで含めた実測ベース**で確定する。
「+N バイト追加」の予測は、それが最終バイナリのトータルサイズに反映される保証がない。
「実装差分の存在」を確認したければ、バイナリ内の**特徴バイトパターンの直接検索**を判定基準にすべき。

（正式起票は本工程完了後に kaizen.txt へ提案。本設計書内では言及のみ）

### 2.2 yuios 絶対ゲート値の再凍結（v1.2 で根本改訂）

**v1.1 の予測は誤りであったため、Pre-3 実測結果に基づき改訂する。**

| 項目 | v1.1 予測 | v1.2 実測確定 |
|---|---|---|
| yuios 絶対ゲート（サイズ） | 56,424B（+8B 予想） | **56,416B（v12.7 と同一・不変）** |
| yuios 絶対ゲート（内容） | サイズ一致のみ | **サイズ 56,416B ＋ TCR-ACK バイトパターン `21102300230190fc` が 1 箇所存在** |
| リファレンス `REF_BIN` | `yuios_ref_road2_I3.bin`（v12.7 由来） | `yuios_ref_road2_I4.bin`（v12.8 由来・Pre-5 で凍結） |
| 旧リファレンス扱い | 現用 | `yuios_ref_road2_I3_archived.bin` にリネーム保持（Q-B 保持決定・前版情報欠落防止） |

**サイズが不変である構造的理由**：

kernel_v12_8.asm には kernel_v12_7.asm と同一の `.org` 指定が並ぶ（$0020, $0030, $01C0, $02C0, $0380, $03D0, $0440, $0460, $0520, $0700, …）。v12.8 で追加された +8B の TCR-ACK 命令列（`.org $0030` セクション内・具体位置 offset $003D）は、次の `.org $01C0` までのゼロパディング領域（$01C0 - $0030 = 400B の余裕）が -8B されるだけで、次のセクション以降のアドレスは変わらない。結果として：

- kernel .obj のコードサイズ：v12.7=5,238B、v12.8=**5,238B**（変わらず）
- kernel .obj のシンボル数：v12.7=167、v12.8=**169**（TCR / TCR_ACK_REARM の 2 EQU 分のみ増加）
- yuios.bin のトータルサイズ：v12.7=56,416B、v12.8=**56,416B**（変わらず）

これは YSD8800 ISA / hasm23 の `.org` 挙動として正常。

**v12.8 の実装差分が確かに反映されている根拠**（Pre-3 実測）：

- 両バイナリを `cmp -l` すると **offset $003D から 271 バイトが差分**（v12.8 で +8B シフトした結果、以降 264B のずれ相当が続く形）
- v12.8 版 offset $003D-$0044 は **`21 10 23 00 23 01 90 fc`**（TCR-ACK 8B パターン）
- v12.7 版 offset $003D は `22 00 92 47 ...`（既存の別命令）

### 2.3 新 AC-1（TCR-ACK バイトパターン方式）

**v1.1 の「+8B・56,424B 完全一致」判定は構造的に成立不能のため、以下に改訂する。**

**新 AC-1**：`yuios_road2.bin` に対し、**TCR-ACK 命令列の 8B バイトパターン `21 10 23 00 23 01 90 fc`**（連続 16 進文字列 `21102300230190fc`）が **1 箇所ちょうど**存在すること。

**弁別性の実証**（Pre-3 実施済）：

- v12.7 版バイナリ：0 hit（TCR-ACK パターン存在せず）
- v12.8 版バイナリ：**1 hit**（offset $003D に存在）

判定コマンド例：
```bash
od -An -tx1 -v yuios_road2.bin | tr -d ' \n' | grep -oE '21102300230190fc' | wc -l
# 期待値: 1
```

（`xxd -p` 相当だが、環境によって `xxd` が無い場合の代替として `od -An -tx1 -v | tr -d ' \n'` を用いる。）

**バイトパターンの根拠**（実源）：

| 命令 | ISA2.3 バイト表現 | 根拠 |
|---|---|---|
| `LDW B, #$0023` | `21 10 23 00` | hasm23_v1_04.c L763 / L1064〜1073 の LDW opcode=$21・B_reg=$10・imm16 little-endian |
| `STW B, [$FC90]` | `23 01 90 fc` | 同・STW opcode=$23・B_reg=$01・abs16 little-endian |

- kernel_v12_8.asm L353 `TCR_ACK_REARM EQU $0023` は TIMER_EN($01) | IRQ_EN($02) | IRQ_ACK($20) = $23
- kernel_v12_8.asm L458-459 で `LDW B, #$TCR_ACK_REARM` / `STW B, [TCR]`
- `TCR` は L352 で `EQU $FC90`

Pre-3 実測で本パターンは v12.8 版 yuios.bin の offset $003D-$0044 に確認済。

### 2.4 Dhrystone 絶対ゲートは不変

| 項目 | Makefile v1.1 | Makefile v1.2 |
|---|---|---|
| Dhrystone 絶対ゲート | 819/48785/P:20 | **819/48785/P:20 変更なし** |

Dhrystone は kernel を積まない C 単体プログラム（`dhry_timer.c` + `startup_harness23_v17.asm`）で構成される。kernel v12.7/v12.8 の差異は Dhrystone の実行経路に影響しない。

## 4. 工程分割理由（原則87 系）

「kernel v12.7 → v12.8 化」と「V8-b（yuios.bin RTL 実行）」を **同一工程で実施しない**のは、失敗時の弁別可能性を確保するため。

同時実施した場合：
- V8-b で失敗した際、「v12.8 実装バグ」／「RTL バグ」／「新絶対ゲート値誤設定」のいずれが原因か切り分け不能。

分割実施の場合：
- Pre 工程で emu23 上の v12.8 動作を確定 → RTL 側の凍結との整合が確認できた状態で V8-b に着手 → V8-b で失敗した場合は「RTL vs emu23 の差」に切り分けが絞られる（原則87：弁別能力のある負例）。

さらに Pre-4 の AC-2（案C）自体が原則87 の直接適用となっており、「v12.7 は永久停止する / v12.8 は完走する」の弁別対比で TCR-ACK 修正の妥当性そのものを実証する。

**v1.2 補記**：AC-1 も v1.2 で「v12.7 版=0 hit / v12.8 版=1 hit」の弁別性判定に改訂され、Pre 工程内で **AC-1・AC-2 の両方が原則87 の直接適用**となった。

## 9. Pre-3 実測時の教訓（原則76・原則87 の運用強化）

**教訓1（原則76 の適用範囲拡張）**：
実源照合は「命令サイズ計算」だけでは不十分。**メモリマップ制約（`.org` パディング・セクション境界）まで含めた実源照合**が必要。今回、hasm23_v1_04.c で LDW=4B・STW=4B を確定させたのは正しかったが、それが **yuios.bin のトータルサイズにそのまま反映される**という前提が誤っていた。ISA レベルの命令サイズと、リンク後のバイナリレイアウトは別の層。

**教訓2（原則87 の判定基準構造の妥当性）**：
「弁別能力のある判定基準」を立てる際、**判定基準自体の構造妥当性**も確認すべきだった。「サイズ一致」は**サイズが変わる保証がある場合のみ**弁別に使える。今回のように `.org` パディングで吸収される変更では、サイズ判定は弁別性を持たない。より堅牢な判定基準は「**バイナリ内の特徴バイトパターン検索**」など、実装差分の存在を直接確認する方式。

**教訓3（設計予測の実源事前検証）**：
「+8B ちょうど増える」という予測は、実際にビルドして確認するまで検証しなかった。今後、サイズ予測を判定基準に組み込む場合は、**設計書起票時に暫定ビルドで実測確認**することを推奨。今回は Pre-2 で Makefile v1.2 を作った後、Pre-3 で初めて実測した結果、Pre-2 の Makefile 記述と設計書 v1.1 の両方に修正が必要になった。

**再発防止としての判定基準立案チェックリスト**（本設計書 v1.2 で提案・kaizen 提案候補）：

1. [ ] 判定基準の**変化条件**は本当に成立するか？（サイズ変化なら「サイズが変わる保証」があるか？）
