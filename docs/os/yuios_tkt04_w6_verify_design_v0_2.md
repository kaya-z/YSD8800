## 0. 結論先出し —— W-6 で「検証できること」と「できないこと」

本設計に着手して**実源で前提を詰めた結果、W-6 の当初想定は成立しないことが判明した**。
設計方針を提示する前に、この評価を先に述べる。

| 当初想定 | 実源による評価 |
|---|---|
| `TASK_CREATE` を多数回呼べば、TKT-04 の二重条件が**自然発生**する | **❌ 成立しない**（§1） |
| よって W-6 は TKT-04 の「実運用での最終確認」になる | **❌ ならない** |

**W-6 は実装を取り下げる**（§2）。当初 v0.1 で「未カバーの組5 を検証できる」と再定義したが、
**その再定義自体が誤りであった**（`_irq_noready` は保存経路を持たないため m×n の組にならない）。
この点を曖昧にしたまま W-6 を実施し PASS を得ると、
**「TKT-04 は実運用形態でも確認済み」という誤った安心**を生む。

**TKT-04 のクローズは W-5 を根拠とすること**（§3）。

## 1. 二重条件の自然発生が成立しない理由

### 1.1 条件1（`EI` 窓での IRQ0 中断）—— 統計的には踏める

`TASK_CREATE` の `EI` 窓は実測で **2 命令**（`.dbg` 実測）。

```
0612 951 EI                      ← 1バイト命令
0613 952 SUBI X, #2              ┐ 窓（2命令）
0617 953 STW  A, [X]             ┘
0619 954 RET
```

`emu23` のタイマ IRQ は **40,000 サイクル周期**（`YSD8002_init(4000000, 100)`・L1958）で、
YSD8800 は **CPI=1** であるから 40,000 命令に 1 回。

| 項目 | 値 |
|---|---|
| 1 回の `TASK_CREATE` あたりの窓ヒット確率 | `2 / 40,000` = **5×10⁻⁵** |
| 期待ヒット数 λ | `N × 5×10⁻⁵` |
| λ=3（P(≥1回) ≒ 95%）に必要な N | **60,000 回** |

**実行可能性**: PoC 全体（V 系＋W 系）の完走が実測 **16 ms**。
1 試行あたり概算 300 命令として `60,000 × 300` = 1,800 万命令であり、**数秒で完了する**。
→ **条件1 は N=60,000 で統計的に踏める。**

### 1.2 条件2（再開が `_sc_found` 経由）—— ★踏めない★

`_sc_found` は **SYSCALL 契機のスケジューリング経路**である。
条件2 が成立するには「**中断されたタスクとは別のタスクが SYSCALL を発行し、
その延長で中断タスクが再開される**」必要がある。

しかし W-6 のハーネスは `TASK_CREATE` を反復呼出する**単一の実行流**であり、
別タスクが SYSCALL を発行する契機が存在しない。
IRQ0 で中断された場合の再開経路は次のいずれかであり、**`_sc_found` は通らない**。

| READY タスクの有無 | 復元経路 | 実源 |
|---|---|---|
| 無し（全 SLEEPING） | **`_irq_noready`** | L557 以降 |
| 有り | **`_sched_found`** | L582-610 |

### 1.3 タイマ周期の変更 ★v0.2 全面是正: M-3★

> **★v0.1 の誤り（取消線で保持）★**
> ~~条件1 のヒット密度を上げる目的で周期短縮を検討したが、**手段が存在しない**。~~
> ~~MMIO から周期設定 ❌ ｜ `TCR($FC90)` は … **周期レジスタが存在しない**~~
> ~~emu23 のコマンドラインオプション ❌ ｜ `YSD8002_init(4000000, 100)` は**ハードコード**~~
> ~~→ §6 に emu23 改修候補 EMU-D として起票する。~~
>
> **★誤りの本質: 調査対象を取り違えた（KY34 違反）★**
> 引用した L341-364 は **`kernel_v12_11.asm` のカーネル側 EQU 定義**であり、
> **`emu23` の MMIO マップではない**。「カーネルが定義していない」ことを
> 「**エミュレータに機能がない**」と読み替えてしまった。
> **emu23 の機能は emu23 の実体で判定しなければならない。**

**正しい結論: PERIOD レジスタは実在し、周期は PoC から変更できる。**

```c
/* emu23_v111.c L601-605（実体確認済） */
#define TCR_ADDR      0xFC90
#define PERIOD_HI     0xFC92
#define PERIOD_LO     0xFC94
#define CYCLE_LO      0xFC96
#define CYCLE_HI      0xFC98
```

| レジスタ | アドレス | 機能 |
|---|---|---|
| `PERIOD_HI` / `PERIOD_LO` | `$FC92` / `$FC94` | **書込で即座に周期が変わる**（L745-754）。TCR の IRQ_ACK 再武装も PERIOD を参照（L275-277） |
| `CYCLE_LO` / `CYCLE_HI` | `$FC96` / `$FC98` | **総サイクル数の読み出し**。**必ず LO → HI の順**（LO 読み出しが HI をラッチ・L628-633）。書込は無視（読出専用） |

**影響**

| 項目 | 是正内容 |
|---|---|
| **EMU-D の起票** | **不要**（取り下げ）。emu23 は既に対応済み |
| §1.1 の確率計算の前提 | 40,000 サイクル固定ではない。**PERIOD=200 なら窓ヒット率は `2/200` = 1%** となり、λ=3 に必要な試行数は **60,000 → 300** に落ちる |
| λ の算出手段（v0.1 の R-3） | **解決済**。`CYCLE` を PoC 内から読めるため、**emu23 の外部出力に頼らず自前計算できる** |

## 2. W-6（`TASK_CREATE` 反復による統計試験）の取り下げ

### 2.1 取り下げの決定

**本設計書 v0.1 §2 以降で提案した「組5 の統計試験」としての W-6 は取り下げる。**
理由は 3 点であり、いずれもレビュー v1.0 の実体照合により判明した。

### 2.2 理由1: 「組5＝IRQ0 保存 × `_irq_noready` 復元」という定義が成立しない（M-1）

```asm
; kernel_v12_11.asm L573-580（実源）
; 本経路ではTCBへのコンテキスト保存を行っていない（非RUNNINGのため
; BNE _irq_sched でスキップ済）ので、入口退避の IRQ_WK_* 3本を戻せば
; 中断点が完全復元される。FLAGSはIRETが復元する。
_irq_noready:
    LDW  A, [IRQ_WK_A]
    LDW  B, [IRQ_WK_B]
    LDW  X, [IRQ_WK_X]
    IRET
```

| `CUR_TASK` の state | 保存 | 復元 |
|---|---|---|
| RUNNING(2) | **する**（L496-516）→ READY(1) 化（L519-520） | 走査で自分自身がヒット → **`_sched_found`** |
| RUNNING 以外 | **しない**（L492-494 `BNE _irq_sched` でスキップ） | READY 不在なら **`_irq_noready`** |

> **★`_irq_noready` に到達するのは「保存を行わなかった」場合だけである。★**
> よって「IRQ0 保存 × `_irq_noready`」という組は**原理的に存在しない**。

| | 組1〜組4 | `_irq_noready` |
|---|---|---|
| 復元元 | **TCB の `saved_a`/`saved_b`** | **`IRQ_WK_A`/`IRQ_WK_B`/`IRQ_WK_X`**（入口退避） |
| 命題 | コンテキストスイッチで A/B が引き継がれるか | **割込ハンドラが破壊した A/B/X を中断点に戻すか** |
| TKT との関係 | **TKT-04**（M-5 の直接対象） | **TKT-00**（M-5 とは無関係） |

**→ `_irq_noready` を m×n 表に「組5」として並べるのは誤り。別軸の検証項目である。**

### 2.3 理由2: ハーネスが確実に暴走する（M-2）

```asm
; kernel_v12_11.asm L911-913（実源・_tc_found）
    ; TCB初期化
    LDW  A, #1
    STW  A, [X]                 ; ★READY(1)
```

`TASK_CREATE` は**生成した TCB を READY(1) にする**。戻り値を積む L951-953 は
**READY 化（L913）よりずっと後**である。

```
L913  STW A,[X]        ; tid=1 が READY になる
L951  EI               ; ★ここから割込が開く。READY タスクが 1 個存在する状態
L952-953               ; ★W-6 が捕まえたい EI 窓
L954  RET
      （PoC 側の比較・カウンタ更新・ループ）
_w6_loop 先頭で DEAD(0) へ戻す ← ★ここまで READY のまま
```

この区間で IRQ0 が入ると `_sched` が tid=1 を拾い **`_sched_found`** 経由で
**新タスクの `entry_addr` へジャンプする**。しかも `CUR_TASK` の TCB は SLEEPING(3) のため
L492-494 で保存がスキップされており、**PoC ループの文脈はどこにも保存されていない＝復帰不能**。

> **★構造的な自己矛盾★ W-6 が捕まえたい事象（`EI` 窓での IRQ0）が起きた瞬間に暴走する。**
> N=60,000 回まわす設計では、この区間を踏むのは**ほぼ確実**である。

### 2.4 理由3: `TASK_CREATE` を絡める必然性が無い

理由1 のとおり `_irq_noready` は保存経路を持たない。
**`TASK_CREATE` を呼ばなければ READY タスクは生まれず、タイマ IRQ は必ず `_irq_noready` を通る。**
すなわち検証目的に対して `TASK_CREATE` は不要どころか**妨害要因**であった。

### 2.5 併せて是正する表現（C-2）

> **★v0.1 の過剰表現（取消線で保持）★**
> ~~条件2 を自然発生させる試験は、現行の PoC 構成では**設計不能**である。~~

**正しくは「本 PoC の単一実行流では成立せず、かつ W-5 が代替済みのため実施しない」。**
原理的には 2 タスク構成（タスク A が `TASK_CREATE` を反復、タスク B が周期的に SYSCALL を発行）で
条件2 は発生しうる。やらない理由は**不可能だから**ではなく、**費用対効果が無いから**である。

> 「不能」と書くと、**Level 2（複数プロセス同時実行）で同種の試験を検討する際に
> 誤った前提が引き継がれる**。
