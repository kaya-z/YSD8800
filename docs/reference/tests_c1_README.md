## 1. 目的

`scc23_v2_00_design_v2_10.docx` §9 の C-1（call 戻り値型の網羅テスト不足）に対応し、
**Phase 2（型システム統合）以降で回帰を検出するセーフティネット**を張る。

本テストは実際に、整備の過程で **scc23 v2.05 の C-3 修正（案D）の網羅性の穴**
（両辺とも未定義 call のとき float 経路に入らず案D が不発 → Q8.8 演算が
`_cc_mul`/`_cc_div` で生成され値破壊）を発見し、v2.06 の案G による修正につながった。

---

## 2. マトリクスの次元

| 次元 | 値 | 記号 |
|---|---|---|
| 戻り値型 | int / float | `i` / `f` |
| 演算 | 加算 / 除算 | `add` / `div` |
| 右辺種別 | 定数 / 変数 / call | `k` / `v` / `c` |
| プロトタイプ | あり / なし | `p` / `n` |

**組合せ数**：2 × 2 × 3 × 2 = **24 ケース**

**ファイル名規約**：`m1_<戻値型>_<演算>_<右辺>_<proto>.c`
（例：`m1_f_div_c_n.c` = float 戻し × 除算 × 右辺 call × プロトタイプなし）

**演算を加算・除算の2種に絞った根拠**（設計書 §1.4）：
元の C-3 バグは**加算で顕在化**しており加算は必須。除算（FDIV）は Q8.8 の
**最複雑経路**（`_fdiv` ランタイム呼出・シフト補正・ゼロ除算保護）。
乗算・減算は挙動が包含されるため削減リスクが低い。完全網羅（48通り）は
C-2（Q8.8 ヘルパ整備）完了後に検討する。

## 3. 期待挙動（scc23 v2.06 基準）

| プロトタイプ | 戻り値型 | 期待 | 件数 |
|---|---|---|---|
| あり | int | `compile_ok` | 6 |
| あり | float | `compile_ok` | 6 |
| なし | int | `error_stop` | 6 |
| なし | float | `error_stop` | 6 |

**内訳：`compile_ok` 12 / `warning_only` 0 / `error_stop` 12**

`proto=なし` が全て `error_stop` になるのは、**v2.06 の案G（未定義関数呼び出しの
error 化＝前方宣言必須化・C99 準拠）**による。v2.05 時点では `proto=なし`×`int` は
`warning_only` だった（設計書 v0.4 §1.2 に旧表を取り消し線で保持）。

### `warning_only` 分類について

**v2.06 時点では該当 0 件**だが、**分類は残置**している（設計書 §2.2）。
理由は、`warning()` 関数自体は scc23 に残っており将来 warning のみを出す検査が
追加される余地があること、判定ロジックの分岐を残しておくこと、
そして「この挙動が発生しないこと自体が保証情報である」ことによる。

## 4. 判定方式

### 4.1 `compile_ok` / `warning_only`

**主判定：v2.06 で凍結した golden asm との byte 一致**（`cmp`）。

誤 I2F 挿入の grep 検出は**主判定に使わない**。`SIR_I2F` の emit は
`LDW B,#8 / SHL A,B` であり、**明示キャスト `(float)i` や正当な int→float 昇格でも
同一命令列が生成される**ため false positive を招く（設計書 §2.3）。
grep は golden 凍結時のサニティ補助にとどめる。

加えて `.expected` の `golden_version` が `v2.06` であることも確認する。

### 4.2 `error_stop`

**非0終了 AND error メッセージに `expect_error_contains` を全て含む**（AND 条件）。

`compile()` は error が発生しても生成を最後まで継続するため
（`return error_count?1:0` のみ）、**壊れた asm がファイルに残る**。
非0終了だけを判定に使うと壊れ asm の残存を見逃すため、メッセージ内容も検査する。

**`expect_error_contains` に何を指定するか（重要）**

v2.06 の V7 実測結果：

| ケース種別 | 案G（`add a prototype declaration before use`） | 案D（`used in float context`） |
|---|---|---|
| 片側 float 定数/変数（`f_*_k_n` / `f_*_v_n`） | 1件 | 1件 |
| **両辺とも未定義 call**（`*_*_c_n`） | 2件 | **0件** |
| int 文脈のみ（`i_*_k_n` / `i_*_v_n`） | 1件 | 0件 |

- **主判定は案G のメッセージ**。全 12 ケースに必ず出るため一律指定して安全
- **案D のメッセージ `used in float context` は一律指定してはならない**。
  片側 float の 4 ケースにしか出ないため、一律指定すると
  **両辺未定義ケースで AND 条件が成立せず FAIL する**

### 4.3 壊れ asm の隔離

`error_stop` ケースで生成された asm は、テスト実行時に自動で
`corrupt_asms/` へ隔離される（設計書 §2.6）。
値破壊を含む asm を後続工程（hasm23）へ渡す事故を防ぐため。

## 4.5 ★復元手順（ナレッジからの再構築）★

プロジェクトナレッジは tar.gz を扱えないため、本スイートは **4ファイル**で保存し、
そこから完全復元する方式をとる。

**保存する4ファイル**：

| ファイル | 役割 |
|---|---|
| `gen_matrix.py` v1.1 | テストソース24 + 期待値24 + ディレクトリを生成 |
| `c1_goldens_bundle_v1_1.txt` | **golden 12件**（v2.06 凍結・再生成不可） |
| `run_c1_matrix.sh` v1.1 | 実行スクリプト |
| `tests_c1_README.md`（本ファイル） | 設計・運用ルール |

**復元手順**：

```bash
mkdir tests_c1 && cd tests_c1
# 上記4ファイルを配置してから
python3 gen_matrix.py                                   # ソース24 + 期待値24 + ディレクトリ
python3 gen_matrix.py --unbundle c1_goldens_bundle_v1_1.txt   # golden 12
cp <compiler> ./scc23
bash run_c1_matrix.sh                                   # 24/24 PASS になれば復元成功
```

**復元検証済**：本方式で golden 12件・期待値24件が byte 単位で原本と完全一致し、
scc23 v2.07 で 24/24 PASS することを確認済み（2026-08-13）。

**なぜ golden だけ生成できないのか**：golden は v2.06 が実際に出力した生成コードの
実体である。ソースから作り直すことは「別版のコンパイラで生成し直すこと」であり、
凍結の意味（当時の基準を保存すること）が失われる。ゆえにバンドルとして保存する。

## 7. ★golden 更新ルール（厳守）★

設計書 §7.5 より。**golden 方式には「回帰時に安易に golden を上書きして
回帰を握り潰す」という典型的な失敗モードがある。** 本テストの存在意義に
直結するため、以下を厳守すること。

1. **原則：golden との差分は「回帰疑い」として調査する。**
   差分が出た時点で自動的に golden を更新してはならない。
2. **調査手順**：差分箇所を特定（`diff out/X.asm goldens/X.golden.asm`）→
   差分が生じたコンパイラ改修を特定 → **意図した仕様変更か／意図しない回帰か**を判定。
3. **golden 更新が許されるのは仕様変更が正当と判断された場合のみ**。その際は
   **変更理由の記録**と `golden_version` の刻み直し（例：`v2.07`）を必須とする。
4. **無検討の上書きは禁止。** 本スクリプトには golden 自動更新機能を
   **意図的に実装していない**。
5. **Dhrystone 絶対ゲート（826/48405/P:20/21846B）との併走**：
   golden 差分が出たら絶対ゲートも同時に確認する。絶対ゲートが破れていれば確実に回帰。
6. **責任分界**：golden 更新の判断は設計レビューを経ること（原則43）。
   テスト実行者が単独で golden を上書きしない。

## 8. 新規テスト追加時の注意（v2.06 の仕様変更）

scc23 v2.06 以降は **前方宣言必須化（C99 準拠）** である。
新しいテストソースや C コードを書く際は：

1. **関数は使用前にプロトタイプ宣言または定義が必要**。
   後方で定義した関数を前方から呼ぶ場合、冒頭にプロトタイプ宣言を置く
2. 組込関数（`putchar` / `getchar` / `puts` / `printf` / `sprintf` /
   `strcpy` / `strcmp` / `memcpy` / `strlen`）は事前登録済みのため宣言不要

また、**期待値は実行前に確定させる**こと（テスト・ファースト）。
実測に合わせて期待値を書くと、テストは間違いを追認する装置になる。
期待値と実測が食い違ったら、**まずどちらが間違っているかを調査する**。
