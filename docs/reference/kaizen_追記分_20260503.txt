■ 設計ルール追加
─────────────────────────────────────────────

■ 原則11: 新規コンポーネント実装前にツールチェーンの健全性を確認する

  新しいForthワードやアセンブラコードを実装する前に、
  使用するツール（Force、hasm23等）が対象命令を正しく
  生成するかを単体テストで先に確認する。

  設計書に以下のステップを「§ XX.0 前提確認」として必ず設ける。

    □ 使用するForth primitiveのコード生成を単体確認する
    □ CODEワードで使用するISA命令をhasm23で単体アセンブルして確認する
    □ エミュレータのMMIO初期値が設計書と一致しているか確認する

  ※ ツールチェーンのバグと実装バグが混在すると
    デバッグの効率が著しく低下する。
    ツールの動作を先に確定させてから実装に入ること。

■ 原則12: ハードウェア仕様→エミュレータ実装は必ず転記チェックを行う

  周辺デバイス設計書（YSD8001/8002/8003/8004等）に
  レジスタ初期値・IRQマスク・STATビット定義を記載したら、
  emu23の対応箇所を同時に更新し、以下を確認する。

    □ レジスタ初期値 → emu23の初期化コードに反映済みか
    □ IRQマスク初期値 → emu23のirq_mask初期値と一致するか
    □ STATビット定義 → emu23のrd8/wr8ハンドラと一致するか

  ※ 設計書とエミュレータの初期値が食い違うと、
    ハードウェア由来のバグとソフトウェアバグの区別がつかなくなる。

■ 原則13: Forthワード定義には標準テンプレートを使用する

  原則7（TOS明示）・原則6（副作用明記）の運用を
  個人の注意に依存させず、設計書のテンプレートに組み込む。

  【Forthワード定義 標準テンプレート】

    ワード名: WORD-NAME
    スタック : ( 引数2 引数1<TOS> -- 戻り値<TOS> )  ← TOS明示必須
    副作用  : 使用ワーク変数=XXX / DSP影響=なし     ← 必須記載
    前提条件: （例）DSPが空であること               ← 必須記載
    危険な組み合わせ: （例）YYYYY直後は呼ばないこと  ← 該当時記載

  ※ このテンプレートに沿って書けば、原則6・7・8を
    自動的に満たす形になる。

■ 原則14: 初期化処理には「呼び出しタイミング前提」を明記する

  初期化ワード（UART-INIT等）の設計書には以下を必ず記載する。

    ・呼び出しタイミング: （例）IRQ有効化の前/後のどちらか
    ・冪等性            : 複数回呼んでも安全か否か
    ・副作用            : 既存データへの影響（バッファクリアの有無等）
    ・禁止タイミング    : （例）IRQ1発火後に呼んではいけない

  ※ 「いつ呼ばれるか」の時系列前提が設計書に無いと、
    初期化処理が既存データを破壊するバグが潜在する。

■ 原則15: 設計書は「次のチャットが読んで迷わず実装できる」水準で書く

  このプロジェクトはチャットをまたぐと記憶がリセットされる。
  設計書の完全性がそのままデバッグコストに直結する。

  設計書に記載すべき「暗黙にしてはいけない前提」の例：

    ・ツールの動作前提（コード生成の制約・既知バグ）
    ・エミュレータの初期値
    ・初期化タイミングの制約
    ・Forthワードのスタック図（TOS明示）と副作用
    ・ハードウェアレジスタのビット定義と初期値

  ※ 「わかっているはず」として省略した情報が、
    デバッグ時に一つずつ再発見されることになる。
