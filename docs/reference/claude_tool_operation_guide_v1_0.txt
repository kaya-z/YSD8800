 Claude ツール操作規律ガイド
================================================================

【目的】
  YSD8800/YUI OSプロジェクトでは1チャットあたりのツール呼び出し
  （view / bash_tool / str_replace / create_file / grep / sed 等）が
  極めて多い。呼び出しの書式ミスが起きると、ツールが実行されず
  呼び出しタグがそのまま地の文として出力され、画面が乱れ、
  トークンが浪費され、やり直しが発生する。

  本ガイドはその書式崩れ・やり直しを防ぐための、Claudeの
  ツール操作の手さばきに関する規律をまとめたものである。

  ※ 設計・デバッグの考え方は kaizen.txt、デバッグ報告の形式は
    debug_style_guide.txt を参照。本ガイドは「ツール操作」専用。

【適用タイミング】
  各チャットの作業開始前（HANDOVER確認・KY活動と同じ段階）に
  本ガイドを1回参照し、本日適用する留意項目を意識する。

================================================================
■ 規律1: bashコマンドは「1コマンド1目的」に分割する
================================================================

  パイプの多段つなぎは書式が崩れやすい。

  悪い例（多段パイプ・崩れやすい）:
    grep -nE "pat" f | sed 's/.../.../' | awk '{print $2}' | sort -u

  良い例（段階分割・各段で結果を確認）:
    1回目: grep -nE "pat" f          ← まず該当行を出す
    2回目: 結果を見てから必要な加工を次のコマンドで行う

  ルール:
    □ パイプは原則2段まで。3段以上必要なら分割する
    □ 複雑な加工は一時ファイルに出してから次段で処理する
    □ ワンライナーで全部やろうとしない

================================================================
■ 規律2: ファイル生成・編集は専用ツールを使う（bashのヒアドキュメント禁止）
================================================================

  ソースコード全体の書き込み:
    × bash の cat > file << 'EOF' …（クォート・特殊文字で崩れる）
    ○ create_file ツール（本文をそのまま渡せる）

  既存ファイルの部分修正:
    × bash の sed -i（範囲指定ミスで崩れる）
    ○ str_replace ツール（old_str / new_str で明示）

  ※ Forthソース（$記号・< >等）やアセンブラ（#・$・コメント;）は
    bashのクォートで特に崩れやすい。専用ツールを使えば回避できる。

================================================================
■ 規律3: str_replace の前に必ず直前 view で対象を確定する
================================================================

  □ str_replace の直前に対象箇所を view で表示する
  □ old_str は view 結果からコピーする
     （行番号プレフィックス「  N\t」は表示専用なので含めない）
  □ 一度に1箇所だけ修正する（複数箇所同時変更で不一致リスク増）
  □ str_replace 成功後は、以前の view 結果は古くなる。
     同じファイルを続けて編集する場合は再度 view してから行う
  □ 修正後は再度 view して確認してから次の修正へ
     （1変更1検証＝kaizen原則と同じ思想）

================================================================
■ 規律4: 1回の応答に詰め込むツール呼び出し数を抑える
================================================================

  □ 1応答の基本単位は「確認 → 1操作 → 結果報告」とする
  □ 「view×5 + bash×3 + str_replace×2」を1応答に詰め込まない
  □ 探索フェーズ（grep / view）と編集フェーズ（str_replace）を
    応答単位で分ける

  ※ 1応答に多数のツールを詰めるほど、途中の1個が書式崩れすると
    その応答全体が乱れる。小さく刻めば崩れても影響範囲が小さい。

================================================================
■ 規律5: 長い出力はそのまま貼らず、必要部分に絞る
================================================================

  □ view は対象範囲を view_range で絞る（全体を毎回出さない）
  □ grep は -n で行番号付き・必要なら件数を head で制限する
  □ emu23等の長大ログはチャットに全量を出さない
     （debug_style_guide.txt のルールD「要約形式」に従う）
  □ 確認のためだけの大量出力は避け、判断に必要な最小限にする

================================================================
■ チェックリスト（作業開始前の自己確認）
================================================================

  本日の作業で以下を意識する:
    □ bashのパイプは2段までに抑える（規律1）
    □ ファイル生成は create_file、編集は str_replace を使う（規律2）
    □ str_replace は直前 view → 1箇所ずつ（規律3）
    □ 1応答にツールを詰め込みすぎない（規律4）
    □ 出力は必要部分に絞る（規律5）
