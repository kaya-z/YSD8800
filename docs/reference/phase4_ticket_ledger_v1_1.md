## §3. TKT-D1 — `state=5` の二重用途

### 3.1 現象

`state=5`（`TASK_WAIT_IPC`）が★意味の異なる2種類の待ち★に共用されている。

| 使用箇所 | 待つ対象 | 起こす者 | 再開位置 |
|---|---|---|---|
| `IPC4_RECV`（L1062） | IPC メッセージ | `_ipc4_enqueue` | `IPC4_RECV` 冒頭 |
| `TASK_WAIT_IPC_ENTRY`（$1100） | ストレージ IRQ 完了 | `wake_stor_waiter` | `STOR-READ-IMPL` 途中 |

### 3.2 危険

`_ipc4_enqueue`（L2152 付近）は `CMPI A,#5` → READY と★無条件に起こす★。
このため★IRQ 完了待ちのドライバを、無関係な他タスクの IPC が叩き起こす経路★が原理的に存在する。

> MC6809/OS-9 で言えば `F$Sleep` と `F$Wait` を同一プロセス状態で表現し、
> 送出側が両者を区別できなくなるのと★同型の誤り★である。

### 3.3 備考

★②-A' の速度依存 FAIL の原因ではない★（真因は TB 判定器・原則136）。
将来の潜在バグとして工程④で対処する。

### 3.4 対処方針（案・未確定）

待ち状態を分離する（例：`TASK_WAIT_IPC` と `TASK_WAIT_IO` を別値にする）。
起こす側は★自分が起こしてよい状態値のみ★を照合する。

## §4. ★TKT-U1 — 出力順序の速度依存レース（本日起票）★

### 4.1 現象（一次情報・2026-08-30 実測）

`tb_cpu_v8b_prod_v0_3` による V8-b RTL シミュレーションの UART 出力が、
`LATENCY_NORMAL` の値によって★バイトの順序だけ★変化する。

```
LAT=12 : YUIOS Booted!\nYUI> 0123M
LAT= 5 : YUIOS Booted!\n0YUI> 123MD
```

★バイト集合は同一。`'0'` がプロンプト `"YUI> "` の前に出るか後に出るかだけが違う。★

### 4.2 機序（推定）

エコー経路（入力文字 `'0'` の出力）とプロンプト出力経路が
★別タスク／別タイミングで UART を叩いており、両者の到達順に保証がない★。
メモリレイテンシが短いほど前段の処理が早く終わるため、`'0'` が先に出る。

### 4.3 重大度

★低（機能上無害）★。出力されるバイトは欠落も重複もしていない。
人間が端末で見た場合の表示順が入れ替わるだけである。

### 4.4 ★②-B における取り扱い（重要）★

★工程②-B ではキャッシュ有効化により実行速度が変わるため、本レースは再び観測される可能性が高い。★

- ゲート G-1 は★「順序が変わっても FAIL としない」★と定義済み（設計書 §8）
- ②-B のデバッグ中に本現象を観測しても★キャッシュのバグと誤認しないこと★
- 本チケットの存在自体が、その誤認を防ぐための一次資料である

### 4.5 ★実測：②-B 段3 で顕在化（2026-08-31 追記）★

★§4.4 の予測が的中した。★ 段3（キャッシュ本体）の G-1 で実際に観測された。

```
  CEN=0 : YUIOS Booted!\nYUI> 0123MD
  CEN=1 : YUIOS Boot0ed!\nYUI> 123MD
```

| 項目 | 内容 |
|---|---|
| 条件 | `CEN=1`・LAT=12。M-5 が 3,754,937 → ★2,176,196 cycle（−42.0%）★に短縮 |
| 現象 | `'0'`（FILEMGR SB-LOAD 開始マーカー）の位置のみが移動。★出力長 25 B・バイト多重集合 md5 は完全一致★ |
| 判定 | ★G-1 は PASS★（設計書 §8・設計メモ §4 の「順序入替は FAIL としない」規定による） |

★**新たに判明した副作用（本項の主眼）**★

| 項目 | 内容 |
|---|---|
| 現象 | `tb_cpu_v8b_prod_v0_3` の ★`M-3` が未検出（`M-3: 0`）★ になる |
| 原因 | TB の判定が★連続文字列の一致★で書かれているため、`'0'` の割り込みでマーカー文字列が分断される |
| ★危険★ | ★これは RTL の欠陥ではない。★ にもかかわらず「マーカー1つが出ない」という★いかにも不具合らしい形★で現れるため、★キャッシュのバグと誤認しやすい★ |
| 位置づけ | ★原則136（PASS/FAIL 判定ロジック自体も容疑者リストに含める）・KY76 の新たな実例★。②-A' の速度依存 FAIL と★同じ構図★である |

> ★段4 以降の申し送り★
> ★`CEN=1` で `M-3: 0` を見ても RTL を疑ってはならない。★
> 判定すべきは ★UART 出力のバイト多重集合★ である。
> ```bash
> fold -w1 run_X/uart_out.log | sort | md5sum   # → 94819b6f... と一致すること
> ```



### 4.6 対処方針（案・未確定）

工程④で UART 出力を単一の出力キューに集約し、順序を確定させる。
ただし★機能上無害であり、優先度は低い★。

## §5. EMU-D — 31文字超シンボル名でブレークポイント不可

emu23 のシンボルテーブルが 31 文字でシンボル名を切り詰めるため、
31 文字を超える名前ではブレークポイントを設定できない。
既に起票済み。工程④またはツール改修時に対処する。
