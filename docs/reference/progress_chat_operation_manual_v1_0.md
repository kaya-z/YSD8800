## 1. 本チャットの役割

```
・工程管理・KY活動を行う場（相談事チャットは免除・かやぬま氏方針）
・日報の代わりとして、作業日ごとにロードマップ更新報告を行う
・次工程へ進む前に、本チャットの最新ロードマップを参照して
  「次工程の確認ヨシ!」の判定を行う場
・停滞している工程への警告を出す場
```

## 2. チャット新設のタイミング

```
全体工程表（ysd8810_master_schedule）が完成してから本チャットを作る
（かやぬま氏確定方針・2026-09-22）。

チャット新設までの作業ログは、後でまとめて本チャットへ転記する
（ysd8810_project_roadmap_v0_7.md §13.3 参照）。
```

## 3. 報告フォーマット（作業日終了時・日報代わり）

### 3.1 基本構造

```
ロードマップ更新（YYYY-MM-DD時点）

```
（コードブロック内に工程ステータスを記述。詳細は §4 参照）
```

⚠️ 本日の重大な自己是正（該当する場合のみ）
（発生した場合のみ記載。無ければこの見出し自体を省略する）

⚠️ 停滞・注意事項
（ユーザー判断待ち事項、確定した方針、ログ長大化警告等）
```

### 3.2 記載の粒度（★最重要原則★）

```
★直近の工程は細部まで状況を報告し、
  未来の工程は大工程のみ記載する。★

  直近工程（現在進行中、または直前に完了した工程）：
    ・設計書の版数遷移（v0.1→v0.4等）
    ・レビュー結果（承認／条件付き承認／指摘事項の有無）
    ・RTL実装の版数と変更点
    ・実測値・検証結果（PASS/FAIL、具体的な数値）
    ・次に何をするか（1行、矢印「→」で示す）

  未来工程（着手前の工程）：
    ・工程名のみの1行
    ・「← 何が完了したら着手するか」の関門条件のみ付記可
```

## 4. 工程ステータス記号

| 記号 | 意味 | 使用場面 |
| --- | --- | --- |
| ✅ | 完了 | その工程・サブタスクが完了し、以後変更しない |
| 🔧 | 進行中 | 現在作業中の工程。入れ子でサブタスクの✅/⬜を記載 |
| ⬜ | 未着手 | まだ手を付けていない工程・タスク |
| ⚠️ | 停滞・注意 | ユーザー判断待ち、方針未確定、リスク事項 |
| 🆕 | 新規発生 | その日新たに判明した事項・追加タスク（自己発見の不備等） |
| 📤 | 分離・移管 | 別プロジェクトへ分離した、または分離検討中の工程 |
| ★〜★ | 強調 | サブタスク中で特に重要な項目名を挟む |

## 5. 入れ子構造の書き方（直近工程の例）

```
✅ 工程①（完了工程は詳細を畳んでよい。理由が要る場合のみ簡潔に付記）
🔧 工程②（進行中工程）
   🔧 ★サブタスク名★ — 状態を一言で（例：大きく進捗、あと一歩）
      ✅ 完了した作業1（成果を具体的に：版数・数値・PASS件数）
      ✅ 完了した作業2
      🆕 その日新たに判明した不備・追加事項（発見の経緯を一言）
      ⬜ ★次のブロッカー★：内容と、何が止めているか
         → ★ユーザー判断待ち：選択肢A or 選択肢B★
      ⬜ 次に着手するサブタスク（優先順位が確定していれば矢印で明示）
   ⬜ サブタスク（着手前）← 前提条件を一言で
⬜ 工程③（大工程のみ）← 関門条件があれば付記
⬜ 工程④（大工程のみ）
📤 軸（分離検討中の別ライン）→ 状況を一言
🆕 サブプロジェクト（本体と独立して発生したもの）
```

## 6. 「本日の重大な自己是正」欄の使い方

```
その日の作業中に、運用ルール・判断基準そのものの誤りが判明し、
方針を是正した場合にのみ記載する。

書き方：
  ・何が誤りだったか（一文）
  ・是正後の方針（一文）
  ・同種の誤りが他にも見つかった場合はその件数・対象も明記

該当が無い日は、この見出し自体を省略する
（無理に埋めない。存在しない自己是正を書かない）。
```

## 7. 「停滞・注意事項」欄の使い方

```
以下を箇条書きで集約する：

  ・ユーザー判断が必要な事項（選択肢を明示すること）
  ・その日確定した運用方針（「〜が確定済み」の形で）
  ・チャットのログ長大化警告
    （長くなった場合は次チャットへの引継ぎを推奨し、
     HANDOVER文書の作成状況を付記する）
  ・その他、次回作業者（次チャットのClaude）が
    見落とすと工程が止まるもの
```

## 8. 停滞警告の運用（かやぬま氏指示事項）

```
★本チャットを確認する際、停滞している工程には警告を出すこと。★

判定基準（目安）：
  ・「⬜」のまま複数回のロードマップ更新をまたいで
    進捗が無い工程・サブタスク
  ・「⚠️ 停滞・注意事項」に記載されたユーザー判断待ちが
    解消されないまま複数日経過している事項
  ・W-1のような「削除禁止の停滞監視対象」として
    工程表側に明記されている項目

警告の出し方：
  ・工程確認時（「進捗と予定の確認(latest)」チャット参照時）に、
    該当工程を指摘し、着手判断を促す
  ・警告は指摘のみに留め、無断で工程を進めたり
    優先順位を変更したりしない
```

## 9. 工程確認・KY活動との関係

```
・工程確認時：本チャットの最新ロードマップを参照し、
  自分が把握している工程と相違が無いか確認する（PDCAのP）。
  相違が無ければ「工程ヨシ!」と回答し指示を待つ。

・次工程へ進む前：本チャットにある最新のロードマップを参照し、
  確認できたら「次工程の確認ヨシ!」と回答する。

・KY活動：本チャットでの工程確認・作業開始と同じ段階で実施する
  （1日1回。危険予知した事項はその日1日は忘れない）。

・相談事チャット：工程確認・KY活動は免除される
  （かやぬま氏方針）。本チャット自体が相談事チャットとして
  使われる場合はこの限りではない。
```

## 10. マスター工程表との関係

```
・ysd8810_master_schedule（マスター工程表）＝工程の骨格・完了条件を
  定義する文書。変更が発生したら随時更新する。

・本チャットのロードマップ更新報告＝マスター工程表の「現在地」を
  日々記録する運用ログ。

・両者の役割分担：
  マスター工程表 → 何を・どの順序で・何をもって完了とするか
  本チャット報告  → 今どこまで進んだか・何が止まっているか

・マスター工程表の内容そのもの（フェーズの追加・削除・順序変更）が
  変わった場合は、マスター工程表側を改版する。
  本チャットのログはその改版履歴とは別に、日々の進捗記録として残る。
```
