### 12.6 ★S5(c)-ISSUE-1: IE 非依存ラッチとハンドラ冪等性要件★

**c6 の検証過程で判明した重要事実**（kaizen 原則69 として登録）:

`irq_pending` の**ラッチ**は `IE` を見ない。`IE` を見るのは**受理**のみである。

| 段階 | emu23 | FPGA RTL | IE参照 |
| --- | --- | --- | --- |
| ラッチ | `ysd8004_raise()` L314-329 | L1223-1225 `if (state == S_IRQCHK && irq_in != 3'd0) irq_pending <= irq_in;` | ★**しない**★ |
| 受理 | L1176 `if (cpu.irq_pending >= 0 && (cpu.flags & FL_IE))` | L590 `if (irq_pending != 3'd0 && flags_ie)` | する |

**帰結**: 「ネスト禁止（受理時 IE=0）」は**受理の抑止**であって**ラッチの抑止ではない**。ハンドラが割込源を沈黙させても、沈黙させる**前**にラッチ済みの pending が `IRET` 後に受理され、ハンドラが**もう1回だけ**起動する。

**これはバグではなく、emu23 と RTL が一致した正しい挙動である。** MC6809 の IRQ でも同じことが起きる（OS-9 の IRQ ポーリングルーチンが「仕事が無ければ即 RTI」と冪等に書かれている理由）。

> ★**YSD8800 上の全ての割込ハンドラは冪等（idempotent）に書かねばならない。**★
> 「ハンドラが必ず1回だけ呼ばれる」前提のコードを書いてはならない。
> → **YUI OS Ph.8（MMU連携・Level 2）のカーネル設計に直結する制約。**
> 文書化: `emu23_device_design_v1_5.docx` §3.2.2

### 18.1 事象

emu23 側の改良2（バス・プルアップ／Phase B' B-C・2026-08-11 完了）にあたり実機想定・RTL・emu23 の三者を照合した結果、**未接続 MMIO 空間の応答値が三者で食い違っていること**が判明した。

| | 未接続 MMIO 読出値 | `$FF00`-`$FF10`（MMU 無効時） |
| --- | --- | --- |
| 実機（想定・データバスはプルアップ） | `$FF` / `$FFFF` | レジスタ応答 |
| **現行 RTL（`ysd8800_mmio_stub_v0_7.sv` L458）** | **`8'h00`** ← ★誤り★ | レジスタ応答（常時） |
| emu23 v1.11（改修前） | `mem[]` フォールスルー（不定） | `--mmu` 無しなら `mem[]` |
| **emu23 v1.12（改修後）** | **`$FF` / `$FFFF`** | **レジスタ応答（`--mmu` 非依存）** |

### 18.2 なぜ `8'h00` が誤りか

**GND に落ちている回路が存在しないにもかかわらず 0 を返すのは、デコーダが値を捏造していることに等しい。** V3 スタブ時代（`mmio_stub_v0_1`「即時ready・固定0x00」）の暫定実装が、以後の改版で見直されないまま残置されたものと判断する。

一方 **`8'hFF` は「プルアップ抵抗という実在の回路をモデル化した値」**であり性格が異なる。`emu23_kairyo.txt` 項番2「実機のバス（データおよびアドレス）はプルアップするのでハイインピーダンス時は 1 としたい」に合致する。

なお **FPGA の内部配線では「誰も駆動しない状態」を作れない**（内部三態バッファは存在せず `z` 記述は合成時にマルチプレクサへ変換される）。したがって RTL における選択肢は実質「`8'h00`（誤）」か「`8'hFF`（プルアップ模倣）」の二択である。※これは内部 MMIO バスに限った話であり、外部バス（PSRAM／SD の物理ピン）には三態バッファが実在する。

### 26.3 ★取得手段の是正 — `--cache-stats` では測れない★

当初計画（`v15` v0.1）は `--cache-stats` を用いる予定であったが、
★実源確認により *h* も *f* も取得できないことが判明した。★

| 実源（`emu23_v2_15.c`） | 内容 |
|---|---|
| L595 | `stat_hit` / `stat_miss` / `stat_charged` の3変数のみ |
| L808 | ★`is_write` を見ずに一括計上★ |
| L645-659 | 出力は `hit`/`miss`/`rate`/`charged` の4値のみ |

→ ★アクセス種別の内訳が出力に残らない。★
→ ★正しい手段は `--trace-addr`（L810-816）★。`cycle, 物理アドレス, 種別(F/W/R), hit` を CSV 出力する。

> ★v0.1 は「`[CACHE]` の hit/miss は書きを含む」という落とし穴を自力で発見していたが、
> 「分離が必要だ」と気づいた次に ★「分離できるのか」を確かめる一歩★ が抜けていた。★
> ★対策が「実施時に確認する」と**実施時送り**になっていたのが原因。★
> ★前提の成否を実施時送りにすると、着手してから止まる。★

### 26.4 ★モデル間の構造差は「どの量をどちらから取るか」で無害化した★

| | 充填コスト |
|---|---|
| emu23（L801） | `line × FILL` = 32 × FILL（クリティカルワードファースト無し） |
| RTL（②-A バースト） | `LAT + 31` |

★構造が異なるため、単純に emu23 のサイクル数を比較しても意味がない。★
しかし ★*h* と *f* はヒット/ミス判定のみで決まりレイテンシに依存しない★ ため、

- ★独立変数（*h*・*f*）は emu23 から取る★
- ★コストモデル（*P* = 10）は設計書 §6.4 の RTL 由来値から取る★

と分離することで ★構造差は予測に混入しない★。

> ★モデル間の差異は「どの量をどちらから取るか」を分離すれば無害化できる。★
> ★差異があるからといって突合を諦める必要はない。★
