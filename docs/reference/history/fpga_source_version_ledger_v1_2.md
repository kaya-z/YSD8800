## 1. 目的・背景

ツールチェーン（Force/scc23/hasm23/lnk23/emu23等）は `tool_version_ledger` で版数を一元管理してきたが、FPGA実装のRTL・TB・V2検証生成器（Python）・黄金値ファイル側には同種の台帳が存在しておらず、版数管理が手薄になっていた（かやぬまさんご指摘、2026-07-11）。本台帳はその是正として新規に独立させたものである。

## 2. 対象範囲

1. V1 CPUコアRTL本体（decoder / regfile / alu / cpu 各1本）
2. V1 CPUコア検証TB群（Stage1「フェッチ」〜Stage5「スタック/制御/割込」）
3. V2 CPUコア単体検証 一式（生成器Python・TB SystemVerilog・黄金値ファイル、V2-a〜V2-e）
4. 上記に対応する設計メモ・レビュー文書
5. **【v1.1追加】V3 メモリ・バス・MMIOデコード（PSRAM統合）関連の全RTL・検証TB・ベクタ生成器・黄金値・設計メモ**

## 7. 所見・課題（今回の実査で判明した事項）

1. **V2-b/c/dの生成器・TB・黄金値ソース一式がプロジェクトナレッジに未登録。** HANDOVER_CHAT78.mdにも「★V2-d/c/bの成果物はプロジェクト未登録の可能性大」と記載されており、今回`ls`/`grep`による実ファイル確認でこれを裏付けた。41/64/75ベクタのALL PASS実績は過去チャットの記録上は存在するが、KY34（実ファイルが真実）に照らすと、これらの検証を将来再現・監査する手段が現状存在しない。
2. **V1 Stage5-1（スタック）・5-2（JSR/RET）のTBソースも同様に未登録。** cpu RTL側の変更履歴には検証ALL PASSの記載があるが、対応するTBファイル実体が見つからない。
3. **V2親設計メモ（v0.1）の実体不明。** v2d設計メモから参照されているが、ファイルとして存在するか確認できなかった。
4. **ysd8800_cpu_v0_1.sv はファイル名(_v0_1)と実版数(v0.5.7)が意図的に乖離**（ヘッダに明記済の運用方針）。V1完成（V2完了後の一括リネーム）までは現状維持で問題ないが、リネーム忘れ防止のため本台帳の追跡対象とする。
5. decoder/regfile/aluの3ファイルはv0.1（2026-06-30作成）から一度も改版されていないことを実ファイルで確認した（第2〜5段の大幅なFSM拡張の間、これら3本には手を入れずに済んでいる＝良好な安定性）。
6. **【v1.1追加】V3実装一式（RTL5本・TB7本・生成器2本・golden一式）が本セッション終了時点でプロジェクトナレッジ未登録。** §1〜2の教訓（V2-b/c/dの二の舞）を踏まえ、本台帳§9に一覧化した上でユーザーへ登録を依頼する。
7. **【v1.1追加】理想メモリTBの限界が実例として顕在化。** V1/V2の理想メモリTB（`mem_ready`固定1）は、ysd8800_cpu_v0_1.svのS_SUBOP mem_rdアサート漏れという実バグを「82ベクタALL PASS」の裏で見過ごしていた。V3の実req/ack型メモリ統合で初めて発覚。kaizen.txt原則63として一般原則化済み（詳細§9・v3_design_memo_v0_3.md §9）。

## 8. 運用ルール（tool_version_ledgerに準拠）

- FPGA関連ファイル（RTL/TB/生成器/黄金値/設計メモ）を新規作成・改修したら、本台帳の該当表を都度更新する。
- 「ALL PASS」等の検証結果をチャット上で報告・記録する際は、対応するソースファイル本体もプロジェクトナレッジへの登録（またはユーザーへの登録依頼）を都度セットで実施する（§7-1/2の再発防止）。
- 現行版更新時も、過去版の系譜（v0.1→v0.5.x等の変更履歴）は欠落させない。
- 本台帳はツールバージョン台帳（tool_version_ledger）とは対象を分離した独立文書として維持する（ツールチェーン側 vs FPGAソース側）。
- ファイル名と内容実版数が乖離する運用（§3のcpuファイル等）を行う場合は、ヘッダにその旨を明記し、本台帳にも追跡事項として記載する。

2. **MMIOスタブ unpacked array port の X固着**

   - → **kaizen 原則65**
3. **MMUベクタ生成器のAレジスタ破壊**
   - 検出: emu23黄金値がベクタ#5/#6で期待と不一致
   - 内容: MMU操作ヘルパ `set_ptr()` / `mmu_on()` / `mmu_off()` はいずれも `LDW A,#imm16` → `STB A,[MMIO]` の2命令列であり、**内部でAレジスタを破壊する**。`get_ptr(A,7)` の直後に呼ぶと読み値が上書きされる
   - 修正: `mov(X, A)` でXへ退避（XはMMU操作ヘルパで未使用）。生成器v0.2
4. **TB側MMIOカウンタ判定の偽FAIL**

### 10.6 V3.5の確定設計（レビュー承認済）

- **MMU挿入位置**: アドレスデコーダ（論理 `$FC80` 判定）が前段。**MMUはその後段・RAM側パスにのみ挿入**する。**MMIO（MMUレジスタ自身を含む）はアドレス変換を受けない**
- **MMUレジスタは常時アクセス可**（MCR.EN=0でも読み書き可）。でなければMCRに書けず有効化できない（鶏と卵）
- **リセット値 PTR[n]=n（恒等写像）/ MCR=`$00`** … MCRが誤って1でもベクタフェッチが破綻しない＝安全側。V7/V8のreset vector問題への布石
- **MMU無効時は V3 と bit-exact 等価**（S5で26/26 PASS実証）
- **ページ境界跨ぎ16bitアクセスは原理上発生しない**（4KB境界は偶数アドレス→跨ぎは奇数開始＝align例外）
- **自己ロックアウト回避（自己救済性）が実証済**（S7ベクタ#6）… PTR[15]=`$1F` で `$F000` 台をリマップした状態でも `$FF07` に到達でき、MCR（`$FF10`）でMMUを切り戻せた
