## 1. 目的・背景

ツールチェーン（Force/scc23/hasm23/lnk23/emu23等）は `tool_version_ledger` で版数を一元管理してきたが、FPGA実装のRTL・TB・V2検証生成器（Python）・黄金値ファイル側には同種の台帳が存在しておらず、版数管理が手薄になっていた（かやぬまさんご指摘、2026-07-11）。本台帳はその是正として新規に独立させたものである。

1. **V2-b/c/dの生成器・TB・黄金値ソース一式がプロジェクトナレッジに未登録。** HANDOVER_CHAT78.mdにも「★V2-d/c/bの成果物はプロジェクト未登録の可能性大」と記載されており、今回`ls`/`grep`による実ファイル確認でこれを裏付けた。41/64/75ベクタのALL PASS実績は過去チャットの記録上は存在するが、KY34（実ファイルが真実）に照らすと、これらの検証を将来再現・監査する手段が現状存在しない。
2. **V1 Stage5-1（スタック）・5-2（JSR/RET）のTBソースも同様に未登録。** cpu RTL側の変更履歴には検証ALL PASSの記載があるが、対応するTBファイル実体が見つからない。
3. **V2親設計メモ（v0.1）の実体不明。** v2d設計メモから参照されているが、ファイルとして存在するか確認できなかった。
4. **ysd8800_cpu_v0_1.sv はファイル名(_v0_1)と実版数(v0.5.7)が意図的に乖離**（ヘッダに明記済の運用方針）。V1完成（V2完了後の一括リネーム）までは現状維持で問題ないが、リネーム忘れ防止のため本台帳の追跡対象とする。
5. decoder/regfile/aluの3ファイルはv0.1（2026-06-30作成）から一度も改版されていないことを実ファイルで確認した（第2〜5段の大幅なFSM拡張の間、これら3本には手を入れずに済んでいる＝良好な安定性）。
6. **【v1.1追加】V3実装一式（RTL5本・TB7本・生成器2本・golden一式）が本セッション終了時点でプロジェクトナレッジ未登録。** §1〜2の教訓（V2-b/c/dの二の舞）を踏まえ、本台帳§9に一覧化した上でユーザーへ登録を依頼する。
7. **【v1.1追加】理想メモリTBの限界が実例として顕在化。** V1/V2の理想メモリTB（`mem_ready`固定1）は、ysd8800_cpu_v0_1.svのS_SUBOP mem_rdアサート漏れという実バグを「82ベクタALL PASS」の裏で見過ごしていた。V3の実req/ack型メモリ統合で初めて発覚。kaizen.txt原則63として一般原則化済み（詳細§9・v3_design_memo_v0_3.md §9）。
8. **【v1.8追加】§3のCPUコア版数記述と実源の乖離（本v1.8で解消したい構造課題の実例）。** 既存§3ではCPUコアを**v0.5.7**（2026-07-11時点）と記述しているが、v1.5の§13.2で「V5でv0.5.8へ昇格」が後段追記されており、実源`ysd8800_cpu_v0_1_FIXED.sv`のヘッダは**v0.5.8**である。§3自体は当時の記録として温存し、**v1.8で新設した冒頭「最新版クイックリファレンス表」で現行版（v0.5.8）を明示**することで一次ソースを本表に一本化した。§3〜§16の縦割り記述に横串を通すことの必要性が、まさにCPUコア版数の現在値把握という基本情報で立証された形。**運用ルール確定**：今後、RTL改修時は本表と該当フェーズ別詳細セクションの両方を必ず更新する（v1.8サマリ表末尾「更新運用ルール」参照）。
9. **【v1.9追加】v1.8「現行版総括」の内訳数値誤記の自己発見・是正（v1.8 レビュー指摘1 反映）。** v1.8 で「RTLファイル総数：18本」と記述していたが、内訳検算すると 4+4+1+4+5+1=19本 + SDモデル1本 = 計20本が正しい。これは**v1.8 で新設した「KY41 5点セルフチェック」運用ルールを本表自身に自己適用したときに初めて検出された**もの。v1.8 レビュー §9 教訓「新設ルールは提起した本表自身にも適用されることを意識すべき」の実例。v1.9 では検算結果を明記した形に是正し、KY41 セルフチェックを 5点→7点に拡張（内訳数値の再検算・照合日更新確認を新設）。**教訓**：新設運用ルールは、そのルール自身にも適用してみることで初めて実効性が確認できる。**「他者へのルール」ではなく「本表自身にも適用されるルール」**という位置付けの明確化が v1.9 の主要成果。
10. **【v1.9追加】齟齬発見時の優先順位明文化（v1.8 レビュー指摘2 反映）。** v1.8「本表を正」ルールは §3〜§16 の変遷記録との齟齬を想定していたが、本表側にタイポが入った場合に実源側を誤修正するリスクがあった。v1.9 では**優先順位「実源ヘッダ > 本表 > §3〜§16 変遷記録」**を明文化し、齟齬発見時の対処を「本表と実源」「本表と変遷記録」の2ケースに分離。実源ヘッダを最上位の一次ソースとする運用の確立。
11. **【v1.9追加】照合日更新運用の明記（v1.8 レビュー指摘3 反映）。** v1.8 は「照合日」の重要性を明示したが、更新運用ルールに「本表更新時は照合日も同時更新」の記載がなかった。v1.9 では**「更新日 ≠ 照合日」**の意味付けとともに、照合日の同時更新を必須ルール化。v1.9 起票時の実源再照合（15/15 完全一致）を実施した上で照合日を 2026-07-30 → 2026-07-31 に更新することで、**運用ルールの自己適用**を実施。過去の照合日を機械コピペする運用の禁止を明文化。

## 8. 運用ルール（tool_version_ledgerに準拠）

- FPGA関連ファイル（RTL/TB/生成器/黄金値/設計メモ）を新規作成・改修したら、本台帳の該当表を都度更新する。
- 「ALL PASS」等の検証結果をチャット上で報告・記録する際は、対応するソースファイル本体もプロジェクトナレッジへの登録（またはユーザーへの登録依頼）を都度セットで実施する（§7-1/2の再発防止）。
- 現行版更新時も、過去版の系譜（v0.1→v0.5.x等の変更履歴）は欠落させない。
- 本台帳はツールバージョン台帳（tool_version_ledger）とは対象を分離した独立文書として維持する（ツールチェーン側 vs FPGAソース側）。
- ファイル名と内容実版数が乖離する運用（§3のcpuファイル等）を行う場合は、ヘッダにその旨を明記し、本台帳にも追跡事項として記載する。

### 10.6 V3.5の確定設計（レビュー承認済）

- **MMU挿入位置**: アドレスデコーダ（論理 `$FC80` 判定）が前段。**MMUはその後段・RAM側パスにのみ挿入**する。**MMIO（MMUレジスタ自身を含む）はアドレス変換を受けない**
- **MMUレジスタは常時アクセス可**（MCR.EN=0でも読み書き可）。でなければMCRに書けず有効化できない（鶏と卵）
- **リセット値 PTR[n]=n（恒等写像）/ MCR=`$00`** … MCRが誤って1でもベクタフェッチが破綻しない＝安全側。V7/V8のreset vector問題への布石
- **MMU無効時は V3 と bit-exact 等価**（S5で26/26 PASS実証）
- **ページ境界跨ぎ16bitアクセスは原理上発生しない**（4KB境界は偶数アドレス→跨ぎは奇数開始＝align例外）
- **自己ロックアウト回避（自己救済性）が実証済**（S7ベクタ#6）… PTR[15]=`$1F` で `$F000` 台をリマップした状態でも `$FF07` に到達でき、MCR（`$FF10`）でMMUを切り戻せた

### 12.6 ★S5(c)-ISSUE-1: IE 非依存ラッチとハンドラ冪等性要件★

**c6 の検証過程で判明した重要事実**（kaizen 原則69 として登録）:

`irq_pending` の**ラッチ**は `IE` を見ない。`IE` を見るのは**受理**のみである。

| 段階 | emu23 | FPGA RTL | IE参照 |
| --- | --- | --- | --- |
| ラッチ | `ysd8004_raise()` L314-329 | L1223-1225 `if (state == S_IRQCHK && irq_in != 3'd0) irq_pending <= irq_in;` | ★**しない**★ |
| 受理 | L1176 `if (cpu.irq_pending >= 0 && (cpu.flags & FL_IE))` | L590 `if (irq_pending != 3'd0 && flags_ie)` | する |

**帰結**: 「ネスト禁止（受理時 IE=0）」は**受理の抑止**であって**ラッチの抑止ではない**。ハンドラが割込源を沈黙させても、沈黙させる**前**にラッチ済みの pending が `IRET` 後に受理され、ハンドラが**もう1回だけ**起動する。

**これはバグではなく、emu23 と RTL が一致した正しい挙動である。** MC6809 の IRQ でも同じことが起きる（OS-9 の IRQ ポーリングルーチンが「仕事が無ければ即 RTI」と冪等に書かれている理由）。

> ★**YSD8800 上の全ての割込ハンドラは冪等（idempotent）に書かねばならない。**★
> 「ハンドラが必ず1回だけ呼ばれる」前提のコードを書いてはならない。
> → **YUI OS Ph.8（MMU連携・Level 2）のカーネル設計に直結する制約。**
> 文書化: `emu23_device_design_v1_5.docx` §3.2.2

### 17.8 V8-b で確認した運用上の要点（手順書§7・§10 に反映済）

1. **iverilog のファイル順序**：`ysd8800_decoder_v0_1.sv` を**必ず先頭**に置く（`package ysd8800_idec_pkg` 前方参照）。さもないと `ysd8800_cpu_v0_1_FIXED.sv:233: syntax error` という**紛らわしいエラー**になる（「package が無い」ではなく import 行の syntax error として出る）。
2. **`MAX_CYCLES` は 10,000,000 が必要**（TB 既定 1,000,000 では M-5 に届かない）。
3. **`UART_STALL_LIMIT` は 5,000,000 が必要**（M-4→M-5 間隔は約 426 万 cycle）。旧値 500,000 では実SPI転送中に誤って stall 判定が発火する。**kaizen 原則83「実SPI転送は fread 前提のOSドライバと約1000倍の乖離」の実証**。
4. **`vvp` の rc=124（timeout）は本工程では正常な時間切れ**の可能性が高い。kaizen 原則61「rc=124 は組み合わせループを第一に疑う」は**短時間で終わるはずのTB**の話であり、5〜15分かかる本工程には当てはまらない（原則72：適用範囲を定義せよ）。
5. **警告2種は無害**：`Port 3 (mem_addr) expects 16 bits, got 20`（TB側20bit宣言・上位4bitは常に0）／ `vvp.tgt sorry: Case unique/unique0 qualities are ignored`（iverilog 12.0 の既知制約・シミュレーション意味論に影響なし）。

## 18. ★未接続MMIO応答の乖離と RTL 追随要件（★v1.11新設・案Q）★

### 18.1 事象

emu23 側の改良2（バス・プルアップ／Phase B' B-C・2026-08-11 完了）にあたり実機想定・RTL・emu23 の三者を照合した結果、**未接続 MMIO 空間の応答値が三者で食い違っていること**が判明した。

| | 未接続 MMIO 読出値 | `$FF00`-`$FF10`（MMU 無効時） |
| --- | --- | --- |
| 実機（想定・データバスはプルアップ） | `$FF` / `$FFFF` | レジスタ応答 |
| **現行 RTL（`ysd8800_mmio_stub_v0_7.sv` L458）** | **`8'h00`** ← ★誤り★ | レジスタ応答（常時） |
| emu23 v1.11（改修前） | `mem[]` フォールスルー（不定） | `--mmu` 無しなら `mem[]` |
| **emu23 v1.12（改修後）** | **`$FF` / `$FFFF`** | **レジスタ応答（`--mmu` 非依存）** |

### 18.2 なぜ `8'h00` が誤りか

**GND に落ちている回路が存在しないにもかかわらず 0 を返すのは、デコーダが値を捏造していることに等しい。** V3 スタブ時代（`mmio_stub_v0_1`「即時ready・固定0x00」）の暫定実装が、以後の改版で見直されないまま残置されたものと判断する。

一方 **`8'hFF` は「プルアップ抵抗という実在の回路をモデル化した値」**であり性格が異なる。`emu23_kairyo.txt` 項番2「実機のバス（データおよびアドレス）はプルアップするのでハイインピーダンス時は 1 としたい」に合致する。

なお **FPGA の内部配線では「誰も駆動しない状態」を作れない**（内部三態バッファは存在せず `z` 記述は合成時にマルチプレクサへ変換される）。したがって RTL における選択肢は実質「`8'h00`（誤）」か「`8'hFF`（プルアップ模倣）」の二択である。※これは内部 MMIO バスに限った話であり、外部バス（PSRAM／SD の物理ピン）には三態バッファが実在する。

### 18.3 是正内容

| 対象 | 現行 | 是正後 |
| --- | --- | --- |
| `ysd8800_mmio_stub_v0_7.sv` **L458** | `else mmio_rdata = 8'h00;  // V3スタブ挙動` | `else mmio_rdata = 8'hFF;  // 未接続=プルアップ` |

**修正規模は 1 行。** ただし RTL 修正は RTL の検証工程（iverilog 回帰・V8-b 等）を要求する。
