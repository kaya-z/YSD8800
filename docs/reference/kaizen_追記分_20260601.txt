■ 原則31: プリエンプティブIRQハンドラには「完全レジスタ保護表」を設計書に必須記載する

  Forthワードの通常設計では「A/Bは揮発でよい」が成り立つ。
  しかしプリエンプティブIRQは任意の命令境界で発火するため、
  「ワード内の演算途中」でも中断される。
  この非対称性をIRQハンドラの設計書に明示すること。

  【IRQハンドラ 完全レジスタ保護チェックリスト】

    保存経路（IRQ受理時）:
      ISAハードウェア自動保存: PC / FLAGS のみ
      カーネル保存責任     : A / B / X （すべてTCBに退避すること）

    復元経路（_sched_found等）:
      復元必須: A(SAVED_A) / B(SAVED_B) / X(SAVED_X)
                SP(SAVED_SP) / PC(SAVED_PC) / FLAGS(SAVED_FLAGS)

    確認表（設計書に記載・レビュー時に全□を埋めること）:
      レジスタ │ 保存（IRQ受理時）  │ 復元（スケジューラ復元部）│ 確認
      ─────────┼────────────────────┼───────────────────────────┼──────
      A        │ IRQ_WK_A → TCB+8  │ TCB+8 → A                │ □
      B        │ IRQ_WK_B → TCB+10 │ TCB+10 → B               │ □
      X        │ IRQ_WK_X → TCB+6  │ TCB+6 → X                │ □
      SP       │ SP+4 → TCB+4      │ TCB+4 → SP               │ □
      PC       │ スタック → TCB+2  │ TCB+2 → スタック          │ □
      FLAGS    │ スタック → TCB+12 │ TCB+12 → スタック         │ □

  ※ 保存は正しく行われていても、復元が漏れていれば同じ結果になる。
    保存と復元を「対になっているか」を設計書の表で明示すること。
  ※ 今回の真因: 保存（TCB+8=SAVED_A）は正しく実装されていたが、
    復元部がSAVED_Aを戻さず、IRET直前にAはSAVED_Xの一時転用値
    ($FA76=負)になっていた。CMPI A,#0 → BLT成立 → ループ途中脱出。

■ 原則32: プリエンプティブ切替と協調切替でレジスタ保護方針を明確に分ける

  同じカーネル内でも切替方式によってA/Bの扱いが異なる。
  設計書にこの違いを必ず明記すること。

  【切替方式別レジスタ保護方針テンプレート】

    切替方式         │ 発火タイミング     │ A/B保護要否 │ 根拠
    ─────────────────┼────────────────────┼─────────────┼──────────────────
    プリエンプティブ  │ 任意の命令境界     │ 必須        │ 演算途中値を保持中
    (IRQ0_HANDLER)   │                    │             │ の可能性あり
    ─────────────────┼────────────────────┼─────────────┼──────────────────
    協調切替          │ ワード境界のみ     │ 不要        │ ワード抜け時点では
    (_sched_common)  │ （明示的yield）    │             │ A/Bは揮発でよい
    ─────────────────┼────────────────────┼─────────────┼──────────────────
    IRQ1_HANDLER     │ デバイス割込       │ 同タスク復帰│ IRQ1は切替を行わず
                     │                    │ →IRQ1_WK   │ 同タスクへIRET

  ※ 「以前から動いていた」協調切替の実績があっても、
    プリエンプティブ切替の新設時はA/B保護を別途確認すること。

■ 原則36: ストレージ系テストの合否判定は全バイト照合を基本とする

  UART出力マーカー（大文字/小文字）だけで合否判定してはならない。
  マーカーはサンプル点による判定であり、欠落が「穴」に入ると誤通過する。

  合否判定の標準手順:
    1. UART出力でマーカーを確認（速報値のみ）
    2. ディスク実体の全バイト照合で確定判定（最終判断・省略禁止）

  全バイト照合スニペット（Python）:
    python3 -c "
    d=open('disk.img','rb').read()
    for lba in (6,7):
        s=d[lba*512:(lba+1)*512]
        expect=[((lba-6)*512+i)&0xFF for i in range(512)]
        miss=[i for i in range(512) if s[i]!=expect[i]]
        print(f'LBA{lba} mismatch:',len(miss),'first:',miss[0] if miss else None)
    "

  ※ UART出力が成功（大文字）でも照合を省略しないこと。
    今回、大文字Xが出たにもかかわらず実体はbyte385-511が欠落していた。

■ 原則37: 「1つ直したら別のバグが出た」が2回続いたらタマネギ構造を疑う

  複数の独立したバグが積み重なって同一症状を出している場合、
  上位層を修正するまで下位層の症状が見えない「タマネギ構造」になる。

  【タマネギ構造バグへの対処ルール】

  「1つ直したら別のバグが出た」が2回続いたら:
    □ 「まだ何層あるか」を現時点の知識で見積もりリストに書く
    □ 全層を修正しなければ完成しないことを引き継ぎ文書に明記する
    □ 1層ずつ修正・確認のサイクルを維持し「次で終わる」と決め打ちしない

  引き継ぎ文書への記載例:
    「現時点で第○層まで確認済み。第△層以降に未知のバグが
     潜在する可能性あり。症状が変化したら別層のバグを疑うこと」

  ※ 今回の層構造:
    第1層: FM-WK-LEN グローバル変数競合（MEMCPY-Bのループ上限破壊）
    第2層: sd_buf_ptr 競合仮説（計測で否定→消去法で前進）
    第3層（真因）: IRQ0_HANDLERのAレジスタ復元漏れ

■ 原則38: タイミング依存バグが複数チャットを経ても解消しない場合はカーネルを疑う

  以下の条件が揃った場合は、アプリ層・ドライバ層だけでなく
  「カーネル・スケジューラ・エミュレータ」を疑いリストに追加する。

    □ 「IRQ・タスク切替のタイミングに依存する」バグが疑われる
    □ アプリ・ドライバ側の修正を複数試みても症状が変化するだけで解消しない
    □ 「以前から動いていた」実績があるコンポーネントが関与している
    □ Dスタック・Rスタックの破壊でないことが計測で確認された

  ※ 「以前から動いていた」はその時点の使われ方での実績にすぎない。
    新しいコンポーネントが追加されてIRQ頻度・タスク切替頻度が増した場合、
    既存コンポーネントの隠れたバグが初めて顕在化することがある。
    MC6809/OS-9でも「ドライバのバグと思っていたらスケジューラのバグだった」
    というパターンは珍しくない。

■ 原則39: Forthワードのアルゴリズムは「ツール制約を前提とした実装方針」を設計書で先決する

  ループ状態の保持方針をForce制約下で設計書に先決すること。
  実装フェーズで試行錯誤しない。

  【Force制約を前提とした実装方針テンプレート】

    ループ状態の保持（Force v1.5制約下での選択）:
      □ Dスタック方式（推奨）: 全状態をDスタックで回す
        → IRQ保護・Rスタック収支の両面で最も安全。Force制約に依存しない。
        → プリエンプション安全性が最も高い。
      □ >R方式: ループカウンタ等をRスタックに退避
        → Force v1.5では >R/R>/R@ の3種のみ（2>R/RPICKは使えない）。
          二段管理が必要な場合はDスタック方式に切り替えること。
      □ VARIABLE方式（禁止）: グローバル変数に保持
        → プリエンプティブ環境では競合リスクあり。使用禁止。

  机上トレース完了確認（実装前に必ず実施）:
    □ 最大Dスタック深さを計算して記録した
    □ Rスタック収支（>R数 = R>数）を全経路で確認した
    □ ループの全経路（正常終了/早期終了）でスタック収支が一致する
    □ プリエンプション安全性の判定を記載した（原則33）

■ 原則40: 引き継ぎ文書に「タマネギ層の見積もり」を記載する

  複数層のバグが疑われる場合、引き継ぎ文書の地雷マップ（原則29）に
  以下を追記すること。

    【地雷マップ タマネギ層見積もり テンプレート】

    ⚠️ タマネギ構造の可能性あり
       現在修正中の問題は複数層に分かれている可能性がある。
       第○層（修正済）: ○○バグ → ○○で解消
       第△層（修正中）: △△バグ → 修正方針○○
       第□層（未確認）: 不明。症状が変化した場合は新層を疑うこと。
       「次で終わる」と決め打ちせず、修正後に全バイト照合で確認すること。
