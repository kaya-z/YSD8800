## 総評

工程表として完成度は高い。Phase 0〜6 の粒度・依存関係・完了条件・本体改変有無の整理は的確で、口頭合意のみだった6フェーズ構成の正式文書化という目的（進捗チャット 2026-07-04 で警告されていた懸案の解消）を果たしている。回帰ゲート厳守・ISA厳守・_poc 必須（KY38）・原則43（詳細設計は着手時）を各Phaseに織り込んでいる点も規律に沿う。

一次情報（C-1/C-2/C-3 定義、T_UINT/T_BOOL 予約、call型伝播バグ、Q16.16 のワーク枯渇）は `scc23_v2_00_design_v2_10.docx` §9・§3 の実記述と一致を確認した（KY34クリア）。

要対応は **M-2（比較命令リネームの実体反映）** が主。これは工数見積りと着手判断に直結する。以下詳述。

## M-2【必須】Phase 2「比較命令リネーム」の実体（機能実装済・名称のみ・退行リスク）を正確に反映

**箇所**: §3 全体像 Phase 2、§4 Phase 2 表「比較命令リネーム」行

**現状記述**: 「比較命令リネーム（SIR_LT→SIR_CMP_LT_S 等）… bool/unsigned実装と同時実施」を Phase 2 の未実施タスクとして計上。

**実ソース照合結果（KY34）**:
- `scc23_v2_03.c` の `sir_op_t` enum は **`SIR_EQ, SIR_NE, SIR_LT, SIR_LE, SIR_GT, SIR_GE`（旧名のまま）**。`SIR_CMP_*_S` へのリネームは**未実施**。
- 一方、比較の emit は既に `Ltrue: LDW A,#1` / `LDW A,#0`（C規格どおり 0/1 を A へ返す）で**機能は完成済**。
- 設計書 `scc23_v2_00_design_v2_10.docx` の記述と整合:
  - §9.1:「比較命令リネーム … **見送り（動作実装済・名称のみ）**。bool実装時に同時実施」
  - §2.5.4:「SIR_CMP_*_S リネームは**見送り**（実体は**既にA=0/1返し済**・bool布石でfloat不要・**退行リスク**）」

**問題**: ロードマップの書き方だと「比較命令の機能実装が Phase 2 に丸ごと残っている」ように読め、工数を過大に見積もる。実体は「**名称変更のみ**（機能は済）」で、しかも設計書は**退行リスクを理由にリネーム自体に消極的**。この温度差が工程表に反映されていない。

**なぜ M か**: 工程の完了条件・工数・着手是非の判断を誤らせる。Phase 2 の「型システム統合」本体（T_BOOL/T_UINT 実装）は実タスクだが、「比較命令リネーム」は付随的な名称整理にすぎず、しかも必須ではない（退行リスク側が勝てば実施しない選択もあり得る）。

**対応案**:
1. §4 Phase 2 表の「比較命令リネーム」行を次趣旨に修正:
   > 比較命令の**リネームのみ**（A=0/1返しの機能は v2.03 で実装済・`scc23_v2_03.c` enum は旧名 SIR_LT 等のまま）。**退行リスクがあり必須ではない**。T_BOOL/T_UINT 実装で符号付き/符号なしの命名区別が実益を持つ場合に**限って**実施する条件付きタスクとする。
2. §3 全体像の Phase 2 見出しから「比較命令リネーム」を必須要素の並記から外す（もしくは「(条件付き)」を付す）。
3. 完了条件に「リネームを実施しない場合はその判断を記録して Phase 2 完了とできる」旨を明記。

> 補足: 設計書 §4.1/§4.2（v2.10）には SIR_CMP_*_S/_U を含む拡張オペコード表が"設計として"存在するが、これは**予約であり実装ではない**。ロードマップは設計書の"予約表"ではなく実ソース `scc23_v2_03.c` の実装状態（旧名）を一次情報とすべき（KY34）。

## N-1【推奨】Phase 3「プリプロセッサ移植」の移植元バージョンを明記

**箇所**: §4 Phase 3 表「プリプロセッサ移植」

**問題**: 「scc22資産（`handle_define` 等）の移植」とあるが、移植元の scc22 版数が未指定。プロジェクトには `scc22_v3_03.c` が実在する。scc22 は ISA2.2 系、scc23 は ISA2.3 系で ISA が異なる。

**対応案**: 「移植元 = `scc22_v3_03.c`（ISA2.2）。移植時に ISA2.3 差分を吸収」と一次情報を確定。プロジェクト規約「ツールを新規開発／更新する際は最新版ソースおよびISA仕様に対応」に沿う。これにより着手時の版探索の迷いを消せる。

---

## N-2【推奨】絶対ゲート値(48405)と Phase 0 実測(47795)のトラック区別を脚注化

**箇所**: §1.1・§2（絶対ゲート 826/48405/P:20/21846B）、§2 P1効果（cycles 47885→47795）

**問題**: 数字はすべて正だが、`48405`（-O0-strict 絶対ゲート）と `47795`（-O1 実測）が**別トラック**であることが明示されていない。後任が「ゲートは48405なのに Phase 0 で47795？」と混乱し得る。

**対応案**: §2 に脚注を1行追加:「絶対ゲート 48405 は **-O0-strict** トラック（peephole 非作動・byte-exact 維持）の値。cycles 47885→47795 は **-O1** トラック（peephole 作動）の値であり、両者は別トラックで別基準管理（P3レビュー時に確定した新旧トラック分離）」。§4 Phase 0 表にも同旨を付すと完全。

---

## N-3【推奨】Phase 6 に ABI仕様書の連動改版を明記

**箇所**: §4 Phase 6、§5 依存関係

**問題**: Phase 6（Q16.16）は「ABI変更を伴う大工事」と正しく認識されているが、**具体的に `YSD8800_ABI_spec.docx` の改版が必須連動する**旨が未記載。現行 ABI は int/pointer=16bit・戻り値=A レジスタ前提（`YSD8800_ABI_spec.docx` §2/§5.4）であり、32bit float は戻り値・引数渡し規約（A レジスタ単体で 32bit を返せない）に影響する。

**対応案**: Phase 6 の前提条件に「memmap 拡張に加え、`YSD8800_ABI_spec.docx` の 32bit 値の戻り値/引数渡し規約改版が必須連動」を追記。設計変更は完了後に文書改版（プロジェクト規約）に沿う。

---

## E-1【軽微】Q16.16 のワーク枯渇アドレス表記を現行 memmap で確定

**箇所**: §4 Phase 6「ワーク領域 $DBE8-$DBFF（24バイト）が完全枯渇」

**確認結果**: 現行 memmap は v2.4 案D-ε で **Cプロセス区画 $D400-$DBFF・ランタイムワーク $DBE8-$DBFF**（`scc23_v2_00_design_v2_10.docx` §1.3/§2.5）。ロードマップの **$DBE8-$DBFF は現行設計と一致・正しい**。旧 memmap（v1.x 系）の $FBxx 表記ではない点を確認した。**修正不要**。

> 注記: 当レビュー当初、レビュア側が旧 memmap（$FBxx 系）の記憶で「不一致か」と疑ったが、実ファイル照合の結果ロードマップ側（$DBxx）が正であった。プロジェクト規約「工程確認時は古い情報を参照しがちなので必ず最新状況か判断せよ」の実例として記録する。

## 論点1〜4 への回答（§6 未確定事項）

- **論点1（Phase 3 並行）**: **直列（Phase 1→2→3）を既定**とし、並行は「リソースに余裕がある場合の明示的オプション」と位置づけるのが安全。Phase 2（型システム）は本体広範を触るため、Phase 3 を並行させるとマージが複雑化しリスク増。→ 直列既定を推奨。
- **論点2（Phase 4 は Phase 2 後）**: **妥当**。関数ポインタは型システム（特に T_PTR 属性）安定後が安全。ISA2.3 に間接JSR が無い制約への「ディスパッチスタブ方式」（既存 `_syscall_disp_ptr` 流用）も現実的。
- **論点3（工程表と詳細設計の分離）**: **妥当**。原則43に沿う。
- **論点4（Phase 5/6 の優先度見直し余地）**: 末尾配置は妥当。**将来の優先度見直し余地を明記すべき**という提案に賛成。特に Phase 6 は ABI 大工事のため、着手是非を都度判断する旨を残すとよい。
