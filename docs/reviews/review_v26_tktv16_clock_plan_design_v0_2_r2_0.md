## 2. Major

### Q-1　§6.4 の決定根拠「シェル起動前なので UART RX の取りこぼしの実害は小さい」は、実測の順序と矛盾する

**事実**
- M-4 は、シェルのプロンプト **"YUI> "** を検出した時点で、cycle＝320,156 です（TB L404「SHELL-START プロンプト」、L441、手順書 L1369）。
- SD の初期化の開始（SD_CMD への書込み）は **cycle＝366,344** です（総括報告書 v0.5 §3.2 の `mmio_trace.log`）。つまり**プロンプトを表示した後**に始まっています。
- その後、M-5（自動事後診断列 "0123MD"、マウント完了）が cycle＝3,754,937 です。

**問題**
- 利用者から見ると、**プロンプトが出てから最悪約2.0秒、入力を受け付けない（割込も通らない）区間がある**ことになります。
- RX のバッファは1バイトなので、プロンプトを見て先行入力した2文字目以降は失われます。
- §6.4 の「起動時点で UART RX を待つ利用者操作は無い（シェル起動前）」という根拠は成り立ちません。

**是正**
1. §6.4 の根拠を事実に合わせて書き直す（「プロンプトの表示後に初期化を行う。最悪約2.0秒の間、先行入力は1文字を残して失われる」）。
2. そのうえで、**かやぬま氏に決定 C-2(i) を再確認していただく**。取りこぼしの実害が小さいという評価自体は、なお成り立つ可能性があります。
3. 選択肢として、**RTL を変更しない軽い対策**を併記する：YUI OS の起動順序を変え、SD の初期化とマウントを**プロンプト表示より前**に行う。これならストールが延びても利用者の入力とは重ならない。これはソフト側の変更なので (e) の範囲外になり、申し送り（U-12 など）とする。

## 3. Minor

| # | 箇所 | 指摘 | 是正案 |
|---|---|---|---|
| Q-2 | §5 K-2 と §4.4 | K-2 の `TICK_RST = CPU_HZ/100` に「割切れることを `$fatal` で検査」とある。しかし §4.4 の代替（4MHz ちょうどでない実周波数を `CPU_HZ` に入れる）では、`CPU_HZ` が100で割り切れない場合がある。そのときは**エラボレーションが止まり、§4.4 の経路が使えない**。§4.4 と §5 が矛盾する | K-2 を round(CPU_HZ/100) にし、検査を「tick 周期の誤差 ≦ 許容値（例：0.1%）」に変える。§4.4 の手順2 の検査項目にも Timer を加える。**(d) の実装前に是正すること** |
| q-3 | §4.3 第1候補 | 基準1〜3で並べると、#13（PFD 27MHz）と #15（PFD 9MHz）は同じ順位になる（VCO はどちらも 864MHz、CLKOUT はどちらも 216MHz）。#13 を採った決め手（PFD が高い方を採る、など）が書かれていない。また、基準1 の「9MHz」（下限の3倍）は経験則であり、一次資料の根拠は無い | 同順位のときの決め方を基準4 として明記する。基準1 は経験則であることを注記する |
| q-4 | §6.2 E-4／U-11 | カードがエラートークンを返したときに、`EXEC_TMO`（0.5秒）まで CPU がストールし続ける。定常運用中に起きるので、D-201（割込遮断）の一因にもなる | R-8 の回答（§4）のとおり、TKT-V14 の関連としてチケット化する |

## 4. 再レビュー論点への回答

| # | 論点 | 回答 |
|---|---|---|
| R-6 | PLL の選定基準の優先順位 | **妥当と判断する**。ジッタについて一次資料の根拠が無いなかで、動作範囲への余裕（PFD、VCO 中域）を優先するのは保守的で筋が通っている。q-3 の同順位の扱いを追記すること。最終選定は (c) の後とする（R-1 の合意どおり） |
| R-7 | INIT_TMO 2.0秒／EXEC_TMO 0.5秒 に分離する案 | **可とする**。EXEC 側のストールを延ばさずに、ACMD41 のタイムアウトが故障したときの保護も残す、よい落としどころ。ただし、初期化で延びるストールの扱いは Q-1 の再確認による |
