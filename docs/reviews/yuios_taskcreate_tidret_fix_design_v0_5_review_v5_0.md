## 2. 実源照合結果（v0.5 の新規主張の検証）

v0.5 で新たに提示された主張を実源で全数検証した。**すべて一致する。**

### 2.1 `TASK_DEAD = 0`（§2.4 訂正・§12.1）

```
229:TASK_DEAD           EQU 0
230:TASK_READY          EQU 1
231:TASK_RUNNING        EQU 2
232:TASK_SLEEPING       EQU 3
233:TASK_WAIT_MSG       EQU 4
234:TASK_WAIT_IPC       EQU 5
235:TASK_WAIT_REPLY     EQU 6
```

```
829:    LDW  A, #0
830:    STW  A, [X]                 ; DEAD
```

**✅ 訂正は正しい。** `TASK_EXIT` は `state=0` を書き、
`TASK_CREATE` の空きスロット探索条件（`state==0`）と一致するため、
**DEAD スロットは自動的に再利用される。枯渇しない。**

### 2.2 SYSCALL 入口に `A` の退避先が存在しない（§2.5(2)）

```
=== SLP_WK 全数 ===
302:SLP_WK_DSP          EQU $478C
303:SLP_WK_PC           EQU $478E
621:    STW  X, [SLP_WK_DSP]
625:    STW  A, [SLP_WK_PC]
644:    LDW  A, [SLP_WK_PC]
649:    LDW  A, [SLP_WK_DSP]
1701:   STW  X, [SLP_WK_DSP]
1705:   STW  A, [SLP_WK_PC]
1724:   LDW  A, [SLP_WK_PC]
1729:   LDW  A, [SLP_WK_DSP]
```

**✅ `SLP_WK` は `DSP` / `PC` の 2 個のみ。`A` の退避先は存在しない。**
§2.5(2) の「実値保存は現状の実装では不可能」は成立する。

### 2.3 コピペ伝播（§2.5(1)）

`TASK_SLEEP` L643-654 と `IPC4_RECV` L995-1008 が、
保存フィールド集合・順序・`$80`・`$477E`・`JMP _sched_common` まで一致することを確認。
**✅ 4/4 の一貫性はコピペ伝播であり、独立事象は 1 件。**

## 3. 特に評価する点

### 3.1 §2.5(2) の発見（v0.5 独自）

**本改版の最大の成果である。**

保存ブロックの `+8`/`+10` 欠落は「保存し忘れた」可能性を排除できない（不作為）。
しかし **SYSCALL 入口が `A` を即座にスクラッチとして潰しており、退避先すら用意していない**
のは「保存する意思が無い」ことの積極的な表明である（作為）。

| | 保存ブロックの欠落 | 入口での破壊 |
|---|---|---|
| 事実 | `+8`/`+10` に書かない | `A` を上書きし、退避先も持たない |
| 証拠の性質 | 不作為（見落としと区別不能） | **作為（意図の表明）** |
| 独立性 | コピペ伝播（証拠力 1 件） | **保存ブロックとは別系統の証拠** |

IRQ0 入口 L456 の `STW A,[IRQ_WK_A]` と対照させた点も効いている。
**同一プロジェクト内で割込とシステムコールが異なる扱いをしている**という比較は、
単独の観察より説得力が高い。

### 3.2 原則109 系4（不作為より作為を証拠として重く見る）

§3.1 を一般化した原則として妥当であり、本プロジェクトで繰り返し使える。
特に「実装の状態から設計意図を読む」場面で有効な判断基準である。

系3（コピペ伝播の判別）と系4（不作為 vs 作為）が組になったことで、
原則109 は「一貫性を証拠として扱う際の作法」として完結した。

### 3.3 §13.3 の A-1／A-2 分岐

「実値保存は現状不可能」という**制約を先に確定させてから**分岐を立てているため、
ABI 議論が空転しない構成になっている。
「ABI が決めるのは保存値であって保存の要否ではない」という切り分けも明快である。

### 3.4 §12.1 の誤記訂正

自らの誤記（v0.4 の「4 (DEAD)」）を特定し、それがレビュー指摘 I-21 の前提を
誤らせたことまで遡って記録している。KY41 準拠の改版として模範的である。

## 4. 軽微指摘

### 4.1 m-01: `TASK_WAIT_MSG` の行番号

**現状（§2.4 注記）**: 「（`4` は `TASK_WAIT_MSG`・**L232**）」

**実源**: `TASK_WAIT_MSG EQU 4` は **L233**。L232 は `TASK_SLEEPING EQU 3`。

**反映要求**: L232 → **L233** に訂正。

### 4.2 m-02: §10.1 の KY41 記述が v0.4 より後退している

**現状**:
> 本書が参照する行の範囲（L223〜L1741）と**重ならない部分が大半である**

**問題**: v0.12.10 の差分は L1750 以降、本書の参照範囲は L1741 まで。
**重なりは 0 である。**「大半」という表現は、読み手に「一部は重なるのか」という
疑問を残す。v0.4 の「**すべて差分より前**」という断定が正確であった。

**反映要求**: v0.4 の表現に戻す。KY41 の 4 点整合は「重ならない」を断定できて初めて意味を持つ。

### 4.3 m-03: TKT-04 実装時の注記（先回り・§9.1 への追加要求）

`_sc_found` に復元 6 行を追加する際、`_sched_found` と同様に
`IRQ_WK_A` / `IRQ_WK_B` を一時退避先に使うことになる。
**両者が同じワーク変数を共有する**ことになるため、以下を記録しておくことを推奨する。

| 項目 | 内容 |
|---|---|
| `_sc_found` の割込状態 | DI 区間内（`TASK_SLEEP` L618 の `DI` から `IRET` まで） |
| IRQ0 ハンドラの性質 | run-to-completion。`IRQ_WK_A/B` が跨いで生存することはない |
| `_sc_idle` の `EI` 窓 | IRQ0 が入っても handler 完了後に `IRET` するため、`_sc_found` 到達時に生存値なし |
| **結論** | **共有は安全** |

**反映要求**: 安全性の結論は変わらないが、
**§9.1「ワーク変数 × 書き手コンテキスト」対応表に `IRQ_WK_A` / `IRQ_WK_B` の行を追加**すること。
現在この表に載っていない。原則105 系2（書き手を書く）の対象が 1 組増える。

## 5. レビュー側の反省と原則提案

### 5.1 I-21 の取り下げ

`TASK_DEAD = 0` の訂正は正しく、**I-21（DEAD スロットの回収）は取り下げる。**

### 5.2 ★責任の所在について★

§12.1 は「私の誤記がレビューを誤らせた」と記しているが、**これは半分だけ正しい。**

レビュー側は I-21 を**設計書 §2.4 の表を根拠に立て、`TASK_DEAD` の定義を実源で確認しなかった。**
これは KY34（実ファイルが真実）と原則107（探索範囲の明示）を、
**レビュー側自身が守らなかった**ということである。

設計書の誤記は 1 件の入力ミスだが、それを検証せずに指摘へ昇格させたのはレビューの責任である。

### 5.3 ★原則110（新規提案）★

> **原則110: レビュー指摘も実源で裏取りする。
> 設計書の表・要約・前版の記述を根拠に指摘を立てない。**
>
> 本件ではレビュー側が設計書 §2.4 の `state` 欄（誤記「4 (DEAD)」）を前提に I-21 を立て、
> 誤った懸念を 1 ラウンド分往復させた。
>
> **レビューは「設計書の内部整合を見る作業」ではなく
> 「設計書と実源の一致を見る作業」である。**
> 設計書の記述を引用して指摘する場合も、引用元の事実を実源で確認する。
>
> **系1**: 指摘文中に設計書からの引用（表・行番号・定数値）が含まれる場合、
> その引用元を実源で確認してから指摘を確定する。
>
> **系2**: 「設計書にこう書いてある」は指摘の根拠にならない。
> 根拠になるのは「実源がこうなっている」だけである。
>
> ※ 原則109 系3 と同根。**一次情報でないものを根拠にすると証拠力が失われる。**
> 「n 箇所の一致（コピペ伝播）」も「設計書の表（伝聞）」も、同じ誤りの型である。

**反映要求**: 原則110 を §8 に追加し、§14 積み残し #10（kaizen 登録）の対象に含めること。

## 7. KY活動

### 7.1 予知

**レビューが「設計書内の整合チェック」に堕し、実源から離れるリスク。**

### 7.2 根拠

本レビューシリーズは v1.0 から v5.0 まで、設計書の版が上がるにつれて
**議論の対象が実源から設計書の記述そのものへ移りつつあった。**
I-21 はその典型で、実源を一度も見ずに設計書の表だけを根拠にした指摘であった。

設計書が精緻になるほど「設計書を読めば分かる」という感覚が生まれるが、
**設計書は実源の写像であり、写像には必ず誤差がある。**

### 7.3 防止策

1. **各レビューで最低 1 回は実源に当たる**。設計書が完成度を増しても省略しない
2. 指摘文に**実源の行番号または実際のコード片を含める**。含められない指摘は
   「設計書内の整合指摘」であることを明示する
3. 設計書の表・定数・行番号を引用する指摘は、**引用元を grep してから確定する**（原則110）
