## 3. 実装時の確認事項（ブロッカーではない・1点）

### 3.1 CONF-1【確認】案D の検出網羅性を設計に明記（実害上の穴はないが未記述）

**論点**: `is_undecl_call(n)` は `n->op == SIR_CALL` を直接判定する。未定義 call が**複合式に埋もれる**ケース（例 `(getval() + 0.0) * 2.0`）では、外側 `binop_promote(SIR_FMUL, l=加算結果, r=2.0)` の `l` は SIR_CALL でなく加算結果ノードのため `is_undecl_call(l)` は false になる。一見、取りこぼしに見える。

**検証結果（実ソース照合・実害なし）**: パーサはボトムアップ評価であり、内側の `getval() + 0.0` を処理する `binop_promote(SIR_ADD, getval(), 0.0)` の時点で（`0.0` が T_FLOAT ゆえ float 経路に入り）`is_undecl_call(getval())` が true となり**そこで error 停止する**。すなわち**未定義 call が float 演算に最初に触れる `binop_promote` 呼び出しで必ず捕捉**され、外側へ伝播する前に停止する。実害上の取りこぼしはない。

**確認事項**: この「ボトムアップ評価により、未定義 call が float 文脈に入る最初の地点で捕捉される（複合式でも漏れない）」という網羅性の論拠を **§3 か §2.4 に1〜2行明記**すること。現状 v0.2 は直接オペランドのケースのみ例示しており、複合式での網羅性が読者に示されていない。実装は現状のままで正しい（コード変更不要・記述追加のみ）。

> 補足: 逆に「未定義 call が **float 文脈に一切入らない**（純 int 演算のみで使われる）」場合は、案D は発火せず案C の警告のみとなる。これは正しい挙動（int 文脈では T_INT フォールバックで従来どおり動作）であり、過剰検出（false positive）もない。案D は「float 経路に入ったときだけ」error 化する設計であり、検出条件は必要十分。

## 4. 特記事項（評価点）

### 4.1 誤結論の撤回が誠実

§1.3 は v0.1 の「型伝播は既に正しい」を明示撤回し、「v0.1 は1段目のみ見て誤結論した」と経緯まで記録した（KY41）。PoC が示す値破壊と結論の矛盾を、実ソース `binop_promote` の2段機序として正しく再構成しており、kaizen（実測と結論の整合）を事後に履行している。

### 4.2 fail-safe 原則の適用が的確

§3.2 の「現行はサイレント破壊（壊れた asm を無警告出力しリンクも実行も通る）→ v2.05 で error 停止させ実機到達前に検出」という論証は、値破壊バグへの対処として正しい方向（fail-safe）。案D を `wrap_i2f` の**直前**に置くことで、値破壊の発生を確実に先回りして止めている。

### 4.3 絶対ゲート非影響の論証が正確

「Dhrystone は float 非使用 → float 経路に入らない → error 発生せず → v2.04 と byte-exact 一致」は実ソースの挙動と整合。案D が Dhrystone 絶対ゲート（826/48405/P:20/21846B）に影響しないことが論理的に示されている。
