## §0. 総評

★案B（ランタイムの共有化）を推奨する判断は正しい。★
§2 の「本質はプロセスごとに同一内容のランタイムを複製している構造」という問題把握が的確であり、
区画サイズの調整（案A/A'）では機能追加のたびに再逼迫するという見立ても支持する。
案C（MMU）と両立する設計にした点、§8 で Dhrystone ベアメタルとの分離を明示した点も良い。

§1 の実源引用はすべて実源と一致した（PROC-LOAD-ADDR L601／PROC-MAX-SIZE L602／
DATA-START tgt L58／scc23 既定値 L373-375／カーネル最終 .org L1984）。

一方、★実装に入ると即座に躓く箇所が 2 つある。★

| # | 要旨 |
|---|---|
| ★M-1★ | ★§8.2 の修正仕様「`check_memory()` を呼ぶ」は動作しない★。スクリプトモードは `lsecs` を経由しない |
| ★M-2★ | ★§4.2 のワーク領域移動（$DBE8→$DBC0）は Dhrystone のビット一致を壊す★。§8.1 と矛盾 |
| ★M-3★ | ★「カーネル変更 0 件」と「crt0 一切変更しない」のどちらかが版数照合で崩れる★ |

## §2. 必須修正の詳細

### 2.1 ★M-1：`check_memory()` はスクリプトモードで空振りする★

§8.2 は「スクリプトモードでも `write_binary()` 前に `check_memory()` を呼ぶ（L1192-1204 の早期
`return 0` を廃止）」と定める。★これは動作しない。★

`lnk23_v2_01.c` を追うと：

| 事実 | 実源 |
|---|---|
| `check_memory()` は ★`lsecs[]`（`nlsecs` 件）を走査★ して重なりを判定する | L577-630 |
| ★`run_script()` は `lsecs[]` を構築しない★。ファイル内容を ★`mem[a]` / `mem_used[a]` に直接書く★ | L885 以降（`mem[a] = c; mem_used[a] = 1;`） |
| L1198 のコメント自身が「★スクリプトモードは mem バッファ直接操作★」と明記 | L1198 |

★したがって早期 return を廃止して `check_memory()` を呼んでも、`nlsecs == 0` で何も検査されない。★
エラーも出ず、★「検出を有効化した」つもりで何も検出しない★ — 申し送り §5.2-1 の指摘が
そのまま残る、最悪の形の未修正である。

**修正要求**：★`mem_used[]` を使え。★ 既に存在する。

```
run_script() のバイト書込箇所（L56 相当）:
    if (mem_used[a]) { /* ★既に書かれている★ */ overlap_count++; ... }
    mem[a] = c; mem_used[a] = 1;
```

- ★バイト単位★の検出になる。§8.2 の「ゼロ詰めを空きとみなす例外は設けない」という
  方針と ★自然に整合する★（`mem_used` はゼロでも 1 になる）
- 重なりの範囲（先頭・末尾）を集計して 1 行で報告し、既定はエラー、
  `--allow-overlap` で警告に落とす（§8.2 後方互換の方針どおり）
- ★Dhrystone の現行 .bin 後勝ちは、この検出で確実に止まる★ → §8.2 の道2 移行が必要になる。
  ★この帰結は変わらない。修正手段だけが変わる。★

**補足（C-3）**：仮に `lsecs` を構築して `check_memory()` を通す設計にした場合、★別の罠がある。★

| 事実 | 実源 |
|---|---|
| `opt_machine` の既定は `MACH_BAREMETAL` | L214 |
| baremetal では ★`text_end > 0x3FFF` をエラー★とする | L640-643 |
| yuios.bin は forth.obj が $5100、Dhrystone は単一セクションが $0100〜$5xxx | §8.2 自身の記述 |

★どちらのビルドも `-m none` または `-m force` を指定しない限りエラーで止まる。★
`mem_used[]` 方式ならこの検査を経由しないため、★M-1 の修正案は C-3 も同時に回避する。★

### 2.2 ★M-2：ワーク領域の移動は Dhrystone のビット一致を壊す★

§4.2 は「ランタイムワーク $DBE8-$DBFF（24B）→ $DBC0-$DBFF（64B）」と定める。
§8.1 は「案B 実装後も Dhrystone ゲートは 819/48785/P:20/21846B に ★ビット一致★」と定める。
★両立しない。★

| 事実 | 実源 |
|---|---|
| ★ワーク番地は `#define C_XSAVE_ADDR 0xDBE8` の絶対値★ | `scc23_v2_07.c` L418 |
| `--data-org` / `--runtime-org` に ★連動しない★（v1.04 で $C7E8→$DBE8 へ手動移動した経緯） | 同 L269, L416 |
| `_C_MUL_A` 等は `EQU $%04X` で ★絶対番地として生成コードに埋め込まれる★ | 同 L3851-3858 |
| ★`C_XSAVE`（inc/dec 退避）はランタイムではなくユーザコード側で使われる★ | 同 L418 コメント |

★すなわち Dhrystone（ベアメタル・`--data-org 0x4000`）も $DBE8-$DBFF を使っている。★
★`#define` を $DBC0 に変えれば、Dhrystone の生成コードの番地が変わり、md5 が変わる。★
サイクル数は変わらないかもしれないが、★§8.1 の「ビット一致」は破れる。★

**修正要求**：

| # | 内容 |
|---|---|
| ★1★ | ★既存の 12 変数（$DBE8-$DBFF）は番地を一切動かさない★ |
| ★2★ | ★拡張分（float 専用の `_C_DIV_*` 等）は $DBC0-$DBE7 に新設する★。既存番地の下側に足す |
| 3 | 新設変数は ★`--rt-shared` 時のみ、または float 使用時のみ★ 参照されるようにし、Dhrystone の生成コードに現れないことを回帰で確認 |

★これで §4.2 の目的（float 共用の解消・64B 化）と §8.1（ビット一致）が両立する。★
★DATA 領域の上端は $DBBF のまま。§4.2 の表は「拡張分 $DBC0-$DBE7 ＋ 既存 $DBE8-$DBFF」と書き分けよ。★

### 2.3 ★M-3：版数照合の置き場所と「変更 0」の主張★

§0 は次の 2 つを掲げる。

- 「Cプロセス区画・辞書天井・PROC-LOAD-ADDR・★crt0 は一切変更しない★」
- 「★既存カーネル定数への変更は 0 件★。変更対象は scc23・lnk23・ビルド手順書・文書のみ」

§4.3-3 は「RT-JT 先頭のマジック/版数を ★crt0 が起動時に照合★ … 要レビュー：crt0 か ProcMgr か」とする。

| 置き場所 | 崩れる主張 |
|---|---|
| crt0 | ★「crt0 は一切変更しない」が崩れる★。64B の crt0 に照合コードを足す余地も要確認 |
| ProcMgr（kernel_forth） | ★「変更対象は scc23・lnk23・文書のみ」が崩れる★（★定数★は不変でも ★コード★は変わる） |

★どちらを選んでも §0 のどちらかが不正確になる。★

**修正要求**：★ProcMgr（kernel_forth の `PROC_EXEC` 系）に置くことを推奨★し、§0 を
「★カーネル定数の変更 0 件・crt0 不変。ProcMgr に版数照合ワードを 1 つ追加★」と正確に書け。

理由：

| # | 理由 |
|---|---|
| 1 | crt0 は 64B 固定で ★ProcMgr のロード手順・区画レイアウトに直結★する。触らない方が安全 |
| 2 | Forth 側なら ★`$2000 @ 期待値 = IF … ELSE エラー終了 THEN` 程度★ で済み、コストが最小 |
| 3 | ★エラー終了の経路（ProcMgr へ返す）は、ProcMgr 側に置く方が自然★。crt0 から ProcMgr へ「エラー」を返す規約が現状無いなら、それを新設する方が大きい変更になる |

★なお照合の対象は RT-JT のマジック/版数だけでよい。★
ユーザバイナリ側に「期待する RT 版数」を持たせるには crt0 かバイナリ形式の変更が要る。
★Level 1 では「ロード時点の RT 版数が、ビルド手順書で指定した版と一致するか」の検査で足りる★
（SD 上の古いバイナリ問題は C-4 参照）。

## §3. 確認事項

### 3.1 C-1：RT 領域は予約の上端に置く方が良い

§4.1 は RT を ★$2000-$2FFF★（予約の下半分）に置き、$3000-$3FFF を予約として残す。
すると次の配置になる。

```
$0010-$1FFF  カーネル本体（実終端 $13xx）
$2000-$2FFF  ★RT（コード・不変）★        ← ここで分断される
$3000-$3FFF  カーネル成長予約
```

★カーネルが $1FFF を超えて成長するとき、RT を飛び越えて $3000 に続けねばならない。★
連続領域を前提にした .org の並びや、将来のオーバーレイ配置で扱いにくい。

★RT を上端（$3000-$3FFF）に置けば、カーネルは $13xx から $2FFF まで 7KB 超を連続に使える。★

| 案 | RT-JT | RT-CODE | カーネル連続成長域 |
|---|---|---|---|
| §4.1 現案 | $2000-$20FF | $2100-$2FFF | $13xx-$1FFF（★約 3.3KB★） |
| ★推奨★ | ★$3F00-$3FFF★（または $3000-$30FF） | ★$3000-$3EFF★ | ★$13xx-$2FFF（約 7.3KB）★ |

★RT-JT を $3F00 に置けば「$3FFF 直下の固定テーブル」という分かりやすい規約になる。★
★§6-1（RT 領域の大きさ）と併せて、4KB 一括で足りる（N-1）。★
★lnk23 の R17（$0000-$3FFF は ROM 扱い・L613）とも整合する。★

### 3.2 C-2：Level 2（Ph.8）への制約を明記せよ

§4.1 と §5-5.1-4 は「案B は Level 2 と両立する」と述べる。★ワーク変数の扱いについては正しい。★
しかし ★もう 1 つ条件がある。★

★MMU 有効時、ユーザプロセスが `JSR $3Fxx`（RT-JT）を実行できるためには、
$2000/$3000 台のページが ★ユーザ空間から read/exec 可能にマップ★されていなければならない。★
カーネル領域を丸ごとユーザから隠す設計にすると RT が呼べなくなる。

**要求**：§4.1 に ★「Ph.8 の MMU 設計は RT ページをユーザ read/exec で共有マップすること」★ を
制約として 1 行残せ。Ph.8 側で「知らずに隠す」事故を防ぐ。

### 3.3 C-4：RT-JT の要否は「バイナリを保存するか」で決まる

§4.3-2 は RT-JT の利点を「ランタイム本体を改版してもユーザバイナリの再コンパイル不要」とする。
★正確には、.inc 方式（JT 無し・直接 JSR）でも「再アセンブル」で済み、再コンパイルは不要である★
（scc23 はシンボル参照を出し、番地は hasm23 時に .inc から解決される）。

★JT が真に効くのは、ユーザバイナリを SD（YUIFS）に保存し、RT 改版後も再ビルドせずに
ロードし続ける運用★ である。その運用があるなら JT は必須、無いなら
★JT は呼出ごとの JMP 1 命令と 256B のコストだけを払う★。

**要求**：§4.3 に ★「SD 上のバイナリを RT 改版後も再ビルドせず使う」運用の有無★ を
判断根拠として明記せよ。★ある★なら JT 採用は正しく、
その場合 ★M-3 の版数照合が「SD の古いバイナリを弾く」役割を持つ★ ことになり、
照合の意味づけが明確になる。

### 3.4 E-1：「実終端 $1300 台」

`kernel_v12_11.asm` L1984 の `.org $1300` は ★最後のセクション開始★ であって実終端ではない。
$1300 以降のコード長を足した値を記されたい（memmap 図の「$0010-$1FFF」の余裕を正確に見積もるため）。
★C-1 の判断（連続成長域の大きさ）にも効く。★
