## §2. M-1：§16.3 の因果が時系列で成立していない

### 2.1 実測値を同じ軸に揃える

§16.3 は次の 2 つを並べ、「同一 `$0f7xx` 帯にあり #4 と整合する」と結論している。

| 観測 | 記載値 |
|---|---|
| 初回 BWR | ★`t=16953000`★ addr=`$0f7fd` blen=32 fill_index_r=38 |
| 初回 MISMATCH | `pa=$0000f79f` cache=$53 expect=$f7 ★`@cycle=631`★ |

★一方は `$time`、もう一方は `cycle_count` であり、単位が違う。★ 揃える。

```
tb_cpu_v8e_dhry_v0_3.sv L122 : `timescale 1ns/1ps
                        L223 : always #125 cpu_clk = ~cpu_clk;   → 周期 250 ns（4 MHz）

t = 16,953,000 ns ÷ 250 ns = ★cycle 67,812★
```

| 事象 | サイクル |
|---|---|
| ★初回 MISMATCH★ | ★631★ |
| ★初回 BWR★ | ★67,812★ |

★MISMATCH が BWR より約 67,000 サイクル先行している。★
★初回 MISMATCH の原因は BWR ではありえない。★

### 2.2 では初回 MISMATCH は何か

★T-4' の構成は `psram_ctrl_v0_3`（★案D 無し★）である。★
したがって ★W-0（窓中の `blen_r=1` 書込が PS_BUSY で出す 1 本のビート）が生きている。★

```
ysd8800_psram_ctrl_v0_3.sv L169 : beat_valid <= 1'b1;   // ★we を問わず立つ★
```

★ドレイン書込が 1 バイトずつ（`blen=1`）発行された場合★ ——
`burst_len_o` が 32 になるのは `fill_sel=1` の期間だけであり、
★`rd_block` を伴わないドレイン（`hold_full`／`upstream_idle & idle_expired`／`flush_req_i`）は
`burst_len_o=1` のまま発行される★ ——
★このとき BWR には計上されないが、窓中であれば W-0 の被害は発生する。★

★すなわち cycle 631 の MISMATCH は W-0 由来である。★

### 2.3 アドレスの一致も根拠として弱い

★`$0f7fd` と `$0f79f` は同じ 256B ページ内にあるが、32B ラインは異なる。★

| アドレス | 所属ライン（32B 境界） |
|---|---|
| `$0f7fd` | ★`$0f7e0`〜`$0f7ff`★ |
| `$0f79f` | ★`$0f780`〜`$0f79f`★ |

★別ラインである。★ さらに BWR 時の `fill_index_r=38` が指すラインは
16KB / 32B ＝ 512 ライン構成では `addr[13:5]=38` の集合であり、
★`$0f79f`（index 444）とも一致しない。★

★「同一 `$0f7xx` 帯」は 256B 単位の粗い一致にすぎず、#4 の証拠にならない。★

### 2.4 修正要求

★真因（BWR）の結論自体は揺らがない。★ §16.4 の説明力の確認は依然として有効であり、
特に ★T-2（案D 適用済）で MISMATCH が 27 件残った★ という事実は、
★W-0 が止まってもなお被害が残る＝BWR の存在★ を示す強い証拠である。

修正すべきは ★§16.3 の「整合する」という 1 行の根拠づけ★ である。次のように改めよ。

| # | 修正内容 |
|---|---|
| ★1★ | ★`$time` を cycle に換算して併記する★（`t=16,953,000 ns ＝ cycle 67,812`） |
| ★2★ | ★初回 MISMATCH（cycle 631）は BWR（cycle 67,812）に先行するため、W-0 由来であると明記★ |
| ★3★ | ★アドレス帯の一致は 32B ライン単位では成立しないため、根拠から外す★ |
| ★4★ | ★BWR と誤充填の対応づけは、案D 適用後（W-0 が消えた状態）の再測定で行う★ ——
  T-2 の 27 件の MISMATCH アドレスと、BWR 時の `addr` / `fill_index_r` を突合する |

★修正4 は §19 V-3 の副産物として得られる。★
★V-3 で MISMATCH=0 になれば、そもそも突合すべき対象が消えるため、
「対策前に 1 回だけ」案D 単独構成（＝T-2 の構成）で BWR プローブを併走させれば取れる。★
★T-2 は既に実施済であるから、★★BWR プローブを付けて T-2 を 1 回だけ再実行する★★ のが最も安い。★

> ★本件は KY10（系をまたぐ値を渡すときは単位を宣言する）の再発である。★
> ★`$time` と `cycle_count` は別の軸であり、並べた瞬間に換算が要る。★
> ★§16.3 は「対策によって沈黙しない検査器」という点では模範だが、
> その出力の読み方で足をすくわれた。★

## §3. 確認事項

### 3.1 C-1：`48,875` は桁入れ替わりでないか

§19.1 の新基準は ★emu23 818 / 48,875★ である。旧基準は ★819 / 48,785★ であった。

★`48,785` → `48,875` は 7 と 8 の入れ替わりで得られる。★
★転記誤りの可能性が排除できない。★

- 命令数が +90 なら、Dhrystones/sec は `4e7 / C` の関係から ★819 → 818 へ 1 下がる★ のは整合的である
  （48,785 → 48,875 は +0.18%、819 × (1 − 0.0018) ≒ 817.5）
- ★すなわち数値としては辻褄が合っており、誤りだと断定はできない★
- しかし ★これは絶対ゲートの値である★。★実行ログから直接転記したことを確認されたい★

★もし正しいなら、それは「scc23 v2.08 / lnk23 v2.02 で Dhrystone の命令数が 90 増えた」という
独立した事実であり、★★ツール改版の副作用として記録に値する★★。★

### 3.2 C-2：`dn_wr_o` と `dn_rd_o` の重なり

案G は `dn_burst_len_o` を `drain_active` で切り替える。
★`drain_active` が落ちるサイクルで `dn_rd_o` が立つと、`burst_len` は 1→32 に変わる。★

このとき ★`dn_wr_o` と `dn_rd_o` が 1 サイクルでも同時に 1 になると、
`psram_ctrl` は `psram_we = cpu_mem_wr`（`cdc_bridge` L133）により
★★書込として受理しつつ `burst_len=32` を拾う★★ ——本件とまったく同じ事故になる。★

実源上は次で排他が取れている見込みである。

```
ysd8800_wbuf_v0_2.sv L192-194 : dn_wr_o = drain_active ? cur_be : 1'b0;
                     L196-197 : dn_rd_o = up_rd_i & ~wb_valid_r;
```

★`drain_active`（`st_r==S_DRAIN`）の間は `wb_valid_r=1` のはずであり、`dn_rd_o=0` になる。★
★ただし `wb_valid_r` が落ちるサイクルと `st_r` が S_DRAIN を出るサイクルの前後関係は、
状態遷移の実装に依存する。★

**要求**：★V-2 に 1 行のアサーションを足せ。★

```
assert (!(dn_wr_o && dn_rd_o)) else $error("[WBUF] wr/rd overlap");
```

★DUT 内に置けば合成対象外（`ifndef SYNTHESIS`）で済み、恒久的な保険になる。★
★案G は `burst_len` を要求経路に載せる改修であるから、
「要求の種別が一意である」ことがこれまで以上に重要になる。★

### 3.4 N-1：V-2 を 2 点で測る

★案G と案D は止めるものが違う（§17.2 の表）。★
