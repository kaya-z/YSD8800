## §0. 総評

★案δ（第5の状態を足す）の構造は妥当であり、支持する。★
「`mem_charge()` に分岐を 1 つ足すだけで関数を分割しない」「`cache_valid[]`/`cache_tag[]` を
一切触らない」「`--cache-size` との同時指定はエラーで停止する（黙って無視しない）」は
いずれも正しい判断である。§7 の K-1（数値が出たことで正しいと見なす危険）を
筆頭に置いた点、§4 で ★自分の提案値を「提案であり決定ではない」と明示した点★ も評価する。

問題は改修の中身ではなく ★判定量の置き方★ にある。

★段7-C は既に RTL 実測で 13.2% という値を得ている。これは「書込ストールを全部消したら
どれだけ減るか」＝ ★ライトバッファ効果の上限そのもの★ である。★
§4 の測定 C（emu23 で書込課金を 0 にする）は ★同じ量を、より粗いモデルで測り直す★ ことになる。
つまり D-1 の提案は、★保留を解消するための新しい情報を生まない。★（詳細 §3）

加えて、実装上の穴が 1 つある（M-1：`charge_enable` の扱い）。
これは ★数値は出るが課金されていない★ という無音の失敗を招く。

## §2. 実装に関する指摘

### 2.1 M-1：`charge_enable` の扱いが抜けている

`emu23_v2_15.c` は ★判定と課金を別変数で持つ★（L570-571・C-9）。
`mem_charge()` の末尾は次のとおりである。

```
if (!charge_enable) return 0;      /* L818付近 */
stat_charged += add;
```

§3.4 は「`--no-cache-model` は `cache_enable` も同時に立てる」と書くが、
★`charge_enable` に触れていない。★ ヘルプ（L3540）も
`--mem-latency ... (requires -mc)` としており、課金の有効化は別系統である。

★このまま実装すると、`--no-cache-model` 単独指定時に全アクセスが判定だけされて
課金 0 になり、測定 A が「理想メモリと同じ値」を返す。★
しかも ★エラーは出ない★ ——数値は出るのに中身が無い、K-1 と同型の無音失敗である。

**修正要求**：次のいずれかを §3.4 に明記せよ。

- (a) `--no-cache-model` は `cache_enable` と ★`charge_enable` の両方★ を立てる
- (b) `--no-cache-model` 単独指定は ★エラーで停止★ し、課金オプションとの併用を必須とする

★どちらでもよいが、「黙って課金 0 で走る」経路だけは残してはならない。★
`--cache-size` 併用をエラーにする §3.4 の判断と同じ規律である。

### 2.2 M-3：U-4 を閉形式の判定式にする

§7 K-1 は「モデルが RTL と一致していないのに数値が出たことで正しいと見なす」危険を挙げ、
U-4 の突合を ★ゲート★ と定めている。★ゲートである以上、合否条件が数値でなければならない。★
現状の「同オーダーか」では、K-1 が防ぎたいものを防げない。

emu23 の課金構造から、測定 A の総サイクルは ★閉形式で書ける★。

```
C_A = C_ideal + (lat_rd − 1)·N_rd + (lat_wr − 1)·N_wr
```

ここで `N_rd`／`N_wr` は `mem_charge()` の呼出回数（★バイト単位★・C-7）である。
したがって RTL 実測から ★実効レイテンシを逆算できる★。

```
lat_eff = 1 + (C_RTL − C_ideal) / (N_rd + N_wr)
```

Dhrystone -O0 の既知値を入れると `C_RTL = 1,070,369`、`C_ideal = 48,785` であるから、
★`lat_eff` が既定値 5 の近傍（例：4.0〜6.0）に収まるかどうかが、モデル妥当性の判定になる。★

**修正要求**：

1. `emu23_v2_16.c` に ★`mem_charge()` 呼出回数（kind 別）の出力★ を追加する
   （`stat_hit`/`stat_miss` は「全件 miss」になるため母数として使えない。★別カウンタが要る★）
2. U-4 の合格条件を「`lat_eff` が 4.0〜6.0 に入ること」等の ★数値★ で事前確定する
3. 外れた場合は ★判定に進まない★（現行の K-1 対策のとおり）

★これは §1.2 の二次目的「`P`=10 の精度（段6 の乖離 −8.4% の主因候補）」の切り分けにも
そのまま効く。★ `lat_eff` が 5 から系統的にずれるなら、`P` ではなく LAT 校正側が主因である
ことが分かる。★1 つの測定で 2 つの目的が片付く。★

### 2.3 C-1（U-2 への回答）：測定 C は改修不要

`--mem-latency` のファイル形式は ★キー名 ＋ 値★ であり、キーは
`FETCH/RD8/WR8/RD16/WR16/FILL` の 6 種、値域は ★1〜65535★ である（L692-712）。

★`WR8 1` / `WR16 1` を与えれば `lat[kind] − 1 = 0` となり、書込課金が 0 になる。★
すなわち ★測定 C に新規オプションは不要であり、コード改修も不要★ である。

これは単なる省力化ではない。★R1（既定経路の完全一致）を脅かす変更点が 1 つ減る★
という意味で、K-2 のリスクを下げる。§3・§8 の実装量を見直されたい。

（値域下限が 1 であるため「0 を指定して課金 0」はできないが、
課金式が `lat − 1` であるため ★1 が実質 0 課金★ になる。仕様と整合している。）

### 2.4 C-2：回帰の範囲

手順4 は ★既定経路（オプション無指定）★ の byte-exact 一致を求めている。これは必要だが十分ではない。

本改修は `mem_charge()` の内部に分岐を足す。★既存のキャッシュ有効経路（測定 B）も
同じ関数を通る。★ したがって次も確認すべきである。

★測定 B が、段6／段7-A で得た emu23 のキャッシュ有効時の数値を再現すること。★

これが崩れると、段7-A の突合（§1.2）の基準そのものが動いてしまう。
手順4 に 1 行加えるだけで済む。

## §3. D-1 への回答

### 3.1 結論：★提案（案γ）は採らないことを推奨する★

理由は 1 点である。★測定 C が与える量は、段7-C が既に RTL 実測で与えている量と同じだからである。★

| 出所 | 量 | 値 |
|---|---|---|
| 段7-C（RTL 実測） | 書込ストールが総サイクルに占める割合 ＝ ★書込待ちを全部消したときの削減量★ | ★13.2%★ |
| 段7-B 測定 C（emu23） | 書込課金を 0 にしたときの削減量 ＝ ★同じ量★ | 未測 |

★どちらも「理想ライトバッファ（無限深度・待ちゼロ）を仮定したときの上限」である。★
そして精度は ★RTL 実測の方が高い★（emu23 は CPI=1 固定・LAT 単一定数の近似モデルであり、
そのモデル自体を U-4 で検証しようとしている段階である）。

★検証対象のモデルを使って、既に高精度で得ている量を測り直しても、判断材料は増えない。★
仮に emu23 が 8% と出て RTL が 13.2% だったとき、★どちらを信じるかの基準が無い。★
これは判定を解消するどころか、争点を 1 つ増やす。

### 3.2 では何が足りないのか

★保留の本質は「上限が 13.2% と分かった。では実際に取れるのはいくらか」である。★

ライトバッファで実際に消える待ち時間は、★書込の到着間隔分布★ に依存する。

- 書込が ★孤立して来る★（前後に十分な間隔がある）なら、★深さ 1 のバッファでもほぼ全部吸収できる★
- 書込が ★連続して来る★（バースト）なら、2 発目以降はバッファが満杯で結局待つ。
  ★深さ 1 では 13.2% のうちごく一部しか取れない★

★13.2% という上限は、この区別を一切含んでいない。★
段7-C の測定は「何サイクル待ったか」であって「その待ちが吸収可能か」ではないからである。

### 3.3 推奨する代替案（案ε）

★emu23 のトレース出力を使って、書込の到着間隔分布を求める。★

トレースは既に ★`cycle, 物理アドレス, 種別, hit`★ の形式で出力される（L811-815）。
★種別 W の行だけを抜き、直前アクセスとのサイクル差を集計すれば分布が得られる。★
すなわち ★emu23 の改修なしに、既存の trace 機能だけで求まる。★

これを使って、深さ D のライトバッファで吸収できる書込の割合 `α(D)` を算出し、

```
実効削減率(D) ≒ 13.2% × α(D)
```

を D = 1, 2, 4 について出す。★判断すべきはこの値である。★

| 実効削減率(D=1) | 判断 |
|---|---|
| 一定値以上 | 工程②.5 へ前倒し（★深さ 1 で足りるなら実装コストは小さい★） |
| 深さを増やさないと届かない | ★工程④へ据え置き★（FPGA 資源と実装コストが跳ね上がるため） |

★閾値は測定前に確定させること（`v18` の運用・K-3 のとおり）。★

★この案の利点★

| # | 内容 |
|---|---|
| 1 | ★emu23 の改修が不要★。R1 を脅かさない |
| 2 | ★13.2% と競合しない★。RTL 実測を上限として使い、emu23 は「その内訳」を与える役割に徹する |
| 3 | ★深さという設計パラメータに直結する★。「前倒しするか」だけでなく「どう作るか」が同時に決まる |
| 4 | 段7-B 本来の目的（A/B の ON/OFF 比較・§1.2 の突合）は ★そのまま実施できる★。案ε は測定 C を置き換えるだけである |

### 3.4 §3・§5 の改修そのものは妥当

★`--no-cache-model`（測定 A）の新設は支持する。★
これは段7-A から持ち越された突合（§1.2）に必要であり、
★emu23 に「キャッシュ非搭載」の基準が無い★ という `v16` §1.3 の制約を解消する唯一の手段である。
課金式（§3.2）も RTL の CEN=0 挙動と対応が取れており、`−1` 規約を新設分だけ変えないという
判断も正しい。

★本回答が否定しているのは測定 C の位置づけだけであり、案δ そのものではない。★
