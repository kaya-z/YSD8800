## 0. 総評

### 0.1 指摘書 v6.0 の A級1件は解消され、成果の質は高い

§4.10 が新設され、**golden 更新が予告 → 受入基準 → 実施記録の順で文書化**された。
特に評価すべきは以下である。

**（1）受入基準 v1.1 の設計ミスを自ら発見し、2段階比較へ改めた（§4.10.2）**

v0.7 の基準「差分は削除のみ。追加が1行でもあれば NG」は、
**同一コンパイラに (A) 符号修正と (B) 細粒度化の2変更が同居している**ことを見落としていた。
これを「混ざった差分を分類する」のではなく「**混ざる前に分ける**」——
中間バイナリ `scc23n` を使った2段階比較——で解決した判断は正しい。
`v1.1 → v1.2（没）→ v1.3（採用）` の失敗記録まで残した点も含め、質が高い。

**（2）段階1の「削除 = 0」を要求条件に据えた設計が優れている**

(A) は既存コードを一切削らない純粋な追加である。したがって削除が1行でも出れば
`_cc_div`/`_cc_mod` 以外に影響が及んだことを意味する。
**これは「期待どおりの差分か」ではなく「期待しない変化が無いか」を直接検査する条件**であり、
golden 比較の本来の目的に合致している。

**（3）実施記録の数値を独立に検算したところ、一致した**

§4.10.5 の「段階1 追加 22行（`m1_i_div_*` 3件のみ）」について、当方で内訳を積算した。

| 内訳 | 行数 |
|---|---:|
| `_cc_div` に追加された命令（§3.3） | **18**（`PUSH X`／`LDW X,#0`／`CMPI A,#0`／`BGE`／`XORI X,#1`／`NOT A`／`ADDI A,#1`／`CMPI B,#0`／`BGE`／`XORI X,#1`／`NOT B`／`ADDI B,#1`／`CMPI X,#0`／`BEQ`／`NOT A`／`ADDI A,#1`／`POP X`（正常経路）／`POP X`（ゼロ除算経路）） |
| 新規ラベル行 | **3**（`_ccdiv_apos:` / `_ccdiv_bpos:` / `_ccdiv_ret:`） |
| §3.7.1 の NOTE コメント行 | **1** |
| **計** | **22** |

**実測 22 行と完全一致する。** 段階1の追加が符号処理そのものであり、
それ以外を一切含まないことの強い裏付けである。
`_cc_mod` が現れないのも、C-1 マトリクスが add/sub/mul/div の4演算で
`%` を含まないことと整合する。

**（4）§4.10.6 の教訓が実務的である**

「bundle → unbundle → 元と一致」の往復検証が PASS してしまった理由が
「既存の `goldens/` が残っていて欠落分が上書きされなかったため」であり、
**「消してから作り直す」検証に変えて初めて検出できた**という記録は、
同種の見落としを広く防ぐ価値がある。

### 0.2 案R2 不要の確定は、実施順序の判断が正しかったことを示している

§4.7-3 の実測（ランタイム終端 **$03C6**・余裕 **49B**）により、
**従来パラメータのまま成立**し、案R1・R2・R6 はいずれも不要となった。
机上試算（$03D2・46B）との差 3B は許容範囲であり、試算の精度も裏付けられた。

指摘書 v5.0 A-1 で求めた順序を踏んだ結果、**5文書への恒久変更を回避し、
ゲート採取も1回で済んだ**。§3.8.3 が実測値を「退避策の記録」として保持し、
将来の再逼迫時は案R2 が第一候補であると明記した扱いも適切である。

## 4. C級指摘

### C-1【記載の曖昧さ】§4.10.5 の行数が「1件あたり」か「合計」か不明

| 段階 | 追加 | 削除 |
|---|---:|---:|
| 段階1 | 22（`m1_i_div_*` 3件のみ） | 0 |
| 段階2 | 0 | 186（全12件） |

当方の積算では **22 は「1ファイルあたり」の行数**である（§0.1(3)）。
また 186 も、6関数ブロックの規模（`_strcmp` だけで 131B ≈ 40命令超）から
**1ファイルあたり**と読むのが自然で、§4.10.2 の v1.1 失敗記録「150行が誤って NG 判定」とも整合する。

しかし「（3件のみ）」「（全12件）」という書き方は**合計値**とも読める。
実際、186 は 12 で割り切れない（15.5）ため、合計と読むと §4.10.1 の
「12件すべてが6関数を一切呼ばない＝同じ6ブロックが削除される」という前提と矛盾する。

**要求**：「**1件あたり 22行（`m1_i_div_*` 3件に発生・他9件は 0）**」
「**1件あたり 186行（全12件で同一）**」のように単位を明示すること。

### C-2【乖離の未説明】§4.7-1 の 9B の差

判定基準「752B → 約260B」に対し実測「約250B」（終端 $D87B）。
`RUNTIME_ORG_DEFAULT`（$D780）からの実占有は **$D87B − $D780 = 251B**。

予測 260B（`putchar` 34 + `_cc_div` 124 + `_cc_mod` 102）との差は **9B**。
§4.2-3 で「見積りと実測の乖離チェック」を検証手法として据えている以上、
**9B の差の由来（EQU 行の有無、ベースブロックの差など）を1行で注記**しておくと、
次回ランタイム構成を変えるときの見積り精度が上がる。判定自体は PASS で問題ない。

### C-3【成果物の保管】中間バイナリ `scc23n` の扱い

§4.10.2 の受入基準 v1.2（2段階比較）は、**(A) のみを含む中間バイナリ `scc23n`** を前提とする。
golden が v2.08 基準になった以降は再現に不要となるが、
**「段階1の削除が 0 であった」という判定を後日再現する唯一の手段**でもある。

**要求**：`scc23n` と `check_golden_v1_3.sh` の保管方針を §4.10 または §7 に1行記載すること
（保管する／再現不要として破棄する、いずれでも可。方針が書かれていないことが問題）。
