## 0. 総評

**TKT-03 の原因分析は正確であり、実体照合で全項目が裏付けられた。**

特に **「本件は実装漏れではなく設計の欠落である（実装は設計に忠実であった）」** と切り分けた §3.1.1 の判断を高く評価する（E-1）。
`emu23_v111.c` を全文検索したところ **`c_iflag` は 1 箇所も出現しない**（`c_lflag` は L463 のみ）。
設計書 v1.2 §3.1 のコード例が `c_iflag` を規定していない以上、実装は忠実だったという評価は正しい。
責任の所在を「実装者の不注意」ではなく「設計の網羅性」に置いたことで、
再発防止の方向（レビュー時に termios の 4 フラグ群すべての規定有無を確認する）が正しく定まる。

`SH-READLINE`（`kernel_forth_v0_10_18.fs` L3148）が **`$0D` のみを行終端として判定**していることも確認した。
§3.1.1 の因果図は実源と完全に一致している（N-3）。

必須指摘は 2 件で、いずれも**旧記述の残置**と**検証手順の後始末**に関するものである。設計方針そのものに異論はない。

## 1. 必須修正（M）

### M-1【重大度：中】§2.2 に v1.2 で撤去したはずの「真 EOF 終了」が残置されている

**指摘内容**

§2.2「終了方法（確定事項）」の第 3 項は次のままである。

> - `read()` が 0 を返す（EOFシグナル）場合も同様に終了条件として扱う。

しかし v1.2 の §3.2 改訂（「あ方針」）は、この `read()==0` 終了を**明示的に撤去**している。

> v1.1 §3.2 が保険として入れた `read()==0`（真EOF）終了を**撤去**。
> 理由＝…パイプ・リダイレクト供給時に入力流し切りで `read()==0` が発火し
> **ブート完了前に emu23 が即終了**して非対話の自動テストが不能になる弊害があった。

確定実装（§3.2 内・`emu23_v111.c`）も `if (n <= 0) return;` で**終了しない**。

**§2.2 は「前提・制約」の節であり、§3 の実装仕様より上位に読まれる。**
v1.3 で TKT-03 を実装する者が §2.2 を根拠に真 EOF 終了を「復活させるべき仕様」と解釈すると、
**v1.2 で潰した回帰（ブート完了前の即終了）を再発させる**。

§3.2 の旧コードは取消線と「v1.2 で撤去済み」の注記で正しく処理されているのに、
**§2.2 だけが処理されていない**。

**修正案**

§2.2 の第 3 項を取消線にし、注記を添える（v1.3 の編集方針＝旧記述を削除せず保持、に合わせる）。

> - ~~`read()` が 0 を返す（EOFシグナル）場合も同様に終了条件として扱う。~~
>   **【v1.2 で撤去】** raw mode + `ICANON` 無効の対話端末では真 EOF は発火せず、
>   パイプ供給時に**ブート完了前の即終了**を招くため。終了トリガーは **0x04 の 1 本**に確定。
>   詳細は §3.2 の「あ方針」改訂を参照。

### M-2【重大度：中】T03-2（LF 単独）の後始末が定義されていない

**指摘内容**

§5.1.2 の T03-2 は「`ver` + **LF** を送出 → 行確定しない（YUI OS 側の仕様どおり）」を期待結果とする。
**この期待自体は正しい**が、実源を見ると **LF は「無視される」のではなく「通常文字として行バッファに積まれる」**。

```forth
\ kernel_forth_v0_10_18.fs L3144-3164（実源・SH-READLINE）
BEGIN
    SH-KEY
    DUP $0D = IF                       \ ★CR のみが行終端
        DROP  0 SH-LINE-BUF SH-LINE-LEN @ + C!  SH-CR EXIT
    THEN
    DUP $08 = OVER $7F = OR IF         \ BS / DEL
        …
    ELSE
        DUP SH-EMIT                    \ ★LF はここでエコーされ
        SH-LINE-LEN @ 64 < IF
            DUP SH-LINE-BUF SH-LINE-LEN @ + C!   \ ★バッファへ格納される
            …
AGAIN ;
```

したがって T03-2 実施後、**行バッファには `ver` + `$0A` の 4 文字が残る**。
この状態で次のテスト（例: T03-1 の再実行）を行うと、
入力は `ver` ではなく `ver\x0A ver` となり、**`SH-STR=` の比較が一致せず未知コマンド扱い**になる。

**T03-1 が PASS するはずの改修版で FAIL する**——という誤判定を招く。

**修正案**

1. **実施順を明記する**: `T03-N → T03-1 → T03-2` の順とし、**T03-2 を PTY 系の最後に置く**。
2. **後始末を手順に加える**: T03-2 の後に **CR を 1 回送って行を確定・破棄**する
   （`ver\x0A` は未知コマンドとしてエラー応答が返るのが正常）。
   あるいは BS（`$08`）を LF の分だけ送ってバッファを巻き戻す。
3. **期待結果の記述を精密化する**:

   > 行確定しない。**LF は無視されるのではなく通常文字としてエコーされ行バッファに積まれる**
   > （`SH-READLINE` L3157-3162）。したがって続けて CR を送ると `ver\x0A` として
   > 未知コマンド応答が返るのが正常である。emu23 が LF を CR に変換してはならない。

この精密化には副次的な価値がある。**「LF がエコーされて画面に改行が出る」ことは、
LF が emu23 を通過して UART RX に届いた証拠**であり、
「LF が届いていないから反応しない」との区別がつく。判定の識別性が上がる。

### C-2 §3.3／§3.4 のコード例が旧関数名のまま

関数名を実装に合わせて更新すること。

### C-3 落とす入力フラグの選定根拠を正確にすべき（`IGNBRK` の欠落／`INPCK` の根拠）

§3.1.1【規定】の表と改訂版コードは次を落とす。

```c
raw.c_iflag &= ~(ICRNL | INLCR | IGNCR | IXON | ISTRIP | BRKINT | INPCK | PARMRK);
```

一方 `cfmakeraw(3)` が落とすのは `IGNBRK | BRKINT | PARMRK | ISTRIP | INLCR | IGNCR | ICRNL | IXON` である。
差分は 2 点。

| フラグ | 設計 | cfmakeraw | 所見 |
|---|---|---|---|
| **`IGNBRK`** | **落とさない** | 落とす | 表に無い。BREAK 条件の扱いが環境依存で残る。「入力の加工を一切させない」という §3.1.1 の方針からは落とすのが一貫する |
| `INPCK` | 落とす | 触らない | 落として実害はない（パリティチェック無効化）が、**「標準的 raw mode の定石」という根拠は不正確** |

**修正案**: `IGNBRK` を追加するか、**意図的に残す理由**を書くこと。
`INPCK` の理由は「定石」ではなく「パリティチェックを無効化しバイナリ透過性を確保するため」と実質で書く。
（なお `IXANY` も同様の位置づけだが、`IXON` を落とせば `IXANY` は無効化されるので追加不要。）

いずれも実害は薄いが、本チケットは**「フラグ群を網羅的に規定していなかったこと」自体が原因**である。
是正版で再び網羅性を欠くと、同じ失敗を小さく繰り返すことになる。

---

### C-4 T03-6（`stty -a` による復元確認）の実施環境を明記すべき

T03-6 は「`-it` 終了後に `stty -a` を確認 → `icrnl`／`ixon` が復元されている」とする。

- **実端末で手動実施する場合**は、そのまま `stty -a` でよい。
- **PTY による自動テストで実施する場合**は、`stty -a` の対象が親シェルの tty になってしまうため、
  **PTY 側の termios を親プロセスから取得して比較**する必要がある。

T03-N〜T03-2 が PTY 前提（§5.1.1）である一方 T03-6 だけ実端末前提に読めるので、
どちらで実施するかを明記すること。

なお `it_disable_raw_mode()` は `it_orig_termios` の**丸ごと復元**（`emu23_v111.c` L470-475）なので、
`c_iflag` も自動的に復旧する。設計書 §3.1.1【スコープ限定】の主張は実源で確認済みである（N-4）。

## 3. 情報（N）

- **N-1【§3.1.1 の事実確認】**: `emu23_v111.c` を全文検索したところ **`c_iflag` は 0 件**である
  （`c_lflag` は L463 の 1 件のみ、`c_oflag` も 0 件）。
  §3.1.1【事実】の表「実装 `emu23_v111.c` L455-468: `c_iflag` **なし**」は正しい。
  **「実装は設計に忠実であった」という評価も正しい。**
- **N-2【期待値の妥当性】**: Dhrystone 期待値 **819 / 48,785 / P:20** は `Makefile` L146 と一致する。
  さらに `Makefile` L12-16 に「絶対ゲート 826/48405/P:20（scc23 v2.03）→ **819/48785/P:20 に更新**」の
  履歴があり、**古い値（826/48405）を参照していない**ことを確認した。
  §5.1.3 の出典表記は妥当である。
- **N-3【因果の裏付け】**: `SH-READLINE`（L3148 `DUP $0D = IF`）は **CR のみ**を行終端とする。
  §3.1.1 の因果図「LF では行を確定しない」は実源と一致する。
- **N-4**: `it_disable_raw_mode()` は `tcsetattr(STDIN_FILENO, TCSANOW, &it_orig_termios)` で
  構造体を丸ごと書き戻す（L470-475）。`c_iflag` の復元に追加実装は不要という §3.1.1 の判断は正しい。

## 4. 評価（E）

- **E-1**: **「実装漏れではなく設計の欠落である（実装は設計に忠実であった）」** という切り分けが本設計書の白眉である。
  実体照合の結果この評価は正確であり、責任の所在を正しく特定できている。
  これにより再発防止策が「実装時の注意」ではなく
  **「設計レビュー時に termios の 4 フラグ群すべての規定有無を確認する」**という
  検査可能な形に落ちる。
- **E-2**: §5.1.1 で **「パイプでは `ICRNL` はそもそも作用しない。パイプで PASS しても何も証明しない」** と、
  **検証手段の妥当性を検証項目より先に論じた**構成。
  §5 の Ctrl+D 検証で得た「パイプ検証の構造的限界」（§8）を、
  別チケットへ**知見として横展開**できている。
- **E-3**: T03-N（ネガティブコントロール先行）を判定条件に組み込み、
  「症状が再現しない環境で改修版を試して PASS しても改修の効果ではない」と明記した点。
  W-5 以来の型が定着している。
- **E-4**: `IXON` を落とす理由を「定石だから」ではなく
  **「`ISIG` を落として生バイトを UART へ渡すという v1.0 以来の設計思想に対し、
  `IXON` を残すと Ctrl+S/Ctrl+Q だけがターミナルに奪われ一貫しない」**と
  **設計思想から導出**した点。判断が追跡可能になっている。
- **E-5**: §6 に `c_oflag`（`ONLCR`）をスコープ外として明記し、
  **「現状表面化していない理由（YUI OS 側が CR/LF を自ら送出）」と
  「将来 `\n` のみを送る OS を載せた場合は再検討」**という条件を添えた点。
  スコープ外事項を「やらない」で終わらせず、**再検討の発火条件**まで書けている。
