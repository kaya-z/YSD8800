## 総評

設計の質は高い。特に以下3点を高く評価する。

1. **§1.3 丸め方向の非対称の発見と方針**：FMUL が `>>8`（算術右シフト＝負の無限大方向 floor）、FDIV が `/`（C 整数除算＝ゼロ方向 truncate）で**丸め方向が異なる**ことを実源から抽出し、「**scc23 の挙動を正確に予測するのが役割であり、あるべき姿を示すことではない。数学的に正しい丸めに直してはならない**」と方針を明示した点。ヘルパの本質を突いており、この一文があるだけで実装時の誤りを大きく減らせる。
2. **§1.5 の実測発見**：単項マイナスが `0 - x` として実行時展開されるため**負のリテラルを含む式は定数畳み込みされず**ランタイム `_fmul`/`_fdiv` で計算される、という発見。起草中の実測で見つけ、ヘルパ出力に「畳み込み対象か否か」の注記を要件追加し、ランタイム丸めの一致確認を §7.5 に申し送った判断は的確。
3. **§3.3 のリスク自覚**：「ヘルパが間違っていると誤った期待値を自動生成する装置になり、手計算より危険（誤りが機械的に量産され、"自動化したから正しい"という誤った安心感を与える）」という認識と、対策4点（実源抽出・selftest 必須・実挙動突合・丸め非対称の意図的再現）は妥当。

**数値の独立検算**：レビュア側で `to_fixed` と `fold_binop_val` を Python で再実装し、設計書記載の全数値を検算した結果、**全件一致**を確認した。

- §2.5 self-test 10件：`8.5→0x0880` / `2.5→0x0280` / `4.0→0x0400` / `1.0→0x0100` / `0.5→0x0080` / `-1.0→0xFF00` / `-2.5→0xFD80` / `2.5/4.0→0x00A0` / `2.5*4.0→0x0A00` / `1.5+2.5→0x0400` すべて正。
- §1.5 実測表5件：`1.0/3.0→85` / `2.0/3.0→170` / `0.5*0.5→64` / `0.1*0.1→2` / `5.0/7.0→182` すべて正。
- §2.4 出力例：`0.1→0x0019`（25、誤差 -0.00234375）も正。

以下、実装前に反映すべき点。

## M-1【必須】self-test に「丸め方向の非対称」を検出できるケースが1件も無い

**箇所**: §2.5 F5 自己検証モードの内蔵ケース表、§4.1 V1

**問題**: §1.3 で「FMUL=floor / FDIV=truncate の非対称は本設計の**重要論点**」と位置づけ、§3.3 対策4で「丸め非対称を意図的にそのまま再現し、数学的に正しく直す誘惑を設計段階で禁止」としている。**にもかかわらず、§2.5 の self-test 10 ケースには、この非対称を検出できるケースが1件も含まれていない。**

内蔵 10 ケースを検算した結果:
- 演算ケース3件（`2.5/4.0`=0.625、`2.5*4.0`=10.0、`1.5+2.5`=4.0）は**すべて割り切れる値**で、丸めが一切発生しない。
- 負値ケース2件（`-1.0`、`-2.5`）は F1（リテラル変換）のみで、**負値の演算**は無い。

すなわち、実装者が誤って FMUL を「ゼロ方向丸め」で実装しても、あるいは FDIV を「floor」で実装しても、**self-test は全 PASS してしまう**。これでは §3.3 の対策2（selftest 必須）が、最重要リスク（丸め方向の取り違え）に対して機能しない。

**対応案**: §2.5 の内蔵ケースに、**負値かつ丸めが発生する演算**を最低2件追加する。丸め方向を取り違えると値が変わるケースを選ぶこと。例（レビュア検算済）:

| 入力 | 期待 hex | 期待10進 | 検出内容 |
|---|---|---|---|
| `-1.0 * 0.1` | `0xFFE7` | -25 | FMUL の floor を検証。`(-256*25)>>8 = -6400>>8 = -25`。ゼロ方向丸めなら -25（同値）※下記注参照 |
| **`1.0 / 3.0`** | `0x0055` | 85 | 正値だが**丸めが発生**（85.33→85）。現行10件には無い |
| **`-1.0 / 3.0`** | `0xFFAB` | -85 | FDIV のゼロ方向を検証。`(-256<<8)/768 = -85.33 → -85`（floor なら -86 で**不一致**） |
| **`0.1 * 0.1`** | `0x0002` | 2 | 丸め発生（625>>8=2）。§1.5 で実測済なのに self-test に無い |

特に **`-1.0 / 3.0`（期待 -85）** は、FDIV を floor で実装すると -86 になり**確実に検出できる**ため、非対称検証の要として必須。

> 注: §1.5 のとおり、負リテラルを含む式は scc23 では畳み込まれずランタイム計算になる。したがって上記の負値演算ケースは「`fold_binop_val` を再現するヘルパの内部ロジック検証」として self-test に入れる位置づけであり、**scc23 実挙動との突合（V2）の対象にはならない**（V2 では正値の丸め発生ケースを使う）。この区別を §2.5 に注記すること。

## N-1【推奨】§6「実装前の追加確認事項」は §1 で既に解決済み。整合を取る

**箇所**: §6（1. `(int16_t)` キャストの処理系依存、2. `>>8` が算術シフトかの確認）

**問題**: §6 は両項目を「実装前に確認すべき事項」としているが、
- §1.5 の実測（`1.0/3.0`→85、`0.5*0.5`→64、`0.1*0.1`→2 等が実測と完全一致）により、**gcc ビルドの scc23 が 2 の補数ラップ・算術右シフトで動作していることは既に実証済**。
- したがって §6 は「未確認事項」ではなく「**確認済・Python 側で明示再現する実装要件**」である。

**対応案**: §6 のタイトルを「実装前の追加確認事項」から「**実装時の再現要件（確認済）**」へ変更し、「§1.5 の実測一致により確認済。Python 実装では `ctypes.c_int16` 等で 2 の補数ラップを、`>>` で算術シフトを明示的に再現する」と記述。未確認事項が残っているかのような記述は、レビュー承認の判断を曖昧にする。

## N-2【推奨】F3 のスコープと §7.1（int/float 混在）の境界を出力で明示

**箇所**: §2.3 スコープ、§7.1

**内容**: F3 は float のみ対応で、`2.5 + 3`（int 混在）は §7.1 の将来課題。しかしユーザが誤って `2.5 + 3` を入力した場合の挙動が未定義。

**対応案**: F3 が int リテラルを検出したら「**未対応（§7.1）**」と明示エラーを返す仕様を §2.3 に追記。黙って float として扱う（`3` を `3.0` とみなす）と、scc23 の実挙動（`wrap_i2f` で `<<8`）と一致するとは限らず、**誤った期待値を生成する**リスクがある（§3.3 の懸念そのもの）。

## E-1【軽微】§1 の節番号順序が乱れている

**箇所**: §1.3 → §1.5 → §1.4 の順に記載

**内容**: 目次上 `1.3 丸め方向の非対称` → `1.5 負のリテラル…` → `1.4 オーバーフロー判定条件` と順序が入れ替わっている。§1.5 が起草中の発見で後から挿入されたためと推察されるが、読み順としては 1.3 → 1.4 → 1.5 が自然。KY41（追記で情報を欠落させない）を守りつつ、番号を振り直すか、§1.5 を §1.6 として末尾に置くのがよい。

## レビュー観点への回答（§9）

1. **§1 の仕様抽出は正確か** → **正確**。レビュア側で独立検算し全数値一致を確認。
2. **§1.3 の丸め非対称の扱いは妥当か** → **妥当**。「scc23 の挙動をそのまま再現し数学的に正しく直さない」は正しい方針。ただし self-test でそれを検証できていない（M-1）。
3. **F1〜F5 は完了条件を満たすか** → 満たす。C-2 の目的（手計算排除）に対し F1・F3 が中核、F5 が品質保証。
4. **self-test の内蔵ケースは十分か** → **不十分**（M-1）。丸め発生ケース・負値演算ケースが欠落。
5. **§3.3 の対策は十分か** → 対策の設計は妥当だが、対策2（selftest）が M-1 により実効を欠く。M-1 反映で十分になる。
6. **§4.2 の突合方式は妥当か** → 妥当。ただし負値式は畳み込まれない（§1.5）ため、V2 の対象は**正値の丸め発生ケース**（`1.0/3.0` 等）とすべき旨を明記推奨。
7. **§1.5 の反映は妥当か** → **妥当**。出力に「畳み込み対象か否か」の注記を付ける要件は的確。
8. **§7 申し送りの優先度は妥当か** → 妥当。特に **§7.5（ランタイム `_fmul`/`_fdiv` の丸めが `fold_binop_val` と一致するか）は優先度を上げる価値がある**。不一致なら「コンパイル時畳み込みと実行時計算で結果が異なる」潜在バグであり、C-3 と同種の値破壊につながる。Phase 2 を待たず、C-2 完了後の短時間調査として実施を推奨。
