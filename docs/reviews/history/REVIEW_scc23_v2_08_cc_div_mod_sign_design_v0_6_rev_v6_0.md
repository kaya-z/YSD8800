## 2. A級指摘

### A-1【検証計画の不成立】細粒度化により C-1 golden 12件が必ず FAIL する

#### 2.1 実源で確定した判定方式

`run_c1_matrix.sh` の golden 比較は以下のとおりである。

```bash
golden_cmp() {
    diff -q \
        <(grep -v '^; scc23 v' "$1") \
        <(grep -v '^; scc23 v' "$2") >/dev/null 2>&1
}
```

**除外されるのはバナー行（`; scc23 vX.XX ...`）のみ**で、それ以外は**生成 .asm の全行**が
比較対象である。`tests_c1_README.md` §4.1 も
「主判定：v2.06 で凍結した golden asm との byte 一致」と明記している。

そして `c1_goldens_bundle_v1_1.txt`（golden の実体）には、
`.org $D780` に続いて `_putchar` / `_getchar` / `_puts` / `_strcpy` / `_strcmp` / `_memcpy` の
**全命令列がそのまま含まれている**。

#### 2.2 帰結

C-1 のテストソース（`m1_*.c`）は算術演算のマトリクスであり、
`putchar` / `getchar` / `puts` / `strcpy` / `strcmp` / `memcpy` を**呼ばない**。

⇒ 細粒度化後は 6関数すべてが出力されなくなる。
⇒ **golden との diff が必ず発生する。**
⇒ **compile_ok 12件が全 FAIL する**（error_stop 12件は asm 比較を行わないため影響なし）。

**§4.7-5 の判定基準「C-1 マトリクス 24/24 PASS」は、原理的に達成できない。**

#### 2.3 これは golden 更新ルールに直撃する

`tests_c1_README.md` §7 および `HANDOVER_SCC23_PHASE1_v1_0.md` §6.1：

> 1. **原則：golden との差分は「回帰疑い」として調査する。** 自動更新してはならない。
> 3. **golden 更新が許されるのは仕様変更が正当と判断された場合のみ**。
>    その際は**変更理由の記録**と `golden_version` の刻み直しを必須とする。
> 4. **無検討の上書きは禁止。**
> 6. **責任分界**：golden 更新の判断は**設計レビューを経ること（原則43）**。
>    テスト実行者が単独で golden を上書きしない。

**§6-6 が求める「設計レビュー」が、まさに本レビューである。**
v0.6 は §4.7-5 に「24/24 PASS」とだけ書き、**golden が変わることに一言も触れていない**。
このまま実装に進むと、実行者が FAIL を見てから判断することになり、
README §7 が「典型的な失敗モード」として名指しした
「回帰時に安易に golden を上書きして回帰を握り潰す」状況を招く。

#### 2.4 幸い、この golden 更新は正当性を機械的に検証できる

**golden は .asm テキストであり、アドレスを含まない**（ラベル参照で書かれている）。
したがって細粒度化による差分は、**6関数ブロックの削除のみ**に限定されるはずである。
命令列の1行も変わってはならない。

**⇒ これは「差分が期待どおりであること」を diff で厳密に確認できる、
きわめて検証しやすい golden 更新である。** 安易な上書きにする必要はまったくない。

#### 2.5 要求

**v0.7 に「C-1 golden 更新方針」を新設し、以下を明記すること。**

1. **細粒度化により golden 12件に差分が生じることを、実装前に予告として明記する。**
   「FAIL が出た」ではなく「FAIL が出るはずである」と先に書く。
   これが README §7-1 の「回帰疑いとして調査する」を形式的に満たす唯一の方法である。
2. **受入基準を定める。** 差分が
   **「`_getchar` / `_puts` / `_strcpy` / `_strcmp` / `_memcpy` / `_putchar` のうち、
   当該テストが使用しない関数のブロックが削除されただけ」**であること。
   **それ以外の行が1行でも変化していれば回帰として調査を打ち切る。**
   確認コマンドを設計書に書いておくこと（例：`diff out/X.asm goldens/X.golden.asm` の
   出力が削除行（`<` 側）のみで、追加・変更行を含まないこと）。
3. **`golden_version` を `v2.06` → `v2.08` へ刻み直す**こと、および
   **変更理由**（細粒度化・設計書 v0.7 §X）を `.expected` に記録すること。
4. **`c1_goldens_bundle_v1_1.txt` → `v1_2` へ改版**すること。
   README §4.5 のとおり golden はバンドルからしか復元できないため、
   バンドルを更新しなければ再構築時に旧 golden が復活する。
   **§7.2 の文書更新表に追加すること。**
5. **§4.7-5 の判定基準を書き換える。**
   「24/24 PASS」→「**①差分が §2 の受入基準を満たすことを確認 → ②golden を v2.08 へ更新 →
   ③再実行して 24/24 PASS**」。
6. **`tests_c1_README.md` の改版（§7-11）に、golden 更新の事実と新 `golden_version` を
   含める**こと。現在 §7-11 は「絶対ゲート記載を改版」としか書いていない。

> **補足**：このルールは「golden を変えるな」ではなく「変えるなら理由を残してレビューを通せ」である。
> 本件は仕様変更として正当であり、差分も機械的に検証できる。
> **手順を踏めば承認できる**ので、v0.7 での追記をもって可とする。

## 4. レビュア側で解消した事項

### 4.1 §3.11.3.5／§5-14 の「ワーク変数 EQU」の懸念は解消してよい

v0.6 §3.11.3.5 は、`_strcpy`/`_strcmp` の `$DBEA`/`$DBEC`、`_memcpy` の
`$DBEE`/`$DBF0`/`$DBF2` について「EQU が関数ブロック内にあると条件化で未定義になる恐れ」
としてリスクに挙げている。

**`c1_goldens_bundle_v1_1.txt` の実生成 asm を確認したところ、
これら6関数はワークをすべて「リテラルの絶対アドレス」で参照しており、
EQU シンボルを一切使っていない。**

```
_puts:      STW  A, [$DBEA]
_strcpy:    STW  A, [$DBEA] / STW  B, [$DBEC]
_strcmp:    STW  A, [$DBEA] / STW  A, [$DBEC]
_memcpy:    STW  A, [$DBEE] / STW  A, [$DBF0] / STW  A, [$DBF2]
```

**⇒ 6関数に EQU 依存は存在しない。条件化しても未定義シンボルは発生しない。**

EQU を使っているのは `_C_DIV_A`/`_C_DIV_B`/`_C_DIV_Q` を参照する `_cc_div`/`_cc_mod` 系だが、
これらは既にフラグ制御されており、EQU の出力も既存の仕組みで扱われている。

**要求**：§3.11.3.5 の当該記述を「実源確認の結果、6関数は絶対アドレス直書きであり
EQU 依存なし」と確定記載へ変更し、§3.11.5 のリスク表および §5-14 から削除すること
（削除ではなく「確認済・リスクなし」として記録する形が望ましい）。

## 6. 特に評価する点

1. **§3.11.3.2 の副次的発見**。`printf` の未実装を実測で確定する過程で、

   ❌/✅ の対比例（ビルド手順書の記載を信じる／`Makefile` L1 を直接読む）も具体的でよい。

一文を加えておくと、この系統の見落としを次も防げると考える。
