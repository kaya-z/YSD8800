## 0. 総評

**問題の特定は的確である。** 特に以下は評価する。

- **§1.1 で「落ちてくれない壊れ方」と表現し、B-C の `$FFFF`＝`IDX_NIL` 問題と同一構造（silent な正常受理）であると位置づけた**こと。問題の性質を正しく捉えている。
- **§1.3 で B-2／B-3 を分離してはならない理由**を「分けると『直したのに使えない』中間状態が生まれ、検証が空振りする」と述べた点。1変更1検証の原則と、検証が成立する単位の設計を両立させている。
- **§2.1 の影響範囲調査**。本レビューでも実源照合し、記載どおりであることを確認した（下記 §0.1）。「KY で懸念した危険が想定より小さいと判明した」という**調査結果が想定を否定した事実をそのまま記録している**点は、設計文書として誠実である。
- **§5.3 の「stdout を汚さないことが絶対条件」**。B-C §2.1 の教訓を正しく継承している。

一方で、**案C の前提そのものに関わる問題が 2 件**（M-1／M-2）ある。加えて、**§1.1 が本件の危険の本質として特定した silent 失敗が、改修仕様で対策されていない**（M-3）。この 3 件は実装前に解消が必要である。

## 1. M（Must：修正必須）

### M-1 `--dbg` / `--sym` を片方だけ指定すると、もう片方の解釈が壊れる

§5.1 の決定表は `.dbg` と `.sym` を**独立に**判定するとしている。しかし**位置引数の解釈をそのまま残す**（案C の核）ため、新オプション自身が `argv[2]`／`argv[3]` を占有してしまう。

**ケース1：`--dbg` のみ指定（＝検証項目 A-2 そのもの）**

```
./emu23 poc.bin --dbg poc.dbg          （argc = 4）
  argv[2] = "--dbg"     … --dbg 指定ありなので .dbg はオプション値を採用 ✅
  argv[3] = "poc.dbg"   … --sym 未指定 かつ argc>=4 ⇒ 決定表により argv[3] を採用
                          ⇒ load_sym("poc.dbg")   ★.dbg ファイルを .sym として読む★
```

`load_sym()` は L1370-1382 で `sscanf(line, "%31s %31s")` の 2 トークンを取り、いずれかが 16 進数字始まりなら**シンボルとして登録してしまう**。`.dbg` の行形式によっては**ゴミシンボルが登録される**（`fopen` は成功するため警告も出ない）。

**すなわち §6.2 の A-2「`.dbg` が読め、`.sym` は自動導出」という期待結果は、決定表どおりに実装すると成立しない。**

**ケース2：`--sym` のみ指定**

```
./emu23 poc.bin --sym poc.sym          （argc = 4）
  argv[2] = "--sym"     … --dbg 未指定 かつ argc>=3 ⇒ load_dbg("--sym")
                          ⇒ fopen 失敗 ⇒ L1367 で黙って return
                          ⇒ ★.dbg の自動導出が行われない★（silent に .dbg を失う）
```

**是正案**：位置引数解釈の対象から「オプション走査が消費した argv」を除外する。

```c
/* 消費済みインデックスを記録する（オプション走査の全パスで共通） */
static char argv_used[ARGV_MAX];   /* 0=未消費 / 1=オプション本体または其の引数 */
...
/* 位置引数の解釈は「未消費」の argv に対してのみ行う */
if (dbg_path_opt)              load_dbg(dbg_path_opt);
else if (argc >= 3 && !argv_used[2]) load_dbg(argv[2]);
else { change_ext(...); load_dbg(extbuf); }
```

**この方式は案A（`-` 始まり判定）とは異なる。** 案A が却下されたのは「`-i uart.bin` の `uart.bin` が `-` 始まりでないため判定漏れする」ためだが、**消費済みマークであれば `-i` とその引数 `uart.bin` の両方が消費済みとなり、判定漏れが原理的に生じない**。

**既存互換への影響**：`emu23_debug_manual_v1_3.md` の `emu23 yuios.bin yuios.dbg yuios.sym -b 1A00 -n 100` 形式（後述 M-2 参照）では、`argv[2]`／`argv[3]` はどのオプションにも消費されないため**未消費のまま位置引数として解釈され、現行と完全に同一に動作する**。

> **本是正を行わない場合の代替**：決定表に「`--dbg` または `--sym` のいずれかが指定された場合、位置引数解釈を全面的に無効化する」を追加する（`.dbg`／`.sym` 独立判定をやめる）。実装は単純だが、`poc.dbg` を位置引数・`.sym` をオプションで渡す混在形が使えなくなる。**どちらを採るか設計判断を求める。**

### M-2 §2.2 が「壊してはならない」とする 9 例は、現時点で既に壊れている

§2.2 は「位置引数で `.sym` 明示」の形式が 9 例現存し「これらを壊してはならない」とする。しかし**実源に照らすと、この形式は現時点でシンボルを読めていない**。

**実例**（`yuios_ph3_storage_design_v1_5.md` L897）

```
./emu23 yuios_v11.bin yuios_v11.sym -i uart_test_input.bin --disk disk.img -q
  argv[2] = "yuios_v11.sym"  → load_dbg()  ★.sym を .dbg として読む★
  argv[3] = "-i"             → load_sym()  → fopen 失敗 → L1367 で黙殺
                               ⇒ シンボルは一切読まれない
```

同形式は `yuios_build_procedure_v1_13.md` L245／L256／L374 にも存在する（`./emu23 yuios.bin yuios.sym --disk disk.img -q` 等）。**いずれも `.sym` が `.dbg` として読まれ、シンボルは読めていない。**

一方、**`emu23_debug_manual_v1_3.md` の形式は正しく動作している**。

```
emu23 yuios.bin yuios.dbg yuios.sym -b 1A00 -n 100     （L111／L129／L306／L571 の 4 例）
  argv[2]=.dbg ✅  argv[3]=.sym ✅
```

**したがって §2.2 の 9 例は 2 群に分けて評価しなければならない。**

| 群 | 形式 | 現状 | 保護の要否 |
| --- | --- | --- | --- |
| **群α**（debug_manual 系・4 例） | `bin dbg sym [opts]` | **正常動作** | **★保護必須★**（実在する互換） |
| **群β**（build_procedure／storage_design 系・5 例前後） | `bin sym [opts]` | **既に破綻**（`.sym` を `.dbg` として読み、シンボル未ロード） | **保護不要。むしろ是正対象** |

**是正**：

1. §2.2 の表を上記 2 群に分割し、**群βが既に破綻している事実**を記載する（`load_dbg()` に `.sym` が渡っていることを実源行番号とともに明記）。
2. §4.1「案C を選んだ理由」の「既存の 9 例が byte 単位で不変」という根拠を、**「群α 4 例が byte 単位で不変」**に訂正する。案C の妥当性自体は群αによって支えられるため結論は変わらないが、**根拠の 5 例分は誤り**である。
3. **群βの文書は改版対象**として §8 に追加する（`yuios_build_procedure` L245／L256／L374、`yuios_ph3_storage_design` L897）。改修後は `--sym` 形式へ書き換えることで正しく動くようになる。

> **★KY（本件から得られた教訓）★** 「文書に載っている起動例は動作しているはずだ」という前提を置かず、**実装の引数解釈規則に照らして 1 例ずつ追跡する**こと。本件では 9 例中 5 例前後が「載っているが動いていない」状態だった。**動作例の文書化と、その例が実際に動くことの検証は別作業である。**

### M-3 §1.1 が本件の危険の本質と特定した silent 失敗が、改修仕様で対策されていない

§1.1 は次のように述べる（設計書の記述として正しい）。

> `load_dbg()`／`load_sym()` は `fopen()` 失敗時に**黙って return する**（L1367）ため、誤認しても**エラーにならず実行が継続**する。
> **★本件の危険度が高い理由★** 落ちてくれない壊れ方である。

ところが **§5 の改修仕様は新オプションの追加と `MAX_SYM` 拡張のみで、L1367 の黙殺には一切手を入れていない。** その結果：

- `--sym typo.sym` とタイプミスしても**無言で通る**（新オプションを使っても危険は残る）
- 位置引数形式の利用者にとっては**現状のまま何も改善しない**

**すなわち「新しい安全な道を用意したが、既存の落とし穴は塞いでいない」状態である。**

**是正**：`load_dbg()` / `load_sym()` の `fopen` 失敗時の扱いを、**指定経路によって切り分ける**。

| 指定経路 | `fopen` 失敗時 | 理由 |
| --- | --- | --- |
| **明示指定**（`--dbg` / `--sym` / 位置引数） | **stderr へ警告を出す**（`[SYM-NOTFOUND]` 等） | 利用者が明示的に指定した以上、読めないことは異常である |
| **自動導出**（`change_ext`） | **従来どおり黙殺** | ファイルが存在しないことが正常（`.dbg` を持たないビルドは普通にある） |

実装は `load_sym(const char *path, int explicit_spec)` のように 1 引数追加すれば足りる。**stdout は汚さない**ため §5.3 の絶対条件と両立する。

> **これを行って初めて、§1.1 が挙げた危険（silent な正常受理）への対策になる。** B-C で `[MMIO-UNMAPPED]` 警告を設けたのと同じ思想である。

## 2. C（要確認：回答次第で M に昇格）

### C-1 `regress` は `2>&1` で stderr を stdout に合流させている

`Makefile` L175 は次のとおりである。

```
@timeout 30 $(EMU) $(DHRY_BIN) -q 2>&1 | grep -iE 'Dhrystones/sec|cycles|P:'
```

**すなわち G-1（Dhrystone ゲート）の経路では stderr が stdout に合流している。** 設計書 §5.3 は「stdout を汚さないこと」を絶対条件とし、警告を stderr に出すことで両立するとしているが、**この経路に限っては両者が同一ストリームに入る**。

現行の `[SYM-TRUNCATED]` 文言は `grep -iE 'Dhrystones/sec|cycles|P:'` のいずれにも一致しないため実害は無い。ただし：

- 将来の警告文言が偶然 `cycles` や `P:` を含むと、**ゲートの grep に紛れ込む**
- §6.1 G-3 の「`2>/dev/null` で比較」は `run` 相当の経路であり、**G-1 の経路とは異なる**

**回答願う**：(a) 警告文言に `cycles`／`P:`／`Dhrystones/sec` を含めない旨を規約化するか、(b) `regress` を `2>/dev/null` に変更するか（ただし Makefile 変更は回帰ゲート自体の変更となるため慎重に）。**(a) を推奨する。**

### C-2 `--dbg` / `--sym` を「4 回スキャン方式」のどのパスで解析するか

§3 の所見のとおり、現行は `-q`/`-i`（L2255〜）／`--disk`（L2354〜）／`-n`/`-b`（L2379〜）／`-m`（L2389〜）の**4 パスに分かれている**。`--dbg`／`--sym` は **`load_dbg()`／`load_sym()` の呼出（L2330-2342）より前**に解析されていなければならないが、`--disk` 以降のパスはすべて L2354 以降＝**呼出より後**である。

**回答願う**：`--dbg`／`--sym` は L2255 の第1パス（`-q`／`-i` と同じ）で解析するという理解でよいか。**設計書 §5.1 に「解析位置」を明記されたい**（実装者が `--disk` の隣に足すと動かない）。

### C-3 `--sym` が最終引数の場合の挙動（設計書 §9 論点1）

他オプションは `i+1 < argc` で黙ってスキップしている。**同じ流儀に揃えると、本件が是正しようとしている silent 失敗をまた 1 つ増やすことになる。**

**回答願う**：**引数欠落はエラーとして `stderr` に出力し `exit(1)` することを推奨する。** 根拠は M-3 と同一で、「明示的に指定したものが機能しないのに黙って続行する」ことが本チケットの敵だからである。既存オプションの流儀に揃える必要は無い（既存の流儀こそが EMU-A の温床である）。

### C-4 §6.2 B-2v の「`MAX_SYM` を一時的に小さくした PoC」は検証対象と別バイナリになる

B-2v は `MAX_SYM` を小さくした emu23 をビルドして打切り警告を確認するとしている。しかし**それは出荷する v1.13 とは別のバイナリ**であり、**実際に出荷されるバイナリの打切り経路が動くことの証明にはならない**。

**回答願う**：**2,049 行以上の `.sym` を合成して与える**方式に変更できないか。`seq` 等で機械生成すれば容易であり、**出荷バイナリそのものを検証できる**。

## 3. N（改善提案）

| ID | 内容 |
| --- | --- |
| **N-1** | **（肯定的確認）** `MAX_SYM` 16 倍化に伴う `lookup_sym()` の線形探索コストを懸念したが、**実源照合の結果、呼出は L2081 の 1 箇所（REPL のブレークポイント設定）のみ**であり、命令実行ループには存在しない。**性能影響は事実上ゼロ**である。設計書に記載は無いが、**この確認結果を §3.2 に追記しておくと、後年「なぜ 2048 でよいと判断したか」の根拠が残る** |
| N-2 | §3.2 の本文「ホスト BSS が **68KB 増える**」は不正確。増加分は 69,632 − 4,352 ＝ **65,280 B（約 64 KB）**であり、68 KB は**増加後の総量**（69,632 B）である。表の「+65 KB」は正しい |
| N-3 | `sym_t.name` は `char[32]` で `snprintf` により**黙って切り詰められる**。1,199 シンボルの PoC で 31 文字超のラベルがあると、**別ラベルが同名になり `lookup_sym()` が誤ヒットする**。名前長の実測（`awk '{print length($2)}' poc.sym \| sort -n \| tail -1` 等）を検証計画に加えるか、切詰め時に警告を出すことを検討されたい |
| N-4 | `[SYM-TRUNCATED]` のタグ名（§9 論点3）は **妥当**と判断する。B-C の `[MMIO-UNMAPPED]`／`[MMIO-UNSUP]`／`[MMIO-SUMMARY]` と体系が揃っており、`grep` 可能な固定接頭辞という要件も満たす。**M-3 を採用する場合は `[SYM-NOTFOUND]` を同体系で追加**されたい |
| N-5 | §9 論点2（先頭 2048 本を採る）は**妥当**。`.sym` の記載順で先頭から採る方式で問題ない。ただし **`[SYM-TRUNCATED]` に「どのシンボル以降が落ちたか」（最後に読めたラベル名）を含める**と、デバッグ時に「目的のラベルが落ちた側かどうか」が即座に判る |
| N-6 | §8 に **emu23 起動時バナー（L2219-2251）の更新**が含まれていない。バナーは①版数表示（`emu23 v1.12` → `v1.13`）②`usage:` への `--dbg` / `--sym` 追加が必要である。**「開発ツールは起動時にバージョンが分かるように表示する」という本プロジェクトの規律に直結するため、§8 ではなく §5（改修仕様）に含めるべき** |
| N-7 | §7 の実装単位は「段1＝MAX_SYM／段2＝オプション新設」の順だが、**段1 完了時点では 1,199 シンボルが読めても位置引数誤認は残る**ため、PoC での実利用は段2 完了まで待つことになる。順序自体は妥当（段1 のほうが影響が局所的）だが、**段1 完了＝EMU-B 解消ではない**旨を明記されたい（§1.3 の趣旨と整合させる） |
