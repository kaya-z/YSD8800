## 0. 総評

構成・粒度ともに良好である。特に以下は高く評価する。

- **§9.1 の陰性対照が実測に置換されている**（KY54 遵守）。N-2b で「`cyc.txt` が実在するためエラーすら出ずシンボルテーブルとしてサイレント誤読される」ことを能動的に暴いた点は、EMU-A の教訓が正しく継承されている。
- **§5.1 の `mc_step()` 設計**（`mc_enable==0` なら表を一切参照せず即 1 を返す）により、R1「既定は現行と完全同一」が構造的に保証されている。段2で G-1〜G-5 全 PASS を要求する検証設計も適切。
- **§7.2 の消費数決定表**で `access()` 判定を明示的に棄却し、その理由（タイプミスのサイレント失敗）を書き残している点。棄却案の記録は良い習慣である。
- **§3.1 の「表の値は IRQCHK 非込み、+1 は加算時」という規約明記**。これを書かずに実装すれば全命令 1 ずれる事故は確実に起きた。

一方、設計書が「実装前に要確認」として留保した **M-1（IRQCHK 二重計上）と C-2（MMU 経路）は、レビュー側の実源照合により本レビューで結論が確定した**。これらは設計書に確定値として書き戻す必要がある（未決のまま実装着手は原則43違反）。加えて、実源照合で新たに 2 件の M（usage 更新漏れリスク・BRK 欠落）を摘出した。

## 2. M 指摘（必須是正：4件）

### M-1 【設計書 §5.2 / §12 M-1 の解決】割込受理は **+8** が正。二重計上は「有る」

設計書が未決としていた本件は、一次情報から結論が出る。

**根拠1** — `ysd8800_cycle_count_table_v1_0.md` §割込関連：

> 割込受理 ｜ 9 ｜ 状態連鎖: **IRQCHK**, IRQ_ACCEPT, PUSH_LO/HI×2, MEMR_LO/HI（ベクタ読）

状態連鎖の**先頭に `IRQCHK` が明記**されている。すなわち「9」は IRQCHK 込みの値である。

**根拠2** — `ysd8800_cpu_v0_1_FIXED.sv` L610-612：

```systemverilog
S_IRQCHK: begin
    ...
        next_state = S_IRQ_ACCEPT;
```

RTL 上でも受理シーケンスは `S_IRQCHK` を**入口として通過**する。命令間共通の IRQCHK と受理シーケンス冒頭の IRQCHK は**同一の 1 サイクル**であり、別物ではない。

**結論**：§3.1 で毎命令 +1 している IRQCHK と、表の「9」に含まれる IRQCHK は重複する。よって

```c
if (mc_enable) cpu.cycle += (mc_irq_accept - 1);   /* 既定 9 → 実加算 8 */
```

**是正要求**：
1. §5.2 の擬似コードを上記に改める。
2. §12 の M-1 を**解決済みとして確定値を記載**し、未決事項から外す。
3. §4.4 / §6.2 の `IRQ` キーに書く値は**表と同じ 9（IRQCHK 込み）**とし、`-1` は加算時に行う旨を §3.1 と同じ調子で明記する。§3.1 が「表の値そのもの＋加算時に +1」なのに対し、IRQ だけ「表の値そのもの＋加算時に −1」となり**符号が逆**である。この非対称は事故要因になるため、§3.1 の直後に IRQ の扱いを並べて記載されたい。

> ⚠ 補足（要確認事項として §12 に残してよい）：表の状態連鎖を素朴に数えると
> IRQCHK(1)+IRQ_ACCEPT(1)+PUSH_LO/HI×2(4)+MEMR_LO/HI(2)=**8** であり、表の値 9 と 1 合わない。
> 表 §1.4 のとおり受理は「較正」由来なので実測値 9 を採るのが妥当だが、
> 偶然にも「9−1=8＝状態数」となるため、**根拠の取り違え**（状態数を数えて 8 にした、と誤解される）
> を防ぐ意味でも、上記の導出過程を設計書に残されたい。

### M-2 【設計書 §4.2 / §12 C-2 の解決】サブオペ peek は `mem[cpu.pc]` 不可。`fetch8(cpu.pc)` とせよ

設計書が「実装前に実源で要確認」とした C-2 は、実源で**確定的に誤り**と判明した。

**根拠** — `emu23_v1_14.c`：

| 行 | 内容 |
|---|---|
| L234-235 | `static inline uint8_t fetch8(uint16_t a) { return phys_rd8(mmu_translate(a)); }` |
| L1714 | 実行部（`case 0x1F`）は `uint8_t sub = fetch8(cpu.pc++);` |

実行部は **MMU 変換を通した `fetch8`** でサブオペを読む。設計書 §4.2 の `mem[cpu.pc]` は論理アドレスで物理配列を直接引くため、`--mmu` 有効時に**実行部と異なるバイトを読む**。結果、CPI だけが誤った値で引かれる（論理結果は正しいまま cycle だけ狂うため、発見が極めて困難な部類のバグである）。

**是正要求**：§4.2 の擬似コードを次に改める。`fetch8()` は `pc` を進めないため、§4.2 の「`cpu.pc` を進めてはならない」という注意はそのまま有効である。

```c
if (opcode == 0x1F)  cpi = mc_table_ext[ fetch8(cpu.pc) ];   /* MMU 経路で peek */
else                 cpi = mc_table[opcode];
```

§12 の C-2 は解決済みとして確定値を記載されたい。

> **横展開（原則122・N扱い）**：同種の直読が `instr_size()`（L1464 `uint8_t op = mem[addr];`、L1523 `mem[(uint16_t)(addr+1)]`）にも存在する。こちらはディスアセンブラ用であり本 Phase の対象外だが、`--mmu` 併用時に逆アセンブル表示が狂う既知リスクとして `emu23_kairyo.txt` に起票を推奨する（本設計書の修正対象とはしない）。

### M-4 【設計書 §4.4】`BRK`（0x06）がデフォルト表から欠落している

emu23 は BRK を実装している。

**根拠** — `emu23_v1_14.c` L1706-1708：

```c
case 0x06: /* BRK — デバッグトラップ (§5) */
    ...
    printf("** BRK at %04x **\n", pc0);
```

一方 `ysd8800_cycle_count_table_v1_0.md` §2 に BRK の行は無く、設計書 §4.4 のデフォルト表にも無い。このままでは BRK 実行時に `MC_UNDEF` → 既定 4 が適用され、§4.3 の警告

```
emu23: [-mc] no cycle entry for opcode 0x06, using default 4
```

が stderr に出る。BRK はデバッグ用途で意図的に踏むものであり、「未定義 opcode に遭遇した」という警告文言は**誤解を招く**。

**是正要求**：BRK の扱いを §4.4 に明記せよ。次のいずれかを選択し、選択理由を記載されたい。

| 案 | 内容 | 備考 |
|---|---|---|
| a | BRK = 2（FETCH, OPFETCH 相当）として表に載せる | RTL に BRK 対応 FSM があるか要確認 |
| b | BRK を「emu23 固有のデバッグ命令であり RTL 実機に存在しない」と位置づけ、警告対象外の特例（CPI=0 または 2）とする | HALT（§3.2）と同じ「表の値をそのまま使わない」系の扱い |

いずれにせよ、**警告文言が出ない**ようにすること。§4.3 の禁止事項（`Dhrystones/sec` / `cycles` / `P:` を含めない）と同様、デバッグ体験を損なわない配慮が必要である。

## 3. C 指摘（確認・明記要求：5件）

### C-1 【§3.2 / §12 C-1】HALT を 2 とする根拠を補強せよ

サイクル表 §2 の HALT 行は状態連鎖が **`FETCH, OPFETCH, HALT` の 3 状態**と明記されている。設計書は「HALT は 2（FETCH, OPFETCH）」としているが、状態数からは 3 が自然である。

表の注記は「CPI=4 は **dbg_halt 到達検出コストを含む**較正基準値」であり、除くべきは「検出コスト（4−3=1）」であって「S_HALT（3−2=1）」ではない可能性がある。

**要求**：`2` を採るなら「S_HALT は停止状態であり以後歩進しないため、命令コストとしては計上しない」等の**論理**を §3.2 に書き足されたい。影響は最終 cycle 値の ±1〜2 に留まるため M とはしないが、根拠が「括弧付きだから使わない」だけでは弱い。

---

### C-2 リセット 2 サイクルの扱いが未定義。§9.2 C-03 の期待値が検算不能

サイクル表 §割込関連に「リセット ｜ 2 ｜ RESET_LO, RESET_HI」がある。emu23 は `cpu.cycle` を 0 起点とし、リセットシーケンスを歩進しない。

§9.2 C-03 の期待値「`cycle = N×(2+1) + 起動分`」の**「起動分」が未定義**であり、このままでは手計算と一致するか判定できない（＝テストが機能しない）。

**要求**：次を §9.2 または §3 に明記されたい。
- `-mc` 時にリセット 2 サイクルを計上するか否か（**計上しない**を推奨。emu23 の cycle 起点定義を変えると G-4 の byte-exact 比較にも波及しうる）
- C-03 の期待値を確定式で記載（例：`cycle = N×3 + HALT分`。HALT を 2 とするなら `N×3 + 3`）

---

### C-3 【§7.2】`-` 始まりファイル名を許容しない制限 — **妥当と判断する**

`access()` 判定を棄却しサイレント失敗を避ける方針は正しい。制限自体は実用上問題ない。

**要求**：§7.2 の「設計書・マニュアル双方に明記する」を実行すること。具体的には §11 の `emu23_debug_manual` v1.6 の改版内容に「`-mc` の節に本制限を記載」と明示的に書き加えられたい（波及文書表が「`-mc` の節を新設」としか書いていないため、制限の記載が抜ける恐れがある）。

---

### C-4 【§4.3】未定義 opcode の既定値 4 — **妥当と判断する**

表 §3 の CPI 分布で 4 が最頻（レジスタ ALU 系）であることは実源で確認した。異論なし。

**要求（軽微）**：警告の「初回のみ」が **主表と拡張表で別カウントか共通カウントか**を明記されたい。共通 1 回だと、主表で 1 回出た後に拡張表の未定義に遭遇しても黙る。opcode 空間が別なので **別カウント（各 1 回）** を推奨する。

---

### C-5 【§4.2】PC ラップ時のサブオペ peek 境界ガードが未記載

`instr_size()` は L1522 で `if (((uint32_t)addr + 1) >= MEM_SIZE) return 2;` とガードしている。設計書 §4.2 の peek には同等のガード記載がない。

`cpu.pc == 0xFFFF` で 0x1F を実行した場合の挙動（`fetch8` は `uint16_t` 引数なのでラップして 0x0000 を読む）を、意図的にそう定めるのか、ガードして既定値を返すのかを明記されたい。
