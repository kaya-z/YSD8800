## 1. Major（v0.2で必須反映）

### M-1　P-1 の事実誤り：R-11（YSD8003）のmd5は台帳に記録されている

- **事実**：台帳 `fpga_source_version_ledger_v1_27.md` の L679 に、`ysd8800_ysd8003_v0_4.sv` が `639a4d6633…` として記録されています（先頭10桁で省略された表記です）。
- **原因の推定**：§2.1 の照合範囲は「32桁16進文字列すべて」でした。台帳の省略表記は32桁ではないので、この方法では拾えません。P-2 で指摘している「リテラル検索による偽陰性」が、計画書自身の照合でも起きています。
- **是正**：
  1. §2.1 の R-11 を「一致（台帳は10桁の省略表記）」に修正する。
  2. P-1 の対象を「5本」から「4本（R-4/R-5/R-10/R-12）」に修正する。
  3. §2.1 の照合方法を「先頭8桁の部分一致」に改める。
  4. 観点H で「無い」と判定するときは、別系統で1回反証する手順を明記する（KY106）。

### M-2　P-4・§2.2 の事実誤り：v0.5.8 に対する V2 再実行の記録は実源にある

- **事実**：
  - v0.5.8 の改版記録（CPU実源 L166-L167）には、改修前のベースラインを取ったうえで同一TBを再走し、等価を確認したと書かれています。結果は「V1系8TB（25 PASS/0 FAIL）・V2e（82ベクタ ALL PASS）」です。
  - v0.5.7 の記録（L181-L183付近）には、理想メモリTB（`tb_cpu_v2a_v0_1`、20ベクタ）で回帰を取り、ALL PASSだったとあります。
- **本当の残存事項**：同じ v0.5.7 の記録（L174-L176付近）には、V2 の82ベクタは理想メモリTB（`mem_ready` 固定1）で実施したため、`S_SUBOP` の `mem_rd` 欠落を見逃したと明記されています（原則63）。したがって、V2 が保証するのは「理想バス上での命令の意味」だけです。実際の req/ack バス上でのCPUの外部挙動は、V3統合TBとシステム全体の実行（V8-b・段7）でしか担保されていません。
- **是正**：
  1. P-4 を「再実行記録あり（実源 L166-L167）。ただし理想メモリTBによる」に修正する。
  2. §2.2 の「★残存事項★」を上記の本当の残存事項に書き換え、原則63を引用する。
  3. これを受けて、CPUの外部I/Fを周辺側から点検する理由を§2.2 に明記する（m-3 と関連）。

### M-3　一次資料にRTL設計メモが入っていない

- **問題**：観点B・Eでは、見つかった簡略化が「承認済みの設計判断」なのか「抜け」なのかを判定する必要があります。ところが §3 の仕様軸は、デバイス設計書（emu23 側の仕様）とUART設計書しか挙げていません。
- **例**：台帳 L679 には YSD8003 について「CRC無視」と記載されています。これが承認済みの判断かどうかは、`v6a_storage_design_memo_v0_2.md`（台帳 L698）と `v6a_integration_design_memo_v0_3.md`（L699）を見ないと決められません。
- **是正**：§3 に「③' RTL設計メモ軸」を追加する。
  - 対象は各RTLの設計根拠となったメモです（V3／V3.5（`v3_5_design_memo_v0_3.md`、ARCHIVE F-02）／V3.7／V4／V5／EN是正（F-06）／V6-A／TKT-V6・V7・V12 系など）。
  - 所在（ナレッジ内か、Drive かを ARCHIVE_INDEX で確認）を段0で一覧化する。
  - 判定区分に「承認済みの簡略化（設計メモ根拠あり）」を加える。ただし、承認済みであっても §1.3 の基準に照らして S-1 または S-2 に該当するなら、重大度は下げない（例：`mem` 配列によるPSRAM挙動モデル）。

### M-4　S-1 候補（P-3：起動経路）の点検が最後の段4になっている

- **問題**：P-3 は計画者自身が「S-1候補」としています。これが「起動経路は無い」と確定した場合、ブートローダの新規設計が必要になり、Q-2 の判断にも工程③のロードマップにも影響します。この点検を最終段に置くと、点検範囲や工程を見直すきっかけが遅れます。
- **是正**：観点Gのうち「起動経路」と「FPGAトップ階層の有無」の2項目を、段1（H・E）と並行する**段0.5**に前倒しする。結果が S-1 だった場合は、段5の総括を待たずに「進捗と予定の確認(latest)」へ速報する手順を§6に追記する。

### M-5　観点Cの抽出が静的解析だけで、別系統の反証がない

- **問題**：シンボルを起点にした静的抽出では、実行時に「ベース＋オフセット」で計算されるアドレス（Forthのワードで合成するものなど）を取りこぼします。観点Cは S-1 の判定を直接左右するので、KY106（「無い」と言う前に別系統で反証する）を満たす手段が必要です。
- **根拠**：`emu23_debug_manual_v1_10.md` によれば、emu23 には次の2つの機能があります。
  - `--trace-addr`（L146）：物理アドレス単位でアクセスを記録する。
  - `--strict-mmio`（L139）：未接続MMIOへのアクセスで停止する。
- **是正**：観点Cに動的な系統を追加する。
  1. 現行の `yuios_road2.bin` を emu23 上でブートし、標準の操作を実行したときの `--trace-addr` 出力から、`$FC80` 以上のアクセスを抽出する。
  2. 静的抽出の結果と突き合わせ、和集合を照合対象とする。
  3. 同じ操作を `--strict-mmio` 付きで実行し、未接続領域へのアクセスが無いことを確認する。
  4. 操作シナリオは、動的抽出の「探索範囲」として結果に併記する（原則107）。

## 4. レビュー依頼事項への回答

### Q-1（boot手順書v1.2の改版時期）
**レビュアの推奨は (a)**。最終判断はユーザーに委ねます。
- HANDOVER_CHAT170 §2（L83-L85）では、boot手順書v1.2の改版を「②本体作業の一部」とすることがユーザー判断で確定しています。(b) を採るとこれを変更することになるので、ユーザーの再承認が必要です。
- (a) で現行RTLの実測を取り直しておけば、それが**是正前のベースライン**になります。是正後の回帰比較に使えます。v0.5.8 の改版でも「改修前ベースライン取得→同一TBで再走」という手順が取られていました（CPU実源 L165-L167）。
- シミュレーションを再実行すれば、観点F・G（どの機能をTBが肩代わりしているか）を動的に確認する材料にもなります。
- 是正後にもう一度実測する分は、boot手順書v1.3として工程③側で扱えば二重作業にはなりません。

### Q-2（観点Gで「無い」と判明した場合）
**計画どおりで可とします**。成果は「所見とTKT起票まで」とし、設計は別工程とします。条件が2つあります。
1. M-4 の速報手順を設けること。
2. ブートローダ等を新規に設計する場合は、ロードマップへ工程を追加する必要があるかを、工程管理チャットで判断してもらうこと。

### Q-3（是正は点検中に行わず、すべてTKT化）
**計画どおりで可とします**。原則43-Cに合っており、点検の前提も固定できます。次の2点を§6に明記してください。
- 次の作業は「RTL改変」に当たらないので許可すること：読み取り専用のシミュレーション実行、emu23の `--trace-addr` 実行、点検用スクリプトの作成。点検用スクリプトには版数を付けて管理すること。
- S-4（台帳の不整合）は、点検中に台帳を改版せず、所見として記録するだけにとどめること。台帳改版はP-1への対処を含めて②完了後に一括で行う。
