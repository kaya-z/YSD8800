## 0. 総評

方針（案A：既存減算ループを維持し、入口で絶対値化・出口で符号付与）そのものは妥当であり、
「1変更1検証」原則にも合致する。§1.1 の実測症状表は算法を追って再現計算した結果、
**全5行が実源アルゴリズムと完全に一致**しており（例：`7/-2` が A=7 に +2 を繰り返し、
16381回目で $8001 へラップして BLT 成立 → 商16381・比較16382回）、原因分析の精度は高い。
§2.2 の商・剰余の期待値も**全ケース C99 準拠で正しい**。

一方で、**境界値（INT_MIN）の検討が完全に欠落**しており、このままでは修正後も同一の
誤値が残る。また **検証計画の前提（絶対ゲート byte-exact 維持）が事実と矛盾**しており、
このまま実装に進むと検証段階で必ず破綻する。さらに §3.5 のワーク領域に関する記述が
事実誤認である。以上3点をA級として差し戻す。

なお設計の核心である符号退避・絶対値化・符号付与の命令列が擬似コード中で
**すべてコメント行**にとどまっており、その部分は現時点でレビュー判定不能である（B-1）。

## 2. A級指摘（ブロッカー）

### A-1【設計欠陥】INT_MIN（-32768 / $8000）で絶対値化が破綻し、誤値が残存する

**該当**: §3.3, §3.4（絶対値化）、§2.2（期待値表）

**内容**:
16bit 2の補数において `|-32768|` は 16bit で表現できず、`NOT + ADDI #1` の結果は
$8000（= -32768）のまま**負値として残る**。したがって §3.3/§3.4 が暗黙に置いている
「絶対値化後は両オペランドが 0〜32767 の非負」という前提が崩れ、`BLT`（符号付き分岐）が
現行 v2.07 と同じ誤判定を起こす。

具体例（本設計適用後の挙動を手追い）:

| 式 | C99期待 | 本設計適用後の予測 | 判定 |
|---|---:|---:|---|
| `-32768 / 2` | -16384 | 絶対値化後 B=$8000(負), A=2 → `CMP A,B`で BLT 成立 → 商0 → 符号付与しても **0** | ✗ 誤値残存 |
| `-32768 % 1` | 0 | 同上、余り $8000 が残り符号付与で **-32768** | ✗ 誤値 |
| `-32768 / -1` | C99上オーバーフロー（UB） | 未定義 | 動作定義が必要 |

**重要**: ISA2.3 の条件分岐は `BEQ / BNE / BLT / BGE` の**符号付き4種のみ**であり
（`hasm23_v1_04.c` L164-168）、`BLO`/`BHS` 等の符号なし比較が存在しない。
したがって「絶対値化後を符号なし16bitとして扱う」という一般的な回避策が**使えない**。
これは本件固有の制約であり、設計書に明記されていない。

**要求**:
1. 被除数 `B == $8000` を入口で `CMPI B,#0` ではなく専用判定（例：`CMPI B,#$8000` + `BEQ`）で
   検出する経路を設けるか、
2. あるいは「INT_MIN は非対応（実装定義動作）」と明示的に宣言し、§2.2 の期待値表に
   境界ケース行を追加して**意図的な非対応であること**を記録する。
3. いずれの場合も、除数側 `A == $8000`（例：`100 / -32768` → 商0・余り100）も併せて検討すること。

**レビュア推奨**: 案1は減算ループでは追加コストが大きい。実用上 INT_MIN 除算は稀であり、
「非対応を明記＋期待値表に記載」（案2）でも承認可能と判断する。ただし**無言で放置は不可**。
「見えているバグは先に潰すこと」の原則に照らし、少なくとも**既知の限界として文書化**が必須。

### A-2【検証計画誤り】Dhrystoneは `/` と `%` を両方使用しており、「絶対ゲート byte-exact 維持」は成立しない

**該当**: §0.3、§4.2

**内容**:
§4.2 は「Dhrystone は負値除算を使用しないため理論上不変のはず」として、v2.07 の生成asmとの
**byte-exact 一致**を検証項目に掲げている。しかし実源を確認したところ:

| 実源 | 該当行 | 使用演算 |
|---|---|---|
| `dhry_all_ansi2.c` L526 | `if (n >= 10) print_num(n / 10);` | `/` → `_cc_div` |
| `dhry_all_ansi2.c` L527 | `putchar('0' + n % 10);` | `%` → `_cc_mod` |
| `dhry_all_ansi2.c` L662 | `Int_1_Loc = Int_2_Loc / Int_3_Loc;` | `/` → `_cc_div` |

したがって Dhrystone ビルドでは `g_use_div=1` かつ `g_use_mod=1` となり
（`scc23_v2_07.c` L2825/L2833/L3146-3147 でフラグ立て、L3893/L3922 で本体出力）、
**ランタイムblobに符号処理・ゼロ除算ガード・PUSH X が追加された分だけ生成asmが必ず変わる**。

**帰結**:
- コードサイズ `21846B` は**必ず増加する**
- `-O1 cycles 47795` も**必ず変化する**（`print_num` は `n/10`・`n%10` を桁数分再帰的に回すため、
  ランタイム1回あたりの増分がループ回数分乗算される）
- §0.3 の「維持確認済」という表現、および §4.2 の「byte-exact」は**達成不可能な検証条件**

**要求**:
§4.2 を以下の主旨に全面改稿すること。
1. 判定基準を「byte-exact 一致」から「**Dhrystone の数値出力（Int_Glob 等の should-be 値）が
   v2.07 と完全一致**」へ変更する。Dhrystone のオペランドは全て非負であるため
   **数値結果は不変であるべき**であり、これが正しい回帰判定基準となる。
2. `826/48405/P:20/21846B` および `cycles 47795` は **v2.08 で再ベースライン**とし、
   新しい実測値を `tool_version_ledger` へ差分更新で記録する手順を §4.2 に明記する。
3. 増分の見積り（追加命令数 × 呼出回数）を設計段階で概算し、実測との乖離チェックに使うこと。

### A-3【事実誤認】「`_fmul`/`_fdiv` は別ランタイム・別ワーク領域」は誤り

**該当**: §3.5（影響範囲）

**内容**:
§3.5 は「`_fmul`/`_fdiv`（float演算）は無変更（別ランタイム・**別ワーク領域**）」と記載するが、
実源では float ランタイムが `_cc_div` のワーク領域を**借用している**。

| 実源 | 記載内容 |
|---|---|
| `scc23_v2_07.c` L3947 | `_C_DIV_A=$DBFA を符号フラグに借用(float中はcc_div非走行)` |
| `scc23_v2_07.c` L4063 | `WN=_C_MUL_A, WD=_C_MUL_B, WQ=_C_MUL_R, WR=_C_DIV_A, WSIGN=_C_DIV_B` |
| `scc23_v2_07.c` L4058-4059 | `_C_DIV_A`/`_C_DIV_B` の EQU を `_fdiv` 側でも条件付き出力 |

すなわち `_C_DIV_A`（$DBFA）・`_C_DIV_B`（$DBFC）は **int除算と float演算で共用**されており、
安全性は「float演算中に `_cc_div`/`_cc_mod` は走らない」という**相互排他の前提**によってのみ
担保されている。「別ワーク領域」という記述は将来の改修者を誤導する。

**要求**:
§3.5 を「`_C_DIV_A`/`_C_DIV_B` は float ランタイム（`_fmul`/`_fdiv`）と**共用**である。
float演算中に int除算が走らない相互排他前提により安全（実源 L3947 の設計意図）。
本改修はこの不変条件を変更しない」と正確に書き換えること。

**補足（B-2への布石）**: 実源確認の結果、`_C_DIV_Q`（$DBFE）は `_cc_div` 専用であり、
`_cc_mod` も `_fdiv`/`_fmul` も使用していない。これは B-2 の代案で活用できる。

## 3. B級指摘（v0.2 で修正）

### B-1【記述不足】擬似コードの核心部が命令列として記述されていない

**該当**: §3.3、§3.4

§3.3/§3.4 の擬似コードにおいて、本改修の本質である以下3処理が**すべてコメント行**であり、
実際の命令列が示されていない。

- 「A(除数)の符号見てNOT+ADDI#1で絶対値化、符号ビットをスタック退避」
- 「符号ビットをXORして最終スタックへ」
- 「result_signがマイナスならA = NOT A; ADDI A,#1」

このため**レビューで最も検証すべき部分が判定不能**である。特に「符号ビットをXORして
最終スタックへ」は、PUSH の回数・POP の順序・`RET` 前にスタックが復元されるか
（`JSR` の戻り番地と同一スタックを共有するため、1回でも過不足があれば暴走する）が
確認できず、§5.1 の未決事項がそのまま残っている。

**要求**: v0.2 では符号処理を含む**全命令列**を擬似コードではなく確定コードとして記述すること。
併せて各分岐経路（正常／ゼロ除算）でのスタック収支が ±0 であることを明記すること。

---

### B-2【設計最適化】`PUSH X` するが X を使用していない。符号フラグの X レジスタ保持を推奨

**該当**: §3.2、§3.3、§3.4、§5.1

§3.2 は「X レジスタは `_fdiv` 同様 callee-save（PUSH X ... POP X）で扱う」とし、
§3.3/§3.4 も入口 `PUSH X` / 出口 `POP X` を置いているが、擬似コード本体で **X を一切使用していない**。
このままでは純粋なデッドコード（バイト・サイクルの無駄）となる。

**推奨案**: 符号フラグを **X レジスタで保持**する。

根拠：実源の減算ループ本体（`_cc_div` L3901-3911、`_cc_mod` L3926-3933）は
`LDW / CMP / BLT / SUB / STW / ADDI / JMP` のみで構成され、**X を使用しない**ことを確認済み。
したがってループを跨いで X に符号情報を保持できる。これにより:

- §5.1 の未決事項（スタック深さ管理、呼出元退避との混同）が**構造的に消滅する**
- `PUSH X` / `POP X` が callee-save として**正当な意味を持つ**
- `_cc_div` は `sign(A) XOR sign(B)` を X に、`_cc_mod` は `sign(B)` のみを X に置けばよく、
  両者で同一構造となり保守性が上がる

実装可能性：`hasm23_v1_04.c` L268-271 で `parse_reg` は "X" を受理し、ALU/比較系命令は
`rD` を汎用に取るため `CMPI X,#0` / `XOR X,A` / `MOV X,A` はアセンブル可能と見込まれる。
ただし**実際にアセンブル・emu23 で動作することを実装初期に確認**すること（未検証事項）。

**代案（併記可）**: `_cc_mod` については `_C_DIV_Q`（$DBFE）が未使用のため
（A-3補足参照）、符号フラグをここに置く手もある。ただし `_cc_div` 側は Q を商に使うため
両者で構造が非対称になる。X保持案を第一推奨とする。

---

### B-3【算術誤記】§2.2 期待値表の「検算」列に符号誤り2件

商・剰余の**期待値そのものは全ケース正しい**（C99準拠を確認）。検算列の表記のみ誤り。

| 行 | 現記載 | 正 |
|---|---|---|
| `-7 / -2` | `6-1=-7` | `(-7/-2)×(-2) + (-7%-2) = 3×(-2) + (-1) = -6-1 = -7` |
| `100 / -7` | `-98+2=100` | `(100/-7)×(-7) + (100%-7) = (-14)×(-7) + 2 = 98+2 = 100` |

いずれも「(a/b)×b」の符号を取り違えている。期待値表は実装後の突合せ基準となる文書であり
（§2 冒頭「実装からの生成禁止」原則の対象）、検算列の誤りは基準の信頼性を損なう。**要修正**。

### B-4【引用誤り】§1.2 の注釈が逆。§1.4 の説明も誤解を招く

**§1.2 の引用コード**:
```
_ccdiv_loop:
    LDW  A, [_C_DIV_B]      ; ← 除数     ★誤り
    LDW  B, [_C_DIV_A]      ; ← 被除数   ★誤り
```
直前で `STW A,[_C_DIV_A]`（A=除数）、`STW B,[_C_DIV_B]`（B=被除数）としているため、
ロード結果は **A ← 被除数、B ← 除数** が正しい。注釈が完全に逆。
なお実源 L3902-3903 に該当コメントは存在せず、**本設計書で付加された注釈**である。

**§1.4 の記述**: 「命名Aと変数レジスタが入れ替わる点に注意」は現象の説明として不正確。
正しくは「**レジスタ名 A/B と ワーク変数名 `_C_DIV_A`/`_C_DIV_B` は対応しない**
（`_C_DIV_A` = 除数、`_C_DIV_B` = 被除数）」。実装者が最も踏みやすい落とし穴であるため、
表現を厳密にすること。

### B-5【網羅性】§2.2 期待値表に境界・追加ケースが不足

以下を追加すること。

| 追加ケース | 目的 |
|---|---|

## 4. C級指摘（推奨・記録）

### C-1【別件起票推奨】減算ループの計算量 O(商)

§3.1 の案比較は 案A（減算ループ維持）と 案B（`_fdiv` の24bitシフト減算へ全面置換）の2案のみで、
**16bit シフト減算（restoring division）案**が検討されていない。減算ループは反復回数が商に比例し、
`32767 / 1` で 32767 反復に達する。シフト減算なら 16 反復固定である。

今回は「1変更1検証」原則から案A採用は妥当と判断するが、A-2 で述べたとおり Dhrystone の
`print_num` は `n/10`・`n%10` を桁数分回すため**実測サイクルへの影響が確実にある**。
性能改善は**別件（v2.09以降）として起票**し、本書 §3.1 に「案C：16bitシフト減算（今回不採用・
性能課題として別件起票）」を追記しておくことを推奨する。

### C-2【仕様明記】ゼロ除算時の 0 返しは実装定義動作

C99 ではゼロ除算は未定義動作である。0 を返す設計自体は実用上妥当だが、
「scc23 の実装定義動作としてこれを採用する」と設計書に宣言し、
`scc23_Functional_Spec` への反映（改版）を §3.5 影響範囲または §5 に記載すること。

### C-3【将来制約】unsigned 型は未実装

実源 `scc23_v2_07.c` L546 に「bool/unsigned型実装時に追加する」とあり、現状 unsigned は未実装。
本設計は全オペランドが符号付きであることを前提に成立している。将来 unsigned を実装する際は
`_cc_div`/`_cc_mod` を符号付き／符号なしで分岐させる必要がある旨を「将来の制約」として明記推奨。

### C-4【軽微】引用行番号のズレ（KY41観点）

| 設計書記載 | 実源 |
|---|---|
| §1.2 `_cc_div` L3892-3938 | L3894-3918 |
| §1.2 `_cc_mod` L3921-3938 | L3923-3937 |
| §3.5 呼出元 L2820-2834 | `JSR` は L2825（div）/ L2833（mod） |

実害は無いが、「台帳と実態の整合を維持する」KY41 の精神に倣い正確を期すこと。

### C-5【体裁】改訂履歴表のセル内改行

「改訂履歴サマリ（KY41）」の v0.1 行がセル内で生の改行を含んでおり、Markdown テーブルとして
レンダリングが崩れる。1行に収めるか `<br>` を使用すること。

§5.1 の1項目目に韓国語（「명시적…」）が混入している。「明示的に」へ修正のこと。

### C-7【用語】「`_fdiv` の符号分離を移植」は不正確

§3 表題および §3.1 は「`_fdiv` の符号分離を移植」とするが、`_fdiv` は符号フラグを
**ワーク領域（`_C_DIV_B` = WSIGN）で保持**する方式であり（実源 L4063）、本設計が採る
スタックまたは X レジスタ保持とは**保持媒体が異なる**。§5.1 自身がこの差異を認めている。
「`_fdiv` と**同等の符号分離方式を、減算ループ構造へ新規適用**する」等、正確な表現に改めること。
