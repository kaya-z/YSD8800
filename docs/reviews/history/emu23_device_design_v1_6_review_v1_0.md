## 0. 総評

設計の**方向性は妥当**であり、特に以下は高く評価する。

- 「デコード層の新設」と「既定値の変更」を峻別し、B-C-1a / B-C-1b / B-C-2 に**分離導入**する方針（切り分け可能性の確保）。
- `$FFFF` が `IDX_NIL` と衝突するという**実機忠実性の副作用を自ら発見し、検知機構（§4.3）で補償**する構成。実機にできない仕事をエミュレータの責務とする整理は正しい。
- §10 で **RTL 側も実機と食い違っている**ことを突き止め、案Q（軸A冒頭で追随）として実施時期まで縛った点。「台帳に記録して保留」を明示的に却下した判断は妥当。
- 実源照合の姿勢。本レビューで以下を再照合し、**記載どおりであることを確認**した。
  - `ysd8800_mmio_stub_v0_7.sv` L458 = `else mmio_rdata = 8'h00; // V3スタブ挙動` → **一致**
  - `emu23_v111.c` L599 / L619 / L694 = UART_BAUD 実装（16bit のみ）→ **一致**
  - `emu23_v111.c` L827 = `rd8` で UART_BAUD を扱わない旨のコメント → **存在を確認**

一方で、**章番号の相互参照が広範に壊れている**（M-1）ほか、**絶対ゲートの対象物が取り違えられている**（M-3）、**検証項目が原理的に成立しない**（M-4）、**新設層の実装仕様（擬似コード）が無い**（M-6）など、このまま実装に渡すと解釈のブレと検証の空振りを生む欠陥がある。

### M-2 「§3.5 既述の方針」は誤参照（UART_BAUD の 8bit 対象外根拠）

§4.1 の `$FC86` 行および §4.4.1 の表が、UART_BAUD を 8bit 経路で扱わない根拠として「**本設計書 §3.5**」を挙げている。しかし本設計書の §3.5 は「IRQ2優先選択（v1.4 クローズ）」であり、UART_BAUD とは無関係である。

実源 `emu23_v111.c` L827 のコメントは

であり、ここでいう「仕様書」は **YSD8001 UART 設計書**（`ysd8001_uart_design_v1_2.docx`）を指すと解される。

**是正**：参照先を `ysd8001_uart_design_v1_2.docx §3.5` に訂正する。あわせて、当該設計書に本当に「8bit 対象外」の規定が存在するかを実源照合し、無ければ**本設計書 §4.4 で新たに規定**すること（コメントが唯一の根拠という状態を残さない）。

### M-3 §11.1 絶対ゲートで 2 つの成果物が取り違えられている

§11.1 の 2 行目は「`yuios.bin` / 56,416 B / md5 `599a7f9d1ebf103f81f58450ea1b6491`」に対し、備考として `build_road2.sh` を挙げている。

実源 `build_road2.sh` L16 は `BIN="yuios_road2.bin"` であり、**このスクリプトが生成するのは `yuios_road2.bin`（md5 `9769f...`）** である。`yuios.bin`（md5 `599a7...`）は別ビルドの成果物であり、両者は**サイズが同一（56,416 B）であるためにかえって混同しやすい**。

**是正**：2 行に分離し、それぞれ「生成スクリプト／ファイル名／サイズ／md5」を対応付けて記載する。3 行目の `-q` 出力ゲートは `yuios_road2.bin` を使うと明記されているため、そちらとの対応も明確にすること。

> **KY 観点**：サイズが同じで md5 が違う 2 つの成果物が絶対ゲートに並ぶ構成は、照合ミスの温床である。ゲート表に**生成コマンドを列として持たせる**ことを推奨。

### M-4 §4.3.2（`-q` で警告抑制）と §11.3 BC-5（`-q` で警告 0 件を確認）が矛盾し、検証が成立しない

- §4.3.2：警告は「`quiet_mode`（`-q`／`-it`）では**抑制する**」
- §11.3 BC-5：「通常の YUI OS 起動（**`-q`**）で**警告が 1 件も出ないこと**」

抑制されている以上、BC-5 は**何を実装しても必ず PASS する空振り試験**である。「BC-5 は本改修の副次的価値が最も現れる項目」と自ら位置づけているだけに、この矛盾は致命的である。

**是正案（いずれかを選択し明記）**：

1. BC-5 を **`-q` 無し**で実施する（ただし `-q` 無し起動の出力を別途基準化する必要あり）。
2. §4.3.3 の**総数サマリのみは `quiet_mode` でも `stderr` に出力する**と規定し、BC-5 は「サマリが 0 件であること」で判定する。**本レビューはこちらを推奨**（`-q` の stdout byte-exact ゲートを壊さず、かつ検知能力を保てる）。

いずれにせよ、§4.3.3 の「総数サマリ」の**出力先と quiet_mode 時の挙動**を明文化すること（現状は未定義）。

### M-5 段階定義が §4.2.4 と §11.2 で食い違っている

**是正**：§4.2.4 を §11.2 と同一の 5 段に統一する（あるいは §4.2.4 を廃し §11.2 に一本化し、§4.2.4 からは参照のみとする）。**同じ情報を 2 箇所に持たない**ほうが改版時の劣化に強い。

### M-6 デコード層の実装仕様（擬似コード・関数分界・判定順序）が無い

§2.3.2 は「責務」を、§2.3.3 は「原則」を述べるが、**実装者が書くべきコードの形が定義されていない**。kaizen の設計原則「設計書の擬似コードに他変数への副作用を明記する」に照らし、少なくとも以下を規定すべきである。

1. **関数分界**：デコード層を新関数（例 `mmio_decode(addr, size, is_write, *val)`）として設けるのか、`rd8/rd16/wr8/wr16` の各先頭にインライン挿入するのか。§2.3.3 は「既存 `if` チェーンの**外側**に設ける」としか述べておらず、4 経路に同じコードを 4 回書く実装を招きうる。
2. **判定順序**：`MMIO 空間判定 → 既存デバイス if チェーン → 未接続処理` の順序と、**各段の戻り規約**（ヒット／ミスの表現）。
3. **フォールスルー廃止の範囲**：B-C-1a 時点では「応答は現行維持（`mem[]` フォールスルー）」とあるが、**デコード層はヒット/ミスを判定しつつ、ミス時は従来どおり `mem[]` に流す**という二重状態になる。この過渡状態の擬似コードを明示すること。
4. **副作用の記述**：ラッチ・自動インクリメント・W2C を伴うレジスタが、デコード層のどの段で発火するか。

**是正**：§2.3 に擬似コード節（§2.3.4）を新設する。

### M-9 §4.4（8bit 経路の被覆漏れ解消）に対する**肯定側の検証項目が存在しない**

しかも §11.1 の絶対ゲート（Dhrystone／yuios）は、§4.4.1 自身が述べるとおり「**全ドライバが 16bit アクセスを行っている**」ため、**8bit 経路の修正が正しいか否かを一切証明しない**。すなわち B-C-1a-2 は「回帰は通るが、直したものが直っている証拠が無い」状態で完了扱いになりうる。

**是正**：以下を §11.3 に追加する（KY54 に従い否定ケース先行）。

| ID | 内容 | 期待結果 |
| --- | --- | --- |
| BC-8N | **改修前**の emu23 で、YSD8002/8003/8004 レジスタに 8bit アクセスする PoC を実行 | デバイスに届かず `mem[]` の値が返る＝**現行欠陥の再現** |
| BC-8P | 同 PoC を改修版で実行 | 16bit アクセス時と**同一の値・同一の副作用回数**が得られる |

## 2. C（要確認：回答次第で M に昇格）

### C-1 「警告は既定で有効」と「B-C-1a の既定は現行維持」の関係

§4.3.2 は α（警告ログ）を**既定で有効**とする。一方 §4.2.4 は B-C-1a の既定動作を「現行維持（`mem[]` フォールスルー）」とする。

- B-C-1a-1 の時点で、**フォールスルーさせつつ警告だけは出す**のか。
- 出すのであれば、`-q` を付けない実行（**Dhrystone 回帰はどうか**）で標準エラー出力に差分が生じる。§11.1 のゲートは 3 値一致のみを見るため実害は無いと思われるが、**判定手順として明記**が必要。

**回答願う**：α の有効化タイミングは B-C-1a-1／1b／2 のどこか。

### C-2 実装済／未接続の境界をまたぐ 16bit アクセスの扱い

§4.1 表では MCR が `$FF10`（1 バイト幅、`$FF11` 以降は予約＝未接続）である。この場合 **`$FF10` への 16bit 読出は、下位＝実装済・上位＝未接続の「部分ヒット」**となる。§4.2.2 は「16bit 読出＝`$FFFF`」としか規定しておらず、部分ヒットが未定義である。

**回答願う**：(a) 部分ヒットは 16bit ヒットとみなし上位を `$00` とするか、(b) `$FF` を合成して `$FFxx` を返すか、(c) MCR を 16bit 幅と再定義して部分ヒット自体を消すか。RTL（`hit_mcr`）の実装形と揃えるのが望ましい。

### C-3 8bit 有効レジスタの上位バイト読出値

`$FCAA` SD_DATA は「8bit 有効」の 16bit レジスタである。**`$FCAB`（上位バイト）への 8bit アクセス**の応答が未定義。

**回答願う**：`$00` を返すか、未接続扱いで `$FF` か。また §4.4.3 の規定により副作用（BUF_PTR 自動インクリメント）は発動しないと解してよいか。

### C-4 §4.4.3「副作用は下位バイト読出で発動」の順序依存

`CYCLE_LO`（`$FC96`）を **上位バイト（`$FC97`）→下位バイト（`$FC96`）の順**で読んだ場合、上位バイト読出時点では `CYCLE_HI` がラッチされていない。この順序で読むコードは一貫性を失う。

**回答願う**：「バイト読出時は必ず下位から」という**利用側規約**として明記するか、あるいは「上位バイト読出でもラッチはするが、下位バイト読出でのみカウンタ副作用を発火」といった分離規定を置くか。

### C-5 「書込を捨てる」範囲にプログラムロード経路が含まれないか

§4.2.2 は未接続領域への書込を捨てると規定する。**バイナリロード・`--disk` イメージ配置・デバッガのメモリ書換が `wr8`/`wr16` を経由する実装**であれば、これらの書込も捨てられ、意図せぬ挙動を生む。

**回答願う**：ロード経路が `mem[]` 直接書込であることの実源確認結果。経由する場合は、デコード層を**バイパスするロード専用経路**を設ける旨を設計に追加すること。

### C-6 `--bus-pullup` と `--strict-mmio` の組合せ規定

`--strict-mmio` 単独指定（`--bus-pullup` なし＝フォールスルー既定）の場合、未接続アクセスで**停止するのか、値はフォールスルー値なのか**が未定義。B-C-2 で既定がプルアップに切り替わった後、`--bus-pullup` オプションを**残すのか廃止するのか**も未記載。

**回答願う**：オプションの状態遷移表（B-C-1b 時点／B-C-2 以降）。

### C-7 §10.5「既知乖離」の記録先台帳

「本節に記録し、軸A での解消をもってクローズとする」とあるが、設計書本文は**参照されなければ発見されない**。`fpga_source_version_ledger` 等、軸A 着手時に必ず開く台帳への相互記載が必要ではないか。

**回答願う**：記録先台帳名と、そこへの記載を B-C 完了条件に含めるか否か。
