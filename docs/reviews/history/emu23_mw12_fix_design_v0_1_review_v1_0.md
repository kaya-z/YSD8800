## 0. 総評

**是正の方向づけと、その根拠の書き方が優れている。** 特に次を評価する。

- **§4.1 で「方向を先に一文で固定する」という手順を踏んだこと。** 「MMU 変換は 3 兄弟で揃える。副作用・課金・警告は 3 兄弟すべてで持たない」——この一文を先に置いたうえで、**逆方向（`mem` を `rd8()` 経由に揃える）を明示的に却下**している。却下理由が「副作用を持つコマンドが 1 個から 3 個に増える。**デバッグで見た値が本番実行を変える**最も再現困難な事故形態を拡大することになる」であり、対称化という一見もっともらしい解が**なぜ悪い方向の対称化なのか**を言語化できている。3 兄弟を揃えるという目標だけを見ていると、揃える先を誤りうる。
- **§2.2 の発見。** 前方一致であるがゆえに `s5` / `b1000` / `mem0400 64` といった**区切り無し引数形式が現に動いている**ことを実源から突き止め、「MW-1 の恒久策が内包する後方互換性の破壊」として方式選定に格上げした。さらに「MW-1 起票時点ではこの点は明示されていない（`kaizen.txt` L3438-3443 は『先頭トークンの完全一致照合へ移行する』とのみ記載）」と**起票内容の不足まで指摘し返している**。起票を鵜呑みにせず実源で確かめる姿勢は KY34 の正しい適用である。
- **§3.4 の衝突検査と §6.1 T-1-5「順序入替え等価試験」。** MW-1 の到達目標を「分岐の順序を入れ替えても結果が変わらないこと」と定義し、それを**実際に順序を入れ替えたビルドで実証する**試験を置いた。目標が検証可能な形に落ちている。`_poc` 付与（KY38）も適切。
- **§4.2 のコメントが `dbg_access` の効力範囲を正確に書いている。** 「★`dbg_access` は課金/統計/トレースしか抑止しない（MMIO 副作用は止まらない）。副作用を止めているのは `phys_rd8()` を使うことである★」——これは前回レビュー C-1 の指摘が正しく内面化された結果である。
- **§9 の却下案記録。** とりわけ「`dbg_access` に MMIO 副作用抑止を追加」を却下した理由——「意味を後から拡張すると、既存 7 箇所の全てに副作用抑止が波及し、`setb` の**意図的な** MMIO 発火まで殺す」——は、フラグの意味を拡張することの危険を具体的な帰結で示している。
- **§6.2 の脚注。** 「T-2-4 の陽性対照が立たない場合、試験が成立していない。その場合は『FIFO が進む』ことをまず別手段で示すまで先に進まない」と、**対照が立たないときの停止条件**まで書いている。

**実源照合結果：§2.3・§2.4 の記述および `phys_rd8()` の引用は正確である。** `phys_rd8()` は L326-329 で `mmu_mode ? phys_mem[pa & 0xFFFFF] : mem[(uint16_t)pa]` であり、`mem_charge()` を通らない——§4.4 の等価性主張（非 MMU 時 `mem` が恒等）は正しい。

**しかし、§2.2 の調査が網羅的でなく、その結果として方式(イ)の前提が成立していない**ことが判明した。加えて MW-2 の兄弟が 1 人漏れている。

## 2. M 指摘（必須是正：2件）

### M-1 ★★重要★★ 【§2.2 / §3.2】区切り無し引数の調査が**数字始まりに限定**されている。方式(イ)は**英字引数を取るコマンドを壊す**

§2.2 は「現在動く入力」として 7 形式を列挙するが、**すべて引数が数字（または `$`）で始まるもの**である。実源には、**引数が英字で始まりうるコマンドが 2 つある。**

**実源1** — `b` コマンド（L3050-3065）：

```c
} else if (cmd[0] == 'b') {
    ...
    char arg[64];
    if (sscanf(cmd + 1, "%63s", arg) != 1) { ... }
    uint16_t addr;
    if (sscanf(arg, "%hx", &addr) != 1) {
        if (!lookup_sym(arg, &addr)) {
            printf("Unknown label: %s\n", arg);
```

**`%63s` で任意文字列を読み、16 進として読めなければ `lookup_sym()` でシンボル解決する。** すなわち **`bmain` と入力すればラベル `main` にブレークポイントを張れる。**

**実源2** — `mmu` コマンド（L3137 / L3152）：

```c
sscanf(cmd + 3, " %31s", sub);
...
if (sscanf(cmd + 3, " ptr %d %x", &n, &v) == 2 && ...
```

サブコマンドは英字である。すなわち **`mmuptr 0 0A`** や **`mmudump`** 等が前方一致で動く。

**方式(イ)の照合規則（§3.3）では、これらはすべて `Unknown command` になる。** `repl_kw(cmd,"b")` は `cmd[1]=='m'`（英字）で NULL を返し、`repl_kw(cmd,"mmu")` は `cmd[3]=='p'` で NULL を返す。

**しかも、これは規則を緩めれば解決する問題ではない。** 仮に「英字も引数開始とみなす」に緩めると、**`bd0` が `b` に食われる**（`d0` をラベル名として解決しようとする）。まさに MW-1 が排除しようとしている事故の再来である。**方式(イ)は原理的に `b <label>` の区切り無し形式を救えない。**

さらに問題なのは、§3.2 の採用根拠3 である。

> 方式(イ)は「キーワードの続きが**英数字であればキーワードの一部**、**数字・`$`・`0x` であれば引数**」という規則で両立する。`setb` と `s`+`etb` の曖昧性は生じない（`etb` は数字でない）

この論証は **「英字で始まる引数は存在しない」ことを暗黙の前提**にしている。その前提が成立していないため、**「両立する」という結論も成立しない。**

**是正要求**：

1. §2.2 の調査を**全 16 分岐について、引数の先頭文字が取りうる文字種**の観点でやり直されたい。列挙ではなく、各分岐の `sscanf` 書式（`%d` / `%hx` / `%63s` / `%31s`）から**機械的に導出**すること。`%s` 系は英字を取りうる。
2. そのうえで、`bmain` / `mmuptr ...` 形式を**壊してよいか**を判断し、設計書に明記されたい。選択肢は次のとおり。

| 案 | 内容 | 評価 |
|---|---|---|
| **イ-1** | 方式(イ)を維持し、**英字引数の区切り無し形式は壊れることを許容**する。`b main` / `mmu ptr 0 0A` と空白区切りで打てばよい | ○ 実用上の影響は小さい。**ただし「後方互換を維持する」という §3.1 の表の主張は撤回**が必要 |
| イ-2 | `b` と `mmu` のみ従来の前方一致を残す特例とする | ✗ 特例が残れば順序依存も残り、T-1-5（順序入替え等価）が PASS しない。**到達目標を自ら壊す** |
| イ-3 | 引数の先頭に区切りを要求する（＝方式(ア)）が、移行措置として旧形式に**警告付きで対応**する | △ 実装が増える。移行期間の管理が必要 |

**推奨は イ-1 である。** §2.2 が挙げた 7 形式（数字始まり）は救われるため、実害はほぼ `bmain` のみに限られる。ただし**「後方互換 ✅ 維持」と書いたまま一部を壊すのは、v0.1 が指摘した「MW-1 起票時点で明示されていない」問題の再生産**である。§3.1 の比較表を「✅ 維持（**数字始まり引数のみ**。英字始まりは方式(ア)同様に破壊）」と正確に改められたい。

3. §6.1 に **T-1-6：`bmain` / `mmuptr 0 0A` の扱いが設計どおりであること**を追加されたい。

> **本件の性質**：これは原則124（レビュー例示は網羅的リストではない）と同型である。v0.1 は §2.2 で「重大な発見」をしたが、**発見した 7 例を全数と扱ってしまった**。7 例は `grep` ではなく観察から得られたものであり、網羅の保証がない。**方式選定という重い判断を、網羅していない調査の上に載せてしまった**点が問題である。

### M-2 【§4.3】MW-2 の兄弟は **4 人**である。CLI `-d` ダンプ（L3719）が漏れている（原則122）

§4.3 は改修対象を `dump_mem()` / `dump_memw()` / `physmem` の 3 兄弟としているが、**同じ欠陥を持つ 4 人目が存在する。**

**実源** — CLI メモリダンプ（L3714-3722）：

```c
if (dump_addr >= 0) {
    printf("MEM[%04X+%d]:", dump_addr, dump_len);
    /* ★v2.13 A-3: CLI 由来アクセス（設計書 §4.1.1）★ */
    dbg_access = 1;
    for (int i = 0; i < dump_len; i++)
        printf(" %04X", rd16((uint16_t)(dump_addr + i*2)));
    dbg_access = 0;
    printf("\n");
}
```

**`rd16()` 経由である。** したがって `memw` とまったく同じく、**MMIO 副作用（UART FIFO 前進）と未マップ警告を持つ。** v2.13 で `dbg_access` に包まれたが、それが抑止するのは課金・統計・トレースのみである——**§4.2 のコメントが自ら述べているとおり**である。

§4.1 の方向「**副作用・課金・警告は 3 兄弟すべてで持たない**」を掲げながら、同じ経路・同じ欠陥を持つ CLI `-d` を対象外にすると、**是正後も `emu23 prog.bin -d FC80` で UART FIFO が進む**。

**構造的にはさらに悪い。** CLI `-d` は `dump_memw()` を呼ばず**独自ループで同じことをしている**。つまり「ワード単位メモリダンプ」が **2 実装存在する**。原則122（兄弟実装は同時確認）の対象そのものである。

**是正要求**：

1. §4.3 の表に **4 人目として CLI `-d`（L3714-3722）** を追加し、`rd16()` → `dbg_rd8()` 合成に改修されたい。
2. あわせて、**`dump_memw()` を呼ぶ形に統合できないか**を検討されたい。統合すれば実装が 1 つになり、以後の改修で片方だけ直す事故が構造的に消える。出力書式が異なる（`MEM[%04X+%d]:` の 1 行形式 vs `dump_memw()` の複数行形式）ため単純置換はできないが、**内側のワード取得だけを共通ヘルパにする**ことは可能である。統合しない場合は、その判断理由を残されたい。
3. §4.4 の記述「`dump_mem`/`dump_memw` は REPL 専用であり `-q` では呼ばれない」は正しいが、**CLI `-d` は `-q` と併用されうる**。`-d` の出力経路を変更する以上、**G-4（`-q` stdout byte-exact）への影響を評価**されたい。非 MMIO 帯・非 MMU では恒等のはずだが、`-q -d` の組み合わせを実際に確認すること。
4. §6.2 に **T-2-7：CLI `-d FC80` で UART FIFO が進まないこと**を追加されたい。

> **なぜ見落としたか**：MW-2 の起票文言が「`mem` / `memw` / `physmem` の非対称是正」と**REPL の 3 コマンド名で書かれていた**ためと推測する。起票の文言を対象範囲として受け取ると、同じ欠陥を持つ別経路が視野から外れる。**「どのコマンドか」ではなく「どの関数経由か」で対象を定義する**と漏れにくい。v0.2 レビューの A-1〜A-3 では `-d` が正しく捕捉されていた（A-3）ことから、**前回捕捉できていた対象が、今回の起票文言によって落ちた**という経緯が見える。

## 3. C 指摘（確認・明記要求：4件）

### C-1 【§4.2】`dbg_rd8()` 内の `dbg_access` 操作は**冗長**であり、ネスト時の解除事故を招く

`dbg_rd8()` は `mmu_translate()` と `phys_rd8()` しか呼ばない。`phys_rd8()` は L326-329 で配列を直読するのみで、**`mem_charge()` を通らない**。したがって **`dbg_access` を立てる意味がない。** §4.2 のコメント自身が「副作用を止めているのは `phys_rd8()` を使うことである」と述べており、認識はあるはずである。

**冗長なだけでは済まない理由が 2 つある。**

1. **ネスト解除**。v2.13 には `dbg_access = 1 ... = 0` の区間が 7 箇所ある。将来それらの内側から `dbg_rd8()` が呼ばれると、**内側の `= 0` が外側の抑止を解除する**。以後そのブロックの残りは課金されてしまう。
2. **評価順序依存**。§4.3 の `(dbg_rd8(a+1) << 8) | dbg_rd8(a)` は、`dbg_rd8()` がグローバル変数を書き換えるため**副作用を持つ式が 1 つの式に 2 回現れる**形になる。現状は結果が変わらないが、清潔ではない。

**要求**：次のいずれかを採り、理由を §4.2 に明記されたい。

| 案 | 内容 |
|---|---|
| **a（推奨）** | `dbg_access` 操作を**除去**する。`phys_rd8()` が課金経路を通らないことが保証であり、フラグは不要 |
| b | `int save = dbg_access; dbg_access = 1; ... dbg_access = save;` と**退避・復元**にする |

案 a を推奨するが、その場合は「**なぜ `dbg_rd8()` にフラグが不要なのか**」をコメントに残すこと。フラグが無いことが「付け忘れ」に見えると、後日誰かが親切に足してしまう。

### C-2 【§6.2 T-2-4】陽性対照の**実証手段**が具体化されていない

§6.2 の脚注は「T-2-4 の陽性対照が立たない場合、試験が成立していない。その場合は『FIFO が進む』ことをまず別手段で示すまで先に進まない」と正しく警告している。**しかし、その「別手段」が何かが書かれていない。**

REPL に UART 受信 FIFO の残量を表示するコマンドは存在しない（`regs` / `mem` / `memw` / `physmem` / `mmu` のいずれも該当しない）。段0 で対照を採ろうとした時点で手段が無く止まる恐れがある。

**要求**：段0 に着手する前に実証手段を確定されたい。候補：

- UART の状態レジスタ（受信データ有無ビット）を `physmem` で観測する（物理直読なので副作用がない）
- `_poc` 版に FIFO 残量を出力するデバッグ printf を一時的に入れる（KY38）
- 既知バイト列を UART 入力に与え、`memw $FC80` を N 回叩いた後にプログラムから読んで**先頭が N 個進んでいる**ことを確認する

いずれにせよ、**観測手段そのものが FIFO を進めない**ことを先に確かめる必要がある。

### C-3 【§4.5】失われる「未接続バスの見え方」の**代替手段**を示されたい

§4.5 は `mmio_report_unmapped()` の警告と `bus_pullup_enabled` 時の合成が失われることを明記し、「**実行経路（プログラムから読む）で確認する必要がある**」としている。判断（Q-3：許容）は支持するが、**代替手段がプログラムを書くことだけだと §1.2 の問題に戻る**——`emu23_memwrite_design` §1.2 は「テスト用 asm を都度作成」を「KY38 の `_poc` ファイルが増え続ける」問題として挙げていた。

バスプルアップは `emu23_device_design` v1.8 で意図的に実装した機能であり、**その挙動を観測する手段が失われる**のは軽くない。

**要求**：次を §4.5 に追記されたい。

1. `physmem` では物理直読のため合成前の値が見える（＝プルアップの効果は見えない）ことの明記
2. 代替観測手段が必要と判断する場合は、**MW-6 として起票**（例：MMIO 帯を実機同等の経路で 1 回だけ読む専用コマンド `peek`）

「失われることを許容する」で終わらせず、**失った機能の受け皿をどうするかまで**記録しておくと、後日「なぜ見えないのか」で調査が発生しない。

### C-4 【§3.5】`?` の扱いに `repl_kw()` を使うと**数字直後を許容してしまう**

§3.5 の特記は「`help` は `repl_kw(cmd,"help") || repl_kw(cmd,"?")` とする。`?` は数字直後を許容しても実害なし」とする。実害が無いのは同意するが、**`?` は 1 文字であり、`?5` のような入力が `help` として通る**。

より重要なのは、`?` に `repl_kw()` を使うと **「`?` の直後が英字なら不一致」** となる点である。`?help` のような入力は現状 `cmd[0]=='?'` で通るが、方式(イ)では通らなくなる。実害は無いと思われるが、**§2.2 と同じ「調査していない入力形式」**である。M-1 の再調査（全 16 分岐の引数文字種）の際に併せて確認されたい。
