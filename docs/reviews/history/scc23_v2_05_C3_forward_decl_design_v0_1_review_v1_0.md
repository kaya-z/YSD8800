## 総評

調査の**過程**（PoC 実測・バグ位置の1次ソース照合・案A/B/C の比較）は丁寧で、案B（2パス化）却下の判断も妥当。しかし**結論が実ソースの事実と逆**になっており、その結果、採用候補の案C が本設計書のゴール（C-3 の修正）を達成しない。以下 C-1 が最重要。

## C-1【致命】§1.3「型伝播は既に正しい」は実ソースと矛盾。採用候補・案C は値破壊を修正しない（ゴール未達）

### 事実（`scc23_v2_04.c` `binop_promote` の実挙動）

PoC `x = getval() + 1.0`（`getval` プロトタイプ未定義）の型昇格経路を実ソースで追うと:

```c
static sir_node_t *binop_promote(sir_op_t int_op, sir_node_t *l, sir_node_t *r) {
    int lf = l && l->type==T_FLOAT;   // l = getval() の SIR_CALL。未定義→ type=T_INT → lf=0
    int rf = r && r->type==T_FLOAT;   // r = 1.0 → T_FLOAT → rf=1
    if (!lf && !rf) { ... }           // rf=1 なので通らない
    /* どちらかfloat -> 両辺floatへ昇格 */
    l = wrap_i2f(l);   // ★ T_INT扱いの getval() に I2F(<<8) を挿入 ★
    r = wrap_i2f(r);   // 1.0 は既にfloat → 素通り
    ...
}
```

`wrap_i2f` は「`n->type==T_FLOAT` でなければ I2F を挿入」する。`getval()` は未定義ゆえ `T_INT` 扱いなので、**実際には既に Q8.8 の戻り値（0x0280=2.5）に `LDW B,#8 / SHL A,B` が挿入され 0x8000 に破壊される**。これは設計書 §1.1 PoC と一致し、**バグは実在する**。

### 矛盾点（設計書内の論理破綻）

- §1.3 の結論「**コンパイラ側の型伝播ロジックは既に正しい。真の課題はユーザに気づかせる手段**」は**誤り**。型伝播は未定義関数を `T_INT` と誤伝播し、それが `wrap_i2f` による I2F 二重昇格＝値破壊の直接原因になっている。「既に正しい」ロジックではない。
- §2.4 採用候補・案C は「**型伝播ロジックは変更せず warning 出力のみ**」。これは**警告を出すだけで 0x8000 の値破壊を一切修正しない**。§1.1 の PoC が示す壊れた asm（`LDW B,#8 / SHL A,B` 挿入）は案C 適用後も**そのまま生成される**。

### なぜ致命か

本設計書のゴール（§0.1）と文書名は「**C-3 型伝播修正**」である。しかし採用候補の案C は型伝播を修正せず、**バグの修正を「警告表示」に置き換えている**。設計書 §9（一次情報）は C-3 を「潜在バグ」「**実害が出る前に対処すべき**既知の制約」と位置づけているが、案C は実害（値破壊）を放置したまま警告を出すだけで、「対処」になっていない。**ゴール未達**。

### C-1 は 1パスのまま解決可能（実ソースで確認済・却下の前提が崩れる）

案B（2パス化）却下は妥当だが、「2パス化 vs 警告のみ」の二者択一が誤り。**1パスのまま局所修正で値破壊を止められる**ことを実ソースで確認した:

- 値破壊の唯一の発生点は `binop_promote` 内の `l = wrap_i2f(l)` / `r = wrap_i2f(r)` が **型不明（未定義関数由来）の T_INT ノードに I2F を挿入する**ことである。
- したがって修正は、**「型が信頼できない SIR_CALL（未定義関数）を float 文脈で使う場合の扱い」**を局所的に是正すればよい。2パス化不要。

**対応案（主候補を差し替え）**:
1. **（推奨・fail-safe）未定義 float 文脈エラー化**: 未定義関数呼び出しの戻り値が float 演算に巻き込まれる（`binop_promote` の float 経路に未定義 `SIR_CALL` が入る）場合、警告ではなく **error で停止**し、壊れたコード生成自体を防ぐ。ユーザはプロトタイプ追加を強制される。最小改変で値破壊を確実に阻止。
2. **（代替）前方宣言の型記録**: §7.2 の `defined` フラグ問題（後述 M-1/N-1）を解消し、**プロトタイプ宣言の戻り値型を SC_FUNC に正しく記録**すれば、前方 float 関数も正しく型伝播し C-3 が根治する。1パスでもプロトタイプさえあれば型は取れる（現に「プロトタイプありなら発現しない」と §1.2 が認めている）。真の課題は「プロトタイプを書いても `defined=1` の扱いで型記録が濁る」点（§1.3 が自認）であり、そhere を直すのが本筋。
3. 案C（warning）は**上記1または2との併用の補助**としては可。ただし**単独では C-3 を解決しない**ことを明記。

§1.3 の「型伝播は既に正しい」を撤回し、「未定義関数を T_INT 誤伝播 → float 文脈で I2F 二重昇格 → 値破壊」と事実に修正すること。

## M-1【必須】案B 却下の議論に「1パス局所修正」の中間案が欠落

**箇所**: §2.1 候補案表、§2.2 案B 却下根拠

**問題**: 案の比較が「案A（何もしない＋文書）／案B（2パス化・大改造）／案C（警告のみ）」の3択で、**「1パスのまま I2F 誤挿入だけを局所的に止める中間案」が存在しない**。C-1 対応案1・2 はいずれも 2パス化せずに値破壊を止める。案B を「リスク過大」で却下した論理は正しいが、それは「2パス化しない＝警告のみ」を意味しない。

**対応案**: §2 に中間案（C-1 対応案）を追加し、案C 単独を主候補から降格。本体改変は「軽微〜中」で、Dhrystone は float 非使用のため絶対ゲートに影響しない（値破壊修正は float 経路のみ触るため）。

---

## N-1【推奨】§7.2 の `defined` フラグ問題は「将来課題」でなく本修正の本丸

**箇所**: §7.2（申し送り）、§1.3

**問題**: §7.2 は「L4300 で `fs->defined=1` を先に立てるため、宣言のみと本体定義済の区別がつかない」を将来課題としている。しかしこれは C-3 の**根治（前方宣言の型を正しく記録する機構）に直結**する。プロトタイプ宣言の戻り値型が正しく SC_FUNC に記録されれば、前方 float 関数呼び出しも正しく型伝播し、値破壊は原理的に起きない。

**対応案**: `defined` フラグ問題を「将来課題」から**本修正のスコープ候補（C-1 対応案2）**へ格上げして検討。少なくとも「案C（警告）だけで済ませ、根治は将来」という構成は、§9 の「実害が出る前に対処」に照らして弱い。

---

## 対応優先度

1. **C-1**（案C 単独では値破壊を直さない事実を認め、1パス局所修正＝未定義float文脈のerror化 or 前方宣言型記録を主候補に据える。§1.3 の誤結論を撤回）
2. **M-1**（中間案を案比較に追加、案C を補助へ降格）
3. **N-1**（`defined` フラグ問題を根治候補として本スコープで検討）

これらを反映し、設計を「値破壊を実際に止める最小修正（＋警告併用）」へ再構成すれば、C-3 修正設計として承認可能な段階に至る。現状の案C 単独構成は、文書名（型伝播修正）とゴール（実害対処）に対して**修正の実体を欠く**ため、実装着手前の再設計が必須。

---

## 補足: 調査の過程は良い

PoC で壊れた asm（`LDW B,#8 / SHL A,B` 挿入）を実測し、バグ箇所を L1868-1898 に特定し、案を比較した過程は丁寧である。惜しむらくは、その PoC が示す「値が壊れる」事実と、§1.3 の「型伝播は既に正しい」という結論が正面から矛盾している点を、設計書自身が拾えなかったことである。PoC が壊れるなら型伝播は正しくない——この単純な突き合わせ（kaizen: 実測と結論の整合確認）を一度行えば、案C 単独では不十分と気づけたはずである。実ソース `binop_promote` の `wrap_i2f` 二段呼び出しが値破壊の機序であり、そこを局所修正すれば 2パス化なしで直る。
