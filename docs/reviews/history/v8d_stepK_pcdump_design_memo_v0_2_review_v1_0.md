## 4. 指摘1（必修正）: エピソード開始 cyc の観測抜け

### 該当箇所

§3.2 擬似コード全体（イベント発生ブロック＋毎cyc動作ブロックの構造）

### 懸念の詳細

擬似コードを SystemVerilog として素直に実装すると、以下のような構造になる：

```systemverilog
while (dbg_halt !== 1'b1 && to_cyc < max_cyc) begin
    @(posedge cpu_clk);
    to_cyc = to_cyc + 1;

    // [イベント発生] PC変化検出 case
    if (dbg_pc !== pc_prev) begin
        case (dbg_pc)
            16'h2610: begin
                k_dump_active <= 1;   // ← ノンブロッキング？ブロッキング？
                k_dump_cnt    <= 0;
                k_episode     <= k_episode + 1;
                $display("★[STEPK ep=%0d] L0140到達...", k_episode);
            end
            ...
        endcase
        pc_prev = dbg_pc;
    end

    // [毎cyc動作]
    if (k_dump_active) begin
        k_dump_cnt++;
        $display("  [K ep=%0d n=%0d cyc=%0d] PC=%04h ...", ...);
        ...
    end
end
```

**問題:** `k_dump_active <= 1` がノンブロッキング代入だと、**同一 cyc の「毎cyc動作」ブロックの `if (k_dump_active)` は false のまま**（次のtime step でのみ 1 になる）。その結果：

- PC=$2610 到達 cyc（エピソード開始 cyc）の生ダンプ 1 行が **抜ける**
- 次 cyc から `n=1` として dump 開始されるが、これは PC=$2610 の 2 cyc 目に相当

一方、`k_dump_active = 1`（ブロッキング）にすれば同一cycで dump ブロックに入るが、次に「その cyc は case で開始メッセージも出て、なおかつ毎cyc dump も 1 行出る」となり、**同一cyc に2行出力**の可能性がある。

**θ1b（LDW writeback バグ）を狙う場合、エピソード開始 cyc = PC=$2610 到達直後こそが最も重要な観測点**。ここが抜けると、次 cyc で既に PC=$248D に飛んでいた場合、writeback バグの発生瞬間を捉え損なう危険がある。

### 修正提案（v0.3 での明記）

以下いずれかを §3.2 に明記：

**案A（推奨・単純）**: `k_dump_active` はブロッキング代入とし、case 文内のエピソード開始メッセージは毎cyc dump と同一cyc に **意図的に併存させる**。ダンプ行の識別は `n=1` で判別可能。読者への説明として §3.3 サンプル出力例の冒頭に「(★開始メッセージ) の直後に n=1 のダンプ行が続く」と明示。

**案B**: `k_dump_active` はノンブロッキングとし、case 文内で **明示的に 1 行 dump を出す**（毎cyc動作と同じフォーマットで、n=0 として）。翌 cyc から通常の n=1 以降が続く。

**案C**: `k_dump_active` をブロッキング化、かつ case 文内のエピソード開始メッセージから状態値ダンプを外し「★L0140到達 — 生ダンプ開始（詳細は次行以降）」のみにする。毎cyc dump 側の n=1 が同一cycで続く。

**レビュア推奨**: **案C**。「★開始マーカ」と「n=1 の詳細行」の役割分担が明快、かつ観測抜けなし。案Aは同一cycに情報が重複、案Bは case とダンプブロックで同じ$display文が2箇所に分散して保守性が落ちる。

## 6. 指摘3（補足）: サンプル出力の LATENCY 整合性

### 該当箇所

§3.3 のサンプル出力例：

```
  [K ep=1 n=1 cyc=123456] ... PSRAM: req=1 we=0 ack=0 addr=0260A wdata=00 rdata=00
  [K ep=1 n=2 cyc=123457] ... PSRAM: req=1 we=0 ack=0 addr=0260A wdata=00 rdata=00
  [K ep=1 n=3 cyc=123458] ... PSRAM: req=1 we=0 ack=1 addr=0260A wdata=00 rdata=F7
```

### 懸念

`ysd8800_psram_ctrl_v0_2.sv` L43 で `LATENCY_NORMAL = 12`（通常時レイテンシ12サイクル）が既定値。命令フェッチや LDW のオペランド読出も含めて req→ack は最短でも 12cyc かかる可能性が高い。

サンプルでは req 1cyc目 → ack 3cyc目に見えており、**実装で得られる実測波形と大きく乖離する可能性**がある。

### 修正提案

案X: サンプル行末に注記「※上記は例示。実際は LATENCY_NORMAL=12 のため req→ack は約12cyc離れる可能性あり」を追加。

案Y: サンプルを実 LATENCY 準拠に書き換える（cyc番号を +12 きざみに）。

いずれでも構わない。読者が「サンプル出力ちょうどでない = TB バグ」と誤診しないよう防止できればよい。
