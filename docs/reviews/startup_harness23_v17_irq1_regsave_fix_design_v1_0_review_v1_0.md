## 4. 指摘1（必修正）: §5.2 検証 TB 案の実源乖離

### 4.1 該当箇所

v1.0 §5.2：

```asm
_main:
    LDW  A, #$1234      ; A に既知値をセット
    LDW  B, #$5678      ; B に既知値をセット
    LDW  X, #$9ABC      ; X に既知値をセット
    ; ここで IRQ1 を意図的に誘発
    STW  something, [$FCB0]   ; IRQ_MASK 経由で IRQ1 発火
    ; IRET 後の A/B/X を検査
    CMPI A, #$1234      ; 保存確認
    BNE  _fail
    ...
```

### 4.2 実源事実

**emu23_v111.c L303**（原文引用）:
```c
#define SD_DISK_HI    0xFCB0  /* DISK_HI:   総セクタ数 上位16bit              */
```

**emu23_v111.c L327**（原文引用）:
```c
#define IRQ_MASK_ADDR 0xFCB4  /* IRQ_MASK: 1=マスク 0=許可                 */
```

$FCB0 は **DISK_HI（総セクタ数上位16bit）** であり、IRQ_MASK ではない。IRQ_MASK は **$FCB4**。

**emu23_v111.c L62-63, L317**（原文引用）:
```
// [YSD8003] SD_CMD=2 (EXEC) 受理時に sd_irq_delay = 512 で予約
//           0 到達時に ysd8004_raise(IRQ_STAT_BIT_STOR)
```

IRQ1 発火は以下の3段階を要する：
1. SD_CMD=0 (READ_SETUP) 書込で LBA 等セットアップ
2. SD_CMD=2 (EXEC) 書込で `sd_irq_delay = 512` セット
3. 512cyc 経過で `ysd8004_raise(IRQ_STAT_BIT_STOR)` 発火

**IRQ_MASK 書込ではIRQ1 は発火しない**。IRQ_MASK は「マスク許可/禁止」のみで、発火自体はストレージ完了イベントに紐づく。

### 4.3 修正提案（v1.1 で §5.2 の TB 案書き直し）

**test_irq1_regsave.asm 概要（正しい版）:**

```asm
; 前提: ホスト側で -d オプションでダミーディスクファイルを与える
;       またはメモリベースの疑似ストレージを設定
;       IRQ_MASK=0 で IRQ1 許可、IE=1 で割込許可

_main:
    ; IRQ許可設定
    LDW  A, #$0000
    STW  A, [$FCB4]     ; IRQ_MASK = 0 (全許可)
    EI                   ; IE = 1

    ; テストレジスタ値セット
    LDW  A, #$1234      ; A に既知値
    LDW  B, #$5678      ; B に既知値
    LDW  X, #$9ABC      ; X に既知値

    ; ★ここから IRQ1 誘発シーケンス（SD_CMD 経由）★
    ; (レジスタ A/B が破壊されるが、それが検証の主眼)
    ; ... 現在の A/B/X をメモリ退避してから SD 操作 ...
    ; 実装案としては、テスト用に別変数に A/B/X 参照値を退避してから
    ; SD_CMD セットアップして完了待ちする形にする

    ; または、より簡潔な方法として:
    ;   ホスト側 emu23 に「N cyc 後に IRQ1 を強制発火」オプションを
    ;   仮に追加する（テスト用フック）

    ; IRET 後（＝IRQ1 ハンドラ復帰後）に A/B/X を検査
    CMPI A, #$1234
    BNE  _fail
    CMPI B, #$5678
    BNE  _fail
    CMPI X, #$9ABC
    BNE  _fail
    HALT ; PASS
_fail:
    HALT ; FAIL（レジスタで区別）
```

**より現実的な代替案（推奨）:**

emu23 の既存機能で IRQ1 を強制発火させる手段が乏しいため、以下の 2 案いずれかを推奨:

**案X1: 実 SD 操作を伴う統合テスト**
- V8-a cat/ls デモの経路を再利用
- ユーザランド側で A/B/X に既知値を仕込み、SD 読出を発行
- IRQ1 完了後の A/B/X を検査
- 実装コストは高いが、実際のストレージ経路で検証できる

**案X2: emu23 にテスト用フック追加**
- emu23 v1.12 に `-tst-irq=<N>` オプション追加（N cyc 後に IRQ1 強制発火）
- テスト用の最小 asm で A/B/X を検査
- ただしこれは emu23 改修を含むため、`emu23_debug_manual` 改版が必要
- スコープが拡大するため、本設計書とは別プロジェクトになる

**案X3（最も現実的）: V8-a cat/ls デモの回帰でのみ検証**
- §5.4 の V4 に統合し、§5.2 の V2 は削除
- 判定は「V8-a cat/ls の出力が修正前と一致すること」
- 直接的な A/B/X 保存の可視化はできないが、退避パターンは `_timer_handler` と同型であり、`_timer_handler` が既に長期間安定動作している実績が間接証拠になる

### 4.4 レビュア推奨

**案X3（V4 統合・V2 削除）を推奨**。理由：
- 本修正の正当性根拠は「`_timer_handler` との対称化」であり、`_timer_handler` の長期安定動作が既にレジスタ保存の間接的証拠になっている
- 直接検証 TB を作るのは魅力的だが、案X1 は工数大、案X2 はスコープ拡大
- 修正案本体（§3.4）は極めてシンプル（6命令追加）で、リスクが低い
- V1・V3・V4 の回帰チェックで実務上十分

もし直接検証を残したい場合は **案X1** を推奨（実運用経路の再現）。

### 4.5 §5.5 判定基準への影響

案X3 採用時、§5.5 の「V2 が『修正前 FAIL / 修正後 PASS』と可視化」の項目を削除。他は変更なし。

## 5. 指摘2〜4（補足）

### 5.1 指摘2: §5.2 内 `STW something` の未定義変数

指摘1と同時に書き直しで解消。個別対応不要。

### 5.2 指摘3: §4.4「+24バイト」の実源根拠明示

現状：

> 増分: **+24バイト**（正確値は hasm23 出力で最終確認）

修正案：

> 増分: **+24バイト**（`hasm23_v1_04.c` L465-483 の LDW/STW サイズ計算関数 `parse_ldw_stw_size` より、`STW rD,[abs]` と `LDW rD,[abs]` は各 1+1+2=4バイト、追加 6 命令で 24 バイトと確定）。

「hasm23 出力で最終確認」の但し書きは削除可（実源から論理的に確定できるため）。

### 5.3 指摘4: §7.4 の `_syscall_handler` 記述

現状：

> `_syscall_handler`（L155-162）は `JMP _harness_dispatch` のみで A/B/X を触らないため、本修正の対象外。

**懸念**: `_syscall_handler` 本体は `JMP` のみだが、その飛び先 `_harness_dispatch` が A/B/X を触る可能性がある。JMP は IRQ ハンドラの継続とみなされるため、`_harness_dispatch` も割込コンテキストで実行される。もし `_harness_dispatch` が呼出元の A/B/X を破壊するなら、それも本バグと同種の問題を持つ。

**修正案**: v1.1 で1文追加：

> `_syscall_handler`（L155-162）は `JMP _harness_dispatch` のみで、飛び先の `_harness_dispatch` も IRQ4 継続コンテキストで実行される。`_harness_dispatch` の実源を確認し、A/B/X を破壊しないこと（または呼出元が承知して呼ぶこと）を確認済。もし破壊するなら同種のバグが存在する可能性があり、別途起票。

これは軽微な補足で、必修正ではない。

## 8. 良かった点

1. **§2.2 IRET 実装の新規一次確認**: バグ指摘書 §7 では触れていなかった「IE 復元経路」を独自に emu23_v111.c L1261-1268 で確認し、退避ワーク共有の安全性根拠を強化。原則76（実源照合）の運用として理想的
2. **§2.4 STW/LDW のフラグ副作用の一次確認**: 「復元シーケンス末尾の LDW X が Z/N を更新するが、IRET で FLAGS 全体復元されるため副作用なし」の解析は、通常のレビューでは見逃しやすい細部を潰しており高評価
3. **§3.3 案B 却下の根拠**: 「本バグ自体が『スタブ実装だから A/B しか使わない → 退避不要』という同種の判断ミスから生まれている可能性が高い」の指摘は洞察が深い
4. **§7.2 規約案の具体化**: バグ指摘書 §7.3 の一般的提案を、具体的な規約文言案として整備している。yuios_design_v2_7.md 追記候補として即座に採用可能
5. **§4.5 「バグが解消される方向に変化する可能性」**: V8-a cat/ls が現状 IRQ1 タイミング依存で偶然通過している可能性への言及は、原則76 の応用として的確
