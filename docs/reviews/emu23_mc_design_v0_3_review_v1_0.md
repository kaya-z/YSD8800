## 2. M 指摘（必須是正：1件・新規）

### M-5 【§4.4 / §6.2】外部定義ファイルに `0x1F` を書くと**サイレントに無視される**（EMU-A と同型の病）

**問題**：

- §4.2 の引き方は `cpu.ir == 0x1F` を**先に**判定して拡張表へ分岐する。したがって **`mc_table[0x1F]` は決して参照されない**。
- §4.4 の主 opcode 表に `0x1F` の行が無く、「上記以外 ｜ `MC_UNDEF`」に落ちる。
- §6.2 の書式は主 opcode キーとして `0xNN` を受理する。ユーザが **`0x1F 8` と書いた場合、パーサは `mc_table[0x1F] = 8` を正常に格納し、エラーも警告も出さないまま、その値は一度も使われない。**

これは「明示的に指定したのに黙って効かない」という、**EMU-A（`--sym` のサイレント誤読）および N-2b（`cyc.txt` のサイレント誤読）とまったく同型の病**である。設計書自身が §7.2 で「サイレント失敗＝EMU-A と同じ病」を排除する方針を掲げている以上、ここだけ穴が残るのは一貫性を欠く。

**是正要求**：次のいずれかを選択し、§4.4 と §6.2 の双方に明記されたい。

| 案 | 内容 |
|---|---|
| **a（推奨）** | パーサで `0x1F` キーを**エラーとして弾く**。`emu23: [-mc] opcode 0x1F is the EXT prefix; use 'X:0xNN' form (line N)` を stderr に出し、その行を無視 |
| b | `0x1F` を予約キーとして受理し、**拡張表全体に一律加算するオフセット**として意味づける（設計が複雑化するため非推奨） |

あわせて §4.4 主 opcode 表に **`0x1F ｜ EXT prefix ｜ —（拡張表へ分岐。主表は参照しない）`** の行を追加し、「上記以外＝MC_UNDEF」に紛れ込まないよう明示されたい。表を読んだだけで 0x1F の扱いが分かる状態にすること。

> **補足**：本件は「実装すれば動くが、ユーザが誤った期待を持つ」類の欠陥であり、動作検証では検出できない。§9.2 に検証項目を追加されたい（例：`C-13 | -mc cyc.txt で '0x1F 8' を指定 | エラー行が出る。黙殺しない`）。

## 3. C 指摘（確認・明記要求：4件）

### C-6 【§3.3】emu23 の BRK は**停止する**。「NOP と同一経路で次命令へ抜ける」は emu23 の挙動と異なる

**実源** — `emu23_v1_14.c` L1706-1710：

```c
case 0x06: /* BRK — デバッグトラップ (§5) */
    // [FIX BUG-1] 単なる break; から停止+通知に変更
    printf("** BRK at %04x **\n", pc0);
    cpu.halted = 1;
    break;
```

§3.3 は「RTL では…**S_FETCH, S_OPFETCH を経て次命令へ抜ける（NOP と同一経路）**。よって CPI = 2」と記す。RTL 側の推論としてはよいが、**emu23 では BRK は `cpu.halted = 1` で停止する**。つまり emu23 上の BRK は、挙動としては NOP ではなく **HALT と同列の「停止命令」**である。

**CPI 値 2 そのものへの実害は無い**（停止後は歩進しないため最終 cycle 値にしか影響しない）。ただし次の 2 点で記述の整合を取られたい。

1. §3.3 に「**emu23 では BRK は停止する**（L1706-1710 `cpu.halted = 1`）。RTL では停止しない。この非対称は emu23 がデバッガであることに由来する既知の差異である」と明記する。
2. §3.2 で HALT を「S_HALT は実在する 1 サイクルゆえ計上する」として **3** にした一方、BRK は **2** としている。emu23 上はどちらも停止命令なのに値が異なるため、**判断基準が RTL 状態連鎖であること**（emu23 の停止有無ではないこと）を §3.3 に一文添えると、後日の「なぜ BRK は 2 で HALT は 3 なのか」という混乱を防げる。

### C-7 【§3.3】RTL の BRK 経路「S_FETCH, S_OPFETCH を経て抜ける」は**推定**である旨を明記せよ

`grep -c "ID_BRK" ysd8800_cpu_v0_1_FIXED.sv` = 0 という事実から言えるのは「**FSM が ID_BRK を個別に分岐していない**」ことまでである。その結果 S_OPFETCH の default 分岐がどこへ遷移するか（S_IRQCHK か、S_EXEC_ALU に落ちて 4 サイクルになるか）は、**default 分岐の実体を読まないと確定しない**。

CPI が 2 か 4 かで最終 cycle 値が変わる。実害は小さい（BRK は停止するため 1 回のみ）が、**「実源で確認した」と「実源から推定した」を混同しない**のが本プロジェクトの規律（KY34）である。

**要求**：次のいずれか。
- (a) S_OPFETCH の default 遷移先を実源で確認し、確定値として記載する
- (b) 「FSM の default 経路の実体は未確認。NOP と同一と**推定**して 2 を採る」と留保を明記する

### C-8 【§4.2】擬似コードに `MC_UNDEF → 既定 4` の置換ロジックが現れていない

§4.2 の引き方は次のとおりで、引いた結果が `MC_UNDEF` だった場合の処理が無い。

```c
if (cpu.ir == 0x1F)  cpi = mc_table_ext[ fetch8(cpu.pc) ];
else                 cpi = mc_table[cpu.ir];
```

§4.3 に規定はあるが、**§4.2 が「実装が参照する擬似コード」の位置づけ**である以上、ここに書かれていないと実装時に落ちる。§4.3 の警告カウント（`mc_warned_main` / `mc_warned_ext`）が主表・拡張表で別なので、置換ロジックも分岐内に置く必要がある。§4.2 の擬似コードを完全形に改められたい。

あわせて **§3.1 の `+1`（IRQCHK）を `mc_step()` のどこで加算するか**も擬似コードに含めると、M-1 の符号非対称による事故をさらに防げる。

### C-9 【§8 / §9.4】版数更新（G-6）と byte-exact 一致（G-4）の非干渉を確認せよ

G-4 は「`-q` stdout が v1.14 と **byte-exact 一致**」、G-6 は「起動バナーに v2.00 が出る」を要求する。版数文字列が `-q` の stdout に混入すれば**両立しない**。

実源を見る限り両立する見込みである（L2618 のバナーは REPL 経路、L2290 の版数ブロックは `argc < 2` 時の **stderr** 出力）が、設計書に**非干渉の確認が明記されていない**。

**要求**：§8 または §9.4 に「版数 7 点のうち **stdout に出るものが無い**ことを段6 の検証時に確認する（G-4 と G-6 の非干渉）」を追記されたい。段6 で G-6 のみ検証する手順になっているため、G-4 の再確認が抜ける恐れがある。
