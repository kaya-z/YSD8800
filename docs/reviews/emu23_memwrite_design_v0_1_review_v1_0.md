## 0. 総評

企画の妥当性は高い。とりわけ次を評価する。

- **§2 で `sim_impl_policy_v0_2.md` に照らした実現可能性検討を先に置いている。** 「ハードウェア実現不可能な機能をシミュレータに実装してはならない」という承認済みポリシーに対し、ASSIST09 の `M` コマンドや JTAG/SWD 経由の書き込みという**実機側の相当機能を具体的に挙げて**抵触しないことを示している。さらに「工程②.5 のデバッグ DIO 設計の先行検討として位置づけられる」と、機能追加を将来工程に接続している。ポリシーを形式的に通過させるのではなく、実質的に検討した跡がある。
- **§4.1 が課金汚染を最重要論点として最初に置いたこと。** 改良4 で `mem_charge()` が入った直後にこの機能を足すのだから、ここを見落とせば昨日確定した 339,240 が静かに壊れる。案A/B/C を比較し、案B を「原則122（兄弟実装）違反」、案C を「キャッシュ統計の汚染を防げない」として棄却した理由付けも妥当である。
- **§5.3 の否定形テスト先行が具体的**（N1〜N7）。とりわけ **N7（`setb` 実行後に `-mc` の値が変わらないこと）を「本機能で最も重要な否定形テスト」と位置づけた**判断は正しい。
- **§3.3 の読み返し表示に「原則123：動作確認≠正常性確認」を引いている点。** 書き込みが成功したことを書き込み側だけで判断しない、という発想は正しい。
- **§4.1 の KY 注意（`dbg_access` の戻し忘れ）で、`grep -c` による機械照合まで指定している。** 「気をつける」ではなく検証手段を示している。

**しかし、実源照合により本設計には 3 件の重大な欠落が判明した。とりわけ M-1 は致命的である。**

## 2. M 指摘（必須是正：3件）

### M-1 ★★致命的★★ 【§5.1】`s`（step）との前方一致衝突により、**4 コマンドすべてが不到達になる**

**実源** — `emu23_v2_10.c` L2648、REPL ディスパッチの**最初の分岐**：

```c
if (cmd[0] == 's') {
```

**`setb $0400 12` と入力すると `cmd[0] == 's'` に一致し、step コマンドとして解釈される。** `setb` / `setw` / `setpb` / `setpw` の 4 分岐には**どこに置いても到達しない**（`s` 分岐より前に置かない限り）。

さらに悪いことに、**エラーにならない**。`s` 分岐は `cmd + 1` から歩進数をパースするため、`"etb $0400 12"` の数値パースに失敗して既定値で**黙って 1 命令実行する**。ユーザから見れば「書き込んだつもりで、実際には CPU が 1 命令進んだだけ」となる。

**これは、本プロジェクトが繰り返し排除してきたサイレント失敗そのものである**（EMU-A の `--sym` 誤読、`-mc` の `cyc.txt` 誤読、キャッシュ設計の `mc_table[0x1F]` 無視）。しかも本件は**実行状態を書き換える**副作用を伴うため、それらより悪質である。

**決定的なのは、同型の罠が既にこのファイルに記録されていることである。** L2680 直前のコメント：

```
//   cmd[0]=='b' が "bd" も先取りし、この分岐が不到達になる。
```

**`bd` が `b` に食われて不到達になった事故が過去に発生し、`bd` を `b` より前に置くことで解決した記録が、同じ関数内に残っている。** 設計書 §5.1 は「REPL コマンド解析に 4 分岐を追加（約 80 行）」としか書かず、**挿入位置について一言も触れていない**。KY34（実ファイルが真実）に照らせば、追加先の関数を読んだ時点で気づけたはずである。

**是正要求**：

1. §5.1 に**挿入位置**を明記する。最低限「`if (cmd[0] == 's')` より**前**に置く」こと。
2. ただし位置合わせは**対症療法**であり、コマンドが増えるたびに同じ事故が再発する。**ディスパッチ方式そのものの是正**を推奨する。

| 案 | 内容 | 評価 |
|---|---|---|
| a | `setb`〜`setpw` を `s` 分岐より前に置く | △ 最小変更だが、次に `st` 等を足すとまた壊れる |
| **b（推奨）** | **先頭トークンを空白まで切り出し、完全一致で照合する** | ◎ 構造的解決。`s` は `s` に完全一致、`setb` は `setb` に完全一致 |
| c | 全分岐を長い順に並べ替える | ✗ 順序依存が残り、`bd`/`b` の教訓を再生産する |

**案 b を推奨する。** 現行の `strncmp(cmd,"mem",3)` 系も同じ危険を抱えており（`mem` が `memw` を先取りしないよう順序で回避している）、トークン化すれば順序依存が消える。ただし既存コマンドの挙動変更は G-4（`-q` byte-exact）に影響しないものの**回帰範囲が広がる**ため、案 b を採るなら**別チケットに切り出し、本機能は案 a で先行**するのも合理的である。いずれを採るにせよ、**選択と理由を設計書に残されたい**。

3. §5.3 の否定形テストに **N8：`setb` と入力して step が実行されないこと**を追加されたい。現行の N1〜N7 はいずれもこの事故を検出できない。

### M-2 【§3.3 / §1.1】`mem` は **MMU 変換をしない**。`setb` は変換する。**読み書きが非対称**であり、読み返し表示が誤情報を与える

**実源** — `dump_mem()`（L1884-1898）：

```c
static void dump_mem(uint16_t addr, int n) {
    ...
            if (i + j < n) printf("%02x ", mem[addr + i + j]);
```

**`mem[]` を直読しており、`mmu_translate()` を通していない。** 一方 `wr8()` は `mmu_translate()` を経て物理アドレスに書く（L1813 近傍の `mem_charge(pa, ACC_WR8)` が物理アドレス `pa` を受け取っていることからも明らか）。

したがって **`--mmu` 有効時**：

| 操作 | 実際に触るアドレス |
|---|---|
| `mem $0400` | **`mem[0x0400]`（変換なし）** |
| `setb $0400 12` | **`mmu_translate(0x0400)` の指す物理アドレス** |

**書いた場所と読んだ場所が違う。**

これは §3.3 の設計意図を直接破壊する。§3.3 は「MMIO 領域では書いた値がそのまま読めるとは限らない。**読み返して表示することで、書けたつもりで書けていない事故を防ぐ**」と述べるが、読み返しに `dump_mem` を使えば、`--mmu` 時には**書いた場所と無関係な値を「書き込み結果」として表示する**。**事故を防ぐはずの機能が、事故を隠蔽する。**

§1.1 の現状表も、この点で不正確である。

| | 設計書 §1.1 の記述 | 実際 |
|---|---|---|
| `mem` / `memw` | 「論理アドレス」 | **変換なし（実質は物理配列の直読）** |
| `physmem` | 「物理アドレス」 | ✅ 正しい（`phys_mem[]` 直読・L2801） |

**是正要求**：

1. §1.1 の表を実源に合わせて訂正する（`mem`/`memw` が MMU 非対応である事実の記載）。
2. §3.3 の読み返しを **`dump_mem()` に依存させない**。`setb` が実際に書いた物理アドレスから読み返す専用経路を用意し、**書き込みと読み返しが同一アドレスを指すことを構造的に保証**されたい。
3. `mem`/`memw` の MMU 非対応そのものは**既存の欠陥**である。「見えているバグは先に潰すこと。残したまま進行しないこと」という本プロジェクトの方針に照らし、**別チケットとして起票**されたい（本設計での同時修正は G-4 への影響があるため必須とはしない。ただし放置の判断は明示的に行うこと）。
4. §5.3 に **N9：`--mmu` 有効時に `setb` で書いた値が読み返しと一致すること**を追加されたい。

> **なぜ M か**：`--mmu` を使わない限り顕在化しないが、本機能の主目的（§1.2）である「特定の変数値でのみ再現するバグの調査」は、**YUI OS Level 2（MMU 連携）でこそ最も必要になる**。将来 MMU 環境で使った瞬間に、誤った読み返し表示に基づいて誤った結論を出すことになる。

### M-3 【§4.1】`dbg_access` の適用範囲が**書き込みに限定されている**。既存 `reset` コマンドが既に課金経路にある（原則122）

**実源** — `reset` コマンド（L2754-2756）：

```c
} else if (strncmp(cmd, "reset", 5) == 0) {
    cpu.pc          = rd16(0x0000);
```

**`rd16()` を呼んでおり、L1427-1428 で `mem_charge(pa_lo, ACC_RD16)` / `mem_charge(pa_hi, ACC_RD16)` を通る。** すなわち **v2.10 の時点で、デバッガ操作による課金汚染が既に存在する**。

`reset` は直後に `cpu.cycle = 0` を代入するため**サイクル値への実害は消える**が、**キャッシュ統計（`stat_hit`/`stat_miss`）と `--trace-addr` のトレースは汚染される**。§4.1 が案C（`cpu.cycle` の保存・復元）を「キャッシュ統計の汚染を防げない」として棄却したのと**同じ理由**が、`reset` にも当てはまる。

設計書は書き込み経路のみを論じているが、**原則122（兄弟実装は同時確認。片方修正時は全員確認）**に照らせば、`dbg_access` を導入する以上、**CPU の命令実行に由来しないメモリアクセスを全数洗い出して同時に対応する**のが正しい。

**是正要求**：

1. `grep -n "rd8\|rd16\|wr8\|wr16\|fetch8" emu23_v2_10.c` で **REPL・CLI 由来の呼び出しを全数抽出**し、§4.1 に一覧として掲載されたい。現時点で判明しているのは `reset`（L2755）だが、`disas`（L2723）や `b <label>` のシンボル解決経路にも同種の呼び出しがある可能性がある。
2. 抽出した全箇所を `dbg_access` で包む。
3. §5.2 の実装順序 #1 に「既存のデバッガ由来アクセスの `dbg_access` 化」を含める。
4. §4.1 の `dbg_access` の説明文——「CPU の命令実行に由来しないアクセスはサイクルを消費しない」——は**方針として正しい**。問題はその方針を**新規コマンドにしか適用していない**ことである。

> **補足**：この網羅確認は §4.1 の KY 注意（立てる箇所と戻す箇所を `grep -c` で機械照合）と同じ枠組みで実施できる。**「立てる箇所の数」を数える前に、「立てるべき箇所の数」を確定する必要がある。**

## 3. Q-1〜Q-5 への回答

### Q-1：コマンド名を `setb`/`setw`/`setpb`/`setpw` としてよいか

**名前は妥当。ただし M-1 のとおり照合方式が問題である。**

既存の `mem`/`memw`/`physmem` と対をなす命名であり、`physmem` に対する `setpb`/`setpw` の `p` も一貫している。MC6809 系モニタの流儀（ASSIST09 の `M`、OS-9 の `dEd`）に寄せる案も挙げられているが、**emu23 の既存コマンド体系は英単語ベース**（`mem`/`regs`/`disas`/`reset`/`help`）であり、ここだけ 1 文字コマンドを持ち込むと一貫性を欠く。**既存体系との対称性を優先する現案を支持する。**

なお `setb` と `setpb` は先頭 4 文字が異なる（`setb` / `setp`）ため、両者の間では衝突しない。問題は `s` との衝突のみである。

### Q-2：物理側 MMIO の扱いは案1（MMIO ディスパッチしない）でよいか

**案1 を承認する。** 実源で `physmem` が `phys_mem[(pa + i) & 0xFFFFF]` を直読していることを確認した（L2801）。読み出しが純粋な物理配列アクセスである以上、**書き込みも同じであるべき**であり、対称性の論拠は正しい。

「MMIO は MMU 変換対象外であるから『物理アドレス $FC80』という概念は本来存在しない」という §4.3 の論理も妥当である。§4.3 に「**物理側で MMIO を叩きたい場合は論理側 `setb` を使う**」と明記されている点も良い——利用者の逃げ道が塞がれていない。

### Q-3：`dbg_access` 方式（案A）でよいか

**方式は承認する。ただし M-3 のとおり適用範囲の拡張が必要。**

課金点が `mem_charge()` の 1 箇所に集約されているため抑止も 1 箇所で済む、という論拠は実源で確認した（L634 の単一定義、呼び出しは L300/1427/1428/1591/1592/1703/1813 の 7 箇所すべてがこの関数を通る）。案A は正しい。

### Q-4：MMIO 帯では読み返しを省略すべきか

**省略を推奨する。** ただし**無言で省略してはならない。**

読み返し自体が副作用を持つ MMIO は実在する（受信データレジスタの読み出しで FIFO が進む、ステータス読み出しで割込フラグがクリアされる等）。§3.3 の目的は「書けたつもりを防ぐ」ことだが、**読み返しがハードウェア状態を変えてしまえば、それは確認ではなく別の操作である**。

推奨する表示形式：

```
YUI> setb $FC80 41
FC80: <41 written; readback skipped (MMIO)>
[WARN] MMIO write: side effects may occur
```

**「読み返していない」ことを明示する**のが要点である。値だけ表示すると、利用者はそれを読み返し結果と誤認する。§3.3 が防ごうとしている「書けたつもり」を、形を変えて再生産することになる。

なお MMIO 帯の判定は §4.4-1 の警告表示と**同一の判定式を共用**されたい。判定が 2 箇所に分かれると、片方だけ範囲が変わる事故が起きる（原則122）。

### Q-5：レジスタ書き込み（`set A 1234` 等）も実装すべきか

**本設計では対象外でよい。** 理由を 2 点挙げる。

1. **論点の性質が異なる。** メモリ書き込みは `mem_charge()` という共有経路を持つため課金汚染が主要論点になるが、レジスタ書き込みは `cpu.a = v` の代入のみで課金経路を持たない。混ぜると §4.1 の議論が薄まる。
2. **1変更1検証の原則。** 本機能は M-1 の照合衝突という構造的リスクを抱えており、まずそれを片付けるべきである。

ただし**別チケットとして起票することを推奨する**。§1.2 の「ブレークポイント停止後の状態を変えて分岐を試す」という用途では、**レジスタ書き換えの方がメモリ書き換えより有用な場面が多い**（条件分岐はフラグとレジスタで決まる）。加えて、フラグレジスタの書き換えは KY54 の異常値注入と相性が良い。

## 4. C 指摘（確認・明記要求：4件）

### C-1 【§4.4-3】「`-q` モードでは無効」の意味が不明瞭

REPL は `-it` 指定時に入る経路であり、`-q` は出力抑止オプションである。両者は直交する。「`-q` モードでは無効」が意味するのは次のどちらか。

- (a) `-it` 非指定時は REPL に入らないので自明に無効 → **安全策として記述する意味がない**
- (b) `-it -q` を同時指定した場合に、REPL には入るがコマンドを拒否する → **実装が必要**

§5.3 の N6 は「そもそも REPL に入らない」と (a) の理解を示しているが、§4.4-3 は安全策として掲げている。どちらであるかを明記されたい。(a) であれば §4.4 から削除し、(b) であれば実装項目として §5.1 に追加すること。

### C-2 【§3.2】`setw` のエンディアン記述は既存 `wr16()` の実装に従うことを明記されたい

§3.2 の例は `setw $F000 1234` → `$F000=0x34, $F001=0x12`（リトルエンディアン）としている。サイクル表の状態連鎖が `MEMW_LO/HI` の順であることと整合するが、**設計書で独自に定義するのではなく「既存 `wr16()` の実装に従う」と書く**べきである。そうしておけば、万一実装が異なっていた場合に設計書が誤りの根拠にされずに済む。あわせて §5.3 に「N10：`setw` で書いた値が `memw` の表示と一致すること」を追加されたい。

### C-3 【§4.1】`dbg_access` は課金だけでなく**キャッシュ状態の更新も抑止する**

`mem_charge()` は課金値を返すだけでなく、内部で `cache_valid[idx]` / `cache_tag[idx]` を更新する（L634-652 以降）。冒頭で `return 0` すれば、**キャッシュのタグ・有効ビットも更新されない**。

これは意図として正しい（デバッガ操作がキャッシュ状態を変えるべきではない）。ただし**実機との差異**ではある——実機のデバッグモニタでメモリを書き換えれば、キャッシュとの一貫性問題が生じる。emu23 はキャッシュにデータを持たず `mem[]` 一本であるためデータ不整合は起きないが、**この差異を §4.1 に明記**されたい。工程②のキャッシュ RTL 設計時に「デバッグ書き込み時のキャッシュ無効化」が論点になるため、先行検討の記録として価値がある。

### C-4 【§6】G-3 の `dhry_final.bin` 21,846 B の出所を確認されたい

絶対ゲート表に挙げられているが、他の設計書（`emu23_cache_base_design` 等）の絶対ゲート表では G-1/G-2 のみが定型で、`dhry_final.bin` のサイズは登場していない。**台帳（`tool_version_ledger`）に登録された値か、本設計書で初出か**を確認されたい。初出であれば、どの手順でビルドしたものかを併記しないとゲートとして機能しない。

| **N-1** | §3.2 | `<addr>` にシンボル名を許容する際、**既存 `b <addr\|label>` と同じ解決経路を再利用**するとしている点は正しい（EMU-A/EMU-B の教訓）。ただし、シンボルが**見つからなかった場合**の挙動が未定義。`setb Ch_1_Glob 41` で `Ch_1_Glob` が未定義のとき、16 進として `0x0` 等に解釈されて**別のアドレスに書く**危険がある。「シンボル解決に失敗したら書き込まずエラー」と明記し、§5.3 に否定形テストを追加されたい。 |
| **N-2** | §3.2 | `<val>` の値域チェックが未定義。`setb $0400 1FF` のように 8bit を超える値を与えた場合、切り詰めるのか拒否するのか。`-mc` の定義ファイル（`emu23_mc_design` §6.4）が値域チェックを明示している前例に倣い、**拒否＋エラー表示**を推奨する。 |
| **N-3** | §7 | 波及範囲に **`kaizen.txt`** が挙がっていない。M-1 の「前方一致ディスパッチへのコマンド追加は既存分岐に食われうる」は、L2680 の `bd`/`b` に続く**2 度目の発生**であり、原則として登録する価値がある（例：「**前方一致で分岐する箇所に新規キーワードを追加する際は、既存の短いキーワードに先取りされないことを確認する**」）。同種の構造は YUI OS シェルのコマンド照合（先頭 1 文字マッチ）にも存在するため、横展開の価値も高い。 |
