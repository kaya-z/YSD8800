## §0. 結論を先に

★真因は `burst_len` である。★

```
ysd8800_cache_v0_6.sv L513 : burst_len_o = fill_sel ? 32 : 1
ysd8800_v5_membus_v0_14.sv L542 → L638 : cache_burst_len が wbuf を迂回して psram_ctrl へ直結
ysd8800_wbuf_v0_2.sv      L165-167 : drain_start に ★rd_block★ が含まれる
```

★フィル要求が立っている（＝`burst_len=32` が出ている）まさにその瞬間に、
wbuf は `rd_block` を契機としてドレイン**書込**を下流へ発行する。★
★psram_ctrl はその書込要求を `blen_r=32` でラッチする。★

その結果、`ysd8800_psram_ctrl_v0_3.sv` で次が連鎖する。

| # | 実源 | 起きること |
|---|---|---|
| ★1★ | L164-165 `if (we && (blen_r == 1))` | ★条件が偽 → `mem[]` に書かれない ＝ **書込消失**★ |
| ★2★ | L172-186 | `blen_r≠1` のため ★PS_BURST へ遷移★ |
| ★3★ | ★L193-195 `beat_valid <= 1'b1`★ | ★書込なのに 32 本のビートを出す。★★案D は PS_BUSY しか変えていないので効かない★ |
| 4 | — | cache は `fill_gate_ps` 開・`fill_armed_r`=1 のため 32 本を吸い込む → ★**書込先アドレスのメモリ内容**でラインを充填★ |
| 5 | L197-199 | 最終ビートで `ack` → `br_ready_i` → `fill_done` → ★`valid_r` が立つ（誤データのまま恒久化）★ |

★これ 1 本で、観測されている全事象が説明できる。★

| 観測事実 | 説明 |
|---|---|
| ★案D で直らない★ | ★#3：PS_BURST の `beat_valid` は無条件。案D は PS_BUSY のみ★ |
| ★MISMATCH=27★ | #1 の書込消失 ＋ #4 の誤充填 |
| ★2026-09-20 の「書込消失」報告★ | ★#1 のとおり実在する。v0.3 §5.2-R.1 の撤回は誤りであった（§3.1）★ |
| DHRY FAIL（停止はしない） | #4 で得た値は「別アドレスの正当なデータ」であり X ではないため走り続ける |

★W-A（1 サイクルの ready 重なり）は成立しない（§2.3）。T-4 を実施しても `N_short == 0` になる。★

## §2. 真因の詳細

### 2.1 M-1：`rd_block` がドレインの契機になっている

v0.3 §5.2-R.1 は「フィル中は `upstream_idle=0` となって wbuf はドレインを開始しない」とした。
★`drain_start` の条件を全部読むと、そうではない。★

```
ysd8800_wbuf_v0_2.sv L163-167:
  wire drain_start = (st_r == S_HOLD) &&
                     (hold_full | ★rd_block★ | wr_block | flush_req_i |
                      (upstream_idle & idle_expired));

  L142: wire rd_block = en & up_rd_i & wb_valid_r;
```

★`rd_block` は「読出が来ていて、かつバッファが埋まっている」＝ まさにフィル要求中の状態である。★
★`upstream_idle` は 5 つの契機のうちの 1 つにすぎず、それだけを見て排他を結論したのが誤りだった。★

そしてこのとき cache 側は：

```
ysd8800_cache_v0_6.sv L513: assign burst_len_o = fill_sel ? BLEN_W'(LINE_SIZE) : BLEN_W'(1);
（fill_sel = ccr_cen_i & (fill_req | fill_active_r)）
```

★`fill_req` が立った時点で `burst_len_o = 32` になる。★
そして `membus_v0_14` L542 → L638 で ★wbuf を通らずに psram_ctrl へ直結している。★

★v0.3 §3.1-R.1 の表は、この直結を「迂回経路」として正しく列挙していた。★
★しかし「迂回しているのはデータ経路（`beat_valid`/`psram_rdata`）である」と読み、
`burst_len` が**要求の属性**であることを見落とした。★
★`burst_len` は下流へ向かう制御であり、要求経路の一部である。★

> ★要求経路を横取りしたのに、その要求に付随する属性を横取りしなかった。★
> ★結果、wbuf が発行した書込要求に、cache が出した「32 バイト読め」という属性が付いた。★

### 2.2 M-3：案D が届いていない箇所

§5.5.3 は PS_BURST を変更しない理由を次のように述べた。

> 「バースト書きは v0.3 M-3 で未サポートと明記され `blen_r==1` に限定済みであり、
> ★PS_BURST に入るのは読出だけである★」

★`blen_r==1` に限定されているのは「`mem[]` への書込」であって、「PS_BURST への遷移」ではない。★

```
ysd8800_psram_ctrl_v0_3.sv L164-186:
  if (we && (blen_r == BLEN_W'(1)))  mem[mem_idx] <= wdata;   ← ★書込だけが限定★
  ...
  if (blen_r == BLEN_W'(1)) begin ack…PS_WAIT_REQ_LOW; end
  else begin beat_cnt <= 1; ★ps_state <= PS_BURST;★ end        ← ★we を見ていない★
```

★`we=1` かつ `blen_r=32` の要求は、書込を捨てたうえで PS_BURST に入り、32 本のビートを出す。★
★L193-195 の `beat_valid <= 1'b1` は無条件である。★

★したがって案D（PS_BUSY のみ `~we`）は、この経路のビートを 1 本も止めていない。★
★T-2 で MISMATCH が残ったのは当然である。★

★なお L161-163 のコメント「バースト書きは未サポート。blen_r==1 に限定して無害化する」は、
★「無害化できている」という記述が誤りである。★ 書込を捨てるだけで、
★ビート生成とメモリ読出（L166 `rdata <= mem[mem_idx]`）は止めていない。★
★この記述も是正対象である（v0.3 のとき指摘した「コメントと実装の乖離」と同型）。★

### 2.3 W-A が成立しない根拠

§15.3 手順 5 は「`dn_ready_i` がまだ 1 のまま」を前提とする。★これは実装上あり得ない。★

```
ysd8800_cdc_bridge_v0_5.sv L151:
  suppress_r <= ack_sync[0] & ~ack_sync[1];
L159:
  assign cpu_mem_ready = suppress_r;
```

★`ready` は `ack` の立上りを検出した次の 1 サイクルだけ立つ、幅ちょうど 1 のパルスである。★
（L145-148 のコメントも「★抑止幅はちょうど 1 cpu cyc★」と明記している。）

- ドレイン最終 ack のサイクル：`wb_valid_r` はまだ 1 → `rd_block` 優先で `up_ready_o=0` ✅（§15.3 手順 4 のとおり）
- ★その次のサイクル：`wb_valid_r=0` になるが、`suppress_r` も既に 0 に戻っている★
- したがって `up_ready_o = up_rd_i & dn_ready_i = 0`

★重なりは存在しない。W-A は棄却してよい。★
★§17 の「レビューで特に見てほしい点 2」への回答でもある。★

### 2.4 M-2：T-4 は誤った結論へ導く

§16.1 の判定は「`N_short > 0` なら W-A 成立＝真因確定。`N_short == 0` なら W-A 棄却し §17-2 へ」である。

★真因（§0）のもとでは、cache は 32 本のビートを実際に受け取る。★
★`fill_done` 成立時の `beat_cnt_r` は 32（＝BLEN）であり、`N_short == 0` になる。★

★すなわち T-4 は「W-A ではない」という正しい結論を返すが、
そこから §17-2（窓以外の経路説）へ誘導され、★真因からさらに遠ざかる。★

**判別点の差し替え（1 点で決まる）**：

```
（TB・階層参照・DUT 無改変）
always @(posedge psram_clk)
    if (u_membus.u_psram_ctrl.req && !req_d
        && u_membus.u_psram_ctrl.we
        && u_membus.u_psram_ctrl.burst_len != 1)
        burst_write_count <= burst_write_count + 1;
```

★`burst_write_count > 0` なら §0 の真因が確定する。★
★これは `beat_valid` にも `fill_done` にも依存せず、案D の有無にも影響されない。★
★観測は psram_clk 単一ドメインで閉じるため、§17「見てほしい点 3」の CDC またぎ問題も生じない。★

★併せて、そのときの `addr` と cache 側の `fill_index_r` が指すラインを記録すれば、
#4（誤アドレスからの充填）まで一度に実証できる。★

## §3. 確認事項

### 3.1 C-1：撤回した「書込消失」は事実だった

v0.3 §5.2-R.1 は次のように記録している。

> ★本節は 2026-09-20 に一度「書込消失が起きる」と誤って報告した件の訂正記録である。★
> ★要求経路の直結だけを見て排他制御を確認せずに断定した。KY34（実源優先）の不徹底。★

★「書込消失が起きる」という最初の報告は正しかった。★
★誤っていたのは、それを撤回した二度目の判断である。★

撤回の根拠は「フィル中は `upstream_idle=0` だからドレインしない」であったが、
★`drain_start` の 5 つの契機のうち 1 つしか見ていなかった★（§2.1）。

★KY34 を適用したつもりで、条件式の一部しか読まなかった。★
★これは「実源を見た」と「実源を読み切った」の差である。★

> ★KY 候補：撤回・否定の判断は、肯定の判断と同じかそれ以上に実源の全条件を確認してから行う。★
> ★誤った肯定は次の検証で捕まるが、誤った撤回は探索範囲から外れて戻ってこない。★

★本件では、正しい報告を撤回したことで 1 日分の探索が別方向へ向いた。★
★§14-追補の KY⑧（症状が変わったことを「原因が別」の根拠にしない）と対になる教訓である。★

### 3.2 C-2：§15.1 の指摘自体は正しい

★`br_ready_i` の実源が cdc_bridge から wbuf へ付け替わったという §15.1 の指摘は、事実として正しい。★
★`up_ready_o` が「書込吸収でも 1 になる」ことも、L204-208 のとおりである。★

★ただし本件の主因ではない。★ §2.3 のとおり、ready のパルス幅が 1 であるため
「読出完了でないのに `fill_done` が立つ」経路は閉じている。

★とはいえ、これは「たまたま閉じている」形である。★
★`suppress_r` の幅が 1 であることに依存しており、cdc_bridge を将来変更すれば開く。★
★§15.1 の指摘は KY⑥（信号の意味が変わる）の良い実例として残す価値がある。★
★真因ではないが、削除せずに「本件の主因ではないが潜在的な脆弱性」として格下げ保存されたい（KY41）。★

### 3.3 C-3：`tb_psram_equiv_v0_1` の優先度が上がる

§17-4 は「v0.2 参照のため実行不能・未解消」とする。
★本件で psram_ctrl をさらに触る（案G は psram_ctrl を触らないが、案D は残す）以上、
等価 TB が動かない状態は放置できない。★
★特に案D は `beat_valid` の対外仕様を変える改修であり、等価性の基準そのものに関わる。★

## §4. M-4：対策（案G）

★§16.3 の案E・F・A' はいずれも真因に対応していない。★

| 案 | 本件に対する評価 |
|---|---|
| E（`fill_done` を読出 ack 限定） | ★W-A への対策。W-A は成立しないので不要★ |
| F（`fill_done` にビート数条件） | 同上。★CDC をまたぐ条件を増やすだけ★ |
| A'（窓を塞ぐ） | ★ドレイン自体を止めれば症状は消えるが、`burst_len` の不整合は残る★。対症療法 |

**推奨：★案G — `burst_len` を wbuf 経由にする★**

```
membus:  cache.burst_len_o → ★wbuf.up_burst_len_i★ → wbuf.dn_burst_len_o → psram_ctrl.burst_len

wbuf 内（組合せ・1 行）:
  assign dn_burst_len_o = ~en           ? up_burst_len_i
                        : drain_active  ? BLEN_W'(1)      // ★ドレイン書込は必ず 1★
                        :                 up_burst_len_i;
```

| 観点 | 評価 |
|---|---|
| 真因への直接性 | ★◎★ ドレイン書込が `blen_r=1` で受理される → 書込が成立し、PS_BURST に入らない |
| 案D との関係 | ★案D と併用する。★ `blen_r=1` なら PS_BUSY のみを通るので、案D がビートを止める。★2 つで完全になる★ |
| cache への改変 | ★無し★（TKT-V7 直後の cache に触れないという §3.1 の方針を維持） |
| psram_ctrl への改変 | ★無し★（案D のみ） |
| 一般化との整合 | ★v0.4 §3.1-R.2 の一般化「迂回経路があると切り離されない」を、★★迂回をやめることで★★解消する★ |
| バイパス同一性 | `~en` で素通しのため W-0 は維持 |

★案G は v0.4 §3.1-R.2 で自ら書いた一般化に、素直に従った対策である。★
★「挿入点を迂回するサイドバンド経路がある限り切り離されない」——ならば迂回をやめればよい。★

★検証★：案G 適用後、§2.4 の `burst_write_count` が ★0 になること★ を確認する。
これは対策の効果を直接見る判定であり、★検査器が対策によって沈黙しない★（案D で起きた問題の回避）。

## §5. N-1：KY の強化
