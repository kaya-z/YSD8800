## 0. 総評

**評価する点**

1. ★**「TB が DUT の外部契約を独自に再実装し、そちらが間違う」という問題の言語化**★（§1.1）。3 チャット分の損失を「TB のバグ」で終わらせず、★**契約の実装が 2 箇所ある**という構造的原因★（KY78）まで掘り下げた点が本設計の価値です。
2. ★**§3.1「DUT 側に常設する。TB 側ではない」**★の判断とその理由（TB 側に置くと同じ人が同じ誤解をする）。★契約は DUT の性質であるという原則論として正しく、かつ実務的にも正しい★です。

4. ★**§1.2 の非対称性の指摘**★（効きすぎ＝性能劣化で気づける／効かなさすぎ＝静かに壊れる）。段5 を前に本対策を置くという工程判断の根拠として説得力があります。

**差戻しとする理由**

★**契約 C-α が実 CPU の動作と正面から矛盾しています**★（M-1）。§2.1 は「実 CPU は ready と同時に要求を下げるため発生しない」としますが、★実源を追うとこれは事実ではなく、C-α の assert は 16 ビットアクセス・PUSH・POP・命令フェッチのたびに発火します★。導入すれば G-0/G-1 が assert の洪水になります。

### M-2 ★§3.3 の `assert property` は Icarus 12.0 で使用できない（実地確認済）★

|---|---|

```systemverilog
// ============================================================
//  ★バス契約アサーション C-α'（TKT-V1 / T-B）★
//    目的: TB が外部契約を再実装して食い違った場合に即座に落とす。
//    契約: ready の次サイクルで要求を継続する場合、それは
//          ★新しい要求（アドレスまたは種別が変化）★でなければならない。
//    経緯: 段4 で TB が ready 後も同一要求を保持し、再送が発生した。
//    注意: ★Icarus 12.0 は assert property を未サポート★のため手続き版。
//          `always_ff` にすると $error に合成不可の警告が出るため `always` を使う。
//    合成: `ifndef SYNTHESIS で囲む（工程③へ持ち込まない）
// ============================================================
`ifndef SYNTHESIS
    logic                ready_d, rd_d, wr_d;
    logic [PHYS_AW-1:0]  addr_d;
    always @(posedge cpu_clk or negedge cpu_rst_n) begin
        if (!cpu_rst_n) begin
            ready_d <= 1'b0; rd_d <= 1'b0; wr_d <= 1'b0; addr_d <= '0;
        end else begin
            if (ready_d && (cpu_mem_rd || cpu_mem_wr)
                        && (cpu_mem_rd == rd_d) && (cpu_mem_wr == wr_d)
                        && (cpu_phys_addr == addr_d))
                $error("[CONTRACT C-a] same req held after ready: addr=%h rd=%b wr=%b t=%0t",
                       cpu_phys_addr, cpu_mem_rd, cpu_mem_wr, $time);
            ready_d <= cpu_mem_ready;
            rd_d    <= cpu_mem_rd;
            wr_d    <= cpu_mem_wr;
            addr_d  <= cpu_phys_addr;
        end
    end
`endif
```

**当方の実行結果（Icarus 12.0）**

```
== 陰性1: 実CPU相当 S_MEMR_LO->S_MEMR_HI (addr変化) ==
     （発火なし）
== 陽性: 段4のバグ相当 ready後に同一要求を保持 ==
ERROR: [CONTRACT C-a] same req held after ready: addr=02000 rd=1 wr=0 t=105
```

★陰性（実 CPU 相当の連続アクセス）で発火せず、陽性（段4 のバグ相当）で発火する★ことを確認しました。§3.5 の手順 1・2 に相当する試験を、★設計段階で先に通してあります★。

> ★実装時の注意★：`always_ff` を使うと `warning: System task ($error) cannot be synthesized in an always_ff process.` が出ます。★`ifndef SYNTHESIS` で囲んでいるため実害はありませんが、警告ゼロを保つなら `always` を使ってください。★

## 3. C：確認事項

### C-1 `bus_tasks.svh` の `ready` サンプリングが領域順序に依存する

§4.2 の `do @(posedge cpu_clk); while (!cpu_mem_ready);` は、★`@(posedge)` で起動した **Active 領域**で `cpu_mem_ready` を読む★ため、読める値は ★直前サイクル中に確定していた値★になります。現行の `cpu_mem_ready`（`cdc_bridge` の登録出力）ではこれが意図どおりに働きます。

ただし ★キャッシュ導入後、`mem_ready` は組合せ出力になります★（`v11_cache_core_design` §7.1：`(CEN & hit & data_q_valid) ? 1'b1 : ...`）。組合せ信号でも Active 領域では前サイクルの確定値が読めるため ★結論としては同じ★ですが、★TB 側が NBA で `cpu_mem_rd` を駆動し、それが組合せで `mem_ready` に戻る★構成になるため、★同一時刻内の評価順序が絡みます★。

★1 サイクルヒット（フェッチ）が正しく 1 サイクルで完了することを、`bus_tasks.svh` 導入時に波形で確認★されたい。§4.4 の「T1〜T7 ALL PASS 維持」に加えて、★**アクセス 1 回あたりのサイクル数が期待どおりか**★を確認項目に足すと安全です（TKT-V1 と同種の「TB 側のサイクルずれ」を再発させないため）。

### C-2 C-β / C-γ の assert 記述案が無い

§3.3 は C-α の記述案のみを示し、C-β・C-γ の具体的な記述がありません。§6 の実装順序 2・3 は「同上」とされていますが、★C-β は `psram_clk` ドメインで、しかも「req 受理サイクル」という**イベント**を捉える必要があり、C-α より記述が難しい★です。

具体的には ★`ps_state == PS_IDLE && req` のサイクルで `burst_len`／`we` が `1'bx` でないこと★、および ★受理後 `PS_WAIT_REQ_LOW` に至るまで `we` が変化しないこと★ の 2 本になります。後者は受理時に `we` をシャドウレジスタへ保存して比較する形になります。★M-2 の参照実装と同じ構造で書けますが、記述案を §3.3 に明示★されたい。
