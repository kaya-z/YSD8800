## §2. 必須修正の詳細

### 2.1 ★M-1：T-3 は案D の後では何も検出できない★

§7.6 T-3 は次を定める。

> `cache_v0_6` L497 のアサーションから ★`fill_armed_r` 条件を外した検査版★ を用意し、
> ★残存窓への到達を計数★する。

そして §5.5.5 限界2 は「★T-3 の計数が 0 でないなら、案D は窓を塞いだのではなく被害だけを消している★」とする。

★この論理は成立しない。★ 実源を見る。

```
ysd8800_cache_v0_6.sv L495-499:
    if (psram_rst_n && fill_gate_ps && beat_valid_i
        && !fill_armed_r && !burst_start)
        $error("[CACHE] unarmed beat consumed: P-A/P-B broken @%0t", $time);
```

★検出条件の第 2 項は `beat_valid_i` である。★
★案D は、まさにその `beat_valid` を書込時に立てなくする改修である。★

| 状態 | 書込が残存窓に到達したとき |
|---|---|
| 案D 適用前（v0.3） | `beat_valid=1` → 検出可能 |
| ★案D 適用後（v0.4）★ | ★`beat_valid=0` → 検出条件が成立しない★ |

★`fill_armed_r` を外しても、`beat_valid_i` が立たない以上、計数は必ず 0 になる。★
★そして §5.5.5 の論理に従えば「0 だったので窓は塞がれた」と読まれる。★
★実際には窓はそのまま存在している（§5.5.5 限界1 が正しく認めているとおり）。★

★T-3 は「直したから見ない」を防ぐ項目として立てられた。★
★しかし現状の T-3 自体が「見ているつもりで見ていない」検査器である。★
★これは §5.2-R.2 で問題にした「沈黙するアサーション」と同じ構造を、対策側で再生産している。★

**修正要求（2 点）**：

**(1) ★検出対象を「beat」から「要求」へ変える★**

残存窓の本質は ★「cpu_clk 側でフィルが終わったのに psram_clk 側の `fill_gate_ps` がまだ 1 の期間に、
非フィルの要求が psram_ctrl に到達すること」★ である。
★beat はその結果であって、原因ではない。★ 原因を直接見る。

```
（TB 内・階層参照・DUT 無改変）
always @(posedge psram_clk)
    if (psram_rst_n
        && u_membus.u_cache.fill_gate_ps          // ★残存窓★
        && u_membus.u_psram_ctrl.req              // 要求到達
        && u_membus.u_psram_ctrl.we               // ★非フィル（書込）★
        && !req_d)                                // 立上りのみ計数
        window_hit_count <= window_hit_count + 1;
```

★この検出器は `beat_valid` に依存しないため、案D の前後どちらでも同じ値を返す。★
★DUT を改変しないため `cache_v0_6_assert_poc.sv` も不要になり、§13-4 が消える。★

**(2) ★案D 適用「前」にベースラインを取る★**

★窓の実在を数値で示せるのは、案D 適用前だけである。★

| 順 | 内容 | 得られるもの |
|---|---|---|
| ★T-3a★ | ★`psram_ctrl v0.3` のまま、上記検出器で計数★ | ★窓への到達回数（実測）★＝真因の直接証拠 |
| T-3b | 案D 適用後、同じ検出器で計数 | ★T-3a と同数になるはず★＝「窓は残っている」ことの実証 |

★T-3a は §9-追補4（波形での直接確認は未実施）を埋める最も安価な手段でもある。★
★波形を追わずとも、窓の実在とその回数が数値で確定する。★

★そして T-3a と T-3b が同数であることをもって、§5.5.5 限界1
「案D は構造自体は残す」が ★主張ではなく実測★ になる。★

### 2.2 ★M-2：psram_ctrl の単体回帰が抜けている★

案D は ★`psram_ctrl` の出力仕様の変更★ である。
しかし §7.6 の T-1〜T-5 も §13 の実装順も、★結合レベルの測定しか含んでいない。★

## §3. 確認事項

### 3.1 C-1：沈黙の原因は 1 つではない

§5.2-R.2 の表 #5 は「★`fill_armed_r=1` のため L497 のアサーションは発火しない＝無音破壊★」とする。
★原因はもう 1 つある。★

残存窓への混入は ★フィル完了後、`beat_valid` が一度 0 に落ちてから立つ★。
したがって `burst_start = fill_gate_ps & beat_valid_i & ~beat_valid_d` ★が成立する。★
L498 の条件には ★`!burst_start`★ が含まれるため、★`fill_armed_r` を外しても沈黙する。★

★これが M-1 の「`fill_armed_r` を外しただけでは検出できない」もう一つの理由である。★
★§5.2-R.2 の表に 1 行追加されたい★（原因を 1 つと書くと、対策も 1 つで足りると読まれる）。

さらに ★`burst_start=1` が成立するということは、混入した書込ビートが★
★`req_offset_r` / `fill_index_r` の再ラッチまで引き起こす★（L406-407 の `off_use` / `idx_use`）。
★汚染先は「直前ライン」とは限らず、そのとき cpu 側が保持している `fill_index_r` の指す位置になる。★
★§5.2-R.2 の #4「直前ラインを汚染」は、より広い被害になりうる。★
（実測の MISMATCH が `wbv=0` に偏っていたこととも整合する。）

### 3.2 C-2：§5.5.4 根拠2 の補強

「書込時の `beat_valid` を利用している受け手は cache の I-2 のみ」——★RTL については正しい。★

| 受け手 | `beat_valid` を見るか | 実源 |
|---|---|---|
| `cache_v0_6` I-2 | ★見る（弾く対象として）★ | L382-383, L409 |
| `cdc_bridge_v0_5` | ★見ない（`ack` のみ）★ | L196-198 |
| ★TB（`tb_psram_ctrl` / `tb_psram_equiv`）★ | ★§2.2 のとおり★ | — |

★根拠2 の洗い出しに TB を含めれば、M-2 の必要性も同じ表から導ける。★

### 3.3 C-3：§3.1-R.2 の一般化に 1 軸加える

> 挿入位置の妥当性は「★挿入によって、下流の要求発行者が何個になるか★」で判定すべきであった。

★正しい。もう 1 軸あると、今回の真因まで届く。★

> ★上流モジュールが下流との間に置いている暗黙の時間的前提を、挿入が何個壊すか。★

今回壊れたのは ★P-B（`fill_gate_ps` 中に非フィルのバーストが出ない）★ である。
★これは「要求発行者が 2 個になった」ことの帰結だが、P-B は `cache_v0_6` L490-494 に
★明文で書かれていた★。★読めば分かる形で存在していた前提である。★

★挿入位置を決めるとき、上流モジュールのヘッダに書かれた前提を読み直す——
これを一般化に含めておけば、次の挿入（例えば工程③のバス幅変更）で効く。★

### 3.4 N-1：単体TB での再現可能性

§9-追補5 は「単体TB の下流モデルは `beat_valid` を模擬していないため本件を検出できない」とする。
★事実として正しい。★ そして ★模擬すれば検出できるようになる。★

★下流モデルに「書込時にも `beat_valid` を立てる」v0.3 の挙動を実装すれば、
残存窓の再現を単体TB で作れる。★ ただし `fill_gate_ps` は cache 側の信号であるため、
★wbuf 単体TB ではなく「cache + wbuf + psram モデル」の中規模TB が要る。★

★本工程で作る必要はない。★ 限界として記録されているので十分である。
★ただし §9-追補5 に「模擬すれば検出可能である（＝TB の限界であって原理的な限界ではない）」★
と一言添えておくと、将来の判断材料になる。
