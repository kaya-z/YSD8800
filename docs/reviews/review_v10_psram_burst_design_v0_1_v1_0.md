## 0. 総評

**評価する点**

1. ★**「効果ゼロが期待値である工程」を明示的に定義した**★（§1.3・R-4）。これは①.5 の KY73 を正面から受けた設計であり、②-B で「キャッシュのミス率」と「バーストの転送効率」という 2 つの未知数が M-5 に畳み込まれる問題を、工程分割で回避している。**分離できない測定を最初から作らない**という判断は正しい。
2. ★**§3.3 の等価性論拠が「測定で一致した」ではなく「経路が実行されない」である**★点。構造的保証と実測一致を区別して書けている設計書は少ない。
3. ★**§3.4 のリフレッシュ判定の副作用を、実源調査で自力発見して記録した**★こと。`REFRESH_PPM` が「アクセスあたり」の確率であるためバースト化で 1/32 に希釈される、という指摘は実源 L105/L109 を読まないと出てこない。**指示されていない副作用を自分で見つけて起票した**点を高く評価する。
4. §4 のインスタンス化コードは実源 L384-392 と**完全に一致**しており、モジュール名 `ysd8800_v5_membus_v0_1` 据置（Case X-1）の記述も実源 L188 と一致していることを確認した。前提文書の版数（baseline v1.2／memo v0.4／cdc_bridge v0.4／membus v0.5）も**全て実在版と一致**。①.5 の M-1／M-13 の反省が効いている。

**条件付きとする理由**

§3 の FSM 設計が★**状態遷移図の粒度に留まり、レジスタレベルの設計が無い**★。特に `mem_idx` を `addr` の純配線から `addr + beat_cnt` へ変える改修は、§3.3 の等価性論拠そのものを支える箇所であるにもかかわらず記載がない（M-1）。原則43 に基づき承認の対象とするには情報が不足している。

加えて、C-3（バースト書き非実装）を採る場合の**未定義動作の穴**（M-3）が、設計書自身が R-2 で最も恐れている「静かに誤データを返す」形態と同型である。

## 3. C：確認事項

### C-1 `burst_len = 0` の扱いが未定義

§2.1 は「1 = 従来動作」とするが、**0 が来た場合**の挙動が定義されていない。§3.2 の FSM をそのまま実装すると `PS_BUSY` で「残り」が `0-1` へアンダーフローし、★`BLEN_W` 幅の全域（最大 63 バイト）を転送しようとする★可能性がある。M-1 の `beat_cnt` 設計と併せ、次のいずれかを明記されたい。

- (a) `blen_r <= (burst_len == 0) ? 1 : burst_len;`（**飽和・推奨**。誤要求でも破壊しない）
- (b) 契約として禁止し assertion で検出（M-3・C-1 と同じ枠組み）

### C-2 損益分岐の簡約式と表の数値が一致しない

§1.2 は `h ≒ 1 − 1/S` と書きつつ、表では **32B → 97.4%／64B → 98.7%** としている。式に代入すると **96.9%／98.4%** であり、★0.3〜0.5 ポイントの差★がある。`emu23_cache_base_design_v1_0.md` §3.5 からの引用値と簡約式のどちらが正なのか、あるいは簡約式が定数項を落としているのか、**注記一行で出所を示されたい**。結論（キャッシュ単独は成立しない）は揺るがないが、読み手が再現できない数値は後で検証工数を生む。

### C-3 「1 バイト/psram cyc」という前提が②-B の設計判断を規定する

§1.2 の「バースト有り 約 10 cpu cyc」および B-4 の「総サイクル = LAT+31」は、★**`PS_BURST` が 1 psram cyc につき 1 バイトを出せる**★という前提に立つ。§1.4 で「本 FSM は挙動モデルである」と正しく断ってはいるものの、この前提が★②-B のライン長選択と損益分岐ヒット率（約 60%）を直接決めている★。

工程③で実機 PSRAM（HyperBus 等）の物理タイミングが判明した際に、**この前提が崩れたら②-B の設計判断を再評価する**という条件を §1.4 に明記されたい。「モデルである」と断ることと、「モデルが外れたら何を見直すか」を書くことは別である。

### C-4 KY73 の引用意図

§1.3 は「①.5 では A-2 単独版をネガコンに選んで −7.3% 動いてしまい**失敗**した（KY73）」とするが、memo v0.4 L151 の KY73 の本文は★「単体 TB の**負荷モデルが実ワークロードを代表しない**場合〜」★であり、ネガコン選定の失敗そのものではなく**負荷モデルの代表性**を教訓としている（同一インシデントだが抽出した教訓が異なる）。引用の意図を確認されたい。M-5 の議論とも関係するため、**どちらの教訓を根拠にしているかで §1.3 の主張の強さが変わる**。

## 4. N：推奨事項

### N-1 C-1（assertion の合成対象外扱い）への回答

貴殿の推奨（assertion を置く）を支持します。合成対象外とする方法は次が確実です。

```systemverilog
`ifndef SYNTHESIS
    always_ff @(posedge clk) begin
        if (ps_state == PS_IDLE && req) begin
            if (burst_len > 1 && we)
                $error("PSRAM: burst write not supported (blen=%0d)", burst_len);
            if (burst_len > 1 && (addr[$clog2(BURST_MAX)-1:0] != '0))
                $error("PSRAM: burst must start at line boundary (addr=%h)", addr);
        end
    end
`endif
```

- Gowin EDA は合成時に `SYNTHESIS` マクロを定義するため、上記は**合成対象から確実に外れる**
- Icarus（`-g2012`）では通常通りコンパイルされる
- ★`// synthesis translate_off` 系のコメントプラグマはツール依存で挙動が割れるため、`ifndef` を推奨★

なお M-3 の対応①（RTL で `we && blen_r==1` に限定）と組み合わせると、**シミュレーションでは顕在化し、実機では破壊しない**という二段防御になります。

### N-2 B-4 に「`PS_BURST` 中 `ack==0`」の明示チェックを追加

§5.2 B-4 の期待は「`beat_valid` 32 回・最終のみ `ack`」だが、★「最終のみ」を検証するには**中間 31 beat で `ack==0` であることを能動的に確認**する必要がある★。「最終で ack が立った」だけでは、中間でも立っていた場合を検出できない。TB に `assert (ack == 1'b0)` を `PS_BURST` 期間中に置くことを推奨する。

### N-3 ②-B への申し送りを §1.4 に明記

M-2 の補足で述べた通り、`cdc_bridge_v0_4` L149 の `assign cpu_mem_rdata = psram_rdata;` は**組合せ**であるため、★ブリッジ経由でバーストを流すと beat 毎に `cpu_mem_rdata` が揺れる★。②-B のキャッシュは **`psram_ctrl` に直結**して `beat_valid` を受ける構成でなければ成立しない。§1.4 の非目標「CDC ブリッジのライン転送経路（②-B）」に、この**構造的制約**を一行添えておくと②-B の設計が迷わない。
