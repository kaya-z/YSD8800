## 2. Major（正誤表 v0.1）

### G-1　「OS は BUSY をポーリングして動いている」は誤り。YUI OS の SD 読出しは**完了割込**で動いている

**事実**（実源）
- ドライバは EXEC の前に IRQ を有効にします（Forth L1385 `1 SD-IRQ-CTRL !`）。
- そして EXEC を発行し（L1388 `2 SD-CMD !`）、**完了割込を待って休眠**します（L1390-L1403：割込を禁止してから STAT を再確認し、`TASK-WAIT-IPC-ENTRY`）。
- SD_STAT を読むのは、**完了割込の後の割込ハンドラ**（asm L1663-L1666、2回読み）と、即時に問い合わせる `STOR-STAT-IMPL`（Forth L1535-L1548）だけです。EXEC の進行中に STAT をポーリングするループはありません。
- ysd8003 は、完了時（L725-L726）にも ERROR 時（L736-L737「エラーでも予約：emu23互換」）にも、`IRQ_EN` が立っていれば割込を発生させます。

**影響**
1. 正誤表 §1.3 の「読み取り」と E-2 ②（「直接 EXEC では OS の BUSY ポーリングで成立」）は誤りです。直接 EXEC でブートが正常に動くのは、**OS が STAT を読む時点ではすでに完了（READY）しているから**です。§1.2 の4,989回のポーリングは、**TB（`tb_tktv16f_ready`）がポーリングした値**で、OS の挙動ではありません。
2. **保留 EXEC の経路でも、OS は割込を待って休眠しているので、STAT を読まず、ストールしません**。ストールが起きうるのは、`STOR-STAT-IMPL`（即時問い合わせの IPC）が、進行中の保留 EXEC と重なったときだけです。
3. したがって D-201 が実際に起きる範囲は、正誤表 E-5 の「保留 EXEC の経路に限られる」よりも**さらに狭い**（R-14 の判断材料）。

**是正**（正誤表 v0.2）
1. E-2 ②と §1.3 の「読み取り」を、「OS は完了割込で動く。STAT を読むのは完了後（割込ハンドラ）だけ」に訂正する。
2. §1.2 の注記に「ポーリングは TB が行ったもの」と明記する。
3. E-5 に「OS の定常のフローでは、保留 EXEC でもストールしない。例外は `STOR-STAT-IMPL`」を追記する。
4. §1.3 の「OS の最初の SD アクセス（`addr=0xC`）」は **SD_IRQ_CTRL（$FCAC）← 0**（Forth L1345、ドライバ初期化）と同定できる。366,344 は READ_SETUP（L1374 `0 SD-CMD !`）。設計書 §6.5.9 の「未確認」も解消する。

## 3. 再レビュー論点への回答

| # | 論点 | 回答 |
|---|---|---|
| R-14 | C-2(i)・U-12 の再確認 | ① **C-2(i) は維持できる**。G-1 により、OS の定常のフローでは保留 EXEC でもストールが起きない。そのため、延長（最悪約1.5秒）が利用者から見える影響はほぼ無い（`STOR-STAT-IMPL` との重なりだけ）。② **U-12 は「不要（取り下げ）」を推奨する**。初期化は既にリセット直後に始まっていて、OS の EXEC は完了割込を待つ。どちらの言い換えでも、解決すべき問題が残っていない。残すなら TKT-V18 の検討項目に吸収する。③ 実カードの初期化時間は、**工程③（実機）での実測項目**とする。C-2(i) の根拠は、G-1 により実カードの初期化時間にほとんど依存しなくなった（知らんけど：`STOR-STAT-IMPL` の発行頻度による） |
| R-15 | 正誤表の妥当性 | **G-1 を条件に妥当と判断する**。E-1、E-3〜E-8 の実源の行と実測の根拠は確かで、16,429 clk と L18 の 16.8k の整合や、MMIO トレースでは内部動作を捉えられないという指摘も的確。E-5 の「撤回せず、根拠を訂正して再判定を待つ」扱いも適切。**②の本体は改版せず、正誤表による追補で足りる**。②の完了条件#1（r5.0 承認）は、「正誤表 v0.2 の承認を以て訂正済み」と注記すれば維持できる |
| R-16 | F-2 の是正（v0_7）とそれに伴う OS の ERROR 処理 | **是正は妥当と判断する**。陽性対照（v0_6 では FAIL）と、正常系の回帰がビット一致していることを確認した。OS の ERROR 処理は**存在する**：S_ERROR で完了割込が出て（L736-L737）、ハンドラが STAT を保存し、ドライバは bit2（READY）が0なら ERROR の経路に入る（Forth L1405-L1410）。設計書 §6.5.8 の「未確認事項①」は、この根拠で解消してよい。ただし、ERROR の経路でアプリにどう報告されるか（上位でのリトライの有無）は TKT-V18 で確認する |
| R-17 | 派生元 v0.3 の照合 | **別のファイルだった**。r3.0 でレビューした v0.3 は md5 `57e6e880d6f63fb6…`（296行、L1 は `v0_3`）。v0.4 の派生元は `a7974b4d5c20d57e…`（309行、L1 は `v0_2`）。**v0.3 が2系統存在した**ことになる。内容は v0.5 で収束しているので実害は無いが、台帳に両方の md5 を記録し、「r3.0 の承認対象は 57e6e880、v0.4 の派生元は a7974b4d」と明記すること（版数管理） |
