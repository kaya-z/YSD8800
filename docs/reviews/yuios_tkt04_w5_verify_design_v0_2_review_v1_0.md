## 0. 総評

**前回指摘 M-1〜M-7・C-1〜C-6・N-1/N-2 は全件クローズ**した。実体照合の結果、
反映内容に誤りは無く、特に §2.3・§7 の全面改訂は実源と完全一致していた（E-1・E-2）。
取消線による旧記述保持（KY41）、§8 指摘対応表、§10 別途起票項目の整理はいずれも適切である（E-3）。

新規指摘は 2 件で、**いずれも「実際に走らせると止まる／動かない」種類**のものである。

- **M-8**: §4.4 の `_w5_pc` プレースホルダ `$0530` が**実測値と大きく異なる**（実測 **`$0613`**）。
  `$0530` は一見それらしい値のため、置換を失念したまま実装される危険が高い。
- **M-9**: §4.6 の実行手順は **`c` が停止しない**。W-5 → `_w3` → `TASK_SLEEP` → `_sc_idle`

いずれも設計思想ではなく手順値の問題であり、方式・判定基準・安全根拠には手を入れる必要がない。
よって**条件付き承認**とする。

## 1. 必須修正（M・新規）

### M-8【重大度：高】`_w5_pc` の値 `$0530` は誤り — 実測値は **`$0613`**

**指摘内容**

§4.4 のコード断片は以下となっている。

```asm
    LDW  A, #$0530              ; ★_w5_pc（§4.3 で実測確定した直値に置換）
```

`$0530` は `TASK_CREATE`（`$0520`）の **16 バイト目**であり、L952 の位置ではあり得ない。
L861〜L954 の間に `.org` は無く（実体 grep 済）、次の `.org` は `$0700`（`TASK0_ENTRY`）であるため、
L952 は `$0520`〜`$0700` の**末尾側**に位置する。

**実測（本査読で実施）**

`hasm23 v1.04` をビルドして `kernel_v12_11.asm` を単体アセンブルし、生成された `.dbg`（アドレス／行番号／命令）を確認した。

```
060a 949 LDW  A, [L1_WK_A]           ; ★EIより前にtidを確保
060e 950 LDW  X, [TC_WK_TID]
0612 951 EI
0613 952 SUBI X, #2                  ← ★_w5_pc
0617 953 STW  A, [X]
0619 954 RET
```

シンボル表も整合する。

```
0520 TASK_CREATE
0588 _tc_found
0700 TASK0_ENTRY
```

> **★`_w5_pc` = `$0613`（`EI` は `$0612`、1 バイト命令）★**

**修正案**

```asm
    LDW  A, #$0613              ; _w5_pc = L952 SUBI X,#2（§4.3 手順で実測確定）
```

併せて、**プレースホルダを置く場合は `$FFFF` など明らかに不正な値**とし、
`; TODO: §4.3 手順で実測値に置換すること` を添えること。
`$0530` のような「もっともらしい値」は置換忘れを検出できない。

> **補足**: 本実測は PoC 本ビルド（`hasm23 -c` ＋ `lnk23`、フラグメント連結後）ではなく
> `kernel_v12_11.asm` 単体アセンブルによるものである。`TASK_CREATE` は `.org $0520` 絶対配置のため
> 一致するはずだが、**§4.3 手順 2〜4 は予定どおり実施し、PoC 本ビルドおよび陰性対照カーネルの双方で
> `$0613` を確認**すること（KY34）。

### M-9【重大度：高】§4.6 の実行手順は停止しない — ブレークポイントが必須

**指摘内容**

§4.6 は以下のコマンド列を示す。

```bash
printf 'c\nmem 46a0 32\nmem 4680 16\nq\n' | ./emu23 ...
```

`emu23_v111.c` の `c` コマンドの実装は次の通りである。

```c
/* emu23_v111.c L1677-1680 */
// c  — continue (run until halt or breakpoint)
} else if (cmd[0] == 'c') {
    if (cpu.halted) { printf("CPU is halted\n"); continue; }
    while (!cpu.halted && !is_break(cpu.pc)) exec_one();
}
```

**halt かブレークポイントに到達するまでステップ上限なしで回る。**
（`--wm-steps` による打切りは `-w`＝ウォーターマーク計測モード専用であり、対話 `c` には効かない。）

一方 W-5 は §4.4 で `JMP _w3` により W-3 へ引き継ぐ。W-3 の実体は以下である。

```asm
; vprobe_fragment_poc.asm L426-431（実源）
_w3_go:
    ; TASK_SLEEP を呼ぶ（戻ってこないため、保存結果は _sc_idle 到達前に
    ; TCB へ書かれている。BP で停止して採取する運用とする）
    LDW  X, #$46E0              ; 疑似DSP
    JSR  TASK_SLEEP
    HALT
```

`TASK_SLEEP` は末尾で `_sched_common` へ JMP し、READY 不在のため `_sc_idle`（`EI`/`NOP`/`DI` ループ）へ入る。
**`HALT` には到達しない。** W-3 のコメント自身が「BP で停止して採取する運用とする」と明記している。

したがって §4.6 のコマンドは **emu23 がハングし、`mem` 以降が実行されない**。

**修正案**

`c` の前にブレークポイントを設定する。`emu23` は `b <addr|lbl>` でラベル指定が可能（L1824、`.sym` 参照）。

```bash
printf 'b _w5_land\nc\nmem 46a0 32\nmem 4680 16\nq\n' | \
  ./emu23 yuios_vprobe_poc.bin -i uart_empty.bin --disk disk.img
```

- **`_w5_land` を採るのが最も安全**である。W-5 の判定値（`$46AE`）は L953 で確定済みであり、
  `_w5_land` 到達＝完走そのものを意味するため、W-3 の副作用（TCB の DEAD 化等）を一切受けない。
- `_w3` を BP にしても採取は可能だが、`_w5_land` のほうが「W-5 だけを切り出す」意図に合致する。
- なお `_w5_land` で止めた場合、**完走マーカ `$4686` は BP の直前に書かれる**（`_w5_land` 内の
  `STW A,[$4686]` は BP 到達後の命令）ため、**マーカが未書込のまま採取される**。
  BP は `_w5_land` の**末尾（`JMP _w3` の位置）** に置くか、`_w3` を BP にすること。
  設計書には**どちらを採るか明記**すること（本査読の推奨は `b _w3`）。

## 2. 確認推奨（C）

### C-7 `_w5_pc` の確定手順に `.dbg` の利用を追記すべき

§4.3 は disasm23 実測に一本化しているが、**hasm23 が生成する `.dbg` を使うほうが直接的で誤りにくい**。
`.dbg` は「アドレス／ソース行番号／命令」の3列であり、行番号から一発で引ける。

```bash
awk '$2==952' kf_r2_kern.asm.dbg
# → 0613 952 SUBI X, #2
```

本査読でも disasm23 は `--start 0x0640 --end 0x06FF` で**空出力**となった
（バイナリの収録範囲・パディング扱いに依存するため、範囲指定を誤ると「命令が無い」ように見える）。
disasm23 単独に依存すると、この空出力を「アドレスが違う」と誤読する危険がある。

**修正案**: §4.3 の手順表に「2'. `.dbg` の 952 行エントリで直接確認する（推奨・第一手段）」を追加し、
disasm23 は交差確認の位置づけにする。

---

### C-8 `mem` の第2引数は **10進**である旨を明記すべき

`emu23_v111.c` L1750-1753 の実装は `sscanf(cmd + 3, "%hx %d", &addr, &n)` である。
すなわち**アドレスは16進、バイト数は10進**。

§4.6 の `mem 46a0 32` は `$46A0`〜`$46BF`（32 バイト）で `$46AE` を含み、
`mem 4680 16` は `$4680`〜`$468F` で `$4686` を含むため、**結果としては正しい**。
ただし `32` を 16 進と誤読すると範囲認識がずれるため、表に一言添えること。

---

### C-9 §4.6 の `--disk` / `mkfs_yuifs` は W-5 では不要

W-5 はストレージを一切使用しない（`_w5` / `_w5_fillslp` / `_w5_land` のいずれも SD へ触れない）。
`mkfs_yuifs_v1_1.py` によるディスクイメージ生成と `--disk disk.img` は W-5 の必須要素ではない。

**修正案**: 手順を簡素化するか、「W-1／W-4 と同一コマンドで実施することにより
**両者の実行環境差をゼロにする**ため踏襲する」と理由を明記する。後者なら現状のままでよい。

## 3. 情報（N）

- **N-3**: `_w5_pc = $0613` は**奇数アドレス**である（`EI` が 1 バイト命令のため）。
  命令フェッチにアライメント制約は無いので問題ないが、`saved_pc` に偶数前提を置いた記述が
  他文書にある場合は注意。`_sc_found` は `saved_pc` を `[SP+2]`（偶数）へ格納するだけなので影響なし。
- **N-4**: 本査読の実測で得た配置は `TASK_CREATE=$0520` / `_tc_found=$0588` / `TASK0_ENTRY=$0700` であり、
  設計書 §4.3-1 の「`.org $0520` 固定」および `kernel_v12_11.asm` L210 のメモリマップ注記
  「`$0520-$073F TASK_CREATE`」と整合する。

## 4. 評価（E）

- **E-1**: §2.3 の因果改訂は実源 L496-498 と完全一致。取消線で旧記述を保持しており **KY41 準拠**。
  「`$F87E` は構造的必然ではない」という §2.4 の含意まで導いて R-1 の判断根拠と接続した点が良い。
- **E-2**: §7 の全面改訂は実源で全項目を検証した結果、**誤り無し**。
  特に §7.2 の安全根拠 2（`saved_sp = SP+4` により HW push 域は `$46EC`/`$46EE` に落ち、
  `[$46F0]` が保全される）は、SP 収支を 1 語単位で追わないと出てこない指摘であり、精度が高い。
  「対策」ではなく「成立根拠」として書き分けた構成も、KY 記録として正しい形である。
- **E-3**: §8 レビュー指摘対応表と §10 別途起票項目の分離は良い。
  設計書のスコープ内（M/C 反映）とスコープ外（DOC-A〜C）を混ぜずに整理できている。
  特に DOC-A を「**実装着手前に実施**」と優先度付けした点は、C-2 の趣旨を正しく汲んでいる。
- **E-4**: §3.3 に「検証しないこと」の行を設けた責務分界（N-2 反映）は、
  将来「W-5 が PASS だから TKT-01 も検証済み」と誤読されるのを防ぐ良い記述である。
