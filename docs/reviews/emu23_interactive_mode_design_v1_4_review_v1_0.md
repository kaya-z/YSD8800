## 0. 総評

**前回指摘 M-1・M-2・C-1〜C-4 および EMU-E 申し送りは全件クローズ**した。
反映の質が高く、特に 2 点を評価する。

- **C-3 への対応**が「`IGNBRK` を足す」で終わっていない。
  §3.1.1 に **「本チケットはそもそも『フラグ群を網羅的に規定していなかったこと』自体が原因であり、
  是正版で再び網羅性を欠くのは同じ失敗の反復にあたる」**と原理を書いたうえで、
  **`cfmakeraw(3)` の 8 フラグを完全包含＋`INPCK` を上乗せ**という構成に整理した（E-1）。
- **M-2 への対応**が指摘より一歩踏み込んでいる。後始末について
  「CR 1 回で十分・BS 送出は不要」を **`SH-READLINE` 入口 L3145 の `0 SH-LINE-LEN !` を根拠に確定**させた（E-2）。
  実源を確認したところこの判断は正しい（N-2）。

新規の必須指摘は **1 件のみ**である。

- **M-1**: **§4「変更ファイル一覧」に TKT-03（v1.12）の変更行が無い。**
  §4 は v1.09 実装時点の表のままで、**本版で実装すべき範囲が §4 から読めない**。

## 1. 必須修正（M）

### M-1【重大度：中】§4「変更ファイル一覧」が v1.09 実装時点のままで、TKT-03 の変更が載っていない

**指摘内容**

§4 の表は次の 8 行で構成されており、**すべて v1.09（`-it` 新設）時点の内容**である。

```
| emu23_v1XX.c | #include <termios.h> 追加                        | 1行     |
| 同上         | enable_raw_mode() / disable_raw_mode() 新設       | 約20行  |
| 同上         | ysd8001_poll_rx_interactive() 新設                | 約20行  |
| 同上         | cleanup_on_exit() 新設・atexit/signal登録         | 約10行  |
| 同上         | -it モード用メインループ追加                       | 約12行  |
| 同上         | ysd8001_tick() 内の呼び出しを関数ポインタ経由に変更 | 1行変更 |
| 同上         | オプション解析に -it 分岐・排他チェック追加        | 約6行   |
| 同上         | ヘルプ文字列追記                                   | 2行     |
```

**TKT-03 の変更（`it_enable_raw_mode()` への `c_iflag` 2 行追加）が 1 行も無い。**

ヘッダのステータスは「**v1.4 レビュー指摘反映済・実装着手可**」であり、
これから `emu23 v1.11 → v1.12` を実装する段階にある。
その状態で「変更ファイル一覧」が**前回リリースの内容しか載せていない**のは、
**実装スコープが表から確定できない**ことを意味する。

実装者は §3.1.1【改訂版コード】を見れば正しく実装できるので実害は限定的だが、
原則43（設計→レビュー→承認→実装）において
**承認の対象＝実装範囲**を明示する節が §4 である以上、ここは埋めるべきである。
また変更規模が表にないと、実装後のレビューで「設計どおりの範囲か」を照合できない。

**修正案**

§4 を版ごとに分割し、旧記述を保持したまま本版分を追加する（v1.4 の編集方針に合わせる）。

```markdown
# 4. 変更ファイル一覧

## 4.1 v1.09 実装時（-it 新設・記録保持）
（現行の 8 行の表をそのまま残す）

## 4.2 ★v1.12 TKT-03 の変更（本版で実装する範囲）★

| ファイル | 変更内容 | 変更規模 |
|---|---|---|
| emu23_v111.c → emu23_v112.c | `it_enable_raw_mode()` に `raw.c_iflag &= ~(IGNBRK\|BRKINT\|PARMRK\|ISTRIP\|INLCR\|IGNCR\|ICRNL\|IXON\|INPCK);` を追加 | **2行追加** |
| 同上 | バージョン表示文字列を v1.12 に更新 | 1行変更 |
| 同上 | 変更履歴コメント（ファイル冒頭）に TKT-03 を追記 | 数行 |

**本版の変更は `it_enable_raw_mode()` 内の 2 行のみ**であり、
`-q` / `-i` / 既定モード（Dhrystone・`yuios.bin` 生成）は本関数を通らないため非回帰である（§3.1.1【スコープ限定】）。
```

バージョン表示の更新は、プロジェクト規律
「開発ツールを開発・修正した際は起動時にバージョンが分かるように表示する」に対応する項目であり、
**表に載せておかないと実装漏れになりやすい**ので明示を推奨する。

## 2. 確認推奨（C）

### C-1 §3.3 のコード例が使う `it_mode_should_exit` は確定実装の変数名と異なる

§3.3（v1.1 原案・記録保持）のメインループは `while (!cpu.halted && !it_mode_should_exit)` を使うが、
§3.2 の確定実装（v1.2）および `emu23_v111.c` の実際の変数名は **`it_should_exit`** である。

§3.3 に追加された v1.4 注記（C-2 対応）は読み替え対象として
`it_enable_raw_mode()` / `it_disable_raw_mode()` / `it_orig_termios` / `it_raw_mode_active` の
**4 つの関数・変数名を挙げているが、`it_should_exit` が入っていない**。

**修正案**: 注記の読み替えリストに `it_mode_should_exit` → **`it_should_exit`** を追加する。

---

### C-2 ヘッダ「対象ツール」欄が「本版 v1.3」のまま

ヘッダ表の対象ツール欄が次のままである。

> **emu23 v1.11 → v1.12（本版 **v1.3** で TKT-03 を追加。版数確定は B-C と同時＝Phase B' 完了時）**

C-1（前回）で文書末尾の版数は v1.4 に是正されたが、**ここが残っている**。
「本版 v1.4 で…」または「v1.3 で TKT-03 を追加・v1.4 でレビュー指摘反映」に是正すること（KY41 4 点整合）。

---

### C-3 T03-N の期待結果にも「改行だけがエコーされる」を加えるとよい

§5.1.2.1 で T03-2 について書かれた副次的価値——
「LF がエコーされて画面に改行が出ること自体が、LF が UART RX へ届いた証拠である」——は、
**T03-N にもそのまま当てはまる**。

T03-N（改修前・`ver` + CR）では `ICRNL` により CR が LF に変換され、
その LF が `SH-READLINE` の ELSE 分岐でエコーされる。したがって観測されるのは
**「無反応」ではなく「改行だけが出る」**である。

期待結果を「応答なし」だけにしておくと、
**「emu23 が固まっている／ブートが完了していない」との区別がつかない**。

**修正案**: T03-N の期待結果を
「`YUIOS V0.10.18` の応答は返らないが、**改行だけがエコーされる**（＝入力自体は届いている）」
と精密化する。T03-2 と同じ論法であり、症状再現の確度が上がる。

---

### C-4 §3.1.1 表の「既定」欄を実際の既定値で書くとよい

【規定】表の「既定」欄が `INPCK` / `PARMRK` / `BRKINT` / `IGNBRK` / `ISTRIP` で
一律「環境依存」となっている。Linux の一般的な tty 既定は次のとおりで、区別できる。

| フラグ | Linux の一般的な既定 |
|---|---|
| `ICRNL` / `IXON` / `BRKINT` | **有効** |
| `IGNBRK` / `INLCR` / `IGNCR` / `ISTRIP` / `PARMRK` / `INPCK` | **無効** |

落とす対象である以上どちらでも結果は同じだが、
**T03-N で何が観測されるかの予測**（→ C-3）に効くので、判明している範囲は実値で書くほうがよい。

## 3. 情報（N）

- **N-1**: `IGNBRK` / `BRKINT` / `PARMRK` をすべて落とした場合、BREAK は `\0` 1 バイトとして読まれる。
  §3.1.1 の表の記述「`BRKINT` と併せて落とすことで BREAK は `\0` として素通しされる（`cfmakeraw(3)` と同一の扱い）」は
  termios の規定どおりで正しい。
- **N-2【M-2 対応の根拠確認】**: 「CR 1 回で確実に初期化される・BS 不要」という結論は正しい。
  `SH-READLINE` 入口の `0 SH-LINE-LEN !`（L3145）で行長がリセットされる。
  `SH-LINE-BUF` の中身自体はクリアされないが、`C!` は常に `BUF + SH-LINE-LEN` へ書き、
  CR 確定時に同位置へ NUL を置く（L3149）ため、**長さのリセットだけで十分**である。
- **N-3**: T03-N と T03-1 は**別バイナリ＝別プロセス**であるため、
  T03-N が残した行バッファ内容が T03-1 を汚染することはない。
  §5.1.2.1 が問題にしている汚染は**同一ラン内での T03-2 → 後続**に限られる。
  この区別を 1 行添えておくと、手順の意図がより明確になる。
- **N-4**: T03-3 のコマンド `emu23 yuios.bin -q --disk disk.img` は
  emu23 の引数順序規律（`emu23 prog.bin [options]`）に適合している。

## 4. 評価（E）

- **E-1**: C-3 への対応が模範的である。単に `IGNBRK` を追加するのではなく、
  **「本チケットは網羅性の欠如そのものが原因であり、是正版で再び網羅性を欠くのは同じ失敗の反復」**
  という原理を §3.1.1 に明記したうえで、
  **`cfmakeraw(3)` の 8 フラグを完全包含＋`INPCK` 上乗せ**という**根拠のある集合**に整理した。
  「なぜこの 9 個なのか」が後年でも追跡できる形になっている。
- **E-2**: M-2 への対応が指摘を超えている。査読側は
  「CR 送出でバッファ破棄、あるいは BS を LF の分だけ送る」の 2 案を挙げたが、
  設計書は **L3145 の `0 SH-LINE-LEN !` を実源で確認して「BS は不要」と確定**させた。
  選択肢を残さず一意に決めており、手順書として正しい形である。
- **E-3**: 副次的価値（LF のエコー＝到達証拠）を §5.1.2.1 に取り込んだ点。
  査読の付随的コメントを**判定の識別性向上**という形で本文に定着させている。
- **E-4**: EMU-E を「本文注記＋別チケット起票推奨」として扱い、
  **スコープ外を明示しつつ論点を消滅させない**処理をした点。
  「本版では変更しない」と実装方針まで書き切っているので、実装者が迷わない。
- **E-5**: M-1 の是正で、単に取消線を引くだけでなく
  **「§2.2 は『前提・制約』として §3 より上位に読まれるため、
  ここを根拠に真 EOF 終了を復活させると v1.2 で潰した回帰を再発させる」**
  という**なぜ危険か**を残した点。将来の編集者が §2.2 を軽々に戻さないための抑止になっている。
