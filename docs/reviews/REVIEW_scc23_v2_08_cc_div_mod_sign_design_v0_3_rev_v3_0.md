## 3. C級指摘

### C-1【任意】`LDW X,#0` をガード前へ移せば `CMPI A,#0` を1本削減できる

現行 §3.3 は `CMPI A,#0` を2回実行している。

```
    PUSH X
    CMPI A, #0          ← 1回目（ゼロ除算ガード用）
    BEQ  _ccdiv_zero
    LDW  X, #0          ← Z/N を破壊する（ISA 付録A: 0x21 の FLAGS = Z/N）
    CMPI A, #0          ← 2回目（符号判定用・1回目の結果が使えないため必要）
    BGE  _ccdiv_apos
```

`LDW X,#0` をガードより**前**へ移すと、1回の `CMPI` で `BEQ`・`BGE` の両方を賄える。

```
    PUSH X
    LDW  X, #0          ; 符号フラグ初期化（この時点のフラグは次の CMPI が上書き）
    CMPI A, #0
    BEQ  _ccdiv_zero    ; 除数0 → 経路C
    BGE  _ccdiv_apos    ; 除数が正 → 絶対値化不要
    XORI X, #1
    NOT  A
    ADDI A, #1
_ccdiv_apos:
```

**安全性の根拠**：`BEQ`(0x61) は ISA 付録A で **FLAGS = `—`**（フラグ不変）。
したがって `CMPI` が設定した Z/N は `BEQ` を跨いで `BGE` まで生き残る。
ゼロ除算経路では X=0 が設定済みとなるが、`_ccdiv_zero` は X を参照しないため無害。

**効果**：`CMPI`(4B) が各ルーチン1本ずつ減り、**−8 B・呼出あたり数サイクル**。

**判断**：採否は任意。現行形は「ガード用」「符号判定用」の意図が命令列に明示されていて
読みやすいという利点があり、「1変更1検証」の観点から**今回は現行のまま**とし、
**採用する場合は §4.3 の全20ケース実測で担保する**という判断も妥当である。
**レビュアとしてはどちらでも承認する。**

### C-2【計数誤り・当方 v2.0 の誤り由来】`print_num(20)` の `_cc_div` 呼出回数

**該当**：§4.2-1 第2項「`print_num(20)` は再帰1段、すなわち `_cc_div` 2回・`_cc_mod` 2回のみ」

正しくは **`_cc_div` 1回・`_cc_mod` 2回**である。

```c
void print_num(int n) {
    if (n >= 10) print_num(n / 10);   /* n=20 のとき 20/10 → _cc_div ×1 */
    putchar('0' + n % 10);            /* n=20 で ×1、n=2 で ×1 → _cc_mod ×2 */
}
```

- `print_num(20)`：`20 >= 10` は `CMPI`/`BGE` であり除算ではない。`20 / 10` で **`_cc_div` ×1**。
- `print_num(2)`：`2 >= 10` が偽なので除算なし。`2 % 10` で **`_cc_mod` ×1**。
- `print_num(20)` に戻り `20 % 10` で **`_cc_mod` ×1**。

**この誤りは当方が v2.0 指摘書 B-5 で「`_cc_div` 2回・`_cc_mod` 2回」と記述したものを
v0.3 がそのまま引き継いだものである。当方の検証不足であり、訂正しておわびする。**

なお §4.2-1 の**結論は変わらない**。いずれも測定区間外・オペランドは正であり、
PASS条件「数値出力の完全一致」の成立根拠に影響しない。

### C-3【重複】`-32768 / 1` が2つの表に重複している

§2.2 の「追加ケース」表の4行目（`-32768 | 1`・反復回数の最悪値）と、
「境界ケース：INT_MIN」表の2行目（`-32768 | 1`）が**同一ケース**である。

したがって §4.3 の「**全20ケース**（基本7＋ゼロ除算2＋追加4＋境界7）」は重複込みの計数であり、
**ユニークなケースは19**。

**対応（いずれでも可）**：
- 追加ケース表の該当行に「※境界ケース表と同一。最悪反復数の根拠として再掲」と注記する、または
- §4.3 を「全20ケース（うち1件は再掲・ユニーク19）」と明示する。

実測時に同一ケースを2回測っても害は無いため、**注記だけで足りる**。

### C-4【出典誤り・当方 v2.0 の誤り由来】バイト長表の `RET` の出典

**該当**：§4.2-3 バイト長表の最終行「`RET` | 1 | 同 L428 近傍」

直前行の出典が `hasm23_v1_04.c` L465-467 であるため「同」は `hasm23_v1_04.c` を指すが、
`RET` のバイト数はそこには書かれていない。

**正しい出典**：`ISA2_3_v231.docx` 付録A の `0x69 | RET | 1 | PC←pop | —` 行。

**この出典指定も当方が v2.0 指摘書 B-4 の表に書いたものをそのまま引き継いだものである。
当方の誤りであり、訂正しておわびする。値（1バイト）は正しい。**

### C-5【軽微】`_cc_mod` のループ行番号

§3.2 は「既存ループ本体（`_cc_div` L3901-3911、`_cc_mod` **L3925-3933**）」とするが、
`_cc_mod` のループは **L3926-3933**（L3926 が `_ccmod_loop:`）。
L3925 は `STW B, [_C_DIV_B]` でループ外。1行のズレ。

### C-6【表記】スタック収支表の「経路N'」

§3.3 のスタック収支表は「経路N」「経路N'」「経路C」の3行だが、
経路N' は `_ccdiv_done` 内の `BEQ _ccdiv_ret` による分岐であり、
**経路N の内部分岐**であって独立した出口経路ではない。

「全3経路」という本文記述と表の行数が一致しているため実害は無いが、
§3.4 の `_cc_mod` 側には対応する行が無く非対称になっている。
表を「経路N（符号付与あり／なし）」「経路C」の2行に整理するか、
§3.4 側にも同じ粒度で記載するか、どちらかに揃えることを推奨する。

- **§3.7 の警告コメント出力を忘れないこと**（設計書 §5-6 にもあるが、
  生成 asm 側の出力は実装時に最も落ちやすい）。
- **`_cc_mod` を `_cc_div` からコピーして作らないこと**（設計書 §5-3）。
  除数側の `XORI X,#1` の有無が唯一かつ致命的な差分である。
- **`-32768 / 1` の 32768 反復**は emu23 の実行ステップ上限に触れる可能性がある。
  §4.3 で測定する際、打切り設定を事前に確認しておくこと
  （`emu23_debug_manual_v1_8.md` 参照）。
- 実装後に設計と実装の差分が生じた場合は、**v0.4 として再レビューに戻すこと**
  （§4.1 のスモークテスト NG 時の扱いと同様）。
