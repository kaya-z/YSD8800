## §3. 詳細

### 3.1 M-4：`MAX_CYCLES` の値が未定義

D-5 は「異常終端は `MAX_CYCLES` 到達のみとする」と定めたが、その値が本書にない。
本番 TB の既定値は ★phase-1 用の `1_000_000`★ である（`tb_cpu_v8b_prod_v0_3.sv` L104）。

- U-4 の見積り「emu23 48,785 cycle の数倍〜十数倍」＋ UART 送出待ち約 37,500 cycle（N-2）
- 十数倍側に振れると 1,000,000 に近接し、★TIMEOUT で測定不能になる★

**要求**：§4.2 D-5 または §5.1 T-2/T-3 に
★`MAX_CYCLES = 10_000_000`（phase-2 相当）を既定とする★ と明記せよ。
U-4 の試走結果が想定を大きく超えた場合の引上げ手順（phase-3 = 100,000,000）も
1 行添えると再現時に迷わない。

### 3.2 C-6：判定器の数え上げ漏れ（KY95 の自己適用）

§4.1 は本番 TB の判定器を 5 件挙げたが、★6 件目がある★。

| 実源 | 内容 | Dhrystone での挙動 |
|---|---|---|
| L442-452 | ★失敗マーカー早期検出（`'i'`=$69 / `'g'`=$67 / `'v'`=$76）★。`m2_reached` ゲート | 出力 9 バイト（`N = 1 0 \n P : 2 0`）に i/g/v は無く ★誤発火はしない★ |
| L512-516 | 上記検出時の `finalize_and_exit(0)` | 同上 |

★誤発火はしないが、D-2 で `m2_reached` を削除すると本ブロックはコンパイル不能になる。★
D-2 の「M-1〜M-5 を撤去」の内訳に ★失敗マーカー検出も含む★ ことを明記せよ。
KY95（判定器の全数を数え上げてから差分を確定する）を本書自身に適用する形になる。

### 3.3 Q-3 への回答：CL-3 SP assert の撤去は妥当かつ必須

`tb_cpu_v8b_prod_v0_3.sv` L474-481：

```
if (cpu_rst_n && m1_reached && !cl3_sp_checked && dbg_sp == 16'h477E)
```

- `$477E` は `kernel_v12_8.asm` の `KERN_SP_TOP`（L303 コメント）。Dhrystone の SP は `$F7FE`（ハーネス L88）
- `m1_reached` ゲートのため ★残しても誤発火はしない★ が、D-4 で `m1_reached` を消す以上 ★撤去は必須★

**過不足の判定：D-4 は妥当。** 不足は §3.2 の失敗マーカー 1 件のみ。

### 3.4 C-7 / Q-2 への回答：C-total / C-body の扱い

★C-5 の要求は満たしている。★ ただし定義精度に 1 点。

C-first は ★`'N'` の送信「開始」時点★ である。したがって C-body には
`"=10\n"`（4 バイト）の送出待ちが残る。N-2 の実測値で ★4 × 4167 ≒ 16,668 cycle★ になる。

- **簡易案**：C-body の定義に「`"=10\n"` の送出待ち約 16.7k cycle を含む」と注記する
- **推奨案（N-3）**：★9 バイト全ての TX 発生 cycle を配列に記録する。★
  そうすれば `C_TX('P') − C_TX('\n')` で ★Dhrystone ループ本体＋`'\n'` 送出待ち 1 文字分★ を
  事後に切り出せる。TB 側の実装コストは配列 1 本であり、差分最小方針に反しない

### 3.5 N-1 / Q-1 への回答：P-7 は正しい。加えて P-17 を追加せよ

**Q-1：`"N=10\n"` ＋ `"P:20"` ＝ 9 バイトで正しい。** 実源で確認した（`dhry_timer.c` L625, L551-554）。

★さらに重要な事実が 1 つ未記載である。★ `putchar` は TX レディをポーリングする。

```
scc23_v2_07.c L3648-3656:
  _putchar:
  ...
  _putchar_wait:
  ...
      BEQ  _putchar_wait
```

これは J-2（UART 出力一致）の妥当性の ★根拠そのもの★ である。
ビジーウェイトが無ければ、RTL の実速度では ★文字落ちが起き、その落ち方が CEN=0/1 で
異なりうる★（＝ J-2 が速度依存の判定器に化ける）。
`_putchar_wait` の存在により、★9 バイトは必ず全て出る★ ことが保証される。

**要求**：P-17 として §1.1 に追加し、§6.1 J-2 から参照せよ。
「判定器に速度依存を持ち込まない」という本計画の一貫した方針の裏付けになる。

### 3.6 N-2：UART 送出待ちの定量値

C-5 の影響は無視できる量ではない。実源で確認した。

| 事実 | 実源 |
|---|---|
| ★`TX_CYCLES = 4167`（1 文字あたり）★ | `ysd8800_ysd8001_v0_1.sv` L138 |
| TX ダウンカウンタ：`wr_tx` で `TX_CYCLES` をロードし、`tx_busy` 中はデクリメント | 同 L252-259 |
| `UART_BAUD`（リセット値 416）は ★本版では保持のみで動作影響なし★ | 同 L69, L145 |

★9 バイト × 4167 ≒ 37,500 cycle★（＋ポーリングループのオーバーヘッド）。
emu23 実測 48,785 cycle と ★同オーダー★ である。

- この 37,500 は ★MMIO アクセスであり、キャッシュの影響を原理的に受けない★（`is_mmio = addr >= $FC80`・P-15）
- CEN=0/1 で共通の定数として ★分母のみを膨らませ、削減率を過小に見せる★
- RTL 総サイクルが仮に 500k なら ★約 7.5% の希釈★

**要求**：§5.2 に上記の数値と「MMIO はキャッシュ非対象であるため削減の対象外」である旨を明記せよ。
§6.2 O-1（フェッチ由来の削減比率）を解釈する際、この定数を差し引かないと段6 との比較を誤る。

### 3.7 Q-4 への回答：N-1 の扱い

★妥当。支持する。★
J-3（`'P'` ＝ `dhrystone()` の内部自己検証）は Dhrystone が本来持つ検証機構であり、
これが通れば主要な大域変数群は期待値に一致している。
通常時にチェックサム比較を重ねるのは冗長であり、§8-3 に異常時手段として保持する判断が適切。
