## 総評

起点ソース `scc23_v2_01.c` を実ソースで照合した結果、本設計書の前提（§0.3: peephole 基盤=方式B 実装済み・P2a/P2b 実装済み・P3/P1/P4 未実装、§3.5: -O1 のみ作動）は**すべて実コードと一致**している。中核論証も妥当である:

- §1.4／§4: 加算の可換性 `B₀+A₀ = A₀+B₀` により、置換後 `ADD A,B` の **A 最終値・FLAGS（Z/N）が置換前と完全同値**であり、唯一のリスクは **B の値が変わる（B が live なら不正）** ことだけ、という核心の捉え方は的確。
- §3.2 G4 の固定窓 dead 証明（B 再定義を窓内で積極証明できた時のみ置換、未確定は非置換）は安全側に閉じており妥当。
- §4 の「P3 はフラグ専用ガード不要（両者とも最後に ADD が Z/N を同値で確定）」も正しい。

ISA2.3 命令意味論（§1.2: `ADD`=Z/N更新、`MOV`=フラグ不変）も実仕様（`ISA2_3_v231.docx` 0x40/0x20）と一致を確認済み。

以上より本設計は基本的に良好で、下記 M-1 と N-1 を反映すれば実装着手に進める段階と判断する。

## N-1【軽微だが実害あり・要修正】§3.3 境界の分岐命令リストが ISA2.3 と不一致

**箇所**: §3.3「境界（dead 証明を打ち切り非置換とする）」の分岐命令列挙

**現状記述**: 「分岐命令 `JMP` / `BEQ` / `BNE` / `BMI` / `BPL` 等」

**問題（実仕様で確定）**: `ISA2_3_v231.docx` の命令表を確認した結果、ISA2.3 の制御フロー命令は以下が全てである。

| OP | 命令 | 条件 |
| --- | --- | --- |
| 0x60 | `JMP rel16` | 無条件 |
| 0x61 | `BEQ rel16` | Z=1 |
| 0x62 | `BNE rel16` | Z=0 |
| 0x63 | `BLT rel16` | N=1 |
| 0x64 | `BGE rel16` | N=0 |
| 0x68 | `JSR imm16` | 無条件 |
| 0x69 | `RET` | — |
| 0x04 | `IRET` | — |

すなわち:
- **`BMI` / `BPL` は ISA2.3 に存在しない**（条件分岐は Z/N ベースの BEQ/BNE/BLT/BGE のみ。`BMI/BPL/BGT/BLE` 等は非実装）。
- **実在する `BLT` / `BGE` が §3.3 のリストから抜けている**。

この不一致は安全側に倒れる保証が無い。G4 は「窓内で B 再定義を積極証明できた時のみ置換」だが、**`BLT`/`BGE` を境界として認識しないと、窓内に `BLT`/`BGE` が在るのに dead 証明を打ち切らず、分岐先で B が live な経路を見落として置換してしまう**穴になり得る（§1.4 の B live 不正置換＝値破壊）。`BMI/BPL` という存在しない名前を書いていることは、実在分岐の取りこぼしと表裏一体である。

**対応案（いずれか）**:
- (推奨) 字句で網羅:「**`JMP` および `B` で始まる全ニーモニック（BEQ/BNE/BLT/BGE）、`JSR`/`RET`/`IRET` を境界とする**」と書き、将来 ISA に分岐が増えても `B*` で捕捉できるようにする。ただし `B` で始まる非分岐（例: ISA2.3 の `BRK` 0x06）を除外する注記を付すこと。
- (代替) ISA2.3 実機の分岐ニーモニックで確定列挙:「`JMP` / `BEQ` / `BNE` / `BLT` / `BGE` / `JSR` / `RET` / `IRET`」。`BMI`/`BPL` の記載は削除。

KY39（使用前に実ソース内での存在を確認）に照らし、存在しない命令名を設計書に残さないこと。

## M-1【必須】P2→P3 のパス順序相互作用を検証計画に追加

**箇所**: §3.4 補足（P2a→P2b→P3 の順で適用）、§5 検証計画

**問題**: 本設計は P3 を P2a/P2b の**後段**に置く（基盤 `peephole_pass()` 内で P2a→P2b→P3）。これは「P2 が冗長 MOV / dead store を除去した後の素直な命令列に P3 を当てる」意図で妥当だが、**パス順序依存は peephole の典型的な落とし穴**であり、設計書に「相互作用で取りこぼし／誤拾いが無い」ことの実証計画が無い。

静的に読む限り問題は出ない（下記の自分の分析）が、これは机上判断であり、実証が要る。

- P2b の dead store 除去対象は「A を書く命令(`MOV A,reg`/`LDW A,..`)直後に、**A を読まず A を上書き**する命令」。P3 対象ペアの後者 `MOV A,B` は **source に B を含む**ため、起点ソース `scc23_v2_01.c` の `overwrites_A_no_read()` は `MOV A,B` を「A を読む」と見て**偽**を返す（`src[0]=='A'` 等の判定）。したがって **P2b が `ADD B,A; MOV A,B` ペアの `MOV A,B` を除去することはない**と読める。
- P2a は「完全同一連続 MOV」のみ対象で、`ADD B,A; MOV A,B` には作用しない。

→ よって P2 が P3 対象ペアを破壊する経路は無さそうだが、**実測 35 例が P2 適用後にいくつ残るか**は実機で確認すべき（P2 が周辺の dead store を消すことでペアの 3 命令目以降が変わり、G4 窓走査の判定が変化する可能性がある）。

**対応案**: §5 検証計画に次を追加。
- **V3'**: P2a/P2b 適用**後**の命令列に対して P3 が、実測 35 例（うち dead 確定 29 例）を取りこぼし・誤拾いゼロで処理することを `*_poc`（KY38）で確認。特に「P2b が周辺 dead store を除去した結果、G4 の固定窓 W=6 内の B 再定義到達が変わらないか」を目視確認する。
- G4 の窓走査は §3.4 のとおり P2 完了後（前詰め確定後）の配列に対して読み取り専用で行う旨を、検証項目としても明記。

## N-2【軽微】§2.3 JSR 越え例の ABI 根拠を一行補強

**箇所**: §2.3（`JSR _putchar` 1例）、§3.3 境界（JSR/RET）

**問題**: `JSR` を「呼出規約依存・保守的に非置換」とした結論は正しいが、YSD8800 ABI で B レジスタが caller-saved か callee-saved かの**根拠引用が無い**。

**対応案**: `YSD8800_ABI_spec` の B レジスタ保存区分を一行引用し、「B が呼び出し先で破壊され得る（または保存される）ため、いずれにせよ JSR 越えは保守的に dead 証明を打ち切る」と根拠づける。結論（非置換）は変更不要。

## E-1【軽微・確認のみ】絶対ゲート値・cycles 記載は実台帳と一致

**箇所**: §5 V1（826/48405/P:20）、§5 V4（「48055 から更に短縮」）

**確認結果**: `tool_version_ledger`（v1.7）および設計書 `scc23_v2_00_design_v2_7.docx` §9.2.10 と照合し、**-O0-strict 絶対ゲート 826/48405/P:20、-O1 で v2.01 が達成した 48405→48055 はいずれも正**。V4 の「48055 から更に短縮されるはず」という期待は、v2.01 の -O1 cycles=48055 を起点とする記述として整合している。**本項は修正不要**（前バージョンレビューで数値の出所を疑った点は、起点 v2.01 実在の確認により解消）。

念のための要望: V4 で得た P3 後の新 cycles は、v2.02 の新基準として `tool_version_ledger` v1.8 へ記録すること（§8 に記載済みのため確認のみ）。
