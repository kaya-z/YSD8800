## §0. 総評

§15（B-20・C-24・R-11 付帯条件の反映）は**承認**する。

§16 は、300 秒制限の実測（C-0 212.6 秒・C-2 295 秒タイムアウト・外挿 309 秒）と、`nohup`/`setsid` が永続化しないことの確認まで含めて、**断念の根拠は丁寧に取れている**。
§16.4 で「失う忠実度」を自分から書き出しているのも良い。

しかし、**「M-5（"0123MD"）まで走らせる必要がある」という前提自体が検証されていない**。この前提を外すと、**本番カーネルのまま 300 秒に収まる**見込みがある（A-5）。
加えて、v1.4 の B-20 に**レビュー側の誤り**があったことが実源で判明した（§4）。判定⑥の位置づけに直接影響するので、B-21 として併せて是正する。

## §1. ★A級指摘★

### ★A-5★ 「"0123MD" まで待つ」は M-10 の必要条件ではない — 本番カーネル＋「YUI> 起点」で 300 秒に収まる見込み

**事実**

| 事象 | サイクル | 出典 |
|---|---|---|
| 最初の `"YUI> "` | **356,663** | `yuios_rtl_boot_reproduce_procedure_v1_1.md` L464（旧 RTL での実測） |
| `"0123MD"`（マウント完了） | 3,754,937（現行・M-0） | §14.3.1 |

本番カーネルでは、シェルは **マウント完了の約 10 分の 1 の時点で入力を受け付けられる**。
シェルの入力経路（`SH-KEY` → IPC → UART ドライバ、L3141）は STOR／FILEMGR に依存しない。

§16.7 は派生カーネル用に、対話開始トリガを「最初の `"YUI> "`」へ変更している。**同じ変更を本番カーネルにそのまま適用できる**。

**所要時間の見積り**（根拠つき・実測で確認すること）

| 区間 | サイクル | 秒（C-2 実測 12,000〜14,000 cycle/秒） |
|---|---|---|
| リセット〜最初の `"YUI> "` | 約 0.36M | 約 26〜30 |
| 対話①〜③（TX 約 60 バイト＋RX 13 バイト。1 バイト 4170 サイクル）＋シェル処理 | 約 0.5〜1.0M | 約 36〜83 |
| **合計** | **約 0.9〜1.4M** | ★**約 60〜115 秒**（300 秒の半分以下）★ |

注：`"YUI> "` の到達サイクルは旧 RTL での値であり、現行（ysd8001_v0_3・素版）では多少ずれる。数値は見込みであり、**実測で確認すること**（知らんけど）。

**本番カーネル＋YUI> 起点の利点**（派生カーネル方式との比較）

| 観点 | 派生カーネル（§16） | ★本番＋YUI> 起点（本提案）★ |
|---|---|---|
| 被試験バイナリ | 新規ビルド（md5 管理・出力名衝突回避が必要・§16.6） | **`yuios_road2.bin` そのもの**（md5 `599a7f9d`） |
| B-18（ISR 遅延）の負荷 | 本番より**軽い**（§16.4） | ★**本番より重い**。マウント処理（STOR の SPI 転送・FILEMGR）と対話が同時に走る★ |
| 使用禁止コマンド | `run`/`ls`/`cat`（§16.5） | 同左（マウント途中のため）。ただし理由が「未起動」ではなく「未完了」 |
| 本番方式 M-10 の持ち越し（R-16） | 発生する | ★**発生しない**★ |

★B-18 について：派生カーネルは「緩い条件で合格」だが、本提案は「**実機のペースト時より厳しい条件**」で試験できる。検証の向きが逆になる。★

**本提案で新たに生じる課題とその処置**

| 課題 | 処置 |
|---|---|
| マウント中のマーカー `0` `1` `2` `3` `M` `D` が対話出力に**割り込む** | 期待列の完全一致をやめ、「**対話期待列とマーカー列の、各々の順序を保った併合（interleave）になっているか**」で判定する。TB 内で実装してもよいし、`uart_out.log` を後段の Python で判定してもよい。マーカー文字と ver 出力の `0`・`1` は衝突するが、併合判定は動的計画法で一意に決まる（2 列の併合可否判定は標準的な DP） |
| マーカーの一部がシミュレーション終了までに出ない | マーカー列は「**先頭からの部分列（prefix）**」として許容する |
| C-21 の多重集合規則 | 併合判定が上位互換になるので置換してよい |

**是正要求**

1. §16 の方式選定の前に、**本番カーネル＋YUI> 起点**を試し、所要時間を実測すること。
2. 300 秒に収まれば、これを M-10 の正式方式とし、§16.2〜§16.6（派生カーネル）は**予備方式**へ格下げする（記述は残す）。
3. 収まらなかった場合に限り派生カーネル方式へ進む。その際は、**実測値を §16.1 に追記**して選定根拠とすること。

## §2. B級指摘

### ★B-21★ 判定⑥（TX 上書き 0 回）は M-10 の刺激タイミングでは**検出力ゼロ** — レビュー v1.4 の誤りの是正

v1.4 B-20 は「マーカー（"0123MD"）も `emit-char` 直」と書き、「③でだけ発火する可能性」とした。**これは誤りである。** 実源で確認した事実は次のとおり。

| 実源 | 事実 |
|---|---|
| L2836-2839 `FILEMGR-PUTC-M` 他 | マーカーは `UART-PUTC-OP` による **IPC → UART ドライバ経由**。L1170 の正しいループ（`1 AND`）を通る |
| `emit-char` の呼出し元（grep） | **`BOOT-MSG`（L3433-3435）と `TASK-PRINT-ID`（L812-813）のみ**。後者は呼出し元 0 件 |
| L3443-3444 | `BOOT-MSG` は `SHELL-START` の**前**に 1 回だけ実行される |

★したがって、TB が最初の `"YUI> "` の後に送信を始める限り、`emit-char` はもう一度も実行されない。判定⑥は**本番・派生のいずれのカーネルでも原理的に発火しない**。★
これは原則「通ったのはゲートが見ていなかっただけ」の典型である。

**是正要求**

1. 判定⑥は安価なので残してよい。ただし §15.1 に「**M-10 の刺激タイミングでは検出力ゼロ**（上記の根拠）」と明記すること。
2. 検出力を持たせるため、**負試験 M-10N** を 1 件追加する。内容は、TB が `"YUIOS"` の `Y` を検出した直後（`BOOT-MSG` の実行中）に 1 バイト送信する、というもの。
   - 期待：判定⑥が発火し、`BOOT-MSG` の出力に壊れたフレームが現れる。★**つまり B-20 のカーネル欠陥を実証する試験**★になる。
   - 実機でも、電源投入直後にキーを押せば同じ条件が成立する。
3. B-20 のカーネル欠陥（L797 は `UART-STAT @ 1 AND` にすべき）は、M-10N の結果を待たずに **YUI OS 側チケットとして今すぐ起票**すること。1 語の修正で済み、実機では条件が成立しうる。★「見えているバグは先に潰す」★

### B-22 §16.4（失う忠実度）の記載漏れ

A-5 を採らず派生カーネルへ進む場合でも、§16.4 は次の 2 点を欠いている。

| 失うもの | 内容 |
|---|---|
| SD SPI とマウント処理の同時稼働 | STOR（SPI 転送）と UART 対話の同時動作は、派生カーネルでは一切起きない。B-18 の ISR 遅延の主因候補（割込み禁止区間）は、むしろこの経路にある |
| 判定⑥の検出力 | B-21 のとおり、どちらの方式でも M-10 本体では検出力ゼロ。M-10N でしか見られない |

## §3. C級指摘

| # | 内容 |
|---|---|
| C-29 | §16.5「`run`/`ls`/`cat` は tid=0 宛で不定動作」について。`STOR-DRV-TID`／`FILEMGR-TID-ADDR` の初期値が 0 であれば、IPC の宛先はルートタスク（L3445 で `TASK-SLEEP` ループ中）になり、シェルは**応答待ちで停止**する公算が高い。「不定」より「**シェルがハングする**」と書く方が、誤送信時の症状の切り分けに役立つ。初期値は実源で確認のこと |
| C-30 | §16.1 の C-2 スループット低下（17,660 → 12,000〜14,000 cycle/秒、約 25% 減）の原因を一度確認しておくとよい。候補は R-10 の `$isunknown` 監視と TB 側の独立受信器（毎サイクル評価）。TB 側が原因なら、監視をビット中央サンプルだけにする等で、本番方式の余裕がさらに増える |
| C-31 | §16.1 の結論「本番方式は完走不可能」は、「**M-5 まで**走らせる本番方式は完走不可能」と範囲を限定して書くこと（A-5 と整合させるため） |

## §4. レビュー側の不備（記録）

v1.4 B-20 は、`emit-char` の欠陥を正しく見つけた一方で、「マーカーも `emit-char` 直」と**呼出し元を確認せずに**書いた。
根拠は L3428 のコメント（「emit-char 直（ドライバ非依存）」）であり、これは `BOOT-MSG` についての記述だった。それを**マーカーにも当てはまると読み違えた**。
その結果、判定⑥に「③でだけ発火しうる」という**実在しない検出力**を与えてしまい、設計書 §15.1 にもそのまま転記された。

これは原則67（TB と DUT が同じ誤った前提を共有すると偽合格）の**レビュー版**である。以後、「ある関数を通る」という主張は、**コメントではなく呼出し元の grep で確認してから**書く。
