## 2. M 指摘（必須是正：4件）

### M-1 【§3.2.2 / §4.1】★最重要★ **ライン充填コストが計上されていない**。このままではラインサイズの評価ができない

**問題の所在**：

§4.1 でラインサイズを **32 バイト（可変パラメータ）** と定めている。ダイレクトマップ・ライトスルーのキャッシュでリードミスが起きた場合、実機では **ライン全体（32 バイト）を PSRAM から読み出す**。ところが §3.2.2 の課金式は次のとおりである。

```
ミス時（1バイト）: 追加課金 = (LAT - 1)
```

**ミスしたそのバイトの分しか課金していない。** 残り 31 バイトの充填コストがどこにも計上されない。

**帰結（これが致命的である理由）**：

ライン充填を無視すると、**ラインサイズを大きくするほど無条件に有利という誤った結論が出る**。

- ラインを大きくする → 空間局所性によりヒット率が上がる → 課金が減る（**この利得だけが計上される**）
- ラインを大きくする → 1 ミスあたりの充填コストが増える（**この損失が計上されない**）

現行モデルでラインサイズを掃引すれば、「ライン 256 バイトが最適」「いや 1 KB が最適」といった、**実機では成立しない結論**にいくらでも到達できる。

§1.1 は本改良の目的を「将来のキャッシュ RTL 開発（工程②）に必要な**定量的基盤**を整備する」と述べ、§1.3 は「キャッシュ方式（容量・ライン長・連想度）の決定」を非目標としつつ、その決定を後段工程で行う前提に立っている。**その決定に使うデータを産出するのが本改良である以上、ラインサイズの評価が原理的にできないモデルは目的を達成しない。**

**是正要求**：

リードミス時のライン充填コストをモデル化されたい。最小限、次を §3.2.2 に追加する。

```
リードヒット      : 追加課金 0
リードミス        : 追加課金 = (LINE_SIZE × LAT_FILL) − 1
                    ※ 表が既に 1 サイクル計上済のため末尾 −1
```

`LAT_FILL` はバースト転送時の 1 バイトあたりコストであり、単発アクセスの `LAT` とは**別パラメータ**とすべきである（PSRAM はバースト転送でコマンド発行オーバーヘッドが償却されるため、通常 `LAT_FILL < LAT`）。両者を同一値に潰すと、今度はライン充填を過大評価してラインサイズが不当に不利になる。

あわせて次を明記されたい。

1. **クリティカルワードファーストの有無**（ミスしたバイトを先に返すか、ライン全体の充填完了まで待つか）。前者なら課金式が変わる
2. §6 のオプションに `LAT_FILL` を追加（§3.3 の種別表に 1 行追加）
3. §8.1 に **T-05：ラインサイズ掃引テスト**を追加し、ラインを 2 倍にしたとき「ヒット率上昇による削減」と「充填コスト増」が**両方**動くことを手計算で確認する

> **KY 的補足**：本件は §10 のリスク表に載っていない。§10 リスク1 は「二重計上」＝**課金しすぎ**の危険だけを見ている。M-1 は**課金しなさすぎ**の危険であり、方向が逆である。二重計上を警戒するあまり控えめに課金する設計になった、という構図に見える。§10 に「**未計上（課金漏れ）**」をリスクとして追加されたい。

### M-2 【§3.2.2 / §4.1】ライトスルーの**書き込み課金が未定義**。書きヒットを 0 課金とするのは誤り

§4.1 は書き込み方式を **ライトスルー / ノーライトアロケート**と定めている。ライトスルーの定義上、**書き込みは常に下位メモリ（PSRAM）へ到達する**。したがって：

| 事象 | 実機での PSRAM アクセス | §3.2.2 の課金 | 判定 |
|---|---|---|---|
| 読みヒット | 無し | 0 | ✅ 正しい |
| 読みミス | 有り（ライン充填） | (LAT−1) | ❌ M-1（過少） |
| **書きヒット** | **有り（ライトスルー）** | **0** | ❌ **誤り** |
| **書きミス** | **有り（ノーライトアロケート＝ラインは充填せず直接書く）** | (LAT−1) | ✅ 概ね正しい |

§3.2.2 は「ヒット時：追加課金 0（表の値がそのまま正しい）」と**アクセス種別を区別せずに**書いている。このままでは**書きヒットが 0 課金**となり、ライトスルーの効果を著しく過大評価する。Dhrystone のようなストア頻度の高いベンチマークでは無視できない誤差になる。

**是正要求**：§3.2.2 の課金式を**読み／書きで分けて**記述されたい。

```
読みヒット   : 0
読みミス     : (LINE_SIZE × LAT_FILL) − 1        ← M-1
書きヒット   : (LAT_WR − 1)     ★ライトスルーゆえヒットでも PSRAM へ到達する★
書きミス     : (LAT_WR − 1)     ★ノーライトアロケートゆえライン充填は無い★
```

すなわち **ライトスルー／ノーライトアロケートでは、書き込みのヒット判定は課金に影響しない**。この事実を §4.1 の直下に明記しておけば、実装者が「書きもヒット判定して 0 にする」誤りを犯さない。

あわせて **ライトバッファの有無**を §4.1 に明記されたい。ライトバッファがあれば書き込みは非ブロッキングになり課金は 0 に近づく。無いなら上記のとおり毎回課金する。**この一言が無いと、実装者が勝手にどちらかを仮定する。**

> 参考：MC6809 系の周辺には該当しないが、ライトスルー＋ライトバッファは 68030 以降や ARM7 で一般的な構成である。RTL 側で採るか否かは工程②の判断になるため、本設計では「**現時点ではライトバッファ無しを仮定する。有りの場合の課金は別途モデル化**」と留保を置くのが妥当である。

### M-3 【§6 / §8.1】キャッシュ容量・ラインサイズを**指定する手段が存在しない**。T-01/T-02 が実行不能

§4.1 は容量 16 KB・ライン 32 バイトを「**可変パラメータ**」と明記し、§8.1 T-01 は「**キャッシュ容量を 32 バイト（1 ライン）に設定し**、32 バイト離れた 2 アドレスを交互にアクセスして必ずミスさせる」というテストを規定している。

**ところが §6 のオプション仕様に、容量とラインサイズを指定する手段が無い。** `--mem-latency` と `--trace-addr` の 2 つしか定義されていない。このままでは T-01 も T-02 も実行できず、§7 段4 の完了条件「§8.1 の手計算検算 PASS」が満たせない。

**是正要求**：§6 に次を追加されたい。

```
--cache-size N        キャッシュ総容量（バイト。既定 16384）
--cache-line N        ラインサイズ（バイト。既定 32）
```

あわせて次を規定されたい。

1. **2 の冪の検査**（ダイレクトマップのインデックス計算はマスク演算のため、非 2 冪は不正）。不正時は stderr + `exit(1)`。§6.1 の `--mem-latency` が「typo によるサイレント誤読の防止」を掲げている以上、ここも黙って丸めてはならない
2. `--cache-size < --cache-line` の場合の扱い（エラーとすべき）
3. **`--cache-size` / `--cache-line` は `cache_enable` を立てるか否か**。§5.3 の R1 死守（既定は完全非退行）との関係を明示すること。「レイテンシもトレースも指定していないがサイズだけ指定した」場合の挙動が現状では不定である

### M-4 【§3.1.2 / §9】「実測逆算 約 5.0 CPU cyc/byte」は**現時点では導出不能**（根拠が循環している）

§3.1.2 の表は次のように記す。

| 検証 | 値 |
|---|---|
| 机上再計算 | 約 5〜6 CPU cyc/byte |
| **実測逆算（下記）** | **約 5.0 CPU cyc/byte** |

しかし「下記」に示されているのは次の 3 数値のみである。

- emu23 `-mc`：351,761 cycles
- RTL 実測：1,317,401 cycles
- 差＝965,640 cycles

**この 3 数値から cyc/**byte** は出せない。** バイト数で割る必要があるが、**総アクセスバイト数 B は §9 の手順 1 で初めて測定する**と設計書自身が述べている（「Dhrystone を `-mc --trace-addr` で走らせ、総アクセスバイト数 B を実測する」）。つまり：

- §3.1.2 が「実測逆算 5.0」を主張する ← B が必要
- B は §9 で測る ← §9 は本改良を**実装した後**でないと実行できない
- §9 の手順 3 は「`LAT − 1 = 965,640 ÷ B` から LAT を逆算する」← **これから求める値**

**「これから測って求める値」を、既に求まったかのように前提に置いている。** 循環である。

さらに **机上再計算「約 5〜6」の計算過程も記載されていない。** cpu:psram = 1:8 という比だけでは cyc/byte は決まらない（PSRAM 側が 1 バイトあたり何 psram_clk サイクル要するかが不明）。965,640 ÷ 1,317,401 = 73% がメモリ待ちという事実は言えるが、それは cyc/byte ではない。

**是正要求**：

1. §3.1.2 の「実測逆算」の行を削除するか、**「机上推定」と正しくラベル**し直す。KY34（実ファイルが真実）の精神に照らし、**推定を実測と称してはならない**
2. 机上再計算の**計算過程**（PSRAM 1 バイトあたりの psram_clk サイクル数の根拠を含む）を明記する。根拠が無いなら「暫定値」と明示する
3. §3.3 の既定値 5 は「**§9 で確定するまでの仮値であり、設計判断の根拠に用いてはならない**」と明記する
4. §9 の手順に「**手順 1 の B が得られるまで、LAT の確定値は存在しない**」と順序依存を明記する

> **なぜ M なのか**：この 5.0 という数値は §3.1.2 の「⚠ 改良4 への帰結」で **psram_clk 昇圧案を無意味と断ずる根拠**として使われ、さらに §11 で `cache_study_handover_v1_0.md` の **v1.1 改版（優先度高）** を要求する根拠にもなっている。**未確定値が他文書の改版を駆動している**状態は危険である。「60 は誤り」という指摘自体は正しいが、**正しい値が 5 だという主張はまだ立証されていない**。

## 3. C 指摘（確認・明記要求：4件）

### C-1 【§3.1.2】「律速は PSRAM 側にない」は自己矛盾である

§3.1.2 は次のように述べる。

> `psram_clk 25→81MHz で 3.2 倍` 改善案は**無意味化**。現行は既に 32MHz であり、**CPU が 4MHz なので律速は PSRAM 側にない**

しかし同じ節が「差＝メモリ待ちの実費 **965,640**」を示しており、これは全 1,317,401 cycles の **73%** に相当する。**実行時間の 7 割がメモリ待ちであるなら、律速は明白に PSRAM 側にある。**

クロック比が 1:8 であることは「PSRAM が CPU より速いクロックで動いている」ことしか意味しない。1 バイト転送にコマンド発行を含む複数の psram_clk サイクルを要するなら、**クロックを上げれば待ち時間は減る**。5 cyc/byte @ cpu 4MHz は psram_clk 換算で 40 サイクル/byte に相当し、これはプロトコルオーバーヘッドが支配的であることを示唆する。

**要求**：
- 「無意味化」という断定を撤回し、「**旧見積もり（60 cyc/byte）に基づく 3.2 倍改善という試算は前提が誤っており、再評価が必要**」という表現に改める
- PSRAM 1 バイトあたりの psram_clk サイクル数を実源（`ysd8800_psram_ctrl_v0_2.sv` の FSM）で確認すれば、昇圧の効果は定量的に判断できる。§11 に調査項目として起票することを推奨する

> この訂正は §11 の起票 1（`cache_study_handover` v1.1 改版）の内容にも波及する。**誤った前提を正しい前提に置き換えるのは良いが、置き換えた先も検証されていなければ同じことを繰り返す。**

### C-2 【§6.3】`--trace-addr` 単独時の `cyc` 列の意味が変わる

§6.3 は「`--trace-addr` のみ → 課金せずトレースのみ出力（キャッシュ判定は行う）」とする。このとき `-mc` が無ければ **CPI=1 固定**であり、§6.2 の `cyc` 列は「実行命令数」を意味する。`-mc` 併用時とは**単位が異なる**。

Python 後処理（H-1）が `cyc` 列を時間軸として使う場合、単独指定のトレースを食わせると誤った分析結果になる。

**要求**：トレースファイルの**先頭にヘッダコメント行**を出力し、`-mc` の有無・LAT 値・キャッシュ構成を記録されたい。例：

```
# emu23 v2.10 trace / mc=1 lat=5 cache=16384/32 unified wt-nwa
cyc,pa,kind,hit
```

これは Python 側で前提の取り違えを検出できるようにするためであり、**H-1 の二段構え（Python で確定後に emu23 へ取り込む）を安全に回すための前提条件**である。

### C-3 【§3.3】`LAT_RD8` と `LAT_RD16` を別種別にする理由

§3.3 は 5 種別を定義し、`LAT_RD16` は「1 バイトあたりの値」と注記する。しかし §3.2.3 が述べるとおり **RTL は 16bit アクセスをバイト 2 回に分割**している。ならば `RD8` と `RD16` の**バイトあたりレイテンシは物理的に同一**のはずである。

種別を分ける利点（分析時に 8bit/16bit 別の集計が取れる）は理解できるが、**既定で異なる値を設定できてしまう**と、物理的にありえない条件でのシミュレーションが可能になる。

**要求**：次のいずれかを明記されたい。
- (a) 分析用途のため種別は分けるが、**既定では全種別同値**とし、異なる値を設定した場合は警告する
- (b) `RD16`/`WR16` 種別を廃し、16bit アクセスは `RD8`/`WR8` を 2 回課金する（§5.1 のフック設計と整合する）

なお `LAT_FETCH` を分けることには意味がある（命令フェッチは逐次アクセスでバースト効率が異なりうる）。

### C-4 【§5.4 / §6】統計 `stat_hit` / `stat_miss` の**出力方法**が未定義

§5.4 に統計変数が定義されているが、**いつどこへ出力するのか**が §6 にも §8 にもない。ヒット率は本改良の主要な成果物であり、トレースを Python で後処理せずとも emu23 が直接出せるべきである。

**要求**：終了時に stderr へ 1 行サマリを出力する仕様を追加されたい。あわせて、**警告文言規約**（`Dhrystones/sec` / `cycles` / `P:` を含めない。Makefile が `2>&1` 合流後に grep するため）を満たすこと。これは Phase C §4.3 で確立した規約であり、**本設計書には当該規約への言及が一切ない**のは横展開漏れである（原則122）。

例：`[CACHE] hit=123456 miss=7890 rate=93.98% charged=31560`（`cycles` の語を避けている点に注意）

| **N-2** | §8.1 T-01 | 「32 バイト離れた 2 アドレスを交互にアクセス」は、**ダイレクトマップで同一インデックスに衝突させる**意図と読める。容量 32 バイト（1 ライン）なら全アドレスが同一インデックスに落ちるため成立するが、**その理屈を一言添える**と検証意図が明確になる（後日ライン数を増やしたときにテストが壊れる理由が分かる）。 |
| **N-3** | §5.4 | `cache_tag[]` / `cache_valid[]` を分離した 2 配列にしているが、`valid` を tag の最上位ビットに畳むか、構造体配列にする方がキャッシュ効率（ホスト側の）が良い。20 万アクセス規模なら実用差は小さいため N 止まり。 |
| **N-4** | §10 | リスク表に **M-1 で指摘した「課金漏れ」** と、**M-4 で指摘した「未確定値を確定値として扱う」** を追加されたい。後者は本プロジェクトで繰り返し現れるパターン（`cache_study_handover` の 60 cyc/byte がまさにそれ）であり、KY として登録する価値がある。 |

**特に M-1 と M-2 は、課金式（§3.2.2）の書き換えを要する。** この 2 つを入れると課金式は次の 4 分岐になる（ライトバッファ無しの場合）。

| 事象 | 追加課金 |
|---|---|
| 読みヒット | 0 |
| 読みミス | `(LINE_SIZE × LAT_FILL) − 1` |
| 書きヒット | `LAT_WR − 1` |
| 書きミス | `LAT_WR − 1` |

この 4 分岐を §3.2.2 に据えたうえで、§8.1 の T-01〜T-04 を **4 分岐すべてを手計算検算できるよう再設計**されたい。現行の T-01〜T-04 は読み系に偏っており、**書きヒットのテストが存在しない**（M-2 が発見されにくかった理由でもある）。
