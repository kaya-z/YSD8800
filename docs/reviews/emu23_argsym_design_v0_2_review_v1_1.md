## 1. M（Must：v0.3 で是正）

### M-6 `ARGV_MAX` の境界処理が未定義（配列外アクセスの余地）

§5.2 は次を定めるのみである。

```c
#define ARGV_MAX 64
static unsigned char argv_used[ARGV_MAX];  /* 0=未消費 1=オプション本体/その引数 */
```

マーク付与規則は「`argc` を超える位置には立てない（範囲外アクセス防止）」とするが、**これは `argc` 側の上限しか見ていない**。前置パスは `i` を `argc-1` まで走査するため、**`argc > 64` の場合に `argv_used[64]` 以降へ書き込む**。`static` 配列であるため、隣接する静的変数を破壊する。

実運用で 64 引数に達することは考えにくいが、**silent な壊れ方を潰すことが目的のチケットで、新たな silent な壊れ方を作ってはならない**。

**是正案**：前置パス冒頭で `argc` を検査し、超過時はエラー終了する（§5.5 と同じ流儀）。

```c
if (argc > ARGV_MAX) {
    fprintf(stderr, "emu23: too many arguments (max %d)\n", ARGV_MAX);
    return 1;
}
```

> **代替（推奨度低）**：`argv_used` を `calloc(argc, 1)` で動的確保すれば上限自体が消える。ただし emu23 の既存コードは静的配列主体であり、**上限を明示して弾くほうが方針として一貫する**。

### M-7 A-7 は `-q` 下では観測できない（M-5 と同型の残存）

§6.2 は M-5 を受けて `-q` 欄を新設し、B 系については正しく整理された。しかし **A-7 が `-q`＝有のまま**である。

| ID | `-q` | 期待（改修前） |
| --- | --- | --- |
| **A-7** | **有** | `.sym` が `.dbg` として読まれ**シンボル 0 件** |

`Loaded %d label symbols`（L1386）は `if (!quiet_mode)` 配下であり、**`-q` では出力されない**。したがって「シンボル 0 件」を出力で確認できず、**M-5 で指摘したのと同一構造の判定不能な試験**になっている。

**是正案（いずれか）**：

1. **A-7 の `-q` を「無」に変更する**（最も単純。群β形式の再現に `-q` は本質的でない）。
2. `-q` を保つなら、判定手段を出力以外にする（REPL でラベル BP を張り、`lookup_sym()` が失敗することを確認する等）。

**1 を推奨する。**

> **★再発防止★** §6.2 の各行について、**期待結果に現れる観測対象が当該 `-q` 設定で実際に出力されるか**を機械的に照合されたい。現状 `Loaded ...` を期待結果に持つ行は A-N／A-1／A-7／B-N／B-1 であり、このうち **A-7 のみが `-q`＝有**である。

## 2. C（要確認：v0.3 で回答）

### C-5 本改修により「自動導出が実際に成功するようになる」副作用が明記されていない

方式(イ)の帰結として、**これまで silent に失敗していた位置引数解釈が自動導出に切り替わる**。絶対ゲートの実行形がまさにこれに該当する。

```
$(EMU) $(YUIOS_BIN) -q --disk $(DISK)          （Makefile L172）

【現行 v1.12】
  argv[2]="-q"      → load_dbg("-q")     → fopen 失敗 → L1367 黙殺
  argv[3]="--disk"  → load_sym("--disk") → fopen 失敗 → L1367 黙殺
  ⇒ .dbg / .sym とも未ロード

【改修後 v1.13】
  argv[2] / argv[3] とも消費済み
  ⇒ change_ext() により yuios_road2.dbg / yuios_road2.sym を自動導出
  ⇒ ★ファイルが存在すれば実際にロードされる★
```

`-q` 下では `Loaded %d dbg entries`（L1362）／`Loaded %d label symbols`（L1386）とも `!quiet_mode` 配下のため抑制され、**G-3（`-q` stdout byte-exact）は通る**。

しかし **`-q` を付けない実行では、stdout に上記 2 行が新規に出現する**。これは改善（本来読まれるべきものが読まれるようになった）だが、**設計書のどこにも「非 `-q` 実行の stdout は変わる」と書かれていない**。§5.8 は群β形式の制約のみを述べ、本件に触れていない。

**回答願う**：

1. **§5.8 に「本改修の意図した挙動変化」として明記**されたいか。「回帰ではなく改善である」と事前に文書化しておかないと、実装時に `Loaded ...` の出現を見て回帰と誤認するおそれがある。
2. G-3 の適用範囲（`-q` のみ）で十分か。**非 `-q` の stdout は「変わることが正しい」ため byte-exact ゲートの対象にしない**、という整理でよいか。

> 本件は M ではなく C とした。**挙動としては正しく、危険も無い**が、**明記が無いと検証時の誤判定を招く**ためである。
