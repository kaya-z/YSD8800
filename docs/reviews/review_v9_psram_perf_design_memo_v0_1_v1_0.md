## 0. 総評

**良い点（積極的に評価する）**

1. §3 の**量子化構造の発見と、それを根拠にした「CDC 優先」の論理**は本メモの核心であり、実測に裏打ちされている。「PSRAM 側は 8 psram cyc 単位でしか見えないが、CDC 側は整数 cpu cyc で素直に効く」という非対称性の提示は、工程判断として説得力が高い。
2. §3.2 の**線形外挿の禁止**注記、§6 の**KY54 両方向検証（わざと 1 cyc 増やして悪化を確認）**は、KY66 の教訓が正しく反映されている。
3. §4.4 で A-4（2FF→1FF）を**理由付きで明示的に却下**した点は良い。メタステービリティを性能で買う判断を残さない姿勢は原則82 と整合する。
4. 実源の行番号引用（cdc L89-90/L92-96/L98-100/L106-110）は**全て正確**であることを確認した。

**差戻しとする理由**

推奨方針である **A-2 先行**が、以下 2 点により「低リスクで確実に −1 cpu cyc」とは言えない：

- **M-5**：A-2 は `cpu_mem_ready` 単独では**機能破壊**になる（`cpu_mem_rdata` が 1 サイクル遅れて無効データを掴む）。メモは「懸念2」として弱く扱っているが、これは懸念ではなく**必須の同時変更**である。
- **M-6**：`req_hold` との相互作用により、**連続アクセス（命令フェッチ列）では −1 cyc が相殺され得る**。M-2→M-3 区間はフェッチ主体であるため、効果予測 −21% の前提が崩れる可能性がある。

加えて **M-7** により、A-1 の削減量記述は物理的に成立しない。方針の骨格は正しいので、v0.2 での是正で足りると判断する。

### M-5 A-2 は `cpu_mem_rdata` の同時変更なしには**機能破壊**である（懸念2 の格上げ）

| 項目 | 内容 |
|---|---|
| 該当 | §4.2 案 A-2、特に「実装規模：数行」「安全性（論理）：✅」「懸念2」 |
| 実源（cdc L92-98） | 現行は同一 `always_ff` 内で `cpu_mem_ready <= 1'b1;` と `cpu_mem_rdata <= psram_rdata;` を**同じエッジで登録**している。したがって両者は **N+1 サイクルで同時に有効**になり、整合が取れている |
| 問題 | A-2（`assign cpu_mem_ready = ack_sync[1] & ~ack_sync_d;`）だけを適用すると、**ready は N サイクル、rdata は N+1 サイクル**となり位相がずれる。CPU が ready を見て N サイクルで rdata をラッチすると、**前回アクセスの残留データ**を読む。これは性能劣化ではなく**論理誤り**であり、Dhrystone / YUI OS が確実に壊れる |
| 結論 | 「懸念2」は**懸念ではなく必須の同時変更**。A-2 の正しい姿は最低でも次の 2 行同時変更である：<br>`assign cpu_mem_ready = ack_sync[1] & ~ack_sync_d;`<br>`assign cpu_mem_rdata = psram_rdata;` |
| 補足（この同時変更の安全性） | `ysd8800_psram_ctrl_v0_2.sv` L117-128 を確認：`rdata` は**登録出力**であり、`PS_WAIT_REQ_LOW` 状態で **req が下がるまで ack と共に保持**される（4 相ハンドシェイク）。したがって同期済み ack で修飾された `psram_rdata` の組合せ引き渡しは**論理的には成立する**（一般的な CDC データハンドオフ）。ただし M-5 の帰結として FPGA では**真の非同期パス**となり、`set_max_delay` 等の STA 制約が**必須**になる（メモの「必要になる可能性」→「必須」） |
| 対応 | ①「安全性（論理）✅」の記述を撤回し、**ready 単独変更は不可**と明記<br>②「実装規模：数行」を「**RTL は数行だが、STA 制約と CDC レビューを伴う**」に改める<br>③ §7 論点 2 を「懸念」から「**A-2 の構成要件**」へ移動 |

### M-6 A-2 の −1 cpu cyc は `req_hold` により**連続アクセスでは相殺され得る**

| 項目 | 内容 |
|---|---|
| 該当 | §4.2「削減量：1 cpu cyc」「効果予測：M-5 約 −21%」 |
| 分析（実源 cdc L75, L94-101 に基づくサイクル追跡） | **現行**<br>N: `ack_sync[1] & ~ack_sync_d` 成立 → 各レジスタ更新<br>N+1: `ready=1`・`rdata` 有効・`req_hold=1` → `req_level` 強制 0<br>N+2: `req_hold=0` → CPU が N+1 で見た ready を受けて発行した次 req が通る<br><br>**A-2 適用後**<br>N: `ready=1`（組合せ）<br>N+1: `req_hold=1` → `req_level` 強制 0。**CPU が N で ready を見て N+1 に上げた次 req はここで潰される**<br>N+2: `req_hold=0` → 次 req が通る<br><br>→ ★**次アクセスが立ち上がるサイクルは両者とも N+2 で同一**★ |
| 帰結 | **CPU がメモリアクセスを連続で行う場合（命令フェッチ列・16bit アクセスの上位/下位バイト連続）、A-2 の 1 サイクルは `req_hold` の不感帯に吸収されて外に出ない。**単発アクセス（間に演算がある場合）でのみ 1 cyc が効く |
| 影響の重大性 | 主指標に定めた **M-2→M-3 区間はフェッチ主体**である。すなわち「効果が最も確実に出る」としていた区間が、**最も相殺されやすい区間**である可能性がある。§5 の「A-2 を先行させる理由：効果が確実だから」という論拠が成立しない |
| 対応 | ①**実装前に、上記の N/N+1/N+2 タイミング図を設計メモに明記**し、相殺の有無を確定させること（★原則131：テスト手順の事前妥当性確認＝「その手順で効果が検出できるのか」を先に検証する★）<br>②相殺が確認された場合、A-2 と A-3（`req_hold` 除去）は**独立案ではなく結合案**として扱い直すこと。あるいは `req_hold` の生成条件を組合せ ready と同位相にする **A-2'** を新設して検討すること<br>③ `tb_cdc_bridge_v0_1.sv` の波形で**連続 req 時の req 立上り間隔**を BASE 版／A-2 版で比較すれば、フルビルド前に相殺の有無を判定できる（低コスト・先行実施を推奨） |

> 本指摘は「見えているバグは先に潰す」の適用ではなく、**「見えている効果ゼロを先に潰す」**である。実装してから −0% を測るのは 1 サイクル分の工数を捨てることになる。

### M-7 A-1 の「削減量：約 4.25 cpu cyc」は成立しない（単位の非可換）

| 項目 | 内容 |
|---|---|
| 該当 | §4.1 案 A-1 の「削減量：★約 4.25 cpu cyc（CDC 全廃）★」 |
| 問題 | A-1 は **CPU を 4MHz → 32MHz に変更する案**である。このとき `cpu_clk` の周期が 250ns → 31.25ns に変わるため、**「cpu cyc」という単位そのものが 8 分の 1 の意味になる**。BASE-01 と cycle_count を直接引き算することはできない |
| 定量（レビュー側の試算） | 現行 1 バイト = 5.75 cpu cyc @250ns = **1,437.5 ns**<br>A-1 後：CDC 分 4.25 は消滅するが、**PSRAM 本体 `LATENCY_NORMAL=12` は psram cyc の値なので、1:1 化により 1.5 cpu cyc → 12 cpu cyc に「増える」**。1 バイト ≒ 12〜13 cpu cyc @31.25ns = **375〜406 ns**<br>→ ★**実時間では約 3.5 倍高速。しかし cycle_count（=バイトあたり cpu cyc）は 5.75 → 約 13 へ「悪化」する**★ |
| 影響 | ①「削減量 4.25 cpu cyc」は誤り。**増減が逆符号に見える**<br>②§6 の検証方法は M-1〜M-5 の **cycle_count 差分比較**を主指標としているが、A-1 ではこの指標が**単調に悪化する方向に動く**ため、そのままでは合否判定できない<br>③ A-1 では**量子化が消える代わりに、PSRAM レイテンシ 12 が丸ごと CPU に見えるようになる**。したがって A-1 と「LATENCY_NORMAL の低減」は A-1 後に**強く結合する**（現在は効果ゼロだった LAT 改善が、A-1 後は 1:1 で効く） |

## 3. C：確認事項

### C-1 `cache_study_numbers_audit_v1_0.md` の実在確認

ヘッダの前提文書に挙げられているが、**プロジェクトナレッジ内に当該ファイルは見当たらない**（存在するのは `cache_study_handover_v1_0.md`）。チャット内でのみ生成された文書か、ナレッジ未登録か、あるいは文書名の誤りか。**設計書台帳（design_inventory v20.0）での採番有無**と併せて確認されたい。存在しない場合は §2.3 の「三者独立で一致」の三者目が検証不能になる。

### C-2 CDC/PSRAM 比率の表記突合

本メモは **CDC 74% / PSRAM 26%**、`emu23_cache_base_design_v1_0.md` の改版履歴（v0.3）は「内訳比率を **30%/70%**」と記載されている。数値としては `PSRAM 26% / CDC 74%` と `30%/70%` は近いが、**どちらが分子か**の表記順が逆に読める。誤読防止のため、**本メモ側で「PSRAM : CDC = 26 : 74」と明示**し、旧記述との対応関係を注記されたい（KY41：旧情報を消さず対応付ける）。

### C-3 A-2 実装時のポート宣言変更

`cpu_mem_ready` / `cpu_mem_rdata` は現在 `always_ff` で駆動されるため **`output logic`（変数）**として宣言されているはずである。`assign` 化に伴い、宣言そのものの変更は不要（SystemVerilog では `logic` に `assign` 可）だが、**同一信号を `always_ff` と `assign` の両方から駆動していないこと**を実装後に必ず確認されたい。この取り違えは Icarus では通っても Gowin 合成でエラーになる典型例である。

## 4. N：推奨事項

### N-1 §5 の Step 順序を「等価性 → 効果」に入替え

現行は `Step 1: 実装・実測` → `Step 2: 効果と等価性を確認`。**等価性（UART 出力一致・PROD PASS）が崩れた状態の性能値には意味がない**ため、Step 2 を「等価性確認」、Step 3 を「効果測定」に分離し、**等価性を先行ゲート**とすることを推奨する。

### N-2 絶対ゲートの md5 明記

§6 #6 は Dhrystone G-1（819/48,785/P:20）のみ。RTL 変更ではビルド成果物 `yuios_road2.bin` は不変のはずなので、**「56,416B / md5 `599a7f9d1ebf103f81f58450ea1b6491` が変化していないこと」を #1 の基準健全性に併記**すると、「測定対象バイナリが入れ替わっていた」という事故を防げる。

### N-3 §7 論点 4（`LATENCY_NORMAL` パラメータ化）は①.5 では実施しない

P-1 指摘への対応自体は妥当だが、**性能改善と同一工程で行うと 1 変更 1 検証（PDCA 規律）に反する**。かつ M-7 の通り、A-1 採否によって `LATENCY_NORMAL` の意味付けが変わる。**工程② のキャッシュ RTL 着手時に、キャッシュのパラメータ群と一括で整理する**ことを推奨する。
