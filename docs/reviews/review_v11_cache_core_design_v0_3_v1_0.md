## 2. C：確認事項

### C-8 `fill_abort_r`（フラッシュ中止）時に `fill_hit_byte_r` を返してよいか

§7.6 は、フィル途中でフラッシュが発行された場合 ★`valid_r` / `tag_ram` を更新しない★ と規定しています。一方 §7.2 手順 4 は ★要求バイトを `fill_hit_byte_r` から返す★ とします。

**両者の関係が未記述です。** 当方の理解では：

- `fill_hit_byte_r` は ★PSRAM から実際に読み出した正しいバイト★ である
- キャッシュに載せない（`valid` を立てない）ことと、★CPU に正しい値を返すこと★ は独立である
- したがって ★**中止時も `fill_hit_byte_r` を返してよい**★（返さないと CPU の当該読み出しが完了しない）

この理解でよいか確認されたい。★**「キャッシュへの登録を中止する」と「CPU への応答を中止する」を混同すると、`mem_ready` が返らずハングします。**★ §7.6 に一行明記しておくと、実装時の取り違えを防げます。

## 3. N：推奨事項

### N-5 M-11 の修正機構は §6.3 の解析を「RTL に埋め込まない」形にできる

M-11 の推奨修正（`spec_addr_r` との一致比較）を採ると、★**§6.3 で確定した「フェッチ 1 cyc／データ 2 cyc」という非対称性が、RTL に明示的に書かれることなく自動的に発現します**★。

これには次の利点があります。

1. ★CPU コアが将来変更されても（例：ISA3.0／YSD8810 で `mem_addr` の駆動が変わっても）、キャッシュ側は自動追従する★
2. §6.3 の解析結果を「定数」や「状態デコード」として RTL に持ち込まずに済む。★解析が間違っていた場合でも機能は壊れない（遅くなるだけ）★
3. `tb_cache_core_poc` での検証が「1 cyc であること」ではなく ★**「返るバイトが正しいこと」**★ を主眼にできる

★設計解析の結論を RTL の前提条件にするのではなく、RTL が自力で正しく振る舞う構造にしておく★ほうが、後工程の変更に強くなります。§6.3 は**性能予測の根拠**として残し、**機能の前提**にはしない、という整理を推奨します。
