## 1. 評価する点

### 1.1 M-6 への対応が指摘の範囲を超えている

当方は「出典欄を追加せよ」としか求めていませんが、v0.2 は §5.1 で次まで踏み込んでいます。

- 全ての基準値に★**「二次情報」ラベル**★を付与
- ★**「二次情報のまま最上位ゲートの基準にしてはならない」**★と明記
- ★**段 0 で実ログを再取得し一次情報として確定させてから G-0 に据える**★という手順化

★これは KY34（実ファイルが真実／ハンドオーバー文書は二次情報）の正しい運用そのものです。★ 出典を書くだけなら「どこから来たか」しか分かりませんが、**一次／二次の区別を付けたことで「そのまま使ってよいか」まで判定できる表**になりました。KY70 の防止策に「基準値表には出典欄を設ける」を追加する提案も、起票で終わらせない姿勢として妥当です。

### 1.2 §3 のレジスタレベル設計と擬似コード

サイクル単位でトレースし、★**論理的な誤りは見つかりませんでした**★。特に次を確認しています。

**`blen_r=2` のトレース**（T ＝ `PS_BUSY` で `busy_cnt==0` のサイクル）

| サイクル | 状態 | `beat_cnt` | `mem_idx` | 次サイクルに現れる値 |
|---|---|---|---|---|
| T | PS_BUSY | 0 | `addr+0` | `rdata=mem[addr]`・`beat_valid=1` |
| T+1 | PS_BURST | 1 | `addr+1` | `rdata=mem[addr+1]`・`beat_valid=1`・`ack=1` |
| T+2 | PS_WAIT_REQ_LOW | 1 | — | `beat_valid=0` |

→ beat が 2 回、最終 beat と `ack` が同一サイクル、§2.3 の契約と一致 ✅

**`blen_r=32` のサイクル数**：`PS_IDLE`(1) ＋ `PS_BUSY`(11) で beat0 が T+1、以降 31 サイクル → **LAT+31 = 43** ✅ §1.2 の試算・B-4 の期待と整合。

**C-2 の検算**：厳密式に `LAT=LAT_FILL=5, S=32` を代入すると `4/159 = 2.516%` → **h = 97.48%**、`S=64` で `4/319 = 1.254%` → **98.75%**。★表の 97.4%／98.7% と一致することを確認★しました。近似式との差（+0.5pt／+0.3pt）も再現できます。

**§3.2 の縮退**：`burst_len=1` で `beat_cnt=0` のまま `PS_BURST` を踏まないため `mem_idx = addr[MEM_AW-1:0]` に縮退し、実源 L73 とビット単位で同一 ✅ G-0 の構造的保証が**検証可能な形**になりました。

### 1.3 C-4（KY73）の整理

「同一インシデントから、KY73 は**負荷モデルの代表性**を、本設計は**ネガコンの選定条件**を、別の教訓として抽出している」という整理は正確です。さらに ★**「②-A の論拠を KY73 に寄りかからせてはならない。構造的不変のみで自足する」**★ と自ら論拠を切り離した点は、M-5 の限定とも整合しており、論証として強くなりました。

### M-8 ★§5.4 assertion のライン境界条件が `BURST_MAX` 固定であり、`burst_len<32` で誤発火する★

> ★**まず、この誤りは当方が前回 N-1 で提示したコード例に起因します。訂正します。**★

| 項目 | 内容 |
|---|---|
| 該当 | §5.4 assertion 第 2 項<br>`if (burst_len > 1 && (addr[$clog2(BURST_MAX)-1:0] != '0)) $error(...)` |
| 問題 | `$clog2(BURST_MAX) = $clog2(32) = 5` のため、この条件は★**常に `addr[4:0] == 0`（32 バイト境界）を要求する**★。しかし §2.4 の契約が求めているのは「**そのバーストが境界を跨がないこと**」であり、必要なアラインメントは `BURST_MAX` ではなく ★`burst_len`★ に依存する |
| ★具体的な誤発火★ | ・**B-3**（`burst_len=4`）：正しくは `addr[1:0]==0` で足りるのに、`addr=0x0004` などで**誤って `$error` が出る**<br>・**B-7**（`burst_len=2`）：同様に `addr=0x0002` で誤発火<br>→ ★**§5.2 の正常系ベクタが assertion で汚染される**★。段 2 で「TB が悪いのか RTL が悪いのか」の切り分けに時間を取られる |

### M-9 `beat_valid` の波形定義が「1 psram cyc パルス」と実際の挙動で不整合（B-4 の計数方法が定まらない）

| 項目 | 内容 |
|---|---|
| 該当 | §2.1「1 バイト確定を示す **1 psram cyc パルス**」／§2.3「各バイト確定時に 1 psram cyc パルス」／§5.2 B-4「`beat_valid` **32 回**」 |
| §3.3 擬似コードから導かれる実挙動 | `PS_BUSY`(beat0) で `beat_valid <= 1`、`PS_BURST` でも毎サイクル `beat_valid <= 1`、`PS_WAIT_REQ_LOW` で `<= 0`。<br>→ ★**`burst_len=32` では `beat_valid` は 32 サイクル連続で High になり、立上りエッジは 1 回しか存在しない**★ |
| 問題 | 「1 psram cyc パルス」という語は**単発パルスが beat ごとに分離して現れる**波形を想起させる。★TB が素直に「立上りエッジを計数」で B-4 を実装すると、期待 32 に対し **1** を得て失敗する★。逆に「High のサイクル数」で数えれば 32 になる |
| ★なぜ今潰すか★ | 段 2 で B-4 が落ちたとき、原因が FSM なのか TB の計数方法なのかの切り分けが発生する。★契約の言葉の曖昧さは、実装前に潰すのが最も安い★ |
| 対応 | §2.1／§2.3 の記述を次に改めること：<br>★「`beat_valid` は**そのサイクルの `rdata` が有効なバイトであること**を示す。バースト中は `burst_len` サイクル連続で 1 となる（パルス列ではない）」★<br>あわせて **B-4 の期待を「`beat_valid` が 1 であるサイクルを計数して 32」**と明記し、TB がエッジ計数を実装しないよう指示すること |

## 3. C：確認事項

### C-5 §1.2 内で `LAT` の値が 4 と 5 に揺れている

同じ §1.2 のなかで、

- 充填コスト表：**32 × 4 = 128 cpu cyc**（※注で「この 4 は A-2q 適用後」と明記済）
- 損益分岐の検算：★`LAT = LAT_FILL = **5**` を代入★して 97.4% を導出

となっており、**同一節で LAT が 4 と 5 の二つの値を取っています**。97.4% は `emu23_cache_base_design v1.0`（A-2q 以前）の値なので経緯としては理解できますが、A-2q 後の `LAT=4` で厳密式を解くと `3/127 = 2.36%` → ★**h = 97.6%**★ となり、表の 97.4% とは別の値になります。

結論（バースト無しでは成立しない）は 97.4% でも 97.6% でも揺るぎませんが、**どちらの LAT に基づく数値かを表に併記**されたい。§1.2 注記が「再校正（Q2 承認済）で確定させる」としている以上、★再校正の対象に「損益分岐の再計算」も含まれることを明記★しておくと②-B で漏れません。

### C-6 §5.1 の「異なる機序ゆえ転記ミスではない」は現時点では**仮説**である

ビン A（`74,512 / 222,977 / 320,196 / 3,755,316`）と A-2q（`74,512 / 222,994 / 320,156 / 3,754,937`）の差について、「PSRAM 側短縮と CDC 側短縮は量子化の受け方が違う」という説明は**もっともらしい**のですが、次が未説明です。

> ★機序が違うのなら、**なぜ M-2 だけが 74,512 で完全一致するのか**★

機序が異なるなら M-2 も違う値になるのが自然で、M-2 のみ一致するのは偶然か、あるいは M-2 が量子化ビンの内側に収まっているためかのどちらかです。**段 0 で一次確定させる方針は既に立っている**ので実務上の問題はありませんが、★「転記ミスではない」と**断定形**で書くのは段 0 の結果が出るまで避け、「〜と推定される。段 0 で確定する」とされたい★（KY34 の趣旨）。

### C-7 size cast（`MEM_AW'()` / `PS_BLEN_W'()`）の Icarus 12.0 対応を段 1 で確認

§3.2 の `MEM_AW'(addr[MEM_AW-1:0] + MEM_AW'(beat_cnt))`、§3.1 の `BLEN_W'(1)`、§4 の `PS_BLEN_W'(1)` は SystemVerilog-2012 のサイズキャストです。**幅を明示する方針自体は正しい**（暗黙拡張に頼らないという §3.2 の判断を支持します）が、★Icarus Verilog 12.0（`-g2012`）でのパラメータを用いたサイズキャストの解釈は取りこぼしがあり得る★ため、段 1 の最初のコンパイルで**通ることを確認**されたい。通らない場合の代替は次の通りです。

```systemverilog
assign mem_idx = addr[MEM_AW-1:0] + {{(MEM_AW-BLEN_W){1'b0}}, beat_cnt};
```

## 4. N：推奨事項

### N-4 B-10 では `$error` の発火が**期待動作**である旨を TB に明記

B-10（`we=1, burst_len=4`）は ★assertion が意図的に発火する唯一のベクタ★です。TB のログ判定が「`$error` が 1 件でもあれば FAIL」という作りだと、**正常なのに落ちる**ことになります。B-10 の行に「★`$error` の発火を期待する（発火しなければ FAIL）★」と明記し、他ベクタと判定基準が逆であることを目立たせてください。

### N-5 `PS_IDLE` で `beat_valid <= 0` を明示代入

§3.3 の擬似コードでは `beat_valid` の 0 クリアが `PS_WAIT_REQ_LOW` の 1 箇所のみです。M-7 のリセット追加で初期値は担保されますが、★`PS_IDLE` でも `beat_valid <= 1'b0;` を明示代入しておく★と、将来 `PS_WAIT_REQ_LOW` を経由しない遷移が追加されても取りこぼしません。実源 L102 が `PS_IDLE: ack <= 1'b0;` と**同じ理由で ack を毎回落としている**のと同じ考え方で、実装方針としても一貫します。
