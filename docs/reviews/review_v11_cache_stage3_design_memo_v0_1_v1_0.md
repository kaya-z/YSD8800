## 0. 総評

**評価する点**

1. ★**段3 の実装直前に「たぶん大丈夫」で通せる 2 件を止めて起票した**★判断。②-A' で 3 チャットを費やした経験を「同じ CDC 領域だから実装前に決着させる」という判断基準に変換できています。★これは原則43 を形式的に守っているのではなく、**どこで止まるべきかを自分で見つけている**★点で質が違います。
2. ★**§2.2 の「懸念の解消」を実源 3 点（(a) ack は最終ビートまで立たない／(b) ready は 2FF 遅れる／(c) req_offset_r は準静的）で構成した**★こと。当方でも `cdc_bridge_v0_4` L139 を追って検算しました：`ack` 立上り → 次の cpu edge で `ack_sync[0]<=1` → その次の edge で `suppress_r<=1` → ★**ack から 2 cpu cyc（＝16 psram cyc）後に ready**★ となり、(b) の主張は正確です。
3. ★**多ビット信号に 2FF 同期器を掛けるほうが危険である**★という D-C2 の論拠。ビット間スキューで中間値が出るという古典的な誤りを正しく指摘しており、★「同期器を入れないことが正しい」という判断を、根拠付きで下せている★点を評価します。安易に 2FF を足す設計より遥かに良い。
4. §3 で全状態変数のドメインを一覧化し、★`fill_hit_byte_r` だけが `psram_clk` である★と名指しした点。実装時の取り違えを防ぐ実用的な表です。

**条件付きとする理由**

★**D-C1 の `fill_active` が「いつ 1 になるか」が未定義**★であり、これが登録信号（§3 の `fill_active_r`）である限り ★**ミスの初回サイクルに間に合わない**★（M-1）。加えて ★D-C3（段3＝読み出しのみ）のまま `CEN=1` で G-1 を回すと、書き込みがキャッシュに反映されず必ず失敗します★（M-3）。

## 3. C：確認事項

### C-1 `fill_active_r` の deassert タイミングと `suppress_r` の相互作用

M-1 の対応で `fill_sel = fill_req | fill_active_r` とする場合、★`fill_active_r` をいつ落とすか★が重要になります。

- 落とすのが早すぎる：フィル完了前に `br_phys_addr_o` の丸めが外れ、★`psram_ctrl` は `addr` をラッチしていない（実源 L101-102）ため、バースト途中でアドレスが変わる★ → **転送先が飛ぶ**
- 落とすのが遅すぎる：次のアクセスまで丸めが残り、★誤ったアドレスで要求を出す★

`ack` 到達時、`cdc_bridge` は `suppress_r` を 1 cpu cyc だけ立てて `req_level` を落とします（L119）。★`fill_active_r` の deassert は `suppress_r` と同位相（＝`cpu_mem_ready` 成立と同時）★ が自然と考えられますが、明記されたい。§3 の表の「責務」欄に **assert 条件と deassert 条件**を書き足すのが確実です。

### C-2 G-0 を 2 ビン（LAT=12／5）に絞る根拠

設計書 v0.3 §8.1 は ★5 ビン（LAT=4/5/6/7/12）の一次確定値★を持っていますが、本メモ §4 は G-0 を 2 ビンとしています。★群1 の代表として 5、群2 の代表として 12 を選ぶという意図★であれば妥当な省力化ですが、その旨を明記されたい。

なお ★段3 では `CEN=0` の経路しか動かないため、ビン間で差が出ることは原理的にありません★。むしろ ★2 ビンで差が出たら、それは `CEN=0` にキャッシュ段が漏れ込んでいる証拠★ という積極的な意味付けができます。この観点を §4 に書いておくと、G-0 が単なる回帰ではなく**診断能力を持つゲート**になります。

## 4. N：推奨事項

### N-1 STA 制約は `set_false_path` ではなく `set_max_delay` を推奨

§2.4 は「`set_false_path` または `set_max_delay`」としますが、M-2 の解析どおり ★`req_offset_r` の余裕は無限ではなく約 4 psram cyc（125 ns）★ です。

- `set_false_path` は「この経路のタイミングは**一切検証しない**」という宣言であり、★配置配線が 125 ns を超える遅延を作っても警告が出ません★
- `set_max_delay` なら上限を明示でき、★`LATENCY_NORMAL` を下げたときに制約値を見直すべきことが制約ファイルに残ります★

`fill_hit_byte_r` → `cpu_clk` 側についても同様で、こちらは余裕 16 psram cyc（500 ns）と大きいものの、★同じ理由で `set_max_delay` が安全★です。Step 8-Impl への申し送りに ★**制約種別と値の根拠（余裕サイクル数）**★ まで書いて渡されたい。

### N-2 余裕サイクル数を RTL コメントに残す

M-2・N-1 の数値（`req_offset_r`：余裕 `LATENCY_NORMAL − 8` psram cyc／`fill_hit_byte_r`：余裕 16 psram cyc）は、★RTL のソースコメントにも残す★ことを推奨します。設計メモは追補文書であり、将来 `LATENCY_NORMAL` を触る人が本メモに辿り着く保証がありません。★KY34（実ファイルが真実）の裏返しで、**制約の根拠は実ファイル側にも置く**★のが確実です。
