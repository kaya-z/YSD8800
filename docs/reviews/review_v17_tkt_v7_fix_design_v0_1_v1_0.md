## §2. 必須修正（M）の詳細

### 2.1 M-1：T-4/T-5 の「サイクル不変」を一律の合格基準にできない

§5 の注記「本修正は返却値のみを是正するものであり、タイミングを変えてはならない」は
★MISMATCH=0 だったビンについては正しい。★ しかし MISMATCH>0 だったビンには適用できない。

| ビン | 修正前 MISMATCH | 修正でデータが変わるか | サイクル不変を要求できるか |
|---|---|---|---|
| Dhrystone -O0 / CEN=0 | 0 | 変わらない | ★可（1,070,369）★ |
| Dhrystone -O0 / CEN=1 | 0 | 変わらない | ★可（612,074）★ |
| YUI OS / CEN=0 | 0 | 変わらない | ★可（3,754,937）★ |
| ★YUI OS / CEN=1★ | ★3★ | ★変わる（$24 → $02）★ | ★不可★ |

★誤った値が CPU に返っていた以上、その値は実行に取り込まれている。★
是正すれば分岐・ループ回数・UART 出力タイミングが変わりうるのだから、
M-5 が 2,010,458 と一致する保証はない。★一致しないことは欠陥ではない。★

**修正要求**：T-5 の合格基準を次のように分けよ。

| # | CEN | 合格基準 |
|---|---|---|
| T-5a | 0 | ★M-5 = 3,754,937 と完全一致★（データ不変であるため） |
| T-5b | 1 | ★MISMATCH = 0 かつ M-1〜M-5 全マイルストン到達（機能 PASS）★。M-5 の値は ★記録して差分を分析する★。2,010,458 との一致は要求しない |

★差が出た場合は「3 件の誤返却が実行に与えていた影響量」として記録すること。★
これは §1.2 の「M-5 一致は安定の証拠ではなかった」という主張の定量的な裏付けになる。

### 2.2 M-2（R-2 への回答）：`fill_index_r` の CDC 前提が残る

§2.3(2) は `req_offset_r` のみを挙げるが、★`fill_index_r` は同一の前提に立っている。★

```
ysd8800_cache_v0_5.sv L88-89:
//    I-3: フィル先 index も psram_clk 側で必要。req_offset_r と同時に
//         fill_index_r としてラッチし、同じ CDC 余裕論法を適用する。
```

ポートA は `data_ram[{fill_index_r, beat_cnt_r[OFF_W-1:0]}]`（L412-414）で
★裸の `fill_index_r` を psram_clk 側で使用している。★
B' で offset だけを psram 側にラッチすると、★同じ前提に立つ 2 信号のうち片方だけが
保護された非対称な構造★になり、KY98 の再発源が残る。

**修正要求**：§3.5 のバースト開始ラッチで ★`fill_index_ps_r <= fill_index_r` も同時に取り、
ポートA は `fill_index_ps_r` を使う★ こと。§2.3 の表(2)も「`req_offset_r` および `fill_index_r`」に改めよ。

（補足：現行構造でも `fill_index_r` の更新は前フィルの `fill_done`＝`br_ready_i` 成立後であり、
バースト終了後になる可能性が高い。しかし ★それは「タイミング上たまたま間に合う」という
今回と同種の論法★ であり、B' の利点3「同期の根拠を実イベントに移す」を index にも適用すべきである。）

### 2.3 M-3（R-3 への回答）：ポートAのビート番号

I-1 の指摘内容は正しいが、★§3.5 の実装イメージにポートAが現れていない。★
そのまま実装すると次の不具合が残る。

- バースト開始サイクルで、ポートAの `always_ff` が参照する `beat_cnt_r` は ★ノンブロッキング代入前の旧値★
- すなわち前バーストが残した値（波形例では 34 やラップ後の値）で `data_ram` に beat 0 を書く
- ★ライン先頭バイトが誤位置に格納され、かつ正位置は未更新のまま `valid` が立つ★

**修正要求**：ビート番号を組合せで一本化し、捕捉比較とポートAの双方で共用せよ。

```
wire burst_start = fill_gate_ps & beat_valid_i & ~beat_valid_d;
wire [BLEN_W-1:0] beat_no = burst_start ? BLEN_W'(0) : beat_cnt_r;   // ★現ビート番号★

// 捕捉
if (fill_gate_ps && beat_valid_i) begin
    beat_cnt_r <= beat_no + BLEN_W'(1);
    if (beat_no == BLEN_W'(burst_start ? req_offset_r : req_off_ps_r))
        fill_hit_byte_r <= psram_rdata_i;
end

// ポートA
if (fill_gate_ps && beat_valid_i)
    data_ram[{burst_start ? fill_index_r : fill_index_ps_r,
              beat_no[OFF_W-1:0]}] <= psram_rdata_i;
```

★この形なら I-2（1 ビートずれ）も構造的に起きない★（`beat_no` が「現ビート番号」の
単一の定義になるため）。§3.5 の注意点 I-2 は「実装時に気をつける」ではなく
★構造で排除する★のが望ましい（原則：内部状態変数の変更箇所を集約）。

### 2.4 M-4：§3.4 の前提が 1 つ不足

§3.4 が検証しているのは ★「バースト内で `beat_valid` が途切れないこと」★ のみである。
B' が成立するにはもう 1 つ必要である。

★前提：`fill_gate_ps` が 1 の期間中に、フィル以外のバースト（blen=1 の単バイト読出／書込）が
psram_ctrl に発行されないこと。★

- `beat_valid` は ★単バイト読出でも書込でも立つ★（`ysd8800_cache_v0_5.sv` L82／`psram_ctrl` L169）
- これが起きると、その立上りが ★フィルのバースト開始と誤認され★、`beat_cnt_r` と
  `req_off_ps_r` がフィル途中でリセットされる ＝ ★今回と同型の欠陥が別経路で再発する★
- 実際には cdc_bridge の 4 相ハンドシェイクにより単一未完了要求しか存在しないはずだが、
  ★これは前提であって検証されていない★

**修正要求**：§3.4 に本前提を追加し、T-2 の検証項目に
「`fill_gate_ps==1` かつ `beat_valid_i` 立上りが ★フィル由来のみ★ であること」を含めよ。
TB 側アサーションとして常設するのが確実である（`fill_gate_ps && burst_start && !fill_active_r` で $error 等）。

## §3. 確認事項（C）の詳細

### 3.1 C-1：案 B' と、段4 で撤去された「案3」の関係

`ysd8800_cache_v0_5.sv` L190-195 に次の記録がある。

```
//     案3: フィルゲートを beat_valid 静穏後に武装する
//          → 効果なし。残留ビートではなかった。
//     3案とも ★不要と確認のうえ撤去済み★
```

★B' は「`beat_valid` の立上りを同期点に使う」点で案3 と外形が似ている。★
本設計書を読んだ第三者（あるいは後日の本人）が「一度否定された案では」と誤読する余地がある。

**要求**：§3.2 の却下案表に案3 を 1 行加え、次を明記せよ。

- 案3 は ★段4 の別問題（TB 起因の残留ビート）に対する対策★として試され、その問題には効かなかった
- B' が対象とするのは ★連続ミス時のカウンタ未リセット★ であり、★問題が異なる★
- したがって「効果なし」の記録は B' の否定材料にならない

★過去の否定記録を無視するのではなく、射程が違うことを明示する★のが KY41 の趣旨に適う。

### 3.2 C-2：RTL コメントと実装の乖離

`ysd8800_cache_v0_5.sv` L370-386 は「★段4-fix（I-2 の不備是正）★」と題し、
「是正: ゲートを開いた後 beat_valid の静穏を確認してから武装する」と記述している。
★しかし当該 `always_ff` に静穏確認は実装されていない★（リセット根拠は `!fill_gate_ps` のみ）。
かつ L190-195 では同じ案が「効果なし・撤去済み」と記録されている。★同一ファイル内で矛盾している。★

これは今回の欠陥が長く潜伏した一因になり得る（読み手は「対策済み」と誤認する）。

**要求**：v0.6 の変更内容に ★L370-386 のコメント整理★ を含めよ。
「段4 の結論は TB 起因であり、RTL 側の是正は行っていない」旨に改める。
情報は削らず、経緯として残すこと（KY41）。

### 3.3 C-3（R-4 への回答）：MISMATCH モニタの観測点

§4.2 の擬似コードは `mem_addr < 20'hFC80` で MMIO を除外している。
★`mem_addr` が 20bit（物理・MMU 出力側）か 16bit（論理・CPU 側）かで意味が変わる。★

| 観測点 | `$FC80` 比較の妥当性 |
|---|---|
| CPU 側（論理 16bit） | ★正しい★。デコーダの `is_mmio = (cpu_mem_addr >= 16'hFC80)` と同一基準（`ysd8800_addr_decoder_v0_1.sv` L43） |
| MMU 出力側（物理 20bit） | ★MMIO はそもそも RAM パスに来ない★（MMIO はデコーダ前段で分岐）ため除外は不要。逆に ★物理 `$0FC80`〜`$0FFFF` は正当な RAM★ であり、これを除外すると ★見逃し（偽陰性）が生じる★ |

YUI OS は MMU を使うため、この違いは実害になる。

**要求**：§4.2 に観測信号の階層パスを明記し、上表の判断を添えよ。
物理側で観測するなら ★`$FC80` フィルタは削除★ が正しい。

### 3.4 N-1：段7-A 計画書への波及

§4.3 で G-M を常設ゲート化する以上、★`v16_stage7a_rtl_dhrystone_plan_v0_2.md` の
§4.2 差分表に D-7（MISMATCH モニタの追加）が必要★である。
現状の同書は差分 6 点で確定しており、このままでは段7-A の TB に G-M が入らない。

段7-A 計画は既に承認済（M-4 反映条件）であるため、★v0.3 で D-7 を追記し、
本指摘書を出典として記録★されたい（KY41）。
