## 総評

本設計メモは、これまでレビューした一連の設計書の中でも特に完成度が高い。以下を確認した。

### 実源照合（KY34）— 正確

- **§1.2 `fold_binop_val` = floor**：`return (int16_t)(tmp >> 8)`（算術右シフト）を確認。正確。
- **§1.3 `_fmul` = ゼロ方向**：`emit_runtime` の生成コードを実源で確認。両オペランドを `NOT`+`ADDI #1` で絶対値化 → 符号フラグ（`_C_DIV_A`）を XOR で管理 → 非負でシフト加算 → 末尾で符号適用、という方式であり、**全体としてゼロ方向丸めであることは正しい**。
- **§1.5 `_fdiv` は一致**：`_fdiv` も同じ絶対値方式（`_C_DIV_B` を符号フラグに使用）で、`fold_binop_val` の FDIV も C 整数除算＝ゼロ方向。**両者一致・修正対象は FMUL のみ**という判断は正しい。

### 数値検証 — 全件正確（レビュア独立検算）

**§1.4 の不一致表8件、§2.6 の等価性検算表11件とも、当方の独立検算で全件一致を確認した。**

> 検算過程での自己訂正: 当方は初回検算で `to_fixed(0.3)` を 77 と誤り、`-2.5 * 0.3` を「不一致」と誤判定した。正しくは `0.3 × 256 = 76.8` → ゼロ方向切り捨てで **76**、`tmp = -640 × 76 = -48640`（256 の倍数）ゆえ **fold/_fmul ともに -190 で一致**。**設計書の記載が正しく、当方の検算が誤っていた**。設計書は `to_fixed` を正しく経由している。

### 修正案の等価性 — 網羅検証で完全一致

§2.5 の修正案（絶対値化 → `>>8` → 符号付与）を Python で再実装し、ランタイム `_fmul` の絶対値方式と突合した：

- 境界値（`0, ±1, ±25, ±128, ±256, ±640, ±1024, 32767, ±32768` 等）の全組合せ 324 ケース
- ランダム 200,000 ケース（`a, b ∈ [-32768, 32767]`）

**合計 200,324 ケースで不一致 0 件**。修正案はランタイムと完全に等価である。`INT32_MIN` 到達不可の論証（`|tmp| ≤ 32768² = 2³⁰`）も妥当。

### 論証 — 妥当

- **§1.6.1 の発見が決定的**：`0.1 * -0.1` は畳み込まれず -2、**`(0.0 - 0.1) * 0.1` は畳み込まれて -3**。数学的に同一の式が書き方で結果が変わることを実測で示し、本件を「潜在バグ」から「**現行 v2.06 で既に発現しているバグ**」へ位置づけ直した点は的確。
- **案A 採用の根拠**：「コンパイル時畳み込みは実行時と同じ結果を先に計算する最適化に過ぎず、**最適化が挙動を変えてはならない**。ゆえにコンパイル時を実行時に合わせるのが原理的に正しい」——この論理は正しく、案B（ランタイム改修・コード量/サイクル増・FPGA 検証済バイナリに差分）却下の判断も妥当。
- **§3.3 の波及追跡**：`q88.py` の `q_mul()` 修正、self-test C2/C3 の期待値変更（-3→-2、-13→-12）、README・C-2 設計メモの改版まで漏れなく列挙。§7.1 で「グループC の目的が『非対称の検出』→『ゼロ方向丸めの検証』へ変わるが検出力は維持」と整理した点も正確。

## N-1【推奨・別件起票】§7.4 の懸念は実在する。`_cc_div`（int 除算）に符号処理が無い

**箇所**: §7.4「同種の不一致の総点検」

**内容**: §7.4 は「`_cc_mul`/`_cc_div`（int 演算）についても同様の突合を推奨。int 除算は C も `_cc_div` もゼロ方向と思われるが**未確認**」としている。当方で先行確認したところ、**懸念は実在し、しかも丸め方向の 1 LSB ずれより深刻**であった。

**実源（`emit_runtime` の `_cc_div`）**:

```
_cc_div:
    CMPI A, #0
    BEQ  _ccdiv_zero
    STW  A, [_C_DIV_A]      ; 除数
    STW  B, [_C_DIV_B]      ; 被除数
    LDW  A, #0
    STW  A, [_C_DIV_Q]
_ccdiv_loop:
    LDW  A, [_C_DIV_B]      ; 残り
    LDW  B, [_C_DIV_A]      ; 除数
    CMP  A, B
    BLT  _ccdiv_done        ; 残り < 除数 で終了（符号付き比較）
    SUB  A, B
    ...Q++...
```

**`_fmul`/`_fdiv` が持つ符号分離（絶対値化＋符号フラグ）が `_cc_div` には無い**。単純な引き算ループであり、`BLT` は符号付き比較のため負値で破綻する。当方のシミュレーション結果：

| 式 | C（`fold_binop_val` int 経路） | `_cc_div`（実行時） | 判定 |
|---|---|---|---|
| `7 / 2` | 3 | 3 | 一致 |
| `100 / 7` | 14 | 14 | 一致 |
| **`-7 / 2`** | **-3** | **0**（初回で `rem < b` が真→即終了） | **不一致** |
| **`-100 / 7`** | **-14** | **0** | **不一致** |
| **`7 / -2`** | **-3** | **無限ループの恐れ**（`rem -= b` で増加し続ける） | **重大** |

すなわち **int の負値除算は、コンパイル時畳み込みなら正しい値、実行時なら 0 または無限ループ**という状態である。

**対応案**: 本件は v2.07（FMUL 丸め）の**スコープ外**であり、本設計書に取り込むべきではない（1変更1検証の原則）。ただし §7.4 を「未確認・推奨」から「**確認済・別件として起票要**」へ格上げし、以下を明記することを推奨する。

- `_cc_div` に符号処理が無いことは**実源で確認済**（丸め方向の問題ではなく符号未対応）
- 負値の int 除算は実行時に破綻する（0 返し／無限ループ）
- **Phase 2 を待たず別チケットで起票**すべき重大度である（無限ループは実機ハングに直結）
- `_cc_mod`（同じ引き算ループ方式）も同様の疑いがあり、併せて点検が必要

> 補足: 既存ソース（Dhrystone 等）で顕在化していないのは、負値の int 除算が使われていないためと推測される。ただし C コードで `-x / y` は自然に書かれうるため、実害リスクは FMUL より高い。

## N-2【推奨】§4.1 V1 の検証式に「畳み込み経路」の明示を

**箇所**: §4.1 V1

**内容**: V1 は §1.6.1 の 2 式（`0.1 * -0.1` と `(0.0 - 0.1) * 0.1`）の結果一致で検証するとしている。これは適切だが、**修正後は両者が -2 で一致する**ことになる。検証時に「両方 -2」を確認するだけでなく、**それぞれが期待通りの経路を通っている**（前者は `JSR _fmul` あり＝実行時、後者はランタイム呼出 0 件＝畳み込み）ことも併せて確認すべき。

理由: 仮に修正の副作用で `(0.0 - 0.1) * 0.1` が畳み込まれなくなった場合、両者とも実行時パスとなり「-2 で一致」するが、それは**畳み込みが効かなくなった別の退行**である。経路の確認がないと見逃す。

**対応案**: V1 の合格基準に「`(0.0 - 0.1) * 0.1` はランタイム呼出 0 件（畳み込み維持）、`0.1 * -0.1` は `JSR _fmul` 1 件（実行時維持）であること」を追加。

## E-1【軽微】§1.4 の表に `to_fixed` 値を併記すると検算しやすい

**箇所**: §1.4 不一致表
