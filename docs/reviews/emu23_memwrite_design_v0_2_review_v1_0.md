## 2. C 指摘（確認・明記要求：3件）

### C-1 ★重要★ 【§4.1.1】`dbg_access` は **MMIO 副作用を止めない**。A-1 の「対応」欄が解決済みに読める

§4.1.1 の確定リストは A-1（`dump_memw()`）の対応を「★`dbg_access` で包む★」と記す。しかし **`dbg_access` が抑止するのは `mem_charge()` だけ**である。`rd16()` の内部で行われる **MMU 変換と MMIO ディスパッチは止まらない**。

したがって `dbg_access` で包んだ後も：

| 汚染の種類 | `dbg_access` で解決するか |
|---|---|
| サイクル課金（`-mc` / `--mem-latency`） | ✅ **解決する** |
| キャッシュ統計（`--cache-stats`） | ✅ **解決する** |
| トレース（`--trace-addr`） | ✅ **解決する** |
| **MMIO 副作用（`memw $FC80` で UART FIFO が進む）** | ❌ **解決しない。残る** |

v0.2 は MW-2 として別起票しているため**認識はある**。問題は表記である。§4.1.1 の表だけを読むと A-1 が片付いたように見え、§5.2 手順2 の検証項目も「`--cache-stats` が `memw`/`reset`/`-d` で動かないこと」と**課金側だけ**を見ている。この検証が PASS しても MMIO 副作用は残る。

**要求**：

1. §4.1.1 の A-1 行に「★**課金・統計・トレースのみ抑止。MMIO 副作用は残る（→ MW-2）**★」と明記されたい。
2. §5.2 手順2 の検証欄に「**ただし `memw $FC80` の MMIO 副作用は本手順では解消しない**」と併記されたい。
3. `dbg_access` の定義コメント（§4.1）は「デバッガ由来のメモリアクセス中は 1。CPU の命令実行に由来しないアクセスは**サイクルを消費しない**」となっており、**サイクルに限定した表現で正確**である。この正確さを §4.1.1 の表でも保つこと。

> **なぜ重要か**：MW-1 と MW-2 はともに「高」優先度で先送りされている。先送りの判断自体は妥当だが、**MW-2 の残存範囲が §4.1.1 の表で見えなくなる**と、v2.13 完了時に「A-1 は対応済み」と誤認して MW-2 の再判断が飛ぶ恐れがある。§10 の但し書き（「v2.13 完了後、①.5 着手前に MW-1 / MW-2 の実施可否を判断すること」）を生かすためにも、残存範囲は表に書いておくべきである。

### C-2 ★重要★ 【§4.1.1】L3280 を包まない判断は、**`emu23_mc_design` §3.4 のリセット非計上方針と衝突する**

§4.1.1 は L3280（`cpu.pc = rd16(0x0000); // reset vector`）を包まない理由を次のように述べる。

> **CPU リセット動作の一部**であり、デバッガ由来ではない。実機の CPU もリセット時にベクタを読む。**課金対象として正しい**

基準の言語化（REPL/CLI 由来か否か）は明快であり、**基準そのものは支持する**。しかし結論「課金対象として正しい」は、**既存の確定方針と食い違う**。

| 文書 | 記述 |
|---|---|
| `emu23_mc_design_v0_6.md` §3.4 | **リセットシーケンスは emu23 では非計上**（サイクル表にはリセット 2 があるが計上しない） |
| `cycle_table_v1_1_revision_design_v0_2.md` §14 / v0.1 §6 要因3 | 「リセットシーケンス：**emu23 非計上**・RTL 2 サイクル」 |

すなわち **emu23 は「リセットは計上しない」という方針を明示的に採っている**。にもかかわらず L3280 の `rd16()` は `mem_charge()` を通り、**キャッシュ統計とトレースに 2 アクセスを記録する**。

**実害の評価**：

- `-mc` の cycle 値：**影響なし**（L3280 は初期化時で、以降 `cpu.cycle` が 0 起点になる）。339,240 は揺らがない
- `--cache-stats` の `stat_hit`/`stat_miss`：**リセットベクタ読み出しの 2 バイトが混入する**
- `--trace-addr` のトレース：**先頭に $0000/$0001 の 2 行が現れる**

実害は小さいが、**判断基準が 2 つ存在し、設計書はその衝突に気づいていない**。

| 基準 | L3280 の扱い |
|---|---|
| §4.1.1 の基準（REPL/CLI 由来か） | 由来しない → **包まない** |
| mc_design §3.4 の方針（リセットは非計上） | リセット動作 → **計上すべきでない** |

**要求**：どちらの扱いを採るかを明示し、**採らなかった方との整合を §4.1.1 に一言記載**されたい。推奨は次のとおり。

> **L3280 は包まない（現案どおり）。ただし「リセット非計上」は `-mc` のサイクル計上に関する方針であり、キャッシュ統計・トレースへの記録可否とは別の論点である。統計に 2 アクセスが混入することは既知の仕様とし、`--cache-stats` の解釈時に留意する。**

このように**論点を分離して整理**すれば、両者は矛盾しない。逆に整理せずに置くと、後日 `--cache-stats` の値を検算した人が「なぜ 2 多いのか」で必ず躓く。§4.1.1 の「基準を取り違えると逆方向の汚染を招く」という良い洞察を、**この一件にも適用**されたい。

### C-3 【§3.3】読み返しに用いる**物理アドレスの取得方法**が未定義。二重変換の危険がある

§3.3 は次のように述べる。

> 読み返しは ★**書き込みで実際に確定した物理アドレスから行う**★。書き込みルーチン内で得た物理アドレスをそのまま読み返しに用い、**同一アドレスであることを構造的に保証**する

**方針は正しいが、実現方法が書かれていない。** `wr8()` は内部で `mmu_translate()` を呼び、**物理アドレスを呼び出し側に返さない**。したがって呼び出し側が物理アドレスを得るには、次のいずれかが必要である。

| 方法 | 評価 |
|---|---|
| a | 呼び出し側でも `mmu_translate(addr)` を別途呼ぶ | ✗ **二重変換**。両者の間に MMU マッピングが変われば別アドレスを読む |
| **b（推奨）** | `wr8()` に物理アドレスを出力する引数を足すか、デバッガ用の薄いラッパを用意して**変換を 1 回だけ行い保持**する | ◎ 構造的保証が実際に成立する |

**方法 a には具体的な事故シナリオがある。** `setb` で **MMU の PTR レジスタを書き換えた**場合、書き込み後に再変換すると**書いた先とは別の物理アドレスを読む**。まさに §3.3 が防ごうとしている「書けたつもり」の再生産である。

実際にはこの事故は起きない——MMU PTR は MMIO 帯にあり、§3.3 の MMIO 判定により読み返しが省略されるからである。**しかし、その安全性が「MMIO 判定式の共用」に依存していることが設計書に書かれていない。** 判定範囲が将来変われば安全性が失われる。

**要求**：

1. §3.3 に物理アドレスの取得方法（推奨は方法 b）を明記されたい。
2. あわせて「MMU 制御レジスタへの書き込みは MMIO 帯判定により読み返しが省略されるため、二重変換の問題は生じない」という**依存関係を明示**されたい。原則122 の「判定式を単一箇所で共用する」という §3.3 の方針が、**MMIO 警告のためだけでなく、この安全性のためにも必要**であることが読み取れる形にすること。
