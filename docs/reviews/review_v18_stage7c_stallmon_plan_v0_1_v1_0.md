## §2. 必須修正の詳細

### 2.1 M-1：G-M の観測点移行が抜けている

TKT-V7 v0.3 §4.2 で ★G-M の正式仕様は「キャッシュ境界（`u_membus.u_cache` のポート・物理 20bit）」に確定した。★
しかし現行 TB の MISMATCH モニタは ★旧観測点のまま★ である。

```
tb_cpu_v8e_dhry_v0_2.sv L546-548:
  if (cpu_rst_n && mem_rd && mem_ready && (mem_addr < 20'hFC80)) begin
      if (mem_rdata !== u_membus.u_psram_ctrl.mem[mem_addr]) begin
```

★これは CPU 側（論理）観測＋`$FC80` フィルタであり、v0.3 が「偶然正しかっただけ」と
評価して置き換えた方の実装である。★

- C-4 規律により、モニタを触れば測定はやり直しになる
- ★本計画は 4 ビンを測り直す唯一の機会であり、ここで移行しなければ次の機会は工程③以降になる★
- 放置すれば「設計書には確定と書いたが実装していない」＝ ★KY100 を自ら踏む★
  （§1 で P-3 について同じ理由を挙げているのだから、G-M にも同じ論理が適用される）

**修正要求**：§5.1・§5.2 のチェックリストに項目 g を追加せよ。

| # | 項目 | 種別 |
|---|---|---|
| ★g★ | ★MISMATCH モニタの観測点を `u_membus.u_cache.cpu_phys_addr_i` / `cpu_rd_i` / `cpu_ready_o` / `cpu_rdata_o` へ移行（`$FC80` フィルタは削除）★ | TKT-V7 §4.2 |

★併せて、移行前後で YUI OS CEN=1 の MISMATCH が 0 のまま変わらないことを確認する★
（TKT-V7 §4.4.1 と同じ「観測点非依存」の確認。修正後は両方 0 であるから、
0 のまま一致することが確認になる）。

### 2.2 M-2：IRQ0 の期待値モデル

§4.2 の期待値 `C_total / 40,000` は ★タイマが自走している場合の値★ である。
しかし YSD8002 v0.3 は ★ワンショット＋ソフト再武装★ モデルである。

| 事実 | 実源 |
|---|---|
| ★発火すると `armed_r <= 1'b0`（自己武装解除）★ | `ysd8800_ysd8002_v0_3.sv` L288-290 |
| ★再武装は TCR bit5（IRQ_ACK）書込のみ★。`cnt_r <= cycle_i + period_r` | 同 L323-325, L456 |
| `fire = armed_r & fire_en & (cycle_i >= cnt_r)`、`fire_en = timer_en_r & irq_en_r` | 同 L210, L232 |
| リセット時に `timer_en_r=1 / irq_en_r=1 / armed_r=1 / period_r=40000 / cnt_r=40000` | 同 L270-274 |

★したがって `irq0_fire_count` は「タイマ RTL の正常性」ではなく、
「RTL ＋ ハンドラの再武装ループ」の複合指標である。★
低い値が出ても、それが RTL 側か software 側かを ★この 1 指標では分離できない。★

さらに、Dhrystone 実測（CEN=0 で 1 回・CEN=1 で 0 回）の解釈は次のように分かれる。

| 観測 | 示唆 |
|---|---|
| ★0 回★ | ★一度も発火していない★ → `fire_en` / `cycle_i` / `armed_r` 側の問題。`C_total`(612,074) > 40,000 である以上、初回発火すら無いのは異常 |
| ★1 回★ | ★初回は発火したが再武装されていない★ → ハンドラの TCR-ACK 書込側の問題 |

★この 0 と 1 の差は本質的に意味が違う。★ 計画がこの区別を持たないまま
「±20% 以内か否か」だけで重大度を決めると、本調査の起票内容が定まらない。

**修正要求**：

1. §5.1 e / §5.2 e に ★TCR-ACK 書込回数の計数★ を追加する
   （`u_membus.u_mmio_stub.u_ysd8002` の TCR 書込かつ `wdata_i[5]` を計数、
   または `armed_r` の立上りを計数。後者の方が階層参照が 1 本で済む）
2. §4.2 に ★終了時点の `armed_r` / `timer_en_r` / `irq_en_r` / `cnt_r` の値を `$display`★ する
   （最終状態のスナップショットは、原因の当たりを付ける最も安価な情報である）
3. §4.2 の判断表を ★2 軸（fire 回数 × ACK 回数）★ に改める

| fire | ACK | 示唆 | 重大度 |
|---|---|---|---|
| 期待値近傍 | 期待値近傍 | 正常 | 低（維持） |
| 0 | 0 | ★発火自体が起きていない★ | ★高★ |
| 1 | 0 | ★再武装されていない（ソフト側）★ | ★高★ |
| 1 | ≥1 | ACK は出ているが再武装が効いていない（RTL 側） | ★高★ |

★追加コストはほぼゼロであり、C-4 規律のもとでは「1 回の測定で得られる情報量」を
最大化することが最も価値が高い。★ §8-2（原因究明は本計画の対象外）というスコープ制限は
維持したままで、★次の調査の入口を狭められる。★

### 2.3 M-3：MMIO アクセスの混入

§2.2 の 3 分類は TB トップの `mem_rd`/`mem_wr` を見るため、★MMIO アクセスを含む。★
これは 2 つの経路で判断を歪める。

| 経路 | 影響 |
|---|---|
| Dhrystone | ★UART ビジーウェイトのポーリング読出★。`TX_CYCLES = 4167`／文字 ×9 バイト ≒ ★37,500 cyc★（`ysd8800_ysd8001_v0_1.sv` L138）。この間 `mem_rd && mem_ready` が繰り返され ★`bus_ack` と `C_total` を膨らませる★ |
| YUI OS | UART 出力・MMIO レジスタアクセスが同様に混入 |

★結果として書込ストール率（`stall_wr / C_total`）は過小に出る。★
§4.1 の閾値 15% は母数の定義に直接依存するのだから、
★母数に「キャッシュと無関係なサイクル」を含めたまま閾値判定するのは危うい。★

**修正要求**：`is_mmio = (mem_addr >= 'hFC80)` で分離し、次を別々に計数せよ。

| カウンタ | 内容 |
|---|---|
| `stall_wr` / `stall_rd` / `bus_ack` | ★RAM 側のみ★（キャッシュ対象） |
| `mmio_acc` | MMIO アクセスサイクル（参考値） |

★§4.1 の判断は RAM 側の値で行う★ とし、`C_total` に対する比率と
「MMIO を除いた実効サイクル」に対する比率の ★両方を記録★ すること。
（TKT-V7 §4.2 で `$FC80` フィルタを不要にしたのは ★観測点が RAM パス専用だったから★ であり、
本計画の観測点は CPU 側バスなのでフィルタが要る。★観測点が違えば必要な処理も違う★ という
対比を §2.1 に 1 行入れておくと、将来の読み手が混乱しない。）

## §3. 確認事項

### 3.1 C-1：「ライトスルーの代償」という表現

§2.2 は `stall_wr` を「★ライトスルーの代償（本命）★」と位置づけているが、
★書込はキャッシュの有無にかかわらず PSRAM へ出る★（ノーライトアロケート／ライトスルー）。
すなわち ★CEN=0 と CEN=1 で `stall_wr` はほぼ同一になるはずである。★

これは 2 つの意味を持つ。

1. ★追加の陰性対照として使える★：`stall_wr(CEN=0) ≒ stall_wr(CEN=1)` を確認せよ。
   大きく違えば、モニタか前提のどちらかがおかしい（§3.1 の陽性対照と対をなす）
2. ★用語の明確化が要る★：ライトバッファの検討動機は「キャッシュが読出を速くした結果、
   ★書込の相対比率が上がった★」ことであって、キャッシュが書込を遅くしたわけではない。
   §4.1 の判断を将来読み返すとき、この違いは重要である

### 3.2 C-3：`pass_final` に前提検証を含める

§2.2 は `bus_both != 0` なら ★本測定は無効★ と定めている。
それならば §5.3 の `pass_final` にも `(bus_both == 0)` を含めるのが一貫する。
★「前提が破れているのに PASS と表示される」のは、まさに S-1 で是正しようとしている
不一致と同型である。★

### 3.3 N-1：取りこぼしの検算

3 分類が排他かつ網羅であることを、★恒等式でアサートする★ ことを推奨する。

```
stall_wr + stall_rd + bus_ack + idle == C_total    // idle = バス非アクセスサイクル
```

これが成立しないなら、`mem_rd`/`mem_wr`/`mem_ready` の組合せに
想定外のパターン（例：ready 成立後も要求が残る）があることを意味する。
★測定値そのものより先に、測定系の健全性が確認できる。★

## §4. 本レビューで実源確認した事実（v0.2 へ転記可）

§4.2 の「★RTL もカーネルのタイマ処理も一行も読んでいない★」という但し書きは
スコープ制限として適切だが、★期待値 40,000 の根拠だけは確認済にできる。★

| # | 事実 | 実源 |
|---|---|---|
| V-1 | ★`period_r` のリセット値は `32'd40000`、`cnt_r` も同値（初回発火は cycle 40,000）★ | `ysd8800_ysd8002_v0_3.sv` L272-273 |
| V-2 | ★リセット時点で `timer_en_r=1 / irq_en_r=1 / armed_r=1`★ ＝ ソフトの初期化なしで武装済 | 同 L270-274 |
| V-3 | ★カーネル（`kernel_v12_11.asm`）にも Dhrystone ハーネスにも PERIOD レジスタへの書込は無い★。両者とも TCR($FC90) しか触らない | `kernel_v12_11.asm` L389-392, L497-498／`startup_harness23_v17.asm` L110-112 |
| V-4 | ★`cycle_i` は `cpu_clk` 1 周期につき +1（クロック数）★。emu23 の `cpu.cycle`（命令数・CPI=1）とは ★単位が異なる★ | `ysd8800_v5_membus_v0_12.sv` L386-390 およびヘッダ注記 |

★V-1〜V-3 により、YUI OS 側でも期待周期は 40,000 cyc であることが確定する。★
（V-3 が重要：カーネルが独自の周期を設定していれば期待値の前提が崩れるところだった。）

★V-4 は §4.2 に明記されたい。★ 「40,000 cyc 周期」がクロック数であってサイクル数＝命令数ではない
ことは、emu23 との比較を行う段7-B で必ず効いてくる。
