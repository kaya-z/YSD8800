## 1. 総評

V8 は、これまで積み上げた全設計（案(D) wait-state・W1C stor割込・SPI-FSM・YUIFS）が、実ファイルシステムを通して初めて統合される最終関門である。read専用 cat/ls に絞り CMD24 書込を回避（A-1）した判断は、統合の本質（SPI read → FS解釈 → OS動作）を最短で実証する賢い割り切りである。

本レビューで最も注視したのは**偽合格の構造**——「TBが実SD読み出しを検証しているか、別経路の期待値と一致しただけか」。実源照合の結果、**本設計は偽合格を構造的に回避できている**（§2）。依頼5件すべて承認する。Mレベルの指摘は無い。KY54 の負例に1段の強化余地があり、これを追加推奨として挙げる（§3）。

## 2. ★偽合格回避の構造を確認（本統合試験の生命線）★

### 2.1 懸念：期待値とディスク内容がどちらも mkfs 由来

期待文字列 `Hello, YUI OS!` は mkfs の `DEFAULT_FILE_CONTENT`（L63 で実照合）そのもの。素朴には「mkfs の仕様を2回書いて突き合わせただけ＝SD経路を検証していない」偽合格を疑うべき局面である。

### 2.2 結論：偽合格は起きない。経路全体を通さねば期待文字列が出ない

実源照合により、本設計が健全であることを確認した：

| 検証点 | 実源根拠 |
|---|---|
| デモCは sd_read 経由でしかデータを得ない | 雛形 `v6_sdread_test_poc.c` L69 sd_read → L106 実呼び出し。ハードコード "Hello" 文字列は無い（grep 確認） |
| SDモデルは当該LBAの実バイトを返す | `img_mem[cur_lba*512 + data_idx]`（§3.1）。既存アドレッシング L79-80 と同一 |
| FS解釈の全経路が必要 | superblock読(magic照合) → dir走査(flags&USED) → data sector読 → size分出力。どこが壊れても `Hello, YUI OS!` は出ない |

★核心：期待値が mkfs 由来なのは**問題ではなく、むしろ正しい**。「SDに書かれた内容を、SD経由で読み、FS解釈して取り出す」という往復の全経路を通さねば期待文字列に到達しないため、期待値＝ディスク内容の一致は「往復が正しく機能した」ことの証明になる。これは偽合格ではなく、統合の正しい合格条件である。★

### 2.3 mkfs レイアウトの正確性（§2.1）

メモ§2.1 の YUIFS レイアウト記述は実源と一致：
- `FS_MAGIC = b"YUIFS\x00\x00\x00"`（8B, L45）
- superblock オフセット（magic/ver/sec_size/dir_start/data_start/file_count）は struct.pack_into で定義（L191-201）と整合
- `--add-file`: 内容 `Hello, YUI OS!\n`(15B)、dir index 0、file_count=1（L63・L152・L187）

メモの KY34 実確認は正確。

## 3. ★追加推奨：KY54 の負例を1段強化（内容差し替え負例）★

メモ§5/§7-Step4 の負例は「期待文字列を意図的にずらす or 空イメージ」とする。これは**TBの照合機構が働くこと**は確認できるが、**デモCが本当にSDの中身を読んでいること**までは保証しない。

より鋭い負例を1本推奨する：

> **内容差し替え負例**：mkfs で `--add-file` の内容を別文字列（例 `Goodbye, YUI!\n`）にしたイメージを積み、デモCが**その別文字列を出力する**ことを確認する。期待文字列は正例の `Hello, YUI OS!` のままにしておく → MISM 検出。

**狙い**：これが PASS（MISM検出）すれば、「デモCはSDの実内容を読んでおり、ハードコードしていない」ことが積極的に証明される。空イメージ負例は「読めないと落ちる」を見るが、内容差し替え負例は「**読んだ内容がそのまま出る**」を見る。後者の方が「SD→FS→出力」の因果を強く縛る。

- 実装コスト僅少（mkfs の --add-file 内容を変えて再 hex 化するだけ、デモC・TB は不変）。
- KY54 の「負例先行」の精神をさらに徹底する。空イメージ負例と併用すれば、照合機構の健全性（空で落ちる）と経路の忠実性（内容差で追従する）の両方を押さえられる。

> 任意だが費用対効果が高い。特に本統合は「期待値＝ディスク内容」ゆえ、ハードコード混入があっても正例は通ってしまう構造的リスクがある。内容差し替え負例はその唯一の直接的検出手段である。

## 5. その他の所見

- **§3.3 デモCの ISA健全性確認**（hasm23 で ISA外命令なしを確認）：適切。統合の複雑なCコードでもコンパイラがISA2.3内に収めることの確認は、原則（ISAに無い命令を使わない）に忠実。
- **§4 ビルドチェーン**：CHAT111 §1.3 準拠（scc23 3オプション必須・harness JSR _main sed直書き・道結合）。既存手順の踏襲で妥当。ただし build 手順書(yuios_build_procedure)の版と整合しているか、KY として結合前に確認を。
- **§6 無改修死守**（sd_sample.c / mkfs / RTL は触らない）：本統合の価値の核。cat/ls が**既存の無改修コード**で動くことこそ「OS統合成功」の意味。この一線を守る姿勢は正しい。SDモデル(TB環境)とデモC(新規)のみ可変、という切り分けも明確。
- **§7 段階**：Step1(イメージ生成)→Step2(モデル単体)→Step3(デモC+ビルド)→Step4(統合TB)→Step5(ALL PASS) の1変更1検証は的確。特に Step2 でモデル単体($readmemh→LBA返却)を先に固めるのは、統合前にモデルの正しさを独立検証する good practice。

## 6. 総合判定

**承認（Mレベル指摘なし）。原則43により実装着手可。**

- **依頼1-5すべて承認**。$readmemh供給・UART照合・8KBイメージ・出力フォーマット・HELLO.TXT はいずれも妥当。
- **偽合格回避の構造を確認**：期待値=ディスク内容(mkfs由来)は、SD→FS→出力の全経路を通さねば到達しないため、正しい合格条件である。
- **★追加推奨（KY54強化）**：内容差し替え負例（別文字列イメージを積みデモCが追従することを確認）を1本追加。「デモCがSD実内容を読む(ハードコードでない)」ことの唯一の直接的証明。空イメージ負例と併用推奨。★
- **確定順序の注意**：期待出力はデモC出力仕様をStep3でfixしてからバイト単位で確定（LF/末尾改行/ラベルのズレ防止）。

本統合が ALL PASS すれば、YSD8003(ストレージ)+YUIFS+YUI OS が実SPI経由で結合し、OS無改修で cat/ls が動くことが実証される——V6-A から続くストレージ工程の到達点である。実装（Step1）へ進んでよい。

> **所見**：この統合試験は「emu23 という黄金が使えない領域で、mkfs が書いた実イメージを SD 経由で読み FS 解釈して取り出す」という往復突合を正解に据えた。これは前回 V6-A 単体レビューで述べた「判定軸を外部契約に移す」の正しい発展形であり、mkfs（書く側）と デモC（読む側）が独立に YUIFS 仕様を実装していることが、相互検証（一方のバグは不一致で露見）としても機能する。設計として筋が良い。
