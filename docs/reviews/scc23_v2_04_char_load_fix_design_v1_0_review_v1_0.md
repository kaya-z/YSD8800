## 1. 総評

CHAT119 で判明した「char ロード幅不一致（1バイト書き STB / 2バイト読み LDW の非対称性）」に対する修正設計として、**技術的に妥当かつ実装リスクが最小化された良い設計書**。特筆すべき点：

- **§1.3 のバグ位置特定が実源と完全一致**（scc23_v2_03.c L2510-2522 を1バイト単位で確認済）
- **§1.4 の類似箇所点検が網羅的**（LDW A,[X+...] を出す全経路を列挙、L2278/L2352-2354/L2423-2425/L2498-2500/L2817-2819 の各位置の正当性を1件ずつ判定）
- **§2 の ISA 制約確認が実源準拠**（LDB は [imm16] と [X] のみ、[X+off] 非対応。ADDI/SUBI の X 対応）
- **案1〜4 の比較が明確**（案2 の Cの意味論違反による却下、案4 の対症療法性の指摘、案3 の根本治療性）
- **§4.4 割込との相互作用の判定に §2.5 の一次確認を根拠として明示**
- **§7 申し送りに将来の規約明文化まで含めている**

**原則43（実装前レビュー）・原則76（実源照合）・原則57（仮説絞込）の実践として模範的。** 実装着手を止めるべき懸念はない。

以下、レビュー精査で気づいた**軽微な補足4件**を挙げる。すべて実装ブロッカーではないが、v1.1 改版時 or 実装時のコメント補足で反映を推奨する。

## 4. 指摘1（補足）: 命令サイズの確定値記載

### 該当箇所

v1.0 §4.5：

> 既存 `LDW A,[X+imm16]` = 4バイト（EXT+sub+imm16）に対し、修正後 `ADDI X,#imm + LDB A,[X] + SUBI X,#imm` = 4B+2B+4B = **10バイト**（EXT prefix と ADDI/SUBI の実バイト数は次項で要検算・現状概算）

### 実源確認による確定

**hasm23_v1_04.c L800-802**（PASS1 サイズ計算）:

```c
pc += 1;                           // opcode
if (in->has_reg) pc += 1;          // reg byte
if (in->has_imm) pc += 2;          // imm16
```

ADDI/SUBI は L145/L147 で has_reg=1, has_imm=1 → **各 4 バイト（opcode+reg_byte+imm16）で確定**。

**hasm23_v1_04.c L1053-1055**（PASS2 LDB/STB 出力）:

```c
OUT_BYTE(EXT_PREFIX);
OUT_BYTE(ei->sub_opcode);
pc += 2;
```

LDB [X] (EXT_INDRX) は L1056 の `if (am == EXT_ABS)` 分岐に入らない → **2 バイト（EXT_PREFIX + sub_opcode）で確定**。

**hasm23_v1_04.c L479**（LDW サイズ計算）:

```c
if (strncmp(ins,"X+",2)==0 || strncmp(ins,"X +",3)==0) return 1+1+2; // [X+imm]
```

既存 LDW A,[X+imm] = **4 バイト**で確定。

### 修正提案

§4.5 の「（EXT prefix と ADDI/SUBI の実バイト数は次項で要検算・現状概算）」を削除し、確定値のみで記述：

> 既存 `LDW A,[X+imm16]` = 4バイト（opcode+reg+imm16、hasm23_v1_04.c L800-802 で確定）に対し、修正後 `ADDI X,#imm + LDB A,[X] + SUBI X,#imm` = 4B+2B+4B = **10バイト**（LDB [X] は EXT prefix+sub_opcode=2B、hasm23_v1_04.c L1053-1055 で確定）。**+6バイト増**。

Ch_1_Loc/Ch_2_Loc の読出しは Func_1 内で数回発生する程度なので、コードサイズ増分は数十バイト以内で許容範囲。

### 影響

コンパイル済コードサイズの見積り精度が上がり、`toolchain23_design_v1_2.docx` や `HANDOVER_CHAT120.md` へ引き継ぐ際の情報が確定する。**実装ブロッカーではない**。

## 5. 指摘2（補足）: 書式指示子の一貫性

### 該当箇所

v1.0 §3.3 修正案：

```c
} else if (off>0) {
    emit("    ADDI X, #%d", off);
    emit("    LDB  A, [X]");
    emit("    SUBI X, #%d", off);
} else {
    emit("    SUBI X, #%d", -off);
    emit("    LDB  A, [X]");
    emit("    ADDI X, #%d", -off);
}
```

一方、既存 L2519-2520：

```c
else if (off>0) emit("    LDW  A, [X + #%d]", off);
else            emit("    LDW  A, [X + #$%04X]", (unsigned short)off);
```

### 分析

既存の LDW 経路は「off<0 の場合、`(unsigned short)off` で符号を 16bit 符号なしに変換し、`$%04X` で hex 表記」している。生成される即値そのものは `LDW A, [X + #$FFFC]` のような形になる（例: off=-4 → $FFFC）。

修正案では「off<0 の場合、`-off` で正の値にしてから `SUBI X, #%d`」を使う。生成される即値は `SUBI X, #4`（10進表記）。

**両者の差**:
- 既存 LDW: `[X + #$FFFC]`（符号なし 16bit hex 表現）
- 修正 SUBI: `#4`（10進表現）

**実害はない**（hasm23 は両表現とも解釈できる、L253 の `parse_addr` で `$` prefix 判定あり）。ただし、生成アセンブラを人間が読んだ際に「なぜ LDW は $FFFC で SUBI は 4 なのか」と混乱する可能性がある。

### 修正提案

v1.1 で以下の1行コメントを §3.3 修正案内 or §4.5 に追記推奨：

> 修正案で `SUBI X, #%d` に `-off`（正の数）を渡すのは、SUBI が加算値を正で扱う設計と整合させるため。既存 LDW 経路の `[X + #$%04X]` 表記（符号なし 16bit）とは表記が異なるが、生成アセンブラのアセンブル結果は等価。

### 影響

生成アセンブラを目視デバッグする際の可読性向上。**実装ブロッカーではない**。

## 6. 指摘3（補足）: 検証計画 V3 の判定手順明確化

### 該当箇所

v1.0 §5.3 V3 RTL 回帰：

> a〜d 全て PASS = 修正成功。特に **b の PASS が本修正の合否判定**。

### 懸念

- どの TB (`tb_cpu_v8d_ret_probe_v0_1.sv` を「用いる」とあるが、初期化パターン $FF/$AA/$55 版はまだ存在しないはず) を新規作成/派生するのか
- 各 TB の PASS 判定条件（UART=P:20? HALT? cycle上限?）
- 判定担当者と時系列（誰が→何を→いつ）

### 修正提案

v1.1 §5.3 に以下を追記推奨：

> **判定手順:**
> 1. `tb_cpu_v8d_ret_probe_v0_1.sv` を派生し、PSRAM 初期化パターンを $00/$FF/$AA/$55 の 4版として `tb_cpu_v8d_char_fix_v0_1_{00,ff,aa,55}.sv` を作成
> 2. scc23 v2.04 で dhry_timer.c を再ビルド、hex を各 TB に投入
> 3. 各 TB で iverilog 走行、UART 出力に `"N=1\nP:20"` を含むこと・HALT 到達を判定
> 4. **b ($FF 初期化) の PASS が本修正の合否判定**（他は補強証拠）

### 影響

実装フェーズでの検証作業手順が明確化。**実装ブロッカーではない**。

## 7. 指摘4（補足）: §7.3 の規約明文化提案の具体化

### 該当箇所

v1.0 §7.3：

> 本修正の安全性は「割込ハンドラが X を値保存以外に使わない」という現行前提に依存する。この前提を YUI OS 側のコーディング規約として明文化すべきかを検討（yuios_design_v2_7.md への追記候補）。

### 修正提案

「検討」で留めず、**具体的なルール文言案を §7.3 に付記**することを推奨：

> **提案ルール文言案（yuios_design_v2_7.md 追記候補）:**
>
> ```
> [規約: 割込ハンドラの X レジスタ使用制限]
>
> 割込ハンドラ内では、X レジスタを「STW で退避 → LDW で復元」以外の
> 用途に使用してはならない。理由: scc23 v2.04 以降、char 型ローカル変数の
> 読出に「ADDI X,#off → LDB A,[X] → SUBI X,#off」の3命令列を生成する。
> 中間の LDB/SUBI 実行中に割込が入り、割込ハンドラが X をフレームポインタ
> 相当に書き換えると、復帰時にユーザランド側の X が不正となる。
> 本規約に反する必要が生じた場合は scc23 修正案の再検討必須。
> ```

### 影響

将来 YUI OS 開発者が「なぜ割込ハンドラで X を触ってはいけないか」の**理由付きルール**を得る。scc23 との依存関係が明示され、YUI OS 側で規約違反する際に scc23 側との整合検討が必須と分かる。**実装ブロッカーではない**。

## 10. 良かった点（設計書としての完成度）

1. **§0.2 着手前の絶対条件**で「承認前の実装着手は厳禁」を冒頭に明示。原則43 の実践として理想的
2. **§1.3 のバグ位置提示に L2511 で `is_char` 算出済のコードを引用**し、「is_char は既に計算されているのに参照されていない」構造を視覚的に示している。1行修正で解決できる根拠が明確
3. **§1.4 の類似箇所点検表**が「用途/is_char 扱い/判定」の3列で網羅的。「バグは1箇所のみ」の主張根拠が確定
4. **§2.5 で割込ハンドラの実源を確認**し、§4.4 の判定に接続。**「危険を否定するために実源を確認する」**姿勢が原則76（実源照合）の理想
5. **§3.4 で案4（対症療法）を「保留」として棄却**し、根本治療の案3 を選択。§7.1 で案4 の将来最適化余地も残す、バランス感覚
6. **§4.4 の割込との相互作用**が「懸念→§2.5 一次確認→判定→前提条件」の4段構成で、論理的に検証されている
7. **§7 申し送りが3件**（案4 のピープホール化、フラグ更新差異、割込ハンドラ規約）で、将来課題を欠落させない意識

## 11. 本レビューでの追記

これは Step K シリーズの設計メモ v0.5 で「HANDOVER §4 準拠 θ1/θ2/θ3 + L115 KY予測反映 θ4」を維持した判断が正解だったことを示している。
