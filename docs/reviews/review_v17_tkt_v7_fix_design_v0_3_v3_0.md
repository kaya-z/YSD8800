## §2. Q-2 への回答：`beat_no` 一本化は M-3 を満たすか

### 2.1 結論

★満たしている。★ §3.5 のコードを 1 サイクルずつ追い、次を確認した。

| 検証項目 | 結果 |
|---|---|
| バースト開始サイクルで `beat_no = 0` になるか | ★可★。`burst_start` が 1 のため |
| ポートAが先頭バイトを `{idx, 0}` に書くか | ★可★。`idx_use`／`beat_no` 共用により旧値参照が消えた |
| `req_offset == 0` の捕捉（今回の顕在化パターン） | ★可★。`beat_no(0) == off_use(req_offset_r)` が開始サイクルで成立 |
| 1 ビートずれ（旧 I-2） | ★構造的に発生しない★。`beat_cnt_r <= beat_no + 1` により開始サイクルで 1 が入る |
| 2 ビート目以降 | `burst_start=0` → `beat_no = beat_cnt_r`、`off_use = req_off_ps_r`（ラッチ値）で閉じる |
| 連続ミス（本欠陥） | ★解消★。新バーストの beat 0 で `beat_no` が 0 にリセットされ、offset 0 を捕捉できる |

★`beat_no` を「現ビート番号の単一定義」とし、捕捉比較・カウンタ更新・ポートAの
3 箇所すべてで共用した点が要点である。★
これは「内部状態変数の変更箇所を集約する」という設計原則の適用そのものであり、
I-2 を「実装時の注意」から「構造による排除」へ格上げした点を評価する。

### 2.2 `off_use` / `idx_use` の三項演算子について

開始サイクルだけ生値（`req_offset_r` / `fill_index_r`）を、以降はラッチ値を使う形は
一見すると冗長に見えるが ★正しい★。ラッチは同じサイクルの終わりに入る（ノンブロッキング）ため、
開始サイクルの比較には生値を使うほかない。★`beat_no` と同じ「その瞬間の値」を与える対称な書き方★
になっており、可読性も保たれている。

### 2.3 N-1：無音の失敗経路が 1 本残る（実装時の補強提案）

現コードは ★`burst_start` が観測されなかったバーストのビートも `beat_cnt_r` の旧値で消費する。★

```
if (fill_gate_ps && beat_valid_i) begin      // ← burst_start とは独立の条件
    beat_cnt_r <= beat_no + BLEN_W'(1);
    ...
```

P-A・P-B が成立する限りこれは起きない。しかし ★成立しなくなったときの壊れ方が
今回とまったく同じ「無音のデータ破壊」である。★ 具体的には次の 2 経路。

| 経路 | 状況 | 現コードの挙動 |
|---|---|---|
| (a) | `fill_gate_ps` の立上りがバースト beat 0 に間に合わなかった場合（LATENCY 短縮・CDC 段数変更など） | `burst_start` が立たず、旧 `beat_cnt_r` から数え始める＝★今回と同型★ |
| (b) | P-B が破れ、フィル中に非フィルバーストが割り込んだ場合 | 誤った `burst_start` でカウンタとラッチが上書きされる |

**推奨（実装時）**：

1. ★`!fill_gate_ps` のときの `beat_cnt_r <= '0` を残す★（旧コードの規律を捨てない）。
   機能上は不要だが、波形の可読性が上がり、(a) の被害を「先頭からのずれ」に限定できる
2. ★`fill_armed_r` を設ける★：`burst_start` でセット、`!fill_gate_ps` でクリア。
   ビート消費条件を `fill_gate_ps && beat_valid_i && fill_armed_r` とする
3. ★`fill_gate_ps && beat_valid_i && !fill_armed_r && !burst_start` で `$error`★
   （`ifndef SYNTHESIS` 内。`psram_ctrl` L228 以降と同じ書き方）

これで (a)(b) はいずれも ★無音の誤返却ではなく即時のアサーション失敗★になる。
KY96（内部状態を扱う機能には直接照合器を用意する）を、G-M だけでなく
★RTL 内部にも適用する★という位置づけである。

★なお本項は設計の誤りの指摘ではない。★ 現設計は前提のもとで正しい。
提案の採否は実装者判断でよいが、採らない場合はその判断を設計書に残されたい。

### 2.4 C-2：前提 P-C（ラッチ時点の安定性）

`burst_start` で `req_offset_r` / `fill_index_r` を ★生のまま★ラッチする以上、
その時点で安定であることが前提になる。これは P-A/P-B とは別の前提である。

成立根拠は既存コメント（L84-89）の余裕論法と同じで、
★バースト開始は psram への req 受理から `LATENCY_NORMAL−2` 以上経過した時点★であり、
`req_offset_r` は req 発行前に cpu 側で確定している。したがって余裕は 10 psram cyc 以上ある。

**要求**：§3.4 に P-C として 1 項起こし、上記の余裕を数値で記せ。
★`LATENCY_NORMAL` を将来短縮する改造が入ったとき、真っ先に見直すべき箇所★だからである
（L386 の「⚠ LATENCY_NORMAL <= 2 では本前提が崩れる」と同じ注意が B' にも要る）。

## §3. Q-1 への回答：§2.5 と KY100

### 3.1 結論：★妥当。起票を支持する。★ ただし教訓は 2 層に分けられる

§2.5 の事実認定は実源と一致している（L373-386 の「是正」記述と L190-195 の「案3・撤去済み」が
同一ファイル内で矛盾し、L387 以降に静穏確認の実装が無い）。
「文書と実装の乖離は、欠陥そのものより長く生き残る」という KY100 の表現も的確である。

★ただし、より深い教訓がもう 1 層ある。★

段4 の結論（真因は TB 側）は ★それ自体は正しかった★。原則136 の実例として記録されており、
`bus_tasks` の deassert タイミングという真因も特定されている。
問題は結論が誤っていたことではなく、★同じ症状を生む経路が他にもあり得ることを確認しなかった★点である。

- 段4：症状 = `fill_hit_byte_r` が前回値のまま返る → 真因 TB → ★TB を直したら症状が消えた★
- ★症状が消えたことをもって、その症状を生む経路は 1 つだったと暗黙に結論した★
- 実際には ★同じ症状を生む第二の経路（連続ミス時のカウンタ未リセット）が RTL 側に残っていた★

**提案（N-2）**：KY101 として次を追加されたい。

> ★KY101★：★症状が消えたことは、その症状を生む経路が 1 つだけだったことを意味しない。★
> 真因を特定して対処した後も、★同じ症状を生む他の経路が閉じたか★を別途確認する。
> 段4 は TB 起因の真因を正しく特定し症状も消えたが、RTL 側の第二経路（連続ミス）は
> 4 日後まで残った。

KY100（書いた対策が実装されているか確認せよ）と KY101（症状消失を経路の唯一性の証拠にするな）は
★別の失敗様式★であり、分けて起票する価値がある。

### 3.2 N-3：G-M の前提（本レビューで確認済）

§4 の MISMATCH モニタが ★偽陽性を出さない★ ことを実源で確認した。記載を推奨する。

書込がポステッド（psram 完了前に ready を返す）だと、直後の読出ヒットで
「キャッシュは新値・`mem[]` は旧値」となり ★偽の MISMATCH が出る★。しかし：

| 事実 | 実源 |
|---|---|
| ★書込時の `cpu_ready_o` は `br_ready_i` 素通し★（`ccr_cen_i & cpu_rd_i` が偽のため）＝ psram の ack を待つ | `ysd8800_cache_v0_5.sv` L440-442 |
| `psram_ctrl` は `mem[mem_idx] <= wdata` と `ack <= 1'b1` を ★同一サイクル★で実行 | `ysd8800_psram_ctrl_v0_3.sv` L165-172 |

★→ ready 成立時点で `mem[]` は必ず更新済であり、書込直後の読出でも偽陽性は生じない。★
これは ★G-M をハードゲート（total=0 で FAIL）にできる根拠★であるから、§4.3 に 1 行残されたい。

### 3.3 Q-3（クローズ済）についての所見

U-A の決着内容（観測点をキャッシュ境界の物理アドレスへ）は ★妥当であり、支持する。★
特に §4.4.1 の ★観測点非依存の確認★ — 新旧の観測点で結果が完全一致することを実測した点 — は、
「モニタが観測点の実装詳細ではなく欠陥そのものを捕らえている」ことの適切な裏付けである。
★偽陰性が無かったことを確認したうえで、なお「正しかったのは偶然」として新観測点に移した判断★
（§4.2.1）は、Ph.8 を将来工程に持つ本プロジェクトとして正しい。

## §4. Q-4 への回答：T-5b の合格基準

### 4.1 結論：★妥当。支持する。★

§5.1 の理由づけ（誤った値は実行に取り込まれているのだから、是正すれば実行が変わりうる）は
論理的に正しい。★一致しないことは欠陥ではない★という明記も重要である。
「差が出たら 3 件の誤返却が実行に与えていた影響量として記録する」という扱いも適切で、
§1.2 の主張の定量的裏付けになるという位置づけに賛成する。

### 4.2 C-1：一致した場合／しなかった場合の扱いを先に決めておく

T-5b は ★どちらに転んでも「想定内」である★ 珍しい試験である。
だからこそ、★結果を見てから解釈を決めない★よう、判定表を先に用意されたい。

| T-5b の結果 | 意味 | 記録・処置 |
|---|---|---|
| M-5 が 2,010,458 と一致 | 3 件の誤返却は ★制御フローにもタイミングにも影響していなかった★ | 段6 の値をそのまま維持。G-C1 は不変 |
| M-5 が変化 | 誤返却が実行に影響していた（影響量が定量化された） | ★新値を G-C1 の基準として採用し、段6 の旧値は取り消さず併記★（§6.1 の方針どおり） |

★併せて G-1（UART バイト列 md5）の扱いを判定項目に加えよ。★
出力が変われば md5 も変わる。その場合は ★G-1 の期待値更新が必要★であり、
「G-1 不一致＝FAIL」と機械的に処理すると ★正しい修正を欠陥と誤判定する。★
T-5b の合格基準に「G-1 md5 は一致を要求せず、変化した場合は基準値を更新する（旧値併記）」
と明記されたい。★これは今回の修正に限った例外的な扱いであるから、理由も添えること。★

（`HANDOVER_CHAT153.md` §6-4 の md5 算出方法の版差問題が未決である点にも注意。
基準更新を行うなら、算出方法を固定してから行うのが望ましい。）
