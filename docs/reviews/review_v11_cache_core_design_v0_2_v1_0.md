## 1. 評価する点

### 1.1 §1（M-1 対応）は設計として完成度が高い

★**CDC が発生する箇所を 2 イベントに限定した整理**★（§1.3）が本節の白眉です。

```
  フィル要求発行  : cpu_clk → psram_clk （既存 req 経路に相乗り）
  各 beat の書込  : psram_clk 内で完結（CDC 不要）
  フィル完了通知  : psram_clk → cpu_clk （既存 ack 経路に相乗り）
  タグ／valid 更新: cpu_clk 内（フィル完了時の 1 イベントのみ）
```

★**既存の `cdc_bridge` の req/ack 経路に相乗りする**ことで、新規の CDC を一切増やさずにラインフィルを成立させている★点が優れています。①.5 で `ack_sync` の 1 サイクルに費やした議論を思えば、CDC を増やさない設計は資産です。

さらに §1.5 で ★**「valid をフィル完了時にのみ立てる」ことが DPB 競合の回避策そのものである**★ と喝破した点。競合を調停ロジックで解くのではなく、**競合が起きても結果が使われない構造**にして消しています。これは①.5 の A-2q（`suppress_r` 単一 FF でグリッチ源を構造的に消した）と同じ筋の良さです。

### 1.2 M-6 への対応が「撤回」で終わっていない

誤った基準を消すだけでなく、★**「ビン構造が示すのは『LAT の微調整では性能が動かない＝レイテンシを削る方向は打ち止め』ということのみ。だからこそ②-B に意味がある、という動機づけとして用いる」**★ と用途を再定義されました。★測定結果の解釈を捨てずに、適用範囲だけを正した★のは良い処理です。

### 1.3 KY-B10 の起票

★「実源を見ずに ISA から構造を推論する」★を KY として残された点。M-3 は当方が指摘した個別の誤りですが、それを**再発防止の型**に一般化したのは KY 活動の正しい使い方です。

## 3. C：確認事項

### C-5 `mem_ready` が `mem_addr` に組合せ依存する構成は本設計が初（CPU L197-198 の閉路履歴）

§7.1 の `assign mem_ready = (CEN & hit) ? 1'b1 : bridge_ready;` により、★`state → mem_addr → mmu → index → tag_ram/valid_r → hit → mem_ready` という**新しい組合せ経路**★が生まれます。

CPU コア **L197-198** には次の履歴があります。

> 当初 `mem_addr` を `stack_ctx` 依存の三項で選択したが、`mem_addr → mem_ready → state → stack_ctx` の閉路で Icarus が byte TB でハング

当方の解析では、★`mem_ready → next_state → (posedge) → state → mem_addr` の経路には **`state` レジスタが挟まる**ため組合せループは閉じません★。また現行 L853-861 の `always_comb` は `state` とレジスタファイルのみに依存し `mem_ready` には依存しないため、安全と判断します。

ただし ★①.5 の A-2q でも同種の議論に相当の工数を要した★経緯があるため、**段 2 の最初のシミュレーションで「Icarus がハングしないこと」を明示的な確認項目**に入れておかれることを推奨します。ハングは他の不具合と症状が全く異なるため、想定していれば切り分けが一瞬で済みます。

### C-6 §7.5 の「フィルは cpu_clk 約 4 サイクル」は過小

§7.5 は「フィルは psram_clk 32 サイクル ＝ cpu_clk 約 4 サイクル」としますが、②-A 設計書 §3.3 の検算どおり ★**バースト所要は `LAT + 31 = 43` psram cyc**★（初回ビートまでに `LATENCY_NORMAL=12` を要する）です。cpu_clk 換算で ★**約 5.4 サイクル**★、CDC 往復を加えると約 8〜9 サイクルになります。

「待たせても軽微」という結論は変わりませんが、★この値は §6.1 の損益分岐計算で使う「キャッシュミス 10 cyc」の内訳そのもの★なので、整合させておく価値があります。

### C-7 DPB の read-during-write を「無害」と明記されたい

§6.3 の投機読出は ★フィル進行中も毎サイクル `data_ram` を読み続けます★。したがって §1.5 が想定する「同一アドレス同時アクセス」は**回避されるのではなく常時発生**します。

結論（無害）は正しいです。Gowin の DPB は read-during-write 時の読出データが不定になりますが、★`valid_r[index]=0` によりヒットが成立せず結果が捨てられる★ためです。ただし §1.5 の現記述は「**発生させない**」と読めるため、★「発生するが、結果が使われないため無害」★と正確に書き改められたい。`tb_cache_cdc_poc` の検証意図もそちらです。

## 4. N：推奨事項

### N-4 D-B2（ラインサイズ）は M-8 の結論が出るまで暫定とする

§11.1 は D-B2 を「✅ 確定」としていますが、その理由が ★「M-2 解決の結果ヒットは 1 cyc であり、16 B へ転じる必要はない」★ である以上、M-8 により**根拠が保留**になります。

- ヒット 1 cyc（フェッチのみでも可）→ 32 B 維持が妥当
- ヒット 2 cyc 確定 → 損益分岐 `h > 75%` となり、★ミスペナルティが約半分になる 16 B の再評価が必要★

★D-B1（8 KB）・D-B3（ダイレクトマップ）・D-B4・D-B5・D-B6 は M-8 の影響を受けないため、確定のままで問題ありません。★ D-B2 のみ「暫定確定（M-8 の結果で再確認）」と状態を変えられたい。なお 16 B へ変更する場合も、②-A の `burst_len` はキャッシュ側が駆動する値なので ★`BURST_MAX=32` のまま `burst_len=16` を発行すればよく、②-A 側の RTL 変更は不要★です（M-10 の対応をしていれば自然に吸収されます）。
