## 総評

バグの分析・案の比較・安全性解析いずれも質が高い。特に評価できる点:

- **穴の機序を実源で正確に特定**：`binop_promote` の `lf=0 && rf=0`（両辺とも未定義 call → 両方 T_INT フォールバック）で int 経路へ抜け、案D の判定に到達しない——という2行の条件式レベルまで落とし込んでいる。
- **実測で実証**：`m1_f_div_c_n.c` で `_cc_div` 生成・`errors=0` 通過を確認し、さらに probe で **return 文・関数引数でも同じ穴**が開くことを実証（§1.3）。これにより案E（`parse_assign` 限定）を根拠をもって却下できている。
- **演算別の実害分析が的確**：加減算は Q8.8 と int でビット演算として同一ゆえ実害が顕在化せず、乗除算のみ確実に壊れる、という切り分けは正しい。
- **案G の網羅性が原理的**：未定義 call を入口（`parse_primary`）で止めるため、float 文脈の種類・複合式の深さ・両辺の組合せを問わず閉塞する。fail-safe として筋が良い。
- **後方互換を実測で裏付け**：既存 C ソース全6本で undeclared warning **0 件**を確認しており、案G 適用の実害ゼロが数字で示されている。

私自身、v2.05 レビュー時の CONF-1 で「ボトムアップ評価により複合式でも漏れない」と確認したが、**「両辺とも未定義 call」の場合に float 経路自体へ入らない**という前提の抜けを見落としていた。本設計書 §7.4/§7.5 がその訂正と教訓を記録している点も適切である。

以下、実装前に反映すべき点。

---

## M-1【必須】案G は「後方定義関数をプロトタイプなしで呼ぶ」書き方を全面禁止する。影響範囲として明記すべき

**箇所**: §2.4 案G の詳細、§3.1 既存 C ソースへの影響、§2.5 妥当性根拠4

**問題**: §3.1 は「プロジェクト内の全 C ソースで undeclared warning が 0 件 → 影響ゼロ」と結論しているが、これは**現存ソースがたまたま全てプロトタイプ完備（または定義順が適切）だった**ことの確認であり、**案G が持ち込む仕様変更の範囲そのものの説明にはなっていない**。

実源で確認した事実（`scc23_v2_05.c`）:
- 関数シンボルに `sclass=SC_FUNC` が立つのは **`parse_global` で関数定義（またはプロトタイプ宣言）に到達した時点**（`fs->sclass=SC_FUNC; fs->defined=1;`）。
- したがって、**ファイル後方で定義された関数を、プロトタイプなしで前方から呼ぶ**と `sym_find` は SC_FUNC を返さず、案G により **error** となる。
- 組込関数（`putchar/getchar/puts/printf/sprintf/strcpy/strcmp/memcpy/strlen`）は `compile` 冒頭で `sclass=SC_FUNC` 登録済みのため **error にならない**（安全・確認済）。

つまり案G は「未定義関数」だけでなく、実質的に **「使用前にプロトタイプまたは定義が必要」という前方宣言必須化**である。C89 で許容されていた「暗黙 int 宣言に頼って後方定義関数を先に呼ぶ」書き方は**全てコンパイルエラーになる**。これは §2.5 根拠4（C99 で implicit function declaration 禁止）の通り現代 C として正当だが、**仕様変更の影響範囲としてユーザに明示されるべき**である。

**対応案**:
1. §3.1 のタイトル/結論を「**既存ソースへの影響（実測ゼロ）**」から一歩進め、「**案G は前方宣言必須化（C99 準拠）であり、後方定義関数のプロトタイプなし呼び出しは新たに error となる。現存ソースは全てこの条件を満たすため実害ゼロ**」と、**仕様変更の内容**と**実測結果**を分けて記述する。
2. §7.1（K&R スタイルサポート）に、この前方宣言必須化が**今後 C ソースを新規に書く際の制約**になる旨を追記（新規テストコード・ユーザランド C を書くとき、関数は使用前に宣言する必要がある）。
3. エラーメッセージは既に「add a prototype declaration before use」と適切。§2.4 の実装コード案はこのままでよい。

> 本指摘は案G の却下を求めるものではない。案G は網羅性・最小改変・fail-safe の点で妥当な選択である。ただし「影響ゼロ」という表現は**現存ソースについては真だが、仕様としては変更が入っている**ため、その区別を設計書に明記すべきという趣旨である。

## N-1【推奨】案D 残置による error 二重出力の扱いを検証項目に含める

**箇所**: §2.4「案D の扱い」、§4 検証計画

**内容**: §2.4 は案D を多重防御として残置し、「1つの未定義 call に対し最大2件の error が出る可能性があるが許容」としている。判断自体は妥当（どちらも同じ対処法を示すため）。ただし:

- 案G により `parse_primary` で error が出た後も **`cn->type = T_INT` を入れて解析継続**するため、その call ノードが float 文脈に入れば案D も発火し得る。
- C-1 マトリクステストの `expect_error_contains` は複数指定＝AND 条件（C-1 設計メモ §2.4）なので、**どちらのメッセージが出るかでテストの期待値が変わる**。

**対応案**: §4 の検証項目に「未定義 call を float 文脈で使ったケースで、error が案G 由来（`add a prototype declaration before use`）・案D 由来（`used in float context`）のどちらが、何件出るかを実測し、C-1 の `expect_error_contains` に反映する」を追加。C-1 期待値の確定に必要。

## N-2【推奨】§3.4 の C-1 期待値改訂で `warning_only` が 0 件になる点の波及

**箇所**: §3.4

**内容**: 案G により C-1 の期待値分類 `warning_only` が **6 件 → 0 件**になる。これは C-1 設計メモ §2.2 の3分類のうち一つが**実質使われなくなる**ことを意味する。

**対応案**: C-1 設計メモ改訂時に、`warning_only` 分類を(a)削除するか、(b)将来 warning のみのケースが生じ得る枠として残すかを明示。残す場合は「v2.06 時点では該当ケース 0 件」と注記。判定ロジック（`run_c1_matrix.sh`）が空分類を扱えるかも確認。

## E-1【軽微・良い判断】golden 未凍結のタイミングは幸運

**箇所**: §3.4「golden 基準版」

**確認**: 「C-1 はまだ golden を凍結していない（本件で中断）ため、握り潰しのリスクなく更新できる（不幸中の幸い）」という記述は正しい。私が C-1 v0.2 レビューで OBS-2 として「golden 更新ルールを golden 作成前に確定させよ」と指摘した通り、**golden 凍結前に仕様変更が入った**のは結果的に最良のタイミングだった。golden 基準版を v2.06 へ更新する判断で問題ない。

1. **M-1**（案G が前方宣言必須化という仕様変更である点を §3.1/§7.1 に明記。「実害ゼロ」と「仕様変更あり」を分けて記述）
2. **N-1**（案G/案D の error 二重出力の実測を検証項目に追加し C-1 期待値へ反映）
3. **N-2 / E-1**（`warning_only` 分類の扱い明示／golden 基準版 v2.06 更新は妥当）

M-1 を反映すれば本設計メモは承認に値する。案G（未定義 call の error 化）は、網羅性が原理的に完全・実装が最小（`warning`→`error` の1行）・後方互換の実害ゼロ（実測）・C99 準拠・fail-safe の5点で妥当な選択である。

## 補足: レビュア側の反省（KY34・CONF-1 の見落とし）

v2.05 レビュー（`scc23_v2_05_C3_forward_decl_design_v0_2_review_closure_v1_0.md` §3.1 CONF-1）で、私は「ボトムアップ評価により未定義 call が float 演算に最初に触れる `binop_promote` で必ず捕捉され、複合式でも漏れない」と確認した。しかし**「両辺とも未定義 call の場合、そもそも float 経路に入らない（`lf=0 && rf=0` で int 経路へ return）」**という分岐を追い切れておらず、穴を見逃した。

教訓: 「捕捉される経路」を確認する際は、**その経路に到達しないケース**（早期 return・別分岐）を同時に洗う必要がある。本件は C-1 マトリクステスト整備が実測で検出したものであり、**テストによるセーフティネットが設計レビューの見落としを補足した実例**として、§7.5 の kaizen 候補に加える価値がある。
