## 1. 総評

Pre-3 実測で「+8B・56,424B」予測が構造的に誤りであったことを発見し、**AC-1 を「サイズ判定」から「バイトパターン検索」へ根本改訂**した本 v1.2 は、以下の点で模範的：

- **判定基準の構造的欠陥**（`.org` パディング吸収を見落としたサイズ判定）を実測で発見し、隠さず §1.1 経緯表に「予測が構造的に誤り」と明記
- **AC-1 改訂の根拠**を実源（`.org` 指定の並び・`.org $0030` と `.org $01C0` 間の 400B 余裕）で構造的に説明（§2.2 L106-114）
- **新 AC-1（バイトパターン `21102300230190fc`）の弁別性を Pre-3 で実証済**（v12.7=0 hit / v12.8=1 hit）
- **§9 教訓 3件と判定基準立案チェックリスト 5項目**を設計書内に組み込み、kaizen 提案候補として明示化
- **候補原則 A（v1.0 継承）＋ 候補原則 B（v1.2 新設）**の 2 本立てで、原則追加を系統的に整理
- **R-6/R-7 新設**：`xxd` 不在時の代替手段と偽陽性の低確率を明示的に扱う
- **AC-3 補記**：新旧リファレンスがサイズ同一（56,416B）でも内容が異なるため**ハッシュ値記録必須**とした注意深さ

**技術的根拠すべて実源で検算確認済**（§2 実源照合サマリ参照）。特に TCR-ACK 8B バイトパターン `21 10 23 00 23 01 90 fc` は hasm23_v1_04.c の LDW/STW opcode 割当・reg byte 符号化・imm16 little-endian 順から機械的に導出でき、設計書の主張と**完全一致**。

**TCR-ACK バイトパターン `21 10 23 00 23 01 90 fc` の機械的導出検算**：

- `LDW B, #$TCR_ACK_REARM`（= `LDW B, #$0023`）
  - opcode = 0x21（LDW #imm、hasm23 L1078）
  - reg byte = `(rD<<4) | rS` = `(1<<4) | 0` = `0x10`（B=1、rS=0）
  - imm16 LE = `$23, $00`
  - → **`21 10 23 00`** ✓
- `STW B, [TCR]`（= `STW B, [$FC90]`）
  - opcode = 0x23（STW [abs]、hasm23 L1114）
  - reg byte = `(rD<<4) | rS` = `(0<<4) | 1` = `0x01`（rD=0、rS=B=1）
  - imm16 LE = `$90, $FC`
  - → **`23 01 90 fc`** ✓
- 合計 8B: **`21 10 23 00 23 01 90 fc`** ← 設計書 §2.3 の主張と**完全一致**

**結論**: 技術的根拠すべて実源で検算確認済。v1.2 の AC-1 改訂は完全に妥当。

## 4. 指摘1（補足）: R-7 の理論的根拠の精度

### 4.1 該当箇所

v1.2 §6 R-7（原文引用）:

> **R-7（新設・v1.2）**: TCR-ACK パターン `21102300230190fc` が偶然の一致（別命令列でも同じ 8B）で誤検出 | AC-1 が偽陽性を返す | v12.7 版で 0 hit を Pre-3 で実測確認済。8B の連続一致は約 $2^{-64}$（極めて低確率）。yuios.bin サイズ 56,416B ≪ $2^{16}$ の探索空間で偶然一致する確率は事実上ゼロ。

### 4.2 懸念

- 「8B 連続一致 = $2^{-64}$」は**バイトが独立ランダム分布**の場合の確率
- 実際のバイナリは命令コードなので、opcode バイト（0x21, 0x23）は他の LDW/STW 命令でも同じ値を取る
  - opcode=0x21 は `LDW rD, #imm` 全般で出現
  - opcode=0x23 は `STW rD, [abs]` 全般で出現
- したがって「たまたま 0x21」の確率は 1/256 より高い可能性
- yuios は kernel + forth + OS で LDW/STW を頻繁に使うため、opcode バイトの出現頻度は特に高い

### 4.3 実務結論としては問題なし

ただし、**「v12.7 で実測 0 hit」という実測結果**が最強の根拠であり、以下 2 点で偽陽性はほぼ排除される：

1. **imm16 部分の一意性**: `$0023` (LDW imm) と `$FC90` (STW abs) の組合せは、kernel v12.7 の別の命令列で偶然一致する可能性が低い（$FC90 は TCR MMIO の固定アドレスで、これを LDW/STW 対で扱う命令はほぼ TCR-ACK 用途に限定される）
2. **8B 連続一致の実測 0 hit**: v12.7 全体 56,416B での実測結果

したがって v1.2 §6 R-7 の**結論は正しい**。ただし理論的な根拠付け（$2^{-64}$）はやや杜撰で、レビュー時に「本当に独立ランダムか？」と反論される余地がある。

### 4.4 修正提案（v1.3）

v1.3 で R-7 を以下のように書き直し推奨：

> **R-7**: TCR-ACK パターン `21102300230190fc` が偶然の一致（別命令列でも同じ 8B）で誤検出 | AC-1 が偽陽性を返す | **主根拠：v12.7 版で 0 hit を Pre-3 で実測確認済**（実バイナリ全 56,416B に対する走査で偶然一致なし）。**副根拠：imm16 部分 `$0023` (LDW immediate) と `$FC90` (TCR MMIO アドレス) の対応関係が TCR-ACK 用途にほぼ限定される**（他の kernel コードでは $FC90 を LDW/STW 対で扱う経路が稀）。理論的な独立ランダム確率 $2^{-64}$ は目安として参考扱い（命令コードのバイト分布は独立ランダムではないため）。

### 4.5 影響

**実装ブロックにはならない**。R-7 の結論は正しく、Pre-3 の合格判定は既に PASS 済。理論的根拠の精度向上は文書としての完成度を上げる補足。

## 5. 指摘2（補足）: R-3 の解消理由の精度

### 5.1 該当箇所

v1.2 §6 R-3（原文引用）:

> R-3: 新 yuios サイズがメモリマップに収まらない | Pre-3 完了不能 | **✅ Pre-3 で解消**（サイズ不変が構造的必然と判明）。

### 5.2 懸念

「サイズ不変が構造的必然」だけを解消理由にすると、**もっと大きな変更（例：+500B）だった場合の判定**を暗黙に含んでしまう。実際には：

- v12.8 の +8B は `.org $0030` から `.org $01C0` の 400B 枠内で吸収された
- もし追加サイズが 400B を超えていたら、hasm23_v1_04.c L915-917 の `.org backward` エラーで**ビルド失敗**していた
- **サイズ不変が構造的必然になるのは、追加サイズが枠内に収まる場合のみ**

### 5.3 hasm23 実源での確認

**hasm23_v1_04.c L915-917**（原文引用）:

```c
if (new_pc < pc) {
    fprintf(stderr, "hasm23: -c mode: .org $%04X < current pc $%04X (backward .org not supported)\n", new_pc, pc);
    return 1;
}
```

`.org $01C0` に到達したときに `pc > $01C0` なら**ビルド失敗**。v12.8 の +8B 追加は幸い 400B 枠内に収まったため、この条件に触れず解消できた。

### 5.4 修正提案（v1.3）

v1.3 で R-3 に一言追記推奨：

> R-3: 新 yuios サイズがメモリマップに収まらない | Pre-3 完了不能 | **✅ Pre-3 で解消**（$0030-$01C0 の 400B 枠に +8B が収まったため `.org` パディングで吸収され、サイズ不変となった。もし追加サイズが枠を超えていたら hasm23 L915 で `.org backward` エラーで検知される安全機構あり）。

### 5.5 影響

**実装ブロックにはならない**。R-3 の結論は正しく、実測結果とも整合。より本質的な理由の一言追記は文書としての完成度向上の補足。

## 7. 特に評価すべき点

### 7.1 「予測が構造的に誤り」を隠さず明記した誠実さ

v1.2 §1.1 経緯表 L52（原文）:

> **CHAT124 2026-07-29 Pre-3 実測時** | **AC-1 予測（+8B → 56,424B）が構造的に誤り**であったことが実測で判明。真因は `.org` パディング吸収。

これは「レビューを通ってしまった予測が実測で覆された」という事実を隠さず記録している。**設計負債の「直す前に記録」姿勢を、レビュー承認済の予測にも適用**しており、原則77 の理想的な運用形態。

### 7.2 候補原則 A + B の 2 本立て整理

v1.0/v1.1 での候補原則 A（実装契機の変更時の Makefile 追随タグ）に加え、v1.2 で候補原則 B（バイト数予測はメモリマップ制約まで含めた実測ベース）を追加。**同じ根っこの問題（追随漏れ・予測甘さ）を系統的に整理**しており、kaizen.txt への追加提案として非常に価値大。

### 7.3 §9 教訓 3件 + 判定基準立案チェックリスト 5項目

v1.2 §9 で以下を明示化：

- 教訓1: 原則76 の適用範囲拡張（メモリマップ制約まで含めた実源照合）
- 教訓2: 原則87 の判定基準構造の妥当性チェック
- 教訓3: 設計予測の実源事前検証
- チェックリスト 5項目（変化条件・変化しない場合・弁別性・実測可能性・偶然一致排除）

これは「本件だけの教訓」に留まらず、**今後の全ての設計書レビューで使えるチェックリスト**として一般化されている。原則43 の理想的な運用の一環。

### 7.4 R-6/R-7 の先読み

`xxd` 不在への代替手段（`od -An -tx1 -v | tr -d ' \n' | grep -oE`）を Pre-3 実測時に確立し、R-6 として文書化。バイトパターン判定の運用性を担保した。

新旧リファレンスが**サイズ同一（56,416B）で内容が異なる**という現実に気づき、AC-3 で「ハッシュ値の記録は必須」と補記。バイト単位で異なるものを識別するのはハッシュしかない、という当然の帰結を明文化した。

### 7.6 R-1/R-3/R-5 の完了マーキング

Pre 工程で解消済のリスクを「**✅ Pre-N で解消**」と明示的にマーキング。**現存リスクとクローズ済リスクを一覧で区別できる**運用は、リスク管理として理想的。

## 8. 本レビューでの追記

**教訓（レビュー承認済の予測にも実測時の見直しを許容する運用）**: 本 v1.2 は「v1.0 で `+8B` 予測を含む記述はレビューで承認された」「v1.1 で +8B 予測を明示的に精緻化した」ものが、Pre-3 実測で覆された事例。**レビュー承認 = 実測不要ではない**ことを示している。

v1.2 §9 教訓3「設計予測の実源事前検証」で「Pre-2 で暫定ビルドで実測確認する」ことを推奨しているが、より一般化すると「**予測を判定基準に組み込む場合、その予測が実測前提であるか予測前提であるかを明示する**」ことが望ましい。今後の設計書では、判定基準に含まれる数値や条件について「実測確定」「予測（実測未実施）」を明示するタグ運用を推奨。
