## 4. 指摘1（軽微修正）: Ch_Loc の型に関する事実誤認

### 該当箇所

v0.5 §3.2 case `16'h2610` 内コメント（L129-131）：

```
        // ★v0.5 新規: Ch_Loc実値をエピソード開始マーカに含める
        //   $2610 = LDW A, [X + #$FFFA] は Ch_Loc の読み出し。
        //   Ch_Loc は [X-6] (下位バイト) + [X-5] (上位バイト) に格納。
        //   Ch_Loc値の変動を観測することで、Ch_Loc==$248D 相当値の周回を捕捉。
```

### 実源事実

- **dhry_timer.c L1035**: `Capital_Letter Ch_Loc;` — `Capital_Letter` は typedef char で **1バイト変数**
- **HANDOVER_CHAT116.md L40**: `Ch_Loc = 'A' の代入 → L3055: STB B, [X] (1バイト書き)` — STB は Store Byte、1バイト書きが実源で確認済
- **HANDOVER_CHAT116.md L42-43**: 「STB で1バイトしか書かないため、**上位バイトは Func_2 入口時のスタック残骸（前フレームのゴミ 0xF7）**がそのまま」

つまり Ch_Loc は 1バイト値であり、**[X-6] が Ch_Loc 実値、[X-5] は Ch_Loc とは無関係の隣接メモリ**（前フレームゴミ 0xF7）。

$2610 の LDW A,[X+#$FFFA] が 2バイト読みするのは、**発見2で説明された「scc23 が char 変数の参照時に LDW（2バイト読み）を発行する型不整合の結果」**であって、Ch_Loc 自体が 2バイトなのではない。

### 修正提案

コメントを以下に修正：

```
        // ★v0.5 新規: Ch_Loc実値をエピソード開始マーカに含める
        //   Ch_Loc は char型 1バイト変数（dhry_timer.c L1035）で [X-6] に格納。
        //   $2610 = LDW A, [X + #$FFFA] は char を LDW (2バイト読み) するため、
        //   A 上位バイトに [X-5] の隣接メモリ残骸（HANDOVER L42-43 参照）が乗る。
        //   [X-6] の Ch_Loc実値変動と [X-5] のゴミ値パターンを観測し、
        //   $248D 遷移との相関を捕捉する。
```

### 影響

**実装コードそのものには影響しない**（$display 引数の順序は正しい）。しかし後日この設計メモを読む人（特に θ3 scc23 コード生成バグを追う担当）が「Ch_Loc は 2バイト」と誤認すると、scc23 側の修正方針を誤る危険がある。

## 5. 指摘2（軽微修正）: $display 書式文字列の可読性

### 該当箇所

v0.5 §3.2 L132：

```systemverilog
$display("★[STEPK ep=%0d cyc=%0d] $2610 (L_0140) 到達 - PC遷移生ダンプ開始  Ch_Loc [X-6=%04h][X-5]=%02h %02h",
         k_episode, to_cyc,
         dbg_x - 16'd6,
         u_membus.u_psram_ctrl.mem[dbg_x - 16'd6],
         u_membus.u_psram_ctrl.mem[dbg_x - 16'd5]);
```

### 懸念

書式文字列を展開すると：

```
Ch_Loc [X-6=FC8A][X-5]=59 F7
```

`[X-5]=` の直後に **2つのバイト値** `59 F7` が並ぶが、これは実際には「[X-6] の値=59、[X-5] の値=F7」を意味する。**書式ラベル位置と値の対応が視覚的に一致せず、読み手が「[X-5]=59F7 という2バイト値」と誤読する可能性**がある。

### 修正提案

```systemverilog
$display("★[STEPK ep=%0d cyc=%0d] $2610 (L_0140) 到達 - PC遷移生ダンプ開始  Ch_Loc addr=%04h [X-6]=%02h [X-5]=%02h",
         k_episode, to_cyc,
         dbg_x - 16'd6,
         u_membus.u_psram_ctrl.mem[dbg_x - 16'd6],
         u_membus.u_psram_ctrl.mem[dbg_x - 16'd5]);
```

展開結果：

```
Ch_Loc addr=FC8A [X-6]=59 [X-5]=F7
```

各ラベルと値が1対1で並ぶ。`addr=` の追加で「アドレス指定は $FC8A」も明示される。

指摘1と指摘2はセットで対応推奨。

## 6. 指摘3（補足）: 50000行安全弁の見積り妥当性と失敗時の次手

### 現状

v0.5 §3.4-2：

> 累計 50000 行到達 → `$finish`（安全弁・上限見込み: 3557回×20cyc=71,140行、50000行で ep≈2500 相当）

### 分析

- Step I 集計「$2610到達 3557回」に対し、50000/20 = 2500 ep をカバー
- サンプル率 = 2500/3557 ≈ **70.2%**
- $248D 異常遷移エピソードが Dhrystone 走行中に 3557回中 X回 発生すると仮定：
  - X=100（3%）なら 70% サンプルで検出確率 ≈ 1 - 0.3^100 ≒ 1.0（ほぼ確実）
  - X=10（0.3%）なら 検出確率 ≈ 1 - 0.3^10 ≒ 1.0（ほぼ確実）
  - **X=1（1回のみ発生）なら 検出確率 = 70%**（30%取りこぼしリスク）

Step I の情報から $248D 到達が「Func_2 が Func_2 入口に戻る」現象で 1回しか観測されていない可能性は否定できない（HANDOVER L26 は `JSR _Func_2 ($08E8) 通過=1回のみ`、L27 は `Func_2 RET ($27B8) 直前=0回到達`。異常遷移の頻度は Step I まででは不明）。

### 修正提案（軽微）

§7 事前予測に「累計 50000行到達も $248D 未到達」の場合の具体的次手を1文で補強：

> 累計50000行到達も $248D 未到達 → 「サンプル不足」→ Ch_Loc の値変化パターンをログから解析、$248D 発生条件を推定。**次工程では観測窓 20cyc を維持したまま累計上限を 100000〜200000 に段階的に緩和 or, Ch_Loc の値がなんらかの特定パターンになった時のみ ep をフル観測する条件付きサンプリングに切り替え**

50000 で始めて足りなければ次段で緩和する、という段階的アプローチは原則57（仮説絞込）の実践として妥当。
