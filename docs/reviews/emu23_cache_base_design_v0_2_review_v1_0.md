## 0. 総評

**前回 M 4件・C 4件はすべて消化されている。** 対応の質は高く、特に次を強く評価する。

- **M-1 への対応が、指摘の範囲を超えて価値を生んでいる。** レビューは「ライン充填コストを計上せよ」「`LAT_FILL < LAT` が通例だから別パラメータにせよ」と述べたが、v0.2 は `ysd8800_psram_ctrl_v0_2.sv` を実源調査し、**現行 RTL はバースト非対応ゆえ `LAT_FILL = LAT` である**と突き止めた。そのうえで §3.5 に「32B ラインの充填コストは約 152 CPU cyc に達し、**キャッシュの利得を食い潰す可能性がある**」「**キャッシュ RTL より先に PSRAM バースト対応を検討すべきという結論すらあり得る**」と記した。**レビューの前提（バースト償却がある）が現行 RTL には当てはまらないと指摘し返している**わけで、これは指示に従っただけでは到達しない。工程②の優先順位を左右しうる発見である。

## 2. M 指摘（必須是正：2件・新規）

### M-5 【§9】★校正手順の**大前提が未検証**である。この 1 件で LAT の確定値が丸ごと狂う

§9 の手順 2-3 は次のとおりである。

> 手順 2：RTL 実測との差分 **965,640 cycles**（＝1,317,401 − 351,761）を分子とする
> 手順 3：`LAT − 1 = 965,640 ÷ B` から LAT を逆算する

**この引き算が「メモリ待ちの実費」を与えるためには、次の前提が成り立たねばならない。**

> **RTL を理想メモリ（`mem_ready` 常時 1）で走らせたときのサイクル数が、emu23 `-mc` の 351,761 と一致する。**

**この前提は本設計書のどこにも検証されていない。** §3.1.1 が示すのは「サイクル表 v1.0 は v0.5.8 に対しても有効（CPI 差分なし）」までであり、これは**個々の命令の CPI が表と一致する**という話にすぎない。Dhrystone 全体（48,785 命令）の総サイクル数が一致することの証明ではない。両者がずれる要因は少なくとも次がある。

| 要因 | 内容 |
|---|---|
| 割込受理コスト | emu23 は実加算 8（`emu23_mc_design` §3.1.1）。RTL 実測との一致は未確認 |
| MMIO アクセスのサイクル | emu23 は MMIO を非課金とするが、RTL では `mmio_stub` 経由で固有のサイクルを要する |
| リセットシーケンス | emu23 は非計上（`emu23_mc_design` §3.4）。RTL は 2 サイクル |
| 表に無い命令 | emu23 は既定 4 で代替。RTL の実際の値と一致する保証はない |

**もし RTL 理想メモリ実測が例えば 360,000 だったなら、真のメモリ待ちは 957,401 であり、分子が約 1% 狂う。** 逆に 340,000 なら分子は 977,401 になる。**LAT はこの分子を B で割って求めるのだから、分子の誤差はそのまま LAT の誤差になる。** そして LAT は改良4 の全成果物（トレース解析・ラインサイズ評価・工程②の判断材料）の基礎である。

**是正要求**：§9 に**手順 0** を新設されたい。

> **手順 0（KY54・校正の前に必ず実施）**
> RTL を**理想メモリ構成**（`mem_ready` 常時 1、PSRAM/CDC をバイパス）で Dhrystone を走らせ、
> 総サイクル数が emu23 `-mc` の **351,761 と一致する**ことを確認する。
> **不一致の場合、その差分の原因を先に特定すること。**
> 差分を残したまま `965,640` を分子として用いてはならない。

これは §9 手順 5 が既に述べている「机上推定 4.75 と実測値の乖離が大きい場合はモデルの誤りを疑う（KY54 の精神）」の**前段**にあたる。乖離を評価する前に、**引き算の両辺が同じものを測っているか**を確かめる必要がある。

> **なぜ M か**：本件は「実装の欠陥」ではなく「測定計画の欠陥」である。段1〜段8 の実装作業は本件と無関係に進められるため、**実装着手を止める必要はない**。ただし §9 の校正を実行する前には必ず消化されたい。未消化のまま校正すると、誤った LAT が §11-1（`cache_study_handover` v1.1 改版）を駆動し、**v0.1 で犯した「未確定値が他文書の改版を駆動する」誤りを、値を変えて繰り返す**ことになる。

### M-6 【§8.1 T-05】M-1 是正の**検証項目が定性的**であり、PASS/FAIL を判定できない

§8.1 の各テストは手計算で検算できる期待値を持つが、**T-05 だけが定性的**である。

| ID | 期待値 | 判定可否 |
|---|---|---|
| T-01 | `(-mc のみ) + N × ((32 × LAT_FILL) − 1)` | ✅ 数式 |
| T-02 | 追加課金 0 | ✅ 数式 |
| T-03 | 読み 0／書き `2 × (LAT_WR − 1)` | ✅ 数式 |
| T-04 | 追加課金 0 | ✅ 数式 |
| **T-05** | **「ヒット率上昇による削減と充填コスト増が両方動くこと」** | ❌ **定性的** |
| T-06 | `N × (LAT_WR − 1)` | ✅ 数式 |

§8.1 の見出しは「**手計算検算テスト**」であり、T-05 はその要件を満たしていない。「両方動く」だけでは、動いた量が正しいかを検証できない。

**T-05 は M-1 の是正（ラインサイズを評価できるモデルであること）を確認する唯一の項目**である。ここが定性的なままでは、**M-1 が本当に是正されたかを検証する手段が存在しない**ことになる。

**是正要求**：T-05 に手計算可能な期待値を与えられたい。設計例を示す。

> **T-05 設計案**：ライン内に収まる連続読み `L` バイトを 1 単位とし、これを M 単位分、
> 互いに異なるラインにまたがるよう配置して読む。ライン長 `S` のとき：
>
> ```
> ミス回数   = (アクセス総バイト数) ÷ S        （ライン先頭で 1 回ずつミス）
> 追加課金   = ミス回数 × ((S × LAT_FILL) − 1)
> ```
>
> ライン 32B と 64B で実行し、**ミス回数が半減し、1 ミスあたり充填コストが倍増する**ことを
> 上式で予測した値と実測が**一致すること**を確認する。
>
> 現行 RTL（`LAT_FILL = LAT`、バースト非対応）では両者が相殺し **総課金がほぼ不変**になるはずであり、
> **この「相殺する」という予測自体が §3.5 の主張（バースト非対応ではライン拡大に利得が無い）の直接証明になる。**

上記のように組めば、T-05 は単なる回帰テストではなく **§3.5 の重要な結論を実証する項目**になる。§3.5 が工程②の優先順位を左右する主張をしている以上、その裏付けは定量的であるべきである。

## 3. C 指摘（確認・明記要求：5件）

### C-5 【§3.1.3】ack 同期段数が **2 段ではなく 3 段の可能性**がある

`ysd8800_cdc_bridge_v0_2.sv` L89-90 の実体は次のとおりである。

```systemverilog
ack_sync   <= {ack_sync[0], psram_ack};
ack_sync_d <= ack_sync[1];
```

**2FF 同期器（`ack_sync`）の後段に、さらに `ack_sync_d` という 1 段がある。** これは立ち上がりエッジ検出（`ack_sync[1] & ~ack_sync_d`）のための遅延段と読める。そのうえで `cpu_mem_ready` は `always_ff` 内で駆動されるため、**エッジ検出成立からさらに 1 サイクル**を要する。

素直に数えると `psram_ack` 立ち上がりから `cpu_mem_ready` 到達まで **3 CPU サイクル**であり、§3.1.3 の表が置く **2.00** より 1 大きい。そうであれば机上推定は **4.75 → 5.75 CPU cyc/byte** となり、§3.1.3 の内訳比率（PSRAM 側 37% / CDC 側 63%）も **30% / 70%** に変わる。§3.5 の充填コスト試算（32B で約 152 cyc）も約 184 cyc になる。

**要求**：`cpu_mem_ready` 生成経路を段数まで追い、内訳表を確定されたい。ただし §3.1.3 が「**机上推定であり設計判断の根拠に用いてはならない**」と自ら限定しているため、精度の問題として C に留める。M-5 の手順 0 を実施すれば実測で決着する事項でもある。

> 参考：§3.1.3 の結論（**支配項は CDC 同期であり psram_clk 昇圧の効果は限定的**）は、CDC 側が 3.00 でも 4.00 でも**変わらない**——むしろ CDC 側が大きいほど結論は強まる。したがって C-1 への回答の**向きは正しい**。数値の精度だけの問題である。

### C-6 【§3.1.3】`LATENCY_NORMAL = 12` を**そのまま 12 サイクル**として換算してよいか

`ysd8800_psram_ctrl_v0_2.sv` L110 は次のようにカウンタを初期化している。

```systemverilog
? LATENCY_REFRESH : LATENCY_NORMAL) - 2;
```

**`- 2` の補正が入っている。** パラメータ値 12 がそのまま滞在サイクル数になるのか、`PS_IDLE` / `PS_WAIT_REQ_LOW` の分を含めて 12 になるよう調整されているのかは、この 1 行だけでは決まらない。

§3.1.3 の表は「PSRAM アクセス本体 12 psram cyc」としているが、**この 12 が FSM 全体の滞在サイクル数なのか `PS_BUSY` だけなのかを確認**されたい。前者なら現行の換算で正しく、後者なら `PS_IDLE` と `PS_WAIT_REQ_LOW` の分を加算する必要がある。

C-5 と同じく、机上推定の精度の問題であり M-5 の手順 0 で実測すれば決着する。

### C-7 【§3.2.2】16bit アクセスが**ライン境界をまたぐ**場合の扱いが未定義

`rd16()` / `wr16()` はバイト 2 回に分割して `mem_charge()` を呼ぶ（§5.1）。このとき `pa` と `pa+1` が**異なるラインに属する**場合がある（`pa % LINE_SIZE == LINE_SIZE - 1` のとき）。

- 両バイトともミス → **ライン充填が 2 回**発生し、課金は `2 × ((LINE_SIZE × LAT_FILL) − 1)`
- 同一ライン内で 1 バイト目がミス → 2 バイト目はヒット（充填済）→ 課金は 1 回分のみ

前者が正しいモデルであるが、設計書に明記が無いため、実装者が「16bit は 1 回だけ判定する」と実装する余地がある。**§3.2.2 に「判定は必ずバイトごとに行う。ライン境界跨ぎでは充填が 2 回発生しうる」と明記**されたい。あわせて §8.1 に境界跨ぎのテストを追加すると確実である。

### C-8 【§12 改版履歴】v0.1 行から**情報が削除されている**（KY41）

v0.1 の改版履歴には次の記述があったが、v0.2 の v0.1 行から**消えている**。

- 「**PSRAM は約 60 ではなく約 5 CPU cyc/byte**」
- 「**ペナルティは『バイトごとに (LAT−1)』**と §3.2 に明記」

KY41 は「文書改版は追記のみ、削除禁止」「前の版の情報を欠落させない」を要求する。**当該記述が誤りであったとしても、v0.1 時点でそう書かれていた事実は記録として残すべき**である。

もっとも、§3.1.2 に「v0.1 の重大な誤り（自己申告）」として詳細が残っているため**実質的な情報欠落は生じていない**。よって C に留めるが、履歴表は「その版に何が書かれていたか」の一次記録であり、**後から正しさを理由に書き換えると、誤りの発生した版が特定できなくなる**。v0.1 行は原文のまま復元し、誤りであった旨は v0.2 行に記す形が正しい。

### C-9 【§5.2 / §6.6】`--trace-addr` 単独時に「課金せずトレースする」分岐が未設計

§6.6 は「`--trace-addr` のみ → **課金せず**トレースのみ出力（キャッシュ判定は行う）」と規定する。一方 §5.2 の `mem_charge()` は課金とトレースを兼ねる単一関数であり、**戻り値は「追加課金サイクル数」**である。

「判定はする・記録はする・課金はしない」という状態を実現する内部フラグ（例：`charge_enable` を `cache_enable` と別に持つ）が §5.4 の状態変数表に無い。`cache_enable` 1 本では表現できない。**状態変数を分離するか、`mem_charge()` の戻り値を呼び出し側で捨てるかを明記**されたい。
