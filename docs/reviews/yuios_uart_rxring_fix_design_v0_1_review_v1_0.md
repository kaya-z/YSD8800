## 1. 総評

実装は設計書の記載どおりであることを実源で確認した（`wake_uart_waiter` L1788-1792、`rx_pop` L1839-1846）。着弾解析・構造的原因の分析はいずれも正確で、特に §4「対になるコードの非対称性」と §8 原則102 の提案は本質を突いている。事後起票としての目的（実源記録・構造的原因・検証定義）は達成されている。

ただし以下3点により条件付き承認とする。

1. §7「要調査」は**調査可能であり、結論は「改版必須」**である（本書 §2）
2. メモリ配置に誤記があり、被害範囲が過小に記載されている（I-01・I-02）
3. **修正2箇所の外側に未検出の潜在契約欠陥が残存**している（I-03）

## 2. ★最重要★ §7 の判定：**改版必須**（調査完了）

### 2.1 実源照合結果

`yuios_ph3_uart_design_v1_4.md` §5.5.3「wake_uart_waiter 擬似コード」を実源確認した。

```
    STW  A, [IPC4_WK_SRCTCB]
    MOV  X, A

    ; A4': r0=byte (rx_pop), r1=0, r2=0, r3=0 を TCB+16/+18/+20/+22 へ
    JSR  rx_pop                 ; A=byte（下位8bit）
    STW  A, [X + #16]           ; ipc_msg[0] = byte（※注: r0 を msg0 に置く）
    LDW  A, #0
```

**設計書の擬似コードにも X 復元が存在しない。**

### 2.2 判定

| 判定軸 | 評価（確定） |
|---|---|
| 設計書記載の手順・仕様が誤っていたか | **YES**。§5.5.3 擬似コードに `rx_pop` 復帰後の X 復元がない |
| 設計書の副作用記載（原則6）に漏れがあったか | **YES**。§5.5.2 の処理対応表（A3→A4）にも `rx_pop` の破壊レジスタ（A,B,X）の記載がない |
| データ構造・アドレスに変更があったか | なし |

→ **欠陥①は実装ミスではなく設計書由来のバグである。** 実装者は設計書のとおりに正しく実装した。
→ **`yuios_ph3_uart_design` の改版は必須。** A-5 は「改版必須」で確定してよい。

### 2.3 改版時の追記要求（A-5 向け）

1. §5.5.3 擬似コードに `LDW X, [IPC4_WK_SRCTCB]` を `JSR rx_pop` 直後へ挿入
2. §5.5.2 の A4 行に「`rx_pop` は A,B,X を破壊する。X（TCBポインタ）を `IPC4_WK_SRCTCB` から復元すること」を明記
3. §5.5.1 の必須ルールに「**コピー元に存在しない挿入命令は規約の保証範囲外であり、独立にレビューすること**」を追記（下記 §2.4）

### 2.4 ★さらに上位の構造的原因（§4 の一段上）★

設計書 §5.5.1 は「**IPC4_REPLY をコピペベースに実装すること**」を必須ルールとして課している。
しかし `IPC4_REPLY` には `JSR rx_pop` は存在しない。

> **コピペルールが保証するのは「コピー元と同じ部分の正しさ」だけであり、
> 差し替え箇所に新規挿入した命令（`JSR rx_pop`）は保証範囲外だった。**

§5.5.1 の禁止事項「✗ 本設計書 §5.5 擬似コードだけで実装する」という警告は皮肉にも機能せず、
**擬似コードと実装が一致したまま両方誤っていた**。実装照合レビューでは原理的に検出できない。

これが本件の最上位原因であり、§8 kaizen 提案に**系3**として追加することを強く推奨する（本書 §6）。

## 3. 必須指摘

### 3.1 I-01: §1 の `$FC5C` は「予約」ではなく `UART_DRV_TID`

**実源 `kernel_v12_9.asm` L392**:
```asm
UART_DRV_TID        EQU $FC5C       ; UARTドライバタスクID  v0.12.0: $F036→$FC5C
```

**問題**: §1 のメモリ配置図で `$FC5C` を「(予約)」としているが誤り。
これに伴い §2.3 の着弾解析表で `STW A,[X+#22]` → `$FC5C` を「予約領域」としているのも誤りで、
実際は **UART ドライバタスク ID が 0 で破壊**される。欠陥①の被害範囲は本書の記載より広い。

**反映要求**: §1 メモリ配置図および §2.3 着弾解析表を訂正。

**訂正後の §2.3（TAIL=0）**:

| 命令 | 意図した宛先 | 実際の着弾先 | 影響 |
|---|---|---|---|
| `STW A,[X+#16]` | TCB+16 ipc_msg[0] | `$FC56` | HEAD 破壊 |
| `STW A,[X+#18]` | TCB+18 ipc_msg[1] | `$FC58` | TAIL 破壊 |
| `STW A,[X+#20]` | TCB+20 ipc_msg[2] | `$FC5A` | COUNT 破壊 |
| `STW A,[X+#22]` | TCB+22 ipc_msg[3] | `$FC5C` | **UART_DRV_TID 破壊**（★訂正） |
| `STW A,[X+#24]` | TCB+24 ipc_valid=1 | `$FC5E` UART_WAIT_TID | ★致命★ |
| `STW A,[X+#26]` | TCB+26 ipc_sender | `$FC60` | 未割当領域 |

---

### 3.2 I-02: §2.3 の着弾解析が TAIL=0 のみで網羅性がない

**問題**: X = `$FC46 + TAIL` であるため、着弾先は TAIL に依存して全体がシフトする。
本書は TAIL=0 のみを解析しており、事後設計確定書としての網羅性を欠く。

**TAIL 依存の着弾範囲**（`[X+#16]`〜`[X+#26]` = `$FC56+TAIL` 〜 `$FC60+TAIL`）:

| TAIL | 着弾範囲 | 到達先 |
|---|---|---|
| 0 | `$FC56`–`$FC60` | HEAD / TAIL / COUNT / DRV_TID / **WAIT_TID** / 未割当 |
| 4 | `$FC5A`–`$FC64` | COUNT / DRV_TID / WAIT_TID / 未割当 / **STOR_DRV_TID** |
| 15 | `$FC65`–`$FC6F` | **ストレージ専用変数領域全域** |

さらに L1808 `LDW A,[X]` は `buf[TAIL]` を state として読み、値が 6（TASK_WAIT_REPLY）と一致した場合
L1812 で `buf[TAIL]=1` を書き込む（リングバッファ本体のデータ破壊）。

**「永久ハング」という症状になったのは TAIL=0 だったからであり、TAIL≠0 では
ストレージドライバ破壊という別症状**になり得た。

**反映要求**:
- §2.3 に上記 TAIL 依存の着弾表を追加
- §5.3 のダンプ範囲を `$FC46`–`$FC5F`（26B）→ **`$FC46`–`$FC6F`（42B）** に拡大
- V-3 に TAIL≠0 のケース（例: TAIL=4）を追加し、`STOR_DRV_TID` の健全性も確認基準に含める

## 4. 重要指摘（未検出の潜在欠陥）

### 4.1 I-03: `wake_uart_waiter` が `COUNT>0` の前提条件を継承宣言していない

**実源対比**:

`rx_pop` ヘッダ L1825:
```asm
; 入力: COUNT>0であること (呼び出し側が保証)
```

`wake_uart_waiter` ヘッダ L1759-1762:
```asm
; 入力: UART_WAIT_TID = 待ちクライアントtid (0=なし)
; 出力: クライアントTCBに ipc_msg[0]=byte, ipc_valid=1, state=READY
;       UART_WAIT_TID = 0 (クリア)
; 破壊: A, B, X (呼び出し元IRQ1_HANDLERが全退避済)
```

**`COUNT>0` が宣言されていない。** L1768-1769 は `UART_WAIT_TID != 0` のみ判定し、
COUNT を確認せずに L1787 で `JSR rx_pop` を実行する。

**現状の安全性は偶然に依存している**:
唯一の呼出元は L1313（IRQ1_HANDLER S7）であり、L1301 の `JSR rx_push`（S4）の直後にある。
このため COUNT≥1 が成立する（オーバーラン破棄時も COUNT=16 で成立）。
すなわち**呼出順序という暗黙の事実によってのみ契約が満たされている**。

**リスク**:
将来「起床漏れの救済」「タイムアウト時の再起床」等で別経路から `wake_uart_waiter` を呼ぶと、
`rx_pop` L1849-1851 の `SUBI B,#1` により **COUNT が `0-1 = $FFFF` にアンダーフロー**し、
同時に TAIL も進む。さらに `rx_push` L1343-1345 の `CMP A,#16 / BGE` が `$FFFF` を
どう評価するかによって、オーバーラン判定そのものが破綻し得る。

**位置づけ**: これは本件（呼び出し側が破壊レジスタ一覧を守らなかった）と**完全に同じクラスの契約欠陥**であり、
§8 原則102 の「明記だけでは防げない」の 2 例目である。修正2箇所の外側にあるため本書の視野に入っていなかった。

**反映要求**（(a) は必須、(b) は推奨）:
- **(a)** `wake_uart_waiter` ヘッダに前提条件を追記
  ```asm
  ; 入力: UART_WAIT_TID = 待ちクライアントtid (0=なし)
  ;       UART_RX_COUNT > 0（★必須。呼出元 IRQ1_HANDLER S4 の rx_push 後であること）
  ```
- **(b)** `rx_pop` 先頭に `COUNT==0` ガードを追加し、0 なら A=0 で即 RET（防御的実装）
- **(c)** V-1 の合否基準に「**COUNT がアンダーフロー（`$FFFF`）しないこと**」を追加

## 5. 中程度・軽微

本書は関連文書として `yuios_ph3_uart_design_v1_5.md` を挙げているが、

**反映要求**: v1.5 の実在を確認し、KY41 の4点整合（ファイル名／バージョン文字列／ヘッダ日付／変更履歴）を点検。
存在しない場合は参照を v1.4 に訂正する。

### 5.2 I-05: §4 表「rx_push のインデックス保持先 = B」は厳密には不正確

**実源 L1348-1359**:
```asm
    LDW  B, [UART_RX_HEAD]     ; B = HEAD
    LDW  A, #$FC46
    ADD  A, B                   ; A = &buf[HEAD]   ← 以降 B はデッド
    MOV  X, A
    LDW  A, [IRQ1_WK_BYTE]
    STB  A, [X]
    LDW  A, [UART_RX_HEAD]     ; ★メモリから再取得
    ADDI A, #1
    ANDI A, #$000F
    STW  A, [UART_RX_HEAD]
```

B は L1350 の `ADD A,B` 以降**デッド**であり、以後参照されない。
`rx_push` が正しく動作する真の理由は **L1356 でメモリから再取得している**点のみである。

すなわち「レジスタを分離していたから正しかった」のではなく「**再取得していたから正しかった**」。
原則102 の**系2 が本質**であり、系1（レジスタ分離）は本件では副次的である。

**反映要求**: §4 の表と本文を「再取得が本質」の観点に精密化。

### 5.3 I-06: V-1 / V-2 の実施手順が未定義

| ID | 未定義事項 | 要求 |
|---|---|---|
| V-1 | 「待機者不在の状態」の作り方。シェルは通常 GETC 待機に入るため `UART_WAIT_TID≠0` である | ブート中投入等、`UART_WAIT_TID==0` を保証する具体手順を明記 |
| V-2 | 「TAIL=15 の状態」の作り方。事前に 15 バイトの push/pop が必要 | 前処理手順を明記 |

## 6. §8 kaizen 原則102 への意見

**提案は妥当**。系1・系2 とも本件から正しく抽出されている。以下を**系3**として追加することを推奨する。

> **系3: 「既存実装をコピーベースに作れ」という規約は、
> コピー元に存在しない新規挿入命令を保証しない。**
>
> 差し替え・挿入した箇所は「コピペ規約の適用範囲外」であり、
> **その箇所だけは独立にレビューする**必要がある。
> コピペ規約は「同じ部分の正しさ」を保証するが、
> 「違う部分の正しさ」については何も言っていない。
>
> **実例**: `wake_uart_waiter` は `IPC4_REPLY` のコピペベースで作られ、
> コピー部分（TCB 書込・state 遷移・A7 の条件判定）は正しかった。
> 誤ったのは `IPC4_REPLY` に存在しない `JSR rx_pop` の挿入箇所だけであった。
> しかも設計書 §5.5.3 の擬似コードも同じ誤りを持っていたため、
> 「実装が設計書どおりか」の照合レビューでは**原理的に検出できなかった**。
>
> **系3の運用**: 設計書に擬似コードを載せる際、コピー元との差分箇所を
> 明示的にマーキングし（例: `★差替` コメント）、レビュー時はその行に
> 呼出先の副作用一覧を突き合わせることを必須手順とする。

なお §8 末尾の「明記だけでは防げないことの実例」という指摘は正しく、
本レビューで発見した I-03（`COUNT>0` 契約の非宣言）がその2例目である。
原則102 の本文に I-03 を追記すると説得力が増す。

## 7. KY活動

**予知**: **事後設計確定書は「実装の追認」に流れやすく、実装に残っている別の欠陥を見落とす。**

本件がまさにそれであり、I-03（`COUNT>0` 契約の非宣言）は「修正済み2箇所」の外側にあったため
本書の視野に入っていなかった。事後起票は「何を直したか」に焦点が絞られる性質上、
同一関数内の未修正部分が盲点になりやすい。

**防止策**: 事後設計確定書のレビューでは、修正差分だけでなく
**修正対象関数の呼び出し規約（入力前提・破壊レジスタ・呼出元との契約）を全項目再点検する**
ことを手順に含める。本件でいえば `wake_uart_waiter` / `rx_pop` / `rx_push` の
3関数のヘッダを実源で読み直し、宣言と実装の整合を確認する。
