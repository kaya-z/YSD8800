## 3. §3.2 の系統訂正を承認（最重要）

**メモの訂正は実源で完全に裏付けられる。承認する。**

実源で確定した割込系統：

```
IRQ0系統: YSD8002(timer) ──[irq_in=1]──> CPU     （YSD8004を経由しない独立系統）
IRQ1系統: UART_RX/STOR/UART_TX ──> YSD8004(ワイヤードOR) ──[irq1_o]──> CPU
```

- emu23 で `irq_pending=1`（タイマー）は L1557 で直接セットされ、`ysd8004_raise`（=2をセット）を通らない。
- したがって `irq0_ack` は **YSD8004を経由せず YSD8002 へ直結**するのが正しい。
- 結果、**UART（V4完了・19/19 PASS）・YSD8004 は完全無改修**。デグレ危険を系統ごと排除できる。

前回回答書の「YSD8004経由でデバイスに伝える」は、割込アクノリッジの一般論（INTAはPIC経由）に引きずられた記述で、本プロジェクトのIRQ0直結構成には当てはまらなかった。本メモの訂正が正確である。

> **補足（irq0_ack が iret_pulse_o と異なる点は変わらず有効）**：irq0_ack が「割込プロトコル（受理＝アクノリッジ）の一部」でありバス上正当、という前回の論拠は維持される。IRQ0直結でも、それは「受理サイクルの一部をデバイスへ返す」ものであって、命令意味論（IRETした）の暴露ではない。系統が直結かYSD8004経由かは、この正当性に影響しない。

## 4. β点（受理確定点）の選択を承認

**§3.4 の生成条件は実源と厳密に一致する。承認する。**

```systemverilog
irq0_ack = (state==S_MEMR_HI) && mem_ready && (stack_ctx==CTX_IRQVEC) && (irq_latch==3'd1);
```

実源 `L1042-1045`：
```systemverilog
S_MEMR_HI: begin
    if (mem_ready && stack_ctx == CTX_IRQVEC) begin
        rf_we_pc    = 1'b1;
        rf_wdata_pc = {mem_rdata, mem_lo}; // PC←ベクタ値
    end
end
```

- この瞬間に PC がベクタ値へ書き換わり、`L715-718` で `next_state=S_FETCH` に進む。**受理が後戻りしない確定点**である。
- emu23 で発火チケットが消費される（`irq_pending=-1`）タイミングと最も等価。β点選択の論理は正しい。
- α点（S_IRQ_ACCEPT入口）を避けた理由「受理途中アボート時に線を早く消しすぎるリスク」も、将来の安全側として妥当。現状アボート経路は無いが、予防的設計として支持する。

## 5. 未決事項（§5）への実源回答

### 5-1. fire と irq0_ack の同クロック競合 → **fire優先を推奨**

- 現実には両者は数クロック離れる（fireは発火時、irq0_ackはその数クロック後の受理確定時）ため競合しない、という認識は正しい。
- 安全側の明文化として、**万一の同クロック競合時は fire(set) を優先**すべき。理由：発火イベントの取りこぼしは割込欠落（回復不能）を招くが、クリアの1クロック遅延は次サイクルで受理されるだけで無害。emu23 も「発火チケットを置く」が優先で、消費はその後。set優先が黄金と整合する。
- 実装：`if (fire) irq_req_r<=1; else if (irq0_ack) irq_req_r<=0;`（fireを先に評価）。

### 5-2. irq0_ack を comb assign で出せるか → **出せる。既存ff無改変を保証できる**

- β点条件（S_MEMR_HI/mem_ready/CTX_IRQVEC/irq_latch==1）は、実源で既に**comb always ブロック内**（`rf_we_pc=1'b1` をブロッキング代入している L1042 のブロック）で評価されている量のみで構成される。
- したがって同じ comb ブロックに `irq0_ack = (上記条件);` を1行足すだけで生成でき、**既存 ff（順序回路）には一切触れない**。§4.3の「追加はすれど改変せず」を厳密に満たせる。
- これによりCPU改修は「出力ポート1本＋comb代入1行」に封じ込められ、デグレ危険が最小化される。**推奨実装である。**

### 5-3. align/syscall受理でのCTX_IRQVECガード → **irq_latch==1ガードで正しく排除される**

- 実源 `L832` により、**timer/device/align/syscall の全受理が CTX_IRQVEC を共通で通る**（ベクタアドレスは irq_latch*2 で区別）。
- したがって `stack_ctx==CTX_IRQVEC` だけでは全受理で irq0_ack が立ってしまうが、**`irq_latch==3'd1` ガードにより timer 受理時のみ抽出される**。device(2)/align(3)/syscall(4) 受理では irq0_ack は立たない。
- ガードは必須かつ有効。設計は健全。§5-3の懸念は解消される。

## 6. emu23 等価性の確認（§3.6）

メモ§3.6の等価表は正しい。実源に照らして追認する：

| ケース | emu23 | 修正後RTL（期待） | 等価性 |
|---|---|---|---|
| noack | fire→受理→irq_pending消費→再武装なし→**CNT1** | fire→irq_req_r=1→**受理でirq0_ackクリア**→再武装なし→**CNT1** | ✓ |
| ack | fire→受理→消費→ACKで再武装→周期発火→**CNT30/OUTC200** | fire→受理でクリア→ACKで再武装→周期発火→**CNT30/OUTC200** | ✓ |

「受理でチケット消費」を irq0_ack が写像し、「ACK＝再武装専任」に戻す構造は、emu23 の2層モデルと構造的に一致する。**ACK を割込線クリアと再武装に短絡させていた元バグが、根本から解消される。**

## 7. デグレ対策（§4.2）への所見

§4.2 の絶対ゲートは的確。特に以下を厳守されたい：

- **V1/V2 全82ベクタ再走 → デグレゼロ**：CPU改修（出力ポート追加）が入るため必須。ただし §5-2 の通り comb 1行追加なら既存 ff 不変で、デグレ確率は極めて低い見込み。それでも実証は省略しないこと。
- **Dhrystone 絶対ゲート 826/48405/P:20**：前回判断で分析した通り、Dhrystoneは割込を受理しない（IE=0）ため irq0_ack は一度も立たず、結果は不変の見込み。実証で確定すること。
- **★noack=CNT1 と ack=OUTC200 の両方回復★**：これが真因クローズの条件。前回回答書§6で指摘した通り、ack側FAIL（OUTC=33）も同じ irq_req_r 問題に由来するはずだが、ACK書込→irq_req_r=0 の経路（現L282）が正しく効くかは別途確認が要る。片方だけの回復で満足しないこと（原則63）。

## 8. MC6840 PTM との対比（参考）

本設計は、MC6840 PTM の割込プロトコルに正確に対応している。PTMでは「割込フラグのクリア（ステータス読み等）」と「タイマー再スタート」が別操作であった。案0-a' は：

- **irq0_ack ＝ 割込線クリア**（＝受理による割込フラグ解消。PTMのステータスアクセス相当）
- **ACK(bit5) ＝ 再武装**（＝タイマー再スタート）

と、両者を正しく分離した。元のRTLがこの2つをACK一発に短絡させていたのが誤りで、本設計はPTMの作法に回帰する。OS-9のデバイスドライバが「割込を受理してから、しかるべき時にデバイスを再アームする」二段構えだったのと同じ構造であり、設計として正統である。
