### M-11 ★A-2' の `ack_edge_c` は同時遷移によるデコードグリッチを生じ、それが 32MHz でサンプルされる★

**本指摘が、A-2' 実装着手の停止条件です。**

| 項目 | 内容 |
|---|---|
| 該当 | §4.3 案 A-2' のコード `wire ack_edge_c = ack_sync[1] & ~ack_sync_d;`／§9 論点1 |
| 機序 | `ack_edge_c` は 2 つの FF 出力の**デコード**である。通常の立上り系列では片方ずつしか変化しないためグリッチは生じないが、★**ack 立下り時に `ack_sync[1]` と `ack_sync_d` が同一エッジで 1→0 に同時遷移する**★。<br>このとき `ack_sync_d` の Q が `ack_sync[1]` の Q より先に落ちると、**一瞬 `a=1, b=0` が成立し `ack_edge_c` に幅数百 ps のハザードが出る** |
| ★影響1（req_level 側・重大）★ | A-2' では `req_level = (rd\|wr) & ~ack_edge_c` であり、★**`req_level` は `req_sync` により psram_clk（31.25ns 周期）でサンプルされる CDC 信号**★。2FF 同期器は**メタステービリティを抑えるものであって、実在するグリッチのサンプリングは防げない**。<br>幅 Δt のハザードが捕捉される確率はおよそ `Δt / 31.25ns` であり、`Δt = 0.5ns` なら**1 アクセスあたり約 1.6%**。M-2→M-3 区間だけで数万アクセスが走ることを考えると、無視できる確率ではない |

## 4. C：確認事項

### C-4 A-2' におけるアドレス変更と req 抑止の時間差

A-2' では CPU が N サイクルで組合せ ready を受け、同じ N で次アクセスの `cpu_phys_addr` を出す可能性がある。一方 `req_level` の抑止が psram 側に届くのは `req_sync` の 2FF 分（約 2 psram cyc）遅れるため、★**N の開始から約 62.5ns の間、「新しいアドレス」かつ「`psram_req` が依然 1」という窓が存在する**★。

実源 L125-128 より、この期間 `psram_ctrl` は `PS_WAIT_REQ_LOW` にあり **req を新規受理しない**ため論理的には安全と判断できるが、A-2' 固有の窓であるため §4.3 に**明示的に安全と記録**されたい（後から読む人が同じ検証を繰り返さないため）。

### C-5 `cpu_mem_rdata` のリセット系が変わる

現行 L86 は `cpu_rst_n` で `cpu_mem_rdata <= 8'h00;` としている。`assign cpu_mem_rdata = psram_rdata;` に変えると、リセット時の値は **`psram_rst_n` 系で初期化された `psram_rdata`** に従うことになる。両リセットが同時解除でない構成の場合、`cpu_rst_n` 解除直後の `cpu_mem_rdata` が不定になり得ないか確認されたい。あわせて `mmio_stub` の `8'h00`→`8'hFF` 是正（KY57 の経緯）と同種の「リセット値の暗黙前提」に該当しないかも一読を推奨する。

### C-6 PoC の BASE 実測 5 cpu_clk は §2.3 内訳の第三の独立検証になる

§2.3 は 1 バイトあたり **4.75〜5.90（採用 5.75・最悪値）**と見積もっている。PoC の BASE 実測は **5 cpu_clk** であり、これは ★`req_sync 0.25 + PSRAM 1.5 + ack_sync 2（最悪値でなく典型値）+ req_hold 1 = 4.75 ≒ 5`★ と整合する。

すなわち **PoC は §2.3 の内訳表そのものを独立に裏付けている**。C-1 で失われた「三者目の検証」の代替として、§2.3 に「PoC 実測 5 cpu_clk と整合（ack 側が典型値 2 で成立）」を追記することを推奨する。**実測が机上内訳の妥当性を支持した、という事実は残しておく価値がある。**
