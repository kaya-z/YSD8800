## §2. 必須修正の詳細

### 2.1 M-1：`--stats-at-cycle` の単位取り違え

§3.3.3 は次を定める。

> ★`N` には M-5 到達サイクル（YUI OS CEN=0 で 3,754,937）を与える。★
> ★これにより「RTL の `C_RTL` と同じ地点までの `I`／`N`」が得られ、連立の前提が揃う。★

★これは成立しない。★

| 系 | `cycle` の意味 | 実源 |
|---|---|---|
| emu23 | ★命令数（CPI=1 固定）★。`cpu.cycle++` は L1230 の 1 箇所のみ | `ysd8800_v5_membus_v0_12.sv` L156（本書 §2.3 が自ら引用） |
| RTL | ★クロック数（実 CPI ≒ 18）★ | 同 L157 |

★3,754,937 は RTL のクロック数である。★
これを emu23 の cycle として与えると、emu23 は ★3,754,937 命令★ 実行した地点で統計を出す。
RTL が M-5 に到達したのは ★約 208,000 命令★ の地点である（3,754,937 ÷ 18）。

★すなわち `I`／`N` は `C_RTL` の約 18 倍の実行区間から採られる。★
この `I`／`N` を連立に入れれば、★`b` は本来の 1/18 程度に出る。★
§5.1.4 で「モデルの正否ではなく丸め誤差を判定している」と喝破したのと同種の誤り
——★今度は丸め誤差ですらなく、別の実行区間を測ることになる。★

★根本原因は §2.3 で自ら書いた「単位が違う」という事実を、§3.3.3 で適用しなかったことである。★
（§5.1.4 では「課金しないため cycles は命令数そのものである」と正しく注記している。
★同じ注意が §3.3.3 に及ばなかった。★）

**修正要求**：★停止契機を「同一プログラム地点」に改めよ。★

- 連立が要求するのは「★`C_RTL` と同じ命令列を実行し終えた時点★」の `I`／`N` である
- 揃えるべきは ★プログラム状態★ であって、時間軸の値ではない
- §3.3.3 の「マーカー検出は UART 出力順序（TKT-U1）に依存する」という懸念は
  ★UART バイト列の順序についての話であり、プログラム地点の同定には当たらない。★
  ★PC アドレスで止めるなら順序依存は無い。★

具体案は §3.1（C-1）に示す。

### 2.2 M-2：案D — 段7-C の実測を使えば連立自体が不要

★U-4 のゲートが本当に要求しているのは `b`（実効 LAT − 1）の妥当性確認である。★
`a` は「偶然フィットを弾く」ための副次条件にすぎない（§5.1.3 条件2）。

段7-C は ★CEN=0 ビンを含む 4 ビンで、ストールサイクルを実測している★
（`v18` の `stall_rd`／`stall_wr`／`bus_ack`）。★これは「メモリ待ちに費やしたクロック数」そのものである。★

したがって ★1 ビンだけで直接求まる。★

```
b_measured = (stall_rd + stall_wr) / N          ← 実効 LAT − 1
a_measured = (C_total − stall_rd − stall_wr) / I ← RTL の基本 CPI
```

| 項目 | 案D | 現行（2 ビン連立） |
|---|---|---|
| 必要なビン数 | ★1★ | 2 |
| 条件数の問題 | ★無い（除算のみ）★ | ★あり（§5.1.4）★ |
| YUI OS の `I`／`N` | ★不要★（Dhrystone -O0 CEN=0 で完結。★HALT するので atexit が走る★） | 必要 |
| emu23 改修 | ★`--stats-at-cycle` は不要★（`stat_calls[]` と命令数カウンタのみ） | 案A が必要 |
| 期待値との突合 | ★`b_measured ≒ 4`／`a_measured ≒ 18` を直接照合できる★ | 連立の解を帯で判定 |

★段7-C のストール定義（`mem_wr && !mem_ready` の積算）は、課金規約の `lat − 1`
（＝CPU 側の 1 サイクルと重なる分を引いた「追加で待つ量」）と ★同じ量を数えている。★
したがって `b_measured` は `lat − 1 = 4` と ★直接比較できる。★

**修正要求**：★案D を第一候補として検討し、採否を §5.1 に記録せよ。★
採るなら ★`--stats-at-cycle`（案A）は不要になり、R1 を脅かす変更点が 1 つ減る。★
採らない場合も、★なぜ 1 ビンで足りないのかを記すこと。★

（注意点として、段7-C のストール値が ★MMIO を含むか RAM 側のみか★ を確認すること。
指摘書 v18 §2.3 で MMIO 分離を要求しているため、`v18` v0.4 に RAM 側の値があるはずである。
★MMIO 込みの値を使うと `b` が過大に出る。★）

### 2.3 M-3：YUI OS ビンでも悪条件になりうる

§5.1.4 は ★「U-4 のゲートは YUI OS ビンでなければ通せない」★ と結論する。
理由は「`I/N` を Dhrystone と大きく変えられる唯一の手段であるため」とする。

★しかしこれは仮説であって、確認されていない。★

- Dhrystone の `I/N` は ★0.1461★（1 命令あたり約 6.8 バイトアクセス）
- YUI OS も同じ YSD8800 命令セットの、同じコンパイラ／アセンブラで作られたコードである
- ★1 命令あたりのバイトアクセス数は命令長とオペランドで決まるため、同じ ISA なら似た値になりやすい★

★仮に YUI OS の `I/N` が 0.15 近傍だった場合、§5.1.4 とまったく同じ悪条件に陥る。★
そのときは ★`--stats-at-cycle` を実装し、YUI OS を走らせ、連立を解いた末に
「やはり判定できない」と分かる★ ——最も高くつく失敗の仕方である。

**修正要求**：§5.3（測定無効条件）に条件5 を追加せよ。

| # | 条件 |
|---|---|
| ★5★ | ★2 ビン連立の条件数が閾値（例：100）を超える★ — この場合 `a`／`b` の値によらず判定不能とし、★不合格とは記録しない★（§5.1.4 と同じ扱い） |

★さらに、YUI OS の `I`／`N` が得られた時点で、連立を解く前に条件数を先に計算すること。★
条件数が閾値を超えたら ★その時点で止める★（解いた値を見てから判断しない＝K-3 の精神）。

★案D を採れば、この問題は構造的に消える。★ これも案D を推す理由である。

## §3. 確認事項

### 3.1 C-1：既存オプションが案A の代替になりうる

emu23 には ★正常終了する打切り手段★ が既に 2 つある。

| オプション | 内容 | 実源 |
|---|---|---|
| ★`-n N`★ | ★N ステップ実行して終了★（非対話） | L3479, L3518, L3917, L3962 |
| ★`-b ADDR`★ | ★指定アドレス到達後★ に `-n` のステップを実行 | L3964 のコメント |
| `--wm-steps N` | `-w` 併用時の常駐 OS 打切り上限（既定 2,000,000） | L540, L3582, L3940 |

★正常終了すれば `atexit(cache_report_summary)`（L3609）が走り、統計は出力される。★
すなわち ★§5.1.5 の「YUI OS は HALT しないため統計が出ない」は、既存手段で回避できる可能性がある。★

さらに ★`-b ADDR` は M-1 の解でもある。★
M-5 に対応するカーネル内の PC（例：M-5 の出力を行うルーチンの入口）で止めれば、
★プログラム地点で揃えられる★ ——サイクル数で揃えるより厳密であり、
§3.3.3 が懸念した UART 順序依存とも無関係である。

**要求**：§5.1.5 の選択肢表に ★案A'（既存の `-b`／`-n`／`--wm-steps` を使う）★ を追加し、
採否を判断せよ。★採れるなら emu23 の改修は `stat_calls[]` と命令数カウンタだけで済む。★

（ただし `--wm-steps` は `-w`（スタック watermark 計測）併用時のみ有効であり
（L3940：`if (wm_enable && ++steps >= wm_max_steps)`）、★単独では効かない★。
`-n` または `-b` を使うこと。★実装前に実源で挙動を確認されたい。★）

### 3.2 案A を採る場合の最小要件

案A'（既存手段）が使えず案A を実装する場合、★オプション名と単位を一致させること。★

- `--stats-at-cycle` という名前で ★emu23 の cycle（＝命令数）★ を取るなら、
  与える値は ★RTL のクロック数ではない★。名前と単位が一致していても、
  ★§3.3.3 の運用指示（3,754,937 を与える）が誤り★ である
- 推奨は ★`--stats-at-pc <ADDR>`★（プログラム地点で揃える）。M-1 の要求に直接応える

U-10（判定を命令境界に置く）は正しい着眼であり、★PC 契機にすれば自然に命令境界になる。★

### 3.3 N-1：K-9 の提案

§5.1.4 で得た教訓は ★危険として登録する価値がある。★

> ★K-9★：★条件の悪い連立の解を「不合格」と読み違える危険★
> — 悪条件下の解はモデルの正否ではなく入力の丸め誤差を反映する。
> ★連立を解く前に条件数を確認し、閾値を超えたら「判定不能」として記録する（不合格ではない）。★

> ★見えないものを「良い」と読むのが KY99、判定できないものを「悪い」と読むのが本項である。★
