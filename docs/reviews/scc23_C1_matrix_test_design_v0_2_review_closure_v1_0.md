## 1. 総合判定

**全4項目（M-1 / M-2 / N-1 / N-2）クローズ。** 新規の必須指摘なし。

v0.2 は指摘に的確に対応し、特に N-2 は**実際に `case2_no_proto.c` を実行して「262 行の壊れた asm が出力され `LDW B,#8` 誤 I2F が残存」と実測**した上で反映しており、机上でなく実データで裏を取っている点が良い。§2.6（error_stop 時の asm 隔離運用）の新設は指摘の主旨を超えた良い追加である。

ただし、M-1（主判定を golden 差分へ変更）を採用したことに伴う**伝播漏れ・運用未定義が2点**残る（下記 §3）。いずれも軽微（E/N 相当）でブロッカーではないが、テストを「Phase 2 のセーフティネット」として機能させるには反映が望ましい。

## 3. 残課題（軽微・v0.3 で反映推奨・ブロッカーではない）

### 3.1 OBS-1【E相当】§7.2 が v0.1 の記述のまま残り、§2.3 の主判定変更と矛盾

**箇所**: §7.2「Q8.8 数値検証」

**現状記述**: 「現状は**『生成 asm に誤 I2F 挿入がないか』の構造的検証のみ**。C-2 の Q8.8 ヘルパ整備後、期待値との数値一致検証を追加」

**問題**: §2.3 で主判定を **golden asm との byte 一致**へ変更した（M-1 反映）にもかかわらず、§7.2 は v0.1 時点の「構造的検証（誤 I2F grep）のみ」という記述のまま残っており、**v0.2 本文と食い違う**。読者が §7.2 だけを見ると、主判定が今も grep だと誤解する。

**対応案**: §7.2 を「現状は **golden asm との byte 一致による構造的検証**（誤 I2F grep は補助）。C-2 の Q8.8 ヘルパ整備後、**演算結果の数値一致検証**を追加」と更新（KY41: 旧記述は取り消し線保持でよい）。

### 3.2 OBS-2【N相当】golden の作成・更新手順が §5／§6 に未定義

**箇所**: §5 検証計画、§6 実装手順、§2.4（`golden_version`）

**問題**: M-2 で `golden_version=v2.05` を刻む設計にしたが、
- **golden をどう作成するか**（§6 実装手順に「golden 凍結」ステップが無い。手順は 1.ディレクトリ作成 → 2.ソース生成 → 3.期待値生成 → 4.スクリプト → 5.README → 6.PASS 実測、で golden 生成が抜けている）
- **Phase 2 で挙動が正当に変わったとき golden をどう更新するか**（更新手順・承認フロー・`golden_version` の刻み直し）

が未定義。golden 方式は「更新手順を決めておかないと、回帰時に安易に golden を上書きして回帰を握り潰す」典型的な失敗モードがある。

**対応案**:
1. §6 実装手順に「**2.5. v2.05 で各テストをコンパイルし出力 asm を `goldens/` へ凍結（`golden_version=v2.05` を記録）**」を追加。
2. §7 に「**golden 更新ルール**」を新設: 「golden と差分が出た場合、原則は回帰疑いとして調査する。仕様変更が正当と判断された場合のみ、**変更理由を記録した上で** golden を更新し `golden_version` を新版へ刻み直す。無検討の上書き禁止」。
3. V3（§5.3）に「golden が v2.05 で生成されたものであることの確認」を追加。

### 3.3 OBS-3【参考・対応不要】error() の exit 化は Phase 2 課題として妥当

§2.6 が「exit 化するかは Phase 2 以降の課題（現行の設計思想を尊重し本 C-1 では触らない）」としたのは妥当な判断。C-1 は本体非改変タスクであり、`error()` の挙動変更は本体改変になるためスコープ外とするのが正しい。§2.6 の隔離運用で実害（壊れた asm の誤使用）は防げる。

## 4. クローズ宣言

レビュー指摘書 `scc23_C1_matrix_test_design_v0_1_review_v1_1.md`（M-1 / M-2 / N-1 / N-2）は、`scc23_C1_matrix_test_design_v0_2.md` への反映により**全項目クローズ**とする。

OBS-1 / OBS-2 は**軽微な文書整合・運用定義の不足**であり、実装着手のブロッカーではない。ただし OBS-2（golden 作成・更新手順）は、テストが Phase 2 のセーフティネットとして機能するかを左右するため、**実装フェーズで golden を作る前に**手順を確定させることを推奨する。

本設計メモは**承認に値する**。C-1（マトリクステスト整備）は本体非改変タスクにつき原則43 軽量版でよく、着手時は 工程確認（「工程ヨシ!」）→ KY →「ご安全に！」を経ること。

> 総括: v0.2 は主判定を golden 差分へ切り替え、error_stop を AND 条件化し、壊れた asm の隔離運用まで定義した。実測（262 行の壊れた asm・誤 I2F 残存）で裏付けた姿勢は KY34 の実践である。残る OBS-2（golden 更新ルール）を定めれば、Phase 2 型システム統合時の回帰検出網として十分に機能する。
