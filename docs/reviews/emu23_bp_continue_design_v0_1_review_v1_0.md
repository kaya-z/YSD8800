## 0. 総評

**原因分析・修正方式・検証計画のいずれも妥当であり、設計として実装に渡せる水準にある。** 特に以下を評価する。

- **原因の特定が実源と完全一致**している（§0.1 参照）。「`while` の入口で `is_break(cpu.pc)` を判定しているため、BP 停止位置では 0 回ループになる」という説明は、欠陥の全体を過不足なく述べている。
- **§3.3 の全数確認**。「`exec_one()` を回す REPL ループは 3 箇所のみ」を実源 grep で確定させた手続きは正しく、**本レビューでも同一の結論を得た**。
- **§8.1 の教訓**。「同じ形をしたコードが複数ある場合、1 箇所の修正は**残りが未修正であることの証拠でもある**」という一般化は、`[FIX BUG-8]` の横展開漏れという実例から導かれており、kaizen 原則として価値がある。
- **§8.2 の教訓**。「BP 判定自体を無効化しても『前進する』ため、前進の確認だけでは修正成功と誤認する」という指摘は、**検証設計として本質的**である。B4-02／B4-04 がこの認識から導出されている点も一貫している。
- **案2 を却下した理由**が「内部状態変数の変更箇所は一か所に集約」というコンパイラ実装設計原則3 に基づいており、**プロジェクト横断の原則を他ツールに適用**している。

指摘は **M-1（KY41 の取りこぼし）／M-2（`s` の生存確認欠落）** の 2 件と、確認事項 2 件である。いずれも局所的である。

**★BREAK 表示との整合（設計書に記載は無いが、修正の成立に必須の事実）★**

BREAK 表示は **REPL ループ冒頭（L2064）で `is_break(cpu.pc)` により行われる**。したがって do-while 化した `c` が BP で停止すると、次のループ周回の冒頭で `** BREAK @xxxx **` が表示される。**表示ロジックには一切手を入れる必要がない**ことを確認した。この事実を §4 に 1 行添えておくと、実装者が表示側も直すべきかと迷わずに済む。

**★`c` / `t` を先取りする分岐が無いことの確認★**

REPL の `else if` チェーンは `s` → `c` → `t` → `bd` → `b` → `regs` → `disas` → `memw` → `mem` → `irq` → `reset` → `q` → `mmu` の順である。`cmd[0]=='c'` および `cmd[0]=='t'` を先取りする分岐は存在せず、**L2102 の `bd` が L2115 の `b` より前に置かれている**（v1.06 F-001 の対策）構造も維持されている。**本修正はコマンド分岐順序に影響しない。**

## 1. M（Must：v0.2 で是正）

### M-1 KY41 四点整合の「バージョン文字列」が起動バナー内の**版数履歴リスト**を取りこぼしている

§7.3 は 4 点を次のように定義している。

| # | 対象 |
| --- | --- |
| 2 | バージョン文字列（起動バナー `v1.14`） |
| 4 | 変更履歴（**冒頭コメント**の改版履歴に v1.14 行を追加） |

しかし実源のバナーは、**1 行目の版数表示に加えて、版ごとの履歴リストを内蔵している**。

```c
    if (argc < 2) {
        fprintf(stderr,
            "emu23 v1.13 (2026-08-14) for YSD8800 ISA2.3\n"          ← ②が指すのはここ
            "  - v1.13: EMU-A argv consume-mark (--dbg/--sym, no more option\n"   ★
            "           misread as .dbg/.sym) + EMU-B MAX_SYM 128->2048\n"        ★
            "           with [SYM-TRUNCATED]/[SYM-NOTFOUND]/[DBG-NOTFOUND]\n"     ★
            "  - v1.12: TKT-03 c_iflag (B-1) + MMIO decode layer, 8bit coverage,\n"
            "  - v1.11: TCR fire-EN OR->AND (IRQ_EN now masks; plan-B EN fix)\n"
            ...
```

**v1.04 以降のすべての版が 1 行ずつ積み上げられており、v1.14 行を追加しなければ履歴が途切れる。** これは「冒頭コメントの改版履歴」（§7.3 の #4）とは**別の第 3 の箇所**である。

**是正**：§7.3 を 5 点に拡張する。

| # | 対象 |
| --- | --- |
| 1 | ファイル名（`emu23_v1_14.c`） |
| 2 | バージョン文字列（起動バナー 1 行目 `emu23 v1.14 (2026-08-17)`） |
| 3 | ヘッダ日付（`2026-08-17`） |
| 4 | 変更履歴（**ソース冒頭コメント**の改版履歴に v1.14 行を追加） |
| **5** | **★起動バナー内の版数履歴リストに `- v1.14: ...` 行を追加★** |

追加する行の案（既存行と体裁を揃える）：

```
"  - v1.14: REPL 'c'/'t' resume from breakpoint (do-while; was 0-iteration\n"
"           at BP due to entry-side is_break check) (B-4 EMU-C)\n"
```

> **KY 観点**：本プロジェクトでは v1.6→v1.7→v1.8 の設計書レビューでも**節番号・参照の取りこぼしが 3 回連続**した。**「版数を書く場所を全数列挙してから直す」**という手順を、ソースにも適用されたい。今回は `grep -n "v1\.13" emu23_v1_13.c` で全出現を洗い出してから着手するのが確実である。

### M-2 §6.2 に `s` の生存確認が無い（§8.2 の自らの教訓に照らして不足）

§8.2 は次のように述べる（**正しい原則である**）。

> **修正の検証は「直したい症状の消失」と「壊してはいけない機能の生存」を対で取る。**

ところが §6.2 の B4-01〜B4-05 は **`c` と `t` のみ**を対象としており、**`s` の生存確認が無い**。§5.3 は「`s` は既に後置判定であり、挙動は一切変わらない（非回帰）」と述べるが、**これは主張であって実測ではない**。

`s` は次の理由で確認対象とすべきである。

1. **`s` は BP 停止位置から前進できる唯一の既存手段**である。これが壊れると、BP 機能そのものが実質使用不能になる。
2. 修正箇所は `s` と**同一の `else if` チェーン内**であり、編集ミスで `s` ブロックの波括弧や分岐構造を壊す可能性は非ゼロである。
3. **`s` こそが本修正の手本**（§3.2）であり、手本が壊れていないことの確認は論理的に必要である。

**是正**：§6.2 に以下を追加する。

| ID | 手順 | 期待結果 |
| --- | --- | --- |
| **B4-06** | BP 停止位置（`BREAK @0104`）で **`s`** | **1 命令前進**（PC=0106、A レジスタが `0002` に更新されること） |
| **B4-07** | `s 8` のように**複数ステップ指定**で BP を跨ぐ | **BP アドレス到達時点で停止**すること（`[FIX BUG-8]` の生存確認） |

> **B4-07 の意義**：`s N` の途中で BP に当たったら止まる、という `[FIX BUG-8]` の挙動が維持されていることを確認する。**本修正は「BUG-8 の横展開漏れ」の是正であるから、BUG-8 本体の生存確認は対で取るべきである。**

## 2. C（要確認：v0.2 で回答）

### C-1 B4-04 の `reset` はメモリ・汎用レジスタを保存するため、2 周目が 1 周目と同一条件にならない

実源 L2177-2183 の `reset` は次のみを初期化する。

```c
} else if (strncmp(cmd, "reset", 5) == 0) {
    cpu.pc          = rd16(0x0000);
    cpu.flags       = 0;
    cpu.irq_pending = -1;
    cpu.halted      = 0;
    cpu.cycle       = 0;
    YSD8002_init(ysd8002.cpu_freq_hz, ysd8002.irq_hz);
    printf("CPU reset. PC=%04x\n", cpu.pc);
```

すなわち **`cpu.a` / `cpu.b` / `cpu.x` は保存され、メモリ（`mem[]`）も保存される**（コメントにも `memory preserved` とある）。ブレークポイント配列も保存される（`bp[]` / `bp_count` に触れていない）ため **B4-04 は実行可能**であるが、以下の点を確認したい。

1. **PoC が自己書換や結果保持を行う場合、2 周目の実行経路が 1 周目と異なりうる。** `b4_bp_poc_v2.asm` v0.2 がその性質を持たないことを確認済みか。
2. **BP 機能の生存確認としては B4-02（2 個目の BP `010c` で止まる）で既に達成されている。** B4-04 は「同一 BP に再度到達しても止まる（BP は消費されない）」ことの確認と位置づけるほうが、目的が明確になる。

**回答願う**：B4-04 の位置づけを「補助確認」と明記するか、あるいは **emu23 を再起動して同一シナリオを再実行する**形（条件が完全に同一になる）に変更するか。

> 併せて、**`reset` がメモリを保存する仕様**は §5 の仕様確定の対象外（本修正で変更しない）である旨を明記しておくと、後年の誤解を防げる。

### C-2 G-6（起動バナー）の取得条件が未記載

実源のバナーは **`if (argc < 2)` の場合にのみ、`fprintf(stderr, ...)` で出力**される。したがって：

- `./emu23`（**引数なし**）で起動する必要がある
- 出力先は **stderr** であり、`2>/dev/null` では消える（G-1 と同じ注意）

**回答願う**：G-6 の取得手順（`./emu23 2>&1 | head -1` 等）を §6.3 に明記されたい。**G-1 について同種の注意（stderr に出る）を既に書いているため、G-6 にも同じ配慮が必要である。**
