## 3. 特記事項（高く評価する点）

### 3.1 レビュア提示ケースの不備を検算で発見・差し替え（M-1）

当方は M-1 で FMUL 検証ケースとして `-1.0 * 0.1` を提示したが、v0.2 は反映時の検算により **このケースが floor/truncate ともに -25 となり分岐しない**（tmp = -6400 が 256 の倍数）ことを見抜き、実際に分岐する C2 `-0.1*0.1` / C3 `-0.5*0.1` へ差し替えた。

**当方でも独立に検算し、v0.2 の判断が正しいことを確認した**：

| 式 | a | b | tmp | floor（正） | truncate（誤） | 分岐 |
|---|---|---|---|---|---|---|
| `-1.0 * 0.1`（当方提示） | -256 | 25 | -6400 | -25 | -25 | **✗ 同値・検証不能** |
| `-0.1 * 0.1`（v0.2 採用） | -25 | 25 | -625 | **-3** | -2 | ✅ 分岐 |
| `-0.5 * 0.1`（v0.2 採用） | -128 | 25 | -3200 | **-13** | -12 | ✅ 分岐 |
| `-1.0 / 3.0`（C1） | -256 | 768 | — | -86（誤） | **-85**（正） | ✅ 分岐 |

**当方の誤り**：「負値なら丸め方向で分岐する」と暗黙に仮定していたが、正しい分岐条件は **「負値**かつ** tmp が 256 の倍数でない」**である。v0.2 §2.5.3 の「tmp が 256 の倍数だと両者は一致するため、倍数でない負値を選ぶ必要がある」という分析は正確であり、当方の指摘を単に採用せず検証した点は模範的である。

### 3.2 指摘範囲を超えた重要発見（§6 #3）

N-1（§6 の位置づけ変更）に対応する過程で、v0.2 は**当方が指摘していない実装上の落とし穴**を自ら発見している：

> **Python の `//` は floor のためそのまま使えない。`abs()` で商を取り符号を後付けする実装が必須**（§6 #3）

これは重要である。scc23 の FDIV は C の整数除算＝**ゼロ方向**だが、Python の `//` は **floor**。素朴に `//` を使うと C1（`-1.0/3.0`）で **-85 が -86 になり**、まさに §3.3 が警戒した「誤った期待値を自動生成する装置」が完成してしまう。設計段階でこれを明文化した価値は大きい。

### 3.3 negative test の追加（§4.1）

「意図的に誤実装した版で self-test が FAIL すること」を確認する negative test を追加した点も良い。self-test は「PASS すること」を確認するだけでは、**そもそも検出力があるのか**が保証されない。M-1 で露呈した問題（全 PASS だが非対称を検出できない）の再発を構造的に防ぐ設計である。

## 5. 申し送りへの意見（再掲・優先度）

**§7.5（ランタイム `_fmul`/`_fdiv` の丸めが `fold_binop_val` と一致するか）** が v0.2 で「Phase 2 以降」→「**C-2 完了後の短時間調査**」へ引き上げられたのは妥当。

理由を改めて記す。§1.6 のとおり負リテラルを含む式は畳み込まれずランタイム計算になるため、**同じ式がコンパイル時に畳み込まれるか実行時に計算されるかで結果が変わり得る**。仮に `_fmul`（アセンブラ実装）の丸めが `>>8`（floor）でなくゼロ方向だった場合、`-0.1 * 0.1` はコンパイル時 -3・実行時 -2 となり、**C-3 と同種の「文脈によって値が変わる」潜在バグ**である。C-2 で丸め仕様の正本が確定した今が、突き合わせる好機である。
