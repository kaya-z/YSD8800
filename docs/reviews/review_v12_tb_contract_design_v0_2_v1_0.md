## 1. 評価する点

### 1.1 M-1 の是正が「取消線＋理由」で行われている

§2.1 は ★旧 C-α を取消線で残したうえで、なぜ誤っていたか（`suppress_r` 側だけを見て CPU 側の状態遷移を見なかった）を記述★しています。KY41 の趣旨どおりで、★将来「なぜ同一アドレス条件が付いているのか」を読み解く人にとって決定的な情報★になります。単に書き換えるより価値が高い。

### 1.2 M-4 への対応が指摘を超えている

当方は「配置先にキャッシュ段を追加せよ」としか求めていませんが、§3.2 は ★**「監視する境界」列を新設し、境界ごとに監視対象の信号名まで列挙**★しました。さらに §3.2 の注記で ★「両者とも同一の契約 C-α' の検査器であり、DUT の外部契約の再実装ではない」★ と、★KY78（契約の実装が 2 箇所あると片方が古くなる）と矛盾しないことを自ら論証★しています。★検査器を 2 箇所に置くことと、契約を 2 箇所に実装することの違いを区別できている★点は重要です。

### 1.3 C-β を 2 本に分けた判断

§3.3.2 で C-β を ★C-β-1（受理サイクルで不定でないこと）★ と ★C-β-2（転送中 `we` が変化しないこと）★ に分割したのは正しい設計です。★C-β-2 が段4 の真因を直接捉える★という位置づけも的確で、`psram_ctrl` L165 が `we` をポート直接参照する（受理時ラッチではない）という実源根拠も添えられています。

## 2. M：必須修正（★新設された C-β／C-γ 記述に対する新規指摘★）

### M-5 ★★§3.3.3 の C-γ 検査器は契約違反を検出できない（実行して実証）★★

**本指摘が本レビューの主眼です。**

| 項目 | 内容 |
|---|---|
| 該当 | §3.3.3 C-γ の記述案 |
| ★問題★ | ```systemverilog```<br>`if (wr && (addr == CCR_HI_ADDR) && (ccr_r !== ccr_shadow))`<br>`    $error(...);`<br>`ccr_shadow <= ccr_r;`<br>```<br>`ccr_shadow` は★前サイクルの `ccr_r`★を保持する。書込が起きるサイクル N において、`ccr_r` は ★まだ古い値★（書込は NBA でサイクル末に反映）である。したがって ★`ccr_r === ccr_shadow` が成立し、条件が偽になる★。<br>変化が現れるのは N+1 だが、そのときには ★`wr` が既に 0★ なので条件は成立しない。<br>→ ★**どのタイミングでも発火しない**★ |
| ★実証★ | Icarus 12.0 で §3.3.3 の記述をそのまま実装し、★`$FF13` 書込で CCR が変化してしまう契約違反 DUT★ を接続して実行しました：<br><br>```<br>== 契約違反を注入: $FF13 に1サイクル書込 ==<br>== 終了: ccr_r=0100 （0100 なら違反が起きている）<br>```<br>★**CCR は 0000 → 0100 に変化しているにもかかわらず、`$error` は一度も出ませんでした。**★ |
| ★危険度★ | ★これは §7 R-1（assert が一度も発火せず「効いている気」になる）そのもの★です。しかも §3.5 の陽性試験を「`$FF13` に書いて CCR が変わらないことを確認する」という形で実施すると、★検査器が壊れていても TB は PASS する★ため、★陽性試験でも見抜けません★。陽性試験は ★**違反 DUT を用意して発火させる**★ 形でなければならない |
| ★対応（検証済みの修正案）★ | 書込を 1 サイクル遅延させ、★書込前後の CCR を比較★する：<br><br>```systemverilog```<br>`` `ifndef SYNTHESIS ``<br>`    logic [15:0] ccr_shadow;`<br>`    logic        wr_hi_d;`<br>`    always @(posedge cpu_clk or negedge cpu_rst_n) begin`<br>`        if (!cpu_rst_n) begin ccr_shadow <= '0; wr_hi_d <= 1'b0; end`<br>`        else begin`<br>`            // ★前サイクルが $FF13 書込なら、CCR が変化していないこと★`<br>`            if (wr_hi_d && (ccr_r !== ccr_shadow))`<br>`                $error("[CONTRACT C-g] CCR changed by write to $FF13: %h -> %h t=%0t",`<br>`                       ccr_shadow, ccr_r, $time);`<br>`            wr_hi_d    <= wr && (addr == CCR_HI_ADDR);`<br>`            ccr_shadow <= ccr_r;`<br>`        end`<br>`    end`<br>`` `endif ``<br>```<br><br>**当方の実行結果**：<br>```<br>ERROR: [CONTRACT C-g] CCR changed by write to $FF13: 0000 -> 0100 t=35<br>```<br>★同一の違反 DUT に対して正しく発火することを確認済み★です |

> ★皮肉な構図です。★ 本設計書は「TB が契約を再実装して間違う」問題を解こうとしていますが、★C-γ は**検査器そのものが間違っていて、しかも黙っている**★という、より悪い形をしています。★§3.5 の陽性試験（違反 poc を作って発火させる）を必須にした判断が、まさにこれを捕まえるためのものです。設計段階で捕まえられたのは幸運でした。★

## 3. C：確認事項

### C-3 `do_write` の `wdata` 保持と下げ順序

§4.2 に `do_write` が追加されたことを確認しました。前回 M-3 で挙げた 4 点のうち、★④「`cpu_mem_wdata` は `cpu_mem_wr` を下げた**後に**変更する」★ が守られているかを確認されたい。

C-β-2 は ★`we` の変化★ のみを監視しますが、`psram_ctrl` L165-166 は `we` と同時に ★`wdata` もポート直接参照★します（`mem[mem_idx] <= wdata;` は受理から `LATENCY_NORMAL` サイクル後に実行）。したがって ★`wdata` が転送中に変化すると、`we` は変化していないのに誤った値が書かれます★。

→ ★C-β-2 に `wdata` の監視を加える★ことを推奨します（`we_shadow` と同様に `wdata_shadow` を置く）。★書込側の契約は `we` だけでは閉じていません。★

## 4. N：推奨事項

### N-3 境界②の C-α' は、段3 メモ C-1 の検証器としても働く

§3.2 の境界②（キャッシュ段 ⇔ `cdc_bridge`）に置いた C-α' は、★フィル完了時に `fill_active_r` の解除が 1 サイクル遅れると発火します★。これは誤検出ではなく ★実際に同一要求（丸めたライン先頭アドレス）が再送されている★ことを意味するため、★発火するのが正しい★挙動です。

すなわち ★境界②の C-α' は、`v11_cache_stage3_design_memo` C-1（`fill_active_r` の deassert タイミング）が正しく実装されているかの検証器を兼ねます★。この効用を §3.2 に一行書いておくと、段5 で発火したときに ★「TB のせいか DUT のせいか」ではなく「deassert タイミングを見よ」★ と即座に切り分けられます。

### N-4 §3.5 の陽性試験を「違反 DUT を用意する」形に明記

M-5 の教訓として、★陽性試験は「違反する TB を作る」だけでなく「違反する DUT を作る」形も必要★です。

- C-α'：★違反する TB★（段4 の壊れた `do_read`）で発火させる ← 現行どおり
- C-γ：★違反する DUT★（`$FF13` 書込で CCR が変わる poc 版 `mmio_stub`）で発火させる

★C-γ は「TB が悪い」ことを検出する検査器ではなく「DUT が契約どおりか」を検出する検査器★であるため、陽性対照の作り方が C-α' と異なります。§3.5 の表に ★契約ごとに「何を壊して発火させるか」の列★を追加されたい。★これを明記していれば、M-5 は実装時に必ず捕まりました。★
