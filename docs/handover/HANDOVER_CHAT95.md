## 2. ★確定した真因（有識者訂正版・これが正）★

### 2.1 起票者解析の誤り
- 依頼書§3.3 の「emu23 は 発火・保持・再武装 の3層」は **誤り**。
- **irq_stat 再評価層は IRQ1(UART/STOR)専用であり、タイマー(IRQ0)には適用されない**（実源照合で確定）。
- emu23タイマーの発火判定は `YSD8002_tick`(emu23_v109.c L1556)一箇所のみ。

### 2.2 emu23タイマーの正しいモデル（2層）
1. **発火**: tick が1回だけ `irq_pending=1`(チケット)を置く → `next_irq_cycle=UINT64_MAX` で発火源が黙る
2. **再武装**: IRET/ACK が `next_irq_cycle=cycle+period` を再設定するまで沈黙
- 発火チケットは **CPU受理で消費**(`irq_pending=-1`)。
- ゆえに noack=CNT1 は「1回発火・受理・再武装されず二度と発火しない」= **ワンショットタイマー＋割込アクノリッジの正しい挙動**。実機非等価ではない。

### 2.3 RTL の真のバグ
- RTL の `irq_req_r` は「発火イベント(ワンショット)」と「割込線の生成/消滅」の2概念を1信号に潰している。
- `irq_req_r` を下ろす契機を **ACK(bit5)だけ**にした。しかし emu23 では割込線消滅(チケット消費)は**受理**で起きる。
- **★受理で割込線を下ろす経路が RTL に無いことが真のバグ★**。
- ACK は本来「再武装」契機であって「割込線クリア」契機ではない。両者を ACK 一発に短絡させた。
- MC6840 PTM 作法でも「割込フラグのクリア」と「タイマー再スタート」は別操作。

### 2.4 noack で値が分かれる理由
| emu23 (CNT1) | RTL (17069) |
|---|---|
| tick発火→irq_pending=1, next=MAX | fire→irq_req_r=1(レベルhigh) |
| 受理→irq_pending=-1(消費) | 受理→irq_req_r=1のまま(下がる経路なし) |
| IRET(ACKなし)→next=MAXのまま→二度と発火せず | IRET(ACKなし)→irq_req_r継続→EI復帰で即再発火 |
| CNT=1停止 ✓ | CNT=17069暴走 ✗ |

## 3. ★次工程(CHAT96)の残タスク★

有識者回答書 §8「実施順序の提案」に従う。

- **S1**: 案0-a / 0-b の選択を確定（設計レビュー・承認。原則43）。
  - **0-a(推奨)**: `fire`を1クロックパルス化＋`armed_r=0`で自己武装解除。`irq_timer_o`を「パルスで立てCPU受理でクリアするラッチ」に。CPUの割込受理(S_IRQ_ACCEPT到達)を `irq_ack` として YSD8002 に返す。
    - ★`irq_ack` は却下した `iret_pulse_o` とは本質的に異なる。iret_pulse_o は命令意味論の暴露で不正。irq_ack は割込プロトコルの一部(INTA相当)でバス上正当。MC6809のベクタフェッチ自体がアクノリッジの一形態。YSD8004経由でデバイスに伝える設計は正統。★
  - **0-b**: `armed_r=0`(自己武装解除)だけ入れ、割込ラッチは既存 S_IRQCHK 機構に委ねる。`irq_timer_o`は`fire`で1パルスのみ。CPU改修不要に近いが、パルスがS_IRQCHKと同期しないと取りこぼす懸念。要タイミング検証。
- **S2**: emu23は変更しない(黄金は正しい)。RTL(YSD8002 + 必要なら割込アクノリッジ経路)を修正。`v0_2_poc`→次版。
- **S3**: 統合TB再実行。★noack=CNT1 と ack=OUTC200 の**両方**★の回復を確認(回答書§6)。片方だけの回復で満足しないこと(原則63)。
- **S4**: Dhrystone絶対ゲート再確認(826/48405/P:20)。CPU改修が0-aで入る場合はV1/V2全82ベクタ再走(デグレゼロ)。
- **S5**: 文書はemu23無変更ゆえ黄金ref関連の再ベースライン不要。RTL版数と `fpga_source_version_ledger` のみ更新。
- **★案3を採らないため全リグレッションの再ベースラインは発生しない★**（案0の決定的優位）。

### 3.1 ack側FAIL(T2/T5 OUTC=33)の注意（回答書§6）
- 同根の部分: `irq_req_r`レベル立ちっぱなしで高頻度再受理→メインが割込に食われOUTC伸びず。
- ★別途確認: ack ハンドラが `$0023` を書いた「後」も OUTC=33 なら、ACK が `irq_req_r` を正しく下ろせていない可能性(L282到達不全)。案0適用後、ack側が OUTC=200 になるか再測。ならなければ ACK書込→irq_req_r=0 経路に別バグ。★
