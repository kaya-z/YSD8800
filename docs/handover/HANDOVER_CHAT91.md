## 2. ★★本チャットの最重要成果：設計欠陥の発見と是正★★

### 2.1 発見した欠陥

**実源根拠（`ysd8800_cpu_v0_1_FIXED.sv` L153-157）:**
```
S_IRQCHK での irq_in ラッチ条件に irq_pending==0(空)を追加。
修正: if (state==S_IRQCHK && irq_in != 3'd0 && irq_pending == 3'd0)
```

**★CPU は `irq_in` を「S_IRQCHK 状態のときだけ」サンプルする（レベル検出）★**

| 信号 | 形式（v0.1） | CPU のサンプル | 結果 |
|---|---|---|---|
| `irq1_o` (UART) | **レベル** | S_IRQCHK で拾える | ✅ |
| **`irq_timer_o`** | **★1クロックパルス★** | S_IRQCHK は命令境界にしか来ない（実CPI≒18） | **★18クロックに1回しか窓が無い → パルスが落ちる★** |

**★emu23 はなぜ動くのか★**
```c
L1591: if (cpu.irq_pending < 0 && YSD8002_tick(cpu.cycle)) cpu.irq_pending = 1;
```
emu23 は**命令境界で `YSD8002_tick()` を呼ぶ**ため、**パルスと窓が定義上必ず一致**する。
**RTL では両者が非同期であり、この等価性が崩れる。**

> **★これは「emu23 で動いたから RTL でも動く」が成立しない典型例である。★**
> **統合TB を書いてから発見していたら、「タイマーが発火しない」という症状に対し、**
> **結線・デコード・pending保護・cycle駆動のどこが原因か切り分け不能になっていた。**
> **（＝本チャットの KY で予測したとおりの罠。実装前レビュー＝原則43 が効いた）**

### 2.2 却下した代案（★次チャットで蒸し返さないこと★）

| 案 | 内容 | 却下理由 |
|---|---|---|
| **B-1e**<br>パルスストレッチ | `irq_timer_o` を N クロック保持し、命令境界に必ず重なるようにする | **★ユーザー指摘により却下★**<br>**CPU/バスクロックが変動すると危険。**<br>PSRAM ウェイト増・キャッシュ導入（BSRAM 温存＝将来計画）・PLL 比変更で1命令長が変動すると、**N の前提が静かに崩壊**。<br>**「タイマーが時々発火しない」という再現性の低い間欠故障**となり最悪。<br>**★ハンドシェイクで解くべき問題を、タイミングで誤魔化す設計だった★** |
| 案C<br>CPU 改修 | CPU 側でパルスをラッチ | **★却下★** CPU v0.5.8 は S5/S6 で 82ベクタ回帰 PASS 済み。触ると全回帰やり直し |
| **D13-B**<br>RTL も「1回で自己沈黙」 | `irq_req_r` を `armed_r` で AND する等 | **★却下★** ACK の意味が消え、**ACK なしでも動いてしまう**。<br>YUI OS が ACK を忘れてもテストが通る＝**偽合格**。V5 の中核（ACK 義務）を検証不能にする |

### 2.3 ★採用した設計（D12 = 案 B-1a）【ユーザー承認 2026-07-14】★

**レベル＋ハンドシェイク = MC6840 PTM の作法。★クロック非依存★**

```
fire (cycle >= cnt) ──set──> irq_req_r = 1  ★立ちっぱなし★
                              armed_r  = 0  （自己武装解除・v0.1 と同じ）
                                  │
                        CPU が S_IRQCHK でレベル検出 → 受理 → ★IE=0★ → ハンドラへ
                                  │
                    ハンドラ: TCR ← $0023 ──clear──> irq_req_r = 0  ★ACK★
                                          ──同時に──> armed_r  = 1  ★再武装★
                                          ──同時に──> cnt_r = cycle + period
                                  │
                                IRET → IE=1 復帰。irq_req_r は既に 0 → 再受理されない
```

**★受理中は IE=0 なので、`irq_req_r` が立ちっぱなしでも多重受理は起きない。★**
**★ACK を IRET より前に実行する限り、クロック非依存で正しく動く。★**

## 4. ★★YSD8002 単体TB 19/19 ALL PASS（回帰なし）★★

### 4.1 デバッグ報告（debug_style_guide 準拠）

**【事象】** v0.2_poc（レベル化）に対し単体TBが **T2/T3/T4/T5/T6 の5本 FAIL**（`fire_count` が 204〜206 に爆増）。

**【仮説】** RTL のバグではなく、**TB の観測方法が v0.1（1クロックパルス）前提**であるため。レベルだと ACK まで毎クロック +1 される。

**【検証】** TB L71 を実源確認 → `if (rst_n && irq_timer) fire_count++;`（**毎クロック計数**）を確認。**立ち上がりエッジ検出**に変更。

**【結果】** **19/19 ALL PASS**。**★RTL は無修正のまま、TB の観測方法のみの変更で全 PASS 回復★**
→ **仮説が正しかったことが機械的に立証された。**

**【傍証（★重要★）】**
- `fire_count` が 204→206（**+2 のみ**）＝ **ACK で一度落ちて次周期まで静か** ＝ **ACK クリアが動作している**
- T3「no refire w/o ACK」= **1** ＝ **ACK なしでは *再発火* しない**（`armed_r` の自己武装解除は健在）
- T5「periodic fire (2nd)」= **2** ＝ **TCR-ACK で再武装し周期発火**

### 4.2 回帰性

| 項目 | v0.1 | v0.2_poc | 判定 |
|---|---|---|---|
| 単体TB 19本 | 19 PASS | **19 PASS** | ✅ **回帰なし** |
| **期待値（1/1/1/2/2）** | — | **★同一（書き換えなし）★** | ✅ |
| 変更箇所 | — | **TB の観測方法のみ**（パルス計数→エッジ計数） | ✅ RTL 論理は等価 |

> **★「発火回数」という論理的性質は完全に保存されている。変わったのは *割込線の保持形態* だけである。★**
> **これは B-1a が「論理を変えず、CPU が拾える形にしただけ」であることの証明である。**

## 10. ★kaizen 原則 追加候補（S10 で登録）★

### 原則78: 「デバイスごとにアドレスデコードのビット幅は違う。使い回すな」
YSD8001($FC80-$FC87, 8バイト) は 3bit で足りるが、YSD8002($FC90-$FC9F, **16バイト**) は **4bit** 要る。
先行デバイスの `assign ys1_off = mmio_addr[2:0];` をコピペすると V3.7 BUG-1 が再演する。
**→ アドレス定数は必ず実源から機械導出し、衝突表を作ってからビット幅を決めよ（KY44）。**

### 原則79: 「レジスタ書込が【いつから効くか】を実源で確認せよ」
`PERIOD_LO` 書込は `period`/`cycles_per_irq` を更新するが **`next_irq_cycle` は更新しない**（emu23 L741-744）。
→ PERIOD は**次回 rearm から**効き、**初回発火には効かない**。
**「レジスタに書いた ≠ 即座に反映される」。設定レジスタは【反映タイミング】まで含めて仕様である。**

### 原則80: 「アセンブルが通っても、実行が正しいとは限らない」
`.org $0000` に割込ベクタ[0]を置いた。**$0000 は【リセットベクタ】**であり暴走した。
**ツールが通すことは、意味が正しいことを保証しない。**
**同様に、古いバイナリが残っていると【ビルド失敗しても偽の実行結果が出る】。**
**→ ビルド前に成果物を rm し、ビルド成否は【生成物の存在】で判定せよ。**

### ★原則81（新規・CHAT91）: 「シミュレータで動いた ≠ RTL で動く。【サンプリング形態】を確認せよ」★

**emu23 は割込を「命令境界でポーリング」する。**
```c
L1591: if (cpu.irq_pending < 0 && YSD8002_tick(cpu.cycle)) cpu.irq_pending = 1;
```
**→ デバイスの「発火イベント」と CPU の「サンプル窓」が【定義上必ず一致】する。**

**しかし RTL では両者は【非同期】である。**
CPU は `irq_in` を **S_IRQCHK 状態でしかサンプルしない**（実CPI≒18 → 18クロックに1回しか窓が無い）。
**1クロックパルスで割込を出すと、ほぼ確実に取りこぼされる。**

> **★「emu23 で動いたから RTL でも動く」は成立しない。★**
> **★シミュレータは【イベント駆動】、RTL は【クロック駆動】であり、**
> **信号の【保持形態（パルス/レベル）】が等価性の成否を決める。★**
>
> **デバイス→CPU の非同期な要求信号は、必ず【レベル＋ハンドシェイク】にせよ。**
> **受け手が受理するまで下がってはならない。これがクロック非依存の唯一の解である。**
> **（MC6809 の IRQ/FIRQ、MC6840 PTM のステータスビットはすべてこの形）**

### ★原則82（新規・CHAT91）: 「タイミングで誤魔化すな。ハンドシェイクで解け」★

**パルスストレッチ（N クロック保持して命令境界に重なるようにする）は【禁じ手】である。**

| 変動要因 | 破綻の仕方 |
|---|---|
| PSRAM ウェイト増（tRC・リフレッシュ） | 1命令長が N を超える → 取りこぼし |
| キャッシュ導入（BSRAM 温存＝将来計画） | 命令クロック数が可変になり N の前提が崩壊 |
| CPU/PSRAM クロック比の変更（PLL 設定） | 同上 |
| MMU ミス・アラインメント例外 | 命令が伸びる |

**→ N は「たまたま今のクロック比で通る値」でしかない。**
**★壊れ方は「タイマーが時々発火しない」という再現性の低い間欠故障であり、最悪のバグである。★**

> **★論理で解けるものをタイミングで解くな。★**
> **「N クロック待てば大丈夫」は設計ではなく【祈り】である。**
> **クロック周波数・ウェイト・キャッシュ構成が変わっても成立する設計だけが正しい。**
