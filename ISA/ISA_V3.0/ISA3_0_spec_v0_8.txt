YSD8800 ISA3.0 仕様書 V0.4
========================================
Version: 0.4
Status: フリーズ版（命令仕様、レジスタ仕様、ABI、スタック仕様が確定）
Date: 2026-04-09


1. 設計方針
========================================

1.1 基本原則
- ISA2.2との完全バイナリ互換を維持
- 既存プログラム（kernel.asm等）は変更なしで動作
- 拡張プレフィックス（0x1F）配下で拡張機能を提供
- シンプルなハード実装を維持（単サイクル～軽量パイプライン想定）

1.2 設計焦点
- マルチレジスタ対応による関数呼び出し効率化
- ユーザ/カーネルスタック分離による保護強化
- コンパイラABI最適化との親和性向上


2. データ幅仕様（確定）
========================================

2.1 基本データ幅
- レジスタ幅：16bit
- メモリデータ幅：16bit（LDW/STW）
- スタック操作単位：16bit（PUSH/POP で 16bit 単位）
- 8bit データアクセス：LDB/STB で対応

2.2 アドレッシング
- メモリアドレス：16bit（64KB論理空間）
- MMU 対応で最大1MB物理空間に拡張可能
- すべての16bitアクセスに整列制約あり（奇数アドレスはアラインメント例外）

2.3 メモリアライメント仕様（確定）

【16bit（ワード）アクセスのアライメント】

16bitデータアクセス（LDW, STW, PUSH, POP, 割り込み処理等）は、
以下のアライメント要件を満たす必要がある：

  ✅ 要件：アドレス & 0x0001 = 0 （偶数アドレス）
  
例：
  - Address 0x0000: OK
  - Address 0x0002: OK
  - Address 0x0004: OK
  - Address 0x0001: ❌ アラインメント例外（irq3）
  - Address 0x0003: ❌ アラインメント例外（irq3）

【アライメント例外（IRQ ID=4）】

奇数アドレスへの16bitアクセスが試みられた場合：

  CPU は以下を実行する：
    irq_pending = 4（align 例外）
    割り込み受理条件を確認
    （IE=1 であれば即座に受理）

【8bit アクセスのアライメント】

LDB/STB は奇数アドレスでも実行可能（アライメント制約なし）

【ハードウェア実装上の注記】

- メモリバスが16bit であり、アドレス0の偶数要件がある
- アライメント違反のハード検知が推奨（性能向上、デバッグ容易化）
- ソフトウェア（コンパイラ/リンカ）は、
  スタック操作が常に偶数アドレスで行われることを保証する

2.4 スタックポインタ（SP/USP）の範囲と制約

【SP/USP の有効範囲】

SP（カーネルスタック）：
  初期値：0xFC7E
  通常の動作範囲：0xF800 ～ 0xFC7E

USP（ユーザスタック）：
  初期値：0xF7FE
  通常の動作範囲：0xE000 ～ 0xF7FE

【アンダーフロー/オーバーフロー】

SP/USP がスタック範囲を超えた場合：

  ✅ 動作：制約なし（未定義動作）

  - ハード側はチェックを行わない
  - 範囲外のメモリアクセスが発生する可能性あり
  - ソフトウェア（OS/コンパイラ）が範囲管理を責務

【理由】

- FPGA実装簡潔化（範囲チェック削除）
- OS側で明示的にスタック保護が行える
- パフォーマンス最優先設計



2.4 メモリエンディアン仕様（確定）

【エンディアン定義】

YSD8800 は **リトルエンディアン** を採用

定義：
  16bit データをメモリに格納する場合、
  下位バイトが低アドレスに格納される

例：
  16bit値 0xABCD をアドレス 0x1000 に格納する場合

  ✅ リトルエンディアン（YSD8800）:
    [0x1000] = 0xCD （下位バイト）
    [0x1001] = 0xAB （上位バイト）

  ❌ ビッグエンディアン（YSD8800では非対応）:
    [0x1000] = 0xAB （上位バイト）
    [0x1001] = 0xCD （下位バイト）

【実装上の注記】

- emu22/emu30 はリトルエンディアンで実装
- FPGA実装（SystemVerilog）もリトルエンディアン必須
- クロスプラットフォーム開発時は、エンディアン変換が必要な場合がある

3.2 FLAGS レジスタ仕様（確定）

bit | 名称 | 説明 | 更新タイミング
----|------|------|---------------
0   | Z    | ゼロフラグ（結果=0で1） | 演算・CMP命令後
1   | N    | ネガティブフラグ（結果<0で1） | 演算・CMP命令後
2   | C    | キャリーフラグ（桁上がりで1） | 演算・CMP命令後
3   | V    | オーバーフローフラグ（溢れで1） | 演算・CMP命令後
4   | IE   | 割り込みイネーブル（1で有効） | EI/DI/IRET
5   | UM   | (予約) ユーザモード判別用 | 将来拡張
6-15| -    | (予約) | -

ビット配置の詳細：
  bit0: Z （Zero）
    - 演算結果が 0 の場合に 1
    - CMP/CMPI でも設定

  bit1: N （Negative）
    - 演算結果が負（bit15=1）の場合に 1
    - 符号あり演算でのフラグ

  bit2: C （Carry）
    - 加算で桁上がり、減算で桁借りが発生した場合に 1
    - 符号なし演算、シフト演算で更新可能

  bit3: V （Overflow）
    - 符号あり演算で数値範囲を超えた場合に 1
    - 符号あり整数演算の結果判定に使用

  bit4: IE （Interrupt Enable）
    - 1 で割り込み受け入れ可能
    - 0 で割り込みマスク

  bit5: UM （User Mode）
    - ISA3.0では予約（常に 0）
    - ISA3.1以降でユーザ/カーネルモード判別に使用予定

注記：
  - Z, N, C, V は算術・論理演算で自動更新
  - CMP/CMPI は FLAGS を更新するが、他のレジスタは変更なし
  - IE は割り込み受け入れ制御（EI=1で有効、DI=0で無効）
  - SHL/SHR/SAR はシフト出力ビットを C に格納（実装依存）

【フラグビット更新の詳細】

【重要：未更新フラグビットの扱い】

任意の命令で FLAGS を更新する場合、更新されないビットは
**元の値をそのまま保持する**（クリアや不定値にしない）

例：
  AND命令で Z, N のみ更新
    → C（キャリー）は前の値をそのまま保持
    → V（オーバーフロー）は前の値をそのまま保持
  
  MOV命令で Z, N のみ更新
    → C, V は変更されない（前の値をそのまま）

**重要な原則：**
  命令で更新されないフラグビットは、**値を保持する**
  （前回の値がそのまま保持される）

【Z（ゼロフラグ）の更新詳細】
  - ALU演算後、結果=0 なら Z=1
  - データ転送後、読み込んだ値=0 なら Z=1
  - 比較後、rD-rS=0 なら Z=1

**N（ネガティブフラグ）:**
  - ALU演算後、結果の bit15=1 なら N=1
  - データ転送後、読み込んだ値の bit15=1 なら N=1
  - 比較後、rD-rS の bit15=1 なら N=1

**C（キャリーフラグ）:**
  - ADD/ADDI: 加算で桁上がり発生なら C=1
  - SUB/SUBI: 減算で桁借り発生なら C=1
  - AND/OR/XOR系: C=0（リセット）
  - SHL/SHLI: 左シフト時、最後に左に押し出されたビット
  - SHR/SHRI: 右シフト時、最後に右に押し出されたビット
  - SAR/SARI: 右シフト時、最後に右に押し出されたビット
  - CMP/CMPI: 比較（減算）の桁借りで C=1

**V（オーバーフローフラグ）:**
  - ADD/ADDI: 符号あり加算で溢れ発生なら V=1
  - SUB/SUBI: 符号あり減算で溢れ発生なら V=1
  - AND/OR/XOR系: V 不変（更新しない）
  - シフト: V 不変
  - CMP/CMPI: 比較（減算）の溢れで V=1

3.3 USP（ユーザスタックポインタ）- 特殊レジスタ

- 汎用レジスタ番号を持たない（非アドレッサブル）
- PUSH/POP/PUSHM の対象外
- XCHG_SP 命令でのみアクセス可能
- ユーザランド実行時にスタック保護を提供
- ISA3.0では SP/USP の2つのスタックポインタが存在
  * SP: カーネルスタック（割り込みハンドラ等）
  * USP: ユーザスタック（アプリケーション）

【USPと割り込みの関係（確定）】

**重要：割り込み発生時は常にSPを使用し、USPは影響を受けない**

詳細：
  1. ユーザランド実行中に割り込み発生
     → CPU は自動的に PC, FLAGS を **SP** にpush
     → USP は変更されない

  2. 割り込みハンドラ実行中
     → すべてのスタック操作は **SP** を使用
     → USP は非アクティブ

  3. 割り込みハンドラから復帰（IRET）
     → スタックから PC, FLAGS を復元
     → USP はそのまま（変更なし）

  4. ユーザランド復帰前に XCHG_SP を実行
     → SP ↔ USP が交換
     → ユーザスタックに切り替え

【理由】

- カーネルモードとユーザモードを厳密に分離
- 割り込みハンドラはカーネルの責任で実行
- ユーザランドのスタック状態を保護

3.4 PC（プログラムカウンタ）

- 読み取り専用（直接変更禁止）
- JMP/JSR/IRET でのみ変更可能
- 間接JSRでは「PC_next」（次の命令アドレス）をスタックにpush

3.5 SP（スタックポインタ）とオーバーフロー/アンダーフロー（確定）

SP は通常の16bitレジスタとして動作：

  - PUSH/POP/PUSHM/POPMで自動更新
  - 値の範囲：0x0000-0xFFFF

【スタック操作のオーバーフロー/アンダーフロー】

SP がメモリ範囲（0x0000-0xFFFF）を超える場合：

  推奨実装：**チェックなし（未定義動作）**

  - SP -= 2 で SP < 0x0000 の場合：ラップアラウンド
    例：SP = 0x0000; SP -= 2 → SP = 0xFFFE （16bit 循環）
  
  - SP += 2 で SP > 0xFFFF の場合：ラップアラウンド
    例：SP = 0xFFFF; SP += 2 → SP = 0x0001 （16bit 循環）

【理由】

- シンプル設計（チェック回路不要）
- FPGA規模最小化
- ソフトウェア（OS/コンパイラ）が SP 範囲管理を保証

【ソフトウェア側の責務】

- メモリマップに基づいて SP初期値を設定
- スタック領域のサイズを計算し、溢れないことを保証
- 必要に応じて警告出力（デバッグ用）


4. 命令フォーマット
========================================

4.1 基本フォーマット（ISA2.2継承）

拡張プレフィックスなし：
  byte0: opcode (8bit)
  byte1: rD(4bit) | rS(4bit)
  byte2-3: imm16 (必要な命令のみ)

拡張プレフィックス（opcode=0x1F）あり：
  byte0: 0x1F (拡張プレフィックス)
  byte1: sub-opcode (8bit) ← 新しい sub-opcode 配置ルールに従う
  byte2: (命令により異なる)
  byte3-4: imm16 (必要な命令のみ)

4.2 未定義opcode の扱い（確定）

【未定義命令の動作】

ISA3.0で定義されていない opcode が実行された場合：

  ✅ 動作：NOP（何もしない）として扱う

  - PC は自動で進む（1命令分）
  - FLAGS は変更されない
  - レジスタは変更されない
  - 割り込みは発生しない
  - 例外トラップなし

【理由】

1. **拡張性**：将来のISA拡張で新命令を追加可能
2. **実装簡潔性**：例外処理を最小化
3. **互換性**：ISA3.1等で新命令追加時、
   古いコード実行時も動作継続可能（ただし新機能は使用不可）

【注記】

- コンパイラ/アセンブラは、未定義命令を生成しないこと
  （デバッグ困難になる）
- シミュレータ/エミュレータは、未定義命令実行時に
  ワーニングメッセージを出すことが推奨

例：
  未定義 opcode 0x07 が実行された場合
  → PC += 1 （命令長は1byteと仮定）
  → 次命令へ進行

【未定義動作の定義（重要）】

以下の情況も **例外を発生せず、未定義動作として扱う**：

1. **不正な PUSHM/POPM mask**
   - bit12-15 が 0 でない場合
   - 例：mask=0x1234 （bit12-15 = 0x1）
   - 動作：上位ビットは無視、下位12ビットのみ処理

2. **未アラインメモリアクセス**
   - 16bit アクセスが奇数アドレスの場合
   - 動作：アラインメント例外（irq4）を発生
   - 例外トラップ：irq4 ハンドラに分岐
   - 例外なしモード：未定義動作（結果不定）

   推奨：
     ソフトウェア（コンパイラ/リンカ）は
     スタック操作が常に偶数アドレスで行われることを保証

3. **未定義な sub-opcode （0x1F prefix 配下）**
   - 例：0x1F 0x60 （0x60 は定義外）
   - 動作：NOP 扱い（例外なし）

4. **その他の不正な命令形式**
   - 動作：NOP 扱い（例外なし）

【実装上のガイドライン】

シミュレータ/エミュレータ：
  - 未定義動作検出時に警告メッセージ出力
  - 実行継続（NOP扱い）

FPGA実装：
  - 例外トラップ回路は不要（コスト削減）
  - デバッグモード追加で、不正命令検出・報告可能


4.4 sub-opcode 空間配置（0x1Fプレフィックス配下）

0x00-0x1F : 汎用レジスタ操作
  - PUSH rS / POP rD
  - XCHG_SP
  - (予約)

0x20-0x2F : スタック操作
  - PUSHM mask
  - POPM mask
  - (予約)

0x30-0x3F : シフト/ビット操作
  - SHLI rD, #imm4
  - SHRI rD, #imm4
  - SARI rD, #imm4
  - (予約)

0x40-0x4F : 制御系（JSR拡張など）
  - JSR rS (間接)
  - (予約)

0x50-0x5F : 特殊レジスタ（USP等）
  - (予約: 将来のUSP直接操作等）

0x60-0x7F : 予約（将来ALU拡張）

0x80-0xFF : 予約（大規模拡張）


5. opcode 空間全体（ISA2.2+3.0）
========================================

range    | 用途
---------|---------------------------
0x00-0x1E| ISA2.2: Control/System, 基本命令
0x1F     | 拡張プレフィックス → sub-opcode 0x00-0xFF
0x20-0x7F| ISA2.2: Data Transfer, Arithmetic, Branch


6. ISA2.2互換命令セット（完全継承）
========================================

6.1 Control/System（0x00-0x06）
  0x00: NOP
  0x01: HALT
  0x02: EI  （割り込みイネーブル）
  0x03: DI  （割り込みディセーブル）
  0x04: IRET （割り込みリターン）
  0x05: SYSCALL imm16
  0x06: BRK （デバッグトラップ）

6.2 Data Transfer（0x20-0x3F）
  0x20: MOV rD, rS
  0x21: LDW rD, #imm16
  0x22: LDW rD, [imm16]
  0x23: STW rS, [imm16]
  0x24: LDW rD, [rS]
  0x25: STW rS, [rD]
  0x26: LDW rD, [X + imm16]
  0x27: STW rS, [X + imm16]
  0x1F 0x10-0x17: LDB/STB（詳細はISA2.2参照）

6.3 Arithmetic/Logic（0x40-0x5F）
  0x40: ADD rD, rS
  0x41: ADDI rD, #imm16
  0x42: SUB rD, rS
  0x43: SUBI rD, #imm16
  0x44: CMP rD, rS
  0x45: CMPI rD, #imm16
  0x50: AND rD, rS
  0x51: ANDI rD, #imm16
  0x52: OR rD, rS
  0x53: ORI rD, #imm16
  0x54: XOR rD, rS
  0x55: XORI rD, #imm16
  0x56: NOT rD
  0x57: SHL rD, rS  （レジスタでシフト量指定）
  0x58: SHR rD, rS
  0x59: SAR rD, rS

6.4 Branch/Flow（0x60-0x6F）
  0x60: JMP rel16
  0x61: BEQ rel16
  0x62: BNE rel16
  0x63: BLT rel16  （符号あり）
  0x64: BGE rel16  （符号あり）
  0x68: JSR imm16  （直接）
  0x69: RET

【RET 命令の詳細仕様】

命令: RET
format: 0x69
動作:
  PC = mem[SP]
  SP = SP + 2

詳細説明：
  - スタックから PC を読み出す
  - SP を+2進める
  - PC に読み出した値を設定
  - 次命令の取得が行われる

用途: 関数呼び出しからの復帰（JSR/JSR rS で push された PC を復元）

【重要な注記】
JSR/JSR rSで PC_next が push されるため、
RET で正しく次の命令に復帰する。

スタック動作例：
  関数呼び出し時:
    JSR func
      → mem[SP] = PC_next
      → SP -= 2
  
  関数内の RET:
      → PC = mem[SP]      （PC_next を復元）
      → SP += 2

【IRET 命令の詳細仕様】

命令: IRET
format: 0x04
動作（順序厳密）:
  FLAGS = mem[SP]     ← 最初に FLAGS を復元
  SP = SP + 2
  PC = mem[SP]        ← その次に PC を復元
  SP = SP + 2

順序が重要：
  ❌ 誤り：PC を先に復元してから FLAGS
  ✅ 正確：FLAGS → PC の順

詳細説明：
  1. スタックトップから FLAGS を読み出す
  2. SP を+2進める
  3. スタックから PC を読み出す
  4. SP をさらに+2進める
  5. PC に読み出した値を設定
  6. 次命令の取得が行われる

用途: 割り込みハンドラからの復帰（割り込み受理時に push された FLAGS/PC を復元）

【スタック構造】

割り込み受理時のスタック push 順序：
  SP -= 2 → mem[SP] = PC
  SP -= 2 → mem[SP] = FLAGS  （スタックトップ）

復帰時の pop 順序（IRET）：
  FLAGS = mem[SP]           （スタックトップから）
  SP += 2
  PC = mem[SP]              （その次から）
  SP += 2

結果：スタックはリセットされ、割り込み前の状態に完全復帰

【重要：RET と IRET の区別】

RET:  PC のみ復元（関数復帰用）
IRET: FLAGS と PC を復元（割り込み復帰用）
      復帰順序は固定（FLAGS → PC）

【重要：RET と IRET の区別】

スタックに以下のように混在する場合、呼び出し元が適切に復帰できる：

  例：割り込みハンドラから通常関数に RET で復帰

    [FLAGS] ← 割り込みで push
    [PC]    ← 割り込みで push
    [PC]    ← JSR で push (関数呼び出し)
    ...
    
  関数の RET：PC のみ復元
    PC = [SP-4]  (相対的)
    SP = SP + 2
    
  その後 IRET：FLAGS, PC を復元
    FLAGS = [SP-2]
    PC = [SP]
    SP = SP + 4

注記：
  - RET は JSR/JSR rS で push された PC のみを復元
  - IRET は割り込み受理時に push された FLAGS と PC を復元
  - 両者の順序が異なる（IRET は FLAGS → PC）

注記：
  - ISA2.2の命令セットは完全互換（変更なし）
  - ISA3.0では新しい命令を拡張プレフィックス配下に追加


7. ISA3.0新規命令
========================================

【ISA3.0で追加される新規命令の一覧】

✅ ISA2.2互換命令（既存）：
  - MOV rD, rS （汎用レジスタ転送）：任意のレジスタ組み合わせに対応拡張

✅ ISA3.0で追加：
  1. PUSH rS / POP rD （汎用スタック操作）
  2. XCHG_SP （スタックポインタ交換）
  3. SHLI / SHRI / SARI （即値シフト）
  4. PUSHM / POPM （複数レジスタ操作）
  5. JSR rS （間接JSR）
  6. MOV X, SP （スタック→インデックス転送）
  7. MOV SP, X （インデックス→スタック転送、制約あり）

計9個の拡張命令。

7.1 汎用PUSH/POP（sub-opcode 0x00-0x01）

命令: PUSH rS
format: 0x1F 0x00 rS?? (byte2の上4bit)
動作:
  SP = SP - 2
  mem[SP] = rS
制約:
  - rS は reg_id (0-11) を指定可能
  - ISA2.2の PUSH A/B/X との互換性維持

命令: POP rD
format: 0x1F 0x01 rD?? (byte2の上4bit)
動作:
  rD = mem[SP]
  SP = SP + 2
制約:
  - rD は reg_id (0-11) を指定可能
  - ISA2.2の POP A/B/X との互換性維持

7.2 スタックポインタ交換（sub-opcode 0x02）

命令: XCHG_SP
format: 0x1F 0x02
動作:
  temp = SP
  SP = USP
  USP = temp
副作用: なし（FLAGS不変）
用途:
  - システムコール時のスタック切り替え
  - カーネル/ユーザランド間の保護

【XCHG_SPのアトミック性（重要）】

XCHG_SP は **不可分（アトミック）** 操作である：

  - 実行中に割り込みが発生しない
  - 途中状態（SP と USP が部分的に交換された状態）が
    外部に観測されない
  - 割り込みが待機している場合、XCHG_SP 実行後に
    割り込み判定が行われる

理由：
  - ユーザランド/カーネル間のスタック分離保護が必須
  - 途中で割り込まれると、不正なスタック状態で
    割り込みハンドラが実行される危険

実装上の注記：
  - CPU内部で XCHG_SP 実行中は割り込み禁止（IE状態に関わらず）
  - 実装は XCHG_SP を1マイクロ命令で実行することを推奨
  - または、割り込み遅延を使用（次命令まで割り込み遅延）


7.3 即値シフト命令（sub-opcode 0x30-0x32）

命令: SHLI rD, #imm4
format: 0x1F 0x30 rD imm (byte2の上4bit=rD、下4bit=imm)
動作:
  imm_val = imm & 0x0F    ← 下4bit のみ有効（0-15）
  rD = rD << imm_val
  FLAGS.Z = (rD == 0) ? 1 : 0
  FLAGS.N = (rD < 0) ? 1 : 0

imm範囲: 0-15（4bit）

命令: SHRI rD, #imm4
format: 0x1F 0x31 rD imm
動作:
  imm_val = imm & 0x0F    ← 下4bit のみ有効（0-15）
  rD = rD >> imm_val  （論理右シフト）
  FLAGS.Z = (rD == 0) ? 1 : 0
  FLAGS.N = 0

imm範囲: 0-15（4bit）

命令: SARI rD, #imm4
format: 0x1F 0x32 rD imm
動作:
  imm_val = imm & 0x0F    ← 下4bit のみ有効（0-15）
  rD = rD >> imm_val  （算術右シフト、符号拡張）
  FLAGS.Z = (rD == 0) ? 1 : 0
  FLAGS.N = (rD < 0) ? 1 : 0

imm範囲: 0-15（4bit）

用途:
  - 小規模乗除の効率化
  - ISA2.2の SHL/SHR/SAR は rS レジスタでシフト量指定
  - ISA3.0では即値化により、より効率的なコード生成が可能

【即値シフトの重要な制約】

imm は常に下位4bitのみが有効：
  実効シフト量 = imm & 0x0F （0-15の範囲）

例：
  SHLI r0, #20  （imm=20 = 0x14）
  → 実効シフト量 = 0x14 & 0x0F = 4（20 ではなく 4 ビット）
  → r0 = r0 << 4

理由：
  - ハードウェア（シフタユニット）は 4bit imm で十分（0-15シフト）
  - 16ビット以上のシフトは現実的に不要
  - FPGA規模最小化


7.4 複数レジスタ操作（sub-opcode 0x20-0x21）

命令: PUSHM mask
format: 
  byte0: 0x1F
  byte1: 0x20
  byte2: mask_low (下8bit)
  byte3: mask_high (上8bit)
  結果: 16bit mask

動作（逐次更新）:
  for bit_pos = 15 down to 0:
    if (mask & (1 << bit_pos)):
      SP = SP - 2          ← 逐次更新（各レジスタごと）
      mem[SP] = reg[bit_pos]

  注記：SP は各レジスタpush ごとに更新される
        まとめて更新ではない
  
【メモリ書き込み順序の可視性】

PUSHM の実行は、以下の順序で メモリ書き込みが
可視的に発生することを保証する：

  例：mask = 0x000F （R0-R3 をpush）
    
    1. SP -= 2; mem[SP] = R3  ← R3 が最初に書き込まれる
    2. SP -= 2; mem[SP] = R2  ← R2 が次に書き込まれる
    3. SP -= 2; mem[SP] = R1  ← R1
    4. SP -= 2; mem[SP] = R0  ← R0 が最後に書き込まれる
  
    結果スタック（低アドレスから）：
      [R0]
      [R1]
      [R2]
      [R3]  ← SP

  重要：この順序は可視的（メモリアクセスが分散）

命令: POPM mask
format:
  byte0: 0x1F
  byte1: 0x21
  byte2: mask_low
  byte3: mask_high

動作（逐次更新）:
  for bit_pos = 0 to 15:
    if (mask & (1 << bit_pos)):
      reg[bit_pos] = mem[SP]
      SP = SP + 2          ← 逐次更新（各レジスタごと）

  注記：SP は各レジスタpop ごとに更新される
        まとめて更新ではない

可逆性保証（重要）:
  同一mask で以下の操作を行った場合、
  全レジスタは元の値に復元されることを保証する：

    PUSHM mask
    ; ... 処理（レジスタ変更なし）
    POPM mask

  前提条件：
    - mask が変わらない
    - 処理中に mask で指定されたレジスタを変更しない
    - mask のbit3(SP)は0であること

mask定義（16bit）：
  bit0: R0 (A)
  bit1: R1 (B)
  bit2: R2 (X)
  bit3: R3 (SP) - **使用禁止**（ハード実装は無視する）
  bit4: R4 (PC) - 非推奨（通常コードでは使用禁止）
  bit5: R5 (FLAGS) - 非推奨（通常コードでは使用禁止）
  bit6: R6 (T0)
  bit7: R7 (T1)
  bit8: R8 (T2)
  bit9: R9 (T3)
  bit10: R10 (S0)
  bit11: R11 (S1)
  bit12-15: **予約（必ず0であること）**

【mask上位ビット制約の厳格化】

PUSHM/POPM の mask には以下の制約がある：

  ✅ 必須：bit12-15 は 0 でなければならない

  実装の扱い：
    - 厳密実装：bit12-15 が 0 でない → エラー（実装依存）
    - 簡潔実装：bit12-15 を無視（推奨）

  コンパイラ責務：
    → mask の bit12-15 は常に 0 を出力する

【例】

  ✅ 正しい：mask = 0x0FFF（bit12-15 = 0）
  ❌ 不正：mask = 0xFFFF（bit12-15 = 1）
         → 未定義動作（例外なし）

制約:
  - mask=0 は NOP
  - bit3(SP)は操作禁止（実装は無視する）
  - bit4(PC)は非推奨（IRET で復帰すべき）
  - bit5(FLAGS)は通常コードで禁止（コンパイラは生成しない）
  - bit12-15は予約で、ここにセットされたビットは0であること
    → 上位4ビットに意味あるビットがセットされた場合、
      動作は未定義（実装が無視してもよい）

【FLAGS更新表の凡例】

✓ : フラグを更新する
- : フラグを更新しない（前回の値を保持）

例：
  AND命令：Z=✓, N=✓, C=-, V=-
  → Z, N は更新
  → C, V は前回の値をそのまま保持

【重要な注記：mask のビット12-15（予約）に関する制約】

PUSHM/POPM の mask パラメータで、bit12-15 に 1 がセットされている場合：

  ❌ 不正な mask（予約ビット使用）
  
  - bit12-15 は **必ず 0 であること**
  - 0 でない mask が与えられた場合：
    → 動作は **未定義**
    → 例外を発生しない（NOP扱い、または無視）

例：
  PUSHM 0x1234 （bit12=1 が誤ってセット）
  → 不正（予約ビット使用）
  → 動作未定義（実装依存）

実装上の推奨：
  - アセンブラ: bit12-15 のセット時、警告出力
  - エミュレータ: bit12-15 のセット時、警告出力
  - FPGA: 予約ビットを無視する（簡潔実装）


7.5 間接JSR（sub-opcode 0x40）

命令: JSR rS
format: 0x1F 0x40 rS?? (byte2の上4bit)
動作:
  SP = SP - 2
  mem[SP] = PC_next
  PC = rS

【PC_next の厳密な定義（重要）】

PC_next = 現在実行中命令の最終バイトのアドレス + 1

例：
  命令フェッチ時の PC = 0x1000
  
  1byte命令（opcode=0x60）
    byte0 @ 0x1000: 0x60
    → 最終バイト = 0x1000
    → PC_next = 0x1001
  
  3byte命令（0x1F prefixで2byte sub-opcode）
    byte0 @ 0x1000: 0x1F
    byte1 @ 0x1001: 0x40
    byte2 @ 0x1002: rD
    → 最終バイト = 0x1002
    → PC_next = 0x1003
  
  5byte命令（0x1F prefixで4byte以上）
    byte0 @ 0x1000: 0x1F
    byte1 @ 0x1001: 0x20  (PUSHM)
    byte2 @ 0x1002: mask_low
    byte3 @ 0x1003: mask_high
    → 最終バイト = 0x1003
    → PC_next = 0x1004

用途:
  - 関数ポインタの呼び出し
  - ジャンプテーブルの実装
  - ISA2.2の JSR imm16（直接分岐）とは別


7.6 スタックポインタ転送命令（ISA3.0新規追加）

【MOV X, SP 命令】

命令: MOV X, SP
format: 0x20
         byte0: 0x20
         byte1: 0x23 （rD=2=X, rS=3=SP）
動作:
  X = SP

用途:
  - スタック領域をインデックスベースアドレッシングで参照する場合
  - スタックフレーム内のローカル変数アクセス
  - デバッグ用スタックトレース

制約: **制限なし**（常に使用可能）

【MOV SP, X 命令】

命令: MOV SP, X
format: 0x20
         byte0: 0x20
         byte1: 0x32 （rD=3=SP, rS=2=X）
動作:
  SP = X

用途:
  - スタックフレーム復元
  - スタックポインタの動的設定

【制約（重要）】

MOV SP, X は以下の場合のみ使用可能：

✅ **許可される場所：**
  1. 関数エピローグ
     例：
       func_epilogue:
         MOV SP, X  ; フレームポインタ相当の処理
         RET
  
  2. 割り込み復帰前
     例：
       isr_exit:
         MOV SP, X  ; スタック復元
         IRET
  
  3. コンパイラ生成コードのみ
     - 手動アセンブリで MOV SP, X を使用することは禁止
     - hasm22/hasm23 は警告を出すことが推奨

❌ **禁止される場所：**
  - ユーザアプリケーションコード（明示的なアセンブリ）
  - ランダムなポイントでのSP操作
  - スタック損傷の危険性が高い位置

【実装上の注記】

アセンブラ/コンパイラ：
  - MOV X, SP はいつでも許可
  - MOV SP, X はコンパイラ生成フラグを確認
  - ユーザアセンブリで MOV SP, X が使用された場合、警告を出す

エミュレータ：
  - MOV SP, X の使用位置をログに記録（デバッグ用）
  - スタック範囲外へのSP設定は検出可能

FPGA実装：
  - 制約チェックは不要（ソフトウェア責務）
  - MOV命令のデコードは通常の rD, rS でOK


8. 割り込み仕様（ISA3.0）
========================================

8.1 割り込みベクタテーブル

IRQ_ID | 名称    | 用途
-------|---------|----------------------------------
0      | reset   | リセット（ベクタ参照）
1      | irq0    | **タイマー割り込み（専用）**
2      | irq1    | 外部割り込み1
3      | irq2    | 外部割り込み2
4      | align   | アラインメント例外
5      | syscall | SYSCALL 命令

ベクタテーブル配置：
  Address 0x0000: reset handler
  Address 0x0002: irq0 (タイマー) handler
  Address 0x0004: irq1 handler
  Address 0x0006: irq2 handler
  Address 0x0008: align handler
  Address 0x000A: syscall handler

8.2 ハードウェア割り込み受理動作（確定）

割り込み条件:
  irq_pending >= 0 && (FLAGS.IE == 1)

受理時の動作:
  SP = SP - 2
  mem[SP] = PC_current
  SP = SP - 2
  mem[SP] = FLAGS_current
  FLAGS.IE = 0
  PC = mem[irq_id * 2]
  irq_pending = -1

【重要：割り込み時のSP】

【USPと割り込みの独立性（確定）】

割り込み受理時および ISR 実行中：
  - SP（カーネルスタック）のみを使用
  - USP は完全に無関係（変更されない）
  - ISR 内で XCHG_SP を実行しない限り、USP は変わらない

理由：
  1. 割り込みはカーネルコンテキスト
  2. ISR はカーネルモード実行
  3. ユーザランド復帰は OS が明示的に XCHG_SP で実行

例：
  ユーザランド実行中に割り込み発生
    → ISH内では SP を使用（USP は不変）
    → IRET で割り込み前のユーザコンテキストに復帰
    → ユーザランド側は USP を使用継続

このパターンにより、ユーザランドのスタック
（USP）が ISR に汚染されることはない

割り込み受理時は常にカーネルスタック（SP）を使用する
USP（ユーザスタックポインタ）は無関係（変更されない）

理由：
  - 割り込みハンドラはカーネルモード（常にSP使用）
  - ユーザランドから割り込みで入ったとしても、
    割り込みハンドラ内では SP でスタック操作
  - ユーザランド復帰前に XCHG_SP をマイクロカーネルが実行
    してユーザスタック（USP）に切り替え

例：
  ユーザランド実行中に割り込み発生
    → ISH ハンドラ内では SP を使用
    → ハンドラ終了後 IRET で割り込み前状態に復帰
    → 必要に応じてマイクロカーネルが XCHG_SP で切り替え

注記：
  - PC_current は割り込み時点のプログラムカウンタ
  - 復帰後 RET で正しい位置に復帰
  - ネスト割り込みをサポート（ハンドラ内で明示的に EI）


8.3 割り込み復帰（IRET）

命令: IRET
動作:
  FLAGS = mem[SP]
  SP = SP + 2
  PC = mem[SP]
  SP = SP + 2

注記：
  - FLAGS と PC の順序は厳密（FLAGS → PC）
  - これにより割り込み前の状態へ完全に復帰


8.4 割り込みネストの扱い（デフォルト：禁止）

【デフォルト動作：割り込みネスト禁止】

割り込みハンドラ実行中は、他の割り込みは受け入れられない
（自動的に割り込みがマスクされる状態）

理由：
  1. 割り込み受理時に IE = 0 が設定される
  2. ハンドラ内で明示的に EI を実行しない限り、
     割り込みは受け入れられない
  3. IRET で復帰時に、割り込み前の IE 状態が復元される

【割り込みネストを許可する場合】

ハンドラ内で明示的に EI を実行することで、
ハンドラ内での割り込み受け入れを許可できる：

例：
  timer_isr:
    PUSHM mask
    EI              ← 割り込みを再度有効化（ネスト許可）
    ; ISR処理
    DI              ← 処理前に割り込みディセーブル（推奨）
    POPM mask
    IRET

【推奨】

一般的には、ハンドラ内での割り込み再有効化は慎重に：
  - スタック溢れの危険
  - デバッグの複雑化
  - リアルタイム性が必須な場合のみ使用

ISR の基本構造：
  isr_handler:
    PUSHM mask        ; 必要なレジスタを退避
    ; ISR処理
    POPM mask         ; レジスタを復元
    IRET              ; 割り込みから復帰

注記：
  - 必要なレジスタのみ PUSHM で退避（全レジスタ退避は不要）
  - caller-save レジスタは ISR責務で保存
  - callee-save レジスタが必要な場合も ISR が保存


8.5 リセット時の初期化（確定）

リセット発生時、CPU は以下を実行する：

【ハードウェア初期化】
  PC    ← mem[0x0000]  （ベクタテーブルからリセットハンドラ取得）
  FLAGS ← 0x00         （すべてのフラグをクリア）
    bit0(Z)   ← 0
    bit1(N)   ← 0
    bit2(C)   ← 0
    bit3(V)   ← 0
    bit4(IE)  ← 0    （割り込みディセーブル）
    bit5(UM)  ← 0    （カーネルモード）
  
  SP    ← 0xFC7E       （カーネルスタック初期値）
  USP   ← 0xF7FE       （ユーザスタック初期値）
  
  A, B, X      ← 未定義（実装依存、不定値）
  T0, T1, T2, T3 ← 未定義
  S0, S1       ← 未定義

【初期値の根拠】

SP = 0xFC7E:
  - カーネルスタック領域（0xF800-0xFC7F）の上端
  - メモリマップ ISA2.2 に基づく（F800-FC7F: stacks）
  - emu22_mmu との整合性維持

USP = 0xF7FE:
  - ユーザスタック領域（E000-F7FF）の上端
  - Forthマシンメモリマップ（E000-F7FF: workspace）と整合
  - ユーザランド起動時の初期スタックポインタ

【割り込い初期状態】
  IE = 0  （割り込みディセーブル状態でリセット）
  → リセット直後に EI 命令が必要（カーネル初期化処理で実行）

【MMU初期状態】
  - MMU は disable（論理アドレス = 物理アドレス）
  - emu22_mmu_design と整合性維持


9. ABI仕様（確定）
========================================

9.1 レジスタ分類

caller-save（関数呼び出しで破壊可能）:
  R0 (A), R1 (B), R2 (X)
  R6 (T0), R7 (T1), R8 (T2), R9 (T3)

callee-save（関数呼び出しで保証）:
  R10 (S0), R11 (S1)

特殊レジスタ（直接操作禁止が原則）:
  R3 (SP): スタック管理（自動更新）
  R4 (PC): 直接変更禁止（JMP/JSR/IRET で制御）
  R5 (FLAGS): 原則変更禁止（EI/DI で IE のみ操作）

9.2 関数引数渡し規約

第1引数  → R0 (A)
第2引数  → R1 (B)
第3引数以降 → スタック（右から左へpush）

例：
  f(a, b, c, d)
  → R0=a, R1=b, [SP+4]=c, [SP+2]=d （呼び出し時）

9.3 戻り値

R0 に格納（16bit）
64bit以上の戻り値はスタック経由（ポインタ返却等）

9.4 呼び出しシーケンス

【caller 側】
  1. 引数設定（R0/R1/スタック）
  2. 必要な caller-save を PUSHM で退避
  3. JSR (直接) または JSR rS (間接)
  4. POPM で caller-save を復元

【callee 側】
  1. 必要な callee-save を PUSHM で退避
  2. ローカル変数領域を SP で確保
  3. 処理実行
  4. 戻り値を R0 に設定
  5. POPM で callee-save を復元
  6. RET で復帰

9.5 スタック構造

|------------------------|
| 第4引数以降（caller側） |
|------------------------|
| 戻り値アドレス          | ← JSR がpush
|------------------------|
| callee-save 退避        | ← callee の PUSHM
|------------------------|
| ローカル変数/スピル      |
|------------------------|  ← SP

9.6 フレームポインタ

ISA3.0 では フレームポインタを使用しない
  - ローカル変数は [SP + offset] でアクセス
  - 尾部呼び出し最適化(TCO)を容易化
  - レジスタ数制限を回避

9.7 最適化許容事項

許可:
  - caller-save 全体を省略可能（関数内で非破壊な場合）
  - callee-save を部分的に省略可能（使用しない場合）
  - リーフ関数（他の関数を呼び出さない）の最適化
  - PUSHM を部分的に使用可能（全レジスタpush不要）

禁止:
  - callee-save レジスタの未保存破壊（呼び出し規約違反）


10. ISA2.2との互換性（確定）
========================================

10.1 バイナリ互換性（逆方向）

ISA2.2で生成されたバイナリはISA3.0環境で変更なし実行可能
  - 基本命令（0x00-0x7F）は ISA2.2 と同一
  - ISA2.2コンパイル出力は ISA3.0で直接実行可能
  - 既存プログラム（kernel.asm等）は変更なし動作

10.2 アセンブラ互換性

ISA2.2で作成されたアセンブラプログラム（.asm）:
  - ISA3.0アセンブラで「そのまま」コンパイル可能
  - 新規命令（XCHG_SP, SHLI等）は ISA3.0のみで利用可能
  - 既存プログラムは変更なし動作

10.3 レジスタ命名後方互換性

A, B, X, SP, PC, FLAGS の reg_id は ISA2.2と同一
  - ISA2.2: reg_id=0-5
  - ISA3.0: reg_id=0-11（後方互換）
  - ISA2.2デコーダは reg_id(4bit)の上位のみ使用 → 新規レジスタ存在に影響なし

10.4 ISA2.2との主要差分表

機能              | ISA2.2 | ISA3.0 | 備考
------------------|--------|--------|----------------------------
汎用レジスタ数    | 2(A,B) | 10(含むT,S) | caller/callee分類
ユーザスタック    | なし   | あり(USP)  | XCHG_SP で管理
即値シフト        | なし   | あり       | SHLI/SHRI/SARI
複数レジスタ操作  | なし   | あり       | PUSHM/POPM
間接JSR           | なし   | あり       | 関数ポインタ対応
割り込みベクタ    | 5個   | 6個       | irq0がタイマー専用


11. フリーズ仕様範囲（確定）
========================================

以下の仕様は ISA3.0 として確定（今後変更なし）:

【命令仕様】
  - ISA2.2 の全基本命令
  - ISA3.0 の全新規命令（拡張プレフィックス 0x1F 配下）
  - sub-opcode 配置ルール（0x00-0x1F, 0x20-0x2F等）
  - 間接JSR の PC_next 動作

【レジスタ仕様】
  - 12本の汎用/特殊レジスタ（A, B, X, T0-T3, S0-S1）
  - FLAGS（bit0-5, 予約bit3以降）
  - USP（XCHG_SP のみで操作）
  - caller/callee-save 分類

【ABI仕様】
  - 引数渡し規約（R0, R1, スタック）
  - 戻り値（R0）
  - スタック構造
  - フレームポインタなし

【スタック仕様】
  - 16bit 単位の push/pop
  - SP による動的管理
  - PUSHM/POPM による複数レジスタ操作

【割り込み仕様】
  - 6種類の割り込み（reset, irq0-2, align, syscall）
  - irq0 = タイマー専用
  - PC/FLAGS の push-pop 順序
