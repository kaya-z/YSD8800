■ 原則6: ワードの「副作用スコープ」を設計書・コメントに明記する

  Forthワード（およびサブルーチン）の設計書・ヘッダコメントには
  スタック図だけでなく以下を必ず記載する。

    : WORD-NAME  ( 入力 -- 出力<TOS> )
      \ 副作用: 使用するワーク変数（例: L1_WK_TMP, L1_WK_C）
      \ DSP上の既存データへの影響: なし / あり（要退避）
      \ 呼び出し時の前提条件: （例: DSPが空であること）

  ※ アセンブラルーチンにおける「レジスタ保存一覧」と同じ位置づけ。
  ※ 単体では正しく動くが「組み合わせると壊れる」パターンの
    主な原因は、この副作用の記載漏れである。

■ 原則7: スタック図にTOSを明示する

  複数の値を返すワードは、どの値がTOSかを必ずスタック図に示す。

    変更前（曖昧）: \ IPC4-CALL ( tid -- r3 r2 r1 r0 )
    変更後（明示）: \ IPC4-CALL ( tid -- r3 r2 r1 r0<TOS> )
                    \ r0=result(TOS), r1/r2/r3=reserved

  そのワードを使う側は「TOS=何か」を先に確認してから
  DROP / NIP / >R 等の順序を決めること。

■ 原則8: 「危険な組み合わせ」を設計書の注意事項として明記する

  単体では正しいが組み合わせると副作用が生じるパターンは
  設計書の注意事項セクションに明示する。

  記載例:
    【注意】IPC4-RECV 後の DSP 状態
    IPC4-RECV 実行後、DSP には msg3 msg2 msg1 msg0<TOS> が積まれる。
    この状態で DSP を操作するすべての Forth ワードを呼ぶ際は、
    msg 群を R スタックに退避するか、CODE 実装で DSP を経由しない
    方式を選ぶこと。

■ 原則9: DSP状態に依存する低レベル操作はCODEワードで実装する

  以下の操作は高水準 Forth ワードに任せず、
  CODE ワードで DSP を直接制御する設計とする。

    - TCBフィールドの直接読み書き
    - IPCメッセージの送受信（IPC4-SENDER 等）
    - スケジューラ内部のコンテキスト操作

  理由: 高水準 Forth ワードは内部で DSP を使用するため、
  呼び出し元の DSP 上の既存データを破壊するリスクがある。

■ 原則10: デバッグ初手はダンプから始める（原則3の具体化）

  症状が現れた時点で、まず以下を機械的に実施してから原因を考える。

    □ DSP / RSP の全内容をダンプする
    □ 関連するメモリ領域（TCB, IPCバッファ, ワーク変数）をダンプする
    □ 期待値と実測値を数値で比較する
    □ 「壊れているはず」の変数を仮説なしで全部ダンプする
    □ ↑ここまで完了してから初めて原因の仮説を立てる

  「こうなっているはず」で仮説を先に立てると、
  的外れな場所を長時間追い続けるリスクがある。
