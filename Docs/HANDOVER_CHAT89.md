## 3. ★★本日の最重要発見（原則76）★★

### 設計メモは実装から遅れていた — **TCR EN ビットは AND ではなく OR**

**設計メモ v0.2 §3.5（擬似コード）:**
```
発火: armed_r && (cnt_r == 0) && TIMER_EN && IRQ_EN     ← ★AND（誤り）★
```

**黄金リファレンス emu23_v110.c L696（実源）:**
```c
ysd8002.irq_enabled = (ysd8002.tcr & 0x03) ? 1 : 0;     ← ★OR★
```

**★設計メモを信じて AND で RTL を書いていたら、S8 の協調等価で初めて落ちていた。★**

#### なぜ通常テストでは見つからないか

| TCR | emu23（OR） | AND だったら | 実運用で書かれるか |
|---|---|---|---|
| `$03`（通常運用・ACK=`$0023`） | 発火 | 発火 | ✅ 常用。**差なし** |
| `$04`（`timer_start()`） | 発火せず | 発火せず | ✅ Dhrystone。**差なし** |
| **`$01` / `$02`** | **発火する** | 発火しない | ❌ 現状書かれない |

→ **通常系のテストをいくら通しても発見できない。**
→ だから **実装前の実源照合**（原則76）と **KY54 ネガティブラン**が要る。

### 【D7 決定・ユーザー承認 2026-07-14】

**RTL は emu23（OR）に合わせた。** `assign fire_en = timer_en_r | irq_en_r;`

理由: emu23 が黄金リファレンスである以上、RTL は emu23 と等価でなければならない。
V5 のスコープは「再武装方式の是正」であり「TCR ビット意味論の是正」ではない。

## 4. ★★★申し送り：近日中の抜本改修（★失念厳禁★）★★★

> ## ★ユーザー指示（2026-07-14）★
> ## **「(A)として近日中に抜本的な改修を行うことにする」**

### 何が問題か

**OR であるため `IRQ_EN`(bit1) は名前どおり機能していない。**

- `TCR ← $01`（TIMER_EN=1, **IRQ_EN=0**）と書いても **★割込は出続ける★**
- 「割込を禁止するつもりで IRQ_EN を落としたのに、割込が止まらない」
- **レジスタ名と挙動が矛盾＝デバイスの契約違反**
- **S7 の T8 で実証済み**（`$22`＝IRQ_EN のみでも発火する）

### 正しい姿（MC6840 PTM 系の作法）

| bit | 名称 | 正しい意味 |
|---|---|---|
| 0 | TIMER_EN | **カウンタを進めるか**（0=カウンタ停止） |
| 1 | IRQ_EN | **割込を出すか**（0=カウンタは進むが IRQ は出さない＝マスク） |

**発火条件は AND であるべき: `armed && (cnt==0) && TIMER_EN && IRQ_EN`**

「タイマーは動かすが割込は出さない」（TIMER_EN=1 / IRQ_EN=0）は
デバイスとして**正当かつ有用な状態**（ポーリング計測・SW_BUSY 計測）。
**現行の OR ではこの状態が表現できない。**

### 改修範囲

| 対象 | 内容 |
|---|---|
| `emu23` | L696 `(tcr & 0x03) ? 1 : 0`（OR） → **AND** へ |
| `emu23` | **TIMER_EN=0 時のカウンタ停止**（現行は `irq_enabled` 一本で兼用しており、カウンタ停止の概念がない） |
| YSD8002 RTL | `fire_en = timer_en_r \| irq_en_r` → **`& `** （または EN 分離） |
| `dhry_timer.c` | `timer_start()` の `TCR ← $0004` が IRQ_EN を殺す件（CHAT88 §5 誤り1）も**同時に是正** |
| **回帰** | ★★**Dhrystone 黄金値 826/48405/P:20 が変わる可能性がある**★★ 全回帰やり直し必須 |
| 文書 | `ysd8002_timer_design_v1_0.docx` の TCR 定義を AND に是正 |

### ★★V5 完了（S10）後に、独立した工程として実施すること★★

V5 の最中に混ぜると、**再武装方式の検証と EN 意味論の検証が混線して原因切り分けが不能**になる。

**判定基準（黄金値）を動かす変更は、その判定基準を使っている工程の「最中」にやってはならない。**
落ちたときに「実装が悪いのか、判定基準が変わったのか」区別できなくなる（原則75 の裏返し）。

### 5.2 ★結線：タイマー優先★

```systemverilog
// V4（現行 tb_cpu_v4uart_v0_2.sv L77）
assign irq_in = (irq_en && irq1_o) ? 3'd2 : 3'd0;

// ★V5（S8）★ タイマー(IRQ0)優先
assign irq_in = irq_timer ? 3'd1 : ((irq_en && irq1_o) ? 3'd2 : 3'd0);
```

**根拠（emu23 の評価順序）:**
```c
L1591: if (irq_pending < 0 && YSD8002_tick(...)) irq_pending = 1;  // ★タイマー先★
L1611: if (irq_pending < 0 && irq_stat != 0)     irq_pending = 2;  // IRQ1 は後
```

> ★**ここが CPU v0.5.8 の pending 保護と噛み合う**★
> 保護がないと、タイマーが pending 中に IRQ1 が上書きしてタイマーを蹴落とす。
> **S5 の改修はこのためにある。** S8 で初めてその効果が検証される。

### 5.3 ★★S8 最大の論点：`cycle_i` を何で駆動するか★★

**YSD8002 RTL は `cycle_i[31:0]`（CPU の経過サイクル数）を外部から受ける。**
**しかし V4 統合TB には cycle カウンタが存在しない。**

#### ★★★これは既知の地雷である★★★

`tb_cpu_v4uart_v0_2.sv` **L305-306** が既に警告している:

> RTL の `tx_cnt_r=4167` は**【クロック】基準**であり、
> **実CPI(約18)の分だけ TX 復帰までのループ回数が違う。**

**つまり:**

| | emu23 | FPGA RTL |
|---|---|---|
| `cycle` の意味 | **命令数**（CPI=1 固定） | **クロック数**（実CPI ≈ 18） |

**★emu23 の `cpu.cycle` と RTL のクロック数は【定義上一致しない】★**
（memory / kaizen にも既登録: 「emu23 の cycle は CPI=1 固定のため FPGA との
cycle 一致は定義上不可。リグレッションゲートは『完走＋論理結果一致』のみ」）

#### 選択肢（★S8 冒頭で設計判断すること・原則43★）

| 案 | 内容 | 論点 |
|---|---|---|
| **A** | `cycle_i` を **RTL のクロックカウンタ**で駆動 | 実機と同じ。ただし **PERIOD=40000 クロック ≈ 命令数 2200 程度**となり、emu23（40000命令）と**発火タイミングが約18倍ずれる** |
| **B** | `cycle_i` を **CPU の命令完了カウンタ**で駆動 | emu23 と等価になるが、**実機では命令数を数える回路が要る**（現実的でない） |
| **C** | TB 側で **PERIOD を調整**して発火回数を合わせる | 協調等価の判定を「発火回数」に絞る。**実機とは別設定**になる |

> ★**推奨は A**★（実機が真実。emu23 とは「発火する/しない」「ACK で再武装する」という
> **論理**が一致すればよく、**絶対時刻の一致は求めない**）。
> ただし**これは設計判断であり、S8 冒頭でユーザー承認を得ること（原則43）。**
> 判定基準を「完走＋論理結果一致」に置くという既存方針とも整合する。
