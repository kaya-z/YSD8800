■ 原則21: hasm23に「シンボル二重定義検出」を実装する

  EQU定数・ラベル・CODEワード名を同一名前空間で管理し、
  既登録シンボルを再定義しようとした場合はエラーで停止する。

    実装方針:
      Pass1でシンボル登録時に既登録チェックを追加する。
      エラー例: "ERROR: symbol 'TASK_WAIT_IPC' already defined at line XX"

  ※ 「二重定義禁止」をルール化するだけでは不十分。
    人間はミスをするのでツールが防壁として機能しなければ再発する。
    MC6809の標準アセンブラ（AS9等）でも二重定義はエラーが常識。

■ 原則22: hasm23に「.org後退時の警告」を実装する

  .org値が現在のPC値を下回る場合は警告を出力する。
  意図的な後退の場合は --allow-org-backtrack で抑制可能とする。

    警告例: "WARNING: .org $1000 is behind current PC $1200 (possible overlap)"

  ※ Step 8-Fで対処予定だが、スロットサイズ超過バグの再発を
    防ぐために優先度を上げること。

■ 原則23: ツールの既知制約を「制約台帳」として設計書に一元管理する

  各ツールの既知制約・未対応機能を設計書の専用セクションに記載し、
  実装チャット開始前に必ず参照する。新たに制約が判明した場合は
  その場で追記することを義務とする。

  【制約台帳テンプレート（設計書 §制約一覧）】

    ツール名     │ 制約事項             │ 代替手段
    ─────────────┼──────────────────────┼──────────────────────
    Force v1.2   │ DO/LOOP 未対応       │ BEGIN/WHILE/REPEAT
    Force v1.2   │ LOCALS 未対応        │ 変数ワードで代替
    scc23        │ char*にLDW生成       │ putchar()直接使用
    hasm23       │ .org後退を警告しない │ Step 8-Fで対処予定

  ※ 設計書にDO/LOOPが書かれていても、Forceが対応していなければ
    実装フェーズで全て書き直すことになる。
    設計書を書く時点で制約台帳を参照し、使えない構文を排除する。

■ 原則24: emu23デバッグマニュアルを独立文書として整備する

  チャットをまたぐたびに使い方を調べ直すオーバーヘッドを
  一度の作業でゼロにするため、以下の内容で文書を作成する。

  【emu23_debug_manual.md に記載すべき内容】

  §1 コマンドラインオプション一覧
    -b ADDR : ADDR到達時点でトレース開始
    -n N    : N命令実行後に停止（トレースと併用）
    -t      : 全命令トレース出力
    -m      : メモリダンプ（範囲指定）
    -q      : 静粛モード（UART出力のみ）
    --disk  : ストレージイメージ指定
    -i FILE : UART受信をファイルから供給

  §2 ブレークポイントの使い方
    ・アドレスで指定すること（ラベル名では指定不可）
    ・手順: .symファイルをgrepでアドレス取得 → -bで指定
    ・例: grep WORD_STOR_DRV_TASK yuios.sym → $xxxx → -b $xxxx

  §3 クラッシュ解析の定石手順
    1. 出力から異常発生タイミング（サイクル数）を特定する
    2. -n <サイクル数> で直前命令群を取得する
    3. PC・SP・レジスタ値で原因を絞る
    4. 必要なら -b <アドレス> で更に絞る

  §4 IRQ番号とirq_pendingのオフセット対応表
    IRQ0（タイマー）  = irq_pending 1, vec=$0002
    IRQ1（デバイス）  = irq_pending 2, vec=$0004
    計算式: vec = irq_pending × 2

  §5 emu23_watch / emu23_w2 の使い方
    （特定アドレスへの読み書きをログする機能）

■ 原則25: 割り込みハンドラの設計書には「全状態×全イベント」表を必須記載する

  IRQ0_HANDLER等の割り込みハンドラは、CUR_TASKが指すタスクが
  必ずしもRUNNING状態とは限らない（アイドル中は直前に寝た
  タスクのtidがCUR_TASKのまま残る）。
  
  この前提を設計書に以下の形式で必ず記載する。

  【IRQ0_HANDLER 状態別動作表テンプレート】

    CUR_TASKのstate  │ IRQ0_HANDLERの動作
    ─────────────────┼────────────────────────────────────────
    RUNNING(2)       │ コンテキスト保存 → READY化 → スケジュール
    READY(1)         │ コンテキスト保存禁止 → スケジュールのみ
    WAIT_IPC(5)      │ コンテキスト保存禁止 → スケジュールのみ
    WAIT_REPLY(6)    │ コンテキスト保存禁止 → スケジュールのみ
    アイドル中       │ コンテキスト保存禁止 → スケジュールのみ

  ※ 「CUR_TASKが指すタスク = 現在実行中のタスク」は成り立たない。
    アイドル中にIRQが来た場合の動作を設計書に定義しなければ、
    寝ているタスクのsaved_pcをアイドルループのPCで上書きするバグが潜在する。
    （2026-05-17 IRQ0_HANDLER state==RUNNINGチェック追加で修正）

■ 原則26: 構造体・メッセージレイアウトは設計書と実装の対照表で管理する

  設計書に構造体・メッセージのレイアウトを定義したら、
  実装のEQU定数との対照表を必ずセットで記載する。

  【msgレイアウト対照表テンプレート】

    フィールド  │ 設計書オフセット │ 実装EQU定数     │ 一致確認
    ────────────┼──────────────────┼─────────────────┼──────────
    msg0 (op)   │ +0              │ MSG0_OFS EQU 0  │ □
    msg1        │ +2              │ MSG1_OFS EQU 2  │ □
    msg2        │ +4              │ MSG2_OFS EQU 4  │ □
    msg3        │ +6              │ MSG3_OFS EQU 6  │ □

  設計書改版時・実装完了時の両方でこの表を埋めること。

  ※ オフセットの逆転バグ（msg0↔msg3）は対照表があれば
    レビュー時点で発見できる。「設計書の図を見れば分かる」では不十分。

■ 原則27: 固定アドレスAPIスロットの「コードサイズ上限」を設計書に明記する

  .orgで固定アドレスに配置するAPIスロットは、
  各スロットが許容するコードサイズの上限を設計書に数値で明記する。
  実装後はhasm23のリンクマップでスロットサイズを確認すること。

  ※ hasm23は.orgでコードが重なっても警告しない（原則22で対処予定）。
    設計書にサイズ上限がなければ、実装者が自分でサイズを計算しなければ
    ならず、踏み越えバグが検出できない。

■ 原則28: バグの種類によってデバッグ初手を使い分ける

  以下の種類のバグはemu23トレースを初手とする。
  論理分析だけで追おうとすると時間を大きく浪費する。

    【トレース初手が必須のバグ種別】
      ・IRQタイミング依存のバグ
      ・スケジューラの状態遷移バグ
      ・スタック破壊・PC異常（$0000ジャンプ等）
      ・「特定の実行順序でのみ発生する」バグ

    【論理分析でも対応可能なバグ種別】
      ・特定命令のロジックエラー（計算・分岐の誤り）
      ・設計書との単純な実装ミス（オフセット違い等）

  クラッシュ解析の定石手順（原則24 §3と合わせて使うこと）:
    1. 異常発生タイミング（サイクル数）を出力から特定する
    2. -n <サイクル数> で直前命令群を取得する
    3. PC・SP・レジスタ値で原因箇所を特定する

■ 原則29: 引き継ぎ文書に「地雷マップ」セクションを設ける

  引き継ぎ文書（HANDOVER_CHATnn）には、次のチャットへの警告として
  「地雷マップ」セクションを必ず設ける。

  【地雷マップ記載テンプレート】

    § 実装上の地雷マップ（次のチャットへの警告）

    以下は実装中に踏む可能性が高い。事前に必ず読むこと。

    ⚠️ 地雷1: CUR_TASKはアイドル中も変化しない
       → IRQ0_HANDLERではstate==RUNNINGを必ずチェックすること

    ⚠️ 地雷2: IPC4_CALL固定スロットのコードサイズ上限は○○B
       → hasm23は無警告で隣のスロットを踏み越える

    ⚠️ 地雷3: Force v1.2はDO/LOOP未対応
       → BEGIN/WHILE/REPEATで代替すること

    （発見した地雷は必ずここに追記すること）

  ※ 引き継ぎ文書に地雷が書かれていなければ、
    次のチャットは同じ地雷を踏み直すことになる。
    「前のチャットで分かっていたこと」を引き継ぐことが最重要。

■ 原則30: 設計書レビューに「チェックリスト」を義務付ける

  設計書レビューは「気づいた点を指摘する」方式ではなく、
  以下のチェックリストを使って機械的に確認する方式とする。

  【カーネル設計書レビュー 必須確認チェックリスト】

    □ 割り込みハンドラの全状態×全イベント表が存在するか
    □ 固定アドレスAPIの各スロットのサイズ上限が数値で明記されているか
    □ 構造体・メッセージレイアウトの設計書↔実装対照表が存在するか
    □ 初期化関数の呼び出しタイミング制約が明記されているか（原則14）
    □ CUR_TASKが非RUNNING状態のときの割り込み動作が定義されているか
    □ ツール制約台帳が参照されており、使えない構文が排除されているか
    □ 設計書の擬似コードをそのまま実装に落とせる精度に達しているか
    □ Forthワード定義に標準テンプレートが使われているか（原則13）
    □ スタック容量の最大使用量計算と余裕率が記載されているか（原則16）
    □ 多重アクセスシナリオが定義されているか（原則18）

  ※ レビューが完了していないうちは次工程に進まないこと（プロジェクト規則）。
    チェックリスト全項目に□を入れることがレビュー完了の条件とする。
