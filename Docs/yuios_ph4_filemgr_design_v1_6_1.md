## 1. 概要

### 1.1 目的

本書は、YUI OS Ph.4 において、YSD8003 ストレージ上に独自フラットファイルシステム（以下フラットFS）を構築し、それを管理する **FileMgr サーバタスク**を独立タスクとして実装するための詳細設計書である。

Ph.3-B まででストレージは独立ドライバタスク（STOR-DRV-TASK、tid=3）として実装され、セクタ単位の READ/WRITE が IPC4-CALL 経由で利用可能になった。Ph.4 ではその上位に「名前付きファイル」の抽象を構築する。クライアントタスク（将来のシェル・ProcMgr・Cユーザランド）は IPC4-CALL 経由で FileMgr にファイル操作を要求する。

## 2. アーキテクチャ上の位置づけ

### 2.1 レイヤ構成

```
┌─────────────────────────────────────────────┐
│ クライアント（シェル / ProcMgr / Cアプリ）   │  tid=5,6,7..
│   FILE_OPEN / READ / WRITE / ... を IPC4-CALL │
├─────────────────────────────────────────────┤
│ FileMgr サーバタスク           tid=4          │  ★本書の対象
│   ・ディレクトリ管理（検索・追加・削除）       │
│   ・オープンファイルテーブル（4スロット）      │
│   ・セクタバッファ（512B×1）                  │
│   ・論理オフセット ⇔ LBA 変換                 │
├─────────────────────────────────────────────┤
│ STOR-DRV-TASK（ストレージドライバ）  tid=3    │  Ph.3-B（利用するだけ）
│   STOR_READ / STOR_WRITE / STOR_STAT          │
├─────────────────────────────────────────────┤
│ YSD8003 ストレージコントローラ（MMIO）        │
└─────────────────────────────────────────────┘
```

FileMgr は**二重の役割**を持つ：

1. **サーバ**：クライアントからの SVC_FILE 要求を IPC4-RECV で受け、IPC4-REPLY で応答する。
2. **クライアント**：ストレージ I/O のため STOR-DRV-TASK へ IPC4-CALL を発行する。

### 2.2 ★最重要設計制約：FileMgr の二重役割と nested CALL 禁止

yuios_ipc4_pool_design_v1_3.md §4.4 原則6 で、**「WAIT_REPLY 状態のタスクが IPC4-CALL を発行することは禁止」**（nested CALL 禁止）が API 規約として確定している。これは A→B→A 循環デッドロックを防ぐためのものである。

FileMgr はサーバでありながら STOR-DRV-TASK のクライアントにもなるため、この制約への適合を設計段階で確認する必要がある。

**結論：本設計は nested CALL 禁止に抵触しない。** 根拠は以下のとおり。

| **時点** | **FileMgr の state** | **動作** | **判定** |
| --- | --- | --- | --- |
| 要求待ち | WAIT_IPC (5) | IPC4-RECV でブロック | — |
| 要求受信〜処理中 | RUNNING (2) | クライアント要求を処理 | — |
| STOR へ I/O 要求 | RUNNING → **WAIT_REPLY (6)** | STOR-DRV-TASK へ IPC4-CALL | ここで WAIT_REPLY になる |
| STOR からの応答受信 | WAIT_REPLY → RUNNING | IPC4-CALL から復帰 | — |
| クライアントへ応答 | RUNNING | IPC4-REPLY を発行 | — |

FileMgr が STOR へ IPC4-CALL を発行する時点では、FileMgr 自身は **RUNNING 状態**である（クライアント要求を IPC4-RECV した後、まだ自分は IPC4-REPLY を返していない）。FileMgr が WAIT_REPLY になるのは、その IPC4-CALL を発行した「結果」であって、CALL 発行「時点」では RUNNING である。

nested CALL 禁止が禁じるのは「**既に** WAIT_REPLY のタスクが **さらに** CALL する」ことであり、FileMgr のように「RUNNING のタスクが CALL して WAIT_REPLY になる」のは正常動作である。

```
クライアント(tid=5)              FileMgr(tid=4)             STOR-DRV(tid=3)
   IPC4-CALL ───────────────────> IPC4-RECV
   [WAIT_REPLY]                   [RUNNING] 要求処理
                                  IPC4-CALL ───────────────> IPC4-RECV
                                  [WAIT_REPLY]               [RUNNING] セクタ転送
                                  IPC4-CALL から復帰 <─────── IPC4-REPLY
                                  [RUNNING] 応答組立
   IPC4-CALL から復帰 <─────────── IPC4-REPLY
   [RUNNING]
```

このシーケンスでは、各タスクが WAIT_REPLY になるのは「自分が CALL した相手の応答待ち」の1段のみであり、循環は発生しない。クライアント→FileMgr→STOR は一方向の依存（DAG）であり、STOR が FileMgr や クライアントを CALL し返すことはない。

**【Ph.5 以降の依存連鎖：4 段 DAG】（v1.1 追記。社内レビュー指摘）**

yuios_design_v2_2.md §8.2 の ProcMgr 実行フローでは、ProcMgr（tid=5）が FileMgr に対し FILE_OPEN → FILE_STAT → FILE_READ を順次 IPC4-CALL する。したがって Ph.5 以降の最大依存連鎖は以下の **4 段**となる：

```
Shell(tid=6) ──CALL──> ProcMgr(tid=5) ──CALL──> FileMgr(tid=4) ──CALL──> STOR-DRV(tid=3)
  [WAIT_REPLY]            [WAIT_REPLY]              [WAIT_REPLY]            [RUNNING]
```

この 4 段でも nested CALL 禁止には抵触しない。各タスクは「自分が CALL を発行した時点では RUNNING」であり、CALL の結果として WAIT_REPLY になる。連鎖の各段で WAIT_REPLY 中のタスクが**さらに**別の CALL を発行することはなく、依存は Shell → ProcMgr → FileMgr → STOR の一方向（DAG、4 ノード一直線）である。末端の STOR が上位を CALL し返さない限り循環は生じない。本設計（FileMgr）はこの DAG の中間ノードとして適合する。

**【設計ルール】** FileMgr のメインループでは、IPC4-RECV と IPC4-REPLY の間で STOR への IPC4-CALL を行ってよい。ただし FileMgr 自身が他タスクから IPC4-CALL を受けて WAIT_REPLY 中に、さらに別の IPC4-CALL を発行してはならない（この状況は本設計のシーケンス上発生しないが、将来の改修時の禁止事項として明記する）。Ph.5 で ProcMgr を実装する際も、ProcMgr は同じ規律（RECV〜REPLY 間でのみ下位を CALL）を守ること。

### 2.3 多重クライアントシナリオ（kaizen 原則18）

| **項目** | **設計** |
| --- | --- |
| 想定クライアント数 | 最大 11 タスク（tid=5〜15） |
| 多重アクセス時の動作 | **キューイング対応**（IPC4 Pool 方式により自動） |
| 直列化の保証 | FileMgr は単一タスク。メインループが IPC4-RECV に戻るまで次要求は処理されない。IPC4 Pool（MsgPool 32 エントリ）が保留メッセージを FIFO 保持する |
| FileMgr 内部状態の保護 | 単一タスクかつ「1要求を最後まで処理してから次の IPC4-RECV」方式のため、ディレクトリ・オープンテーブル・セクタバッファへの同時アクセスは構造上発生しない |

ストレージドライバ（§3.3）と同じく「単一サーバタスク + 同期RPC」でアトミシティを保証する。FileMgr は STOR への IPC4-CALL 中（WAIT_REPLY 中）にスケジューラに切り替わるが、その間 FileMgr のメインループは IPC4-RECV に戻っていないため、新規 SVC_FILE 要求は IPC4 Pool にキューイングされるだけで FileMgr の内部状態は変更されない。

**【MsgPool エントリ消費の試算】（v1.1 追記。社内レビュー指摘）**

FileMgr が STOR へ IPC4-CALL 中（WAIT_REPLY）に新規 SVC_FILE 要求が来た場合、その要求は MsgPool（32 エントリ、yuios_ipc4_pool_design_v1_3.md）にキューイングされる。最悪ケースの試算は以下のとおり。

| 消費要因 | 同時占有エントリ数 | 備考 |
| --- | --- | --- |
| FileMgr の入力キュー（保留中 SVC_FILE 要求） | 最大 11 | 想定クライアント tid=5〜15 が各 1 件発行（同期 RPC のため 1 クライアント＝同時 1 件） |
| FileMgr → STOR への発行中メッセージ | 1 | FileMgr は同期 RPC、同時 1 件のみ |
| STOR の入力キュー（FileMgr 以外からの要求） | 0〜数件 | STOR を直接使うクライアントがいれば加算 |
| IPC4-REPLY 経路 | 0 | REPLY はプールを使わず TCB に直接書込（IPC4 設計 §4.2） |

最悪同時占有 ≒ 11 + 1 + α ＜ 32。**MsgPool 32 エントリで枯渇しない**。ただし将来クライアント数が増えた場合や、ProcMgr が FileMgr へ短時間に複数要求を積む設計に変わった場合は再試算が必要。IPC4-CALL は ERR_IPC_NOSLOT（プール枯渇）を返しうるため、FileMgr の STOR 呼び出し箇所では戻り値を必ずチェックする（§5.4・KY6）。

## 3. フラットFS ディスクレイアウト

### 3.1 全体レイアウトと容量設計

フラットFS は YSD8003 ディスク（disk.img）上に以下のレイアウトで構築する。

| **LBA** | **セクタ数** | **領域** | **用途** |
| --- | --- | --- | --- |
| 0 | 1 | スーパーブロック | FS 識別子・バージョン・諸元 |
| 1〜3 | 3 | ディレクトリ領域 | ディレクトリエントリ 32 個（48B × 32 = 1536B = 3 セクタ） |
| 4〜 | 残り全部 | データ領域 | ファイル本体（連続割り当て） |

**容量設計（kaizen 原則17：上限の根拠と拡張試算）：**

| **項目** | **値** | **根拠** |
| --- | --- | --- |
| LBA 幅 | 16 bit | STOR_READ/WRITE の arg0 が 1 ワード（yuios_ph3_storage_design_v1_3.md §6.1） |
| 最大セクタ数 | 65536 | 16bit LBA の表現範囲（0〜65535） |
| セクタサイズ | 512 B | YSD8003 仕様 |
| **最大ディスク容量** | **32 MB** | 65536 × 512 = 33,554,432 B |
| メタ領域 | 4 セクタ（2048 B） | スーパーブロック 1 + ディレクトリ 3 |
| 最大データ領域 | 65532 セクタ（約 31.99 MB） | 65536 − 4 |

**【2GB 非対応の明記】** 当初ユーザ要望は 2GB であったが、現行 YUI OS / YSD8003 アーキテクチャの LBA 幅は 16bit であり、扱えるのは 32MB が上限である。2GB を扱うには 32bit LBA 化（IPC4 メッセージ構造・STOR ドライバ・YSD8003 MMIO 仕様・emu23 すべての改修）が必要であり、これは Ph.4 のスコープ外の別フェーズ級改修である。本設計は **案A（32MB 上限）**を採用する（2026-05-18 ユーザ確定）。32bit LBA 化は将来フェーズに送る。

**【拡張試算】** 将来 32bit LBA 化した場合、本書のディスクレイアウト（スーパーブロック・ディレクトリ・データ領域の構造）はそのまま流用可能である。スーパーブロックの諸元フィールド（total_sectors 等）を 32bit 化し、ディレクトリエントリの start_sec / sec_count を 32bit 化すれば対応できる。ディレクトリエントリは 48B のうち 22B が予約領域であり、フィールド拡幅の余地は十分にある（§3.4）。

**【emu23 実行時のディスクサイズ】** Ph.3-B の動作確認では `dd if=/dev/zero of=disk.img bs=512 count=2048`（2048 セクタ = 1 MB）が用いられている。Ph.4 のテストでも 1 MB で十分（§8）。設計上の上限は 32MB だが、テスト用イメージサイズは別途指定する。

### 3.2 スーパーブロック（LBA=0、512 B）

スーパーブロックは FS のメタ情報を保持する。512B のうち先頭 32B を使用し、残りは予約とする。

| **オフセット** | **サイズ** | **フィールド名** | **型** | **内容** |
| --- | --- | --- | --- | --- |
| +0 | 8 B | magic | バイト列 | FS 識別子。ASCII 文字列 `"YUIFS\0\0\0"`（後述） |
| +8 | 1 B | ver_major | u8 | フラットFS フォーマット メジャーバージョン。本書は **1**（v1.1 で分離） |
| +9 | 1 B | ver_minor | u8 | フラットFS フォーマット マイナーバージョン。本書は **1**（v1.1 で分離） |
| +10 | 2 B | sector_size | u16 | セクタサイズ（512 固定） |
| +12 | 2 B | total_sectors | u16 | ディスク全体のセクタ数（mkfs が設定） |
| +14 | 2 B | dir_start | u16 | ディレクトリ領域開始 LBA（=1 固定） |
| +16 | 2 B | dir_sectors | u16 | ディレクトリ領域セクタ数（=3 固定） |
| +18 | 2 B | dir_entries | u16 | ディレクトリエントリ総数（=32 固定） |
| +20 | 2 B | data_start | u16 | データ領域開始 LBA（=4 固定） |
| +22 | 2 B | data_sectors | u16 | データ領域セクタ数（= total_sectors − 4） |
| +24 | 2 B | next_free_sec | u16 | 次に割り当てるデータセクタの LBA（連続割り当て用の「先頭ポインタ」。後述 §3.5） |
| +26 | 2 B | file_count | u16 | 現在の有効ファイル数（0〜32） |
| +28 | 4 B | (予約) | — | 将来拡張（32bit LBA 化時の上位ワード等） |
| +32〜+511 | 480 B | (予約) | — | 将来拡張 |

**【version フィールドの major/minor 分離】（v1.1 変更。review18 指摘）**

v1.0 では version を 2 B 単一フィールドとしていたが、review18 の指摘により **+8 ver_major（1 B）／ +9 ver_minor（1 B）に分離**する。フィールド全体のオフセット（+8 から 2 B）は v1.0 と同一であり、ディスクレイアウトの後続フィールドはずれない。

マウント時の version 照合方針（§5.4 FS-MOUNT で実装）：

| 照合結果 | FileMgr の動作 | 理由 |
| --- | --- | --- |
| magic 不一致 | 未マウント（FS-MOUNTED=0、全操作 E_IOERR） | 未フォーマット or 別 FS |
| magic 一致・ver_major 不一致 | **マウント拒否**（FS-MOUNTED=0、全操作 E_IOERR） | レイアウト非互換。誤ったレイアウト解釈による破壊を防ぐ |
| magic 一致・ver_major 一致・ver_minor 不一致 | **マウント許可（警告のみ）** | 後方互換変更（予約フィールドの利用等）。動作は継続 |
| magic 一致・両方一致 | 正常マウント | — |

この分離により、将来 Phase 2/FAT 移行や DE 拡張で「magic は一致するが layout が違う」ケースに対し、ディスク破壊を伴わず安全にマウント拒否できる。Phase 1 では ver_major=1, ver_minor=1 を mkfs が書き込み、FileMgr は ver_major=1 のみ受理する。

**magic フィールドの値：** 8 バイト固定で、ASCII の `'Y' 'U' 'I' 'F' 'S' 0x00 0x00 0x00` とする。FileMgr 起動時にこの値を照合し、不一致なら「未フォーマット」と判断する（§5.4）。

**設計判断：**
- スーパーブロックに諸元（dir_start 等）を持たせることで、FileMgr のコードはアドレスをハードコードせずスーパーブロックから読む方式も採れる。ただし Phase 1 では値が固定（dir_start=1 等）であるため、FileMgr 実装はこれらを定数として扱ってよい（§5.5 で後述）。スーパーブロックの諸元は「将来の柔軟性のための記録」と「magic 照合・next_free_sec / file_count の永続化」の2つの役割を持つ。
- `next_free_sec` と `file_count` は **書き込みのたびに更新され、ディスクに書き戻される**動的フィールドである（§3.5・§4.4）。

### 3.3 ディレクトリ領域（LBA=1〜3）

ディレクトリ領域は 3 セクタ（1536 B）で、48B のディレクトリエントリを 32 個格納する。

| **項目** | **値** |
| --- | --- |
| 開始 LBA | 1 |
| セクタ数 | 3 |
| 1 エントリサイズ | 48 B |
| エントリ総数 | 32（= 1536 B / 48 B、3 セクタにちょうど収まる） |
| 1 セクタあたりエントリ数 | 10.66… → **後述の配置規則参照** |

**【重要】エントリのセクタ跨ぎ：** 48B エントリは 512B セクタを割り切らない（512 / 48 = 10.67）。エントリ index と LBA・セクタ内オフセットの対応は「ディレクトリ領域全体を 1536B の連続バイト列とみなし、`index × 48` で算出した絶対オフセットを 512 で割って LBA とオフセットを求める」方式とする。

```
エントリ index e（0〜31）に対し:
  abs_offset = e * 48
  LBA        = 1 + (abs_offset / 512)        … 整数除算
  sec_offset = abs_offset mod 512
```

この結果、一部のエントリ（例：index=10 は abs_offset=480、セクタ末尾に 32B、次セクタに 16B）は **2 セクタにまたがる**。FileMgr のディレクトリ読み書きは「ディレクトリ領域 3 セクタを一括でバッファに読み込んでから操作する」方式とし、セクタ跨ぎ問題を回避する（§5.2・§5.6）。

| エントリ index | abs_offset | LBA | sec_offset | セクタ跨ぎ |
| --- | --- | --- | --- | --- |
| 0 | 0 | 1 | 0 | なし |
| 10 | 480 | 1 | 480 | **あり**（LBA1 末尾32B + LBA2 先頭16B） |
| 21 | 1008 | 2 | 496 | **あり**（LBA2 末尾16B + LBA3 先頭32B） |
| 31 | 1488 | 3 | 464 | なし（末尾 48B が LBA3 内に収まる：464+48=512） |

### 3.4 ディレクトリエントリ構造（48 B）

yuios_design_v2_2.md §7.1.2 の定義を基線とし、本書で各フィールドの詳細を確定する。

| **オフセット** | **サイズ** | **フィールド** | **型** | **説明** |
| --- | --- | --- | --- | --- |
| +0 | 16 B | name | char[16] | ファイル名。NULL 終端 ASCII 文字列。最大 15 文字 + NULL。未使用バイトは 0 |
| +16 | 4 B | size | u32 | ファイルサイズ（バイト単位）。32bit |
| +20 | 2 B | start_sec | u16 | ファイル先頭データの LBA |
| +22 | 2 B | sec_count | u16 | ファイルが占有するセクタ数 |
| +24 | 2 B | flags | u16 | 属性ビット（下表） |
| +26 | 22 B | (予約) | — | 将来拡張（タイムスタンプ・FAT12 移行時のクラスタ番号等） |

**flags ビット定義：**

| **ビット** | **名称** | **意味** |
| --- | --- | --- |
| bit0 | FLG_USED | 1 = 使用中エントリ、0 = 空きエントリ |
| bit1 | FLG_EXEC | 1 = 実行可能ファイル（Cバイナリ。Ph.5 ProcMgr が参照） |
| bit2〜15 | (予約) | 将来拡張（読み取り専用・隠し属性等） |

**設計判断：**
- 空きエントリの判定は **flags の bit0（FLG_USED）が 0** であることとする。name の先頭バイトが 0 かどうかでも判定可能だが、flags を正とする（明示的なフラグの方が削除済みエントリの再利用などで混乱が少ない）。
- `size` はバイト単位の正確なファイルサイズ。`sec_count` は `ceil(size / 512)` であり、ファイル末尾セクタには未使用パディングが生じる。
- `start_sec` と `sec_count` で「ファイルは start_sec から sec_count 個の連続セクタ」を表す（連続割り当て、§3.5）。

**【Phase 1 ファイルサイズ上限（★v1.6.1・C1 対応・known limitation）】**

DE の size は 4B（u32）として確保されているが、**Phase 1 では下位 16bit のみを運用する**（DE-SIZE/OT-SIZE とも Forth の `@`/`!` で 16bit 読み書き）。これにより Phase 1 のファイルサイズ上限は **65535 バイト（≈ 64KB）**となる。

| 項目 | Phase 1 の値 |
| --- | --- |
| 1 ファイルの最大サイズ | 65535 B（u16 上限。size 上位 16bit は 0 固定運用） |
| ディスク総容量（テスト構成） | 32KB（64 セクタ、§8.4）。データ領域は LBA4〜63 = 60 セクタ = 30720 B |
| 矛盾の有無 | **なし**。テスト構成のディスク総容量（32KB）が既にファイルサイズ上限（64KB）より小さいため、u16 運用で実害は生じない |

**根拠（kaizen 原則3：実測突き合わせ）：** §8.4 のテスト構成はディスク 32KB（64 セクタ）であり、単一ファイルがディスク全体を占めても最大 30720 B（データ領域 60 セクタ分）にしかならない。これは u16 上限（65535 B）の範囲内であり、Phase 1 で size を 16bit 運用してもファイルサイズが上限に達することはない。将来 64KB を超えるファイルや大容量ディスクを扱う場合（Phase 2 の FAT12 移行時等）に size を u32 フル運用へ拡張する（§10 将来課題）。FILE_READ（§4.3.3）が file_size を読み取り上限計算に使う際も、この 16bit 運用前提で動作する。

### 3.5 セクタ割り当て方式：連続割り当て（contiguous allocation）

Phase 1 のフラットFS は**連続割り当て**を採用する。各ファイルは start_sec から始まる連続したセクタ列に格納される。

**設計判断の根拠：**

| **項目** | **連続割り当て（採用）** | **採用しないFAT方式** |
| --- | --- | --- |
| メタデータ | start_sec + sec_count の 4 B のみ | セクタ連鎖テーブル（FAT）が必要 |
| 実装複雑度 | 低（LBA = start_sec + 論理セクタ番号） | 高（連鎖をたどる） |
| 断片化 | 発生する（削除後の穴） | 発生しにくい |
| ファイル拡張 | 困難（後続セクタが空いていないと不可） | 容易 |
| Phase 1 適合性 | ◎（シェル+簡易FSには十分） | 過剰 |

連続割り当ては「ファイルの途中削除で穴が空く」「既存ファイルの拡張ができない」という欠点があるが、Phase 1 のフラットFS は「実装の簡易さを優先」する位置づけ（yuios_design_v2_2.md §7.1）であり、これらの欠点は許容する。断片化の本格対策・ファイル拡張は Phase 2（FAT12 移行）で解決する。

**空きセクタ管理：next_free_sec 方式（追記専用アロケータ）**

Phase 1 では空きセクタビットマップを持たず、スーパーブロックの `next_free_sec` 1 個だけで管理する。

```
ファイル新規作成時のセクタ割り当て:
  必要セクタ数 n = ceil(size / 512)
  割り当て start_sec = next_free_sec
  next_free_sec += n          … 単調増加
```

- `next_free_sec` は**単調増加**する。ファイルを削除しても `next_free_sec` は戻さない（穴は再利用しない）。
- これにより「割り当て済み領域は data_start 〜 next_free_sec−1 の連続範囲」というシンプルな不変条件が保たれる。
- 欠点：削除を繰り返すとディスクが論理的に枯渇する（物理的には空きがあるのに next_free_sec が末尾に達する）。Phase 1 では許容し、Phase 2 で空き管理を導入する。

**【設計判断：FILE_WRITE が新規ファイル作成時にサイズを要求する理由】** 連続割り当て + next_free_sec 方式では、ファイル作成時に「最終的なファイルサイズ」が分からないとセクタ数を確保できない。よって本設計の FILE_WRITE は「**新規ファイルを作成し、指定サイズ分のデータを一括書き込みする**」セマンティクスとする（§4.4）。逐次追記によるサイズ拡張は Phase 1 では非対応とする（§4.5 で制約を明記）。

## 4. IPC4 メッセージ仕様（SVC_FILE = 0x02）

### 4.1 サービス操作一覧

yuios_design_v2_2.md §7.2 の 8 操作を基線とする。opcode は上位 8bit = サービスID（0x02）、下位 8bit = 操作番号。

| **操作名** | **opcode** | **msg1 (arg0)** | **msg2 (arg1)** | **msg3 (arg2)** | **戻り値 (r0)** |
| --- | --- | --- | --- | --- | --- |
| FILE_OPEN | 0x0201 | name_addr | 0 | 0 | fid（0〜3） or 負のエラーコード |
| FILE_CLOSE | 0x0202 | fid | 0 | 0 | 0=成功 / 負=エラー |
| FILE_READ | 0x0203 | fid | dst_addr | size | 実読み込みバイト数 / 負=エラー |
| FILE_WRITE | 0x0204 | name_addr | src_addr | size | 0=成功 / 負=エラー（§4.4 参照） |
| FILE_SEEK | 0x0205 | fid | offset | 0 | 新オフセット / 負=エラー |
| FILE_STAT | 0x0206 | name_addr | stat_buf | 0 | 0=成功 / 負=エラー |
| FILE_LIST | 0x0207 | buf_addr | buf_size | 0 | エントリ数 / 負=エラー |
| FILE_DELETE | 0x0208 | name_addr | 0 | 0 | 0=成功 / 負=エラー（open 中は E_BUSY。§4.6） |

**【FILE_WRITE の引数が他と異なる点に注意】** 後述 §4.4 の設計判断により、FILE_WRITE は fid ではなく name_addr を受け取る（新規ファイル作成 + 一括書き込みセマンティクス）。yuios_design_v2_2.md §7.2 では FILE_WRITE の arg0 が「ファイルID」となっているが、連続割り当て方式（§3.5）との整合のため本書で name_addr に変更する。これは上位設計書からの逸脱であり、§10 で yuios_design_v2_2.md §7.2 の改版を要請する。

### 4.2 エラーコード定義

戻り値 r0 が負値のときエラー。エラーコードは 16bit の負値（2 の補数）で表現する。

**【v1.1 変更：FS 系エラーコードを $FE00 台へ分離】（社内レビュー＋review18 指摘）**

v1.0 では FS エラーを $FFFF 〜 $FFF7（−1 〜 −9）に割り当てていたが、IPC4 Pool のプール枯渇エラー `ERR_IPC_NOSLOT = $FFFE`（yuios_ipc4_pool_design_v1_3.md §5.5）と `E_NOSPC` が同値になり、クライアントが「ディスク満杯（リトライ無効）」と「カーネル IPC 枯渇（リトライ有効）」を区別できない問題があった。両者は運用対処が全く異なる。

v1.1 では **namespace を分離**する：

| 値域 | 用途 |
| --- | --- |
| $FF00 台（$FF00〜$FFFF） | カーネル／IPC 系エラー（ERR_IPC_NOSLOT 等。IPC4 設計書の管轄） |
| $FE00 台（$FE00〜$FEFF） | FileMgr／FS 系エラー（本書の管轄） |

FileMgr エラーコード（v1.1 確定、v1.2 で E_BUSY 追加）：

| **定数名** | **値（16bit）** | **意味** |
| --- | --- | --- |
| E_OK | $0000 (0) | 成功 |
| E_NOENT | $FE01 | ファイルが存在しない |
| E_NOSPC | $FE02 | ディスク空き容量不足（next_free_sec 超過） |
| E_MFILE | $FE03 | オープンファイル数が上限（4）に達した |
| E_BADF | $FE04 | 不正な fid（未オープン・範囲外） |
| E_NAMETOOLONG | $FE05 | ファイル名が 15 文字を超える |
| E_EXIST | $FE06 | 同名ファイルが既に存在する（FILE_WRITE 時） |
| E_NODIRSPC | $FE07 | ディレクトリエントリの空きがない（32 個使用済み） |
| E_IOERR | $FE08 | ストレージ I/O エラー（STOR_READ/WRITE が −1 を返した） |
| E_INVAL | $FE09 | 引数不正（size 過大・offset 負値等） |
| E_FSVER | $FE0A | FS フォーマットの ver_major 不一致（マウント拒否。§5.4） |
| E_BUSY | $FE0B | 対象ファイルが open 中のため操作不可（FILE_DELETE 時。§4.6・v1.2 追加） |

**【エラー判定方法】** 戻り値 r0 は「成功＝0／正値（READ の実バイト数・OPEN の fid 等）」または「FS エラー＝$FE0x」または「IPC エラー＝$FF0x」のいずれか。クライアントは以下で判別する：

```
r0 == 0           → 成功（戻り値なし操作）
0 < r0 < $FE00    → 成功（戻り値あり：fid, 実読み込み量, エントリ数 等）
$FE00 <= r0 < $FF00 → FileMgr エラー（FS 系。リトライ可否は種別による）
$FF00 <= r0       → IPC/カーネルエラー（プール枯渇等。リトライで回復しうる）
```

すべて 16bit 符号付きで見れば負値であり、「r0 < 0 ならエラー」という大まかな判定も従来どおり成立する。値域で IPC 系と FS 系を切り分けられる点が v1.0 からの改善である。

**【fid の値域との非干渉】** FILE_OPEN が返す fid は 0〜3 であり、エラー値域（$FE00 以上）と干渉しない。FILE_READ が返す実読み込みバイト数は最大でもファイルサイズ（32MB 未満）だが、1 回の READ 要求サイズは呼び出し側 size 引数で制限され、$FE00（=65024）を超える単一 READ は §4.3.3 で E_INVAL とするため、戻り値が誤ってエラー値域に入ることはない（§4.3.3 に上限チェックを明記）。

### 4.3 メッセージ詳細：読み取り系（OPEN / READ / SEEK / STAT / LIST / CLOSE）

#### 4.3.1 FILE_OPEN (0x0201)  ★v1.6 拡充

クライアント側：
```forth
\ name-addr: NULL終端ファイル名文字列のアドレス
0 0 name-addr FILE-OPEN-OP FILEMGR-TID @ IPC4-CALL
\ r0 = fid（0〜3） or 負エラー（E_NOENT, E_MFILE, E_NAMETOOLONG, E_IOERR）
```

##### 4.3.1.1 引数仕様

| 引数 | 名前 | 型 | 値域 | 説明 |
|---|---|---|---|---|
| arg0 | name_addr | 16bit unsigned | $0000-$FFFF | NULL 終端ファイル名文字列の先頭アドレス |
| arg1 | (予約) | 16bit | **必ず 0** | 将来拡張用（open フラグ等）。Phase 1 では検査せず無視する（§4.3.1.6 参照） |
| arg2 | (予約) | 16bit | **必ず 0** | 同上 |

##### 4.3.1.2 処理手順

1. name_addr の文字列長を NAME-LEN で検査。**16（=NULL 含めて 16 バイトに収まらない、すなわち 15 文字超）**なら E_NAMETOOLONG を返す
2. FS-MOUNTED が 0 なら E_IOERR を返す（未マウント時の共通動作。§5.4）
3. DIR-FIND で name 一致 & FLG_USED=1 のディレクトリエントリ index を検索。見つからなければ（index = -1）E_NOENT を返す
4. オープンファイルテーブル（§5.3）の空きスロット（OT-USED=0 の最小 index）を DIR-FIND-FREE と同型の走査で探す。空きがなければ E_MFILE を返す
5. 見つけたスロット fid に、以下をディレクトリエントリからコピーして記録する：
   - OT-USED = 1（使用中へ遷移）
   - OT-DIR-INDEX = 手順 3 で得た dir_index
   - OT-START-SEC = DE の start_sec（DE+20、検索省略用キャッシュ）
   - OT-SIZE = DE の size 下位 16bit（DE+16）
   - OT-POS = 0（論理オフセット初期化）
6. スロット index を fid（0〜3）として r0 に返す

##### 4.3.1.3 戻り値

| 戻り値 r0 | 意味 |
|---|---|
| **0〜3（fid）** | オープン成功。以降この fid で READ/SEEK/STAT/CLOSE する |
| **E_NAMETOOLONG** ($FE05) | ファイル名が 15 文字超 |
| **E_IOERR** ($FE08) | FS 未マウント |
| **E_NOENT** ($FE01) | 指定 name のファイルが存在しない |
| **E_MFILE** ($FE03) | オープン数が上限（4）に達した |

戻り値の値域は §4.2 のとおり「0〜3＝非負＝有効 fid」「$FE00 台＝符号付き負＝エラー」で完全に分離されており、クライアントは `r0 < 0`（符号付き）または `r0 >= $FE00`（符号なし）でエラー判定できる。

##### 4.3.1.4 境界条件

| 条件 | 動作 |
|---|---|
| name_addr が空文字列（先頭が NULL） | NAME-LEN=0。DIR-FIND は「長さ 0 の名前」を探すが、mkfs/FILE_WRITE は空名ファイルを作らないため通常 E_NOENT。異常系として許容（クラッシュしない） |
| name 長 = 15 文字（ちょうど上限） | OK（NAME-LEN=15 < 16）。オープン可能 |
| name 長 = 16 文字以上 | E_NAMETOOLONG（NAME-LEN は 16 で打ち切るため 16 を返し、`16 < 16` が偽 → 長さ超過と判定） |
| 同名ファイルを 2 回以上 open | **いずれも成功**（多重 open 許可。§4.6）。各 fid は独立スロット・独立 pos を持つ |
| 全 4 スロット使用中 | E_MFILE |
| FS-MOUNTED = 0 | E_IOERR（一切走査しない） |

##### 4.3.1.5 副作用

| 対象 | 影響 |
|---|---|
| FS-DIRBUF | 読み取りのみ（DIR-FIND が走査） |
| FS-OPENTAB | 成功時、1 スロットを「使用中」に書き換える（OT-USED/DIR-INDEX/START-SEC/SIZE/POS を設定） |
| FM-WK-* | DIR-FIND が FM-WK-SRC/LEN/A/B/C/DST を破壊する。OPEN 固有のループ変数は R スタックで保持し、ワーク変数の流用を避ける（§5.8） |

##### 4.3.1.6 arg1/arg2 を検査しない理由（v1.6 設計判断）

FILE_LIST（§4.3.6）は arg2≠0 を E_INVAL で弾くガードを持つが、FILE_OPEN は **arg1/arg2 を検査しない**。理由：

- Phase 1 の FILE_OPEN は「name 指定・読み取り専用ハンドル取得」のみで、open フラグ（O_RDONLY/O_WRONLY 等）の概念がない。将来フラグを arg1 に載せる際、「Phase 1 は 0 必須」と固定してしまうと、フラグ導入時に旧クライアントとの互換が複雑化する
- クライアント（§4.3.1 の呼び出し例）は arg1/arg2 に 0 を積むことを規約とするが、FileMgr 側は将来の拡張余地を残すため未検査とする
- これは FILE_OPEN が「name という 1 引数で完結する操作」であり、arg1/arg2 が純粋に未使用枠である点が FILE_LIST（arg2 を「予約=0 必須」として明示的に値域定義した）と異なるためである

**【kaizen 原則7：前提条件の明記】** クライアントは arg1/arg2 に 0 を積むこと（将来互換のため）。FileMgr はこれらを読まないが、規約としては 0 とする。

#### 4.3.2 FILE_CLOSE (0x0202)  ★v1.6 拡充

```forth
0 0 fid FILE-CLOSE-OP FILEMGR-TID @ IPC4-CALL
\ r0 = 0（成功） or E_BADF
```

##### 4.3.2.1 引数仕様

| 引数 | 名前 | 型 | 値域 | 説明 |
|---|---|---|---|---|
| arg0 | fid | 16bit | 0〜3（有効）/ それ以外は E_BADF | クローズ対象のファイル ID（OPEN が返した値） |
| arg1 | (予約) | 16bit | **必ず 0** | 将来拡張用。未検査（§4.3.1.6 と同方針） |
| arg2 | (予約) | 16bit | **必ず 0** | 同上 |

##### 4.3.2.2 処理手順

1. FID-VALID?（§6.6・実装済み）で fid を検査する。FID-VALID? は「fid が 0〜3 の範囲内（`0 <= fid < FS-MAX-OPEN`）かつ OT-USED=1」のときのみ真を返す
2. FID-VALID? が偽（範囲外 or 未オープン）なら E_BADF を返す
3. 有効なら、当該スロットの OT-USED を 0 にする（使用中→未使用へ遷移）。他のフィールド（DIR-INDEX/START-SEC/SIZE/POS）はクリアしなくてよい（OT-USED=0 が「無効スロット」を意味するため、残存値は次回 OPEN 時に上書きされる）
4. r0 = E_OK（0）を返す

##### 4.3.2.3 戻り値

| 戻り値 r0 | 意味 |
|---|---|
| **0（E_OK）** | クローズ成功 |
| **E_BADF** ($FE04) | 不正な fid（範囲外 0..3 外、または既に未オープンのスロット） |

##### 4.3.2.4 境界条件

| 条件 | 動作 |
|---|---|
| fid が負値（符号付き）または 4 以上 | E_BADF（FID-VALID? の範囲チェックで弾く） |
| fid が範囲内だが OT-USED=0（二重 close / 未 open） | E_BADF（FID-VALID? の used チェックで弾く） |
| FS-MOUNTED = 0 | FILE_CLOSE は FS-OPENTAB（RAM）のみ操作しディスクに触れないため、未マウントでも fid が有効なら成功する。ただし未マウント中は OPEN が成立しないため、通常 OT-USED=1 のスロットは存在せず E_BADF となる |

**【設計判断・v1.6】FS-MOUNTED チェックを CLOSE に置かない理由：** FILE_OPEN/STAT/LIST/READ/WRITE/DELETE は全て FS-DIRBUF またはディスクへアクセスするため FS-MOUNTED ガードが必要だが、FILE_CLOSE は FS-OPENTAB（RAM）の used フラグを下ろすだけでディスクに一切触れない。よって FS-MOUNTED チェックは不要であり、むしろ「マウント中にオープンしたファイルを、何らかの理由で再マウント（FILEMGR-INIT 再実行）された後に close しようとする」ような異常系でも、fid が範囲外/未used なら E_BADF で安全に弾ける。FID-VALID? 一本で判定が閉じる。

##### 4.3.2.5 副作用

| 対象 | 影響 |
|---|---|
| FS-OPENTAB | 成功時、当該スロットの OT-USED を 0 にする（それ以外のフィールドは不変） |
| FS-DIRBUF / ディスク | 一切触れない |
| FM-WK-* | REPLY-OK が FM-WK-A/B を破壊するのみ。CLOSE 本体はワーク変数を使わない（スタック上で完結） |

##### 4.3.2.6 OPEN/CLOSE ペアのライフサイクル（v1.6・KY19）

FILE_OPEN と FILE_CLOSE は FS-OPENTAB を介して対をなす。両者が共有する不変条件を以下に確定する（§5.3 の状態遷移と一体）：

- **OPEN は OT-USED 0→1 への唯一の遷移点**。OPEN 成功時のみスロットが「使用中」になる
- **CLOSE は OT-USED 1→0 への唯一の遷移点**。CLOSE 成功時のみスロットが「未使用」に戻る
- READ/SEEK/STAT/WRITE/DELETE は OT-USED を変更しない（READ/SEEK は OT-POS のみ更新）
- この「遷移点を OPEN/CLOSE の 2 箇所のみに限定する」設計により、スロット状態の一貫性が構造的に保たれる（kaizen 設計原則3：状態変数の変更箇所を一箇所に集約、の精神）

#### 4.3.3 FILE_READ (0x0203)

```forth
size dst-addr fid FILE-READ-OP FILEMGR-TID @ IPC4-CALL
\ r0 = 実読み込みバイト数 or 負エラー
```

FileMgr 動作：
1. fid のオープンスロットを取得（不正なら E_BADF）
2. size が $FE00（=65024）以上なら E_INVAL（戻り値値域がエラー値域と干渉しないため。§4.2）。通常 size は 1 セクタ〜数 KB であり実用上問題ない
3. 現在の論理オフセット pos から、min(size, file_size − pos) バイトを読む（実読み込み量 = actual）。file_size は OPENTAB スロットの OT-SIZE（Phase 1 は下位 16bit 運用、最大 65535 B。§3.4 ファイルサイズ上限 known limitation 参照）
4. pos を含むセクタから順に STOR_READ でセクタ単位に読み込み、必要部分を dst_addr へコピー
5. 論理オフセット pos を actual だけ進める
6. r0 = actual を返す（EOF 到達時は actual < size、pos==file_size なら actual=0）

セクタ境界をまたぐ場合の詳細は §6.3 に記載。

#### 4.3.4 FILE_SEEK (0x0205)

```forth
0 offset fid FILE-SEEK-OP FILEMGR-TID @ IPC4-CALL
\ r0 = 新しい論理オフセット or 負エラー
```

FileMgr 動作：fid のオープンスロットの論理オフセットを offset（ファイル先頭からの絶対位置）に設定する。Phase 1 では絶対シークのみ（SEEK_SET 相当）。offset がファイルサイズを超える場合は E_INVAL（Phase 1 ではファイル末尾を超えるシークを許可しない）。

#### 4.3.5 FILE_STAT (0x0206)

```forth
0 stat-buf name-addr FILE-STAT-OP FILEMGR-TID @ IPC4-CALL
\ r0 = 0 or E_NOENT
```

FileMgr 動作：name のディレクトリエントリを検索し、stat_buf に以下の構造（16 B）を書き込む。

| オフセット | サイズ | フィールド | 内容 |
| --- | --- | --- | --- |
| +0 | 4 B | size | ファイルサイズ（バイト） |
| +4 | 2 B | start_sec | 先頭 LBA |
| +6 | 2 B | sec_count | セクタ数 |
| +8 | 2 B | flags | 属性 |
| +10 | 6 B | (予約) | 0 埋め |

#### 4.3.6 FILE_LIST (0x0207)  ★v1.5 拡充

```forth
0 buf-size buf-addr FILE-LIST-OP FILEMGR-TID @ IPC4-CALL
\ r0 = 列挙したエントリ数 or 負エラー
```

##### 4.3.6.1 引数仕様

| 引数 | 名前 | 型 | 値域 | 説明 |
|---|---|---|---|---|
| arg0 | buf_addr | 16bit unsigned | $0000-$FFFF | 名前リストの書き込み先（呼び出し側で確保） |
| arg1 | buf_size | 16bit unsigned | 0-$FFFF（バイト単位） | buf_addr の有効サイズ |
| arg2 | (予約) | 16bit | **必ず 0** | 将来拡張用。0 以外は E_INVAL を返す |

##### 4.3.6.2 出力形式（Phase 1）

buf_addr に「**16 バイト固定長の name フィールド × エントリ数**」を連続書き込みする。

```
buf_addr +  0 : entry[0].name (16B, 末尾は \0 パディング)
buf_addr + 16 : entry[1].name (16B)
buf_addr + 32 : entry[2].name (16B)
              :
buf_addr + 16*(n-1) : entry[n-1].name (16B)
```

- name フィールドはディレクトリエントリの `DE-NAME` オフセット +0 から 16B をそのまま転記する（NUL パディング含む）
- ファイルサイズ・フラグ等のメタ情報は **含まない**（必要な場合は FILE_STAT で個別取得）
- セパレータは入れない（呼び出し側は固定 16B ストライドで読む）

##### 4.3.6.3 戻り値

| 戻り値 r0 | 意味 |
|---|---|
| **n（0以上）** | buf_addr に書き込んだエントリ数（n 個 × 16B = 16n バイト書き込まれた） |
| **E_IOERR** ($FE01) | FS 未マウント |
| **E_INVAL** ($FE03) | arg2 が 0 でない |

##### 4.3.6.4 境界条件

| 条件 | 動作 |
|---|---|
| buf_size = 0 | 0 を返す（書き込みは一切行わない、正常終了扱い） |
| buf_size < 16 | 0 を返す（1 エントリすら入らないので何も書かない） |
| FLG_USED=1 エントリ数 = 0 | 0 を返す（ディレクトリが空） |
| buf_size ≥ 16N かつ 使用中エントリ数 = N | N を返す（全件書き込み完了） |
| buf_size = 16K, 使用中エントリ数 > K | K を返す（K 件だけ書いて打ち切り、エラーにはしない） |
| FS-MOUNTED = 0 | E_IOERR を返す（一切走査しない） |

**重要**：buf 不足は **エラーではない正常打ち切り**として扱う。呼び出し側は「`r0 = K` で `K * 16 == buf_size_used` なら全件取れた」と判定するのではなく、再呼び出しではなく **buf を増やして再呼び出し**することで全件取得する設計とする（Phase 1 のため簡素化）。

##### 4.3.6.5 副作用

| 対象 | 影響 |
|---|---|
| FS-DIRBUF | 読み取りのみ（変更なし） |
| buf_addr 領域 | 書き込み（最大 16 × FS-DIR-ENTRIES = 512B = 32エントリ） |
| FM-WK-* | 走査用一時変数として使用（呼び出し前の値は破壊される） |

##### 4.3.6.6 FS-DIRBUF 前提

DIR-LOAD が事前に呼ばれている必要がある。FILEMGR-INIT で DIR-LOAD 済みのため、通常の使用では問題ない（§5.4.2 参照）。

#### 4.3.7 読み取り系の共通注意

OPEN / SEEK / STAT / LIST / CLOSE は FileMgr の内部状態（オープンテーブル）またはディレクトリの読み取りのみで完結し、STOR への書き込みは発生しない。ただし STAT / LIST / OPEN はディレクトリ領域を STOR_READ で読む必要がある（§5.6 のディレクトリキャッシュ方針参照）。

### 4.4 メッセージ詳細：書き込み系（FILE_WRITE）

#### 4.4.1 FILE_WRITE (0x0204) の設計判断

§3.5 で述べたとおり、連続割り当て + next_free_sec 方式では「ファイル作成時に最終サイズが必要」である。よって FILE_WRITE は次のセマンティクスとする：

> **FILE_WRITE は「新規ファイルを作成し、src_addr から size バイトを一括で書き込んで確定する」操作である。**

```forth
size src-addr name-addr FILE-WRITE-OP FILEMGR-TID @ IPC4-CALL
\ r0 = 0（成功） or 負エラー
```

FileMgr 動作（v1.1：I/O エラー時ロールバック対応）：

1. name の長さ検査（15 文字超なら E_NAMETOOLONG）
2. DIR-LOAD でディレクトリ 3 セクタを FS-DIRBUF に読み込む（STOR_READ エラーなら E_IOERR）
3. 同名ファイルの存在チェック（既存なら E_EXIST。Phase 1 は上書き非対応）
4. 空きディレクトリエントリ index di を探す（なければ E_NODIRSPC）
5. 必要セクタ数 n = ceil(size / 512) を算出
6. 空き容量チェック：next_free_sec + n − 1 が total_sectors を超えるなら E_NOSPC
7. **【v1.1】ロールバック用に現在値を退避**：`old_next_free = FS-NEXT-FREE`、`old_file_count = FS-FILE-COUNT`
8. start_sec = FS-NEXT-FREE を確保（この時点ではメモリ値 FS-NEXT-FREE はまだ進めない）
9. src_addr のデータを 512B セクタ単位で STOR_WRITE（最終セクタの端数は 0 パディング、§6.4）。
   **STOR_WRITE が 1 回でもエラー（r0 ≠ 0）を返したら、即座にロールバックして E_IOERR を返す**（後述 §4.4.2）
10. ディレクトリエントリ（FS-DIRBUF 上の di）に name, size, start_sec, sec_count=n, flags=FLG_USED を書き込む
11. ディレクトリ領域（3 セクタ）をディスクへ DIR-STORE で書き戻す。
    **DIR-STORE がエラーを返したらロールバックして E_IOERR を返す**
12. **メモリ値を確定更新**：`FS-NEXT-FREE += n`、`FS-FILE-COUNT += 1`
13. スーパーブロックの next_free_sec, file_count を SB-STORE でディスクへ書き戻す。
    **SB-STORE がエラーを返したらロールバックして E_IOERR を返す**（§4.4.2 で扱いを詳述）
14. r0 = E_OK（0）を返す

**【v1.0 からの変更点】** v1.0 では手順 6 でメモリ値 next_free_sec を即座に進めていたが、v1.1 では**メモリ値の更新（手順 12）をディスク書き込み成功後まで遅延**させる。これにより I/O エラー時に「メモリ値だけ進んでディスクは古い」という不整合（review18 指摘）を構造的に防ぐ。手順 8 の start_sec 算出は old_next_free の読み取りのみで、FS-NEXT-FREE 変数自体は書き換えない。

#### 4.4.2 FILE_WRITE の I/O エラー時ロールバックと原子性（v1.1 改訂）

**【RAM 内ロールバック】（review18 最重要指摘）**

FILE_WRITE 処理中に STOR_WRITE / DIR-STORE / SB-STORE が I/O エラー（r0 ≠ 0）を返した場合、FileMgr は以下の RAM 内ロールバックを行ってから E_IOERR をクライアントへ返す。これは journaling ではなく単純な RAM 変数の復元であり、実装コストは極めて低い。

| エラー発生箇所 | ロールバック動作 | ディスクの状態 | 復旧可否 |
| --- | --- | --- | --- |
| 手順 9（STOR_WRITE 失敗） | FS-NEXT-FREE / FS-FILE-COUNT は手順 12 未実施のため**そもそも進んでいない**。FS-DIRBUF も手順 10 未実施で未変更。何もせず E_IOERR 返却 | データ領域に部分書き込みが残るが、DE 未登録・next_free_sec 不変のため次回 FILE_WRITE で同じ領域が再利用され上書きされる（孤児セクタ＝実害なし） | ◎ 自動回復 |
| 手順 11（DIR-STORE 失敗） | FS-NEXT-FREE / FS-FILE-COUNT は手順 12 未実施で未変更。FS-DIRBUF のメモリ上の変更は破棄してよい（次回操作で DIR-LOAD し直す）。E_IOERR 返却 | ディレクトリは旧状態のまま（DE 未登録）。データは孤児セクタ。SB も旧状態 | ◎ 自動回復 |
| 手順 13（SB-STORE 失敗） | **FS-NEXT-FREE = old_next_free、FS-FILE-COUNT = old_file_count に巻き戻す**。E_IOERR 返却 | ディレクトリには DE が登録済み（手順 11 成功）だが、SB の next_free_sec は旧値。次回起動時に SB を読むと next_free_sec が古く、登録済みファイルのデータ領域が再割り当て対象になりうる | △ 部分的（後述） |

**手順 13 失敗時の残存リスク：** 手順 11（DIR-STORE）成功後・手順 13（SB-STORE）失敗のケースでは、ディスク上は「DE は登録されたが SB の next_free_sec は古い」という状態になる。次回マウント時、FileMgr は古い next_free_sec を読むため、既存ファイルの領域を新規ファイルに再割り当てしてしまう恐れがある。これは Phase 1 では**許容**する（クラッシュ耐性は Phase 2 課題）。ただし**メモリ上の FS-NEXT-FREE は old に巻き戻す**ことで、「同一起動セッション中」は不整合が顕在化しない（メモリ値が正、次回 FILE_WRITE は old_next_free から再試行されディスク SB も含めて整合する）。完全な対策（SB を先に予約状態で書く 2 フェーズコミット等）は §10 の将来課題とする。

**【Phase 1 既知制限：SB-STORE 失敗時のディスク不整合】（v1.2 明記・review19 指摘）**

上記の手順 13 失敗ケースについて、review19 の指摘を受け Phase 1 の既知制限（known limitation）として以下を明記する。隠さず明示することで、運用時の混乱と「バグか仕様か」の議論を避ける。

| 項目 | Phase 1 の実態 |
| --- | --- |
| 回復可能性 | **FileMgr 単体では完全回復不能**。メモリ巻き戻しは「同一起動セッション中」の整合性のみを保つ。一度電源を切り再 mount すると、ディスク上の「DE 登録済み・SB 古い」状態がそのまま残る |
| fsck の有無 | **未実装**。ディスクの整合性を検査・修復する機構は Phase 1 には存在しない |
| 再 mount 時のリスク | SB の古い next_free_sec を起点に新規 FILE_WRITE を行うと、既に DE 登録済みファイルのデータ領域へ**再割り当て（領域衝突）**が起こりうる。先に書かれたファイルの内容が破壊される |
| 推奨される運用 | SB-STORE 失敗（FILE_WRITE が E_IOERR を返し、かつそれが書き込み末尾段階で起きたと判断される場合）が発生したら、**ディスクの再フォーマット（mkfs）を推奨**する。mkfs により SB・ディレクトリ・next_free_sec が一貫した初期状態へリセットされる |
| 発生頻度の見込み | SB-STORE は LBA0 への 1 セクタ書き込みのみ。emu23 上のストレージは I/O エラーをほぼ起こさないため、本制限が顕在化するのは実 FPGA + 実ストレージで媒体劣化等が起きた場合に限られる。Phase 1 の検証範囲では実害はほぼない |
| 恒久対策 | §10.3 の「クラッシュ耐性（ジャーナリング）」。SB を 2 フェーズコミット（予約状態で先行書き込み → データ確定後に有効化）する方式を Ph.7 以降で導入 |

この制限は contiguous + append-only + no-fsck という Phase 1 の割り切り（§4.6）の裏返しであり、Phase 1 の設計意図の範囲内である。シェル実装時（Ph.6）には、FILE_WRITE が E_IOERR を返した場合のユーザ向けメッセージに「ディスクの再フォーマットを検討してください」の旨を含めることが望ましい。

**【原子性】** FileMgr は単一タスクであり、FILE_WRITE 処理中は他の SVC_FILE 要求を受け付けない（§2.3）。よって FileMgr 内部から見た FILE_WRITE はアトミック（他要求と混ざらない）である。I/O エラー時の RAM 内ロールバックにより、「メモリキャッシュとディスクの不整合」は手順 13 失敗のレアケースを除き発生しない。電源断・ハードクラッシュに対する完全な一貫性保証（ジャーナリング等）は Phase 2 以降の課題とする（§10）。

**【ロールバック用退避変数】** old_next_free / old_file_count は §5.2 の FileMgr 変数領域に 2 ワード確保する（FS-WR-OLD-NEXT / FS-WR-OLD-COUNT）。FILE_WRITE 以外では使用しない。

#### 4.4.3 書き込み順序の設計（重要）

手順 9（データ）→ 手順 11（ディレクトリ）→ 手順 13（スーパーブロック）の順序を**厳守**する。

理由：先にディレクトリ・スーパーブロックを更新してからデータを書くと、データ書き込み中のクラッシュで「ディレクトリ上は存在するがデータが不正なファイル」が生じ、しかも next_free_sec が進んでいるため復旧不能になる。データを先に書けば、最悪でも「孤児セクタ」で済む（§4.4.2）。

加えて v1.1 では**メモリ値 FS-NEXT-FREE / FS-FILE-COUNT の更新（手順 12）をディレクトリ書き戻し成功後・スーパーブロック書き戻し直前に置く**。これにより、データ書き込み失敗時（手順 9）・ディレクトリ書き戻し失敗時（手順 11）には、メモリ値が一切汚れていない状態でロールバックが完了する（実質「何もしない」で済む）。

### 4.5 Phase 1 の制約（明示）

| **制約** | **内容** | **回避策 / Phase 2 での解決** |
| --- | --- | --- |
| 既存ファイルへの追記不可 | FILE_WRITE は新規作成専用。既存ファイルのサイズ拡張はできない | ファイルを削除して作り直す。Phase 2 で FAT12 化により追記対応 |
| 同名ファイルの上書き不可 | 同名が存在すると E_EXIST | 先に FILE_DELETE してから FILE_WRITE |
| FILE_READ 経由の書き込み不可 | fid でオープンしたファイルへの書き込み API はない（fid は読み取り専用ハンドル） | FILE_WRITE（name 指定・一括）を使う |
| セクタの再利用なし | 削除しても next_free_sec は戻らない（§3.5） | Phase 2 で空きセクタ管理を導入 |
| ディレクトリ階層なし | サブディレクトリ非対応（フラット） | 設計方針（Phase 2 でも FAT12 ルート固定のため階層は持たない） |
| クラッシュ耐性なし | 書き込み途中のクラッシュで一貫性は保証されない（§4.4.2） | Phase 2 以降でジャーナリング検討 |
| SB-STORE 失敗時の不整合は完全回復不能 | FILE_WRITE 末尾の SB-STORE が I/O 失敗すると「DE 登録済み・SB 古い」状態が残り、再 mount 時に領域衝突しうる（§4.4.2 既知制限） | 発生時は mkfs（再フォーマット）を推奨。Phase 2 で SB 2 フェーズコミット化 |
| fsck（整合性検査・修復）なし | ディスク不整合を検出・修復する機構は持たない | Phase 2 以降で検討。Phase 1 は mkfs が実質的な回復手段 |

これらは「フラットFS は実装の簡易さを優先」というプロジェクト方針（yuios_design_v2_2.md §7.1）に基づく意図的な制約である。SB-STORE 失敗時の不整合と fsck 非実装の詳細は §4.4.2「Phase 1 既知制限」を参照のこと。

### 4.6 ファイルオープンのセマンティクス確定（v1.1 新設・review18 指摘）

review18 の指摘により、FILE_OPEN の以下のセマンティクスを Phase 1 仕様として確定・明文化する。

**【同一ファイルの多重 open】**

- 同一ファイル名に対する FILE_OPEN は**複数回成功してよい**（同時オープン上限 4 スロットの範囲内）。
- 各 fid（オープンスロット）は**独立した論理オフセット pos を持つ**。FILE_SEEK / FILE_READ による pos 変更は、その fid のスロットにのみ作用し、同じファイルを指す他の fid には影響しない。
- FileMgr は UNIX の inode のような「ファイル単位の共有状態」を持たない。複数の fid が同一のディレクトリエントリ index（dir_index）を参照することは許容され、それぞれ独立した読み取りカーソルとして機能する。
- これは UNIX 的なファイルディスクリプタの挙動と同じであり、Phase 1 ではこの単純な「open ごとに独立 pos」方式を採用する。

この仕様により、例えばシェルが同じファイルを 2 つの fid で開き異なる位置から読む、といった操作が破綻なく行える。Phase 1 では FILE_OPEN は読み取り専用ハンドルを返す（書き込みは FILE_WRITE の name 指定・一括方式のみ。§4.5）ため、多重 open による書き込み競合は構造上発生しない。

**【append-only ファイルシステムとしての性質の明示】**

§3.5 の連続割り当て + next_free_sec 方式と、FILE_DELETE がディレクトリエントリの無効化のみ行う設計（§6.5）を合わせると、Phase 1 のフラットFS は実質的に **append-only filesystem（追記専用ファイルシステム）**である。これは Phase 1 として意図的かつ筋の通った割り切りであり、以下を仕様として明記する：

| 項目 | Phase 1 仕様 |
| --- | --- |
| 空き領域回収（space reclaim） | **非対応**。FILE_DELETE してもディスクの空き容量は増えない |
| FILE_DELETE の実体 | ディレクトリエントリの FLG_USED クリアのみ。データセクタは解放しない（§6.5） |
| 削除済み領域の再利用 | 不可。next_free_sec は単調増加（§3.5） |
| 論理的な「ディスク満杯」 | 削除を繰り返すと、物理的に空きがあっても next_free_sec が末尾に達し E_NOSPC になる |
| 空き領域の回復手段 | ディスクの再フォーマット（mkfs）が実質的な garbage collection を兼ねる |
| 本格的な空き管理 | Phase 2（FAT12 移行）で空きビットマップ／FAT を導入し対応（§10） |

**この性質を明示する理由：** 仕様として書いておかないと、運用時に「FILE_DELETE したのにディスク容量が減らない」という挙動が「バグなのか仕様なのか」で混乱する。Phase 1 では**これは仕様である**。シェルの `df` 相当コマンド（将来）は「next_free_sec ベースの使用量」を表示することになり、削除では減らない旨をユーザに示す必要がある。

**【open 中ファイルの削除の扱い】（v1.2 追加・review19 指摘）**

`FILE_OPEN → FILE_DELETE → FILE_READ(fid)` のように、オープン中のファイルに対して FILE_DELETE を発行する操作の扱いを Phase 1 仕様として確定する。

| 項目 | Phase 1 仕様 |
| --- | --- |
| open 中ファイルの削除 | **禁止**。FILE_DELETE は、対象ファイルを参照中の fid が FS-OPENTAB に 1 つでも存在する場合、削除を行わず **E_BUSY を返す**（§4.2 にエラーコード追加） |
| open reference count | **持たない**。FileMgr は inode 的な参照カウンタを実装しない。FILE_DELETE は FS-OPENTAB の全 4 スロットを走査し、対象ファイルの dir_index と一致するスロットが 1 つでもあれば「使用中」と判定する |
| 判定方法 | FILE_DELETE は対象 name から dir_index を求め（DIR-FIND）、FS-OPENTAB の各スロット +2（dir_index フィールド、§5.3）と照合する。一致スロットがあれば E_BUSY |
| UNIX との違い | UNIX は「削除後も open 中の fd は有効、最後の close で実体解放」（遅延 unlink）だが、append-only でセクタ解放を行わない Phase 1 FS ではこの挙動に意味がなく、かえって「DE が消えたのに fid が dir_index を参照し続ける」という危険な dangling 参照を生む。Phase 1 では単純に「open 中は削除禁止」とする |

**設計判断：** open 中削除を禁止することで、「FILE_READ(fid) の最中に DE が無効化されている」という未定義状態を構造的に排除できる。reference count を持たない分 FileMgr の状態が単純になり、Phase 1 の簡易性方針に合致する。クライアント（シェル等）は「削除したいファイルは先に全 fid を FILE_CLOSE してから FILE_DELETE する」という規律で運用する。E_BUSY を受けたクライアントは、自分または他タスクがそのファイルを開いたままであることを認識できる。

## 5. FileMgr サーバタスクの設計

### 5.1 タスク構成とメインループ

```forth
: FILEMGR-TASK  ( -- )
    FILEMGR-INIT
    BEGIN
        IPC4-RECV                   \ ( -- msg3 msg2 msg1 msg0 )  要求待ち
        IPC4-SENDER-DIRECT >R       \ R: client_tid（応答先を退避）
        FILE-REORDER-MSG            \ ( -- arg2 arg1 arg0 op )  ※§5.7。実体は恒等
        R>                          \ ( -- arg2 arg1 arg0 op tid )
        FILE-DISPATCH               \ op で分岐、内部で IPC4-REPLY
    AGAIN ;
```

メインループ構造はストレージドライバ（yuios_ph3_storage_design_v1_3.md §4.1）を踏襲する。ただし FileMgr の操作は引数が最大 3 個（arg0/arg1/arg2）あるため、3 引数まで扱う FILE-REORDER-MSG を用いる（STOR の REORDER-MSG-3 は arg1 までだった点に注意。§5.7 参照）。

**【設計ルール／kaizen 原則6・7】FILEMGR-TASK のスタック効果と副作用：**
```
ワード名: FILEMGR-TASK
スタック : ( -- )                    無限ループ、戻らない
副作用  : ディレクトリキャッシュ・オープンテーブル・セクタバッファを更新
前提条件: FILEMGR-INIT が STOR-DRV-TASK 起動後に呼ばれること（§5.4）
危険な組合せ: なし（メインループは IPC4-RECV で必ず DSP を空に戻す）
```

### 5.2 メモリ配置（v1.1 全面改訂・両レビュー重大指摘）

**【v1.0 配置の問題】** v1.0 では FileMgr バッファを `$E700-$EF5F` に置いていたが、両レビューがこれを重大問題として指摘した。現行の正典であるメモリマップ設計書 **yuios_memmap_design_v1_2.md** によれば：

- `$5000-$EFFF` は **Forth ゾーン**（Forth 辞書・Forth ワーク・テストバッファ。可変領域）
- うち `$E000-$EBFF`（3 KB）は Forth ワークスペース（HERE 等）
- うち `$EC00-$EFFF`（1 KB）は **テストバッファ予約**（TEST_SRC_BUF=$EC00 / TEST_DST_BUF=$EE00）

v1.0 の FileMgr 配置 `$E700-$EF5F` は、Forth 辞書の可変成長領域とテストバッファ予約領域に深く侵入しており、Force の辞書成長やテストバッファと衝突する危険があった。また v1.0 が根拠とした「yuios_design_v2_1.md §2.1 で $E200-$FBFF が Force VARIABLE 領域」という記述は**廃番の旧版設計書**であり、現行 memmap v1.2 と一致しない。

**【v1.1 の解決：カーネル成長予約領域へ移設】**

memmap v1.2 §4 は既に **`$4800-$4FFF`（2 KB）を「カーネル成長予約（FileMgr / inode / block cache 等）」として明示的に確保**している。FileMgr のバッファはまさにこの領域に置くのが memmap v1.2 の設計意図どおりである。v1.1 では FileMgr 専用ワーク領域を**カーネル成長予約領域 `$4800` 以降**へ全面移設する。

FileMgr 専用変数・バッファ（v1.1 確定配置）：

| **アドレス** | **サイズ** | **シンボル名（Forth）** | **用途** |
| --- | --- | --- | --- |
| $4800 | 2 B | FILEMGR-TID | FileMgr タスク ID（=4） |
| $4802 | 2 B | FS-MOUNTED | FS マウント状態（0=未マウント, 1=マウント済） |
| $4804 | 2 B | FS-NEXT-FREE | next_free_sec のメモリキャッシュ |
| $4806 | 2 B | FS-FILE-COUNT | file_count のメモリキャッシュ |
| $4808 | 2 B | FS-TOTAL-SEC | total_sectors のメモリキャッシュ |
| $480A | 2 B | FS-WR-OLD-NEXT | FILE_WRITE ロールバック退避（old_next_free。§4.4.2） |
| $480C | 2 B | FS-WR-OLD-COUNT | FILE_WRITE ロールバック退避（old_file_count。§4.4.2） |
| $480E | 2 B | FS-FSVER | マウント済 FS の version（上位=major 下位=minor。§5.4） |
| $4810 | 16 B | (予約) | FS メタ情報拡張用 |
| $4820 | 64 B | FS-OPENTAB | オープンファイルテーブル（16B × 4 スロット） |
| $4860 | 512 B | FS-SECBUF | 汎用セクタバッファ（1 セクタ分。READ/WRITE 中継用） |
| $4A60 | 1536 B | FS-DIRBUF | ディレクトリキャッシュ（3 セクタ = 全ディレクトリ） |

合計使用量：$4800〜$505F（2144 B）。

**【★要対応：カーネル成長予約 2 KB をわずかに超過】**

FileMgr 専用領域は **2144 B** を要し、memmap v1.2 のカーネル成長予約 `$4800-$4FFF`（2048 B）を **96 B 超過**する（末尾 FS-DIRBUF が $5000-$505F に食い込む）。`$5000-` は Forth ゾーン先頭であるため、このままでは Forth 辞書先頭と衝突しうる。

対応方針（v1.1 で§10 に memmap 改版要請として記載。下記いずれか）：

| 案 | 内容 | 評価 |
| --- | --- | --- |
| 案1（推奨） | memmap v1.3 でカーネル成長予約を `$4800-$50FF`（2304 B）へ拡張し、Forth ゾーン先頭を `$5100` へ繰り下げる | FileMgr に 160 B の余裕。最も素直 |
| 案2 | FS-DIRBUF の常駐をやめ、ディレクトリ 3 セクタを 1 セクタずつ FS-SECBUF 経由で扱う | §5.6 のセクタ跨ぎ回避方針が崩れる。不採用 |
| 案3 | FS-SECBUF と FS-DIRBUF を時分割共用（READ 中は DIRBUF 不要等） | 状態管理が複雑化。Phase 1 では過剰 |

**v1.1 は案1を前提**とし、§10.1 で memmap 設計書 v1.2 → v1.3 への改版（カーネル成長予約 2 KB → 2304 B 拡張、Forth ゾーン先頭 $5000 → $5100）を正式に要請する。memmap 改版が完了するまでは本書のメモリ配置は暫定であり、§11 実装前チェックリスト I-1 で memmap v1.3 確定を実装着手の前提条件とする。

**【FileMgr 領域を $4800 系に置くことの妥当性】** FileMgr は常駐サーバタスクでありページ解放を行わないため、固定アドレス確保が適切である。カーネル成長予約領域（$4800-）はカーネル RAM の一部であり、Forth 辞書の可変成長やテストバッファと物理的に分離されている。これにより v1.0 で懸念された「Force 辞書成長との衝突」「テストバッファとの重複」は構造的に解消される。

### 5.3 オープンファイルテーブル（FS-OPENTAB）

同時オープン数の上限は **4**。各スロットは 16 B。

| **オフセット** | **サイズ** | **フィールド** | **内容** |
| --- | --- | --- | --- |
| +0 | 2 B | used | 1=使用中, 0=空き |
| +2 | 2 B | dir_index | このファイルのディレクトリエントリ index（0〜31） |
| +4 | 2 B | start_sec | ファイル先頭 LBA（DE からコピー、検索省略用） |
| +6 | 4 B | size | ファイルサイズ（バイト） |
| +10 | 4 B | pos | 現在の論理オフセット（バイト、FILE_SEEK/READ で更新） |
| +14 | 2 B | (予約) | — |

fid（ファイルID）は **スロット index 0〜3** そのものである。FILE_OPEN は空きスロットの index を返し、以降クライアントはその fid で READ/SEEK/CLOSE する。

**設計判断：** 同時オープン 4 という上限は、Phase 1 の想定用途（シェルが cat/run でファイルを1個ずつ開く、ProcMgr がバイナリを1個ロードする程度）に対して十分な余裕がある。上限超過時は E_MFILE を返す。スロット数は §5.2 の FS-OPENTAB を 64B 確保しているので、将来 16B×4=64B の範囲で増減できる（拡張試算：8 スロットにするには 128B 必要、予約領域からの拡張で対応可能）。

#### 5.3.1 fid 値域規約（★v1.6 新設・single source of truth・KY23 対応）

fid（ファイル ID）に関する値域規約を本節で一元定義する。**OPEN / CLOSE / READ / SEEK / STAT の全 IMPL はここを唯一の真値として参照すること。** 各 IMPL が独自に値域を仮定してはならない（kaizen 設計原則：値域規約の取り違え防止）。

| 区分 | 値 | 意味 |
|---|---|---|
| 有効 fid | 0, 1, 2, 3（= 0 〜 FS-MAX-OPEN−1） | OPEN が返すスロット index。非負 |
| エラー（OPEN 失敗時の r0） | $FE01〜$FE0B（§4.2） | 16bit 符号付きで負値。fid 値域（0〜3）と完全に分離 |

**【規約の核心】**

1. **有効 fid は常に非負の小整数（0〜3）**。これは FS-OPENTAB のスロット index そのものである
2. **OPEN がエラーを返すときは $FE00 台のエラーコード**。これは符号付き 16bit で見れば負値（bit15=1）であり、`fid 0< `（符号付き比較）で「負＝無効」と判定できる
3. **FID-VALID?（§6.6・実装済み）が fid 検査の唯一の正規手段**。その実装は：
   - `DUP 0< IF DROP 0 EXIT`（負値 → 無効。エラーコードを fid として誤って渡した場合もここで弾ける）
   - `DUP FS-MAX-OPEN >= IF DROP 0 EXIT`（4 以上 → 無効）
   - `OT-USED + @ 0= INVERT`（範囲内なら used フラグの真偽を返す）
4. **READ/SEEK/CLOSE は受け取った fid を必ず FID-VALID? に通してから使う**。FID-VALID? が偽なら E_BADF（CLOSE/READ/SEEK 共通）を返す

この規約により、「エラーコード（$FE0x）を誤って fid として後続 API に渡す」事故が起きても、FID-VALID? の `0<` 判定（$FE0x は符号付き負）で確実に弾かれる。**新たに $FFFF 等の専用エラー fid 値を導入する必要はなく、既存のエラーコード体系（§4.2）をそのまま fid 値域規約に流用する**のが最もシンプルで、READ/WRITE 実装時の追加判断を不要にする（6 方針判断 #6 の確定事項）。

#### 5.3.2 スロット状態遷移（★v1.6 新設・KY19 対応）

各 OPENTAB スロットは「未使用（OT-USED=0）」と「使用中（OT-USED=1）」の 2 状態のみを取る。状態遷移を以下に確定する：

```
        FILE_OPEN 成功
  ┌──────────────────────┐
  │                       ▼
[未使用]                [使用中]
  ▲   OT-USED=0          OT-USED=1
  │                  OT-DIR-INDEX/START-SEC/SIZE 設定
  │                  OT-POS = 0（初期化）
  │                       │
  └───────────────────────┘
        FILE_CLOSE 成功
        （OT-USED = 0、他フィールドは残存・次回 OPEN で上書き）

  使用中での自己遷移（OT-USED は不変）:
    FILE_READ / FILE_SEEK → OT-POS のみ更新
    FILE_STAT             → スロット参照なし（name 検索）、状態不変
```

| 遷移 | トリガ | 変更されるフィールド |
|---|---|---|
| 未使用 → 使用中 | FILE_OPEN 成功 | OT-USED←1, OT-DIR-INDEX, OT-START-SEC, OT-SIZE, OT-POS←0 |
| 使用中 → 未使用 | FILE_CLOSE 成功 | OT-USED←0（他は不変） |
| 使用中 → 使用中 | FILE_READ/SEEK | OT-POS のみ |

**【重要・KY19】OT-USED の遷移点は OPEN（0→1）と CLOSE（1→0）の 2 箇所のみ。** 他のどの IMPL も OT-USED を書き換えてはならない。これにより「READ 中にスロットが勝手に解放される」「STAT が誤ってスロットを使用中にする」等の不整合を構造的に排除する。FILEMGR-INIT は起動時に全スロットを OT-USED=0 で初期化する（§5.4・実装済み `FS-OPENTAB 0 64 MEMSET-B`）。

#### 5.3.3 fid 再利用ポリシー（★v1.6 新設・6 方針判断 #4）

FILE_OPEN が空きスロットを探す際の方針を「**最小空き index 方式**」に確定する：

- OPEN は fid=0 から順に走査し、**最初に見つかった OT-USED=0 のスロット index** を返す
- これは既存の DIR-FIND-FREE（§6.6・実装済み）と同型の「最小 index 線形探索」イディオムであり、FileMgr 内のコードスタイルが統一される
- CLOSE 直後のスロットは即座に再利用可能（最小 index なので、close した fid が他より小さければ次の OPEN で再び同じ fid が割り当てられる）

**ラウンドロビン方式を採らない理由：** ラウンドロビンは「次に割り当てる index」を保持する追加の状態変数が必要になり、FileMgr の状態が増える。最小空き index 方式は状態を持たず（毎回 0 から走査）、テスト時に fid の割り当てが予測可能（最初の OPEN は必ず fid=0）という利点がある。Phase 1 の同時オープン 4 という規模では走査コストも無視できる。

**【テスト予測性】** この方式により、テスト F2（最初の FILE_OPEN）は必ず **fid=0** を返す。テストの期待値が決定的になり、デバッグが容易になる（§8.2 F2 の期待 r0=0）。

### 5.4 FILEMGR-INIT と FS マウント

```forth
: FILEMGR-INIT  ( -- )
    \ オープンテーブル全クリア（v1.1: DO/LOOP → BEGIN/WHILE/REPEAT）
    0 >R
    BEGIN  R@ 4 <  WHILE
        0  R@ 16 *  FS-OPENTAB +  !
        R> 1 + >R
    REPEAT
    R> DROP
    \ FSマウント: スーパーブロック読み込み + magic/version 照合
    FS-MOUNT ;

: FS-MOUNT  ( -- )
    0 FS-MOUNTED !                  \ まず未マウントに初期化
    \ LBA0 を FS-SECBUF へ STOR_READ（msg: 0 FS-SECBUF 0 op tid）
    0 FS-SECBUF 0 STOR-READ-OP STOR-DRV-TID @ IPC4-CALL
    DROP DROP DROP                  \ r1 r2 r3 捨て、stack: r0
    0= INVERT IF
        EXIT                        \ STOR_READ 失敗 → 未マウントのまま
    THEN
    \ magic 照合（"YUIFS\0\0\0"）
    FS-SECBUF MAGIC-CHECK 0= IF
        EXIT                        \ magic 不一致 → 未マウントのまま
    THEN
    \ version 照合（v1.1 追加・v1.2 で明示 pack 化）: +8=ver_major, +9=ver_minor
    FS-SECBUF 8 + C@                \ ver_major（1 バイト読み）
    DUP 1 = 0= IF
        \ ver_major 不一致 → マウント拒否（§3.2 表）
        DROP EXIT                   \ 未マウントのまま
    THEN
    \ ver_minor は警告のみ（マウントは継続）。version を明示 pack してキャッシュ
    \ v1.2: セル幅(@)に依存せず、C@ で 1 バイトずつ読み major<<8 | minor を構成
    FS-SECBUF 8 + C@  8 LSHIFT      \ major を上位バイトへ（major はスタックに残存）
    FS-SECBUF 9 + C@  OR            \ minor を下位バイトへ OR
    FS-FSVER !                      \ FS-FSVER = (major<<8) | minor
    \ 諸元をキャッシュ（24/26/12 は u16 フィールド。@ で 16bit 読み）
    FS-SECBUF 24 + @ FS-NEXT-FREE !
    FS-SECBUF 26 + @ FS-FILE-COUNT !
    FS-SECBUF 12 + @ FS-TOTAL-SEC !
    1 FS-MOUNTED ! ;
```

**【version 照合の動作】（v1.1 追加・review18 指摘）**

§3.2 で定義した ver_major / ver_minor を FS-MOUNT で照合する：

- **ver_major 不一致** → マウント拒否（FS-MOUNTED=0 のまま）。レイアウト非互換のディスクを誤解釈してデータ破壊するのを防ぐ。以降の全 SVC_FILE 操作は E_IOERR を返す。
- **ver_major 一致・ver_minor 不一致** → マウント継続（警告扱い）。後方互換変更を想定。Phase 1 ではログ出力機構が限定的なため、警告は FS-FSVER に値を残すのみ（将来シェルの `ver` 等で参照可能）。
- Phase 1 の mkfs は ver_major=1, ver_minor=1 を書き込む。FileMgr は ver_major=1 のみ受理する。

**【FS-FSVER の明示 pack 化】（v1.2 変更・review19 指摘）**

v1.1 のコードは `FS-SECBUF 8 + @` でディスク上の +8/+9 の 2 バイトをセル読み（`@`）して FS-FSVER に格納していた。しかしこの方法は `@` のアクセス幅（YSD8800 Forth では 16bit だが、移植先 CPU では異なりうる）とエンディアンに依存し、major/minor がどちらのバイトに入るかが処理系依存になる。YUI OS は他 CPU アーキテクチャへの移植性を設計原則とするため（プロジェクト方針）、v1.2 では **`C@` で 1 バイトずつ読み、`major<<8 | minor` を明示的に構成**する方式に変更した。

これにより FS-FSVER は常に「上位バイト=major、下位バイト=minor」と定義が固定され、ディスク上のバイト並び・処理系のセル幅・エンディアンに依存しない。シェルの `fsinfo` / `ver` 等で FS-FSVER を参照する際も、`FS-FSVER @ 8 RSHIFT`（major）、`FS-FSVER @ $FF AND`（minor）で安定して取り出せる。`LSHIFT` / `RSHIFT` / `OR` / `AND` は ISA2.3 の SHL（0x57）／SHR（0x58）／ビット演算命令にマップされ、Force v1.2 でも kernel_forth_v0_8_5.fs に多数の使用実績がある（例：行 333-334 の `LSHIFT` による tid×80 計算、行 595 の `8 RSHIFT`、行 1369-1371 の HEX ダンプ）。`C@` も同 PAGE 関連ワードで使用実績があり、ISA にない命令は一切使用しない（kaizen 原則）。

なお ver_major 不一致を明示的に区別したい場合は E_FSVER（$FE0A）を使うが、Phase 1 の FS-MOUNT は「マウントしない（FS-MOUNTED=0）」で一括処理し、個別操作は E_IOERR で応答する（§5.4 末尾「未マウント時の動作」）。E_FSVER は将来 FILE_STAT 等で「なぜマウントできないか」をクライアントに伝えたい場合の予約コードとする。

**【kaizen 原則14：初期化タイミングの明記】**
```
ワード名: FILEMGR-INIT
呼び出しタイミング: FILEMGR-TASK の先頭で1回。STOR-DRV-TASK（tid=3）起動後でなければならない
                    （FS-MOUNT が STOR へ IPC4-CALL するため）
冪等性          : 冪等（複数回呼んでも安全。オープンテーブルをクリアし再マウントするだけ）
副作用          : FS-OPENTAB クリア、FS-MOUNTED / FS-NEXT-FREE / FS-FILE-COUNT
                  / FS-TOTAL-SEC / FS-FSVER を設定
禁止タイミング  : STOR-DRV-TASK 起動前（IPC4-CALL の宛先が存在せず永久ブロック）
```

起動順序は yuios_design_v2_2.md §4.4.1 で「MEMMGR(1) → UART(2) → STOR(3) → FileMgr(4) → ProcMgr(5) → Shell(6)」と確定しており、FileMgr は STOR より後に起動するため上記の前提は満たされる。

**未マウント時の動作：** FS-MOUNTED=0 の場合、全ての SVC_FILE 操作は E_IOERR を返す（FileMgr 自体は動作し続け、要求にエラー応答する）。ディスクが未フォーマットでもシステムはハングしない。

### 5.4.2 DIR-LOAD 必須呼出（★v1.4 新設・Step 5-1 真因①修正反映）

#### 5.4.2.1 背景

Step 5-1 デバッグ（v0.10.2e〜v0.10.2i、HANDOVER_CHAT32）で、FILEMGR-INIT-DBG（FILEMGR-INIT のデバッグ用版）が **DIR-LOAD を呼んでいなかった**ために、後続の STAT-IMPL 等が呼び出す DIR-FIND が「FS-DIRBUF が DIR-LOAD 済み」前提のまま空のバッファを参照し、操作が破綻する問題が顕在化した（真因①）。

#### 5.4.2.2 確定設計

FILEMGR-INIT は FS-MOUNT 成功後、続けて **DIR-LOAD を必ず呼び出してディレクトリ全 3 セクタ（LBA 1-3）を FS-DIRBUF に読み込む**ことを必須とする。

```forth
: FILEMGR-INIT  ( -- )
    \ オープンテーブル全クリア（§5.4 のとおり）
    0 >R
    BEGIN  R@ 4 <  WHILE
        0  R@ 16 *  FS-OPENTAB +  !
        R> 1 + >R
    REPEAT
    R> DROP
    \ FSマウント
    FS-MOUNT
    \ ★v1.4 追加：マウント成功時のみ DIR-LOAD を実行
    FS-MOUNTED @ IF
        DIR-LOAD DROP               \ Phase 1 では r0 エラー時もマウント済扱い継続
                                    \ （DIR-FIND は空バッファ走査で「該当なし」を返す）
    THEN ;
```

#### 5.4.2.3 失敗時の扱い（Phase 1 制限）

DIR-LOAD は内部で 3 回の STOR-READ を行う。途中でいずれかのセクタ読み出しに失敗した場合、Phase 1 では r0 を DROP するに留め、FS-MOUNTED は 1 のまま維持する。DIR-FIND は空または部分的に読み込まれた FS-DIRBUF を走査するが、FLG_USED=0 のエントリは「未使用」と解釈されるため誤動作はせず、結果として全ての FILE_OPEN 等が「ファイルなし」応答となる。Phase 2 で fsck 相当の機構を追加する際に、DIR-LOAD 失敗を明示的なマウント失敗に格上げする予定。

#### 5.4.2.4 設計ルール（kaizen 原則 7：前提条件の明記）

```
ワード名: DIR-FIND / DIR-FIND-FREE / FILE-OPEN / FILE-DELETE 等
前提条件: 呼び出し前に DIR-LOAD が実行されており、FS-DIRBUF が
          ディスク上の最新ディレクトリ内容を保持していること
ガード方式: FILEMGR-INIT で必ず DIR-LOAD を実行する（本節）。
            個別ワードでは前提を再確認しない（性能上の理由・呼び出し頻度高）
```

これにより「FS-DIRBUF を DIR-LOAD 済み前提とする全ワード」は、起動シーケンスにおいて自動的に前提を満たすことが保証される。

### 5.5 FileMgr が使うディスクレイアウト定数

§5.4 のとおり FILEMGR-INIT でスーパーブロックを読みキャッシュするが、Phase 1 ではレイアウトが固定のため、以下は定数として実装してよい（kaizen 原則31「シンボルアドレスのハードコード禁止」はカーネル内 Forth シンボルアドレスに関する原則であり、FS のディスクレイアウト定数は対象外。ただし定数定義は一箇所に集約すること）。

| **定数名** | **値** | **意味** |
| --- | --- | --- |
| FS-DIR-START | 1 | ディレクトリ領域開始 LBA |
| FS-DIR-SECTORS | 3 | ディレクトリ領域セクタ数 |
| FS-DIR-ENTRIES | 32 | ディレクトリエントリ総数 |
| FS-DATA-START | 4 | データ領域開始 LBA |
| FS-DE-SIZE | 48 | ディレクトリエントリサイズ |
| FS-SECSIZE | 512 | セクタサイズ |

### 5.6 ディレクトリキャッシュ方式

§3.3 で述べたとおり、48B エントリは 512B セクタを割り切らずセクタ跨ぎが発生する。これを回避するため、**ディレクトリ領域 3 セクタ（1536B）を一括で FS-DIRBUF に読み込んでから操作する**方式を採る。

| **操作** | **ディレクトリキャッシュの扱い** |
| --- | --- |
| FILE_OPEN | FS-DIRBUF にディレクトリ 3 セクタを読み込み → メモリ上で名前検索 |
| FILE_STAT | 同上 |
| FILE_LIST | 同上 |
| FILE_WRITE | FS-DIRBUF に読み込み → 空きエントリ探索 → メモリ上で更新 → 3 セクタ書き戻し |
| FILE_DELETE | 同上（flags の FLG_USED をクリア → 書き戻し） |

**ディレクトリ読み込みワード：**（v1.1：DO/LOOP → BEGIN/WHILE/REPEAT。§11.3 参照）
```forth
: DIR-LOAD  ( -- )
    \ LBA 1,2,3 を FS-DIRBUF[0], [512], [1024] へ
    \ i は R スタックでカウント（0..FS-DIR-SECTORS-1）
    0 >R                                    \ R: i = 0
    BEGIN  R@ FS-DIR-SECTORS <  WHILE
        0                                   \ msg3=0(arg2 未使用)
        FS-DIRBUF  R@ FS-SECSIZE * +        \ msg2=dst = FS-DIRBUF + i*512
        FS-DIR-START R@ +                   \ msg1=LBA = 1 + i
        STOR-READ-OP STOR-DRV-TID @ IPC4-CALL
        DROP DROP DROP DROP                 \ r0..r3 捨て（エラー処理は §6.3 参照）
        R> 1 + >R                           \ i++
    REPEAT
    R> DROP ;

: DIR-STORE  ( -- )
    \ FS-DIRBUF の 3 セクタを LBA 1,2,3 へ書き戻し
    0 >R                                    \ R: i = 0
    BEGIN  R@ FS-DIR-SECTORS <  WHILE
        0
        FS-DIRBUF  R@ FS-SECSIZE * +
        FS-DIR-START R@ +
        STOR-WRITE-OP STOR-DRV-TID @ IPC4-CALL
        DROP DROP DROP DROP
        R> 1 + >R
    REPEAT
    R> DROP ;
```

エントリ index e のメモリ上アドレスは `FS-DIRBUF + e * 48` で求まる（FS-DIRBUF は 1536B 連続なのでセクタ跨ぎを意識しなくてよい）。

**【v1.1 注記：DO/LOOP 不使用】** v1.0 では DO/LOOP を用いていたが、§11.3 のとおり Force v1.2 は DO/LOOP に対応していない（kernel_forth_v0_8_5.fs での実装実績ゼロ、ループは全て BEGIN/WHILE/REPEAT）。v1.1 では §6 の全ループを **BEGIN/WHILE/REPEAT** に書き換え、ループカウンタは R スタックで保持する。これは kernel_forth の既存ワード（PAGE スキャン等）と同じイディオムである。なお STOR / DIR の書き戻しで I/O エラー戻り値の本格的なチェックは §6.3（FILE-WRITE-IMPL）側で行う。DIR-LOAD/DIR-STORE 単体は戻り値を捨てるが、呼び出し元（FILE-WRITE-IMPL 等）が STOR の戻り値を見られるよう、実装時には DIR-STORE を「最後の STOR-WRITE の r0 を残す」形に拡張してもよい（§6.3 で扱う）。

**設計判断：** ディレクトリキャッシュを「常駐」させず操作の都度ロードするのは、FileMgr の状態を最小化し「ディスク上のディレクトリが常に正」という単純な不変条件を保つためである。1536B を都度読むコストは STOR_READ 3 回（各 512B PIO 転送）であり、Phase 1 の性能要件では許容範囲。将来性能が問題になればディレクトリ常駐キャッシュ + dirty フラグ方式に改修する（§10）。

### 5.7 FILE-REORDER-MSG：3引数メッセージ整列ワード（v1.1 全面改訂）

ストレージドライバは `REORDER-MSG-3`（arg1 まで取り出す）を使うが、FileMgr の操作は arg2 まで使う（FILE_READ/WRITE が 3 引数）。本書では **FILE-REORDER-MSG** を新規に定義する（STOR の同名ワードとの名前衝突回避のため最初から別名。§11 I-2）。

**【v1.1：IPC4 メッセージ並び順を実装ソースで確定】（社内レビュー重大指摘）**

v1.0 では「IPC4-RECV 後のスタックは底→TOS で `arg2 arg1 arg0 op` であり整列不要」と結論していたが、社内レビューで**上位設計書間の表記矛盾**が指摘された：

| 文書 | IPC4-CALL のスタック効果表記 |
| --- | --- |
| yuios_design_v2_2.md §4.4 | `( msg0 msg1 msg2 msg3 tid -- r0 r1 r2 r3 )` |
| yuios_ph3_storage_design_v1_3.md §3 | `( msg3 msg2 msg1 msg0 tid -- )` |

両者は msg の並び順が逆であり、どちらが実装の真実かを確定しなければ FILE-REORDER-MSG の正否が定まらない。**v1.1 では実装ソース kernel_v12_5.asm（kernel v0.12.6 相当）を直接確認し、以下を確定した。**

**確定事実（kernel_v12_5.asm の実装より）：**

1. `IPC4_CALL` 本体（ラベル `.org $08C0`）のコメントに `IPC4-CALL ( msg3 msg2 msg1 msg0 tid -- r3 r2 r1 r0 )` と明記。
2. `_ipc4_enqueue`（IPC4_CALL から JSR）のコメントに「DSP レイアウト（TOS 側=低位）: `[WK_X+0]=msg0(op) [+2]=msg1 [+4]=msg2 [+6]=msg3`」と明記。IPC4_WK_X は IPC4_CALL 冒頭で tid を pop した直後の DSP。つまり **tid の次（底側）が msg0、その先が msg1→msg2→msg3**。
3. `IPC4_RECV` 本体（`.org $07E0`）のコメントに `IPC4-RECV ( -- msg3 msg2 msg1 msg0 )`。msg コピーループは `entry.msg[3]` から開始し `[3]→[2]→[1]→[0]` の順に DSP へ push する。各 push は DSP をデクリメント（アドレス低位＝TOS 方向）。**最後に push された msg0 が TOS、底側が msg3**。

**結論：実装の真実は `IPC4-CALL ( msg3 msg2 msg1 msg0 tid -- ... )`（底=msg3, TOS=tid）、`IPC4-RECV ( -- msg3 msg2 msg1 msg0 )`（底=msg3, TOS=msg0）である。** STOR 設計書 v1.3 の表記が正しく、**yuios_design_v2_2.md §4.4 の表記が誤り**である（§10.1 で v2.2 の改版を要請）。

**FILE-REORDER-MSG が恒等でよいことの確定的根拠：**

クライアントの呼び出し（§4.3 各ワード）は Forth のスタック push 規則（左から順に積む＝最後がTOS）に従い、例えば FILE_READ は `size dst-addr fid FILE-READ-OP FILEMGR-TID @ IPC4-CALL` と書く。IPC4-CALL 直前の DSP は底→TOS で `size dst-addr fid op tid`。これを IPC4-CALL の `( msg3 msg2 msg1 msg0 tid -- )` に対応させると：

```
msg3 = size      = arg2
msg2 = dst-addr  = arg1
msg1 = fid       = arg0
msg0 = op
tid  = 宛先
```

IPC4-RECV は `( -- msg3 msg2 msg1 msg0 )` を積むので、サーバ側 DSP は底→TOS で `msg3 msg2 msg1 msg0` = `arg2 arg1 arg0 op`。これは FILE-DISPATCH が要求する並び `( arg2 arg1 arg0 op tid -- )`（tid は別途 IPC4-SENDER で取得）の arg 部分と**完全に一致**する。

```forth
\ FILE-REORDER-MSG ( msg3 msg2 msg1 msg0 -- arg2 arg1 arg0 op )
\   IPC4-RECV 直後の並び (底→TOS: msg3 msg2 msg1 msg0) は
\   実装確定事実より (底→TOS: arg2 arg1 arg0 op) と既に一致する。
\   よって整列操作は不要。恒等ワードとして定義する。
\   ※ kernel_v12_5.asm の IPC4_RECV/IPC4_CALL/_ipc4_enqueue で確認済（v1.1）
: FILE-REORDER-MSG  ( msg3 msg2 msg1 msg0 -- arg2 arg1 arg0 op )
    ;   \ 恒等。msg と arg の対応が一致するため操作不要
```

**【3 引数目（arg2）が STOR で未検証だった点への対応】** STOR の `REORDER-MSG-3` は arg1 までしか取り出さず（`( -- arg1 arg0 op )`、msg3 を実質 DROP）、3 引数目の順序は STOR 実装では検証されていなかった。FileMgr は FILE_READ/WRITE で初めて arg2 を使うため、上記の実装ソース確認をもって arg2 の並びを確定した。FILE-REORDER-MSG が恒等であることは机上で確定したが、念のため §8 のテスト F1（FILE_WRITE、3 引数 name/src/size）が PASS することで実機検証も兼ねる（§11 I-2）。

**【名前衝突回避】** 本ワードは STOR の `REORDER-MSG-3` とは別名 `FILE-REORDER-MSG` とする。両者は引数個数（FileMgr=3, STOR=2）が異なり挙動も異なるため、同名にすると Forth 辞書上の再定義で混乱する。§11 実装前チェックリスト I-2 で名前の一意性を確認する。

## 6. アルゴリズム詳細

### 6.1 FILE-DISPATCH

```forth
: FILE-DISPATCH  ( arg2 arg1 arg0 op tid -- )
    >R                              \ R: tid（応答先）
    DUP FILE-OPEN-OP   = IF DROP R> FILE-OPEN-IMPL   EXIT THEN
    DUP FILE-CLOSE-OP  = IF DROP R> FILE-CLOSE-IMPL  EXIT THEN
    DUP FILE-READ-OP   = IF DROP R> FILE-READ-IMPL   EXIT THEN
    DUP FILE-WRITE-OP  = IF DROP R> FILE-WRITE-IMPL  EXIT THEN
    DUP FILE-SEEK-OP   = IF DROP R> FILE-SEEK-IMPL   EXIT THEN
    DUP FILE-STAT-OP   = IF DROP R> FILE-STAT-IMPL   EXIT THEN
    DUP FILE-LIST-OP   = IF DROP R> FILE-LIST-IMPL   EXIT THEN
    DUP FILE-DELETE-OP = IF DROP R> FILE-DELETE-IMPL EXIT THEN
    \ 未知 op
    DROP DROP DROP DROP             \ arg2 arg1 arg0 op を捨てる
    E-INVAL 0 0 0 R> IPC4-REPLY ;
```

**【スタック消費の注意】** FILE-DISPATCH 進入時 DSP には底→TOS で `arg2 arg1 arg0 op tid` の 5 ワードがある。`>R` で tid を退避後、各分岐の判定は `DUP ... =` で行うため op を残したまま比較する。分岐確定後 `DROP`（op 破棄）→ `R>`（tid 復帰）で、各 IMPL ワードには `( arg2 arg1 arg0 tid -- )` が渡る。各 IMPL は使わない引数を自分で DROP する。

### 6.2 ディレクトリ名前検索

```forth
\ DIR-FIND ( name-addr -- dir_index | -1 )
\   FS-DIRBUF（DIR-LOAD 済み前提）から name 一致 & FLG_USED のエントリを探す
\   見つからなければ -1
\ 副作用: なし（FS-DIRBUF を読むのみ）
\ 前提条件: 呼び出し前に DIR-LOAD を実行しFS-DIRBUFが最新であること
\ v1.1: DO/LOOP → BEGIN/WHILE/REPEAT（§11.3）。i は R スタックで保持。
\ v1.5.1: マジックナンバー（FS-DIRBUF R@ FS-DE-SIZE * + / 24 + / 1 AND）を
\         実装ソース kernel_forth と同一のシンボル（DE-ADDR / DE-FLAGS / FLG-USED）
\         に統一（案X・M1/M2対応）。オフセット根拠は §3 DE レイアウト対照表。
: DIR-FIND  ( name-addr -- index )
    0 >R                                 \ R: i = 0、データ: ( name )
    BEGIN  R@ FS-DIR-ENTRIES <  WHILE
        R@ DE-ADDR                       \ ( name ent ) エントリ i のアドレス（DE-ADDR §6.6）
        DUP DE-FLAGS + @ FLG-USED AND IF \ flags bit0(FLG_USED)?（DE-FLAGS=+24 §3）
            DUP                           \ ( name ent ent )
            >R OVER R> NAME-EQ? IF        \ name と ent+DE-NAME(+0) を比較
                DROP R> EXIT             \ 一致 → ( index ) を返して終了
            THEN
            DROP                          \ ent 破棄、( name ) に戻る
        ELSE
            DROP                          \ ent 破棄、( name ) に戻る
        THEN
        R> 1 + >R                         \ i++
    REPEAT
    R> DROP                               \ i 破棄
    DROP -1 ;                             \ name 破棄、-1 を返す
```

**【スタック注記】** ループ正常終了（一致発見）時は `DROP R> EXIT` で「name を捨て、R スタックの i を index としてデータスタックへ移し」終了する。BEGIN/WHILE/REPEAT は DO/LOOP と違い `UNLOOP` を要しない（R スタックの i は明示的に `R>` で回収する）。これは Force v1.2 で安全に動作するイディオムである（§11.3）。

NAME-EQ? は 16B 以内の NULL 終端文字列比較ワード（最大 16 バイト、両方が NULL に達するまで比較）。実装は §6.6 に記載。

### 6.3 FILE_READ のセクタ境界処理

論理オフセット pos から len バイトを読む処理。連続割り当てなので、論理オフセット pos に対応する LBA は単純計算で求まる：

```
論理セクタ番号  lsec = pos / 512
セクタ内オフセット sofs = pos mod 512
物理 LBA        lba  = start_sec + lsec
```

読み出しアルゴリズム（擬似コード）：

```
function FILE_READ_IMPL(fid, dst, size):
    slot = FS-OPENTAB[fid]
    if slot 不正: return E_BADF
    pos  = slot.pos
    fsz  = slot.size
    actual = min(size, fsz - pos)        # EOF を超えない
    if actual <= 0: return 0             # 既に EOF
    remain = actual
    d = dst
    while remain > 0:
        lsec = pos / 512
        sofs = pos mod 512
        lba  = slot.start_sec + lsec
        # 1セクタを FS-SECBUF へ読み込み
        STOR_READ(lba, FS-SECBUF)         # IPC4-CALL、エラーなら E_IOERR
        # このセクタからコピーできるバイト数
        chunk = min(512 - sofs, remain)
        memcpy(d, FS-SECBUF + sofs, chunk)
        d      += chunk
        pos    += chunk
        remain -= chunk
    slot.pos = pos                        # 論理オフセット更新
    return actual
```

**設計判断：** セクタバッファ FS-SECBUF を経由する「2 コピー方式」（STOR→SECBUF→dst）を採る。STOR_READ の dst に直接クライアントバッファを渡せば 1 コピーで済むが、その場合「セクタ境界をまたぐ部分読み込み」で dst の前後にセクタ全体（512B）が書き込まれ、クライアントバッファの想定外領域を破壊する。FS-SECBUF を緩衝することで、クライアントには要求された chunk バイトだけを正確にコピーする。先頭・末尾のセクタが部分読み込みになるため、この緩衝は必須である。

**最適化の余地：** pos と size が両方とも 512 の倍数（セクタ境界揃い）の場合は、中間セクタについて FS-SECBUF を経由せず STOR_READ で dst へ直接転送できる。Phase 1 では実装の単純さを優先し全セクタ緩衝とするが、§10 に最適化候補として記録する。

### 6.4 FILE_WRITE のセクタ書き込み

§4.4.1 の手順番号に対応する。I/O エラー時の RAM 内ロールバック（§4.4.2）を含む。

```
function FILE_WRITE_IMPL(name, src, size):
    # 手順1
    if strlen(name) > 15: return E_NAMETOOLONG
    # 手順2: ディレクトリロード
    if DIR-LOAD() failed: return E_IOERR
    # 手順3: 同名チェック
    if DIR-FIND(name) >= 0: return E_EXIST
    # 手順4: 空きエントリ
    di = DIR-FIND-FREE()                  # 空きエントリ index、なければ -1
    if di < 0: return E_NODIRSPC
    # 手順5: 必要セクタ数
    n = ceil(size / 512)
    # 手順6: 空き容量チェック
    if FS-NEXT-FREE + n - 1 >= FS-TOTAL-SEC: return E_NOSPC
    # 手順7: ロールバック用に現在値を退避
    FS-WR-OLD-NEXT  = FS-NEXT-FREE
    FS-WR-OLD-COUNT = FS-FILE-COUNT
    # 手順8: start_sec 確保（FS-NEXT-FREE 変数はまだ進めない）
    start = FS-NEXT-FREE
    # 手順9: データ書き込み（セクタ単位）
    remain = size ; s = src ; lba = start
    while remain > 0:
        chunk = min(512, remain)
        if chunk == 512:
            r = STOR_WRITE(lba, s)              # セクタ丸ごと
        else:
            memset(FS-SECBUF, 0, 512)           # 端数セクタ: 0 パディング
            memcpy(FS-SECBUF, s, chunk)
            r = STOR_WRITE(lba, FS-SECBUF)
        if r != 0:                              # I/O エラー → ロールバック（§4.4.2）
            return E_IOERR                      # メモリ値は未変更、巻き戻し不要
        s += chunk ; remain -= chunk ; lba += 1
    # 手順10: ディレクトリエントリ更新（FS-DIRBUF 上）
    ent = FS-DIRBUF + di * 48
    memcpy(ent + 0, name, 16)                   # name（NULL 終端、16B 内）
    store32(ent + 16, size)
    store16(ent + 20, start)
    store16(ent + 22, n)
    store16(ent + 24, FLG_USED)                 # flags = bit0
    # 手順11: ディレクトリ書き戻し
    if DIR-STORE() failed:                      # I/O エラー → ロールバック
        return E_IOERR                          # メモリ値は未変更、巻き戻し不要
    # 手順12: メモリ値を確定更新（ディスク書き込み成功後）
    FS-NEXT-FREE  += n
    FS-FILE-COUNT += 1
    # 手順13: スーパーブロック書き戻し
    if SB-STORE() failed:                       # I/O エラー → メモリ値を巻き戻す
        FS-NEXT-FREE  = FS-WR-OLD-NEXT
        FS-FILE-COUNT = FS-WR-OLD-COUNT
        return E_IOERR
    # 手順14
    return E_OK
```

**【ロールバックの要点】（§4.4.2 参照）** 手順 12（メモリ値更新）をディスク書き込み（手順 9・11）の成功後に置くことで、手順 9・11 で I/O エラーが起きてもメモリ値 FS-NEXT-FREE / FS-FILE-COUNT は一切汚れておらず、明示的な巻き戻しは不要（`return E_IOERR` のみ）。手順 13（SB-STORE）の失敗時のみ、手順 12 で進めたメモリ値を FS-WR-OLD-NEXT / FS-WR-OLD-COUNT から復元する。これにより「メモリ値だけ進んでディスク SB は古い」という review18 指摘の不整合を防ぐ。

**端数セクタの 0 パディング：** 最終セクタが 512B 未満の場合、FS-SECBUF を 0 クリアしてから chunk バイトをコピーし、512B 丸ごと書き込む。これによりファイル末尾の未使用領域は 0 で埋まる（ゴミデータが残らない）。

**SB-STORE：** スーパーブロックの動的フィールド（next_free_sec, file_count）を更新してディスクへ書き戻す。実装は「LBA0 を FS-SECBUF へ読み込み → +24/+26 を書き換え → LBA0 へ書き戻し」とする（スーパーブロック全体をメモリ常駐させず、都度読み書きする）。STOR_READ または STOR_WRITE のいずれかがエラーを返したら SB-STORE は失敗（手順 13 のロールバック対象）。

### 6.5 FILE_DELETE

```
function FILE_DELETE_IMPL(name):
    # 手順1: ディレクトリロード
    if DIR-LOAD() failed: return E_IOERR
    # 手順2: 対象エントリ検索
    di = DIR-FIND(name)
    if di < 0: return E_NOENT
    # 手順3: open 中チェック（§4.6）。開いているファイルは削除拒否
    for slot in FS-OPENTAB(全4スロット):
        if slot.used and slot.dir_index == di:
            return E_BUSY                     # open 中 → 削除しない（v1.2）
    # 手順4: ロールバック用に file_count を退避
    FS-WR-OLD-COUNT = FS-FILE-COUNT
    # 手順5: flags の FLG_USED をクリア（FS-DIRBUF 上）
    ent = FS-DIRBUF + di * 48
    store16(ent + 24, 0)                      # flags = 0（エントリを空きに）
    # 手順6: ディレクトリ書き戻し
    if DIR-STORE() failed: return E_IOERR     # FS-FILE-COUNT 未変更、巻き戻し不要
    # 手順7: メモリ値を確定更新
    FS-FILE-COUNT -= 1
    # 手順8: スーパーブロック書き戻し
    if SB-STORE() failed:                     # I/O エラー → メモリ値を巻き戻す
        FS-FILE-COUNT = FS-WR-OLD-COUNT
        return E_IOERR
    return E_OK
```

**設計判断：** FILE_DELETE はディレクトリエントリの FLG_USED をクリアするだけで、データセクタは解放しない（§3.5 next_free_sec 方式のため）。削除されたファイルのデータセクタはディスク上に残るが、ディレクトリから参照されなくなるため論理的に「消える」。物理的なセクタ回収は Phase 2 の課題（§10）。

**open 中削除の拒否（v1.2・review19 指摘）：** オープン中のファイルの削除は **E_BUSY** で拒否する（§4.6）。FS-OPENTAB の全 4 スロットを走査し、対象 dir_index と一致する used スロットが 1 つでもあれば「使用中」と判定する。これにより「オープン中スロットの dir_index が、無効化された DE を指したまま宙に浮く（dangling 参照）」状態を構造的に防ぐ。v1.1 までは戻り値を E_BADF としていたが、E_BADF は「不正な fid」の意味であり FILE_DELETE の文脈に合わないため、v1.2 で専用コード E_BUSY（$FE0B）に変更した。

**ロールバック（v1.2）：** FILE_DELETE も FILE_WRITE と同じく、メモリ値（FS-FILE-COUNT）の更新を DIR-STORE 成功後に置き、SB-STORE 失敗時は FS-WR-OLD-COUNT から巻き戻す。FILE_DELETE は next_free_sec を変更しないため退避は file_count のみでよい。SB-STORE 失敗時のディスク不整合（DE は更新済み・SB は古い file_count）は §4.4.2 の既知制限と同性質であり、Phase 1 では許容する（mkfs 推奨）。

#### 6.7.2 擬似コード（設計過程メモ・★不採用★）

> ⚠️ **【写経禁止・本節は説明用の不採用版です】**
> 本節の擬似コードは設計検討の過程を示すもので、EXIT による疑似 LEAVE 等の
> 未完成・破綻したロジックを含みます。**実装には絶対に使用しないでください。**
> 実装は必ず **§6.7.3 案I（確定版）** を用いること。
> さらに本 v1.5 初版の案では MEMCPY-B との変数衝突バグがあり、v1.5.1 案P で
> 専用変数（FM-WK-COUNT/REMAIN/PTR）に修正しています。確定実装は §6.7.3 を参照。

```forth
\ FILE-LIST-IMPL ( arg2 arg1 arg0 tid -- )
\   arg0 = buf_addr, arg1 = buf_size, arg2 = 0, tid = client
: FILE-LIST-IMPL
    >R                              \ R: tid

    \ ガード1: FS-MOUNTED チェック
    FS-MOUNTED @ 0= IF
        DROP DROP DROP              \ arg0/arg1/arg2 を捨てる
        E-IOERR R> REPLY-OK EXIT
    THEN

    \ ガード2: arg2 = 0 か（予約値域チェック）
    \ 現状 DSP: ( arg2 arg1 arg0 ), TOS=arg0
    \ arg2 を見るには ROT が必要
    ROT                              \ ( arg1 arg0 arg2 )
    DUP IF
        DROP DROP DROP              \ 後始末（arg2/arg0/arg1）
        E-INVAL R> REPLY-OK EXIT
    THEN
    DROP                             \ arg2=0 確認済み、捨てる
                                     \ ( arg1 arg0 ) ※ arg1=buf_size, arg0=buf_addr<TOS>

    \ buf_addr を FM-WK-DST に保存、buf_size はそのままスタック
    DUP FM-WK-DST !                  \ ( arg1 arg0 )  FM-WK-DST = buf_addr
    DROP                             \ ( arg1 )       arg0 用済み
                                     \ ( buf_size )  TOS = buf_size

    \ buf_size を退避（後でループ中の残量チェックに使う）
    \ Force/Forth では複雑な式は避け、buf_end_addr 方式で持つのが簡素
    \ buf_end_addr = buf_addr + buf_size
    FM-WK-DST @ +                    \ ( buf_end_addr )
    FM-WK-A !                        \ FM-WK-A = buf_end_addr（走査上限）

    \ カウンタ初期化
    0 FM-WK-LEN !                    \ 書き込み済みエントリ数 = 0
    0 >R                             \ R: tid i=0

    \ メインループ: i = 0 .. FS-DIR-ENTRIES-1
    BEGIN  R@ FS-DIR-ENTRIES <
    WHILE
        R@ DE-ADDR                   \ ( de_addr )
        DUP DE-FLAGS + @ FLG-USED AND IF
            \ このエントリは USED → コピー対象
            \ 書き込み先・残量チェック: FM-WK-DST + 16 ≤ FM-WK-A か？
            FM-WK-DST @ 16 +          \ ( de_addr next_dst )
            DUP FM-WK-A @ > IF
                \ buf あふれ → ループ脱出
                DROP DROP             \ ( ) ※ de_addr, next_dst 両方捨てる
                R> DROP               \ i 捨てる
                0 >R                  \ ダミー push（後段の R> DROP に合わせる）
                EXIT                  \ 本来は BEGIN…WHILE 抜けるが
                                     \ 簡素化のため EXIT で抜けて REPLY 側へ飛ばす設計
                                     \ ※ 実装側は LEAVE 相当の制御で代替する

            \ MEMCPY-B ( dst src len -- ) で de_addr+DE-NAME から FM-WK-DST へ 16B
            FM-WK-DST @ SWAP         \ ( de_addr next_dst dst ) 整理が複雑なので
                                     \ 以下は再整形した形で示す
            \ [整形後] スタック: ( de_addr )  +  事前にDSTを別途持つ方が綺麗
            \  → 実装は §6.7.3 の手順で簡素化する
        ELSE
            DROP                     \ FREE エントリ：de_addr 捨てる
        THEN
        R> 1 + >R                    \ i++
    REPEAT
    R> DROP                          \ i 捨てる

    \ 成功 REPLY: r0 = FM-WK-LEN
    FM-WK-LEN @ R> REPLY-OK ;
```

#### 6.7.3 実装簡素化の指針

上記擬似コードはスタック操作が複雑なため、**実装では以下のいずれかの簡素化案を採る**：

**案I（推奨・★v1.5.1 確定版／案P適用）：buf あふれ判定を「ループ前の最大可能件数計算」で代替**

> **v1.5.1 修正点**：カウンタ・ポインタを MEMCPY-B が破壊しない専用変数
> （FM-WK-COUNT / FM-WK-REMAIN / FM-WK-PTR）に変更した。
> 旧 v1.5 は FM-WK-A/LEN/DST を流用していたが、MEMCPY-B が FM-WK-LEN/DST を
> 破壊するためカウンタとポインタが壊れるバグがあった（案P で恒久修正）。

```forth
: FILE-LIST-IMPL  ( arg2 arg1 arg0 tid -- )
    >R                                  \ R: tid
    \ --- ガード1: FS-MOUNTED チェック ---
    FS-MOUNTED @ 0= IF
        DROP DROP DROP                  \ arg0/arg1/arg2 を捨てる
        E-IOERR R> REPLY-OK EXIT
    THEN
    \ --- ガード2: arg2 ≠ 0 チェック（予約値域）---
    ROT DUP IF                          \ ( arg1 arg0 arg2 ), arg2 を検査
        DROP DROP DROP
        E-INVAL R> REPLY-OK EXIT
    THEN
    DROP                                \ arg2(=0) 捨てる ( arg1 arg0 )
    \ 残: ( buf_size buf_addr ) TOS=buf_addr
    SWAP                                \ ( buf_addr buf_size )
    \ --- max_n = buf_size / 16 を計算 ---
    \ Force は SLASH(/) 未対応のため SHR(0x58) で代替: max_n = buf_size >> 4
    \ （force_memory_contract v1.1 §6.1）
    4 RSHIFT                            \ ( buf_addr max_n )
    FM-WK-REMAIN !                      \ FM-WK-REMAIN = max_n（残り書込可能枠）( buf_addr )
    FM-WK-PTR !                         \ FM-WK-PTR = buf_addr（書き込み先ポインタ）( )
    0 FM-WK-COUNT !                     \ FM-WK-COUNT = 0（書き込み済み件数）

    0 >R                                \ R: tid i=0
    \ --- メインループ: i < FS-DIR-ENTRIES かつ 残枠 > 0 の間 ---
    BEGIN  R@ FS-DIR-ENTRIES <
           FM-WK-REMAIN @ 0 > AND       \ 残り書込可能枠が 0 でない間
    WHILE
        R@ DE-ADDR                       \ ( de_addr )  DE-ADDR §6.6
        DUP DE-FLAGS + @ FLG-USED AND IF \ ( de_addr ) USED 判定（DE-FLAGS=+24 §3）
            \ --- USED エントリ: name 16B を FM-WK-PTR へコピー ---
            \ MEMCPY-B ( dst src len -- ): dst=FM-WK-PTR, src=de_addr+DE-NAME, len=16
            \ 注: MEMCPY-B は FM-WK-LEN/SRC/DST を破壊するが、本実装は
            \     カウンタ類を FM-WK-COUNT/REMAIN/PTR に置くため安全（案P）
            FM-WK-PTR @                  \ ( de_addr dst )
            OVER DE-NAME +               \ ( de_addr dst src )  src = de_addr+0
            16 MEMCPY-B                  \ ( de_addr )  16B コピー実行
            \ --- ポインタ・カウンタ更新（専用変数のみ操作）---
            FM-WK-PTR @ 16 + FM-WK-PTR !       \ 書き込み先を 16B 進める
            FM-WK-COUNT @ 1 + FM-WK-COUNT !    \ 書き込み済み件数 +1
            FM-WK-REMAIN @ 1 - FM-WK-REMAIN !  \ 残枠 -1
        THEN
        DROP                             \ de_addr 捨てる
        R> 1 + >R                        \ i++
    REPEAT
    R> DROP                              \ i 捨てる

    \ --- 成功 REPLY: r0 = 書き込み済み件数 ---
    FM-WK-COUNT @ R> REPLY-OK ;
```

**案I の利点：**

- `BEGIN ... WHILE ... REPEAT` 単一ループで完結（複雑な LEAVE 不要）
- `max_n = buf_size >> 4` で「あと何件書けるか」を持ち、残枠が 0 になったらループ終了
- Force コンパイラの SLASH 未対応問題（force_memory_contract v1.1 §6.1）を `4 RSHIFT` で回避
- 引数 0 / buf_size < 16 のケースも自然に処理される（max_n = 0 ならループに入らず 0 を返す）
- **カウンタ・ポインタを MEMCPY-B が破壊しない専用変数に分離（案P）したため、ループ内 MEMCPY-B 呼び出しでカウンタが壊れない**

**案II（将来検討）：** Force に LEAVE 相当を実装してから書き直す（今は採用しない）

実装は **案I を採用する**。

#### 6.7.4 注意事項

- `buf_size >> 4` で 16 で割っているが、Force は SLASH(/) を未対応なので `4 RSHIFT` を使う（force_memory_contract v1.1 §6.1）
- `RSHIFT` は kernel_forth で利用可能であることをビルド前に確認すること（ysd8800.prim §RSHIFT）
- **カウンタ・ポインタは専用変数 FM-WK-COUNT / FM-WK-REMAIN / FM-WK-PTR を使う（案P・v1.5.1）**。MEMCPY-B/MEMSET-B が破壊する FM-WK-LEN/SRC/DST/VAL は使用禁止。これらの専用変数は実装ソース kernel_forth の VARIABLE 定義群（現状 FM-WK-DST/SRC/LEN/VAL/A/B/C）に追加すること（§5.3 ワーク変数表・§11 実装前チェックリスト参照）
- 専用変数 3 個の追加メモリは +6B。Force は VARIABLE をデータ領域 $C000 系に配置するため、FileMgr 専用領域（$4800-$505F）を圧迫しない（force_memory_contract v1.1 §4.4 / DATA-START=$C000）
- ループ上限は `FS-DIR-ENTRIES`（=32）で確定。32 を超えるディレクトリは Phase 1 では想定しない

```
    ワード（MEMCPY-B/MEMSET-B/DIR-FIND/NAME-EQ?）を呼ばない
  - name 長チェック（NAME-LEN）は DIR-FIND より前に行う（DIR-FIND は
    FM-WK-SRC に name_addr を入れるため、順序を守る）
```

#### 6.8.2 擬似コード（案I・確定版）

DIR-FIND-FREE は引数なしで「最初の空き DE index」を返すが、OPEN が欲しいのは「最初の空き **OPENTAB スロット** index」である。両者は探索対象が異なる（DE vs OPENTAB）ため、OPEN 専用に **空きスロット走査をインライン**で書く（DIR-FIND-FREE の OPENTAB 版に相当）。

```
function FILE_OPEN_IMPL(name_addr):           # arg2/arg1 は無視
    # --- 手順1: name 長チェック ---
    if NAME-LEN(name_addr) >= 16: return E_NAMETOOLONG
    # --- 手順2: マウントチェック ---
    if FS-MOUNTED == 0: return E_IOERR
    # --- 手順3: ディレクトリ検索 ---
    di = DIR-FIND(name_addr)                  # FM-WK 破壊。-1 なら不在
    if di == -1: return E_NOENT
    # --- 手順4: 空き OPENTAB スロット探索（最小 index 方式・§5.3.3）---
    fid = -1
    for i in 0 .. FS-MAX-OPEN-1:              # i は R スタックで保持
        if OPENTAB[i].used == 0:
            fid = i ; break                    # 最初の空きを採用
    if fid == -1: return E_MFILE
    # --- 手順5: スロットにエントリ情報を記録 ---
    slot = FS-OPENTAB + fid * OT-SLOT-SIZE
    de   = DE-ADDR(di)                          # FS-DIRBUF + di*48
    slot[OT-USED]      = 1
    slot[OT-DIR-INDEX] = di
    slot[OT-START-SEC] = de[DE-START-SEC]       # de+20（u16）
    slot[OT-SIZE]      = de[DE-SIZE]            # de+16（u32、下位16bit運用）
    slot[OT-POS]       = 0
    # --- 手順6: fid を返す ---
    return fid
```

#### 6.8.3 Forth 実装方針（案I・★v1.6.1 で C2 反映＝Rスタック保持に変更）

実装は STAT-IMPL（v0.10.3 実装済み）と同じ構造テンプレートを踏襲する。要点：

- 進入時 `>R` で tid を R スタックへ退避
- arg1/arg2 を未検査で捨てるため、進入直後（tid 退避後）に `DROP DROP` で `( name_addr )` にする
- name 長・マウント・DIR-FIND の各ガードで失敗したら `（不要値を DROP）→ E-xxx R> REPLY-OK EXIT`
- DIR-FIND 成功後、得た **dir_index を R スタックへ退避**してから空きスロット走査に入る（走査で dir_index を保持するため）
- 空きスロット走査は DIR-FIND-FREE（§6.2 と同イディオム）と同型の R スタックループ。`-1`（未発見マーカ）と走査カウンタ i を扱い、複合 WHILE 条件（`未発見 AND i<FS-MAX-OPEN`）で抜ける

**【C2 反映・v1.6.1：見つけた fid は R スタック／データスタックで保持し、ワーク変数を流用しない】**

v1.6 では「見つけた fid」を FM-WK-B に記録する方針だったが、レビュー C2 の指摘（「将来、走査ループ内に FM-WK 破壊ワードを足すと fid が壊れる時限装置」）を受け、**fid 記録もワーク変数を使わず R スタック／データスタックで完結させる方針に変更**した。これは v1.5.1 で確立した責務分離の精神に沿い、事故耐性が高い。具体イディオム（DIR-FIND の「結果を R スタックで持ち回る」変形）：

```forth
\ DIR-FIND 成功後、( name_addr ) は不要。dir_index を R に積んで走査開始。
\ スタック表記: R: tid（既に退避済み）
\ DIR-FIND 結果 di を得た直後の例（di はデータスタック TOS）:
   >R                               \ R: tid di     （di を退避）
   -1                               \ ( found=-1 )  見つけた fid、初期 -1
   0 >R                             \ R: tid di i=0  走査カウンタ
   BEGIN
       R@ FS-MAX-OPEN <             \ i < 4
       OVER -1 = AND                \ かつ未発見（found==-1）
   WHILE
       R@ SLOT-ADDR OT-USED + @ 0= IF   \ slot[i].used == 0 ?
           DROP R@                  \ found = i（古い-1を捨てR@=iを採用）
       THEN
       R> 1 + >R                    \ i++
   REPEAT
   R> DROP                          \ i 破棄、R: tid di
\ ここで ( found ) がデータTOS。found==-1 なら E_MFILE。
```

この方式では「見つけた fid（found）」をデータスタックに、dir_index と tid を R スタックに保持し、ワーク変数を一切使わない。走査ループ内も副作用ワード（FM-WK 破壊系）を呼ばないため安全（§6.8.1 危険な組合せ）。

**【手順5：スロット記録の書き込み順序・M1 同一規約で確定】**

found（fid）が有効なら、スロットの各フィールドを `!` の `( val addr -- )` 規約（§6.6）に従い「**値を先に積み、アドレスを TOS にして `!`**」で書き込む。OT-USED→OT-DIR-INDEX→OT-START-SEC→OT-SIZE→OT-POS の順（順序自体は任意だが、各書き込みは val→addr→`!`）：

```forth
\ 前提: found=fid（データ）、R: tid di。de = DE-ADDR(di) で算出。
\ 各フィールド書き込みは「値 アドレス !」の順序（§6.6 ! = (val addr --)）
   \ 例: OT-USED = 1
   1                                \ ( fid 1 )            値
   OVER SLOT-ADDR OT-USED +         \ ( fid 1 addr )       アドレス=fid*16+base+0
   !                                \ ( fid )              書き込み
   \ 例: OT-DIR-INDEX = di（R から取得）
   R@                               \ ( fid di )           値（di を R から複製）
   OVER SLOT-ADDR OT-DIR-INDEX +    \ ( fid di addr )
   !                                \ ( fid )
   \ OT-START-SEC = de+DE-START-SEC の内容、OT-SIZE = de+DE-SIZE の内容、
   \ OT-POS = 0 も同様に「値 アドレス !」順で書く（実装フェーズで確定）
```

**【スタック設計の注意・kaizen 原則】** 具体的なスタック操作（OVER/DUP の最小化、de アドレスの保持方法）は実装フェーズ（Step 5-3）で STAT-IMPL を雛形に確定し、机上検証する。確定の指針は「① fid はデータスタックに保持（最後に REPLY-OK の r0 になる）、② di と tid は R スタック、③ 各フィールド書き込みは例外なく `val addr !` 順」の 3 点。

#### 6.8.4 注意事項

- NAME-LEN は「16 で打ち切り」実装（§6.6・実装済み）なので、15 文字超は戻り値 16 となる。判定は `NAME-LEN 16 < 0= IF E_NAMETOOLONG`（= 16 以上なら長すぎ）
- DIR-FIND は内部で FM-WK-SRC に name_addr を格納する。name 長チェック（NAME-LEN）を **DIR-FIND より前**に済ませること（NAME-LEN は副作用なしなので順序自由だが、可読性のため先頭に置く）
- 空きスロット探索の `OT-USED + @` は SLOT-ADDR（§6.6・( fid -- addr )）を使い `fid SLOT-ADDR OT-USED + @` で読む
- **スロット各フィールドの書き込みは `!` = `( val addr -- )`（§6.6）に従い「値を先に積み、アドレスを TOS にして `!`」の順序で統一する（M1・v1.6.1）**
- size は u32 だが Phase 1 は下位 16bit のみ運用（DE-SIZE/OT-SIZE とも `@` で 16bit 読み書き、§3.4 のファイルサイズ上限 known limitation 参照）
- **見つけた fid・dir_index はワーク変数でなく R スタック／データスタックで保持する（C2・v1.6.1）。走査ループ内で FM-WK 破壊ワードを呼ばない**

### 6.9 FILE-CLOSE-IMPL（★v1.6 新設、Step 5-4 対象）

#### 6.9.1 ワード定義（標準テンプレート）

```
ワード名: FILE-CLOSE-IMPL
スタック : ( arg2 arg1 arg0 tid -- )
            arg2 = 予約（未検査）
            arg1 = 予約（未検査）
            arg0 = fid<TOS の下>
            tid<TOS> = REPLY 先クライアント tid
副作用  :
  - 成功時 FS-OPENTAB の当該スロットの OT-USED を 0 にする（他フィールド不変）
  - FS-DIRBUF / ディスクには一切触れない
  - REPLY-OK が FM-WK-A/B を破壊する
  - 戻り値 r0 = E-OK(0) または E_BADF を IPC4-REPLY
前提条件:
  - tid が有効なクライアント TCB（IPC4 ランタイムが保証）
  - FS-MOUNTED は問わない（RAM のみ操作するため。§4.3.2.4）
危険な組合せ:
  - fid は必ず FID-VALID? に通してから使う（負値・範囲外・未used を一括判定）
  - CLOSE 本体はワーク変数を使わずスタック上で完結させる（REPLY-OK の FM-WK-A/B のみ）
```

#### 6.9.2 擬似コード（確定版）

```
function FILE_CLOSE_IMPL(fid):                # arg2/arg1 は無視
    # --- 手順1-2: fid 検査（FID-VALID? 一本）---
    if not FID-VALID?(fid): return E_BADF      # 範囲外 or 未オープン
    # --- 手順3: スロットを未使用へ（OT-USED 1→0）---
    slot = FS-OPENTAB + fid * OT-SLOT-SIZE
    slot[OT-USED] = 0
    # --- 手順4: 成功 ---
    return E_OK
```

#### 6.9.3 Forth 実装方針

CLOSE は最も単純な IMPL である。要点：

- 進入時 `>R` で tid を退避、`( arg2 arg1 arg0 )` が残る
- arg2/arg1 を `DROP DROP` で捨て `( fid )` にする
- `DUP FID-VALID? 0= IF DROP E-BADF R> REPLY-OK EXIT THEN`（無効なら E_BADF。`DUP` で fid を残して FID-VALID? に渡し、偽なら元の fid を `DROP`）
- 有効なら、当該スロットの OT-USED を 0 にする。**`!` のスタック効果は `( val addr -- )`（値が NOS、アドレスが TOS）**（§6.6・ysd8800.prim PRIM STORE で確定）なので、**値 0 を先に積み、書き込み先アドレスを TOS にして `!` する**：

```forth
\ スタックは ( fid )。値0を先に積み、アドレスをTOSにして書き込む。
0  SWAP                          \ ( 0 fid )    値0をfidの下へ
   SLOT-ADDR OT-USED +           \ ( 0 addr )   addr = fid*16 + FS-OPENTAB + OT-USED(=+0)
   !                             \ ( )          *addr = 0（OT-USED を 0 に）
```

- 上記は「`fid` の前に `0` を積みたい」ため `0 SWAP` で `( fid )` → `( 0 fid )` とし、`SLOT-ADDR OT-USED +` で fid をアドレスへ変換、TOS をアドレス・NOS を値 0 にして `!`（= `( val addr -- )`）で書き込む。これにより `!` のスタック効果と完全に整合する
- 最後に `0 R> REPLY-OK`（E_OK=0 を返す）

**【v1.6.1・M1 修正】** v1.6 では本箇所を `SLOT-ADDR OT-USED + 0 SWAP !` と記述していたが、`!` の `( val addr -- )` に対するスタック遷移が一意に確定しておらず（addr を作ってから 0 を積んで SWAP する読み筋と、別解釈が併存）、kaizen 原則「擬似コードは実装に落とせる精度であること」に抵触した。v1.6.1 で上記の `0 SWAP ... ! `（値先積み・アドレス TOS）形に確定し、OPEN 側（§6.8）の全フィールド書き込みも同一の `val ... addr !` 順序規約で閉じた。OT-USED は OPENTAB スロット先頭（オフセット +0）であり `OT-USED +` は実質加算 0 だが、可読性と将来のオフセット変更耐性のため明示的に `OT-USED +` を書く。

#### 6.9.4 OPEN/CLOSE 一体テストの設計意図（KY19）

OPEN と CLOSE を別々の Step（5-3/5-4）で実装するが、**設計は本節で一体**として詰めた。理由（KY19 防止策）：

- OPEN が OT-USED を 1 にし、CLOSE が 0 に戻す。両者の「遷移点の対」が崩れると、二重 close で他スロットを誤って解放したり、close 漏れでスロットが枯渇したりする
- 本設計では FID-VALID?（範囲＋used 同時チェック）を CLOSE の唯一のガードとすることで、「未 open スロットの close」「範囲外 fid の close」「エラーコードを fid として渡す事故」を全て E_BADF で安全に弾く
- §8.2 のテストは OPEN（F2, 'O' 出力）と OPEN+CLOSE ペア（'OC' 出力）を用意し、両 IMPL の整合を実機で確認する（実装は個別だがテストはペア）

## 8. FileMgr テストタスクの設計

### 8.1 テスト方針

ストレージドライバの STOR-TEST-TASK（yuios_ph3_storage_design_v1_3.md §7）と同様、FILEMGR-TEST-TASK を Forth 側に追加し起動時自動実行する。

**【★最重要・KY 項目】テストタスクの tid に関する注意：**

ストレージ設計書の STOR-TEST-TASK は tid=5、UART-TEST-TASK は tid=4 を使っていた。しかし yuios_design_v2_2.md §4.4 の正式 TID 確定により、**tid=4 は FileMgr、tid=5 は ProcMgr** に割り当てられた。したがって：

- FileMgr のテストタスクを追加する場合、**tid は 7 以降の空き番号**を使う（tid=4,5,6 は FileMgr/ProcMgr/Shell に予約済み）。
- 既存の UART-TEST-TASK（旧 tid=4）・STOR-TEST-TASK（旧 tid=5）を Ph.4 でも併用する場合、これらの tid も 7 以降へ変更する必要がある。
- 本書では FILEMGR-TEST-TASK に **tid=7** を提案する（レビューで確定）。

この tid 衝突は kaizen 原則のとおり「設計上の地雷」であり、§9 KY 項目および §11 実装前チェックリストで再掲する。

### 8.2 FILEMGR-TEST-TASK のテスト内容

| ステップ | 内容 | 期待 |
| --- | --- | --- |
| F0 | 区切りスペース出力（UART_PUTC ' '） | — |
| F1 | FILE_WRITE で "hello.txt"（内容 "YUI OS Ph4!" 11B）を作成 | r0=0 |
| F2 | FILE_OPEN "hello.txt" | r0=fid（0〜3） |
| F3 | FILE_READ fid → dst_buf（16B 要求） | r0=11（実サイズ） |
| F4 | dst_buf 先頭 11B を "YUI OS Ph4!" と比較 | 一致 |
| F5 | FILE_STAT "hello.txt" → stat_buf | size=11 |
| F6 | FILE_DELETE "hello.txt"（fid を open したまま実行） | r0=E_BUSY（$FE0B）。open 中削除拒否の確認（§4.6・v1.2） |
| F7 | FILE_CLOSE fid | r0=0 |
| F8 | FILE_DELETE "hello.txt"（close 後に実行） | r0=0。close 後は削除成功 |
| F9 | 結果出力：全 PASS なら 'Q'、失敗なら 'f' | 'Q' |

**期待出力：** 既存 Ph.3 出力 `ABCXD P` の後にスペース + `Q` が追加され、`ABCXD P Q` となる。

**【F6/F8 追加の意図】（v1.2）** review19 指摘の「open 中削除」仕様（§4.6）を実機検証するため、F6 で「open 中の FILE_DELETE は E_BUSY」、F8 で「close 後の FILE_DELETE は成功」を確認するステップを追加した。F6→F7→F8 の順で「open 中は拒否、close すれば削除可」という Phase 1 仕様の往復を 1 本のテストで押さえる。

**【設計判断】** テスト出力文字を 'Q' とした理由：ストレージテストが 'P'（PASS）を使っているため、FileMgr テストは次の文字 'Q' を使い、出力を見ただけでどのフェーズまで通ったか分かるようにする（ABCXD=UART, P=STOR, Q=FileMgr）。

### 8.3 テストバッファ配置

テストタスク（FILEMGR-TEST、tid=7）が使う作業バッファは、memmap v1.2 の**テストバッファ予約領域 `$EC00-$EFFF`（1 KB）**内に確保する。この領域は元々 STOR/UART テスト用のバッファ予約であり、FileMgr のテストもここを使うのが memmap の設計意図に沿う。STOR-TEST/UART-TEST のテストと FileMgr-TEST は同時実行しない（テストは順次実施）ため、領域の時分割共用が可能である。

| シンボル | アドレス | サイズ | 用途 |
| --- | --- | --- | --- |
| FT-NAME-BUF | $EC00 | 16 B | テスト用ファイル名 "hello.txt" |
| FT-SRC-BUF | $EC10 | 512 B | 書き込みデータ（1 セクタ未満のテストデータ） |
| FT-DST-BUF | $EE00 | 512 B | 読み出し先（FILE_READ の dst） |
| FT-STAT-BUF | $EF00 | 32 B | FILE_STAT 結果 |

合計 $EC00-$EF1F（約 1.1 KB 弱）。テストバッファ予約 $EC00-$EFFF（1 KB）にほぼ収まるが、FT-DST-BUF 末尾が $EFFF を 32 B 超える。テスト時のみの一時利用であり、かつ FileMgr 常駐領域（$4800 系）とは無関係なので実害はないが、§11 実装前チェックリスト I-1（memmap v1.3 改版）の際に、テストバッファ予約を $EC00-$F03F 等へ 64 B 拡張するか、FT-SRC/DST-BUF を各 256 B に縮めることを検討する。

**【v1.0 からの修正】** v1.0 ではテストバッファを `$EF60-$EF9F` に置き「FileMgr 領域 $EF5F の続き」としていたが、これは memmap v1.2 のテストバッファ予約領域（$EC00-$EFFF）と部分的に重なる中途半端な配置だった。v1.1 では FileMgr 常駐領域を $4800 系へ移したため（§5.2）、テストバッファは素直に memmap のテストバッファ予約領域 $EC00 起点に置く。

### 8.4 動作確認手順

```bash

#    Step 4-6 動作確認: --size-kb 32 (32KB = 64セクタ)
python3 mkfs_yuifs.py disk.img --size-kb 32 -v

# 2. UART RX テスト用入力
printf 'X' > uart_test_input.bin

# 3. 実行（emu23 v1.04 以降）
./emu23 yuios_v13.bin yuios_v13.sym -i uart_test_input.bin --disk disk.img -q

# 期待出力 (Step 5-2 後): 0A BC123MPDQ L
#  - 'M' (大文字) = FS-MOUNT 成功（マウント済みで FILEMGR-TASK が動作）
#  - 'm' (小文字) = マウント失敗（magic/version 不一致）

# 4. ディスク内容確認（hello.txt のデータがデータ領域に書かれているか）
hexdump -C -s 2048 -n 32 disk.img    # LBA4 = offset 2048
# 期待: 59 55 49 20 4f 53 20 50 68 34 21 ...（"YUI OS Ph4!"）
```

#### 8.4.1 LBA 配置の運用ルール（v1.3 追加）

Ph.4 実装時に **LBA=0 共有問題** が発覚した（HANDOVER_CHAT30 §1.2 参照）。
LBA=0 はスーパーブロック専用領域だが、Ph.3-B 開発時の STOR-TEST-TASK が
LBA=0 に "STOR_TST" を書き込んでいたため、FS-MOUNT の MAGIC-CHECK が必ず失敗していた。

**対処（v1.3 確定）:**

| テスト名 | 使用 LBA | 設計書 |
|---|---|---|
| STOR-TEST-TASK (Ph.3-B) | LBA=10 | yuios_ph3_storage_design v1.4 §7.1 |
| FILEMGR-TEST-TASK (Ph.4) | **LBA=10 は使用禁止**、別 LBA を使用 | 本書 §8.2 |
| 将来のテスト群 | LBA=10〜15 は STOR-TEST / 将来予約として保留 | （本書） |

**FILEMGR-TEST-TASK の LBA 使用方針:**

- FileMgr の FILE_WRITE 経由で書き込まれるデータ領域は **mkfs の `next_free_sec` 起算**（通常 LBA=4 から自動採番）
- 直接 LBA を指定する箇所は無いため、FILEMGR-TEST と STOR-TEST の LBA 衝突は起きない
- ただし、`hexdump` での確認等で LBA=10 を覗くと STOR-TEST が書いた "STOR_TST" が見える可能性がある（バグではなく動作の重ね合わせ）

#### 8.4.3 Step 5-2 試験手順（★v1.5 新設、FILE-LIST-IMPL 単体動作確認）

##### 8.4.3.1 試験ワード FILE-LIST-TEST の実装方針

FILEMGR-TEST-TASK 内に試験ワード FILE-LIST-TEST を追加する。本ワードは以下を実施する：

1. テスト用 buf を `TEST-DST-BUF + $100`（=$EF00、256B 領域）から確保。既存の TEST-DST-BUF は 512B 確保（$EE00-$EFFF）のうち先頭 256B のみ FILE_STAT 用に使われており、後半 256B が空いている。**【v1.5.2 訂正】v1.5/v1.5.1 では「$F900-$F9FF（タスクスタック未使用領域）」と記載していたが、memmap v1.4 §5.3 によると $F900-$F97F は tid=2 のデータスタック領域であり、未使用ではなく衝突する。kaizen 原則 3（実測した状態を起点に）に従い実装ソースを精査して訂正した。
2. FILE-LIST-OP を `IPC4-CALL` で発行（buf_size=256, buf_addr=`TEST-DST-BUF $100 +`, arg2=0）
3. 戻り値 r0 を取得
4. **判定**：
    - mkfs_yuifs.py で hello.txt 1個を作っているので、期待 r0 = 1
    - r0 = 1 なら `L` を出力（成功）
    - r0 ≠ 1 なら `l`（小文字）を出力（失敗）

##### 8.4.3.2 試験用ディスクの前提

`mkfs_yuifs.py` がデフォルトで以下のディレクトリ状態にする：

| index | name | flags |
|---|---|---|
| 0 | "hello.txt"+NUL+... | FLG_USED=1 |
| 1..31 | (未使用) | FLG_USED=0 |

このため期待エントリ数は **1** となる。

##### 8.4.3.3 異常系の追加試験（将来）

Phase 1 では正常系（r0 = 1）のみ確認する。以下は Phase 2 以降の検討事項：

- buf_size = 0 → r0 = 0 期待
- buf_size = 8 (16未満) → r0 = 0 期待
- arg2 = 1 → r0 = E_INVAL (=$FE09) 期待
- FS 未マウント時 → r0 = E_IOERR (=$FE08) 期待

> **【v1.6 訂正】** 旧 v1.5 では本箇所を「E_INVAL (=$FE03)」「E_IOERR (=$FE01)」と誤記していた。正しくは §4.2 のとおり **E_INVAL=$FE09、E_IOERR=$FE08** である（$FE03 は E_MFILE、$FE01 は E_NOENT）。実装ソース kernel_forth_v0_10_3.fs の CONSTANT 定義（E-IOERR=$FE08, E-INVAL=$FE09）が正。v1.6 で訂正（kaizen 原則：見えているバグは先に潰す）。

##### 8.4.3.5 デバッグ手順（fail 時）

`l`（小文字）が出た場合、または 'L' すら出ない場合は以下の順で原因を切り分ける：

1. r0 の値を `put-hex4` 等で出力して E_IOERR/E_INVAL/その他のどれか確認
2. r0 ≠ 1 かつ r0 ≥ 0 なら、エントリ数の計算ロジックを疑う（DIR-FIND 系の挙動と比較）
3. r0 = E_IOERR なら、FS-MOUNTED の状態を疑う（FILEMGR-INIT の DIR-LOAD 完了確認）
4. emu23 トレース（-b $WORD_FILE_LIST_IMPL）で IMPL 内部の動作を観察

#### 8.4.4 Step 5-3/5-4 試験手順（★v1.6 新設、FILE-OPEN-IMPL / FILE-CLOSE-IMPL 単体動作確認）

##### 8.4.4.1 試験方針

Step 5-2（LIST）と同じく、FILEMGR-TEST-TASK に試験ステップを追加し、起動時自動実行で結果を 1 文字出力する。OPEN は Step 5-3 で 'O'、CLOSE は Step 5-4 で 'C'（OPEN に続けて 'OC'）を出力する。

LIST-TEST が `0A BC123MPDQL` を出力する版（v0.10.3）に追記する形で、出力は段階的に伸びる：

| Step | 実装版 | 期待出力 |
|---|---|---|
| 5-2 完了（現状） | v0.10.3 | `0A BC123MPDQL` |
| 5-3（OPEN 追加） | v0.10.4 | `0A BC123MPDQLO` |
| 5-4（CLOSE 追加） | v0.10.5 | `0A BC123MPDQLOC` |

##### 8.4.4.2 OPEN 単体試験（Step 5-3、'O' 出力）

| ステップ | 内容 | 期待 |
|---|---|---|
| O1 | FILE_OPEN "hello.txt"（mkfs が作成済みの 1 ファイル） | r0 = 0（最小空き index 方式により最初の OPEN は必ず fid=0。§5.3.3） |
| O2 | r0 = 0 なら 'O' 出力、それ以外は 'o'（小文字）出力 | 'O' |

試験名バッファは LIST-TEST と同じ TEST-SRC-BUF 系を使い、"hello.txt\0" を書き込む（LIST-TEST が使う "no.txt" とは別オフセット、または上書き）。

```forth
\ FILE_OPEN: msg3=arg2=0, msg2=arg1=0, msg1=arg0=name_addr, msg0=op
0                                       \ msg3 = arg2 = 0
0                                       \ msg2 = arg1 = 0
<name_addr>                             \ msg1 = arg0 = "hello.txt"
FILE-OPEN-OP                            \ msg0 = $0201
FILEMGR-TID-ADDR @                      \ tid
IPC4-CALL
>R DROP DROP DROP R>                    \ r0 のみ残す
\ r0 == 0 なら 'O'、else 'o'
0 = IF $4F FILEMGR-PUTC ELSE $6F FILEMGR-PUTC THEN
```

**【注意】** O1 の期待 r0=0 は「fid=0」であり、エラーではなく**成功**である。`0 =` 判定で 'O' を出すのは「fid=0 が返った＝最小空きスロットが正しく割り当てられた」ことの確認。もし hello.txt が存在しなければ E_NOENT（$FE01）が返り `0 =` は偽となり 'o' が出る（識別可能）。

##### 8.4.4.3 OPEN+CLOSE ペア試験（Step 5-4、'OC' 出力）

OPEN で得た fid をそのまま CLOSE する。Step 5-3 の O1/O2 に続けて：

| ステップ | 内容 | 期待 |
|---|---|---|
| C1 | O1 で得た fid（=0）を保持しておき FILE_CLOSE fid | r0 = 0（E_OK） |
| C2 | r0 = 0 なら 'C' 出力、それ以外は 'c'（小文字）出力 | 'C' |

```forth
\ O1 の r0（fid）を R スタック等で保持しておく
\ FILE_CLOSE: msg3=arg2=0, msg2=arg1=0, msg1=arg0=fid, msg0=op
0                                       \ msg3 = arg2 = 0
0                                       \ msg2 = arg1 = 0
<fid>                                   \ msg1 = arg0 = fid（O1 の戻り値）
FILE-CLOSE-OP                           \ msg0 = $0202
FILEMGR-TID-ADDR @                      \ tid
IPC4-CALL
>R DROP DROP DROP R>                    \ r0 のみ残す
\ r0 == 0 なら 'C'、else 'c'
0 = IF $43 FILEMGR-PUTC ELSE $63 FILEMGR-PUTC THEN
```

**【二重 close 確認（任意・推奨）】** C1 の後にもう一度同じ fid を CLOSE すると、OT-USED が既に 0 なので FID-VALID? が偽となり E_BADF（$FE04）が返るはず。これを追加ステップ C3 として確認すれば、CLOSE の冪等性ガードを実証できる（Phase 1 では任意、'OC' が出れば Step 5-4 完了とする）。

##### 8.4.4.5 デバッグ手順（fail 時）

`o` または `c`（小文字）が出た場合の切り分け：

1. **'o' が出る（OPEN 失敗）**：r0 を put-hex4 で出力し、E_NOENT（$FE01）/E_IOERR（$FE08）/E_MFILE（$FE03）/E_NAMETOOLONG（$FE05）のどれか確認
   - E_NOENT → mkfs に hello.txt が入っているか確認（`--add-file hello.txt`）。DIR-LOAD/DIR-FIND の挙動を LIST-TEST（'L' が出ているか）と比較
   - E_IOERR → FS-MOUNTED 確認（'M' が出ているか）
   - r0 が 1,2,3 のいずれか → fid は返っているが 0 でない（先に他スロットが使われている？ FILEMGR-INIT の OPENTAB クリア確認）
2. **'O' は出るが 'c' が出る（CLOSE 失敗）**：CLOSE の r0 を確認
   - E_BADF → FID-VALID? が偽を返している。O1 で保持した fid が正しく C1 に渡っているか（R スタック退避の depth 確認）。OPEN が OT-USED=1 を実際に書いたか emu23 メモリダンプ（$4820 の OT-USED）で確認
3. emu23 トレース（`-b $WORD_FILE_OPEN_IMPL` / `-b $WORD_FILE_CLOSE_IMPL`）で IMPL 内部を観察
4. FS-OPENTAB（$4820〜）を `-d $4820 64` 等でダンプし、OPEN 後に slot0 の OT-USED=1・OT-DIR-INDEX が正しいか、CLOSE 後に OT-USED=0 になっているか確認

### 11.4 スタック容量の見積もり（kaizen 原則16）

**データスタック（DSP）：** FileMgr の各 IMPL ワードで DSP に同時に積まれる最大ワード数を見積もる。

| 局面 | 最大同時積み上げ | 備考 |
| --- | --- | --- |
| FILE-DISPATCH 進入時 | 5（arg2 arg1 arg0 op tid） | tid は即 >R |
| FILE_READ ループ内（IPC4-CALL 発行前） | 約 6（dst, remain, lba, chunk, fid 等） | ループ変数は R スタックで保持 |
| FILE_READ ループ内で STOR へ IPC4-CALL する瞬間 | 上記 6 のうち保持必要分 + CALL 引数 5 | 後述の対策で瞬間最大を抑制 |
| 最大同時（対策後） | **約 12 ワード** | 下記対策込みの安全側見積もり |

**【v1.1：FILE_READ ループ内 IPC4-CALL 時の瞬間最大の精査】（社内レビュー指摘）**

§6.3 の FILE_READ セクタループは、ループ内で STOR へ `0 buf lba STOR-READ-OP tid IPC4-CALL`（5 ワード）を発行する。このとき「ループ継続に必要な変数（残バイト数 remain、現 LBA、コピー先 dst、fid 等）」を保持したまま 5 ワードを積むと DSP が深くなる。

v1.1 の対策：**ループ継続変数（remain / lba / dst の 3 値）は IPC4-CALL を挟む区間では R スタックに退避**する。具体的には、ループ 1 周の構造を次のようにする：

```
ループ先頭:  ループ変数を R スタックから R@ で必要分だけ複製参照
IPC4-CALL前: CALL 引数 5 ワードのみを DSP に積む（ループ変数は R スタック上）
IPC4-CALL後: 戻り値 r0..r3 を処理（4 ワード）、R スタックの変数を更新
```

これにより IPC4-CALL 発行の瞬間、DSP 上にあるのは「CALL 引数 5 ワード」＋「直前計算の一時値 数ワード」のみとなり、瞬間最大は約 9〜10 ワードに収まる。ループ変数を DSP に置いたまま CALL する設計（瞬間 11+ ワード）は採らない。R スタックの使用深さは「戻りアドレス + ループ変数 3」で +6B 程度。

**最大使用量（DSP）：** 12 × 2B = 24 B。余裕率 2.0 を適用し **48 B 以上**をデータスタックに確保する。

**【参照文書の更新（v1.1）】** v1.0 は「タスクあたりデータスタック 128B（yuios_design_v2_1.md §3.3）」を根拠にしていたが、v2.1 は旧版である。現行 **yuios_design_v2_2.md §4.3** のタスクスタック仕様で再確認すること（§11 実装前チェックリスト I-7）。v2.2 の値が 128B であれば本見積もり（48B 必要）は十分に余裕がある。万一 v2.2 でスタック幅が縮小されていた場合は再評価する。

**コールスタック：** FileMgr の最大ネスト深さは FILEMGR-TASK → FILE-DISPATCH → FILE_xxx_IMPL → DIR-FIND → NAME-EQ? → MEMCPY-B 程度（約 6 段）。IPC4-CALL は内部でスケジューラに遷移しコールスタックを消費しない（saved_pc 方式）。1 段あたり戻りアドレス 2B として 6×2=12B、加えて §6.3 の対策で R スタックにループ変数 3 値（6B）を退避するため計 18B 程度。余裕率 2.0 で 36B 以上。タスクあたりコールスタック（v2.2 §4.3 で確認）に対し十分。

**【結論】** タスクあたりのスタック（yuios_design_v2_2.md §4.3 で確認すること）で FileMgr は問題なく動作する見込み。FileMgr 用に特別なスタック拡張は不要。ただし最終確定は §11 I-7 で v2.2 の値を確認後とする。
