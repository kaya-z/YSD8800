## 1. 実ソース突合（道2 の成立根拠・KY34）

道2 の技術的成立可否を左右する核心を実ソースで突合した。

| 設計書の主張 | 実ソース | 突合結果 |
|---|---|---|
| YOF セクションヘッダに load_addr フィールドが既存・8B 不変（§3.1.1） | lnk23.c:85-91 `yof_sec_t`（8 バイト、末尾に `uint16_t load_addr`） | ✅ 一致。構造体拡張不要。バイト数・レイアウト不変の主張は正確。 |
| 現状 load_yof は load_addr を読まず 0 固定（道2 で読込みに変更） | lnk23.c:341（8B 読込）→ L351 `ls->load_addr = 0`（読まずに 0 代入） | ✅ 一致。L341 で 8B 読むが load_addr を捨て L351 で 0 上書き。道2 はここを「読んで使う」に変える局所改修。 |
| `.bin` 入力は既に load_addr 固定で自動配置スキップ（道2 と同型の前例） | lnk23.c:459-473（`ls->load_addr = inp->bin_addr`）／L492-493（`INPUT_BIN` は place_sections で continue） | ✅ 一致。道2 の「load_addr 非0 なら自動配置スキップ」は `.bin` 経路と構造同型。局所改修の主張を裏付け。 |
| 自動連続配置が $0000 から積み ROM 超過（旧前提崩壊の原因） | lnk23.c:486-501（text_cur=$0000 起点で順次積む）／L592-593（`TEXT exceeds ROM area ($3FFF)`） | ✅ 一致。症状記述・エラーメッセージとも実コードに存在。 |

→ 道2 の前提・症状・局所性の主張はすべて実ソースで裏付け済み。設計の技術的骨格は健全。

## 2. 指摘事項

### M（必須修正・承認ブロッカー）

#### M-3：道2 で固定配置されるセクションに対する ROM 境界／overlap チェックの適用関係を明記すること

道2 は YOF セクションを load_addr で固定配置するが、配置後の `check_memory()`（lnk23.c:528-600）は load_addr ベースで動く。ここで2点、設計書が**現状の挙動と道2 の意図が一致するか**を明記していない。

1. **overlap チェック（L569-578）**：道2 で forth@$5100／kernel@$0000 を固定配置した場合、両者は重ならないので通る——という PoC 実証（§3.5.4「overlap なし」）は確認済み。ただし check_memory のオーバーラップ判定は**全セクション総当たり**であり、道2 固定配置セクションと自動配置セクションが混在した場合の挙動（固定が先か自動が先か、衝突時のエラー文言）が設計書に無い。YUI OS は forth/kernel の2固定のみで自動配置が無いため現状は問題化しないが、**「道2 では自動配置と固定配置の混在を当面サポートしない（全 YOF セクションが load_addr を持つ前提）」のか「混在可」なのかを §3.5.3 に明記**すること。

2. **ROM 境界チェック（L592-593）**：forth@$5100 は ROM 境界 $3FFF を超えるが、これは RAM 領域であり正当。しかし check_memory の baremetal チェックは `text_end > 0x3FFF` で**一律エラー**（L592）。forth セクションが TEXT 型なら text_end が $5100+ となり**このエラーに引っかかる**はず。PoC で I1 相当が通った（§3.5.4）理由が設計書から読み取れない——forth を DATA 型扱いにしているのか、baremetal チェックを通らない経路なのか、あるいは別の仕掛けか。**道2 で forth@$5100 が ROM 境界チェックをどう通過するのかを §3.5.3 に明記**すること。これは「見えているバグの芽」になり得る最重要確認点。

> 補足：L592 は `opt_machine == MACH_BAREMETAL` 限定。YUI OS のリンクが baremetal モードか否か、forth の SEC 型（TEXT/DATA）が何かによって結論が変わる。PoC が通った事実があるので破綻はしていないはずだが、**なぜ通るかの機序を設計書に残さないと、後日 baremetal 化や型変更で静かに再発する**。

### C（要確認・確定・承認ブロッカー）

#### C-3：load_addr=0 の意味論を確定すること（Q6 の本文確定）

§7 Q6 が「load_addr=0 は自動配置（後方互換）」とするが、これは**「$0000 への意図的固定配置」と区別できない**という自己申告どおりの曖昧さを残したまま「要確認」で本文に降りていない。kernel は `.org $0000` であり、道2 では sec_origin=$0000 → load_addr=$0000 が記録される。すると「kernel を $0000 に固定したい」意図と「load_addr 未指定＝自動配置」が同じ $0000 で表現され、衝突する。

PoC では kernel@$0000 が正しく置かれた（§3.5.4）が、これが「load_addr=0 を自動配置した結果たまたま $0000 になった」のか「$0000 固定として置いた」のか、機序が確定していない。**推奨**：道2 では「YOF セクションが `.org` を1つでも持てば sec_origin が確定し、load_addr に**明示フラグ（has_org 等）と共に**記録される」とし、`load_addr=0 かつ has_org=1` を「$0000 固定」、`has_org=0` を「自動配置」と区別する。8B ヘッダに新フラグを足す余地が無ければ、flags バイト（lnk23.c:86 `uint8_t flags`）の空きビットを用いる。いずれにせよ **§3.5.3 で load_addr=0 の解釈を一意に確定**すること。Q6 を「要確認」のまま実装に入れない。

### D（設計判断・非ブロッカー）

#### D-2：道2 採用と α-A 不採用の記録（§3.6）は適切

α-A（位置独立化）の不採用理由を「内部参照が reloc 化されず絶対埋め込み」という実装事実に基づき記録した点は良い。将来 scc23 Phase 2 で分割コンパイル（R_SECREL 導入）に進む際、この判断記録が「なぜ当時 reloc 化しなかったか」の一次資料になる。kaizen への原則追記を推奨（「位置独立化は全内部参照 reloc 化を要し影響甚大。固定配置で足りるなら .org 尊重を優先」）。

#### D-3：Q1（Force `.global` 付与＝案F2）は実証済につき承認推奨

Q1 は前回 L-4 で「結合テスト前に確定要」とした論点。v2.0 では案F2 を kernel_forth v0.10.18 実物で実証済（§7 Q1）。**案F2 で確定として承認可**。ただし §3.7.1 後処理2 の「WORD_OS_START 定義ラベル直前に `.global` 挿入」が、複数公開シンボル（§3.7.3 で6個に増えた）すべてに対し機械的に効くこと——挿入位置の特定ロジックが全シンボルで破綻しないこと——を実装時に確認のこと。

### N（助言）

#### N-3：T9 の overlap チェック観点を1ケース追加

T9（lnk23 固定配置）に、**意図的に重なる load_addr を与えて overlap エラーが正しく出る**異常系を1ケース追加すると、M-3-1 の混在挙動が検証できる。正常系（重ならない）だけでなく、ガードが効くことの確認を推奨。

#### N-4：I3 バイト比較の「空白部差異のみ許容」の判定基準を明文化

I3（道2 版と従来 .bin 版のバイト比較）で「空白部の差異のみ許容」とあるが、空白部（パディング $00）の範囲を具体アドレスで定義しておくと、比較スクリプトが自動判定でき、人手の見落としを防げる。

### E（軽微）

#### E-2：§3.1.1 の版数注記の誤り

§3.1.1 冒頭に「**【v2.1・C-1 確定（v1.1）→ v2.0 で全面撤回】**」とあるが、「v2.1」は「v1.1」の誤記と思われる（当該 C-1 は v1.1 で確定したもの）。KY41 の版数整合の観点で修正のこと。

#### E-3：§4 影響表 emu23 の版数

§4 で emu23「v1.06 維持（F-001 修正済・Step 8-F-1）」とあり、前回 E-1 で指摘した v1.05 から v1.06 へ更新されている。F-001 が別工程で修正完了したならこの記載で正しいが、本設計の前提でないことは明確にされており問題なし（確認のみ）。

## 5. 結論

**条件付き承認**。道2 への方針転換は技術的に妥当で、実ソース突合でも裏付けられた。残る確定事項は lnk23 改修に伴う M-3（ROM 境界・混在挙動）と C-3（load_addr=0 の意味論）の2点のみ。これらを §3.5.3 に追記確定すれば、§6 実装ステップへの着手を可とする。

特に **M-3-2（forth@$5100 が ROM 境界チェックを通る機序）** は、PoC が通った事実の裏にある仕組みを言語化しておかないと、後日の baremetal 設定変更やセクション型変更で静かに壊れる「見えにくいバグの芽」になる。ここだけは確実に機序を残してほしい。

実装フェーズでは前回の §4 留意事項（1 変更 1 検証、道2 の非 YOF Dhrystone 非回帰の必須確認＝§5.3）を引き続き遵守のこと。
