## M-1【必須・重み高】P2「冗長MOV削除」の置換条件が不十分

**箇所**: §9.2.5 パターン表 P2 行

**現状記述**: 「`MOV A,B` / `MOV B,A`（連続・冗長）→ 後者削除」「初版（最安全・SP非関与）」

**問題**:
`MOV A,B`（A←B）に続く `MOV B,A`（B←A）は、B が「いま A に入れた値（=元の B）」で上書きされるだけなので後者は実質no-opに見えるが、これを「冗長MOVの一般パターン」として実装すると取り違えが起きる。

1. **逆順 `MOV B,A; MOV A,B` では意味が異なる**（1命令目で B←A した後、2命令目で A←B=元のA に戻る。後者削除すると B に A の値が残り、結果が変わる）。
2. 「後者削除が安全」と言えるのは、**削除で生き残る側のレジスタ値が後続コードで前提とされていない**場合に限る。`MOV A,B; MOV B,A` の意図が「A と B を同値化」なら、後者削除で B が変化し得る。
3. 「最安全」を名乗るなら、対象を自明ケースに絞るべき。

**対応案**:
- P2 の「冗長」を厳密定義する。最小安全集合は次のいずれか:
  - (a) **完全同一命令の連続** `MOV X,Y` / `MOV X,Y`（後者削除＝確実に冗長）
  - (b) 1命令目 `MOV A,B` の直後に**A を読まずに A を上書きする命令**が来る場合の1命令目削除（dead store除去）
- 「`MOV A,B`→`MOV B,A` 後者削除」を残すなら、**前提条件「2命令目のdst（B）が、当該基本ブロック内で次に上書きされるまで読まれない（dead）」を必須ガードとして明記**する。
- 例示1パターンだけ書くのではなく、**置換成立の前提（どのレジスタがdeadであること）を全パターンに付す**。

## M-2【必須】3トラック（-O0-strict / -O0 / -O1）の不変・可変が未明記

**箇所**: §9.2.1 背景、§9.2.3 絶対ゲートの扱い、§9.2.2 opt_level表

> **前提（方針は妥当）**: §9.2.3 の「byte-exact は -O0-strict で従来通り維持し、-O1 を新トラックで別記録する」という新旧ゲートのトラック分離は、(i) peephole が -O1 のみ作動し -O0-strict バイナリは不変である実体に即しており、(ii) 最適化OFFの既知正解を退行検出の錨として保全する点で**設計判断として正しい**。本指摘は §9.2.3 を否定するものではなく、2極（strict / -O1）の間にある **-O0（非strict）** の扱いが未明記である点を補完するものである。

**問題**:
§9.2.1 に「現状 -O0/-O1 の Dhrystone が byte-exact 一致」とある。これは現状 -O1 の代数簡約（§7.1 の x*0, x+0 等）が Dhrystone では発火していない事実を示す。peephole 投入後は §9.2.7 検証1「-O1 で冗長MOVが消える」とある以上、**-O1 と -O0 の asm が byte 単位で乖離する**。これは想定どおりだが、§9.2.3 は「-O1 は新トラック」と言うのみで、**-O0（strict無し）が peephole の影響を受けるのか否か**が文面から一意に読めない。opt_level表では peephole=-O1 のみなので -O0 は不変のはずだが、明記が無い。

**対応案**:
- §9.2.3 に3トラックの不変/可変を明記:
  - `-O0-strict`: 全最適化OFF。**byte-exact 826/48405/P:20 を不変維持**（peephole無影響）。
  - `-O0`（非strict）: 定数畳み込みのみ。**peephole非適用＝asm従来と不変**。← この行を追加
  - `-O1`: 代数簡約＋peephole。**新トラックで cycles 新基準を別記録**。
- §9.2.7 検証計画に「**-O0（非strict）の asm も従来と byte 不変であること**」を1項追加。

## M-3【必須・重み高】peephole対象イディオムが「実コードの実体」と一致するか未検証

**箇所**: §9.2.5 パターン表全般（特に P1 のスタック往復）

**問題**:
プロジェクト規律 KY34「実ソースが真実（コメント・要約・記憶でなく実ソースを確認）」に照らすと、§9.2.5 のパターンは現行 scc23 v2.00 が**実際に吐いている命令列**に基づくべきだが、その実測根拠が本節に無い。特に P1 は `SUBI SP,#2` / `STW A,[SP]` … `LDW B,[SP]` / `ADDI SP,#2` というスタック往復を前提にしているが、§6.1 の spill は `PUSH B` / `PUSH X`・`POP X` / `POP B` を使っている。**式評価のスタック退避が `PUSH/POP` 形なら、P1 の前提（`SUBI SP,#2; STW`）は実体と食い違う**。パターンが実 emit と一致していなければ、実装しても1つもマッチしない「絵に描いた餅」になる。

**対応案**:
- §9.2 に**前提作業を1項追加**:「**P2 着手前に、現行 scc23 v2.00 が代表プログラム（Dhrystone等）で吐く asm を実測し、冗長パターンの実頻度を計測。パターン表(§9.2.5)はその実測に基づいて確定する**」。
- P1 の命令イディオム（`PUSH/POP` 形か `SUBI SP/STW` 形か）を実 emit で確認し、表記を実体に合わせる。
- これは KY34・「動作中リファレンスと直接比較」の徹底でもある。

## M-4【必須】P1 のSP判定条件に「フレーム相対アクセス」が抜けている

**箇所**: §9.2.6 リスクと防止策

> **前提（方針は妥当）**: §9.2.6 が P1（スタック往復除去）を最高リスクと位置づけ、「基盤が固まるまで着手しない」「_fmul の X 破壊バグと同種の危険」「判定は保守的に・不明なら非置換」とした**危険源の見立てと優先度付けは的確**である。本指摘は §9.2.6 を否定するものではなく、その「保守的判定」を実装者が取りこぼさないよう、**何を検出すれば保守的になるのかの具体条件**を明文化する補完である。

**現状記述**: 「前後のSP操作判定を誤るとスタック破壊」「介在命令の有無を厳密確認」

**問題**:
P1（スタック往復→`MOV B,A`）を安全に行うには、往復区間の間に SP の値に依存する命令が無いことが条件。本ISAは SP相対 `[SP+imm16]`（LDW/STW）でフレーム変数にアクセスする。§9.2.6 は「介在命令の有無」までしか書いておらず、**`[SP+imm]` フレーム相対アクセスや SP を読む/書く命令を保守的に検出対象に含める**点が明文化されていない。X(フレームポインタ)破壊バグ（§2.5.8 _fmul の件）と同種の事故になり得る。

**対応案**:
- §9.2.6 に明記:「P1 の置換可否判定では、往復区間内に **(i) SP を読む/書く命令、(ii) SP相対アクセス `[SP+imm]` を含む LDW/STW、(iii) サブルーチン呼び出し（JSR/RET）** のいずれかが介在する場合は置換しない。判定が少しでも不明なら保守的に非置換」。

## E-1【軽微・文書整合】§7.5・§9.1 と §9.2 の O2/O1 記述が矛盾したまま

**箇所**: §7.5、§9.1、§9.2.2

**問題**:
§9.2.2 で peephole を O1 へ繰り上げる方針だが、§7.5（ゼロ比較正規化＝O2送り）・§9.1（peephole項＝O2フェーズ）は依然 O2 を指している。§9.2.8 で「v2.01確定時に改版予定」と予告済みだが、**現時点の読者が §7.5/§9.1 と §9.2 の食い違いに先に出会う**。

**対応案**:
- append-only（KY41）を保ちつつ、§7.5・§9.1 の該当行に相互参照注記を**今**追加: 「→ §9.2 で O1 繰り上げを検討中（v2.01で確定予定）」。削除や取消線でなく追記で対応。

## E-2【軽微】版数台帳・絶対ゲートの新基準管理が改版予定に未記載

**箇所**: §9.2.3、§9.2.8

**問題**:
§9.2.1 で scc23 v2.01 へ版数が上がり、§9.2.3 で -O1 の cycles 新基準を別記録する。これは管理対象ゲート値（現 826/48405/P:20）に「-O1 新基準」が増えることを意味するが、§9.2.8 の改版予定に **tool_version_ledger（版数台帳）への新基準・新版数の反映**が項目化されていない。

**対応案**:
- §9.2.8 に1項追加:「tool_version_ledger を scc23 v2.01・-O1新基準値で更新（KY41 4点整合：ファイル名/版数/ステータス/改版履歴）」。

## E-3【軽微】P番号と導入順の不一致で誤読リスク

**箇所**: §9.2.5 パターン表

**問題**:
導入順は P2→P3→P1→P4 だが、番号は P1 が先頭に見えるため「P1から着手」と誤読しやすい。

**対応案**:
- 表に「**導入順：①P2 ②P3 ③P1 ④P4（任意）**」を明示するか、番号を導入順に振り直す。最安全パターンが最初という意図を番号からも読めるようにする。
