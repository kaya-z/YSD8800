## 1. 総評

本工程は、これまでの全レビューと質的に異なる。**黄金リファレンス emu23 に SPIプロトコルが存在しない**ため、「emu23実照合で正否を判定」という従来の拠り所が原理的に使えない。メモがこの非対称（§1）を正面から捉え、判定軸を「OSが観測する外部契約」に置いた点は正しい。

MMIO互換I/F（$FCA0-$FCB0）でOS無改修を狙い、内部実装（EXEC=SPI状態機械）だけを別物にする設計方針は妥当で、承認する。sim_impl_policy G1-G4の適用も適切。

ただし——**§2.3の整合問題について、メモの第一候補（案A）は物理的に実現不能である。**本レビューで定量分析した結果、約1000倍のタイミング乖離があることが判明した。代わりに、V3で確立した mem_ready 滞留機構を使う**案(D)を推奨する**。以下、最重要論点として詳述する。

---

## 2. ★最重要：§2.3 整合問題 — 案(A)は実現不能、案(D)を推奨★

### 2.1 リスクの実在を実照合で確定

メモ§2.3の危機認識は正しい。両側を実照合した：

**emu23側（fread即完了）** — `emu23_v109.c` L713-733：
```c
if (cmd_val == 2) {  // EXEC
    sd_busy_latch = 1;
    sd_stat = 0x00;               // BUSY中
    size_t got = fread(sd_buf, 1, 512, disk_fp);
    sd_stat = (got == 512) ? 0x04 : 0x02;   // ★その場で即READY★
}
```

**OS側（2回読み固定・リトライ無し）** — `sd_sample.c` L97-107：
```c
int sd_wait_ready(void) {
    stat = *p;   // 1回目: BUSYラッチクリア
    stat = *p;   // 2回目: 実STAT値
    if (stat & STAT_ERROR) return 1;
    if (stat & STAT_READY) return 0;
    return 1;    // ★READYもERRORも無い=異常(即return)★
}
```

呼び出し側（L141/L166）にもリトライループは無い。**2回読んでREADYが無ければ即異常**。emu23ではfreadが即完了しているので2回目で必ずREADY——だから成立していた。

### 2.2 ★案(A)は物理的に実現不能（定量分析）★

メモは案(A)「SPIを十分速くしEXEC〜初回STAT読でSPI完了保証」を第一候補とするが、これは成立しない。

| 項目 | 所要 |
|---|---|
| OSの2回読み間隔 | LDW 1命令分 ≈ 数十クロック（4MHzで**十数µs**） |
| 実SPI 512バイト読出 | 最低 512×8 = 4096 SCK。SCK=4MHz/N（N≧2）ゆえ**最速でも約2000µs** |
| 乖離 | **約1000倍** |

★根本原因：SCKはCPUクロック(4MHz)を分周生成するため、原理的にCPUクロックを超えられない。512バイト転送は必ずCPUの数十クロックより3桁長い。SCK分周をどう上げても、この壁は越えられない。★ よって案(A)は却下。メモの「ワースト転送時間の見積り必須」を実行した結果が、この却下判断である。

案(B)ポーリングループ化・案(C)IRQ待ちは、いずれもOS改修を伴うためメモ自身が却下しており、これは正しい。

### 2.3 ★推奨：案(D) — STAT読みの wait-state 化★

案(A)(B)(C)のいずれでもない第4の道を推奨する。**「SPI転送が完了するまで、STAT読み（$FCA2アクセス）に対して mem_ready を返さない」**——すなわちバス上で CPU を待たせる。

**なぜ成立するか**：
- CPUコアは mem_ready 滞留による**可変レイテンシ耐性を持つ**（V3で実照合済：`if(mem_ready)` で待つ、25箇所）。STAT読みが数千クロック待たされても、CPUは正しく待って続行する。
- OSの2回読みのうち**2回目のSTAT読みが、SPI完了まで自然にブロックされる**。転送完了と同時に mem_ready を立てて READY(0x04) を返せば、OSから見れば「2回目でREADYが返った」ことになり、`sd_wait_ready` は**無改修で成立する**。
- emu23 の「BUSYは実質ゼロ時間（freadが即完了）」を、RTLでは「BUSY中はSTAT読みを待たせる」に写像する。**外部契約（2回目でREADYが返る）は完全に保たれる。**

**emu23等価性の考え方（重要）**：
この工程では「emu23とcycle一致」は求められない（そもそもSPIが無い）。求められるのは**「OSが観測するレジスタ遷移の契約」の一致**である。案(D)は、OSから見た観測（STAT読み→READY）を保存する。cycle数はemu23と全く違うが、それは元々検証対象外（FPGA回帰ゲートは完走＋論理結果一致・cycle除外）。案(D)はこのプロジェクトの検証哲学と整合する。

**実装上の注意**：
- wait-state化はSTAT読み（$FCA2）に限定する。他レジスタ（LBA/BUF_PTR/DATA）は通常応答。
- SPIが本当に完了する（またはタイムアウトでERROR確定する）ことを保証し、**mem_readyを永久に返さない事態（ハングアップ）を絶対に避ける**。SPIタイムアウトカウンタを設け、規定SCK数を超えたらERROR(bit1)を立ててmem_readyを返す。これがKY。
- この方式はV3のCDC/PSRAMで確立した「変レイテンシデバイスをmem_readyで待たせる」思想の再利用であり、YSD8003に固有の新機軸ではない。設計資産の一貫適用。

**MC6809的対比**：これはMC6809のMRDYによるクロックストレッチで低速デバイスを待たせる古典構成そのもの。SDカードのような低速ストレージをCPUに繋ぐとき、CPUを待たせるのは正道である。案(A)がやろうとした「デバイスをCPU速度に合わせる」より、「CPUをデバイス速度に待たせる」方が、ハードウェアとして自然かつ確実。

## 3. 諮問事項への回答

| # | 諮問 | 回答 |
|---|---|---|
| **1** | §2.3整合＝案(A)でよいか。OS微修正を許容するか | ★案(A)却下・案(D)推奨★。案(D)ならOS無改修を守れるため、OS微修正は不要。まず案(D)の成立可否（wait-state化がバス/mmio_stubで無理なく組めるか）を実装前に検討されたい。案(D)が技術的に困難と判明した場合のみ、OS側sd_wait_readyのループ化（案B）をかやぬまさんに相談する二段構え。 |
| **2** | セクタバッファ512BをBSRAMで取るか分散RAMか | 512B=4KbitはBSRAM(468Kbit)の1%未満。将来キャッシュ用温存の観点でも影響軽微だが、**分散RAM(LUTRAM)を推奨**。理由：512BはBSRAM 1ブロックを占有するには小さすぎ、BSRAMは将来のキャッシュ/フレームバッファ用にブロック単位で温存する方が筋。ただしGW1NR-9のLUTRAM容量とのトレードオフはG2合成見積りで確認。 |
| **3** | SCK分周＝2段切替か可変レジスタか | **2段固定切替を推奨**（初期化100-400kHz / 読出高速）。可変レジスタは自由度が高いが、OSドライバがそれを設定する経路が要り「OS無改修」と衝突する。固定2段ならRTL内部で完結しOS非依存。SDカード規格の初期化低速要件も満たす。 |
| **4** | CDC不要（SPI=4MHzドメイン完結）でよいか | 承認。SCKを4MHz分周で生成しSPI全体を単一ドメインに収める判断は正しい。PSRAMのような別クロック源が無いためCDC不要。ただし案(D)のwait-state（mem_ready制御）はCDCではなくバスハンドシェイクの範疇であり、これは別途必要。 |
| **5** | V6-A範囲＝読出(CMD17)のみ、書込(CMD24)はV6-Bか | 承認。roadmap通り。読出で SPI-FSM/wait-state整合/OSブートの骨格を確立し、書込は同じ骨格の拡張としてV6-Bで積むのが順当。スコープ分割は妥当。 |

## 4. 検証戦略（§4）への所見

- **emu23協調等価が使えない**という認識は正しく、その代替として `sd_spi_model_v0_1_poc.sv`（SDカードSPIビヘイビアモデル）を正解リファレンスに据える判断は的確。これがこの工程唯一の「黄金」になる。
- ★モデルの正しさ自体が検証の土台になる点に注意★：sd_spi_modelがSD規格（R1/R7/トークン0xFE/CRC）を正しく模擬していないと、RTLが誤っていてもTBが通る偽合格が起きる。モデルはSD Physical Layer仕様（CMD17のレスポンスシーケンス）に忠実に作り、可能なら**実SDカードのバスキャプチャ or 既知の正しいSPI SDモデルと1点照合**しておくと盤石。モデルの権威付けが要る。
- T5（negative先行・KY54）でCRCエラー/トークン不達時にERROR(bit1)が立つ検証は適切。**案(D)を採る場合、T5に「SPIタイムアウト→ERROR確定→mem_ready返却（ハングしない）」を必ず含めること**（§2.3の永久待ち回避の検証）。
- 統合検証（§4.4 OS無改修でcat/ls）が最終関門という位置づけは正しい。案(D)ならここが通る見込み。

## 5. sim_impl_policy G1-G4 への所見

G1/G4=✅は妥当。G2（リソース）/G3（タイミング）=要確認も正しい。ただしG3の焦点を修正されたい：

- メモはG3の焦点を「§2.3のワースト転送時間 vs OS2回読み」とするが、**案(D)採用によりこの焦点は消滅する**（CPUを待たせるので転送時間の絶対値は問題にならない）。案(D)でのG3の新しい焦点は「**SPI-FSMとwait-state制御が4MHzでタイミング収束するか**」と「**SPIタイムアウト値が現実的なSDカード応答時間をカバーするか**」に移る。
- 「RTLで実現不能な抽象（fread相当）をRTLに持ち込まない＝実SPIで実装する」という本設計の核は、sim_impl_policyの精神そのもの。emu23がfreadで隠蔽したものを、RTLは正直にSPIで起こす——この方向は完全に正しい。

## 6. 総合判定

**設計方針は承認。§2.3のみ案(A)を却下し案(D)を推奨。**

- 非対称の把握（§1）・MMIO互換I/F（§2）・SPI-FSM構成（§3）・検証戦略（§4）・G1-G4（§5）は妥当。
- ★§2.3：案(A)は物理的に実現不能（OS2回読み間隔とSPI転送に約1000倍の乖離）。案(D)＝STAT読みのwait-state化を推奨。CPUのmem_ready滞留（可変レイテンシ耐性・V3実照合済）を使い、SPI完了までSTAT読みを待たせることで、OS無改修のまま外部契約を保つ。MC6809のMRDYクロックストレッチと同じ正道。★
- 諮問2（分散RAM）/3（2段固定分周）/4（CDC不要・承認）/5（読出のみ・承認）。
- 検証：sd_spi_modelの正しさの権威付けを。T5にSPIタイムアウト→ERROR→ハングしない検証を追加。

### 実装着手の条件
本メモを **v0.2 に改版**し、§2.3を案(D)ベースに書き換えたうえで実装着手されたい（原則43）。案(D)の骨子——「STAT読みwait-state化＋SPIタイムアウトでERROR確定」——を§2.3に明記すること。それ以外はこのまま進めてよい。

> **kaizen候補（原則78）**：「黄金リファレンスが特定機構（SPI等）を隠蔽している工程では、emu23一致は検証軸にならない。判定軸を『OSが観測する外部契約（レジスタ遷移）』に移し、cycle等価は放棄する。隠蔽層をRTLで起こす際、OS側の固定的前提（例：2回読み）が実機タイミングと衝突しうるため、OSドライバのアクセスパターンを実源で確認し、必要ならwait-stateで吸収する。」——本件はこの教訓の典型例。
