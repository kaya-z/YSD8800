## 1. P1 とは（実装対象の確定仕様）

**P1 = スタックラウンドトリップ除去。** 4命令固定窓を1命令へ置換:

```
SUBI SP, #2      →
STW  A, [SP]        MOV B, A
LDW  B, [SP]
ADDI SP, #2
```

- 実測（dhry_timer.c -O1）: push_a/pop_b 対応ペア 197件中、4命令窓一致は **24件**。
- 生成起源: **境界偶然マッチ**（emit経路プローブ実測で確定）。異なるSIRノードの pop_b 後半 `ADDI SP,#2` と別ノードの push_a 前半 `SUBI SP,#2` が命令ストリーム上で偶然隣接して窓を成す。当初の「配列添字ネスト由来・単一空ペア」説、レビュア仮説「右オペランドemitの0命令化」はいずれも実測で棄却（真の空往復ペアは0件）。
- 安全性: 生成起源に**依存しない**。4命令窓の局所正味効果が閉じている（SP収支ゼロ・`[SP]`はSP−2番地の自己完結領域・窓内に分岐/JSR/SP相対なし）→ `B=A`（＋デッドストア＋SP収支ゼロ）＝ `MOV B,A`（0x20・FLAGS不変）と外部観測等価。

---

## 2. 実装ガード G1〜G5（設計確定・実装必須）

全て真のときのみ置換:

- **G1**: 4命令が完全隣接（間にラベル・命令・コメント実体なし）。
- **G2**: 行1=`SUBI SP, #2`、行4=`ADDI SP, #2`（同量対応）。
- **G3**: 行2=`STW A, [SP]`、行3=`LDW B, [SP]`。
- **G4**: 行2・行3の `[SP]` はオフセット無し（`[SP+imm]` を含まない）。
- **G5【フラグ意味論保護・最重要】**: **窓直後の命令が Z/N を読む条件分岐（`BEQ`/`BNE`/`BLT`/`BGE`）なら非置換。**
  - 根拠: 元列末尾 `ADDI SP,#2` は Z/N を更新するが `MOV B,A` は FLAGS 不変。直後がその Z/N を読む分岐だと置換で挙動が変わる。
  - 除外4命令で必要十分（ISA2.3実仕様裏取り済み・`ISA2_3_v231.docx` L228–231/L254）:
    - Z/N を読むのは `BEQ`(0x61)/`BNE`(0x62)/`BLT`(0x63)/`BGE`(0x64) の4種のみ。
    - `JMP`(0x60)/`JSR`(0x68)/`RET`(0x69) は無条件でフラグを読まない。
    - フラグをレジスタへ移す命令（MC6809 `TFR CC,r` 相当）は ISA2.3 に**不在**。
    - 割り込みは FLAGS を push 退避し `IRET` で pop 復元＝Z/N可視性に透過的。

## 3. 実装方式（設計確定）

- 既設の**方式B**（関数生成区間のみ `g_insbuf[]` にバッファ化 → `peephole_pass()` → `insbuf_flush()`）に**1パターン追加**。
- 走査は既存 P2a/P2b/P3 と**同一の w/r 前詰め方式**:
  ```
  一致 → free 4命令, g_insbuf[w++]=strdup("    MOV  B, A"), r+=4
  不一致 → g_insbuf[w++]=g_insbuf[r], r+=1
  ```
  （strdup失敗時は元4命令温存の安全分岐を用意）
- **-O1 のみ**作動（-O0/-O0-strict は非適用＝byte不変）。
- 既存 P2a/P2b/P3 の**後段**に配置。
- **KY38厳守**: 実装は `scc23_v2_03_poc.c`（本番 `scc23_v2_02.c` は直接改変**禁止**）。poc には C-1検証用 `--no-peep` が既に搭載済み。

## 5. Dhrystone ビルド手順（実証済み・再現用）

**注意: 2系統ある。P1検証は -O1 系統。**

### 5.1 絶対ゲート -O0（Makefile）
```
make regress SCC=./scc23      # 826/48405/P:20・21846B
```

### 5.2 -O1 検証（peephole用・手順の核心）
HANDOVER_PEEPHOLE_P1_v1_0.md §2.2 記載の手順。ただし**本チャットのV4検証では obj方式（--runtime-org 0x3000）で実施し成功**している。両方式が存在するので注意:

**方式X（obj方式・本チャットV4で使用・成功）**:
```
scc23 --code-org 0x0400 --data-org 0x4000 --runtime-org 0x3000 -O1 -o dhry.asm dhry_timer.c
hasm23 -c dhry.asm                              # → dhry.asm.obj
hasm23 -c startup_harness23_v15.asm             # → startup_harness23_v15.asm.obj
lnk23 --machine force dhry.asm.obj startup_harness23_v15.asm.obj -o dhry.bin
emu23 dhry.bin -q                               # ★引数順: bin先・-q後（手順書v1.4§4.7既出）
```

**方式Y（bin方式・HANDOVER_P1_v1_0.md §2.2記載・runtime-org 0x0100）**: sed で `JSR _main` 実アドレス置換が必要。§2.2 参照。

> **重要な既知事実（本チャットで解明）**: base/p1 の obj は共に「20822 bytes code」でサイズ同一に見えるが、これは `code_buf_pos`（.org確保長＝最大到達オフセット）であり置換未反映ではない。実コード量は非ゼロバイトで 10149→9957（−192B）と減少。**実行比較の前に必ず base/p1 の obj/bin を `cmp` で差分確認**し「同一binを2回実行して偽の一致」を排除すること（KY事項）。

### 5.3 使用ツール（確定バージョン・使用前に要バージョン確認）
- scc23 v2.02 / hasm23 v1.04 / lnk23 v2.01 / emu23 v1.09 / Force v1.5
- 台帳: `tool_version_ledger_v1_9.md`（最新）。P1完成後 v1.10 へ更新予定。
