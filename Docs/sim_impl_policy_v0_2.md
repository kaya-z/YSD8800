## 0. 本文書の位置づけと適用範囲

### 0.1 なぜ本文書が必要か

Step 8（FPGA実装）において、シミュレータ emu23 に実装済みの機能が
**FPGA では原理的に実装できない**ことが複数判明し、実装工程が遅延した。

原因は単純である。emu23 は「ソフトウェアとして自然な実装」を選んできたが、
それは必ずしも「ハードウェアに写像可能な実装」ではなかった。
ソフトウェアには、ハードウェアに存在しない自由（無限の値・任意の情報参照・
アトミックな複合動作）があり、その自由を無自覚に使うと**ハードでは再現不能な仕様**が生まれる。

本文書は、この失敗を ISA3.0 以降に持ち込まないための規範である。

### 0.2 最上位原則

> ## ★原則0：ハードウェアで実現できないことは、シミュレータでも実装しない。★
>
> シミュレータは「ハードウェアのモデル」である。
> 「ハードウェアの上位互換」でも「ハードウェアより賢い実行系」でもない。
>
> 実装が容易だから、ソフトなら自然だから、という理由で
> ★ハードに写像できない機構を導入してはならない。★

この原則は、他のいかなる利便性・実装効率にも優先する。

### 0.3 適用範囲

| 対象 | 適用 |
|---|---|
| ISA3.0 以降のシミュレータ（emu30 等） | ★適用（全面）★ |
| ISA3.0 以降のデバイスモデル・周辺仕様 | ★適用（全面）★ |
| ISA3.0 以降の ISA 仕様策定そのもの | ★適用（命令の追加時に §2 ゲート必須）★ |
| 既存 emu23（ISA2.3系） | **適用しない（遡及適用なし）**。既存資産の安定を優先 |
| hasm / lnk / scc / Force 等、実行時モデルを持たないツール | 原則0の対象外（ただし §2 G2 は生成コードに適用しうる） |

### 0.4 既存の方針との関係

本規範は、既に承認済みの以下の方針を**否定しない**。

> 「外部観測等価は守る／内部構造は FPGA が簡素になるよう自由に組む／
> 　emu23 の内部実装を逐一模倣しない」（FPGA V1工程で承認）

上記は「**RTL 側がシミュレータの内部構造を真似る義務はない**」という
★ハード→ソフト方向★の自由を認めたものである。

本規範は、その**逆方向**を規律する。すなわち
「**シミュレータ側が、ハードに写像できない構造を作ってはならない**」という
★ソフト→ハード方向★の制約である。両者は矛盾せず、対をなす。

```
   ソフト（シミュレータ）              ハード（RTL）
        │                                 │
        │  ── 内部構造の模倣は不要 ──▶   │   （承認済方針）
        │                                 │
        │  ◀── 写像可能性は必須 ────      │   （★本規範★）
        │                                 │
   　　　外部観測等価（両者の接点・検証ゲート）
```

## 1. 失敗の類型（本規範の実証的根拠）

本規範は机上の理想論ではない。Step 8 で**実際に発生した**問題から帰納した。

### 1.1 類型I：CPU内部状態の外部参照（情報経路の不在）

**実例：emu23 v1.09 のタイマー再武装機構**

emu23 では、IRET 命令の実行時に `YSD8002_iret()` を直接呼び出し、
`timer_in_service` フラグを見てタイマーを再武装していた。

ソフトでは自然である。IRET を実行する場所も、タイマーの状態変数も、
同じプロセスのメモリ空間にあり、いつでも触れるからだ。

しかし RTL では不可能であった。`v5_design_memo_v0_3.md` L64 が記す通り：

> CPU から `iret_pulse_o`（命令実行の内部事情を晒す信号）を引く必要があるが、これは不可

**何が問題だったのか**：
CPU が「いま IRET を実行した」という情報は、CPU の**内部事情**である。
実回路において、周辺デバイスは CPU のアドレスバス・データバス・制御線しか見ていない。
命令の種類など知りようがない。**その情報を運ぶ配線が存在しない。**

**正しい姿**：
再武装は、割り込みハンドラが**明示的にレジスタへ書き込む**ことで行う（TCR-ACK 方式）。
デバイスは「バスに ACK 書き込みが来た」という、**実際に配線されている情報**だけで動作する。

### 1.2 類型II：無限・非有限値の使用（有限性の破れ）

**実例：`next_irq_cycle = UINT64_MAX`**

`v5_design_memo_v0_3.md` L37 が記す通り、タイマー発火時に
`next_irq_cycle = UINT64_MAX` を代入して「自己武装解除」を表現していた。

ソフトでは自然である。「事実上、永遠に来ない時刻」を表す慣用句だからだ。

しかし RTL に `UINT64_MAX` は存在しない。レジスタは有限ビット幅であり、
「無限」を表すビットパターンは無い。
`0xFFFFFFFFFFFFFFFF` を実際に格納しようとすれば **64bit のカウンタが必要**になり、
本来 16bit で足りる回路が肥大する。しかもその値は「大きい数」であって「無限」ではないため、
カウンタが一周すれば**誤発火する**。

**正しい姿**：
「武装解除」は**イネーブルビット1本**で表現する。値ではなく状態で表す。

### 1.3 類型III：タイミングの抽象化（サイクルの虚構）

**実例：emu23 の `cycle` は CPI=1 固定**

emu23 は 1 命令 = 1 cycle として数える。
実 CPU では命令ごとにサイクル数が異なり（メモリアクセス・分岐・多バイト命令）、
FPGA との cycle 一致は**定義上不可能**である。

これは「バグ」ではなく「**モデルの粒度の宣言**」であり、それ自体は許容される。
ただし★宣言せずに使う★と、後段で「なぜサイクルが合わないのか」という
存在しない不具合を追うことになる。

**正しい姿**：
サイクルモデルの粒度を**仕様書に明記**し、
検証ゲートを「サイクル一致」ではなく「**完走＋論理結果一致**」に置く（既確立）。

### 1.4 類型IV：複合動作のアトミック実行（同時性の錯覚）

**実例：`exec_one` の巨大 switch**

1 命令の処理を 1 ステップで完結させる構造。メモリ読み → ALU → メモリ書きを
「一息に」行う。ソフトでは当然である。

RTL では、これらは**必然的に複数サイクルの FSM** になる。
ここで危険なのは、ソフトが「同時に成立している」と暗黙に仮定した中間状態が、
ハードでは**観測可能な中間状態として露出する**ことである。
（例：メモリ書き込みの途中で割り込みが入ったらどうなるか？）

**正しい姿**：
多サイクル化それ自体は正常である（§2.3 参照）。
問題は「**中間状態で割り込み・例外が入った場合の定義**」を
シミュレータ側が持っていないことである。**定義を仕様として持て。**

## 2. 実装可否の判定ゲート（G1〜G4）

ISA3.0 系のシミュレータ・デバイスモデルに新機能を実装する前に、
以下の 4 ゲートを**全て通過**すること。1つでも NG なら、実装ではなく**設計に戻る**。

### G1：情報経路ゲート（Information Path）

> **問い：その情報は、実回路上で、その場所に「配線として」届くか？**

- 参照しようとしている情報の**物理的な運搬経路**を答えられること
- 「同じ構造体のメンバだから見える」は理由にならない。ソフトの都合である
- 特に **CPU 内部状態（実行中の命令種別・パイプライン段・内部フラグ）を
  　周辺デバイスが参照する設計は原則 NG**

| 判定 | 例 |
|---|---|
| ❌ NG | デバイスが「CPU が IRET を実行した」ことを知る |
| ❌ NG | デバイスが「CPU の PC の値」を直接読む |
| ✅ OK | デバイスが「自分のアドレスに書き込みが来た」ことを知る |
| ✅ OK | デバイスが割り込み線を上げ、CPU がそれを見る |
| ✅ OK | CPU が「バスエラー線」を見る（実配線が定義されているなら） |

★NG になった場合の作法★：
「その情報を運ぶ配線を新設する」という解決に飛びつく前に、
**そもそもその情報を参照せずに済む設計はないか**を必ず先に検討すること。
V5 では、IRET 通知線の新設ではなく、TCR-ACK 方式（既存のバス書き込みだけで完結）が正解であった。

### G2：有限性ゲート（Finiteness）

> **問い：その値・その構造は、有限のビット幅／有限の記憶素子に写像できるか？**

- すべての状態変数について、★ビット幅を答えられること★
- 「無限」「未定」「存在しない」を表す特別値（`UINT64_MAX`, `NULL`, `-1` 等）は、
  それが**何ビットの何という信号になるか**を答えられなければ NG
- 可変長データ構造（動的確保のリスト・可変長配列・再帰的構造）は原則 NG

| 判定 | 例 |
|---|---|
| ❌ NG | `next_irq_cycle = UINT64_MAX`（無限を値で表現） |
| ❌ NG | デバイスが可変長のイベントキューを持つ |
| ❌ NG | ~~ポインタが `NULL` かどうかで動作を分岐する~~ ★【v0.2訂正・下記に置換】★ |
| ❌ NG | ★動的確保・可変長のポインタ連鎖に依存する設計（リスト辿り等）／有効ビット1本で表せる状態をポインタの有無で表現する設計★ |
| ✅ OK | イネーブルビット1本で「武装/解除」を表す |
| ✅ OK | ★特定ビットパターンとの等値比較による分岐（有効ビット付きタグ・センチネル値比較）★（v0.2追記） |
| ✅ OK | 深さを固定した FIFO（★深さを仕様に明記すること★） |
| ✅ OK | 16bit カウンタのラップアラウンド（★境界動作を仕様に明記すること★） |

★【v0.2 補足・指摘2】値の等値比較分岐そのものは G2 適合である。★
`$0000` や全1（`$FFFF`）といったセンチネル値との比較は、実ハードに日常的に存在する
（有効ビット付きタグ、空きスロット判定等）。G2 が禁じるのは「値の比較」ではなく、
「**動的確保・可変長の構造そのものへの依存**」である。両者を混同しないこと。

★「無限」は状態で表せ、値で表すな。★

### G3：資源写像ゲート（Resource Mapping）

> **問い：その動作は、有限のクロック・有限の演算器・有限のバス帯域に写像できるか？**

⚠️ **本ゲートは「1クロックで完結すること」を要求するものではない。**
多サイクル動作・FSM・パイプライン・順次バスアクセスは、すべて**正常な実装**である。
本ゲートが禁じるのは「**有限資源に落とせない同時性**」だけである。

| 判定 | 例 |
|---|---|
| ✅ OK | 乗除算が 16 サイクルかかる（多サイクルは正常） |
| ✅ OK | メモリアクセスが FSM で 3 サイクルに分割される |
| ✅ OK | 命令フェッチが複数サイクルに分かれる |
| ❌ NG | 1 命令の中で、独立した 3 箇所のメモリを★同一サイクルに★読む前提の設計 |
| ✅ OK | 自己更新レジスタ（`ACC ← ACC + B`）★FFを介するので正常★（v0.2訂正） |
| ❌ NG | ~~演算結果が、その演算の入力に同一サイクル内で依存する（組合せループ）~~ ★【v0.2訂正・下記に置換】★ |
| ❌ NG | ★FF（レジスタ）を介さず、演算結果が同一演算の入力へ戻る**非同期**の自己参照ループ（例：`a = a & b` を組合せ論理だけで閉じる）★ |
| ❌ NG | 中間状態が存在しないことを前提にした設計（＝割り込み・例外の定義が無い） |

★多サイクル化を認めるなら、その中間状態における
　割り込み・例外・リセットの挙動を★仕様として定義すること★。★
これを怠ると、類型IV（同時性の錯覚）に陥る。

★【v0.2 補足・指摘1】「結果が入力に依存する」こと自体は禁止対象ではない。★
アキュムレータ（`ACC ← ACC + B`）のように、演算結果が次サイクルの入力になる構造は、
間に FF が挟まる限り**完全に合法な順序回路**であり、あらゆる CPU の基本要素である。
G3 が禁じるのは「**FF を介さず**、組合せ論理だけで出力が入力へ戻る**非同期閉ループ**」のみ。
これは論理シミュレータでは値が振動または不定となり、合成では警告・実機では準安定を招く。
判定の要点は「サイクル内か否か」ではなく「**FF による分離があるか否か**」である。

### G4：実装可能性の存在証明（Existence Proof）

> **問い：この機構が有限のハードウェアで実現できることを、何によって示せるか？**

G1〜G3 が「禁止事項」であるのに対し、G4 は「**説明責任**」である。

証明の手段は、以下のいずれでもよい（★順不同・優劣なし★）：

1. **RTL の概念コードを書ける**（最も強い証明）
2. **必要な信号線・レジスタ・記憶素子を列挙できる**
3. **同等の機構を持つ実在デバイスを挙げられる**（参考例）

#### ⚠️ 実在デバイス参照に関する重大な注意

3. の「実在デバイス」は **参考例（inspiration）であって、適合基準（conformance）ではない。**

- MC6809 / MC6840 PTM / MC6850 ACIA 等は、本プロジェクトが敬意を払う設計であり、
  ★優れた着想の宝庫★である。実際、V5 の TCR-ACK 方式は MC6840 の
  「ハンドラがレジスタを叩いて ACK する」という作法から着想を得て正解に到達した。
- **しかし「MC6840 に無いから NG」は、判断として誤りである。**
  実在デバイスは、その時代の製造技術・コスト・用途の制約下で作られている。
  それらの制約を無批判に輸入すれば、★より優れた設計が埋もれる。★
- ★実在デバイスは「できることの下限」を示すのであって、「できることの上限」を示さない。★

**正しい使い方**：
- 「実在デバイスに前例がある」→ **実装可能性の強い傍証**（採用してよい）
- 「実在デバイスに前例がない」→ **それだけでは何も意味しない**。
  　1. または 2. によって独自に実装可能性を示せばよい

**独自機構を採用する場合の追加義務**：
前例のない機構を採用する場合は、G4 の 1.（RTL 概念コード）または
2.（信号・素子の列挙）を★必ず設計書に記載する★こと。
「前例がない」ことを理由に萎縮する必要はないが、
「前例がない」ぶん、実装可能性の説明責任は重くなる。

## 3. デバイスモデル記述規約

ISA3.0 系のデバイス（タイマー・UART・ストレージ・MMU 等）は、以下に従うこと。

### 3.1 インタフェースの制限

デバイスが CPU と接続してよい経路は、**以下のみ**：

| 経路 | 方向 | 内容 |
|---|---|---|
| MMIO レジスタ | CPU → Dev | アドレス・データ・書き込みストローブ |
| MMIO レジスタ | Dev → CPU | アドレス・読み出しデータ |
| 割り込み線 | Dev → CPU | レベル信号（1本／デバイス） |
| リセット線 | System → Dev | 非同期または同期リセット |
| クロック | System → Dev | クロック |

★上記以外の経路を必要とする設計は、G1 違反として棄却する。★

### 3.2 禁止事項（★厳守★）

- ❌ デバイスモデルから CPU の内部状態（`pc`, `flags`, 実行中命令, レジスタ）を参照すること
- ❌ CPU の命令実行フック（IRET フック等）からデバイス関数を呼ぶこと
- ❌ デバイス間で、バスを介さずに直接状態をやり取りすること

### 3.3 割り込み ACK の標準形

割り込みの再武装・確認応答（ACK）は、
★必ず「ハンドラによるレジスタ書き込み」で行うこと。★

IRET 実行を契機とする自動 ACK は、G1 違反であり**禁止**する。
（V5 で採用した TCR-ACK 方式を標準形とする。詳細は §付録A）

### 3.4 割り込み線の性質

- 割り込み線は★レベル信号★を標準とする（パルスではない）
- レベル信号であれば、RTL 側で「CPU が取りこぼす」問題が原理的に起きない
- パルス方式を採用する場合、★パルス幅と取りこぼし防止機構を仕様に明記★すること

### 3.5 中間状態における割り込み受理の標準パターン（★v0.2 新設・指摘3★）

G3・§1.4 が要求する「多サイクル命令の中間状態での割り込み挙動の定義」について、
毎回ゼロから悩まぬよう、本プロジェクトの標準パターンを定める。
本プロジェクトが範とする **MC6809** の作法に倣う。

> **標準パターン（6809流）：**
> ★割り込みは「命令境界」でのみ受理することを既定とする。★
> 1命令の実行はアトミックとみなし、命令の途中（多サイクルの中間状態）では
> 割り込みを受理しない。命令が完了してから、次命令の実行前に受理判定を行う。

この既定により、多サイクル命令（例：byte-enable 方式で2サイクルに分割される
`LDW`/`STW` の奇数アドレス跨ぎアクセス、`LDB`/`STB` 等）の中間状態は
「割り込みから隔離された不可分区間」として扱え、中間状態の割り込み挙動を
個別に定義する必要がなくなる。

**例外を設ける場合の義務**：
命令境界外での受理を許す機構（割り込み可能な長大命令、ブロック転送の中断・再開等）を
設計する場合は、★その命令と、中断・再開の仕様を各機能設計書に明示的に列挙する★こと。
（6809 においても、この種の「割り込み可能命令」は限定的にしか存在しない。
みだりに増やさないこと。）

## 4. タイミングモデル規約

### 4.1 サイクルモデルの粒度宣言（★必須★）

シミュレータは、自身のサイクルモデルの粒度を**仕様書冒頭に明記する**こと。

宣言すべき事項：
- 1 命令あたりのサイクル数をどう数えるか（CPI=1 固定か、命令別テーブル参照か）
- そのサイクル数が RTL と一致することを**保証するのか、しないのか**
- サイクル数を用いた検証を**行うのか、行わないのか**

★宣言なきサイクル値は、後段で「存在しない不具合」を生む。★
（emu23 の CPI=1 は、宣言されていなかったために FPGA 工程で混乱を招いた）

### 4.2 検証ゲートの定義

RTL との等価性検証において、比較すべきものを明確に定義する：

| 項目 | 比較する | 根拠 |
|---|---|---|
| 実行結果（レジスタ・メモリ最終状態） | ★する★ | 外部観測等価の本体 |
| 出力列（UART 出力等・MD5） | ★する★ | 外部観測等価の本体 |
| 割り込み発火の**順序** | ★する★ | 論理的な観測対象 |
| 割り込み発火の**サイクル数** | **しない** | サイクルモデルの粒度が異なる（§4.1） |
| 内部状態（中間レジスタ・FSM 状態） | **しない** | 内部構造は自由（承認済方針） |

### 4.3 サイクル表の先行確定（ISA3.0 での新規要求）

~~ISA3.0 では、シミュレータ実装より先に、命令別サイクル表を確定すること。~~
★【v0.2訂正・指摘4】上記を以下の2段構えに訂正する。★

正確なサイクル数は RTL の FSM 構造が確定しないと定まらないため、
「先行確定」を厳格に読むと工程がデッドロックする
（ISA2.3 でも `ysd8800_cycle_count_table_v1_0.md` は RTL 後追いで作られた）。
そこで2段構えとする：

1. **見積りサイクル表の先行確定**：設計時点で、命令ごとの**見積り**サイクル数を
   　サイクル表として先に確定する。シミュレータはこの見積り表に従って実装する。
2. **実測値による改版**：RTL の FSM 確定後、**実測サイクル数**で同表を改版する
   　（KY41：追記・取消線保持）。

★§4.3 でいう「先行確定」とは、上記(1)の見積り表を指す。★
これにより工程のデッドロックを避けつつ、シミュレータが早期にサイクル数を
持てるようにする。（`ysd8800_cycle_count_table_v1_0.md` は(2)実測改版の先例）

## 付録A：設計パターン集（V5 由来）

⚠️ 本付録は**規範本体（§2〜§5）ではなく、参考パターン**である。
V5 が未完了（S5以降残存）のため、本付録は V5 完了後に追記・改版する余地を残す。

### A.1 TCR-ACK パターン（割り込み再武装）

**問題**：ワンショットタイマーの再武装契機を、どこに置くか。

**アンチパターン**（emu23 v1.09）：
```
IRET 実行 → CPU が YSD8002_iret() を呼ぶ → タイマー再武装
```
→ G1 違反（CPU 内部事情の外部露出）

**採用パターン**（emu23 v1.10 / TCR-ACK）：
```
ハンドラが TCR に IRQ_ACK ビット(bit5)を書く → デバイスが再武装
　　TCR 書き込み値 $0023 = TIMER_EN | IRQ_EN | IRQ_ACK
```
→ G1 適合（バス書き込みのみで完結）
→ G4 適合（実装可能性：MMIO 書き込みデコード＋1bit ストローブ。実在デバイスにも同種の作法あり）

**副次的利点**：ACK が明示的になることで、
「割り込みを受けたが再武装しない」という★意図的な選択★が可能になった。
IRET フック方式では表現できなかった動作である。
（＝ハード制約に従った結果、表現力が増した例）

### A.2 「無限」の表現

**アンチパターン**：`next_irq_cycle = UINT64_MAX`
→ G2 違反

**採用パターン**：イネーブルビット
```
timer_enable = 0   ← 「発火しない」を状態で表す
```
→ G2 適合（1bit）
