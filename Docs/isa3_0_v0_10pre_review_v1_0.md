## 0. 前提の確定事項（本レビューで確認済み）

本命令追加は **将来のISA3.0（YSD8810）向け** であることが確定した。
したがって現行実装系列（ISA2.3：emu23 / hasm23 / scc23）への混入リスクは
「別系列である」という明確な線引きにより回避される。ただし仕様書本文に
ISA2.3への言及が残っている箇所があり（M-1）、帰属を文面上も明確化する必要がある。

---

## 1. 総評

§7.7の追加提案の設計思想は妥当と評価する。

- 6809 の `,U++` / `,--U` に倣った対称ペアであり、
  データスタック（DS：SP直結 PUSH/POP）と
  リターンスタック（RS：汎用レジスタ＋インデックス修飾）の
  命令コスト非対称を解消する動機が明快。
- `R>` = `LDW rD,[rB]+`、`>R` = `STW rS,[-rB]` という Forth 内部インタプリタへの
  マッピングが自然で、OS-9 / Fig-Forth 系の設計思想と整合する。
- sub-opcode 0x18/0x19 は 0x10台メモリアクセス系の空きであり、
  既存の 0x10-0x17（LDB/STB）や 0x50台（特殊レジスタ予約）と衝突しない
  （現行 emu23_v109 の実装照合により、0x18/0x19 未使用を確認済み）。

一方で、V0.10 への昇格（確定）前に解消すべき指摘が複数ある。

## 2. M（必須修正）

### M-1. ISA系列の帰属を文面上も明確化すること

§7.7冒頭（1169行付近）に
「ISA2.3 では RS を汎用レジスタ＋インデックス修飾で回すと複数命令を要し」
という記述がある。本仕様書は **ISA3.0（YSD8810）** の仕様書であり、
現行実装系列である ISA2.3（YSD8800、emu23実装）とは別系列である。

- 帰属は「ISA3.0（YSD8810）向け」で確定した。
- ただし本文の "ISA2.3 では〜" という書き方は、
  「現状（ISA2.3）の問題点を述べ、それをISA3.0で解決する」という
  動機説明の文脈であることが読み取りにくい。
- **修正案**：
  「（現行）ISA2.3 では RS操作に複数命令を要していた。
   本命令は ISA3.0（YSD8810）で追加し、この非対称を解消する」
  のように、問題の所在（ISA2.3）と解決の場（ISA3.0）を明示的に分離すること。

**根拠**：帰属が曖昧なままだと、実装中の ISA2.3 系ツール（scc23/hasm23）に
本命令を誤って混入させる恐れがある。命令追加先ISAの一意性は
バイナリ互換性の根幹に関わる（原則：コンパイラ/アセンブラはISAに無い命令を使わない）。

### M-2. UMビットのビット位置が §13 で誤記（bit3 → bit5）

- §3.2（154-162行）：bit3=V, bit4=IE, **bit5=UM**（正）
- §8.5（1443行）：bit5(UM)←0（正）
- §13.1（1644行）：「**UM ビット（FLAGS bit3）** の活用」（**誤**）

§13.1 の "bit3" は旧版（UMがbit3であった時代）の記述が残存したものと推定される。
現行配置では bit3=V、UM=bit5 であるから、§13.1 を **bit5** に修正すること。

**根拠**：4点整合（ファイル名/バージョン文字列/ヘッダ日付/変更履歴）に加え、
文書内のビット定義は全箇所で一致していなければならない。
1箇所の食い違いが将来のUMビット実装（ISA3.1）でデコーダ誤設計を招く。

### M-3. SHRI の N フラグ更新規則が §3.3表 と §7.3本文 で不一致

- §7.3（764行）：SHRI 動作 → `FLAGS.N = 0`（常に0）
- §3.3 FLAGS更新表（217行）：SHRI は「N=✓」（条件更新）
- §3.3 N定義（292-295行）：一般則「結果の bit15=1 なら N=1」

論理右シフトでは結果の bit15 は必ず0になるため、
「条件更新した結果たまたま常に0」と「無条件で0」は結果値としては一致し、
実害は無い。しかし仕様記述としては別物であり、FPGA/emu実装者が
どちらを正とするか判断できない。

**修正案（いずれか）**：
- (a) §7.3 を「N は演算結果基準で更新（論理右シフト結果ゆえ実効的に常に0）」と改め、
  §3.3表の「✓」と整合させる。→ 実装は Z/N を結果基準で一律更新すればよく簡潔。
- (b) §3.3表を「SHRI: N=0固定」と明記し、§7.3を正とする。

**推奨は(a)**。Z/N を「演算結果に対して一律更新」する実装が
最もFPGAデコーダを単純化でき、MC6809のシフト系フラグ更新の考え方とも近い。

## 3. C（確認推奨）

### C-1. §7.7 命令フォーマットに即値/ディスプレースメントが無い（ストライド+2固定）

byte2 に「上位4bit=rD/rS, 下位4bit=rB」（1183/1212行）を詰めており、
命令長3バイトで即値もディスプレースメントも持たない。
reg_id 0-11 は4bitに収まるためエンコード自体は健全。

ただしストライドが **+2固定** であるため、
Forth内部インタプリタ以外の用途（構造体走査、配列イテレーション等）で
「+2以外のストライド」や「+n」が欲しくなった場合の拡張余地がない。

**確認事項**：V0.10確定は可。ただし将来 `[rB]+n`（ディスプレースメント付き）を
検討する可能性があるなら、§13（将来拡張検討項目）に一行残すことを推奨。
6809 の `n,U` 相当を将来欲する可能性は高い。

### C-2. §7.7 ポストインクリメントのFPGA実装 案A/案B（確認事項5）

1272-1275行の案A（regfile 2write port化）／案B（rB更新を次サイクル分離）は、
「実装フェーズ送り」で妥当。ISA仕様として案を確定させる必要はない。

**ただし注記追加を推奨**：
案A（2write port化）を採る場合、regfileモジュールのインタフェース変更が発生する。
YSD8810のRTL実装時、regfile を 2write port 構成にするなら
デコーダ／FSMのライトバック経路も併せて設計する必要がある。
「案A採用時は regfile を2write port版とし、ライトバック経路を追加設計する」旨を
実装責務欄（1268-1275行付近）に一文追加しておくと、後工程の見落としを防げる。

（補足：GW1NR-9 は BSRAM/LUT リソースに余裕があり、2write port化のコストは
FPGA規模的には許容範囲。タイミングクロージャ次第だが案Aは現実的。知らんけど）

### C-3. §7.7 プリデク時、アライメント例外発生時の rB 状態を明記すること

1216-1217行：`rB = rB - 2` → `mem[rB] = rS` の順（プリデクリメント）。
1226-1228行：アライメント判定は減算後アドレスで行う（**方針として正しい**。
実際のアクセスアドレスと一致するため既存LDW/STW機構を流用できる）。

**確認事項**：減算後アドレスが奇数でアライメント例外（irq4）が飛ぶ場合、
例外ハンドラから見た **rB は減算済みか否か** を明記すること。

- 減算済みで例外に入る（6809流：更新レジスタは更新済み）
- ロールバックして例外に入る（rBは減算前の値）

の2択。ISA3.0の方針を確定する必要がある。
本プロジェクトの確定事項「アライメント例外時のpush PCは次命令のPC」と併せ、
「例外時 rB は減算済み・ストアは中止」等の明文化を推奨。

**根拠**：例外ハンドラでスタック/ポインタ復旧を行う際、
rBの状態が未定義だと復旧コードが書けない。FPGA実装でも
例外時のライトバック抑止条件を一意に決める必要がある。

### C-4. §7.7 使用例の S0=RSP 割当 と §9 ABI（S0=callee-save）の関係

1238行で S0（reg_id 10、callee-save）を Forth の RSP に割当てる例を示している。
ForthカーネルがRSPを固定利用するなら、それはABI上
「グローバル予約レジスタ」であって callee-save の枠組みとは別扱いになる。

**確認事項**：§9 ABI表（1482-1483行）と矛盾しないよう、
「Forthカーネル実行コンテキストでは S0 を RSP 専用に予約する」旨の
但し書きを §9 または YUI OS / Forth側設計書に置くこと。
（callee-save レジスタを大域的にRSPへ転用することは、
 通常のC関数ABIと衝突しうるため、コンテキスト境界を明示する）

## 6. レビュー確認事項(1)-(5)への回答

仕様書§7.7末尾（1280-1286行）で提示された確認事項に対する所見：

| # | 確認事項 | 所見 | 判定 |
|---|---------|------|------|
| (1) | sub-opcode 0x18/0x19 の割当妥当性 | 0x10台の空き。emu23実装照合で未使用確認。0x50台予約と衝突なし | **妥当** |
| (2) | FLAGS 不変の方針 | 既存スタック系（PUSH/POP/PUSHM/POPM/XCHG_SP）と一貫。妥当 | **妥当** |
| (3) | rB=SP 時の非推奨扱い（禁止せずデコーダ簡潔化） | POP/PUSH等価を許容しデコーダを特別扱いしない方針は簡潔で妥当 | **妥当** |
| (4) | プリデク時アライメント判定を減算後アドレスで行う点 | 実アクセスアドレスと一致し正しい。ただしC-3（例外時rB状態）を要明記 | **妥当・要追記** |
| (5) | ポストインク FPGA実装 案A/案B の実装フェーズ送り | 妥当。ただしC-2の注記追加を推奨 | **妥当** |

確認事項そのものは(1)-(3)(5)が妥当、(4)は方針妥当だが例外時rB状態の追記が必要。

## 7. 総合判定と次アクション

**V0.10 への昇格は、下記M項目の解消を条件として保留する。**

設計の方向性（§7.7の命令ペア追加）は承認に値する。
帰属（YSD8810向け）も確定した。残る昇格条件は文書整合（M-1〜M-3）である。

**昇格条件（必須）**：
1. M-1：ISA2.3（問題）とISA3.0（解決）の文面分離
2. M-2：§13.1 UMビット位置 bit3→bit5 修正
3. M-3：SHRI の N更新規則を §3.3表 と §7.3 で一致させる

**昇格推奨条件（強く推奨）**：
4. C-3：プリデク例外時の rB 状態明記
5. C-4：S0=RSP 割当のABI但し書き

上記を反映すれば V0.10 として確定可能と判断する。
