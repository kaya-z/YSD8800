## 1. これまでの経緯（要約）

### 1.1 P1設計の確定事項
- P1初版スコープ = **空区間往復のみ**（超保守）。asm上の4命令連続
  `SUBI SP,#2 / STW A,[SP] / LDW B,[SP] / ADDI SP,#2` を `MOV B,A` に置換。
- dhry_timer.c -O1 で対象は **24件**（実測確定）。効果 = 72命令削減見積り。
- 設計書 `scc23_v2_03_peephole_P1_design_v1_1.md`（M-1/N-1/E-1クローズ、C-1条件付き）。

### 1.2 C-1追補調査で判明した重大事実（前チャットの最大の発見）
poc `scc23_v2_03_poc.c` にemit経路プローブを仕込んで実測した結果:
- **単一 emit_push_a()/emit_pop_b() ペアで区間内命令0（真の空往復）は 0 件**。
  区間内命令数の分布は between=1:73件, =2:28件, =3:6件…**最小1、0は皆無**。
- しかし asm上の4命令連続空往復パターンは grep/awk 厳密一致で **24件 実在**。
- **結論 = 境界偶然マッチ**: 24件は単一ペアが空になったのではなく、
  異なるSIRノードの pop_b 後半（ADDI SP,#2）と別ノードの push_a 前半（SUBI SP,#2）等が
  命令ストリーム上で隣接し4命令窓に偶然マッチしたもの。24件すべて**直前行が `MOV A,B`**。
- ∴ レビュアの因果仮説（右オペランドemitの0命令化）も、当初説明（配列添字ネスト）も
  **両方とも実データで否定された**。
- 中間メモ: `P1_C1_addendum_investigation_v0_9.md`（v0.9・未完）。

### 1.3 安全性の論点（未確定・次チャットの主題）
境界偶然マッチと判明したことで、v1.1設計の正当化「空区間ゆえA不変」の**論拠が崩れた**。
ただし4命令を純粋な命令列として見れば「STW A,[SP] 直後に LDW B,[SP]、間に命令なし・SP不変」
であり、正味効果 = `B=A` ＋ デッドストア（[SP-2]に書いて即SP復帰）。
→ **MOV B,A とのローカル等価は別ペア由来でも成立しうる**が、**emu23実行等価で最終判定が必要**。

## 2. 次チャットの作業 = emu23実行等価検証

**目的**: 24件を MOV B,A に置換した dhry が、元と外部観測等価（出力・P値・正常終了）かを確認。
一致すれば P1（空区間往復置換）の安全性が確定する。

**KY観点（前チャットで挙げた事項・継続）**:
- 出力一致は必要条件であって十分条件ではない。SP収支不変の機械確認と併せて多面的に見る。
- emu23実行は timeout 付き（KY29）。

## 3. 確立済みビルド手順（★最重要・これが前チャットの主収穫）

過去チャット実績＋前チャットで再確認した正しい手順。**勝手判断せずこれに従う**こと。

```
# 前提ツール（プロジェクトナレッジからビルド）
scc23  = scc23_v2_02.c        → gcc -O2 -w -o scc23   （v2.02確認）
hasm23 = hasm23_v1_04.c       → gcc -O2 -w -o hasm23  （v1.04）
lnk23  = lnk23_v2_01.c        → gcc -O2 -w -o lnk23   （v2.01）
emu23  = emu23_v109.c         → gcc -O2 -w -o emu23   （v1.09）
harness= startup_harness23_v15.asm

# (1) 基準asm生成 ★ --runtime-org は 0x3000（0x0100はbackward .orgエラー）
./scc23 --code-org 0x0400 --data-org 0x4000 --runtime-org 0x3000 -O1 -o dhry_base.asm dhry_timer.c

# (2) P1置換版asm生成（p1_apply.py使用・24件置換・SP収支検証内蔵）
python3 p1_apply.py dhry_base.asm dhry_p1.asm
#   → 置換件数24 / SP純移動 置換前後とも -110 で不変 を確認すること

# (3) obj化（★ hasm23 -c。harnessの_mainはrelocで残りlnk23が解決）
./hasm23 -c dhry_base.asm
./hasm23 -c dhry_p1.asm
./hasm23 -c startup_harness23_v15.asm
#   → *.asm.obj が生成される（.binではない）

# (4) リンク（★ code→harness順・--machine force・:0xADDRサフィックス無し）
./lnk23 --machine force dhry_base.asm.obj startup_harness23_v15.asm.obj -o dhry_base.bin
./lnk23 --machine force dhry_p1.asm.obj   startup_harness23_v15.asm.obj -o dhry_p1.bin

# (5) 実行（★ emu23 -q = HALTまで実行・UART出力のみ。timeout付き）
timeout 60 ./emu23 -q dhry_base.bin
timeout 60 ./emu23 -q dhry_p1.bin
#   → 両者の出力・P値・cyclesを比較。P:20不変・出力完全一致が合格。
```

ビルド手順書 `yuios_build_procedure_v1_8.docx` は resident OS 用。
Dhrystone単体は上記CLI手順（過去実績）による。手順変更あれば手順書改版を促すこと。

## 5. ★要確認点・未解決の論点（次チャットで必ず見ること）

1. **base と p1 の obj が両方 20822 bytes code で同一サイズ**だった。
   `MOV B,A`（1命令）と置換前4命令（SUBI/STW/LDW/ADDI）はバイト数が異なるはずで、
   サイズ同一は不審。次の可能性を検証:
   - (a) hasm23が何らかの理由でパディングしている
   - (b) obj の "bytes code" フィールドの意味が命令バイト総和ではない
   - (c) 置換が実は反映されていない（p1_apply.pyのobj化前後で取り違え）
   → **リンク前に `dhry_base.asm.obj` と `dhry_p1.asm.obj` の実バイナリ差分（cmp）を取り、
     置換が確実にobjへ反映されているか確認してから実行比較に進むこと。**
   （これを飛ばすと「同じbinを2回動かして一致」という偽の合格を出す危険＝KY事項）

2. emu23実行後、出力一致だけでなく **cycles差**も記録。P1は72命令削減見積りなので
   cyclesが減っていれば置換が効いている傍証。cyclesが全く同じなら置換未反映を疑う。

## 8. 教訓（前チャット・kaizen候補）

- **環境再構築を伴う重い検証（emu23実行等価等）は、1チャットで環境構築から実行まで
  やると書式崩れリスクが高い**。次回は build スクリプトを create_file で一括投入し
  ツール呼び出し回数を圧縮する、または検証専用の新チャットを短コンテキストで使う。
