## 第Ⅰ部：総則

### 1. 目的とスコープ
- 1.1 目的：emu23 v1.08 の `exec_one()` と外部観測等価な YSD8800 CPUコアを、多サイクル・ステートマシンとして SystemVerilog で実装するための設計を確定する
- 1.2 スコープ境界：
  - **V1 が設計するもの**：命令フェッチ／デコード／実行／メモリアクセス要求の FSM、レジスタファイル（A/B/X/SP/PC/FLAGS）、ALU、分岐ユニット、割り込み受理 FSM
  - **V1 が設計しないもの（V2 以降）**：PSRAM コントローラの物理実装（V2）、MMU 変換（V3.5）、デバイス MMIO（V4-）。V1 は「バスへアドレス/データ/rd/wr/byte選択を出し ready を待つ」抽象バス I/F までを設計し、実メモリは TB のビヘイビアモデルで代替する
- 1.3 正解リファレンス：emu23 v1.08 `exec_one()`（L1089-）。ISA真実＝ISA2_3_v231

### 2. 全体方針
- 2.1 多サイクル FSM 方針（V0本体 §2.1 を継承）：1命令を複数状態に分解、状態ごと1クロック
- 2.2 emu23 exec_one の3段階構造を FSM の骨格とする：**(A) IRQ受理チェック → (B) FETCH → (C) DECODE/EXEC**（emu23 L1094-1115 実照合）
- 2.3 抽象バス I/F 方針：V1 では `mem_addr/mem_wdata/mem_rdata/mem_rd/mem_wr/mem_be/mem_ready` の抽象バスを定義。PSRAM の実レイテンシは V2、V1 の TB では固定レイテンシのビヘイビアメモリで代替

## 第Ⅱ部：CPUコア アーキテクチャ設計

### 3. レジスタファイル
- 3.1 構成：A/B/X/SP/PC/FLAGS（各16bit、V0本体 §3.1）。レジスタ番号 0-5
- 3.2 FLAGS の有効ビット：Z(bit0)/N(bit1)/IE(bit7) のみ（C/V 無し、V0本体 §3.2）。RTL では3bitレジスタ＋未使用ビット0固定で実装するか16bit保持するかを本体で決める
- 3.3 書き込みポート：FETCH での PC++、EXEC でのレジスタ更新、割り込みでの SP 操作の競合整理

### 4. ALU
- 4.1 演算種別：ADD/SUB/AND/OR/XOR/シフト（V0本体 §3.4 Arith-Logic 0x40-0x5F）
- 4.2 **フラグ生成（C/V 無しの帰結）**：Z＝結果==0、N＝結果bit15。**キャリー・オーバーフロー線は持たない**（V0本体 §3.2/§3.9）。乗除算等でキャリーが要る場合の扱い（emu23 がどう処理しているか）を実照合して本体に確定
- 4.3 フラグ更新する命令／しない命令の区別：**LDB/STB は FLAGS 不変**（V0本体 §3.4 実照合済）。MOV 等のフラグ挙動を emu23 実照合で網羅

### 5. 命令デコードと分類
- 5.1 デコード方式：opcode 1バイト（emu23 FETCH は `ir=fetch8(pc++)`、追加 imm16 は命令ごとに後続フェッチ。L1111）
- 5.2 EXT プリフィックス 0x1F の扱い（V0本体 §3.3）
- 5.3 **命令分類表（53命令・emu23 switch 実照合）**：各命令を「必要状態数」でクラス分け
  - クラスA：レジスタ内完結（NOP/MOV/ALU reg-reg）＝ FETCH+EXEC の最小状態
  - クラスB：imm16 追加フェッチあり（LDB/STB [imm16]・分岐 rel16・JMP abs）
  - クラスC：メモリアクセスあり（LD/ST 16bit・LDB/STB・PUSH/POP）
  - クラスD：制御フロー（JSR/RET/IRET・SYSCALL・割り込み受理）＝多段スタック操作
- 5.4 各クラスの代表命令とマイクロステップ（本体で全命令を表に展開）

### 6. FSM 状態遷移設計（V1 の核心）
- 6.1 トップレベル状態：`S_IRQCHK → S_FETCH → S_DECODE → S_EXEC[…] → S_WRITEBACK → (next)`
- 6.2 IRQ受理 FSM：`irq_pending>=0 && IE` で受理シーケンス（PC push→FLAGS push→IE=0→PC=rd16(pending×2)）。V0本体 §5.2 の pending∈{1,2,3,4} 体系を厳守。reset 経路は別系統（V0本体 §8.2）
- 6.3 メモリアクセス状態：抽象バスに req を出し `mem_ready` を待つ wait 状態（多サイクル）。16bit アクセスは偶数アドレス隣接2バイトを分割処理（V0本体 §7.4/§7.5）
- 6.4 align 例外の発火：16bit アクセスで `addr[0]==1` のとき irq_pending=3 をセットしアクセス中断（V0本体 §5.4）。read/write 両経路
- 6.5 状態数の見積もりとクラス別状態遷移図（本体で図示）

### 7. 抽象バス I/F
- 7.1 信号定義：`mem_addr[15:0]/mem_wdata[7:0]/mem_rdata[7:0]/mem_rd/mem_wr/mem_ready`（byte粒度、V0本体 §6.2/§7.4）
- 7.2 16bit アクセスのバイト分割プロトコル（lo=addr, hi=addr+1、リトルエンディアン、V0本体 §7.4）
- 7.3 V1 TB でのビヘイビアメモリ（固定レイテンシ）。実 PSRAM ctrl は V2

## 第Ⅲ部：検証設計

### 8. 検証方式（emu23 突合）
- 8.1 突合基準フォーマット：`PC=%04x A=%04x B=%04x X=%04x SP=%04x F=%02x`（emu23 dump_regs/トレース出力 L1534 と同形式）
- 8.2 **emu23 突合ハーネス**：emu23 の **`-n N`（Nステップ実行＋トレースダンプ、非対話）**（L1742）を golden 生成に用いる。【訂正記録】当初 V0 レビュー申し送りは `-it` 活用としたが、`-it` は**インタラクティブモード**（対話用）であり突合には不適。正しくは `-n`／トレース機構を使う（KY34 実照合 L1742/L1534）
- 8.3 命令別単体 TB：各命令につき初期レジスタ/メモリを与えて1命令実行し、RTL 状態と emu23 `-n 1` 相当の状態を diff
- 8.4 完了条件（V1 工程）：53命令すべての単体 TB が emu23 と一致

### 9. V1 で消化する追加検証項目
- 9.1 **D-3（分岐 Z/N 網羅）**：BEQ/BNE/BLT/BGE を Z/N の境界値（0・正・負・0x8000）で網羅突合（V0本体 §10.3）
- 9.2 D-1（1段ラッチ）・D-2（align）は V2/V3 で消化（V1 ではバス経路の align 発火のみ確認）

## 第Ⅳ部：付録

### 10. 未確定論点（レビューで詰める）
- LV-1 ALU でキャリーが論理上必要な演算（乗算等）を emu23 がどう実装しているか実照合し、RTL 方針を確定（§4.2）
- LV-2 FLAGS を 3bit 実装するか 16bit 保持するか（§3.2）
- LV-3 抽象バスの 16bit 分割を「8bit×2 トランザクション」とするか「16bit byte-enable 一括」とするか（V0本体 C-1 と連動、V2 確定だが V1 バス I/F 定義に影響）
- LV-4 EXT プリフィックス 0x1F 後続命令が現状の YUI OS バイナリで実際に使われているか（使用実績の確認で実装優先度を判断）
