## 1. P1 パターンの定義と意味論（ISA2.3 根拠）

### 1.1 設計書原案（§9.2.5 / §9.2.9 M-4）

原案の P1 は「`SUBI SP,#2`/`STW A,[SP]` … `LDW B,[SP]`/`ADDI SP,#2`（区間内に SP 依存なし）→ `MOV B,A`」。M-4 は「区間内に (i) SP 読み書き・(ii) `[SP+imm]`・(iii) JSR/RET が介在したら非置換」という**判定指針**（確定アルゴリズムではない）。

### 1.2 対象イディオムの実体（KY34・scc23_v2_02.c 確認済み）

- `emit_push_a()`（L2146-2149）= `SUBI SP, #2` / `STW A, [SP]`
- `emit_pop_b()`（L2150-2153）= `LDW B, [SP]` / `ADDI SP, #2`

### 1.3 「往復→MOV B,A」が成立する条件と生成元【C-1 反映】

区間内で **A が一切変更されず、SP も動かされない**場合に限り `MOV B, A` で代替できる。A が上書きされる標準二項演算は誤置換になる（§4 S1）。

**【C-1 反映: 空区間往復24件の生成元】**

v1.0 では「24件は空区間往復」と実測したのみで生成元が未特定だった。

**～～v1.1 の説明（配列添字ネスト説）～～ ※ v1.2 で実測により否定。取り消し線で保持（KY41）:**

> ~~**生成元 C 式**: 添字に算術式を持つ配列アクセス（例 `Arr_1_Par_Ref[Int_Loc+1] = ...`／dhry_timer.c L1002 等）。~~
> ~~**機序**: 添字式（例 `Int_Loc+1`）を二項演算で評価し、その結果（A）を外側の配列アドレス計算の左オペランドとして **push_a** した直後、外側の右オペランド評価が **pop_b** で始まる経路のため、push と pop の間に命令が出ず**空区間**になる。~~
> ~~**意味論の鎖**: 空区間ゆえ A 不変は生成経路上も保証され、pop_b が復元する値は push_a 時の A と同一 → `MOV B,A` と完全等価。~~

**【v1.2 訂正: 実測により「境界偶然マッチ」と判明】**（根拠: `P1_C1_addendum_investigation_v1_0.md` §2）

poc `scc23_v2_03_poc.c` に emit経路プローブ（`emit_push_a`/`emit_pop_b` の呼出境界と区間内命令数を記録）を仕込んで実測した結果:

- **単一の push_a/pop_b ペアで区間内命令数が 0（真の空往復）となるものは 0 件**。区間内命令数の分布は 1:73件, 2:28件, 3:6件… で最小1、0は皆無。
- したがって asm 上の4命令連続パターン24件は、**単一ペアが空になったものではない**。実体は **境界偶然マッチ（boundary coincidence match）**——あるSIRノードの pop_b 後半（`ADDI SP,#2`）と、別ノードの push_a 前半（`SUBI SP,#2`）等が命令ストリーム上で偶然隣接し、4命令窓に一致したもの。24件すべて直前行が `MOV A,B`。
- これにより v1.1 の「配列添字ネスト由来・単一ペアが空」という因果、およびレビュア因果仮説（右オペランドemitの0命令化）は**いずれも実データで否定**された。

**【v1.2 安全性正当化の差し替え】**

生成起源が単一ペアか境界偶然マッチかに**関わらず**、当該4命令を純粋な命令列として見れば正味効果は次のとおり:

```
SUBI SP, #2    ; SP -= 2
STW  A, [SP]   ; [SP] = A   （デッドストア: 直後にSP復帰し書いた値は死ぬ）
LDW  B, [SP]   ; B = [SP] = A
ADDI SP, #2    ; SP += 2    （SP収支ゼロ）
```

すなわち **B = A ＋ デッドストア（[SP-2]へ書いて即SP復帰）＋ SP収支ゼロ**。`MOV`（0x20）は FLAGS 不変ゆえ、これは `MOV B, A` と**外部観測等価**である。

この等価性は emu23 実行等価検証で実証済み（§5 V4・`addendum v1.0` §3）:

- 手順健全性: base/p1 の obj を `cmp` で差分確認（char 850 相違＝置換はobjに反映）。「同一binを2回実行して偽の一致」の危険を排除。
- 実行結果: **N=10 一致・P:20（計算結果）一致・正常終了(HALT)一致**。差分は cycles（47885→47795, **−90**）とその派生値のみ。cycles 減少は置換が実際に効いた積極的証拠。

> 補足: hasm23 の "bytes code" は base/p1 とも 20822 で同一だが、これは `.org` 固定レイアウトの確保長（`code_buf_pos`）であり、実コード量は非ゼロバイトで 10149→9957（−192B）と確実に減少している。サイズ同一は「置換未反映」を意味しない（addendum v1.0 §3.3）。

## 2. 実 emit 実測（KY34・dhry_timer.c / scc23 v2.02 系）

計測: `p1_measure.py`（SP 深度スタックで push_a/pop_b を対応付け、区間内走査）。

### 2.0 実測条件【C-1 反映】

- 実測対象 asm は **-O1（peephole P2a/P2b/P3 適用後）**の出力である。P1 は peephole 後段（§3.5）に置かれるため、P1 が実行時に見る入力と実測条件は一致する。
- さらに poc `scc23_v2_03_poc.c` の `--no-peep`（-O1 のまま peephole のみ OFF）で比較した結果、**空往復 foldable 候補は peephole ON/OFF いずれも 24 件・総数 197 で不変**。24 件は peephole の産物ではなく**コード生成そのものに由来**する（根拠: `P1_C1_investigation_v1_0.md` §3）。したがって実測条件による揺れはない。

### 2.1 全体集計

| 区分 | 件数 | 比率 |
|------|------|------|
| push_a/pop_b 対応ペア総数 | **197** | 100% |
| **置換可能候補（空区間往復）** | **24** | 12% |
| G1: 区間内で A 上書き | 172 | 87% |
| G3_SP_nest: ネスト往復介在 | 42 | — |
| G2: 分岐・ラベル介在 | 52 | — |
| G3_SP/G4_SPrel: SP操作・SP相対介在 | 13 | — |

（違反理由は重複計上。総数197は HANDOVER 実測値と一致。）

### 2.2 置換可能 24 件の正体

24 件はすべて**空区間往復**。例（-O1 ON dhry.asm L521-524／OFF dhry_O1_nopeep.asm L535-538）:
```
    SUBI SP, #2     ← push_a
    STW  A, [SP]
    LDW  B, [SP]    ← pop_b（間に命令ゼロ）
    ADDI SP, #2
```
4 命令が `MOV B, A` 1 命令と完全等価。生成元は §1.3（配列添字ネスト境界）。

### 2.3 実測からの含意

- 原案が想定した「区間内に右辺評価を挟む往復」は **G1=172件**で本質的に畳めない。
- 安全に畳めるのは**空区間往復のみ**（初版スコープ）。
- KY 予知のネスト介在（G3_SP_nest=42）が実在 → 深度スタック対応付けが必須と実証。

## 3. 実装仕様

### 3.1 置換規則（P1・初版スコープ = 空区間往復のみ）

正規化後に連続する 4 命令が
```
SUBI SP, #2
STW  A, [SP]
LDW  B, [SP]
ADDI SP, #2
```
に**完全一致**するとき `MOV B, A` 1 命令へ置換。間にラベル・命令が1つでも挟まれば非置換。

### 3.2 置換成立の必須ガード（全て真のときのみ置換）

- (P1-G1) 4 命令が**この順で完全隣接**（間にラベル・命令・コメント実体なし）。
- (P1-G2) 行1=`SUBI SP, #2`、行4=`ADDI SP, #2`（同量対応）。
- (P1-G3) 行2=`STW A, [SP]`、行3=`LDW B, [SP]`。
- (P1-G4) 行2・行3 の `[SP]` はオフセット無し（`[SP+imm]` を含まない）。
- **(P1-G5)【M-2 v1.3 新設: 直後フラグ依存分岐の除外】** 4 命令窓の**直後の命令が Z/N フラグを読む条件分岐でないこと**。直後が `BEQ`／`BNE`／`BLT`／`BGE` のいずれかなら**非置換**。
  - 根拠: 元の 4 命令列は末尾 `ADDI SP,#2` が Z/N を更新するが、置換後の `MOV B,A`（0x20）は **FLAGS 不変**（`ISA2_3_v231.docx` L254）。境界偶然マッチでは窓直後に来る命令がノード境界次第で一定しないため、直後が「`ADDI SP,#2` の設定した Z/N を読む条件分岐」だと置換で分岐挙動が変わる余地が残る。これを構造的に塞ぐ。
  - **除外対象が4命令で必要十分な理由（ISA2.3 実仕様で裏取り・KY34）**: ISA2.3 で Z/N フラグを**読む**（条件として参照する）命令は `BEQ`(0x61,Z=1)／`BNE`(0x62,Z=0)／`BLT`(0x63,N=1)／`BGE`(0x64,N=0) の**4種のみ**（`ISA2_3_v231.docx` 命令テーブル L228–231）。`JMP`(0x60)/`JSR`(0x68)/`RET`(0x69) は無条件でフラグを読まない。フラグをレジスタへ移す命令（6809 の `TFR CC,r` 相当）は ISA2.3 に存在しない。割り込みは FLAGS を push 退避し `IRET` で pop 復元するため Z/N 可視性に透過的（考慮不要）。ゆえにこの4種除外で `ADDI SP,#2` の FLAGS 更新値を後続が使う経路はすべて塞げる。
  - 実測 24 件への影響: 24 件は emu23 実行等価で P:20 一致（＝直後 Z/N 依存が無かった）ため、G5 追加後も**全数が置換対象として残る**。ガードは取りこぼしを増やさず、将来別プログラム適用時の一般安全性のみ底上げする（超保守設計として一貫）。

### 3.3 フラグ意味論の安全性確認（ISA2.3・KY39）

- `MOV`（0x20）は **FLAGS 不変**（`ISA2_3_v231.docx` L254）。
- ~~置換区間の直後で FLAGS が読まれる用途は無い（pop 直後の算術が改めて FLAGS を設定する）。V2 の asm 実測で駄目押しする。~~ ← **【M-2 v1.3 訂正・取り消し線保持（KY41）】** この論拠は旧前提（4命令が単一 push_a/pop_b 由来で直後は必ず二項演算の続き）に依存していた。境界偶然マッチ（§1.3）では窓直後の命令はノード境界次第で一定せず、一般には成立しない。
- **【M-2 v1.3 補強】** 元の 4 命令列末尾 `ADDI SP,#2` は Z/N を更新するが `MOV B,A` は FLAGS 不変。この差が問題化するのは「窓直後が `ADDI SP,#2` の Z/N を読む条件分岐」のときのみ。これを **(P1-G5)** で構造的に除外する（直後が `BEQ`/`BNE`/`BLT`/`BGE` なら非置換）。ISA2.3 で Z/N を読むのはこの4命令に限る（§3.2 G5 根拠）ため、G5 により置換後も FLAGS 意味論は保存される。
- 実測 24 件では窓直後が Z/N 依存分岐であるものは無く（emu23 実行等価 §5 V4 で P:20 一致＝結果的確認）、G5 は一般安全性の底上げとして機能する。

### 3.4 走査アルゴリズム【M-1 反映: 既存 P2/P3 と同一の w/r 前詰め方式に統一】

v1.0 は `i += 1`（1回適用）と別方式で記述していたが、既存 P2a/P2b/P3 は **w/r 前詰め方式**（`g_insbuf[w++]=g_insbuf[r]`、L676-737 で確認）である。P1 も**同方式に統一**する。

```
int w = 0;
for (int r = 0; r < g_insbuf_n; ) {
    if (r+3 < g_insbuf_n
        && is_line(g_insbuf[r],   "SUBI SP, #2")
        && is_line(g_insbuf[r+1], "STW  A, [SP]")
        && is_line(g_insbuf[r+2], "LDW  B, [SP]")
        && is_line(g_insbuf[r+3], "ADDI SP, #2")) {
        free(g_insbuf[r+1]); free(g_insbuf[r+2]); free(g_insbuf[r+3]);
        free(g_insbuf[r]);
        g_insbuf[w++] = strdup("    MOV  B, A");   /* strdup失敗時は安全側で元4命令温存する分岐を用意 */
        r += 4;                                     /* 4命令消費 */
    } else {
        g_insbuf[w++] = g_insbuf[r];
        r += 1;
    }
}
g_insbuf_n = w;
```

- **連続空往復の健全性【M-1 反映】**: `r += 4` で消費するため、`push_a;pop_b;push_a;pop_b;` が連続しても次の 4 命令窓が独立に判定され、取りこぼさない。シミュレータ `p1_fold_sim.py` で確認済み（dhry には2連続実在しないが、ロジック上は連続でも畳める。SP純移動 -110 が置換前後で不変＝スタックバランス保存も確認）。
- 文字列比較は既存 `is_mov_line` 等と同じ正規化ヘルパに合わせる。

### 3.5 適用条件

- **-O1 のみ**作動（-O0/-O0-strict は非適用＝byte不変）。
- 既存 P2a/P2b/P3 の**後段**に置く。パス順序の相互作用は V3 で確認。

## 4. 誤置換シナリオの列挙（レビュー必須項目）

| # | シナリオ | asm 上の形 | 初版での扱い | 理由 |
|---|---------|-----------|------------|------|
| S1 | 右辺評価を挟む二項演算 | push_a → (Aを書く命令群) → pop_b | 非置換(G1) | left値が失われ誤置換 |
| S2 | ネスト往復（2D配列添字等） | push → push → … → pop → pop | 非対象／一致時も局所安全（脚注参照） | ネスト内側 pop/push が4命令固定窓に一致しない限り非対象。仮に境界偶然で窓一致しても局所正味効果=B=A で閉じる |
| S3 | 区間に JSR 介在（_cc_mul 等） | push → JSR → pop | 非置換(隣接せず) | 呼び先がSP/Aを破壊 |
| S4 | 区間に分岐/ラベル介在 | push → BEQ/ラベル → pop | 非置換(隣接せず) | 制御流合流で前提崩壊 |
| S5 | SP相対アクセス介在 | push → LDW x,[SP+n] → pop | 非置換(隣接せず) | フレーム変数参照のずれ |

> **脚注【C-1 反映／M-1 v1.3 訂正】**: 上記 S1〜S5 のうち S1・S3・S4・S5 は 4 命令固定窓 `SUBI SP,#2 / STW A,[SP] / LDW B,[SP] / ADDI SP,#2` に構造的に一致しない（間に A を書く命令・JSR・分岐/ラベル・SP相対アクセスが挟まる）ため、そもそも置換対象にならない。
>
> ~~**置換可能なのは §1.3 の空区間往復（配列添字ネスト境界由来）のみ**。~~ ← **【M-1 v1.3 で訂正・取り消し線保持（KY41）】** §1.3 のとおり生成起源は「境界偶然マッチ」（異なるノードの pop_b 後半 `ADDI SP,#2` と別ノードの push_a 前半 `SUBI SP,#2` が命令ストリーム上で偶然隣接）であり、「配列添字ネスト由来」ではない。したがって置換の安全性は**生成起源に依存しない**。
>
> **【M-1 v1.3 追記: 局所正味効果による安全性（切り取り元非依存）】** 4 命令窓が何を切り取ったものであっても、窓の局所正味効果は閉じている:
> - 窓内の SP 収支はゼロ（−2 して +2）。
> - 窓が触れるメモリは `[SP]`（入口 `SUBI` で確保した SP−2 番地）ただ1箇所。この番地は入口で確保し `STW` で書き `LDW` で読み `ADDI` で解放する**自己完結領域**で、窓外の SP 状態・スタック内容に依存しない。
> - 窓内に SP 相対アクセス（`[SP+imm]`）・分岐・JSR は固定パターンゆえ構造的に存在しない。
>
> ゆえに **S2 のように窓の外側がネスト往復の途中であっても、窓の局所正味効果は `B = A`（＋デッドストア＋SP収支ゼロ）で確定**し、`MOV B, A` と外部観測等価（§1.3・emu23 実行等価 §5 V4）。この「局所安全性は切り取り元に依存しない」土台を S2 にも一貫適用する。
>
> 参考: S2 が仮に窓一致しなかった通常ケースの深いネスト実例は scc23_v2_02.c L2279-2294（SIR_INDEX2D、push/pop ネスト + `JSR _cc_mul` 介在）で、この場合は JSR 介在により窓不一致＝非対象。

## 6. KY活動（本設計フェーズ）

- **危険**: 区間を素朴な行隣接で対応付けると、ネスト往復（実測42件）で push/pop の対応を取り違え SP 段ずれ→スタック破壊（_fmul X破壊と同種）。
- **防止策**: (1) 対応付けは SP 深度スタックで行う。(2) 初版スコープを空区間限定とし、ネスト・介在が1つでもあれば非置換。(3) 誤置換シナリオ S1〜S5 を §4 に列挙。(4)【追加】P1 前詰め置換の SP 収支保存をシミュレータで機械確認（§3.4）。

## 7. リスク評価まとめ

- 初版スコープを空区間往復に限定したことで、区間内に SP/A を触る命令が原理的に存在せず、**実リスクは P2a 並みの低リスク**。
- ~~生成元が §1.3 で特定されたことで、24 件が「偶然消せる形」ではなく「特定構文から必然的に生じる形」と判明。~~ **【v1.2 訂正】** 24件の生成元は「配列添字ネスト由来の単一空ペア」ではなく **境界偶然マッチ**（異なるノードの pop_b 後半と push_a 前半の偶然隣接）であることが emit経路プローブ実測で判明。ただし安全性は生成起源に依存せず、4命令ローカル正味効果（B=A＋デッドストア＋SP収支ゼロ）と `MOV B,A` の**外部観測等価が emu23 実行等価（P:20一致・cycles−90）で実証済み**。よってリスク評価の結論（P2a並みの低リスク）は変わらない。
- 残リスクは「4命令一致パターンの取りこぼし/誤検出」のみで V2/V5 の asm 差分で機械検証可能。
- 非空区間 P1（副作用なし命令の区間許容）は**本書スコープ外**（§8）。
