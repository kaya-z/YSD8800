# **1. 概要**

本設計書はemu23（YSD8800 ISA2.3エミュレータ）に実装するデバイス群の設計を定める。

| **デバイス** | **チップ名** | **説明** |
| --- | --- | --- |
| タイマー（MMIO化） | YSD8002 | 既存タイマーを関数直接呼び出しからMMIO方式に変更 |
| ストレージ | YSD8003 | SDカード相当ブロックデバイス（emu23ではファイルイメージ） |
| 割り込みコントローラ | YSD8004 | 複数デバイスの割り込みを集約しIRQ1に接続 |

# **2. デバイス設計方針**

## **2.1 デバイス制御はMMIO**

全てのハードウェアデバイス制御はMMIOレジスタへの読み書きで行う。FPGA実装との対応関係が明確になり、デバイスドライバの移植性が高まる。

## **2.2 OSサービスはSYSCALL**

カーネルが提供するOSサービス（プロセス管理・ファイルシステム等）はSYSCALL命令を使用する。従来のSYSCALL 0x0010/0x0011（Dhrystone計測）はYSD8002 MMIOに移行し廃止する。

| **項目** | **変更前（emu23 v1.00）** | **変更後（emu23 v1.01以降）** |
| --- | --- | --- |
| SYSCALL処理 | emu23 Cコードでif/else判定 | 単純にIRQ4を発火するだけ |
| デバイス制御 | SYSCALLフック経由 | MMIO直接アクセス |
| ディスパッチ | emu23側で処理 | YSD8800側ディスパッチテーブル |

## **2.3 ★MMIOアドレスデコード層（v1.6 新設・改良2）★**

### 2.3.1 現行実装の事実（v1.5 まで未記載）

**現行 emu23（v1.11）には「アドレスデコーダ」という層が存在しない。** `rd8()`／`rd16()`／`wr8()`／`wr16()` の4関数がそれぞれ独立した `if` チェーンで個別レジスタのアドレスを逐次判定し、**いずれにも一致しなかったアドレスは通常メモリ経路へフォールスルーする**（`emu23_v111.c` L610-679 ほか実源照合済）。

その帰結として、**未接続 MMIO 空間は「読めば `mem[]` の実体値を返し、書けば `mem[]` に書き込まれて読み返せる」＝ RAM として振る舞う**。

| | 従来の想定 | **実装の実際（v1.6 で判明）** |
| --- | --- | --- |
| 未接続 MMIO 読出 | `$0000` を返す | **`mem[]` の実体値（不定）** |
| 未接続 MMIO 書込 | 捨てられる | **`mem[]` に格納され読み返せる** |

これは `yuios_memmap_design_v2_4.md` L225 の規約「**$FC80 以降は MMIO 専用領域。RAM として使用してはならない**」に対し、**エミュレータ側が規約違反を検出できない**状態であることを意味する。

### 2.3.2 デコード層の責務

改良2 は「既定値の変更」ではなく、**デコード層の新設**である。本層は次の責務を負う。

1. **アドレスが MMIO 空間（`$FC80`〜`$FFFF`）に属するかを判定する**（空間の定義は memmap v2.4 §15 に従う）
2. MMIO 空間内であれば、**実装済みデバイスへ振り分ける**（8bit／16bit を統一的に扱う。§4.4）
3. MMIO 空間内で**どのデバイスにも該当しなければ「未接続」**として扱い、§4.2 の応答仕様を適用する
4. 未接続アクセスを**検知して記録する**（§4.3）
5. MMIO 空間外であれば従来どおり通常メモリ経路へ渡す

### 2.3.3 設計原則

- **本層は既存の `if` チェーンを置き換えるのではなく、その外側に設ける。** 既存のデバイス判定ロジックは無改変のまま残し、差分を最小化する（退行時の切り戻しを容易にするため）。
- **実機忠実性と検証容易性を両立させる。** 返す値は実機（プルアップ）と同一にしつつ（§4.2）、**実機にはできない「誤アクセスの記録」をエミュレータの責務として担う**（§4.3）。両者は排他ではない。
- **段階導入とする。** デコード層の新設・被覆漏れ解消（B-C-1a）と、プルアップ既定値の適用（B-C-1b）は**実装・回帰とも分離**する。混在させると回帰差分の由来が切り分け不能になる。

### **2.3.4 ★実装仕様（擬似コード・v1.7 新設・レビュー M-6）★**

#### (1) 粒度：バイト単位で判定する

**デコード層はバイト粒度で判定する。16bit アクセスは 2 バイトの合成として扱う。**

これは新たな方針ではなく、**現行実装が既にその構造である**ことに合わせたものである（`emu23_v111.c` L668-669：`rd16` は MMU 域を `rd8(a)` と `rd8(a+1)` に委譲。L672-675：通常メモリも `phys_rd8` 2 回）。RTL 側も `mmio_rdata` が 8bit でありバイト粒度である（`ysd8800_mmio_stub_v0_7.sv`）。**三者の粒度が揃う。**

この採用により、**レビュー C-2 の「部分ヒット」問題は概念ごと消滅する**（後述 (5)）。

#### (2) 関数分界

**4 経路に同じコードを 4 回書いてはならない。** 単一の判定関数を設け、各経路はこれを呼ぶ。

```c
/* MMIO空間の判定結果 */
typedef enum {
    MMIO_NOT_IN_SPACE,        /* $FC80未満 = 通常メモリ */
    MMIO_MAPPED,              /* MMIO空間内・実装済レジスタ・当該幅で対応 */
    MMIO_MAPPED_UNSUPPORTED,  /* MMIO空間内・実装済だが当該アクセス幅では未対応 ★v1.8★ */
    MMIO_UNMAPPED             /* MMIO空間内・どのレジスタにも属さない = 未接続 */
} mmio_class_t;

/* アドレス1バイトを分類する。副作用を持たない純関数とすること。
 * ★v1.8: size 引数を追加（第4状態はアクセス幅に依存するため。M-11） */
static mmio_class_t mmio_classify(uint16_t addr, int size);
```

**`mmio_classify()` は純関数（副作用なし）とする。** 副作用（ラッチ・自動インクリメント・W2C）は従来どおり既存のデバイス処理側で起こす。分類と副作用を同じ関数に同居させると、分類のためだけの呼び出しが副作用を誘発する事故を招く。

#### (3) 判定順序と各経路の構造

```c
uint8_t rd8(uint16_t a) {
    switch (mmio_classify(a, /*size=*/1)) {
    case MMIO_NOT_IN_SPACE:
        break;                     /* 従来どおり下へ抜ける */
    case MMIO_MAPPED:
        break;                     /* 既存のifチェーンに処理させる */
    case MMIO_MAPPED_UNSUPPORTED:  /* ★v1.8: 実装済だが当該幅で未対応 */
        if (mmio_warn_enabled)     /* ★C-8: 段階ガード（B-C-1b以降で有効） */
            mmio_report_unsup(a, /*is_write=*/0, /*size=*/1);
        return 0x00;               /* mem[]へは落とさない（§2.3.4(7)） */
    case MMIO_UNMAPPED:
        if (mmio_warn_enabled)     /* ★C-8: 段階ガード（B-C-1b以降で有効） */
            mmio_report_unmapped(a, /*is_write=*/0, /*size=*/1);
        if (bus_pullup_enabled) return 0xFF;                   /* §4.2 B-C-1b */
        break;                     /* B-C-1a時点: 従来どおりフォールスルー */
    }

    /* ↓ 既存のifチェーン（無改変）＋ §4.4 で追加する8bit被覆分 */
    if (a == UART_STAT) return ...;
    ...
    /* ↓ 従来どおりの通常メモリ経路 */
    return phys_rd8(mmu_translate(a));
}
```

> **★段階ガードの規定（v1.8 新設・レビュー C-8）★**
> **`mmio_warn_enabled` は B-C-1a-1／1a-2／1a-3 では偽、B-C-1b で真になる**（§12.1）。擬似コードに段階情報を持たせないと、実装者が 1a 段で警告を出す実装をしてしまい、**1a を「完全な非機能変更」に保つ**という段階分離の前提が崩れる。
> **`MMIO_MAPPED_UNSUPPORTED` の `return 0x00` は段階ガードの対象外**（B-C-1a-2 の被覆漏れ解消と同時に有効化する）。これは §4.4 の是正そのものであり、警告出力とは性格が異なるため。**この 1 点は 1a-2 での意図的な挙動変更**であり、§11.3.1 BC-8B で検証する。

#### ★(3-b) `size` 引数の意味と 16bit 経路の擬似コード（v1.9 新設・レビュー F-2）★

##### `size` の定義（★二義性の解消★）

> **`size` は「その CPU アクセスの幅」（1 または 2）である。分類対象バイトの幅ではない。**
> **16bit アクセスでは、下位バイト・上位バイトそれぞれの分類呼び出しに対しても同じ `size=2` を渡す。**

**この確定が必要な理由**：`$FC86` UART_BAUD は 16bit アクセスに対応済（`emu23_v111.c` L619／L694）だが 8bit では非対応（L827）である。もし `size` を「分類対象バイトの幅（常に 1）」と解釈すると、**正常な 16bit BAUD アクセスが `MMIO_MAPPED_UNSUPPORTED` と分類され、`$00` を返して `[MMIO-UNSUP]` 警告を吐く**という退行が起きる。**`size` はアクセス幅でなければならない。**

##### `rd16` の擬似コード

```c
uint16_t rd16(uint16_t a) {
    /* ★バイト粒度で2回分類し合成する（§2.3.4(1)(5)）。
     * ★size は「CPUアクセス幅」=2 を両バイトに渡す（上記定義） */
    mmio_class_t c_lo = mmio_classify(a,               /*size=*/2);
    mmio_class_t c_hi = mmio_classify((uint16_t)(a+1), /*size=*/2);

    if (c_lo == MMIO_MAPPED && c_hi == MMIO_MAPPED) {
        /* 両バイトとも実装済 → 既存のifチェーンに委譲（従来どおり）
         * 例: $FC86 UART_BAUD は size=2 のためここに来る */
    } else if (c_lo == MMIO_NOT_IN_SPACE) {
        /* MMIO空間外 → 従来どおり通常メモリ経路 */
    } else {
        /* 部分ヒットを含む混在ケース: バイトごとに解決して合成 */
        uint8_t lo = mmio_byte_read(a,               c_lo, /*size=*/2);
        uint8_t hi = mmio_byte_read((uint16_t)(a+1), c_hi, /*size=*/2);
        return (uint16_t)(lo | ((uint16_t)hi << 8));
    }
    /* ↓ 既存のifチェーン（無改変）→ 通常メモリ経路 */
    ...
}
```

**具体例（MCR）**：`$FF10` は MAPPED、`$FF11` は UNMAPPED（§2.3.4(6-ex)）。よって 16bit 読出は **`mcr | $FF00`**（プルアップ有効時）となる。§2.3.4(5) の表と一致する。

##### `wr16` の擬似コード（要点のみ）

```c
void wr16(uint16_t a, uint16_t v) {
    mmio_class_t c_lo = mmio_classify(a,               /*size=*/2);
    mmio_class_t c_hi = mmio_classify((uint16_t)(a+1), /*size=*/2);

    if (c_lo == MMIO_UNMAPPED && c_hi == MMIO_UNMAPPED) {
        if (mmio_warn_enabled) mmio_report_unmapped(a, /*is_write=*/1, /*size=*/2);
        if (bus_pullup_enabled) return;   /* 書込を捨てる（§4.2.2） */
    }
    /* 両バイトMAPPED → 既存のifチェーンに委譲（副作用は既存側で発火・§2.3.4(4)） */
    ...
}
```

**16bit 書込では副作用は既存のデバイス処理側で 1 回だけ発火する**（デコード層は関与しない）。**8bit 書込の副作用規定は §4.4.3.1 を参照すること。**

**要点**

- **既存の `if` チェーンは無改変で残す。** デコード層はその**前段**に置く。`MMIO_MAPPED` の場合は何もせず既存チェーンに委ねる（＝実装済レジスタの処理は一切変わらない）。
- **`MMIO_UNMAPPED` の扱いが段階で変わる。** B-C-1a では**報告のみ行いフォールスルーする**（応答は現行維持）。B-C-1b で `bus_pullup_enabled` により `$FF` を返すようになる。**この過渡状態を許容することが、段階分離を成立させている。**
- `wr8`/`wr16` も同一構造。`MMIO_UNMAPPED` かつプルアップ有効時は**何もせず return**（書込を捨てる）。

#### (4) 副作用の発火位置

**副作用（`CYCLE_LO`/`SCORE_LO` のラッチ、`SD_DATA` の BUF_PTR 自動インクリメント、`IRQ_STAT` の W2C）は、すべて既存のデバイス処理側（`if` チェーン内）で発火する。デコード層では一切発火させない。**

デコード層が発火に関与するのは「`MMIO_UNMAPPED` なら既存チェーンに到達させない」という点のみである。未接続アドレスに副作用は存在しないため矛盾は生じない。

#### (5) 16bit アクセスの合成規則（レビュー C-2 への回答）

16bit アクセスは下位・上位の 2 バイトを**それぞれ独立に分類**し、結果を合成する。

| 下位バイト | 上位バイト | 16bit 読出の結果 |
| --- | --- | --- |
| MAPPED | MAPPED | 従来どおり（デバイス値） |
| **MAPPED** | **UNMAPPED** | **下位＝デバイス値、上位＝`$FF`**（プルアップ有効時） |
| UNMAPPED | UNMAPPED | `$FFFF` |

> **★v1.9 注記（レビュー N-14）★** 本表に `MMIO_MAPPED_UNSUPPORTED` の行が無いのは、**現時点では `size=2`（16bit アクセス）で本状態が発生しないため**である。16bit 非対応のレジスタは存在しない（`$FC86` UART_BAUD は 16bit のみ対応＝8bit 側が非対応）。**`MMIO_MAPPED_UNSUPPORTED` は `size=1` でのみ生じる。** 将来 16bit 非対応レジスタを追加する場合は本表に行を追加すること。

**具体例（C-2 で問われた MCR）**：MCR は `$FF10` の 1 バイト幅、`$FF11` 以降は未接続。よって `$FF10` への 16bit 読出は **`mcr | $FF00`** となる。これは現行実装の構造（2 バイト合成）をそのまま踏襲した自然な帰結であり、「部分ヒット」という特別な概念を導入する必要はない。**RTL がバイト粒度である以上、この扱いが RTL とも整合する。**

#### (6) レジスタスロットの定義（レビュー C-3 への回答）

**MMIO レジスタは偶数アドレス起点の 16bit スロット（2 バイト）を占有する**ものとし、その**奇数アドレスは当該レジスタの上位バイトとして `MMIO_MAPPED` に分類する**（未接続ではない）。

| 対象 | 8bit 読出の応答 | 副作用 |
| --- | --- | --- |
| `$FCAA`（SD_DATA・8bit 有効） | データ値 | **発火する**（BUF_PTR 自動インクリメント） |
| **`$FCAB`（同・上位バイト）** | **`$00`**（8bit 有効レジスタの上位は 0） | **発火しない** |

`$FF` を返さない理由は、**当該アドレスが「未接続」ではなく「実装済レジスタの一部」だから**である。ここを未接続扱いにすると、実在するレジスタに対して誤アクセス警告（§4.3）が出てしまい、検知機構の信頼性を損なう。

##### ★(6-ex) MMU レジスタファイルは本規則の適用対象外（v1.8 新設・レビュー M-10）★

**MMU レジスタファイル（`$FF00`〜`$FF10`）はバイト粒度レジスタであり、上記 16bit スロット規則を適用してはならない。**

| アドレス | 実体 | 幅 |
| --- | --- | --- |
| `$FF00`〜`$FF0F` | **PTR[0]〜PTR[15]（16 個の独立した 8bit レジスタ）** | 各 1 B |
| `$FF10` | MCR | 1 B |
| `$FF11` 以降 | **未接続**（§4.1） | — |

実源：`emu23_v111.c` **L135**（`PTR[0]〜PTR[15]: 0xFF00〜0xFF0F`）・**L836-837**（`if (a >= MMU_PTR_BASE && a < (MMU_PTR_BASE + 16)) return mmu.ptr[a - MMU_PTR_BASE];`）。

**すなわち `$FF01` は PTR[0] の上位バイトではなく、PTR[1] という独立したレジスタである。** スロット規則を素直に適用すると「奇数アドレス＝上位バイト＝`$00`」となり、**PTR[1]／[3]／[5]…の奇数番 8 本が読めなくなる**（MMU が壊れる）。

**あわせて v1.7 の (5) と (6) の矛盾を解消する。** v1.7 では `$FF11` の扱いが (5)（＝UNMAPPED）と (6)（＝MCR スロットの上位バイト＝MAPPED）で食い違っていた。**本除外規定により (5) 側に統一**し、§4.1／§4.2.1 の検算（MCR 1 B・`$FF11`〜`$FF1F` は未接続 15 B）とも整合する。

##### ★(6-v) 分類規則の全数検算（v1.8 新設・レビュー M-10 の再発防止）★

**規則を新設した以上、§4.1 の実装済レジスタ全数に当てはめて検算した結果を以下に記す**（実源：`emu23_v111.c` L295-303／L326-327／L596-608／L135-136・2026-08-11 照合）。

| デバイス | アドレス | 本数 | 配置 | スロット規則 |
| --- | --- | --- | --- | --- |
| YSD8001 UART | $FC80／82／84／86 | 4 | 偶数・2B 間隔 | ✅ 適用 |
| YSD8002 タイマー | $FC90／92／94／96／98／9A／9C／9E | 8 | 偶数・2B 間隔 | ✅ 適用 |
| YSD8003 ストレージ | $FCA0〜$FCB0 | 9 | 偶数・2B 間隔 | ✅ 適用 |
| YSD8004 割込 | $FCB2／$FCB4 | 2 | 偶数・2B 間隔 | ✅ 適用 |
| **MMU PTR/MCR** | **$FF00〜$FF10** | **17** | **バイト粒度** | **❌ 除外（(6-ex)）** |

**例外は MMU の 1 系統のみ。他 23 本はすべて規則に適合する。**

> **★KY（レビュー指摘を採用・v1.8）★** 本件は「**一般規則を作ったら、その例外が既に実装に存在していた**」型の欠陥である。**規則を新設する際は、既存の実装済オブジェクト全数を規則に当てはめて検算すること。** 今回は例外が MMU 1 系統だけだったが、その 1 件を見落とせば MMU が壊れた。上表はその検算の記録である。

#### (7) ★第4の分類状態：`MMIO_MAPPED_UNSUPPORTED`（v1.8 新設・レビュー M-11）★

**v1.7 の 3 値分類（NOT_IN_SPACE／MAPPED／UNMAPPED）には、「実装済レジスタだが当該アクセス幅では未対応」という状態が欠けていた。**

該当するのは **`$FC86` UART_BAUD への 8bit アクセス**である。v1.7 の分類では次の経路をたどる。

```
$FC86 への rd8:
  mmio_classify() → MMIO_MAPPED（実装済レジスタのスロット）
    → 既存 if チェーンへ委譲
      → rd8 は UART_BAUD を扱わない（L827：意図的対象外）
        → phys_rd8(mmu_translate(a)) ＝ mem[] フォールスルー ★問題★
```

**結果として UART_BAUD の 2 バイトに限り「MMIO 空間が RAM として振る舞う」状態が残存し、しかも `MMIO_MAPPED` と分類されているため §4.3 の警告も出ない。** これは §2.3.1 が「規約違反を検出できない状態」として問題視した現象そのものであり、**デコード層を新設する目的に反する**。

**規定：分類に第4状態を追加する。**

```c
typedef enum {
    MMIO_NOT_IN_SPACE,          /* $FC80未満 = 通常メモリ */
    MMIO_MAPPED,                /* 実装済レジスタ・当該幅で対応 */
    MMIO_MAPPED_UNSUPPORTED,    /* 実装済レジスタだが当該アクセス幅では未対応 ★v1.8★ */
    MMIO_UNMAPPED               /* 未接続 */
} mmio_class_t;
```

| 状態 | 読出 | 書込 | `mem[]` へ落とすか | 警告 |
| --- | --- | --- | --- | --- |
| `MMIO_MAPPED_UNSUPPORTED` | **`$00`** | **無視** | **落とさない** | **`[MMIO-UNSUP]`** 1 行（抑制ルールは §4.3.3 を共用） |

**読出値を `$00` とする根拠**：YSD8001 は既に「値の無いバイトは 0」を採用している。`ysd8001_uart_design_v1_2.docx` **L160-162**「UART_RX 16bit 読み出し: 下位 8bit に受信値、**上位 8bit は 0**」「UART_STAT 16bit 読み出し: … **上位 8bit は 0**」（実源照合済・2026-08-11）。**(6) の `$FCAB`＝`$00` とも一貫する。**

**却下した代替案**

| 案 | 却下理由 |
| --- | --- |
| UART_BAUD を UNMAPPED と分類する | **実在するレジスタを未接続と偽ることになり、(6) の「未接続警告の信頼性」の論理と矛盾する** |
| 8bit 対象外を撤回し UART_BAUD も 8bit 対応する | UART 設計書 L166 の規定変更を伴い、**影響が本工程を超える** |

## **3.1 IRQ優先順位**

| --- | --- | --- | --- | --- |
| 0（最高） | IRQ3 | アラインメント例外 | NMI | IE=0中でも即時発生（v1.2確定） |
| 1 | IRQ0 | YSD8002 タイマー | マスク可 | 外部デバイス最高位・YSD8004経由なし |
| 2 | IRQ1 | YSD8004経由（複数デバイス） | マスク可 | YSD8001 UART / YSD8003 ストレージ完了等 |
| ~~3~~ | ~~IRQ2~~ | ~~予備~~ | ~~マスク可~~ | **★v1.4削除★ ISA2.3にIRQ2は存在しない（ISA2.3 §8.1/§8.2 実源照合済）。ベクタ$0006 は irq_id=3＝アラインメント例外に割り当て済みであり、「IRQ2」という割込源は本設計書の記載誤りであった** |

**【重要】IRQ3（アラインメント例外）はNMI（Non-Maskable Interrupt）扱いとする。IE=0中（割り込み禁止中）であっても即時発生する。アラインメント違反はプログラムバグによる例外であり、無視して処理を続けることは危険なためである。**

## **3.2 同時発生時の動作**

| **ルール** | **説明** |
| --- | --- |
| NMI優先 | IRQ3はIE状態に関わらず最優先で即時受理する |
| 優先処理 | IE=1のときpending中で最も優先順位の高いIRQを受理する |
| 低優先IRQ保持 | 低優先IRQはpendingとして保持し、IRET後に再評価して受理する |
| ネスト禁止 | IRQ受理時にIE=0となるため、ハンドラ実行中は原則ネスト禁止 |
| ★IE非依存ラッチ（v1.5追記）★ | 上記「ネスト禁止」は**受理**の抑止であり、**`irq_pending` のラッチは IE=0 中も継続する**。その結果ハンドラは「余分に1回」起動しうる。**ハンドラは冪等に書くこと**。詳細は §3.2.2 参照 |
| ネスト許可 | ハンドラ内でEI命令を実行した場合のみ高優先IRQのネスト割り込みを許可する |
| IRET後再評価 | IRET実行時にpending中IRQがあれば次命令フェッチ前に再評価・受理する |

### **3.2.1 実質序列（v1.4新設・FPGA V3.7で確定）**

emu23 の実装事実として、`irq_pending` の調停は **2段構え**であり、その結果生じる実質的な序列は次のとおりである。

```
timer(IRQ0) / align(IRQ3)  >  IRQ1(YSD8004経由)  >  SYSCALL(IRQ4)
```

**【第1段】pending保護**（`ysd8004_raise()` 内）
後着の IRQ1 は、先着の timer(pending=1) / align(pending=3) を**蹴落とさない**。一方 SYSCALL(pending=4) は IRQ1 に**譲る**。

**【第2段】IRQ_STAT 再評価**（毎命令）
第1段の保護によって後回しにされた IRQ1 は、`IRQ_STAT != 0` である限り毎命令再評価され、IRET後に復活する。したがって IRQ1 は**取りこぼされない**。

**【FPGA実装への写像】**
第2段は、YSD8004 の `irq1_o` を**レベル出力**（`IRQ_STAT != 0`）とすることで自動的に成立する（V3.7 で実証済）。第1段（優先度比較）は V5（Timer）実装時の設計論点として残る。詳細は `v3_7_design_memo_v0_3.md` §4.4b を参照。

### **3.2.2 ★IE 非依存ラッチとハンドラ冪等性要件（v1.5新設・FPGA V4 S5(c)で確定）★**

#### **【事実】`irq_pending` のラッチは IE を見ない**

emu23・FPGA RTL のいずれも、`irq_pending` への**ラッチ**（取り込み）は `IE`（`FL_IE` / `flags_ie`）を**参照しない**。`IE` を見るのは**受理**（accept）のみである。

| 段階 | emu23 実源 | FPGA RTL 実源 | IE を見るか |
| --- | --- | --- | --- |
| **ラッチ**（取り込み） | `ysd8004_raise()` L314-329<br>`IRQ_STAT`再評価 L1576-1578 | L1223-1225<br>`if (state == S_IRQCHK && irq_in != 3'd0) irq_pending <= irq_in;` | ★**見ない**★ |
| **受理**（accept） | L1176<br>`if (cpu.irq_pending >= 0 && (cpu.flags & FL_IE))` | L590<br>`if (irq_pending != 3'd0 && flags_ie)` | **見る** |

#### **【帰結】ハンドラ実行中（IE=0）でも pending は積まれ続ける**

§3.2 の「ネスト禁止」（受理時 `IE=0`）は**受理の抑止**であって、**ラッチの抑止ではない**。したがって:

> **ハンドラが割込源を沈黙させても、沈黙させる「前」に既にラッチされた `irq_pending` は消えない。`IRET` で `IE=1` に戻った瞬間、その pending が受理され、ハンドラが「もう1回だけ」起動する。**

これは異常ではなく、**emu23 と FPGA RTL が一致した正しい挙動**である。

#### **【MC6809 との対応】**

これは MC6809 の `IRQ`/`FIRQ` でも起きる古典的挙動である。6809 において `CC` の `I` ビットを立てても、既に内部でラッチされた要求は `RTI` 後に処理される。

**OS-9 の IRQ ポーリングルーチンが「デバイスの STAT を読み、自分の仕事が無ければ何もせず即 RTI」という構造になっているのは、まさにこの「余分な1発」を吸収するためである。** YSD8800 でも同じ規律が必要となる。

#### **【★OS設計上の必須要件★】割込ハンドラは冪等（idempotent）に書くこと**

YUI OS を含む YSD8800 上のすべての割込ハンドラは、次を満たさねばならない:

1. **冒頭でデバイス STAT を読み、自分に処理すべき仕事があるかを判定する。**
2. **仕事が無ければ、何もせず直ちに `IRET` する。**（＝ 空振り起動を許容する）
3. **2回以上起動しても状態が壊れないこと。**（カウンタの二重加算・バッファの二重取り出し等を起こさない）

★**「ハンドラが必ず1回だけ呼ばれる」ことを前提にしたコードを書いてはならない。**★

#### **【実証】FPGA V4 / S5(c) c6（UART_TX_IRQ_TDRE）**

TX(TDRE) はレベル（§3.3 注3）であるため、この性質が最も顕著に現れる。

- ハンドラが**1回目の起動で**即座に `IRQ_MASK` bit2 をセットし `irq1_o` を落とす。
- にもかかわらず、ハンドラ実行中（`IE=0`）に `irq_pending ← 2` が再ラッチされている。
- `IRET` 後にそれが受理され、ハンドラは**合計2回**起動する（実測 `cnt=2`）。

したがって「ハンドラ起動回数 = 2」が、**TDRE がレベル信号であることの証明**として機能する（パルスであれば `cnt=1` となる）。

#### **【V5（Timer）への申し送り】**

`v3_7_design_memo_v0_3.md` §4.4b に記載の「第1段（timer/align の pending 保護）」を FPGA RTL に実装する際、この IE 非依存ラッチの性質を前提とすること。**保護ロジックを `flags_ie` で条件付けてはならない**（emu23 と乖離する）。

## **3.4 IRET時のタイマー再設定（v1.3新設・Step 8-I）**

タイマー（YSD8002）の次回IRQ発火サイクル再設定（YSD8002_iret相当）は、
**タイマーIRQ（IRQ0）から復帰するIRETでのみ実行する。** 他のIRQ
（IRQ1=YSD8004経由・IRQ3=アラインメント・IRQ4=SYSCALL）のIRETでは
タイマー再設定を行ってはならない。これは ysd8002_timer_design_v1_0.docx §5.3
「IRQ0（タイマー）のみを対象とする。他のIRQのIRETでは呼び出さない」の明文化である。

**背景（既知不具合の是正）**: emu23 v1.06以前はIRET命令（case 0x04）が
IRQ種別を問わず無条件にYSD8002_iret()を呼んでいた（§5.3違反の実装バグ）。
このためIRQ1等のハンドラがIRETするたびタイマーの次回発火が「現在cycle+period」へ
先送りされ、タイマーとIRQ1が高頻度衝突する負荷下でタイマーIRQが大量欠落していた。
emu23 v1.07で「タイマーIRQ実行中フラグ（timer_in_service）」を導入し、
タイマーIRQ受理時にセット・IRET時にこのフラグが真の場合のみYSD8002_iret()を
呼んでクリアする方式で是正した。

**検証**: タイマー(IRQ0)とIRQ1を高頻度衝突させる専用テスト（理論タイマーIRQ=983）で、
v1.06=1回受理（欠落）→ v1.07=983回受理（欠落ゼロ）を実証。通常動作（衝突なし）の
回帰は、yuios 56416バイト一致・Dhrystone 826/48405/P:20一致・v1.06/v1.07同一
バイナリ出力完全一致で確認済み。

**FPGA実装への含意**: timer_in_serviceフラグは逐次実行エミュレータ固有の足場であり、
ハードのRTLには写像されない。ハードのタイマーは自走カウンタ＋オートリロードで
CPUのIRETと無関係に時を刻むため、本不具合はハードには元来存在しない。
詳細は step8i_irqfix_design_v0_2.md §3.3 を参照。

**現行 RTL（`ysd8800_mmio_stub_v0_7.sv` L458）は未接続 MMIO に `8'h00` を返しているが、これは誤りである。** GND に落ちている回路が存在しないにもかかわらず 0 を返すのは、**デコーダが値を捏造している**ことに等しい。V3 スタブ時代の暫定実装が残置されたものと判断する。

なお **FPGA の「内部」配線では「誰も駆動しない状態」を作れない**。内部配線に三態バッファは存在せず、`z` 記述は合成時にマルチプレクサへ変換されるため、RTL では必ず default 値を書かざるを得ない。したがって RTL における選択肢は実質「`8'h00`（誤）」か「`8'hFF`（プルアップ模倣）」の二択であり、後者を採る（§10 参照）。

## **4.3 ★未接続アクセスの検知機構（v1.6 新設）★**

### 4.3.1 必要性：`$FFFF` は YUI OS の番兵と衝突する

未接続読出値をプルアップ模倣（`$FFFF`）とすると、**誤アクセスの結果が YUI OS の予約値と完全に一致する**という問題が生じる。

| 値 | 意味 | 出典 |
| --- | --- | --- |
| **`$FFFF`** | **`IDX_NIL`（IPCキューの終端番兵）** | `kernel_v12_11.asm` L292 |
| `$FFFE` | `ERR_IPC_NOSLOT`（プール枯渇） | 同 L293 |
| `$FFFF` | `rx_pop` の異常センチネル | 同 L1904-1918 |

IPC キュー処理は `CMPI A, #$FFFF`（L1042・L1086）で終端を判定する。**壊れたポインタが未接続領域を指した場合、読み出した `$FFFF` は「キューが空」という完全に正常な状態として受理され、タスクは正常に `WAIT_IPC` で寝る。**例外もログも出ない。症状は「なぜかタスクが起きてこない」という形で、**発生地点から遠く離れた場所・時刻に現れる**。

現行の `mem[]` フォールスルー（不定値）は、多くの場合 `$FFFF` にならないため**派手に落ちてくれる**。プルアップ化はこの「親切さ」を失わせる。

**ただしこれはプルアップを採らない理由にはならない。** 実機のバスがプルアップされている以上 `$FFFF` が返るのが物理的に正しく、ここは譲らない。論点は「実機忠実性を取ったときに失われるデバッグ可能性を、エミュレータ側でどう補うか」である。**emu23 は実機ではないため、実機と同じ値を返しつつ同時に記録できる。これは実機にはできない仕事である。**

### 4.3.2 α：警告ログ（**B-C-1b 以降・オプション指定不要で有効**／★v1.8 是正・レビュー C-9★ v1.7 の「既定で有効」は B-C-1a-1〜1a-3 の間は無効であることと矛盾して読めた）

未接続 MMIO へのアクセスを検知した場合、**アクセスアドレスと当該アクセスを行った PC を 1 行で記録する**。

- 出力先は診断ログ（`stderr`）とし、**`quiet_mode`（`-q`／`-it`）では抑制する**（他文書参照：`emu23_interactive_mode_design_v1_6.md` §2.4「診断ログ抑制（A方針）」。v1.7 是正：v1.6 の「§2.4 の A方針」は本設計書内の節と誤読される記載だった）。対話画面と自動テストの汚染防止のため
- **ただし §4.3.3 の総数サマリのみは `quiet_mode` でも `stderr` に出力する**（v1.7 新規規定・レビュー M-4 対応）。`-q` の **stdout** に対する byte-exact ゲート（§11.1）は `stderr` の内容に影響されないため、ゲートを壊さずに検知能力を保てる
- 読出・書込の別、8bit/16bit の別を含める

### 4.3.3 ログ長大化の抑制（必須要件）

**未接続アクセスがループ内で発生すると、警告が毎命令出力されログが長大化する。** 本プロジェクトではログ長大化がツール動作の不安定化を招く実害として認識されている。したがって抑制機構を**必須要件**とする。

| 要件 | 内容 |
| --- | --- |
| 同一 PC の重複抑止 | **同一 PC からの警告は初回のみ**出力する |
| 総数上限 | **N = 16** 件で打切る（既定値） |
| 打切り時の明示 | 上限到達時に「以降抑制」を 1 行出力する |
| 総数サマリ | **実行終了時に未接続アクセスの総件数を 1 行で報告**する（打切り後も計数は継続する。件数が消えると検知機構の意味が失われるため） |
| **サマリの出力先（v1.7 新規規定）** | **`stderr`。`quiet_mode`（`-q`／`-it`）でも抑制しない。** 個別警告は抑制するがサマリは残す。これにより `-q` 実行でも「未接続アクセスが 0 件であること」を検証可能とする（§11.3 BC-5）。**総件数 0 の場合もサマリ行を出力する**（出力の有無で判定させると「実装漏れ」と「0 件」が区別できなくなるため） |

### 4.3.4 β：`--strict-mmio`（オプション）

`--strict-mmio` 指定時、**未接続 MMIO アクセスを検出した時点で実行を停止**し、アドレス・PC・アクセス種別を報告する。既定では停止しない（実機忠実性を既定とし、厳格検査は明示的に選択させる）。

本オプションは、`$FFFF` が正常値に化けて症状が遠方に現れる問題（§4.3.1）に対し、**発生地点そのものを押さえるための手段**である。

## **4.4 ★8bit アクセス経路の被覆漏れ解消（v1.6 新設・B-C-1a）★**

### 4.4.1 現行実装の欠陥

**`rd8()`／`wr8()` が扱うレジスタ集合は、`rd16()`／`wr16()` より大幅に狭い。** 未処理のレジスタに 8bit アクセスすると、デバイスに届かず `mem[]` へフォールスルーする（`emu23_v111.c` L823-842／L844-870 実源照合済）。

| レジスタ | 16bit 経路 | **8bit 経路（現行）** | v1.6 での扱い |
| --- | --- | --- | --- |
| UART_STAT／RX／TX | ✅ | ✅ | 現状維持 |
| UART_BAUD（$FC86） | ✅ | ❌（**意図的に対象外**・**§4.4.5**／一次根拠 `ysd8001_uart_design_v1_2.docx` L166。★v1.8 是正・M-12★） | **意図的対象外を維持**（欠陥ではない）。ただし **`MMIO_MAPPED_UNSUPPORTED` として分類し `$00` を返す**（§2.3.4(7)・v1.8 新設）。`mem[]` へは落とさない |
| **YSD8002 全8本**（TCR／PERIOD_HI/LO／CYCLE_LO/HI／SW_RUNS／SCORE_LO/HI） | ✅ | **❌ 未処理** | **★対応する★** |
| YSD8003 SD_DATA（$FCAA） | ✅ | ✅ | 現状維持 |
| **YSD8003 の7本**（SD_CMD／SD_STAT／LBA_LO/HI／BUF_PTR／IRQ_CTRL／DISK_LO/HI） | ✅ | **❌ 未処理** | **★対応する★** |
| **YSD8004 の2本**（IRQ_STAT／IRQ_MASK） | ✅ | **❌ 未処理** | **★対応する★** |
| MMU レジスタ | ✅ | ✅ | 現状維持（ただし `--mmu` 依存を解消・§4.1 注記） |

**現状これが露見していないのは、全ドライバが 16bit アクセスを行っているためにすぎない。** 潜在的な欠陥として残置されている状態である。

### 4.4.2 対応方針（案b＝同時解消）

**デコード層で 8bit／16bit を統一的に扱い、被覆漏れごと解消する。**

デコード層を新設する以上、8bit と 16bit で別々の経路判定を残すのは新設層の意味を損なう。また、被覆漏れを残したままプルアップを適用すると、上表の ❌ 群への 8bit アクセスが `mem[]` フォールスルー経由で `$FF` 固定に変わるだけであり、**「デバイスに届かない」という誤りは是正されない**。

### 4.4.3 バイトアクセスの規定

16bit レジスタへの 8bit アクセスに対する規定を以下のとおり定める。

| 項目 | 規定 |
| --- | --- |
| アドレス対応 | **リトルエンディアン**に従う。偶数アドレス＝下位バイト、奇数アドレス＝上位バイト |
| 読出 | 対応する 16bit レジスタ値の該当バイトを返す |
| 書込 | 対応する 16bit レジスタの該当バイトのみを更新する |
| **副作用を伴うレジスタ（読出）** | **★要注意★ 該当レジスタの全数と規定は §4.4.3.2 に表として示す（v1.10 で表形式に整理）。**基本規定は「**副作用は下位バイト読出時に発動し、上位バイト読出では発動させない**」（16bit 読出時と副作用の発生回数を一致させるため） |
| **★副作用を伴うレジスタ（書込）★（v1.9 新設・レビュー F-4）** | **書込側の副作用も同様に「下位バイト書込時に発動」とし、上位バイト書込では発動させない。** 実装照合の結果、**書込副作用を駆動するビットはすべて下位バイトに存在する**ため、この規定で 16bit 書込と副作用回数が一致する（下表参照） |

#### ★4.4.3.1 書込副作用の一覧と規定（v1.9 新設・レビュー F-4）★

**v1.8 までの §4.4.3 は読出側の副作用のみを規定しており、書込側の規定が欠落していた。** BC-8WT／BC-8WP はこの規定なしには期待値を書けない。実源照合（`emu23_v111.c` の `wr16`）に基づき以下を規定する。

| レジスタ | 書込副作用 | 駆動ビットの所在 | **下位バイト書込** | **上位バイト書込** |
| --- | --- | --- | --- | --- |
| `TCR`（$FC90） | `SW_START`(bit2)／`SW_STOP`(bit3)／`IRQ_ACK`(bit5) の**自動クリア型トリガ** | **すべて下位バイト**（`tcr = v & 0x37`） | **発動する**（各トリガは 1 回のみ・自動クリア） | **発動しない**（有効ビットが存在しない） |
| `SD_CMD`（$FCA0） | `cmd_val == 2`（EXEC）で**コマンド起動**（`fread`/`fwrite` 即時実行・BUF_PTR リセット） | **下位バイト**（`cmd_val = v & 0xFF`） | **発動する** | **発動しない** |
| `SD_DATA`（$FCAA） | バッファ書込＋**BUF_PTR 自動インクリメント** | **下位バイト**（`sd_buf[...] = v & 0xFF`） | **発動する**（+1） | **発動しない**（§2.3.4(6) の `$FCAB`＝上位バイトと同じ扱い） |
| `IRQ_STAT`（$FCB2） | **Write-to-Clear**（`irq_stat &= ~v`） | 16bit 全体（bit0-2 使用） | **下位バイトに対応するビットのみクリア**（上位ビットは保持） | **上位バイトに対応するビットのみクリア** |
| `BUF_PTR`（$FCA8） | 値の更新のみ（副作用なし）。**ただし 9bit 値**（`v & 0x01FF`） | 16bit（bit0-8） | **下位 8bit のみ更新し、bit8 は保持する** | **bit8 のみ更新する** |

> **★実装上の注意★** `IRQ_STAT` と `BUF_PTR` は**上位バイトにも意味がある**ため、「上位バイト書込は無視」としてはならない。一方 `TCR`／`SD_CMD`／`SD_DATA` は**有効ビットが下位バイトに閉じている**ため、上位バイト書込は状態を変えない。**この非対称性が、書込側を一律規定にできない理由である。**

> **★KY★** 本規定を誤ると `SD_CMD` の EXEC が**バイト書込で意図せず 2 回起動**したり、`TCR` の `SW_START` が二重発火して Dhrystone の計測値が狂う。§11.3.1.1 の BC-8WT／BC-8WP で必ず検証すること。

#### ★4.4.3.2 読出副作用の全数一覧と規定（v1.10 新設）★

**v1.9 までの §4.4.3 は読出副作用として `CYCLE_LO`／`SCORE_LO`／`SD_DATA` の 3 件を本文中に列挙するのみで、全数であることが担保されていなかった。実際 `SD_STAT` が漏れていた**（B-C-1a-2 の実装準備で `rd16` を全数確認した際に発見）。§12.9 の原則候補 B（規則を作ったら全数に当てはめて検算する）を適用し、**実装から全数抽出して表とする**。

| レジスタ | 読出副作用 | 実装（`rd16` 内） | **下位バイト読出** | **上位バイト読出** |
| --- | --- | --- | --- | --- |
| `CYCLE_LO`（$FC96） | `cycle_hi_latch` に `cpu.cycle >> 16` をラッチ | `ysd8002.cycle_hi_latch = cpu.cycle >> 16;` | **発動する** | **発動しない** |
| `SCORE_LO`（$FC9C） | `score_hi_latch` に `score >> 16` をラッチ | `ysd8002.score_hi_latch = ysd8002.score >> 16;` | **発動する** | **発動しない** |
| `SD_DATA`（$FCAA） | `BUF_PTR` 自動インクリメント | `sd_buf_ptr = (sd_buf_ptr + 1) & 0x1FF;` | **発動する** | **発動しない**（§2.3.4(6)：上位バイトは `$00`） |
| **`SD_STAT`（$FCA2）** | **`sd_busy_latch` を 1 回目の読出でクリア**（BUSY ラッチ方式・§6） | `if (sd_busy_latch) { stat = 0x0001; sd_busy_latch = 0; }` | **発動する** | **発動しない** |

**上記 4 件が読出副作用の全数である**（`rd16` の実装を全数走査して確認・2026-08-11）。他のレジスタは純粋な値の読出であり、読出によって状態は変化しない。

> **★`SD_STAT` を漏らした場合の発現★** 上位バイト（`$FCA3`）読出で BUSY ラッチが消える。**BUSY 監視ループを 8bit アクセスで書いた場合、BUSY を取りこぼして完了前に次のコマンドを発行する**という形で現れる。現状は全ドライバが 16bit アクセスのため露見しないが、**8bit 経路を塞ぐのが B-C-1a-2 の目的である以上、塞いだ穴から新たな欠陥を入れることになる。**

> **★検証項目★** §11.3.1 の BC-8S に `SD_STAT` を追加すること（v1.10）。

> **★実装上の危険（KY）★** 副作用付きレジスタのバイトアクセス規定を誤ると、**ラッチ／自動インクリメントが 1 回のはずが 2 回発動する**（下位・上位の各バイト読出で発動してしまう）。これは Dhrystone のサイクル計測値（`CYCLE_LO`/`SCORE_LO` 経由）を直接狂わせる。**ただし Dhrystone は 16bit アクセスしか行わないため、8bit 経路の副作用二重発動は絶対ゲートでは検出できない**（v1.7 是正・レビュー M-9）。§11.3 BC-8S で個別に検証すること。

### 4.4.4 ★副作用付きレジスタのバイト読出順序（v1.7 新設・レビュー C-4 への回答）★

`CYCLE_LO`（`$FC96`）／`SCORE_LO`（`$FC9C`）は**下位バイト読出時に上位16bitをラッチする**。したがって**上位バイト（`$FC97`／`$FC9D`）を先に読むと、ラッチ前の値を読むことになり一貫性を失う**。

**規定：バイト単位で読む場合は必ず下位アドレスから読むこと（利用側規約）。**

| 選択肢 | 採否 | 理由 |
| --- | --- | --- |
| (a) 上位バイト読出でもラッチする | ❌ | ラッチが 2 回発動し、16bit 読出時と副作用回数が一致しなくなる |
| **(b) 利用側規約として「下位から読む」を明記する** | ✅ **採用** | 16bit 読出（`LDW`）と副作用回数が一致する。実際のドライバは全て `LDW` を使用しており、バイト読出は想定されない |

**本規約は「バイト読出を推奨する」ものではない。** 64bit カウンタのラッチ方式（§5.2）は 16bit アクセスを前提に設計されており、**バイト読出は非推奨**である。本節は「8bit 経路の被覆漏れを塞いだ結果、バイト読出が物理的に可能になった」ことに対する安全規定である。

### 4.4.5 ★UART_BAUD を 8bit 対象外とする規定（v1.7 新設・レビュー M-2 への対応）★

**`$FC86` UART_BAUD は 8bit 経路（`rd8`/`wr8`）の対象外とする。** これは被覆漏れではなく**意図的な仕様**である。

- 一次根拠：`ysd8001_uart_design_v1_2.docx` **L166「UART_BAUD: 16bit アクセスのみサポート」**（実源照合済・2026-08-11）
- 実装：`emu23_v111.c` L827 のコメントが同規定を参照している

**規定の所在が実装コメントのみという状態を避けるため、本設計書にも明記する。** §4.4 の被覆漏れ解消作業において、本レジスタを 8bit 経路に追加してはならない。

### **5.1.2 SW_BUSY状態遷移（v1.2更新）**

| **状態** | **SW_BUSY値** | **遷移条件** | **次状態** | **カウンタ動作** |
| --- | --- | --- | --- | --- |
| IDLE | 0 | SW_START書き込み | MEASURING | 計測カウンタをリセットして開始 |
| MEASURING | 1 | SW_STOP書き込み | IDLE | カウンタ停止・SCORE確定 |
| MEASURING | 1 | SW_START再書き込み | MEASURING | カウンタをリセットして再スタート（v1.2追加） |

**【重要】SW_START再発行（計測中にSW_STARTを書き込む）時は、カウンタをリセットして計測を再開始する。直前のSCOREは上書きされる。**

## **5.2 64bitカウンタのラッチ方式**

64bitカウンタを16bitレジスタで2回に分けて読み出す際の一貫性保証：CYCLE_LO読み出し時に上位16bitをラッチする。SCORE_LOも同様。

LDW  A, [$FC96]      ; CYCLE_LO読み出し → この瞬間CYCLE_HIもラッチ

LDW  B, [$FC98]      ; CYCLE_HI（ラッチ値）を読み出す

### **6.2.1 SD_CMDコマンド値**

| **値** | **名称** | **説明** |
| --- | --- | --- |
| 0 | READ_SETUP | 読み込み準備（LBA設定後に発行） |
| 1 | WRITE_SETUP | 書き込み準備（LBA設定後に発行） |
| 2 | EXEC | 転送実行。BUF_PTRリセット・BUSY=1セット後にfread()/fwrite()実行 |

### **6.2.2 SD_STATビット定義**

| **ビット** | **名称** | **説明** |
| --- | --- | --- |
| bit0 | BUSY | BUSY挙動はBUSYラッチ方式参照（v1.2） |
| bit1 | ERROR | 1=直前のコマンドがエラー |
| bit2 | READY | 1=デバイス準備完了（--diskでイメージが開けた） |
| bit3〜15 | （予約） | 常に0 |

### **6.2.3 BUSYラッチ方式（v1.2確定）**

emu23はシングルスレッドのためEXEC発行後即座にfread()/fwrite()が完了するが、実機との乖離を防ぐため以下のラッチ方式を採用する。

| **タイミング** | **BUSY値** | **sd_busy_latch** | **説明** |
| --- | --- | --- | --- |
| EXEC発行直後 | 1 | 1 | 転送処理完了後もBUSY=1を維持 |
| 1回目のSD_STAT読み出し | 1 | 0→クリア | BUSY=1を返しラッチをクリア |
| 2回目以降のSD_STAT読み出し | 0 | 0 | BUSY=0を返す（転送完了） |

これによりポーリングコードは最低2回SD_STATを読み出す動作となり、実機との挙動差異が最小化される。

*【注】これはemu23固有の擬似実装であり、FPGA実機では実際の転送時間に応じてBUSYが維持される。*

### **6.2.4 IRQ_CTRLビット定義**

| **ビット** | **名称** | **説明** |
| --- | --- | --- |
| bit0 | IRQ_EN | 1=転送完了時にYSD8004経由でIRQ1を発火 |
| bit1 | ERR_EN | 1=エラー時にYSD8004経由でIRQ1を発火 |
| bit2〜15 | （予約） | 常に0 |

### **6.2.5 BUF_PTRオーバーラン仕様**

| **条件** | **BUF_PTR動作** |
| --- | --- |
| BUF_PTR = 0〜510 のとき DATA 読み書き | BUF_PTR += 1 |
| BUF_PTR = 511 のとき DATA 読み書き | BUF_PTR → 0（ラップアラウンド・エラーなし） |
| EXEC発行 | BUF_PTR → 0（自動リセット） |
| BUF_PTRへの直接書き込み | 任意値（0〜511）に設定可能 |

*【注】将来的に16bit DATAレジスタへの拡張を考慮した設計とする。現バージョンは8bitCPU互換性のため8bit固定。*

## **6.3 転送シーケンス**

### **6.3.1 セクタREAD（LBA=5、読み込み先=$5000）**

; ① LBA設定

LDW  A, #0

STW  A, [$FCA6]          ; LBA_HI = 0

LDW  A, #5

STW  A, [$FCA4]          ; LBA_LO = 5

; ② READ_SETUP

LDW  A, #0

STW  A, [$FCA0]          ; SD_CMD = READ_SETUP

; ③ EXEC発行（BUF_PTR=0・BUSY=1・fread()実行・latch=1）

LDW  A, #2

STW  A, [$FCA0]          ; SD_CMD = EXEC

; ④ 完了待ち（1回目: BUSY=1返却・latchクリア / 2回目: BUSY=0）

_wait_read:

    LDW  A, [$FCA2]      ; SD_STAT読み出し

    ANDI A, #0x0001      ; BUSY bit

    BNE  _wait_read      ; BUSY=1なら再読み出し

; ⑤ PIOで512バイト読み出し

LDW  X, #$5000

LDW  B, #512

_pio_read:

    LDB  A, [$FCAA]      ; DATA読み出し（BUF_PTR自動インクリメント）

    STB  A, [X]

    ADDI X, #1

    SUBI B, #1

    BNE  _pio_read

### **6.3.2 セクタWRITE（LBA=5、書き込み元=$5000）**

; ① LBA設定・WRITE_SETUP

LDW  A, #0 / STW  A, [$FCA6]  ; LBA_HI = 0

LDW  A, #5 / STW  A, [$FCA4]  ; LBA_LO = 5

LDW  A, #1 / STW  A, [$FCA0]  ; SD_CMD = WRITE_SETUP

; ② BUF_PTRリセット＋PIOで512バイト書き込み

LDW  A, #0 / STW  A, [$FCA8]  ; BUF_PTR = 0

LDW  X, #$5000 / LDW  B, #512

_pio_write:

    LDB  A, [X] / STB  A, [$FCAA]  ; DATA書き込み

    ADDI X, #1 / SUBI B, #1 / BNE  _pio_write

; ③ EXEC発行（BUSY=1・fwrite()実行・latch=1）

LDW  A, #2 / STW  A, [$FCA0]  ; SD_CMD = EXEC

; ④ 完了待ち

_wait_write:

    LDW  A, [$FCA2] / ANDI A, #0x0001 / BNE  _wait_write

## **10.5 emu23 と RTL の等価性に関する注記**

案Q を採る間、**emu23 と RTL の間に「未接続 MMIO 応答値」の既知の乖離が残る**（emu23=`$FF` / RTL=`$00`）。Step 8-Sim で確立した等価性は、**未接続アクセスに関してのみ**成立しない状態となる。実コードが未接続領域にアクセスしないため既存の回帰テストでは差が出ないが、**潜在的乖離として本節に記録し、軸A での解消をもってクローズとする**。

# **12. ★レビュー指摘への回答（v1.7 新設）★**

`emu23_device_design_v1_6_review_v1_0.md`（2026-08-11・条件付き差戻し・M:9／C:7／N:7／E:5）に対する回答を以下に記す。

## **12.1 C-1：α（警告ログ）の有効化タイミング**

**回答：α は B-C-1b で有効化する。B-C-1a-1／1a-2／1a-3 では警告を出さない。**

理由は、**B-C-1a を「完全な非機能変更」に保つ**ためである。1a 段でデコード層は分類のみ行い、応答も出力も一切変えない。これにより 1a の回帰で差分が出た場合、それは**分類ロジックそのものの誤り**であると断定できる。警告出力を混ぜると `stderr` に差分が生じ、切り分けの純度が落ちる。

なお §11.1 のゲートは Dhrystone 3 値・md5・**stdout** の byte-exact であり、いずれも `stderr` の影響を受けない。したがって 1b 以降に警告が出ても**ゲート判定手順は変更不要**である（本回答を §11.1 の `-q` 行に注記済）。

## **12.2 C-6：オプションの状態遷移**

| --- | --- | --- |

**規定：サマリ出力は `atexit` に登録し、かつ `it_cleanup_on_exit` より後に実行されるようにする。** `atexit` ハンドラは**登録と逆順に実行される**ため、**`it_cleanup_on_exit` の登録より前にサマリ出力を登録する**こと（そうすれば復帰→サマリの順になる）。raw mode のまま `stderr` へ出力すると改行が `\r` を伴わず表示が乱れるため、この順序は必須である。

## **12.10 警告メッセージ書式（N-4／v1.8 で N-8・N-9 反映）**

`debug_style_guide.txt` に準拠し、**grep 可能な固定接頭辞**を持たせる。

```
[MMIO-UNMAPPED] rd8 addr=FCB8 pc=0A3C
[MMIO-UNMAPPED] wr16 addr=FF20 pc=0B14 val=1234
[MMIO-UNMAPPED] suppressed after 16 reports
[MMIO-UNSUP] rd8 addr=FC86 pc=0C20
[MMIO-SUMMARY] unmapped=0 unsup=0
```

- 固定接頭辞 **`[MMIO-UNMAPPED]` / `[MMIO-UNSUP]` / `[MMIO-SUMMARY]`** により `grep` 可能
- フィールド順：**種別 → アドレス → PC → （書込時のみ）値**
- **★v1.8 是正（N-8）★ フィールド区切りは半角スペース 1 個に固定する。** v1.7 の書式例は `[MMIO-SUMMARY]` の後を 2 スペースにしていたが、**区切りが不定だと `awk` 等での機械処理が崩れる**。桁揃えが必要な場合はフィールド内の固定幅で行う
- **★v1.8 追加（N-9）★ `[MMIO-UNSUP]`** は §2.3.4(7) の `MMIO_MAPPED_UNSUPPORTED` を報告する。抑制ルール（同一 PC 初回のみ・上限 16・サマリ計上）は `[MMIO-UNMAPPED]` と共用する
- **`[MMIO-SUMMARY]` は 0 件でも必ず出力する**（§4.3.3）。**未接続と幅未対応を別カウントで報告する**
