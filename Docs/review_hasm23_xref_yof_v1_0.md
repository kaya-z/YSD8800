## 2. 指摘事項

### M（必須修正）

#### M-1：D-2 対処を両経路（即値・分岐）に入れる旨を実装ステップに明記すること

UNDEF 化処理は即値経路（L1006-1035 系）と分岐経路（L1106-1135 系）に**別ルーチンとして二重に存在**する。設計書 3.3.2 は「参照箇所（即値側・分岐側の両方）」と正しく書いているが、§6 実装ステップでは「改修 (B) is_undef 複数参照対応」と一括りで、**両経路に同一改修を入れること／片方忘れを検証すること**が手順として明示されていない。

MC6809 系の手書きアセンブラに典型的な「即値と分岐で処理が分離した」構造そのままであり、片側だけ直す事故が起きやすい。§6 に「改修 (B) は即値経路・分岐経路の両方へ適用し、片側漏れがないことを T3/T4 で確認」と明記すること。

#### M-2：reloc 生成位置の集約を設計書 3.3.2 に明示すること（最重要・現バグの根）

設計書 3.3.2 は対処を「`find_sym` がヒットしても `is_undef` なら毎回 reloc 生成」と記述するが、**コード構造上どこへ reloc 生成を移すかを明示していない**。実ソースでは reloc 生成が即値 L1020-1027・分岐 L1123-1130 の通り **`if(!s)` ブロックの内側**に置かれている。

このため、設計書の対処を素直に「`else` 側へ分岐を足す」だけで実装すると、

- 2 個目の参照（`find_sym` ヒット）は `else` 経由となり、**`if(!s)` 内の既存 reloc 生成コードに到達しない**
- 結果として「`else` 側に reloc 生成を新規追加」と「`if(!s)` 内の旧 reloc 生成」が**二重定義**になるか、あるいは旧コードが死蔵される

という、kaizen「コンパイラ内部状態の変更箇所は一か所に集約」に反する実装になりかねない。

**要求**：3.3.2 に「reloc 生成を `if(!s)` ブロックから括り出し、`s==NULL || s->is_undef` を満たす共通後処理として **1 箇所に集約**する」旨を、改修後の制御構造（疑似コード）込みで明記すること。具体的には以下の 3 分岐に整理されることを示すこと。

- `s == NULL`：UNDEF 新規登録（`is_undef=1`）→ reloc 生成（集約点）
- `s != NULL && s->is_undef`：登録済みにつき再登録せず → reloc 生成（集約点・同一）
- `s != NULL && !s->is_undef`：`s->addr` を確定値として使用（reloc 不要）

これが本設計で唯一の「見えているバグの芽」であり、本文確定までは実装着手不可（原則43）。

### C（要確認・確定）

#### C-1：`is_undef` は内部表現のみで YOF オンディスク形式（36 バイト固定）不変、を明記

L440 `YOF_SYM_SZ 36` を確認。設計書 Q4 が言及する「過去のパディング齟齬（36/6 vs 38/8）」はこの固定長定数が効く論点。`symbol_t` への `is_undef` メンバ追加が**アセンブラ内部表現に閉じ、YOF 書き出し形式（36 バイト）には乗らない**ことを設計書本文（3.3.2 または 3.1）に明記すること。

もし `is_undef` を YOF レコードに載せる設計なら `YOF_SYM_SZ` 変更＝lnk23 の load 側整合が崩れ、「lnk23 無改修」という本設計の根幹前提が崩壊する。Q4 を「要確認」のまま残さず、「YOF 形式不変・lnk23 無改修を保証」と確定文言で閉じること。

#### C-2：`.global` の v1.03 における仕様を確定（Q2/T5 の表裏）

T5「`.global` 宣言したが当該ファイルで未定義のシンボル」の期待挙動が未確定のまま実装ステップに入っている。これは export（`.global` / XDEF 相当）と import（`.extern` / XREF 相当）の境界を決める本質的論点であり、未確定では T5 のテストコードが書けない。

**推奨方針**：v1.03 では `.global` を「**定義済みシンボルを GLOBAL へ格上げする export 専用**」とし、`.global` 宣言したシンボルが当該ファイル内で未定義ならエラーとする。import（`.extern`）は別バージョンへ分離（設計書 3.2.3 が示唆する `.global`/`.extern` 対称ペアの導入は v1.03 のスコープ外と明記）。これで仕様が閉じ、T5 が「未定義 → エラー」と一意に定まる。

別方針（GLOBAL-UNDEF として export 許容）を採る場合は、YOF 種別の組合せ（GLOBAL かつ addr 未確定）に対する lnk23 の挙動確認が新たに必要となり「lnk23 無改修」前提と衝突しうる。いずれにせよ本文で一意に確定すること。

### D（設計判断）

#### D-1：案 F2（後処理での `.global` 挿入）採用は妥当。ただし目的記述との整合を取る

§4.1 の案 F2（ビルドスクリプト後処理で `.global` 行を機械挿入）採用は、Force 本体改修（案 F1）の影響回避として妥当な判断。ただし本設計は新たに「`.global` 挿入の後処理」を増やすため、No.1（Force 混入行）sed の残置と合わせ、実像は「**sed は減るが後処理スクリプトは残る**」。

設計書 1.2 の「sed を全廃」的トーンと §4.1 の現実が読み手にズレて伝わる。1.2 を「**No.2/3/6 の sed を廃止（No.1 の Force 混入行 sed および `.global` 付与後処理は残置）**」と正確化すること。誇大表現を避け、後工程での期待値ズレを防ぐ。

### N（助言）

#### N-1：T4 に即値＋分岐混在の 3 参照ケースを加える

T4「3 参照以上」に、即値・分岐を混在させた 1 ケース（例：`LDW A,#$WORD_X` ／ `JSR WORD_X` ／ `BRA WORD_X` が同一 UNDEF を参照）を含めること。M-1（両経路適用）と M-2（reloc 集約）が一括で検証でき、片側漏れを一発で炙り出せる。

#### N-2：`.global` 前方参照のテストを 1 ケース

3.2.2 の PASS1 登録について、`.global` 宣言がラベル定義行より**前**に来ても拾えること（前方参照）をテストに 1 ケース追加。PASS1 全走査なら自然に満たすが、回帰の観点で明示テスト化を推奨。

---

### E（軽微）

#### E-1：影響表 emu23 のバージョン表記

§4 影響表で emu23「v1.06 維持」とあるが、現行確定版は **v1.05**（F-001 未修正）。emu23 v1.06 は F-001 修正後の予定版であり本設計の前提ではない。「v1.05（F-001 は別工程 Step 8-F-1）」へ修正し、版数の混同を避けること。
