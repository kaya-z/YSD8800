# 1. 目的とスコープ

本文書は、scc23 Cコンパイラ（Small-C移植ベース・YSD8800 ISA2.3対応）の v2.03 以降の改良工程を Phase 0〜6 として定義する工程表である。従来この6フェーズ構成は口頭合意のみで正式文書化されておらず、進捗と予定の確認(latest) 2026-07-04 ロードマップにて「次回scc23系チャットで文書化を推奨」と警告されていた懸案を解消するために起草する。

本文書は工程の粒度・依存関係・完了条件・本体改変の有無を定義することに限定し、各Phaseの詳細設計（IR拡張の具体仕様・命令生成の実装詳細等）には踏み込まない。詳細設計は各Phase着手時に行い、レビュー承認を経てから実装する（原則43）。

## 1.1 設計原則（本ロードマップ全体に適用）

- **汎用性原則**：scc23の拡張機能は「既存YUI OS（Forthカーネル＋Cユーザランド）でも、将来の置き換えC言語OSでも使える汎用機能」として設計する。特定OS専用の妥協はしない。両OSは非排他であり、いずれか一方向けに機能を歪めない。

- **unsigned実装方式の確定**：符号なし型は、OS拡張設計側の `is_unsigned` フラグ追加方式ではなく、v2.x側で既に予約済みの **`T_UINT`（IR層の型種別）方式** に統一する。IR層に型を持たせる方式のほうが符号なし専用命令（`SIR_CMP_LT_U` 等）を活かした最適化がしやすく、どちらのOSでも恩恵を受けられるため。

- **ISA厳守**：ISA2.3（ISA2_3_v231.docx）に存在しない命令を生成コードに混入させない。

- **回帰ゲート厳守**：コンパイラ本体を改修する各Phaseの完了条件に、Dhrystone絶対ゲート（-O0-strict：826/48405/P:20/21846B）の維持を必須で含める。

# 2. 現在地（2026-07-05時点）

| 系列 | 状態 |
| --- | --- |
| scc23 並行系列 | **v2.03**（Phase 0＝P1 peephole 完了・確定） |
| 絶対ゲート | -O0-strict：826/48405/P:20/21846B（v2.03で維持確認済） |
| 完了済最適化 | peephole P2a/P2b（デッドストア除去）→P3（ADD統合）→P1（スタックラウンドトリップ除去）|
| P1効果 | -O1で cycles 47885→47795（−90）・P:20不変・836 DPS |

**【N-2 脚注・トラック区別】** 絶対ゲート 48405 は **-O0-strict トラック**（peephole 非作動・byte-exact 維持）の値。cycles 47885→47795 は **-O1 トラック**（peephole 作動）の値であり、両者は**別トラックで別基準管理**される（P3レビュー時に確定した新旧トラック分離）。「ゲートは48405なのに Phase 0 で47795」と混同しないこと。-O0-strict は byte-exact 回帰基準、-O1 は最適化効果測定トラックである。

## Phase 1：検証負債対応（C-1／C-2／C-3）

v2.00 Step10のバグ修正（call型伝播）で露呈した検証負債（scc23_v2_00_design_v2_10.docx §9）に対応する。Phase 2で型システムに手を入れる前に片付けておくことで、型変更時の回帰検出網を先に整備する狙い。

| 項目 | 根拠（設計書§9） | 完了条件 | 本体改変 |
| --- | --- | --- | --- |
| **C-3**：float関数の前方宣言なし呼び出し（潜在バグ） | 未定義関数callはT_INTフォールバック。前方未定義のfloat返し関数を先に呼ぶと誤昇格が再発しうる。「実害が出る前に対処すべき既知の制約」 | プロトタイプ宣言の型記録 or 2パス化により、前方未定義float関数呼び出しで正しい戻り値型が伝播すること。回帰テスト追加 | あり（前方宣言の型記録機構） |
| **C-1**：call戻り値型の網羅テスト不足 | float関数()+定数バグがStep1〜9をすり抜けた。戻り値型(float/int)×演算(+/-/*/÷)×右辺種別(定数/変数/call)のマトリクステストを回帰スイートに追加すべき | 上記マトリクステストを回帰スイートに追加し全PASS | なし（テスト整備のみ） |
| **C-2**：Q8.8期待値の手計算ミス防止 | 期待値手計算で誤記が発生（8.5を0x0850と誤記、正0x0880）。C式→Q8.8 hex変換ヘルパスクリプトを用意し手計算を排除すべき | C式→Q8.8 hex変換ヘルパスクリプトを整備し、期待値生成を自動化 | なし（補助スクリプトのみ） |

**着手順**：C-3（本体改変を伴い、かつ実害リスクありのため最優先）→ C-1（マトリクステスト整備）→ C-2（ヘルパスクリプト）。C-1/C-2は本体非改変のため、C-3の検証にも活用できる。

**注意**：C-3は本体改変を伴うため、着手時は `_poc` 生成（本番非改変・KY38）とし、Dhrystone絶対ゲート維持を完了条件に含める。C-1/C-2はテスト・スクリプト整備のみで本体を触らない。

## Phase 2：型システム統合（T_BOOL＋T_UINT＋比較命令リネーム）

v2.00で型enumに予約のみ確保した T_BOOL／T_UINT を実装に格上げする。

| 項目 | 根拠 | 内容 |
| --- | --- | --- |
| T_UINT実装 | 設計書§型システム表「uint：T_UINT・予約のみ・今回未実装」 | 符号なし型を実装。符号拡張ロジック（LDB等）を追加。unsignedは前述の通りT_UINT方式で統一 |
| T_BOOL実装 | 設計書§型システム表「bool：T_BOOL・予約のみ・今回未実装」 | bool型を実装に格上げ |
| 比較命令リネーム **(条件付き・必須でない)** | 設計書§9.1「見送り（動作実装済・名称のみ）」／§2.5.4「リネームは見送り（実体はA=0/1返し済・退行リスク）」／実ソース scc23_v2_03.c 照合 | **機能は v2.03 で実装済**（比較emitは `Ltrue: LDW A,#1` / `LDW A,#0` でC規格どおり0/1をAへ返す）。`scc23_v2_03.c` の enum は **旧名 SIR_LT/SIR_LE/SIR_GT/SIR_GE のまま**（`SIR_CMP_*_S` リネーム未実施）。リネームは名称整理にすぎず、しかも**退行リスクがあり必須ではない**。T_BOOL/T_UINT 実装で符号付き/符号なしの命名区別が実益を持つ場合に**限って**実施する条件付きタスクとする |
| 回帰確認 | 回帰ゲート厳守原則 | Dhrystone絶対ゲート（826/48405/P:20/21846B・-O0-strict）不変確認 |

**本体改変**：あり（T_BOOL/T_UINT の IR型種別実装化・符号拡張ロジック追加）。`_poc` 生成必須。

**完了条件（M-2反映）**：T_BOOL/T_UINT の実装完了＋絶対ゲート維持をもって Phase 2 完了とする。**比較命令リネームは実施してもしなくてもよく、実施しない場合はその判断（退行リスク回避のため見送り 等）を記録すれば Phase 2 完了と扱える**。設計書§4.1/§4.2 の `SIR_CMP_*_S/_U` 拡張オペコード表は"予約"であり実装ではない点に注意（一次情報は実ソース `scc23_v2_03.c` の旧名enum・KY34）。

## Phase 3：OS拡張・独立機能（直列既定・並行は明示オプション）

型システムと無関係な独立機能。低リスク。将来の独立C言語OS向けだが、現YUI OSとも非排他。

| 項目 | 内容 |
| --- | --- |
| プリプロセッサ移植 | **移植元 = `scc22_v3_03.c`（ISA2.2）**。`handle_define` 等を移植し、移植時に **ISA2.3 差分を吸収**（プロジェクト規約「ツール新規開発／更新時は最新版ソースおよびISA仕様に対応」に沿う・N-1）。型システムと無関係で低リスク |
| static変数（sclass拡張） | `SC_STATIC_GLOBAL`／`SC_STATIC_LOCAL` 追加。型システムと無関係 |

**本体改変**：あり。**着手順は直列（Phase 1→2→3）を既定**とする（論点1）。Phase 3 は型システムと独立のため技術的には Phase 2 と並行可能だが、Phase 2 が本体広範を触りマージが複雑化しリスク増となるため、**並行はリソースに余裕がある場合の明示的オプション**と位置づける。

# 5. 依存関係と着手順の要約

- Phase 0（完了）→ Phase 1 を次に着手する。
- Phase 1 のうち C-1/C-2 は本体非改変のため先行整備可。C-3 は本体改変あり。着手順は C-3→C-1→C-2。
- **着手順は直列（Phase 1→2→3）を既定**とする（論点1）。Phase 2（型システム）は Phase 1 完了後に着手。Phase 3 は技術的には Phase 2 と並行可能だが、**並行はリソースに余裕がある場合の明示的オプション**（Phase 2は本体広範を触りマージ複雑化のリスク増のため）。
- Phase 4（関数ポインタ）は Phase 2 完了（型システム・特にT_PTR属性 安定）が着手条件（論点2・妥当と確認）。
- Phase 5 は最適化枠（O2フェーズ）。
- Phase 6 は memmap拡張＋ABI仕様書改版（N-3）が前提のため最後。**Phase 5/6は優先度が低く、着手是非は都度判断・将来の優先度見直し余地あり**（論点4）。

# 6. レビュー論点と確定事項（v1.0で回答済）

v0.1 で提示した論点1〜4は、レビュー指摘書 v1.0 の回答をもって以下に確定した（前版の論点文は保持）。

- **論点1**（v0.1）：Phase 3 の Phase 1/2 との並行可否。
  → **確定**：直列（Phase 1→2→3）を既定とし、並行はリソースに余裕がある場合の明示的オプション。Phase 2 が本体広範を触りマージ複雑化のリスク増のため。
- **論点2**（v0.1）：Phase 4 の着手条件を「Phase 2完了後」としてよいか。
  → **確定**：妥当。関数ポインタは型システム（特に T_PTR 属性）安定後が安全。ISA2.3 に間接JSRが無い制約への「ディスパッチスタブ方式」（既存 `_syscall_disp_ptr` 流用）も現実的。
- **論点3**（v0.1）：本ロードマップは工程表に限定し詳細設計は着手時に別途（原則43）でよいか。
  → **確定**：妥当。原則43に沿う。FPGAロードマップ文書（§1）と同方針。
- **論点4**（v0.1）：Phase 5/6 の末尾配置と将来の優先度見直し余地。
  → **確定**：末尾配置は妥当。**将来の優先度見直し余地を明記**。特に Phase 6 は ABI大工事のため、着手是非を都度判断する旨を Phase 6 定義に記載済。
