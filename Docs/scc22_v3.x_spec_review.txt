① rvalueセマンティクス（D1〜D5）

ここは今回の設計で一番価値がある部分。

should_load()の導入は正解で、特に

配列
struct/union
struct member chain途中

を一括で「アドレス扱い」にしたのは、Cの“配列は常にポインタに崩れる”モデルと整合している。
このレベルで統一してるなら、局所的なif地獄はほぼ消える。

ただし一点、致命傷になり得る抜けがある。

❗ ポインタ型が抜けている

今の条件：

if (n->is_array) return 0;
if (n->type==T_STRUCT||T_UNION) return 0;
if (n->struct_idx >= 0) return 0;

ここに

if (n->type == T_POINTER)

が無い。

何が起きるか
int *p;
*p

のとき：

p は「値としてのアドレス」→ load必要
*p は「メモリ参照」→ load必要

でも

p + 1

は「アドレス計算」なので load必要

つまり

👉 ポインタは “常にロード対象” だが、その後の使われ方で意味が変わる

今の設計だと

「配列＝非ロード」
「ポインタ＝ロード」

の区別はOKだが、

👉 emit_lval(SIR_DEREF)との整合が壊れる可能性がある

改善提案

should_loadではなく “value category”を明示する方が安全

enum value_kind {
    VK_RVALUE,   // 値
    VK_LVALUE,   // アドレス
};

should_loadはその派生にする：

return (kind == VK_RVALUE);

👉 これで「配列・struct・ポインタ・deref」の扱いが破綻しない

② SIR_CALL引数評価（D2）

これは非常に良い。実務的にも正しい。

if (should_load(arg)) emit_expr
else                  emit_lval

この設計は

配列 → decayしてポインタ
struct → アドレス渡し

というC ABIの簡略版として成立してる。

ただし問題が1つ。

❗ ABI未定義問題

現状：

emit_push_a();

だけだが、

サイズが2byte固定前提
structをどう渡すか未定義
問題

将来こうなる：

struct S { int a; int b; };
foo(s);

今の仕様だと

👉 アドレス渡し固定

になるが、

C的には

小さいstruct → レジスタ or スタック展開
大きいstruct → アドレス渡し

の2系統

改善提案（今やるべき）

仕様に明記すべき：

👉 「structは常にポインタ渡し（by reference）」

これを書かないと将来ABI地獄になる

③ メモリ配置（D6・D7）

これは非常に良い判断。

全変数DW単位

これは

ISAが16bit
アラインメント例外あり

なので合理的。

👍 良い点
data_offsetと実体が一致
LDB/STBだけ特別扱いすればいい
FPGA実装も単純
❗ ただし1点だけ危険
char配列 → DW ceil(N/2)

ここで

👉 C的なサイズと乖離する

例
char a[3];
sizeof(a) == 3   ← C的期待
実配置 = 4byte
影響
sizeof
memcpy
pointer演算

全部ズレる

改善案（2択）
A. 現状維持（推奨）

👉 「メモリ上はパディングあり」を仕様化

sizeofは論理サイズ（3）
実配置は4byte

その代わり

👉 sizeofはIR段階で確定値を持つ

B. 完全一致（非推奨）

byte単位管理に戻る → 地獄再発

④ フレーム設計（D8）

「宣言時SUBI SP」はかなり攻めてるが、筋は通ってる。

👍 良い点
実装が簡単
IRとの対応が直感的
❗ 最大の問題

👉 スコープをまたぐと崩壊する

{
  int a;
}
{
  int b;
}

現状：

aでSUBI
bでさらにSUBI

👉 解放されない

改善案（必須）

ブロックスコープ単位でSP巻き戻し

enter_block:
    save SP (or offset)

leave_block:
    restore SP

もしくは

👉 IRで「ブロックサイズ」を持つ

⑤ メモリマップ（D9・D10）

これは完璧。

特に

$FBD0移動
ROM/RAM明確化

はツールチェーン成立の前提条件なので、ここをFixしたのは非常に大きい。

⑥ ISAとの整合性

ISA2.2の特性との一致も確認。

👍 良い一致点
X固定フレームポインタ → [X+imm]活用
PUSH/POPが2byte単位 → DW設計と一致
アラインメント例外あり → 偶数配置必須

👉 コンパイラ設計がISAにきれいにフィットしてる
