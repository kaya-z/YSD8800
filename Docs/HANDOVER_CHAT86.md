## 2. ★最重要成果: S5(c)-ISSUE-1 — IE非依存ラッチとハンドラ冪等性要件★

### 2.1 事実（実照合済み・kaizen 原則69）

**`irq_pending` の「ラッチ」は IE を見ない。「受理」だけが IE を見る。**

| 段階 | emu23 実源 | FPGA RTL 実源 | IE参照 |
| --- | --- | --- | --- |
| **ラッチ** | `ysd8004_raise()` L314-329<br>`IRQ_STAT`再評価 L1576-1578 | L1223-1225<br>`if (state == S_IRQCHK && irq_in != 3'd0)`<br>`    irq_pending <= irq_in;` | ★**しない**★ |
| **受理** | L1176<br>`if (cpu.irq_pending >= 0 && (cpu.flags & FL_IE))` | L590<br>`if (irq_pending != 3'd0 && flags_ie)` | する |

### 2.2 帰結

「ネスト禁止（受理時 IE=0）」は**受理の抑止**であって**ラッチの抑止ではない**。

> **ハンドラが割込源を沈黙させても、沈黙させる「前」にラッチ済みの `irq_pending` は消えない。**
> **`IRET` で `IE=1` に戻った瞬間、その pending が受理され、ハンドラが「もう1回だけ」起動する。**

**これはバグではない。emu23 と FPGA RTL が一致した正しい挙動である。**

### 2.3 MC6809 / OS-9 との対応

MC6809 の IRQ でも同じことが起きる。`CC` の `I` ビットを立てても、既にラッチされた要求は `RTI` 後に処理される。

**OS-9 の IRQ ポーリングルーチンが「デバイス STAT を読み、自分の仕事が無ければ何もせず即 RTI」という構造になっているのは、まさにこの「余分な1発」を吸収するためである。**

### 2.4 ★OS設計上の必須要件★

**YSD8800 上のすべての割込ハンドラは冪等（idempotent）に書かねばならない:**

1. 冒頭でデバイス STAT を読み、自分に処理すべき仕事があるか判定する
2. 仕事が無ければ、何もせず直ちに `IRET` する（空振り起動を許容）
3. 2回以上起動しても状態が壊れないこと（カウンタ二重加算・バッファ二重取り出しを起こさない）

> ★**「ハンドラが必ず1回だけ呼ばれる」前提のコードを書いてはならない。**★

**→ YUI OS Ph.8（MMU連携・Level 2）のカーネル割込処理設計に直結する制約。**
守らないと「タイマー割込が二重カウント」「UARTバッファから二重取り出し」といった**再現性の低い厄介なバグ**を踏む。

**文書化先**: `emu23_device_design_v1_5.docx` §3.2.2

## 4. ★次工程: V5（タイマー YSD8002）への申し送り★

### 4.1 V5 は原則69 が直撃する工程である

V4 で TX(TDRE) について解決した論点が、**そのままの形で再来する**:

| 論点 | V4（UART）での結論 | V5（Timer）での課題 |
| --- | --- | --- |
| 割込信号は**レベルかパルスか** | TX=**レベル** / RX=パルス | **タイマー割込をどちらにするか要決定** |
| ハンドラ再入 | レベルゆえ「余分1発」が入る → **冪等ハンドラで吸収** | 同じ問題が起きる。設計時に織り込むこと |

### 4.2 pending 保護（第1段）の実装

`v3_7_design_memo_v0_3.md` §4.4b に申し送られている**「第1段: timer/align > IRQ1 の pending 保護」**を FPGA RTL に実装する必要がある。

- **第2段（IRQ_STAT 再評価）は YSD8004 の `irq1_o` がレベル出力であるため自動充足済み**（V3.7 で実証）
- **第1段は未実装。V5 の主要設計論点。**

**設計選択肢:**

| 案 | 内容 |
| --- | --- |
| **Case A** | CPU の `irq_pending` 更新ロジックに優先度比較を追加（RTL L1223-1225 を改修） |
| **Case B** | timer 側をレベルホールドにする |

> ★**Case B（level-hold）が有力に見える。** V4 で TX をレベルにした設計判断が正しかったことが c6 で実証されたため。
> ただし**レベルにすると原則69 の「余分1発」が発生する**ので、タイマーハンドラを冪等に書くことが前提になる。★

### 4.3 ★V5 実装時の必須制約★

> **第1段の保護ロジックを `flags_ie` で条件付けてはならない。**
> emu23 の `ysd8004_raise()` は `FL_IE` を見ないため、`flags_ie` で条件付けると **emu23 と乖離する**（＝協調等価が取れなくなる）。

### 4.4 V5 で CPU コアを改修する場合の注意

Case A を選ぶと **CPU コアが3フェーズぶりに改修対象**になる（v0.5.7 → v0.5.8）。
その場合、**V1/V2 の全 TB（82ベクタ）を再走させてデグレを確認すること**（KY: CPUコア改修は影響範囲が全域）。

### ★CHAT85 で実際に踏んだ落とし穴（再発防止）★

1. **`tb_cpu_v4uart_v0_1.sv` で `irq_in` が `irq1_o` から未結線だった。**
   S5(b) の「RX後に `irq1_o`=1」は割込コントローラ出力を覗いただけで、**CPU は割込を一切受けていなかった**。
   → v0.2 で `irq_en` ゲート付きで結線。`irq_en=0` により (a)(b) の検証条件が**構造的に**従来と同一であることを保証した（(a) 7/7 再現で実証）。

2. **`LDW`/`STW` abs のレジスタ nibble が非対称。**（KY34 実照合の成果）
   ```
   LDW rD,[imm16] = 0x22, レジスタ = rb >> 4    (上位nibble)
   STW rS,[imm16] = 0x23, レジスタ = rb & 0x0F  (下位nibble)  ← ★非対称★
   ```
   EXT(`0x1F`) のサブオペではなく**独立オペコード**である。推測で書くと必ず間違える。

3. **IRQ1 の `irq_in` 番号は `2`（`1` ではない）。** `1` はタイマー。
   ベクタ = `irq*2` = **`$0004`**（emu23 L310 / L1183 実照合）。
