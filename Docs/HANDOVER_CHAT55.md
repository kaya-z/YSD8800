### (A) memmap v2.3 ドラフト作成 → レビュー → v2.4 承認（案D-ε）

**経緯：** 方向D を「高位領域($DC00-$EFFF)の精査・縮小再配置」として着手 → PAGE-POOL 縮小案(D-α)を検討 → かやぬま指示「PAGE-POOL は MMU 見越しで温存」→ Shell が C 実装（v2.6 §9.1）である事実から「Shell を辞書外へ追い出せば辞書天井を下げられる」案D-ε に到達 → さらに「単一ロード領域では run 不成立」の構造制約を発見 → Level 区分で決着。

**案D-ε 確定配置（v2.4・承認済）：**
```
$5100-$D3FF  Forth 辞書（天井 $DBFF→$D3FF へ引下げ）実終端 $C15F・余裕 4768B
$D400-$DBFF  C プロセス領域 2KB ★$C000 から辞書外へ移設（子プロセス専用1スロット）
$DC00-$DCFF  DATA(VARIABLE) 256B          【v2.2 不変】
$DD00-$ECFF  PAGE-POOL 16pg/4KB            【v2.2 不変・MMU 見越し温存】
$ED00-$EFFF  テストバッファ 768B           【v2.2 不変】
$F000-$FFFF  スタック/guard/OS共有/MMIO    【不変】
```

**C プロセス区画 $D400 ベース再計算（v2.4 確定）：**

|---|---|---|

### (B) Level 1/Level 2 区分の正式導入（OS-9 Level I/II リスペクト・かやぬま決定）

| 項目 | **Level 1**（現状・MMU なし） | **Level 2**（Ph.8 MMU 後・将来） |
|---|---|---|
| 動的 C プロセス(`run`起動) | **同時 1 個** | **複数同時実行** |
| システムサービス | 複数並行常駐（マイクロカーネル） | 同左 |
| Shell 実装 | **Forth 常駐**（辞書） | **C 実装**（ユーザランド・v2.6 §9.1 到達目標） |
| C プロセス領域 | 1 スロット（$D400-$DBFF・子専用） | MMU バンクで複数 |
| PAGE-POOL | $DD00-$ECFF/16pg 温存 | 論理ページプール昇格 |
| IPC IF | FILE_*/PROC_*/MEM_* | **Level 1 から不変**（サービス層無改造で移行） |

**Level 1 "1 プロセス" の定義：** `run` で起動する動的 C プロセスが同時 1 個。Forth 常駐 Shell・各サービスタスク（FileMgr/MemMgr/UART/ProcMgr）はカーネル側常駐でカウント外。

**構造制約（なぜ Level 1 は 1 プロセスか）：** ProcMgr は C バイナリを固定アドレス（PROC-LOAD-ADDR）へ FILE-READ → TASK-CREATE する単一ロード領域モデル。Shell が `run fib` すると fib が同じアドレスへロードされ実行中の Shell 自身を上書き破壊する。MMU なし（単一物理空間）＋crt0 固定エントリ（非PIC）の 2 制約による。OS-9 Level I が MMU なしで複数プロセスを動かせたのは PIC 徹底のため（scc23 非PIC 出力ではそのまま不可）。Level 1 では Shell を Forth 常駐とし C プロセス領域を子プロセス専用 1 スロットにすることで `run` を成立させる。
